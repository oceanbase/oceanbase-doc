# Create a table-level hot cache policy

This topic describes how to create a table-level hot cache policy (`STORAGE_CACHE_POLICY`) by using SQL statements: 

* Create a hot cache policy for a regular table.
* Create a hot cache policy for an index table.

## Considerations

You can specify the hot cache strategy when you create a table or index in shared storage mode.

## Create a hot cache strategy for a regular table

To specify a table-level hot cache strategy when you create a table, add the `STORAGE_CACHE_POLICY` option to the `CREATE TABLE` statement. The syntax is as follows:

```sql
CREATE TABLE table_name (table_definition_list)
    STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Parameters

`STORAGE_CACHE_POLICY` is an optional parameter. If you do not specify the `STORAGE_CACHE_POLICY` option, the default value of the tenant-level parameter [default_storage_cache_policy](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2120.default_storage_cache_policy.md) is used. The `storage_cache_policy_option` parameter defines different attributes in the Key-Value format. The semantics of each attribute are as follows:

* `GLOBAL = {"hot" | "auto"}`: specifies the hot cache strategy for the entire table. Valid values: 

  * `hot`: specifies that all data in the table is hot data. If the cache disk space is sufficient, all data in the table will be cached to the local cache disk.
  * `auto`: specifies that the hot data in the table is automatically identified by the system.

* `timeline_strategy_list`: specifies the list of time-axis strategy parameters. Parameters are separated by commas. The hot cache time-axis strategy supports a mechanism to determine whether partition data is hot data based on time. The system automatically adjusts the partition data on the local cache disk based on the configured strategy.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>When using the time-axis strategy, note the following: <ul><li>Only Range-partitioned tables (either primary or secondary) are supported. This is because time is used to determine whether data has expired, but double Range partitioning is not supported because it is unclear which Range partition's time to use. </li><li>When using the time-axis strategy, the partition expression can only contain column names and does not support expression conversion. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code> is not supported. </li><li><code>BOUNDARY_COLUMN</code> must be a partition key. If the partition key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column to determine whether the partition has expired. </li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: specifies the column used to determine hot data. Supported data types are integers (`BIGINT` or `INT`, in the Unix timestamp format) and time types (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If `BOUNDARY_COLUMN` is an integer, the table supports Range or Range Columns partitioning.
    * If `BOUNDARY_COLUMN` is a time type, the table must use Range Columns partitioning.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter can only be set when `BOUNDARY_COLUMN` is an integer. If the integer value is used as a timestamp, you must specify the timestamp unit to avoid incorrect parsing of the time. Valid values:

    * If the partition column is of the `INT` type, `BOUNDARY_COLUMN_UNIT` must be `s`.
    * If the partition column is of the `BIGINT` type, `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

      <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>If the format is not a Unix timestamp, the system cannot correctly identify the time represented by the <code>INT</code> type. </p>
      </main>

  * `HOT_RETENTION = intnum retention_time_unit`: specifies the time range for hot data.

    * `intnum`: specifies an integer.
    * `retention_time_unit`: specifies the time unit. Valid values:

      * `YEAR`: specifies years.
      * `MONTH`: specifies months.
      * `WEEK`: specifies weeks.
      * `DAY`: specifies days.
      * `HOUR`: specifies hours.
      * `MINUTE`: specifies minutes.

### Examples

* Specify hot data manually. 

    ```sql
    CREATE TABLE tbl1 (
        col1 INT, 
        col2 INT)
        STORAGE_CACHE_POLICY (GLOBAL = "hot");
    ```

* Specify hot data based on the time-axis strategy. 

    ```sql
    CREATE TABLE tbl2 (
        col1 BIGINT NOT NULL,
        col2 VARCHAR(50),
        col3  DATE NOT NULL)
        STORAGE_CACHE_POLICY (
            BOUNDARY_COLUMN = col3,
            HOT_RETENTION = 1 MONTH)
        PARTITION BY RANGE COLUMNS(col3) (
            PARTITION M202001 VALUES LESS THAN('2020/02/01'),
            PARTITION M202002 VALUES LESS THAN('2020/03/01'),
            PARTITION M202003 VALUES LESS THAN('2020/04/01'),
            PARTITION MMAX VALUES LESS THAN MAXVALUE);
    ```

## Configure the hot cache strategy for an index table

You can configure the hot cache strategy for an index table in the following ways: 

* When you create an index, you can configure the hot cache strategy for the index table.
* When you create a table, you can create an index and configure the hot cache strategy for the index table.
* When you add an index to an existing table, you can configure the hot cache strategy for the index table.

For more information about how to create an index, see [Create an index](../500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).

### Configure the hot cache strategy for an index table when you create an index

The syntax is as follows: 

```sql
CREATE INDEX index_name ON table_name (column_name)
    STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Configure the hot cache strategy for an index table when you create a table

The syntax is as follows: 

```sql
CREATE TABLE table_name (
    column_name column_definition,
    [column_name column_definition,...],
    INDEX index_name(column_name) STORAGE_CACHE_POLICY (storage_cache_policy_option)
    );

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Configure the hot cache strategy for an index table when you add an index to an existing table

The syntax is as follows: 

```sql
ALTER TABLE table_name ADD INDEX index_name(column_name)
    STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Parameters

You can configure the hot cache strategy for an index table. 

* For a local index, you can configure the table-level `STORAGE_CACHE_POLICY`. If you do not configure the table-level `STORAGE_CACHE_POLICY`, the default value is `none`, which indicates that the hot cache strategy for the index partitions follows that for the data table partitions.

* For a global index, you can configure the table-level `STORAGE_CACHE_POLICY`. If the index table is partitioned, you can also configure the partition-level `STORAGE_CACHE_POLICY`. If you do not configure the table-level `STORAGE_CACHE_POLICY`, the default value is `none`.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Starting from V4.4.1, if you do not configure the table-level <code>STORAGE_CACHE_POLICY</code> for a global index, the hot cache strategy for the index follows that for the primary table if the primary table uses the Global strategy. If the primary table uses the time-axis strategy, the hot cache strategy for the index is <code>hot</code> by default.</p>
  </main>

When you configure the table-level `STORAGE_CACHE_POLICY`, you can define different attributes in the `storage_cache_policy_option` parameter in the key-value format. The attributes are described as follows:

* `GLOBAL = {"hot" | "auto" | "none"}`: specifies whether the data of the index is hot data. Valid values: 

  * `hot`: specifies that the index is hot-stored. If the cache disk space is sufficient, all data in the index table is cached to the local cache disk.
  * `auto`: specifies that the system automatically identifies hot data in the index table.
  * `none`: the default value. This indicates that the hot cache strategy for the index follows that for the primary table `STORAGE_CACHE_POLICY`.

* `timeline_strategy_list`: specifies the time-axis strategy parameters. The parameters are separated by commas. The hot cache time-axis strategy supports a mechanism that determines whether partition data is hot data based on time. The system automatically adjusts the partition data on the local cache disk based on the configured strategy. We recommend that you do not use this parameter for a local index.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>A time-axis strategy is supported only for a RANGE partitioned table. This is because the time-axis strategy requires time to determine whether data is expired. However, a double RANGE partitioned table is not supported. This is because it is impossible to determine which RANGE partition to use for the time-axis strategy. <ul><li>When you use the time-axis strategy, the partition expression can contain only column names. Expressions are not supported. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code> is not supported. </li><li><code>BOUNDARY_COLUMN</code> must be a partitioning key. If the partitioning key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column to determine whether the partition is expired. </li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: specifies the column that determines hot data. The column can be of the integer type (`BIGINT` or `INT`) in the Unix timestamp format or the time type (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If the `BOUNDARY_COLUMN` is of the integer type, the table can be RANGE or RANGE COLUMNS partitioned.
    * If the `BOUNDARY_COLUMN` is of the time type, the table can be RANGE COLUMNS partitioned only.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: specifies the time unit of the `BOUNDARY_COLUMN`. This parameter is supported only when the `BOUNDARY_COLUMN` is of the integer type. If the integer value is used as a timestamp, you must specify the timestamp unit. Otherwise, the system may incorrectly parse the timestamp. Valid values: 

    * If the partitioning column is of the `INT` type, the value of `BOUNDARY_COLUMN_UNIT` can be `s` only.
    * If the partitioning column is of the `BIGINT` type, the value of `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

  * `HOT_RETENTION = intnum retention_time_unit`: specifies the time range of hot data.

    * `intnum`: specifies an integer.
    * `retention_time_unit`: specifies the time unit. Valid values: 

      * `YEAR`: year.
      * `MONTH`: month.
      * `WEEK`: week.
      * `DAY`: day.
      * `HOUR`: hour.
      * `MINUTE`: minute.

### Examples

* Configure the table-level `STORAGE_CACHE_POLICY` for an index when you create an index:

  1. Create a table named `tbl3`. 

      ```sql
      CREATE TABLE tbl3 (col1 INT, col2 INT, col3 INT);
      ```

  2. Create an index named `idx1_tbl3` and configure the data of the index as hot data. 

      ```sql
      CREATE INDEX idx1_tbl3 ON tbl3 (col1) LOCAL 
          STORAGE_CACHE_POLICY (GLOBAL = "hot");
      ```

* Configure the data of an index as hot data when you create a table and create an index.

    ```sql
    CREATE TABLE tbl4 (col1 INT, col2 INT,
        INDEX idx2 ((col1 + 1)) STORAGE_CACHE_POLICY (GLOBAL = "hot"), UNIQUE KEY ((col1 + col2)));
    ```

* Configure the data of an index as hot data when you add an index to an existing table.

    ```sql
    ALTER TABLE tbl4 ADD INDEX idx3(col1, col2) GLOBAL 
        STORAGE_CACHE_POLICY (GLOBAL = "hot");
    ```
