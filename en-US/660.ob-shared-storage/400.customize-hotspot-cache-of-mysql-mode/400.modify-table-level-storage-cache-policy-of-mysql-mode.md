# Modify the table-level hot cache policy

This topic describes how to modify the table-level hot cache policy (`STORAGE_CACHE_POLICY`) by using SQL statements: 

* Modify the hot cache policy of a regular table.
* Modify the hot cache policy of an index table.

## Considerations

You can modify the hot cache strategy for a table or index only in shared storage mode.

## Modify the hot cache strategy for a regular table

After a table is created, you can use the `ALTER TABLE` statement to modify the hot cache strategy (`STORAGE_CACHE_POLICY`) of the table. The syntax is as follows:

```sql
ALTER TABLE table_name SET STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Parameter description

The `storage_cache_policy_option` parameter defines different attributes in the Key-Value format. The attributes are described as follows:

* `GLOBAL = {"hot" | "auto"}`: specifies the hot cache strategy for all data in the table. Valid values:

  * `hot`: indicates that all data in the table is hot data. If the local cache disk has enough space, all data in the table will be cached to the local cache disk.
  * `auto`: indicates that the system automatically identifies hot data in the table.

* `timeline_strategy_list`: specifies the list of parameters for the timeline strategy. Parameters are separated by commas. The hot cache timeline strategy determines whether partition data is hot data based on time. The system automatically adjusts the partition data on the local cache disk based on the configured strategy.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>A timeline is a partitioning range that is used to cache hot data. When a certain time condition is met, the data in the partition is considered hot data. When you use the timeline strategy, note the following: <ul><li>Only Range-partitioned tables can use the timeline strategy. A Range partition can be a primary or secondary partition. This is because time is used to determine whether data has expired. However, Double Range partitions are not supported. This is because it is impossible to determine which Range partition to use for time-based expiration. </li><li>When you use the timeline strategy, the partition expression can contain only column names, not expressions. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code> is not supported. </li><li><code>BOUNDARY_COLUMN</code> must be a partition key. If the partition key contains multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column, which is used to determine whether the partition has expired. </li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: specifies the column used to determine hot data. Supported data types: integer (`BIGINT` or `INT`, in the Unix timestamp format) and time (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If the data type of `BOUNDARY_COLUMN` is an integer, the table can be partitioned by Range or Range Columns.
    * If the data type of `BOUNDARY_COLUMN` is a time type, the table can be partitioned by Range Columns only.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: specifies the time unit of the `BOUNDARY_COLUMN` parameter. This parameter is supported only when the data type of `BOUNDARY_COLUMN` is an integer. If the integer value is used as a timestamp, you must specify the timestamp unit to avoid incorrect parsing of the timestamp. Valid values:

    * When the partition column is of the `INT` type, the value of `BOUNDARY_COLUMN_UNIT` must be `s`.
    * When the partition column is of the `BIGINT` type, the value of `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

      <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>If the timestamp is not in the Unix timestamp format, the system cannot correctly identify the time represented by the <code>INT</code> type. </p>
      </main>

  * `HOT_RETENTION = intnum retention_time_unit`: specifies the time range for hot data.

    * `intnum`: specifies an integer.
    * `retention_time_unit`: specifies the time unit. Valid values:

      * `YEAR`: year
      * `MONTH`: month
      * `WEEK`: week
      * `DAY`: day
      * `HOUR`: hour
      * `MINUTE`: minute

### Examples

* Modify the hot cache strategy for table `tbl1` to let the system automatically identify hot data.

    ```sql
    ALTER TABLE tbl1 SET STORAGE_CACHE_POLICY (GLOBAL = "auto");
    ```

* Modify the hot cache strategy for table `tbl2` to let the system identify partitions with data within two months from the current time as hot data based on the value of `col3`.

    ```sql
    ALTER TABLE tbl2 SET STORAGE_CACHE_POLICY (BOUNDARY_COLUMN = col3, HOT_RETENTION = 2 MONTH); 
    ```

## Change the hotspot cache strategy of an index table

You can use the `ALTER TABLE` statement to modify the hotspot cache strategy (`STORAGE_CACHE_POLICY`) of an existing index table. The syntax is as follows:

```sql
ALTER TABLE table_name ALTER INDEX STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    | BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

### Parameters

* `GLOBAL = {"hot" | "auto" | "none"}`: specifies whether the index table stores hot data. The value can be as follows:    

  * `hot`: indicates that the index table stores hot data. If the local cache disk has enough space, all data in the index table will be cached to the local cache disk.    
  * `auto`: indicates that the system automatically identifies hot data.    
  * `none`: indicates the strategy for the index table follows the `STORAGE_CACHE_POLICY` parameter of the partition table. This is the default value.    

* `timeline_strategy_list`: specifies the timeline strategy parameters. These parameters are separated by commas. The timeline strategy identifies hot data in partitions by time. The system automatically adjusts the partition data on the local cache disk. We recommend that you do not specify this strategy for local indexes.    

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>A timeline is a range specified by the partition key. The system caches the hot data in the timeline. The following items are the details on using the timeline strategy: <ul><li>A range partition table can be specified for the timeline strategy. Range partitions can be primary or secondary, but double range partitions are not supported. The reason is that the expiration time of the double range partitions cannot be determined. </li><li>Expressions are not supported. You can only specify column names. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code> is not supported. </li><li><code>BOUNDARY_COLUMN</code> must be the partition key. If the table has multiple partition keys, <code>BOUNDARY_COLUMN</code> must be the first partition key to determine whether the partition has expired. </li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: specifies the column for identifying hot data. Supported data types are integers (`BIGINT` and `INT`, which should be in the Unix timestamp format), and timestamps (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If `BOUNDARY_COLUMN` is of the integer type, the table partitions by range and range columns are supported.    
    * If `BOUNDARY_COLUMN` is of the time type, the table partitions only by range columns are supported.    

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: specifies the time unit for `BOUNDARY_COLUMN`. This parameter is supported only when `BOUNDARY_COLUMN` is an integer. If `BOUNDARY_COLUMN` is specified as a timestamp, you must specify a time unit, otherwise the timestamp may be parsed incorrectly. Valid values:    

    * When the partition is of the `INT` type, the value of `BOUNDARY_COLUMN_UNIT` can be only `s`.    
    * When the partition is of the `BIGINT` type, the value of `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.    

  * `HOT_RETENTION = intnum retention_time_unit`: specifies the time range for caching hot data.    

    * `intnum`: specifies an integer.    
    * `retention_time_unit`: specifies the time unit. Valid values:    

      * `YEAR`: year.    
      * `MONTH`: month.    
      * `WEEK`: week.    
      * `DAY`: day.    
      * `HOUR`: hour.    
      * `MINUTE`: minute.    

### Examples

Set the hotspot cache strategy of index `idx2` to `auto`.

```sql
ALTER TABLE test_tbl2 ALTER INDEX idx2
    STORAGE_CACHE_POLICY (GLOBAL = "auto");
```
