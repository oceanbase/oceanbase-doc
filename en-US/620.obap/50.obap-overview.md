# Overview of OceanBase AP

## What is OceanBase AP?

In the database scenario, **transaction processing (TP)** focuses on high-concurrency and strong-consistency online transactions, while **analytical processing (AP)** focuses on real-time analysis and complex queries of massive data. Together, they support enterprises' data management and analysis needs. OceanBase has long maintained a technical lead in the TP domain, serving numerous core business applications with its self-developed distributed architecture, financial-grade high availability, and extreme elasticity. As the demand for enterprise-level real-time analysis has surged, OceanBase extended its capabilities from TP to AP in V4.3. This version introduced native columnar storage and integrated row-column storage, and equipped it with a vectorized execution engine. On the optimizer side, it enhanced the cost model and statistics for columnar storage, enabling automatic selection of access paths based on cost. These storage, execution, and optimization capabilities work together to allow the same engine to handle both transactional workloads and real-time analysis, delivering integrated data management and real-time analysis value to enterprises.

## Core features

* **Integrated storage foundation supporting row, column, and hybrid storage:** Users can flexibly specify row, column, or hybrid storage when creating tables to match different business types. **Columnar tables** in the storage engine use a combination of baseline columnar storage and incremental row storage. Baseline columnar storage optimizes complex query performance, while incremental row storage still supports high-concurrency data writes.

* **Strong transaction and high-concurrency guarantees for real-time analysis:** Continuing with distributed ACID and multi-replica strong consistency architecture, analytical scenarios can meet data strong consistency requirements. Smooth scaling and dynamic load balancing between nodes are supported, ensuring linear performance scaling with resource expansion. Multi-dimensional **resource isolation** capabilities are supported: resource isolation between tenants; within a tenant, resource groups can isolate resources at the user, SQL, and foreground/background task levels; and in a read-only columnar replica deployment, TP and AP traffic can be separated to different replicas, achieving physical strong isolation at the node level.

* **Vectorized execution engine for large-scale data analysis acceleration:** The vectorized execution engine processes data in batches, using efficient columnar data description formats and optimizing operators and expressions for batch iteration. The storage layer aligns with this format, accelerating projection, predicate, and aggregation paths through SIMD and other methods, and supports adaptive batch size adjustment based on workload. Compared to the traditional row-based volcano model, analytical query performance can improve by about an order of magnitude.

* **Enterprise-grade query optimizer for real-time analysis performance:** The optimizer is designed for HTAP and real-time analysis: it performs query rewriting and strategy selection in a larger plan space; adopts **one-phase distributed plan generation**, considering data distribution and parallelism when enumerating join orders and algorithms, avoiding the issue of single-machine optimal but distributed suboptimal; automatically selects between **row and column access paths** based on access characteristics, and establishes cost models and statistics for columnar scans to evaluate the scanning benefits of mechanisms like **SkipIndex**. For queries with high scanning costs, **automatic parallelism (AUTO DOP)** can be enabled to shorten response time; through **SQL Plan Management (SPM)**, plans can be managed during data volume, statistics, or version changes, and plan rollback can be suppressed through gray-scale validation of real traffic, ensuring stable operation.

* **Smart materialized views with multi-layer precomputation and frequent real-time refreshes:** Users can define precomputed results using declarative SQL, and OceanBase automatically manages refresh mechanisms and table dependencies, eliminating the need for complex ETL or data pipelines. It supports **real-time materialized views**, which can be scheduled to refresh based on target freshness (e.g., 30 seconds, 5 minutes); through **automatic incremental view maintenance**, only changes since the last refresh are incrementally computed, reducing refresh costs and ensuring freshness. When the optimizer identifies available materialized views, it automatically rewrites queries against the base table to read from the materialized view, accelerating complex queries without requiring SQL changes.

* **Multi-mode data types for AI-fusion analysis:** Native support for complex types like Array, Roaring Bitmap, Map, JSON, and Vector is provided, along with capabilities like JSON multi-value indexing, vector indexing, and full-text indexing to narrow scan ranges and accelerate retrieval. It supports typical analysis scenarios like tag analysis and audience targeting, and also meets AI-related requirements like knowledge retrieval and semantic search through unified storage and hybrid retrieval capabilities.

* **Seamless integration with open ecosystems to empower business innovation:** OceanBase can access data from various external systems and collaborate with upstream and downstream tools. It supports real-time data ingestion and processing from streaming systems like Kafka and Flink; data migration and synchronization with existing databases or data warehouses through tools like OMS; and access to multiple file and object storage formats via external tables, with support for Hive Metastore, Iceberg, and other catalogs for unified metadata access. The SQL layer is highly compatible with MySQL and Oracle, facilitating easy integration with BI, ETL, and other analysis tools. Integration with scheduling systems like DolphinScheduler and Airflow is supported, as well as monitoring, visualization, and analysis tools like Prometheus, Grafana, Tableau, and QuickBI, supporting data chain governance and business insights.

## Scenarios

#### Scenario 1: HTAP hybrid workload scenario

* Unified architecture: A single engine and a single set of data support both transactional and analytical workloads. You can choose to deploy the system in either a row-column hybrid mode or a columnar mode based on your business requirements.
* Low-cost massive storage: Based on the LSM-Tree and advanced compression encoding technology, the storage cost is reduced by 70% to 90% compared with traditional solutions.
* High-concurrency computing: The peer-to-peer architecture of OceanBase Database natively supports parallel computing across multiple servers. It can support up to PB of data and provides a stable storage foundation for your business's data.
* Multi-scenario isolation: Through resource isolation at the lower layer and user resource groups, tasks of different scenarios and users are isolated from each other.

#### Scenario 2: Real-time data analysis scenario

* Real-time data updates: Based on the LSM-Tree architecture, OceanBase Database supports efficient real-time writes. Incremental data is stored in rows and baseline data in columns. Regular or adaptive major compactions are performed to generate new columnar baseline data. After data is written, it can be queried immediately, ensuring data real-time.
* High accuracy and strong consistency: The Multi-Paxos protocol is used to ensure data consistency across multiple replicas. The MVCC model supports non-blocking reads and writes and ensures transaction consistency for read data. It also supports strong reads from the primary replica and weak reads from other replicas. The WAL mechanism is used to ensure data persistence and atomicity.
* High-performance computing: Columnar storage, compute pushdown, and query processing based on compressed data are used to achieve high-performance data queries. The optimizer is used to rewrite queries and select plans based on rules or costs. Parallel execution engines and vectorized engines are used to optimize execution and achieve high computing performance. Materialized views are provided to further support queries and analysis on massive data.
* High availability: Inheriting the high availability capabilities of TP systems, OceanBase Database has an RPO of 0 and an RTO of less than 8 seconds. It supports flexible deployment from a single IDC to three regions with five IDCs. It supports automatic disaster recovery. Cloud Database OceanBase Database also supports a single-replica architecture based on shared storage and independent log services, which reduces costs while ensuring high availability.
* Smooth scaling: You can smoothly scale out or scale in the system without interrupting services. During horizontal scaling, the built-in data dynamic balancing mechanism ensures that data and service loads are evenly distributed across nodes.
* Multi-model fusion: OceanBase Database fully supports various models, including B-tree indexes, JSON multi-value indexes, full-text indexes, and vector indexes.
* Separation of storage and computing: OceanBase Database supports multiple computing nodes to access the same storage data. It combines local persistent caching and object storage to achieve a cost-effective separation of storage and computing.

#### Scenario 3: PL/SQL batch processing scenario

* Extreme performance improvement, breaking through processing bottlenecks. OceanBase Database's columnar storage engine is specifically designed for analytical scenarios. Data is stored in columns, which increases the compression ratio and reduces I/O. Combined with the vectorized execution engine, the CPU can perform calculations on a batch of data (instead of a single row) in memory at once, significantly improving CPU cache hit rate and computing efficiency. For typical batch processing tasks, performance can be improved by 10 times or more, easily meeting or even shortening the business batch processing window, making near-real-time analysis possible.
* Seamless migration with minimal business risk. OceanBase Database is highly compatible with Oracle, not only supporting common SQL syntax and data types, but also highly compatible with PL/SQL stored procedures. This means that customers can migrate stored procedures from Oracle to OceanBase Database with minimal or no modifications. Application layer code does not need to be changed, significantly reducing migration risks, costs, and time, making system modernization possible.
* Unified architecture for cost reduction and efficiency improvement. Traditional architectures separate OLTP databases from data warehouses or big data platforms, requiring maintenance of two systems and complex ETL/CDC synchronization, resulting in high costs. OceanBase Database's unified architecture supports both online transactions and batch processing analysis with a single system. Its built-in resource isolation mechanism ensures that analytical tasks running on columnar data do not conflict with transactional tasks running on row-based data. This simplifies the technology stack, reduces operational complexity, and avoids redundant data storage and cross-system synchronization, significantly lowering the total cost of ownership (TCO) for enterprises.
