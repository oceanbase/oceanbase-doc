# AP FAQ

## Columnar FAQ

### What are columnar storage databases?

OceanBase Columnar is a data storage format that stores static data on the disk in columnar format and modified data in memory in row-based format, balancing scan performance and transaction processing capabilities.

For analytical queries, columnar storage can significantly improve query performance, making it an indispensable feature for OceanBase to support HTAP. In traditional AP databases, columnar data is typically static and not easily updated in-place. However, OceanBase's LSM tree architecture features static SSTables that are well-suited for columnar storage, while dynamic MemTables remain in row-based format for transactional processing, thus impacting only transactional operations. This design allows OceanBase to balance the performance of both TP and AP queries to a significant extent.

### What is a columnstore index?

OceanBase Database supports columnstore indexes. A columnstore index is an index table that uses the columnar storage format.

For example, suppose we have the row store table `t6` and we want to compute the sum of column `c3` in the best performance, we can build a column store index on `c3`.

```sql
create table t6(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
);

create /*+ parallel(2) */ index idx1 on t6(c3) with column group (each column);
```

In addition, you can also create indexes in these ways:

* Allows you to store extra rows in the indexes.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(all columns, each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(all columns, each column);
  ```

* Index-only scans are supported.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(each column);
  ```

The use of the `STORING` clause in a database index serves to store additional non-indexed column data within the index itself. This can optimize specific queries by either avoiding the need to access the table for the original rows or reducing the overhead of sorting. When a query only requires accessing the columns stored in the index without needing to retrieve the original rows, this can significantly enhance query performance.

### Common questions and answers about columnar tables and columnar replicas

#### What's the difference between a columnar table and a columnar replica? How are they related?

Both describe different dimensions:

* **Columnar tables**: This refers to the **table-level storage mode** (row, full column, or hybrid row and column), which is determined by `WITH COLUMN GROUP` or the tenant-level `default_table_store_format`. Data is physically stored on **F (full-featured) and R (read-only) replicas** of the tenant. On these replicas, MemTables and dumps are organized row-wise, while the baseline can be stored in columnar or hybrid row/column format. The read path integrates incremental updates with the baseline. When executing semantic-compatible operations on F or R replicas, **strong-consistent reads are achieved by default**, consistent with the replica's role (related to transactions, isolation levels, etc.).

* **Columnstore replica (C replica)**: A **replica type independent of the default rowstore**. Typically located in a standalone Zone. **Does not participate in Paxos elections or voting**, and asynchronously synchronizes data with the F/R replicas through logs. The **major compaction** for local data uses columnstore format, mainly for user tables. The same logical table can be stored in **rowstore format on F/R replicas** and **columnstore format on C replicas**, for **AP/TP resource isolation**.

**Relationship** : The two are independent. Columnstore tables can be created in tenants **without** C replicas (data exists only in columnar or hybrid format in F/R). In tenants with C replicas, **columnar data can be stored on F/R and accessed in read-only analysis mode by the C replicas.** Columnstore tables can also coexist with C replicas, configured as needed.

* **Read consistency**: Replicas in C have a lag behind the log source. **Before OceanBase V4.6.0**, the majority of analytical queries accessed from independent ODPs are typically planned as **weak read**s. **From V4.6.0 onwards**, users can configure **strong read or weak read**s on C replicas (e.g., through `ob_read_consistency`), and the execution of columnar plans is controlled by parameters like `ap_query_route_policy`.

#### Do I need columnar replicas to create a **columnar table**? Can I create a columnar table on a full replica?

**You can also create a columnstore table on a full (F) replica without requiring a columnstore replica.**

Columnstore tables are a table-level storage format configuration specified by using the `WITH COLUMN GROUP` option during table creation or through the tenant-level configuration item `default_table_store_format`. As long as the tenant has at least one F/R replica (such as `F@zone1, F@zone2`), you can create columnstore tables or hybrid columnar tables in any Locality. Data will be stored in F/R replicas in columnar (or hybrid) form. Columnstore replicas (C replicas) are an optional standalone deployment configuration used for isolating read-only analysis traffic in TP or AP scenarios. The presence of C replicas does not affect the ability to create columnstore tables.

#### Can OceanBase create a standalone columnstore table directly? Or is it required to be based on a rowstore table?

**You can create a standalone columnar table without needing to build on a rowstore table.**

You can create a pure columnstore table by specifying the `WITH COLUMN GROUP (each column)` option. For example:

```sql
CREATE TABLE t (pk INT PRIMARY KEY, c1 INT, c2 INT) WITH COLUMN GROUP (each column);
```

For partitioned tables, the primary key columns store data in row format for efficient point queries, while the rest of the table remains columnar. You can also create a row-store table first and then convert it to a columnar table using DDL commands like `ALTER TABLE ... ADD COLUMN GROUP (each column);`. For more details, see "How to create a columnar table?" in this topic.

#### How is data consistency maintained between columnar and row storage? What is the latency if it's asynchronous?

There are two types of scenarios:

* **Column Store Tables (on F/R Replicas):** Base tables are stored as columnar or row-column mixed, with incremental data in row format (MemTable/dump). Reading involves combining both base and incremental data, ensuring **strong consistency** under F/R's default semantics without extra cross-replica latency.
* **Columnar replicas (C replicas)**: C replicas do not participate in Paxos. They use **asynchronous logs** to catch up with and replay F/R logs, leading to some **lag in data compared to the logs**. In **versions before V4.6.0**, C replicas mainly provided **eventually consistent reads** for analysis. Starting from **V4.6.0**, you can configure **strong reads** on C replicas. Strong reads wait for the replicas to catch up with a readable point, resulting in longer latency compared to weak reads. If the requirement is that the **logs must be exactly the same as those for TP and C replicas should not lag**, analysis tasks are still preferred to be performed on **columnar tables or hybrid-row-and-column tables on F/R**.

#### How to separate TP and AP traffic? What about disaster recovery when the AP fails?

**Separate traffic:**

* **No C replicas** : TP and AP share the same set of F/R replicas and access points, with the optimizer automatically choosing between row/column storage paths. **No** physical isolation of TP/AP cabinets or links.
* **With C replicas (OceanBase Database V4.6.0 and earlier)**: A typical approach is to route TP workloads through the F/R entry point (strong read/write), while AP workloads go through a **dedicated ODP**, with weak read settings enabled. ODP configurations include parameters like `proxy_primary_zone_name`, `route_target_replica_type = 'ColumnStore'`, and `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`, ensuring TP/AP workloads are isolated from C replicas. Refer to [Use a columnstore replica](../600.manage/300.replica-management/150.the-use-of-columnstore-replica.md) for more information on O&M and replica management.
* **C replicas (V4.6.0 or later):** In addition to the **ODP deployment (Option 1)**, you can **connect directly to the OBServer node** (or through a regular ODP without dedicated columnar routing configuration) and let the **optimizer automatically attempt to find columnar plans** through commands like **`ap_query_route_policy`**. This **Option 2** eliminates the need to maintain a separate ODP configuration for C replicas.

**C copy side disaster recovery and limitations: **

* A standby instance of the C mode cannot be promoted to a leader; **physical recovery is not supported for standby instances of the C mode** (if the C mode is in the locality of a tenant, the restoration will fail); and when the leader instance does not have a standby instance of the C mode, it is also not recommended to deploy a standby instance of the C mode for the follower instance.
* If the Zone of C replica or the ODP has a failure, the AP query **can fall back to a F/R replica**: Change the AP client to connect to the primary ODP or adjust the routing so that the analysis request executes with strong reads on the F/R replica (which shares resources with TP).
* C instances can be deployed with **multiple copies** (up to 3) starting from V4.3.5 BP1, and multiple C instances can be deployed across multiple Zones. C replicas can be routed through ODP (Option 1) or with automatic routing (Option 2) to spread AP read load, achieving redundancy and high availability.

### How do I create a columnstore table?

First, create a hybrid rowstore-columnstore table.

- Non-partitioned table:

```sql
create table t1(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (all columns, each column);
```

- Partitioned table:

```sql
create table t2(
   pk int,
   c1 int,
   c2 int,
   primary key (pk)
)
partition by hash(pk) partitions 4
with column group (all columns, each column);
```

When creating a hybrid rowstore-columnstore table, the `with column group (all columns, each column)` syntax is always used. The meaning of this syntax is as follows:

- `all columns`: All columns are aggregated into one group and stored as a wide column, row by row. This is essentially the same as the original rowstore.
- `each column`: Each column in the table is stored in columnar format.

When both `all columns` and `each column` are used together, it means that after creating a columnstore table by default, the rowstore data is also stored, with each replica storing two copies of the baseline data. However, it's worth noting that regardless of the number of baseline data copies, the incremental data in the memtable and the dump are still shared.

Next, create a pure columnstore table.

- Non-partitioned table:

```sql
create table t3(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (each column);
```

- Partitioned table:

```sql
create table t4(
   pk1 int,
   pk2 int,
   c1 int,
   c2 int,
   primary key (pk1, pk2)
)
partition by hash(pk1) partitions 4
with column group (each column);
```

For the t4 table, a columnstore is created for each of the columns pk1, pk2, c1, and c2, and a rowstore is created for the combination of (pk1, pk2).

### How do I make the tables created by a tenant default to columnstore tables?

Set a tenant-level parameter:

```sql
alter system set default_table_store_format = "column";
```

Similarly, you can set the default table creation to rowstore or both rowstore and columnstore:

```sql
alter system set default_table_store_format = "row";   // Rowstore
alter system set default_table_store_format = "compound"; // Both rowstore and columnstore data
```

### What are the recommended configurations for columnstore?

```sql
# Set the collation to utf8mb4_bin to boost performance by 15%
set global collation_connection = utf8mb4_bin;
set global collation_server = utf8mb4_bin;

set global ob_query_timeout= 10000000000;
set global ob_trx_timeout= 100000000000;
set global ob_sql_work_area_percentage=30;
set global max_allowed_packet=67108864;
# Recommended to be 10 times the number of CPU cores
set global parallel_servers_target=1000;
set global parallel_degree_policy = auto;
set global parallel_min_scan_time_threshold = 10;
# Limit the maximum DOP when parallel_degree_policy is set to auto
# A high DOP may cause performance issues. The following value is recommended to be set to cpu_count * 2
set global parallel_degree_limit = 0;

alter system set compaction_low_thread_score = cpu_count;
alter system set compaction_mid_thread_score = cpu_count;
alter system set default_table_store_format = "column";
```

  <p>In the above code, <code>cpu_count</code> represents the <code>min_cpu</code> specified when the tenant was created.</p>

### Can I add or drop columns in a columnstore table?

* Yes, you can add or drop columns.

* You can change the length of a Varchar column to be larger or smaller.

* Columnstore supports various Offline DDL operations, just like rowstore tables.

For more information about modifying columnstore tables, see [Convert a table from rowstore to columnstore (MySQL mode)](../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/600.change-table-of-mysql-mode.md) and [Convert a table from rowstore to columnstore (Oracle mode)](../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/100.manage-tables-of-oracle-mode/600.change-table-of-oracle-mode.md).

### What are the characteristics of queries on columnstore tables?

* In a hybrid rowstore-columnstore table, the query logic for Range Scan uses columnstore by default, while Point Get queries fall back to rowstore.

* In a pure columnstore table, all queries use columnstore.

### Does columnstore support transactions, and are there any size limitations?

Yes, columnstore supports transactions, and there are no size limitations on transactions, ensuring high consistency.

### Are there any special considerations for log synchronization, backup, and restore in columnstore tables?

No, columnstore tables behave the same as rowstore tables. The synchronized logs are in rowstore format.

### Can I convert a rowstore table to a columnstore table using DDL operations?

Yes. You can add columnstore and drop rowstore. Here are some examples:

```sql
create table t1( pk1 int, c2 int, primary key (pk1));

alter table t1 add column group(all columns, each column);
alter table t1 drop column group(all columns, each column);

alter table t1 add column group(each column);
alter table t1 drop column group(each column);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After executing <code>alter table t1 drop column group(all columns, each column);</code>, you don't need to worry about any group to hold the data. All columns will be placed into a default group called <code>DEFAUTL COLUMN GROUP</code>.</p>
</main>

### Can I group multiple columns together in columnstore?

In OceanBase Database V4.3.0, only **either each column is stored separately or all columns are stored together as a row** is supported. Grouping a subset of columns together is not supported.

### Does OceanBase Database support updates on columnar tables? What is the structure of the MemTable?

In OceanBase Database, add, delete, and update operations are performed in memory. The data is stored in the MemTable in row-based format. The baseline data is read-only and stored in columnar format on disk. When a column is read, the system combines the row-based data in the MemTable with the columnar data on disk in real time and returns the result to the user. This means that **OceanBase Database supports strong-consistency reads on columnar data, with no data latency**. Data written to the MemTable can be dumped, and the dumped data is still stored in row-based format. After the merge, the row-based data and baseline columnar data are combined to form new baseline columnar data.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>For columnar tables, if there are a large number of update operations and no timely major compactions are performed, query performance will be affected. Therefore, it is recommended to perform a major compaction after batch data import to achieve optimal query performance. However, a small number of update operations will not significantly impact performance.</p>
</main>

### What are the characteristics of queries on columnar tables?

In a redundant rowstore table, columnar table queries default to range scans in columnar mode, while point get queries fall back to rowstore mode.

In a pure columnar table, all queries are performed in columnar mode.

### Can an index be created on a specific column of a columnar table?

Yes. OceanBase Database does not differentiate between creating an index on a columnar table or a rowstore table. The index structure is the same in both cases.

Creating an index on one or more columns of a columnar table allows for the construction of a covering index, which can improve point query performance, or for sorting specific columns to enhance sorting performance.

### What is the maximum number of columns supported?

Currently, a columnar table can support up to 4096 columns.

### What are the considerations when using columnar tables?

**First**: After batch data import, it is recommended to perform a major compaction to optimize read performance. After data import, trigger a major compaction within the tenant to ensure all data is baseline. Execute `alter system major freeze;` within the tenant, and then check the status by running `select STATUS from CDB_OB_MAJOR_COMPACTION where TENANT_ID = tenant_id;` in the system tenant. When the `STATUS` changes to `IDLE`, the major compaction is complete.

**Second**: After a major compaction, it is recommended to collect statistics. The method for collecting statistics is as follows:

- In the business tenant, collect statistics for all tables using a single command, with 16 threads running concurrently:

  ```sql
  CALL DBMS_STATS.GATHER_SCHEMA_STATS ('db', granularity=>'auto', degree=>16);
  ```

- You can monitor the statistics collection progress by querying the `GV$OB_OPT_STAT_GATHER_MONITOR` view.

**Third**: You can use full direct load to batch import data. Tables imported using this method do not require a major compaction to achieve optimal columnar scan performance. Tools that support full direct load include obloader and the native LOAD DATA command.

**Fourth**: For non-large, wide tables, using columnar tables may not necessarily provide performance comparable to columnar tables. This is due to the row-column hybrid storage architecture at the microblock level in OceanBase Database's rowstore version (which is normal).

**Fifth**: For tables with large amounts of data, the performance of cold runs and hot runs may differ.

**Sixth**: The optimizer automatically selects whether to use rowstore or columnar data access based on cost estimation.

**Seventh**: The merge speed of columnar tables will be slower.

### Are there any special considerations for log synchronization, backup, and restore for columnar tables?

No, they are the same as for rowstore tables. The synchronized logs are in rowstore format.

## FAQ about data import and migration

### What is bypass import? How do I perform bypass import?

Bypass import is a method to accelerate data import and data query. For large tables, we recommend that you use bypass import. Currently, the `load data` command and the `insert into select` statement support bypass import. For more information, see [Overview of bypass import](300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

Yes. For more information, see [Use Flink CDC to synchronize data from a MySQL database to OceanBase Database](../500.data-migration/200.migrate-data-from-mysql-database-to-oceanbase-database/600.use-flink-cdc-to-migrate-data-from-mysql-database-to-oceanbase-database.md).

## FAQ on performance optimization

### What are other methods to further improve AP Query performance?

Based on practical experience, first, if there are no special sorting requirements, do not use the utf8mb4 character set when creating tables, but instead use the binary character set to improve performance. For example:

```sql
create table t5(c1 TINYINT, c2 VARVHAR(50)) CHARSET=binary with column group (each column);
```

Second, if users or businesses can accept it, specify the utf8mb4_bin character set when creating tables for MySQL tenants, using the following syntax: `CHARSET = utf8mb4 collate=utf8mb4_bin`

Additionally, increasing the IOPS of the UNIT can speed up the direct import.

### What are the characteristics of the optimizer for columnar storage?

Compared to the optimizer for row-based storage, the optimizer for columnar storage has the following features:

- The ability for the optimizer to autonomously select between row and columnar storage.
- The ability to control the selection between row and columnar storage using hints at the table level.
- Adapted plan cost calculation for columnar storage.
- Late materialization optimization for columnar storage.
