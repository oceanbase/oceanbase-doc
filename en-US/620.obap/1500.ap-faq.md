# AP FAQ

## Columnar FAQ

### What is columnar storage?

OceanBase Columnar Store is a data storage form that saves disk static data as columnar data and memory modified data as rowar data. It provides a good balance between scan performance and transaction processing capability.

Columnstore significantly improves query performance for analytical queries, making it a crucial feature for OceanBase's HTAP capability. In traditional AP databases, columnar data is static and difficult to update in place. However, OceanBase's LSM Tree architecture features static SSTables, ideal for columnar implementation, while dynamic MemTables remain row-based, not impacting transactional performance. This hybrid approach allows us to balance the performance of both transactional and analytical queries.

### What is a Columnstore index?

OceanBase Database also supports columnar indexes. In OceanBase Database, a columnar index means that an index table is stored in columnar format, rather than storing an index in columnar format.

For example, we already have a rowstore table `t6`, and we want to sum `c3` with the best performance. In this case, we can create a columnstore index on `c3`:

```sql
create table t6(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
);

create /*+ parallel(2) */ index idx1 on t6(c3) with column group (each column);
```

In addition to the aforementioned methods, we also support the following index creation methods:

* Supports the storage of redundant rows in an index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(all columns, each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(all columns, each column);
  ```

* Supports columnar storage.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(each column);
  ```

Using the `STORING` clause in a database index allows you to store additional non-indexed column data within the index. This can optimize query performance by avoiding table lookups and reducing the cost of index sorting. When a query only needs to access columns stored in the index and doesn't need to retrieve the original row data from the table, it significantly improves query efficiency.

### Frequently Asked Questions about Columnstore Tables and Columnstore Replicas

#### What are the differences between columnar tables and columnar replicas? What is their relationship?

They describe different aspects:

* **Column store tables**: This refers to **table-level storage formats** (row-based storage, pure columnar storage, or hybrid row-column storage), which are determined by `WITH COLUMN GROUP` or the tenant-level `default_table_store_format`. Data is physically stored on the **F (Full) or R (Read-Only) replicas** of the tenant. On these replicas, MemTable and dumps remain row-oriented, while the baseline can be columnar or hybrid row-column storage. Read paths integrate incremental and baseline data. For F or R replicas, executing queries that follow the path will **default to obtaining strongly consistent reads** in accordance with the replica role, and are subject to semantic constraints (such as transactions and isolation levels).

* **Columnstore Replica (C-Replica):** A **type of independent replica** usually placed in a separate zone; it **does not participate in Paxos elections or voting**, but asynchronously catches up with full-row and row-based replicas through logs. **Major compactions are primarily columnar**, and the data of the user table is stored using a columnar data format. A **F/R replica of the same logical table could use a row or hybrid row-column format, while the C-Replica stores data in a columnar format**. This **separates resources between AP and TP**.

**Relation:** The two are independent. A column store table can be created in a tenant that does not have C replicas (data exists only in columnar or hybrid format in F/R). On the other hand, F/R can provide read-only analysis in columnar format for the same column store table stored in C replicas. Column store tables and C replicas can coexist and be configured based on architectural requirements.

* **Consistency**：The C-Replica is behind the log source. **Before OceanBase Database V4.6.0**, analytical queries accessing the C-Replica through an independent ODP typically used **weak-consistency reads**. Starting with **V4.6.0**, you can configure sessions to use **strong or weak consistency** (such as `ob_read_consistency`), and settings like `ap_query_route_policy` control whether to attempt columnar plans.

#### Is a column store replica required to create a **column store table**? Can a column store table be created on a Full replica?

**You can create columnar tables even if no columnar replicas are specified, on Full (F) replicas.**

Columnar storage format is a table-level storage configuration. It can be specified when creating a table with the `WITH COLUMN GROUP` clause or at the tenant level through the `default_table_store_format` configuration item. As long as the tenant has a F/R replica: columnar or hybrid row and column storage tables can be created in any Locality (e.g., `F@zone1, F@zone2`), and the data will be stored in the columnar or row and column redundant form on the F/R replicas. Column replicas (C replicas) are optional and can be deployed independently for physical or logical isolation in TP/AP scenarios and read-only analytical traffic. The ability to create a columnar storage table is not dependent on the presence of a column replica.

#### Can a pure column table be created directly in OceanBase, or must it be created based on a row store table?

You can directly create a columnar table without relying on a rowstore table.

Specify the `WITH COLUMN GROUP (each column)` clause when you create a table to create a pure columnstore table (only the columnar baseline, no row baseline). For example:

```sql
CREATE TABLE t (pk INT PRIMARY KEY, c1 INT, c2 INT) WITH COLUMN GROUP (each column);
```

In partitioned tables, an extra copy of rows will be reserved for each row-based partition for point queries, but the table is still considered a pure columnar table. You can also create a row-based table and convert it into a column-based table by using the `ALTER TABLE ... ADD COLUMN GROUP (each column);` DDL statement. For more information, see How do I create a columnar table?

#### How to ensure data consistency between rowstore and columnstore? If it's asynchronous, what is the delay?

**Two scenarios:**

* **Columnar tables (on F/R replicas)**: Bases are stored in columnar or hybrid row-columnar layouts, while incremental updates are stored in row-based format (MemTable/dump). During reads, the incremental and base data are integrated, ensuring **strong consistency** under F/R's default semantics without any additional lag across replicas.
* **Columnstore replicas (C replicas)**: C replicas do not participate in Paxos. Instead, they asynchronously catch up with F/R replicas by replaying logs, resulting in **data lag** relative to the log source. **Prior to V4.6.0**, analytic read operations against C replicas were **weakly consistent**. **Starting from V4.6.0**, you can configure **strong reads** on C replicas. Strong reads wait for replicas to reach a readable point, introducing higher latency than weak reads. If **identical logs as TP, with no C replica lag** are required, analytic operations are still preferable to be conducted on **columnstore or hybrid column-rowstore tables on F/R replicas**.

#### How do I isolate TP and AP traffic? What are the disaster recovery options if an AP fails?

**Traffic Separation:**

* **No C replica**: TP and AP share the same set of F/R replicas and access points, with the optimizer automatically selecting the row/column storage path; **no** physical isolation of TP/AP cabinets or link levels.
* **With C replicas**: Transactional (TP) traffic is routed to the primary ODP, accessing the strong-read/write replicas of F and R. Analytical (AP) traffic is routed to an **ODP independent from the primary ODP**, and weak reads (e.g., `obproxy_read_consistency = 1` ) are configured. Requests are only routed to zones where the C replicas reside (e.g., `proxy_primary_zone_name`, `route_target_replica_type = 'ColumnStore'`, and `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`). This achieves physical isolation for TP and AP. For more information, see [Deploy and use columnstore replicas](150.obap-deploy/150.uesing-columnstore-replica.md).
* **If you are using a C-Replica (V4.6.0 and later) **: In addition to the aforementioned **independent ODP (Method 1)**, you can also **directly connect to an OBServer** (or a regular ODP without columnar dedicated line configuration) and the **optimizer will automatically attempt a columnar plan** (Method 2). You do not need to maintain a separate set of ODP routing items specifically for the C-Replica.

**Disaster Recovery and Limitations for (C Copy) AP Side: **

* C replicas cannot become leaders; **physical recovery is not supported for C replicas** (a failure will occur if a C replica exists in the tenant's locality). If no C replicas are present in the primary database, then C replicas should not be deployed in the standby database.
* If the C replica zone or the ODP fails, AP queries can **fallback to F/R replicas**: Switch the AP client to connect to the primary ODP or adjust the routing so that the analytical requests are executed with strong reads on the F/R replicas (which will share resources with TP).
* Multiple **C copies** (up to 3, recommended) can be deployed since V4.3.5 BP1. C replicas can be deployed across zones and their application payload (AP) load can be spread out with routing (Method I) or automatic routing (Method II) in ODP, to achieve redundancy and high availability.

### How do I create a columnstore table?

First, create a hybrid table that stores data in both row and column formats.

- For a non-partitioned table:

```sql
create table t1(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (all columns, each column);
```

- For a partitioned table:

```sql
create table t2(
   pk int,
   c1 int,
   c2 int,
   primary key (pk)
)
partition by hash(pk) partitions 4
with column group (all columns, each column);
```

When you create a hybrid table, you always use the `with column group (all columns, each column)` syntax. The meaning of this syntax is as follows:

- `all columns`: All columns are grouped together into a wide column and stored row by row. This is essentially the same as the original rowstore.
- `each column`: Each column is stored separately in column format.

When both `all columns` and `each column` are used together, it means that after creating a columnstore table, the data is redundantly stored in both rowstore and columnstore formats. Each replica stores two copies of the baseline data. However, it's worth noting that regardless of how many baseline data copies there are, the incremental data in the memtable and the dumps still share the same baseline data.

Next, create a pure columnstore table.

- For a non-partitioned table:

```sql
create table t3(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (each column);
```

- For a partitioned table:

```sql
create table t4(
   pk1 int,
   pk2 int,
   c1 int,
   c2 int,
   primary key (pk1, pk2)
)
partition by hash(pk1) partitions 4
with column group (each column);
```

For the t4 table, a columnstore is created for each of the columns pk1, pk2, c1, and c2, and a rowstore is created for the combination of (pk1, pk2).

### How do I make a tenant's default table type columnstore?

Set a tenant-level parameter:

```sql
alter system set default_table_store_format = "column";
```

Similarly, you can set the default table type to rowstore or to both rowstore and columnstore:

```sql
alter system set default_table_store_format = "row";   // Rowstore
alter system set default_table_store_format = "compound"; // Both rowstore and columnstore
```

### What are the recommended configurations for columnstore?

```sql
# Set the collation to utf8mb4_bin for a 15% performance boost.
set global collation_connection = utf8mb4_bin;
set global collation_server = utf8mb4_bin;

set global ob_query_timeout= 10000000000;
set global ob_trx_timeout= 100000000000;
set global ob_sql_work_area_percentage=30;
set global max_allowed_packet=67108864;
# We recommend setting this to 10 times the number of CPU cores.
set global parallel_servers_target=1000;
set global parallel_degree_policy = auto;
set global parallel_min_scan_time_threshold = 10;
# Limit the maximum DOP when parallel_degree_policy is set to auto.
# A high DOP may cause performance issues. We recommend setting this to cpu_count * 2.
set global parallel_degree_limit = 0;

alter system set compaction_low_thread_score = cpu_count;
alter system set compaction_mid_thread_score = cpu_count;
alter system set default_table_store_format = "column";
```

### How do I determine whether a query is executed in columnstore mode?

When a query is executed in rowstore mode, the `explain` statement displays `TABLE FULL SCAN`. When a query is executed in columnstore mode, the `explain` statement displays `COLUMN TABLE FULL SCAN`. For example, consider the t5 table:

create table t5(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT,
   c4 INT,
   c5 INT,
   PRIMARY KEY(c1, c2)
) with column group(all columns, each column);

### Can I add or drop columns in a columnstore table?

* Yes, you can add or drop columns.

* You can increase or decrease the length of a Varchar column.

* Columnstore tables support various Offline DDL operations, similar to rowstore tables.

For more information about modifying columnstore tables, see [Convert a table from rowstore to columnstore (MySQL mode)](../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/600.change-table-of-mysql-mode.md) and [Convert a table from rowstore to columnstore (Oracle mode)](../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/100.manage-tables-of-oracle-mode/600.change-table-of-oracle-mode.md).

### What are the characteristics of queries on columnstore tables?

* In a hybrid table, range scans are executed in columnstore mode by default, while point get queries fall back to rowstore mode.

* In a pure columnstore table, all queries are executed in columnstore mode.

### Does columnstore support transactions, and are there any limitations on transaction size?

Yes, columnstore supports transactions, and there are no limitations on transaction size. It ensures high consistency.

### Are there any special considerations for log synchronization, backup, and restore in columnstore tables?

No, there are no special considerations. The behavior is the same as for rowstore tables. Synchronization logs are in rowstore format.

### Can I convert a rowstore table to a columnstore table using DDL?

Yes. You can add columnstore storage and drop rowstore storage. Here are some examples:

```sql
create table t1( pk1 int, c2 int, primary key (pk1));

alter table t1 add column group(all columns, each column);
alter table t1 drop column group(all columns, each column);

alter table t1 add column group(each column);
alter table t1 drop column group(each column);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After you execute <code>alter table t1 drop column group(all columns, each column);</code>, you do not need to worry about data being lost. All columns will be moved to a default column group named <code>DEFAUTL COLUMN GROUP</code>.</p>
</main>

### Can I group multiple columns together in a columnstore table?

In OceanBase Database V4.3.0, you can either store each column separately or store all columns together as a row. You cannot select a subset of columns to store together.

### Does OceanBase Database support updates on columnar tables? What is the structure of data in the MemTable?

In OceanBase Database, insert, update, and delete operations are performed in memory. The data is stored in the MemTable in row format. The baseline data is read-only and stored in columnar format on disk. When a column is queried, the system combines the row data in the MemTable with the column data on disk in real time and returns the result to the user. This means that **OceanBase Database supports strong-consistency reads on columnar tables without data latency**. The data written to the MemTable can be dumped, and the dumped data is still stored in row format. After a major compaction, the row data and baseline columnar data are combined to form new baseline columnar data.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>For columnar tables, if there are a large number of update operations and no major compaction is performed in a timely manner, query performance will be affected. Therefore, it is recommended to perform a major compaction after a batch import to achieve optimal query performance. A small number of update operations will not significantly affect performance. </p>
</main>

### What are the characteristics of queries on columnar tables?

In a redundant rowstore table, columnar table queries default to range scans in columnar mode, while point gets revert to rowstore mode.

In a pure columnar table, all queries use columnar mode.

### Can an index be created on a specific column of a columnar table?

Yes. OceanBase Database does not differentiate between creating an index on a columnar table or a rowstore table. The index structures are the same.

Creating an index on one or more columns of a columnar table allows for the construction of a covering index, which can improve point query performance, or for sorting specific columns to enhance sorting performance.

### What is the maximum number of columns supported?

Currently, a columnar table can have up to 4096 columns.

### What are the considerations when using columnar tables?

**First**: After a batch import, it is recommended to perform a major compaction to optimize read performance. After importing data, trigger a major compaction within the tenant to ensure all data is in the baseline. Execute `alter system major freeze;` within the tenant, and then check the status by running `select STATUS from CDB_OB_MAJOR_COMPACTION where TENANT_ID = tenant_id;` in the system tenant. When the `STATUS` changes to `IDLE`, the major compaction is complete.

**Second**: After a major compaction, it is recommended to collect statistics. To collect statistics, follow these steps:

- In the business tenant, collect statistics for all tables using 16 threads in parallel:

  ```sql
  CALL DBMS_STATS.GATHER_SCHEMA_STATS ('db', granularity=>'auto', degree=>16);
  ```

- Monitor the statistics collection progress using the `GV$OB_OPT_STAT_GATHER_MONITOR` view.

**Third**: You can use full direct load to batch import data. Tables imported using this method do not require a major compaction to achieve optimal columnar scan performance. Tools that support full direct load include obloader and the native LOAD DATA command.

**Fourth**: In non-large wide table scenarios, using rowstore tables can achieve performance comparable to columnar tables. This is due to the row-column hybrid storage architecture at the microblock level in OceanBase Database's rowstore version (this is normal).

**Fifth**: For tables with large amounts of data, the performance of cold runs and hot runs differs.

**Sixth**: The optimizer automatically selects whether to use rowstore or columnar mode for accessing column data based on cost estimation.

**Seventh**: The compaction speed of columnar tables slows down.

### Are there any special considerations for log synchronization, backup, and restore for columnar tables?

No. They are the same as for rowstore tables. The synchronized logs are in rowstore mode.

## FAQ about data import and migration

### What is a bypass import and how do I perform a bypass import?

A bypass import is a method of data import that can accelerate data import and data query. For large tables, we recommend that you use a bypass import. Currently, the `load data` command and the `insert into select` statement support bypass imports. For more information about how to perform a bypass import, see [Overview of bypass import](300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

## FAQ on performance tuning

### What are other methods to further improve AP Query performance?

Based on some practical experience, first, if there are no special sorting requirements, do not use the utf8mb4 character set when creating tables, but instead use binary, which can improve performance. For example:

```sql
create table t5(c1 TINYINT, c2 VARVHAR(50)) CHARSET=binary with column group (each column);
```

Secondly, if the user or business can accept it, when creating tables for the MySQL tenant, specify the utf8mb4_bin character set by adding: `CHARSET = utf8mb4 collate=utf8mb4_bin`

Additionally, increasing the IOPS of the UNIT can accelerate the direct import.

### What are the characteristics of the optimizer for columnar storage?

Compared to the optimizer for row-based storage, the optimizer for columnar storage has the following features:

- The ability for the optimizer to autonomously choose between row-based and columnar storage.
- The ability to control the selection of row-based or columnar storage using hints at the table level.
- Adapted plan cost calculation for columnar storage.
- Added late materialization optimization for columnar storage.
