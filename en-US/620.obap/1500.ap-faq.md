# AP FAQ

## Columnar FAQ

### What is columnar storage?

Columnar storage in OceanBase Database stores static data on disk as columnar data and modifies data in memory as row-based data. This approach balances scanning performance and transaction processing capabilities.

For analytical queries, columnar storage significantly improves query performance. It is also an essential feature for OceanBase Database's HTAP capabilities. In classic AP databases, columnar data is typically static and difficult to update in place. However, in OceanBase Database's LSM Tree architecture, SSTables are static and naturally suitable for columnar storage. MemTables, on the other hand, are dynamic and still row-based, which does not affect transaction processing. This allows us to balance the performance of TP and AP queries.

### What is a columnar index?

OceanBase Database also supports the concept of a columnar index, which is different from building an index on a columnar table. A columnar index refers to an index table that is stored in columnar format.

For example, if we have a row-based table `t6` and want to sum the values in column `c3` for optimal performance, we can create a columnar index on `c3`:

```sql
create table t6(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
);

create /*+ parallel(2) */ index idx1 on t6(c3) with column group (each column);
```

In addition to this, we support other index creation methods:

* Redundant row-based data in the index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(all columns, each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(all columns, each column);
  ```

* Pure columnar data in the index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(each column);
  ```

The purpose of using the `STORING` clause in database indexes is to store additional non-indexed column data within the index. This can optimize query performance by avoiding table lookups and reducing the cost of index sorting. When a query only needs to access columns stored in the index and does not require a table lookup, it can significantly enhance query efficiency.

### What is the difference between a columnar table and a columnar replica?

A columnar table refers to a table where both the leader and follower partitions are stored in columnar format, and OLAP queries can be read with strong consistency. A columnar replica, on the other hand, is a type of replica that is stored in columnar format, but only the leader replica of a read-only partition is columnar. OLAP queries on a columnar replica can only be read with weak consistency.

### Common questions about columnar tables and columnar replicas

#### What is the difference between a columnar table and a columnar replica? What is their relationship?

**They are not the same concept.**

* **Columnar table**: Refers to the **storage format** of a table. In a tenant's F (Full) or R (Read) replica, baseline data is stored in columnar format (with optional row-based, columnar, or hybrid row-column storage modes). In a columnar table, both the leader and follower partitions are stored in columnar format, and OLAP queries can be read with strong consistency.
* **Columnar replica (C replica)**: Refers to a **type of replica**. It is deployed in an independent zone. In this zone, baseline data of user tables is stored in columnar format. C replicas do not participate in Paxos elections or voting. Instead, they asynchronously follow the logs of F/R replicas and locally replay them. In versions V4.5.0 and earlier, C replicas only provide read-only and weak-consistency read services. In version V4.6.0, C replicas support strong-consistency reads.

**Relationship**: They are independent. You can create a columnar table in a tenant that does not have a columnar replica (the table exists only in F/R replicas in columnar format). Conversely, in a tenant with a C replica, the leader and follower partitions in F/R replicas are stored in row-based format, while the same table in the C replica is stored in columnar format for weak-consistency reads.

#### Do I need a columnar replica to create a columnar table? Can I create a columnar table in a Full replica?

**You do not need a columnar replica to create a columnar table in a Full (F) replica.**

A columnar table is a table-level storage format configuration. You can specify it when creating a table using the `WITH COLUMN GROUP` clause or set it at the tenant level using the `default_table_store_format` parameter. As long as the tenant has F/R replicas, you can create a columnar table or a hybrid row-column table in any locality (e.g., `F@zone1, F@zone2`). The data will be stored in columnar (or hybrid) format in the F/R replicas. Columnar replicas (C replicas) are optional and can be deployed independently for TP/AP physical isolation and weak-consistency reads. They are not required to create a columnar table.

#### Can I directly create a pure columnar table in OceanBase Database? Do I need to base it on a row-based table?

**Yes, you can directly create a pure columnar table without basing it on a row-based table.**

Specify `WITH COLUMN GROUP (each column)` when creating a table to get a pure columnar table (only columnar baseline, no row-based baseline). For example:

```sql
CREATE TABLE t (pk INT PRIMARY KEY, c1 INT, c2 INT) WITH COLUMN GROUP (each column);
```

In a partitioned table, the primary key column is redundantly stored in row-based format for point queries, but the table is still considered a pure columnar table. You can also create a row-based table first and then convert it to a columnar table using `ALTER TABLE ... ADD COLUMN GROUP (each column);` and other DDL operations. For more information, see "How to create a columnar table?" in this topic.

#### How is data consistency ensured between columnar and row-based storage? What is the latency if it is asynchronous?

**It depends on the scenario:**

* **Columnar table (in F/R replicas)**: Baseline data is stored in columnar format, and incremental data is stored in row-based format (MemTable/dump). During reads, the system real-time fuses row-based incremental data with columnar baseline data, providing **strong consistency** with no additional latency.
* **Columnar replica (C replica)**: C replicas do not participate in Paxos. They asynchronously follow the logs of F/R replicas and locally replay them, providing **weak-consistency reads**. The specific latency values are not provided in the documentation. The actual delay depends on network conditions, load, and the progress of log catching. As an observer, C replicas "real-time catch up" with logs, generally achieving latency in seconds or sub-seconds. The actual performance depends on the environment. For strong-consistency analysis, use columnar tables or hybrid row-column tables in F/R replicas instead of reading from C replicas.

#### How can I separate TP and AP traffic? What disaster recovery options are available if AP fails?

**Traffic separation:**

* **Without a C replica**: TP and AP traffic share the same F/R replicas and ODP. The optimizer automatically selects the row-based or columnar path. Physical isolation is not possible.
* **With a C replica**: TP traffic uses the primary ODP and accesses F/R replicas for strong-consistency reads/writes. AP traffic uses an **independent ODP**, configured for weak-consistency reads (e.g., `obproxy_read_consistency = 1`), and routes requests only to the zone where the C replica is located (e.g., `proxy_primary_zone_name`, `route_target_replica_type = 'ColumnStore'`, `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`). This achieves physical isolation between TP and AP traffic. For more information, see [Deploy and use columnar replicas](150.obap-deploy/150.uesing-columnstore-replica.md).

**Disaster recovery and limitations for AP (C replica) side:**

* C replicas **cannot** become leaders. **Physical recovery is not supported for C replicas** (if a tenant's locality includes a C replica, recovery will fail). If the primary database does not have a C replica, it is not recommended to deploy one on the standby database.
* If the zone or ODP where the C replica is located fails, AP queries can **fallback to F/R replicas**: Change the AP client to connect to the primary ODP or adjust the routing to direct analysis requests to execute with strong consistency on F/R replicas (which will share resources with TP traffic).
* Starting from V4.3.5 BP1, you can deploy **multiple C replicas** (up to 3 recommended) across multiple zones. By routing AP queries to different C replicas through the ODP, you can achieve redundancy and high availability for AP reads.

### How do I create a columnstore table?

First, create a hybrid row-columnstore table.

- Non-partitioned table:

```sql
create table t1(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (all columns, each column);
```

- Partitioned table:

```sql
create table t2(
   pk int,
   c1 int,
   c2 int,
   primary key (pk)
)
partition by hash(pk) partitions 4
with column group (all columns, each column);
```

When creating a hybrid row-columnstore table, you must use the `with column group (all columns, each column)` syntax. The syntax means the following:

- `all columns`: All columns are grouped together as a wide column and stored row by row. This is consistent with the original rowstore.
- `each column`: Each column is stored in columnar format.

When `all columns` and `each column` are used together, it means that after creating a columnstore table, the data is redundantly stored in both rowstore and columnstore formats. Each replica stores two copies of the baseline data. However, it is worth noting that, regardless of the number of baseline data copies, the incremental data in the memtable and the dump is shared.

Next, create a pure columnstore table.

- Non-partitioned table:

```sql
create table t3(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (each column);
```

- Partitioned table:

```sql
create table t4(
   pk1 int,
   pk2 int,
   c1 int,
   c2 int,
   primary key (pk1, pk2)
)
partition by hash(pk1) partitions 4
with column group (each column);
```

For the t4 table, a columnstore is created for each of the columns pk1, pk2, c1, and c2. Additionally, a rowstore is created for the combination of (pk1, pk2).

### How do I make a tenant's default table type columnstore?

This is simple. You just need to set a tenant-level parameter:

```sql
alter system set default_table_store_format = "column";
```

You can also set the default table type to rowstore or both rowstore and columnstore:

```sql
alter system set default_table_store_format = "row";   //rowstore
alter system set default_table_store_format = "compound"; //both rowstore and columnstore
```

### What are the recommended configurations for a columnstore?

```sql
# Set the collation to utf8mb4_bin to improve performance by 15%
set global collation_connection = utf8mb4_bin;
set global collation_server = utf8mb4_bin;

set global ob_query_timeout= 10000000000;
set global ob_trx_timeout= 100000000000;
set global ob_sql_work_area_percentage=30;
set global max_allowed_packet=67108864;
# Recommended value is 10 times the number of CPU cores
set global parallel_servers_target=1000;
set global parallel_degree_policy = auto;
set global parallel_min_scan_time_threshold = 10;
# Limit the maximum degree of parallelism when parallel_degree_policy is set to auto.
# A high degree of parallelism may cause performance issues. The recommended value is cpu_count * 2.
set global parallel_degree_limit = 0;

alter system set compaction_low_thread_score = cpu_count;
alter system set compaction_mid_thread_score = cpu_count;
alter system set default_table_store_format = "column";
```

### Can I add or drop columns in a columnstore table?

* Yes. You can add or drop columns.

* You can increase or decrease the maximum length of a VARCHAR column.

* A columnstore supports various offline DDL operations, just like a rowstore.

For more information about modifying a columnstore table, see [Convert a table from rowstore to columnstore (MySQL mode)](../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/600.change-table-of-mysql-mode.md) and [Convert a table from rowstore to columnstore (Oracle mode)](../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/100.manage-tables-of-oracle-mode/600.change-table-of-oracle-mode.md).

### What are the characteristics of queries on a columnstore table?

* In a hybrid row-columnstore table, range scans default to using the columnstore, while point get queries fall back to the rowstore.

* In a pure columnstore table, all queries use the columnstore.

### Does a columnstore support transactions, and are there any size limitations?

Yes, a columnstore supports transactions, and there are no size limitations on transactions. It provides high consistency.

### Are there any special considerations for log synchronization, backup, and restore in a columnstore table?

No, a columnstore table behaves the same as a rowstore table. The synchronized logs are in rowstore format.

### Can I convert a rowstore table to a columnstore table using DDL operations?

Yes. You can add a columnstore and drop a rowstore. Here is an example:

```sql
create table t1( pk1 int, c2 int, primary key (pk1));

alter table t1 add column group(all columns, each column);
alter table t1 drop column group(all columns, each column);

alter table t1 add column group(each column);
alter table t1 drop column group(each column);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After you execute <code>alter table t1 drop column group(all columns, each column);</code>, you do not need to worry about any group to store the data. All columns will be placed in a default group named <code>DEFAUTL COLUMN GROUP</code>.</p>
</main>

### Can I group multiple columns together in a columnstore?

In OceanBase Database V4.3.0, you can either store each column separately or store all columns together as a rowstore. You cannot select a subset of columns to store together.

### Does OceanBase Database support updates on columnar tables? What is the structure of the MemTable?

In OceanBase Database, add, delete, and modify operations are performed in memory. The data is stored in the MemTable in row-based format. The baseline data is read-only and stored in columnar format on disk. When reading data from a column, the system combines the row-based data in the MemTable with the columnar data on disk in real time and returns the result to the user. This means that **OceanBase Database supports strong-consistency reads on columnar tables, with no data latency**. Data written to the MemTable can be dumped, and the dumped data is still stored in row-based format. After compaction, the row-based data and baseline columnar data are combined to form new baseline columnar data.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>For columnar tables, if there are a large number of update operations and no timely compaction, query performance will be affected. Therefore, it is recommended to initiate a compaction after bulk data import to achieve optimal query performance. However, a small number of update operations will have minimal impact on performance.</p>
</main>

### What are the characteristics of queries on columnar tables?

In a redundant rowstore table, columnar table queries default to range scans in columnar mode, while point get operations fall back to rowstore mode.

In a pure columnar table, all queries are performed in columnar mode.

### Can an index be created on a specific column of a columnar table?

Yes. OceanBase Database does not differentiate between creating an index on a columnar table or a rowstore table. The index structure is the same in both cases.

Creating an index on one or more columns of a columnar table allows for the construction of a covering index, which can enhance point query performance, or for sorting specific columns to improve sorting performance.

### What is the maximum number of columns supported?

Currently, a columnar table can support up to 4096 columns.

### What are the considerations when using columnar tables?

**First**: After bulk data import, it is recommended to perform a compaction to optimize read performance. After data import, trigger a compaction within the tenant to ensure all data is baseline. Execute `alter system major freeze;` within the tenant, then check the compaction status in the system tenant using `select STATUS from CDB_OB_MAJOR_COMPACTION where TENANT_ID = tenant_id;`. When `STATUS` changes to `IDLE`, the compaction is complete.

**Second**: After compaction, it is recommended to collect statistics. The method for collecting statistics is as follows:

- In the business tenant, collect statistics for all tables using 16 concurrent threads:

  ```sql
  CALL DBMS_STATS.GATHER_SCHEMA_STATS ('db', granularity=>'auto', degree=>16);
  ```

- Monitor the statistics collection progress using the `GV$OB_OPT_STAT_GATHER_MONITOR` view.

**Third**: You can use full bypass import to batch import data. Tables imported using this method do not require compaction to achieve optimal columnar scan performance. Tools that support full bypass import include obloader and the native LOAD DATA command.

**Fourth**: In non-large wide table scenarios, using rowstore instead of columnar tables may still achieve performance comparable to columnar tables. This is due to the microblock-level row-column hybrid storage architecture in OceanBase Database's rowstore version (this is not surprising).

**Fifth**: For tables with large amounts of data, the performance of cold and hot runs differs.

**Sixth**: The optimizer automatically selects whether to use rowstore or columnar access based on cost estimation.

**Seventh**: The compaction speed of columnar tables will slow down.

### Are there any special considerations for log synchronization, backup, and restore in columnar tables?

No, they are the same as for rowstore tables. Synchronized logs are in rowstore format.

## Performance tuning FAQ

### What other methods can further improve AP Query performance?

Based on some practical experience, first, if there are no special sorting requirements, do not use the utf8mb4 character set when creating a table, but instead use binary. This can improve performance. For example:

```sql
create table t5(c1 TINYINT, c2 VARVHAR(50)) CHARSET=binary with column group (each column);
```

Second, if users or businesses can accept it, specify the utf8mb4_bin character set when creating tables in MySQL tenants, and include: `CHARSET = utf8mb4 collate=utf8mb4_bin`

Additionally, increasing the IOPS of the UNIT can speed up direct load.

### What are the characteristics of the optimizer for columnar storage?

Compared to the optimizer for row-based storage, the optimizer for columnar storage has the following features:

- The ability for the optimizer to autonomously choose between row and columnar storage.
- The ability to control the choice between row and columnar storage using hints (at the table level).
- Adapted cost calculation for columnar storage plans.
- Added late materialization optimization for columnar storage.
