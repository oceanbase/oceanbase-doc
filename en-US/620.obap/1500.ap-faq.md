# AP FAQ

## Columnar FAQ

### What is columnar storage?

Columnar storage in OceanBase Database is a data storage format that stores static data on disk in a columnar format and modifies data in memory in a row format. This format balances scanning performance and transaction processing capabilities.

For analytical queries, columnar storage can significantly improve query performance. It is an essential feature for OceanBase Database to achieve HTAP capabilities. In traditional AP databases, columnar data is typically static and difficult to update in place. However, in OceanBase Database's LSM tree architecture, SSTables are static and naturally suitable for columnar storage. MemTables are dynamic and still row-based, which does not affect transaction processing. This allows OceanBase Database to balance the performance of TP and AP queries to some extent.

### What is a columnar index?

OceanBase Database also supports the concept of a columnar index, which is different from "building an index on a columnar table." A columnar index refers to an index table that is stored in a columnar format.

For example, if we have a row-based table `t6` and want to sum the values in column `c3` with the best performance, we can create a columnar index on `c3`:

```sql
create table t6(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
);

create /*+ parallel(2) */ index idx1 on t6(c3) with column group (each column);
```

In addition to this, we also support other index creation methods:

* Redundant row-based data in the index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(all columns, each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(all columns, each column);
  ```

* Pure columnar data in the index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(each column);
  ```

The purpose of using the `STORING` clause in database indexes is to store additional non-index column data in the index. This can provide performance optimization for specific queries, avoiding the need to access the base table and reducing the cost of index sorting. When a query only needs to access the columns stored in the index and does not require accessing the original rows, the query efficiency can be significantly improved.

### What is the difference between a columnar table and a columnar replica?

A columnar table refers to a table where both the leader and follower partitions have a columnar schema, and OLAP queries can be strongly consistent reads. On the other hand, a columnar replica is a type of replica that is deployed in an independent zone. In this zone, the baseline data of user tables is stored in a columnar format. Columnar replicas do not participate in Paxos elections and voting, and instead asynchronously follow the logs of F/R replicas and locally replay them. In versions prior to V4.5.0, columnar replicas only provided read-only and weakly consistent read services. Starting from V4.6.0, columnar replicas support strongly consistent reads.

### Common questions about columnar tables and columnar replicas

#### What is the difference between a columnar table and a columnar replica? What is their relationship?

**They are not the same concept.**

* **Columnar table**: Refers to the **storage format** of a table. In a tenant's F (Full) or R (Read) replicas, the baseline data of the table is stored in a columnar format (with optional row-based, columnar, or hybrid row-column storage modes). In a columnar table, both the leader and follower partitions are in a columnar format, and OLAP queries can be strongly consistent reads.
* **Columnar replica (C replica)**: Refers to a **replica type** deployed in an independent zone. In this zone, the baseline data of user tables is stored in a columnar format. C replicas do not participate in Paxos elections and voting, and instead asynchronously follow the logs of F/R replicas and locally replay them. In versions prior to V4.5.0, C replicas only provided read-only and weakly consistent read services. Starting from V4.6.0, C replicas support strongly consistent reads.

**Relationship**: They are independent. You can create a columnar table in a tenant that does not have any C replicas (the table exists only in the F/R replicas in a columnar format). Conversely, in a tenant with C replicas, the F/R replicas store the table in a row-based format, while the C replica stores the same table in a columnar format for weakly consistent reads.

#### Is it necessary to have a columnar replica to create a **columnar table**? Can a columnar table be created on a Full replica?

**No, a columnar table can be created on a Full (F) replica without the need for a columnar replica.**

The storage format of a columnar table is specified at the table level using the `WITH COLUMN GROUP` clause during table creation or through the tenant-level configuration parameter `default_table_store_format`. As long as the tenant has F/R replicas, you can create a columnar table or a hybrid row-column table in any locality (e.g., `F@zone1, F@zone2`). The data will be stored in a columnar format (or hybrid row-column format) in the F/R replicas. Columnar replicas (C replicas) are optional and can be deployed independently for physical isolation and weakly consistent reads, and are not dependent on the ability to create columnar tables.

#### Can I directly create a **pure columnar table** in OceanBase Database? Or must it be based on a row-based table?

**Yes, you can directly create a pure columnar table without needing a row-based table.**

Specify `WITH COLUMN GROUP (each column)` during table creation to get a pure columnar table (only columnar baseline, no row-based baseline). For example:

```sql
CREATE TABLE t (pk INT PRIMARY KEY, c1 INT, c2 INT) WITH COLUMN GROUP (each column);
```

In partitioned tables, the primary key column will be redundantly stored in a row-based format for point queries, but the table is still considered a pure columnar table. You can also create a row-based table first and then convert it to a columnar table using `ALTER TABLE ... ADD COLUMN GROUP (each column);` and other DDL statements. For more information, see "How to create a columnar table?" in this topic.

#### How is data consistency ensured between columnar and row-based storage? What is the latency if it is asynchronous?

**There are two scenarios:**

* **Columnar table (on F/R replicas)**: The baseline data is stored in a columnar format, and incremental data is stored in a row-based format (MemTable/dump). During reads, the row-based incremental data and columnar baseline data are real-time fused, providing **strong consistency** with no additional latency.
* **Columnar replica (C replica)**: C replicas do not participate in Paxos and instead asynchronously follow the logs of F/R replicas and locally replay them. They provide **weakly consistent reads**. The document does not specify exact latency values, as the actual delay depends on network conditions, load, and the progress of log catching. C replicas "real-time follow" logs as observers, generally achieving latency in the range of seconds or sub-seconds, depending on the actual environment. For strongly consistent analysis, use columnar tables or hybrid row-column tables on F/R replicas instead of reading from C replicas.

#### How can I separate TP and AP traffic? What disaster recovery options are available if an AP fails?

**Traffic separation:**

* **Without C replicas**: TP and AP traffic share the same F/R replicas and ODP. The optimizer automatically selects the row-based or columnar path based on the query. Physical isolation is not possible.
* **With C replicas**: TP traffic uses the primary ODP and accesses F/R replicas (strong reads/writes). AP traffic uses an **independent ODP**, configured for weak reads (e.g., `obproxy_read_consistency = 1`), and is routed only to the zone containing the C replica (e.g., `proxy_primary_zone_name`, `route_target_replica_type = 'ColumnStore'`, `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`, etc.), achieving physical isolation between TP and AP traffic. For more information, see [Use columnar replicas](../600.manage/300.replica-management/150.the-use-of-columnstore-replica.md).

**Disaster recovery and limitations for AP (C replica) side:**

* C replicas **cannot** become leaders; **physical recovery is not supported** for C replicas (if a tenant's locality includes a C replica, recovery will fail). If the primary database does not have a C replica, it is not recommended to deploy one on the standby database.
* If the zone or ODP containing the C replica fails, AP queries can **fallback to F/R replicas**: Change the AP client to connect to the primary ODP or adjust the routing, so that analytical queries execute with strong reads on the F/R replicas (which will share resources with TP queries).
* Starting from V4.3.5 BP1, you can deploy **multiple C replicas** (up to 3 recommended) across multiple zones. You can route AP queries to different C replicas using an ODP, achieving redundancy and high availability for AP reads.

### How to create a columnstore table?

First, create a hybrid row-columnstore table.

- Non-partitioned table:

```sql
create table t1(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (all columns, each column);
```

- Partitioned table:

```sql
create table t2(
   pk int,
   c1 int,
   c2 int,
   primary key (pk)
)
partition by hash(pk) partitions 4
with column group (all columns, each column);
```

When creating a hybrid row-columnstore table, the `with column group (all columns, each column)` syntax is always used. This syntax has the following meanings:

- `all columns`: All columns are grouped together into a single wide column and stored row by row. This is essentially the same as the original rowstore.
- `each column`: Each column is stored separately in columnar format.

When both `all columns` and `each column` are specified, it means that a columnstore table is created by default, and the data is redundantly stored in both rowstore and columnstore formats. Each replica stores two copies of the baseline data. However, it's worth noting that regardless of the number of baseline data copies, the incremental data in the memtable and the dump is shared.

Next, create a pure columnstore table.

- Non-partitioned table:

```sql
create table t3(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (each column);
```

- Partitioned table:

```sql
create table t4(
   pk1 int,
   pk2 int,
   c1 int,
   c2 int,
   primary key (pk1, pk2)
)
partition by hash(pk1) partitions 4
with column group (each column);
```

For the t4 table, a columnstore is created for each of the columns pk1, pk2, c1, and c2, and a rowstore is created for the combination of (pk1, pk2).

### How to make the tables created by a tenant default to columnstore tables?

This is simple. You just need to set a tenant-level parameter:

```sql
alter system set default_table_store_format = "column";
```

You can also set the default table creation format to rowstore or to both rowstore and columnstore:

```sql
alter system set default_table_store_format = "row";   // Rowstore
alter system set default_table_store_format = "compound"; // Both rowstore and columnstore
```

### What are the recommended configurations for columnstore?

```sql
# Set the collation to utf8mb4_bin, which can improve performance by 15%.
set global collation_connection = utf8mb4_bin;
set global collation_server = utf8mb4_bin;

set global ob_query_timeout= 10000000000;
set global ob_trx_timeout= 100000000000;
set global ob_sql_work_area_percentage=30;
set global max_allowed_packet=67108864;
# It is recommended to set this to 10 times the number of CPU cores.
set global parallel_servers_target=1000;
set global parallel_degree_policy = auto;
set global parallel_min_scan_time_threshold = 10;
# Limit the maximum degree of parallelism (DOP) when parallel_degree_policy is set to auto.
# A high DOP may cause performance issues. It is recommended to set this to cpu_count * 2.
set global parallel_degree_limit = 0;

alter system set compaction_low_thread_score = cpu_count;
alter system set compaction_mid_thread_score = cpu_count;
alter system set default_table_store_format = "column";
```

### How to determine whether a query is executed in columnstore mode?

create table t5(
   c1 TINYINT,
   c2 SMALLINT,

### Can columns be added or dropped from a columnstore table?

* Yes, you can add or drop columns.

* You can increase or decrease the maximum length of a VARCHAR column.

* Columnstore tables support various offline DDL operations, just like rowstore tables.

For more information about modifying columnstore tables, see [Convert a table from rowstore to columnstore (MySQL mode)](../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/600.change-table-of-mysql-mode.md) and [Convert a table from rowstore to columnstore (Oracle mode)](../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/100.manage-tables-of-oracle-mode/600.change-table-of-oracle-mode.md).

### What are the characteristics of queries on columnstore tables?

* In a hybrid row-columnstore table, range scans are executed in columnstore mode by default, while point get queries fall back to rowstore mode.

* In a pure columnstore table, all queries are executed in columnstore mode.

### Does columnstore support transactions, and what are the limitations on transaction size?

Yes, columnstore supports transactions, and there are no limitations on transaction size. It ensures high consistency.

### Are there any special considerations for log synchronization, backup, and restore in columnstore tables?

No, there are no special considerations. The log synchronization, backup, and restore processes are the same as those for rowstore tables. The synchronized logs are in rowstore mode.

### Can a rowstore table be converted to a columnstore table using DDL operations?

Yes. You can convert a rowstore table to a columnstore table by adding columnstore groups and dropping rowstore groups. Here is an example:

```sql
create table t1( pk1 int, c2 int, primary key (pk1));

alter table t1 add column group(all columns, each column);
alter table t1 drop column group(all columns, each column);

alter table t1 add column group(each column);
alter table t1 drop column group(each column);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After you execute <code>alter table t1 drop column group(all columns, each column);</code>, you do not need to worry about any column groups to store the data. All columns are automatically placed into a default column group named <code>DEFAUTL COLUMN GROUP</code>. </p>
</main>

### Can multiple columns be stored together in a columnstore table?

In OceanBase Database V4.3.0, you can either store each column separately or store all columns together as a rowstore table. You cannot selectively store a subset of columns together.

### Does OceanBase Database support updates on columnar tables? What is the structure of data stored in MemTable?

In OceanBase Database, all DML operations are performed in memory. Data is stored in MemTable in row-based format. The baseline data is read-only and stored in columnar format on disk. When a column is queried, the system combines the row-based data in MemTable with the columnar data on disk in real time and returns the result to the user. This means that **OceanBase Database supports strong-consistency reads on columnar tables without data latency**. Data written to MemTable can be dumped, and the dumped data is still stored in row-based format. After compaction, the row-based data and baseline columnar data are combined to form new baseline columnar data.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>For columnar tables, if there are a large number of update operations and no timely compaction, query performance will be affected. Therefore, we recommend that you initiate a compaction after you batch import data to achieve optimal query performance. A small number of update operations will not significantly impact performance.</p>
</main>

### What are the characteristics of queries on columnar tables?

In a redundant rowstore table, queries on columnar tables default to range scans in columnar mode, while point get operations fall back to rowstore mode.

In a pure columnar table, all queries use columnar mode.

### Can I create an index on a specific column of a columnar table?

Yes. OceanBase Database does not differentiate between creating an index on a columnar table or a rowstore table. The created index structure is the same.

Creating an index on one or more columns of a columnar table allows you to construct a covering index to improve point query performance or sort specific columns to enhance sorting performance.

### What is the maximum number of columns supported?

Currently, a columnar table can support up to 4,096 columns.

### What are the considerations for using columnar tables?

**First**: After you batch import data, we recommend that you perform a compaction to optimize read performance. After you import data, trigger a compaction in the tenant to ensure that all data is moved to the baseline. Execute `alter system major freeze;` in the tenant and then execute `select STATUS from CDB_OB_MAJOR_COMPACTION where TENANT_ID = tenant ID;` in the sys tenant to check whether the compaction is completed. When the `STATUS` field changes to `IDLE`, the compaction is completed.

**Second**: After a compaction, we recommend that you collect statistics. You can collect statistics in the following ways:

- In the business tenant, collect statistics for all tables in one click and start 16 threads for concurrent collection:

  ```sql
  CALL DBMS_STATS.GATHER_SCHEMA_STATS ('db', granularity=>'auto', degree=>16);
  ```

- You can monitor the statistics collection progress by querying the `GV$OB_OPT_STAT_GATHER_MONITOR` view.

**Third**: You can use full direct load to batch import data. Tables that use this method do not need to be compacted to achieve optimal columnar scan performance. Tools that support full direct load include obloader and the native LOAD DATA command.

**Fourth**: For non-large wide tables, using rowstore tables may also achieve performance comparable to columnar tables. This is due to the row-column hybrid storage architecture at the microblock level in the rowstore version of OceanBase Database (do not be surprised if you encounter this situation).

**Fifth**: For tables with a large amount of data, the performance of cold runs and hot runs may differ.

**Sixth**: The optimizer automatically selects whether to access columnar data in rowstore or columnar mode based on cost estimation.

**Seventh**: The compaction speed of columnar tables will be slower.

### Are there any special considerations for log synchronization, backup, and restore of columnar tables?

No. The log synchronization, backup, and restore of columnar tables are the same as those of rowstore tables. The synchronized logs are in rowstore mode.

## FAQ on performance tuning

### What are other methods to further improve the performance of AP queries?

Based on some practical experience, if there are no special sorting requirements, you can use the binary character set instead of the utf8mb4 character set when you create a table. This can improve the performance. For example:

```sql
create table t5(c1 TINYINT, c2 VARVHAR(50)) CHARSET=binary with column group (each column);
```

If users or businesses can accept it, you can specify the utf8mb4_bin character set when you create a table for a MySQL tenant. You can add the `CHARSET = utf8mb4 collate=utf8mb4_bin` clause.

In addition, you can improve the performance of direct load by increasing the IOPS of a unit.

### What are the features of the optimizer for columnar storage?

Compared with the optimizer for rowstore, the optimizer for columnar storage has the following features:

- The optimizer can automatically select rowstore or columnar storage.
- You can use hints to control the selection of rowstore or columnar storage at the table level.
- The optimizer supports cost calculation for columnar storage.
- The optimizer supports late materialization optimization for columnar storage.
