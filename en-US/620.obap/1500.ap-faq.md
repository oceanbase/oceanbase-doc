# AP FAQ

## Columnar FAQ

### What is columnar storage?

Columnar storage in OceanBase Database stores static data on disk as columnar data and modifies data in memory as row-based data. This approach balances scanning performance and transaction processing capabilities.

Columnar storage can significantly enhance query performance for analytical queries, and it is an essential feature of OceanBase Database for its HTAP capabilities. In traditional AP databases, columnar data is typically static and difficult to update in-place. However, the LSM tree architecture of OceanBase Database contains static SSTables that are well-suited for columnar implementations, while dynamic MemTables are still used for row storage and do not impact transaction processing. This design allows OceanBase Database to balance the performance of both transactional (TP) and analytical (AP) queries.

### What is a columnar index?

OceanBase Database supports the concept of columnstore index, which is different from building an index on a columnstore. A columnstore index means the index table uses the columnstore structure.

For example, you have a rowstore table `t6`. You want to perform a fast summation on the `c3` column of the table. In this case, you can create a columnstore index on the `c3` column of the table:

```sql
create table t6(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
);

create /*+ parallel(2) */ index idx1 on t6(c3) with column group (each column);
```

In addition to the index creation methods mentioned, we also support more index creation methods:

* Supports redundant rows in the index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(all columns, each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(all columns, each column);
  ```

* Index-organized tables are supported.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(each column);
  ```

The purpose of using the `STORING` clause in the index is to store additional non-indexed column data in the index itself. This can optimize query performance by avoiding the need to go back to the table and by reducing the cost of sorting. If a query only needs to access the columns stored in the index and does not require fetching the original row from the table, this approach significantly improves query efficiency.

### Frequently Asked Questions about columnstore tables and columnstore replicas

#### What is the difference between a columnar table and a columnar replica? How do they relate?

They describe **different dimensions** of the business:

* **ColumnStore tables**: refer to **table-level storage formats** (rowstore, pure columnar, row-column hybrid, etc.), determined by `WITH COLUMN GROUP` or the tenant-level `default_table_store_format`. Data is physically stored on the **F (full-featured) / R (read-only) replicas** of the tenant. On these replicas, the MemTable and dumps are organized by row, while the baseline can be organized either by column or by row-column redundancy. The read path will combine incremental and baseline data. When executing semantic-compliant paths on F/R replicas, **strong consistent reads** are **guaranteed** in line with the **replica roles** (related to transactions, isolation levels, etc.).

* **Column Store Replica (C-R) replica**: a **type of independent replication** of the user table. Typically, C-R replicas are in an independent zone. C-R replicas **do not participate in Paxos election or voting**. It **synchronizes with F/R replicas by asynchronously applying the log**. **Major compaction on the C-R replica uses columnar storage** to store user table data. A single logical table can be **row-store or hybrid row-column store on the F/R replica** and **columnar store on the C-R replica**, which allows for **resource isolation** between the AP and TP systems.

**Relationship**: The two are independent. A columnar table can be created **without** a C replica (data exists only in columnar or hybrid form in F/R). In a tenant with a C replica, you can also use the columnar form of the table on the C replica for read-only analysis, while the table is stored in the F/R. Columnar tables and C replicas can coexist based on architectural needs.

* **Read consistency**: The C replica lags behind the source log. **Before OceanBase Database V4.6.0**, analysis queries accessing the C replica through means such as the ODP would typically be scheduled for **weak read**. **V4.6.0 and later** support configuring the **strong read or weak read** setting per session on the C replica using the `ob_read_consistency` parameter. Whether to attempt columnar plans can be controlled by parameters like `ap_query_route_policy`.

#### Do I need a columnar replica to create a **columnstore table**? Can I create a columnstore table on a Full replica?

**You can create a columnar table in a Full (F) replica without using columnar replicas.**

A column store is a table-level storage format configuration, specified during table creation using `WITH COLUMN GROUP` or at the tenant level via the `default_table_store_format` option. As long as a tenant has F/R replicas, you can create column store or hybrid row-column store tables in any locality (e.g., `F@zone1, F@zone2`). Data will be stored in columnar (or row-column redundant) format on F/R replicas. Column replicas (C replicas) are an optional, standalone deployment option for physical or logical isolation of TP/AP workloads and read-only analytical traffic, independent of whether you can create column store tables.

#### Can OceanBase Database directly create a **pure columnstore table**? Or must it be created based on a rowstore table?

**It is supported to directly create a columnar table without requiring a row-based table as a base.**

Specify the `WITH COLUMN GROUP (each column)` clause when creating a table to obtain a pure columnar table. For example:

```sql
CREATE TABLE t (pk INT PRIMARY KEY, c1 INT, c2 INT) WITH COLUMN GROUP (each column);
```

In partitioned tables, primary key columns will be stored separately in-row for efficient point queries, but the overall table is still considered a pure columnar table. Alternatively, you can first create a rowstore table and then convert it to a columnar table using `ALTER TABLE ... ADD COLUMN GROUP (each column);`. For more information, see the section "How to create a columnar table?" in this topic.

#### How is data consistency ensured between columnar and row storage? What is the asynchronous delay?

**The following are two scenarios:**

* **Columnar tables (on F/R replicas)**: Base tables are stored in either columnar or hybrid layout, and incremental updates are stored in row-oriented format (MemTable/dump). When reading, the system integrates both the baseline and incremental data to ensure **strong consistency** under default F/R semantics, without additional cross-replica latency.
* **Columnar replica (C replica)**: A C replica does not participate in the Paxos consensus protocol. The C replica asynchronously catches up with and replays the logs of the follower leader (F/R) replica, causing a certain lag between the logs of the C replica and those of the log source. **Before V4.6.0**, read operations targeting C replicas are not consistent. **From V4.6.0**, you can configure C replicas to provide **strong consistency read operations**. Strong consistency read operations cause a delay compared with weakly consistent read operations. To ensure that analysis read operations are based on the same logs as TP operations and have no C replica lag, it is still recommended that you run analysis read operations on **columnar or hybrid columnar-row tables of F/R replicas**.

#### How to separate the traffic of the TP and AP? If an AP fails, will the service be affected?

**Traffic isolation: **

* **No C replicas**: TP and AP share the same set of F/R replicas and access points, and the optimizer automatically selects row-wise or column-wise storage paths; TP and AP do **not** have physical isolation at the cabinet or link level.
* **Replica of C type (OceanBase Database of a version earlier than V4.6.0):** The typical approach involves using a strong-read/strong-write replica for OLTP workloads and an independent ODP (OceanBase Data Proxy) for OLAP workloads. The ODP is configured to enable weak reads and routes requests to the C-type replica through settings such as `proxy_primary_zone_name`, `route_target_replica_type = 'ColumnStore'`, and `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`. This establishes separate links for OLTP and OLAP workloads to the C-type replica.
* **ODP independent of C replicas** (Option 1): In this case, ODP queries the database only when it cannot find a columnstore plan in the `ap_query_route_policy` option, and it cannot directly connect to OBServer nodes. The ODP must maintain a route table that includes routing entries for each C replica. * **ODP not independent of C replicas** (Option 2): In this case, you can directly connect ODP to OBServer nodes (or non-columnstore ODPs). You do not need to maintain a separate routing table for columnstore entries. The ODP automatically queries the database for columnstore plans through the `ap_query_route_policy` option.

**C Disaster Recovery and limitations for AP (C Replica):**

* C standby databases cannot be restored as leaders; physical restore of C standby databases is not supported (the restore operation fails if the tenant Locality contains a C standby database); and it is not recommended to deploy a C standby database for a standby instance if the primary instance does not have a C standby database deployed.
* If the zone or ODP where the C replicas are located fails, the AP queries can **fallback to FR replicas**: the AP client is changed to connect to the primary ODP or the routes are adjusted to enable strong reads on the FR replicas (which share resources with TP).
* Multiple C replicas (up to 3) can now be deployed, either across zones for high availability and redundancy, or within a single zone. ODP routing and Auto routing (as described in the following sections) help distribute AP read operations to reduce hotspots.  This feature was introduced in V4.3.5 BP1.

### How do I create a columnstore table?

First, create a hybrid table.

- Non-partitioned table:

```sql
create table t1(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (all columns, each column);
```

- Partitioned table:

```sql
create table t2(
   pk int,
   c1 int,
   c2 int,
   primary key (pk)
)
partition by hash(pk) partitions 4
with column group (all columns, each column);
```

When creating a hybrid table, the `with column group (all columns, each column)` syntax is always used. This syntax means the following:

- `all columns`: All columns are grouped together into a wide column and stored row by row. This is essentially the same as the original rowstore.
- `each column`: Each column is stored in a separate column format.

When both `all columns` and `each column` are used, it means that after creating a columnstore table, rowstore data is also stored redundantly. Each replica stores two copies of the baseline data. However, it's worth noting that regardless of how many copies of the baseline data there are, the incremental data in the memtable and the dump is still shared.

Next, create a pure columnstore table.

- Non-partitioned table:

```sql
create table t3(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (each column);
```

- Partitioned table:

```sql
create table t4(
   pk1 int,
   pk2 int,
   c1 int,
   c2 int,
   primary key (pk1, pk2)
)
partition by hash(pk1) partitions 4
with column group (each column);
```

For the t4 table, a columnstore is created for each of the columns pk1, pk2, c1, and c2, and a rowstore is created for the combination of (pk1, pk2).

### How do I make a tenant's default table type columnstore?

Set a tenant-level parameter:

```sql
alter system set default_table_store_format = "column";
```

Similarly, you can set the default table type to rowstore or to both rowstore and columnstore:

```sql
alter system set default_table_store_format = "row";   //rowstore
alter system set default_table_store_format = "compound"; //both rowstore and columnstore
```

### What are the recommended configurations for columnstore?

```sql
# Set collation to utf8mb4_bin to improve performance by 15%
set global collation_connection = utf8mb4_bin;
set global collation_server = utf8mb4_bin;

set global ob_query_timeout= 10000000000;
set global ob_trx_timeout= 100000000000;
set global ob_sql_work_area_percentage=30;
set global max_allowed_packet=67108864;
# Recommended value is 10 times the number of CPU cores
set global parallel_servers_target=1000;
set global parallel_degree_policy = auto;
set global parallel_min_scan_time_threshold = 10;
# Limit the maximum DOP when parallel_degree_policy is set to auto
# A high DOP may cause performance issues. The recommended value is cpu_count * 2
set global parallel_degree_limit = 0;

alter system set compaction_low_thread_score = cpu_count;
alter system set compaction_mid_thread_score = cpu_count;
alter system set default_table_store_format = "column";
```

  <h4>Note</h4>
  <p>In the above code, <code>cpu_count</code> represents the <code>min_cpu</code> specified when the tenant was created.</p>
</main>

### Can I add or drop columns in a columnstore table?

* Yes, you can add or drop columns.

* You can increase or decrease the length of a VARCHAR column.

* Columnstore supports various offline DDL operations, similar to rowstore tables.

For more information about modifying columnstore tables, see [Convert a table from rowstore to columnstore (MySQL mode)](../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/600.change-table-of-mysql-mode.md) and [Convert a table from rowstore to columnstore (Oracle mode)](../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/100.manage-tables-of-oracle-mode/600.change-table-of-oracle-mode.md).

### What are the characteristics of queries on columnstore tables?

* In a hybrid table, the default query execution plan for range scans uses columnstore, while point get queries fall back to rowstore.

* In a pure columnstore table, all queries use columnstore.

### Does columnstore support transactions, and are there any size limitations?

Yes, columnstore supports transactions, and there are no size limitations. It provides high consistency.

### Are there any special considerations for log synchronization, backup, and restore in columnstore tables?

No, columnstore tables behave the same as rowstore tables. Synchronization logs are in rowstore format.

### Can I convert a rowstore table to a columnstore table using DDL?

Yes. You can add columnstore and drop rowstore. Here are some examples:

```sql
create table t1( pk1 int, c2 int, primary key (pk1));

alter table t1 add column group(all columns, each column);
alter table t1 drop column group(all columns, each column);

alter table t1 add column group(each column);
alter table t1 drop column group(each column);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After executing <code>alter table t1 drop column group(all columns, each column);</code>, you don't need to worry about any group to hold the data. All columns will be moved to a default group called <code>DEFAUTL COLUMN GROUP</code>.</p>
</main>

### Can I group multiple columns together in columnstore?

In OceanBase Database V4.3.0, you can either store each column separately or store all columns as a rowstore. You cannot selectively group some columns together.

### Does OceanBase Database support updates on columnar tables? What is the structure of the MemTable?

In OceanBase Database, add, delete, and modify operations are performed in memory. The data is stored in the MemTable in row format. The baseline data is read-only and stored in columnar format on disk. When a column of data is read, the system combines the row data in the MemTable with the columnar data on disk in real time and returns the result to the user. This means that **OceanBase Database supports strong-consistency reads on columnar tables without data latency**. The data written to the MemTable can be dumped, and the dumped data is still stored in row format. After compaction, the row data and baseline columnar data are combined to form new baseline columnar data.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>For columnar tables, if there are a large number of update operations and no timely compaction, query performance will be affected. Therefore, it is recommended to perform a compaction after batch data import to achieve optimal query performance. However, a small number of update operations will not significantly impact performance.</p>
</main>

### What are the characteristics of queries on columnar tables?

In a redundant rowstore table, queries on columnar tables default to range scans in columnar mode, while point gets revert to rowstore mode.

In a pure columnar table, all queries are performed in columnar mode.

### Can an index be created on a specific column of a columnar table?

Yes. OceanBase Database does not differentiate between creating an index on a columnar table or a rowstore table. The index structure is the same in both cases.

Creating an index on one or more columns of a columnar table allows for the construction of a covering index, which can improve the performance of point queries, or enable sorting on specific columns to enhance sorting performance.

### What is the maximum number of columns supported?

Currently, a columnar table can support up to 4096 columns.

### What are the considerations when using columnar tables?

**First**: After batch data import, it is recommended to perform a compaction to optimize read performance. After importing data, trigger a compaction within the tenant to ensure all data is moved to the baseline. Execute `alter system major freeze;` within the tenant and then run `select STATUS from CDB_OB_MAJOR_COMPACTION where TENANT_ID = tenant_id;` in the system tenant to check if the compaction is complete. When the `STATUS` changes to `IDLE`, the compaction is complete.

**Second**: After compaction, it is recommended to collect statistics. To collect statistics:

- In the business tenant, collect statistics for all tables concurrently using 16 threads:

  ```sql
  CALL DBMS_STATS.GATHER_SCHEMA_STATS ('db', granularity=>'auto', degree=>16);
  ```

- Monitor the statistics collection progress using the `GV$OB_OPT_STAT_GATHER_MONITOR` view.

**Third**: You can use full direct load to batch import data. Tables imported using this method do not require a compaction to achieve optimal columnar scan performance. Tools that support full direct load include obloader and the native LOAD DATA command.

**Fourth**: In scenarios other than large wide tables, using columnar tables may not be necessary to achieve performance comparable to columnar tables. This is due to the row-column hybrid storage architecture at the microblock level in OceanBase Database's rowstore version (do not be surprised if you encounter this).

**Fifth**: For tables with large amounts of data, the performance of cold and hot runs differs.

**Sixth**: The optimizer automatically selects whether to access columnar data using rowstore or columnar mode based on cost estimation.

**Seventh**: The compaction speed of columnar tables will be slower.

### Are there any special considerations for log synchronization, backup, and restore for columnar tables?

No, they are the same as for rowstore tables. The synchronized logs are in rowstore mode.

Bypass import is a method for accelerating data import and query operations. It is recommended for importing data from large tables. Currently, the `load data` command and the `insert into select` statement support bypass import. For more information about how to use bypass import, see [Overview of bypass import](300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

## FAQ on performance optimization

### What are other ways to further improve the performance of AP queries?

According to some practical experience, if there are no special sorting requirements, do not use the utf8mb4 character set when creating a table, but instead use the binary character set. This can improve performance. For example:

```sql
create table t5(c1 TINYINT, c2 VARVHAR(50)) CHARSET=binary with column group (each column);
```

Secondly, if users or businesses can accept it, specify the utf8mb4_bin character set when creating tables in a MySQL tenant, and add the following clause: `CHARSET = utf8mb4 collate=utf8mb4_bin`

Additionally, increasing the IOPS of the unit can speed up direct load.

### What are the characteristics of the optimizer for columnar storage?

Compared to the optimizer for row-based storage, the optimizer for columnar storage has the following features:

- The optimizer can autonomously choose between row-based and columnar storage.
- The optimizer can control the selection of row-based or columnar storage using hints at the table level.
- The optimizer has adapted the cost calculation for columnar storage plans.
- The optimizer has added late materialization optimization for columnar storage.
