# AP FAQ

## Frequently asked questions about columnar storage

### What is a columnar store?

OceanBase columnar storage is a data storage method that stores disk static data in a columnar format and memory modified data in a rowar format. It balances scan performance and transaction processing capabilities.

Columnar storage significantly enhances query performance for analytical queries and is a crucial feature for OceanBase's HTAP capabilities. In traditional AP databases, columnar data is typically static and difficult to update in-place. However, OceanBase's LSM Tree architecture features static SSTables ideal for columnar storage while maintaining dynamic MemTables for row-based data. This hybrid design allows OceanBase to efficiently handle both TP and AP queries without compromising transactional integrity or performance.

### What is a column store index?

OceanBase Database also supports columnstore indexes, which are different from indexes on columnstore tables. In a columnstore index, the index table uses a columnar format.

For example, suppose that you have a rowstore table `t6`, and you want to sum up the `c3` column with the best performance. You can create a columnstore index for the `c3` column:

```sql
create table t6(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
);

create /*+ parallel(2) */ index idx1 on t6(c3) with column group (each column);
```

In addition, we support more types of index creation:

* Supports storing redundant rows in the index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(all columns, each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(all columns, each column);
  ```

* Support columnar storage in the index.

  ```sql
  create index idx1 on t1(c2) storing(c1) with column group(each column);
  alter table t1 add index idx1 (c2) storing(c1) with column group(each column);
  ```

The use of the `STORING` clause in database indexes aims to store additional, non-indexed column data within the index. This can lead to performance optimizations by avoiding the need to reference the base table and reducing the cost of index sorting. When queries only require accessing columns stored in the index and do not need to access the original rows from the base table, this approach significantly improves query efficiency.

### Common questions about columnar tables and columnar replicas

#### What is the difference between a column-oriented table and a column-oriented replica? How are they related?

They describe different dimensions:

* **ColumnStore tables**: This term refers to the **table-level storage format** (row-based, pure columnar, or row-column hybrid formats), determined by the use of `WITH COLUMN GROUP` or the tenant-level `default_table_store_format` parameter. Data is physically stored on the **F (Full) / R (Read-Only) replicas** of the tenant. On these replicas, MemTables and dumps remain organized by rows, while the baseline can be organized by columns or by a hybrid row-column format. Reads will combine increments with the baseline. When executing statements that conform to semantics, you can obtain **strong consistent reads** consistent with the role of the F/R replicas (affected by transactions, isolation levels, etc.) by default on F/R replicas.

* **Column-oriented replicas (C replicas)**: A column-oriented data storage format. C replicas are independent of the standard row-oriented replicas (F/R), often located in a separate zone. These replicas do not participate in the Paxos consensus algorithm for leadership elections or voting processes. Data consistency between the C replicas and the F/R replicas is asynchronously synchronized through logs. The C replicas mainly use the columnar major storage layer to store user table data. For the same logical table, the data storage format of the F/R and C replicas can be different. For example, the F/R replicas can use row-oriented storage, while the C replicas can use columnar storage. This setup isolates resources for applications requiring Analytical Processing (AP) and those requiring Transactional Processing (TP).

**Relations**: They are independent of each other. A columnar table can be created on a tenant without a C replica, where data exists only in columnar or hybrid form on F/R. Alternatively, on a tenant with a C replica, the data can be stored in hybrid form on F/R and in columnar form on the C replica, providing read-only analysis. Columnar tables and C replicas can coexist and be combined based on the schema requirements.

* **Read Consistency**: There is a lag in C copies relative to the log source. **Prior to OceanBase Database V4.6.0**, most analytical queries accessing C copies using standalone ODP or other independent methods used **weak reads** as the default read consistency. Starting from **V4.6.0**, **strong read** or **weak read** consistency can be configured for C copies on a session-by-session basis using parameters like `ob_read_consistency`. The decision to attempt columnar execution plans is controlled by settings such as `ap_query_route_policy`.

#### Do I need a columnar storage replica to create a **columnar table**? Can I create a columnar table on a Full replica?

**Columnstore tables can be created on Full (F) replicas without the need for a columnstore replica.**

In a columnar table, data is stored in columnar format. In a hybrid table, data is stored in hybrid mode. A columnar table or a hybrid table can be created as long as an F/R replica exists in a locality. You can create a columnar table or a hybrid table on an F/R replica in a locality (such as `F@zone1, F@zone2`). A columnar replica (C replica) is an optional mode for isolation. A columnar table or a hybrid table can be created as long as an F/R replica exists in a locality.

#### Can OceanBase Database directly create a **pure columnstore table**? Or is it based on a rowstore table?

**You can directly create a pure column-oriented table without creating a row-oriented table first.**

To create a pure columnar storage table with only columnar baseline and no row-based baseline, you can specify `WITH COLUMN GROUP (each column)` when you create a table. For example:

```sql
CREATE TABLE t (pk INT PRIMARY KEY, c1 INT, c2 INT) WITH COLUMN GROUP (each column);
```

In a partitioned table, the primary key column stores the row data for point queries, and the rest of the data is stored as a pure columnar storage table. You can also create a row-store table first and then convert it to a columnar storage table by executing the `ALTER TABLE ... ADD COLUMN GROUP (each column);` DDL statement. For more information, see How to create a columnar storage table?

#### How is data consistency ensured between columnar and row storage? How much latency will there be if the synchronization is asynchronous?

There are two cases:

* **Columnar tables (in F/R replicas)**: The baseline uses columnar or hybrid row-columnar layouts, while the incremental data is organized by row (MemTable/dumps). During reads, the incremental and baseline data are merged, ensuring **strong consistency** in F/R replicas under default semantics, with no additional cross-replica latency.
* **C-Replica**: C-Replica does not participate in Paxos. It asynchronously catches up with F/R by playing back logs and replays logs. Data may **lag behind the log source**. Before **V4.6.0**, analytics read operations on C-Replicas were **weakly consistent**. From **V4.6.0** onwards, you can configure **strong reads** on C-Replicas: Strong reads wait for the replica to catch up to a readable point, resulting in **higher latency** compared to weak reads. If **TP logs must be fully consistent, with no lag from C-Replicas**, analytics reads should prioritize **C-Replicas, columnar tables, or hybrid column-row tables on F/R**.

#### How do I separate TP and AP traffic? What happens in the event of an AP failure?

**Traffic separation:**

* **No C copies**. TP and AP share the same F/R replicas and access points, and the optimizer automatically chooses the row or column-based path. **There is no** physical isolation between TP and AP at the cabinet or link level.
* **Use OceanBase Database V4.6.0 or earlier in F/R deployment mode**: A typical approach is to use the primary F/R replica for read/write operations and the independent ODP for read-only operations. You need to configure the ODP with the weak-read policy and direct requests to the C replica. The following sample statements show how to set the read policy to weak read and specify the C replica as the target for routing requests: `proxy_primary_zone_name`, `route_target_replica_type = 'ColumnStore'`, and `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`. This approach enables isolation between the TP and AP and the C replica. For more information about replica management, see [Use a columnar store replica](../600.manage/300.replica-management/150.the-use-of-columnstore-replica.md).
* **ODP with ColumnStore (V4.6.0 and later) is available**: In addition to the aforementioned **ODP method (Option 1)**, you can also **directly connect to an OBServer** (or a standard ODP that does not have columnar storage dedicated line configurations) via **`ap_query_route_policy`** and let the optimizer automatically try columnar storage plans (**Option 2**). There is no need to maintain a separate ODP routing configuration for columnar storage.

**Data center disaster recovery (AP) and its limitations:**

* C replicas **cannot be promoted to leaders**; **C replicas cannot be restored from physical backups** (restoration will fail if a tenant includes C replicas in its locality); it is also not recommended to deploy C replicas on standby databases if they are not deployed on primary databases.
* In the event of a zone failure or an ODP failure, AP queries can **fallback to F/R replicas**. This involves changing the AP client to connect to the primary ODP or adjusting the routing so that analytical queries execute with strong consistency (sharing resources with TP).
* Starting from V4.3.5 BP1, the deployment of **multiple C replicas** (up to 3 recommended) is supported. These replicas can be distributed across multiple zones to route AP read traffic using either ODP routing (Option 1) or automatic routing (Option 2), enabling redundancy and high availability.

### How do I create a columnstore table?

First, create a hybrid row-columnstore table.

- Non-partitioned table:

```sql
create table t1(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (all columns, each column);
```

- Partitioned table:

```sql
create table t2(
   pk int,
   c1 int,
   c2 int,
   primary key (pk)
)
partition by hash(pk) partitions 4
with column group (all columns, each column);
```

When creating a hybrid row-columnstore table, the `with column group (all columns, each column)` syntax is always used. This syntax means the following:

- `all columns`: All columns are aggregated into a single group, treated as a wide column, and stored row by row. This is essentially the same as the original rowstore.
- `each column`: Each column is stored separately in columnar format.

When both `all columns` and `each column` are specified, it means that after creating a columnstore table, the data is redundantly stored in both rowstore and columnstore formats, with each replica storing two copies of the baseline data. However, it's worth noting that regardless of the number of baseline data copies, the data in the memtable and the incremental data in the dump are shared.

Next, create a pure columnstore table.

- Non-partitioned table:

```sql
create table t3(
   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT
) with column group (each column);
```

- Partitioned table:

```sql
create table t4(
   pk1 int,
   pk2 int,
   c1 int,
   c2 int,
   primary key (pk1, pk2)
)
partition by hash(pk1) partitions 4
with column group (each column);
```

For the t4 table, a columnstore is created for each of the columns pk1, pk2, c1, and c2, and a rowstore is created for the combination (pk1, pk2).

### How do I make a tenant's default table type columnstore?

Set a tenant-level parameter:

```sql
alter system set default_table_store_format = "column";
```

Similarly, you can set the default table type to rowstore or both rowstore and columnstore:

```sql
alter system set default_table_store_format = "row";   // rowstore
alter system set default_table_store_format = "compound"; // rowstore and columnstore
```

### What are the recommended configurations for columnstore?

```sql
# Set the collation to utf8mb4_bin to boost performance by 15%
set global collation_connection = utf8mb4_bin;
set global collation_server = utf8mb4_bin;

set global ob_query_timeout= 10000000000;
set global ob_trx_timeout= 100000000000;
set global ob_sql_work_area_percentage=30;
set global max_allowed_packet=67108864;
# Recommended value is 10 times the number of CPU cores
set global parallel_servers_target=1000;
set global parallel_degree_policy = auto;
set global parallel_min_scan_time_threshold = 10;
# Limit the maximum DOP when parallel_degree_policy is set to auto
# A high DOP may cause performance issues. The recommended value is cpu_count * 2
set global parallel_degree_limit = 0;

alter system set compaction_low_thread_score = cpu_count;
alter system set compaction_mid_thread_score = cpu_count;
alter system set default_table_store_format = "column";
```

   c1 TINYINT,
   c2 SMALLINT,
   c3 MEDIUMINT,

### Can I add or drop columns in a columnstore table?

* Yes, you can add or drop columns.

* You can increase or decrease the character length of a VARCHAR column.

* Columnstore supports various offline DDL operations, similar to rowstore tables.

For more information about modifying columnstore tables, see [Convert a table from rowstore to columnstore (MySQL mode)](../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/600.change-table-of-mysql-mode.md) and [Convert a table from rowstore to columnstore (Oracle mode)](../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/100.manage-tables-of-oracle-mode/600.change-table-of-oracle-mode.md).

### What are the characteristics of queries on columnstore tables?

* In a hybrid row-columnstore table, the query logic for range scans defaults to columnstore, while point get queries fall back to rowstore.

* In a pure columnstore table, all queries use columnstore.

### Does columnstore support transactions, and are there any limitations on transaction size?

Yes, columnstore supports transactions, and there are no size limitations on transactions, ensuring high consistency.

### Are there any special considerations for log synchronization, backup, and restore in columnstore tables?

No, columnstore tables behave the same as rowstore tables. Synchronized logs are in rowstore format.

### Can I convert a rowstore table to a columnstore table using DDL operations?

Yes. You can add columnstore and drop rowstore. Here are some example syntaxes:

```sql
create table t1( pk1 int, c2 int, primary key (pk1));

alter table t1 add column group(all columns, each column);
alter table t1 drop column group(all columns, each column);

alter table t1 add column group(each column);
alter table t1 drop column group(each column);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After executing <code>alter table t1 drop column group(all columns, each column);</code>, you don't need to worry about any group to hold the data. All columns will be placed into a default group called <code>DEFAUTL COLUMN GROUP</code>.</p>
</main>

### Can I group multiple columns together in columnstore?

In OceanBase Database V4.3.0, you can either store each column separately or store all columns together as a rowstore. You cannot selectively group a subset of columns together.

### Does OceanBase Database support updates on columnar tables, and what is the structure of the MemTable?

In OceanBase Database, add, delete, and modify operations are performed in memory. The data is stored in the MemTable in row-based format. The baseline data is read-only and stored in columnar format on disk. When a column is queried, the row-based data in the MemTable and the columnar data on disk are dynamically combined and returned to the user. This means that **OceanBase Database supports strong-consistency reads on columnar tables without data latency**. Data written to the MemTable can be dumped, and the dumped data is still stored in row-based format. After compaction, the row-based data and baseline columnar data are combined to form new baseline columnar data.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>For columnar tables, if there are a large number of update operations and no compaction is performed in a timely manner, query performance will be affected. Therefore, it is recommended to perform a compaction after batch data import to achieve optimal query performance. However, a small number of update operations will not significantly impact performance.</p>
</main>

### What are the characteristics of queries on columnar tables?

In a redundant rowstore table, columnar table queries default to range scans in columnar mode, while point gets fall back to rowstore mode.

In a pure columnar table, all queries are performed in columnar mode.

### Can an index be created on a specific column of a columnar table?

Yes. OceanBase Database does not differentiate between creating an index on a columnar table or a rowstore table. The index structure is the same in both cases.

Creating an index on one or more columns of a columnar table allows for the construction of a covering index, which can improve point query performance, or for sorting specific columns to enhance sorting performance.

### What is the maximum number of columns supported?

Currently, a columnar table can support up to 4096 columns.

### What are the considerations when using columnar tables?

**First**, after batch data import, it is recommended to perform a compaction to optimize read performance. After importing data, trigger a compaction within the tenant to ensure all data is baseline. Execute `alter system major freeze;` within the tenant, and then check the status by executing `select STATUS from CDB_OB_MAJOR_COMPACTION where TENANT_ID = tenant_id;` in the system tenant. When the `STATUS` changes to `IDLE`, the compaction is complete.

**Second**, after compaction, it is recommended to collect statistics. The method for collecting statistics is as follows:

- In the business tenant, collect statistics for all tables using 16 threads in parallel:

  ```sql
  CALL DBMS_STATS.GATHER_SCHEMA_STATS ('db', granularity=>'auto', degree=>16);
  ```

- Monitor the statistics collection progress using the `GV$OB_OPT_STAT_GATHER_MONITOR` view.

**Third**, you can use full direct load to batch import data. Tables imported this way do not require a compaction to achieve optimal columnar scan performance. Supported tools for full direct load include obloader and the native LOAD DATA command.

**Fourth**, for non-large wide tables, using columnar storage may not be necessary to achieve performance comparable to columnar storage. This is due to the row-column hybrid storage architecture at the microblock level in OceanBase's rowstore version (this is not surprising).

**Fifth**, the performance of large tables can vary between cold and hot runs.

**Sixth**, the optimizer automatically selects between rowstore and columnar access based on cost estimation.

**Seventh**, the compaction speed of columnar tables will be slower.

### Are there any special considerations for log synchronization, backup, and restore in columnar tables?

No, they are the same as for rowstore tables. Synchronized logs are in rowstore format.

## Performance Tuning FAQ

### What are other methods to further improve AP Query performance?

Based on some practical experience, first, if there are no special sorting requirements, do not use the utf8mb4 character set when creating a table; instead, use the binary character set to improve performance. For example:

```sql
create table t5(c1 TINYINT, c2 VARVHAR(50)) CHARSET=binary with column group (each column);
```

Second, if users or businesses can accept it, when creating a MySQL tenant, specify the utf8mb4_bin character set by adding the following parameters: `CHARSET = utf8mb4 collate=utf8mb4_bin`

Additionally, increasing the IOPS of the UNIT can accelerate direct load.

### What are the characteristics of the optimizer for columnar storage?

Compared to the optimizer for row-based storage, the optimizer for columnar storage has the following features:

- The ability for the optimizer to autonomously choose between row-based and columnar storage.
- The ability to control the choice between row-based and columnar storage using hints at the table level.
- Adapted plan cost calculation for columnar storage.
- Late materialization optimization for columnar storage.
