# Deploy and use columnstore replicas

To support mixed workloads such as TP and AP, OceanBase Database supports **columnstore replicas** (COLUMNSTORE, abbreviated as **C replicas**). C replicas can be deployed in an independent zone. User tables (including replicated tables, excluding index tables, internal tables, and system tables) are stored in the C replica in columnar format.

This topic describes how to deploy C replicas in the **Locality** of a tenant and how to **use** C replicas.

### Limitations and considerations

* **Limitations**

  * C replicas cannot be converted to **F** or **R** replicas, and vice versa.
  * **Physical restore** is not supported for C replicas. If a tenant's locality includes a C replica, the restore will fail.

* **Deployment recommendations**

  * Starting from V4.3.5 BP1, you can deploy multiple C replicas. We recommend that you deploy at most **3** C replicas.
  * For OceanBase Database versions earlier than V4.6.0, we recommend that you deploy only C replicas in the zone where the C replicas are located. The independent ODP must be **ODP V4.3.2 or later**.
  * If the primary database does not have a C replica, **we recommend that you do not deploy a C replica** in the standby database.

* **Considerations during O&M**

  * When you execute DDL operations in a cluster that has C replicas, the system resource consumption usually increases. This is because the system processes both rowstore and columnstore data at the same time, and the commit logs (clogs) must be synchronized to the corresponding replicas. This results in higher pressure on the CPU, memory, disk, and I/O resources.
  * **Major compactions** of C replicas are generally slower than those of F/R replicas. **You cannot initiate a new major compaction of a tenant until the previous one is completed**. Before you manually initiate a major compaction, we recommend that you view [CDB_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/12000.o-cdb_ob_zone_major_compaction-of-sys-tenant.md) and [DBA_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13000.o-dba_ob_zone_major_compaction-of-mysql-mode.md). For more information, see [View major compaction information](../../700.reference/200.system-management/500.manage-data-storage/200.merge-management/500.view-merge-process.md).

## Deploy a columnstore replica

In the **Locality** of the tenant, specify the C replica. The following two scenarios are common:

* **Scenario A**: Create a tenant with a C replica.
* **Scenario B**: Add a C replica to an existing tenant (add a new zone and adjust the Locality).

The following sample SQL statements use CPU, memory, and disk values as examples. You must adjust the values based on your actual load and resource planning.

### Scenario A: Create a tenant with a C replica

Assume that you have deployed a cluster in the 2F1A mode (two replicas and one arbitration service). The cluster has three zones: zone1, zone2, and zone3. The arbitration service is deployed in zone3. You need to create a tenant with a C replica in the cluster. Perform the following steps:

1. Find a server that can communicate with the cluster and deploy ODP on the server.

   To prevent resource contention, we recommend that you deploy ODP on a server separately. When you deploy ODP, make sure that its version is ODP V4.3.2 or later. For more information about how to deploy ODP, see [Deploy ODP](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000001600960).

2. Create a resource unit named `unit1` for the tenant.

    ```sql
    CREATE RESOURCE UNIT unit1,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

3. Create a resource pool named `pool1` for the tenant and specify `unit1` as the resource unit.

    ```sql
    CREATE RESOURCE POOL pool1
        UNIT='unit1',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone1','zone2','zone3');
    ```

4. Create a tenant named `tenant_c` and specify its Locality as `F@zone1,F@zone2,C@zone3`.

    ```sql
    CREATE TENANT tenant_c
        LOCALITY = 'F@zone1,F@zone2,C@zone3',
        PRIMARY_ZONE='zone1;zone2,zone3',
        RESOURCE_POOL_LIST=('pool1') SET ob_tcp_invited_nodes = '%';
    ```

    In this example, the tenant is created in MySQL compatible mode by default. If you want to create an Oracle compatible tenant, you must explicitly specify `ob_compatibility_mode='oracle'` by using the system variable [ob_compatibility_mode](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/6100.ob_compatibility_mode-global.md).

### Scenario B: Add a C replica to an existing tenant

Assume that the cluster has a tenant named `tenant_c` with the Locality `F@zone1,F@zone2,F@zone3`. The resource pool of the tenant is `pool1`, and the `ZONE_LIST` of the resource pool is `'zone1','zone2','zone3'`. You need to add a C replica to the tenant. You can add **zone4** and change the Locality of the tenant to `F@zone1,F@zone2,F@zone3,C@zone4`. Perform the following steps:

1. Add a new zone named **zone4** to the cluster. For more information about how to add a zone, see [Add a zone](../../600.manage/100.cluster-management/300.common-cluster-operations/800.add-a-zone.md).

2. Add nodes to **zone4**. For more information about how to add a node, see [Add a node](../../600.manage/100.cluster-management/300.common-cluster-operations/400.add-a-node.md).

3. Create a resource unit named `unit2`.

    ```sql
    CREATE RESOURCE UNIT unit2,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

4. Create a resource pool named `pool2` and specify `unit2` as the resource unit.

    ```sql
    CREATE RESOURCE POOL pool2
        UNIT = 'unit2',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone4');
    ```

5. Add `pool2` to the tenant.

    ```sql
    ALTER TENANT tenant_c RESOURCE_POOL_LIST = ('pool1','pool2');
    ```

6. Change the Locality of the tenant to `F@zone1,F@zone2,F@zone3,C@zone4`.

    ```sql
    ALTER TENANT tenant_c LOCALITY = 'F@zone1,F@zone2,F@zone3,C@zone4';
    ```

## Use columnar replicas

### Use of the C replica

* Before V4.6.0, you need to configure an independent ODP for the C replica. Business requests are sent to the C replica through the independent ODP.

  That is, you need to configure a **separate ODP** and set weak-consistency reads, routing, and `init_sql` (commonly `ob_route_policy = COLUMN_STORE_ONLY`) on the ODP.

* From V4.6.0 onwards, the C replica does not require an independent ODP. The C replica shares the ODP with the F replica, and the database automatically selects the routing strategy, which is **automatic routing for columnar replicas**.

For more information about the automatic routing rules for columnar replicas, see [AP query and columnar replica routing rules](300.ap-query-column-replica-routing-rules.md).

### Before V4.6.0: Deploy an independent ODP to send business requests to the C replica

This method applies to **V4.6.0 and earlier** or **V4.6.0 and later** if you still need to use an **independent ODP** to route AP weak-consistency reads to the C replica and isolate the TP link.

#### Deploy an ODP

Deploy an **ODP dedicated for accessing the C replica** on a server that can communicate with the cluster. We recommend that you deploy it on a single server. The version must be **no earlier than ODP V4.3.2**. For more information, see [Deploy an ODP](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000001600960).

#### Configure the routing forwarding strategy and weak-consistency read

Log in to the ODP as `root@proxysys`, for example:

```shell
obclient -uroot@proxysys -h10.10.10.1 -P2883 -p
```

Select **Option 1** or **Option 2**. **We recommend that you select:**

* **Option 1** (`proxy_primary_zone_name`) if you know the **zone where the C replica resides** and want to converge weak-consistency read traffic by zone.
* **Option 2** (`route_target_replica_type`) if you prefer to route traffic by **replica type (ColumnStore)** instead of binding it to a specific zone.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The meanings of ODP configuration items may differ from their literal descriptions. In the example, <code>obproxy_read_consistency = 1</code> indicates weak-consistency reads. For parameters such as <code>obproxy_read_only</code>, refer to the documentation of the ODP version you are using.</p>
</main>

* **Option 1**

  * Configuration items related to read-only and weak-consistency reads:

      ```shell
      obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
      obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
      ```

  * Configure the ODP to route all requests to the zone where the C replica resides and generate query plans for the C replica. For example, the zone where the C replica resides is `zone4`.

      ```shell
      obclient> ALTER PROXYCONFIG SET proxy_primary_zone_name='zone4';
      obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
      ```

* **Option 2**

  * Configuration items related to read-only and weak-consistency reads:

      ```shell
      obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
      obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
      ```

  * Configure the ODP to route all requests to the C replica and generate query plans for the C replica:

      ```shell
      obclient> ALTER PROXYCONFIG SET route_target_replica_type = 'ColumnStore';
      obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
      ```

  * Configure the ODP to select only replicas for all requests. If all replicas are unavailable, the ODP disconnects from the client:

      ```shell
      obclient> ALTER PROXYCONFIG SET proxy_route_policy='TARGET_REPLICA_TYPE_FOLLOWER_ONLY';
      ```

After the configuration is modified, run the following statement to confirm the modification result:

```shell
obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_only';
obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_consistency';
obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_primary_zone_name';
obclient> SHOW PROXYCONFIG ALL LIKE 'init_sql';
obclient> SHOW PROXYCONFIG ALL LIKE 'route_target_replica_type';
obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_route_policy';
```

After the configuration is successful, OLAP services access the **independent ODP** and direct queries to the C replica.

### V4.6.0 and later: C replicas and F replicas use the same ODP and automatic routing

This applies to scenarios where **C replica deployment is complete** and you want all business requests to be sent to the database through a unified access entry. Please use the **same connection method as for F/R**: through the **same set of business ODPs**.

**Quick usage example** (replace the table name and conditions according to your environment):

```sql
-- 1. Check if the automatic routing-related variables exist and their default values
SHOW VARIABLES LIKE 'ap_query%';

-- 2. Keep the default AUTO or explicitly specify it (optional)
SET SESSION ap_query_route_policy = 'AUTO';

-- 3. Check if there are any plan operators related to the columnar side (actual operators may vary)
EXPLAIN SELECT COUNT(*) FROM your_table;
```

Whether to plan for read-only operations on the C replica is jointly determined by **`ap_query_route_policy`, `ap_query_cost_threshold`, and `ap_query_replica_fallback`** along with [routing rules](300.ap-query-column-replica-routing-rules.md) and read consistency. For a complete description of the variables, see **Columnar Replica Automatic Routing**.

#### Columnstore replica auto-routing

Starting from **OceanBase Database V4.6.0**, you can control whether **read-only queries** **attempt to execute** on **C replicas** using system variables.

The `ap_query_route_policy` variable is the control switch for **columnstore replica auto-routing**, determining whether the system attempts to generate execution plans targeting C replicas for qualifying analytical queries. For detailed determination rules, see [AP Query and Columnstore Replica Routing Rules](300.ap-query-column-replica-routing-rules.md).

##### Prerequisites

* **Tenant**: The target tenant has configured **C replicas** in Locality, and the replicas are available for read operations.
* **Variables**: Execute `SHOW VARIABLES LIKE 'ap_query%';` to confirm the existence of variables such as `ap_query_route_policy`, `ap_query_cost_threshold`, and `ap_query_replica_fallback`.

##### System variable description

The following variables are used for columnstore replica auto-selection. The meanings are based on the cluster's `SHOW VARIABLES` and the current version's documentation.

**`ap_query_route_policy` values**

| Value | Description |
| ---- | ---- |
| **OFF** | Disables columnstore replica auto-selection logic; queries follow default rowstore paths (consistent with behavior before V4.6.0). |
| **AUTO** | Default value. The optimizer automatically determines whether to attempt columnstore plans based on rules and cost. |
| **FORCE** | Prioritizes attempting to execute read-only queries on C replicas when conditions are met. |

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_route_policy';
obclient> SET ap_query_route_policy = 'AUTO';
obclient> SET ap_query_route_policy = 'FORCE';
```

**`ap_query_cost_threshold`**: In **AUTO** mode, if the cost of a single parallelism plan exceeds this threshold, it participates in the decision to attempt columnstore plans. The default value is determined by `SHOW VARIABLES` (commonly `200000`).

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_cost_threshold';
obclient> SET SESSION ap_query_cost_threshold = 300000;
```

**`ap_query_replica_fallback`**: If the target is a C replica but it is unavailable or planning fails, whether to fall back to rowstore.

| Value | Description |
| ---- | ---- |
| ON | Allows fallback; queries will attempt to succeed. |
| OFF | Does not fallback due to this reason; may result in errors. |

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_replica_fallback';
obclient> SET SESSION ap_query_replica_fallback = OFF;
```

##### Relationship with `ob_route_policy`

* **`ap_query_route_policy`**: Determines whether the optimizer attempts to generate columnstore plans (auto-select, force, or disable).
* [`ob_route_policy`](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8900.ob_route_policy-global.md): Determines the types of replicas available for read paths within an OBServer (e.g., `COLUMN_STORE_ONLY`).

These two settings operate at different levels and are not simple replacements. When accessing a C replica through an independent ODP, it is common to set **`ob_route_policy = COLUMN_STORE_ONLY`** in `init_sql`, alongside ODP routing, to direct traffic to columnstore. **Columnstore replica auto-routing**, on the other hand, is primarily governed by the `ap_query_route_policy` variable on the OBServer side.

##### Strategy selection by scenario

| Scenario | Recommended Strategy | Description |
| -------- | -------- | ---- |
| Smart selection: Try rowstore first, then attempt C replicas if AP characteristics are met (most scenarios) | `ap_query_route_policy = AUTO` (default) | Judged based on cost, parallelism, etc. Adjust with `ap_query_cost_threshold`. |
| Prefer C replicas for analytical reads within a session | `ap_query_route_policy = FORCE` | Writes still go to the primary replica. |
| Align with pre-upgrade columnstore behavior, disable auto-selection | `ap_query_route_policy = OFF` | Follows default rowstore paths. |
| Accept fallback to rowstore when C replicas are down | `ap_query_replica_fallback = ON` (default) | Reduces query failure rate. |
| Must only use columnstore; errors if it fails | `ap_query_replica_fallback = OFF` | |
| More queries attempt columnstore in AUTO mode | **Lower** `ap_query_cost_threshold` | E.g., `100000`. |
| Only heavy queries attempt columnstore in AUTO mode | **Raise** `ap_query_cost_threshold` | E.g., `300000`. |
| Single SQL differs from session default | Hint `/*+opt_param('ap_query_route_policy', '...')*/` | See below for query-level control. |

##### Quick steps

After understanding the configuration methods and strategy selection for different scenarios, you can follow these steps to complete the setup.

* The default value of `ap_query_route_policy` is `AUTO`. You can manually change it to `FORCE` or `OFF` if needed.
* The system will only attempt to generate columnstore plans if the tenant has **available C replicas** and the query meets the relevant criteria.
* You can adjust the sensitivity to heavy queries in `AUTO` mode using `ap_query_cost_threshold`, and control whether to fall back to rowstore execution when C replicas are unavailable or planning fails using `ap_query_replica_fallback`.

Recommended order of operations:

1. Confirm that C replicas have been deployed as described in the **Deploy Columnstore Replica** section.
2. Check variables: `SHOW VARIABLES LIKE 'ap_query%';`
3. Adjust as needed for the current session, for example: `SET SESSION ap_query_route_policy = 'FORCE';` or modify `ap_query_cost_threshold` and `ap_query_replica_fallback`.
4. Run `EXPLAIN` on the target SQL to check for columnstore-related operators; also check the status of C replicas using `DBA_OB_CS_REPLICA_STATS` / `CDB_OB_CS_REPLICA_STATS`.

##### Query-level control

Use hints for **temporary verification**, **single SQL optimization**, or **without changing session-level defaults**:

* Try to plan this statement according to columnstore strategies (if allowed by policy and replicas):

    ```shell
    obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'FORCE')*/ *
       FROM t1, t2
       WHERE t1.c1 = t2.c1;
    ```

* Disable auto-selection of columnstore for this statement:

    ```shell
    obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'OFF')*/ *
        FROM t1, t2
        WHERE t1.c1 = t2.c1;
    ```

##### Read consistency on columnstore replicas

**Before V4.6.0**, accessing C replicas only supported weak reads (`ob_read_consistency = 'weak'`). **Starting from V4.6.0**, you can also perform **strong-consistency reads** on C replicas. For global variable details, see [ob_read_consistency](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8700.ob_read_consistency-global.md).

###### Strong-consistency reads on columnstore replicas

In strong read scenarios, the transaction layer checks whether the C replicas (Followers) have caught up to a readable point based on the **global consistent snapshot**. If necessary, it **waits for the log replay** before executing the query. The following are **simplified steps for easier understanding**, not implementation details:

1. Obtain the global consistent snapshot version (e.g., through GTS).
2. Determine if the C replica has caught up to this version.
3. If not ready, wait; otherwise, execute the read.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Strong reads may introduce latency due to waiting for log replay. Short-point queries are generally not suitable for strong reads on C replicas. </p>
</main>

###### Comparison between strong read and weak read

| Feature | Strong read | Weak read |
| ---- | ---- | ---- |
| Consistency | Consistent with the primary replica | Eventually consistent, possibly slightly outdated |
| Latency | May require waiting for log replay | Typically lower |
| Typical scenario | High-consistency AP reads | AP reads that can tolerate brief delays |
| Setting | `ob_read_consistency = 'strong'` (default) | `ob_read_consistency = 'weak'` |

**Recommendation:** Use strong read (default) when high consistency is required; use weak read when latency can be tolerated, as it often performs better.

When **`ap_query_route_policy = AUTO`**, the system evaluates **weak read, parallelism, and cost threshold** to determine whether to attempt a columnar plan. **Weak read is one of the conditions that may trigger this attempt**, but it is not the only condition. For more information, see [AP query and columnar replica routing rules](300.ap-query-column-replica-routing-rules.md).

##### Verification and troubleshooting recommendations

Check the following in order:

* **C replica**: Ensure that the tenant's locality includes C, the replica is available, and row-to-column conversion is complete (see **Row-based storage** and `CDB_OB_CS_REPLICA_STATS` / `DBA_OB_CS_REPLICA_STATS`).
* **Variables**: Run `SHOW VARIABLES LIKE 'ap_query%';` to confirm that `ap_query_route_policy` and other variables meet expectations.
* **Execution plan**: Execute `EXPLAIN` (or view the actual execution plan) for the target SQL query to check if columnar operators are present.
* **Still not using columnar storage**: Compare the basic conditions and AUTO trigger items in [AP query and columnar replica routing rules](300.ap-query-column-replica-routing-rules.md).

For tenants without C replicas, enabling the above variables typically does not change the basic planning behavior when columnar storage is unavailable.
