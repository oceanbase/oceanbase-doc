# AP query routing decision rules

In **OceanBase Database V4.6.0 and later**, if a tenant has configured **columnstore replicas (C replicas)** and enabled **columnstore replica auto-selection** controlled by variables such as **`ap_query_route_policy`**, the optimizer will follow **fixed rules** to determine whether the read-only part of a statement will **attempt** to plan or execute on a C replica.

For details on **system variable default values, how to enable or disable this feature, and read/write consistency settings**, see [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md#cs-auto-routing).

## Understand the judgment rules

You can understand the AP query routing judgment rules as two layers of constraints: the **basic conditions** and the **policy branches**:

1. **First layer: basic conditions**

   All basic conditions must be **satisfied** for the system to consider the columnstore replica for automatic selection.

   If any of the basic conditions are not satisfied, the system will not attempt to use the columnstore path. This is different from **`ap_query_route_policy = OFF`**, which **completely disables** columnstore replica automatic selection. Not satisfying the basic conditions means that **this specific SQL statement** is not considered for columnstore routing.

2. **Second layer: policy branches (`ap_query_route_policy`)**

   After all basic conditions are satisfied, the value of `ap_query_route_policy` (set to `FORCE`, `AUTO`, or `OFF`) determines **whether additional conditions** such as weak reads, parallelism, or cost thresholds are required:

   * `FORCE`: After all basic conditions are satisfied, the system **directly attempts** to use the columnstore replica plan without requiring weak reads, parallelism, or cost thresholds. This is different from `AUTO`, where these conditions are still required.
   * `AUTO` (default): After all basic conditions are satisfied, the system will also require **at least one of the AUTO conditions** to be met before attempting to use the columnstore replica plan.
   * `OFF`: Columnstore replica automatic selection is disabled, and the system will use the default rowstore path (e.g., without columnstore replicas).

In summary, **basic conditions must be satisfied first**, and then the policy branch determines whether additional conditions are required. For `AUTO`, at least one of the AUTO conditions must be satisfied after all basic conditions are met. For `FORCE`, these additional conditions are **not required** after all basic conditions are met.

## Basic conditions (must be satisfied simultaneously)

Only when the following conditions are **all satisfied** will the SQL statement proceed to the `FORCE` or `AUTO` branches:

| Condition | Description |
| ---- | ---- |
| **Single-statement transaction** | The statement runs in a **single-statement transaction** context. For example, an independent `SELECT` statement that does not explicitly use `BEGIN` or `START TRANSACTION`, or a single DML statement when `autocommit` is enabled. **Statements within an explicit transaction** typically do not meet this condition and will not be considered for columnstore automatic selection. |
| **Tenant has columnstore replicas** | The tenant's `LOCALITY` configuration includes **C replicas**, and the columnstore replicas are available for read operations (including scenarios such as row-to-column conversion and major compactions, as described in [Deploy and Use Columnstore Replicas](150.uesing-columnstore-replica.md#cs-auto-routing)). |
| **Automatic selection is not disabled** | The session/global `ap_query_route_policy` and any hints on the current SQL statement are not set to `OFF`. |
| **Accessing user base tables** | The execution plan involves **at least one user base table**. Statements that do not involve user base tables (such as `SELECT 1` or `SELECT NOW()`) do not meet this condition. |
| **Consistent with fallback policy** | The `ap_query_replica_fallback` parameter controls whether to fallback to rowstore replicas when columnstore replicas are unavailable or cannot generate a columnstore plan. This is **not** a standalone condition for attempting columnstore routing, but it should be considered alongside replica availability to avoid situations where columnstore is expected but always falls back. |

## AUTO conditions (any one of the following is sufficient)

When **`ap_query_route_policy = AUTO`** and **all basic conditions are satisfied**, the system will attempt to use the columnstore replica plan if **any of the following conditions** is met:

| Condition | Description |
| ------ | ---- |
| **Weak read** | The current statement uses weak-consistency reads. For example, when the session-level `ob_read_consistency` is set to `'weak'`. For more information about read consistency levels, see [ob_read_consistency](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8700.ob_read_consistency-global.md). |
| **Parallel execution** | The parallelism of the **`SELECT`** part of the plan is **greater than 1** (this includes the use of the `PARALLEL` hint or optimizer auto-parallelism, based on the actual plan). |
| **Cost exceeds threshold** | In a **single-parallelism** scenario, the estimated cost of the **`SELECT`** part exceeds `ap_query_cost_threshold`. For statements with multiple `SELECT` fragments (such as `UNION ALL` or nested subqueries), the cost **accumulation rules apply as of the current version**. |

When **`ap_query_route_policy = FORCE`**, the system **does not require** the weak read, parallelism, or cost conditions from the previous table. As long as **all basic conditions are satisfied**, the system can attempt to use the columnstore path, provided it is allowed.

## Interactions with other settings

The following settings are directly relied upon or need to be considered alongside the judgment rules:

* **`ap_query_route_policy`**: Determines whether to **disable**, use **AUTO (with trigger conditions)**, or use **FORCE (without trigger conditions)**.
* **`ob_read_consistency`**: Weak read is one of the **common trigger conditions** in AUTO mode.
* **`ap_query_cost_threshold`**: Used in **AUTO mode** to trigger based on cost exceeding the threshold.
* **`ap_query_replica_fallback`**: Does not determine whether to attempt columnstore routing, but affects whether to **fallback to rowstore** when columnstore replicas are unavailable or cannot generate a columnstore plan.

For session-level settings like **`ob_route_policy`** that are related to replica types, refer to [ob_route_policy](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8900.ob_route_policy-global.md) and [Deploy and Use Columnstore Replicas](150.uesing-columnstore-replica.md#cs-auto-routing).

## Scenarios where columnstore automatic selection is not used

| Scenario | Description |
| ---- | ---- |
| `ap_query_route_policy = OFF` | Columnstore replicas are not used; the system follows the default rowstore path. |
| Any basic condition is not satisfied | For example, the statement is within an explicit transaction, no user base tables are involved, or no C replicas are available. |
| `AUTO` and none of the three trigger conditions are met | If the statement is not a weak read, does not use parallelism, and the cost of the `SELECT` part does not exceed `ap_query_cost_threshold`, the system will typically follow the default rowstore path (e.g., for simple point queries or queries with small result sets). |

## Examples

### FORCE: A columnar access operator is added to the plan if the basic conditions are met

```shell
obclient> SET ap_query_route_policy = 'FORCE';
obclient> EXPLAIN SELECT * FROM t1 LIMIT 1;
```

If the **columnar access operator** (such as `COLUMN TABLE FULL SCAN`) appears in the plan, it indicates that the system has attempted to use the columnar replica path.

### AUTO: A columnar access operator is added to the plan if the degree of parallelism is greater than 1

```shell
obclient> SET ap_query_route_policy = 'AUTO';
obclient> EXPLAIN SELECT /*+parallel(4)*/ COUNT(*) FROM t1;
```

### AUTO: The relationship between cost and threshold

If the cost of the `SELECT` part in the query plan exceeds the threshold specified by the [ap_query_cost_threshold](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/40.ap_query_cost_threshold-global.md) system variable (default value is 200000), the query is identified as an AP query. Lowering the `ap_query_cost_threshold` value makes it easier for complex queries to trigger columnar plan retries. Raising the threshold means more queries will remain in the row-based plan.

- Example of setting a lower cost threshold:

```shell
obclient> SET ap_query_route_policy = 'AUTO';
-- Set the cost threshold to 50000.
obclient> SET ap_query_cost_threshold = 50000;
-- Complex queries (with cost exceeding the threshold) are automatically routed to columnar replicas.
obclient> EXPLAIN SELECT * FROM t1, t2 WHERE t1.c1 = t2.c1;
```

- Example of setting a higher cost threshold (cost does not exceed the threshold, so columnar routing is not triggered):

```shell
obclient> SET ap_query_route_policy = 'AUTO';

-- After raising the threshold: If the estimated cost of the SELECT part is **below** the new threshold, the cost does not exceed the threshold, and columnar routing is not triggered.
obclient> SET ap_query_cost_threshold = 1000000;
obclient> EXPLAIN SELECT * FROM t1, t2 WHERE t1.c1 = t2.c1;
```

If the plan still contains **row-based** access operators (such as `TABLE FULL SCAN`) and does not include any **columnar** access operators, it indicates that the columnar path was not triggered based on cost.

### No user table: Basic conditions are not met

```shell
obclient> EXPLAIN SELECT 1;
```

Such plans typically do not involve user table access and are **not** included in the automatic selection process for columnar replicas.
