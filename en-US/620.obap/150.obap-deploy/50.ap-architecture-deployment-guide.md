# Deploy an AP architecture

This topic describes how to plan and deploy the AP architecture of OceanBase Database. It covers row-column hybrid storage, single-node and distributed topologies, readable replica types, routing and disaster recovery strategies, and resource control in batch processing scenarios. This helps you effectively use AP columnar replicas and routing strategies under a TP write-centric model.

## Version and access path decision

The **deployment method** of columnstore replicas (C replicas) and how **read requests reach the C replicas** are closely related to the OceanBase Database version. Please confirm the version before selecting the access path:

| OceanBase Database Version | Typical way to use columnstore replicas after deployment |
| -------------------------- | -------------------------------------- |
| **Before V4.6.0** | Typically, you need to **deploy ODP (V4.3.2+) separately** to access the C replicas. Configure weak reads, `route_target_replica_type`, `proxy_route_policy`, and `init_sql` (such as `ob_route_policy = COLUMN_STORE_ONLY`) on ODP to route AP traffic to the C replicas. For more information, see **「Before V4.6.0: Access C replicas through ODP」** and [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md). |
| **V4.6.0 and later** | **No need** to deploy a separate ODP or configure the above ODP routing variables for columnstore replicas. If the tenant has configured C replicas, you can **directly connect to OBServer** or continue to access them through existing ODP, based on session or global variables. For more information, see [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md#cs-auto-routing). |

The deployment of **hybrid row-columnstore tables** (without independent C replicas) does not have the above ODP requirements. It still follows table-level storage and `ob_table_access_policy`.

## Architecture overview

The typical AP architecture of OceanBase Database can be understood from three dimensions:

* **Hybrid row-columnstore architecture**: TP writes are the main focus, and AP read/write separation can be achieved by combining columnstore replicas. Routing supports automatic routing and forced specification (the specific methods vary with the version, as shown in the version table above).
* **Single-node topology**: In a single zone or simple multi-zone setup, F replicas (all-purpose) support both TP and AP; C replicas (pure columnstore) are only suitable for pure AP.
* **Distributed topology**: In multi-zones or multi-datacenter setups, columnstore replicas work with routing strategies, disaster recovery downgrade, and load balancing. Heavy workloads like batch processing can be controlled using Resource Manager.

## Hybrid row-columnstore architecture

### Read/write separation: TP writes as the main focus, AP columnstore replicas

OceanBase Database supports TP and AP workloads within the same cluster. Common scenarios include:

* **Hybrid row-columnstore tables**: A single table can have both row and columnstore formats. TP writes use rowstore, and AP queries can automatically choose between rowstore or columnstore paths based on the optimizer's decision. This is suitable for mixed TP/AP workloads where strong consistency reads are required. For more information, see [OceanBase table types and storage formats](../200.obap-data-design/10.obap-table.md).
* **Columnstore replicas (C replicas)**: Deployed in an independent zone, these are read-only. TP writes and strong reads use primary/standby replicas (F replicas), while AP analysis uses C replicas to achieve physical isolation between TP and AP resources and save storage space.
  * **Before V4.6.0**: AP access to C replicas typically relies on **independent ODP** and routing variables on ODP, and is mostly for weak reads.
  * **V4.6.0 and later**: You can directly connect to or use regular connections to access C replicas through **columnstore replica auto-selection**. **No need** to deploy ODP separately for C replicas; read consistency can still be configured using [ob_read_consistency](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8700.ob_read_consistency-global.md) as specified by the version.
  General information about replicas and locality is available in [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md#cs-auto-routing).

### Routing strategies: automatic routing and forced specification

* **V4.6.0 and later (with columnstore replica auto-selection)**: If the tenant has configured C replicas, the execution of queries on columnstore replicas is determined by variables such as `ap_query_route_policy`, `ap_query_cost_threshold`, and `ap_query_replica_fallback`, along with optimizer behavior. You can also use hints to control individual SQL statements. For more information, see [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md#cs-auto-routing). Session-level [ob_route_policy](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8900.ob_route_policy-global.md).
* **Before V4.6.0 (accessing C replicas through ODP)**: If not explicitly specified, the default ODP strategy and `ob_route_policy` determine the access path. AP traffic is often directed to columnstore replicas through ODP's `route_target_replica_type`, `proxy_route_policy`, and `init_sql` with `ob_route_policy = 'COLUMN_STORE_ONLY'`.

For detailed information about readable replica types, ODP routing, disaster recovery downgrade, and load balancing, see the **Columnstore replicas and routing strategies (detailed)** section of this topic and [ODP read/write separation and routing strategies](../../700.reference/1200.database-proxy/700.route-management/400.odp-routing-policy/100.read-write-splitting.md).

### How to deploy the hybrid row-columnstore architecture

- If you adopt the **hybrid row-columnstore table without deploying C replicas** (TP and AP in the same database, strong consistency reads), follow these steps:

  1. **Choose row-columnstore or columnstore when creating tables**: Specify the storage format using table attributes, and let the optimizer automatically choose between rowstore and columnstore paths based on the query. For more information, see [Columnstore](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/320.columnstore-engine.md).
  2. **(Optional) Configure access preferences**: Use the system variable `ob_table_access_policy` (such as `COLUMN_STORE`, `ROW_STORE`, or `AUTO`) to specify the preferred access path.
  3. **(Optional) Run batch jobs and isolate resources**: For heavy workloads like materialized view refreshes or large-scale imports, configure resource groups or limits using Resource Manager to avoid affecting online TP/AP. For more information, see [DBA_OB_RSRC_DIRECTIVES](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/11020.o-dba_ob_rsrc_directives-of-mysql-mode.md).

  **Verification**: Execute point queries and range scans on hybrid row-columnstore tables to confirm that the execution plan uses the expected storage format.

- If you adopt the **TP writes as the main focus, AP using columnstore replicas**, this falls under the **「Single-node/Distributed + C Read」** scheme. For more information, see **「Single-node topology - How to deploy C Read」** or **「Distributed topology - How to deploy columnstore replicas」** below.

## Standalone architecture

In a standalone or single-zone deployment, or in a scenario with a small number of zones, the relationship between the read replica type and AP is as follows.

### F read (Follow read): All-purpose replica, supporting both TP and AP

* **Full replicas** (F replicas) contain both the leader and followers in Paxos and participate in log synchronization. They can handle both strong-consistency reads and writes and weak reads.
* In a standalone or multi-zone topology, if you do not deploy an independent C replica, AP queries can be directed to the F replica (the columnar part of a hybrid row-columnar table). The optimizer and `ob_table_access_policy` determine whether to use the row or columnar path.
* Features: No need for a dedicated columnar zone; simple deployment; TP and AP share the same set of replicas, so resource isolation (e.g., through Resource Manager or user resource groups) is necessary.

**How to deploy F read**: No additional deployment is required for AP. After deploying the cluster as usual, when creating a table, choose hybrid row-columnar or columnar storage (see **How to deploy a hybrid row-columnar architecture**). TP and AP can then share the same set of F replicas. For heavy workloads like batch processing, it is recommended to configure Resource Manager for resource isolation.

### C read: Pure columnar store replica, suitable only for AP

* **ColumnStore replicas** (C replicas) are read-only and pure columnar, not participating in Paxos elections. They are dedicated to AP workloads.
* In a standalone topology, if you add a C replica to a tenant (e.g., an F replica in a single zone plus an independent C replica in a separate zone), the way AP traffic reaches the C replica **varies by version**:
  * **Before V4.6.0**: You must configure an **independent ODP** to route traffic **only to columnar replicas** (e.g., `route_target_replica_type = 'ColumnStore'` and `proxy_route_policy = 'TARGET_REPLICA_TYPE_FOLLOWER_ONLY'`) to achieve read isolation from TP.
  * **V4.6.0 and later**: After deploying the C replica in the tenant's locality, you only need to configure the **automatic selection of columnar replicas** without deploying an ODP for the C replica.
* Use cases: When the primary workload is analytical and you want to physically isolate read paths from TP; whether to use weak or strong reads depends on business requirements and [ob_read_consistency](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8700.ob_read_consistency-global.md) and the version.

**How to deploy C read** (C replicas in standalone or multi-zone deployments):

1. **Specify C replicas for the tenant**: When creating a tenant, specify C in the `LOCALITY` (e.g., `F@zone1,F@zone2,C@zone3`). For existing tenants, add a zone and node, create a resource pool, and then execute `ALTER TENANT ... LOCALITY` to add `C@zone4`. See [Deploy and use columnar replicas](150.uesing-columnstore-replica.md#cs-auto-routing) for the complete SQL.

2. **Configure access paths based on the version**
   * **OceanBase Database ≥ V4.6.0**: Configure `ap_query_route_policy` as described in [Deploy and use columnar replicas](150.uesing-columnstore-replica.md#cs-auto-routing). Applications can connect to OBServer or existing proxies without deploying an ODP for the C replica or configuring `route_target_replica_type`, `proxy_route_policy`, or `init_sql` for the ODP.
   * **OceanBase Database < V4.6.0**: Deploy an ODP (V4.3.2 or later) on a separate machine. Log in as `root@proxysys` and set the following parameters: `obproxy_read_consistency = 1`, `route_target_replica_type = 'ColumnStore'`, `proxy_route_policy='TARGET_REPLICA_TYPE_FOLLOWER_ONLY'`, and `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`. Verify with `SHOW PROXYCONFIG`.

3. **Verify**: Execute a typical AP query and confirm that the execution plan and monitoring data show that the data is sourced from the C replica (e.g., columnar scan operators). You can also check the row-to-column conversion progress using `DBA_OB_CS_REPLICA_STATS` or `CDB_OB_CS_REPLICA_STATS`.

## Deploy in a distributed topology

When you deploy in multiple zones, multiple IDCs, or across regions, you need to consider disaster recovery and load balancing in addition to replica types and routing.

### Use the Resource Manager to control resources for batch processing

* Batch processing, large-scale data import, and materialized view refresh are background AP tasks that consume a large amount of CPU and I/O resources, which may affect the performance of foreground TP or online AP queries.
* OceanBase Database provides the **Resource Manager** feature, which allows you to isolate resources and set limits for different types of tasks (such as materialized view refresh, MLOG purge, and batch processing tasks) to avoid resource exhaustion.
* We recommend that you configure a resource group or a Resource Manager strategy for batch processing tasks in a distributed AP architecture to ensure the stability of online TP/AP queries. For more information, see [DBA_OB_RSRC_DIRECTIVES](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/11020.o-dba_ob_rsrc_directives-of-mysql-mode.md).

#### How to deploy the Resource Manager for batch processing

In a distributed topology, if you need to rerun batch processing or materialized view tasks, you can configure a resource group or set CPU/IO limits for the corresponding tasks through the Resource Manager. You do not need to modify the replicas or the database proxy. For more information, see [DBA_OB_RSRC_DIRECTIVES](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/11020.o-dba_ob_rsrc_directives-of-mysql-mode.md) and the documentation on resource isolation.

### Columnstore replicas and routing strategy (distributed)

In a distributed topology, the planning of **columnstore replicas + routing** can be understood in two parts:

| Dimension | Before V4.6.0 (ODP accesses C replicas) | V4.6.0 and later |
| ---- | ------------------------------ | ------------- |
| **Replica type selection** | Specify `ColumnStore` for the `route_target_replica_type` parameter in ODP. This parameter cannot be combined with `Full` or `Readonly`. | The optimizer decides whether to execute tasks on columnstore replicas based on the `ap_query_route_policy` parameter. You can still use the `ob_route_policy` parameter as described in the version notes. |
| **Disaster recovery and fallback** | `proxy_route_policy`: When accessing columnstore replicas, the value is `TARGET_REPLICA_TYPE_FOLLOWER_ONLY`. | Whether to fallback to rowstore replicas when columnstore replicas are unavailable is controlled by the `ap_query_replica_fallback` parameter. For more information, see [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md#cs-auto-routing). |
| **Load balancing** | ODP LDC/IDC affinity: Configure `IDC`/`REGION` for the OBServer zone and `proxy_idc_name` for ODP. | If the connection still goes through ODP, the LDC rules still apply. If the connection directly connects to the OBServer, the load and replica selection logic on the OBServer side are used. |

#### How to deploy columnstore replicas in a distributed topology

1.  Specify C replicas in the tenant's locality (supporting multiple zones).

2. **If OceanBase Database is V4.6.0 or later**: Configure session or global variables as described in [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md). **You do not need to deploy an ODP separately for C replicas.**

3. **If OceanBase Database is earlier than V4.6.0**: Deploy an independent ODP (V4.3.2 or later) to access C replicas. Configure weak reads, set `route_target_replica_type='ColumnStore'`, `proxy_route_policy='TARGET_REPLICA_TYPE_FOLLOWER_ONLY'`, and `init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY'`.

4. Verify the request and row-to-column conversion progress. In a multi-IDC scenario, you can continue to configure the `IDC`/`REGION` for zones and the `proxy_idc_name` for ODP to achieve LDC affinity. For a complete locality example, see [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md).

## Columnstore replicas and routing strategy

### Readable replica type when accessing C replicas through ODP (route_target_replica_type)

Applicable to versions before V4.6.0.

* **Full**: A full replica (leader + follower) that participates in log synchronization and supports TP+AP.
* **Readonly**: A read-only replica for read scaling.
* **ColumnStore**: A columnstore replica for AP; **cannot be combined with Full or Readonly**. When configured for only columnstore, the disaster recovery strategy is fixed to disallow fallback to the primary replica, and `proxy_route_policy` must be set to `TARGET_REPLICA_TYPE_FOLLOWER_ONLY`.

### Routing and disaster recovery (proxy_route_policy)

Applicable to versions before V4.6.0.

* `TARGET_REPLICA_TYPE_WITH_LEADER`: Routes to both the primary and specified replicas, without disaster recovery logic.
* `TARGET_REPLICA_TYPE_FOLLOWER_FIRST`: Prioritizes specified-type replicas, falling back to the primary if all are unavailable.
* `TARGET_REPLICA_TYPE_FOLLOWER_ONLY`: Routes only to specified-type replicas, disconnecting if unavailable and not falling back to the primary; **this strategy is fixed when directing traffic to columnstore replicas**.

### Columnstore replica selection on the server side

Applicable to V4.6.0 and later.

* Based on `ap_query_route_policy`, `ap_query_cost_threshold`, and `ap_query_replica_fallback`. For more information, see [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md#cs-auto-routing).
* [ob_route_policy](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8900.ob_route_policy-global.md) specifies the replica type for optional reads on the OBServer.

### Load balancing (LDC/IDC)

* When **traffic passes through ODP**, ODP uses LDC to sort available replicas by IDC → Region → Cross-Region, achieving affinity and load balancing.
* Configure `IDC` and `REGION` for zones on the OBServer side and `proxy_idc_name` for ODP. For more information, see [ODP read/write splitting and routing strategy](../../700.reference/1200.database-proxy/700.route-management/400.odp-routing-policy/100.read-write-splitting.md) and [SQL routing](../../700.reference/100.oceanbase-database-concepts/600.data-link/200.database-proxy/200.sql-routing.md).

## Prerequisites and decision-making

### Prerequisites

Before deployment, ensure the following:

* **Version and path**: Based on the decision in the **「Version and Access Path Decision」** section, determine whether to use **ODP dedicated routing (for versions below V4.6.0)** or **columnstore replica auto-selection (for V4.6.0 and above)**.
* **ODP (only for versions below V4.6.0 accessing C replicas)**: The ODP accessing C replicas must be **V4.3.2 or later**. We recommend that you deploy ODPs for accessing C replicas separately from those for accessing F replicas.
* **Cluster and tenant**: The cluster has been deployed as planned (e.g., 2F1A or 3F). If you use C replicas, at least one zone is used to deploy C replicas, and we recommend that you deploy only C replicas in this zone.
* **Network and permissions**: The application and OBServer/ODP nodes are interconnected. The account for executing locality, tenant, and ODP configurations has the required permissions.

### Recommendations

| Scenario | Recommendation |
| ---- | ---- |
| Selection | If you need TP+AP and strong-consistency reads in the same database, use a hybrid row-columnstore table. If you need physical isolation of TP/AP and analysis queries on C replicas, use columnstore replicas and select ODPs or auto-selection variables based on the version. |
| Number of C replicas | Starting from V4.3.5 BP1, you can deploy multiple C replicas. We recommend that you deploy at most three C replicas. |
| Access to C replicas | **For versions below V4.6.0**: Use an independent ODP and routing variables. **For V4.6.0 and above**: You do not need to deploy ODPs separately for C replicas. We recommend that you deploy only C replicas in the zone where C replicas are located to avoid mixing with F or R replicas. |
| Batch processing and resources | If you need to rerun batch processing or refresh materialized views, we recommend that you configure the Resource Manager for resource isolation and limits. |
| Merging and DDL | Merging in C replicas is slower. You cannot initiate a new tenant-level merge until the current one is completed. DDL operations increase resource usage. We recommend that you perform DDL operations during off-peak hours. |

For more information, see [Deploy and use columnstore replicas](150.uesing-columnstore-replica.md#cs-auto-routing).
