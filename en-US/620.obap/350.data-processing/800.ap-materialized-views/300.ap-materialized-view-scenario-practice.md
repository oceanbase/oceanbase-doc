# Practice with materialized views

This topic provides **step-by-step SQL practice** in **MySQL mode** (e.g., `orders` tutorial, `tbl*` snippets, and **external table** full MV). You can follow the sections in order. **Use this with the [materialized view query acceleration](200.ap-materialized-view-query-acceleration.md) `sales` / `items` examples** for a complete end-to-end exercise.

## Build a real-time data warehouse using materialized views: scenario selection

To facilitate quick decision-making in real-time data warehouse construction, you can select based on the sequence "data freshness requirements -> computational complexity -> data source type".

| Use Cases | Recommended Feature Combination | Key Characteristics | Chapter |
| --- | --- | --- | --- |
| Dashboard for summary of periodic tasks, real-time updates | `REFRESH FAST` + Mlog + scheduling | Low incremental maintenance cost, suitable for stable aggregation of metrics | Getting Started; Scenario 2: Real-time metrics processing pipeline |
| Columnar scan + Query Rewriting (optional) | Columnar scan with a few columns queried | Use this feature for scenarios like operational analysis and report drilling | |
| Low-latency online query (computations triggered by queries) | `ENABLE ON QUERY COMPUTATION` | In exchange for simpler updates, computation occurs on the fly when a query is performed. Suitable for hot-query models. | Scenario 2: Real-time processing of metrics. |
| SQL transparent acceleration (minimal changes to business SQL required) | `ENABLE QUERY REWRITE` + alignment of indexes/metrics | Rewriting relies on matching rules; ideal for fixed analysis templates | Scenario 2: Real-time metric processing pipeline |
| After file data is ingested into the data lake, it is periodically loaded. | External tables + `REFRESH COMPLETE` | Data from files is synchronously loaded offline and then queried. | Scenario 3: Data from files is periodically loaded. |

The order of application of recommended practices is as follows:

1. **Define the scope and refresh strategy**: Clarify whether it is "incremental updates every minute" or "real-time calculation upon query".
2. **Re-refresh mechanism**: First evaluate whether FAST (Mlog) meets the criteria; if not, then use COMPLETE.
3. **Optimize the query side**: Add columnar storage, indexes, and query rewriting only as needed to avoid introducing too many variables at once.

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p>The real-time data warehouse does not necessarily mean "all queries are real-time." For most use cases, if acceptable latency is minutes, use FAST + scheduling; introduce <code>ENABLE ON QUERY COMPUTATION</code> only when there is a clear need for low latency and it's acceptable to pay the query execution cost. </p>
</main>

## Get started: Full and incremental refresh of an orders table

The following uses the **orders** table in the business database to demonstrate: how to maintain a materialized view by using the **default full maintain** option, how to maintain a materialized view by using the **Mlog + FAST** option, and how to manually refresh and automatically schedule a materialized view (for information about refreshing a materialized view, see [Refresh a materialized view](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/400.refresh-materialized-views-of-mysql-mode.md)).

### Create table, generate data, and create full materialized views

```sql
CREATE TABLE orders (
  order_id INT PRIMARY KEY,
  user_id INT,
  item_id INT,
  item_count INT,
  item_price INT,
  region VARCHAR(100)
);

INSERT INTO orders VALUES
  (1, 10001, 1, 20, 100, 'HZ'),
  (2, 10002, 1, 10, 150, 'BJ'),
  (3, 10001, 2, 50, 50, 'SH');

CREATE MATERIALIZED VIEW mv1
AS
SELECT region, SUM(item_count * item_price) AS sum_price
FROM orders
GROUP BY region;

SELECT * FROM mv1;
```

When you create a materialized view, it undergoes **initial materialization**; if you don't explicitly define a refresh strategy, you usually need to perform **a full manual refresh** to keep it continuously aligned with the base table.

### Perform a complete refresh manually (DBMS_MVIEW.REFRESH)

After you continue to write data to the base table, the result of the materialized view will not change automatically. You need to perform a refresh.

```sql
INSERT INTO orders VALUES
  (4, 10002, 2, 10, 100, 'SH'),
  (5, 10003, 1, 2, 20, 'HZ');

SELECT * FROM mv1;
```

Return result:

```shell
+--------+-----------+
| region | sum_price |
+--------+-----------+
| HZ     |      2000 |
| BJ     |      1500 |
| SH     |      2500 |
+--------+-----------+
3 rows in set
```

The result of the materialized view is not automatically updated. Execute the following SQL statement to manually refresh it:

```sql
CALL DBMS_MVIEW.REFRESH('mv1', 'c', refresh_parallel => 2);

SELECT * FROM mv1;
```

Returns a result such as:

```shell
+--------+-----------+
| region | sum_price |
+--------+-----------+
| HZ     |      2040 |
| BJ     |      1500 |
| SH     |      3500 |
+--------+-----------+
3 rows in set
```

`'c'` indicates a **complete refresh**; parameters like `refresh_parallel` follow the specifications in [DBMS_MVIEW.REFRESH](../../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/9950.dbms-mview-mysql/300.refresh-mysql.md).

Query the status of a refresh operation (example):

```sql
SELECT MVIEWS, METHOD, START_TIME, END_TIME
FROM oceanbase.DBA_MVREF_RUN_STATS;
```

### Switch to Incremental Refresh: Mlog + FAST

```sql
DROP MATERIALIZED VIEW mv1;

CREATE MATERIALIZED VIEW LOG ON orders
  WITH PRIMARY KEY, ROWID, SEQUENCE (item_count, item_price, region) INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW mv1(region, c, sum_price, cnt_price)
  REFRESH FAST
  ON DEMAND START WITH sysdate() NEXT sysdate() + INTERVAL 5 MINUTE
AS
SELECT region,
       COUNT(*) AS c,
       SUM(item_count * item_price) AS sum_price,
       COUNT(item_count * item_price) AS cnt_price
FROM orders
GROUP BY region;
```

After inserting a new order, observe the Mlog and then **manually incrementally refresh** it:

```sql
INSERT INTO orders VALUES (6, 10001, 3, 30, 70, 'HZ');

SELECT * FROM mlog$_orders;

CALL DBMS_MVIEW.REFRESH('mv1', 'f');

SELECT * FROM mlog$_orders;
SELECT region, sum_price FROM mv1;
```

If `START WITH ... NEXT ...` was specified when it was created, you can query the `DBA_SCHEDULER_JOBS` views for information about the job (field descriptions depend on the version).

### Purge order

When deleting a materialized view, materialized view log, and base table, note that you must delete the materialized view first, then the materialized view log, and finally the base table. (If the base table is still bound to the materialized view log, directly using `DROP TABLE` may result in errors).

```sql
DROP MATERIALIZED VIEW mv1;
DROP MATERIALIZED VIEW LOG ON orders;
DROP TABLE orders;
```

## Scenario 1: Operating analysis and report query

In operational analytics and report query scenarios, common issues include tables with many columns in the details, large scan ranges, and frequent changes in query conditions.

Scenarios in this category are typically read-oriented and are well-suited for reducing the scanning of irrelevant columns by using a columnar stored materialized view. Additionally, the performance of queries can be further optimized by combining this with indexes and query rewriting when necessary.

This section provides a simple example of how to use columnar materialized views to support wide table queries and multidimensional analysis.

```sql
CREATE TABLE IF NOT EXISTS tbl1 (col1 INT PRIMARY KEY, col2 VARCHAR(20), col3 INT);

CREATE MATERIALIZED VIEW mv_ec_tbl1
    WITH COLUMN GROUP(each column)
    AS SELECT *
       FROM tbl1;
```

In the case of using **query rewriting**, ensure that the rewritten conditions can utilize the indexes on the materialized view (for details, see [Query rewriting](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/500.materialized-views-rewrite-of-mysql-mode.md)).

```sql
CREATE INDEX idx1_mv_ec_tbl1 ON mv_ec_tbl1(col1);
```

## Scenario 2: Real-time metric calculation and query

In real-time metric scenarios, common requirements include hierarchical aggregation, incremental maintenance, low-latency queries, and minimal changes to business SQL.

These scenarios typically require a combination of capabilities rather than a single one. Depending on the business's timeliness requirements, nested materialized views, materialized view logs, FAST refresh, real-time materialized views, and query rewriting can be used together.


### Nested materialized views

When a query involves multiple layers of aggregation or steps of processing, intermediate results can be stored in one materialized view, and then another layer of materialized view can be created based on that. This approach is suitable for hierarchical precomputation scenarios, allowing complex metrics to be maintained in multiple steps.

```sql
CREATE TABLE IF NOT EXISTS tbl3(id INT, name VARCHAR(30), PRIMARY KEY(id));
CREATE TABLE IF NOT EXISTS tbl4(id INT, age INT, PRIMARY KEY(id));

CREATE MATERIALIZED VIEW mv1_tbl3_tbl4 (PRIMARY KEY (id1, id2))
    REFRESH COMPLETE
    AS SELECT tbl3.id id1, tbl4.id id2, tbl3.name, tbl4.age
        FROM tbl3, tbl4
        WHERE tbl3.id = tbl4.id;

CREATE MATERIALIZED VIEW mv_mv1_tbl3_tbl4
    REFRESH COMPLETE
    AS SELECT SUM(age) age_sum
        FROM mv1_tbl3_tbl4;

CREATE MATERIALIZED VIEW mv1_mv1_tbl3_tbl4
    REFRESH COMPLETE INCONSISTENT
    AS SELECT SUM(age) age_sum
        FROM mv1_tbl3_tbl4;
```

If a layer undergoes a full refresh, any dependent nested materialized views typically need to be fully refreshed again before incremental refreshes are performed (see the documentation on creation and refresh).

### Materialized view logs and FAST refresh

If the business prioritizes refresh efficiency over recalculating all data from scratch, consider using materialized view logs with FAST refresh. This method records changes in the base table and processes only incremental data during refreshes.

For OceanBase Database V4.3.5, the **Mlog automatic management** feature is supported starting from V4.3.5 BP4 and is not supported in V4.5.0. When **Mlog automatic management** is not enabled, you must create the mlog before creating a `REFRESH FAST` materialized view.

```sql
CREATE TABLE IF NOT EXISTS tbl5 (col1 INT PRIMARY KEY, col2 INT, col3 INT);

CREATE MATERIALIZED VIEW LOG ON tbl5
    WITH SEQUENCE (col2, col3) INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW mv_tbl5
    REFRESH FAST
    AS SELECT col2, COUNT(*) cnt, COUNT(col3) cnt_col3, SUM(col3) sum_col3
       FROM tbl5
       GROUP BY col2;

CALL DBMS_MVIEW.REFRESH('mv_tbl5');
CALL DBMS_MVIEW.REFRESH('mv_tbl5', 'c');
```

### Real-time materialized views

For scenarios requiring higher query timeliness and nearly real-time results, but where frequent manual refreshes are not feasible, assess whether real-time materialized views are suitable. This approach uses query-time computation to achieve higher data freshness.

```sql
CREATE TABLE IF NOT EXISTS tbl2(col1 INT, col2 INT, col3 INT);

CREATE MATERIALIZED VIEW LOG ON tbl2
    WITH PRIMARY KEY, ROWID, SEQUENCE (col1, col2, col3) INCLUDING NEW VALUES;

CREATE MATERIALIZED VIEW mv_tbl2_rt
    ENABLE ON QUERY COMPUTATION
    AS SELECT col1, COUNT(*) AS cnt
       FROM tbl2
       GROUP BY col1;
```

### Query rewriting (ENABLE QUERY REWRITE)

If you want to minimize changes to business SQL and allow the optimizer to automatically use materialized view results, combine this with query rewriting. Query rewriting is suitable for fixed analysis scenarios, but whether it is triggered depends on whether the query conditions match the materialized view definitions.

```sql
CREATE TABLE IF NOT EXISTS test_tbl1 (col1 INT, col2 INT, col3 INT);
CREATE TABLE IF NOT EXISTS test_tbl2 (col1 INT, col2 INT, col3 INT);

CREATE MATERIALIZED VIEW mv_test_tbl1_tbl2
    ENABLE QUERY REWRITE
    AS SELECT t1.col1 col1, t1.col2 t1col2, t1.col3 t1col3, t2.col2 t2col2, t2.col3 t2col3
    FROM test_tbl1 t1, test_tbl2 t2
    WHERE t1.col1 = t2.col1;

SET query_rewrite_enabled = 'force';

SELECT COUNT(*), test_tbl1.col1 col1
FROM test_tbl1, test_tbl2
WHERE test_tbl1.col1 = test_tbl2.col1 AND test_tbl2.col2 > 10
GROUP BY col1;
```

## Scenario 3: File data import and regular refresh

When data comes from files instead of online business tables, you can first use an external table to read the file data and then create a full-refresh materialized view based on that external table. This approach is suitable for periodic updates, offline synchronization queries, and regular data ingestion in lakehouse scenarios.

Starting from V4.3.5 BP2, you can create **full-refresh** materialized views with an external table as the base. First, configure `secure_file_priv`, prepare the external file, and execute `CREATE EXTERNAL TABLE` (for complete steps, see [Create a materialized view — Based on an external table](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/300.create-materialized-views-of-mysql-mode.md)).

```sql
CREATE EXTERNAL TABLE ext_tbl1 (
    id INT,
    name VARCHAR(50),
    c_date DATE
)
LOCATION = '/home/admin'
FORMAT = (
  TYPE = 'CSV'
  FIELD_DELIMITER = ','
  FIELD_OPTIONALLY_ENCLOSED_BY = '\''
)
PATTERN = 'ext_tbl1.csv';

CREATE MATERIALIZED VIEW mv_ext_tbl1
    REFRESH COMPLETE
    AS SELECT * FROM ext_tbl1;
```

For more information about external tables, see: [Import data using an external table](../../300.obap-data-collection/300.obap-import-data/30.external-table.md) and [Overview of external tables](../../400.data-lake/200.external-table/100.external-table-overview.md).
