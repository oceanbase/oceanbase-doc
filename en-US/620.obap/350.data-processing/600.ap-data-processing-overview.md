# Data processing in OceanBase

Data processing involves cleaning, transforming, integrating, and aggregating raw data to make it more suitable for analysis, application, or presentation. In the **AP / Data Warehouse** scenario of OceanBase, common data processing paths can be categorized into three types:

* **SQL / PL**: Use SQL within the tenant to perform transformations and data loading, and orchestrate execution using asynchronous jobs, scheduled tasks, etc.
* **Materialized views**: Convert repetitive computations into refreshable materialized results, reducing the cost of online analytical processing (OLAP) by combining incremental/real-time processing with query rewriting.
* **External computing (e.g., Flink)**: Perform stream and batch processing or modeling in external engines such as Flink, DataWorks, and dbt, and then synchronize or write the results to OceanBase.

## SQL/PL batch processing and task scheduling within the database

Use SQL (and PL packages in Oracle mode) directly within the database to perform batch writes, overwrites, and periodic scheduling. This is suitable for scenarios with short data processing chains where computation needs to be close to the data.

### `INSERT OVERWRITE SELECT` operation

The `INSERT OVERWRITE SELECT` operation is used to insert query results into a target table and overwrite existing data in the target table. It is primarily used in data cleaning and transformation processes to efficiently batch insert processed data into the database. This operation ensures atomicity, meaning that if any exceptions occur during execution, the entire operation will be rolled back.

#### Use cases

+ When you need to batch import data and overwrite the target table, the `INSERT OVERWRITE SELECT` operation provides a convenient method.
+ When you want to replace existing data in the target table with new data during data cleaning.
+ When the source table can be an internal or external table in the database.

#### Syntax example

```sql
INSERT [/*+PARALLEL(N)*/] OVERWRITE table_name [(list_of_columns)] [PARTITION (partition_name, ...)] select_stmt;
```

#### Considerations

+ Use this operation with caution, as it will delete all data from the target table or partition. Ensure that you have backed up your data to prevent accidental data loss.
+ Ensure that the data returned by the `SELECT` query matches the structure of the target table to avoid data insertion failures.
+ The difference between `INSERT INTO SELECT` and `INSERT OVERWRITE SELECT` is that `INSERT INTO SELECT` does not clear the target table or partition before inserting the processed data, and the processed data is incrementally written to the target table.
+ Do not use `INSERT OVERWRITE SELECT` to write data to the same table as real-time write operations (such as `INSERT INTO`, `REPLACE INTO`, `DELETE`, and `UPDATE`), as the real-time data will be discarded.

For more information about this operation, see [Use the INSERT OVERWRITE SELECT statement to insert data in MySQL mode](../../300.develop/100.application-development-of-mysql-mode/400.write-data-of-mysql-mode/100.insert-data-of-mysql-mode-in-develop.md) and [Use the INSERT OVERWRITE SELECT statement to insert data in Oracle mode](../../300.develop/200.application-development-of-oracle-mode/400.write-data-of-oracle-mode/100.insert-data-of-oracle-mode-in-develop.md).

### Submit job (`Submit Job`)

In OceanBase Database, the job submission feature allows users to submit and execute complex data processing tasks. These tasks can include batch data processing, ETL (extract, transform, load) jobs, or other background data processing operations. When using `INSERT INTO` or `INSERT OVERWRITE SELECT` to import data, the default execution mode is synchronous. For large data volumes, this may require prolonged session keep-alive. Therefore, for large-scale data scenarios, it is recommended to submit data import tasks asynchronously.

#### Use cases

+ Regular execution of complex data processing operations such as batch data import, data cleaning, and report generation.
+ Scheduling large-scale data migration or transformation tasks.

#### Submit job example

```sql
-- Submit a job.
SUBMIT JOB INSERT OVERWRITE test
SELECT ex1.c1,t2.c2,sum(ex1.c3)
FROM ex1,t2
WHERE ex1.id = t2.id
GROUP BY ex1.c1,t2,c2;
-- Query the status of an asynchronous task.
SHOW JOB STATUS WHERE job='job_id';
```

Jobs typically consist of multiple steps, such as data extraction, transformation, and loading, ensuring the full data processing workflow is automated.

For more information about the syntax and behavior, see [SUBMIT JOB (MySQL mode)](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/8750.submit-job-of-mysql-mode.md).

### Scheduled jobs

A scheduled job is a job that is executed at specified intervals. By using scheduled jobs, you can automate data processing and reduce the cost of manual maintenance.

#### Scenarios

+ Periodically clean up expired data, generate reports, and synchronize data.
+ Automatically execute data processing jobs at specific times or periodically.

#### Example of creating a scheduled job

- **MySQL mode**: Use the `Event Scheduler` command to create a scheduled job.

```sql
-- Create a scheduled job
CREATE EVENT myevent
    ON SCHEDULE AT '2024-12-26 00:00:00' + INTERVAL 1 DAY
    DO
      INSERT INTO test SELECT * FROM ex_test WHERE date_key = curdate();

-- View the scheduled job
SELECT * FROM information_schema.events WHERE event_name='myevent';
```

- **Oracle mode**: Use the `DBMS_SCHEDULER` system package to create a scheduled job.

```sql
-- Create a scheduled job
BEGIN
    DBMS_SCHEDULER.CREATE_JOB(
        job_name         => 'myscheduler',                      -- The name of the job.
        job_type         => 'STORED_PROCEDURE',                 -- The type of the job is a stored procedure.
        job_action       => 'data_cleaning',                    -- The stored procedure to be executed.
        number_of_argument => 0,                                -- No parameters are required.
        start_date       => SYSDATE,                            -- The time when the job starts to be executed.
        repeat_interval  => 'FREQ=DAILY; INTERVAL=1',           -- The job is executed once a day.
        end_date         => NULL,                               -- The job is executed indefinitely.
        job_class        => 'DEFAULT_JOB_CLASS',                -- The job class is default.
        enabled          => TRUE,                               -- The job is enabled.
        auto_drop        => TRUE,                               -- The job is automatically deleted after it is completed.
        comments         => 'Daily scheduled data cleaning and conversion',               -- The comment of the job.
        credential_name  => NULL,                               -- No credentials are required.
        destination_name => NULL,                               -- No destination database is required.
        max_run_duration => 0                                   -- No maximum runtime is specified.
    );
    COMMIT;
END;
/
-- View the scheduled job
SELECT * FROM DBA_SCHEDULER_JOBS WHERE job_name = 'myscheduler';
SELECT * from DBA_SCHEDULER_JOB_RUN_DETAILS WHERE job_name ='myscheduler';
```

## Materialized views: Precomputation, refresh, and query rewriting

Materialized views can be used to materialize the results of wide tables, aggregations, and multi-table joins. These results can be refreshed in full, incrementally, or in real time. By combining columnar storage and query rewriting, materialized views can reduce the need for repeated scans and aggregations on detail tables.

* **[Accelerate queries with materialized views](800.ap-materialized-views/200.ap-materialized-view-query-acceleration.md)**: A set of examples that demonstrate how to use materialized views for full, incremental, and real-time refreshes, nested views, columnar storage, query rewriting, and indexing.

## External computing (Flink, etc.): ecosystem and stream-batch integration

Complex stream processing, cross-system ETL, or cloud vendor-managed pipelines are typically handled in **OceanBase external computing engines** (such as **Flink**, DataWorks, dbt, and AWS Glue), and then synchronized or loaded into OceanBase.

For information about tool selection, Flink CDC links, and ODC, see **[Data processing tools](700.ap-data-processing-etl-tools.md)**.
