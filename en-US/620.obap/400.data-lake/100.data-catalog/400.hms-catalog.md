# HMS catalog

OceanBase Database V4.4.1 and later support HMS (Hive Metastore) connections, allowing users to create HMS catalogs. This feature enables unified access to tables managed by Hive Metastore, including traditional Hive tables and Iceberg-formatted tables with metadata registered in Hive Metastore. Users can directly query data managed by HMS in the Hadoop ecosystem without data migration, ideal for accelerating data lake queries.

- Unified metadata management: Automatically synchronize table structures through Hive Metastore.
- Federated queries: Join and analyze data with internal OceanBase tables.
- Read-only security: Prevent accidental modifications to source data.

OceanBase Database officially supports HMS catalog functionality starting from V4.4.1. This document is provided in the V4.3.5 documentation collection to help users understand and plan for OceanBase Database's AP capabilities.

## Supported features

- **Read-only access**: All objects under HMS catalog are read-only. Currently, no DML/DDL operations such as `INSERT`, `UPDATE`, or `DROP TABLE` are supported.

- **Supported table types**:

  + **Hive tables**: ORC, Parquet, TextFile, and CSV.

    * In the current version, only the ARRAY type of Parquet format is supported for complex types.
    * For more information about the ARRAY type, see [Overview of array element types](../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/1200.array-data-type-of-mysql-mode/100.array-data-type-overview-of-mysql-mode.md).

  + **Iceberg tables**: V1 and V2. Parquet format is recommended.

- **Advanced features**:

  + Iceberg schema evolution (column addition and deletion)
  + Iceberg partition transformation (such as bucket() and year() partition expressions)

- **Hive version compatibility**

  + Supported versions: Hive 1.2.x, Hive 2.3.x, Hive 3.1.x, and Hive 4.x.
  + **Notes on Iceberg table compatibility**:
    * Hive 4.x and later: Hive natively supports Iceberg tables. You can create and update Iceberg tables in Hive and directly access them through HMS catalog in OceanBase Database.
    * Hive 1.2.x, 2.3.x, and 3.1.x: Hive does not support Iceberg tables. In such environments, Iceberg tables are typically created and written to by computing engines such as Spark or Flink, and their metadata is registered in the Hive Metastore. OceanBase Database relies on this metadata to identify and read Iceberg tables.

      Therefore, as long as the metadata of Iceberg tables is correctly registered in the Hive Metastore (regardless of the engine used to write them), OceanBase Database can access them.

## Prerequisites

1. **Environment dependencies**: If the underlying storage is HDFS, you must deploy the Java SDK environment.
For more information, see [Deploy the OceanBase Java SDK environment](../../../400.deploy/300.deploy-oceanbase-enterprise-edition/500.deploy-the-ob-java-sdk-environment.md).

2. **Permissions**

   - HMS service: The OceanBase cluster must be able to access Hive Metastore (Thrift protocol).
     The address and port of the HMS service must be provided by the customer's operations and maintenance team. The default port for open-source Hive is 9083, but this may vary in actual deployment. Please refer to the on-site configuration.

   - Storage system: All OBServer nodes must be readable from HDFS, S3, or OSS.

## Syntax for creating an HMS catalog

```sql
CREATE EXTERNAL CATALOG [IF NOT EXISTS] catalog_name
PROPERTIES (
    TYPE = 'HMS',
    URI = 'thrift://host:port',
    [PRINCIPAL = '...'],
    [KEYTAB = '...'],
    [KRB5CONF = '...'],
    [MAX_CLIENT_POOL_SIZE = 20],
    [SOCKET_TIMEOUT = 10000000]
);
```

## Parameters

| Parameter | Required | Description |
|------|----------|----------|
| TYPE | Yes | Fixed to `'HMS'` |
| URI | Yes | The Thrift address of HMS. Format: `thrift://$host:$port`<ul><li> `$host`: specifies the IP address of Thrift. </ul></li><ul><li> `$port`: specifies the port of Thrift. The IP address and port of HMS are provided by the customer's O&M team. In an open-source Hive cluster, the default port is 9083. However, the actual port may vary in a deployed cluster. </ul></li>If high availability mode is enabled for your HMS, you can specify multiple HMS addresses separated by commas, for example: `"thrift://<HMS IP address 1>:<HMS port number 1>,thrift://<HMS IP address 2>:<HMS port number 2>,thrift://<HMS IP address 3>:<HMS port number 3>"`. |
| PRINCIPAL | No | The Kerberos principal, which is usually in the `service/HOST@REGION.com` format. Example: `hive/hadoop@QA.COM`. |
| KEYTAB | No | The path of the KEYTAB key file required to access the HMS service enabled with Kerberos authentication. If the OceanBase cluster is deployed in a distributed manner, the file must exist on all nodes of the corresponding OBServer. **Notice**: The KEYTAB parameter is required only when Kerberos authentication is enabled for HMS. |
| KRB5CONF | No | The path of the Kerberos configuration file, such as `/etc/krb5.conf`. If the OceanBase cluster is deployed in a distributed manner, the file must exist on all nodes of the corresponding OBServer. |
| MAX_CLIENT_POOL_SIZE | No | The size of the HMS client connection pool. Default value: 20. This value indicates the maximum number of HMS clients that can be started to connect to the HMS service. |
| SOCKET_TIMEOUT | No | The timeout for connecting to the Hive metastore, in microseconds. Default value: 10000000 (10 seconds). |

## Create an HMS catalog with SIMPLE authentication

The SIMPLE authentication mode does not require location authentication.

```sql
obclient> CREATE EXTERNAL CATALOG test_hms_catalog
    PROPERTIES = (
        TYPE = 'HMS',
        URI = "thrift://xxx.xxx.xxx.xxx:xxxx"
    );
```

For more information about Hadoop authentication modes, see the "Authentication mechanisms for HMS catalogs and HDFS storage" section below.

## Create an HMS catalog with Kerberos authentication

For more information about Hadoop authentication modes, see the section "Authentication mechanisms of an HMS catalog and an HDFS storage" in the following sections.

### Step 1: Create an HMS catalog with Kerberos authentication (metadata layer)

```sql
CREATE EXTERNAL CATALOG hms_kerberos
PROPERTIES (
    TYPE = 'HMS',
    URI = 'thrift://hms.example.com:9083',
    PRINCIPAL = 'hive/hms.example.com@EXAMPLE.COM',
    KEYTAB = '/etc/ob/hive.keytab',
    KRB5CONF = '/etc/krb5.conf'
);
```

### Step 2: Create an HDFS location with Kerberos authentication (data layer)

```sql
CREATE LOCATION hdfs_kerberos_ha
URL = 'hdfs://namenode:8020/'
CREDENTIAL (
    PRINCIPAL = "ob_hdfs@EXAMPLE.COM",
    KEYTAB   = "/etc/ob/hdfs.keytab",
    KRB5CONF = "/etc/krb5.conf",
    CONFIGS  = '...'  -- For more information, see the HA configuration in the preceding steps.
);
```

The HMS catalog can discover the table structure, and the HDFS location can securely read the HDFS data files.

## Switch a catalog

```sql
SET CATALOG hms_catalog;
```

## Query an external data source by using a catalog

```sql
-- Hive table
SELECT city, COUNT(*) FROM hive_db.customer WHERE dt >= '2025-04-01' GROUP BY city;

-- Iceberg table
SELECT product_id, SUM(sales) FROM iceberg_db.sales_iceberg WHERE event_time >= '2025-04-01' GROUP BY product_id;

-- Federated query
SELECT o.order_id, h.city
FROM internal.test_db.orders o
JOIN hms_catalog.hive_db.customer h ON o.user_id = h.id;
```

## Authentication mechanisms for HMS catalog and HDFS storage

In OceanBase Database, accessing Hive Metastore (HMS) involves two independent authentication layers:

- **Catalog layer**: This layer is used to connect to Hive Metastore and retrieve metadata such as table structure and partitions.

- **Location layer**: This layer is used to read data files stored in file systems such as HDFS.

The authentication methods for these two layers must be configured separately and must align with the security policies of the Hadoop cluster.

### The authentication mode of Hadoop is determined by the server

The Hadoop cluster defines its security mode through the `hadoop.security.authentication` configuration item in `hdfs-site.xml`:

```xml
<property>
  <name>hadoop.security.authentication</name>
  <value>kerberos</value> <!-- or simple -->
</property>
```

- `kerberos`: Enables Kerberos authentication. All clients (including HMS Client and HDFS Client) must pass Kerberos authentication.
- `simple`: Uses the operating system user (i.e., the user who started the process) for permission verification without Kerberos.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This configuration is located on the Hadoop server side (<code>$HADOOP_HOME/etc/hadoop/hdfs-site.xml</code>). OceanBase does not directly read this file but adapts to this mode through its own catalog and Location configurations.</p>
</main>

### Authentication configurations of OceanBase

| Hadoop mode | HMS catalog configuration | HDFS Location configuration |
|-------------|------------------|--------------------|
| SIMPLE | Do not specify the authentication method when you create a catalog. The default value is SIMPLE. | <ul><li>If the HDFS directory is readable by all users (such as the directory with the permission `drwxr-xr-x`), you do not need to create a location. </ul></li><ul><li>If the directory is accessible only by specific users (such as the owner hive or impala), you must explicitly specify the HDFS user with the `CREATE LOCATION ... CREDENTIAL (USER = 'xxx')` statement. <ul><li> |
| KERBEROS | Specify `AUTHENTICATION = 'KERBEROS'` when you create a catalog, and provide `PRINCIPAL`, `KEYTAB`, and `KRB5CONF`. | You must create an HDFS location with Kerberos authentication, and provide Principal, Keytab, and krb5.conf. |

**Important configuration rules**: If Kerberos is enabled for HMS or HDFS, check whether the deployment is correct.

### Two authentication modes

#### SIMPLE mode (common in development and testing environments)

**Scenarios:**

- Kerberos is not enabled for HDFS, and Linux file permissions are used for control.

- The table is written by a specific user (for example, the Impala user, whose HDFS path owner is impala, or the Hive on Tez user, whose HDFS path owner is the job submitter, such as hive).

**Configuration requirements:**

- **Anonymous readable path**: The HDFS directory has open permissions (such as drwxr-xr-x), allowing any user to read it. In this case, you do not need to create a location.
- **Restricted path**: If the OceanBase Database observer process user (such as admin) is not in the directory authorization user or group, you must:

  + Create a location and specify the user with permissions:

    ```sql
    CREATE LOCATION my_loc URI = 'hdfs://mycluster/'
    CREDENTIAL = (USER = 'username');
    ```

##### Scenario 1: No Kerberos authentication and no need to specify an HDFS user (default anonymous)

- **Applicable to**: Development or testing environments where Kerberos authentication is not enabled for the HDFS cluster (i.e., hadoop.security.authentication=simple).

- **Operation**: No need to create a location.

##### Scenario 2: No Kerberos authentication, but need to specify an HDFS user

- **Applicable to**: Development or testing environments where Kerberos authentication is not enabled for the HDFS cluster (i.e., `hadoop.security.authentication=simple`), but the data files of the target Hive table are stored in a restricted HDFS path (such as a path written by Impala, Hive, or another engine, whose owner is a specific user and does not have global read permissions).

- **Typical situations**:

  + The Impala user writes the table to an HDFS path whose owner is impala.
  + The Hive job submitter writes the table to an HDFS path whose owner is a specific user, such as hive or etl_user.
  + By default, the OceanBase Database observer uses the operating system user (such as admin) to access HDFS. If this user does not have read permissions, the query fails.

- **Example**: Assume that the HDFS path of a Hive table written by Impala is `hdfs://namenode:8020/warehouse/sales.db/click_log`.

```sql
CREATE LOCATION hdfs_impala_data
URL = 'hdfs://namenode:8020/'    -- URL, see the following description
CREDENTIAL (
  USER = 'username'  -- Specify the username for accessing HDFS.
);
```

**How to determine the correct URL:**

1. Execute the following statement in Hive CLI or Beeline:

   ```sql
   SHOW CREATE TABLE your_db.your_table;
   ```

2. Check the LOCATION field in the output, for example:

   ```sql
   LOCATION 'hdfs://namenode:8020/warehouse/your_db.db/your_table'
   ```

3. Extract the protocol, service name, and port number as the URL. In other words, the URL in CREATE LOCATION is `hdfs://namenode:8020/`.

##### Scenario 3: No Kerberos authentication and HDFS is highly available (HA)

**Operation**: No need to set the PRINCIPAL, KEYTAB, and KRB5CONF parameters.

```sql
CREATE LOCATION hdfs_location_ha
    URL = 'hdfs://${nameservice_id}'  -- We recommend that you use the logical service name.
    CREDENTIAL (
        CONFIGS = 'dfs.nameservices=${nameservice id}#dfs.ha.namenodes.${nameservice id}=${namenode1}, ${namenode2}#dfs.namenode.rpc-address.${nameservice id}.${namenode1}=${namenode 1 address}#dfs.namenode.rpc-address.${nameservice id}.${namenode2}=${namenode 2 address}#dfs.ha.automatic-failover.enabled.${nameservice id}=true#dfs.client.failover.proxy.provider.${nameservice id}=org.apache.hadoop.hdfs.server.namenode.ha.ConfiguredFailoverProxyProvider'
        );
```

#### KERBEROS mode (Production environment)

**Applicable scenarios:**

- Enterprise-level Hadoop clusters where Kerberos authentication is enabled for HMS or HDFS.

**Configuration requirements:**

- **HMS catalog**:

  ```sql
  CREATE EXTERNAL CATALOG hms_krb
    PROPERTIES (
      'type' = 'hms',
      'hive.metastore.uris' = 'thrift://metastore:9083',
      'authentication' = 'KERBEROS',
      'kerberos.principal' = 'ob@REALM',
      'kerberos.keytab' = '/path/to/ob.keytab',
      'kerberos.krb5.conf' = '/etc/krb5.conf'
    );
  ```

- **HDFS Location**:

  ```sql
  CREATE LOCATION hdfs_krb_loc
    URI = 'hdfs://nn:8020',
    CREDENTIAL = (
      KERBEROS = (
        PRINCIPAL = 'ob@REALM',
        KEYTAB = '/path/to/ob.keytab',
        KRB5CONF = '/etc/krb5.conf'
      )
    );
  ```

##### Scenario 4: Kerberos is enabled, and HDFS is a single NameNode (non-HA mode)

```sql
-- Create a LOCATION with Kerberos authentication and a single HDFS node
CREATE LOCATION hdfs_kerberos_single
URL = 'hdfs://namenode.example.com:8020/'   -- Obtain the complete HDFS path of the table by executing the SHOW CREATE TABLE statement, and extract the root URL.
CREDENTIAL (
  PRINCIPAL = "hdfs/TEST@EXAMPLE.COM",
  KEYTAB   = "/data/hdfs.keytab",
  KRB5CONF = "/data/krb5.conf",
  CONFIGS  = 'dfs.data.transfer.protection=integrity'
);
```

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p><ul><li>The <code>dfs.data.transfer.protection</code> parameter in <code>CONFIGS</code> specifies the security level of the HDFS data transfer channel, such as <code>authentication</code>, <code>integrity</code>, <code>privacy</code>, or <code>null</code>. </ul></li><ul><li>The value of this parameter must be consistent with the value of <code>dfs.data.transfer.protection</code> in the <code>hdfs-site.xml</code> file of the Hadoop cluster. Otherwise, the data read operation may fail due to a mismatch in the security strategy. </ul></li><ul><li>We recommend that you obtain the actual value of this parameter from the Hadoop administrator or directly view the <code>hdfs-site.xml</code> file of the HDFS cluster. </ul></li></p>
</main>

##### Scenario 5: Kerberos is enabled, and HDFS is in high availability (HA) mode

```sql
CREATE LOCATION hdfs_kerberos_ha
URL = 'hdfs://${nameservice id}'  -- We recommend that you use the logical service name.
CREDENTIAL (
    PRINCIPAL = "ob_hdfs@EXAMPLE.COM",
    KEYTAB   = "/etc/ob/hdfs.keytab",
    KRB5CONF = "/etc/krb5.conf",
    CONFIGS  = 'dfs.data.transfer.protection=integrity#dfs.nameservices=mycluster#dfs.ha.namenodes.mycluster=nn1,nn2#dfs.namenode.rpc-address.mycluster.nn1=nn1:8020#dfs.namenode.rpc-address.mycluster.nn2=nn2:8020#dfs.client.failover.proxy.provider.mycluster=org.apache.hadoop.hdfs.server.namenode.ha.ConfiguredFailoverProxyProvider'
);
```

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p><ul><li>Deploy the same keytab and krb5.conf files on all OBServer nodes. </ul></li><ul><li>If the "Unknown Host" error occurs, add the HDFS node mapping to the /etc/hosts file. </ul></li></p>
</main>

## Configuration notes

- **Authentication separation**: Catalog (metadata) and Location (data) authentication are configured independently.
- **Mode alignment**: The authentication method of OceanBase must be consistent with the `hadoop.security.authentication` setting of the Hadoop cluster.
- **Kerberos consistency**: If either HMS or HDFS is enabled with Kerberos, both must be configured with Kerberos credentials.
- **Permissions in SIMPLE mode**: Ensure that the Observer user or the specified USER has read permissions for the HDFS path.
