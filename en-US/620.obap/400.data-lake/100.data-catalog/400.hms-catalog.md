# HMS Catalog

OceanBase Database supports HMS (Hive Metastore) since V4.4.1. You can use HMS to create an HMS catalog and access Hive-managed tables, including traditional Hive tables and Iceberg tables whose metadata is registered in Hive Metastore. This way, you can query data managed by HMS in the Hadoop ecosystem without data migration, which is suitable for accelerating data lake queries.

- Unified metadata management: The schema of Hive-managed tables is automatically synchronized with that of tables in OceanBase Database.
- Federated query: Join analysis can be performed between tables in OceanBase Database and Hive-managed tables.
- Read-only security: Prevents accidental modification of source data.

OceanBase Database supports the HMS catalog since V4.4.1. This topic provides the usage instructions for the HMS catalog in the V4.3.5 documentation set to help you understand and plan the AP capabilities of OceanBase Database.

## Supported capabilities

- **Read-only access**: All objects under HMS Catalog are read-only. Currently, you cannot execute DML/DDL operations such as `INSERT`, `UPDATE`, and `DROP TABLE`.

- **Supported table types**:

  + **Hive tables**: ORC, Parquet, TextFile, and CSV.

    * In the current version, only the ARRAY type in Parquet format is supported for complex types.
    * For more information about the ARRAY type, see [Overview of array element types](../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/1200.array-data-type-of-mysql-mode/100.array-data-type-overview-of-mysql-mode.md).

  + **Iceberg tables**: V1, V2, and V3. Parquet format is recommended.

- **Advanced features**:

  + Iceberg schema evolution (add and drop columns)
  + Iceberg partition transformation (such as bucket() and year() partition expressions)

- **Hive version compatibility**

  + Supported versions: Hive 1.2.x, Hive 2.3.x, Hive 3.1.x, and Hive 4.x.
  + **Compatibility with Iceberg tables**:
    * Hive 4.x and later: Hive engine natively supports Iceberg tables. You can create tables and update metadata through Hive. OceanBase Database can directly access these tables through HMS Catalog.
    * Hive 1.2.x, 2.3.x, and 3.1.x: Hive does not support Iceberg tables. In such environments, Iceberg tables are typically created and written by computing engines like Spark or Flink, and their metadata is registered in the Hive Metastore. OceanBase Database relies on this metadata to identify and read Iceberg tables.

      Therefore, as long as the metadata of Iceberg tables is correctly registered in the Hive Metastore (regardless of the engine used for writing), OceanBase Database can access them.

## Prerequisites

1. **Environment dependencies**: If HDFS is used as the underlying storage, the Java SDK environment must be deployed in advance.
For more information, see [Deploy the OceanBase Java SDK environment](../../../400.deploy/300.deploy-oceanbase-enterprise-edition/500.deploy-the-ob-java-sdk-environment.md).

2. **Permissions**

   - HMS service: The OceanBase cluster must have access to Hive Metastore (Thrift protocol).
     The address and port of the HMS service must be provided by the customer's operations team. Open-source Hive typically uses port 9083 by default, but this may vary in actual deployments. Please refer to the on-site configuration.

   - Storage system: All OBServer nodes must be readable from HDFS/S3/OSS.

## Syntax for creating an HMS catalog

```sql
CREATE EXTERNAL CATALOG [IF NOT EXISTS] catalog_name
PROPERTIES (
    TYPE = 'HMS',
    URI = 'thrift://host:port',
    [PRINCIPAL = '...'],
    [KEYTAB = '...'],
    [KRB5CONF = '...'],
    [MAX_CLIENT_POOL_SIZE = 20],
    [SOCKET_TIMEOUT = 10000000]
);
```

## Parameter description

| Parameter | Required | Description |
|------|----------|----------|
| TYPE | Yes | Fixed to `'HMS'`. |
| URI | Yes | The Thrift address of HMS. Format: `thrift://$host:$port`<ul><li> `$host`: specifies the IP address of Thrift. </ul></li><ul><li> `$port`: specifies the port of Thrift. The IP address and port number of HMS are provided by the customer's O&M team. In an open-source Hive cluster, the default port number is 9083. However, the actual port number may vary in a deployed cluster. </ul></li>If high availability mode is enabled for your HMS, you can specify multiple HMS addresses separated by commas. Example: `"thrift://<HMS IP address 1>:<HMS port number 1>,thrift://<HMS IP address 2>:<HMS port number 2>,thrift://<HMS IP address 3>:<HMS port number 3>"`. |
| PRINCIPAL | No | The Kerberos principal, in the `service/HOST@REGION.com` format. Example: `hive/hadoop@QA.COM`. |
| KEYTAB | No | The path of the KEYTAB key file required to access the HMS service with Kerberos authentication enabled. If OceanBase Database is deployed in a distributed manner, the corresponding OBServer nodes on all machines must have this file. **Notice**: The KEYTAB parameter is required only when Kerberos authentication is enabled for HMS. |
| KRB5CONF | No | The path of the Kerberos configuration file, such as `/etc/krb5.conf`. If OceanBase Database is deployed in a distributed manner, the corresponding OBServer nodes on all machines must have this file. |
| MAX_CLIENT_POOL_SIZE | No | The size of the HMS client connection pool. Default value: 20. This indicates that up to 20 clients can be started to connect to the HMS service. |
| SOCKET_TIMEOUT | No | The timeout period for connecting to the Hive metastore, in microseconds. Default value: 10000000 (10s). |

## Create an HMS catalog with SIMPLE authentication

In SIMPLE authentication mode, no location authentication is required.

```sql
obclient> CREATE EXTERNAL CATALOG test_hms_catalog
    PROPERTIES = (
        TYPE = 'HMS',
        URI = "thrift://xxx.xxx.xxx.xxx:xxxx"
    );
```

For more information about Hadoop authentication modes, see the "Authentication mechanisms for HMS catalogs and HDFS storage" section below.

## Create an HMS catalog with Kerberos authentication

For more information about the authentication modes of Hadoop, see the Authentication mechanisms of HMS catalogs and HDFS storage section.

### Step 1: Create an HMS catalog with Kerberos authentication (metadata layer)

```sql
CREATE EXTERNAL CATALOG hms_kerberos
PROPERTIES (
    TYPE = 'HMS',
    URI = 'thrift://hms.example.com:9083',
    PRINCIPAL = 'hive/hms.example.com@EXAMPLE.COM',
    KEYTAB = '/etc/ob/hive.keytab',
    KRB5CONF = '/etc/krb5.conf'
);
```

### Step 2: Create an HDFS location with Kerberos authentication (data layer)

```sql
CREATE LOCATION hdfs_kerberos_ha
URL = 'hdfs://namenode:8020/'
CREDENTIAL (
    PRINCIPAL = "ob_hdfs@EXAMPLE.COM",
    KEYTAB   = "/etc/ob/hdfs.keytab",
    KRB5CONF = "/etc/krb5.conf",
    CONFIGS  = '...'  -- HA configurations as described above
);
```

The HMS catalog can discover the table schema, and the HDFS location can securely read the data files.

## Switch Catalog

```sql
SET CATALOG hms_catalog;
```

## Query external data sources through the catalog

```sql
-- Hive table
SELECT city, COUNT(*) FROM hive_db.customer WHERE dt >= '2025-04-01' GROUP BY city;

-- Iceberg table
SELECT product_id, SUM(sales) FROM iceberg_db.sales_iceberg WHERE event_time >= '2025-04-01' GROUP BY product_id;

-- Federated query
SELECT o.order_id, h.city
FROM internal.test_db.orders o
JOIN hms_catalog.hive_db.customer h ON o.user_id = h.id;
```

## Authentication mechanisms for HMS catalog and HDFS storage

In OceanBase Database, accessing Hive Metastore (HMS) involves two independent authentication layers:

- **Catalog layer**: This layer is used to connect to Hive Metastore and retrieve metadata such as table structures and partitions.

- **Location layer**: This layer is used to read data files stored in file systems like HDFS.

The authentication methods for these two layers must be configured separately and must align with the security policies of the Hadoop cluster.

### The Hadoop authentication mode is determined by the server

The Hadoop cluster defines its security mode through the `hadoop.security.authentication` configuration item in `hdfs-site.xml`:

```xml
<property>
  <name>hadoop.security.authentication</name>
  <value>kerberos</value> <!-- or simple -->
</property>
```

- `kerberos`: Enables Kerberos authentication. All clients (including HMS Client and HDFS Client) must pass Kerberos authentication.
- `simple`: The Hadoop server trusts the client's declared operating system username and does not verify passwords or credentials. Permission control is based solely on the owner, group, and POSIX permission bits (e.g., `drwxr-xr-x (755)`) of HDFS files and directories, without Kerberos authentication.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This configuration is located on the Hadoop server (<code>$HADOOP_HOME/etc/hadoop/hdfs-site.xml</code>). OceanBase does not directly read this file but adapts to the mode through its own Catalog and Location configurations.</p>
</main>

### Authentication configuration in OceanBase

| Hadoop mode | HMS catalog configuration | HDFS location configuration |
|-------------|------------------|--------------------|
| SIMPLE | No authentication method is specified when creating the catalog (default is SIMPLE). | <ul><li>If the HDFS directory is readable by all users (e.g., with permission `drwxr-xr-x`), no location needs to be created.</ul></li><ul><li> If the directory is accessible only to specific users (e.g., owner is hive or impala), you must explicitly specify the HDFS user with `CREATE LOCATION ... CREDENTIAL (USER = 'xxx')`.<ul><li> |
| KERBEROS | Specify `AUTHENTICATION = 'KERBEROS'` when creating the catalog, and provide `PRINCIPAL`, `KEYTAB`, and `KRB5CONF`. | You must create an HDFS location with Kerberos authentication, and provide Principal, Keytab, and krb5.conf |

**Important configuration rules**: If Kerberos is enabled for HMS or HDFS, check whether the deployment is correct.

### Two authentication modes

#### SIMPLE mode (common in development and testing environments)

**Scenarios:**

- Kerberos is not enabled for HDFS, and Linux file permission control is used.

- Tables are written by specific users (for example, the owner of the HDFS path written by Impala is impala, and the owner of the HDFS path written by Hive on Tez is the user who submits the job, such as hive).

**Configuration requirements:**

- **Anonymous readable path**: ● The HDFS directory has open permissions (such as drwxr-xr-x (755)), and any user can read without creating a location.
  + Meaning: The owner has read, write, and execute permissions (rwx = 4+2+1 = 7);
The group and other users have only read and execute permissions (r-x = 4+0+1 = 5);
  + In such paths, OceanBase Database does not need to create a location and can directly access the path.

- **Restricted path**: If the user of the OceanBase Database observer process (such as admin) is not in the authorized user or group of the directory, you must:

  + Create a location and specify a user with permissions:

    ```sql
    CREATE LOCATION my_loc URI = 'hdfs://mycluster/'
    CREDENTIAL = (USER = 'username');
    ```

##### Scenario 1: No Kerberos authentication and no need to specify an HDFS user (default anonymous access)

- **Applicable to**: Development or testing environments where Kerberos authentication is not enabled for the HDFS cluster (i.e., hadoop.security.authentication=simple).

- **Operation**: No need to create a location.

##### Scenario 2: No Kerberos authentication, but need to specify an HDFS user

- **Applicable to**: Development or testing environments where Kerberos authentication is not enabled for the HDFS cluster (i.e., `hadoop.security.authentication=simple`), but the data files of the target Hive table are stored in a restricted HDFS path (for example, written by Impala, Hive, or another engine, with the path owner being a specific user and without global read permissions).

- **Typical cases**:

  + The HDFS path owner is impala when the table is written by Impala.
  + The HDFS path owner is hive or etl_user when the table is written by a Hive job.
  + The OceanBase Database observer process, by default, accesses HDFS as the operating system user (such as admin). If this user does not have read permissions, the query will fail.

- **Example**: Assume that a Hive table is written by Impala, and the HDFS path is `hdfs://namenode:8020/warehouse/sales.db/click_log`.

```sql
CREATE LOCATION hdfs_impala_data
URL = 'hdfs://namenode:8020/'    -- URL, see the following description
CREDENTIAL (
  USERNAME = 'username'  -- Specify the username for accessing HDFS
);
```

**How to determine the correct URL:**

1. Execute the following command in Hive CLI or Beeline:

   ```sql
   SHOW CREATE TABLE your_db.your_table;
   ```

2. View the LOCATION field in the output, for example:

   ```sql
   LOCATION 'hdfs://namenode:8020/warehouse/your_db.db/your_table'
   ```

3. Extract the protocol, service name/host name, and service port as the URL. In other words, fill in `hdfs://namenode:8020/` in the URL of CREATE LOCATION.

##### Scenario 3: Kerberos is not enabled, and HDFS is highly available (HA)

**Operation**: No need to set the PRINCIPAL, KEYTAB, and KRB5CONF parameters.

```sql
CREATE LOCATION hdfs_location_ha
    URL = 'hdfs://${nameservice_id}'  -- It is recommended to use the logical service name
    CREDENTIAL (
        CONFIGS = 'dfs.nameservices=${nameservice id}#dfs.ha.namenodes.${nameservice id}=${namenode1}, ${namenode2}#dfs.namenode.rpc-address.${nameservice id}.${namenode1}=${namenode 1 address}#dfs.namenode.rpc-address.${nameservice id}.${namenode2}=${namenode 2 address}#dfs.ha.automatic-failover.enabled.${nameservice id}=true#dfs.client.failover.proxy.provider.${nameservice id}=org.apache.hadoop.hdfs.server.namenode.ha.ConfiguredFailoverProxyProvider'
        );
```

#### Kerberos mode (standard for production environments)

**Applicable scenarios:**

- Enterprise-level Hadoop clusters where Kerberos authentication is enabled for HMS or HDFS.

**Configuration requirements:**

- **HMS Catalog**:

  ```sql
  CREATE EXTERNAL CATALOG hms_krb
    PROPERTIES (
      'type' = 'hms',
      'hive.metastore.uris' = 'thrift://metastore:9083',
      'authentication' = 'KERBEROS',
      'kerberos.principal' = 'ob@REALM',
      'kerberos.keytab' = '/path/to/ob.keytab',
      'kerberos.krb5.conf' = '/etc/krb5.conf'
    );
  ```

- **HDFS Location**:

  ```sql
  CREATE LOCATION hdfs_krb_loc
    URI = 'hdfs://nn:8020',
    CREDENTIAL = (
      KERBEROS = (
        PRINCIPAL = 'ob@REALM',
        KEYTAB = '/path/to/ob.keytab',
        KRB5CONF = '/etc/krb5.conf'
      )
    );
  ```

##### Scenario 4: Kerberos is enabled, and HDFS is a single NameNode (non-HA mode)

```sql
-- Create a LOCATION: Kerberos authentication + single HDFS
CREATE LOCATION hdfs_kerberos_single
URL = 'hdfs://namenode.example.com:8020/'   -- Obtain the complete HDFS path of the table by executing the SHOW CREATE TABLE statement, and extract the root URL.
CREDENTIAL (
  PRINCIPAL = "hdfs/TEST@EXAMPLE.COM",
  KEYTAB   = "/data/hdfs.keytab",
  KRB5CONF = "/data/krb5.conf",
  CONFIGS  = 'dfs.data.transfer.protection=integrity'
);
```

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p><ul><li>The <code>dfs.data.transfer.protection</code> parameter in <code>CONFIGS</code> specifies the security level of the HDFS data transmission channel, such as <code>authentication</code>, <code>integrity</code>, <code>privacy</code>, or <code>null</code>.</ul></li><ul><li>This value must be exactly the same as the <code>dfs.data.transfer.protection</code> parameter configured in the <code>hdfs-site.xml</code> file of the Hadoop cluster. Otherwise, the data read operation may fail due to a mismatch in the security policies.</ul></li><ul><li>We recommend that you confirm the actual value of this parameter with the Hadoop administrator or directly view the <code>hdfs-site.xml</code> file of the HDFS cluster.</ul></li></p>
</main>

##### Scenario 5: Kerberos is enabled, and HDFS is highly available (HA)

```sql
CREATE LOCATION hdfs_kerberos_ha
URL = 'hdfs://${nameservice id}'  -- We recommend that you use the logical service name.
CREDENTIAL (
    PRINCIPAL = "ob_hdfs@EXAMPLE.COM",
    KEYTAB   = "/etc/ob/hdfs.keytab",
    KRB5CONF = "/etc/krb5.conf",
    CONFIGS  = 'dfs.data.transfer.protection=integrity#dfs.nameservices=mycluster#dfs.ha.namenodes.mycluster=nn1,nn2#dfs.namenode.rpc-address.mycluster.nn1=nn1:8020#dfs.namenode.rpc-address.mycluster.nn2=nn2:8020#dfs.client.failover.proxy.provider.mycluster=org.apache.hadoop.hdfs.server.namenode.ha.ConfiguredFailoverProxyProvider'
);
```

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p><ul><li>Deploy the same keytab and krb5.conf files on all OBServer nodes.</ul></li><ul><li>If you encounter an "Unknown Host" error, add the HDFS node mapping to the /etc/hosts file. </ul></li></p>
</main>

For more information about the Location parameters, see [Create Location](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000003980422).

## Configuration notes

- **Authentication separation**: Catalog (metadata) and Location (data) authentication are configured separately.
- **Mode alignment**: The authentication method of OceanBase must be consistent with the `hadoop.security.authentication` setting of the Hadoop cluster.
- **Kerberos consistency**: If either HMS or HDFS is enabled with Kerberos, both must be configured with Kerberos credentials.
- **Permissions in SIMPLE mode**: Ensure that the Observer user or the specified USER has read permissions for the HDFS path.
