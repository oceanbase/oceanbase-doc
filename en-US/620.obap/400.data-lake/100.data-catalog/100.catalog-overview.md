# Data catalog overview

OceanBase supports the ODPS catalog starting with V4.3.5 BP2. In V4.4.1, OceanBase further introduced the HMS catalog (Hive Metastore Catalog), enabling seamless access to both data lakes and offline data warehouses. With this feature, users can run standard SQL queries directly on Hive tables, Iceberg tables managed by Hive Metastore (HMS), and offline tables in MaxCompute (ODPS).

These tables are typically stored in efficient columnar formats like Parquet or ORC, within distributed storage systems such as HDFS, OSS, or S3. They form a critical part of an enterprise's core data lake.

OceanBase goes beyond simple metadata integration—it is not just about being able to "read" data from the lake. OceanBase serves as a high-performance compute engine, delivering significant query acceleration for data lake sources. This is made possible by several built-in analytical optimizations:

- **Predicate pushdown and column pruning:** WHERE clauses and SELECT column information are pushed down to the data source (for example, the ODPS Storage API or HDFS file reader).
- **Parallel execution and vectorized computation:** Large table scans are automatically parallelized, and the vectorized engine efficiently processes columnar data.
- **External table data caching (optional):** For frequently accessed static lake tables, OceanBase can cache data files to reduce latency for repeated queries.

Thanks to these capabilities, users do not need to migrate raw data from the data lake or data warehouse into the database. OceanBase enables query acceleration directly on:

- Real-time business tables within OceanBase, such as orders or user profiles.
- Historical logs, wide tables, or Iceberg tables in the data lake (like user behavior or IoT time-series data), as well as offline tables in cloud-native warehouses like ODPS.

This makes OceanBase a true **entry point for data lake queries**, delivering a federated analytics experience: **query once, access all your data**. With a single SQL statement, you can seamlessly access data across both the database and the data lake. This greatly simplifies cross-source analytics and makes working with data lakes easier and more efficient.

| Cross-IDC deployment recommendation | HDFS storage dependency |
|----------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| If HMS and OBServer are deployed across IDCs, network latency can cause metadata retrieval to take up to seconds, significantly increasing query latency. It is recommended to deploy HMS and OBServer within the same low-latency network.   | When the underlying storage is HDFS, Java Runtime Environment (JRE) (JDK 8 or 11) must be deployed on the OBServer node, and Java support must be enabled (`enable_java = true`). ## Relationship between catalogs and external tables

OceanBase provides two modes for accessing external data:

| Mode | Applicable scenarios | Metadata management | Typical usage |
|------|----------|------------|----------|
| Catalog mode<br>(Such as HMS catalog and ODPS catalog) | Predefined, structured data sources (such as Hive data warehouses and ODPS projects) | Automatic metadata synchronization | `SET CATALOG my_hms;`<br>`SELECT * FROM db1.sales;` |
| Explicit external tables<br>(file/JDBC/ODPS external tables) | Temporary files, custom paths, or non-catalog data sources | Manual table creation and structure definition | `CREATE EXTERNAL TABLE t1 (...) LOCATION = 'oss://...';` |

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><ul><li>A catalog is a metadata abstraction of the underlying data (such as Parquet/ORC files and ODPS tables).<ul><li>Currently, HMS catalog only supports integration with Hive Metastore and cannot directly point to any HDFS path. To access files not registered in HMS, use the <code>CREATE EXTERNAL TABLE ... LOCATION</code> method.</ul></li></ul></p>
</main>

## Catalog types

In OceanBase, a catalog is a top-level namespace for organizing and isolating metadata from different data sources. OceanBase supports the following catalog types:

| Catalog type | Data source | Supported table types | Typical scenarios |
|--------------|--------|------------|----------|
| Internal catalog | OceanBase local storage | OceanBase tables | Core internal business data |
| ODPS catalog | Alibaba Cloud MaxCompute (ODPS) | ODPS tables | Big data offline analysis |
| HMS catalog | Hive Metastore (HMS) | Hive tables, Iceberg tables | Hadoop ecosystem integration |

## Create a catalog

The built-in internal catalog in OceanBase is used to manage the metadata of the database itself and does not need to be manually created. To use external data sources, you can execute the [`CREATE EXTERNAL CATALOG`](../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/2150.create-external-catalog-of-mysql-mode.md) statement to create an ODPS catalog or HMS catalog.

## Access a catalog

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Currently, only OceanBase Database's MySQL mode supports the data catalog feature. </p>
</main>

### View the catalogs of the current tenant

You can execute the `SHOW CATALOGS;` statement to view all catalogs created under the current tenant.

Example:

```sql
SHOW CATALOGS;
```

### View data in a catalog

You can execute any query operation on tables in a catalog, or perform a join query across catalogs.

Example:

```sql
SELECT * FROM internal.ap_db.ap_table, odps_catalog.odps_db.odps_table;
```

### Query data across catalogs

OceanBase Database allows you to access data in multiple catalogs (such as internal, hive_catalog, and odps_catalog) in a single SQL statement to perform a join query. You can use the following two methods to reference tables in a different context.

**Core principle:**

- If you do not switch the session context, you must use the complete three-part identifier: `catalog_name.database_name.table_name;`
- If you have switched to the target catalog and database, you can directly use the abbreviated table name.

#### Method 1: Use the three-part identifier (no context switch required)

Regardless of the current catalog, you can use the `catalog.db.table` three-part identifier to directly access tables in any catalog.

**Example 1: Query a table in the HMS catalog**

```sql
-- View the current session context
SELECT CURRENT_CATALOG();   -- Returns 'internal'
SELECT DATABASE();  -- Or use SELECT SCHEMA(); to return the current database, such as 'ap_db'

-- Query a table in the Hive catalog across catalogs
SELECT * FROM hive_catalog.hive_db.hive_table;
```
You can also use the `catalog.db.table` three-part identifier to directly access local tables in the HMS catalog.

**Example 2: Perform a join query across catalogs (mixed sources)**

```sql
-- Assume the current context is internal.ap_db
SELECT CURRENT_CATALOG();   -- Returns 'internal'
SELECT DATABASE();  -- Or use SELECT SCHEMA(); to return the current database, such as 'ap_db'

-- Query tables in both the HMS catalog and the local catalog
SELECT h.*, o.*
FROM hive_catalog.hive_db.hive_table h
JOIN internal.ap_db.ap_table o ON h.id = o.id;
```

#### Method 2: Switch the session context and use the abbreviated table name

You can explicitly switch the current session's catalog and database using `SET CATALOG` and `USE`, and then directly use the table name without any prefix.

**Example: Perform a join query in the hive_catalog.hive_db catalog**
```sql
-- Switch the catalog and database
SET CATALOG hive_catalog;
USE hive_db;

-- Verify the current context
SELECT CURRENT_CATALOG();   -- Returns 'hive_catalog'
SELECT DATABASE();  -- Returns 'hive_db'

-- You can now directly reference tables in hive_db, such as hive_table.
-- You can also still use the three-part identifier to access other catalogs, such as internal.
SELECT h.*, o.*
FROM hive_table h                      -- Abbreviated: current catalog + DB
JOIN internal.ap_db.ap_table o ON h.id = o.id;
```

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p><ul><li>If you do not execute <code>SET CATALOG</code> and <code>USE</code>, and directly write <code>SELECT * FROM hive_table;</code>, an error will occur. This is because the system will search for the table in the current catalog (such as internal). </ul></li><ul><li>Switching the context only affects subsequent statements and does not affect the connection or transaction state. </ul></li></p>
</main>



For more information, see [View CATALOG](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/950.manage-catalog-of-mysql-mode/300.view-catalog-of-mysql-mode.md)

### Switch catalogs

You can execute the `SET CATALOG catalog_name;` statement to switch to a catalog, or explicitly specify the catalog in a query:

```sql
SELECT * FROM odps_catalog.database_name.table_name;
```

For more information about the SQL syntax, see [SET CATALOG](../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/8250.set-catalog-of-mysql-mode.md)

## Supported features of HMS/ODPS catalog

### Supported features of HMS catalog

**Access mode**

- **Read-only access**: All objects in HMS catalog are read-only. You cannot execute DML/DDL operations such as `INSERT`, `UPDATE`, and `DROP TABLE`.

**Supported table types**

| Table type | Supported formats | Description |
|--------|----------|------|
| Hive table | ORC, Parquet, TextFile, and CSV | - Only the ARRAY type in Parquet format is supported for complex types.<br>For more information, see [Overview of array element types](../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/1200.array-data-type-of-mysql-mode/100.array-data-type-overview-of-mysql-mode.md). |
| Iceberg table | V1/V2 (Parquet is recommended) | Supports advanced features such as schema evolution (addition and deletion of columns) and partition transform (such as `bucket()` and `year()`). |

**Hive version compatibility**

| Hive version | Iceberg support |
|-----------|------------------|
| Hive 4.x | Hive engine natively supports Iceberg tables. You can create or update an Iceberg table in Hive. OceanBase Database can directly access the table through HMS catalog. |
| Hive 1.2.x / 2.3.x / 3.1.x | Hive engine does not support Iceberg tables. However, if an Iceberg table is created by an engine such as Spark or Flink and its metadata is registered in the Hive Metastore, OceanBase Database can still read the table. |

Key principle: If the metadata of an Iceberg table is correctly registered in HMS (regardless of which engine writes the table), OceanBase Database can access the table.

### Supported features of ODPS catalog

- **Supported operations**: Analytical queries such as `SELECT`, `JOIN`, and `GROUP BY`;
- **Unsupported operations**: Write operations and DDL operations such as `INSERT`, `UPDATE`, and `DROP TABLE`;
- **Optimization capabilities**: Automatic partition pruning and column pruning to reduce the amount of data transmitted from ODPS.

## Catalog privilege management

OceanBase Database supports fine-grained privilege management at the catalog level. Users must have the appropriate privileges to create, switch to, or query external catalogs (such as ODPS and HMS).

- Catalog privileges are divided into two levels:

  * User Level (global level): Applies to all catalogs (corresponding to *.* in MySQL mode)
  * Catalog Level (object level): Applies only to the specified catalog

### Privilege system in MySQL-compatible mode

| Privilege | Scope | Description |
|------|----------|------|
| `CREATE CATALOG` | User Level | Allows the execution of `CREATE` and `DROP EXTERNAL CATALOG` |
| `USE CATALOG` | User Level or Catalog Level | Allows `SET CATALOG`, `SHOW CATALOGS`, and `SELECT FROM catalog.db.table` |

### Syntax

**Grant global privileges**

This is suitable for administrators who need to operate on any catalog:

```sql
GRANT CREATE CATALOG ON *.* TO 'user1';
GRANT USE CATALOG ON *.* TO 'user1' WITH GRANT OPTION;

REVOKE CREATE CATALOG ON *.* FROM 'user1';
REVOKE USE CATALOG ON *.* FROM 'user1';
```

**Grant specific catalog privileges**

This is suitable for regular users who only need to access a specific catalog (recommended approach):

```sql
-- Grant the USE and SELECT privileges on the catalog 'odps_prod'
GRANT SELECT, USE CATALOG ON CATALOG odps_prod TO 'user1' WITH GRANT OPTION;

-- Revoke the privileges
REVOKE USE CATALOG ON CATALOG odps_prod FROM 'user1';
```

**Important notes:**

1. **The creator automatically has privileges**

After a user successfully executes `CREATE EXTERNAL CATALOG ...`, they automatically gain the `USE CATALOG` and `SELECT` privileges on that catalog, without needing additional authorization.

Example:

```sql
-- user1 executes
CREATE EXTERNAL CATALOG odps_dev TYPE = 'ODPS' ...;

-- At this point, user1 can directly use this catalog
SET CATALOG odps_dev;
SELECT * FROM project_db.table1 LIMIT 1;
```

2. **Catalog privileges ≠ Data access privileges**

Even if a user has the `USE CATALOG` and `SELECT` privileges, querying tables within the catalog may still fail. The reasons are:

  * Catalog level: Used to connect to the Hive Metastore (to retrieve metadata such as table structure and partitions)
  * Location level: Used to read data files stored in file systems like HDFS

Authentication methods for both levels need to be configured separately and must align with the security policies of the Hadoop cluster.

Example:

```sql
-- user1 has the USE CATALOG privilege on odps_prod
SET CATALOG hms_prod;
USE sales_db;

-- Querying the table fails
SELECT * FROM sales_log LIMIT 1;
-- An error occurs

-- Reason: No location is created, or user1 does not have access privileges for this location
-- Solution: Create a location with authentication information
CREATE LOCATION hms_sales URL = 'hdfs://nn:8020/sales/'
  CREDENTIAL (USER = 'username');
```
For more information about the authentication mechanism between HMS catalogs and HDFS storage, see [HMS Catalog](400.hms-catalog.md).

### Privilege verification example

```sql
-- Grant privileges
GRANT SELECT, USE CATALOG ON CATALOG ca1 TO zhangsan WITH GRANT OPTION;

-- View privileges
SHOW GRANTS FOR zhangsan;
```

Output:

```shell
+-------------------------------------------------------------------------+
| Grants for zhangsan@%                                                      |
+-------------------------------------------------------------------------+
| GRANT USAGE ON *.* TO 'zhangsan'                                           |
| GRANT SELECT, USE CATALOG ON CATALOG `ca1` TO 'zhangsan' WITH GRANT OPTION |
+-------------------------------------------------------------------------+
```
