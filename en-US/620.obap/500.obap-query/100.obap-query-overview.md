# Overview of query acceleration

## What is query acceleration

In analytical processing (AP) scenarios, a single query often requires scanning massive amounts of data, performing complex aggregations, and executing joins. Query response time (RT) and resource utilization directly determine analysis efficiency and the business experience. **Query acceleration** refers to using the optimizer, parallel execution, and targeted configurations to make analytical SQL run faster, more stably, and with lower resource consumption. This enables shorter response times and more predictable resource usage without significantly rewriting business SQL.

## How to accelerate queries

OceanBase accelerates queries in AP scenarios through two main approaches:

- **Optimizer-side**: Enable the optimizer to generate better execution plans based on accurate and timely statistics (including row/column storage path selection, distributed plans, and SkipIndex utilization), avoiding high-cost plans such as full table scans or incorrect join orders.
- **Execution-side**: Leverage CPU and I/O through parallel query execution (multi-threading/multi-machine collaboration) to shorten the RT for individual queries. Combined with an appropriate degree of parallelism (manual DOP or Auto DOP), this accelerates queries while controlling resource contention.

## When to accelerate queries

It is recommended to proactively configure and tune query acceleration in the following situations:

- **Analysis on large tables or partitioned tables**: Tables/partitions contain a large amount of data. Full or wide-range scans take a long time. Accurate statistics are needed to choose the row/column storage path and scan scope, and parallelism should be used to improve throughput and shorten RT.
- **After batch import or large-scale updates**: Data changes are significant, and default statistics may not be updated or may be inaccurate, leading to suboptimal execution plans. You can enable online statistics collection, use maintenance windows, or collect statistics manually, and enable or adjust parallelism when needed.
- **Analytical query RT does not meet requirements**: If the bottleneck is confirmed to be in the plan or parallel resources, first check whether the statistics are timely and accurate, then evaluate whether to enable Auto DOP or increase the manual DOP and related parameters.
- **Resource contention caused by concurrent queries**: System load is too high after enabling parallelism. Limit the parallel threshold and upper limit using parameters such as `parallel_degree_limit` and `parallel_min_scan_time_threshold`, or combine this with resource group/tenant isolation for overall management.

For the above scenarios, you can configure and tune step by step in the order of **table structure, then statistics and parallelism**, to achieve better execution plans, shorter response times, and more controllable resource usage in AP scenarios.
