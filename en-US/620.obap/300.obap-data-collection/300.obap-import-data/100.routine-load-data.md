# Import data from Kafka using Routine Load

## Overview

Routine Load is a feature introduced in **V4.6.0** of OceanBase Database that allows for continuous data import from Kafka. After executing the `CREATE ROUTINE LOAD` statement to create a job, the system automatically pulls messages from Kafka and writes them to the target table at scheduled intervals, eliminating the need for repeated execution of import commands. This is ideal for real-time data import scenarios.

**Execution mechanism**: Routine Load leverages OceanBase Database's **DBMS Scheduler** for periodic task execution. When a job is created, a periodic task is registered in the scheduler. The task is triggered at the configured frequency, automatically completing the process of connecting to Kafka, consuming messages, parsing and converting them, writing to the target table, and updating the consumption offset. Therefore, Routine Load is a "declarative configuration, background execution" import method, where users only need to create, pause, resume, or stop jobs, without manually writing DML statements.

This topic describes how to use the Routine Load feature of OceanBase Database to continuously consume data from an Apache Kafka cluster and import it into a specified OceanBase table, achieving near-real-time data synchronization.

## Prerequisites

Before using Routine Load, ensure the following:

* OceanBase Database version is **≥ V4.6.0**.
* The **target table has been created**, and the current user has the **INSERT** privilege on the target table.
* The **Kafka cluster is reachable**, and it provides valid broker addresses (`bootstrap.servers`).
* The **Kafka topic exists**, and the current account has the consumption privilege on the topic. If SASL/SSL authentication is enabled for Kafka, configure the corresponding security parameters in the job parameters.
* The Kafka message content is in **CSV format** and matches the column structure (number of columns, types, order, etc.) of the target table or can be mapped using `COLUMNS`.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Routine Load is suitable for continuous and stable Kafka data streams. For one-time bulk data imports, we recommend using `LOAD DATA` or the direct load feature.</p>
</main>

## Limitations

| Item | Description |
| ---- | ---- |
| Data source | Only **Apache Kafka** is supported as the data source. |
| Data format | Only **CSV** format is supported. |
| bootstrap.servers | Only the broker list of **one** Kafka cluster can be configured. Mixing addresses from multiple clusters is not allowed, as the behavior is undefined. |
| Consumption offset (offset) | The `kafka_offsets` value cannot be less than the current **low watermark** of the Kafka server's partition. It is not recommended to set it higher than the **high watermark**, as the behavior will be determined by the Kafka server parameter `auto.offset.reset`. |
| Target table and privileges | The target table must already exist. If the table does not exist or the privileges are insufficient, the job will enter an error state and needs to be stopped, corrected, and the job recreated. |

## Create a Routine Load job

### Syntax

```sql
CREATE ROUTINE LOAD job_name ON table_name
[LOAD PROPERTIES (load_property_list)]
FROM STREAM '(' job_properties_expr ')';
```

* `job_name`: the name of the job, which must be unique within the current tenant and is used to identify the Routine Load job.
* `table_name`: the name of the destination table, to which the data will be imported.
* `LOAD PROPERTIES`: optional. The data loading properties, such as the concurrency, column mapping, partition, conflict strategy, and filter conditions.
* `FROM STREAM`: the data source type. Currently, only Kafka is supported. `job_properties_expr` specifies the Kafka and format-related configurations.

### LOAD PROPERTIES (optional)

| Parameter | Description | Default value |
| ---- | ---- | ------ |
| `PARALLEL = n` | The number of threads involved in data consumption. | `1` |
| `COLUMNS (col1, col2, ...)` | The mapping between the columns of the Kafka message and the destination table. | Corresponds to the columns of the message and the destination table in order. |
| `PARTITION (p1, p2, ...)` | The destination partitions to import data to. | If not specified, the data is written to the partitions based on the routing rules. |
| `IGNORE` / `REPLACE` | The strategy to handle primary key or unique key conflicts: ignore the conflicting rows or overwrite the conflicting rows. | Selected based on business requirements. |
| `WHERE condition` | The row-level filter condition. Only rows that meet the condition are written to the destination table. | None. |

### FROM STREAM: Kafka and format configurations (job_properties_expr)

`job_properties_expr` is a key-value pair. **The key names are case-sensitive.** In addition to the format configurations, you can also specify Kafka standard consumer parameters, such as `security.protocol` and `sasl.mechanism`. **You do not need to** specify `group.id`. The system will automatically establish the correspondence between the consumption threads and partitions based on the concurrency.

#### Required and commonly used Kafka parameters

| Parameter (key name) | Description | Required | Default value/Description |
| ------------ | ---- | ---- | -------------- |
| `bootstrap.servers` | The list of Kafka broker addresses, separated by commas, such as `broker1:9092,broker2:9092`. This specifies the entry address for clients to connect to Kafka for the first time. | Yes | — |
| `kafka_topic` | The name of the Kafka topic to consume. | Yes | — |
| `kafka_partitions` | The list of partitions to consume, such as `"0,1,2"`. If not provided, all partitions of the topic are consumed. | No | All partitions |
| `kafka_offsets` | The starting consumption offset for each partition, corresponding to `kafka_partitions`. If only one value is specified, it applies to all partitions. Supports numeric values, `OFFSET_BEGINNING`, and `OFFSET_END`. | No | `OFFSET_END` (consumes from the latest message) |
| `max_batch_interval` | The **maximum running time** for each import thread in each round, in seconds. | No | `60` |
| `max_batch_rows` | The **maximum number of messages** that each import thread can read in each round. Must be **≥ 200000**. | No | `10000000` |
| `max_batch_size` | The **maximum number of bytes** that each import thread can read in each round, in bytes. The range is 100 MB to 1 GB. | No | `1073741824` (1 GB) |

**Term explanations**:

* **offset (consumption offset)**: the logical position of each message in a Kafka partition. `OFFSET_BEGINNING` indicates the earliest readable message in the partition, and `OFFSET_END` indicates the latest position.
* **low / high watermark**: the minimum and maximum offset that can be consumed in a Kafka partition. The specified offset must not be lower than the low watermark.

#### FORMAT (CSV parsing options)

Only the **CSV** format is supported. The syntax aligns with the existing CSV parsing capabilities of OceanBase Database. For more information, see [LOAD DATA (MySQL mode)](../../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/5900.load-data-of-mysql-mode.md) for the format description. The following table describes the commonly used options:

| Option | Description | Default value |
| ---- | ---- | ------ |
| `LINE_DELIMITER` | The line delimiter. | `'\n'` |
| `FIELD_DELIMITER` | The field delimiter. | `'\t'` |
| `ESCAPE` | The escape character, which is a single byte. | `'\'` |
| `FIELD_OPTIONALLY_ENCLOSED_BY` | The character that encloses the field value (such as double quotation marks). This option is commonly used for CHAR, VARCHAR, TEXT, and JSON data types. | Empty |
| `ENCODING` | The character set encoding. | `UTF8MB4` |
| `NULL_IF` | The string that is considered NULL. | Empty |
| `TRIM_SPACE` | Whether to remove leading and trailing spaces from the field. | `FALSE` |
| `SKIP_BLANK_LINES` | Whether to skip blank lines. | `FALSE` |
| `EMPTY_FIELD_AS_NULL` | Whether to treat an empty string as NULL. | `FALSE` |

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The CSV parsing of Routine Load does not support <code>PARSE_HEADER</code> or <code>SKIP_HEADER</code>. In other words, you cannot treat the first row as the column names or skip the header row. </p>
</main>

## Manage a Routine Load job

| Operation | Syntax | Description |
| ---- | ---- | ---- |
| Pause | `PAUSE ROUTINE LOAD FOR job_name;` | Pauses data consumption, retains the job configuration and the current offset, and allows you to resume the job later. |
| Resume | `RESUME ROUTINE LOAD FOR job_name;` | Resumes data consumption from the offset at which the job was paused. |
| Stop | `STOP ROUTINE LOAD FOR job_name;` | Terminates the job. |

## Execution mechanism

### Background scheduling and data flow

* When you create a Routine Load job, the system creates a scheduled task in the internal table managed by **DBMS Scheduler**. The execution frequency is determined by the system configuration (default: continuous execution).
* Each time the task is triggered, the system automatically performs the following operations: parses the Kafka configurations, connects to Kafka, consumes messages from the specified partitions and offsets, parses and converts the messages into table rows based on the CSV rules, writes the rows to the destination table, and updates the consumption progress (offset).

For more information about the scheduled task mechanism, see [Overview of DBMS Scheduler](../../../../700.reference/600.pl-reference/300.pl-oracle/1400.pl-system-package-oracle/14200.dbms-scheduler-oracle/100.dbms-scheduler-overview-oracle.md) (Oracle mode).

### Errors and retries

* **The destination table does not exist or the user does not have sufficient privileges**: the job enters an error state (such as CANCELLED). You need to stop the job by using `STOP ROUTINE LOAD`, and then recreate the job.
* You can also end the job by using **STOP ROUTINE LOAD** when the job fails or needs to be taken offline.

## View the status of a routine load job

You can query the following system views to view the basic information, status, and consumption progress of a routine load job:

| View | Description |
| ---- | -------- |
| `DBA_OB_ROUTINE_LOAD_JOBS` | Queries the routine load jobs of the current tenant in the current database. |
| `CDB_OB_ROUTINE_LOAD_JOBS` | Queries the routine load jobs of all tenants in the current database. |

### Status description

| Status | Description |
| ---- | ---- |
| RUNNING | The routine load job is running and is consuming data from Kafka and writing data to the destination table. |
| PAUSED | The routine load job is paused and is not consuming data. |
| STOPPED | The routine load job is stopped and cannot be resumed. |
| CANCELLED | The routine load job is canceled due to an error. |

## Examples

### Example 1: Import data from a Kafka topic in CSV format

The destination table exists, and the messages in the Kafka topic are in CSV format. The columns in the messages are in the same order as the columns in the destination table.

```sql
-- Create the destination table.
CREATE TABLE user_behavior (
  user_id INT PRIMARY KEY,
  action VARCHAR(50),
  timestamp TIMESTAMP
);

-- Create a routine load job.
CREATE ROUTINE LOAD user_behavior_load ON user_behavior
FROM STREAM (
  "bootstrap.servers" = "127.0.0.1:9092",
  "kafka_topic" = "test-topic",
  "kafka_partitions" = "0",
  "kafka_offsets" = "0",
  FORMAT = (TYPE = 'CSV', FIELD_DELIMITER = ',')
);
```

### Example 2: Import data with authentication, filtering, and concurrency

Use SASL authentication to import only the rows where the `amount` column is greater than 100. Increase the concurrency and the number of rows per batch.

```sql
-- Create the destination table.
CREATE TABLE sales_data (
  order_id BIGINT PRIMARY KEY,
  product_id INT,
  amount DECIMAL(10,2),
  order_time TIMESTAMP
);

-- Create a routine load job with SASL authentication and filtering.
CREATE ROUTINE LOAD sales_load ON sales_data
  PARALLEL = 3,
  WHERE amount > 100
)
FROM STREAM (
  "bootstrap.servers" = "127.0.0.1:9092",
  "kafka_topic" = "test-topic",
  "kafka_partitions" = "0,1,2",
  "kafka_offsets" = "0,0,OFFSET_BEGINNING",
  "max_batch_interval" = "60",
  "max_batch_rows" = "2000000",
  "max_batch_size" = "1000000000",
  "security.protocol" = "sasl_plaintext",
  "sasl.mechanism" = "PLAIN",
  "sasl.username" = "consumer1",
  "sasl.password" = "consumer1-password",
  FORMAT = (TYPE = 'CSV', FIELD_DELIMITER = ',', TRIM_SPACE = TRUE)
);
```

### Example 3: Complete operation

This example demonstrates the following operations in sequence: create a routine load job, view the status of the job, pause the job, view the status again to confirm that the job is paused, and resume the job. Assume that the destination table `user_behavior` and the Kafka topic are ready.

**Step 1: Create a routine load job**

```sql
CREATE ROUTINE LOAD my_kafka_load ON user_behavior
FROM STREAM (
  "bootstrap.servers" = "127.0.0.1:9092",
  "kafka_topic" = "user-events",
  "kafka_partitions" = "0",
  "kafka_offsets" = "0",
  FORMAT = (TYPE = 'CSV', FIELD_DELIMITER = ',')
);
```

**Step 2: View the status of the job**

After the job is created, you can query the system view to confirm that the job exists and is running. You can also view the consumption progress of each partition by using the **`progress`** field, such as the offset:

```sql
SELECT job_id, job_name, table_name, state, progress, create_time
FROM DBA_OB_ROUTINE_LOAD_JOBS
WHERE job_name = 'my_kafka_load';
```

In the example result, if the `state` value is `RUNNING`, the job is consuming data from Kafka and writing data to the destination table. The `progress` value indicates the current consumption offset of each partition, which facilitates progress monitoring.

**Step 3: Pause the job**

If you need to temporarily stop the job for maintenance or throttling, you can pause the job. The job configuration and current consumption offset are retained.

```sql
PAUSE ROUTINE LOAD FOR my_kafka_load;
```

**Step 4: View the status of the job again**

Verify that the job is paused:

```sql
SELECT job_id, job_name, table_name, state
FROM DBA_OB_ROUTINE_LOAD_JOBS
WHERE job_name = 'my_kafka_load';
```

At this time, the `state` value is `PAUSED`, indicating that the job is no longer pulling new data.

**Step 5: Resume the job**

Resume the job from the offset at which it was paused:

```sql
RESUME ROUTINE LOAD FOR my_kafka_load;
```

After the job is resumed, you can execute the query in Step 2 again. The `state` value will be `RUNNING`. If you want to terminate the job and delete the configuration, execute the `STOP ROUTINE LOAD FOR my_kafka_load;` statement. This operation is irreversible.
