# Configure Skip Index and table update mode together

Since **V4.3.0**, the system automatically generates Skip Indexes for baseline data in columnstore tables (by default, the system creates MIN_MAX-type Skip Indexes for columns). Since **V4.6.0**, the system can also generate Skip Indexes for incremental data.

Skip Indexes record aggregated information for columns at the micro-block level in SSTables, such as minimum and maximum values, the number of null values, and optional SUM values. This allows queries to filter out data blocks that do not meet the conditions before scanning, thereby reducing unnecessary I/O and computational overhead. For more information about Skip Indexes, see [Column Skip Index Properties (MySQL Mode)](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/250.identify-skip-index-properties-of-mysql-mode.md). In analytical query scenarios, Skip Indexes are particularly effective for large table scans and queries with range or equality conditions. They significantly reduce the amount of data scanned. In scenarios with large data volumes and highly selective filter conditions, the optimization effects are usually more pronounced.

For columnstore tables, baseline data typically has the necessary aggregated information. However, if Skip Indexes are not generated for incremental data over a long period, new data written to the table may still trigger a significant number of unnecessary micro-block scans during queries, which can negatively impact analytical query performance.

Therefore, in AP scenarios, we recommend that you configure parameters such as **table update mode (MERGE_ENGINE)** and **skip_index_level** based on your business requirements. This ensures that Skip Indexes are generated for incremental data when conditions are met, thereby improving the execution efficiency of filtered queries.

## Default mode in AP scenarios

The value of **[enable_incremental_skip_index](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2120.enable_incremental_skip_index.md)** depends on the combination of the table-level `MERGE_ENGINE` and `skip_index_level` settings. Tenant-level configurations only affect new tables created **after** this setting is applied, provided that the corresponding option is not explicitly specified in the CREATE TABLE statement. The actual definition of the table is determined by the `SHOW CREATE TABLE` command.

Please verify the current values for the following settings:

- **[default_table_merge_engine](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md)** (tenant-level)
  - **Query**: `SHOW PARAMETERS LIKE 'default_table_merge_engine';`
  - **Default**: `PARTIAL_UPDATE`. **AP Recommendation**: Change it to `delete_insert` or `append_only`, or explicitly specify `MERGE_ENGINE` in the CREATE TABLE DDL statement.
  - **If not matching**: `ALTER SYSTEM SET default_table_merge_engine = 'delete_insert';` (or `'append_only'`). **This only affects new tables created after this change, provided that the DDL statement does not specify `MERGE_ENGINE`.**

- **[default_skip_index_level](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2110.default_skip_index_level.md)** (tenant-level)
  - **Query**: `SHOW PARAMETERS LIKE 'default_skip_index_level';`
  - **Default**: In AP scenarios, it is `1`. When specifying `skip_index_level` at the table level, it inherits the value from `default_skip_index_level`.
  - **If not matching**: `ALTER SYSTEM SET default_skip_index_level = 1;` (or `0`). **This only affects new tables created after this change, provided that the DDL statement does not specify `skip_index_level`.**

- **Table-level `MERGE_ENGINE` (Table Update Mode)**
  - **Query**: `SHOW CREATE TABLE dbname.tblname;`
  - **To enable incremental Skip Index**: It must be set to `DELETE_INSERT` or `APPEND_ONLY` (not `PARTIAL_UPDATE`).
  - **If not matching**: You cannot use `ALTER TABLE` to change the table mode. Instead, you must **create a new table** and specify `MERGE_ENGINE` for the new table, then **migrate the data**. When creating the new table, you can also explicitly specify `MERGE_ENGINE` in the DDL statement, without relying on the tenant's default setting.

- **Table-level `skip_index_level`**
  - **Query**: `SHOW CREATE TABLE dbname.tblname;` or the **SKIP_INDEX_LEVEL** view ([DBA_TABLES](../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/15620.o-dba_tables--of-mysql-mode.md) / [CDB_TABLES](../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/13200.o-cdb_tables-of-sys-tenant.md)).
  - **To enable incremental Skip Index**: It must be set to `1`, and the table mode must also meet the requirements.
  - **If not matching**: If the table mode is already `DELETE_INSERT` or `APPEND_ONLY`, execute `ALTER TABLE tbl SET skip_index_level = 1;` (or `0`). **The incremental Skip Index will take effect after the next major compaction or minor compaction.**

**To create a new table with the desired settings and minimize reliance on tenant defaults**: Explicitly specify `MERGE_ENGINE = delete_insert` (or `append_only`) and `skip_index_level = 1` in the `CREATE TABLE` statement. For columnar analysis, you can also add `WITH COLUMN GROUP(each column)` to the statement. See the "Syntax Examples" section below for details.

For more information about the configuration items, see [default_table_merge_engine](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md) and [default_skip_index_level](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2110.default_skip_index_level.md).

### Syntax examples

```sql
-- Specify the parameters when you create a table.
CREATE TABLE logs (
  event_time TIMESTAMP,
  level VARCHAR(10)
)
MERGE_ENGINE = DELETE_INSERT
skip_index_level = 1;

-- Modify the skip_index_level parameter of an existing table. You cannot modify the MERGE_ENGINE parameter.
ALTER TABLE logs SET skip_index_level = 1;
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p>If you do not specify the <code>MERGE_ENGINE</code> or <code>skip_index_level</code> parameter in a CREATE TABLE statement, the parameter inherits the value of the <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md">default_table_merge_engine</a> or <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2110.default_skip_index_level.md">default_skip_index_level</a> parameter at the tenant level. The <code>ALTER TABLE ... SET skip_index_level</code> statement only modifies the table-level switch and <strong>cannot</strong> modify the <code>MERGE_ENGINE</code> parameter.</p>
</main>

## Technical analysis

For information about what to check and how to modify the settings at the tenant and table levels, see **Default mode in AP scenarios**. This section describes the baseline and incremental differences and the meaning of the `skip_index_level` parameter at the storage layer.

### Generate Skip Index for baseline data

* **Support**: OceanBase Database supports generating Skip Indexes for **baseline data** (Major SSTables). For columnar tables, Skip Indexes of the MIN_MAX type are generated by default starting from V4.3. For rowstore tables, you must explicitly specify `SKIP_INDEX(MIN_MAX)` or `SKIP_INDEX(SUM)` on the column. Skip Indexes are generated during the baseline merge.
* **Conditions**: For columnar tables, Skip Indexes are automatically generated during Major Compaction according to the engine strategy (default is MIN_MAX, and SUM can be added based on column attributes). For rowstore tables, Skip Indexes are generated only when the column has the Skip Index attribute during the baseline merge. This is unrelated to the table update mode (MERGE_ENGINE).

### Generate Skip Index for incremental data

* **Support**: Whether Skip Indexes are generated for incremental data (Memtable, Mini/Minor SSTables) is strongly related to the **table update mode**. Skip Indexes can be safely generated for user columns only when the incremental data contains **complete rows**.
* **Conditions** (all must be met):
  1. **Table mode**: `MERGE_ENGINE` is set to `DELETE_INSERT` or `APPEND_ONLY`.
  2. **Table-level configuration**: `skip_index_level = 1` (specified when creating the table or inherited from the tenant's `default_skip_index_level = 1`).
  3. **Effective timing**: After the **next Mini Compaction (minor compaction)** or Minor Compaction (major compaction), Skip Indexes will be generated for the incremental layer.

<main id="notice" type='explain'>
<h4>Note</h4>
<p>For <code>PARTIAL_UPDATE</code> tables, only the changed columns are recorded, and the incremental layer cannot reliably obtain complete rows for aggregation information such as min/max. Therefore, even if <code>skip_index_level = 1</code> is set, the system will not generate Skip Indexes for incremental user columns.</p>
</main>

### skip_index_level parameter values and behaviors (table level)

| Value | Description |
|----|------|
| `0` | For columnar tables, Skip Indexes are generated according to the engine strategy. For rowstore tables, Skip Indexes are generated based on schema column attributes. **Incremental SSTables do not generate** any Skip Indexes. |
| `1` | The baseline behavior is the same as for `0`. **Incremental SSTables** generate Skip Indexes in the same way as baseline data when the table is in `DELETE_INSERT` or `APPEND_ONLY` mode. For columnar tables, Skip Indexes are generated based on priority and space constraints. For rowstore tables, Skip Indexes are generated based on schema. New tables that do not explicitly specify `skip_index_level` inherit the tenant's **default_skip_index_level** (usually `1`, depending on the actual parameter). |

If you do not explicitly specify `skip_index_level` when creating a table, the value of the tenant-level parameter **default_skip_index_level** is used. After you modify `skip_index_level`, the new configuration takes effect during the **next minor compaction** or major compaction.

## Applicability

### Not applicable or with considerations

* **PARTIAL_UPDATE tables**: Skip Index for **incremental** user columns is not generated; even if `skip_index_level = 1` is set, it will be ignored. Baselines are still generated as columnar or rowar with schema.
* **Column types and attributes**: Skip Index aggregation is not generated for the following columns: virtual generated columns; JSON and spatial (geo) types; and outrow LOBs.
* **Small tables or infrequent AP queries**: The storage and compaction overhead of Skip Index may outweigh the benefits. You can set `skip_index_level = 0` or avoid relying on incremental Skip Index as needed.
* **High-concurrency update TP tables** (`PARTIAL_UPDATE`): If you expect to use **incremental** user column Skip Index for analysis filtering, the system will not generate it. Avoid tuning based on AP incremental Skip Index expectations.

### Recommended (AP)

* **Columnar analysis tables**: Use `WITH COLUMN GROUP(each column)`, along with `MERGE_ENGINE = DELETE_INSERT` and `skip_index_level = 1`, to benefit both baselines and increments from Skip Index.
* **Log/metric append writes**: Use `MERGE_ENGINE = APPEND_ONLY` with `skip_index_level = 1` (as needed).

## Example: Configure the table update mode and Skip Index for an AP columnstore table

### Scenario description

* Table usage: Store business events or metric details in a columnstore table and perform range queries and aggregations based on columns such as `event_time`.
* Objective: Set the following parameters: `WITH COLUMN GROUP(each column)`, `MERGE_ENGINE = DELETE_INSERT`, and `skip_index_level = 1`. Optionally, explicitly specify the `SKIP_INDEX(MIN_MAX, SUM)` attribute for some columns.

### Step 1: View the current tenant-level parameters

Execute the following statements in the **system tenant** (or in the sys tenant to view the parameters for a specific tenant) to confirm the current default table update mode and Skip Index level:

```sql
-- View the default table update mode (usually partial_update by default)
SHOW PARAMETERS LIKE 'default_table_merge_engine';

-- View the default skip_index_level for newly created tables (usually 1 in AP scenarios)
SHOW PARAMETERS LIKE 'default_skip_index_level';
```

If the tenant primarily uses AP, ensure the following settings (note that **default_skip_index_level** is commonly set to `1`, so focus mainly on **default_table_merge_engine**):

```sql
ALTER SYSTEM SET default_table_merge_engine = 'delete_insert';
-- If it is not set to 1, execute: ALTER SYSTEM SET default_skip_index_level = 1;
```

These changes only apply to tables created after the modification and do not affect existing tables.

### Step 2: Specify the table update mode and Skip Index level when creating a table

When creating a table, explicitly specify the following parameters: `WITH COLUMN GROUP(each column)`, `MERGE_ENGINE = delete_insert`, and `skip_index_level = 1`. Optionally, specify the Skip Index attribute for some columns:

```sql
CREATE TABLE ap_logs (
  log_id     BIGINT,
  event_time TIMESTAMP,
  level      VARCHAR(32),
  duration_ms INT,
  extra      VARCHAR(1024),
  c3         FLOAT SKIP_INDEX(MIN_MAX, SUM),
  PRIMARY KEY (log_id)
) MERGE_ENGINE = delete_insert
  skip_index_level = 1
  WITH COLUMN GROUP(each column);
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p><ul>
<li><code>WITH COLUMN GROUP(each column)</code>: Creates a <strong>columnstore table</strong>. By default, the baseline of the columnstore table generates MIN_MAX Skip Indexes for each column. Incremental data is generated based on the table mode and <code>skip_index_level</code> in the same manner.</li>
<li><code>MERGE_ENGINE = delete_insert</code>: Enables full-column updates and safe Skip Index generation for incremental data.</li>
<li><code>skip_index_level = 1</code>: Incremental SSTables of the table will generate Skip Indexes based on the baseline strategy.</li>
<li><code>c3 FLOAT SKIP_INDEX(MIN_MAX, SUM)</code>: Specifies the Skip Index type (MIN_MAX + SUM) for the column in the schema. This type will be prioritized in sorting.</li>
</ul></p>
</main>

### Step 3: Modify the Skip Index for an existing table

If the table already exists and is of type `DELETE_INSERT` or `APPEND_ONLY`, execute the following statement to enable incremental Skip Index generation:

```sql
ALTER TABLE ap_logs SET skip_index_level = 1;
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p>The new configuration takes effect after the next <strong>minor compaction</strong> or <strong>major compaction</strong> for incremental data. The <code>MERGE_ENGINE</code> parameter <strong>cannot</strong> be modified using <code>ALTER TABLE</code>. Only when the table is of type <code>DELETE_INSERT</code> or <code>APPEND_ONLY</code> will the <code>skip_index_level = 1</code> parameter enable Skip Index generation for incremental user columns. For <code>PARTIAL_UPDATE</code> tables, this parameter has no effect. For more information about the tenant-level default value, see <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2110.default_skip_index_level.md">default_skip_index_level</a>.</p>
</main>
