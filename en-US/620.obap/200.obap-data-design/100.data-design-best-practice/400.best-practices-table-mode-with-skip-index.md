# Configure Skip Index in conjunction with table update mode

Since **V4.3.0**, columnstore tables support automatically generating Skip Indexes for **baseline data** (columnstore tables default to creating MIN_MAX type Skip Indexes for columns). Since **V4.6.0**, Skip Indexes can also be generated for **incremental data**.

Skip Indexes record aggregated information for columns at the micro-block level in SSTables, such as minimum and maximum values, number of null values, and optional SUM information. This allows queries to filter out data blocks that do not meet the conditions before scanning, reducing unnecessary I/O and computational overhead. For more information about Skip Indexes, see [Column Skip Index Properties (MySQL Mode)](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/250.identify-skip-index-properties-of-mysql-mode.md). In analytical query scenarios, Skip Indexes are effective for large table scans and queries with range or equality conditions, significantly reducing the amount of data scanned. In scenarios with large data volumes and highly selective filter conditions, the optimization effect is typically more pronounced.

For columnstore tables, baseline data usually has the necessary aggregated information. However, if Skip Indexes for incremental data are not generated for a long time, new data written to the table may still trigger many unnecessary micro-block scans during queries, which can impact analytical query performance.

Therefore, in AP scenarios, it is recommended to configure parameters such as **table update mode (MERGE_ENGINE)** and **skip_index_level** based on business characteristics. This ensures that **incremental data** can also generate Skip Indexes when conditions are met, thereby improving the execution efficiency of queries with filter conditions.

## Default mode in AP scenarios

The value of **Skip Index for incremental user column** depends on the combination of the table-level `MERGE_ENGINE` and `skip_index_level`. Tenant-level settings only affect **newly created tables** where the corresponding options are **not explicitly specified** in the DDL statement. The actual table definition is determined by `SHOW CREATE TABLE`.

Please verify the current values based on the following items:

- **[default_table_merge_engine](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md)** (tenant-level)
  - **Query**: `SHOW PARAMETERS LIKE 'default_table_merge_engine';`
  - **Default**: `PARTIAL_UPDATE`. **AP Recommendation**: Change it to `delete_insert` / `append_only`, or explicitly specify `MERGE_ENGINE` in the DDL statement when creating the table.
  - **If not matching**: `ALTER SYSTEM SET default_table_merge_engine = 'delete_insert';` (or `'append_only'`). **This only affects newly created tables** where the DDL statement does not specify `MERGE_ENGINE`.

- **[default_skip_index_level](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004386530)** (tenant-level)
  - **Query**: `SHOW PARAMETERS LIKE 'default_skip_index_level';`
  - **Default**: `1` in AP scenarios; when specifying `skip_index_level` at the table level, it inherits the value of `default_skip_index_level`.
  - **If not matching**: `ALTER SYSTEM SET default_skip_index_level = 1;` (or `0`). **This only affects newly created tables** where the DDL statement does not specify `skip_index_level`.

- **Table-level `MERGE_ENGINE` (table update mode)**
  - **Query**: `SHOW CREATE TABLE dbname.tblname;`
  - **To enable incremental Skip Index for user columns**: Must be `DELETE_INSERT` or `APPEND_ONLY` (not `PARTIAL_UPDATE`).
  - **If not matching**: **Cannot** change the table mode using `ALTER TABLE`; must **create a new table** and specify `MERGE_ENGINE` and **migrate data**. You can also explicitly specify it in the DDL statement when creating the table, without relying on the tenant's default.

- **Table-level `skip_index_level`**
  - **Query**: `SHOW CREATE TABLE dbname.tblname;` or view **SKIP_INDEX_LEVEL** ([DBA_TABLES](../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/15620.o-dba_tables--of-mysql-mode.md) / [CDB_TABLES](../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/13200.o-cdb_tables-of-sys-tenant.md))
  - **To enable incremental Skip Index**: Must be `1`, and **must also** meet the previous table mode requirement.
  - **If not matching**: If the table mode is already `DELETE_INSERT` / `APPEND_ONLY`, execute `ALTER TABLE tbl SET skip_index_level = 1;` (or `0`). **This change will take effect on the next major compaction or minor compaction**.

**For newly created tables that you want to configure without relying on tenant defaults**: Explicitly specify `MERGE_ENGINE = delete_insert` (or `append_only`) and `skip_index_level = 1` in the `CREATE TABLE` statement. For columnar analysis, you can also add `WITH COLUMN GROUP(each column)`. See the "Syntax examples" section below for details.

For more information about the configuration items, see [default_table_merge_engine](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md) and [default_skip_index_level](https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004386530).

### Syntax examples

```sql
-- Specify when creating a table
CREATE TABLE logs (
  event_time TIMESTAMP,
  level VARCHAR(10)
)
MERGE_ENGINE = DELETE_INSERT
skip_index_level = 1;

-- Modify an existing table (only skip_index_level can be changed, MERGE_ENGINE cannot be changed)
ALTER TABLE logs SET skip_index_level = 1;
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p>If <code>MERGE_ENGINE</code> or <code>skip_index_level</code> is not specified in the DDL statement, they inherit the tenant-level <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md">default_table_merge_engine</a> and <a href="https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004386530">default_skip_index_level</a> respectively. <code>ALTER TABLE ... SET skip_index_level</code> only modifies the table-level setting and <strong>cannot</strong> change <code>MERGE_ENGINE</code>.</p>
</main>

## Technical analysis

For tenants and tables, refer to the **Default mode in AP scenarios** section for details on what to check and how to modify. This section explains the baseline and incremental differences and the meaning of the `skip_index_level` parameter from the storage layer.

### Skip Index generation for baseline data

* **Support**: OceanBase Database supports generating Skip Indexes for **baseline data** (Major SSTables). For columnstore tables, MIN_MAX type Skip Indexes are generated by default for each column starting from V4.3. For rowstore tables, you must explicitly specify `SKIP_INDEX(MIN_MAX)` or `SKIP_INDEX(SUM)` for each column. Skip Indexes are generated during major compactions.
* **Generation conditions**: For columnstore tables, Skip Indexes are automatically generated during major compactions based on the engine strategy (default is MIN_MAX, and SUM can be added based on column properties). For rowstore tables, Skip Indexes are generated during major compactions only if the column has the Skip Index attribute. This is unrelated to the table update mode (MERGE_ENGINE).

### Skip Index generation for incremental data

* **Support**: Whether Skip Indexes are generated for incremental data (Memtable, Mini/Minor SSTables) is strongly related to the **table update mode**. Skip Indexes can be safely generated for user columns only when the incremental data contains **complete rows**.
* **Generation conditions** (all must be met):
  1. **Table mode**: `MERGE_ENGINE` is set to `DELETE_INSERT` or `APPEND_ONLY`.
  2. **Table-level configuration**: `skip_index_level = 1` (specified during table creation or inherited from the tenant's `default_skip_index_level = 1`).
  3. **Effective timing**: Skip Indexes are generated in the incremental layer after the **next Mini Compaction (minor compaction)** or **Minor Compaction (major compaction)**.

<main id="notice" type='explain'>
<h4>Note</h4>
<p>For <code>PARTIAL_UPDATE</code> tables, only the changed columns are recorded, and the incremental layer cannot reliably obtain complete rows for min/max aggregation. Therefore, even if <code>skip_index_level = 1</code> is set, the system will not generate Skip Indexes for incremental user columns.</p>
</main>

### skip_index_level values and behaviors (table level)

| Value | Description |
|----|------|
| `0` | For columnstore tables, Skip Indexes are generated based on the engine strategy. For rowstore tables, Skip Indexes are generated based on schema column properties. **No Skip Indexes are generated** for incremental SSTables. |
| `1` | The baseline behavior is the same as for `0`. **Incremental SSTables** generate Skip Indexes based on the same strategy as the baseline when the table is set to `DELETE_INSERT` or `APPEND_ONLY`. For new tables, if `skip_index_level` is not explicitly specified, it typically inherits the tenant's **default_skip_index_level** (which is usually `1`, based on actual parameters). |

If `skip_index_level` is not explicitly specified during table creation, the tenant-level parameter **default_skip_index_level** is used. After modifying `skip_index_level`, the new configuration takes effect during the **next minor compaction** or **major compaction**.

## Applicable scenarios

### Not applicable or with considerations

* **PARTIAL_UPDATE tables**: No **incremental** user column Skip Indexes are generated. Even if you set `skip_index_level = 1`, it will be ignored. Baseline Skip Indexes are still generated based on columnstore/rowstore and schema.
* **Column types and properties**: Skip Indexes are not generated for the following columns: virtual generated columns; JSON and spatial (geo) types; and outrow LOB columns.
* **Small tables or low-frequency AP queries**: The storage and compaction overhead of Skip Indexes may outweigh the benefits. You can use `skip_index_level = 0` or avoid relying on incremental Skip Indexes as needed.
* **High-concurrency TP tables** (`PARTIAL_UPDATE`): Do not rely on **incremental** user column Skip Indexes for analysis filtering. Avoid optimizing based on AP incremental Skip Index expectations.

### Recommended (AP)

* **Columnstore analysis tables**: Use `WITH COLUMN GROUP(each column)` and set `MERGE_ENGINE = DELETE_INSERT` and `skip_index_level = 1` to benefit both baseline and incremental data with Skip Indexes.
* **Log and metric append writes**: Set `MERGE_ENGINE = APPEND_ONLY` and use `skip_index_level = 1` as needed.

## Example: Configure the table update mode and skip index for an AP columnstore table

### Scenario

* Table usage: Store business events or metric details in a columnstore table and perform range queries and aggregations based on columns such as `event_time`.
* Goal: Set `WITH COLUMN GROUP(each column)`, `MERGE_ENGINE = DELETE_INSERT`, and `skip_index_level = 1`. Optionally, explicitly specify `SKIP_INDEX(MIN_MAX, SUM)` for some columns.

### Step 1: View the current tenant-level parameters

Execute the following statement in the **sys tenant** (or in the sys tenant to view the parameters for a specified tenant) to confirm the current default table update mode and skip index level:

```sql
-- View the default table update mode (usually partial_update by default)
SHOW PARAMETERS LIKE 'default_table_merge_engine';

-- View the default skip_index_level for new tables (1 by default in AP scenarios)
SHOW PARAMETERS LIKE 'default_skip_index_level';
```

If the tenant is primarily used for AP scenarios, ensure the following settings (note that **default_skip_index_level** is commonly set to `1`, so focus mainly on **default_table_merge_engine**):

```sql
ALTER SYSTEM SET default_table_merge_engine = 'delete_insert';
-- If not set to 1, execute: ALTER SYSTEM SET default_skip_index_level = 1;
```

These changes only take effect for tables created after the modification and do not affect existing tables.

### Step 2: Specify the table update mode and skip index level when creating the table

When creating the table, explicitly set `WITH COLUMN GROUP(each column)`, `MERGE_ENGINE = delete_insert`, and `skip_index_level = 1`. Optionally, specify the skip index properties for some columns:

```sql
CREATE TABLE ap_logs (
  log_id     BIGINT,
  event_time TIMESTAMP,
  level      VARCHAR(32),
  duration_ms INT,
  extra      VARCHAR(1024),
  c3         FLOAT SKIP_INDEX(MIN_MAX, SUM),
  PRIMARY KEY (log_id)
) MERGE_ENGINE = delete_insert
  skip_index_level = 1
  WITH COLUMN GROUP(each column);
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p><ul>
<li><code>WITH COLUMN GROUP(each column)</code>: Creates a <strong>columnstore table</strong>. By default, the baseline of a columnstore table generates MIN_MAX and other skip indexes for each column. Incremental data will also generate skip indexes following the same strategy when the table mode and <code>skip_index_level</code> are met.</li>
<li><code>MERGE_ENGINE = delete_insert</code>: Enables full-column updates, allowing safe generation of skip indexes for incremental data.</li>
<li><code>skip_index_level = 1</code>: Specifies that incremental SSTables of this table will generate skip indexes following the baseline strategy.</li>
<li><code>c3 FLOAT SKIP_INDEX(MIN_MAX, SUM)</code>: Specifies the skip index type (MIN_MAX + SUM) for this column in the schema. This type will be generated and prioritized in sorting.</li>
</ul></p>
</main>

### Step 3: Modify the skip index level for existing tables

If the table already exists and is set to `DELETE_INSERT` or `APPEND_ONLY`, you can execute the following statement to enable incremental skip indexes:

```sql
ALTER TABLE ap_logs SET skip_index_level = 1;
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p>The new configuration takes effect only for incremental data after the <strong>next major compaction or minor compaction</strong>. The <code>MERGE_ENGINE</code> parameter <strong>cannot</strong> be modified using <code>ALTER TABLE</code>. Only when the table is already set to <code>DELETE_INSERT</code> or <code>APPEND_ONLY</code> will <code>skip_index_level = 1</code> actually generate skip indexes for incremental user columns; it has no effect on <code>PARTIAL_UPDATE</code> tables. For more information about the tenant-level default values, see <a href="https://www.oceanbase.com/docs/common-oceanbase-database-cn-1000000004386530">default_skip_index_level</a>.</p>
</main>
