# Best practices for optimizing storage structure and query performance

Designing data tables is a crucial aspect of database system design and optimization. A well-designed table structure not only ensures data integrity and consistency but also significantly improves query performance, storage efficiency, and system scalability. As data volumes grow and query patterns become more complex, scientifically designing data tables, selecting appropriate storage structures, and choosing the right indexing strategies are key challenges in database optimization.

This topic will cover best practices for designing data tables, including selecting table storage formats, creating columnar tables without primary keys, partitioning, primary key design, and using indexes in HTAP scenarios.

## Choose the storage format for a table

OceanBase Database supports columnar and row-column hybrid storage formats for tables. You can choose the appropriate storage format based on your business scenarios.

+ **Columnar storage**: Use columnar storage for OLAP scenarios.
+ **Row-column hybrid storage**: Use row-column hybrid storage for HTAP scenarios that require both OLAP and OLTP capabilities.

You can set the default storage format for tables in a tenant by using the [default_table_store_format](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) parameter.

```sql
-- Set the default storage format for tables in the tenant to columnar.
ALTER SYSTEM SET default_table_store_format = "column";

-- Set the default storage format for tables in the tenant to row-column hybrid.
ALTER SYSTEM SET default_table_store_format = "compound";
```

## Design a primary key

Designing a primary key is a core aspect of designing tables in a relational database. In OceanBase Database, a primary key not only ensures data uniqueness but also optimizes performance for range queries because data is sorted by the primary key. Different primary key design schemes are suitable for different business scenarios.

### Scenarios without a primary key

#### Use a non-partitioned, non-clustered table

In data warehouse or online analytical processing (OLAP) scenarios, business data tables often contain a large amount of data, and most queries involve only specific columns. If the business does not have special requirements, such as ensuring data uniqueness, avoiding data duplication, or performing transactional updates or inserts, creating a non-partitioned, non-clustered table is more efficient:

+ **Data import:** In AP scenarios, data does not need to be sorted by the primary key, so the import performance of large amounts of data is faster compared to tables with a primary key.
+ **Reduced management costs of primary keys.**

```sql
show parameters like "%store_format%";

  CREATE TABLE customer (
  user_id bigint NOT NULL,
  login_time timestamp NOT NULL,
  customer_name varchar(100) NOT NULL,    -- Assume that the customer name is up to 100 characters.
  phone_num bigint NOT NULL,               -- Store the phone number as a bigint.
  city_name varchar(50) NOT NULL,          -- Assume that the city name is up to 50 characters.
  sex int NOT NULL,                        -- Store the gender as an int (0 for female, 1 for male).
  id_number varchar(18) NOT NULL,          -- Assume that the ID number is up to 18 characters.
  home_address varchar(255) NOT NULL,      -- Assume that the home address is up to 255 characters.
  office_address varchar(255) NOT NULL,    -- Assume that the office address is up to 255 characters.
  age int NOT NULL                         -- Store the age as an int.
);
```

### Scenarios with a primary key

In AP scenarios, **heap tables** are used by default. The characteristics of heap tables are as follows:

* **Data storage:** Data is stored in the order of insertion without physical sorting.
* **Functions of the primary key:**

  + Ensures data uniqueness by including a field that uniquely identifies a record (such as user_id).
  + Supports **partitioning key embedding**, where the primary key must include all partitioning keys (such as user_id and age) to ensure even data distribution.
  + Accelerates queries when combined with indexes or partitioning strategies (such as `ORDER BY`).

Example: Design a heap-organized table with a primary key

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    -- The primary key includes all partitioning keys (user_id and age).
    PRIMARY KEY (user_id, age, login_time)
)
-- Primary partitioning: Hash partitioned by user_id.
PARTITION BY HASH(user_id)
PARTITIONS 128
SUBPARTITION BY RANGE(age)
SUBPARTITION TEMPLATE (
    -- Example partitions: Partitioned by age groups.
    SUBPARTITION p_youth VALUES LESS THAN (25),      -- Age <25
    SUBPARTITION p_adult VALUES LESS THAN (40),      -- 25 ≤ age <40
    SUBPARTITION p_middle_aged VALUES LESS THAN (60),-- 40 ≤ age <60
    SUBPARTITION p_senior VALUES LESS THAN (MAXVALUE) -- Age ≥60
);
```

### Scenarios with a primary key

* **Ensure data uniqueness:** When data in the table must be unique, a primary key must be designed.
* **Improve query efficiency:** A primary key helps the optimizer generate more efficient query plans. If data queries depend on the primary key, it is recommended to include the query fields in the primary key to leverage it for performance improvements.

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    -- The primary key includes all partitioning keys (user_id and age).
    PRIMARY KEY (user_id, age, login_time)
)
-- Primary partitioning: Hash partitioned by user_id.
PARTITION BY HASH(user_id)
PARTITIONS 128
SUBPARTITION BY RANGE(age)
SUBPARTITION TEMPLATE (
    -- Example partitions: Partitioned by age groups.
    SUBPARTITION p_youth VALUES LESS THAN (25),      -- Age <25
    SUBPARTITION p_adult VALUES LESS THAN (40),      -- 25 ≤ age <40
    SUBPARTITION p_middle_aged VALUES LESS THAN (60),-- 40 ≤ age <60
    SUBPARTITION p_senior VALUES LESS THAN (MAXVALUE) -- Age ≥60
);
```

## Optimize queries in HTAP scenarios

OceanBase Database provides various methods to meet the requirements of both transactional (TP) and analytical (AP) workloads in hybrid transactional/analytical processing (HTAP) scenarios. OceanBase Database supports rowstore, columnstore, and hybrid rowstore/columnstore tables for data tables, and also supports specifying the storage format for index tables. You can combine the advantages of rowstore and columnstore tables to process different scenarios.

For more information about how to create a columnstore index, see [Create a columnstore index in MySQL mode](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md) and [Create a columnstore index in Oracle mode](../../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/400.manage-indexes-of-oracle-mode/200.create-an-index-of-oracle-mode.md).

### Rowstore base table + columnstore index

**Scenarios:** The table is a wide table, and the workload is primarily transactional but also includes analytical queries.
**Optimization strategy:** Create a columnstore index to improve the performance of analytical queries.

+ **Advantages:** Only part of the data is redundantly stored in columnstore format.
+ **Disadvantages:** You need to identify the fields to be indexed based on the query statements. You also need to maintain the index table data during data write operations, which may affect the write performance.

### Columnstore base table + rowstore index

**Scenarios:** The workload is primarily analytical, but efficient simple queries (such as point queries) are required.
**Optimization strategy:** Create a covering index to avoid table scans.

+ **Advantages:** Only part of the data is redundantly stored. You can add a rowstore index to optimize queries without converting a columnstore table to a rowstore table or a hybrid rowstore/columnstore table online.
+ **Disadvantages:** You need to identify the fields to be indexed based on the query statements. You also need to maintain the index table data during data write operations, which may affect the write performance.

### Rowstore and columnstore redundancy: rowstore base table + columnstore base table

**Scenarios:** The workload includes both transactional and analytical queries, and the query types are diverse.
**Optimization strategy:** Redundantly store the data of both the rowstore and columnstore base tables. Let the system generate an appropriate execution plan based on the query characteristics. By default, the system performs range scans in columnstore mode and point queries in rowstore mode.

+ **Advantages:** You do not need to analyze the query characteristics of analytical queries. The results of analytical queries are strongly consistent.
+ **Disadvantages:** The system consumes more disk space. The execution plans may be inaccurate.

### Columnstore replica: 2F1A1C

**Scenarios:** The workload is primarily analytical, but the transactional workload cannot be affected by the analytical workload. You can accept weakly consistent reads for analytical queries.
**Optimization strategy:** Use the isolation characteristics of columnstore replicas to ensure that analytical and transactional workloads do not affect each other.

+ **Advantages:**
    1. You do not need to store redundant data in multiple replicas. This saves disk space.
    2. The analytical and transactional workloads are isolated from each other.
    3. The write performance is not affected.
+ **Disadvantages:**
    1. Columnstore replicas support only weakly consistent reads.
    2. You need to provide independent access endpoints.
