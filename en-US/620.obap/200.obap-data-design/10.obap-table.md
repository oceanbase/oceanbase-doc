# Overview of data tables

In **OceanBase** Database, tables are the fundamental data storage units. Tables contain all the data accessible to users, with each table consisting of multiple rows of records. Each row contains several columns. The design and usage of each table must be reasonably planned based on business requirements to ensure the system's efficiency and scalability.

## Table types

OceanBase Database supports various table types, including partitioned tables, replicated tables, primary key tables, non-primary key tables, and external tables.

* Partitioned tables: OceanBase Database allows you to divide the data of a regular table into different partitions based on specific rules and store the data of each partition together. This type of table is called a partitioned table. OceanBase Database supports basic partitioning strategies, including range partitioning, list partitioning, and hash partitioning.
* Replicated tables: A replicated table is a special type of table in OceanBase Database. Data in a replicated table can be read from any healthy replica.
* Primary key tables and non-primary key tables: A primary key table is a table that contains a primary key. A non-primary key table is a table that does not contain a primary key.
* External tables: In a database, the data of a regular table is stored in the database's storage space, while the data of an external table is stored in an external storage service.
* Heap tables: In a heap-organized table, the primary key is used to enforce uniqueness, and queries rely on the primary table. When user data is sorted by time, skip indexes can be more effectively utilized to improve query efficiency.

In **AP scenarios**, OceanBase Database supports various table types, including **replicated tables**, **partitioned tables**, **primary key tables**, and **non-primary key tables** in **TP scenarios**. Based on the data storage method, which is row-based or column-based, new table types are introduced: **columnstore tables** and **hybrid row-column tables**.

* **Columnstore tables**: In a columnstore table, data is stored by column rather than by row. This significantly improves the performance of analytical queries, especially in scenarios involving large amounts of data and frequent aggregation analysis. For more information, see [Columnstore tables](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/320.columnstore-engine.md).

* **Hybrid row-column tables**: In a hybrid row-column table, data is stored both by row and by column. The system automatically determines whether to use row-based or column-based queries based on the query statement. This type of table is suitable for scenarios that require both transactional and analytical operations.

## Table update modes

OceanBase Database allows you to specify the write and query modes when creating a table. When creating a table, you can use the `merge_engine` parameter in the `CREATE TABLE` statement to choose between the **delete_insert update mode** and the **partial_update update mode**. These modes are data update strategies designed for different business scenarios.

+ **delete_insert (full-column update mode)**

  This mode prioritizes **query performance**. Each update writes a complete row (delete the old row + insert the new row), ensuring that each row contains all column values. This mode supports skip indexes for incremental data (Memtable/Delta SSTable). During queries, the system can push down filters to incremental data. If the filtering results do not involve updates to baseline data, the system can batch process baseline and incremental data separately, reducing read amplification. This mode is suitable for **OLAP scenarios with a high proportion of incremental data, frequent complex queries, or batch processing analysis**, but incremental data occupies more storage space.

+ **partial_update (partial update mode)**

  This mode only records the modified columns (delta), saving storage space. During queries, the system needs to merge multiple data sources to obtain the latest values, resulting in relatively lower performance. However, this mode is more suitable for **OLTP scenarios with frequent updates but low query requirements** or environments sensitive to storage costs.

| **Feature Category** | **delete_insert Update Mode** | **partial_update Update Mode** |
| --- | --- | --- |
| **Storage Method** | Each update writes two rows (`DELETE` and `INSERT`) in the SSTable, containing all column data. | Each update only records the values of the modified columns, saving storage space. |
| **Query Efficiency** | Supports Delta SSTable Skip Index. During queries, the system can calculate and push down filter operators on Memtable/Delta SSTable. If the filtering results do not involve updates to baseline data, the system can batch process baseline and incremental data separately, reducing read amplification. If the filtering results involve updates to baseline data, the system merges incremental and baseline records to obtain the latest values for projection. | During queries, the system needs to merge records from multiple Memtables/SSTables to obtain the latest values of the primary key, which may affect performance. This mode is suitable for scenarios sensitive to storage costs and with frequent update operations. |
| **Applicable Scenarios** | OLAP scenarios with a high proportion of incremental data, frequent complex queries, or batch processing analysis. | OLTP scenarios with frequent updates but low query requirements. |

For more information, see [Create a table in MySQL mode](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/200.create-a-table-for-mysql-tenant-of-mysql-mode.md) and [Create a table in Oracle mode](../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/100.manage-tables-of-oracle-mode/200.create-a-table-for-oracle-tenant-of-oracle-mode.md).

## Data distribution

OceanBase Database distributes data across different partitions by creating partitioned tables. Data in different partitions can be distributed across different machines. During queries, partition pruning reduces the amount of data scanned and leverages multi-machine resources to improve query performance. By default, data between different tables is randomly distributed and has no direct relationship. Load balancing ensures that data from a table is evenly distributed across the entire cluster.

In a distributed AP system, tables often contain a large amount of data. When data from different tables is randomly distributed, the overhead of data transmission during table joins can be significant. Using [table groups](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md) (Table Group) aligns partitioned tables with the same partitioning strategy according to specific rules. This allows related data to be aggregated on the same machine, enabling Partition Wise Join during table joins. This effectively reduces data transmission overhead during joins and improves performance.

![](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer/ap/table-group.png)

OceanBase Database supports primary and secondary partitioned tables and provides three types of partitioning: RANGE, LIST, and HASH.

OceanBase Database provides three types of table groups:

1. NONE: All tables in the table group are aggregated on the same machine.

2. PARTITION: Data of each table in the table group is scattered by primary partitions. For secondary partitioned tables, all secondary partitions under each primary partition are aggregated.

3. ADAPTIVE: Data of each table in the table group is scattered based on adaptive strategies. For primary partitioned tables, data is scattered by primary partitions. For secondary partitioned tables, data is scattered by secondary partitions under each primary partition.

For more information, see [Data distribution](../../600.manage/300.replica-management/400.data-distribution.md), [Table groups in MySQL mode](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md), and [Table groups in Oracle mode](../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/300.manage-table-groups-of-oracle-mode/100.about-table-groups-of-oracle-mode.md).

## Index types

Indexes are key components for improving query performance. OceanBase Database supports various index types in AP scenarios to provide flexible and efficient data retrieval. The following are some common index types and their use cases:

* **Local indexes**: Local indexes are created on individual partitions and are suitable for scenarios requiring localized data queries. When data is strictly partitioned, local indexes significantly reduce the data scanning scope during queries, thus improving query efficiency.
* **Unique indexes**: Unique indexes ensure that each value in a column is unique. By creating unique indexes on certain columns, databases can effectively prevent data duplication and accelerate query processes.
* **Non-unique indexes**: Unlike unique indexes, non-unique indexes do not require all values in a column to be unique. They are primarily used to accelerate data queries, especially when retrieving multiple records that meet specific conditions.
* **Full-text indexes**: OceanBase Database supports full-text search capabilities compatible with MySQL. By preprocessing text content and building keyword indexes, it effectively enhances full-text search efficiency. For more information about full-text indexes, see [Full-text indexes](../../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/300.index-of-oracle-mode/320.full-text-indexes-of-mysql-mode-in-concepts.md).
* **JSON multi-value indexes**: OceanBase Database's MySQL mode supports multi-value indexes, which are particularly useful for JSON documents and other collection data types. This feature allows indexes to be created on arrays or collections, thereby improving query efficiency when searching based on JSON array elements. For more information about multi-value indexes, see [Multi-value indexes](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).
* **Spatial indexes**: Spatial indexes are used to optimize the efficiency of queries on geographic space data. They are widely applied in geographic information systems (GIS) and location-based services. In these applications, spatial indexes can quickly retrieve data within a geographic coordinate range, providing strong support for location services.
* **Columnstore indexes**: In HTAP (Hybrid Transactional and Analytical Processing) scenarios, OceanBase Database has supported columnstore indexes since version V4.3.0. When creating tables, you can specify the storage format as columnstore. Indexes and data tables are both stored as tables, so you can also store data in index tables in columnstore format. Columnstore indexes store data based on columns rather than rows, significantly improving the performance of analytical queries, especially when processing large-scale data. For more information about columnstore, see [Columnstore](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/320.columnstore-engine.md).

For more information about indexes, see [Indexes in MySQL mode](../../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/300.index-of-oracle-mode/100.index-overview-of-mysql-mode.md) and [Indexes in Oracle mode](../../700.reference/100.oceanbase-database-concepts/400.database-objects/100.database-objects-of-oracle-mode/300.index-of-oracle-mode/100.the-index-overview-of-oracle-mode.md).

## Data types

Before creating and using tables, database administrators need to plan the table structure and data types based on business requirements. To ensure efficient data storage and optimized queries, administrators should follow these principles:

* **Normalize the table structure**: Design tables to minimize data redundancy and improve query efficiency.
* **Select appropriate SQL data types**: Choose the most suitable SQL data types for each column to reduce storage space and enhance query speed.

Common SQL data types include:

* **Basic data types**: such as `INT`, `VARCHAR`, and `DATE`.
* **Complex data types**: such as `JSON`, `ARRAY`, and `BITMAP`, suitable for storing more complex data structures.

For detailed descriptions of SQL data types, see:

## Views

OceanBase Database supports standard views and materialized views.

* **Standard views**: Standard views, also known as non-materialized views, are the most common type of view. They store only the SQL query that defines the view, not the query results.
* **Materialized views**: Unlike standard views, materialized views physically store the query results. OceanBase Database supports asynchronous materialized views, which means that materialized views are not immediately updated when the base table data changes. This ensures the execution performance of DML operations on the base table. For more information, see [Materialized views in MySQL mode](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/100.materialized-views-overview-of-mysql-mode.md) and [Materialized views in Oracle mode](../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/500.manage-views-of-oracle-mode/200.manage-materialized-views-of-oracle-mode/100.materialized-views-overview-of-oracle-mode.md).

## Create a table example

Create a table that contains partitions, columnar, and row-based indexes

```sql
CREATE TABLE salesdata (
    sale_id INT,
    product_id INT NOT NULL,
    saledate DATE NOT NULL,
    saledate_int INT, -- Defined as a regular column
    quantity INT,
    price DECIMAL(10, 2),
    customer_id INT,
    PRIMARY KEY (sale_id, saledate_int) -- The primary key can contain regular columns.
)
PARTITION BY RANGE COLUMNS (saledate_int) (
    PARTITION p2023_q1 VALUES LESS THAN (202304),
    PARTITION p2023_q2 VALUES LESS THAN (202307),
    PARTITION p2023_q3 VALUES LESS THAN (202310),
    PARTITION p2023_q4 VALUES LESS THAN (202401)
)
WITH COLUMN GROUP (each column);

CREATE INDEX idx_product_id ON salesdata(product_id);
CREATE INDEX idx_customer_id ON salesdata(customer_id);
```

1. **Partitions**: The `salesdata` table uses **range-based partitioning** (RANGE).

   * `PARTITION BY RANGE COLUMNS (saledate_int)`: The table is partitioned based on the `saledate_int` column.

   * Four partitions are defined:

     - The `p2023_q1` partition contains data from before 202304 (i.e., the first quarter of 2023).
     - The `p2023_q2`, `p2023_q3`, and `p2023_q4` partitions contain data for the second, third, and fourth quarters of 2023, respectively.

2. **Columnar storage**: **Columnar storage** is specified using `WITH COLUMN GROUP (each column)`. Data from these columns will be stored in a columnar format, which is suitable for large-scale data analysis scenarios.

3. **Row-based indexes**: Two indexes (`idx_product_id` and `idx_customer_id`) are created on the `product_id` and `customer_id` columns, respectively. Row-based indexes can accelerate queries based on specific columns, especially for frequently executed small queries.

When creating and using a columnar storage table, if you import a large amount of data, you need to perform a **compaction** operation to improve read performance and collect **statistics** to adjust the execution strategy.

* **Compaction**: After importing data in batches, it is recommended to perform a compaction operation. This helps improve read performance because the compaction operation organizes fragmented data, making it more contiguous in physical storage and reducing disk I/O during reads. After importing data, trigger a compaction operation in the tenant to ensure that all data is merged into the baseline layer. For more information, see [MAJOR and MINOR (MySQL mode)](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1500.alter-system-freeze-of-mysql-mode.md) and [MAJOR and MINOR (Oracle mode)](../../700.reference/500.sql-reference/100.sql-syntax/300.common-tenant-of-oracle-mode/900.sql-statement-of-oracle-mode/100.ddl-of-oracle-mode/4600.alter-system-major-freeze-of-oracle-mode.md).

* **Statistics collection**: After the compaction operation is completed, we recommend that you collect statistics. This is important for the optimizer to generate effective query plans and execution strategies. For more information, see [GATHER_SCHEMA_STATS (MySQL mode)](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/15900.dbms-stats-mysql/1800.gather-schema-stats-mysql.md) and [GATHER_SCHEMA_STATS (Oracle mode)](../../700.reference/600.pl-reference/300.pl-oracle/1400.pl-system-package-oracle/15900.dbms-stats-oracle/1800.gather-schema-stats-oracle.md). Monitor the progress of the statistics collection by querying the [GV$OB_OPT_STAT_GATHER_MONITOR (MySQL mode)](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/6100.gv_ob_opt_stat_gather_monitor-of-mysql-mode.md) and [GV$OB_OPT_STAT_GATHER_MONITOR (Oracle mode)](../../700.reference/700.system-views/500.system-view-of-oracle-mode/300.performance-view-of-oracle-mode/2000.gv-ob_opt_stat_gather_monitor-of-oracle-mode.md) views.

Note that as the amount of data in the columnar storage table increases, the speed of the compaction operation may decrease.
