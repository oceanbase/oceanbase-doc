# Overview of tables

In **OceanBase** Database, tables are the most fundamental data storage units. Tables contain all the data that users can access, and each table consists of multiple rows. Each row contains multiple columns. The design and usage of each table must be reasonably planned based on business requirements to ensure the system's efficiency and scalability.

## Table types

OceanBase Database supports various table types, including partitioned tables, replicated tables, primary key tables, non-primary key tables, external tables, and heap tables.

* **Partitioned tables**: A partitioned table divides data from a regular table into different partitions based on specific rules, storing the data of the same partition together. OceanBase Database supports range, list, and hash partitioning.
* **Replicated tables**: A replicated table is a special type of table in OceanBase Database. Data in a replicated table can be read from any healthy replica.
* **Primary key tables and non-primary key tables**: A primary key table contains a primary key, while a non-primary key table does not specify a primary key.
* **External tables**: Data in a regular table is stored in the database's storage space, while data in an external table is stored in an external storage service.
* **Heap tables**: In a heap-organized table, the primary key is used for uniqueness constraints, and queries rely on the primary table. When user data is sorted by time, the Skip Index can be more effectively utilized to improve query efficiency.

In **AP scenarios**, OceanBase Database supports various table types, including **replicated tables**, **partitioned tables**, **primary key tables**, and **non-primary key tables** as in **TP scenarios**. Additionally, based on the data storage method (row-based or column-based), new table types are introduced: **columnstore tables** and **hybrid row-column tables**.

* **Columnstore tables**: Columnstore tables store data by columns rather than by rows, significantly improving the performance of analytical queries. They are particularly suitable for scenarios with large amounts of data and frequent aggregation analysis. For more information, see [Columnstore tables](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/320.columnstore-engine.md).

* **Hybrid row-column tables**: Data is stored both by rows and by columns. The system automatically determines whether to use row-based or column-based queries based on the query statement. These tables are suitable for scenarios that require both transactional and analytical operations.

## Table update modes

OceanBase Database allows you to specify the write and query modes when creating a table. You can use the `merge_engine` parameter in the `CREATE TABLE` statement to choose between **delete_insert** and **partial_update** update modes. These modes are designed for different business scenarios.

* **delete_insert (full-column update mode)**

  This mode prioritizes **query performance**. Each update writes a complete row (delete the old row + insert the new row), ensuring that each row contains all column values. This mode supports Skip Index for incremental data (Memtable/Delta SSTable). During queries, incremental data can be filtered and pushed down. If the filtering result does not involve updates to baseline data, baseline and incremental data can be batch-processed separately, reducing read amplification. This mode is suitable for **OLAP scenarios with a high proportion of incremental data, frequent complex queries, or batch processing analysis**, but incremental data will occupy more storage space.

* **partial_update (partial update mode)**

  This mode only records the modified columns (delta), saving storage space. During queries, multiple data sets need to be merged to obtain the latest value, resulting in relatively lower performance. However, this mode is more suitable for **scenarios with frequent updates but low query requirements** (such as OLTP scenarios) or environments sensitive to storage costs.

* **append_only (insert-only update mode)**

  This mode allows only `INSERT` operations and prohibits all other DML and DDL operations that modify stored data. It is suitable for scenarios such as IoT, monitoring, and financial transactions. If you need to clean up expired data, you can use the TTL feature.

| **Feature Category** | **delete_insert Update Mode** | **partial_update Update Mode** | **append_only Update Mode** |
| --- | --- | --- | --- |
| **Storage Method** | Each update writes two rows (`DELETE` and `INSERT`) in the SSTable, containing all column data. | Only the modified columns are recorded, saving storage space. | Inserts new data into the SSTable. |
| **Query Efficiency** | Supports Delta SSTable Skip Index. During queries, filtering operators can be pushed down to the Memtable/Delta SSTable. If the filtering result involves updates to baseline data, the latest value can be obtained by merging incremental and baseline records. | During queries, multiple Memtable/SSTable records need to be merged to obtain the latest primary key value, which may affect performance. | **Skip Index Support Scope** | Baseline + All incremental SSTables (minor/mini) | Only baseline SSTables | Baseline + All incremental SSTables |

## Data distribution

OceanBase Database distributes data across different partitions by creating partitioned tables. Data in different partitions can be distributed across different machines. During queries, partition pruning reduces the amount of data scanned and leverages resources across multiple machines to enhance query performance. By default, data across different tables is randomly distributed without direct relationships. Load balancing ensures a relatively even distribution of a table's data across the entire cluster.

In distributed AP systems, tables often contain large amounts of data. When data across different tables is randomly distributed, the overhead of data transmission during table joins can be significant. Using [Table Groups](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md) (Table Group) allows partitioned tables with the same partitioning method to align data according to specific rules. This aggregates related data on the same machine, enabling the use of Partition Wise Join during table joins. This significantly reduces data transmission overhead in join scenarios and improves performance.

OceanBase Database supports primary and secondary partitioned tables and supports RANGE, LIST, and HASH partitioning types.

OceanBase Database provides three types of table groups:

1. NONE: All tables in the table group are aggregated on the same machine.

2. PARTITION: Data of each table in the table group is scattered by primary partitioning. If the table is a secondary partitioned table, all secondary partitions under each primary partition are aggregated.

3. ADAPTIVE: Data of each table in the table group is scattered based on adaptive methods. If the tables in the table group are primary partitioned tables, they are scattered by primary partitioning. If the tables in the table group are secondary partitioned tables, they are scattered by secondary partitioning under each primary partition.

For more information, see [Data distribution](../../600.manage/300.replica-management/400.data-distribution.md), [Table groups in MySQL mode](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md), and [Table groups in Oracle mode](../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/300.manage-table-groups-of-oracle-mode/100.about-table-groups-of-oracle-mode.md).

## Index types

Indexes are key components for improving query performance. OceanBase Database supports various index types in AP scenarios to provide flexible and efficient data retrieval methods. Here are some common index types and their use cases:

* **Local Index**: A local index is created for a single partition and is suitable for scenarios requiring localized data queries. When data is strictly partitioned into multiple partitions, a local index can significantly reduce the data scanning scope during queries, thereby improving query efficiency.
* **Unique Index**: A unique index ensures that each value in a data column is unique. By creating a unique index on certain columns, the database can effectively prevent data duplication and accelerate query processes.
* **Non-Unique Index**: Unlike a unique index, a non-unique index does not require all values in a column to be unique. It is primarily used to accelerate data queries, especially when retrieving multiple records that meet specific conditions, significantly improving retrieval efficiency.
* **Full-Text Index**: OceanBase Database supports full-text search capabilities compatible with MySQL. By preprocessing text content and establishing keyword indexes, it effectively enhances the efficiency of full-text searches. For more information about full-text indexes, see [Full-text indexes](../../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/300.index-of-oracle-mode/320.full-text-indexes-of-mysql-mode-in-concepts.md).
* **JSON Multi-Value Index**: OceanBase Database's MySQL mode supports multi-value indexing, which is particularly useful for JSON documents and other collection data types. This feature allows you to create indexes on arrays or collections, thereby improving the efficiency of queries based on JSON array elements. For more information about multi-value indexes, see [Multi-value indexes](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).
* **Spatial Index**: Spatial indexes optimize the efficiency of geographic spatial data queries and are widely used in geographic information systems (GIS) and location-based services. In these applications, spatial indexes can quickly retrieve data information within a geographic coordinate range, providing strong support for location services.
* **Columnstore Index**: In Hybrid Transactional and Analytical Processing (HTAP) scenarios, OceanBase Database, starting from version V4.3.0, supports creating tables with a specified storage format as columnstore. Indexes and data tables are both considered as tables, so it also supports storing data in index tables in a columnar format. Columnstore indexes store data based on columns rather than rows, significantly enhancing the performance of analytical queries, especially when handling large-scale data, by greatly reducing the time required for data retrieval and analysis, thus enabling real-time analytics. For more information about columnstore, see [Columnstore](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/320.columnstore-engine.md).

For more information about indexes, see [Overview of indexes in MySQL mode](../../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/300.index-of-oracle-mode/100.index-overview-of-mysql-mode.md) and [Overview of indexes in Oracle mode](../../700.reference/100.oceanbase-database-concepts/400.database-objects/100.database-objects-of-oracle-mode/300.index-of-oracle-mode/100.the-index-overview-of-oracle-mode.md).

## Data types

Before creating and using tables, database administrators need to plan the table structure and data types based on business requirements. To ensure efficient data storage and optimized queries, administrators should follow these principles:

* **Normalize the table structure**: Design tables to minimize data redundancy and improve query efficiency.
* **Select appropriate SQL data types**: Choose the most suitable SQL data types for each column to reduce storage space and enhance query speed.

Common SQL data types include:

* **Basic data types**: Such as `INT`, `VARCHAR`, `DATE`, etc.
* **Complex data types**: Such as `JSON`, `ARRAY`, `BITMAP`, etc., suitable for storing more complex data structures.

For detailed descriptions of SQL data types, see:

## Views

OceanBase Database supports standard views and materialized views.

* **Standard views**: Standard views are also known as non-materialized views. They are the most common type of view. They store only the SQL query that defines the view, not the query results.
* **Materialized views**: Unlike standard views, materialized views store the results of the query in physical storage. OceanBase Database supports asynchronous materialized views, where the materialized view is not immediately updated when the base table data changes, ensuring the performance of DML operations on the base table. For more information, see [Materialized views in MySQL mode](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/100.materialized-views-overview-of-mysql-mode.md) and [Materialized views in Oracle mode](../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/500.manage-views-of-oracle-mode/200.manage-materialized-views-of-oracle-mode/100.materialized-views-overview-of-oracle-mode.md).

## Sample of creating a table

The following example creates a table with partitions, columnstore, and rowstore indexes.

```sql
CREATE TABLE salesdata (
    sale_id INT,
    product_id INT NOT NULL,
    saledate DATE NOT NULL,
    saledate_int INT, -- Defined as a regular column
    quantity INT,
    price DECIMAL(10, 2),
    customer_id INT,
    PRIMARY KEY (sale_id, saledate_int) -- Primary key can include regular columns
)
PARTITION BY RANGE COLUMNS (saledate_int) (
    PARTITION p2023_q1 VALUES LESS THAN (202304),
    PARTITION p2023_q2 VALUES LESS THAN (202307),
    PARTITION p2023_q3 VALUES LESS THAN (202310),
    PARTITION p2023_q4 VALUES LESS THAN (202401)
)
WITH COLUMN GROUP(each column);

CREATE INDEX idx_product_id ON salesdata(product_id);
CREATE INDEX idx_customer_id ON salesdata(customer_id);
```

1. **Partitioning**: The `salesdata` table uses **range partitioning**.

   * `PARTITION BY RANGE COLUMNS (saledate_int)`: Partitions the table using the `saledate_int` column.

   * Defined four partitions:

     - The `p2023_q1` partition contains data before `202304` (i.e., the first quarter of 2023).
     - The `p2023_q2`, `p2023_q3`, and `p2023_q4` partitions contain data for the second, third, and fourth quarters of 2023, respectively.

2. **Columnstore**: The **columnstore storage** is specified using `WITH COLUMN GROUP(each column);`. This stores data for these columns in a columnar format, which is ideal for large-scale data analysis.

3. **Rowstore indexes**: Two indexes `idx_product_id` and `idx_customer_id` are created on the `product_id` and `customer_id` columns, respectively. Rowstore indexes can accelerate queries based on specific columns, especially for frequent, small queries.

When creating and using a columnstore table, if you import a large amount of data, you need to execute a **major compaction** to improve read performance and to **collect statistics**, and adjust the execution strategy.

* **Major compaction**: After you import data in batch, we recommend that you perform a major compaction. A major compaction organizes fragmented data to make it more contiguous in physical storage. This reduces disk I/O during reads. After the data is imported, we recommend that you trigger a major compaction within a tenant to ensure that all data is merged into the baseline layer. For more information, see [MAJOR and MINOR (MySQL mode)](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1500.alter-system-freeze-of-mysql-mode.md) and [MAJOR and MINOR (Oracle mode)](../../700.reference/500.sql-reference/100.sql-syntax/300.common-tenant-of-oracle-mode/900.sql-statement-of-oracle-mode/100.ddl-of-oracle-mode/4600.alter-system-major-freeze-of-oracle-mode.md).

* **Statistics collection**: After you complete a major compaction, we recommend that you collect statistics. This is important for the optimizer to generate effective query plans and execution strategies. Execute [GATHER_SCHEMA_STATS (MySQL mode)](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/15900.dbms-stats-mysql/1800.gather-schema-stats-mysql.md) or [GATHER_SCHEMA_STATS (Oracle mode)](../../700.reference/600.pl-reference/300.pl-oracle/1400.pl-system-package-oracle/15900.dbms-stats-oracle/1800.gather-schema-stats-oracle.md) to collect statistics for all tables. You can monitor the progress of the statistics collection by querying the [GV$OB_OPT_STAT_GATHER_MONITOR (MySQL mode)](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/6100.gv_ob_opt_stat_gather_monitor-of-mysql-mode.md) or [GV$OB_OPT_STAT_GATHER_MONITOR (Oracle mode)](../../700.reference/700.system-views/500.system-view-of-oracle-mode/300.performance-view-of-oracle-mode/2000.gv-ob_opt_stat_gather_monitor-of-oracle-mode.md) view.

Note that as the amount of data in the columnstore table increases, the major compaction might take more time.
