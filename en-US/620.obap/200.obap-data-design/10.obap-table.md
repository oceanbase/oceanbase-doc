# Overview of tables

In **OceanBase** Database, tables are the fundamental data storage units. Tables contain all the data that users can access. Each table consists of multiple rows, and each row contains multiple columns. The design and usage of each table must be reasonably planned based on business requirements to ensure the efficiency and scalability of the system.

## Table types

OceanBase Database supports various table types, including partitioned tables, replicated tables, primary key tables, non-primary key tables, and external tables.

* Partitioned tables: OceanBase Database allows you to partition a regular table into different partitions based on specific rules. Data in the same partition is physically stored together. This type of table is called a partitioned table. OceanBase Database supports basic partitioning strategies such as range partitioning, list partitioning, and hash partitioning.
* Replicated tables: A replicated table is a special type of table in OceanBase Database. This table allows you to read the latest data modifications from any "healthy" replica.
* Primary key tables and non-primary key tables: A primary key table is a table that contains a primary key. A non-primary key table is a table that does not specify a primary key.
* External tables: Data of a regular table is stored in the storage space of the database, while data of an external table is stored in an external storage service.
* Heap tables: In a heap-organized table, the primary key is used for uniqueness constraints, and queries rely on the primary table. When user data is sorted by time, the Skip Index feature can be more effectively utilized to improve query efficiency.

In the **AP scenario**, OceanBase Database supports various table types, including **replicated tables**, **partitioned tables**, **primary key tables**, and **non-primary key tables** as in the **TP scenario**. Based on the data storage method, whether data is stored by rows or columns, new table types are introduced: **columnstore tables** and **hybrid row-column tables**.

* **Columnstore tables**: Columnstore tables store data by columns rather than by rows. This significantly improves the performance of analytical queries, especially in scenarios with large amounts of data and frequent aggregation analysis. For more information, see [Columnstore tables](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/320.columnstore-engine.md).

* **Hybrid row-column tables**: Data is stored both by rows and columns. The system automatically determines whether to use row-based or column-based queries based on the query statement. This type of table is suitable for scenarios that require both transactional and analytical operations.

## Table update modes

OceanBase Database allows you to specify the write and query modes for data when creating a table. When creating a table, you can use the `merge_engine` parameter in the `CREATE TABLE` statement to choose between **delete_insert update mode** and **partial_update update mode**. These two modes are data update strategies designed for different business scenarios.

* **delete_insert (Full Column Update Mode)**

  This mode prioritizes **query performance**. Each update writes a complete row (delete the old row + insert the new row), ensuring that each row contains all column values. This mode supports Skip Index for incremental data (Memtable/Delta SSTable). During queries, incremental data can be filtered and pushed down. If the filtering result does not involve updates to the baseline data, baseline and incremental data can be batch processed separately, reducing read amplification. This mode is suitable for **OLAP scenarios with a high proportion of incremental data, frequent complex queries, or batch processing analysis**, but incremental data will occupy more storage space.

* **partial_update (Partial Update Mode)**

  This mode only records the modified columns (delta), saving storage space. During queries, multiple data sets need to be merged to obtain the latest value, resulting in relatively lower performance. However, this mode is more suitable for **scenarios with frequent updates but low query requirements** (such as OLTP scenarios) or environments sensitive to storage costs.

* **append_only (Only INSERT Update Mode)**

  This mode allows only `INSERT` operations and prohibits all other DML and DDL operations that would modify stored data. It is suitable for scenarios such as IoT, monitoring, and financial transactions. If you need to clean up expired data, you can use the TTL feature.

| **Feature Category** | **delete_insert Update Mode** | **partial_update Update Mode** | **append_only Update Mode** |
| --- | --- | --- | --- |
| **Storage Method** | Each update writes two rows (`DELETE` and `INSERT`) in the SSTable, containing all column data. | Only the modified columns are recorded, saving storage space. | The `INSERT` operation writes new data to the SSTable. |
| **Query Efficiency** | Supports Delta SSTable Skip Index. During queries, filtering operators can be calculated and pushed down on the Memtable/Delta SSTable. If the filtering result does not involve updates to the baseline data, baseline and incremental data can be batch processed separately, reducing read amplification. If the filtering result involves updates to the baseline data, the latest value can be obtained by merging incremental and baseline records. | During queries, multiple Memtable/SSTable records need to be merged to obtain the latest value of the primary key, which may affect performance. This mode is suitable for scenarios sensitive to storage costs with frequent updates. | Enables `skip_index_level = 1`, allowing real-time data to be efficiently filtered. |
| **Scenarios** | OLAP scenarios with a high proportion of incremental data, frequent complex queries, or batch processing analysis. | OLTP scenarios with frequent updates but low query requirements. | Scenarios requiring immutability, efficient appending, and simplified queries. |
| **Skip Index Support Scope** | Baseline + all incremental SSTables (minor/mini) | Only baseline SSTables | Baseline + all incremental SSTables |

## Data distribution

OceanBase Database distributes data across different partitions by creating partitioned tables. Data in different partitions can be distributed to different machines. During queries, partition pruning can reduce the amount of data scanned, and the resources of multiple machines can be leveraged to improve query performance. By default, data between different tables is randomly distributed and has no direct relationship. Through load balancing, data of a table can be evenly distributed across the entire cluster.

In a distributed AP system, the amount of data in tables is usually large. When data in different tables is randomly distributed, the overhead of data transmission during table joins is often significant. Using [Table Groups](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md) (Table Group) allows partitioned tables with the same partitioning method to align according to specific rules. This way, related data can be aggregated on the same machine, enabling Partition Wise Join during table joins. This effectively reduces the overhead of data transmission in join scenarios and improves performance.

![](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer/ap/table-group.png)

OceanBase Database supports both primary and secondary partitioned tables, and it supports RANGE, LIST, and HASH partitioning.

OceanBase Database provides three types of table groups:

1. NONE: All tables in the table group are aggregated on the same machine.

2. PARTITION: Data in each table of the table group is scattered by primary partitions. If the table is a secondary partitioned table, all secondary partitions under each primary partition are aggregated.

3. ADAPTIVE: Data in each table of the table group is scattered based on adaptive methods. If the tables in the table group are primary partitioned tables, they are scattered by primary partitions. If the tables in the table group are secondary partitioned tables, they are scattered by secondary partitions under each primary partition.

For more information, see [Data distribution](../../600.manage/300.replica-management/400.data-distribution.md), [Table groups in MySQL mode](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md), and [Table groups in Oracle mode](../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/300.manage-table-groups-of-oracle-mode/100.about-table-groups-of-oracle-mode.md).

## Index types

Indexes are key components for improving query performance. OceanBase Database provides flexible and efficient data retrieval methods in AP scenarios by supporting various index types. Here are some common index types and their use cases:

* **Local indexes**: Local indexes are indexes created on individual partitions. They are suitable for scenarios requiring local data queries. When data is strictly divided into multiple partitions, local indexes can significantly reduce the data scanning scope during queries, thereby improving query efficiency.
* **Unique indexes**: Unique indexes ensure that each value in a column is unique. By creating unique indexes on certain columns, the database can effectively prevent data duplication and accelerate query processes.
* **Non-unique indexes**: Unlike unique indexes, non-unique indexes do not require all values in a column to be unique. They are mainly used to accelerate data queries, especially when searching for multiple records that meet specific conditions, significantly improving retrieval efficiency.
* **Full-text indexes**: OceanBase Database supports full-text search capabilities compatible with MySQL. By preprocessing text content and creating keyword indexes, it effectively improves full-text search efficiency. For more information about full-text indexes, see [Full-text indexes](../../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/300.index-of-mysql-mode/320.full-text-indexes-of-mysql-mode-in-concepts.md).
* **Multi-value JSON indexes**: OceanBase Database's MySQL mode supports multi-value indexing, which is particularly useful for JSON documents and other collection data types. This feature allows you to create indexes on arrays or collections, thereby improving query efficiency when searching for elements within JSON arrays. For more information about multi-value indexes, see [Multi-value indexes](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).
* **Spatial indexes**: Spatial indexes optimize the query efficiency of geographic space data and are widely used in geographic information systems (GIS) and location-based services. In these applications, spatial indexes can quickly retrieve data within a geographic coordinate range, providing strong support for location services.
* **Columnstore indexes**: In Hybrid Transactional and Analytical Processing (HTAP) scenarios, OceanBase Database supports creating tables with columnar storage format starting from version V4.3.0. Indexes and data tables are both considered as tables, so indexes can also be stored in columnar format. Columnstore indexes store data based on columns rather than rows, significantly improving the performance of analytical queries, especially when handling large-scale data by significantly reducing data retrieval and analysis time, enabling real-time analytics. For more information about columnar storage, see [Columnar storage](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/320.columnstore-engine.md).

For more information about indexes, see [Overview of indexes in MySQL mode](../../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/300.index-of-mysql-mode/100.index-overview-of-mysql-mode.md) and [Overview of indexes in Oracle mode](../../700.reference/100.oceanbase-database-concepts/400.database-objects/100.database-objects-of-oracle-mode/300.index-of-oracle-mode/100.the-index-overview-of-oracle-mode.md).

## Data types

Before creating and using tables, database administrators must plan the table structure and data types based on business requirements. To ensure efficient data storage and optimized queries, administrators should follow these principles:

* **Normalize the table structure**: By designing the table structure appropriately, minimize data redundancy and improve query efficiency.
* **Choose appropriate SQL data types**: Select the most suitable SQL data type for each column to reduce storage space and enhance query speed.

Common SQL data types include:

* **Basic data types**: Such as `INT`, `VARCHAR`, `DATE`, etc.
* **Complex data types**: Such as `JSON`, `ARRAY`, `BITMAP`, etc., suitable for storing more complex data structures.

For detailed descriptions of SQL data types, see:

## Views

OceanBase Database supports standard views and materialized views.

* **Standard views**: Standard views, also known as non-materialized views, are the most common type of view. They store only the SQL query that defines the view, not the query results.
* **Materialized views**: Unlike standard views, materialized views store the query results physically. OceanBase Database supports asynchronous materialized views, where the materialized view is not immediately updated when the base table data changes, ensuring the performance of DML operations on the base table. For more information, see [Materialized views in MySQL mode](../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/100.materialized-views-overview-of-mysql-mode.md) and [Materialized views in Oracle mode](../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/500.manage-views-of-oracle-mode/200.manage-materialized-views-of-oracle-mode/100.materialized-views-overview-of-oracle-mode.md).

## Create a table with partitions, column store, and row store indexes

The following example shows how to create a table with partitions, column store, and row store indexes:

```sql
CREATE TABLE salesdata (
    sale_id INT,
    product_id INT NOT NULL,
    saledate DATE NOT NULL,
    saledate_int INT, -- Column defined as a normal column.
    quantity INT,
    price DECIMAL(10, 2),
    customer_id INT,
    PRIMARY KEY (sale_id, saledate_int) -- A primary key can include a normal column.
)
PARTITION BY RANGE COLUMNS (saledate_int) (
    PARTITION p2023_q1 VALUES LESS THAN (202304),
    PARTITION p2023_q2 VALUES LESS THAN (202307),
    PARTITION p2023_q3 VALUES LESS THAN (202310),
    PARTITION p2023_q4 VALUES LESS THAN (202401)
)
WITH COLUMN GROUP(each column);

CREATE INDEX idx_product_id ON salesdata(product_id);
CREATE INDEX idx_customer_id ON salesdata(customer_id);
```

1. **Partition**: The `salesdata` table is partitioned by **RANGE**.

   * `PARTITION BY RANGE COLUMNS (saledate_int)` specifies that the table is partitioned by the `saledate_int` column.

   * Four partitions are defined:

     - The `p2023_q1` partition contains data prior to `202304`, representing the first quarter of 2023.
     - The `p2023_q2`, `p2023_q3`, and `p2023_q4` partitions contain data for the second, third, and fourth quarters of 2023, respectively.

2. **Column store**: The `WITH COLUMN GROUP(each column)` statement specifies a **columnar store**. This storage method is suitable for large-scale data analysis.

3. **Row store indexes**: The `idx_product_id` and `idx_customer_id` indexes are created for the `product_id` and `customer_id` columns, respectively. Row store indexes help accelerate queries based on specific columns, especially for high-frequency small queries.

When you create and use a columnar store table and import a large amount of data, you need to perform a **major compaction** to optimize read performance and collect **statistics** to adjust the execution strategy.

* **Major compaction**: After you import data in batches, we recommend that you perform a major compaction. This operation improves read performance by compacting fragmented data and making it more continuous in physical storage, thus reducing disk I/O when read requests occur. After you import data, perform a major compaction in the tenant. For more information, see [MAJOR and MINOR (MySQL mode)](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1500.alter-system-freeze-of-mysql-mode.md) and [MAJOR and MINOR (Oracle mode)](../../700.reference/500.sql-reference/100.sql-syntax/300.common-tenant-of-oracle-mode/900.sql-statement-of-oracle-mode/100.ddl-of-oracle-mode/4600.alter-system-major-freeze-of-oracle-mode.md).

* **Statistics collection**: After the major compaction is completed, we recommend that you collect statistics. This is essential for the optimizer to generate effective query plans and execution strategies. Use the [GATHER_SCHEMA_STATS (MySQL mode)](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/15900.dbms-stats-mysql/1800.gather-schema-stats-mysql.md) or [GATHER_SCHEMA_STATS (Oracle mode)](../../700.reference/600.pl-reference/300.pl-oracle/1400.pl-system-package-oracle/15900.dbms-stats-oracle/1800.gather-schema-stats-oracle.md) statement to collect statistics for all tables. Monitor the statistics collection progress by querying the [GV$OB_OPT_STAT_GATHER_MONITOR (MySQL mode)](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/6100.gv_ob_opt_stat_gather_monitor-of-mysql-mode.md) or [GV$OB_OPT_STAT_GATHER_MONITOR (Oracle mode)](../../700.reference/700.system-views/500.system-view-of-oracle-mode/300.performance-view-of-oracle-mode/2000.gv-ob_opt_stat_gather_monitor-of-oracle-mode.md) view.

Note that the speed of a major compaction may decrease as the amount of data in a columnar store table increases.
