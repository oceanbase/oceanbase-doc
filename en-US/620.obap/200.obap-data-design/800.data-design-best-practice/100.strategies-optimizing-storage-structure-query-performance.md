# Data table design and query optimization in AP scenarios

In the design and optimization of a database system, data table design is a crucial task. A well-designed data table not only ensures data integrity and consistency but also significantly improves query performance, storage efficiency, and system scalability. As data volume grows and query patterns become more complex, how to scientifically design data tables, choose appropriate storage structures, and select suitable index strategies, becomes the core issue in database optimization.

This topic will introduce best practices for data table design by covering topics such as choosing the storage format for tables, designing tables without primary keys, partitioning, primary key design, and using indexes in HTAP scenarios.

## Choose the storage format for a table

OceanBase Database supports columnar and row-column hybrid storage formats for tables. You can choose the appropriate storage format based on your business scenario.

+ **Columnar storage**: suitable for OLAP scenarios.
+ **Row-column hybrid storage**: suitable for HTAP scenarios. This format is suitable for scenarios that contain both OLAP and OLTP operations. It ensures the performance of analysis queries and point queries.

You can set the default storage format for tables in a tenant by using the [default_table_store_format](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) parameter.

```sql
-- Set the default storage format for tables in the tenant to columnar.
ALTER SYSTEM SET default_table_store_format = "column";

-- Set the default storage format for tables in the tenant to row-column hybrid.
ALTER SYSTEM SET default_table_store_format = "compound";
```

## Design primary keys

Designing primary keys is a crucial aspect of relational database table design in OceanBase Database. Primary keys ensure data uniqueness and, since data is sorted by primary keys, they can optimize the performance of range queries. Different primary key design schemes are suitable for different business scenarios.

### No primary key scenario

#### Choose a columnar table without a primary key

In data warehouse or online analytical processing (OLAP) scenarios, business data tables often contain a large amount of data, and most queries only involve certain columns. If the business does not have specific requirements such as ensuring data uniqueness, avoiding duplicate writes, or performing transactional updates or inserts, creating a columnar table without a primary key is more efficient:

+ **Data import:** In AP scenarios, data does not need to be sorted by the primary key, resulting in faster import performance compared to tables with primary keys.
+ **Reduced management costs of primary keys.**

```sql
show parameters like "%store_format%";

  CREATE TABLE customer (
  user_id bigint NOT NULL,
  login_time timestamp NOT NULL,
  customer_name varchar(100) NOT NULL,    -- Assume that the maximum length of customer names is 100 characters.
  phone_num bigint NOT NULL,               -- Store phone numbers as big integers.
  city_name varchar(50) NOT NULL,          -- Assume that the maximum length of city names is 50 characters.
  sex int NOT NULL,                        -- Store gender as integers (e.g., 0 for female and 1 for male).
  id_number varchar(18) NOT NULL,          -- Assume that the maximum length of ID numbers is 18 characters.
  home_address varchar(255) NOT NULL,      -- Assume that the maximum length of home addresses is 255 characters.
  office_address varchar(255) NOT NULL,    -- Assume that the maximum length of office addresses is 255 characters.
  age int NOT NULL                         -- Store age as integers.
);
```

### With primary key scenario

In AP scenarios, **heap tables** are used by default. Their characteristics are as follows:

* **Data storage:** Data is stored in the order of insertion without physical sorting.
* **Role of the primary key:**

  + Ensures data uniqueness by including fields that can uniquely identify records (such as user_id).
  + Supports **partition key embedding**, where the primary key must include all partition keys (such as user_id and age) to ensure even data distribution.
  + Requires the use of indexes or partitioning strategies to accelerate queries (e.g., `ORDER BY`).

Example: Design of a heap-organized table with a primary key

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    -- The primary key includes all partition keys (user_id and age)
    PRIMARY KEY (user_id, age, login_time)
)
-- Main partition: distributed by user_id using hashing
PARTITION BY HASH(user_id)
PARTITIONS 128
SUBPARTITION BY RANGE(age)
SUBPARTITION TEMPLATE (
    -- Example partitions: divided by age groups
    SUBPARTITION p_youth VALUES LESS THAN (25),      -- Age <25
    SUBPARTITION p_adult VALUES LESS THAN (40),      -- 25 ≤ age <40
    SUBPARTITION p_middle_aged VALUES LESS THAN (60),-- 40 ≤ age <60
    SUBPARTITION p_senior VALUES LESS THAN (MAXVALUE) -- Age 60 and above
);
```

### Add primary key scenario

* **Ensure data uniqueness:** When the uniqueness of each record in the table needs to be ensured, a primary key must be designed.
* **Improve query efficiency:** Primary keys help the optimizer generate more efficient query plans. When data queries depend on primary keys, it is recommended to include the fields that will definitely be carried in the queries as primary key fields. This way, primary keys can be used to enhance query performance.

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    -- The primary key includes all partition keys (user_id and age)
    PRIMARY KEY (user_id, age, login_time)
)
-- Main partition: distributed by user_id using hashing

PARTITIONS 128
SUBPARTITION BY RANGE(age)
SUBPARTITION TEMPLATE (
    -- Example partitions: divided by age groups
    SUBPARTITION p_youth VALUES LESS THAN (25),      -- Age <25

    SUBPARTITION p_middle_aged VALUES LESS THAN (60),-- 40 ≤ age <60

```

## Optimize queries in HTAP scenarios

OceanBase Database supports various methods to meet the requirements of both transactional (TP) and analytical (AP) scenarios in hybrid transactional/analytical processing (HTAP) scenarios. OceanBase Database supports both rowstore and columnstore storage formats for data tables and also allows you to specify the storage format for index tables. You can leverage the advantages of rowstore and columnstore to handle corresponding scenarios.

For more information about how to create a columnstore index, see [Create a columnstore index in MySQL mode](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md) and [Create a columnstore index in Oracle mode](../../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/400.manage-indexes-of-oracle-mode/200.create-an-index-of-oracle-mode.md).

### Rowstore base table + columnstore index

**Scenarios**: The table is a large wide table, and the business is mainly transactional but also involves analytical queries.
**Optimization strategy**: Create a columnstore index to improve the performance of analytical queries.

+ **Advantages**: Only part of the data is redundantly stored in columnstore format.
+ **Disadvantages**: You need to identify suitable fields based on the query statements to create a columnstore index. You also need to maintain the index table data when you write data. The write performance is relatively poor.

### Columnstore base table + rowstore index

**Scenarios**: The business is mainly analytical but also involves efficient simple queries, such as point queries.
**Optimization strategy**: Create a covering index to avoid table access.

+ **Advantages**: Only part of the data is redundantly stored. You cannot convert a columnstore table to a rowstore table or a rowstore/columnstore redundant table online. You can add a rowstore index to optimize queries.
+ **Disadvantages**: You need to identify suitable fields based on the query statements to create a rowstore index. You also need to maintain the index table data when you write data. The write performance is relatively poor.

### Rowstore and columnstore redundant: rowstore base table + columnstore base table

**Scenarios**: The business involves both transactional and analytical queries, and the query methods are diverse.
**Optimization strategy**: Redundantly store the baseline data in both rowstore and columnstore formats. Let the system generate an appropriate execution plan based on the query characteristics. By default, the system performs range scans in columnstore mode and point queries in rowstore mode.

+ **Advantages**: You do not need to analyze the characteristics of analytical queries. The results of analytical queries are strongly consistent.
+ **Disadvantages**: The system consumes more disk space. The execution plans may be inaccurate.

### Columnstore replica: 2F1A1C

**Scenarios**: The business is typical HTAP, and you do not want analytical queries to affect transactional queries. You can accept weakly consistent reads in analytical queries.
**Optimization strategy**: Use the isolation feature of columnstore replicas to execute queries for AP and TP scenarios without affecting each other.

+ **Advantages**:
    1. You do not need to store redundant data in multiple replicas, which saves disk space.
    2. AP and TP scenarios are isolated from each other.
    3. The write performance is not affected.
+ **Disadvantages**:
    1. Columnstore replicas support weakly consistent reads.
    2. You need to have an independent access entry.
