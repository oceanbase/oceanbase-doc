# Best Practices for Optimizing Storage Structures and Query Performance

In the design and optimization of database systems, data table design is a crucial task. A well-designed table not only ensures data integrity and consistency but also significantly improves query performance, storage efficiency, and system scalability. As data volumes grow and query patterns become more complex, how to scientifically design data tables, select appropriate storage structures, and implement effective indexing strategies has become a core issue in database optimization.

This topic will introduce best practices for data table design, covering topics such as selecting the storage format for tables, designing tables without primary keys, partitioning strategies, primary key design, and using indexes in HTAP scenarios.

## Choose the storage format of a table

OceanBase Database supports columnar storage and hybrid row-column storage for tables. You can choose the appropriate storage format based on your business scenarios.

+ **Columnar storage**: If your business is purely analytical (OLAP), columnar storage is suitable.
+ **Hybrid row-column storage**: If your business involves both analytical (OLAP) and transactional (OLTP) operations, and you want to ensure both query performance and point query performance, hybrid row-column storage is suitable.

You can configure the default storage format for tables in a tenant using the [default_table_store_format](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) parameter.

```sql
-- Set the default storage format for tables in the tenant to columnar.
ALTER SYSTEM SET default_table_store_format = "column";

-- Set the default storage format for tables in the tenant to hybrid row-column storage.
ALTER SYSTEM SET default_table_store_format = "compound";
```

## Design primary keys

Designing primary keys is a crucial aspect of relational database table design. In OceanBase Database, primary keys ensure data uniqueness and can optimize performance for range queries because data is sorted by the primary key. Different primary key design strategies are suitable for different business scenarios.

### No primary key

#### Use a columnstore table without a primary key

In data warehouse or online analytical processing (OLAP) scenarios, business data tables often contain a large amount of data, and most queries only involve certain columns. If there are no special requirements, such as ensuring data uniqueness, avoiding duplicate writes, or performing transactional updates or inserts, creating a columnstore table without a primary key is more efficient:

+ **Data import:** In AP scenarios, data does not need to be sorted by the primary key. Therefore, the import performance of large datasets is faster compared to tables with primary keys.
+ **Reduced management costs of primary keys.**

```sql
show parameters like "%store_format%";

  CREATE TABLE customer (
  user_id bigint NOT NULL,
  login_time timestamp NOT NULL,
  customer_name varchar(100) NOT NULL,    -- Assuming the customer name is up to 100 characters
  phone_num bigint NOT NULL,               -- Storing the phone number as a BIGINT
  city_name varchar(50) NOT NULL,          -- Assuming the city name is up to 50 characters
  sex int NOT NULL,                        -- Storing gender as an INT (e.g., 0 for female, 1 for male)
  id_number varchar(18) NOT NULL,          -- Assuming the ID number is up to 18 characters
  home_address varchar(255) NOT NULL,      -- Assuming the home address is up to 255 characters
  office_address varchar(255) NOT NULL,    -- Assuming the office address is up to 255 characters
  age int NOT NULL                         -- Storing age as an INT
);
```

### With primary key

In AP scenarios, the default table type is a **heap table**, which has the following characteristics:

* **Data storage:** Data is stored in the order of insertion without physical sorting.
* **Role of the primary key:**

  + Ensures data uniqueness by including a field that uniquely identifies each record (e.g., user_id).
  + Supports **partition key embedding**, where the primary key must include all partitioning keys (e.g., user_id and age) to ensure even data distribution.
  + Requires the use of indexes or partitioning strategies to accelerate queries (e.g., `ORDER BY`).

Example: Designing a heap-organized table with a primary key

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    -- The primary key includes all partitioning keys (user_id and age)
    PRIMARY KEY (user_id, age, login_time)
)
-- Main partitioning: Hash partitioning by user_id
PARTITION BY HASH(user_id)
PARTITIONS 128
SUBPARTITION BY RANGE(age)
SUBPARTITION TEMPLATE (
    -- Example partitions: Partitioning by age groups
    SUBPARTITION p_youth VALUES LESS THAN (25),      -- Age < 25
    SUBPARTITION p_adult VALUES LESS THAN (40),      -- 25 ≤ age < 40
    SUBPARTITION p_middle_aged VALUES LESS THAN (60),-- 40 ≤ age < 60
    SUBPARTITION p_senior VALUES LESS THAN (MAXVALUE) -- Age 60 and above
);
```

### With primary key

* **Ensure data uniqueness:** When data in the table needs to ensure the uniqueness of each record, a primary key must be designed.
* **Improve query efficiency:** A primary key helps the optimizer generate more efficient query plans. When data queries rely on the primary key, it is recommended to include the fields that will definitely be carried in the query as primary key fields. This allows the use of the primary key to enhance query performance.

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,

    PRIMARY KEY (user_id, age, login_time)
)
-- Main partitioning: Hash partitioning by user_id
```

## Optimize queries in HTAP scenarios

OceanBase Database provides multiple methods to support hybrid transactional/analytical processing (HTAP) scenarios and meets both transactional (TP) and analytical (AP) business requirements. In addition to supporting rowstore, columnstore, and hybrid rowstore/columnstore storage formats for data tables, OceanBase Database also allows you to specify the storage format for index tables. You can leverage the advantages of rowstore and columnstore to process corresponding scenarios.

For more information about how to create a columnstore index, see [Create a columnstore index in MySQL mode](../../../700.reference/300.database-object-management/100.manage-object-of-mysql-mode/500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md) and [Create a columnstore index in Oracle mode](../../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/400.manage-indexes-of-oracle-mode/200.create-an-index-of-oracle-mode.md).

### Rowstore base table + columnstore index

**Scenarios**: The table is a large wide table and the business is primarily transactional, with some analytical queries.
**Optimization strategy**: Create a columnstore index to improve the performance of analytical queries.

+ **Advantages**: Only part of the columns are redundantly stored, and the storage format is columnstore.
+ **Disadvantages**: You need to identify the appropriate fields based on the query statements and create a columnstore index. You also need to maintain the index table data during data writing, which may affect the write performance.

### Columnstore base table + rowstore index

**Scenarios**: The business is primarily analytical, but it requires efficient simple queries (such as point queries).
**Optimization strategy**: Create a covering index to avoid table lookups.

+ **Advantages**: Only part of the columns are redundantly stored. At present, you cannot convert a columnstore table to a rowstore table or a hybrid rowstore/columnstore table online. You can add a rowstore index to optimize queries.
+ **Disadvantages**: You need to identify the appropriate fields based on the query statements and create a rowstore index. You also need to maintain the index table data during data writing, which may affect the write performance.

### Hybrid rowstore/columnstore: Rowstore base table + columnstore base table

**Scenarios**: You need to meet both transactional and analytical queries, and the query methods are diverse.
**Optimization strategy**: Redundantly store two base tables, and let the system generate an appropriate execution plan based on the query characteristics. By default, the system performs range scans in columnstore mode and point queries in rowstore mode.

+ **Advantages**: You do not need to analyze the query characteristics of analytical queries. The results of analytical queries are strongly consistent.
+ **Disadvantages**: The system consumes more disk space, and the execution plans may be inaccurate.

### Columnstore replica: 2F1A1C

**Scenarios**: The business is typical HTAP, and you do not want analytical queries to affect transactional queries. However, you can accept weakly consistent reads for analytical queries.
**Optimization strategy**: You can use the isolation characteristics of columnstore replicas to execute queries for AP and TP businesses without affecting each other.

+ **Advantages**:
    1. You do not need to store redundant data in multiple replicas, which saves disk space.
    2. AP and TP businesses are isolated from each other.
    3. The write performance is not affected.
+ **Disadvantages**:
    1. Columnstore replicas support only weakly consistent reads.
    2. You need to provide an independent access entry.
