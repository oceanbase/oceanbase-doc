# SQL FAQ

## FAQ on SQL Operation Execution

### How do I locate errors when creating a PL?

You can use the SHOW ERRORS command to view error messages during the creation of a stored procedure.

### How do I analyze PL error logs?

Users only need to focus on the error logs returned to the client. This is because OceanBase Database records error information left over from resolution attempts in the logs; moreover, if a PL contains an EXPECTION OTHERS statement, an error message will be logged when execution reaches this point. Therefore, the information recorded in the PL error logs is inaccurate and can be ignored; users only need to care about the error logs returned to the client.

### How do I query the source code of an existing PL object?

You can query the DBA_SOURCE, ALL_SOURCE, or USER_SOURCE view to obtain the source code of an existing PL object. The TEXT column contains the PL object's source code.

### Does MySQL-compatible mode support the INSERT ALL INTO syntax?

No. Currently, only Oracle-compatible mode supports the INSERT ALL INTO syntax; MySQL-compatible mode does not support it.

### How are resources allocated and isolated for tenants in terms of SQL engines and transaction engines?

Both SQL engines and transaction engines are tenant-specific and provide complete isolation between different tenants. Specifically:

- The plan cache of an SQL engine is completely independent of the locks of a transaction engine.
- CPU: The CPU usage of an SQL thread of a tenant controls the number of SQL threads that can be active simultaneously.
- Memory: The SQL memory and transaction memory of different tenants are managed separately. If one tenant runs out of memory, it will not affect another tenant.
- Threads: The threads of the SQL engine and transaction engine of different tenants are completely independent. If a thread of one tenant suspends, it will not affect another tenant.

### What is batch execution in OceanBase Database?

When interacting with OceanBase Database using JDBC, grouping multiple requests into one and completing them through a single network transmission is called batch execution, often referred to as "batch processing."

### Why use batch execution?

Sometimes we use batch execution for data consistency, but more often, the primary benefit is performance improvement, which is reflected in the following aspects:

- Batch statements are rewritten to improve performance.
- Batch execution reduces the number of interactions with the database.
- When receiving batch execution, OceanBase Database can perform optimization work to further enhance performance.

### Which classes/objects in JDBC can implement batch execution?

Whether using Statement or PreparedStatement, batch execution can be implemented.

- For implementation and behavior, useServerPrepStmts determines the different behaviors of batch execution.
- For performance, cachePrepStmt, prepStmtCacheSize, prepStmtCacheSqlLimit, and maxBatchTotalParamsNum all contribute to performance improvement.

### What are the differences in behavior and usage between Statement and PreparedStatement objects?

- Using a Statement object:

    ```sql
    conn = DriverManager.getConnection(obUrl);
    conn.setAutoCommit(false);
    Statement stmt = conn.createStatement();
    String SQL = "INSERT INTO test1 (c1, c2) VALUES (1, 'test11')";
    stmt.addBatch(SQL);
    String SQL = "INSERT INTO test1 (c1, c2) VALUES (2, 'test12')";
    stmt.addBatch(SQL);
    String SQL = "INSERT INTO test1 (c1, c2) VALUES (3, 'test13')";
    stmt.addBatch(SQL);
    int[] count = stmt.executeBatch();
    stmt.clearBatch();
    conn.commit();
    ```

- Using a PreparedStatement object:

    ```sql
    conn = DriverManager.getConnection(obUrl);
    conn.setAutoCommit(false);
    String SQL = "INSERT INTO TEST1 (C1, C2) VALUES (?, ?)";
    PreparedStatemen pstmt = conn.prepareStatement(SQL);
    int rowCount = 5, batchCount = 10;
    for (int k=1; k<=batchCount; k++) {
        for (int i=1; i<=rowCount; i++) {
            pstmt.setInt(1, (k*100+i));
            pstmt.setString(2, "test value");
            pstmt.addBatch();
        }
        int[] count = pstmt.executeBatch();
        pstmt.clearBatch();
    }
    conn.commit();
    pstmt.close();
    ```

### What are the types of batch execution in OceanBase Database, and what are the optimization processes for each type of request?

From the perspective of statements, OceanBase Database handles batch execution differently for INSERT, UPDATE, and DELETE operations. Specifically:

  <p>The scenarios described below all assume <code>rewriteBatchedStatements=TRUE</code>.   </p>

**INSERT**

- Scenario 1

  Using a PreparedStatement object:

  | useServerPrepStmts | INSERT |
  | ------ | ------ |
  | TRUE | The VALUES for multiple INSERT statements are concatenated into multiple VALUES fields of a single INSERT statement, represented as: INSERT INTO TEST1 VALUES (?), (?),...,(?) |

  In Scenario 1, the OceanBase server receives one `COM_STMT_PREPARE` request (with `request_type=5`) and one `COM_STMT_EXECUTE` request (with `request_type=6`) for the INSERT statement. From an optimization perspective, this has the following benefits:

  - The batch execution of the INSERT statement is completed with only two communications.
  - The inherent properties of PreparedStatement can reduce compilation time.
  - Assuming there will be more executes in batches later on and reasonable cachePrepStmts and related parameters are set, the number of Prepare requests (`request_type=5`) can be reduced, requiring only execute requests (`request_type=6`).

- Scenario 2

  Using a PreparedStatement object:

  | useServerPrepStmts | INSERT |
  | ------ | ------ |
  | FALSE | The VALUES for multiple INSERT statements are concatenated into a single INSERT statement with multiple specific values, for example: INSERT INTO TEST1 VALUES (1), (2),...,(10) |

  In Scenario 2, the OceanBase server receives one `COM_QUERY` request (`request_type=2`) for the INSERT statement. From an optimization perspective, this has the following benefits:

  - The batch execution of the INSERT statement is completed with only one communication round trip.

- Scenarios 3/4

  Using a Statement object:

  | useServerPrepStmts | INSERT | Scenario |
  | ------ | ------ |------ |
  | TRUE | Multiple separate INSERT statements concatenated with ";" |  Scenario 3 |
  | FALSE | Multiple separate INSERT statements concatenated with ";" |  Scenario 4 |

  In Scenarios 3/4, the OceanBase server receives a request containing multiple INSERT statements concatenated with ";" and executes them sequentially. Therefore, it also has the following benefits:

  - The batch execution of the INSERT statements is completed with only one communication round trip.

**UPDATE**

Using a PreparedStatement object:

| useServerPrepStmts | UPDATE | Scenario |
| --- | --- | --- |
| TRUE | Multiple separate UPDATE statements, where variables are replaced with "?". | Scenario 1 |
| FALSE | Multiple individual UPDATE statements concatenated with a semicolon (;) | Scenario 2 |

Using a Statement object:

| useServerPrepStmts | UPDATE | Scenario |
| --- | --- | --- |
| TRUE | Multiple individual UPDATE statements concatenated with a semicolon (;) | Scenario 3 |
| FALSE | Multiple individual UPDATE statements concatenated with a semicolon (;) | Scenario 4 |

- If `ob_enable_batched_multi_statement` is enabled, for the UPDATE batch executions in Scenarios 2/3/4, the OceanBase Server parses multiple UPDATE statements with consistent formats as one statement and generates a batch physical plan based on the corresponding parameters and data distribution. This can effectively improve the efficiency of batch UPDATE execution. However, explicit transactions must be enabled when using this feature.

The current version does not provide optimization for batch DELETE statements.

### What is the return value of the executeBatch method during batch execution?

After the executeBatch method is called, it returns an integer array int []. For batch INSERT and batch UPDATE operations:

- If the operations are ultimately executed one by one in the OceanBase client, this array returns the number of rows modified by each operation in the batch.
- If the operations are ultimately executed as a whole in the OceanBase client. For example, the JDBC driver combines multiple INSERT statements into a single INSERT statement with multiple VALUES clauses (Scenarios 1 and 2). Another example is when UPDATE statements are executed as a batch physical plan (Scenario 2). In these cases, each element of the array returns -2, indicating successful execution but an unknown number of updated rows.


### How to resolve the "planned vs. unplanned" issue in SQL queries

- **What is the "planned vs. unplanned" issue**:

  The "planned vs. unplanned" issue refers to significant performance differences under different query conditions during SQL statement parsing and execution, because the same SQL ID may correspond to different execution plans. For example, after an SQL statement is parameterized, the plan cache may contain an execution plan that is not suitable for all scenarios. This can lead to the following effects:

  When the system first executes an SQL statement (for example, `select * from items where store = 'taobao';`), the execution plan (p1) may be a full table scan, which is suitable for cases with a very low selectivity.

  If another parameterized SQL statement is executed later (for example, `select * from items where store = 'xiaomaibu';`), and the selectivity is high, the original plan p1 may no longer be the optimal solution, leading to performance degradation.

- **How to identify "planned vs. unplanned" SQL**:

  The key to identifying "planned vs. unplanned" SQL is to monitor fluctuations in logical read rows, affected rows, and returned rows. Specific identification rules include:

   - Fluctuations in logical read rows exceeding 1,000 rows.
   - Fluctuations in affected rows exceeding 1,000 rows.
   - Fluctuations in returned rows exceeding 10,000 rows.

  You can manually count execution records and statistics from views such as `v$ob_sql_audit` to identify SQL statements with the "planned vs. unplanned" issue.

- **How to resolve the "planned vs. unplanned" SQL issue**:

   + Disable the plan cache

     1. **Disable plan cache for a single SQL statement**:

        - Use the `USE_PLAN_CACHE` hint, for example:

          ```sql
          SELECT /*+ USE_PLAN_CACHE(none) */ * FROM items WHERE store = 'taobao';
          ```

        - Or set the session variable `ob_enable_plan_cache`:

          ```sql
          SET ob_enable_plan_cache = 0;
          ```

       Both of the above methods to **disable the plan cache** require modifying the SQL statements in your application. If the issue is discovered after the application goes live, you must release a new version of the application to resolve it. You can refer to the method of **using SQL Outline binding hints**, where the database administrator adds control for the SQL statements.

     2. **Use SQL Outline binding hints**: Control the execution plan of SQL statements through SQL outlines.

        ```sql
        CREATE OUTLINE otl_no_plan_cache1
        ON select /*+ USE_PLAN_CACHE(NONE) */ * from items where store = 'taobao';
        # or use SQL_ID; SQL_ID can be found in views such as V$OB_SQL_AUDIT
        CREATE OUTLINE otl_idx_c2
        ON 'ED570339F2C856BA96008A29EDF04C74'
        USING HINT /*+ USE_PLAN_CACHE(NONE) */;
        ```

- **Enable SQL Plan Management (SPM)**

   We recommend that you enable SPM in OceanBase Database V4.2.1 and later. In some cases, this mechanism can alleviate the "big vs. small account" issue, especially when there is an acceptable single plan among multiple execution plans. The automatic evolution of SPM ensures positive plan evolution during a "Plan Cache Clear", thereby improving execution performance.

- **Address performance degradation caused by "big vs. small account" SQL**

  + Manual tuning: When no suitable single execution plan exists, you can perform manual tuning using the following methods:

    - **Add indexes**: Improve query performance by creating indexes.
    - **cursor_sharing_exact hint**: Add this hint for large accounts to ensure the query obtains an independent execution plan.

  + Limit resource consumption: To prevent "big account" queries from affecting system performance, you can use the following methods to limit resource consumption:

    1. **Maximum concurrency control**: Use the `MAX_CONCURRENT` hint, for example:

       ```sql
       CREATE OUTLINE otl_sql_throttle1 ON 'SQL_ID' USING HINT /*+ MAX_CONCURRENT(10) */;
       ```

    2. **SQL-level resource isolation**: Bind large account queries to a resource group to limit their resource consumption during execution. Example:

       ```sql
       CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
           ATTRIBUTE => 'column',
           VALUE => 'items.store = \'taobao\'',
           CONSUMER_GROUP => 'slow_group');
       ```

       You can specify a resource group for a particular SQL statement using a hint:

       ```sql
       select /*+ RESOURCE_GROUP('slow_group') */ * from items where store = 'taobao';
       ```

    3. **Automatic isolation of large query tasks**: Determine large queries using the parameter `large_query_threshold` and limit their CPU usage to ensure small queries are processed first. If both large and small queries exist, large queries can occupy at most 30% of the tenant's worker threads. This percentage value can be set using the parameter `large_query_worker_percentage`.

## SQL Tuning FAQ

### Query performance degraded by database physical design

Query performance largely depends on the database's physical design, including the schema information of the accessed objects. For example, for a secondary index, if the required projected columns are not included in the index columns, the database must access the primary table through a back-to-table mechanism, significantly increasing query cost. In this case, you can consider adding the user's projected columns to the index columns to form a so-called "covering index," avoiding back-to-table access.

### System load affects response time of individual SQL statements

The overall system load affects not only the system's throughput but also the response time of individual SQL statements. The SQL engine of OceanBase Database uses a queue model. For user requests, if all available threads are occupied, new requests must wait in a request queue until a thread finishes the current request. The queuing time of requests can be viewed in the `(G)V$OB_SQL_AUDIT` view.

### Incorrect execution plan selection due to cost model flaws

OceanBase Database's built-in cost model is an inherent logic of the server, and the optimal execution plan depends on this cost model. Therefore, once plan selection errors occur due to the cost model, users can only ensure the selection of the "correct" execution plan by binding execution plans.

### Routing feedback logic error between client routing and server

One of the main functions of OBProxy is to route SQL queries to the appropriate server node. Specifically, if a user query does not specify the weak-consistency read attribute, the proxy needs to route it to the leader node of the involved table (or specific partition) to avoid secondary forwarding through server nodes; otherwise, the proxy forwards it to the appropriate node based on predefined rules.
Due to the loose coupling between the proxy and the servers, the cached data on the proxy may not be refreshed promptly, leading to incorrect routing choices. Scenarios that may cause routing information changes include:

- Load balancing leading to re-election of a leader
- Network instability causing re-election of a leader between servers
- Re-election of a leader due to server going online/offline, round-robin major compaction, etc.

When a large number of remote executions are found in SQL Audit or the execution plan cache, consider whether it matches any of the above scenarios. There is a routing feedback logic between the client and the server. Once an error occurs, the client will proactively refresh the data physical distribution information, and routing selection will then return to normal.

## FAQ on index monitoring

### Is index monitoring enabled by default and does it impact performance?

Yes, it does. However, the impact is minimal in the default (SAMPLED) mode and can be almost negligible.

### Are the data accurate in sampled mode? For example, if a query is executed once, will it definitely be recorded?

Not necessarily. The purpose of sampling is to filter out some data, so records for a particular query may be discarded.

### Does index monitoring on a standby database only count its own data or synchronize data from the primary database?

Statistics are tenant-level. A standby database can access data synchronized from the primary database but cannot write to it.

## FAQ on partition exchange

### Why does partition exchange fail with an error of index mismatch when the same global index is created for both a partitioned table and a non-partitioned table in OceanBase Database's Oracle-compatible mode?

In OceanBase Database's Oracle-compatible mode, if the `local` keyword is not added when creating an index, it will be created with global storage by default. The prerequisite for partition exchange is that the local storage index of the partitioned table matches one-to-one with all indexes of the non-partitioned table; otherwise, partition exchange cannot proceed.

### Why can't the partitions of a subpartitioned table be exchanged?

In the current version of OceanBase Database, a partition is only a logical concept. At the actual storage layer, tablets are organized by subpartition. Therefore, for a subpartitioned table, the subpartitions must be RANGE or RANGE COLUMNS partitions, but there is no requirement for the format of the partitioning key.

## FAQ on replicated tables

### What is a replicated table?

A replicated table is a special type of table supported by OceanBase Database. Data modifications are immediately visible in all replicas. It is recommended for scenarios with low write frequency but high requirements for read latency and load balancing.

### Application scenarios of replicated tables?

#### Scenario 1: Scenarios with low write frequency, high read latency requirements, and high load balancing requirements

When the data volume of a table is not large but access is extremely frequent, using a regular table will concentrate data on one node, creating a hotspot that affects performance. In this case, you can choose to use a replicated table.

Typical replicated table scenarios:

* Configuration tables, where business reads configuration information through this table.
* Exchange rate storage tables in financial scenarios, which are not updated in real time but only once daily.
* Bank branch or outlet information tables, which rarely have new records added.

Best practices for replicated tables:

1. When creating a replicated table, it is recommended to select it based on actual needs rather than creating a large number of replicated tables in a tenant.
2. When writing data to a replicated table, it is not recommended to perform both writes and reads on the replicated table within the same transaction.
3. When querying a replicated table, if a `JOIN` query is involved, design the SQL query following the order of joining a regular table to a replicated table.

#### Scenario 2: Scenarios where a table cannot be set as a partitioned table but frequently participates in JOINs with partitioned tables

Due to business logic considerations, some tables cannot be split into partitioned tables or there is no need to split them (for example, queries do not have obvious partitioning conditions), yet they frequently involve relationships with partitioned tables. To reduce unnecessary cross-machine distributed queries, such tables can be set as replicated tables. Every node supports strong reads, so regardless of which machine holds the primary replica of the partitioned table's partition, it can perform a table join with the replicated table's replica on the same machine.

### Misuse scenarios of replicated tables?

#### Misuse scenario 1: Setting one of two partitioned tables as a replicated table to avoid cross-node connections between them

To improve performance, blindly setting a partitioned table in a query as a replicated table is unscientific. These tables may not necessarily fit the application scenarios for replicated tables and may not achieve the expected results.

* If the table has frequent write operations, writing to a replicated table comes at a performance cost, as data must be synchronized to all replicas. Theoretically, synchronization is concurrent, but if individual nodes experience very slow synchronization due to network issues, it will degrade the write performance of the entire replicated table.
* If the replicated table contains a large amount of data and has replicas on every node, it will consume a significant amount of storage space.

#### Misuse scenario 2: A transaction contains both writes and reads to a replicated table

Pure write or pure read transactions to a replicated table are recommended. You only need to consider whether the business can accept write latency.

If a transaction involves both writes and reads to a replicated table, since the leader must be written to, it will cause all replicated tables in the transaction to degrade to the performance level of regular tables, failing to leverage the advantage of reading local replicas.

#### Misuse scenario 3: Joining a regular table to a replicated table

ODP (obproxy)'s routing rule for multi-table `JOIN` is to route according to the first table parsed. If it is a replicated table, it will randomly select a replica for routing. If this node happens to be not the leader of the regular table, remote routing will occur, affecting performance.

If your business involves `JOIN` operations between replicated tables and regular partitioned tables, it is recommended to adjust the `JOIN` order to regular partitioned table `JOIN` replicated table. This way, it will route according to the regular partitioned table, generate a local plan as expected, and optimize performance.

#### Misuse scenario 4: Setting a replicated table as a partitioned table

A replicated table automatically creates replicas on all nodes, so there is no need to explicitly set it as a partitioned table.

## FAQ on auto-increment columns

### When should I set the data type of an auto-increment column to BIGINT?

* The business involves rapid data growth and a long data retention period.
* The business does not care whether to use `BIGINT` or `INT` when creating the table.
* Leader dispersion increases the probability of leader switchover (e.g., due to server downtime or random load balancing), which raises the likelihood of value jumps in the auto-increment column.
* In `NOORDER` mode, you need to explicitly specify the value for the auto-increment column.

### When can I keep the data type of an auto-increment column as INT?

* The volume of business data is much smaller than the upper limit of `INT`.
* Migrating from MySQL requires using the `INT` type; otherwise, the application may encounter compatibility issues.
* In a single-node scenario, leader switchover is rare.
* You have sufficient monitoring and maintenance capabilities to handle operations when the number of auto-increment values approaches the upper limit, such as rebuilding the table and importing data, or changing the column type from `INT` to `BIGINT` (since V4.2.2, changing the column type from `INT` to `BIGINT` is an Online DDL operation).

### When can I change the auto-increment column to NOORDER?

* If you do not require list-level order for auto-increment and wish to optimize performance under high-concurrency operations, you can change `ORDER` to `NOORDER`.
* If you require list-level order for auto-increment but all leaders are on one OBServer node and you wish to optimize performance under high-concurrency operations, you can change `ORDER` to `NOORDER`.

### When can I decrease the auto_increment_cache_size for an auto-increment column?

* Value jump issues are significant.
* Business traffic is very low.
* Performance is not critical.
* Performance is a concern, but the system operates in single-node mode with leaders concentrated on one node.
