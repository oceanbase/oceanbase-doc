# SQL FAQ

## FAQ on SQL operation execution

### How do I locate errors during the creation of a PL procedure?

You can execute the SHOW ERRORS statement to view the error information during the creation of a stored procedure.

### How do I analyze the error logs of a PL procedure?

You only need to pay attention to the error logs returned to the client. This is because OceanBase Database records the error information left during the Resolve process in the logs. If the PL procedure contains an EXPECTION OTHERS statement, the error information will be recorded in the logs when it is executed. Therefore, the information recorded in the PL error logs is inaccurate and can be ignored. You only need to pay attention to the error logs returned to the client.

### How do I query the source code of a PL procedure that has been created?

You can query the source code of a PL procedure that has been created from the DBA_SOURCE, ALL_SOURCE, or USER_SOURCE view. The TEXT column contains the source code of the PL procedure.

### Does MySQL mode support the INSERT ALL INTO syntax?

No. Currently, only Oracle mode supports the INSERT ALL INTO syntax. MySQL mode does not support the INSERT ALL INTO syntax.

### How are resources allocated and isolated for SQL engines, transaction engines, and other components for a tenant?

SQL engines and transaction engines are tenant-aware, and different tenants are completely isolated from each other. Specifically:

- The plan cache of the SQL engine and the locks of the transaction engine are completely independent.
- CPU: The CPU usage of an SQL thread for a tenant is used to control the number of active SQL threads.
- Memory: The SQL memory and transaction memory of different tenants are managed separately. If the memory of one tenant is exhausted, it will not affect another tenant.
- Threads: The threads of the SQL engine and transaction engine for different tenants are completely independent. If the threads of one tenant are suspended, it will not affect another tenant.

### What is batch execution in OceanBase Database?

When you use JDBC to interact with OceanBase Database, you can group multiple requests together and complete them in a single network transmission. This is known as batch execution, also referred to as "batch processing."

### Why use batch execution?

Sometimes, batch execution is used to ensure data consistency. However, the primary benefit of using batch execution is to improve performance. This is reflected in the following aspects:

- Batch statements are rewritten to enhance performance.
- Batch execution reduces the number of interactions with the database.
- OceanBase Database can perform optimization work when it receives batch execution, further improving performance.

### Which classes or objects in JDBC can implement batch execution?

You can use either Statement or PrepareStatement to implement batch execution.

### What JDBC configuration properties need to be set for batch execution?

- Functionally, to use batch execution, you must set `rewriteBatchedStatements=TRUE`.
- In terms of implementation and behavior, the useServerPrepStmts property determines the different behaviors of batch execution.
- In terms of performance, cachePrepStmt, prepStmtCacheSize, prepStmtCacheSqlLimit, and maxBatchTotalParamsNum all contribute to performance improvements.

### What are the differences between a Statement and a PrepareStatement?

- Use a Statement object:

    ```sql
    conn = DriverManager.getConnection(obUrl);
    conn.setAutoCommit(false);
    Statement stmt = conn.createStatement();
    String SQL = "INSERT INTO test1 (c1, c2) VALUES (1, 'test11')";
    stmt.addBatch(SQL);
    String SQL = "INSERT INTO test1 (c1, c2) VALUES (2, 'test12')";
    stmt.addBatch(SQL);
    String SQL = "INSERT INTO test1 (c1, c2) VALUES (3, 'test13')";
    stmt.addBatch(SQL);
    int[] count = stmt.executeBatch();
    stmt.clearBatch();
    conn.commit();
    ```

- Use a PrepareStatement object:

    ```sql
    conn = DriverManager.getConnection(obUrl);
    conn.setAutoCommit(false);
    String SQL = "INSERT INTO TEST1 (C1, C2) VALUES (?, ?)";
    PreparedStatemen pstmt = conn.prepareStatement(SQL);
    int rowCount = 5, batchCount = 10;
    for (int k=1; k<=batchCount; k++) {
        for (int i=1; i<=rowCount; i++) {
            pstmt.setInt(1, (k*100+i));
            pstmt.setString(2, "test value");
            pstmt.addBatch();
        }
        int[] count = pstmt.executeBatch();
        pstmt.clearBatch();
    }
    conn.commit();
    pstmt.close();
    ```

### What types of batch execution does OceanBase Database support, and how does it optimize each type?

From the perspective of statements, OceanBase Database optimizes batch execution for INSERT, UPDATE, and DELETE statements differently. Specifically:

**INSERT**

- Scenario 1

  Use the PrepareStatement object:

  | useServerPrepStmts | INSERT |
  | ------ | ------ |
  | TRUE | The VALUES of multiple INSERT statements are concatenated into the VALUES of a single INSERT statement in the form of multiple "?" placeholders, like this: `INSERT INTO TEST1 VALUES (?), (?),...,(?)`. |

  In Scenario 1, the OceanBase Database server receives one `COM_STMT_PREPARE` request (`request_type=5`) and one `COM_STMT_EXECUTE` request (`request_type=6`) for the INSERT statement. From an optimization perspective, this approach offers the following benefits:

  - Only two communications are required to complete the batch execution of the INSERT statement.
  - The inherent properties of PrepareStatement can reduce compilation time.
  - If there are more executeBatch operations and the cachePrepStmts and related parameters are set appropriately, the number of Prepare requests (`request_type=5`) can be reduced, and only execute requests (`request_type=6`) need to be executed.

- Scenario 2

  Use the PrepareStatement object:

  | useServerPrepStmts | INSERT |
  | ------ | ------ |
  | FALSE | The VALUES of multiple INSERT statements are concatenated into the VALUES of a single INSERT statement in the form of specific values, like this: `INSERT INTO TEST1 VALUES (1), (2),...,(10)`. |

  In Scenario 2, the OceanBase Database server receives one `COM_QUERY` request (`request_type=2`) for the INSERT statement. From an optimization perspective, this approach offers the following benefit:

  - Only one communication is required to complete the batch execution of the INSERT statement.

- Scenarios 3 and 4

  Use the Statement object:

  | useServerPrepStmts | INSERT | Scenario |
  | ------ | ------ |------ |
  | TRUE | Multiple separate INSERT statements are concatenated with ";" separators. | Scenario 3 |
  | FALSE | Multiple separate INSERT statements are concatenated with ";" separators. | Scenario 4 |

  In Scenarios 3 and 4, the OceanBase Database server receives a single request containing multiple INSERT statements concatenated with ";" separators and executes them sequentially. This approach also offers the following benefit:

  - Only one communication is required to complete the batch execution of the INSERT statement.

| useServerPrepStmts| UPDATE | Scenario |
| --- | --- |  --- |
| TRUE | Multiple separate UPDATE statements, where variables are replaced with "?" placeholders. | Scenario 1 |
| FALSE | Multiple separate UPDATE statements are concatenated with ";" separators. | Scenario 2 |

| useServerPrepStmts |UPDATE | Scenario |
| --- | --- | --- |
| TRUE | Multiple separate UPDATE statements are concatenated with ";" separators. | Scenario 3 |

### What value does the executeBatch method return when Batch execution is performed?

After the executeBatch method is called, it returns an int [] array. For Batch INSERT and Batch UPDATE:

- If OceanBase Database executes each operation in the batch separately, the array returns the number of rows modified for each operation in the batch.
- If OceanBase Database executes the batch as a single unit, such as when the JDBC driver converts multiple INSERT statements into a single INSERT statement with multiple values (Scenarios 1 and 2), or when an UPDATE statement is executed as a batch physical plan (Scenario 2), each element in the array returns -2, indicating that the execution was successful but the number of updated rows is unknown.

### How to solve the "small account" issue in SQL queries

- **What is the "small account" issue**:

  The "small account" issue refers to the significant performance differences in queries with the same SQL ID but different execution plans. For example, after parameterizing an SQL statement, the plan cache may contain an execution plan that is not suitable for all scenarios. This can lead to the following impacts:

  When a system first executes an SQL statement (such as `select * from items where store = 'taobao';`), the execution plan (p1) may be a full table scan, which is suitable for scenarios with a very low selectivity.

  If the system later executes another parameterized SQL statement (such as `select * from items where store = 'xiaomaibu';`) with high selectivity, the original plan p1 may no longer be the optimal solution, leading to performance degradation.

- **How to identify "small account" SQL statements**:

  The key to identifying "small account" SQL statements is to monitor fluctuations in logical reads, affected rows, and returned rows. The specific identification rules include:

   - Fluctuations in logical reads exceeding 1,000 rows.
   - Fluctuations in affected rows exceeding 1,000 rows.
   - Fluctuations in returned rows exceeding 10,000 rows.

  Users can manually analyze the execution records and statistics of views such as `v$ob_sql_audit` to identify SQL statements with the "small account" issue.

- **How to solve the "small account" issue**:

   + Disable the plan cache

     1. **Disable the plan cache for individual SQL statements**:

        - Use the `USE_PLAN_CACHE` hint, for example:

          ```sql
          SELECT /*+ USE_PLAN_CACHE(none) */ * FROM items WHERE store = 'taobao';
          ```

        - Or set the session variable `ob_enable_plan_cache`:

          ```sql
          SET ob_enable_plan_cache = 0;
          ```

       Both methods require modifying the SQL statements in the application. If the issue is discovered after the application is deployed, a new version of the application must be released to address it. You can refer to the method of **using SQL outlines to bind hints**, where the database administrator can add control to the SQL statements.

     2. **Use SQL outlines to bind hints**: By using SQL outlines, the database administrator can control the execution plan of the SQL statements.

        ```sql
        CREATE OUTLINE otl_no_plan_cache1
        ON select /*+ USE_PLAN_CACHE(NONE) */ * from items where store = 'taobao';
        # Or use SQL_ID; SQL_ID can be found in views like V$OB_SQL_AUDIT
        CREATE OUTLINE otl_idx_c2
        ON 'ED570339F2C856BA96008A29EDF04C74'
        USING HINT /*+ USE_PLAN_CACHE(NONE) */;
        ```

- **Enable SQL Plan Management (SPM)**

   In OceanBase Database V4.2.1 and later, it is recommended to enable SPM. This mechanism can help alleviate the "small account" issue, especially when there is a single acceptable plan among multiple execution plans. SPM's automatic evolution ensures that when the plan cache is cleared, the plans will evolve positively, improving execution performance.

- **Address the performance degradation caused by "small account" SQL statements**

  + Manual tuning methods: When there is no suitable single execution plan, you can manually tune the SQL statements as follows:

    - **Add indexes**: Build indexes to improve query performance.
    - **cursor_sharing_exact hint**: Add this hint to large account SQL statements to ensure they receive independent execution plans.

  + Limit resource consumption: To prevent large account queries from affecting system performance, you can limit resource consumption using the following methods:

    1. **Control maximum concurrency**: Use the `MAX_CONCURRENT` hint, for example:

       ```sql
       CREATE OUTLINE otl_sql_throttle1 ON 'SQL_ID' USING HINT /*+ MAX_CONCURRENT(10) */;
       ```

    2. **Resource isolation at the SQL level**: Bind large account queries to a resource group to limit their resource consumption during execution, for example:

       ```sql
       CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
           ATTRIBUTE => 'column',
           VALUE => 'items.store = \'taobao\'',
           CONSUMER_GROUP => 'slow_group');
       ```

       You can use hints to specify a resource group for specific SQL statements:

       ```sql
       select /*+ RESOURCE_GROUP('slow_group') */ * from items where store = 'taobao';
       ```

    3. **Automatic isolation of large queries**: Configure the parameter `large_query_threshold` to identify large queries and limit their CPU usage to ensure small queries are prioritized. If both large and small queries are present, large queries can consume up to 30% of the tenant's worker threads, with this percentage adjustable via the `large_query_worker_percentage` parameter.

## FAQ about SQL tuning

### Poor database physical design reduces query performance

The performance of a query is largely affected by the physical design of the database, including schema information of the accessed objects. For example, for a secondary index, if the required projected columns are not included in the index columns, the system needs to access the primary table through the table lookup mechanism, which significantly increases the query cost. In this case, you can consider adding the projected columns to the index columns to form a so-called "covering index" to avoid table lookup.

### System load affects the response time of an individual SQL statement

The overall system load not only affects the system throughput but also causes changes in the response time of an individual SQL statement. The SQL engine of OceanBase Database adopts a queue model. If all available threads are occupied when a user request is submitted, the new request is queued in the request queue until a thread completes the current request. The waiting time in the queue can be viewed in the `(G)V$OB_SQL_AUDIT` view.

### Incorrect execution plan selection caused by defects in the cost model

The built-in cost model in OceanBase Database is an inherent logic of the server. The optimal execution plan depends on this cost model. Therefore, if an incorrect execution plan is selected due to defects in the cost model, you can only ensure the selection of the "correct" execution plan by using execution plan binding.

### Routing feedback logic error between the client and the server

One of the main features of obproxy is to route SQL queries to the appropriate server node. Specifically, if a user query does not specify the read-only attribute, the proxy needs to route the query to the primary node of the involved table (or specific partition) to avoid secondary forwarding by the server node. Otherwise, the proxy forwards the query to the appropriate node based on the predefined rules.
Due to the loosely coupled architecture between the proxy and the server, the cached physical distribution information on the proxy may not be refreshed in a timely manner, leading to incorrect routing. The following scenarios can cause changes in routing information:

- Re-election of primary nodes due to load balancing
- Re-election of primary nodes due to unstable network connections between servers
- Re-election of primary nodes due to server online/offline or major compaction

If a large number of remote executions are found in SQL Audit or execution plan cache, you need to check whether the above scenarios apply. A routing feedback logic exists between the client and the server. Once an error occurs, the client actively refreshes the data physical distribution information, and the routing selection will return to normal.

## FAQ about index monitoring

### Does index monitoring affect performance if it is started by default?

Yes, but the impact is negligible in the default (SAMPLED) mode.

### Is the data in the sampled mode accurate? For example, if a query is executed once, will it be recorded?

Not necessarily. The purpose of sampling is to filter some data, so the records of some queries may be discarded.

### Does index monitoring on the standby database only collect data from itself or synchronize data from the primary database?

Index monitoring is at the tenant level. The standby database can query data synchronized from the primary database but cannot write data.

## FAQ about partition exchange

### Why does an error occur when you perform a partition exchange in Oracle mode of OceanBase Database, if the same global indexes are created for both the partitioned and non-partitioned tables?

When you create an index in Oracle mode of OceanBase Database without specifying the `local` keyword, a global index is created by default. For a partition exchange to succeed, the local indexes of the partitioned table must match the global indexes of the non-partitioned table. If they do not match, the partition exchange will fail.

## FAQ about replicated tables

### What is a replicated table?

A replicated table is a special type of table supported by OceanBase Database. It allows you to read the latest data modifications from any replica. Replicated tables are recommended for scenarios with low write frequency and high requirements for read latency and load balancing.

### What are the applicable scenarios for replicated tables?

#### Scenario 1: Low write frequency and high requirements for read latency and load balancing

When the data volume of a table is small but the access frequency is high, using a regular table may lead to hotspots, affecting performance. In such cases, using a replicated table is recommended.

Typical scenarios for replicated tables:

* Configuration tables used by the business to read configuration information.
* Tables storing exchange rates in financial scenarios that are updated only once a day.
* Tables storing branch or outlet information in banks, where new records are rarely added.

Best practices for replicated tables:

1. When creating replicated tables, it is recommended to create them as needed rather than creating a large number of replicated tables in a tenant.
2. Avoid performing write and read operations on a replicated table within the same transaction.
3. When querying a replicated table, if the query involves a `JOIN`, design the SQL query to join a regular table with the replicated table.

#### Scenario 2: Tables that cannot be partitioned and frequently join with partitioned tables

Some tables cannot be partitioned or do not need to be partitioned (e.g., queries do not have obvious partitioning conditions) but frequently join with partitioned tables. To reduce unnecessary cross-node distributed queries, you can set these tables as replicated tables. This way, each node can read from the local replica, regardless of where the leader replica of the partitioned table is located.

### What are the misuses of replicated tables?

#### Misuse 1: Setting one of the partitioned tables as a replicated table to avoid cross-node joins

To improve performance, some users blindly set partitioned tables in queries as replicated tables, which is not scientific. These tables may not be suitable for replicated tables and may not achieve the expected results.

* If a table has frequent write operations, writing to a replicated table incurs performance overhead. The data needs to be synchronized to all replicas. In theory, this synchronization is concurrent. However, if a node experiences slow synchronization due to network issues, the overall write performance of the replicated table will be affected.
* If the data volume of a replicated table is very large, the replicated table will occupy a large amount of storage space on each node.

#### Misuse 2: Transactions involving both write and read operations on a replicated table

Transactions that involve only write or only read operations on a replicated table are recommended. The only thing to consider is whether the business can tolerate write latency.

If a transaction involves both write and read operations on a replicated table, it will require reading from the leader replica. This will cause all replicated tables in the transaction to degrade to regular tables, negating the advantage of being able to read from the local replica.

#### Misuse 3: Joining a replicated table with a regular table

The routing rules for multi-table `JOIN` queries in ODP (obproxy) are based on the first table parsed. If the first table is a replicated table, a random replica will be chosen for routing. If this node is not the leader replica of the regular table, remote routing will occur, affecting performance.

If your business involves joining a replicated table with a regular partitioned table, it is recommended to adjust the `JOIN` order to join the regular partitioned table with the replicated table. This way, the regular partitioned table will be used for routing, and the expected local plan will be generated, optimizing performance.

#### Misuse 4: Setting a replicated table as a partitioned table

Replicated tables are already replicated on all nodes, so there is no need to set them as partitioned tables.

## FAQ about auto-increment columns

### In what scenarios should you set the data type of an auto-increment column to BIGINT?

* The business data grows rapidly and needs to be retained for a long time.
* The business does not care whether `BIGINT` or `INT` is used for table creation.
* Leader sharding and node switching (such as node failures or random load balancing) are frequent, which increases the probability of auto-increment column value jumps.
* In `NOORDER` mode, you need to explicitly specify the auto-increment column value.

### In what scenarios can you keep the data type of an auto-increment column as INT?

* The business data volume is much smaller than the upper limit of `INT`.
* The business is migrated from MySQL and requires the use of `INT` type to avoid compatibility issues.
* In a single-node scenario, node switching is rare.
* You have monitoring and O&M capabilities to handle the situation when the number of auto-increment values approaches the upper limit, such as rebuilding the table or changing `INT` to `BIGINT` (from V4.2.2, changing the column type from `INT` to `BIGINT` is an online DDL operation).

### In what scenarios can you change the auto-increment column to NOORDER?

* If the user does not require ordered auto-increment values at the list level and wants to optimize the performance of high-concurrency operations, you can change `ORDER` to `NOORDER`.
* If the user requires ordered auto-increment values at the list level, all leaders are on the same OBServer node, and wants to optimize the performance of high-concurrency operations, you can change `ORDER` to `NOORDER`.

### In what scenarios can you reduce the auto_increment_cache_size value?

* Auto-increment column value jumps are frequent.
* The business has low traffic.
* Performance is not sensitive.
* Performance is required, but the system is in single-node mode with all leaders concentrated on one node.
