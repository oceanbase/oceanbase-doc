# Vector index

This topic describes the principles of HNSW and IVF series vector indexes.

## HNSW series vector index

OceanBase Database supports HNSW vector indexes, which are divided into static baseline indexes and dynamic incremental indexes. Static baseline indexes are read-only and cannot be modified after they are generated. Dynamic incremental indexes support read and write operations. DML (insert, update, and delete) operations are first written to dynamic incremental indexes. When the incremental data reaches a certain scale, it is dumped to disk. During queries, the static baseline indexes and dynamic incremental indexes are queried separately, and the results are merged and returned to the SQL layer.
When the incremental data reaches a certain scale, the incremental data is merged with the baseline data to control the number of segments and ensure query performance.

### Index storage

#### Data organization

The vector index introduces the concept of segments and organizes data by segment within partitions. After incremental data is persisted, four types of segments exist:

<!--![](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer/V4.6.0/HNSW%E7%B4%A2%E5%BC%95segment%EF%BC%88%E6%A8%AA%EF%BC%89.png)-->

| Segment | Description | Storage location | Read/write |
|---------|------|----------|------|
| Baseline index | A read-only index generated by a full rebuild | Disk | Read-only |
| Active incremental | A writeable incremental index in memory | Memory | Read/write |
| Frozen incremental | An incremental index that is frozen after it is full | Memory | Read-only |
| Persisted incremental | An incremental index that is persisted to disk after it is frozen | Disk | Read-only |

Other notes:

* A partition has only one baseline segment, but can have multiple incremental segments.
* An incremental segment may contain uncommitted or rolled back data, which must be filtered using a visibility bitmap.

### Dumping and merging

#### Dumping

The incremental data in memory is persisted to disk, and the log table is shrunk. The main process is as follows:

1. Freezing: When the active incremental data reaches a threshold (such as the memory size or the number of rows), it is frozen (no more writes) → generates a frozen incremental segment.
2. Persisting: The frozen incremental segment is serialized and written to disk.
3. Updating metadata: The index metadata (version number and segment list) is updated.

#### Merging

| Type | Trigger condition | Purpose |
|---------|------|----------|
| Incremental merge | The number of persisted incremental segments is ≥ 2 | Merges multiple incremental segments to reduce the merge cost during queries |
| Baseline rebuild | The number of vectors in the incremental segments exceeds that in the baseline | Rebuilds the baseline index from scratch to generate a new read-only baseline index |

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>During merging, you can perform quantization compression (such as FP32 → SQ/BQ) to save storage space. </p>
</main>

### Filters

Two types of filters are supported during queries:

| Scenario | Description |
|---------|------|
| Pre_filter | Filters the main table data first, and then queries the vector index (suitable for scenarios where the filter conditions are strong) |
| Post_filter | Queries the vector index first, and then filters the candidate results (suitable for scenarios where most vector results are valid) |

### Common questions

Q: Why are the baseline and incremental indexes built in two stages?
A: Building an HNSW vector index is expensive. Therefore, the index is not suitable for frequent updates. Instead, the index is built in two stages:
* Baseline: Read-only. Periodically rebuilt in full to support queries.
* Incremental: Writable in memory. Supports real-time DML operations. Periodically merged into the baseline.

## IVF series vector index

An IVF series vector index is a vector index based on inverted indexing. It uses a clustering algorithm to divide the high-dimensional vector space into `nlist` subregions defined by cluster centers (centroids). Each cluster center is associated with an inverted bucket that stores the vectors (or their quantized compressed codes) belonging to the subregion. During searches, only the buckets closest to the query vector are accessed, achieving a balance between computational overhead and retrieval accuracy.

### Internal structure

An IVF series vector index can be logically divided into two layers:

* Cluster center layer (coarse clustering layer): Maintains `nlist` cluster centers to determine which buckets to prioritize during queries. The search parameter `nprobe` specifies the number of cluster centers closest to the query vector.
* Inverted bucket data layer: Each cluster center corresponds to a bucket. The bucket stores the vector entries that fall within the cluster region (which can be compressed using techniques like product quantization).

The cluster center layer (coarse clustering layer) has two main physical organization methods, each suitable for different scales of `nlist`:

| Organization method | Suitable scenario      | Search method                        | Features                   |
|----------|--------------|----------------------------------|------------------------|
| ARRAY    | nlist is small   | Linear distance calculation and top selection | Simple implementation, low constant overhead   |
| HGRAPH   | nlist is large   | Graph traversal  | Supports large numbers of cluster centers and is efficient   |

In practice, after the cluster centers are loaded into memory, the system automatically selects the optimal organization method based on the scale of `nlist`. When `nlist` is below a threshold, the `ARRAY` structure is used. When `nlist` exceeds the threshold, the `HGraph` structure is built, and the large contiguous array can be released based on the implementation strategy. Subsequent access to cluster center information is performed through a unified interface.
