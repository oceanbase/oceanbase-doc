# Foreign key constraints

OceanBase Database in MySQL mode supports foreign keys, allowing cross-table references to related data. Foreign key constraints help maintain consistency of related data.

## Characteristics of foreign key constraints

A foreign key relationship involves a parent table that contains primary key values and a child table that contains foreign key values that reference the primary key values. The foreign key constraint is defined on the child table.

The basic syntax for defining a foreign key constraint using the `CREATE TABLE` or `ALTER TABLE` statement is as follows:

```sql
​[CONSTRAINT [symbol]] FOREIGN KEY
    [index_name] (col_name, ...)
    REFERENCES tbl_name (col_name,...)
    [ON DELETE reference_option]
    [ON UPDATE reference_option]

reference_option:
    RESTRICT | CASCADE | NO ACTION | SET DEFAULT
```

A foreign key constraint has the following characteristics:

* Identity

* Conditions and limitations

* Reference behavior

### Identity

The naming convention for foreign key constraints is as follows:

* If `CONSTRAINT symbol` is defined, use that value.

* If the `CONSTRAINT symbol` clause or the `CONSTRAINT` keyword is not followed by a symbol, a constraint name is automatically generated.

* The value, if defined, must be unique in the database. A repeated value would cause an error like the following: `ERROR 1005 (HY000): Can't create table 'test.fk1' (errno: 121)`.

Table and column identifiers in the `FOREIGN KEY ... REFERENCES` clause can be enclosed in backticks (\`).

### Conditions and limitations

Foreign key constraints are subject to the following conditions and limitations:

* To create a foreign key constraint, you must have the `REFERENCES` privilege on the parent table. The column referenced by the foreign key must have a primary key or a unique index.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>In OceanBase Database V4.3.5 and later, you can create a foreign key constraint on a non-unique index. </p>
  </main>

* The data types of the corresponding columns in the foreign key and the reference key must be compatible. The size and sign of fixed-precision data types such as `INTEGER` and `DECIMAL` must be the same. The length of a string type does not need to be the same. For non-binary (character) string columns, the character set and collation must be the same.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>In OceanBase Database V4.3.5 and later, from V4.3.5 BP1 onwards, the foreign key and the reference key can be of the following data types: <ul><li>UNSIGNED FLOAT and FLOAT</li><li>FLOAT and UNSIGNED FLOAT</li><li>UNSIGNED DOUBLE and DOUBLE</li><li>DOUBLE and UNSIGNED DOUBLE</li></ul></p>
  </main>

* By default, an index is created on the referenced key (parent key) in MySQL mode of OceanBase Database, but not on the foreign key.

* You cannot create an index prefix on a foreign key. Therefore, columns of the foreign key cannot be of the `BLOB` or `TEXT` type, because indexes on these columns must always have a prefix length.

* A foreign key constraint cannot reference a generated virtual column.

### Reference behavior

​When a `DELETE` or `UPDATE` operation would affect a matching row in a child table, the result depends on the reference action specified in the `ON UPDATE` and `ON DELETE` clauses of the `FOREIGN KEY` clause. The reference actions are as follows:

* `CASCADE`: The system automatically deletes or updates the matching rows in the child table when a row in the parent table is deleted or updated.

  Both `ON DELETE CASCADE` and `ON UPDATE CASCADE` are supported. Multiple `ON UPDATE CASCADE` clauses are not allowed to act on the same column of the parent table or child table. If the `FOREIGN KEY` clause is specified for both tables in a foreign key relationship, you must specify the `ON UPDATE CASCADE` or `ON DELETE CASCADE` clause for another `FOREIGN KEY` clause to enable cascading operations. If you specify only one of the `ON UPDATE CASCADE` or `ON DELETE CASCADE` clauses, the cascading operation will fail and an error will be returned.

* If the foreign key is self-referential and a row references itself, the row can be successfully deleted in the MySQL mode of OceanBase Database.

* If the foreign key is self-referential, the MySQL mode of OceanBase Database allows cascading updates when the parent key of a row is updated.

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p> Cascading operations in the MySQL mode of OceanBase Database will trigger triggers. </p>
  </main>

* The system triggers an error (error code 1451) when a cyclic update is detected or a table is updated multiple times during an update operation. Here are some examples:

  1. The MySQL mode of OceanBase Database does not support cascading updates for a self-referential foreign key. For example, if an update operation causes the child column to attempt to cascade and update the parent column itself, an error is triggered. Here is an example:

      ```sql
      // Create a table.
      DROP TABLE IF EXISTS t1;
      CREATE TABLE t1(c1 INT UNIQUE, c2 INT, FOREIGN KEY (c2) REFERENCES t1(c1) ON UPDATE CASCADE);
      // Insert test data.
      INSERT INTO t1 VALUES(1, NULL), (2, 1);
      ```

      Perform the following update operation:

      ```sql
      UPDATE t1 SET t1.c1 = 10 WHERE t1.c1 = 1;
      ```

      The return result is as follows:

      ```shell
      ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails
      ```

      The cause of the error is analyzed as follows:

      * The foreign key `c2` in the `t1` table references the `c1` column of the same table.
      * Updating the `c1` column will trigger an update of the `c2` column. However, since the `c2` column is a self-referential foreign key, the system detects a potential cyclic update and therefore returns an error.

  2. The MySQL mode of OceanBase Database does not support cascading updates for cyclic foreign key references. For example, if multiple tables have cyclic foreign key references, an update operation that forms a loop (that is, an update operation where the update path returns to the table being updated) is not supported. Here is an example:

      ```sql
      // Create tables.
      DROP TABLE IF EXISTS t1, t2, t3;
      CREATE TABLE t1(c1 INT PRIMARY KEY, c2 INT);
      CREATE TABLE t2(c1 INT PRIMARY KEY, c2 INT UNIQUE);
      CREATE TABLE t3(c1 INT PRIMARY KEY, c2 INT UNIQUE);
      // Create foreign key constraints.
      ALTER TABLE t1 ADD FOREIGN KEY(c2) REFERENCES t3(c2) ON UPDATE CASCADE;
      ALTER TABLE t2 ADD FOREIGN KEY(c2) REFERENCES t1(c1) ON UPDATE CASCADE;
      ALTER TABLE t3 ADD FOREIGN KEY(c2) REFERENCES t2(c2) ON UPDATE CASCADE;
      // Insert test data.
      INSERT INTO t1 VALUES(1, NULL);
      INSERT INTO t2 VALUES(1, 1);
      INSERT INTO t3 VALUES(1, 1);
      INSERT INTO t1 VALUES(2, 1);
      ```

      Perform the following update operation:

      ```sql
      UPDATE t1 SET t1.c1 = 10 WHERE t1.c1 = 1;
      ```

      The return result is as follows:

      ```shell
      ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails
      ```

      The cause of the error is analyzed as follows:

      * The tables `t1`, `t2`, and `t3` have cyclic foreign key references: `t1 → t2 → t3 → t1`.
      * Updating the `t1` table will trigger cascading updates in the order of the `t2`, `t3`, and `t1` tables. Since the updates return to the `t1` table, a loop is formed, and therefore an error is returned.

  3. The MySQL mode of OceanBase Database does not support cascading updates for multiple tables. For example, if an `UPDATE` statement directly or indirectly triggers a cascading update for a table included in the `UPDATE` statement, an error is returned. Here is an example:

      ```sql
      // Create tables.
      DROP TABLE IF EXISTS t1, t2, t3;
      CREATE TABLE t1(c1 INT PRIMARY KEY, c2 INT);
      CREATE TABLE t2(c1 INT PRIMARY KEY, c2 INT UNIQUE, c3 INT);
      CREATE TABLE t3(c1 INT PRIMARY KEY, c2 INT UNIQUE, c3 INT);
      // Create foreign key constraints.
      ALTER TABLE t2 ADD FOREIGN KEY(c2) REFERENCES t1(c1) ON UPDATE CASCADE;
      ALTER TABLE t3 ADD FOREIGN KEY(c2) REFERENCES t2(c2) ON UPDATE CASCADE;
      // Insert test data.
      INSERT INTO t1 VALUES(1, 5);
      INSERT INTO t2 VALUES(1, 1, 5);
      INSERT INTO t3 VALUES(1, 1, 5);
      ```

      Perform the following update operation:

      ```sql
      UPDATE t1, t2, t3 SET t1.c1 = 10, t2.c1 = 20 WHERE t1.c2 = t2.c3 AND t2.c3 = t3.c3;
      ```

      The return result is as follows:

      ```shell
      ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails
      ```

      The cause of the error is analyzed as follows:

      Updating the `t1` table triggers cascading updates for the `t2` and `t3` tables. However, the `t2` table is included in the `UPDATE` statement. An implicit cycle `t1->t2->t3->t2` is detected during the update of the `t2` table, and therefore an error is returned.

* `RESTRICT`: Prohibits delete or update operations on the parent table.

  Specifying `RESTRICT` (or `NO ACTION`) is equivalent to omitting the `ON DELETE` or `ON UPDATE` clause.

* `NO ACTION`: A standard SQL keyword.

  In the MySQL mode of OceanBase Database, `NO ACTION` is equivalent to `RESTRICT`. If the referenced table contains related foreign key values, the deletion or update operation on the parent table is prohibited. Some database systems support deferred checks and `NO ACTION` specifies a deferred check. In MySQL, foreign key constraints are immediately checked, so that `NO ACTION` has the same effect as `RESTRICT`.

The default action for both `ON DELETE` and `ON UPDATE` is `NO ACTION`. The `ON DELETE NO ACTION` or `ON UPDATE NO ACTION` clause specified explicitly will not appear in the output of the `SHOW CREATE TABLE` statement.

## Common foreign key operations

### Add a foreign key constraint

You can execute the following `ALTER TABLE` statement to add a foreign key constraint to an existing table:

```sql
​ALTER TABLE table_name
ADD [CONSTRAINT [symbol]] FOREIGN KEY
[index_name] (col_name, ...)
REFERENCES tbl_name (col_name,...)
[ON DELETE reference_option]
[ON UPDATE reference_option]
```

A foreign key can reference the same table. When you use the `ALTER TABLE` statement to add a foreign key constraint, make sure to create a index on the referenced column first.

### Drop a foreign key constraint

You can execute the following `ALTER TABLE` statement to drop a foreign key constraint:

```sql
​ALTER TABLE table_name DROP FOREIGN KEY fk_symbol;
```

If a `CONSTRAINT` name is specified in the `FOREIGN KEY` clause when you create a foreign key constraint, you can use the name to drop the foreign key constraint. Otherwise, an internal name is generated for the foreign key constraint, and you must use that name to drop the foreign key constraint. To find the name of a foreign key constraint, use the `SHOW CREATE TABLE` statement.

### Enable foreign key checks

Foreign key checks are enabled by default. If you want to enforce referential integrity, enable foreign key checks during normal operation.

Disabling foreign key checks can improve performance in the following scenarios:

* You want to drop a table that has a foreign key constraint. You can only drop the referenced table after you disable foreign key checks. When you drop a table, any constraints defined on the table are also dropped.

* You want to reload tables in a different order than required by foreign key constraints. This can help speed up the loading process when some indexes are to be rebuilt during the reload.

* You want to import data and can disable foreign key checks to speed up the data import.

* You want to execute the `ALTER TABLE` statement on tables with foreign key constraints.​

However, keep in mind that disabling foreign key checks has the following disadvantages:

* You can drop a database that contains tables referenced by tables outside the database.

* You can drop a table that has a foreign key that references another table.​

Enabling foreign key checks does not trigger a scan of table data. This means that when foreign key checks are re-enabled, the rows added to the table while foreign key checks are disabled are not checked for consistency.

## Foreign key examples

* Use a single-column foreign key to associate a parent table with a child table.

  ```sql
  CREATE TABLE parent (
   id INT NOT NULL,
   PRIMARY KEY (id)
  )
  ​
  CREATE TABLE child (
   id INT,
   parent_id INT,
   INDEX par_ind(parent_id),
   FOREIGN KEY (parent_id) REFERENCES parent (id) ON DELETE CASCADE
  )
  ```

* The `product_order` table has foreign keys to the product table and the customer table. One foreign key has two indexes in the product table, and the other has one index in the customer table.

  ```sql
  CREATE TABLE product (
   category INT NOT NULL,
   id INT NOT NULL,
   price DECIMAL,
   PRIMARY KEY (category, id)
  )
  ​
  CREATE TABLE customer (
   id INT NOT NULL,
   PRIMARY KEY (id)
  )
  ​
  CREATE TABLE product_order (
   no INT NOT NULL AUTO_INCREMENT,
   product_category INT NOT NULL,
   product_id INT NOT NULL,
   customer_id INT NOT NULL,
   PRIMARY KEY (no),
   INDEX(product_category, product_id),
   INDEX(customer_id),
   FOREIGN KEY (product_category, product_id) REFERENCES product (category, id) ON DELETE RESTRICT ON UPDATE CASCADE,
   FOREIGN KEY (customer_id) REFERENCES customer (id)
  )
  ```
