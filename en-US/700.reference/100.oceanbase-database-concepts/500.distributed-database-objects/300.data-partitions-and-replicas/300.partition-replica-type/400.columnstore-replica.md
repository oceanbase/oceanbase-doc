# Columnstore replica

**Columnstore replica (C replica)** is a type of read-only replica in OceanBase Database, primarily used for **analytical (AP) read-only queries**. Data is stored in **columnar** format on C replicas, which work in conjunction with all-purpose replicas (F) and read-only replicas (R). TP writes and regular strong reads are mainly handled by F and R replicas, while AP scans benefit from the optimized storage format on C replicas. On C replicas, all user tables (including replicated tables, excluding index tables, internal tables, and system tables) are stored in columnar format. OLAP workloads access C replicas through a dedicated proxy and execute decision-making and analytical tasks in weak-read mode.

A columnstore replica has the following characteristics:

* Contains full logs, a MemTable, and an SSTable.

* **Baseline (major SSTable):** The baseline data of user tables on C replicas is organized in **columnar** format, facilitating large-scale scans and AP computations.

* **Incremental and hybrid storage:** Incremental data such as MemTables and minor SSTables are still stored in **row-based** format. C replicas asynchronously synchronize logs from source replicas via clogs and then locally replay them.

* Cannot join a Paxos group or participate in log voting as a member of the Paxos group. Instead, it works as a listener that synchronizes logs from the Paxos group members and then locally replays the logs. It does not act as a voting member and therefore causes no latency in transaction commits.

* Provides read-only services if an application does not require strong-consistency reads.

* Stores user tables in the same log stream in columnar storage mode at the major SSTable layer.

* Cannot be converted into a replica of another type.

The following table describes more features of such a replica.

|      Feature           |                      Description                       |
|----------------------|-----------------------------------------------|
| Replica name and abbreviation        | COLUMNSTORE (C)                                   |
| Whether logs are contained           | It has asynchronous logs. It is only a listener instead of a member of the Paxos group (ASYNC_CLOG). |
| Whether a MemTable is contained     | Yes (WITH_MEMSTORE)                              |
| Whether an SSTable is contained       | Yes (WITH_SSSTORE)       |
| Data security             | Medium                                             |
| Time to become the leader  | Not supported                                           |
| Resource cost             | High                                             |
| Service                 | Supports non-consistent read.                                        |
| Limitations on replica type conversion       | Cannot be converted into a replica of another type                                    |

### Scenarios where a C replica temporarily stores data in rowstore format

In OceanBase Database, if a table is created as a rowstore table, the system will create a pure columnstore table on the C replica. If a table is created as a columnstore table, the storage method on the C replica will be consistent with that on the F replica. Therefore, the C replica is responsible for converting user partitions of rowstore tables on the F replica into columnstore format. However, this conversion only indicates the "final" state of the data being stored in columnstore format. At any given time, the C replica does not always store data in columnstore format. In the following scenarios, the C replica temporarily stores data in rowstore format, and the system will automatically schedule row-to-column conversion tasks to convert the latest baseline data into columnstore format.

| Scenario             | Description                                                          |
|-----------------|---------------------------------------------------------------|
| Adding a replica             | For example, if you modify the locality from `F@z1, F@z2` to `F@z1, F@z2, C@z3`: <ul><li>When the baseline data (rowstore data) is migrated from the source replica (F or R replica) to the destination replica (C replica), the rowstore data is first copied to the C replica, and the system will attempt to initiate a row-to-column conversion for the tablet.</li> <li>Since row-to-column conversion is a type of major compaction, if multiple attempts to convert the rowstore data to columnstore format fail (for example, due to a full DAG Scheduler queue, high I/O pressure, or insufficient disk space), the system will provide weak-consistency read queries based on the rowstore data.</li></ul>|
| Rebuilding a log stream                | When a log stream on the C replica is rebuilt, the system will pull the corresponding baseline data to the C replica. If the baseline data is in rowstore format, it will temporarily remain in rowstore format until the system schedules a row-to-column conversion task.|
| Concurrent replica addition and Offline DDL operations  | When the C replica is part of the log stream members, if you execute an Offline DDL operation, the system will directly build a columnstore baseline on the C replica. However, if a replica addition and an Offline DDL operation are executed concurrently, the C replica will not be visible to the log stream leader that executes the DDL operation. In this case, the system will first build a rowstore baseline on the C replica and then convert it to columnstore format after the row-to-column conversion task is scheduled.|
| Full direct load                   | Currently, full direct load only supports importing data to the C replica in rowstore format. After the system schedules a row-to-column conversion task, the data will be converted to columnstore format.|
| Table-level restore                       | Since columnstore tables do not currently support table-level restore, the C replica will only support restoring data to rowstore format. After the system schedules a row-to-column conversion task, the data will be converted to columnstore format.|

During the row-to-column conversion process, although the optimizer generates a columnstore query plan, the actual execution is still based on the rowstore baseline. Users can query the C replica's availability and the progress of the row-to-column conversion using the views [CDB_OB_CS_REPLICA_STATS](../../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/8120.o-cdb_ob_cs_replica_stats-of-sys-tenant.md) (for the sys tenant) and [DBA_OB_CS_REPLICA_STATS](../../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/8220.o-dba_ob_cs_replica_stats-of-mysql-mode.md) (for user tenants). After the row-to-column conversion task is completed, users can perform queries on the C replica.

In the sys tenant, the following example shows how to query the row-to-column conversion progress of all tenants' C replicas in their log streams:

```shell
obclient[oceanbase]> SELECT * FROM oceanbase.CDB_OB_CS_REPLICA_STATS;
```

The query result is as follows:

```shell
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
| TENANT_ID | SVR_IP         | SVR_PORT | LS_ID | TOTAL_TABLET_CNT | AVAILABLE_TABLET_CNT | TOTAL_MACRO_BLOCK_CNT | AVAILABLE_MACRO_BLOCK_CNT | AVAILABLE |
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
|      1004 | xx.xxx.xxx.212 |    63000 |  1001 |             1019 |                 1019 |                 10706 |                     10706 | TRUE      |
|      1006 | xx.xxx.xxx.212 |    63000 |  1001 |              133 |                  133 |                   875 |                       875 | TRUE      |
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
2 rows in set
```

The first row of the query result indicates that for tenant ID 1004, the C replica is located on the server `xx.xxx.xxx.212` at port `63000`; the log stream ID of the C replica is `1001`; the total number of partitions to be converted to columnstore format is `1019`, and the total number of available partitions is `1019`; the total number of baseline macroblocks is `10706`, and the total number of available macroblocks is `10706`. Users can estimate the progress of the row-to-column conversion using `AVAILABLE_TABLET_CNT / TOTAL_TABLET_CNT` or `AVAILABLE_MACRO_BLOCK_CNT /TOTAL_MACRO_BLOCK_CNT`. Only when all tablets in the log stream are available will the log stream be fully available.
