# Monitor DDL execution progress

In a production environment, it is common for DDL execution to take a long time and the execution process to be transparent. To address this, OceanBase Database V4.1 introduces the real-time DDL execution progress monitoring feature, which displays the DDL execution progress in the `GV$SESSION_LONGOPS` view. For more information, see [GV$SESSION_LONGOPS](../../../../700.system-views/300.system-view-of-sys-tenant/300.performance-view-of-sys-tenant/5000.gv-session_longops-of-sys-tenant.md).

This topic describes how to monitor DDL execution progress and diagnose common issues. It uses the creation of indexes, the addition of primary keys, and the deletion of columns as examples to illustrate the monitoring feature of the `GV$SESSION_LONGOPS` view. The index creation is an independent DDL task, the primary key addition involves parent-child DDL tasks, and the column deletion involves parent-child DDL tasks implemented through non-sorting data replenishment.

To monitor DDL execution progress, you need to create two sessions: one for executing DDL operations and the other for querying the `GV$SESSION_LONGOPS` view. Both sessions log in to the system as normal tenants.

You can execute the following statement to view the fields in the `GV$SESSION_LONGOPS` view:

```sql
SELECT * FROM oceanbase.gv$session_longops\G
```

## Create an index on the observation table

The index completion stage is the most time-consuming part of the index creation operation. In some cases, concurrent transactions can affect the index creation process. This topic describes how to monitor the progress of index creation, including the wait-for transaction end stage and the index completion stage.

### Wait for the transaction to end stage

```sql
*************************** 1. row ***************************
             SID: -1
        TRACE_ID: YE5186458A15C-0005EF63AE10FBBB-0-0
          OPNAME: create index
          TARGET: __idx_500005_i1
          SVR_IP: xxx.xx.xxx.xx
        SVR_PORT: 58648
      START_TIME: 2022-12-09
 ELAPSED_SECONDS: 7
  TIME_REMAINING: 0
LAST_UPDATE_TIME: 2022-12-09
         MESSAGE: TENANT_ID: 1004, TASK_ID: 2, STATUS: WAIT TRANS END, PENDING_TX_ID: 76
```

In the wait for transaction end stage, the MESSAGE field displays `WAIT TRANS END`, and the ID of the first unfinished transaction is displayed (for example: PENDING_TX_ID: 76). You can query the `__all_virtual_trans_stat` view for more information about the transaction by using the transaction ID as the `trans_id` parameter.

### Commit phase

```sql
*************************** 1. row ***************************
             SID: -1
        TRACE_ID: YE5186458A15C-0005EF60F182F228-0-0
          OPNAME: create index
          TARGET: __idx_500008_i1
          SVR_IP: xxx.xx.xxx.xx
        SVR_PORT: 58648
      START_TIME: 2022-12-09
 ELAPSED_SECONDS: 38
  TIME_REMAINING: 0
LAST_UPDATE_TIME: 2022-12-09
         MESSAGE: TENANT_ID: 1004, TASK_ID: 6, STATUS: REPLICA BUILD, ROW_SCANNED: 10000000, ROW_SORTED: 19771966, ROW_INSERTED: 0
```

The MESSAGE field contains the following key information during the data completion phase:

- TENANT_ID: Tenant identifier
- TASK_ID: DDL task identifier
- STATUS: The current execution status. `REPLICA BUILD` indicates that data is being completed.
- ROW_SCANNED: Number of rows scanned from the primary table
- ROW_SORTED: The number of sorted rows
- ROW_INSERTED: the number of rows written to the index table

Since the sorting process may involve multiple rounds of merge operations, the value of `ROW_SORTED` is usually greater than the values of `ROW_SCANNED` and `ROW_INSERTED`.

### Columnstore features

After the columnar storage version was introduced, the data completion monitoring has changed. The system distinguishes between columnstore tables and rowstore tables. Tables stored using the columnar storage version or hybrid rowstore-columnstore tables are considered rowstore tables.

The data filling process has differences:

- Rowstore table: Data is written to a temporary file and then directly written to macroblocks.
- Columnstore table: After data is written to temporary files, it needs to be written to the columnar SS table. The total number of rows is column_group_cnt × row_count.

Here is an example of a MESSAGE message during data supplementation:

- In-memory rowstore table: `TENANT_ID: 1004, TASK_ID: 4514, STATUS: REPLICA BUILD, ROW_SCANNED: 779, ROW_SORTED: 0, ROW_INSERTED: 0`
- Columnstore table: `TENANT_ID: 1004, TASK_ID: 6064, STATUS: REPLICA BUILD, ROW_SCANNED: 100000, ROW_SORTED: 200000, ROW_INSERTED_TMP_FILE: 100000, ROW_INSERTED_SSTABLE: 500000 out of 500000 done`

## Add a primary key to an observation



Adding a primary key is different from creating an index. When a primary key is added, the data is completed. At this time, two records are displayed in the `GV$SESSION_LONGOPS` view, which indicates that the index and the table are being changed, respectively. The fields have similar meanings to those in the index creation view.

```sql
*************************** 1. row ***************************
             SID: -1
        TRACE_ID: YE5186458A15C-0005EF60F182F22F-0-0
          OPNAME: create index
          TARGET: __idx_500030_i1
          SVR_IP: xxx.xx.xxx.xx
        SVR_PORT: 58648
      START_TIME: 2022-12-09
 ELAPSED_SECONDS: 6
  TIME_REMAINING: 0
LAST_UPDATE_TIME: 2022-12-09
         MESSAGE: TENANT_ID: 1004, TASK_ID: 8, STATUS: REPLICA BUILD, ROW_SCANNED: 5518389, ROW_SORTED: 0, ROW_INSERTED: 0
*************************** 2. row ***************************
             SID: -1
        TRACE_ID: YE5186458A15C-0005EF60F182F22F-0-0
          OPNAME: add primary key
          TARGET: t1
          SVR_IP: xxx.xx.xxx.xx
        SVR_PORT: 58648
      START_TIME: 2022-12-09
 ELAPSED_SECONDS: 63
  TIME_REMAINING: 0
LAST_UPDATE_TIME: 2022-12-09
         MESSAGE: TENANT_ID: 1004, TASK_ID: 7, STATUS: COPY DEPENDENT OBJECTS, CHILD TASK IDS: [ 8 ]
```
