# Overview of DBMS_LOCK  ## Purpose The `DBMS_LOCK` package provides procedures for managing locks for database resources. Locks are used to control access to shared resources.  ## Syntax `DBMS_LOCK` is a package for managing database locks. The package contains procedures for acquiring, renewing, and releasing locks.  ## Limitations and considerations The `DBMS_LOCK` package is available only to the DBA and to users with the ADMINISTER DATABASE TRIGGERS privilege. For example, the package cannot be called from a remote location or another package. In addition, this package cannot be used to manage lock requests made by other packages. Only procedures in this package can be used to manage lock requests for database resources.  ## Privilege requirements The `DBMS_LOCK` package can be used only by the DBA or users granted the ADMINISTER DATABASE TRIGGERS privilege.  ## Parameters A parameter is an item of data passed to a procedure.  ## Examples Example code for managing database locks using the `DBMS_LOCK` package.  ## References References to related packages and procedures.  ## Exceptions The `DBMS_LOCK` package might raise exceptions during the acquisition, renewal, or release of a lock.  ## Considerations The `DBMS_LOCK` package manages database locks. The `DBMS_LOCK` package provides APIs for managing locks in OceanBase Database.

The `DBMS_LOCK` package provides the following functionality:

* Supports mutual exclusion: provides exclusive access to a device, such as a terminal.

* Be able to detect released locks: After an application releases or clears a lock, other applications should be able to detect it.

* Synchronization: Coordinate and synchronize between applications or workflows.

## Privilege requirements

The database system has a limit on the total number of available locks. When using locks or sharing this package with other users, it is advisable to grant only the `EXECUTE` privilege to specific users or roles.

## Rules and Limitations of DBMS_LOCK

The following table lists the lock compatibility matrix. `Y` indicates a successful request, and `N` indicates a failed request.

| **Lock type** | **NL lock** | **SS lock** | **SX lock** | **S lock** | **SSX lock** | **X lock** |
| --- | --- | --- | --- | --- | --- | --- |
| NL | Y | Y | Y | Y | Y | Y |
| SS | Y | Y | Y | Y | Y | N |
| SX | Y | Y | Y | N | N | N |
| S | Y | Y | N | Y | N | N |
| SSX | Y | Y | N | N | N | N |
| X | Y | N | N | N | N | N |

Set the default lock wait time when requesting a lock by using `maxwait`.

```sql
maxwait  constant integer := 32767;
```

## Considerations for using DBMS_LOCK

* User locks are prefixed with "UL" and do not conflict with table locks.
* If the session is disconnected, then the locks are released.
* The lock ID ranges from (0, 1073741823).
* User locks and table locks behave identically and include all the capabilities of table locks, such as deadlock detection.
Make sure that the user locks used in distributed transactions are released when the transaction is committed, or you might face a deadlock issue.
* For each session, best practices recommend that you limit the number of locks in `DBMS_LOCK` to a few hundred.
