# Use the Time To Live (TTL) feature

The Time To Live (TTL) feature in the SQL mode of OceanBase Database provides the capability to manage expired data. You can define a TTL policy for a table to set the validity period of the data. The system then executes the TTL task to handle the expired data.

For tables with a defined TTL policy, the system processes expired data in the following two steps:

1. When a TTL task is triggered, the system synchronizes a delete marker for the table with the TTL attribute, its index table, and auxiliary table. Data rows that meet the delete rule are marked for deletion and become invisible to users.

2. During the next major compaction, the system permanently deletes the marked data from the storage layer to release storage space.

This topic describes how to initiate a TTL task by using commands or by setting up a periodic task.

## Considerations

* When a TTL task synchronously marks data for deletion, it locks the table, which is mutually exclusive with operations such as major compaction, DDL, and data transfer.

* If the number of partitions in the main table, index table, and auxiliary table exceeds 4000, a transaction timeout may occur, causing the task to fail and retry repeatedly. You can increase the timeout time to resolve this issue. The statement is as follows:

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM SET internal_sql_execute_timeout = 600; /*Execute this statement in the sys tenant. The unit is seconds.*/
  ```

* Since transactions for marking data for deletion are not mutually exclusive with ordinary DML transactions, when two transactions are executed concurrently and the transaction isolation level is Read Committed, phantom reads may occur when querying data that is about to expire in the DML transaction.

  For example, suppose there is a transaction `trans_A` for marking data for deletion, a transaction `trans_B` for DML operations, and a data row `rowkey_A` that is about to expire. During the period from T1 to T3 (T1 < T2 < T3):

  1. At T1: The data row `rowkey_A` has not reached its expiration time, so the DML transaction `trans_B` can read the data of `rowkey_A`.
  2. At T2: The data row `rowkey_A` reaches its expiration time, and the transaction `trans_A` marks `rowkey_A` for deletion.
  3. At T3: The DML transaction `trans_B` reads `rowkey_A` again and finds that the data cannot be read.

* If the TTL task is not executed, you can query data in the table that meets the expiration rules. If you have strict visibility requirements for expired data, you need to add a filter condition to the query statement.

* After executing an offline DDL operation or creating an index on the main table and its indexes, the table data will be rewritten, and the write time of the data will be updated, causing the data to expire later.

* After the TTL task is executed, expired data is asynchronously deleted during the compaction (major compaction) process. The deletion of expired data is performed only within OceanBase Database and will not be synchronized to other application systems downstream.

## Definition of a TTL table

### Limitations

When using the TTL feature to manage expired data, the following limitations apply to TTL tables:

* Foreign key constraints are not supported.

* Triggers are not supported.

* Vector indexes and full-text indexes are not supported.

* Only single-column TTL columns are supported. Virtual columns, generated columns, and expressions are not supported.

* The `partial_update` mode is not supported for the `MERGE_ENGINE` table update mode.

* In the current version, only the internal hidden column `ora_rowscn` (which records the timestamp of the last update) is supported as the TTL column.

* Columns named `ora_rowscn` cannot be added to tables that have the TTL attribute defined.

### Create a table with the TTL attribute

The statement to create a TTL table is as follows:

```sql
CREATE TABLE table_name (table_definition_list) MERGE_ENGINE = {append_only | delete_insert}
   TTL [=] col_name + INTERVAL interval_num ttl_unit BY COMPACTION;
```

The parameters in the statement are described as follows:

* `MERGE_ENGINE`: specifies the update mode of the table. The `partial_update` mode is not supported for the `MERGE_ENGINE` table update mode.

* `col_name`: specifies the TTL filter column. In the current version, only the column named `ora_rowscn` (an internal hidden column that records the timestamp of the last update) is supported.

* `interval_num`: specifies the integer value of the expiration time. The value range is [0, +∞). If the value is `0`, the time unit `ttl_unit` can be any of the supported values, indicating that the data will expire immediately after it is committed.

* `ttl_unit`: specifies the unit of the expiration time. Supported values are `SECOND`, `MINUTE`, `HOUR`, `DAY`, `MONTH`, or `YEAR`.

For example, create a TTL table where data expires after 7 days.

```shell
obclient> CREATE TABLE ttl_tbl1(
   id INT PRIMARY KEY,
   val VARCHAR(100)
) MERGE_ENGINE = append_only TTL ora_rowscn + INTERVAL 7 DAY BY COMPACTION;
```

After the TTL table is created, you can modify the TTL strategy based on your business needs. The statement is as follows:

```shell
obclient> ALTER TABLE ttl_tbl1 SET TTL ora_rowscn + INTERVAL 1 HOUR BY COMPACTION;
```

Similarly, if you no longer need to use the TTL feature, you can delete the TTL strategy from the table. The statement is as follows.

```shell
obclient> ALTER TABLE ttl_tbl1 REMOVE TTL;
```

## TTL tasks

For each table with a TTL attribute, if the TTL feature is enabled, the system periodically schedules TTL tasks to process expired data. After a TTL task is executed, expired data becomes invisible, but it is not actually deleted. Instead, expired data is asynchronously deleted during a major compaction (major compaction) without consuming clogs or write bandwidth. The storage space occupied by expired data is only released after the major compaction task is completed.

### Enable the TTL feature

To initiate a TTL task, the current tenant must have the TTL feature enabled. The TTL feature is controlled by the tenant-level configuration item [enable_ttl] (../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3020.enable_ttl.md) (value `True`). By default, this configuration item is set to `False` when a new tenant is created or a tenant is restored, and must be manually enabled.

1. Log in as an administrator to the `sys` tenant or user tenant of the cluster.

   The following example shows how to connect to the database. Please adjust the connection parameters according to your actual environment.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@mysqltenant#obdemo -p***** -A
   ```

2. Execute the following statement to enable the TTL feature.

   * Enable the TTL feature for a specified tenant.

      ```shell
      obclient(root@sys)[(none)]> ALTER SYSTEM SET enable_ttl = True TENANT = tenant_name;
      ```

   * Enable the TTL feature for the current user tenant.

      ```shell
      obclient> ALTER SYSTEM SET enable_ttl = True;
      ```

### Manually trigger a TTL task

After enabling the TTL feature, you can manually trigger a TTL task.

1. Log in as an administrator to the `sys` tenant or user tenant of the cluster.

   The following example shows how to connect to the database. Please adjust the connection parameters according to your actual environment.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. Execute the following command to manually trigger a TTL task.

   * Trigger a TTL task for all user tenants.

      ```shell
      obclient(root@sys)[(none)]> ALTER SYSTEM TRIGGER TTL TENANT = all_user;
      ```

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>The system tenant cannot manually trigger a TTL task for all Meta tenants by using the <code>ALTER SYSTEM TRIGGER TTL TENANT = all_meta;</code> statement. </p>
      </main>

   * Trigger a TTL task for a specified tenant.

      ```shell
      obclient> ALTER SYSTEM TRIGGER TTL TENANT = tenant_name;
      ```

   * Trigger a TTL task for the current user tenant.

      ```shell
      obclient> ALTER SYSTEM TRIGGER TTL;
      ```

### Configure the time to trigger a TTL task periodically

After enabling the TTL feature, the system periodically triggers a TTL task based on the expiration of data in TTL tables of the tenant. The time to trigger a TTL task periodically is controlled by the tenant-level configuration item [ttl_duty_time](../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8095.ttl_duty_time.md). By default, the system triggers a TTL task at `01:00` every day.

The time specified by `ttl_duty_time` is in the time zone of the tenant. We recommend that you set the time to a low business peak period of the tenant or before the tenant initiates a major compaction. For example, you can set the time to `02:00`.

To modify the time to trigger a TTL task periodically:

1. Log in as an administrator to the `sys` tenant or user tenant of the cluster.

   The following example shows how to connect to the database. Please adjust the connection parameters according to your actual environment.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@mysqltenant#obdemo -p***** -A
   ```

2. Execute the following statement to modify the time to trigger a TTL task periodically.

   * Modify the time to trigger a TTL task periodically for a specified tenant.

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM SET ttl_duty_time = '02:00' TENANT = tenant_name;
     ```

   * Modify the time to trigger a TTL task periodically for the current user tenant.

      ```shell
      obclient> ALTER SYSTEM SET ttl_duty_time = '02:00';
      ```

## TTL task status

During the execution of a TTL task, you can query the `CDB_OB_TTL_TASKS` view (`sys` tenant) or the `DBA_OB_TTL_TASKS` view (user tenant) to obtain the details of the TTL task, including the table information, start time, modification time, and execution status.

* System tenant

   ```shell
   obclient(root@sys)[(none)]> SELECT * FROM oceanbase.CDB_OB_TTL_TASKS;
   ```

* User tenant

   ```shell
   obclient(root@mysqltenant)[(none)]> SELECT * FROM oceanbase.DBA_OB_TTL_TASKS; /*MySQL mode*/
   ```

   ```shell
   obclient(root@oracletenant)[SYS]> SELECT * FROM SYS.DBA_OB_TTL_TASKS; /*Oracle mode*/
   ```

Here is an example of the query result in a user tenant:

```shell
+------------+----------+---------+----------------------------+----------------------------+--------------+------------+------------+------------+
| TABLE_NAME | TABLE_ID | TASK_ID | START_TIME                 | MODIFIED_TIME              | TRIGGER_TYPE | STATUS     | RET_CODE   | TASK_TYPE  |
+------------+----------+---------+----------------------------+----------------------------+--------------+------------+------------+------------+
| NULL       |       -1 |       1 | 2026-01-28 17:31:27.624387 | 2026-01-28 17:31:27.624387 | USER         | TRIGGERING | OB_SUCCESS | COMPACTION |
+------------+----------+---------+----------------------------+----------------------------+--------------+------------+------------+------------+
1 row in set
```

For more information about the fields in the query result, see [CDB_OB_TTL_TASKS](../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/11820.o-cdb_ob_ttl_tasks-of-sys-tenant.md) and [DBA_OB_TTL_TASKS](../../700.system-views/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/15660.o-dba_ob_ttl_tasks-of-mysql-mode.md).

After a TTL task is completed, you can query the [CDB_OB_TTL_TASK_HISTORY (sys tenant)](../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/11830.o-cdb_ob_ttl_task_history-of-sys-tenant.md) view or the [DBA_OB_TTL_TASK_HISTORY (user tenant)](../../700.system-views/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/15670.o-dba_ob_ttl_task_history-of-mysql-mode.md) view to obtain the history of the completed TTL task.
