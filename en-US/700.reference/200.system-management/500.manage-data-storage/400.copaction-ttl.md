# Use the Time To Live (TTL) feature

The Time To Live (TTL) feature in OceanBase Database SQL mode provides the capability to manage expired data. By defining a TTL strategy for a table, you can set the validity period of the data. The system then executes the TTL task to process the expired data.

For tables with a defined TTL strategy, the system processes expired data in the following two steps:

1. When the TTL task is triggered, the table with the TTL attribute, its index table, and auxiliary table will synchronize a rule for marking data as deleted through a transaction. Data rows that meet the rule will be marked as deleted and will no longer be visible to users.

2. For data marked as deleted, during the next Compaction (minor compaction), the system will remove the data from the storage layer to release storage space.

This topic describes how to initiate the TTL task by using commands or by setting up periodic tasks.

## Considerations

* When a TTL task marks data for deletion, it locks the table, which makes it incompatible with operations such as major compaction, DDL, and data transfer.

* When the number of partitions in the primary table, index table, and auxiliary tables exceeds 4000, a transaction timeout may occur, causing the task to fail repeatedly. You can increase the timeout period to resolve this issue. Sample code:

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM SET internal_sql_execute_timeout = 600; /*sys tenant*/
  ```

* Because the transaction of marking data for deletion is not incompatible with a DML transaction, when two transactions are executed concurrently and the transaction isolation level is Read Committed, a phantom read may occur when the DML transaction queries data that is close to expiration.

  For example, suppose that `trans_A` is a transaction of marking data for deletion, `trans_B` is a DML transaction, and `rowkey_A` is a data row close to expiration. In the period from T1 to T3 (T1 < T2 < T3):

  1. At T1, the data row `rowkey_A` has not reached its expiration time, and the DML transaction `trans_B` can read the data of `rowkey_A`.
  2. At T2, the data row `rowkey_A` reaches its expiration time, and the transaction `trans_A` marks `rowkey_A` for deletion.
  3. At T3, the DML transaction `trans_B` reads the data of `rowkey_A` again and finds that the data is no longer available.

* If the TTL task is not executed, you can query data in the table that meets the expiration rules. If you have strict visibility requirements for the expired data, you must add a filter condition in the query statement.

* After you execute offline DDL operations or create an index on the primary table or its index, the table data is rewritten and the write time of the data is updated, which causes the data to expire later.

* After you execute the TTL task, the expired data is asynchronously deleted during major compaction. The deletion of the expired data is performed only within OceanBase Database and is not synchronized to other application systems.

## Define a TTL table

### Limitations

When you use the TTL feature to manage expired data, the TTL table has the following limitations:

* Foreign key constraints are not supported.

* Triggers are not supported.

* Vector indexes and full-text indexes are not supported.

* Only single-column TTL columns are supported. Virtual columns, generated columns, and expressions are not supported.

* The `partial_update` mode is not supported for the `MERGE_ENGINE` parameter.

* Only the internal hidden column `ora_rowscn` (which records the timestamp of the last update) is supported as the TTL column in the current version.

* You cannot add a column named `ora_rowscn` to a table that has the TTL attribute.

### Create a TTL table

The statement for creating a TTL table is as follows:

```sql
CREATE TABLE table_name (table_definition_list) MERGE_ENGINE = {append_only | delete_insert}
   TTL [=] col_name + INTERVAL interval_num ttl_unit BY COMPACTION;
```

The parameters in the statement are described as follows:

* `MERGE_ENGINE`: specifies the update mode of the table. The `partial_update` mode is not supported for the `MERGE_ENGINE` parameter.

* `col_name`: specifies the TTL filter column. In the current version, only the internal hidden column `ora_rowscn` (which records the timestamp of the last update) is supported.

* `interval_num`: specifies the integer value of the expiration time. The value is in the range [0, +∞). If the value is `0`, the time unit `ttl_unit` can be any of the supported values, indicating that the data expires immediately after it is committed.

* `ttl_unit`: specifies the unit of the expiration time. Valid values: `SECOND`, `MINUTE`, `HOUR`, `DAY`, `MONTH`, and `YEAR`.

For example, create a TTL table whose data expires after 7 days.

```shell
obclient> CREATE TABLE ttl_tbl1(
   id INT PRIMARY KEY,
   val VARCHAR(100)
) MERGE_ENGINE = append_only TTL ora_rowscn + INTERVAL 7 DAY BY COMPACTION;
```

After the TTL table is created, you can modify the TTL strategy of the table based on your business requirements. Sample code:

```shell
obclient> ALTER TABLE ttl_tbl1 SET TTL ora_rowscn + INTERVAL 1 HOUR BY COMPACTION;
```

Similarly, if you no longer need to use the TTL feature, you can delete the TTL strategy of the table. Sample code:

```shell
obclient> ALTER TABLE ttl_tbl1 REMOVE TTL;
```

## Triggering TTL tasks

For each table with the TTL attribute enabled, the system periodically schedules TTL tasks to handle expired data. After a TTL task is executed, expired data becomes invisible, but it is not actually deleted. Instead, it is asynchronously removed during the compaction process without consuming clogs or write bandwidth. The storage space occupied by expired data is only released after the compaction task is completed.

### Enable the TTL feature

To initiate a TTL task, the current tenant must have the TTL feature enabled. The TTL feature is controlled by the tenant-level configuration item [enable_ttl] (../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3020.enable_ttl.md) (with a value of `True`). The default value of this configuration item is `False` when a tenant is created or restored, and it must be manually enabled.

1. Log in as an administrator to the `sys` tenant or user tenant of the cluster.

   The following example shows how to connect to the database. Please replace the placeholders with your actual environment details.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@mysqltenant#obdemo -p***** -A
   ```

2. Execute the following statement to enable the TTL feature.

   * Enable the TTL feature for the specified tenant.

      ```shell
      obclient(root@sys)[(none)]> ALTER SYSTEM SET enable_ttl = True TENANT = tenant_name;
      ```

   * Enable the TTL feature for the current user tenant.

      ```shell
      obclient> ALTER SYSTEM SET enable_ttl = True;
      ```

### Configure the time for scheduled TTL tasks

After enabling the TTL feature, the system will periodically trigger TTL tasks based on the expiration of data in TTL tables under the tenant. The time for scheduled TTL tasks is controlled by the tenant-level configuration item [ttl_duty_time](../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8095.ttl_duty_time.md), with a default trigger time of `01:00` daily.

The time specified by `ttl_duty_time` is based on the tenant's time zone. It is recommended to set this time during the tenant's off-peak hours or before the daily compaction starts. For example, you can set it to `02:00`.

To modify the scheduled TTL task time:

1. Log in as an administrator to the `sys` tenant or user tenant of the cluster.

   The following example shows how to connect to the database. Please replace the placeholders with your actual environment details.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@mysqltenant#obdemo -p***** -A
   ```

2. Execute the following statement to modify the scheduled TTL task time.

   * Modify the scheduled TTL task time for the specified tenant.

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM SET ttl_duty_time = '02:00' TENANT = tenant_name;
     ```

   * Modify the scheduled TTL task time for the current user tenant.

      ```shell
      obclient> ALTER SYSTEM SET ttl_duty_time = '02:00';
      ```

### Manually trigger a TTL task

After enabling the TTL feature, you can manually trigger a TTL task.

1. Log in as an administrator to the `sys` tenant or user tenant of the cluster.

   The following example shows how to connect to the database. Please replace the placeholders with your actual environment details.

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. Execute the following command to manually trigger a TTL task.

   * Manually trigger a TTL task for all user tenants.

      ```shell
      obclient(root@sys)[(none)]> ALTER SYSTEM TRIGGER TTL TENANT = all_user;
      ```

      <h4>Notice</h4>
      <p>The system tenant cannot manually trigger a TTL task for all Meta tenants using the <code>ALTER SYSTEM TRIGGER TTL TENANT = all_meta;</code> statement.</p>
      </main>

   * Manually trigger a TTL task for the specified tenant.

      ```shell
      obclient> ALTER SYSTEM TRIGGER TTL TENANT = tenant_name;
      ```

   * Manually trigger a TTL task for the current user tenant.

      ```shell
      obclient> ALTER SYSTEM TRIGGER TTL;
      ```

## TTL task status

You can query the `CDB_OB_TTL_TASKS` view (`sys` tenant) or the `DBA_OB_TTL_TASKS` view (user tenant) to view the details of a TTL task that is being executed. The details include the table information, start time, last modified time, and execution status.

* `sys` tenant

   ```shell
   obclient(root@sys)[(none)]> SELECT * FROM oceanbase.CDB_OB_TTL_TASKS;
   ```

* User tenant

   ```shell
   obclient(root@mysqltenant)[(none)]> SELECT * FROM oceanbase.DBA_OB_TTL_TASKS; /*MySQL mode*/
   ```

   ```shell
   obclient(root@oracletenant)[SYS]> SELECT * FROM SYS.DBA_OB_TTL_TASKS; /*Oracle mode*/
   ```

The query result in a user tenant is as follows:

```shell
+------------+----------+---------+----------------------------+----------------------------+--------------+------------+------------+------------+
| TABLE_NAME | TABLE_ID | TASK_ID | START_TIME                 | MODIFIED_TIME              | TRIGGER_TYPE | STATUS     | RET_CODE   | TASK_TYPE  |
+------------+----------+---------+----------------------------+----------------------------+--------------+------------+------------+------------+
| NULL       |       -1 |       1 | 2026-01-28 17:31:27.624387 | 2026-01-28 17:31:27.624387 | USER         | TRIGGERING | OB_SUCCESS | COMPACTION |
+------------+----------+---------+----------------------------+----------------------------+--------------+------------+------------+------------+
1 row in set
```

For more information about the fields in the query result, see [CDB_OB_TTL_TASKS](../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/11820.o-cdb_ob_ttl_tasks-of-sys-tenant.md) and [DBA_OB_TTL_TASKS](../../700.system-views/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/15660.o-dba_ob_ttl_tasks-of-mysql-mode.md).

After a TTL task is executed, you can query the [CDB_OB_TTL_TASK_HISTORY](../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/11830.o-cdb_ob_ttl_task_history-of-sys-tenant.md) view (`sys` tenant) or the [DBA_OB_TTL_TASK_HISTORY](../../700.system-views/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/15670.o-dba_ob_ttl_task_history-of-mysql-mode.md) view (user tenant) to view the history of the TTL task.

## Manage a TTL task

You can manually pause, resume, or cancel a TTL task during its execution.

### Pause a TTL task

After a TTL task is manually or periodically triggered, you can manually pause the task based on your business requirements.

* Pause all TTL tasks of all user tenants in the `sys` tenant.

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM SUSPEND TTL TENANT = all_user;
  ```

* Pause the TTL tasks of a specified tenant in the `sys` tenant.

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM SUSPEND TTL TENANT = tenant_name;
  ```

* Pause the TTL tasks of the current tenant in the user tenant.

  ```shell
  obclient> ALTER SYSTEM SUSPEND TTL;
  ```

### Resume a paused TTL task

After a TTL task is paused, you can manually resume it.

* Resume all TTL tasks of all user tenants in the `sys` tenant.

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM RESUME TTL TENANT = all_user;
  ```

* Resume the TTL tasks of a specified tenant in the `sys` tenant.

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM RESUME TTL TENANT = tenant_name;
  ```

* Resume the TTL tasks of the current tenant in the user tenant.

  ```shell
  obclient> ALTER SYSTEM RESUME TTL;
  ```

### Cancel a TTL task

During the execution of a TTL task, you can manually cancel the task based on your business requirements.

* Cancel all TTL tasks of all user tenants in the `sys` tenant.

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM CANCEL TTL TENANT = all_user;
  ```

* Cancel the TTL tasks of a specified tenant in the `sys` tenant.

  ```shell
  obclient(root@sys)[(none)]> ALTER SYSTEM CANCEL TTL TENANT = tenant_name;
  ```

* Cancel the TTL tasks of the current tenant in the user tenant.

  ```shell
  obclient> ALTER SYSTEM CANCEL TTL;
  ```
