# Manually trigger a major compaction

You can manually trigger a major compaction. Manual major compactions include tenant-level major compactions, table-level major compactions, and partition-level major compactions.

Adaptive major compaction is essentially a partition-level major compaction. The system automatically initiates partition-level major compactions for partitions that require them. The use cases of adaptive major compaction are similar to those of partition-level major compactions. Adaptive major compaction is mainly used to address scenarios such as data skew, frequent DML operations, and low query efficiency. For more information about adaptive major compaction, see [Adaptive major compaction](320.adaptive-compaction.md). If you have disabled adaptive major compaction for business reasons and are experiencing slow queries, you can manually initiate partition-level major compactions to resolve these issues.

## Limitations and considerations

A partition corresponds to a tablet. When you perform a partition-level major compaction, note the following considerations:

* If a tenant-level major compaction is being performed on the corresponding partition, you cannot initiate a partition-level major compaction.

* If an adaptive scheduling major compaction is being performed on the corresponding partition, you cannot initiate a partition-level major compaction.

* If the replicas of the corresponding partition are in an inconsistent state, you cannot initiate a partition-level major compaction.

* If the corresponding partition is in the RECOVERING or TRANSFER state, you cannot initiate a partition-level major compaction.

* If a major compaction task is paused, you cannot initiate a partition-level major compaction.

A partition-level major compaction is a major compaction task that is performed on multiple replicas of the same partition. This operation consumes CPU and disk I/O resources. Before you perform a partition-level major compaction, you need to evaluate the current resource usage of the tenant. After a partition-level major compaction is successfully initiated, the CPU and I/O usage will increase.

A table-level major compaction is a major compaction task that is performed on all partitions of a table in a tenant. A table-level major compaction has the following limitations:

* A table-level major compaction can be initiated only on a user table whose data is stored in the database.

* Like a partition-level major compaction, a table-level major compaction is an asynchronous task and does not guarantee to be initiated successfully.

## Prerequisites

Before you trigger a major compaction, make sure that the global major compaction is enabled. The global major compaction is controlled by the cluster-level configuration item `enable_major_freeze`, whose default value is `True`, indicating that the global major compaction is enabled.

If the global major compaction is not enabled in the current cluster, perform the following steps to enable it.

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Check whether the global major compaction is enabled.

   ```sql
   obclient> SHOW PARAMETERS LIKE 'enable_major_freeze';
   ```

3. If the global major compaction is not enabled, execute the following statement to enable it.

   ```sql
   obclient> ALTER SYSTEM SET enable_major_freeze='True';
   ```

   For more information about the `enable_major_freeze` configuration item, see [enable_major_freeze](../../../800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/7000.enable_major_freeze.md).

## Manually initiate a major compaction for a system tenant

A system tenant can initiate a major compaction for itself, for all user tenants, or for a specified tenant.

To manually initiate a major compaction, perform the following steps:

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Execute the following statement to initiate a major compaction.

   * Initiate a major compaction for a tenant

      The following SQL statement is used:

      ```sql
      ALTER SYSTEM MAJOR FREEZE TENANT [=] all_user | all | all_meta | tenant_name [, tenant_name ...];
      ```

      In the statement, `[=]` indicates that the equal sign (=) is optional.

      Here are some examples:

      * Initiate a major compaction for the system tenant

          ```sql
          obclient> ALTER SYSTEM MAJOR FREEZE;
          ```

      * Initiate a major compaction for all user tenants

          ```sql
          obclient> ALTER SYSTEM MAJOR FREEZE TENANT = all_user;
          ```

          or

          ```sql
          obclient> ALTER SYSTEM MAJOR FREEZE TENANT = all;
          ```

        <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>Starting from OceanBase Database V4.2.1, <code>TENANT = all_user</code> and <code>TENANT = all</code> have the same semantics. When you need to specify all user tenants, we recommend that you use <code>TENANT = all_user</code>. The <code>TENANT = all</code> option will be deprecated in the future. </p>

      * Initiate a major compaction for all meta tenants

          ```sql
          obclient> ALTER SYSTEM MAJOR FREEZE TENANT = all_meta;
          ```

      * Initiate a major compaction for a specified tenant

          ```sql
          obclient> ALTER SYSTEM MAJOR FREEZE TENANT = tenant1,tenant2;
          ```

   * Initiate a major compaction for a table

      The following SQL statement is used to initiate a major compaction for a table in a specified tenant:

      ```sql
      ALTER SYSTEM MAJOR FREEZE TENANT [=] tenant_name TABLE_ID = table_id;
      ```

      In the statement, `table_id` specifies the ID of the table. You can query the `CDB_OB_TABLE_LOCATIONS` view as the system tenant to obtain the `table_id` value. For more information about the fields in the `CDB_OB_TABLE_LOCATIONS` view, see [oceanbase.CDB_OB_TABLE_LOCATIONS](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/10600.o-cdb_ob_table_locations-of-sys-tenant.md).

      Here is an example of initiating a major compaction for a table in the `tenant1` tenant:

      1. Obtain the `table_id` of the table to be compacted, t1.

         ```shell
         obclient(root@sys)[oceanbase]> SELECT a.tenant_id, b.tenant_name, a.database_name, a.table_id, a.table_name FROM oceanbase.CDB_OB_TABLE_LOCATIONS a, oceanbase.DBA_OB_TENANTS b 
         WHERE a.tenant_id=b.tenant_id 
         AND a.table_name = 't1'
         AND b.tenant_name = 'tenant1';
         ```

         The query result is as follows:

         ```shell
         +-----------+-------------+---------------+----------+------------+
         | tenant_id | tenant_name | database_name | table_id | table_name |
         +-----------+-------------+---------------+----------+------------+
         |      1002 | tenant1     | test          |   500002 | t1         |
         +-----------+-------------+---------------+----------+------------+
         1 row in set
         ```

      2. Execute the following statement to initiate a major compaction for the table.

         ```shell
         obclient(root@sys)[oceanbase]> ALTER SYSTEM MAJOR FREEZE TENANT = tenant1 TABLE_ID = 500002;
         ```

   * Initiate a major compaction for a partition

      The following SQL statement is used to initiate a major compaction for a partition in a specified tenant:

      ```sql
      ALTER SYSTEM MAJOR FREEZE TENANT [=] tenant_name TABLET_ID = tablet_id;
      ```

      In the statement, `tablet_id` specifies the ID of the partition. You can query the `CDB_OB_TABLE_LOCATIONS` view as the system tenant to obtain the `tablet_id` value. For more information about the fields in the `CDB_OB_TABLE_LOCATIONS` view, see [oceanbase.CDB_OB_TABLE_LOCATIONS](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/10600.o-cdb_ob_table_locations-of-sys-tenant.md).

      Here is an example of initiating a major compaction for a partition in the `tenant1` tenant:

      1. Obtain the `tablet_id` of the partition to be compacted, t1.

         ```shell
         obclient(root@sys)[oceanbase]> SELECT a.tenant_id, b.tenant_name, a.database_name, a.table_id, a.table_name, a.tablet_id, a.partition_name, a.subpartition_name FROM oceanbase.CDB_OB_TABLE_LOCATIONS a, oceanbase.DBA_OB_TENANTS b 
         WHERE a.tenant_id=b.tenant_id 
         AND a.table_name = 't1'
         AND b.tenant_name = 'tenant1';
         ```

         The query result is as follows:

         ```shell
         +-----------+-------------+---------------+----------+------------+-----------+----------------+-------------------+
         | tenant_id | tenant_name | database_name | table_id | table_name | tablet_id | partition_name | subpartition_name |
         +-----------+-------------+---------------+----------+------------+-----------+----------------+-------------------+
         |      1002 | tenant1     | test          |   500010 | t1         |    200007 | p0             | NULL              |
         |      1002 | tenant1     | test          |   500010 | t1         |    200008 | p1             | NULL              |
         |      1002 | tenant1     | test          |   500010 | t1         |    200009 | p2             | NULL              |
         +-----------+-------------+---------------+----------+------------+-----------+----------------+-------------------+
         3 rows in set
         ```

      2. Execute the following statement to initiate a major compaction for the partition.

         ```shell
         obclient(root@sys)[oceanbase]> ALTER SYSTEM MAJOR FREEZE TENANT = tenant1 TABLET_ID = 200007;
         ```

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>The partition-level major compaction statement is mutually exclusive with the tenant-level major compaction statement and the major compaction statements initiated by the adaptive scheduling strategy. The successful execution of the partition-level major compaction statement does not necessarily mean that the major compaction has been initiated. You can check the <code>GV$OB_MERGE_INFO</code> view for the major compaction information where <code>ACTION='MEDIUM_MERGE'</code> is specified, or check the <code>GV$OB_TABLET_COMPACTION_HISTORY</code> view for the major compaction information where <code>TYPE='MEDIUM_MERGE'</code> is specified to confirm whether the major compaction has been initiated. For more information, see <a href="500.view-merge-process.md">View major compaction information</a>. </li></p>
      </main>

## Manually initiate a tenant-level or partition-level major compaction

A user tenant can only initiate a tenant-level or partition-level major compaction for its own tenant.

1. Log in to the database as the tenant administrator of the user tenant.

2. Initiate a tenant-level major compaction for the user tenant.

   * Initiate a tenant-level major compaction

      ```sql
      obclient> ALTER SYSTEM MAJOR FREEZE;
      ```

   * Initiate a table-level major compaction

      The SQL statement for initiating a table-level major compaction for a user tenant is as follows:

      ```sql
      ALTER SYSTEM MAJOR FREEZE TABLE_ID = table_id;
      ```

      In the statement, `table_id` specifies the table ID, which can be obtained by querying the `DBA_OB_TABLE_LOCATIONS` view. For more information about the fields in the `DBA_OB_TABLE_LOCATIONS` view, see [DBA_OB_TABLE_LOCATIONS](../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/11200.o-dba_ob_table_locations-of-mysql-mode.md).

      The following example shows how to initiate a table-level major compaction for a user tenant.

      1. Obtain the `table_id` of the table t1 to be compacted.

         :::tab
         tab MySQL mode

         The query statement in MySQL mode is as follows:

         ```shell
         obclient(root@tenant1)[oceanbase]> SELECT database_name, table_id, table_name FROM oceanbase.DBA_OB_TABLE_LOCATIONS WHERE table_name = 't1';
         ```

         The query result is as follows:

         ```shell
         +---------------+----------+------------+
         | database_name | table_id | table_name |
         +---------------+----------+------------+
         | test          |   500002 | t1         |
         +---------------+----------+------------+
         1 row in set
         ```

         tab Oracle mode

         The query statement in Oracle mode is as follows:

         ```shell
         obclient(sys@tenant1)[SYS]> SELECT database_name, table_id, table_name FROM SYS.DBA_OB_TABLE_LOCATIONS WHERE table_name = 'T1';
         ```

         The query result is as follows:

         ```shell
         +---------------+----------+------------+
         | DATABASE_NAME | TABLE_ID | TABLE_NAME |
         +---------------+----------+------------+
         | SYS           |   500002 | T1         |
         +---------------+----------+------------+
         1 row in set
         ```

         :::

      2. Execute the following command to initiate a table-level major compaction.

         ```shell
         obclient> ALTER SYSTEM MAJOR FREEZE TABLE_ID = 500002;
         ```

   * Initiate a partition-level major compaction

      The statement for initiating a partition-level major compaction for a user tenant is as follows:

      ```sql
      ALTER SYSTEM MAJOR FREEZE TABLET_ID = tablet_id;
      ```

      In the statement, `tablet_id` specifies the partition ID, which can be obtained by querying the `DBA_OB_TABLE_LOCATIONS` view. For more information about the fields in the `DBA_OB_TABLE_LOCATIONS` view, see [DBA_OB_TABLE_LOCATIONS](../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/11200.o-dba_ob_table_locations-of-mysql-mode.md).

      The following example shows how to initiate a partition-level major compaction for a user tenant.

      1. Obtain the `tablet_id` of the partition of the table t1 to be compacted.

         :::tab
         tab MySQL mode

         The query statement in MySQL mode is as follows:

         ```shell
         obclient(root@tenant1)[oceanbase]> SELECT database_name, table_id, table_name, tablet_id, partition_name, subpartition_name FROM oceanbase.DBA_OB_TABLE_LOCATIONS WHERE table_name = 't1';
         ```

         The query result is as follows:

         ```shell
         +---------------+----------+------------+-----------+----------------+-------------------+
         | database_name | table_id | table_name | tablet_id | partition_name | subpartition_name |
         +---------------+----------+------------+-----------+----------------+-------------------+
         | test          |   500010 | t1         |    200007 | p0             | NULL              |
         | test          |   500010 | t1         |    200008 | p1             | NULL              |
         | test          |   500010 | t1         |    200009 | p2             | NULL              |
         +---------------+----------+------------+-----------+----------------+-------------------+
         3 rows in set
         ```

         tab Oracle mode

         The query statement in Oracle mode is as follows:

         ```shell
         obclient(sys@tenant1)[SYS]> SELECT database_name, table_id, table_name, tablet_id, partition_name, subpartition_name FROM SYS.DBA_OB_TABLE_LOCATIONS WHERE table_name = 'T1';
         ```

         The query result is as follows:

         ```shell
         +---------------+----------+------------+-----------+----------------+-------------------+
         | DATABASE_NAME | TABLE_ID | TABLE_NAME | TABLET_ID | PARTITION_NAME | SUBPARTITION_NAME |
         +---------------+----------+------------+-----------+----------------+-------------------+
         | SYS           |   500010 | T1         |    200007 | P0             | NULL              |
         | SYS           |   500010 | T1         |    200008 | P1             | NULL              |
         | SYS           |   500010 | T1         |    200009 | P2             | NULL              |
         +---------------+----------+------------+-----------+----------------+-------------------+
         3 rows in set
         ```

         :::

      2. Execute the following command to initiate a partition-level major compaction.

         ```shell
         obclient> ALTER SYSTEM MAJOR FREEZE TABLET_ID = 200007;
         ```

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>The commands for initiating a partition-level major compaction, a tenant-level major compaction, and a major compaction initiated by an adaptive scheduling strategy are mutually exclusive. A successful command execution does not necessarily mean that the partition-level major compaction has been initiated. You can query the <code>GV$OB_TABLET_COMPACTION_HISTORY</code> view to check whether the major compaction of the specified partition has been initiated. The <code>TYPE</code> column specifies the type of the major compaction. If the value of the <code>TYPE</code> column is <code>MEDIUM_MERGE</code>, the major compaction has been initiated. For more information about how to query the major compaction information, see <a href="500.view-merge-process.md">Query major compaction information</a>. </li></p>
      </main>
