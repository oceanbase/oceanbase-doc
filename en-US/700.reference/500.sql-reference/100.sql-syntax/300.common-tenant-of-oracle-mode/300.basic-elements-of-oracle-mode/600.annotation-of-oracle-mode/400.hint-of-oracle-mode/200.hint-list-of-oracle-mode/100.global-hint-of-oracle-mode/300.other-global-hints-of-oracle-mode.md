# Global hints: Other hints

Other hints in the GLOBAL hint category allow developers and database administrators to perform fine-grained control over the execution of SQL statements. The following table lists the other types of hints supported.

| Hint name                               | Description                            |
|---------------------------------------|-------------------------------|
| `APPEND`                              | Collects statistics while performing an INSERT operation; enables direct load mode (DIRECT INSERT) in `INSERT INTO SELECT` statements.  |
| `CURSOR_SHARING_EXACT`                | Controls whether queries are parameterized.                                                   |
| `DIRECT`                              | Enables direct load mode in `LOAD DATA` and `INSERT` statements to improve data import efficiency and performance.                  |
| `NO_DIRECT`                              | Disables direct load mode in `LOAD DATA`, `INSERT INTO SELECT`, and `CREATE TABLE AS SELECT` statements.                 |
| `USE_PX`                 | Executes SQL statements in PX mode, which allows for multi-threaded execution.                             |
| `ENABLE_PARALLEL_DML`                 | Enables parallel DML.                             |
| `DISABLE_PARALLEL_DML`                 | Disables parallel DML.                             |
| `ENABLE_PARALLEL_DAS_DML`                 | Specifies that the current DML statement must use Distributed Data Access Service (DAS) concurrency optimization.                             |
| `DISABLE_PARALLEL_DAS_DML`                 | Specifies that the current DML statement must not use Distributed Data Access Service (DAS) concurrency optimization.                             |
| `DYNAMIC_SAMPLING`                    | Enables dynamic sampling.                              |
| `LOAD_BATCH_SIZE`                     | Specifies the batch size for each insert operation and is only applicable in `LOAD DATA` statements.         |
| `LOG_LEVEL`                           | Specifies the log level for the current query during execution.                  |
| `MAX_CONCURRENT`                      | Specifies the maximum number of concurrent queries allowed.                                           |
| `MONITOR`                             | Enables the capture of SQL Plan Monitor records for the query.                 |
| `MV_REWRITE`                             | When used alone, the `MV_REWRITE` hint allows skipping the rules and cost checks for materialized view query rewriting and directly using the applicable rewrite.                 |
| `NO_MV_REWRITE`                             | Disables materialized view query rewriting and allows specifying a query block.                 |
| `OPT_PARAM`                           | Specifies optimizer-related parameters for the query.                                    |
| `PARALLEL`                            | Specifies the degree of parallelism for the query. Its opposite operation is `NO_PARALLEL`.       |
| `NO_PARALLEL`                         | Disables query parallelism (i.e., sets the degree of parallelism to 1).                                   |
| `QUERY_TIMEOUT`                       | Specifies the query execution timeout period.                                       |
| `READ_CONSISTENCY`                    | Specifies the read consistency level (strong or weak).                                        |
| `RESOURCE_GROUP`                    | Forces the statement to use a specified resource group.                                        |
| `STAT`                                | Tracks the output statistics of query operators.                                        |
| `TRANS_PARAM`                         | Specifies transaction-related variables for the query.                     |
| `TRACING`                             | Tracks the output of query execution operators.                      |
| `USE_PLAN_CACHE`                      | Specifies the plan cache (Plan Cache) usage strategy for the current query.       |
| `DISABLE_TRIGGER`|Temporarily disables triggers in the current DML statement. You can specify one or more trigger names. If you omit the parentheses and the list of trigger names, all triggers related to the statement are disabled. |

## `CURSOR_SHARING_EXACT` Hint

The `CURSOR_SHARING_EXACT` hint specifies that parameterization is disabled at the query level.

When `cursor_sharing='exact'`, parameterization is not required. ## `DIRECT` Hint

The `DIRECT` hint enables direct load in `LOAD DATA` and `INSERT` statements, improving data import efficiency and performance.

### Syntax

The syntax of the `DIRECT` hint is as follows:

```sql
/*+ DIRECT (/*+ direct(need_sort, max_errors_allowed, load_mode) */)*/
```

### Parameter

- `need_sort`: specifies whether to sort the imported data. Valid values: `true` and `false`. `true` indicates that the data is to be sorted. `false` indicates that the data is not to be sorted.

- `max_errors_allowed`: specifies the maximum number of error rows allowed. If this number is exceeded, the import process will fail.

- `load_mode`: specifies the import mode. Valid values:

  + `full`: the default value, indicating full import.
  + `inc`: incremental import, supporting `INSERT` and `IGNORE` semantics.
  + `inc_replace`: incremental import without checking for duplicate primary keys, equivalent to `REPLACE` semantics for incremental import.

### Example

#### `DIRECT` Hint in `LOAD DATA`

**Enable incremental direct load**

```sql
LOAD DATA /*+ DIRECT(true, 0, inc) */
INFILE 'datafile.txt'
INTO TABLE mytable
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\n';
```

In this example, `DIRECT(true, 0, inc)` enables incremental direct load, sorts the data, and allows up to 0 error rows.

**Enable full direct load**

```sql
LOAD DATA
/*+ PARALLEL(4) DIRECT(true, 0, full) */
REMOTE_OSS INFILE 'oss://example.com/datafile.csv'
INTO TABLE my_table
FIELDS TERMINATED BY ',' ENCLOSED BY '"'
LINES TERMINATED BY '\n';
```

In this example, `PARALLEL(4)` sets the parallelism to 4, and `DIRECT(true, 0, full)` enables full direct load, sorts the data, and allows up to 0 error rows.

For more information, see [Direct load](../../../../../../../../../620.obap/300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

#### `DIRECT` Hint in `INSERT INTO SELECT`

To enable direct load in an `INSERT INTO SELECT` statement, use the `enable_parallel_dml` option with the `DIRECT` hint in the following format: `/*+ direct(bool, int, load_mode) enable_parallel_dml PARALLEL(N) */`.

**Enable incremental direct load**

```sql
-- Enable incremental direct load and parallel DML to incrementally import data from old_table to new_table
INSERT /*+ direct(true, 0, 'inc') enable_parallel_dml PARALLEL(4) */ INTO new_table (id, name, value)
SELECT id, name, value
FROM old_table;
```

In this example, `direct(true, 0, 'inc')` enables incremental direct load, sorts the data, and allows up to 0 error rows; `enable_parallel_dml` enables parallel DML; and `PARALLEL(4)` sets the parallelism to 4.

**Enable full direct load**

```sql
-- Enable full direct load and parallel DML to import data from old_table to new_table
INSERT /*+ direct(true, 0, 'full') enable_parallel_dml PARALLEL(4) */ INTO new_table (id, name, value)
SELECT id, name, value
FROM old_table;
```

In this example, `direct(true, 0, 'full')` enables full direct load, sorts the data, and allows up to 0 error rows; `enable_parallel_dml` enables parallel DML; and `PARALLEL(4)` sets the parallelism to 4.

For more information, see [Use the `INSERT INTO SELECT` statement to directly load data](../../../../../../../../../620.obap/300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

## `NO_DIRECT` Hint

The `NO_DIRECT` hint disables direct load in `LOAD DATA`, `INSERT INTO SELECT`, and `CREATE TABLE AS SELECT` statements.

### Syntax

The syntax of the `NO_DIRECT` hint is as follows:

```sql
/*+ NO_DIRECT */
```

### Parameter

`NO_DIRECT`: forces a single SQL statement to not use direct load. If an SQL statement contains this hint, it ignores other direct load hints and performs a regular import.

### Example

* **Use the `NO_DIRECT` hint in a `LOAD DATA` statement**

  ```sql
  LOAD DATA /*+ NO_DIRECT */ [REMOTE_OSS | LOCAL] INFILE 'file_name' INTO TABLE table_name [COMPRESSION]...
  ```

* **Use the `NO_DIRECT` hint in an `INSERT INTO SELECT` statement**

  ```sql
  INSERT /*+ NO_DIRECT */ INTO  table_name select_sentence
  ```

* **Use the `NO_DIRECT` hint in a `CREATE TABLE AS SELECT` statement**

  ```sql
  CREATE /*+ NO_DIRECT */ TABLE table_name [AS] select_sentence
  ```

## `DYNAMIC_SAMPLING` Hint

The `DYNAMIC_SAMPLING` hint specifies whether to enable dynamic sampling for a query.

### Syntax

```sql
/*+ DYNAMIC_SAMPLING ( 0 | 1 ) */
```

### Parameter

The parameters of the `DYNAMIC_SAMPLING` hint are described as follows:

- When the parameter is set to 0, dynamic sampling is disabled.
- When the parameter is set to 1, dynamic sampling is enabled.

### Example

The following example shows how to use the `DYNAMIC_SAMPLING` hint to enable dynamic sampling.

```sql
SELECT /*+ dynamic_sampling(1) */ *
FROM t1 WHERE c1 LIKE "%abc%" AND c2 LIKE "%abc%";
```

## `USE_PX` Hint

The `USE_PX` hint forces the server to execute an SQL statement in parallel execution (PX) mode. PX mode allows SQL statements to be executed using multiple threads, thereby improving query performance. Typically, the `USE_PX` hint is used with the `PARALLEL` hint to specify the number of threads for parallel execution. By default, the system uses the `USE_PX` hint.

### Syntax

The syntax of the `USE_PX` hint is as follows:

```sql
/*+ USE_PX */
```

### Example

The following example shows how to use the `USE_PX` hint:

```sql
SELECT /*+ USE_PX PARALLEL(4)*/ e.dept_id, sum(e.salary)
FROM emp e
WHERE e.dept_id = 1001 GROUP BY e.dept_id;
```

## `ENABLE_PARALLEL_DML` Hint

The `ENABLE_PARALLEL_DML` hint specifies to enable parallel DML for the current query. Its reverse hint is `DISABLE_PARALLEL_DML`, which is used to disable parallel DML.

For more information, see [Parallel DML](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/1000.parallel-dml.md).

### Considerations

- When you use `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/`, the system prioritizes distributed parallel DML (PDML). If the current environment does not support PDML, the system will fall back to DAS concurrent write for performance optimization.

- If a forced parallelism level is set at the session level, its execution behavior will be consistent with the above.

- Even if the current environment does not support parallel DML (PDML), if the system parameter `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` command (its default value is `false`), the system will not enable DAS (Distributed Active Storage) parallel writes, even if the `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used.

- If `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` command (default is `false`) and a forced parallelism level is set at the session level, the system will not enable DAS parallel writes, even if the `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used.

### Syntax

```sql
/*+ ENABLE_PARALLEL_DML */
```

### Example

```sql
insert /*+ enable_parallel_dml parallel(8) */ into t2 select * from t1;
```

## `DISABLE_PARALLEL_DML` Hint

The `DISABLE_PARALLEL_DML` hint specifies to disable parallel DML for the current query. Its reverse hint is `ENABLE_PARALLEL_DML`, which is used to enable parallel DML.

For more information, see [Parallel DML](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/1000.parallel-dml.md).

### Syntax

```sql
/*+ DISABLE_PARALLEL_DML */
```

### Example

```sql
insert /*+ disable_parallel_dml parallel(8) */ into t2 select * from t1;
```

## `ENABLE_PARALLEL_DAS_DML` Hint

The `ENABLE_PARALLEL_DAS_DML` hint specifies to enable concurrent write optimization using Distributed Data Access Service (DAS) for the current DML statement. Its reverse hint is `DISABLE_PARALLEL_DAS_DML`.

### Considerations

- The `ENABLE_PARALLEL_DAS_DML` hint must be used together with the `ENABLE_PARALLEL_DML` hint.

- When the `/*+ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used, the system will prioritize DAS concurrent writes as the forced option and execute operations based on the parallelism specified by `PARALLEL(n)`.

- If the system parameter `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` statement (default is `false`), the `/*+ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` hint will be ineffective. In this case, the system will not execute DAS parallel writes.

### Syntax

```sql
/*+ ENABLE_PARALLEL_DAS_DML */
```

### Example

```sql
insert /*+ ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(10)*/
into t1 select * from t2;
```

## `DISABLE_PARALLEL_DAS_DML` Hint

The `DISABLE_PARALLEL_DAS_DML` hint specifies to disable concurrent write optimization using Distributed Data Access Service (DAS) for the current DML statement. Its reverse hint is `ENABLE_PARALLEL_DAS_DML`.

### Considerations

- The `DISABLE_PARALLEL_DAS_DML` hint must be used together with the `ENABLE_PARALLEL_DML` hint.

- When the `/*+DISABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used, the system will disable DAS concurrent writes, even if other concurrent write optimization options like PDML are enabled.

### Syntax

```sql
/*+ DISABLE_PARALLEL_DAS_DML */
```

### Example

```sql
insert /*+ DISABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(10)*/
into t1 select * from t2;
```

## `MAX_CONCURRENT` Hint

`MAX_CONCURRENT` Hint specifies the maximum number of concurrent queries allowed.

In the `MAX_CONCURRENT` Hint, `intnum` specifies the maximum number of concurrent queries allowed. If the number of concurrent queries exceeds the maximum allowed, an error is returned when the query is executed. If `intnum` is specified as 0, an error is always returned when the query is executed.

Note that currently, the `MAX_CONCURRENT` Hint cannot be directly used in queries. Instead, you can create an outline containing only the `MAX_CONCURRENT` Hint to limit the concurrency of specific SQL statements.

### Syntax

```sql
/*+ MAX_CONCURRENT ( intnum ) */
```

### Example

```sql

USING HINT /*+ max_concurrent(10) */;
```


## Query rewrite hints

The query rewrite control hints include `MV_REWRITE` and `NO_MV_REWRITE`. These two hints take precedence over the system variable `query_rewrite_enabled`.

### `MV_REWRITE` Hint

The syntax of the `MV_REWRITE` hint is as follows:

```sql
/*+ MV_REWRITE (@ queryblock [mv_name_list]) */

mv_name_list:
    mv_name [, mv_name ...]
```

When you use the `MV_REWRITE` hint alone, it skips the rule and cost checks for query rewrite and directly applies the applicable rewrite. If you specify one or more materialized views after the hint, it skips the rule and cost checks and only uses the specified materialized views for rewrite, ignoring all unspecified materialized views.

When you use the `MV_REWRITE` hint to specify a materialized view, you cannot force the use of a materialized view without the `ENABLE QUERY REWRITE` clause. Additionally, you cannot force the use of a non-real-time materialized view when the system variable `query_rewrite_integrity` is set to `enforced`.

### `NO_MV_REWRITE` Hint

The syntax of the `NO_MV_REWRITE` hint is as follows:

```sql
/*+ NO_MV_REWRITE (@ queryblock) */
```

The `NO_MV_REWRITE` hint disables query rewrite and allows you to specify a query block.

### Example of query rewrite control hints

1. Create the base table `tbl2`.

   ```sql
   CREATE TABLE tbl2 (col1 INT, col2 INT);
   ```

2. Insert two rows of data into the base table `tbl2`.

   ```sql
   INSERT INTO tbl2 VALUES (1,2),(3,4);
   ```

   The return result is as follows:

   ```shell
   Query OK, 2 rows affected
   Records: 2  Duplicates: 0  Warnings: 0
   ```

3. Create the materialized view `mv1_tbl2` and enable query rewrite for it.

   ```sql
   CREATE MATERIALIZED VIEW mv1_tbl2 NEVER REFRESH ENABLE QUERY REWRITE AS SELECT * FROM tbl2;
   ```

4. Create the materialized view `mv2_tbl2` and enable query rewrite for it.

   ```sql
   CREATE MATERIALIZED VIEW mv2_tbl2 NEVER REFRESH ENABLE QUERY REWRITE AS SELECT * FROM tbl2 WHERE tbl2.col1 > 1;
   ```

5. Set the system variable `query_rewrite_integrity` to `stale_tolerated`.

    <main id="notice" type='explain'>

      <p>The <code>MV_REWRITE</code> and <code>NO_MV_REWRITE</code> hints take precedence over the system variable <code>query_rewrite_enabled</code>. However, you must set <code>query_rewrite_integrity</code> to <code>stale_tolerated</code> to use non-real-time materialized views for rewrite.</p>

## `NO_PARALLEL` Hint

The `NO_PARALLEL` hint specifies to disable query parallelism (i.e., set the parallelism to 1). Its opposite hint is `PARALLEL`.

The `NO_PARALLEL` hint is equivalent to `/*+ parallel(1)*/`.

### Syntax

```sql
/*+ NO_PARALLEL */
```

### Example

The following query example uses the `NO_PARALLEL` hint to disable query parallelism.

```sql
SELECT /*+ no_parallel */ c1, sum(distinct c2) FROM t1 GROUP BY c1;
```

## `NO_QUERY_TRANSFORMATION` Hint

The `NO_QUERY_TRANSFORMATION` hint disables any query rewrite for the current query.

Note that unlike the `NO_REWRITE` hint in the Query Block Hint, using `NO_QUERY_TRANSFORMATION` prevents the use of Query Block Hint to enable certain rewrites.

For more information about query rewrite, see [Overview of query rewrite](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/500.query-rewrite/100.query-rewrite-overview.md).

### Syntax

```sql
/*+ NO_QUERY_TRANSFORMATION */
```

### Example

The following query example uses the `NO_QUERY_TRANSFORMATION` hint to disable any query rewrite.

```sql
SELECT /*+ NO_QUERY_TRANSFORMATION */ *
FROM (SELECT * FROM t1) v WHERE v.c1 = 3;
```

## `OPT_PARAM` Hint

`OPT_PARAM` Hint specifies optimizer-related configurations or system variables at the query level.

### Syntax

```sql
/*+ OPT_PARAM ( parameter_name [,] parameter_value ) */
```

### Parameter

* `parameter_name`: the name of the configuration or system variable.

* `parameter_value`: the value of the variable.

The `OPT_PARAM` Hint is effective for the following parameters:

* `rowsets_enabled`: specifies whether to enable or disable vectorization. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `rowsets_max_rows`: specifies the batch size of the number of rows to return. The data type is `INT`, and the value ranges from 0 to 65535. The value must not be enclosed in single quotation marks (' ').

* `enable_newsort`: specifies whether to enable or disable the newsort optimization. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `use_part_sort_mgb`: specifies whether to enable or disable the part sort merge group by. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `enable_in_range_optimization`: specifies whether to enable or disable the IN optimization. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `xsolapi_generate_with_clause`: specifies whether to enable or disable the CTE extraction rewrite. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `preserve_order_for_pagination`: specifies whether to add the `order by` clause for pagination queries. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `storage_card_estimation`: specifies whether to use the storage layer for row estimation. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `workarea_size_policy`: specifies the strategy for manually or automatically adjusting the SQL work area size. The data type is `VARCHAR`, and the value can be `'MANUAL'` for manual adjustment or `'AUTO'` for automatic adjustment. The value must be enclosed in single quotation marks (' ').

* `enable_rich_vector_format`: specifies whether to enable or disable vectorization 2.0 (session-level parameter). The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `spill_compression_codec`: specifies the compression algorithm for operators that need to be temporarily materialized. The data type is `VARCHAR`, and the value can be `NONE`, `LZ4`, `SNAPPY`, `ZLIB`, or `ZSTD`, representing different compression algorithms. The default value is `NONE`, indicating no compression.

* `inlist_rewrite_threshold`: specifies the threshold for triggering the rewrite of `inlist` to a `values statement`. The data type is `INT64`, and the value ranges from 1 to 2147483647.

* `orc_filter_pushdown_level`: specifies the level of ORC external table condition pushdown at the statement level. The `parameter_value` can be set to the following values:

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>parameter_name</code> parameter in the <code>OPT_PARAM</code> Hint of OceanBase Database supports the <code>orc_filter_pushdown_level</code> value starting from V4.4.0. </p>
    </main>

  * `0`: disables filter condition pushdown.
  * `1`: pushes down to the file level.
  * `2`: pushes down to the stripe level.
  * `3`: pushes down to the row index level.
  * `4`: pushes down to the encoding level.

* `parquet_filter_pushdown_level`: specifies the level of Parquet external table condition pushdown at the statement level. The `parameter_value` can be set to the following values:

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>parameter_name</code> parameter in the <code>OPT_PARAM</code> Hint of OceanBase Database supports the <code>parquet_filter_pushdown_level</code> value starting from V4.4.0. </p>
    </main>

  * `0`: disables filter condition pushdown.
  * `1`: pushes down to the file level.
  * `2`: pushes down to the RowGroup level.
  * `3`: pushes down to the page level.
  * `4`: pushes down to the encoding level.

### Example

The following example uses the `OPT_PARAM` Hint to specify the `enable_in_range_optimization` value to enable the IN optimization for the current query.

```shell
SELECT /*+ opt_param('enable_in_range_optimization', 'true') */ *
from t1
where c1 in (1,2,3,4,5,...,1000)
and c2 in (1,2,3,4,5,...,1000);
```

## `PARALLEL` Hint

When used as a global hint, the `PARALLEL` Hint specifies the parallelism or parallelism strategy for the current query.

In addition to being a global hint, the `PARALLEL` Hint can also be used as a query block hint to specify the parallelism at the table level. For more information, see the `Parallel` hint in [Access Path Hints](../200.optimizer-hint-of-oracle-mode/100.the-hint-related-to-the-access-path-of-oracle-mode.md).

### Syntax

```sql
/*+ PARALLEL ( AUTO | MANUAL | parallel_degree) */
```

### Parameter

- `AUTO` or `MANUAL`: when `AUTO` or `MANUAL` is used as the parameter in the `PARALLEL` Hint, it specifies the parallelism strategy. For more information, see [Parallelism strategies and priorities](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/500.parallel-execution.md).

- `parallel_degree`: when `parallel_degree` is used as the parameter in the `PARALLEL` Hint, it directly specifies the parallelism.

### Example

The following example uses the `PARALLEL` Hint to specify a parallelism of DOP = 8 or to enable Auto DOP.

```sql
SELECT /*+parallel(8)*/ c1, SUM(distinct c2) FROM t1 GROUP BY c1;

SELECT /*+parallel(auto)*/ c1, SUM(distinct c2) FROM t1 GROUP BY c1;
```

> Note: Some scenarios do not support parallel execution. Even if you specify the PARALLEL hint to enable parallel execution, the execution plan may still disable parallel execution.

## `STAT` Hint

The `STAT` hint specifies the operators in the query plan to be traced.

After adding the `STAT` hint, the query plan will include a `MONITORING DUMP` operator. This operator outputs all data from the sort operator and prints the operator's execution time, number of output rows, and other information in the observer log after execution.

## `TRANS_PARAM` Hint

The `TRANS_PARAM` hint specifies transaction-related parameters at the query level.

### Syntax

```sql
/*+ TRANS_PARAM ['FORCE_EARLY_LOCK_FREE' , 'TRUE'] */
```

### Parameter

Currently, only the `FORCE_EARLY_LOCK_FREE` parameter is supported, which specifies whether to enable early row lock release at the transaction level.

- `FORCE_EARLY_LOCK_FREE`: specifies whether to enable early row lock release at the transaction level. The value **TRUE** indicates that early row lock release is enabled, and **FALSE** indicates that it is disabled.

**Notice**: The parameter name and value must be enclosed in single quotation marks ( ' '). If the value is a number, you can omit the quotation marks.

### Example

```sql
-- Use the TRANS_PARAM hint and set the parameter 'FORCE_EARLY_LOCK_FREE' to 'TRUE' to enable early row lock release at the transaction level.
SELECT /*+ TRANS_PARAM('FORCE_EARLY_LOCK_FREE' 'TRUE') */ *
FROM employees e
WHERE e.department_id = 1001;
```

## `TRACING` Hint

The `TRACING` hint specifies the operators in the query plan to be traced.

The usage of the `TRACING` hint, the changes in the query plan after adding the hint, and the behavior when using the `STAT` hint are the same.

The difference between using the `TRACING` hint and the `STAT` hint is that when using the `TRACING` hint, the `MONITORING DUMP` operator prints all its output data in the observer log.

### Syntax

```sql
/*+ TRACING(TRACING_NUM_LIST)*/
```

### Parameter

- `TRACING_NUM_LIST`: specifies the IDs of the operators to be traced.

### Example

```sql
-- Use the TRACING hint and set the level to 1 to enable tracing for the current query.
SELECT /*+ TRACING(1) */ *
FROM employees e
WHERE e.department_id = 1001;
```

## `USE_PLAN_CACHE` Hint

The `USE_PLAN_CACHE` hint specifies the plan cache strategy for the current query. For more information about the plan cache, see [Execution plan cache](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/200.sql-execution-plan/300.execution-plan-cache.md).

### Syntax

```sql
/*+ USE_PLAN_CACHE ( NONE | DEFAULT ) */
```

### Parameter

- `NONE`: specifies that the query does not use the plan cache.

- `DEFAULT`: specifies that the query uses the system variable [`ob_enable_plan_cache`](../../../../../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/7200.ob_enable_plan_cache-global.md) to control the plan cache strategy.

### Example

```sql
-- When the `NONE` parameter is used, the query does not use the plan cache. When the `DEFAULT` parameter is used, the query uses the system variable `ob_enable_plan_cache` to control the plan cache strategy.
SELECT /*+ USE_PLAN_CACHE(NONE) */ *
FROM employees e
WHERE e.department_id = 1001;

SELECT /*+ USE_PLAN_CACHE(DEFAULT) */ *
FROM employees e
WHERE e.department_id = 1001;
```

## `DISABLE_TRIGGER` Hint

The `DISABLE_TRIGGER` hint temporarily disables triggers during the execution of the current DML statement. It applies to `INSERT`, `UPDATE`, `DELETE`, and DML operations on views, including `INSTEAD OF` triggers.

### Syntax

```sql
/*+ disable_trigger */
/*+ disable_trigger ( trigger_name [, trigger_name ... ] ) */
```

### Parameter

`trigger_name`: an optional parameter that specifies the name of the trigger to temporarily disable. You can specify one or more trigger names, separated by commas. If you omit this parameter, all triggers involved in the query are disabled by default.

### Example

```sql
-- Disable only the trigger named tg_example.
INSERT /*+ disable_trigger(tg_example) */ INTO t1 VALUES (1, NULL);

-- Disable all triggers related to this DML statement.
INSERT /*+ disable_trigger */ INTO t1 VALUES (2, NULL);

-- UPDATE and DELETE statements
UPDATE /*+ disable_trigger */ t_upd SET b = b + 1 WHERE a = 2;
DELETE /*+ disable_trigger */ FROM t_del WHERE a = 2;

-- Specify multiple triggers.
INSERT /*+ disable_trigger(tg_a, tg_b) */ INTO mt_a VALUES (1, NULL);

-- INSTEAD OF trigger on a view.
INSERT /*+ disable_trigger(tg_vsrc) */ INTO v_vsrc VALUES (3, 30);
```
