## `DIRECT` Hint

The `DIRECT` hint enables direct load for `LOAD DATA` and `INSERT` statements to improve the efficiency and performance of data import.

### Syntax

The syntax of the `DIRECT` hint is as follows:

```sql
/*+ DIRECT (/*+ direct(need_sort, max_errors_allowed, load_mode) */)*/
```

#### Parameters

- `need_sort`: specifies whether to sort the imported data. `true` indicates that sorting is required. `false` indicates that sorting is not required.

- `max_errors_allowed`: specifies the maximum number of error rows allowed. If this number is exceeded, the import process will fail.

- `load_mode`: specifies the import mode. Valid values are as follows:

  + `full`: the default value, indicating a full import.
  + `inc`: indicating an incremental import, which supports the `INSERT` and `IGNORE` semantics.
  + `inc_replace`: indicating an incremental import, which does not check for duplicate primary keys, equivalent to the `REPLACE` semantics of incremental import.

### Examples

#### Example in `LOAD DATA` statement

**Enable incremental direct load**

```sql
LOAD DATA /*+ DIRECT(true, 0, inc) */
INFILE 'datafile.txt'
INTO TABLE mytable
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\n';
```

In this example, `DIRECT(true, 0, inc)` indicates that incremental direct load is enabled, data is sorted, and up to 0 error rows are allowed.

**Enable full direct load**

```sql
LOAD DATA
/*+ PARALLEL(4) DIRECT(true, 0, full) */
REMOTE_OSS INFILE 'oss://example.com/datafile.csv'
INTO TABLE my_table
FIELDS TERMINATED BY ',' ENCLOSED BY '"'
LINES TERMINATED BY '\n';
```

In this example, `PARALLEL(4)` specifies a parallelism of 4, and `DIRECT(true, 0, full)` indicates that full direct load is enabled, data is sorted, and up to 0 error rows are allowed.

For more information, see [Direct load](../../../../../../../../../620.obap/300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

#### Example in `INSERT INTO SELECT` statement

To enable direct load in the `INSERT INTO SELECT` statement, you must use the `enable_parallel_dml` option. The format is: `/*+ direct(bool, int, load_mode) enable_parallel_dml PARALLEL(N) */`.

**Enable incremental direct load**

```sql
-- Enable incremental direct load and parallel DML to incrementally import data from old_table to new_table
INSERT /*+ direct(true, 0, 'inc') enable_parallel_dml PARALLEL(4) */ INTO new_table (id, name, value)
SELECT id, name, value
FROM old_table;
```

In this example, `direct(true, 0, 'inc')` enables incremental direct load, sorts the data, and allows up to 0 error rows. `enable_parallel_dml` enables parallel DML. `PARALLEL(4)` sets the parallelism to 4.

**Enable full direct load**

```sql
-- Enable full direct load and parallel DML to import data from old_table to new_table.
INSERT /*+ direct(true, 0, 'full') enable_parallel_dml PARALLEL(4) */ INTO new_table (id, name, value)
SELECT id, name, value
FROM old_table;
```

In this example, `direct(true, 0, 'full')` enables full direct load, sorts the data, and allows up to 0 error rows. `enable_parallel_dml` enables parallel DML. `PARALLEL(4)` sets the parallelism to 4.

For more information, see [Use the `INSERT INTO SELECT` statement to perform direct load](../../../../../../../../../620.obap/300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

## `NO_DIRECT` Hint

The `NO_DIRECT` hint disables the direct load feature in `LOAD DATA`, `INSERT INTO SELECT`, and `CREATE TABLE AS SELECT` statements.

### Syntax

The syntax of the `NO_DIRECT` hint is as follows:

```sql
/*+ NO_DIRECT */
```

### Parameters

`NO_DIRECT`: specifies to force a single SQL statement to not use direct load. If the SQL statement contains this hint, it will ignore other direct load hints and execute a regular import.

### Examples

* **Use the NO_DIRECT hint in a LOAD DATA statement**

  ```sql
  LOAD DATA /*+ NO_DIRECT */ [REMOTE_OSS | LOCAL] INFILE 'file_name' INTO TABLE table_name [COMPRESSION]...
  ```

* **Use the NO_DIRECT hint in an INSERT INTO SELECT statement**

  ```sql
  INSERT /*+ NO_DIRECT */ INTO  table_name select_sentence
  ```

* **Use the NO_DIRECT hint in a CREATE TABLE AS SELECT statement**

  ```sql
  CREATE /*+ NO_DIRECT */ TABLE table_name [AS] select_sentence
  ```

## `USE_PX` Hint

`USE_PX` Hint forces the server to execute an SQL statement in parallel execution (PX) mode. PX mode allows SQL statements to be executed using multiple threads, thereby improving query performance. Typically, the `USE_PX` Hint is used together with the `PARALLEL` Hint to specify the number of threads for parallel execution. By default, the system uses the `USE_PX` Hint.

### Syntax

The syntax of the `USE_PX` Hint is as follows:

```sql
/*+ USE_PX */
```

### Examples

The following example shows how to use the `USE_PX` Hint.

```sql
SELECT /*+ USE_PX PARALLEL(4)*/ e.dept_id, sum(e.salary)
FROM emp e
WHERE e.dept_id = 1001 GROUP BY e.dept_id;
```

## `ENABLE_PARALLEL_DML` Hint

`ENABLE_PARALLEL_DML` Hint specifies that the current query enables parallel DML. Its reverse hint is `DISABLE_PARALLEL_DML`, which is used to disable parallel DML.

For more information, see [Parallel DML](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/1000.parallel-dml.md).

### Considerations

- When you use `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/`, the system prioritizes distributed parallel DML (PDML). If the current environment does not support PDML, the system falls back to DAS concurrent write for performance optimization.

- If a session-level forced parallelism is set, its execution behavior will be consistent with the above behavior.

- Even if the current environment does not support parallel DML (PDML), if the system parameter `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` command (its default value is `false`), the system will not enable DAS (Distributed Active Storage) parallel write operations, even if the `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used.

- If `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` command (default is `false`) and a session-level forced parallelism is already set, using the `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/` hint will not enable DAS parallel write functionality, even if the current environment does not support PDML.

### Syntax

```sql
/*+ ENABLE_PARALLEL_DML */
```

### Examples

```sql
insert /*+ enable_parallel_dml parallel(8) */ into t2 select * from t1;
```

## `DISABLE_PARALLEL_DML` Hint

`DISABLE_PARALLEL_DML` Hint specifies that the current query disables parallel DML. Its reverse hint is `ENABLE_PARALLEL_DML`, which is used to enable parallel DML.

For more information, see [Parallel DML](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/1000.parallel-dml.md).

### Syntax

```sql
/*+ DISABLE_PARALLEL_DML */
```

### Examples

```sql

```

## `ENABLE_PARALLEL_DAS_DML` Hint

`ENABLE_PARALLEL_DAS_DML` Hint specifies that the current DML statement forces the use of Distributed Data Access Service (DAS) concurrent write optimization. Its reverse hint is `DISABLE_PARALLEL_DAS_DML`.

### Considerations

- `ENABLE_PARALLEL_DAS_DML` must be used together with `ENABLE_PARALLEL_DML`.

- When the hint `/*+ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` is used, the system treats DAS concurrent write as a forced option and executes the operation based on the parallelism specified by `PARALLEL(n)`.

- If the system parameter `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` statement (default is `false`), the hint `/*+ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` becomes invalid. In this case, the system will not execute DAS parallel write operations.

### Syntax

```sql
/*+ ENABLE_PARALLEL_DAS_DML */
```

### Examples

```sql
insert /*+ ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(10)*/
into t1 select * from t2;
```

## `DISABLE_PARALLEL_DAS_DML` Hint

`DISABLE_PARALLEL_DAS_DML` Hint specifies that the current DML statement forces the use of Distributed Data Access Service (DAS) concurrent write optimization. Its reverse hint is `ENABLE_PARALLEL_DAS_DML`.

## Materialized view query rewrite hint

Materialized view query rewrite control includes the `MV_REWRITE` and `NO_MV_REWRITE` hints, which have a higher priority than the system variable `query_rewrite_enabled`.

### `MV_REWRITE` Hint

The syntax of the `MV_REWRITE` hint is as follows:

```sql
/*+ MV_REWRITE (@ queryblock [mv_name_list]) */

mv_name_list:
    mv_name [, mv_name ...]
```

When you use the `MV_REWRITE` hint alone, it skips the rules and cost checks for materialized view query rewrite and directly uses the applicable rewrite. If you specify one or more materialized views after the hint, it skips the rules and cost checks and only uses the specified materialized views for rewrite, ignoring all unspecified materialized views.

When you use the `MV_REWRITE` hint to specify materialized views, you cannot force the use of materialized views without the `ENABLE QUERY REWRITE` clause. Additionally, you cannot force the use of non-real-time materialized views when the system variable `query_rewrite_integrity` is set to `enforced`.

### `NO_MV_REWRITE` Hint

The syntax of the `NO_MV_REWRITE` hint is as follows:

```sql
/*+ NO_MV_REWRITE (@ queryblock) */
```

The `NO_MV_REWRITE` hint disables materialized view query rewrite and allows you to specify a query block.

### Example of using materialized view query rewrite control hints

1. Create the base table `tbl2`.

   ```sql
   CREATE TABLE tbl2 (col1 INT, col2 INT);
   ```

2. Insert two rows of data into the base table `tbl2`.

   ```sql
   INSERT INTO tbl2 VALUES (1,2),(3,4);
   ```

   The return result is as follows:

   ```shell
   Query OK, 2 rows affected
   Records: 2  Duplicates: 0  Warnings: 0
   ```

3. Create the materialized view `mv1_tbl2` and enable query rewrite for it.

   ```sql
   CREATE MATERIALIZED VIEW mv1_tbl2 NEVER REFRESH ENABLE QUERY REWRITE AS SELECT * FROM tbl2;
   ```

4. Create the materialized view `mv2_tbl2` and enable query rewrite for it.

   ```sql
   CREATE MATERIALIZED VIEW mv2_tbl2 NEVER REFRESH ENABLE QUERY REWRITE AS SELECT * FROM tbl2 WHERE tbl2.col1 > 1;
   ```

5. Set the system variable `query_rewrite_integrity` to `stale_tolerated`.

    <main id="notice" type='explain'>

## `NO_PARALLEL` Hint

The `NO_PARALLEL` hint disables query parallelism (i.e., sets the parallelism to 1). Its opposite hint is `PARALLEL`.

The `NO_PARALLEL` hint is equivalent to `/*+ parallel(1)*/`.

### Syntax

```sql
/*+ NO_PARALLEL */
```

### Example

The following query example uses the `NO_PARALLEL` hint to disable query parallelism.

```sql
SELECT /*+ no_parallel */ c1, sum(distinct c2) FROM t1 GROUP BY c1;
```

## `NO_QUERY_TRANSFORMATION` Hint

The `NO_QUERY_TRANSFORMATION` hint disables any query rewrite for the current query.

Note that unlike the `NO_REWRITE` hint in Query Block hints, using `NO_QUERY_TRANSFORMATION` prevents the use of Query Block hints to enable certain rewrites.

For more information about query rewrite, see [Overview of query rewrite](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/500.query-rewrite/100.query-rewrite-overview.md).

### Syntax

```sql
/*+ NO_QUERY_TRANSFORMATION */
```

### Example

The following query example uses the `NO_QUERY_TRANSFORMATION` hint to disable any query rewrite.

```sql
SELECT /*+ NO_QUERY_TRANSFORMATION */ *
FROM (SELECT * FROM t1) v WHERE v.c1 = 3;
```

## `OPT_PARAM` Hint

`OPT_PARAM` Hint specifies some optimizer-related configurations or system variables at the query level.

### Syntax

```sql
/*+ OPT_PARAM ( parameter_name [,] parameter_value ) */
```

#### Parameters

* `parameter_name`: the name of a configuration or system variable.

* `parameter_value`: the value to be specified for the variable.

The `OPT_PARAM` Hint is effective for the following parameters:

* `rowsets_enabled`: specifies whether to enable or disable vectorization. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `rowsets_max_rows`: specifies the batch size `batch_size` for returning rows. The data type is `INT`, and the value can be in the range [0, 65535]. The value must not be enclosed in single quotation marks (' ').

* `enable_newsort`: specifies whether to enable or disable the newsort optimization in queries. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `use_part_sort_mgb`: specifies whether to enable or disable the part sort merge group by in queries. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `enable_in_range_optimization`: specifies whether to enable or disable the IN optimization in queries. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `xsolapi_generate_with_clause`: specifies whether to enable or disable the CTE extraction rewrite in queries. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `preserve_order_for_pagination`: specifies whether to add an `order by` clause for pagination queries. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `storage_card_estimation`: specifies whether to use the row estimation of the storage layer. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `workarea_size_policy`: specifies the strategy for manually or automatically adjusting the SQL work area size. The data type is `VARCHAR`, and the value can be `'MANUAL'` for manual adjustment or `'AUTO'` for automatic adjustment. The value must be enclosed in single quotation marks (' ').

* `enable_rich_vector_format`: specifies whether to enable or disable vectorization 2.0 (session-level parameter). The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `spill_compression_codec`: specifies the compression algorithm for operators that need to be temporarily materialized. The data type is `VARCHAR`, and the value can be `NONE`, `LZ4`, `SNAPPY`, `ZLIB`, or `ZSTD`, representing different compression algorithms. The default value is `NONE`, indicating no compression.

* `inlist_rewrite_threshold`: specifies the maximum number of constants that can trigger the rewrite of `inlist` to a `values statement`. The data type is `INT64`, and the value can be in the range [1, 2147483647].

* `orc_filter_pushdown_level`: specifies the level at which to push down filter conditions for ORC external tables at the statement level. The value of `parameter_value` can be:

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>parameter_name</code> parameter of the <code>OPT_PARAM</code> Hint in OceanBase Database supports the <code>orc_filter_pushdown_level</code> value starting from V4.4.0. </p>
    </main>

  * `0`: disables filter condition pushing down.
  * `1`: pushes down filter conditions to the file level.
  * `2`: pushes down filter conditions to the stripe level.
  * `3`: pushes down filter conditions to the row index level.
  * `4`: pushes down filter conditions to the encoding level.

* `parquet_filter_pushdown_level`: specifies the level at which to push down filter conditions for Parquet external tables at the statement level. The value of `parameter_value` can be:

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>parameter_name</code> parameter of the <code>OPT_PARAM</code> Hint in OceanBase Database supports the <code>parquet_filter_pushdown_level</code> value starting from V4.4.0. </p>
    </main>

  * `0`: disables filter condition pushing down.
  * `1`: pushes down filter conditions to the file level.
  * `2`: pushes down filter conditions to the RowGroup level.
  * `3`: pushes down filter conditions to the page level.
  * `4`: pushes down filter conditions to the encoding level.

### Examples

The following example uses the `OPT_PARAM` Hint to enable the IN optimization for the current query by specifying the `enable_in_range_optimization` value.

```shell
SELECT /*+ opt_param('enable_in_range_optimization', 'true') */ *
from t1
where c1 in (1,2,3,4,5,...,1000)
and c2 in (1,2,3,4,5,...,1000);
```

## `PARALLEL` Hint

When used as a global hint, the `PARALLEL` Hint specifies the parallelism or parallelism strategy for the current query.

In addition to being a global hint, the `PARALLEL` Hint can also be used as a query block hint to specify the parallelism at the table level. For more information, see the `Parallel` hint section in [Access Path Hints](../200.optimizer-hint-of-oracle-mode/100.the-hint-related-to-the-access-path-of-oracle-mode.md).

### Syntax

```sql
/*+ PARALLEL ( AUTO | MANUAL | parallel_degree) */
```

#### Parameters

- `AUTO` or `MANUAL`: when used as a parameter in the `PARALLEL` Hint, `AUTO` or `MANUAL` specifies the parallel execution strategy. For more information, see [Parallel execution strategies and priorities](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/500.parallel-execution.md).

- `parallel_degree`: when used as a parameter in the `PARALLEL` Hint, `parallel_degree` specifies the parallelism.

### Examples

The following example uses the `PARALLEL` Hint to specify a parallelism of DOP = 8 or to enable auto DOP.

```sql
SELECT /*+parallel(8)*/ c1, SUM(distinct c2) FROM t1 GROUP BY c1;

SELECT /*+parallel(auto)*/ c1, SUM(distinct c2) FROM t1 GROUP BY c1;
```

> Note: Some scenarios do not support parallel execution, even if you specify the PARALLEL hint to enable it. The execution plan may still disable parallel execution.

```sql
/*+ QUERY_TIMEOUT ( time_usec ) */
```

## `READ_CONSISTENCY` Hint

The `READ_CONSISTENCY` hint specifies the read consistency level for the current query.

### Syntax

```sql
/*+ READ_CONSISTENCY(WEAK[STRONG]) */
```

#### Parameter description

- `WEAK`: specifies to enable weak consistency, that is, weak reads.

- `STRONG`: specifies to enable strong consistency, that is, disable weak reads.

### Examples

```sql
-- Uses the READ_CONSISTENCY hint and sets it to WEAK to enable weak reads for the query.
SELECT /*+ READ_CONSISTENCY(WEAK) */ *
FROM employees
WHERE employees.department_id = 1001;
```

Weak reads are supported when the isolation level is set to Repeatable Read or Serializable. Example:

  ```sql
  obclient> SET transaction read only;
  Query OK, 0 rows affected (0.001 sec)
  obclient> SELECT /*+ read_consistency(weak)*/ * FROM t WHERE a=2;
  +------+------+
  | ID   | A    |
  +------+------+
  | NULL |    2 |
  +------+------+
  1 row in set (0.001 sec)
  ```

## `RESOURCE_GROUP` Hint

The `RESOURCE_GROUP` hint specifies the resource group for the current statement.

The syntax for the `RESOURCE_GROUP` hint is as follows:

```sql
/*+ RESOURCE_GROUP ('resource_group_name') */
```

## `STAT` Hint

The `STAT` hint specifies the operators whose output needs to be traced in the query plan.

After the `STAT` hint is added, the query plan contains a `MONITORING DUMP` operator. This operator directly outputs all data of the sort operator and prints the execution time and number of output rows of the operator in the observer log after the execution.

### Syntax

```sql
/*+ STAT(TRACING_NUM_LIST) */
```

#### Parameter description

- `TRACING_NUM_LIST`: specifies the IDs of the operators to be traced.

### Examples

```sql
-- Displays the query plan before and after adding the `/*+ STAT(0, 2) */` hint.
explain basic
SELECT /*+leading(t1) use_hash(t2)*/ * FROM t1, t2 WHERE t1.c1 = t2.c1;

Query Plan
===========================
|ID|OPERATOR         |NAME|
---------------------------
|0 |HASH JOIN        |    |
|1 |├─TABLE FULL SCAN|T1  |
|2 |└─TABLE FULL SCAN|T2  |
===========================

explain basic
SELECT /*+leading(t1) use_hash(t2) stat(0, 2)*/ *
FROM t1, t2 where t1.c1 = t2.c1;
Query Plan
===============================
|ID|OPERATOR             |NAME|
-------------------------------
|0 |MONITORING DUMP      |    |
|1 |└─HASH JOIN          |    |
|2 |  ├─TABLE FULL SCAN  |T1  |
|3 |  └─MONITORING DUMP  |    |
|4 |    └─TABLE FULL SCAN|T2  |
===============================
```

## `TRANS_PARAM` Hint

The `TRANS_PARAM` hint is used to specify transaction-related parameters at the query level.

### Syntax

```sql
/*+ TRANS_PARAM ['FORCE_EARLY_LOCK_FREE' , 'TRUE'] */
```

#### Parameter description

Currently, only the `FORCE_EARLY_LOCK_FREE` parameter is supported at the transaction level.

- `FORCE_EARLY_LOCK_FREE`: specifies whether to enable early row lock release. Valid values: **TRUE** (enables early row lock release) and **FALSE** (disables early row lock release).

**Notice**: The parameter name and value must be enclosed in single quotation marks ( ' '). If the value is a numeric value, you can omit the quotation marks.

### Examples

```sql
-- Uses the TRANS_PARAM hint and sets the parameter 'FORCE_EARLY_LOCK_FREE' to 'TRUE' to enable early row lock release at the transaction level.
SELECT /*+ TRANS_PARAM('FORCE_EARLY_LOCK_FREE' 'TRUE') */ *
FROM employees e
WHERE e.department_id = 1001;
```

## `TRACING` Hint

The `TRACING` hint specifies the operators whose output needs to be traced in the query plan.

The usage of the `TRACING` hint, the changes in the query plan after adding the hint, and the behavior when using the `STAT` hint are the same.

The difference between using the `TRACING` hint and the `STAT` hint is that when the `TRACING` hint is used, the `MONITORING DUMP` operator prints all of its output data in the observer log.

### Syntax

```sql
/*+ TRACING(TRACING_NUM_LIST)*/
```

#### Parameter description

- `TRACING_NUM_LIST`: specifies the IDs of the operators to be traced.

### Examples

```sql
-- Uses the TRACING hint and sets the level to 1 to enable tracing for the current query.
SELECT /*+ TRACING(1) */ *
FROM employees e
WHERE e.department_id = 1001;
```

## `USE_PLAN_CACHE` Hint

The `USE_PLAN_CACHE` hint specifies the plan cache strategy for the current query. For more information about plan cache, see [Execution plan cache](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/200.sql-execution-plan/300.execution-plan-cache.md).

### Syntax

```sql
/*+ USE_PLAN_CACHE ( NONE | DEFAULT ) */
```

#### Parameters

- `NONE`: specifies that the query does not use the plan cache.

- `DEFAULT`: specifies that the query uses the plan cache strategy controlled by the system variable [`ob_enable_plan_cache`](../../../../../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/7200.ob_enable_plan_cache-global.md).

### Examples

```sql
-- The query does not use the plan cache when the `NONE` parameter is specified. The query uses the plan cache strategy controlled by the system variable `ob_enable_plan_cache` when the `DEFAULT` parameter is specified.
SELECT /*+ USE_PLAN_CACHE(NONE) */ *
FROM employees e
WHERE e.department_id = 1001;

SELECT /*+ USE_PLAN_CACHE(DEFAULT) */ *
FROM employees e
WHERE e.department_id = 1001;
```
