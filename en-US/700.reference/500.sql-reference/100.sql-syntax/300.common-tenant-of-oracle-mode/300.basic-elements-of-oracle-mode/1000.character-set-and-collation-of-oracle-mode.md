# Character sets and collations

The following character sets are supported in the Oracle mode of OceanBase Database:

* binary

* utf8mb4

  <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>To ensure smooth migration, OceanBase Database treats <code>UTF8</code> as a synonym for <code>UTF8MB4</code> in syntax. </p>
    </main>

* gbk

* utf16

* gb18030

* latin1

* gb2312

* gb18030_2022

* ascii

* tis620

* ujis

* euckr

* eucjpms

* cp932

* utf16le

* sjis

* hkscs

* hkscs31

* dec8

* big5

  <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>big5</code> character set is compatible with the <code>big5</code> character set in MySQL. </p>
    </main>

* cp850

* hp8

* macroman

* swe7

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Starting from OceanBase Database V4.3.5 BP1, the following character sets are supported: <code>gb2312</code>, <code>ujis</code>, <code>euckr</code>, <code>eucjpms</code>, <code>cp932</code>, <code>cp850</code>, <code>hp8</code>, <code>macroman</code>, and <code>swe7</code>. </p>
</main>

OceanBase Database supports using a non-default character set for communication with a server. For example, after connecting to the server, you can run the following statement to use the `gbk` character set:

```shell
obclient> SET NAMES gbk;
Query OK, 0 rows affected
```

The default collation for character sets in OceanBase Database operating in Oracle mode is `bin`, but you can use the `NLSSORT()` function to specify a different collation.

```shell
obclient> CREATE TABLE t(a VARCHAR(10));
Query OK, 0 rows affected

obclient> INSERT INTO t VALUES ('a'),('A'),('b'),('B'),('闖'),('闯'),('门'),('醜'),('锌'),('陆'),('ζ');

Records: 11  Duplicates: 0  Warnings: 0

## Convert between GB18030 and GB18030_2022

Implicit conversion from `gb18030` to `gb18030_2022` is not supported in OceanBase Database versions before 1.1. However, you can use the `CONVERT` function to explicitly convert the encoding of a `gb18030` string to `gb18030_2022`. The conversion does not use Unicode and preserves the original encoding. Here is an example.

```shell
obclient> CREATE TABLE t1 (c1 VARCHAR(10));
Query OK, 0 rows affected

obclient> INSERT INTO t1 VALUES ('character');
Query OK, 1 row affected

obclient> SELECT RAWTOHEX(c1), RAWTOHEX(CONVERT(c1, 'ZHS32GB18030_2022')) FROM t1;
+--------------+-------------------------------------------+
| RAWTOHEX(C1) | RAWTOHEX(CONVERT(C1,'ZHS32GB18030_2022')) |
+--------------+-------------------------------------------+
| D7D6         | D7D6                                      |
+--------------+-------------------------------------------+
1 row in set
```

In the Oracle mode of OceanBase Database, the character set of each user table is specified at the tenant level. In a tenant using the `gb18030_2022` character set, all `CHAR`, `VARCHAR2`, and `CLOB` columns use the `gb18030_2022` character set and are collated by using the `gb18030_2022_bin` collation. In Oracle mode, string literals are resolved to the tenant character set to make the character set of SQL statements uniform.

```shell
/* Character set of column c in the gb18030_2022 tenant is gb18030_2022, and collation is gb18030_2022_bin. */
obclient> CREATE TABLE t1(c VARCHAR(100));
Query OK, 0 rows affected

obclient> INSERT INTO t1 values('character');
Query OK, 1 row affected

/* Set the character set of the client to GB18030. */
obclient> SET NAMES gb18030;
Query OK, 0 rows affected

The procedure can be used in scenarios where the statistics are no longer useful or when the statistics are taking up too much storage space.
