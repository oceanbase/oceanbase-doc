# LOB types

Large object (LOB) types are used to store TEXT, binary large object (BLOB), JavaScript Object Notation (JSON), and GEOMETRY data.
LOB data can be stored in INROW or OUTROW storage mode.

## INROW storage

When INROW storage is used, LOB data is stored together with rows in the primary table. Only one access to storage is required to read LOB data.

## OUTROW storage

When OUTROW storage is used, LOB data is stored in an LOB auxiliary table. To read LOB data, the database first obtains locators of the data by reading rows in the primary table and then reads actual LOB data from the LOB auxiliary table based on the locators. The whole process involves two accesses to the storage.

## LOB types

The common LOB types in Oracle mode are described as follows:

* **BLOB**: stores large files such as images, files, and audios.
- **CLOB**: stores single-byte and multi-byte character data.
- **JSON**: stores data in the JSON format. It is commonly used to process structured data.
- **SDO_GEOMETRY**: stores and processes geometric data. It is a composite data type used to represent a two-dimensional or three-dimensional geometric figure.
- **XMLType**: stores data in the XML format. It can facilitate the processing and query of XML files.

<main id="notice" type='explain'>
<h4>Note</h4>
<p>XMLType differs from conventional LOB types in some aspects. It is actually a user-defined type (UDT) that contains a BLOB field. </p>
</main>

## LOB Consistency Check

When external storage is used, the main table and LOB auxiliary table are associated through LOB IDs: the set of LOB IDs in the main table's locator should be consistent with the set of LOB IDs in the LOB auxiliary table. Inconsistencies such as "present in the main table but not in the auxiliary table" or "present in the auxiliary table but not in the main table" can lead to issues like read exceptions or inability to reclaim space.

This feature uses a LOB check task (LOB Task) to scan the main table and collect the set of LOB IDs, then compares it with the set of LOB IDs obtained from scanning the LOB auxiliary table, outputting whether they are consistent and any discrepancies. This helps in routine inspections during off-peak hours or in troubleshooting to confirm normal data relationships.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The commands in this section must be executed in the sys tenant. </p>
</main>

### How to use with resource groups and I/O benchmarks

LOB consistency checks involve scanning the main table and LOB auxiliary table, which can be resource-intensive for I/O and CPU. When setting limits for the check task, such as I/O caps, it relies on the tenant-side disk I/O benchmark, which is generated through I/O calibration. Recommendations vary based on the deployment type:

* In environments like public clouds where I/O calibration is already completed by default: Typically, you can directly configure resource management plans and resource groups within the tenant.
* In private clouds or environments where I/O calibration has not been performed: First, perform disk I/O calibration in the sys tenant. Then, based on the benchmark, plan the `MAX_IOPS` and `MIN_IOPS` for business tenants, and pair these with the I/O limits in the resource group. For details on calibration commands, progress tracking, and resource isolation for background tasks, see [Resource isolation for background tasks](../../../../../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/400.background-resource-isolation-of-mysql-or-oracle-mode.md). For steps on disk performance calibration, see [Disk performance calibration](../../../../../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/200.resource-isolation-of-oracle-mode/150.disk-performance-calibration-of-oracle-mode.md).

### Complete example

Before using the consistency check feature, you need to perform I/O calibration, create a dedicated resource plan for LOB checks, and configure the resource management plan and resource group.

#### Step 1: I/O calibration (optional)

If I/O calibration has not been performed, execute it in the sys tenant. It may take 1-2 minutes for the calibration to take effect.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The commands in this section must be executed in the sys tenant. </p>
</main>

```sql
ALTER SYSTEM RUN JOB 'io_calibration';
```

After calibration, you can view the calibration task status in [GV$OB_IO_CALIBRATION_STATUS](../../../../../../700.system-views/300.system-view-of-sys-tenant/300.performance-view-of-sys-tenant/1100.gv-ob_io_calibration_status-of-sys-tenant.md) and the IOPS benchmark for each node in [GV$OB_IO_BENCHMARK](../../../../../../700.system-views/300.system-view-of-sys-tenant/300.performance-view-of-sys-tenant/1000.gv-ob_io_benchmark-of-sys-tenant.md). When configuring unit IOPS for a tenant, it is recommended to reserve about 10% of the benchmark (e.g., IOPS corresponding to 16 KB read) to avoid disk full issues affecting online business latency.

```sql
SELECT * FROM GV$OB_IO_CALIBRATION_STATUS;
SELECT * FROM GV$OB_IO_BENCHMARK;
```

#### Step 2: Create a dedicated resource plan for LOB checks

In the business tenant where the check needs to be run, create a dedicated resource plan, map LOB check-related background tasks to a dedicated resource group, and limit CPU and IOPS. In the following example, the plan name is `LOB_CHECK`, the resource group name is `LOB_CHECK`, and the `FUNCTION` mapping maps background tasks with the value `LOB_CHECK` to this group. Adjust `MGMT_P1`, `UTILIZATION_LIMIT`, `MAX_IOPS`, `MIN_IOPS`, and `WEIGHT_IOPS` as needed based on your specifications.

```sql
BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN('LOB_CHECK', 'plan for lob_check'); END; /
BEGIN DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP('LOB_CHECK', 'LOB_CHECK'); END; /
BEGIN
  DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
    PLAN => 'LOB_CHECK',
    GROUP_OR_SUBPLAN => 'LOB_CHECK',
    COMMENT => 'LOB_CHECK_GROUP',
    MGMT_P1 => 30,
    UTILIZATION_LIMIT => 30,
    MAX_IOPS => 20,
    MIN_IOPS => 0,
    WEIGHT_IOPS => 20);
END;
/
BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING('FUNCTION', 'LOB_CHECK', 'LOB_CHECK'); END; /
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Unlike the common <code>CALL DBMS_RESOURCE_MANAGER.*</code> syntax in MySQL mode, tenants in Oracle mode typically use <code>BEGIN ... END;</code> anonymous blocks to call resource management procedures. </p>
</main>

After activating the resource management plan, the mapping and limits will take effect for sessions and background tasks:

```sql
SET GLOBAL resource_manager_plan = 'LOB_CHECK';
```

For more information about `resource_manager_plan` and its considerations, see [resource_manager_plan](../../../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/11500.resource_manager_plan-global.md).

For more information about the `DBMS_RESOURCE_MANAGER` procedures, parameters, and privileges, see [DBMS_RESOURCE_MANAGER Overview](../../../../../../600.pl-reference/300.pl-oracle/1400.pl-system-package-oracle/13300.dbms-resource-manager-oracle/100.dbms-resource-manager-overview-oracle.md) and [Configure resource isolation within a tenant (Oracle mode)](../../../../../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/200.resource-isolation-of-oracle-mode/200.resource-isolation-at-user-level-of-oracle-mode.md).

#### Step 3: Configure a scheduled task (optional)

If you want to run the LOB consistency check regularly, you can manually enable the scheduled task. By default, it will trigger at 4:00 AM on Sunday mornings.

```sql
-- Enable the task
CALL DBMS_SCHEDULER.ENABLE('lob_check_job');
-- Disable the task
CALL DBMS_SCHEDULER.DISABLE('lob_check_job');
-- Modify the task's trigger cycle and start time
CALL DBMS_LOB_MANAGER.RESCHEDULE_JOB('2025-12-01 17:48:00', 'FREQ=DAILY; INTERVAL=1');
```

To view the scheduling task information:

```sql
SELECT * FROM DBA_SCHEDULER_JOBS WHERE job_name='lob_check_job';
```

#### Step 4: Run the LOB consistency check

```sql
-- Trigger a consistency check for all data tables with LOB auxiliary tables in the current tenant
CALL DBMS_LOB_MANAGER.CHECK_LOB();

-- Trigger a consistency check for tables with the specified table_id
CALL DBMS_LOB_MANAGER.CHECK_LOB('[500001, 500003]');

-- Task control (only for check tasks)
CALL DBMS_LOB_MANAGER.CANCEL_JOB('check_lob');
CALL DBMS_LOB_MANAGER.SUSPEND_JOB('check_lob');
CALL DBMS_LOB_MANAGER.RESUME_JOB('check_lob');
```

#### Step 5: View the LOB consistency check results

Use `DBA_OB_LOB_CHECK_TASKS` to view the progress of the LOB check task and `DBA_OB_LOB_CHECK_EXCEPTION_RESULT` to view the exception results.

```sql
SELECT * FROM DBA_OB_LOB_CHECK_TASKS;
SELECT * FROM DBA_OB_LOB_CHECK_EXCEPTION_RESULT;
```
