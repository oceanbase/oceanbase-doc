# CREATE TABLE

## Purpose

You can use this statement to create a table in the database.

## Syntax

```sql

      (table_definition_list) [table_option_list] [partition_option] [on_commit_option]
```

### table_mode_value

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Among the listed table modes, except the <code>NORMAL</code> mode, all other modes represent <code>QUEUING</code> tables. <code>QUEUING</code> tables are the most basic type of tables. Except the NORMAL mode, other table modes indicate more proactive major compaction strategies. </p>
</main>

* `NORMAL`: In this mode, the probability of triggering a major compaction after a minor compaction is extremely low. This is the default value.
* `QUEUING`: In this mode, the probability of triggering a major compaction after a minor compaction is low.
* `MODERATE`: In this mode, the probability of triggering a major compaction after a minor compaction is moderate.
* `SUPER`: In this mode, the probability of triggering a major compaction after a minor compaction is high.
* `EXTREME`: In this mode, the probability of triggering a major compaction after a minor compaction is very high.

For more information about major compactions, see [Adaptive major compactions](../../../../../200.system-management/500.manage-data-storage/200.merge-management/320.adaptive-compaction.md).

## Limitations on GTTs in Oracle mode

* With basic data correctness and functionality guarantees, GTTs in the Oracle mode of OceanBase Database are used in a lot of business scenarios.
* Generally, GTTs are used for compatibility purposes with less business construction. You can use GTTs in limited business scenarios with lower performance requirements. If the business scenarios support normal tables, we recommend that you use normal tables.

### Performance and stability

* The SQL execution efficiency of GTTs is basically the same as that of normal tables.
* However, GTTs require data cleanup after a transaction ends or a session is disconnected, which causes additional overhead.
* Check and cleanup operations on GTTs during login may cause pressure on the login thread, resulting in longer login time, and in severe cases even a login failure.

### Create a GTT

When you use a statement to create a GTT, the statement is rewritten as follows by default:

* The `SYS_SESSION_ID` column is added as the primary key.
* The `SYS_SESS_CREATE_TIME` column is added as a normal column.
* A HASH-partitioned table is created, with `SYS_SESSION_ID` being the partitioning key and a fixed number of 16 partitions.

Here is an example:

```shell
CREATE GLOBAL TEMPORARY TABLE t1(
  c1 INT,
  c2 INT,
  PRIMARY KEY(c1)
);
```

The statement will be rewritten as follows:

```shell
CREATE GLOBAL TEMPORARY TABLE t1(
  SYS_SESSION_ID INT,
  SYS_SESS_CREATE_TIME INT,
  c1 INT,
  c2 INT,
  PRIMARY KEY(SYS_SESSION_ID, c1)
)
PARTITION BY HASH(SYS_SESSION_ID) PARTITIONS 16;
```

### DML/Query statements on GTTs

When the database executes an `INSERT` statement, the session ID and session creation time of the current session are respectively inserted into the `SYS_SESSION_ID` and `SYS_SESS_CREATE_TIME` columns by default.

When the database executes an `UPDATE`, `DELETE`, or `SELECT` statement that involves a GTT, the filter condition `SYS_SESSION_ID = session_id of the current session` is added by default to the statement. By using this filter condition, the SQL optimizer can perform partition pruning and extract the query range.

### Data cleanup for GTTs

* For a GTT with the `ON COMMIT DELETE ROWS` option (which is the default option that indicates a transaction-level GTT), when the transaction ends, a new transaction is started and the `DELETE` statement is executed to clean up data in the GTT.
* For a GTT with the `ON COMMIT PRESERVE ROWS` option (which indicates a session-level GTT), when the session is disconnected, the `DELETE` statement is executed to clean up data in the GTT.
* Session IDs may be reused. In OceanBase Database V3.2.4 BP4 and earlier versions, data of the current session ID is checked during login. If the data exists, an additional cleanup is performed.
* Login check and cleanup performed due to a session ID conflict may cause a fault, resulting in a cluster login failure.

### Routing for GTTs

* Transaction-level GTTs (`ON COMMIT DELETE ROWS`)
  Access to a GTT within a transaction can only be routed to the node that starts the transaction.

* Session-level GTTs (`ON COMMIT PRESERVE ROWS`)
  After a session accesses a GTT, the OBServer node instructs the ODP to forward subsequent requests only to the current session.

### Drop a GTT

You can drop a GTT during the execution of DML statements, which is the same as dropping a normal table. Then, all data is deleted from the GTT. However, Oracle databases allow you to drop a GTT only after all sessions do not hold the GTT.

### Feature support by different OceanBase Database versions

| Feature | Supported in V3.2.4 BP4 and earlier | Supported in V3.2.4 BP5 and later V3.2.x versions | Supported in V4.2.0 |
|---|---|---|---|
| Plan sharing among sessions | No| No| Yes|
| Login without triggering checks and cleanup | No| Yes| Yes|
|`MERGE INTO`| No| No |Yes|

### Workaround for serious issues

### Login failure

1. Stop all business related to GTTs, and drop GTTs or perform a major compaction. Generally, the fault is cleared automatically. If the fault persists, go to step 2.
2. Restart the OBServer node that you cannot log in to.

### PL cache bloat due to a plan reuse failure

For example, a PL procedure is defined with statements that use a GTT.

```shell
CREATE PROCEDUCE p1 () (
  INSERT INTO temp_table VALUES (xxx);
  SELECT * FROM temp_table WHERE ROWNUM = 1 INTO var1;
);
```

Different sessions cannot share the plans for the access to GTTs. Therefore, each session needs to compile the `p1` procedure to generate the corresponding cache, which may lead to stability issues. You can rewrite the SQL statement as follows:

```shell
EXCUTE IMMEDIATE 'SELECT * FROM temp_table WHERE ROWNUM = 1 INTO var1;'
```

This way, you have changed SQL statements involving GTTs to dynamic SQL statements to avoid this problem.

### Data is not cleaned up due to a fault

Data may not be fully cleaned up due to a fault. Currently, OceanBase Database does not support automatic cleanup in this case. Generally, this problem does not affect the use of the database. To remove excessive residual data, you can drop the GTTs and rebuild them.
