# ACTIVATE STANDBY

After physical recovery is completed or before switching to the standby tenant in a physical standby scenario, you can use the `ALTER SYSTEM ACTIVATE STANDBY` command to activate the standby tenant as the primary tenant.

After the `ALTER SYSTEM ACTIVATE STANDBY` command is successfully executed, the tenant role of the original standby tenant changes from `STANDBY` to `PRIMARY`. For more information about tenant roles, see [Overview of tenant roles](../../../../../600.manage/400.high-availability/300.physical-standby-database-disaster-recovery/600.role-switch/100.role-switch-overview.md).

## Limitations and considerations

* Before you execute this command, all replicas of the standby tenant's log streams must be online. If any replica is offline, you must wait for it to permanently go offline before executing the command.

* This command can only activate one standby tenant as the primary tenant at a time. If you need to activate multiple tenants, you must execute the command repeatedly.

## Privilege requirements

The command must be executed by the `root` user of the `sys` tenant (`root@sys`) or the administrator user of each tenant. Specifically:

* In MySQL mode, the default administrator user is `root`.

* In Oracle mode, the default administrator user is `SYS`.

## Syntax

```sql
ALTER SYSTEM ACTIVATE STANDBY
    [TENANT tenant_name]
    [VERIFY];
```

## Parameters

| Parameter | Description                                                     |
|--------------|---------------------------------------------------------|
| tenant_name  | The name of the standby tenant to be activated as the primary tenant. <main id="notice" type='notice'> <h4>Notice</h4> <p>Only the system tenant needs to specify the <code>TENANT tenant_name</code> parameter when executing this command. Regular tenants can only execute this command for themselves and do not need to specify this parameter. </p></main> |
| VERIFY      | Optional. When this parameter is used, it performs a preliminary check to confirm whether the necessary prerequisites for executing the `ACTIVATE STANDBY` command are met. <main id="notice" type='notice'><h4>Notice</h4><p><ul><li>There is a risk of failure during the primary-standby tenant role switch. The <code>VERIFY</code> command only performs preliminary verification to assess the prerequisites for the role switch, which helps reduce the possibility of operation failure, but does not actually execute the <code>ACTIVATE STANDBY</code> operation. </li><li>Even if the <code>VERIFY</code> command runs successfully, it does not guarantee that the subsequent <code>ACTIVATE STANDBY</code> operation will succeed. </li></ul></p></main>|

## Examples

* In a physical standby scenario, the system tenant of the cluster where the standby tenant `tenant1` is located activates it as the primary tenant. Alternatively, in a physical backup and restore scenario, the system tenant of the cluster where the standby tenant `tenant1` is located activates it as the primary tenant to provide services.

  ```sql
  obclient [oceanbase]> ALTER SYSTEM ACTIVATE STANDBY TENANT tenant1;
  ```

* In a physical standby scenario, the standby tenant activates itself as the primary tenant. Alternatively, in a physical backup and restore scenario, the standby tenant activates itself as the primary tenant to provide services.

  ```sql
  obclient [SYS]> ALTER SYSTEM ACTIVATE STANDBY;
  ```
