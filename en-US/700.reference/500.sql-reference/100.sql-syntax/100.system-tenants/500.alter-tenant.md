# ALTER TENANT

## Purpose

The `ALTER TENANT` statement is used to modify the properties of a user tenant, including the Locality, primary zone, resource pool list, and system variable values.

To modify the name of a user tenant, you can use the `ALTER TENANT ... RENAME` statement.

To lock or unlock a user tenant, you can use the `ALTER TENANT ... LOCK / UNLOCK` statement. After executing the `ALTER TENANT ... LOCK` statement, the system will no longer allow users to create new connections to the locked tenant. Existing connections will remain unaffected.

## Privilege requirements

Only the `root` user of the `sys` tenant (`root@sys`) can modify a tenant. Other tenants do not support modifying tenants.

## Syntax

### ALTER TENANT

```sql
ALTER TENANT tenant_name
    [SET] [tenant_option_list] [set_sys_var];

tenant_option_list:
    tenant_option [, tenant_option ...]

tenant_option:
      LOCALITY [=] 'locality_description'
    | PRIMARY_ZONE [=] zone
    | RESOURCE_POOL_LIST [=](pool_name [, pool_name...])
    | ENABLE_ARBITRATION_SERVICE [=] {True | False}
    | [DEFAULT] TABLEGROUP [=] {NULL | tablegroup_name}
    | ENABLE_EXTENDED_ROWID [=] {true | false}
    | COMMENT [=]'string'

set_sys_var:
    VARIABLES var_name {TO | =} var_value [,var_name {TO | =} var_value...]
```

### ALTER TENANT ... RENAME

```sql
ALTER TENANT tenant_name RENAME GLOBAL_NAME TO new_tenant_name;
```

### ALTER TENANT ... LOCK / UNLOCK

```sql
ALTER TENANT tenant_name LOCK | UNLOCK;
```

## Parameters

|          **Parameter**          |                                      **Description**                                                                             |
|--------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| tenant_name              | Specifies the name of the tenant to be modified.                                                                                                           |
| LOCALITY                 | Modifies the Locality of the tenant. Locality describes the distribution of replicas across zones. The following types of replicas are supported in the current version:<ul><li>Full-featured replicas: named FULL, abbreviated as F. For more information, see [Full-featured replicas](../../../100.oceanbase-database-concepts/500.distributed-database-objects/300.data-partitions-and-replicas/300.partition-replica-type/200.all-round-replica.md).</li> <li>Read-only replicas: named READONLY, abbreviated as R. For more information, see [Read-only replicas](../../../100.oceanbase-database-concepts/500.distributed-database-objects/300.data-partitions-and-replicas/300.partition-replica-type/300.read-only-replica.md).</li> <li>Columnstore replicas: named COLUMNSTORE, abbreviated as C. For more information, see [Columnstore replicas](../../../100.oceanbase-database-concepts/500.distributed-database-objects/300.data-partitions-and-replicas/300.partition-replica-type/400.columnstore-replica.md).</li></ul></br>Example: `LOCALITY = 'F@z1,F@z2,F@z3'` or `LOCALITY = 'F@z1,R@z2,C@z3'`</br>When increasing the number of zones, the `ZONE_LIST` of the tenant's resource pool must include the new zone. |
| PRIMARY_ZONE             | Modifies the primary zone of the tenant. The supported values are as follows:<ul><li>`RANDOM`: specifies that the primary zone of the tenant is all zones where the tenant is located, indicating that all zones have the same priority.</li> <li>zone_name: specifies a specific zone as the primary zone of the tenant.</li></ul> </br>If the primary zone is not specified when creating the tenant, the default value is `RANDOM`.                     |
| RESOURCE_POOL_LIST       | Modifies the resource pool list of the tenant.</br>If there are multiple resource pools, the `UNIT_NUM` of each resource pool must be the same.<main id="notice" type='notice'><h4>Notice</h4><ul><li>The <code>ZONE_LIST</code> of multiple resource pools for the same tenant must not overlap with each other.</li> <li>When modifying the resource pool list, you can only add or remove one resource pool at a time.</li></ul></main> |
| ENABLE_ARBITRATION_SERVICE | In a scenario where an arbitration service is deployed, modifies the enable status of the tenant's arbitration service.|
| [DEFAULT] TABLEGROUP       | Modifies the default table group information of the tenant. `NULL` indicates that the default table group is canceled.                                                  |
| ENABLE_EXTENDED_ROWID      | Specifies whether to enable the Extended ROWID mode for all tables in the tenant. Once enabled, this mode cannot be disabled. However, you can use the tenant-level configuration item `default_enable_extended_rowid` to specify whether to enable the Extended ROWID mode for newly created tables. For more information about the `default_enable_extended_rowid` configuration item, see [default_enable_extended_rowid](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2000.default_enable_extended_rowid.md).|
| system_var_name          | Modifies the value of a system variable for the tenant.                                                                      |
| RENAME GLOBAL_NAME TO    | Modifies the name of the tenant.                                                                          |
| COMMENT                  | Modifies the comment.                                                                              |

## Examples

* Change the primary zone of the `tenant1` tenant to `zone2`.

  ```shell
  obclient [oceanbase]> ALTER TENANT tenant1 primary_zone='zone2';
  ```

* Change the primary zone of the `tenant1` tenant to `RANDOM`.

  ```shell
  obclient [oceanbase]> ALTER TENANT tenant1 primary_zone = RANDOM;
  ```

  Assume that the `tenant1` tenant has three zones: `zone1`, `zone2`, and `zone3`. The preceding statement is equivalent to the following statement:

  ```shell
  obclient [oceanbase]> ALTER TENANT tenant1 primary_zone = 'zon1,zone2,zone3';
  ```

* Changing the resource pool is typically used in scenarios where you want to scale the number of replicas for a tenant. However, when changing the resource pool, you can only add or remove one resource pool at a time. You cannot directly replace the resource pool of a tenant from `pool1` to `pool2` with the following statement. Otherwise, the following error will occur.

  ```shell
  obclient [oceanbase]> ALTER TENANT tenant1 resource_pool_list=('pool2');
  ```

  The error message is as follows:

  ```shell
  ERROR 1210 (HY000): Incorrect arguments to resource pool list
  ```

  If you want to adjust the available resources for a tenant, such as expanding the tenant, you can increase the specifications of the resource units.

  ```shell
  obclient [oceanbase]> ALTER RESOURCE UNIT unit1 MAX_CPU 15, MEMORY_SIZE '20G', MAX_IOPS 1280, MIN_CPU=10, MIN_IOPS=1024;
  ```

* Change the locality of the `tenant1` tenant to add more replicas. In this example, `F` indicates a full-featured replica, and `B_4` is the name of the new zone.

  Assume that the current locality of the `tenant1` tenant is `F@B_1,F@B_2,F@B_3`, the resource pool is `pool1`, and the `ZONE_LIST` range is `'B_1','B_2','B_3'`.

  1. Create a resource unit named `unit2`.

     ```shell
     obclient [oceanbase]> CREATE RESOURCE UNIT unit2, MAX_CPU=5, MIN_CPU=2.5, MEMORY_SIZE= '32G', MAX_IOPS=10000, MIN_IOPS=5000, LOG_DISK_SIZE=5301023539200;
     ```

  2. Create a resource pool named `pool2`.

     ```shell
     obclient [oceanbase]> CREATE RESOURCE POOL pool2 unit='unit2',unit_num=1,zone_list=('B_4');
     ```

  3. Add the `pool2` resource pool to the `tenant1` tenant.

     ```shell
     obclient [oceanbase]> ALTER TENANT tenant1 resource_pool_list=('pool1','pool2');
     ```

  4. Modify the locality of the `tenant1` tenant.

     ```shell
     obclient [oceanbase]> ALTER TENANT tenant1 LOCALITY='F@B_1,F@B_2,F@B_3,F@B_4';
     ```

     If the replica type to be added is a columnstore replica, the statement to modify the locality of the `tenant1` tenant is as follows:

     ```shell
     obclient [oceanbase]> ALTER TENANT tenant1 LOCALITY = 'F@B_1,F@B_2,F@B_3,C@B_4';
     ```

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <ul><li>When modifying the locality of a tenant, for columnstore replicas, you can only add or remove replicas, but cannot convert the replica type. In other words, if you want to add a columnstore replica, there must be no replicas in the original zone. If you want to remove a columnstore replica, you must change the zone that contains the columnstore replica to a zone with no replicas.</li>
      <li>After adding a columnstore replica to a tenant, you need to deploy ODP and configure it to route connections to the columnstore replica. For more information about columnstore replicas, see <a href="../../../100.oceanbase-database-concepts/500.distributed-database-objects/300.data-partitions-and-replicas/300.partition-replica-type/400.columnstore-replica.md">Columnstore replicas</a>.</li></ul>
      </main>

* If an arbitration service is deployed, enable the arbitration service for the `tenant1` tenant.

  ```shell
  obclient [oceanbase]> ALTER TENANT tenant1 ENABLE_ARBITRATION_SERVICE=true;
  ```

* Rename the name of the ordinary tenant `tenant1` to `tenant101`.

  ```shell
  obclient [oceanbase]> ALTER TENANT tenant1 RENAME GLOBAL_NAME TO tenant101;
  ```

* Lock the `tenant1` tenant.

  ```shell
  obclient [oceanbase]> ALTER TENANT tenant1 LOCK;
  ```
