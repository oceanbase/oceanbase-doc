Other hints in the GLOBAL hint category allow developers and database administrators to perform fine-grained control over the execution of SQL statements. The following table lists the other types of hints supported.

## `DIRECT` Hint

The `DIRECT` hint can be used in `LOAD DATA` and `INSERT` statements to enable direct load, thereby improving the efficiency and performance of data import.

### Syntax

The syntax of the `DIRECT` hint is as follows:

```sql
/*+ DIRECT (/*+ direct(need_sort, max_errors_allowed, load_mode) */)*/
```

### Parameter

- `need_sort`: specifies whether to sort the imported data. Valid values: `true` and `false`. `true` indicates that sorting is required. `false` indicates that sorting is not required.

- `max_errors_allowed`: specifies the maximum number of error rows allowed. If this number is exceeded, the import process will fail.

- `load_mode`: specifies the import mode. Valid values:

  + `full`: the default value, indicating a full import.
  + `inc`: indicating an incremental import, which supports the `INSERT` and `IGNORE` semantics.
  + `inc_replace`: indicating an incremental import that does not check for duplicate primary keys, equivalent to the `REPLACE` semantics of incremental import.

### Example

#### Example in `LOAD DATA` statements

**Enable incremental direct load**

```sql
LOAD DATA /*+ DIRECT(true, 0, inc) */
INFILE 'datafile.txt'
INTO TABLE mytable
FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'
LINES TERMINATED BY '\n';
```

In this example, `DIRECT(true, 0, inc)` enables incremental direct load, performs sorting, and allows up to 0 error rows.

**Enable full direct load**

```sql
LOAD DATA
/*+ PARALLEL(4) DIRECT(true, 0, full) */
REMOTE_OSS INFILE 'oss://example.com/datafile.csv'
INTO TABLE my_table
FIELDS TERMINATED BY ',' ENCLOSED BY '"'
LINES TERMINATED BY '\n';
```

In this example, `PARALLEL(4)` specifies a parallelism of 4, and `DIRECT(true, 0, full)` enables full direct load, performs sorting, and allows up to 0 error rows.

For more information, see [Direct load](../../../../../../../../../620.obap/300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

#### Example in `INSERT INTO SELECT` statements

In `INSERT INTO SELECT` statements, to enable direct load, you must use the `enable_parallel_dml` option in the format of `/*+ direct(bool, int, load_mode)} enable_parallel_dml PARALLEL(N) */`.

**Enable incremental direct load**

```sql
-- Enable incremental direct load and parallel DML to incrementally import data from old_table to new_table.
INSERT /*+ direct(true, 0, 'inc') enable_parallel_dml PARALLEL(4) */ INTO new_table (id, name, value)
SELECT id, name, value
FROM old_table;
```

In this example, `direct(true, 0, 'inc')` enables incremental direct load, performs sorting, and allows up to 0 error rows; `enable_parallel_dml` enables parallel DML; and `PARALLEL(4)` sets the parallelism to 4.

**Enable full direct load**

```sql
-- Enable full direct load and parallel DML to import data from old_table to new_table.
INSERT /*+ direct(true, 0, 'full') enable_parallel_dml PARALLEL(4) */ INTO new_table (id, name, value)
SELECT id, name, value
FROM old_table;
```

In this example, `direct(true, 0, 'full')` enables full direct load, performs sorting, and allows up to 0 error rows; `enable_parallel_dml` enables parallel DML; and `PARALLEL(4)` sets the parallelism to 4.

For more information, see [Use `INSERT INTO SELECT` statements to perform direct load](../../../../../../../../../620.obap/300.obap-data-collection/300.obap-import-data/20.bypass-import/100.overview-of-bypass-import.md).

## `NO_DIRECT` Hint

The `NO_DIRECT` hint disables direct load in `LOAD DATA`, `INSERT INTO SELECT`, and `CREATE TABLE AS SELECT` statements.

### Syntax

The syntax of the `NO_DIRECT` hint is as follows:

```sql
/*+ NO_DIRECT */
```

### Parameter

`NO_DIRECT`: forces a single SQL statement to not use direct load. If an SQL statement contains this hint, it ignores other direct load hints and performs a regular import.

### Example

* **Use NO_DIRECT in a `LOAD DATA` statement**

  ```sql
  LOAD DATA /*+ NO_DIRECT */ [REMOTE_OSS | LOCAL] INFILE 'file_name' INTO TABLE table_name [COMPRESSION]...
  ```

* **Use NO_DIRECT in an `INSERT INTO SELECT` statement**

  ```sql
  INSERT /*+ NO_DIRECT */ INTO  table_name select_sentence
  ```

* **Use NO_DIRECT in a `CREATE TABLE AS SELECT` statement**

  ```sql
  CREATE /*+ NO_DIRECT */ TABLE table_name [AS] select_sentence
  ```


### Parameter

The parameters of the `DYNAMIC_SAMPLING` hint are described as follows:

- When the parameter is 1, dynamic sampling is enabled.

## `USE_PX` Hint

The `USE_PX` hint forces the server to execute an SQL statement in parallel execution (PX) mode. PX mode allows SQL statements to be executed in multiple threads, thereby improving query performance. Typically, the `USE_PX` hint is used with the `PARALLEL` hint to specify the number of threads for parallel execution. By default, the system uses the `USE_PX` hint.

### Syntax

The syntax of the `USE_PX` hint is as follows:

```sql
/*+ USE_PX */
```

### Example

The following example shows how to use the `USE_PX` hint:

```sql
SELECT /*+ USE_PX PARALLEL(4)*/ e.dept_id, sum(e.salary)
FROM emp e
WHERE e.dept_id = 1001 GROUP BY e.dept_id;
```

## `ENABLE_PARALLEL_DML` Hint

The `ENABLE_PARALLEL_DML` hint specifies whether to enable parallel DML for a query. The reverse hint of `ENABLE_PARALLEL_DML` is `DISABLE_PARALLEL_DML`, which is used to disable parallel DML.

For more information, see [Parallel DML](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/1000.parallel-dml.md).

### Consideration

- When you use `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/`, the system will prioritize distributed parallel DML (PDML). If the current environment does not support PDML, the system will fall back to DAS concurrent writes as a performance optimization.

- When a session-level forced parallelism is set, its execution behavior will be consistent with the above.

- Even if the current environment does not support parallel DML (PDML), if the system parameter `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` command (its default value is `false`), the system will not enable DAS (Distributed Active Storage) parallel writes, even if the `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used.

- If `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` command (default is `false`) and a session-level forced parallelism is already set, then even if the current environment does not support PDML, the use of the `/*+ENABLE_PARALLEL_DML PARALLEL(n)*/` hint will not enable DAS parallel writes.

### Syntax

```sql
/*+ ENABLE_PARALLEL_DML */
```

### Example

```sql
insert /*+ enable_parallel_dml parallel(8) */ into t2 select * from t1;
```

## `DISABLE_PARALLEL_DML` Hint

The `DISABLE_PARALLEL_DML` hint specifies whether to disable parallel DML for a query. The reverse hint of `DISABLE_PARALLEL_DML` is `ENABLE_PARALLEL_DML`, which is used to enable parallel DML.

For more information, see [Parallel DML](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/1000.parallel-dml.md).

### Syntax

```sql
/*+ DISABLE_PARALLEL_DML */
```

### Example

```sql
insert /*+ disable_parallel_dml parallel(8) */ into t2 select * from t1;
```

## `ENABLE_PARALLEL_DAS_DML` Hint

The `ENABLE_PARALLEL_DAS_DML` hint specifies whether to enable concurrent writes using the Distributed Data Access Service (DAS) for a DML statement. The reverse hint of `ENABLE_PARALLEL_DAS_DML` is `DISABLE_PARALLEL_DAS_DML`.

### Consideration

- The `ENABLE_PARALLEL_DAS_DML` hint must be used in conjunction with the `ENABLE_PARALLEL_DML` hint.

- When the `/*+ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used, the system will prioritize DAS concurrent writes as the forced option and execute operations based on the parallelism specified by `PARALLEL(n)`.

- If the system parameter `_enable_parallel_das_dml` is set to `true` using the `ALTER SYSTEM SET` command (default is `false`), the `/*+ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` hint will be ineffective. In this case, the system will not execute DAS concurrent writes.

### Syntax

```sql
/*+ ENABLE_PARALLEL_DAS_DML */
```

### Example

```sql
insert /*+ ENABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(10)*/
into t1 select * from t2;
```

## `DISABLE_PARALLEL_DAS_DML` Hint

The `DISABLE_PARALLEL_DAS_DML` hint specifies whether to disable concurrent writes using the Distributed Data Access Service (DAS) for a DML statement. The reverse hint of `DISABLE_PARALLEL_DAS_DML` is `ENABLE_PARALLEL_DAS_DML`.

### Consideration

- The `DISABLE_PARALLEL_DAS_DML` hint must be used in conjunction with the `ENABLE_PARALLEL_DML` hint.

- When the `/*+DISABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(n)*/` hint is used, the system will disable DAS concurrent writes, even if other concurrent write optimization options such as PDML are enabled.

### Syntax

```sql
/*+ DISABLE_PARALLEL_DAS_DML */
```

### Example

```sql
insert /*+ DISABLE_PARALLEL_DAS_DML ENABLE_PARALLEL_DML PARALLEL(10)*/
into t1 select * from t2;
```

The `MAX_CONCURRENT` hint specifies the maximum number of concurrent queries allowed.

In the `MAX_CONCURRENT` hint, the `intnum` parameter specifies the maximum number of concurrent queries allowed. If the number of concurrent queries exceeds the allowed maximum, an error is returned when the query is executed. If `intnum` is specified as 0, an error is always returned when the query is executed.

Note that the `MAX_CONCURRENT` hint cannot be directly used in queries. Instead, you can create an outline containing only the `MAX_CONCURRENT` hint to limit the concurrency of specific SQL statements.


## Hint for query rewriting using materialized views

The query rewriting using materialized views can be controlled by using the `MV_REWRITE` and `NO_MV_REWRITE` hints. These hints have a higher priority than the system variable `query_rewrite_enabled`.

### `MV_REWRITE` Hint

The syntax of the `MV_REWRITE` hint is as follows:

```sql
/*+ MV_REWRITE (@ queryblock [mv_name_list]) */

mv_name_list:
    mv_name [, mv_name ...]
```

When you use the `MV_REWRITE` hint alone, the system skips the rules and cost checks for query rewriting using materialized views and directly uses the applicable rewriting. If you specify one or more materialized views after the hint, the system skips the rules and cost checks and uses only the specified materialized views for rewriting, ignoring all other materialized views.

When you use the `MV_REWRITE` hint to specify a materialized view, you cannot force the use of a materialized view that does not have the `ENABLE QUERY REWRITE` clause. Additionally, you cannot force the use of a non-real-time materialized view when the system variable `query_rewrite_integrity` is set to `enforced`.

### `NO_MV_REWRITE` Hint

The syntax of the `NO_MV_REWRITE` hint is as follows:

```sql
/*+ NO_MV_REWRITE (@ queryblock) */
```

The `NO_MV_REWRITE` hint disables query rewriting using materialized views. You can specify a query block.

### Example of using the query rewriting using materialized views control hints

1. Create the base table `tbl2`.

   ```sql
   CREATE TABLE tbl2 (col1 INT, col2 INT);
   ```

2. Insert two rows of data into the `tbl2` table.

   ```sql
   INSERT INTO tbl2 VALUES (1,2),(3,4);
   ```

   The return result is as follows:

   ```shell
   Query OK, 2 rows affected
   Records: 2  Duplicates: 0  Warnings: 0
   ```

3. Create the materialized view `mv1_tbl2` and enable query rewriting for it.

   ```sql
   CREATE MATERIALIZED VIEW mv1_tbl2 NEVER REFRESH ENABLE QUERY REWRITE AS SELECT * FROM tbl2;
   ```

4. Create the materialized view `mv2_tbl2` and enable query rewriting for it.

   ```sql
   CREATE MATERIALIZED VIEW mv2_tbl2 NEVER REFRESH ENABLE QUERY REWRITE AS SELECT * FROM tbl2 WHERE tbl2.col1 > 1;
   ```

5. Set the system variable `query_rewrite_integrity` to `stale_tolerated`.

## `NO_PARALLEL` Hint

The `NO_PARALLEL` hint specifies to disable query parallelism (i.e., set the parallelism to 1). Its reverse hint is `PARALLEL`.

The `NO_PARALLEL` hint is equivalent to `/*+ parallel(1)*/`.

### Syntax

```sql
/*+ NO_PARALLEL */
```

### Example

The following query example uses the `NO_PARALLEL` hint to disable query parallelism.

```sql
SELECT /*+ no_parallel */ c1, sum(distinct c2) FROM t1 GROUP BY c1;
```

## `NO_QUERY_TRANSFORMATION` Hint

The `NO_QUERY_TRANSFORMATION` hint disables any query rewriting for the current query.

Note that unlike the `NO_REWRITE` hint in the Query Block Hint, using the `NO_QUERY_TRANSFORMATION` hint prevents the use of Query Block hints to enable certain types of rewriting.

For more information about query rewriting, see [Overview of query rewriting](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/500.query-rewrite/100.query-rewrite-overview.md).

### Syntax

```sql
/*+ NO_QUERY_TRANSFORMATION */
```

### Example

The following query example uses the `NO_QUERY_TRANSFORMATION` hint to disable any query rewriting.

```sql
SELECT /*+ NO_QUERY_TRANSFORMATION */ *
FROM (SELECT * FROM t1) v WHERE v.c1 = 3;
```

## `OPT_PARAM` Hint

`OPT_PARAM` Hint specifies optimizer-related configuration items or system variables at the query level.

### Syntax

```sql
/*+ OPT_PARAM ( parameter_name [,] parameter_value ) */
```

### Parameter

* `parameter_name`: the name of the configuration item or system variable.

* `parameter_value`: the value of the variable to be specified.

The `OPT_PARAM` Hint applies to the following parameters:

* `rowsets_enabled`: specifies whether to enable or disable vectorization. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `rowsets_max_rows`: specifies the batch size `batch_size` for returning rows. The data type is `INT`, and the value ranges from 0 to 65535. The value must not be enclosed in single quotation marks (' ').

* `enable_newsort`: specifies whether to enable or disable the newsort optimization. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `use_part_sort_mgb`: specifies whether to enable or disable the part sort merge group by. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `enable_in_range_optimization`: specifies whether to enable or disable the IN optimization. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `xsolapi_generate_with_clause`: specifies whether to enable or disable the CTE extraction rewrite. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `preserve_order_for_pagination`: specifies whether to add the `order by` clause for pagination queries to preserve order or to prohibit adding the `order by` clause. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `storage_card_estimation`: specifies whether to use the storage layer for row estimation. The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `workarea_size_policy`: specifies the strategy for manually or automatically adjusting the SQL workspace size. The data type is `VARCHAR`, and the value can be `'MANUAL'` for manual adjustment or `'AUTO'` for automatic adjustment. The value must be enclosed in single quotation marks (' ').

* `enable_rich_vector_format`: specifies whether to enable or disable vectorization 2.0 (session-level parameter). The data type is `VARCHAR`, and the value can be `'TRUE'` or `'FALSE'`. The value must be enclosed in single quotation marks (' ').

* `spill_compression_codec`: specifies the compression algorithm for operators that require temporary materialization. The data type is `VARCHAR`, and the value can be `NONE`, `LZ4`, `SNAPPY`, `ZLIB`, or `ZSTD`, representing different compression algorithms. The default value is `NONE`, indicating no compression.

* `inlist_rewrite_threshold`: specifies the threshold for the number of constants that can trigger the rewrite of `inlist` to a `values statement`. The data type is `INT64`, and the value ranges from 1 to 2147483647.

* `orc_filter_pushdown_level`: specifies the level at which to push down filter conditions for ORC external tables. The `parameter_value` can be:

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>OPT_PARAM</code> Hint in OceanBase Database supports the <code>orc_filter_pushdown_level</code> parameter starting from version V4.4.0. </p>
    </main>

  * `0`: disables filter condition pushdown.
  * `1`: pushes down to the file level.
  * `2`: pushes down to the stripe level.
  * `3`: pushes down to the row index level.
  * `4`: pushes down to the encoding level.

* `parquet_filter_pushdown_level`: specifies the level at which to push down filter conditions for Parquet external tables. The `parameter_value` can be:

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>OPT_PARAM</code> Hint in OceanBase Database supports the <code>parquet_filter_pushdown_level</code> parameter starting from version V4.4.0. </p>
    </main>

  * `0`: disables filter condition pushdown.
  * `1`: pushes down to the file level.
  * `2`: pushes down to the RowGroup level.
  * `3`: pushes down to the page level.
  * `4`: pushes down to the encoding level.

### Example

The following example uses the `OPT_PARAM` Hint to enable the IN optimization for the current query by specifying the `enable_in_range_optimization` value.

```shell
SELECT /*+ opt_param('enable_in_range_optimization', 'true') */ *
from t1
where c1 in (1,2,3,4,5,...,1000)
and c2 in (1,2,3,4,5,...,1000);
```

## `PARALLEL` Hint

As a global hint, the `PARALLEL` Hint specifies the parallelism or parallelism enable strategy for the current query.

In addition to being a global hint, the `PARALLEL` Hint can also be used as a query block hint to specify the parallelism at the table level. For more information, see the `Parallel` hint section in [Access Path Hints](../200.optimizer-hint-of-mysql-mode/100.the-hint-related-to-the-access-path-of-mysql-mode.md).

### Syntax

```sql
/*+ PARALLEL ( AUTO | MANUAL | parallel_degree) */
```

### Parameter

- `AUTO` or `MANUAL`: when `AUTO` or `MANUAL` is used as the parameter in the `PARALLEL` Hint, it specifies the parallelism enable strategy. For more information, see [Parallelism enable strategies and priorities](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/300.distributed-execution-plan/500.parallel-execution.md).

- `parallel_degree`: when `parallel_degree` is used as the parameter in the `PARALLEL` Hint, it specifies the parallelism directly.

### Example

The following example uses the `PARALLEL` Hint to specify a parallelism of DOP = 8 or to enable Auto DOP.

```sql
SELECT /*+parallel(8)*/ c1, SUM(distinct c2) FROM t1 GROUP BY c1;

SELECT /*+parallel(auto)*/ c1, SUM(distinct c2) FROM t1 GROUP BY c1;
```

> Note: Some scenarios do not support parallel execution. Even if you specify the PARALLEL hint to enable parallel execution, the execution plan may still disable parallel execution.

## `READ_CONSISTENCY` Hint

The `READ_CONSISTENCY` hint specifies the read consistency level for the current query.

### Syntax

```sql
/*+ READ_CONSISTENCY(WEAK[STRONG]) */
```

### Parameter

- `WEAK`: enables weak consistency, i.e., weak reads.

- `STRONG`: enables strong consistency, i.e., disables weak reads.

### Example

```sql
-- Use the READ_CONSISTENCY hint and set it to WEAK to enable weak reads for the query.
SELECT /*+ READ_CONSISTENCY(WEAK) */ *
FROM employees
WHERE employees.department_id = 1001;
```

Weak reads are supported when the isolation level is set to Repeatable Read or Serializable. Example:

  ```sql
  obclient> SET transaction read only;
  Query OK, 0 rows affected (0.001 sec)
  obclient> SELECT /*+ read_consistency(weak)*/ * FROM t WHERE a=2;
  +------+------+
  | ID   | A    |
  +------+------+
  | NULL |    2 |
  +------+------+
  1 row in set (0.001 sec)
  ```

## `STAT` Hint

The `STAT` hint specifies the operators in the query plan whose outputs are to be traced.

After adding the `STAT` hint, the query plan includes a `MONITORING DUMP` operator. This operator directly outputs all data from the sort operator and prints the operator's execution time, number of output rows, and other information in the observer log after execution.

### Syntax

```sql
/*+ STAT(TRACING_NUM_LIST) */
```

### Parameter

- `TRACING_NUM_LIST`: specifies the IDs of the operators to be traced.

### Example

```sql
-- The query plan before and after adding the hint `/*+ STAT(0, 2) */`
explain basic
SELECT /*+leading(t1) use_hash(t2)*/ * FROM t1, t2 WHERE t1.c1 = t2.c1;

Query Plan
===========================
|ID|OPERATOR         |NAME|
---------------------------
|0 |HASH JOIN        |    |
|1 |├─TABLE FULL SCAN|T1  |
|2 |└─TABLE FULL SCAN|T2  |
===========================

explain basic
SELECT /*+leading(t1) use_hash(t2) stat(0, 2)*/ *
FROM t1, t2 where t1.c1 = t2.c1;
Query Plan
===============================
|ID|OPERATOR             |NAME|
-------------------------------

===============================
```

## `TRANS_PARAM` Hint

The `TRANS_PARAM` hint is used to specify transaction-related parameters at the query level.

### Syntax

```sql
/*+ TRANS_PARAM ['FORCE_EARLY_LOCK_FREE' , 'TRUE'] */
```

### Parameter

Currently, only the `FORCE_EARLY_LOCK_FREE` parameter, which specifies whether to enable early row lock release at the transaction level, is supported.

- `FORCE_EARLY_LOCK_FREE`: specifies whether to enable early row lock release at the transaction level. **TRUE** indicates that early row lock release is enabled, and **FALSE** indicates that it is disabled.

**Notice**: The parameter name and value must be enclosed in single quotation marks ( ' '). If the parameter value is a numeric value, you can omit the quotation marks.

### Example

```sql
-- Use the TRANS_PARAM hint and set the parameter 'FORCE_EARLY_LOCK_FREE' to 'TRUE' to enable early row lock release at the transaction level.
SELECT /*+ TRANS_PARAM('FORCE_EARLY_LOCK_FREE' 'TRUE') */ *
FROM employees e
WHERE e.department_id = 1001;
```

## `TRACING` Hint

The `TRACING` hint specifies the operators in the query plan whose outputs are to be traced.

The usage of the `TRACING` hint, the plan shape after adding the hint, and the behavior when using the `STAT` hint are the same.

The difference is that when using the `TRACING` hint, the `MONITORING DUMP` operator prints all of its output data in the observer log.

### Syntax

```sql
/*+ TRACING(TRACING_NUM_LIST)*/
```

### Parameter

- `TRACING_NUM_LIST`: specifies the IDs of the operators to be traced.

### Example

```sql
-- Use the TRACING hint and set the level to 1 to enable tracing for the current query.
SELECT /*+ TRACING(1) */ *
FROM employees e
WHERE e.department_id = 1001;
```

## `USE_PLAN_CACHE` Hint

The `USE_PLAN_CACHE` hint specifies the plan cache (Plan Cache) usage strategy for the current query. For more information about the plan cache, see [Execution plan cache](../../../../../../../../1000.performance-tuning-guide/500.sql-optimization/200.sql-execution-plan/300.execution-plan-cache.md).

### Syntax

```sql
/*+ USE_PLAN_CACHE ( NONE | DEFAULT ) */
```

### Parameter

- `NONE`: specifies that the query does not use the plan cache.

- `DEFAULT`: specifies that the current query uses the system variable [`ob_enable_plan_cache`](../../../../../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/7200.ob_enable_plan_cache-global.md) to control the plan cache strategy.

### Example

```sql
-- When the `NONE` parameter is used, the query does not use the plan cache. When the `DEFAULT` parameter is used, the current query uses the system variable `ob_enable_plan_cache` to control the plan cache strategy.
SELECT /*+ USE_PLAN_CACHE(NONE) */ *
FROM employees e
WHERE e.department_id = 1001;

SELECT /*+ USE_PLAN_CACHE(DEFAULT) */ *
FROM employees e
WHERE e.department_id = 1001;
```

### Parameter
