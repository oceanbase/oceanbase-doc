# Cost Based Transform Hint

In SQL queries, cost-based hints specify whether the optimizer should apply or avoid specific query transformations in certain situations, such as rewriting query structures, merging or not merging views, etc.

| Hint Type          | Description                                                                                                                    |
|--------------------|-------------------------------------------------------------------------------------------------------------------------|
| `COALESCE_SQ`        | Specifies to rewrite subqueries in the query. The reverse operation is `NO_COALESCE_SQ`.            |
| `NO_COALESCE_SQ`     | Disables subquery rewriting. The reverse operation is `COALESCE_SQ`.          |
| `MERGE`              | Allows merging of views. The reverse operation is `NO_MERGE`.    |
| `NO_MERGE`           | Disables merging of external queries with any inline views into a single query. The reverse operation is `MERGE`.    |
| `NO_EXPAND`          | Disables query expansion rewriting for `WHERE` clauses containing `OR` conditions. The reverse operation is `USE_CONCAT`.      |
| `USE_CONCAT`         | Enables query expansion rewriting for `WHERE` clauses containing `OR` conditions. The reverse operation is `NO_EXPAND`.|
| `PLACE_GROUP_BY`     | Enables `Group By` pushdown query rewriting. The reverse operation is `NO_PLACE_GROUP_BY`.                     |
| `NO_PLACE_GROUP_BY`  | Disables `Group By` pushdown query rewriting. The reverse operation is `PLACE_GROUP_BY`.            |
| `SEMI_TO_INNER`      | Optimizes semi-join queries containing EXISTS or IN by converting them to inner join queries. The reverse operation is `NO_SEMI_TO_INNER`.     |
| `NO_SEMI_TO_INNER`   | Prevents the optimizer from converting semi-join queries to inner join queries. The reverse operation is `SEMI_TO_INNER`.               |
| `WIN_MAGIC`          | Enables `WIN MAGIC` query rewriting, which optimizes specific aggregation and self-join queries by eliminating joins and using window functions. This hint allows the optimizer to remove unnecessary joins and replace them with window functions. The reverse operation is `NO_WIN_MAGIC`.     |
| `NO_WIN_MAGIC`       | Disables `WIN MAGIC` query rewriting. The reverse operation is `WIN_MAGIC`.                    |

## `COALESCE_SQ` Hint

`COALESCE_SQ` Hint specifies to merge subqueries in a query. Its reverse operation is `NO_COALESCE_SQ` Hint.

### Syntax

```sql
/*+ COALESCE_SQ [ ( [ @ qb_name ] [ qb_name_list ] ) ] */
```

### Parameters

- `qb_name_list`: Optional. The name list of one or more query blocks. You can specify to merge subqueries in specific query blocks. If this parameter is not specified, all possible subqueries are merged.

### Examples

The following query example specifies to merge subqueries in only the `SEL1` and `SEL2` query blocks by using the `COALESCE_SQ(("SEL1", "SEL2"))` hint.

```sql
UPDATE /*+ COALESCE_SQ(("SEL1", "SEL2")) */ t1
SET c1 = (SELECT /*+ QB_NAME(SEL1) */ c1 FROM t2 A),
    c2 = (SELECT /*+ QB_NAME(SEL2) */ c2 FROM t2 B),
    c3 = (SELECT /*+ QB_NAME(SEL3) */ c3 FROM t2 C),
    c4 = (SELECT /*+ QB_NAME(SEL4) */ c4 FROM t2 D);
```

## `NO_COALESCE_SQ` Hint

`NO_COALESCE_SQ` Hint specifies to disable subquery merging in a query. Its reverse operation is `COALESCE_SQ` Hint.

### Syntax

```sql
/*+ NO_COALESCE_SQ [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `qb_name`: Optional. You can specify to disable subquery merging in specific query blocks. If this parameter is not specified, subquery merging is disabled for all possible subqueries.

### Examples

The following query example specifies to disable subquery merging by using the `NO_COALESCE_SQ` hint, thereby maintaining the original query structure:

```sql
UPDATE /*+ NO_COALESCE_SQ */ t1
SET c1 = (SELECT /*+ QB_NAME(SEL1) */ c1 FROM t2 A),
    c2 = (SELECT /*+ QB_NAME(SEL2) */ c2 FROM t2 B),
    c3 = (SELECT /*+ QB_NAME(SEL3) */ c3 FROM t2 C),
    c4 = (SELECT /*+ QB_NAME(SEL4) */ c4 FROM t2 D);
```

## `MERGE` Hint

`MERGE` Hint specifies to enable view merging in a query. Its reverse operation is `NO_MERGE` Hint.

### Syntax

```sql
/*+ MERGE [ ( [ @ qb_name ] [ > upper_qb_name ] ) ] */
```

#### Parameters

- `upper_qb_name`: Optional. You can specify the specific form of view merging. We recommend that you use the default value.

### Examples

The following query example specifies to enable view merging by using the `MERGE` hint. The `MERGE` hint and the `NO_REWRITE` hint are used together to force the optimizer to merge views and disable other types of query rewriting.

```sql
SELECT * FROM (SELECT /*+ MERGE NO_REWRITE */ * FROM t1);
```

## `NO_MERGE` Hint

`NO_MERGE` Hint specifies to disable view merging in a query. Its reverse operation is `MERGE` Hint.

### Syntax

```sql
/*+ NO_MERGE [ ( [ @ qb_name ] ) ] */
```

### Examples

The following query example specifies to disable view merging by using the `NO_MERGE` hint:

```sql
SELECT * FROM (SELECT /*+ NO_MERGE */ * FROM t1);
```

## `NO_EXPAND` Hint

`NO_EXPAND` Hint specifies to disable query expansion for a `WHERE` clause that contains an `OR` condition. Its reverse operation is `USE_CONCAT` Hint.

### Syntax

```sql
/*+ NO_EXPAND [ ( [ @ qb_name ] ) ] */
```

### Examples

```sql
-- Use the NO_EXPAND hint to instruct the optimizer not to expand queries with OR conditions.
SELECT /*+ NO_EXPAND */ *
  FROM employees e, departments d
  WHERE e.manager_id = 108
     OR d.department_id = 110;
```

## `USE_CONCAT` Hint

`USE_CONCAT` Hint specifies to enable query expansion for a `WHERE` clause that contains an `OR` condition. Its reverse operation is `NO_EXPAND` Hint.

### Syntax

```sql
/*+ USE_CONCAT [ ( [ @ qb_name ] [ expand_cond_str ] ) ] */
```

#### Parameters

- `expand_cond_str`: Optional. You can specify to expand only specific OR conditions. If this parameter is not specified, all OR conditions are expanded.

### Examples

- Example 1: Use the `USE_CONCAT` hint for the first `OR` condition.

```sql
SELECT /*+ USE_CONCAT('b.c1 = c.c1 OR b.c2 = c.c2') */ a.c1, b.c1, c.c1
FROM t1 a
LEFT JOIN (t1 b LEFT JOIN t1 c ON b.c3 = 4 AND (b.c1 = c.c1 OR b.c2 = c.c2))
ON a.c1 = b.c1
WHERE (a.c2 = 3 OR a.c3 = 4)
  AND EXISTS (SELECT * FROM t1 d WHERE a.c1 = d.c1 OR a.c2 = d.c2);
```

- Example 2: Use the `USE_CONCAT` hint for the second `OR` condition.

```sql
SELECT /*+ USE_CONCAT('a.c2 = 3 OR a.c3 = 4') */ a.c1, b.c1, c.c1
FROM t1 a
LEFT JOIN (t1 b LEFT JOIN t1 c ON b.c3 = 4 AND (b.c1 = c.c1 OR b.c2 = c.c2))
ON a.c1 = b.c1
WHERE (a.c2 = 3 OR a.c3 = 4)
  AND EXISTS (SELECT * FROM t1 d WHERE a.c1 = d.c1 OR a.c2 = d.c2);
```

- Example 3: Use the `USE_CONCAT` hint for the `OR` condition in the `EXISTS` clause.

```sql
SELECT /*+ USE_CONCAT('a.c1 = VIEW1.d.c1 OR a.c2 = VIEW1.d.c2') */ a.c1, b.c1, c.c1
FROM t1 a
LEFT JOIN (t1 b LEFT JOIN t1 c ON b.c3 = 4 AND (b.c1 = c.c1 OR b.c2 = c.c2))
ON a.c1 = b.c1
WHERE (a.c2 = 3 OR a.c3 = 4)
  AND EXISTS (SELECT * FROM t1 d WHERE a.c1 = d.c1 OR a.c2 = d.c2);
```

## `PLACE_GROUP_BY` Hint

`PLACE_GROUP_BY` Hint specifies to enable pushing down the `GROUP BY` clause to a more optimal position in the execution plan. This can reduce the amount of data that needs to be grouped and aggregated. Its reverse operation is `NO_PLACE_GROUP_BY` Hint.

### Syntax

```sql
/*+ PLACE_GROUP_BY [ ( [ @ qb_name ] [ ( table_list ) ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. The name of the query block to which the hint applies.
- `table_list`: Optional. You can specify to push down the `GROUP BY` clause to specific joined tables. If this parameter is not specified, the `GROUP BY` clause is pushed down to all joined tables.

### Examples

The following query example specifies to push down the `GROUP BY` clause to a more optimal position in the execution plan by using the `PLACE_GROUP_BY` hint.

```sql
SELECT /*+ PLACE_GROUP_BY */ SUM(t2.c3)
FROM t1
JOIN t2 ON t1.c2 = t2.c2
GROUP BY t1.c2;
```

## `NO_PLACE_GROUP_BY` Hint

`NO_PLACE_GROUP_BY` Hint specifies to disable pushing down the `GROUP BY` clause to a more optimal position in the execution plan. Its reverse operation is `PLACE_GROUP_BY` Hint.

### Syntax

```sql
/*+ NO_PLACE_GROUP_BY [ ( [ @ qb_name ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. The name of the query block to which the hint applies.

### Examples

The following query example specifies to disable pushing down the `GROUP BY` clause to a more optimal position in the execution plan by using the `NO_PLACE_GROUP_BY` hint.

```sql
SELECT /*+ NO_PLACE_GROUP_BY */ SUM(t2.c3)
FROM t1
JOIN t2 ON t1.c2 = t2.c2
GROUP BY t1.c2;
```

## `SEMI_TO_INNER` Hint

`SEMI_TO_INNER` Hint specifies to enable converting semijoins that contain `EXISTS` or `IN` into inner joins. Its reverse operation is `NO_SEMI_TO_INNER` Hint.

### Syntax

```sql
/*+ SEMI_TO_INNER [ ( [ @ qb_name ] [ table ] ) ] */
```

#### Parameters

- `@qb_name`: Optional. The name of the query block to which the hint applies.
- `table`: Optional. You can specify the right table of the semijoin to convert. If this parameter is not specified, all semijoins are converted.

### Examples

The following query example specifies to convert the semijoin between t1 and t2 into an inner join by using the `SEMI_TO_INNER(t2)` hint.

```sql
SELECT /*+ SEMI_TO_INNER(t2) */ *
FROM t1
WHERE EXISTS (SELECT 1 FROM t2 WHERE t1.c1 = t2.c2);
```

## `NO_SEMI_TO_INNER` Hint

The `NO_SEMI_TO_INNER` Hint disables the conversion of semi-join queries to inner join queries. The reverse operation is the `SEMI_TO_INNER` Hint.

### Syntax

```sql
/*+ NO_SEMI_TO_INNER [ ( [ @ qb_name ]  ) ] */
```

#### Parameters

- `@qb_name`: Optional. Specifies the query block to which the hint applies.

### Examples

The following query example uses the `NO_SEMI_TO_INNER` Hint to ensure that the optimizer does not attempt to convert the semi-join in the `EXISTS` clause to an inner join when deriving the result set.

```sql
SELECT /*+ NO_SEMI_TO_INNER */ *
FROM t1
WHERE EXISTS (SELECT 1 FROM t2 WHERE t1.c1 = t2.c2);
```

## `WIN_MAGIC` Hint

The `WIN_MAGIC` Hint enables `WIN MAGIC` query rewriting, which eliminates joins in specific scenarios and optimizes the queries using window functions. This hint instructs the optimizer to remove unnecessary joins and replace them with window functions, thereby improving query execution efficiency. The reverse operation is the `NO_WIN_MAGIC` Hint.

### Syntax

```sql
/*+ WIN_MAGIC [ ( [ @ qb_name ] [ table_list ] ) ] */
```

#### Parameters

- `table_list`: Optional. Specifies which tables should participate in the `WIN_MAGIC` query rewriting operation. If this parameter is omitted, the hint applies to all tables.

### Examples

The following query example uses `WIN_MAGIC(t1 v)` to instruct the optimizer to apply window functions to optimize the processing of table t1 and derived table v.

```sql
SELECT /*+ WIN_MAGIC(t1 v) */ *
FROM t1
JOIN (SELECT AVG(c1), c2 FROM t1 GROUP BY c2) v ON t1.c2 = v.c2
ORDER BY t1.pk;
```

## `NO_WIN_MAGIC` Hint

The `NO_WIN_MAGIC` Hint disables `WIN MAGIC` query rewriting. The reverse operation is the `WIN_MAGIC` Hint.

### Syntax

```sql
/*+ NO_WIN_MAGIC [ ( [ @ qb_name ] ) ] */
```

### Examples

The following query example uses the `NO_WIN_MAGIC` Hint to keep the query unchanged and prevent it from being rewritten using window functions.

```sql
SELECT /*+ NO_WIN_MAGIC */ *
FROM t1
JOIN (SELECT AVG(c1), c2 FROM t1 GROUP BY c2) v ON t1.c2 = v.c2
ORDER BY t1.pk;
```
