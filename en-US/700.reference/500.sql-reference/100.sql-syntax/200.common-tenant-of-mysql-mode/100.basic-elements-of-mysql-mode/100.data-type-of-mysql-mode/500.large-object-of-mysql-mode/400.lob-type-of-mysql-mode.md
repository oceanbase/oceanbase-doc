# LOB types

Large object (LOB) types are used to store TEXT, binary large object (BLOB), JavaScript Object Notation (JSON), and GEOMETRY data.
LOB data can be stored in INROW or OUTROW storage mode.

## INROW storage

When INROW storage is used, LOB data is stored together with rows in the primary table. Only one access to storage is required to read LOB data.

## OUTROW storage

When OUTROW storage is used, LOB data is stored in an LOB auxiliary table. To read LOB data, the database first obtains locators of the data by reading rows in the primary table and then reads actual LOB data from the LOB auxiliary table based on the locators. The whole process involves two accesses to the storage.

## LOB storage switching

Whether INROW or OUTROW storage is used depends on the amount of data in a LOB column. Assume that you have set the storage switching threshold to 8,192 bytes. If data in a LOB column exceeds 8,192 bytes, OUTROW storage is adopted; otherwise, INROW storage is used.

```shell
obclient> CREATE TABLE t(pk int, data text) LOB_INROW_THRESHOLD = 8192;
```

The preceding DDL statement sets the INROW-to-OUTROW switching threshold to 8,192 bytes by specifying the `LOB_INROW_THRESHOLD` parameter.

* When data in a LOB column is within 8,192 bytes, the data is stored together with rows in the primary table.
* When data in a LOB column exceeds 8,192 bytes, the data is stored in a LOB auxiliary table.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Decreasing the value of <code>lob_inrow_threshold</code> is an offline DDL operation. </p>
</main>

INROW storage outperforms OUTROW storage since the former reduces the number of accesses to storage required to read LOB data, thus improving the efficiency. In scenarios where LOB data needs to be accessed frequently, INROW storage can speed up queries and reduce system overhead.

## LOB types

The common LOB types in MySQL mode are sorted in alphabetic order as follows:

* **ARRAY**: stores data of the ARRAY type. It can store a collection of multiple values.
* **RoaringBitmap**: stores data of the Roaring bitmap type. It is mainly used for image processing and representation.
* **BLOB**: stores binary data such as images or files. The maximum length is 65,535 bytes.
* **GEOMETRY**: stores geospatial data. It can be used for spatial analysis and operations.
* **JSON**: stores data in the JSON format. It can facilitate the processing of structured data.
* **LONGTEXT**: stores massive text data. The maximum length is 536,870,910 bytes.
* **LONGBLOB**: stores massive binary data. The maximum length is 536,870,910 bytes.
* **MEDIUMBLOB**: stores a medium amount of binary data. The maximum length is 16,777,215 bytes.
* **MEDIUMTEXT**: stores a medium amount of text data. The maximum length is 16,777,215 bytes.
* **TEXT**: stores a small amount of text data. The maximum length is 65,535 bytes.

## LOB Consistency Check

When an external storage is used, the primary table and LOB auxiliary table are associated by LOB ID: the LOB ID set in the primary table's locator should be consistent with the LOB ID set in the LOB auxiliary table. If there is inconsistency, such as "present in the primary table but not in the auxiliary table" or "present in the auxiliary table but not in the primary table", it may lead to reading exceptions or inability to recycle space.

This feature scans the primary table to collect the LOB ID set and compares it with the LOB ID set scanned from the LOB auxiliary table. It outputs whether they are consistent and the difference information, which facilitates inspection during off-peak hours or data relationship confirmation during troubleshooting.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The LOB consistency check will scan the primary table and LOB auxiliary table, which will consume I/O and CPU resources. Please execute this feature during off-peak hours and configure appropriate resource groups for the task as described below.</p>
</main>

### How to use this feature with resource groups and I/O benchmarks

The LOB consistency check will scan the primary table and LOB auxiliary table, which will consume I/O and CPU resources. When setting I/O limits for the check task, the I/O benchmark of the tenant (generated by I/O calibration) is relied on. The following recommendations are provided for different deployment scenarios:

* In environments where I/O calibration has been completed by default (such as public clouds): You can directly configure resource management plans and resource groups within the tenant.
* In private clouds or environments where I/O calibration has not been performed: First, complete the disk I/O calibration in the system tenant. Then, plan the `MAX_IOPS` and `MIN_IOPS` for business tenants based on the benchmark. Combine these I/O limits with the resource groups. For details about the calibration commands, progress checking, and resource isolation for background tasks, see [Resource isolation for background tasks](../../../../../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/400.background-resource-isolation-of-mysql-or-oracle-mode.md). For the disk performance calibration steps, see [Disk performance calibration](../../../../../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/300.resource-isolation-of-mysql-mode/150.disk-performance-calibration-of-mysql-mode.md).

### Complete example

Before using the LOB consistency check feature, you need to perform I/O calibration, create a dedicated resource plan for LOB checks, and configure the resource management plan and resource groups.

#### Step 1: I/O calibration (optional)

If you have not performed I/O calibration, you need to perform I/O calibration in the system tenant. It may take 1-2 minutes from the completion of calibration to its effectiveness.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>These commands need to be executed in the system tenant.</p>
</main>

```sql
ALTER SYSTEM RUN JOB 'io_calibration';
```

After the calibration is completed, you can check the status of the calibration task by querying [GV$OB_IO_CALIBRATION_STATUS](../../../../../../700.system-views/300.system-view-of-sys-tenant/300.performance-view-of-sys-tenant/1100.gv-ob_io_calibration_status-of-sys-tenant.md) and the IOPS of each node by querying [GV$OB_IO_BENCHMARK](../../../../../../700.system-views/300.system-view-of-sys-tenant/300.performance-view-of-sys-tenant/1000.gv-ob_io_benchmark-of-sys-tenant.md). When configuring the IOPS of a unit, it is recommended to reserve about 10% of the IOPS based on the benchmark (for example, 90% of the IOPS corresponding to 16 KB read) to avoid disk full affecting the latency of online business.

```sql
-- View the calibration progress.
SELECT * FROM GV$OB_IO_CALIBRATION_STATUS;
-- Query the calibration values.
SELECT * FROM GV$OB_IO_BENCHMARK;
```

#### Step 2: Create a dedicated resource plan for LOB checks

In the business tenant where you want to run the check, you can create a dedicated resource plan. You can map LOB check-related background tasks to a dedicated resource group and limit the CPU and IOPS. The following example shows a resource plan named `LOB_CHECK` and a resource group named `LOB_CHECK`. The `FUNCTION` mapping maps background tasks with the value `LOB_CHECK` to this group. Please adjust the `MGMT_P1`, `UTILIZATION_LIMIT`, `MAX_IOPS`, `MIN_IOPS`, and `WEIGHT_IOPS` parameters as needed.

For the syntax and parameter descriptions of the `DBMS_RESOURCE_MANAGER` subprograms, see [DBMS_RESOURCE_MANAGER overview](../../../../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/13300.dbms-resource-manager-mysql/100.dbms-resource-manager-overview-mysql.md).

```sql
CALL DBMS_RESOURCE_MANAGER.CREATE_PLAN('LOB_CHECK', 'plan for lob_check');

CALL DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP( CONSUMER_GROUP => 'LOB_CHECK', COMMENT => 'LOB_CHECK');

CALL DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
  PLAN => 'LOB_CHECK',
  GROUP_OR_SUBPLAN => 'LOB_CHECK',
  COMMENT => 'LOB_CHECK_GROUP',
  MGMT_P1 => 30,
  UTILIZATION_LIMIT => 30,
  MAX_IOPS => 20,
  MIN_IOPS => 0,
  WEIGHT_IOPS => 20);

CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING('FUNCTION', 'LOB_CHECK', 'LOB_CHECK');
```

After the resource management plan is activated, the mapping and limits will take effect for sessions and background tasks:

```sql
SET GLOBAL resource_manager_plan = 'LOB_CHECK';
```

For the meaning and considerations of `resource_manager_plan`, see [resource_manager_plan](../../../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/11500.resource_manager_plan-global.md).

#### Step 4: Execute the LOB consistency check

1. Manually trigger the LOB consistency check

    ```sql
    -- Trigger the LOB consistency check for all tables with LOB auxiliary tables in this tenant.
    CALL DBMS_LOB_MANAGER.CHECK_LOB();
    -- Trigger the LOB consistency check for tables with the specified table IDs in this tenant.
    CALL DBMS_LOB_MANAGER.CHECK_LOB('[500001, 500003]');
    ```

2. Cancel the current task

    ```sql
    CALL DBMS_LOB_MANAGER.CANCEL_JOB("check_lob");
    ```

3. Pause the task

    ```sql
    CALL DBMS_LOB_MANAGER.SUSPEND_JOB("check_lob");
    ```

4. Resume the task

    ```sql
    CALL DBMS_LOB_MANAGER.RESUME_JOB("check_lob");
    ```

5. Modify the trigger cycle and start time of the scheduled task

    ```sql
    CALL DBMS_LOB_MANAGER.RESCHEDULE_JOB('2025-12-01 17:48:00', 'FREQ=DAYLY; INTERVAL=1');
    ```

#### Step 5: View the LOB consistency check results

You can query the `DBA_OB_LOB_CHECK_TASKS` view to view the progress of the LOB check task and the `DBA_OB_LOB_CHECK_EXCEPTION_RESULT` view to view the exception results.

```sql
SELECT * FROM DBA_OB_LOB_CHECK_TASKS;
SELECT * FROM DBA_OB_LOB_CHECK_EXCEPTION_RESULT;
```
