# HYBRID_SEARCH

The `HYBRID_SEARCH` function is used to perform full-text search, vector search, and filtering in a single `SELECT` statement by using a JSON string that conforms to the rules described in this topic. The function returns rows sorted by the hybrid search strategy.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This syntax is applicable only to MySQL mode. </p>
</main>

## Syntax

```sql
SELECT select_expr_list
FROM HYBRID_SEARCH(TABLE table_name, dsl_string) [table_alias];

-- select_expr_list is the SELECT list, which is the same as the syntax of a regular SELECT statement.
```

## Parameters

| Parameter | Description |
| --- | --- |
| `table_name` | The name of the target table. Only heap-organized tables (`ORGANIZATION = HEAP`) are supported, including partitioned and non-partitioned tables. |
| `dsl_string` | A JSON string that describes `query`, `knn`, `rank`, `from`, `size`, and `min_score`. <main id="notice" type='notice'><h4>Notice</h4><p>Except for the differences listed in the "Limitations and Considerations" section, the syntax structure and parameter descriptions are consistent with the <code>search_params</code> of the <a href="../../../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/9000.dbms-hybrid-search-mysql/200.search-mysql.md">SEARCH</a> procedure. Users familiar with the <code>SEARCH</code> syntax can directly understand the differences between the two. </p></main> |

## Global limitations and considerations

This section lists only the syntax limitations. For feature limitations, see the related document `Hybrid search (SQL interface)` at the end of this section, and understand it in conjunction with the content of this section.

Considerations:

* The top-level `query` (full-text search) and `knn` (vector search) can have a maximum of three subqueries combined: `query` counts as one; `knn` counts as one if it is an object, and each element counts as one if it is an array. The total number of these three types must not exceed three, and at least one full-text or vector search must be included.
* Column names in queries are case-insensitive.
* For vector queries, it is recommended to input the vector as a string.
* The `min_score` parameter is only supported in the SQL interface and not in the PL interface.
* Each `query` and `knn` is an independent search path, and the `filter` of one does not affect the others. If a search path requires a filter, the corresponding `filter` must be specified separately in that path. All search results will be merged into a single result set, scored and sorted based on the fusion algorithm, and the top `size` results will be returned.

Limitations:

* The `rank_feature`, `es_mode`, and `_source` parameters are not supported.
* Direct use of `WHERE`, `ORDER BY`, or `LIMIT` at the same level as `HYBRID_SEARCH` is not supported. If further filtering or sorting is needed, process the hybrid search results as a subquery first. For example:
    ```sql
    -- Not supported: Using WHERE at the same level as HYBRID_SEARCH
    SELECT id
    FROM HYBRID_SEARCH(TABLE doc_table, '{"knn":{"field":"vector","k":5,"query_vector":"[1,2,3]"}}')
    WHERE id > 3;

    -- Supported: Use a subquery for filtering
    SELECT id
    FROM (
      SELECT id
      FROM HYBRID_SEARCH(TABLE doc_table, '{"knn":{"field":"vector","k":5,"query_vector":"[1,2,3]"}}')
    ) t
    WHERE id > 3;
    ```
* Nested JSON/ARRAY elements cannot be pushed down if the path is an array of JSON elements.
* Scalar queries, including `term`, `range`, `terms`, `json`, and `array` expressions, do not support scoring or `boost`, and cannot be used in `must` or `should` of `bool`.
* `boost` for non-top-level full-text queries, `boost` for `bool` queries, and column weights and term weights for full-text queries must be greater than `0`. For other cases, `boost` must be greater than or equal to `0`.
* For `multi_match` and `query_string` with multiple full-text columns, the same character set and `collation` must be used, and the same `parser` must be used for the full-text index.
* When `match`, `multi_match`, or `query_string` is used for term-level matching, the corresponding full-text column must use `FTS_INDEX_TYPE = MATCH` (or the default type equivalent to `MATCH` if unspecified). `match_phrase` is only applicable to full-text indexed columns with `FTS_INDEX_TYPE = PHRASE_MATCH`.

## DSL_STRING syntax

`dsl_string` is a JSON string. The syntax of `dsl_string` is described in this section. For more information, see the parameters and examples in this section.

<main id="notice" type='notice'><h4>Recommended reading order</h4><p>First, read the <strong>DSL Skeleton Example</strong> to understand the overall structure of the JSON string. Then, refer to the <strong>BNF Definition</strong> for the syntax. For details about each field, see the <strong>Parameters</strong> table. For more information about how to create a table, see the related documents at the end of this section.</p></main>

### Syntax

This section describes the meaning and usage rules of BNF (Backus-Naur Form) syntax symbols:

1. Optional parameters

   * `[ ]` in BNF indicates that multiple elements are optional. For example, `param_list = param [, param]*` means that `param_list` can contain one or more `param` elements.
   * `[ ]` in `rank_expression` also indicates that the subparameters are optional.
   * `[, "boost" : boost_value]` indicates that the subparameter is optional in an expression that supports `boost`. The `term`, `range`, `terms`, and JSON/ARRAY scalar expressions do not support `boost`.

2. Arrays
   * `[ ]` in a JSON structure indicates an array. For example, `[condition_list]`.

3. Selection
   * `|` indicates a selection. For example, `param = "query" | "knn"` means that `param` can be either "query" or "knn".

4. Repetition
   * `*` indicates zero or more repetitions. For example, `param_list = param [, param]*` means that `param_list` can contain one or more `param` elements.

5. JSON format requirements
   * All JSON column names and string values must be enclosed in double quotation marks.
   * Numerical values do not need to be enclosed in double quotation marks.

### Syntax definition

This section provides a detailed explanation of the syntax for `dsl_string`. For parameter details, refer to the table below.

#### DSL skeleton example

The following is a skeleton of the `dsl_string` equivalent to the example in the "Full-text and vector RRF hybrid search" section. At the top level, you can use `query` (for full-text search), `knn` (for vector search), `rank` (for RRF fusion), `from` / `size` (for pagination), and so on. When performing a single search, you can remove the top-level keys that are not needed. The SQL interface also allows you to optionally add `min_score`, as shown in the parameter table.

:::collapse
```sql
SELECT * FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "match": {
        "content": "oceanbase mysql"
      }
    },
    "knn": {
      "field": "vector",
      "k": 5,
      "query_vector": "[1,2,3]"
    },
    "rank": {
      "rrf": {
        "rank_window_size": 10,
        "rank_constant": 60
      }
    },
    "from": 0,
    "size": 10
  }'
);
```
:::

#### Top-level parameter structure

The top-level parameter structure is used to specify the parameters for hybrid search.

```sql
dsl_string = '{param_list}'
    param_list = param [, param]*
    -- At least one of `query` and `knn` must be specified; both can be used in hybrid search.
    param = "query"     : {query_expression}
          | "knn"       : {knn_expression}
          | "rank"      : {rank_expression}
          | "from"      : number
          | "size"      : number
          | "min_score" : number -- Only supported in the SQL interface.
```

##### Query expression structure

The query expression structure is used to specify the full-text and scalar query conditions for hybrid search.

```sql
query_expression = bool_query | scalar_term | fulltext_term

bool_query = "bool" : {bool_condition_list}
    bool_condition_list = bool_condition [, bool_condition]*
    bool_condition = "must"    : [condition_list]
                  | "should"   : [condition_list]
                  | "must_not" : [condition_list]
                  | "filter"   : [condition_list]
                  | "boost"    : boost_value
    condition_list = query_expression [, query_expression]*
```

The values of `must`, `should`, `must_not`, and `filter` under `bool` are arrays of query expressions. Each item in the array is a complete `query_expression` (which can be nested within another `bool` or followed by `match` / `term`, and so on). The following example shows only the inner part of the `query` object:

:::collapse
```json
{
  "bool": {
    "must": [
      {
        "match": {
          "content": "oceanbase"
        }
      }
    ],
    "filter": [
      {
        "term": {
          "status": 1
        }
      }
    ]
  }
}
```
:::

###### Scalar query structure

The scalar query structure defines scalar query expressions within a single term. It includes `range_query`, `term_query`, and `terms_query`, which correspond to the `range`, `term`, and `terms` expressions in SQL syntax. These represent range queries, exact matches, and multi-value matches, respectively.

```sql
scalar_term = range_query | term_query | terms_query

range_query = "range" : {"field_name" : {range_condition_list}}
    range_condition_list = range_condition [, range_condition]*
    range_condition = "gte" : number
                    | "gt"  : number
                    | "lte" : number
                    | "lt"  : number

term_query = "term" : {term_condition_list}
    term_condition_list = term_condition [, term_condition]*
    term_condition = "field_name" : scalar_value
                   | "field_name" : term_value_object
    term_value_object = "value" : scalar_value

terms_query = "terms" : {terms_condition_list}
    terms_condition_list = terms_condition [, terms_condition]*
    terms_condition = "field_name" : [scalar_value_list]
    scalar_value_list = scalar_value [, scalar_value]*
```

###### Full-text query structure

The full-text query structure defines full-text query expressions within a single term. It includes `match_query`, `match_phrase_query`, `query_string`, and `multi_match`, which correspond to the `match`, `match_phrase`, `query_string`, and `multi_match` expressions in SQL syntax. These represent term-level matching, phrase-level matching, full-text search, and multi-column term-level matching, respectively.

```sql
fulltext_term = match_query | match_phrase_query | query_string | multi_match

match_query = "match" : {"field_name" : match_body}
    match_body = "string_value" | {match_condition}
    match_condition = "query" : "string_value" [, "operator" : ("OR" | "AND")] [, "minimum_should_match" : number] [, "boost" : boost_value]

match_phrase_query = "match_phrase" : {"field_name" : phrase_body}
    phrase_body = "string_value" | {phrase_condition}
    phrase_condition = "query" : "string_value" [, "slop" : number] [, "boost" : boost_value]

query_string = "query_string" : {query_string_condition}
    query_string_condition = "fields" : [field_weight_list]
                           | "query"  : "string_value" -- Supports term-level ^, as described in the section "Weighting operators".
                           | "boost"  : boost_value
                           | "type"   : ("best_fields" | "most_fields")
                           | "default_operator" : ("AND" | "OR")
                           | "minimum_should_match" : number

multi_match = "multi_match" : {multi_match_condition}
    multi_match_condition = "fields" : [field_weight_list]
                         | "query"  : "string_value" -- Does not support term-level ^ within the query string.
                         | "boost"  : boost_value
                         | "type"   : ("best_fields" | "most_fields")
                         | "operator" : ("AND" | "OR")
                         | "minimum_should_match" : number
    field_weight_list = field_weight [, field_weight]*
    field_weight = "field_name[^number]"
```

##### Vector and sorting structure

The vector and sorting structure is used to specify vector search parameters. You can configure the search vector field, similarity, filter conditions, weights, and other information. It supports single and multi-vector searches.

```sql
knn_expression = "knn" : {knn_condition_list} | [multi_knn_condition_list]
    knn_condition_list = knn_condition [, knn_condition]*
    knn_condition = "field"        : "field_name"
                 | "k"            : number
                 | "query_vector" : [vector_values]
                 | "filter"       : [condition_list]
                 | "similarity"   : number
                 | "boost"        : boost_value
    multi_knn_condition_list = {knn_condition} [, {knn_condition}]*
    vector_values = float [, float]*

rank_expression = "rank" : {rank_strategy}
    rank_strategy = "rrf" : {rrf_params}
    rrf_params = "rank_window_size" : number [, "rank_constant" : number]
```

For a single-vector search, `knn` is a single object. For a multi-vector search, `knn` is an array of objects, where each object contains a set of `knn_condition`. The following example shows only the `knn` part for a multi-vector search:

:::collapse
```json
{
  "knn": [
    {
      "field": "vector_a",
      "k": 3,
      "query_vector": "[1,0,0]"
    },
    {
      "field": "vector_b",
      "k": 3,
      "query_vector": "[0,1,0]"
    }
  ]
}
```
:::

The basic data types used in the syntax above.

```sql
field_name = "string_value"
field_list = field_name [, field_name]*
number = integer | decimal
boost_value = integer | float
boolean = true | false
scalar_value = "string_value" | number | boolean
```

#### Weight operator

The weight operator `^` specifies the weight of a column or a token in a **full-text query** statement. The syntax is `column^weight` or `token^weight`. For example, `"title^2.0"`. The following parameters are supported:

* Only `multi_match` and `query_string` support column-level weights.
* Only `query_string` supports token-level weights.

The weight operator specifies the weight of the token on its left. The default weight of a token without a weight operator is 1.0. A token with a weight operator or a group of consecutive tokens without a weight operator is considered a group.

```shell
{
  "query": {
    "query_string": {
      "fields": ["title^2.0", "content"],
      "query": "Red heart dragon fruit jelly orange^1.5 autumn moon pear^1.2 blueberry rambutan"
    }
  }
}
```

As shown in the example, the query token `"Red heart dragon fruit jelly orange^1.5 autumn moon pear^1.2 blueberry rambutan"` is divided into four groups: "Red heart" and "dragon fruit" with a default weight of 1.0, "jelly" and "orange" with a specified weight of 1.5, "autumn moon" and "pear" with a specified weight of 1.2, and "blueberry" and "rambutan" with a default weight of 1.0.

The weight operator can be used with the `boost` parameter. For more information, see the next section `boost parameter`.

#### boost parameter

The `boost` parameter specifies the weight of a query condition in the final relevance calculation. The value must be ≥ `0`. If not specified, the default value is `1`. In the above syntax, `bool`, `single_term`, single- and multi-vector search (`knn`) all support the `boost` parameter. The usage rules of `boost` are as follows:

1. Supported expressions for `boost`

    * `bool` queries.
    * Full-text queries, such as `match`, `match_phrase`, `query_string`, and `multi_match`.
    * Vector queries, such as single- and multi-vector search (`knn`).

2. Unsupported expressions for `boost`

    * Scalar queries: `term`, `range`, and `terms`.
    * JSON/ARRAY scalar expressions.

3. Value constraints

    * The `boost` parameter of non-top-level full-text queries, `bool` queries, and column-level and token-level weights of full-text queries must be greater than `0`.
    * The `boost` parameter in other cases must be greater than or equal to `0`.

4. Examples

    a. Query-level `boost` (`bool`):

    ```shell
    {
      "bool": {
        "filter": [{"term": {"category": "Gaming"}}],
        "boost": 2.0
      }
    }
    ```

    b. Column-level weight (`query_string`):

    ```shell
    {
      "query_string": {
        "fields": ["product_name^2.0", "description^1.0"],
        "query": "gaming keyboard",
        "boost": 1.5
      }
    }
    ```

    c. Vector query `boost` (`knn`):

    ```shell
    {
      "knn": {
        "field": "vector",
        "k": 5,
        "query_vector": "[1,2,3]",
        "boost": 1.5
      }
    }
    ```

## Examples

### Full-text search

This example searches for all rows in the `content` column of the `doc_table` table that contain `oceanbase mysql` and returns the top 4 matching records.

```sql
SELECT * FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "match": {"content": "oceanbase mysql"}
    }
  }'
);
```

### Hybrid full-text and vector RRF search

Create a sample table with a vector column, create a vector index for the vector column, and create full-text indexes for two `VARCHAR` columns.

```sql
CREATE TABLE doc_table(c1 INT, vector VECTOR(3), query VARCHAR(255), content VARCHAR(255), VECTOR INDEX idx1(vector) WITH (distance=l2, type=hnsw, lib=vsag), FULLTEXT INDEX idx2(query), FULLTEXT INDEX idx3(content));
```

Write data.

```sql
INSERT INTO doc_table VALUES(1, '[1,2,3]', "hello world", "oceanbase Elasticsearch database"),
                            (2, '[1,2,1]', "hello world, what is your name", "oceanbase mysql database"),
                            (3, '[1,1,1]', "hello world, how are you", "oceanbase oracle database"),
                            (4, '[1,3,1]', "real world, where are you from", "postgres oracle database"),
                            (5, '[1,3,2]', "real world, how old are you", "redis oracle database"),
                            (6, '[2,1,1]', "hello world, where are you from", "starrocks oceanbase database");
```

```sql
SELECT * FROM HYBRID_SEARCH(
```
