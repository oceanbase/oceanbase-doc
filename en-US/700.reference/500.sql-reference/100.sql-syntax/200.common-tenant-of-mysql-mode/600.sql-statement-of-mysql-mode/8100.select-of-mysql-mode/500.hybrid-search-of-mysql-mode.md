# HYBRID_SEARCH

The `HYBRID_SEARCH` function allows you to perform full-text search, vector search, and filtering in a single `SELECT` statement by specifying the search conditions in a JSON string that follows the syntax described in this topic. The results are returned sorted according to the hybrid search strategy.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This syntax is only applicable in MySQL mode. </p>
</main>

## Syntax

```sql
SELECT select_expr_list
FROM HYBRID_SEARCH(TABLE table_name, dsl_string) [table_alias];

-- select_expr_list is a SELECT list, which is consistent with the syntax of a regular SELECT statement.
```

## Parameters

| Parameter | Description |
| --- | --- |
| `table_name` | The name of the target table. Only heap-organized tables (`ORGANIZATION = HEAP`) are supported. The table can be partitioned or non-partitioned. |
| `dsl_string` | A JSON string that describes the `query`, `knn`, `rank`, `from`, `size`, and `min_score` parameters. <main id="notice" type='notice'><h4>Notice</h4><p>Except for the differences listed in the "Limitations and considerations" section, the syntax and parameter descriptions are the same as those of the <a href="../../../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/9000.dbms-hybrid-search-mysql/200.search-mysql.md">SEARCH</a> procedure's <code>search_params</code> parameter. Users who are familiar with the <code>SEARCH</code> procedure can directly understand the differences between the two procedures. </p></main> |

## General limitations and considerations

This section lists only the syntax limitations. For functional limitations, see the related documentation at the end of this topic: `Hybrid search (SQL interface)`. You must combine this information with the content of this section for a complete understanding.

Considerations:

* The `query` (full-text search) and `knn` (vector search) clauses at the top level can have a combined maximum of three subqueries: one for `query`, and one for each element in a `knn` array. The total number of subqueries must not exceed three, and at least one of them must be a full-text or vector search.
* Column names in queries are case-insensitive.
* For vector queries, it is recommended to input the vector as a string.
* The `min_score` parameter is only supported in the SQL interface and not in the PL interface.
* Each `query` and `knn` clause is an independent search path, and their respective `filter` clauses do not affect each other. If a search path requires a filter, it must be specified separately for that path. All search results will be merged into a single result set, scored, and sorted using a fusion algorithm, and the top `size` results will be returned.

Limitations:

* The `rank_feature`, `es_mode`, and `_source` parameters are not supported.
* You cannot use `WHERE`, `ORDER BY`, or `LIMIT` clauses at the same level as `HYBRID_SEARCH`. If you need to further filter or sort the results, you must first use `HYBRID_SEARCH` as a subquery. For example:
    ```sql
    -- Not supported: Using WHERE at the same level as HYBRID_SEARCH
    SELECT id
    FROM HYBRID_SEARCH(TABLE doc_table, '{"knn":{"field":"vector","k":5,"query_vector":"[1,2,3]"}}')
    WHERE id > 3;

    -- Supported: First use HYBRID_SEARCH as a subquery, then apply the filter
    SELECT id
    FROM (
      SELECT id
      FROM HYBRID_SEARCH(TABLE doc_table, '{"knn":{"field":"vector","k":5,"query_vector":"[1,2,3]"}}')
    ) t
    WHERE id > 3;
    ```
* Some nested JSON/ARRAY element paths are not supported for pushing down, such as when the `path` in `json` is an `array` containing `json` elements. In this case, you cannot specify a path for the `json` elements.
* Scalar queries, including `term`, `range`, `terms`, `json`, and `array` expressions, do not support scoring or `boost`. They cannot be used in the `must` or `should` clauses of a `bool` query.
* The `boost` parameter for non-top-level full-text queries, the `boost` parameter for `bool` queries, and the column and term weights for full-text queries must be greater than `0`. For other types of `boost` parameters, the value must be greater than or equal to `0`.
* For `multi_match` and `query_string` queries involving multiple full-text columns, the columns must use the same character set and `collation`, and the full-text index must use the same `parser`.
* When `match`, `multi_match`, or `query_string` is used for term-level matching, the corresponding full-text column must use `FTS_INDEX_TYPE = MATCH` (or the default type equivalent to `MATCH` if not specified). `match_phrase` is only applicable to full-text columns with `FTS_INDEX_TYPE = PHRASE_MATCH`.

## DSL_STRING syntax

`dsl_string` is a JSON-formatted string. The syntax of `dsl_string` is described in this section. Please refer to the parameters and examples below for a better understanding.

<main id="notice" type='notice'><h4>Recommended reading order</h4><p>First, read the <strong>DSL skeleton example</strong> to understand the top-level fields that make up the overall structure. Then, refer to the <strong>BNF definitions</strong> as needed. For detailed descriptions of each field and its constraints, consult the <strong>Parameters</strong> table. For end-to-end table creation and additional scenario examples, see the relevant documentation index at the end of this section (SQL interface).</p></main>

### Syntax

This section describes the meaning and usage rules of BNF (Backus-Naur Form) syntax symbols:

1. Optional parameters

   * In BNF, `[ ]` indicates that multiple elements are optional. For example, `param_list = param [, param]*` means that `param_list` can contain one or more `param` elements.
   * In `rank_expression`, `[ ]` also indicates that subparameters are optional.
   * `[, "boost" : boost_value]` indicates that the subparameter is optional in an expression that supports `boost`. The `term`, `range`, `terms`, and JSON/ARRAY scalar expressions do not support `boost`.

2. Arrays
   * In JSON structures, `[ ]` indicates an array. For example, `[condition_list]`.

3. Selection relationships
   * `|` indicates a selection relationship. For example, `param = "query" | "knn"` means that `param` can be either "query" or "knn".

4. Repeats
   * `*` indicates zero or more repetitions. For example, `param_list = param [, param]*` means that `param_list` can contain one or more `param` elements.

5. JSON format requirements
   * All JSON column names and string values must be enclosed in double quotation marks.
   * Numerical values do not need to be enclosed in double quotation marks.

### Syntax definition

This section provides a detailed explanation of the syntax structure of `dsl_string`. For more information about the parameters, see the table below.

#### DSL skeleton example

The following is a skeleton of the `dsl_string` used in the "Full-text and vector RRF hybrid search" example. At the top level, you can specify `query` (full-text), `knn` (vector), `rank` (such as RRF), `from` / `size` (paging), and so on. When you perform a single search, you can delete the top-level keys that are not needed. The SQL interface also supports the optional `min_score` parameter. For more information, see the table below.

:::collapse
```sql
SELECT * FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "match": {
        "content": "oceanbase mysql"
      }
    },
    "knn": {
      "field": "vector",
      "k": 5,
      "query_vector": "[1,2,3]"
    },
    "rank": {
      "rrf": {
        "rank_window_size": 10,
        "rank_constant": 60
      }
    },
    "from": 0,
    "size": 10
  }'
);
```
:::

#### Top-level parameter structure

The top-level parameter structure specifies the parameters for hybrid search.

```sql
dsl_string = '{param_list}'
    param_list = param [, param]*
    -- At least one of `query` and `knn` must be specified. You can specify both for hybrid search.
    param = "query"     : {query_expression}
          | "knn"       : {knn_expression}
          | "rank"      : {rank_expression}
          | "from"      : number
          | "size"      : number
          | "min_score" : number -- Supported only in the SQL interface.
```

##### Query expression structure

The query expression structure specifies the full-text and scalar query conditions for hybrid search.

```sql
query_expression = bool_query | scalar_term | fulltext_term

bool_query = "bool" : {bool_condition_list}
    bool_condition_list = bool_condition [, bool_condition]*
    bool_condition = "must"    : [condition_list]
                  | "should"   : [condition_list]
                  | "must_not" : [condition_list]
                  | "filter"   : [condition_list]
                  | "boost"    : boost_value
    condition_list = query_expression [, query_expression]*
```

The values of `must` / `should` / `must_not` / `filter` under `bool` are arrays of query expressions. Each item in the array is a complete `query_expression` (which can be nested `bool` or followed by `match` / `term` and so on). The following example shows only the inner part of the `query` object:

:::collapse
```json
{
  "bool": {
    "must": [
      {
        "match": {
          "content": "oceanbase"
        }
      }
    ],
    "filter": [
      {
        "term": {
          "status": 1
        }
      }
    ]
  }
}
```
:::

###### Scalar query structure

The scalar query structure defines scalar query expressions in a single term. It includes `range_query`, `term_query`, and `terms_query`, which correspond to the `range`, `term`, and `terms` expressions in SQL syntax. These expressions represent range queries, exact matches, and multi-value matches, respectively.

```sql
scalar_term = range_query | term_query | terms_query

range_query = "range" : {"field_name" : {range_condition_list}}
    range_condition_list = range_condition [, range_condition]*
    range_condition = "gte" : number
                    | "gt"  : number
                    | "lte" : number
                    | "lt"  : number

term_query = "term" : {term_condition_list}
    term_condition_list = term_condition [, term_condition]*
    term_condition = "field_name" : scalar_value
                   | "field_name" : term_value_object
    term_value_object = "value" : scalar_value

terms_query = "terms" : {terms_condition_list}
    terms_condition_list = terms_condition [, terms_condition]*
    terms_condition = "field_name" : [scalar_value_list]
    scalar_value_list = scalar_value [, scalar_value]*
```

###### Full-text query structure

The full-text query structure defines full-text query expressions in a single term. It includes `match_query`, `match_phrase_query`, `query_string`, and `multi_match`, which correspond to the `match`, `match_phrase`, `query_string`, and `multi_match` expressions in SQL syntax. These expressions represent term-level matches, phrase-level matches, full-text queries, and multi-column term-level matches, respectively.

```sql
fulltext_term = match_query | match_phrase_query | query_string | multi_match

match_query = "match" : {"field_name" : match_body}
    match_body = "string_value" | {match_condition}
    match_condition = "query" : "string_value" [, "operator" : ("OR" | "AND")] [, "minimum_should_match" : number] [, "boost" : boost_value]

match_phrase_query = "match_phrase" : {"field_name" : phrase_body}
    phrase_body = "string_value" | {phrase_condition}
    phrase_condition = "query" : "string_value" [, "slop" : number] [, "boost" : boost_value]

query_string = "query_string" : {query_string_condition}
    query_string_condition = "fields" : [field_weight_list]
                           | "query"  : "string_value" -- The query string can contain ^ at the term level. For more information, see the description of the weight operator below.
                           | "boost"  : boost_value
                           | "type"   : ("best_fields" | "most_fields")
                           | "default_operator" : ("AND" | "OR")
                           | "minimum_should_match" : number

multi_match = "multi_match" : {multi_match_condition}
    multi_match_condition = "fields" : [field_weight_list]
                         | "query"  : "string_value" -- The query string cannot contain ^ at the term level.
                         | "boost"  : boost_value
                         | "type"   : ("best_fields" | "most_fields")
                         | "operator" : ("AND" | "OR")
                         | "minimum_should_match" : number
    field_weight_list = field_weight [, field_weight]*
    field_weight = "field_name[^number]"
```

##### Vector and sorting structure

The vector and sorting structure specifies the parameters for vector search. You can configure the vector field, similarity, filter conditions, weights, and so on. It supports single- and multi-vector searches.

```sql
knn_expression = "knn" : {knn_condition_list} | [multi_knn_condition_list]
    knn_condition_list = knn_condition [, knn_condition]*
    knn_condition = "field"        : "field_name"
                 | "k"            : number
                 | "query_vector" : [vector_values]
                 | "filter"       : [condition_list]
                 | "similarity"   : number
                 | "boost"        : boost_value
    multi_knn_condition_list = {knn_condition} [, {knn_condition}]*
    vector_values = float [, float]*

rank_expression = "rank" : {rank_strategy}
    rank_strategy = "rrf" : {rrf_params}
    rrf_params = "rank_window_size" : number [, "rank_constant" : number]
```

For single-vector search, `knn` is a single object. For multi-vector search, `knn` is an array of objects. Each object contains a `knn_condition`. The following example shows only the `knn` part for multi-vector search:

:::collapse
```json
{
  "knn": [
    {
      "field": "vector_a",
      "k": 3,
      "query_vector": "[1,0,0]"
    },
    {
      "field": "vector_b",
      "k": 3,
      "query_vector": "[0,1,0]"
    }
  ]
}
```
:::

#### Basic type definitions

The basic data types used in the syntax above.

```sql
field_name = "string_value"
field_list = field_name [, field_name]*
number = integer | decimal
boost_value = integer | float
boolean = true | false
scalar_value = "string_value" | number | boolean
```

#### Weight operator description

The weight operator `^` is used to specify the weight of a column or token in a **full-text query** statement. The syntax is `column_name^weight` or `token^weight`, for example, `"title^2.0"`. The supported parameters are as follows:

* Only `multi_match` and `query_string` support column-level weights.
* Only `query_string` supports token-level weights.

The token-level weight operator specifies the weight of the token on its left (up to the space). The default weight for tokens without a weight operator is 1.0. A group consists of one token with a weight operator or a sequence of tokens without a weight operator.

```shell
{
  "query": {
    "query_string": {
      "fields": ["title^2.0", "content"],
      "query": "Red heart dragon fruit jelly orange^1.5 autumn moon pear^1.2 blueberry rambutan"
    }
  }
}
```

As shown in the example, when querying the tokens `"Red heart dragon fruit jelly orange^1.5 autumn moon pear^1.2 blueberry rambutan"`, the tokens are divided into four groups: "Red heart" and "dragon fruit" with a default weight of 1.0, "jelly" and "orange" with a specified weight of 1.5, "autumn moon" and "pear" with a specified weight of 1.2, and "blueberry" and "rambutan" with a default weight of 1.0.

The weight operator can be used with the `boost` parameter. For more information, see the next section `boost parameter description`.

#### boost parameter description

The `boost` parameter specifies the weight of the query condition in the final relevance calculation. The value must be ≥ `0`. If not specified, the default value is `1`. In the above syntax structure, `bool`, `single_term`, and single- and multi-vector searches (`knn`) support the `boost` parameter. Considering the limitations mentioned in this article, the usage rules for `boost` are as follows:

1. Supported expressions for `boost`

    * `bool` queries.
    * Full-text queries, such as `match`, `match_phrase`, `query_string`, and `multi_match`.
    * Vector queries (single- and multi-vector `knn`).

2. Unsupported expressions for `boost`

    * Scalar queries: `term`, `range`, and `terms`.
    * JSON/ARRAY scalar expressions.

3. Value constraints

    * The `boost` parameter for non-top-level full-text queries, `bool` queries, column weights, and token weights must be greater than `0`.
    * The `boost` parameter in other cases must be greater than or equal to `0`.

4. Examples

    a. Query-level `boost` (`bool`):

    ```shell
    {
      "bool": {
        "filter": [{"term": {"category": "Gaming"}}],
        "boost": 2.0
      }
    }
    ```

    b. Column-level weight (`query_string`):

    ```shell
    {
      "query_string": {
        "fields": ["product_name^2.0", "description^1.0"],
        "query": "gaming keyboard",
        "boost": 1.5
      }
    }
    ```

    c. Vector query `boost` (`knn`):

    ```shell
    {
      "knn": {
        "field": "vector",
        "k": 5,
        "query_vector": "[1,2,3]",
        "boost": 1.5
      }
    }
    ```

### Full-text search

This example searches for all rows in the `content` column of the `doc_table` table that contain `oceanbase mysql` and returns the top 4 matching records.

```sql
SELECT * FROM HYBRID_SEARCH(
  TABLE doc_table,
  '{
    "query": {
      "match": {"content": "oceanbase mysql"}
    }
```

### Hybrid full-text and vector RRF search

Create a sample table with a vector column, create a vector index for it, and create full-text indexes for two `VARCHAR` columns.

```sql
CREATE TABLE doc_table(c1 INT, vector VECTOR(3), query VARCHAR(255), content VARCHAR(255), VECTOR INDEX idx1(vector) WITH (distance=l2, type=hnsw, lib=vsag), FULLTEXT INDEX idx2(query), FULLTEXT INDEX idx3(content));
```

Insert data.

```sql
INSERT INTO doc_table VALUES(1, '[1,2,3]', "hello world", "oceanbase Elasticsearch database"),
                            (2, '[1,2,1]', "hello world, what is your name", "oceanbase mysql database"),
                            (3, '[1,1,1]', "hello world, how are you", "oceanbase oracle database"),
                            (4, '[1,3,1]', "real world, where are you from", "postgres oracle database"),
                            (5, '[1,3,2]', "real world, how old are you", "redis oracle database"),
```

```sql
SELECT * FROM HYBRID_SEARCH(
```
