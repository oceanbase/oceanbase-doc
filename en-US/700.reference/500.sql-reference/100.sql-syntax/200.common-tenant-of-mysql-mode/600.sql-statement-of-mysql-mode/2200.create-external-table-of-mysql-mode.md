# CREATE EXTERNAL TABLE

## Purpose

You can use this statement to create an external table in the database.

An external table is a key feature in a database management system. Generally, the data of a table in the database is stored in the storage space of the database, while an external table is used to access data stored in external storage services.

When you create an external table, you must define the file path and file format of its data, so that users can read the data from the external storage service. External tables are read-only. You can query an external table, but cannot perform DML operations on it. You cannot define constraints or create indexes on external tables.

## Syntax

```sql
CREATE EXTERNAL TABLE table_name (column_definition_list)
    LOCATION = 'file_name'
    FORMAT = (format_type_options)
    [PARTITION BY (column_name [, column_name ...])]
    [PARTITION_TYPE = USER_SPECIFIED]
    [PATTERN = 'regex_pattern']
    [AUTO_REFRESH = 'xxx'];

column_definition_list:
    column_definition [, column_definition ...]

column_definition:
    column_name column_type [AS expr]

format_type_options:
    type_csv_option
    | type_parquet_option
    | type_orc_option

type_csv_option:
    TYPE = 'CSV'
    LINE_DELIMITER = '<string>' | <expr>
    FIELD_DELIMITER = '<string>' | <expr>
    ESCAPE = '<character>' | <expr>
    FIELD_OPTIONALLY_ENCLOSED_BY = '<character>' | <expr>
    ENCODING = 'charset'
    NULL_IF = ('<string>' | <expr>, '<string>' | <expr> ...)
    SKIP_HEADER = <int>
    SKIP_BLANK_LINES = {TRUE | FALSE}
    TRIM_SPACE = {TRUE | FALSE}
    EMPTY_FIELD_AS_NULL = {TRUE | FALSE}

type_parquet_option:
    TYPE = 'PARQUET'

type_orc_option:
    TYPE = 'ORC'
```

## Parameters

|             **Parameter**            |            **Description**              |
|-----------------------------------|-----------------------------------|
| table_name | The name of the external table to be created. |
| column_name | The name of the column in the external table. By default, the data columns in the file are automatically mapped to the columns defined in the external table. |
| column_type | The type of the column in the external table. Constraints such as `DEFAULT`, `NOT NULL`, `UNIQUE`, `CHECK`, `PRIMARY KEY`, and `FOREIGN KEY` cannot be defined. |
| AS expr     | Manually specifies the mappings between columns. If the order of columns in the file does not match that in the external table, you can use the pseudo-columns `metadata$filecol{N}` to specify the mappings between the columns in the external table and the Nth column in the file. For example, `c2 INT AS (metadata$filecol4)` indicates that the `c2` column in the external table corresponds to the fourth column in the file. Note that if you specify manual column mappings, automatic mappings will become invalid, and you will need to define mappings for all columns manually. |
| LOCATION = 'file_name' | The path where the external table file is stored. Generally, the data files of an external table are stored in a dedicated directory. The directory can contain subdirectories. When the external table is created, it automatically collects all files in the directory. For more information, see [file_name](#file_name). |
| FORMAT = (format_type_options) | Specifies the attributes of the external file format. Use `TYPE` to specify the format as `CSV`, `PARQUET`, or `ORC`. This parameter cannot be left empty. For more information, see [format_type_options](#format_type_options). |
| PATTERN    | A regular pattern string used to filter files in the `LOCATION` directory. For each file in the `LOCATION` directory, if the file path matches the pattern string, the external table will access the file. Otherwise, it will skip the file. If this parameter is not specified, the external table will default to accessing all files in the `LOCATION` directory. The external table will store the list of files that match the `LOCATION` directory path in the database system table. During a scan, the external table will access external files based on this list. |
| PARTITION_TYPE = USER_SPECIFIED | When you need to manually add and remove partitions yourself, instead of letting the external table automatically manage partitions, you need to specify `PARTITION_TYPE = USER_SPECIFIED`. |
| AUTO_REFRESH = 'xxx' | Specifies whether the external table should automatically refresh. Valid values: <ul><li>`OFF`: the default value, indicating that automatic refresh is disabled. </li><li>`INTERVAL`: allows you to manage automatic refresh rules for this external table using `dbms_external_table`. </li><li>`IMMEDIATE`: indicates that each SQL access to this external table requires refreshing the related external table META. </li></ul>|

### file_name

The path where the external file is stored has the following formats:

* If the file is stored locally, the `LOCATION` format is as follows: `LOCATION = '[file://] local_file_path'`, where `local_file_path` can be a relative path or an absolute path. If you specify a relative path, the current directory must be the installation directory of OceanBase Database. `secure_file_priv` specifies the file path that the OBServer node has the permission to access. `local_file_path` must be a subpath of the path specified by `secure_file_priv`.

* If the file is stored remotely, the `LOCATION` format is as follows:

  * If the remote file is stored on Alibaba Cloud OSS or AWS S3, the format is as follows: `LOCATION = '{oss\|s3}://$ACCESS_ID:$ACCESS_KEY@$HOST:s3_region/remote_file_path'`, where `$ACCESS_ID`, `$ACCESS_KEY`, and `$HOST` are the access information required to access Alibaba Cloud OSS, AWS S3, and object storage services compatible with the S3 protocol. `s3_region` is the region information selected when you use S3. These sensitive access information is stored in the system tables of the database in an encrypted manner.
  * If the remote file is stored on HDFS, the format is as follows: `LOCATION = hdfs://localhost:port/PATH`, where `localhost` indicates the address of HDFS, `port` indicates the port number of HDFS, and `PATH` indicates the directory path in HDFS.

    * For HDFS with Kerberos authentication, the format is as follows: `LOCATION = 'hdfs://localhost:port/user?principal=xxx&keytab=xxx&krb5conf=xxx&configs=xxx'`. The parameters in the path are separated with <code>&</code>. The following parameters are described:

      * `principal`: the login authentication user.
      * `keytab`: the key file for user authentication.
      * `krb5conf`: the description file for the Kerberos environment.
      * `configs`: the additional HDFS configuration. By default, it is empty. However, in a Kerberos environment, this parameter is usually configured with a value. For example, `dfs.data.transfer.protection=authentication,privacy`, which specifies the data transfer protection level to be `authentication` and `privacy`.

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>When you use object storage paths, make sure that the values of the parameters in the object storage path only contain uppercase and lowercase letters, numbers, <code>/-_$+=</code>, and wildcard characters. If other characters are included, the setting may fail. </p>
  </main>

### format_type_options

* `TYPE = 'CSV'`: specifies the format of the external file as CSV. The following fields are also included:

  * `LINE_DELIMITER`: specifies the line delimiter for the CSV file. The default value is `LINE_DELIMITER='\n'`.
  * `FIELD_DELIMITER`: specifies the field delimiter for the CSV file. The default value is `FIELD_DELIMITER='\t'`.
  * `ESCAPE`: specifies the escape character for the CSV file, which can be only 1 byte in length. The default value is `ESCAPE ='\'`.
  * `FIELD_OPTIONALLY_ENCLOSED_BY`: specifies the characters that enclose the field values in the CSV file. The default value is an empty string.

    <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>If the external data file contains <code>NULL</code> values (not the string <b>NULL</b>, that is, not <b>"NULL"</b>), you must explicitly specify the <code>FIELD_OPTIONALLY_ENCLOSED_BY</code> parameter and set it to a nonempty value. </p>
    </main>

  * `ENCODING`: specifies the character set encoding format of the file. For the character sets supported in MySQL mode, see [Character set](../100.basic-elements-of-mysql-mode/300.character-set-and-collation-of-mysql-mode/200.character-set-of-mysql-mode.md). If this parameter is not specified, the default value UTF8MB4 takes effect.
  * `NULL_IF`: specifies the strings to be treated as `NULL` values. The default value is an empty string.
  * `SKIP_HEADER`: specifies to skip the file header, and specifies the number of lines to skip.
  * `SKIP_BLANK_LINES`: specifies whether to skip blank lines. The default value is `FALSE`, which specifies not to skip blank lines.
  * `TRIM_SPACE`: specifies whether to remove leading and trailing spaces from fields in the file. The default value is `FALSE`, which specifies not to remove leading and trailing spaces from fields in the file.
  * `EMPTY_FIELD_AS_NULL`: specifies whether to treat empty strings as `NULL` values. The default value is `FALSE`, which specifies not to treat empty strings as `NULL` values.

* `TYPE = 'PARQUET'`: specifies the format of the external file as `PARQUET`.
* `TYPE = 'ORC'`: specifies the format of the external file as `ORC`.

## Usage notes

* If an external file is deleted, the file no longer exists in the file list when the external table accesses the file list. In this case, the external table ignores the non-existent file.
* If an external file is modified, the external table accesses the latest data of the external file. If the modification of the external file conflicts with the query of the external table, the result may not meet the expectation. Therefore, you are recommended to avoid modifying the external file while the external table is querying the file.
* If a new file is added to an external directory, the external table only accesses the files in the file list. If you want to add the new file to the file list of the external table, you need to update the files of the external table.

## Example

### Example 1

1. Prepare data. Set the path of `secure_file_priv` to `/home/admin/`, and place the `extdata.csv` file, which corresponds to the external data to be imported, in the `/home/admin/test` directory on the current local OBServer node.

   Here is an example of setting the global security path:

   ```shell
   obclient> SET GLOBAL secure_file_priv = ""
   Query OK, 0 rows affected
   obclient> \q
   Bye
   ```

   <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>Since <code>secure_file_priv</code> is a <code>GLOBAL</code> variable, you need to execute <code>\q</code> to exit and make the setting take effect. </p>
   </main>

   The content of the CSV file is as follows:

   ```shell
   1,'Dave','Smith','dsmith@outlook.com','friend',32
   2,'Xena','Johnson','xjonson@outlook.com','contact',45
   3,'Fred','Jackon','fjackson@outlook.com','co-worker',19
   4,'Alma','Tyler','atyler@outlook.com','friend',53
   ```

2. Log in to the database as the user tenant and create the external table `contacts`.

   ```shell
   obclient> CREATE EXTERNAL TABLE contacts (
       id    INT,
       firstname  VARCHAR(100),
       lastname   VARCHAR(100),
       email      VARCHAR(255),
       category   CHAR(30),
       age        NUMBER
      )
      LOCATION = '/home/admin/test'
      FORMAT = (
        TYPE = 'CSV'
        FIELD_DELIMITER = ','
        FIELD_OPTIONALLY_ENCLOSED_BY ='\''
       )
     PATTERN = 'extdata.csv';
   ```

3. Query data in the `contacts` table.

   ```shell
   obclient> SELECT * FROM contacts;
   +----+-----------+----------+----------------------+-----------+------+
   | id | firstname | lastname | email                | category  | age  |
   +----+-----------+----------+----------------------+-----------+------+
   |  1 | Dave      | Smith    | dsmith@outlook.com   | friend    |   32 |
   |  2 | Xena      | Johnson  | xjonson@outlook.com  | contact   |   45 |
   |  3 | Fred      | Jackon   | fjackson@outlook.com | co-worker |   19 |
   |  4 | Alma      | Tyler    | atyler@outlook.com   | friend    |   53 |
   +----+-----------+----------+----------------------+-----------+------+
   4 rows in set  
   ```

### Example 2

1. Assume that a CSV file exists under a directory on HDFS. The file contains the following data:

    ```sql
    $hdfs dfs -cat /user/test_tbl1.csv
    1,'Emma','2021-09-01'
    2,'William','2021-09-02'
    3,'Olivia','2021-09-03'
    ```

2. Create an HDFS external table.

    **If Kerberos authentication is not enabled in the target HDFS environment:**

    ```shell
    CREATE EXTERNAL TABLE test_tbl1_csv_mysql ( 
      id INT, 
      name VARCHAR(50), 
      c_date    DATE
    )
    LOCATION = 'hdfs://${hadoop namenode hostname}:${hadoop namenode port}/user'
    FORMAT = (
    TYPE = 'CSV'
    FIELD_DELIMITER = ','
    FIELD_OPTIONALLY_ENCLOSED_BY ='\''
    )
    PATTERN = 'test_tbl1.csv';
    ```

    <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>Here, <code>hadoop namenode hostname</code> and <code>hadoop namenode port</code> indicate the hostname and port of the HDFS node, respectively. You need to replace them with actual values. </p>
    </main>

    **If Kerberos authentication is enabled in the target HDFS environment:**

    1. Environment preparation
      The current HDFS bridge implementation uses the jni framework. Therefore, a Java runtime environment is required. If multiple nodes are set for the OBServer, this environment configuration is required on each node.

        **Step 1:** Configure the Java environment

        You can download OpenJDK 8 from [openjdk](https://www.openlogic.com/openjdk-downloads?field_java_parent_version_target_id=416&field_operating_system_target_id=426&field_architecture_target_id=391&field_java_package_target_id=396&page=0).

        **Step 2:** Decompress the installation package

        After decompression, you will find the following files:

        ```sql
        $ ls $JAVA_HOME
        ASSEMBLY_EXCEPTION  bin  include  jre  lib  LICENSE  man  NOTICE  release  sample  src.zip  THIRD_PARTY_README
        ```

        **Step 3:** Configure the HDFS.so dynamic library

        You can download the required dependencies from [https://mirrors.aliyun.com/oceanbase/](https://mirrors.aliyun.com/oceanbase/).  
        After downloading, install them using the following command:

        ```shell
        sudo rpm -Uvh
        devdeps-hdfs-sdk-3.3.6-xxxxx.xxx.xxx.rpm
        ```

        Run the following command to check whether the installation meets expectations. There should be `libhdfs.so` and `libhdfs.so.0.0.0` files, and the corresponding symbolic links should be correct.

        ```shell
        $ll /usr/local/oceanbase/deps/devel/lib
        total 376
        lrwxrwxrwx 1 root root     16 Dec 24 19:49 libhdfs.so -> libhdfs.so.0.0.0
        -rwxr-xr-x 1 root root 384632 Dec 24 19:09 libhdfs.so.0.0.0
        ```

        **Step 4:** Deploy and configure the path for the dependent jar packages  

        After downloading the required jar packages, you can execute the following command to extract and install them:

        ```shell
        sudo rpm -Uvh
        devdeps-java-extensions-3.3.6--xxxxx.xxx.xxx.rpm
        ```

        Check whether the installation meets expectations:

        ```shell
        $ll /home/admin/oceanbase/jni_packages
        total 52756
        drwxr-sr-x 4 root root     4096 Dec 24 20:25 hadoop
        drwxr-xr-x 3 root root     4096 Dec 24 20:25 lib
        -rw-r--r-- 1 root root 54008720 Dec 24 19:52 oceanbase-odps-connector-jar-with-dependencies.jar
        ```

    2. Start OBServer

        Before using the HDFS external table feature, you need to configure the corresponding OBServer node settings. Refer to the following steps:

        <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>Currently, the jni-related configuration options supported by OBServer cannot be dynamically updated and take effect immediately. Therefore, if you need to modify Java environment variables, you must restart OBServer for the changes to take effect. All the following configuration options are cluster-wide settings, meaning they only need to be set once and do not require individual configuration on each node.</p>
        </main>

        * Use the `sys` tenant to execute the following command to enable Java environment support in OBServer:

          ```sql
          alter system set ob_enable_java_env=true;
          ```

        * Execute the following command to set the Java home path for OBServer:

          ```sql
          alter system set ob_java_home="/home/user/openjdk/jdk8u422-b05";
          ```

          <main id="notice" type='explain'>
          <h4>Note</h4>
          <p>The path corresponds to the installation path of OpenJDK Java.</p>
          </main>

        * Configure the Java environment startup options:

          <main id="notice" type='notice'>
          <h4>Note</h4>
          <p>Changes to this configuration require an OBServer restart to take effect. Since the current HDFS integration uses memory copying to directly transfer the HDFS data stream to the C++ memory heap, you can appropriately reduce the settings for <code>-Xmx2048m</code> and <code>-Xms2048m</code>.</p>
          </main>

          ```sql
          alter system set ob_java_opts="-Djdk.lang.processReaperUseDefaultStackSize=true -XX:+HeapDumpOnOutOfMemoryError -Xmx2048m -Xms2048m -Xloggc:/home/user/jvmlogs/gc.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/home/user/jvmlogs/heapdumps/ -XX:+UseG1GC -XX:-CriticalJNINatives";
          ```

          <main id="notice" type='explain'>
          <h4>Note</h4>
          <p>In the above configuration, <code>/home/user/jvmlogs</code> and <code>/home/user/jvmlogs/heapdumps</code> are paths for generating corresponding log files. You need to manually create these directories.</p>
          </main>

        * Set the available `LD_LIBRARY_PATH`:

          <main id="notice" type='explain'>
          <h4>Note</h4>
          <p>Since the JNI SDK supported by OBServer is an extension feature and uses dynamic libraries loaded dynamically, you need to configure the corresponding dynamic library path by setting `LD_LIBRARY_PATH`. This configuration must be applied to all OBServer nodes for proper functionality.</p>
          </main>

          ```shell
          $ vim ~/.bashrc
          export LD_LIBRARY_PATH=/home/user/openjdk/jdk8u422-b05/jre/lib/amd64/server:/usr/local/oceanbase/deps/devel/lib
          ```

    3. Create an HDFS external table

        <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>When using Kerberos authentication, the corresponding OBServer nodes need to be configured with the relevant keytab (user authentication key file) and krb5conf files.</p>
        </main>

        ```shell
        CREATE EXTERNAL TABLE partsupp  ( PS_PARTKEY     INTEGER ,
        PS_SUPPKEY     INTEGER ,
        PS_AVAILQTY    INTEGER ,
        PS_SUPPLYCOST  DECIMAL(15,2)  ,
        PS_COMMENT     VARCHAR(199)  
        ) LOCATION = 'hdfs://localhost:8020/tpch_csv?principal=principal_str&keytab=/path/to/keytab&krb5conf=/path/to/krb5conf_file&configs=xxx=xxx#xxx=xxx'
        FORMAT = (
          TYPE = 'CSV'
          FIELD_DELIMITER = '|'
          FIELD_OPTIONALLY_ENCLOSED_BY ='"'
          )
        PATTERN = 'partsupp.tbl';
        ```

3. Query data from the external table

    ```shell
    select * from test_tbl1_csv_mysql;
    ```

    The query result is as follows:
  
    ```sql
    +----+----------+------------+
    | id | name     | c_date     |
    +----+----------+------------+
    |  1 | Emma     | 2021-09-01 |
    |  2 | William  | 2021-09-02 |
    |  3 | Olivia   | 2021-09-03 |
    +----+----------+------------+
    3 rows in set
    ```
