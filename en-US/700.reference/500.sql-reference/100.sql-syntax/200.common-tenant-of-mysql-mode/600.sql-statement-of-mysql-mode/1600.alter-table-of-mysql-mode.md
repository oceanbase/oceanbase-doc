# ALTER TABLE

## Purpose

This statement is used to modify the structure of an existing table, such as modifying the table and its attributes, adding columns, modifying columns and their attributes, and deleting columns.

## Syntax

```sql
alter_table_stmt:
    ALTER TABLE table_name alter_table_action_list;

alter_table_action_list:
    alter_table_action [, alter_table_action ...]

alter_table_action:
      ADD [COLUMN] column_definition
          [ opt_position_column ]
    | ADD [COLUMN] (column_definition_list)
    | ADD [CONSTRAINT [constraint_name]] UNIQUE {INDEX | KEY}
          [index_name] index_desc
    | ADD [CONSTRAINT [constraint_name]] FOREIGN KEY
          [index_name] index_desc
          REFERENCES reference_definition
          [match_action][opt_reference_option_list]
    | ADD PRIMARY KEY (column_name)
    | ADD CONSTRAINT [constraint_name] CHECK (expression)[[NOT] ENFORCED]
    | ADD PARTITION (range_partition_list)
    | ADD {INDEX | KEY} [index_name] [index_type] (key_part,...) [index_option_list][index_column_group_option]
    | ADD FULLTEXT [INDEX | KEY] [index_name](column_name, [column_name ...]) [WITH PARSER tokenizer_option] [PARSER_PROPERTIES[=](parser_properties_list)] [FTS_INDEX_TYPE [=] {MATCH | PHRASE_MATCH}] [LOCAL]
    | ADD SEARCH INDEX [index_name] (search_index_column [, search_index_column ...])
    | ADD COLUMN GROUP([all columns, ]each column) [DELAYED]
    | ALTER [COLUMN] column_name {
          SET DEFAULT const_value
        | DROP DEFAULT
      }
    | ALTER {CHECK | CONSTRAINT} symbol [NOT] ENFORCED
    | ALTER INDEX index_name [VISIBLE | INVISIBLE] [STORAGE_CACHE_POLICY = {"hot"|"auto"|"none"}]
    | ALTER INDEX index_name
          [VISIBLE | INVISIBLE]
    | CHANGE [COLUMN] column_name column_definition
    | DROP [COLUMN] column_name [, DROP COLUMN column_name ...]
    | DROP {PARTITION | SUBPARTITION} partition_name_list
    | DROP TABLEGROUP
    | DROP FOREIGN KEY fk_name
    | DROP PRIMARY KEY [, ADD PRIMARY KEY (column)]
    | DROP CHECK constraint_name
    | DROP COLUMN GROUP([all columns, ]each column)
    | DROP CLUSTERING KEY
    | MODIFY [COLUMN] column_definition
    | RENAME COLUMN old_col_name [TO|AS] new_col_name
    | RENAME [TO|AS] table_name
    | RENAME {INDEX | KEY} old_index_name [TO|AS] new_index_name
    | [SET] table_option_list
    | TRUNCATE {PARTITION | SUBPARTITION} partition_name_list
    | EXCHANGE PARTITION partition_name WITH TABLE origin_table_name WITHOUT VALIDATION
    | REORGANIZE PARTITION partition_name INTO (split_range_partition_list)
    | PARTITION BY {RANGE [COLUMNS]([column_name_list]) [SIZE('size_value')] [range_partition_list]
                   | partition_option}
    | MODIFY PARTITION partition_name ADD SUBPARTITION (add_subpartition_option)
    | ALTER {PARTITION | SUBPARTITION} partition_name STORAGE_CACHE_POLICY = {"hot" | "auto" | "none"}
    | FORCE
    | REMOVE TTL

column_definition_list:
    column_definition [, column_definition ...]

column_definition:
    column_name data_type
    [DEFAULT const_value] [AUTO_INCREMENT]
    [NULL | NOT NULL] [[PRIMARY] KEY] [UNIQUE [KEY]] [COMMENT string_value] [SKIP_INDEX(skip_index_option_list)] [ opt_position_column ]

skip_index_option_list:
    skip_index_option [,skip_index_option ...]

skip_index_option:
    MIN_MAX
    | SUM

opt_position_column:
    FIRST | BEFORE | AFTER column_name

index_desc:
   (column_desc_list) [index_type] [index_option_list]

match_action:
   MATCH {SIMPLE | FULL | PARTIAL}

opt_reference_option_list:
   reference_option [,reference_option ...]

reference_option:
   ON {DELETE | UPDATE} {RESTRICT | CASCADE | SET NULL | NO ACTION | SET DEFAULT}

column_desc_list:
    column_desc [, column_desc ...]

column_desc:
     column_name [(length)] [ASC | DESC]

key_part:
    {index_col_name [(length)] | (expr)} [ASC | DESC]

search_index_column:
    column_name [WITH (search_col_option_list)]

search_col_option_list:
    [INCLUDE_PATHS = ('path1'[, 'path2']...)]
    [| EXCLUDE_PATHS = ('path1'[, 'path2']...)]
    [| INCLUDE_TYPES = (type1[, type2]...)]

index_type:
    USING BTREE

index_option_list:
    index_option [ index_option ...]

index_option:
     [GLOBAL | LOCAL]
    | block_size
    | compression
    | STORING(column_name_list)
    | COMMENT string_value
    | STORAGE_CACHE_POLICY (storage_cache_policy_option)

index_column_group_option:
    WITH COLUMN GROUP([all columns, ]each column)

tokenizer_option:
    SPACE
    | NGRAM
    | BENG
    | IK
    | NGRAM2

parser_properties_list:
    parser_properties, [parser_properties]

parser_properties:
    min_token_size = int_value
    | max_token_size = int_value
    | ngram_token_size = int_value
    | ik_mode = 'char_value'
    | min_ngram_size = int_value
    | max_ngram_size = int_value

table_option_list:
    table_option [ table_option ...]

table_option:
      TABLEGROUP = tablegroup_name
    | block_size
    | lob_inrow_threshold [=] num
    | compression
    | AUTO_INCREMENT [=] INT_VALUE
    | COMMENT string_value
    | parallel_clause
    | TABLE_MODE [=] 'table_mode_value'
    | AUTO_INCREMENT_CACHE_SIZE [=] INT_VALUE
    | READ {ONLY | WRITE}
    | DUPLICATE_SCOPE= 'none | cluster'
    | enable_macro_block_bloom_filter [=] {True | False}
    | DYNAMIC_PARTITION_POLICY [=] (dynamic_partition_policy_list)
    | SEMISTRUCT_ENCODING_TYPE [=] 'encoding' # Deprecated since V4.4.1. Use SEMISTRUCT_PROPERTIES instead.
    | SEMISTRUCT_PROPERTIES [=] (encoding_type=encoding|none[,freq_threshold=INT_VALUE])
    | STORAGE_CACHE_POLICY (storage_cache_policy_option)
    | CLUSTER BY (column_name_list)
    | HMS_CATALOG_NAME [=] string_value
    | COLUMN_NAME_CASE_SENSITIVE [=] {True | False}
    | DELTA_FORMAT [=] 'flat | encoding'
    | SKIP_INDEX_LEVEL [=] {1 | 0}
    | TTL col_name + INTERVAL interval_num ttl_unit BY COMPACTION

parallel_clause:
    {NOPARALLEL | PARALLEL integer}

table_mode_value:
    NORMAL
    | QUEUING
    | MODERATE
    | SUPER
    | EXTREME

dynamic_partition_policy_list:
    dynamic_partition_policy_option [, dynamic_partition_policy_option ...]

dynamic_partition_policy_option:
    ENABLE = {true | false}
    | PRECREATE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}
    | EXPIRE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}

partition_option:
      PARTITION BY HASH(expression)
      [subpartition_option] PARTITIONS partition_count
    | PARTITION BY KEY([column_name_list])
      [subpartition_option] PARTITIONS partition_count
    | PARTITION BY RANGE {(expression) | COLUMNS (column_name_list)}
      [subpartition_option] (range_partition_list)

subpartition_option:
      SUBPARTITION BY HASH(expression)
      SUBPARTITIONS subpartition_count
    | SUBPARTITION BY KEY(column_name_list)
      SUBPARTITIONS subpartition_count
    | SUBPARTITION BY RANGE {(expression) | COLUMNS (column_name_list)}
      (range_subpartition_list)

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "cold" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit
    | MIXED_RETENTION = intnum retention_time_unit
    | GRANULARITY = {"partition" | "block"}

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE

split_range_partition_list:
    PARTITION split_partition_name VALUES LESS THAN (value)
    [, PARTITION split_partition_name VALUES LESS THAN (value) ...]
     , PARTITION split_partition_name VALUES LESS THAN (source_value)

range_partition_list:
    range_partition [, range_partition ...]

range_partition:
    PARTITION partition_name
    VALUES LESS THAN {(expression_list) | MAXVALUE}
    [STORAGE_CACHE_POLICY = {"hot" | "auto" | "cold" | "none"}]

range_subpartition_list:
    range_subpartition [, range_subpartition ...]

range_subpartition:
    SUBPARTITION subpartition_name
    VALUES LESS THAN {(expression_list) | MAXVALUE}
    [STORAGE_CACHE_POLICY = {"hot" | "auto" | "cold" | "none"}]

expression_list:
    expression [, expression ...]

column_name_list:
    column_name [, column_name ...]

partition_name_list:
    partition_name [, partition_name ...]

partition_count | subpartition_count:
    INT_VALUE

add_subpartition_option:
    {SUBPARTITION subpartition_name VALUES LESS THAN range_partition_expr
        [, SUBPARTITION subpartition_name VALUES LESS THAN range_partition_expr] ...}
    | {SUBPARTITION subpartition_name VALUES IN list_partition_expr
        [, SUBPARTITION subpartition_name VALUES IN list_partition_expr] ...}
```

## Parameters

|                           **Parameter**                           |        **Description**             |
|------------------------------------------------------------|---------------------------------------------------------------------|
| ADD \[COLUMN\]                                             | Adds a column. Generated columns are supported.     |
| \[FIRST  \| BEFORE \| AFTER column_name\]                  | Specifies the position of the added column as the first column of the table or before/after the `column_name` column. Currently, OceanBase Database only supports setting the position of a column in the `ADD COLUMN` syntax.     |
| CHANGE \[COLUMN\]                                          | Renames a column and modifies the column definition. Only the length of specific character data types (such as `VARCHAR`, `VARBINARY`, and `CHAR`) can be modified.    |
| MODIFY \[COLUMN\]                                          | Modifies column attributes. |
| ALTER \[COLUMN\] {SET DEFAULT const_value \| DROP DEFAULT} | Modifies the default value of a column.  |
| DROP \[COLUMN\]                                            | Drops a column.<main id="notice" type='notice'><h4>Notice</h4><p>You cannot drop a primary key column. </p></main>|
| ADD FOREIGN KEY                                            | Adds a foreign key. If you do not specify a foreign key name, the system generates a foreign key name in the format of `table name` + `OBFK` + `creation time`. For example, the foreign key name created for the `t1` table on August 1, 2021, 00:00:00 is `t1_OBFK_1627747200000000`. A foreign key allows cross-table references. When the `UPDATE` or `DELETE` operation affects the key values of the parent table rows that match the rows of the child table, the result depends on the `ON UPDATE` and `ON DELETE` clauses. <ul><li>`CASCADE`: When you delete or update a row in the parent table, the system automatically deletes or updates the matching rows in the child table. </li><li>`SET NULL`: When you delete or update a row in the parent table, the system sets the foreign key column in the child table to `NULL`. </li><li>`RESTRICT`: The system does not allow you to delete or update a row in the parent table. </li><li>`NO ACTION`: Specifies to delay the check. </li></ul> The `SET DEFAULT` operation is also supported. |
| ADD PRIMARY KEY                                            | Adds a primary key. You can specify one or more columns as the primary key. If multiple columns are specified, they form a composite primary key.               |
| ADD FULLTEXT \[INDEX \| KEY\]                              | Adds a full-text index. For more information, see the section on creating a full-text index in [Create an index](../../../../300.database-object-management/100.manage-object-of-mysql-mode/500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).|
| ADD SEARCH INDEX | Adds a search index (Search Index). Syntax: `ADD SEARCH INDEX [index_name] (search_index_column [, search_index_column ...])`. `search_index_column` supports `column_name [WITH (...)]`. `WITH` is only supported for JSON columns. It supports `INCLUDE_PATHS` and `EXCLUDE_PATHS` (choose one) and `INCLUDE_TYPES`.|
| WITH PARSER tokenizer_option                 | Optional. Specifies the tokenizer for a full-text index. For more information, see [tokenizer_option](#tokenizer_option) below.|
| PARSER_PROPERTIES\[=\](parser_properties_list) | Optional. Specifies the properties of the tokenizer. For more information, see [parser_properties](#parser_properties) below.|
| FTS_INDEX_TYPE [=] {MATCH | PHRASE_MATCH} | Optional. Specifies the type of a full-text index. `MATCH` specifies a term-matching index. It supports matching and scoring based on the BM25 algorithm. The stored content contains tokens, document IDs, term frequencies, and document lengths. `PHRASE_MATCH` specifies a phrase-matching index. It supports phrase queries more efficiently than a `MATCH` index and stores the position list of terms. |
| ALTER INDEX                                                | Modifies the visibility of an index. If the index status is `INVISIBLE`, the SQL optimizer does not select this index.    |
| key_part        | Creates a (function) index. |
| index_col_name  | Specifies the column name of the index. You can specify `ASC` (ascending) for each column name, but not `DESC` (descending). The default is ascending. The index is created based on the following rules: First, the values of the first column in `index_col_name` are sorted. Then, the values of the next column are sorted for records with the same value in the previous column. This process continues. |
| expr            | Specifies a valid function index expression, which can be a boolean expression, such as `c1=c1`.<br>**Notice** OceanBase Database does not allow you to create a function index on a generated column.             |
| ADD \[PARTITION\]                                          | Adds a partition to a partitioned table.  |
| DROP {PARTITION \| SUBPARTITION}                           | Drops a partition: <ul><li> `PARTITION`: Drops the specified partition (including all subpartitions under it) of a RANGE or LIST partition. The partition definition and data are dropped, and the indexes on the partition are maintained. </li>   <li> `SUBPARTITION`: Drops the specified subpartition of a `*-RANGE` or `*-LIST` partition. The partition definition and data are dropped, and the indexes on the partition are maintained. </li></ul>    Separate multiple partition names with commas.<br> **Notice** When you drop a partition, avoid active transactions or queries on the partition. Otherwise, an error may occur or an unexpected situation may arise.   |
| TRUNCATE {PARTITION \| SUBPARTITION}                       | Deletes data in a partition: <ul><li> `PARTITION`: Clears all data in the specified partition (and all subpartitions under it) for range or list partitions, and maintains indexes on the partition.</li>   <li> `SUBPARTITION`: Clears all data in the specified subpartition for `*-RANGE` or `*-LIST` subpartitions, and maintains indexes on the partition.</li> </ul>   Separate partition names with commas.<br> **Notice**  Avoid active transactions or queries on the partition being deleted, as this may cause SQL errors or exceptions. |
| RENAME COLUMN old_col_name \[TO\|AS] new_col_name| Renames a column without changing its definition.   <main id="notice" type='notice'><h4>Notice</h4> <p><ul><li>If the target name already exists in the table, the operation will fail.</li><li>Renaming a column in a loop, such as <code>ALTER TABLE t1 RENAME COLUMN a to b, RENAME COLUMN b to a;</code>, is allowed.</li><li>If indexes or foreign key constraints exist on the renamed column, <code>RENAME COLUMN</code> will execute normally, and the indexes and foreign key constraints will be automatically updated.</li><li>Do not include both <code>RENAME COLUMN</code> and <code>ADD PARTITION</code> or <code>ALTER COLUMN</code> in the same <code>ALTER TABLE</code> statement.</li></ul></p></main>|
| RENAME \[TO\|AS] table_name                                   | Renames a table. <main id="notice" type='notice'><h4>Notice</h4><p>During <code>RENAME TABLE</code> operations, table locking and read/write protection are applied, which increases the operation time. To avoid affecting other users' DDL operations, do not perform batch <code>RENAME TABLE</code> operations.</p></main>|
| RENAME {INDEX \| KEY}                                      | Renames an index or key.   |
| DROP \[TABLEGROUP\]                                        | Drops a table group.  |
| DROP \[FOREIGN KEY\]                                       | Drops a foreign key.  |
| DROP \[PRIMARY KEY\]                                       | Drops a primary key.<main id="notice" type='explain'><h4>Note</h4><p>In MySQL mode, you cannot drop a primary key in the following cases:<ul><li>The table is a parent table with foreign key information.</li> <li>The table is a child table, and the primary key column contains foreign key reference columns.</li> </ul> |
| \[SET\] table_option                                       | Sets table-level properties. You can specify the following parameters: <ul><li> `REPLICA_NUM`: Sets the number of replicas (not supported yet).</li>   <li> `tablegroup_name`: Sets the table group to which the table belongs.</li>   <li> `BLOCK_SIZE`: Sets the microblock size of the table. The default value is `16384` (16 KB), and the value ranges from \[1024,1048576\].</li>  <li> `lob_inrow_threshold`: Configures the `INROW` threshold. When the size of LOB data exceeds this threshold, it will be stored in the LOB Meta table as `OUTROW`. The default value is 4 KB.</li>   <li> `COMPRESSION`: Sets the compression method for the table. The default value is `None`, indicating no compression.</li>   <li> `AUTO_INCREMENT`: Sets the next value for the auto-increment column in the table. You can increase or decrease this value.<main id="notice" type='notice'><h4>Notice</h4><p>When decreasing the value of an auto-increment column in a table, note the following: </br> If the table already contains data and the maximum value in the auto-increment column is greater than or equal to the new <code>AUTO_INCREMENT</code> value, the new <code>AUTO_INCREMENT</code> value will be automatically adjusted to the next value after the current maximum value in the auto-increment column. For example, if the current maximum value in the auto-increment column is 5 and the current <code>AUTO_INCREMENT</code> value is 8, and <code>AUTO_INCREMENT</code> is set to any value between 0 and 6, the actual <code>AUTO_INCREMENT</code> value will be adjusted to 6 after the statement is executed. </p></main></li>   <li> `comment`: Sets the comment for the table.</li>   <li> `PROGRESSIVE_MERGE_NUM`: Sets the number of progressive merge steps. The value ranges from \[0,100\].</li>   <li> `parallel_clause`: Specifies the parallelism at the table level.</li> <li> `NOPARALLEL`: Sets the parallelism to `1`, which is the default configuration.</li>   <li> `PARALLEL integer`: Specifies the parallelism. The `integer` value must be greater than or equal to `1`.</li> </ul>     |
| CHECK                                                      | Modifies `CHECK` constraints. Supported operations include: <ul><li> Adding a new `CHECK` constraint.</li>   <li> Dropping the `CHECK` constraint named `constraint_name`. </li>  </ul>  |
| \[NOT\] ENFORCED                                           | Specifies whether to enforce the `CHECK` constraint named `constraint_name`. <ul><li> If omitted or specified as `ENFORCED`, the constraint is created and enforced, which is the default behavior.</li>   <li> If specified as `NOT ENFORCED`, the constraint is created but not enforced. </li> </ul>   |
| ADD COLUMN GROUP([all columns, ]each column) [DELAYED] | Converts the table to a columnar table. The following table describes the parameters. <ul><li><code>ADD COLUMN GROUP(all columns, each column)</code>: Converts the table to a hybrid table that stores data in both row and columnar formats. </li><li><code>ADD COLUMN GROUP(each column)</code>: Converts the table to a columnar table. </li><li>`DELAYED`: An optional parameter. If specified, the conversion from a rowstore table to a columnar table is performed asynchronously. After the table definition is modified, the actual conversion is performed during a major compaction. This operation does not block current DML operations and is considered an online DDL operation. If this parameter is not specified, the conversion is performed synchronously and is considered an offline DDL operation. <main id="notice" type='notice'><h4>Notice</h4><p><ul><li>You can specify the <code>DELAYED</code> option only when you convert a rowstore table to a columnar table (<code>each column</code>) or to a hybrid table that stores data in both row and columnar formats (<code>all columns, each column</code>). </li><li>After you execute the <code>DELAYED</code> option to convert a rowstore table to a columnar table, the actual conversion is performed during a major compaction. Before the major compaction is completed, the data storage format has not been changed. Therefore, the query performance may be lower than expected. </li></ul></p></main></li></ul>|
| DROP COLUMN GROUP([all columns, ]each column) | Removes the storage format of the table. The following table describes the parameters. <ul><li><code>DROP COLUMN GROUP(all columns, each column)</code>: Removes the hybrid storage format of the table. </li><li><code>DROP COLUMN GROUP(all columns)</code>: Removes the rowstore storage format of the table. </li><li><code>DROP COLUMN GROUP(each column)</code>: Removes the columnar storage format of the table. </li></ul>|
| DROP CLUSTERING KEY | Drops the clustering column of the table. <main id="notice" type='explain'><h4>Note</h4><p><ul><li>This parameter is introduced in V4.6.0. </li><li>After you drop the clustering column, the data of the table is no longer guaranteed to be physically ordered and is organized as a heap table. </li></ul></p></main>|
| index_column_group_option | Specifies the index options. The following table describes the parameters. <ul><li><code>WITH COLUMN GROUP(all columns, each column)</code>: Specifies a hybrid index. </li><li><code>WITH COLUMN GROUP(all columns)</code>: Specifies a rowstore index. </li><li><code>WITH COLUMN GROUP(each column)</code>: Specifies a columnar index. </li></ul>|
| SKIP_INDEX | Modifies the Skip Index attribute of a column. Valid values: <ul><li><code>MIN_MAX</code>: The most commonly used aggregate data type in a Skip Index. It stores the maximum value, minimum value, and number of null values of the indexed column at the index node level. This type of data can accelerate the pushdown of filters and `MIN/MAX` aggregations. </li><li><code>SUM</code>: Accelerates the pushdown of `SUM` aggregations for numeric data types. </li></ul>  <main id="notice" type='notice'><h4>Notice</h4><p><ul><li>You cannot create a Skip Index for a JSON or spatial data type column. </li><li>You cannot create a Skip Index for a generated column. </li></ul></p></main>|
| EXCHANGE PARTITION partition_name WITH TABLE origin_table_name | Specifies a partition exchange. In this statement, `partition_name` specifies the name of the partition in the partitioned table, and `origin_table_name` specifies the name of the source table, which is a non-partitioned table or a partitioned table. For more information, see [Partition exchange](../../../../300.database-object-management/100.manage-object-of-mysql-mode/300.manage-partitions-of-mysql-mode/1000.exchange-partition-of-mysql-mode.md).|
| TABLE_MODE | An optional parameter that specifies the major compaction trigger threshold and strategy, which control the behavior of major compactions after data is dumped. For more information, see [table_mode_value](#table_mode_value).|
| AUTO_INCREMENT_CACHE_SIZE | Specifies the number of cached auto-increment values. The default value is 0, which indicates that the system uses the tenant-level parameter [auto_increment_cache_size](../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/100.auto_increment_cache_size-global.md) to set the cache size of an auto-increment column.|
| READ {ONLY \| WRITE} | Specifies the read/write permissions of the table. Valid values: <ul><li>`READ ONLY`: The table can be read but not modified or deleted. <main id="notice" type='notice'><h4>Notice</h4><p>The <code>READ ONLY</code> parameter at the table level takes effect only for users without the <code>SUPER</code> privilege. </p></main></li><li>`READ WRITE`: The default value. The table can be read, modified, and deleted. </li></ul>|
| DUPLICATE_SCOPE | Modifies the duplicate table attribute. Valid values: <ul><li>`none`: Converts the current table to a regular table. </li><li>`cluster`: Converts the current table to a duplicate table. </li></ul> For more information, see [Modify the duplicate table attribute](../../../../300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/650.change-duplicate-scope-of-mysql-mode.md).|
| enable_macro_block_bloom_filter [=] {True \| False} | Specifies whether to persist the Bloom filter at the macroblock level. Valid values: <ul><li><code>True</code>: Enables the persistence of the Bloom filter at the macroblock level. </li></ul><ul></li></li><li><code>False</code>: Disables the persistence of the Bloom filter at the macroblock level. </li></ul>|
| DYNAMIC_PARTITION_POLICY \[=\] \(dynamic_partition_policy_list\) | Modifies the dynamic partition management attribute of the table. `dynamic_partition_policy_list` specifies the list of configurable parameters of the dynamic partition strategy, separated by commas. For more information, see [dynamic_partition_policy_option](#dynamic_partition_policy_option).|
| REORGANIZE PARTITION | Manually split a partition. The following parameters are available: <ul><li>`partition_name`: the name of the partition to be split. </li><li>`split_partition_name`: the name of the new partition after splitting. </li><li>`value`: the boundary for splitting a partition. The `value` range defined for splitting a partition must be the same as the `value` range of the source partition. The `value` range must be defined in ascending order. </li><li>`source_value`: the original boundary of the partition to be split. The `value` of the last split partition is the same as that of the source partition. </li></ul> For more information about manual partition splitting, see [Manually split a partition](../../../../300.database-object-management/100.manage-object-of-mysql-mode/300.manage-partitions-of-mysql-mode/250.partition-splitting-of-mysql-mode/200.manual-partition-splitting-of-mysql-mode.md). <main id="notice" type='notice'><h4>Notice</h4><p>In OceanBase Database in MySQL mode, the current version only supports splitting a partition into multiple partitions, but not multiple partitions into multiple partitions. </p></main> |
| PARTITION BY | Modify the automatic partitioning attributes of a table or modify the partitioning rules. ### table_mode_value

<main id="notice" type='explain'>

* `MODERATE`: Indicates moderate mode. In this mode, the probability of triggering a compaction after a data dump is moderate.
* `SUPER`: Indicates super mode. In this mode, the probability of triggering a compaction after a data dump is high.
* `EXTREME`: Indicates extreme mode. In this mode, the probability of triggering a compaction after a data dump is high.

### parser_properties

* `min_token_size`: The minimum token length. The default value is 3, and the value range is 1 to 16.

* `max_token_size`: The maximum token length. The default value is 84, and the value range is 10 to 84.

* `ngram_token_size`: The token length for the `NGRAM` tokenizer. It is valid only for the `NGRAM` tokenizer. The default value is 2, and the value range is 1 to 10.

* `ik_mode`: The tokenization mode for the `IK` tokenizer. Valid values:

  * `smart`: The default value. This mode uses the dictionary to improve tokenization accuracy and prioritizes the boundaries of dictionary words, which may reduce unnecessary expansions.
  * `max_word`: This mode identifies the words defined in the dictionary but does not limit the maximum expansion of tokenization. Even if the dictionary defines words, the `max_word` mode still tries to split the text into more words.

* `min_ngram_size`: The minimum token length. The value range is [1,16].

* `max_ngram_size`: The maximum token length. The value range is [1,16].

**Here is an example:**

1. Create a table named `tbl1`.

   ```sql
   CREATE TABLE tbl1 (col1 VARCHAR(200), col2 TEXT);
   ```

2. Add a full-text index named `fidx` to the `tbl1` table.

   ```sql
   ALTER TABLE tbl1 ADD FULLTEXT INDEX fidx(col2) WITH PARSER ik PARSER_PROPERTIES=(ik_mode='max_word');
   ```

### dynamic_partition_policy_option

* `ENABLE = {true | false}`: Indicates whether to enable dynamic partition management. Valid values:

  * `true`: The default value. Dynamic partition management is enabled.
  * `false`: Dynamic partition management is disabled.

* `PRECREATE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}`: The time for precreating partitions. When dynamic partition management is scheduled, partitions are precreated to ensure that the **upper bound of the maximum partition > now() + precreate_time**. Valid values:

  * `-1`: The default value. No partitions are precreated.
  * `0`: Only the current partition is precreated.
  * `n {hour | day | week | month | year}`: Partitions are precreated for the specified time span. For example, `3 hour` indicates that partitions for the last 3 hours are precreated.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p><ul><li>When multiple partitions are to be precreated, the intervals between the boundaries of adjacent partitions are <code>TIME_UNIT</code>. </li><li>The boundary of the first precreated partition is the smallest multiple of <code>TIME_UNIT</code> that is greater than or equal to the upper bound of the existing maximum partition. </li></ul></p>
  </main>

* `EXPIRE_TIME = {'-1' | '0' | 'n {hour | day | week | month | year}'}`: Optional. The time when partitions expire. When dynamic partition management is scheduled, all **partitions whose upper bound < now() - expire_time** are deleted. Valid values:

  * `-1`: The default value. Partitions never expire.
  * `0`: All partitions except the current one expire.
  * `n {hour | day | week | month | year}`: The time when partitions expire. For example, `1 day` indicates that partitions expire after 1 day.

For more information about modifying dynamic partition tables, see [Modify a dynamic partition table](../../../../300.database-object-management/100.manage-object-of-mysql-mode/300.manage-partitions-of-mysql-mode/260.dynamic-partition-of-mysql-mode/400.modify-dynamic-partition-table-of-mysql-mode.md).

**Here is an example:**

```sql
ALTER TABLE tbl2 SET DYNAMIC_PARTITION_POLICY(
    ENABLE = true,
    PRECREATE_TIME = '1 day',
    EXPIRE_TIME = '-1'
);
```

### storage_cache_policy

The `storage_cache_policy_option` defines different attributes in the key-value format. The semantics of each attribute are as follows:

* `GLOBAL = {"hot" | "auto" | "cold" | "none"}`: specifies the cold/hot storage strategy for the data of the entire table. Valid values:

  * `hot`: indicates that all data of the specified table is hot data. If the cache disk space is sufficient, all data of the table will be cached to the local cloud disk.
  * `auto`: indicates that the hot data of the specified table is automatically identified by the system.
  * `cold`: indicates that the data of the specified table is cold data. It will not be cached to the local cache disk. For data that has been persisted to the cache, the system will actively trigger cache eviction. Subsequent accesses to the table data can be stored in the macroblock memory cache, without being persisted to the macroblock cache and microblock cache.
  * `none`: indicates that the strategy of the index follows the value of the main table's `STORAGE_CACHE_POLICY`.

    <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>The <code>none</code> attribute can only be used for indexes. </p>
    </main>

* `timeline_strategy_list`: specifies the list of time-axis strategy parameters. Parameters are separated by commas. The time-axis strategy supports a mechanism to determine the cold/hot storage of partitions/macros based on time. The system automatically adjusts the data on the local cache disk based on the configured strategy.

    <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>A time-axis is a partitioning range defined by the Range partitioning method. The system caches hot data based on the partitioning range. When certain time conditions are met, the data of the partition is determined to be hot data. When using the time-axis strategy, note the following: <ul><li>Only Range-partitioned tables are supported (the Range partition can be at the primary or secondary level). This is because the system needs to determine whether the data has expired based on time. However, double Range partitioning is not supported, as it is unclear which Range partition's time to use. </li><li>When using the time-axis strategy, the partitioning expression can only contain column names and does not support expression conversion. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code> is not supported. </li><li><code>BOUNDARY_COLUMN</code> must be a partition key. If the partition key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column to determine whether the partition has expired. </li></ul></p>
  </main>

* `BOUNDARY_COLUMN = column_name`: specifies the column used to determine hot data. Supported types include integer types (`BIGINT` or `INT`, in the format of a Unix timestamp) and time types (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).
  * If the `BOUNDARY_COLUMN` is of an integer type, the table supports Range or Range Columns partitioning.
  * If the `BOUNDARY_COLUMN` is of a time type, the table must use Range Columns partitioning.

* `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter can only be set when `BOUNDARY_COLUMN` is of an integer type. If the integer value is used as a timestamp, you must specify the timestamp unit to avoid incorrect parsing of the timestamp. Valid values:

  * If the partition column is of the `INT` type, the `BOUNDARY_COLUMN_UNIT` can only be `s`.
  * If the partition column is of the `BIGINT` type, the `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

      <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>If the format is not a Unix timestamp, the system cannot correctly identify the timestamp of the <code>INT</code> type. </p>
      </main>

* `HOT_RETENTION = intnum retention_time_unit`: specifies the time range for hot data.
  * `intnum`: specifies an integer.
  * `retention_time_unit`: specifies the time unit. Valid values:
    * `YEAR`: specifies years.
    * `MONTH`: specifies months.
    * `WEEK`: specifies weeks.
    * `DAY`: specifies days.
    * `HOUR`: specifies hours.
    * `MINUTE`: specifies minutes.

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>In the time-axis syntax, at least one of the <code>HOT_RETENTION</code> and <code>MIXED_RETENTION</code> parameters must be set. </p>
  </main>

* `MIXED_RETENTION = intnum retention_time_unit`:

  * If `MIXED_RETENTION` is set, data after the time range of `HOT_RETENTION + MIXED_RETENTION` is considered `cold` data.
  * If `MIXED_RETENTION` is not set, data after the time range of `HOT_RETENTION` is considered `auto` data.
  * If neither `HOT_RETENTION` nor `MIXED_RETENTION` is set, data in the time range of [0, MIXED_RETENTION] is considered `auto` data, and data after the time range of `MIXED_RETENTION` is considered `cold` data.

* `GRANULARITY = {"partition" | "block"}`: optional. Specifies the granularity of the cold/hot storage strategy. Valid values:

  * `partition`: specifies that the cache strategy is applied at the partition level.
  * `block`: specifies that the cache strategy is applied at the macroblock level.

      <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>If no partitioning is used, you can specify <code>block</code> to manually mark data as hot data within a specific time period. For more information about the macroblock cold/hot storage strategy, see <a href="../../../../../660.ob-shared-storage/400.customize-hotspot-cache-of-mysql-mode/700.create-macro-block-level-storage-cache-policy-of-mysql-mode.md">Create a macroblock-level cold/hot storage strategy</a>. </p>
      </main>

### partition_storage_cache_policy

`STORAGE_CACHE_POLICY = {"hot" | "auto" | "cold" | "none"}`: specifies the cold/hot storage strategy for the data of the partition. Valid values:

* `hot`: indicates that the data of the specified partition is hot data. If the cache disk space is sufficient, all data of the partition will be cached to the local cloud disk.
* `auto`: indicates that the hot data of the specified partition is automatically identified by the system.
* `cold`: indicates that the data of the specified partition is cold data. It will not be cached to the local cache disk. For data that has been persisted to the cache, the system will actively trigger cache eviction. Subsequent accesses to the table data can be stored in the macroblock memory cache, without being persisted to the macroblock cache and microblock cache.
* `none`: the default value. Indicates that the strategy of the partition follows the value of the main table's `STORAGE_CACHE_POLICY`.

### Specify the table-level hot/cold storage strategy for an index on an existing table

Syntax:

```sql
ALTER TABLE table_name ADD INDEX index_name(column_name)
    STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

#### Parameter description

You can configure the hot/cold storage strategy for an index table:

* For a local index, you can specify the table-level `STORAGE_CACHE_POLICY`. If you do not specify the table-level `STORAGE_CACHE_POLICY`, it defaults to `none`, which means that the hot/cold storage strategy for the partitions of the local index follows the hot/cold storage strategy for the partitions of the data table.

* For a global index, you can specify the table-level `STORAGE_CACHE_POLICY` and, if the index table is partitioned, you can also specify the partition-level `STORAGE_CACHE_POLICY`. If you do not specify the table-level `STORAGE_CACHE_POLICY`, it defaults to `none`.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>In V4.4.1 and later, if you do not specify the table-level <code>STORAGE_CACHE_POLICY</code> for a global index, the hot/cold storage strategy for the global index follows that of the primary table if the primary table is configured with the Global strategy. If the primary table is configured with the TimeLine strategy, the hot/cold storage strategy for the global index defaults to <code>hot</code>. </p>
  </main>

When you set the table-level `STORAGE_CACHE_POLICY`, different attributes of the `storage_cache_policy_option` parameter are defined in the Key-Value format. The attributes are described as follows:

* `GLOBAL = {"hot" | "auto" | "cold" | "none"}`: specifies the hot/cold storage strategy for the index data. Valid values:

  * `hot`: specifies the index as hot storage. If the cache disk space is sufficient, all data in the index table will be cached to the local cache disk.
  * `auto`: specifies that the system automatically identifies the hot data of the index table.
  * `cold`: specifies the data of the index table as cold data. The data will not be cached to the local cache disk. For data that has been persisted to the cache, the system will actively trigger cache eviction. Subsequent accesses to the table data can be stored in the macroblock memory cache, but will not be persisted to the macroblock cache or microblock cache.
  * `none`: default value. The hot/cold storage strategy for the index follows that of the primary table's `STORAGE_CACHE_POLICY`.

* `timeline_strategy_list`: specifies the list of time-based hot/cold storage strategies. The parameters are separated by commas. The system automatically adjusts the data on the local cache disk based on the configured strategy.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>A time-based hot/cold storage strategy determines whether partition or macroblock data is hot or cold based on the time. When using this strategy, note the following: <ul><li>Only Range-partitioned tables (Range partitioning can be at the primary or secondary level) are supported. This is because the system needs to determine whether data has expired based on time. Double Range partitioning is not supported because it is unclear which Range partition's time to use. </li><li>When using a time-based strategy, the partition expression can only contain column names and cannot be converted to an expression. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code> is not supported. </li><li><code>BOUNDARY_COLUMN</code> must be a partition key. If the partition key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column, which is used to determine whether the partition has expired. </li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: specifies the column used to determine whether data is hot. Supported data types include integers (`BIGINT` or `INT`, in Unix timestamp format) and time types (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If `BOUNDARY_COLUMN` is an integer, the table can be partitioned by Range or Range Columns.
    * If `BOUNDARY_COLUMN` is a time type, the table must be partitioned by Range Columns.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: specifies the time unit for the `BOUNDARY_COLUMN` parameter. This parameter is supported only when `BOUNDARY_COLUMN` is an integer. If you use an integer as a timestamp, you must specify the timestamp unit. Otherwise, the system may incorrectly parse the timestamp. Valid values:

    * If the partition column is `INT`, `BOUNDARY_COLUMN_UNIT` must be `s`.
    * If the partition column is `BIGINT`, `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

  * `HOT_RETENTION = intnum retention_time_unit`: specifies the time range for hot data.

    * `intnum`: an integer.
    * `retention_time_unit`: the time unit. Valid values:

      * `YEAR`: year.
      * `MONTH`: month.
      * `WEEK`: week.
      * `DAY`: day.
      * `HOUR`: hour.
      * `MINUTE`: minute.

#### Examples

* Create an index and specify the table-level `STORAGE_CACHE_POLICY` for the index:

  1. Create a table named `tbl3`.

      ```sql
      CREATE TABLE tbl3 (col1 INT, col2 INT, col3 INT);
      ```

  2. Create an index named `idx1_tbl3` and specify that the data in the index table is hot data.

      ```sql
      CREATE INDEX idx1_tbl3 ON tbl3 (col1) LOCAL 
          STORAGE_CACHE_POLICY (GLOBAL = "hot");
      ```

* Create a table and an index, and specify that the data in the index table is hot data.

    ```sql
    CREATE TABLE tbl4 (col1 INT, col2 INT,
        INDEX idx2 ((col1 + 1)) STORAGE_CACHE_POLICY (GLOBAL = "hot"), UNIQUE KEY ((col1 + col2)));
    ```

* Add an index to an existing table and specify that the data in the index table is hot data.

    ```sql
    ALTER TABLE tbl4 ADD INDEX idx3(col1, col2) GLOBAL 
        STORAGE_CACHE_POLICY (GLOBAL = "hot");
    ```

### Modify the cold/hot storage strategy of an index table

You can use the `ALTER TABLE` statement to modify the cold/hot storage strategy (`STORAGE_CACHE_POLICY`) of an existing index table. The syntax is as follows:

```sql
ALTER TABLE table_name ALTER INDEX STORAGE_CACHE_POLICY (storage_cache_policy_option);

storage_cache_policy_option:
    GLOBAL = {"hot" | "auto" | "none"}
    | timeline_strategy_list

timeline_strategy_list:
    | BOUNDARY_COLUMN = column_name
    | BOUNDARY_COLUMN_UNIT = {"s" | "ms"}
    | HOT_RETENTION = intnum retention_time_unit

retention_time_unit:
    YEAR
    | MONTH
    | WEEK
    | DAY
    | HOUR
    | MINUTE
```

#### Parameters

* `GLOBAL = {"hot" | "auto" | "none"}`: specifies the cold/hot storage strategy for the data of the index table. Valid values are as follows:

  * `hot`: specifies that the data of the index table is stored in hot storage. If the cache disk space is sufficient, all data in the index table will be cached to the local cache disk.
  * `auto`: specifies that the system automatically identifies the hot data of the index table.
  * `none`: the default value. This value indicates that the cold/hot storage strategy of the index table is the same as that of the main table.

* `timeline_strategy_list`: specifies the list of time-axis strategy parameters. Parameters are separated by commas. The time-axis strategy is a mechanism for determining whether partition or macroblock data is hot based on time. The system automatically adjusts the data on the local cache disk based on the configured strategy.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>A time-axis strategy is a mechanism for determining whether partition or macroblock data is hot based on time. When you use a time-axis strategy, note the following points: <ul><li>Only Range-partitioned tables can use a time-axis strategy. This is because the system needs to determine whether data is expired based on time. However, a table cannot be partitioned by two Range partitions. This is because the system cannot determine which Range partition to use for determining whether data is expired. </li><li>When you use a time-axis strategy, the partitioning expression must contain only column names. Expressions are not supported. For example, <code>PARTITION BY RANGE COLUMNS(expr(col3))</code> is invalid. </li><li><code>BOUNDARY_COLUMN</code> must be a partitioning key. If the partitioning key consists of multiple columns, <code>BOUNDARY_COLUMN</code> must be the first column to determine whether the partition is expired. </li></ul></p>
  </main>

  * `BOUNDARY_COLUMN = column_name`: specifies the column used to determine whether data is hot. Supported data types are integer types (`BIGINT` or `INT`, in the format of a Unix timestamp) and time types (`TIMESTAMP`, `DATE`, `DATETIME`, or `YEAR`).

    * If the data type of `BOUNDARY_COLUMN` is an integer type, the partitioning type of the table can be Range or Range Columns.
    * If the data type of `BOUNDARY_COLUMN` is a time type, the partitioning type of the table must be Range Columns.

  * `BOUNDARY_COLUMN_UNIT = {"s" | "ms"}`: specifies the time unit of the parameter `BOUNDARY_COLUMN`. This parameter is supported only when the data type of `BOUNDARY_COLUMN` is an integer type. If the integer value is used as a timestamp, you must specify the timestamp unit. Otherwise, the system may incorrectly parse the value as an invalid timestamp. Valid values are as follows:

    * If the partitioning column is of the `INT` type, the value of `BOUNDARY_COLUMN_UNIT` must be `s`.
    * If the partitioning column is of the `BIGINT` type, the value of `BOUNDARY_COLUMN_UNIT` can be `s` or `ms`.

  * `HOT_RETENTION = intnum retention_time_unit`: specifies the time range of hot data.

    * `intnum`: specifies an integer.
    * `retention_time_unit`: specifies the time unit. Valid values are as follows:

      * `YEAR`: specifies a year.
      * `MONTH`: specifies a month.
      * `WEEK`: specifies a week.
      * `DAY`: specifies a day.
      * `HOUR`: specifies an hour.
      * `MINUTE`: specifies a minute.

    STORAGE_CACHE_POLICY (GLOBAL = "auto");

OceanBase Database does not support modifying or automatically updating the following scenarios:

* If the column to be renamed is referenced by a generated list expression, column renaming is not supported, and an error will be returned.

  ```shell
  obclient> CREATE TABLE tbl12(a INT, b INT AS (a + 1), c INT, d INT, CONSTRAINT d_check CHECK(d > 0)) PARTITION BY HASH(c + 1) PARTITIONS 2;

  obclient> ALTER TABLE tbl12 RENAME COLUMN a TO e;
  ERROR 3108 (HY000): Column 'a' has a generated column dependency
  ```

* If the column to be renamed is referenced by a partitioning expression, column renaming is not supported, and an error will be returned.

  ```shell
  obclient> ALTER TABLE tbl12 RENAME COLUMN c TO e;
  ERROR 3855 (HY000): Column 'c' has a partitioning function dependency and cannot be dropped or renamed.
  ```

* If the column to be renamed is referenced by a `CHECK` constraint, column renaming is not supported, and an error will be returned.

  ```shell
  obclient> ALTER TABLE tbl12 RENAME COLUMN d TO e;
  ERROR 3959 (HY000): Check constraint 'd_check' uses column 'd', hence column cannot be dropped or renamed.
  ```

* If the column to be renamed is referenced by a function index, column renaming is not supported, and an error will be returned.

  ```shell
  DROP TABLE IF EXISTS tbl12;
  obclient> CREATE TABLE tbl12(i INT, INDEX ((i+1)));
  Query OK, 0 rows affected

  obclient> ALTER TABLE tbl12 RENAME COLUMN i TO j;
  ERROR 3837 (HY000): Column 'i' has a functional index dependency and cannot be dropped or renamed.
  ```

* If the column to be renamed is referenced by a view, the `RENAME COLUMN` statement will execute successfully, but querying the view will return an error. You need to manually modify the view definition.

  ```shell
  obclient> CREATE TABLE tbl13(a INT);
  Query OK, 0 rows affected

  obclient> CREATE VIEW v1 AS SELECT a + 1 FROM tbl13;
  Query OK, 0 rows affected

  obclient> SELECT * FROM v1;
  Empty set

  obclient> ALTER TABLE tbl13 RENAME COLUMN a TO b;
  Query OK, 0 rows affected

  obclient> SELECT * FROM v1;
  ERROR 1356 (42S22): View 'test.v1' references invalid table(s) or column(s) or function(s) or definer/invoker of view lack rights to use them
  ```

* If the column to be renamed is referenced by a stored procedure, the `RENAME COLUMN` statement will execute successfully, but the `CALL` procedure statement will return an error. You need to manually modify the stored procedure.

  ```shell
  obclient> CREATE TABLE tbl14(a INT);
  Query OK, 0 rows affected

  obclient> CREATE PROCEDURE proc() SELECT a + 1 FROM tbl14;
  Query OK, 0 rows affected

  obclient> CALL proc();
  Empty set

  obclient> ALTER TABLE tbl14 RENAME COLUMN a TO b;
  Query OK, 0 rows affected

  obclient> CALL proc();
  ERROR 1054 (42S22): Unknown column 'a' in 'field list'
  ```

### Modify the column storage attribute of a table

1. Run the following SQL statement to create a table named `tbl1`.

   ```sql
   CREATE TABLE tbl1 (col1 INT PRIMARY KEY, col2 VARCHAR(50));
   ```

2. Change the `tbl1` table to a rowstore-redundant table and then delete the rowstore-redundant attribute.

   ```sql
   ALTER TABLE tbl1 ADD COLUMN GROUP(all columns, each column);
   ```

   ```sql
   ALTER TABLE tbl1 DROP COLUMN GROUP(all columns, each column);
   ```

3. Change the `tbl1` table to a columnstore table and then delete the columnstore attribute.

   ```sql
   ALTER TABLE tbl1 ADD COLUMN GROUP(each column);
   ```

   ```sql
   ALTER TABLE tbl1 DROP COLUMN GROUP(each column);
   ```

### Modify the Skip Index attribute of a column

Run the following SQL statement to create a table named `test_skidx`.

```sql
CREATE TABLE test_skidx(
  col1 INT SKIP_INDEX(MIN_MAX, SUM),
  col2 FLOAT SKIP_INDEX(MIN_MAX),
  col3 VARCHAR(1024) SKIP_INDEX(MIN_MAX),
  col4 CHAR(10)
  );
```

* Change the Skip Index attribute of the `col2` column in the `test_skidx` table to the `SUM` Skip Index type.

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col2 FLOAT SKIP_INDEX(SUM);
  ```

* Add the Skip Index attribute to the `col4` column in the `test_skidx` table. The `MIN_MAX` Skip Index type is used.

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col4 CHAR(10) SKIP_INDEX(MIN_MAX);
  ```

* Delete the Skip Index attribute of the `col1` column in the `test_skidx` table.

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col1 INT SKIP_INDEX();
  ```

  or

  ```sql
  ALTER TABLE test_skidx MODIFY COLUMN col1 INT;
  ```

### Modify the table attribute

Disable the persistent bloom filter at the macroblock level for the `tb` table.

```sql
ALTER TABLE tb SET enable_macro_block_bloom_filter = False;
```

### Modify the STORAGE_CACHE_POLICY at the table level

* Change the hot cache of the `tbl1` table to be automatically identified by the system.

  ```sql
  ALTER TABLE tbl1 SET STORAGE_CACHE_POLICY (GLOBAL = "auto");
  ```

* Change the data in the `tbl2` table to hot data within two months from the current time based on the `col3` column.

  ```sql
  ALTER TABLE tbl2 SET STORAGE_CACHE_POLICY (BOUNDARY_COLUMN = col3, HOT_RETENTION = 2 MONTH); 
  ```

### Modify the STORAGE_CACHE_POLICY at the partition level

* Add a partition named p2 to the `tbl3` table. The hot data to be cached to the local disk in the p2 partition is automatically identified by the system.

  ```sql
  ALTER TABLE tbl3 ADD PARTITION (PARTITION p2 VALUES LESS THAN(300) STORAGE_CACHE_POLICY = "auto");
  ```

* Change the data in the existing partition p1 of the `tbl3` table to hot data.

  ```sql
  ALTER TABLE tbl3 ALTER PARTITION p1 STORAGE_CACHE_POLICY = 'hot';
  ```

* Change the data in the subpartition sp3 of the `tbl4` table to hot data to be cached to the local disk. The hot data is automatically identified by the system.

  ```sql
  ALTER TABLE tbl4 ALTER SUBPARTITON sp3 STORAGE_CACHE_POLICY = 'auto';
  ```

### Modify or delete the TTL policy of a table

* Modify the TTL policy of the table. For example, set the data expiration time to 1 hour.

  ```shell
  obclient(root@mysql001)[infotest]> ALTER TABLE ttl_tbl1 SET TTL ORA_ROWSCN + INTERVAL 1 HOUR BY COMPACTION;
  ```

* Delete the TTL policy of the table.

  ```shell
  obclient(root@mysql001)[infotest]> ALTER TABLE ttl_tbl1 SET REMOVE TTL;
  ```
