# ls_gc_delay_time

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>This parameter was introduced in V4.2.0. </p>
</main>

## Description

The `ls_gc_delay_time` parameter specifies the time for delaying the deletion of log streams.

Starting from V4.2.0, OceanBase Database has implemented the load balancing module based on the log stream split and merge features. The load balancing module provides capabilities such as scaling out and scaling in. When the database is scaled down, log streams that meet the conditions for garbage collection (GC) are deleted quickly, and the corresponding logs in the Palf store are also cleared.

In addition, starting from V4.2.0, OceanBase Database has implemented a physical standby database based on the network. In the physical standby database architecture, if the source primary tenant or standby tenant has not enabled log archiving and the database is scaled down, the log streams are quickly cleared. This can easily cause the standby tenant to be blocked due to the recovery of logs from the source tenant. Therefore, you can set the value of this parameter to specify the time for delaying the deletion of log streams in the primary tenant or standby tenant.

## Privilege requirements

* Query the parameter

  The `sys` tenant and all user tenants can execute the `SHOW PARAMETERS` statement or view `GV$OB_PARAMETERS` to query this parameter.

* Modify the parameter

  The `sys` tenant and user tenants can modify this parameter.

## Attributes

| **Attribute** | **Description** |
| -------- | -------- |
| Type  | Time |
| Default value    | 0s, indicating that the log stream delay deletion mechanism is disabled. <main id="notice" type='explain'><h4>Note</h4><p>The default value is changed from 3600s to 0s in V4.2.1 BP1. </p></main> |
| Value range  | [0s,+∞) |
| Modifiable | Yes. You can execute the ALTER SYSTEM SET statement to modify this parameter. |
| Effective upon OBServer node restart| No |

## Considerations

* Physical standby database:

  * If the primary tenant or standby tenant at the source end has not enabled log archiving and the default value of the `ls_gc_delay_time` parameter is 3600s, which is 1 hour, the log stream delay deletion mechanism is enabled, and the log streams are delayed for 1 hour.

  * If the primary tenant or standby tenant at the source end has enabled log archiving, log archiving ensures the integrity of log stream data. Therefore, the GC of log streams is not affected by this parameter. In other words, the log stream delay deletion mechanism is disabled regardless of the value of the `ls_gc_delay_time` parameter.

* Tenant deletion:

  The log stream delay deletion mechanism is disabled regardless of the value of the `ls_gc_delay_time` parameter.

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <p>The log stream delay deletion mechanism retains only the log stream entities. Whether the log files of the log streams can be retained depends on the remaining disk space of the current tenant. If the remaining disk space is insufficient, log recycling will still be triggered. </p>
  </main>

## Examples

* Set the log stream delay deletion time for a specified tenant in the `sys` tenant.

  ```shell
  obclient> ALTER SYSTEM SET ls_gc_delay_time='7200s' TENANT = 'mysql_tenant';
  ```

* Set the log stream delay deletion time for the current tenant in a user tenant.

  ```shell
  obclient> ALTER SYSTEM SET ls_gc_delay_time='7200s';
  ```
