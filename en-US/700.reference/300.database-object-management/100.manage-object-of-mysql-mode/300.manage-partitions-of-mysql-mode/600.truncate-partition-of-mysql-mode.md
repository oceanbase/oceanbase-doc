# Truncate partitions

You can truncate partitions in a partitioned table to clear the data in the partitions while retaining the partition structure.

## Support for truncating partitions

In the MySQL mode of OceanBase Database, the support for truncating partitions in primary and composite partitioned tables is shown in the following table.

|    Partitioned table  |    Partitioning type   | Truncate primary partition | Truncate composite partition |
|-----------|---------------|------------------|------------------|
| Primary partitioned table | <ul><li>Range</li><li>Range Columns</li><li>List</li><li>List Columns</li></ul> | Supported | - |
| Primary partitioned table | <ul><li>Hash</li><li>Key</li></ul> | Not supported| - |
| Composite partitioned table | <ul><li>Range + Range</li><li>Range + Range Columns</li><li>Range + List</li><li>Range + List Columns</li></ul> | Supported | Supported |
| Composite partitioned table | <ul><li>Range + Hash</li><li>Range + Key</li></ul> | Supported | Not supported |
| Composite partitioned table | <ul><li>Range Columns + Range</li><li>Range Columns + Range Columns</li><li>Range Columns + List</li><li>Range Columns + List Columns</li></ul> | Supported | Supported |
| Composite partitioned table | <ul><li>Range Columns + Hash</li><li>Range Columns + Key</li></ul> | Supported | Not supported |
| Composite partitioned table | <ul><li>List + Range</li><li>List + Range Columns</li><li>List + List</li><li>List + List Columns</li></ul> | Supported | Supported |
| Composite partitioned table | <ul><li>List + Hash</li><li>List + Key</li></ul> | Supported | Not supported |
| Composite partitioned table | <ul><li>List Columns + Range</li><li>List Columns + Range Columns</li><li>List Columns + List</li><li>List Columns + List Columns</li></ul> | Supported | Supported |
| Composite partitioned table | <ul><li>List Columns + Hash</li><li>List Columns + Key</li></ul> | Supported | Not supported |
| Composite partitioned table | <ul><li>Hash + Range</li><li>Hash + Range Columns</li><li>Hash + List</li><li>Hash + List Columns</li></ul> | Not supported | Supported |
| Composite partitioned table | <ul><li>Hash + Hash</li><li>Hash + Key</li></ul> | Not supported | Not supported |
| Composite partitioned table | <ul><li>Key + Range</li><li>Key + Range Columns</li><li>Key + List</li><li>Key + List Columns</li></ul> | Not supported | Supported |
| Composite partitioned table | <ul><li>Key + Hash</li><li>Key + Key</li></ul> | Not supported | Not supported |

## Truncate partition

### Impact of truncating partitions on global indexes

For tables that use Range/Range Columns or List/List Columns partitioning (for primary and composite partitions) and support the `TRUNCATE` partition operation, the system does not rebuild global indexes. Instead, it uses background compactions to delete data and maintains indexes lazily to keep them valid, thus avoiding query interruptions or performance degradation due to index invalidation. Note that this optimization applies only to regular global indexes. The following scenarios do not trigger this optimization:

* When the primary partition is a Hash partition (even if the composite partition is Range/Range Columns or List/List Columns), truncating the composite partition.
* When the partitioning key is an expression rather than a regular column.

#### Hidden configuration item for controlling global index behavior during partition DDL operations

Starting from V4.3.5 BP2, OceanBase Database introduces a tenant-level hidden configuration item `_ob_enable_truncate_partition_preserve_global_index` in V4.3.5. This item controls whether global indexes remain valid during `TRUNCATE`/`DROP` operations on primary partitions (referred to as partition DDL operations). For upgraded tenants, the default value is `False`, while for new tenants, it is `True`. The behavior is as follows:

| Configuration value | Behavior during partition DDL execution | Result after partition DDL execution |
|----------|-----------------------|-------------------------|
| True | Only the `TRUNCATE`/`DROP` primary partitions are DML-incompatible. Other primary partitions can still perform DML operations. | Global indexes remain valid: DML operations can be performed on the primary table and all index tables, and global indexes related to the primary table remain valid. |
| False | Only the `TRUNCATE`/`DROP` primary partitions are DML-incompatible. Other primary partitions can still perform DML operations. | Global indexes become invalid or are rebuilt: DML operations can be performed on the primary table and all index tables, but global indexes related to the primary table become invalid or are rebuilt. |

**Examples:**

* Global index remains valid.

    ```shell
    obclient> ALTER SYSTEM SET _ob_enable_truncate_partition_preserve_global_index = True;
    ```

* Global index becomes invalid.

    ```shell
    obclient> ALTER SYSTEM SET _ob_enable_truncate_partition_preserve_global_index = False;
    ```

### Impact of truncating partitions on concurrent DDL/DML/queries

Truncating a partition is an offline DDL operation. During this operation, OceanBase Database adds an exclusive lock at the partition level on the target partition.

| Operation type | Impact during truncating a partition |
|----------|------------------------------|
| Concurrent DDL | Prohibited or blocked. Any other DDL operations on the same table cannot be executed concurrently. |
| Concurrent DML | <ul><li>On the target partition: Completely blocked.</li><li>On other partitions: Generally allowed, provided the statements can clearly access other partitions.</li></ul>|
| Concurrent query (`SELECT`) | Not affected, can be executed normally. |

## Truncate a partition

You can truncate a partition of a partitioned table.

The SQL syntax for truncating a partition is as follows:

```sql
ALTER TABLE table_name TRUNCATE PARTITION partition_name[, partition_name ...];
```

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <ul>
    <li>
    <p>When you truncate a partition, you can clear data from one or more partitions. </p>
    </li>
    <li>
    <p>Before you truncate a partition, make sure that no active transaction or query is running on the partition. Otherwise, an error may occur or unexpected behavior may happen. In the <code>sys</code> tenant, query the <code>oceanbase.GV$OB_TRANSACTION_PARTICIPANTS</code> view to obtain the status of ongoing transactions. </p>
    </li>
    <li>
    <p>When you truncate a partition of a subpartitioned table, you can clear data from one or more partitions and their corresponding subpartitions. </p>
    </li>
    </ul>
  </main>

Here are some examples:

* Clear data from the `M202001` and `M202002` partitions in the partitioned table `tbl1_r`.

  ```sql
  obclient> CREATE TABLE tbl1_r (log_id BIGINT NOT NULL,log_value VARCHAR(50),log_date TIMESTAMP NOT NULL)
         PARTITION BY RANGE(UNIX_TIMESTAMP(log_date))
          (PARTITION M202001 VALUES LESS THAN(UNIX_TIMESTAMP('2020/02/01'))
         , PARTITION M202002 VALUES LESS THAN(UNIX_TIMESTAMP('2020/03/01'))
         , PARTITION M202003 VALUES LESS THAN(UNIX_TIMESTAMP('2020/04/01'))
         , PARTITION M202004 VALUES LESS THAN(UNIX_TIMESTAMP('2020/05/01'))
         , PARTITION M202005 VALUES LESS THAN(UNIX_TIMESTAMP('2020/06/01'))
         , PARTITION M202006 VALUES LESS THAN(UNIX_TIMESTAMP('2020/07/01'))
         , PARTITION M202007 VALUES LESS THAN(UNIX_TIMESTAMP('2020/08/01'))
         , PARTITION M202008 VALUES LESS THAN(UNIX_TIMESTAMP('2020/09/01'))
         , PARTITION M202009 VALUES LESS THAN(UNIX_TIMESTAMP('2020/10/01'))
         , PARTITION M202010 VALUES LESS THAN(UNIX_TIMESTAMP('2020/11/01'))
         , PARTITION M202011 VALUES LESS THAN(UNIX_TIMESTAMP('2020/12/01'))
         , PARTITION M202012 VALUES LESS THAN(UNIX_TIMESTAMP('2021/01/01'))
          );
  Query OK, 0 rows affected

  obclient> ALTER TABLE tbl1_r TRUNCATE PARTITION M202001,M202002;
  Query OK, 0 rows affected
  ```

* Clear data from the `p0` partition in the RANGE COLUMNS + LIST COLUMNS partitioned table `t_f_rclc`.

## Truncate a subpartition

The SQL syntax for truncating a subpartition is as follows:

```sql
ALTER TABLE table_name TRUNCATE SUBPARTITION subpartition_name[, subpartition_name ...];
```

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <ul>
    <li>
    <p>Before you truncate a subpartition, make sure that no active transaction or query is running on the subpartition. Otherwise, an error may occur or unexpected behavior may happen. In the <code>sys</code> tenant, query the <code>oceanbase.GV$OB_TRANSACTION_PARTICIPANTS</code> view to obtain the status of ongoing transactions. </p>
    </li>
    <li>
    <p>When you truncate multiple subpartitions, they must belong to the same partition. </p>
    </li>
    </ul>
  </main>

Here is an example of clearing data from the `sp1` and `sp2` subpartitions in the RANGE + RANGE partitioned table `t_f_rr`:

```sql
obclient> CREATE TABLE t_f_rr(col1 INT,col2 TIMESTAMP)
       PARTITION BY RANGE(col1)
       SUBPARTITION BY RANGE(UNIX_TIMESTAMP(col2))
        (PARTITION p0 VALUES LESS THAN(100)
           (SUBPARTITION sp0 VALUES LESS THAN(UNIX_TIMESTAMP('2021/04/01')),
            SUBPARTITION sp1 VALUES LESS THAN(UNIX_TIMESTAMP('2021/07/01')),
            SUBPARTITION sp2 VALUES LESS THAN(UNIX_TIMESTAMP('2021/10/01')),
            SUBPARTITION sp3 VALUES LESS THAN(UNIX_TIMESTAMP('2022/01/01'))
           ),
         PARTITION p1 VALUES LESS THAN(200)
           (SUBPARTITION sp4 VALUES LESS THAN(UNIX_TIMESTAMP('2021/04/01')),
            SUBPARTITION sp5 VALUES LESS THAN(UNIX_TIMESTAMP('2021/07/01')),
            SUBPARTITION sp6 VALUES LESS THAN(UNIX_TIMESTAMP('2021/10/01')),
            SUBPARTITION sp7 VALUES LESS THAN(UNIX_TIMESTAMP('2022/01/01'))
            )
         );
Query OK, 0 rows affected

obclient> ALTER TABLE t_f_rr TRUNCATE SUBPARTITION sp1,sp2;
Query OK, 0 rows affected
```
