# Create a materialized view

This topic describes how to create a materialized view by using an SQL statement.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>At present, OceanBase Database does not support directly modifying the properties of a materialized view, such as the update time and refresh strategy. In this case, you can drop and recreate the materialized view to modify its properties. </p>
</main>

## Privilege requirements

To create a materialized view, you must have the `CREATE TABLE` privilege. For more information about privileges in OceanBase Database, see [Privilege types in MySQL-compatible mode](../../../../../600.manage/500.security-and-permissions/300.access-control/200.user-and-permission/200.permission-of-mysql-mode/100.permission-classification-of-mysql.md).

## Syntax

The syntax for creating a materialized view is as follows:

```sql
CREATE MATERIALIZED VIEW view_name [([column_list] [PRIMARY KEY(column_list)])]
    [table_option_list]
    [partition_option]
    [mv_column_group_option]
    [refresh_clause]
    [query_rewrite_clause]
    [on_query_computation_clause]
    AS view_select_stmt;
```

**The parameters are described as follows:**

* `view_name`: the name of the materialized view to be created.
* `column_list`: optional. The list of columns of the materialized view. If you want to explicitly specify names for the view columns, you can use the `column_list` clause and separate the column names with commas.
* `PRIMARY KEY(column_list)`: optional. The primary key of the materialized view.
* `table_option_list`: optional. The table options of the materialized view.
* `partition_option`: optional. The partitioning options of the materialized view.
* `mv_column_group_option`: optional. The storage format of the materialized view. If this parameter is not specified, a row-based materialized view is created by default.
* `refresh_clause`: optional. The refresh method of the materialized view.
* `query_rewrite_clause`: optional. Specifies whether to enable automatic query rewriting for the materialized view.
* `on_query_computation_clause`: optional. Specifies whether the materialized view is a standard materialized view or a real-time materialized view.
* `AS view_select_stmt`: the query (`SELECT`) statement that defines the data of the materialized view. This statement is used to retrieve data from the base table (a standard table or a materialized view) and store the results in the materialized view.

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>For OceanBase Database V4.3.5, you can create a full-refresh materialized view with an external table as the base table starting from V4.3.5 BP2. </p>
    </main>

For more information about the syntax for creating a materialized view, see [CREATE MATERIALIZED VIEW](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/2250.create-materialized-views-of-mysql-mode-in-sql.md).

## Create a materialized view

### Create a standard materialized view

You can specify or omit the `DISABLE ON QUERY COMPUTATION` clause when you create a standard materialized view.

**Here is an example:**

1. Create a table named `tbl1` as the base table of the materialized view.

    ```sql
    CREATE TABLE tbl1 (col1 INT PRIMARY KEY, col2 VARCHAR(20), col3 INT);
    ```

2. Create a materialized view named `mv_tbl1` based on the `tbl1` table.

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl1
        AS SELECT col1, col2
          FROM tbl1
          WHERE col3 >= 20;
    ```

    Or

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl1
        DISABLE ON QUERY COMPUTATION
        AS SELECT col1, col2
          FROM tbl1
          WHERE col3 >= 20;
    ```

### Create a nested materialized view

A nested materialized view is a materialized view built on another materialized view. For example, in the following figure, the `mv1` materialized view is based on the `tbl1` and `tbl2` tables, which is a typical materialized view. The `mv2` materialized view is based on the `mv1` materialized view and the `tbl3` table, which is a nested materialized view. Similarly, the `mv3` materialized view is based on the `mv1` and `mv2` materialized views, which is also a nested materialized view.

<!-- ![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.3.5/700.reference/300.database-object-management/600.manage-views/%E5%B5%8C%E5%A5%97%E7%89%A9%E5%8C%96%E8%A7%86%E5%9B%BE.png) -->

For OceanBase Database V4.3.5, specifying the refresh strategy for nested materialized views is supported starting from V4.3.5 BP3. The available values are:

* `INDIVIDUAL`: the default value, indicating independent refresh.
* `INCONSISTENT`: indicates cascaded, non-consistent refresh.
*`CONSISTENT`: indicates cascaded, consistent refresh.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>For non-nested materialized views, there is no cascaded refresh behavior. Regardless of the refresh strategy specified, it has no effect and independent refresh is always used by default. The three specified refresh strategies only apply to background tasks. When manually refreshing using the PL package (<a href="../../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/9950.dbms-mview-mysql/300.refresh-mysql.md">DBMS_MVIEW.REFRESH</a>), the refresh is performed according to the parameters specified in the PL call.</p>
</main>

#### Limitations on nested materialized views

* To support incremental refreshes for nested materialized views, you must create a materialized view log on the materialized view (base table).
* If a materialized view is fully refreshed, its nested materialized views must be fully refreshed before incremental refreshes can be performed on them. Otherwise, an error is returned.
* If a nested materialized view is a real-time materialized view, you must perform incremental refreshes on the lower-level materialized views to update the mlogs. The query results of real-time materialized views are obtained by merging the query results of the lower-level materialized views and those of the real-time materialized views themselves. Therefore, you must perform incremental refreshes on the lower-level materialized views to update the mlogs to ensure that the data of real-time materialized views is up to date.

**Here is an example:**

1. Create a table named `tbl3` as the base table of the materialized view.

    ```sql
    CREATE TABLE tbl3(id INT, name VARCHAR(30), PRIMARY KEY(id));
    ```

2. Create a table named `tbl4` as the base table of the materialized view.

    ```sql
    CREATE TABLE tbl4(id INT, age INT, PRIMARY KEY(id));
    ```

3. Create a materialized view named `mv1_tbl3_tbl4` based on tables `tbl3` and `tbl4`.

    ```sql
    CREATE MATERIALIZED VIEW mv1_tbl3_tbl4 (PRIMARY KEY (id1, id2))
        REFRESH COMPLETE
        AS SELECT tbl3.id id1, tbl4.id id2, tbl3.name, tbl4.age
            FROM tbl3, tbl4
            WHERE tbl3.id = tbl4.id;
    ```

4. Create a nested materialized view named `mv_mv1_tbl3_tbl4` based on the `mv1_tbl3_tbl4` materialized view.

    ```sql
    CREATE MATERIALIZED VIEW mv_mv1_tbl3_tbl4
        REFRESH COMPLETE
        AS SELECT SUM(AGE) age_sum
            FROM mv1_tbl3_tbl4;
    ```

5. Create a materialized view (nested materialized view) named `mv1_mv1_tbl3_tbl4` based on the `mv1_tbl3_tbl4` materialized view, with the `INCONSISTENT` refresh strategy.

    ```sql
    CREATE MATERIALIZED VIEW mv1_mv1_tbl3_tbl4
        REFRESH COMPLETE INCONSISTENT
        AS SELECT SUM(AGE) age_sum
            FROM mv1_tbl3_tbl4;
    ```

### Create a real-time materialized view

You can specify the `ENABLE ON QUERY COMPUTATION` clause when you create a materialized view to create a real-time materialized view.

#### Considerations for real-time materialized views

* Before you create a real-time materialized view, you must create a materialized view log on the base tables of the materialized view.
* Only certain types of materialized views support real-time materialized views. If you specify a materialized view that does not meet the conditions for real-time materialized views, an error is returned. The requirements for real-time materialized views are the same as those for incremental refreshes. For more information, see [Refresh materialized views](400.refresh-materialized-views-of-mysql-mode.md) and **Basic requirements for incremental refreshes**.
* If a nested materialized view is a real-time materialized view, you must perform incremental refreshes on the lower-level materialized views to update the mlogs. The query results of real-time materialized views are obtained by merging the query results of the lower-level materialized views and those of the real-time materialized views themselves. Therefore, you must perform incremental refreshes on the lower-level materialized views to update the mlogs to ensure that the data of real-time materialized views is up to date.

**Here is an example:**

1. Create a table named `tbl2` as the base table of the materialized view.

    ```sql
    CREATE TABLE tbl2(col1 INT, col2 INT, col3 INT);
    ```

2. Create a materialized view log on the `tbl2` table.

    ```sql
    CREATE MATERIALIZED VIEW LOG ON tbl2
        WITH PRIMARY KEY, ROWID, SEQUENCE (col1, col2, col3) INCLUDING NEW VALUES;
    ```

3. Create a real-time materialized view named `mv_tbl2` based on the `tbl2` table.

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl2
        ENABLE ON QUERY COMPUTATION
        AS SELECT col1, count(*) AS cnt
           FROM tbl2
           GROUP BY col1;
    ```

4. Use the [DBA_MVIEWS](../../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/5000.o-dba_mviews-of-mysql-mode.md) view to check whether the materialized view is a real-time materialized view.

    ```sql
    SELECT MVIEW_NAME, ON_QUERY_COMPUTATION
    FROM oceanbase.DBA_MVIEWS
    WHERE MVIEW_NAME = 'mv_tbl2';
    ```

    The return result is as follows:

    ```shell

    +------------+----------------------+

    +------------+----------------------+
    1 row in set
    ```

### Create a materialized view with query rewriting enabled

When creating a materialized view, use the `ENABLE QUERY REWRITE` clause to enable automatic rewriting for the current materialized view. For more information about materialized view rewriting and rewrite control, refer to [Query rewriting for materialized views](500.materialized-views-rewrite-of-mysql-mode.md).

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Specifying the <code>ENABLE QUERY REWRITE</code> clause for a materialized view does not necessarily mean that the materialized view will rewrite queries. If a materialized view does not meet the conditions for query rewriting, no error is returned, but the materialized view cannot be used for query rewriting. Since the default value of the system variable <code>query_rewrite_enabled</code> is <code>false</code>, materialized views with the <code>ENABLE QUERY REWRITE</code> clause specified will not be used for query rewriting by default. </p>
</main>

**Here is an example:**

1. Create a materialized view named `mv_spj_tbl1` based on the `tbl1` table and enable automatic query rewriting.

    ```sql
    CREATE MATERIALIZED VIEW mv_spj_tbl1
        ENABLE QUERY REWRITE
        AS SELECT *
           FROM tbl1;
    ```

2. Use the [DBA_MVIEWS](../../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/5000.o-dba_mviews-of-mysql-mode.md) view to check whether the materialized view is a materialized view with query rewriting enabled.

    ```sql
    SELECT MVIEW_NAME, REWRITE_ENABLED
    FROM oceanbase.DBA_MVIEWS
    WHERE MVIEW_NAME = 'mv_spj_tbl1';
    ```

    The return result is as follows:

    ```shell
    +-------------+-----------------+
    | MVIEW_NAME  | REWRITE_ENABLED |
    +-------------+-----------------+
    | mv_spj_tbl1 | Y               |
    +-------------+-----------------+
    1 row in set
    ```

### Create a columnstore-format materialized view

OceanBase Database supports materialized views in rowstore, columnstore, and hybrid rowstore-columnstore formats. You can specify the `mv_column_group_option` option to create a columnstore-format or hybrid rowstore-columnstore-format materialized view. If a materialized view formed by a large wide table through multiple `JOIN` operations is created in columnstore format, the performance of certain queries can be improved. You can specify `WITH COLUMN GROUP(each column)` to create a columnstore-format materialized view.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>If you do not specify the <code>mv_column_group_option</code> option, a rowstore-format materialized view is created by default. </p>
</main>

**Here is an example:**

Create a columnstore-format materialized view named `mv_ec_tbl1` based on the `tbl1` table.

```sql
CREATE MATERIALIZED VIEW mv_ec_tbl1
    WITH COLUMN GROUP(each column)
    AS SELECT *
       FROM tbl1;
```

## Create a materialized view with a primary key

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>When you specify a primary key for a materialized view, if the data does not meet the primary key constraints during maintenance or updates of the materialized view data, the view maintenance will fail. </p>
</main>

**Here is an example:**

Create a materialized view named `mv_pk_tbl1` based on the `tbl1` table and specify a primary key.

```sql
CREATE MATERIALIZED VIEW mv_pk_tbl1(v_id, v_name, PRIMARY KEY(v_id))
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

## Create a materialized view with table options and partition options

When you create a materialized view, you can set table options and design and configure partition options based on data characteristics and access patterns to improve query performance and management efficiency.

For more information about table options and partition options, see [CREATE TABLE](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/2600.create-table-of-mysql-mode.md).

**Here is an example:**

Create a materialized view named `mv_pp_tbl1` based on the `tbl1` table. Set the parallelism of the materialized view to `5`, hash partition the materialized view by the `col1` column into `8` partitions, query records from the `tbl1` table that meet the `col3 >= 20` condition as the base table, and use the query results as the data of the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_pp_tbl1
    PARALLEL 5
    PARTITION BY HASH(col1) PARTITIONS 8
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

## Add an index to a materialized view

You cannot directly create an index when you create a materialized view. You can use the [CREATE INDEX](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/2200.create-index-of-mysql-mode.md) or [ALTER TABLE](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1600.alter-table-of-mysql-mode.md) statement to create an index for a materialized view.

**Here is an example:**

* Create an index named `idx1_mv_tbl1` on the `col1` column of the `mv_tbl1` materialized view.

  ```sql
  CREATE INDEX idx1_mv_tbl1 ON mv_tbl1(col1);
  ```

* Create an index named `idx2_mv_tbl1` on the `col2` column of the `mv_tbl1` materialized view.

  ```sql
  ALTER TABLE mv_tbl1 ADD INDEX idx2_mv_tbl1(col2);
  ```

## Refresh a materialized view

OceanBase Database supports full refresh, incremental refresh, hybrid refresh, and never refresh strategies for materialized views. The refresh strategies are described as follows:

* Full refresh: Recalculates all data in the materialized view to ensure that the data in the view is consistent with that in the source table.
* Incremental refresh: Refreshes only the data that has changed in the source table, avoiding complete recalculation of the view.
* Hybrid refresh: The default option. First attempts an incremental refresh. If the incremental refresh fails, a full refresh is performed.
* Never refresh: The materialized view is refreshed only when it is created and cannot be refreshed again after it is created.

For more information about refreshing materialized views, see [Refresh a materialized view](400.refresh-materialized-views-of-mysql-mode.md).

### Create a materialized view with full refresh strategy

You can specify the `REFRESH COMPLETE` clause when you create a materialized view to set the refresh strategy to full refresh.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If a materialized view is refreshed in full refresh mode, its nested materialized views (nested materialized views) must be refreshed in full refresh mode before they are incrementally refreshed. Otherwise, an error is returned. </p>
</main>

**Here is an example:**

Create a materialized view named `mv_rc_tbl1` based on the `tbl1` table and set the refresh strategy to full refresh (`REFRESH COMPLETE`). Specify that the `col1` and `col2` columns of the `tbl1` table whose `col3` values are greater than or equal to `20` are used as the data source of the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_rc_tbl1
    REFRESH COMPLETE
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

**Here is an example:**

### Create a materialized view with incremental refresh strategy

You can specify the `REFRESH FAST` clause when you create a materialized view to set the refresh strategy to incremental refresh.

#### Considerations for creating a materialized view with incremental refresh strategy

* Currently, incremental refresh for materialized views supports SQL statements in five scenarios: single-table non-aggregation, single-table aggregation, multi-table join, multi-table join with aggregation, and set queries (`UNION ALL`). Incremental refresh is not supported for SQL statements that do not fit into these five scenarios. For detailed requirements on incremental refresh SQL statements, please refer to the **Incremental refreshes** section in [Refresh a materialized view](400.refresh-materialized-views-of-mysql-mode.md).

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>For OceanBase Database V4.3.5, incremental refresh for materialized views supports single-table non-aggregation and set query scenarios starting from V4.3.5 BP3. </p>
    </main>

* The `REFRESH FAST` method uses the records in the materialized view logs to determine the data to be incrementally refreshed. Therefore, you must create materialized view logs for the base table before you create a materialized view for incremental refresh. For more information about materialized view logs, see [Materialized view logs](200.materialized-views-log-of-mysql-mode.md).

**Here is an example:**

1. Create the `tbl5` table as the base table of the materialized view.

    ```sql
    CREATE TABLE tbl5 (col1 INT PRIMARY KEY, col2 INT, col3 INT);
    ```

2. Create materialized view logs for the `tbl5` table and set the option of the materialized view logs to `SEQUENCE` to indicate that the sequence number is used to identify changed data. Specify the columns to be recorded, including the `col2` and `col3` columns.

    ```sql
    CREATE MATERIALIZED VIEW LOG ON tbl5
        WITH SEQUENCE (col2, col3) INCLUDING NEW VALUES;
    ```

3. Create a materialized view named `mv_tbl5` based on the `tbl5` table and set the refresh strategy to incremental refresh. Specify that the `cnt`, `cnt_col3`, and `sum_col3` columns are used as the result of the materialized view. The `cnt` column indicates the number of records in each group of the `tbl5` table based on the `col2` column. The `cnt_col3` column indicates the number of non-null `col3` records in each group. The `sum_col3` column indicates the total value of the `col3` column in each group.

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl5
        REFRESH FAST
        AS SELECT col2, COUNT(*) cnt, COUNT(col3) cnt_col3, SUM(col3) sum_col3 
           FROM tbl5
           GROUP BY col2;
    ```

### Create a materialized view with hybrid refresh strategy (default option)

You can specify the `REFRESH FORCE` clause when you create a materialized view to set the refresh strategy to hybrid refresh.

**Here is an example:**

Create a materialized view named `mv_rf_tbl1` based on the `tbl1` table and set the refresh strategy to hybrid refresh. Specify that the `col1` and `col2` columns of the `tbl1` table whose `col3` values are greater than or equal to `20` are used as the data source of the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_rf_tbl1
    REFRESH FORCE
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

### Create a materialized view with never refresh strategy

You can specify the `NEVER REFRESH` clause when you create a materialized view to set the refresh strategy to never refresh.

**Here is an example:**

Create a materialized view named `mv_nr_tbl1` based on the `tbl1` table and set the refresh strategy to never refresh. Specify that the `col1` and `col2` columns of the `tbl1` table whose `col3` values are greater than or equal to `20` are used as the data source of the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_nr_tbl1
    NEVER REFRESH
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

## Create an auto-refresh materialized view

You can specify the `START WITH datetime_expr` and `NEXT datetime_expr` clauses when you create a materialized view to create an automatic refresh task for the materialized view in the background.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If the <code>NEXT</code> clause is specified, the time expression for the refresh plan must be set to a future time. Otherwise, an error is returned. </p>
</main>

**Here is an example:**

Create a materialized view named `mv_rc_swn_tbl1` based on the `tbl1` table and set the refresh strategy to full refresh. Specify that the materialized view is initially refreshed on the current date and is refreshed every `1` day thereafter.

```sql
CREATE MATERIALIZED VIEW mv_rc_swn_tbl1
    REFRESH COMPLETE
        START WITH sysdate() NEXT sysdate() + interval 1 day
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```
