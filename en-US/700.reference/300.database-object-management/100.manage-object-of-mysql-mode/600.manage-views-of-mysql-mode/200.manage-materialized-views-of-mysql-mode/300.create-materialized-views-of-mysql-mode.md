# Create a materialized view

This topic describes how to create a materialized view by using SQL statements. 

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>OceanBase Database does not support directly modifying the properties of a materialized view, such as the refresh time and refresh strategy. In this case, you can delete and recreate the materialized view to achieve the desired modifications. </p>
</main>

## Privilege requirements

To create a materialized view, you must have the `CREATE TABLE` privilege. For more information about the privileges of OceanBase Database, see [Privilege types in MySQL mode](../../../../../600.manage/500.security-and-permissions/300.access-control/200.user-and-permission/200.permission-of-mysql-mode/100.permission-classification-of-mysql.md).

## Syntax

The SQL statement for creating a materialized view is as follows:

```sql
CREATE MATERIALIZED VIEW view_name [([column_list] [PRIMARY KEY(column_list)])]
    [table_option_list]
    [partition_option]
    [mv_column_group_option]
    [refresh_clause]
    [query_rewrite_clause]
    [on_query_computation_clause]
    AS view_select_stmt; 
```

**Parameters:**

* `view_name`: the name of the materialized view to be created.
* `column_list`: optional. The list of columns in the materialized view. If you want to specify the names of the view columns, you can use the `column_list` clause and separate the column names with commas.
* `PRIMARY KEY(column_list)`: optional. The primary key of the materialized view.
* `table_option_list`: optional. The table options of the materialized view.
* `partition_option`: optional. The partition options of the materialized view.
* `mv_column_group_option`: optional. The storage format of the materialized view. If this option is not specified, a row-based materialized view is created by default.
* `refresh_clause`: optional. The refresh method of the materialized view.
* `query_rewrite_clause`: optional. Specifies whether to enable automatic rewriting for the current materialized view.
* `on_query_computation_clause`: optional. Specifies whether the current materialized view is a regular materialized view or a real-time materialized view.
* `AS view_select_stmt`: the query (SELECT) statement used to define the data of the materialized view. This statement is used to retrieve data from the base table and store the results in the materialized view.

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p><ul><li>OceanBase Database allows you to create a full-refresh materialized view with an external table as the base table.</li><li>OceanBase Database allows you to add the <code>AS OF PROCTIME()</code> clause to the base table when you create a materialized view. If you use the <code>AS OF PROCTIME()</code> clause outside the base table of the materialized view, an error is returned. The <code>AS OF PROCTIME()</code> clause specifies to skip the refresh of this table during incremental refreshes. In addition, you do not need to create an mlog table for the <code>AS OF PROCTIME()</code> table.</li><li>OceanBase Database allows you to declare a regular view as a dimension table (<code>AS OF PROCTIME()</code>) and use it as the base table of an incremental-refresh materialized view.</li></ul></p>
    </main>

For more information about the parameters of the CREATE MATERIALIZED VIEW statement, see [CREATE MATERIALIZED VIEW](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/2250.create-materialized-views-of-mysql-mode-in-sql.md).

## Create a materialized view

### Create a regular materialized view

To create a regular materialized view, omit or specify the `DISABLE ON QUERY COMPUTATION` clause.

**Here is an example:**

1. Create the `tbl1` table as the base table for the materialized view.

    ```sql
    CREATE TABLE tbl1 (col1 INT PRIMARY KEY, col2 VARCHAR(20), col3 INT);
    ```

2. Create a materialized view named `mv_tbl1` based on the `tbl1` table.

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl1
        AS SELECT col1, col2
          FROM tbl1
          WHERE col3 >= 20;
    ```

    Or

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl1
        DISABLE ON QUERY COMPUTATION
        AS SELECT col1, col2
          FROM tbl1
          WHERE col3 >= 20;
    ```

### Create a nested materialized view

A nested materialized view is a materialized view created based on another materialized view. For example, in the following figure, the `mv1` materialized view is created based on the `tbl1` and `tbl2` tables, which is a regular materialized view. The `mv2` materialized view is created based on the `mv1` materialized view and the `tbl3` table, which is a nested materialized view. Similarly, the `mv3` materialized view is created based on the `mv1` and `mv2` materialized views, which is also a nested materialized view.

![1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.3.5/700.reference/300.database-object-management/600.manage-views/%E5%B5%8C%E5%A5%97%E7%89%A9%E5%8C%96%E8%A7%86%E5%9B%BE.png)

When you create a nested materialized view in OceanBase Database, you can specify the refresh strategy. Valid values are as follows:

* `INDIVIDUAL`: The default value. This option indicates that the materialized view is refreshed independently.
* `INCONSISTENT`: This option indicates that the materialized view is refreshed in a cascading manner with inconsistency.
* `CONSISTENT`: This option indicates that the materialized view is refreshed in a cascading manner with consistency.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>For a regular materialized view, the cascading refresh strategy does not take effect regardless of the specified refresh strategy. The specified refresh strategy only takes effect when you manually use the <a href="../../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/9950.dbms-mview-mysql/300.refresh-mysql.md">DBMS_MVIEW.REFRESH</a> package to schedule a refresh. In this case, the refresh is performed based on the specified PL parameters.</p>
</main>

#### Limitations on nested materialized views

* To support incremental refreshes of nested materialized views, you must create materialized view logs on the base tables.
* If a materialized view is fully refreshed, the nested materialized views that depend on it must be fully refreshed before they can be incrementally refreshed. Otherwise, an error will be returned.
* You cannot create a nested materialized view as a real-time materialized view. In other words, you cannot specify the `ENABLE ON QUERY COMPUTATION` clause when creating a nested materialized view.

**Here is an example:**

1. Create the `tbl3` table as the base table for the materialized view.

    ```sql
    CREATE TABLE tbl3(id INT, name VARCHAR(30), PRIMARY KEY(id));
    ```

2. Create the `tbl4` table as the base table for the materialized view.

    ```sql
    CREATE TABLE tbl4(id INT, age INT, PRIMARY KEY(id));
    ```

3. Create a materialized view named `mv1_tbl3_tbl4` based on the `tbl3` and `tbl4` tables.

    ```sql
    CREATE MATERIALIZED VIEW mv1_tbl3_tbl4 (PRIMARY KEY (id1, id2))
        REFRESH COMPLETE
        AS SELECT tbl3.id id1, tbl4.id id2, tbl3.name, tbl4.age
            FROM tbl3, tbl4
            WHERE tbl3.id = tbl4.id;
    ```

4. Create a nested materialized view named `mv_mv1_tbl3_tbl4` based on the `mv1_tbl3_tbl4` materialized view.

    ```sql
    CREATE MATERIALIZED VIEW mv_mv1_tbl3_tbl4
        REFRESH COMPLETE
        AS SELECT SUM(AGE) age_sum
            FROM mv1_tbl3_tbl4;
    ```

5. Create a nested materialized view named `mv1_mv1_tbl3_tbl4` based on the `mv1_tbl3_tbl4` materialized view. The refresh strategy is `INCONSISTENT`.

    ```sql
    CREATE MATERIALIZED VIEW mv1_mv1_tbl3_tbl4
        REFRESH COMPLETE INCONSISTENT
        AS SELECT SUM(AGE) age_sum
            FROM mv1_tbl3_tbl4;
    ```

### Create a real-time materialized view

To create a real-time materialized view, specify the `ENABLE ON QUERY COMPUTATION` clause.

#### Considerations

* Before you create a real-time materialized view, you must create materialized view logs on the base tables on which the materialized view depends.

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>OceanBase Database supports automatic management of materialized view logs. If you enable automatic management of materialized view logs, you do not need to create materialized view logs on the base tables when you create a real-time materialized view. OceanBase Database automatically creates the corresponding materialized view logs or updates the existing materialized view log tables to include the columns required by the new materialized view. For more information, see <a href="250.automatic-management-materialized-views-log-of-mysql-mode.md">Automatic management of materialized view logs</a>.</p>
    </main>

* Only specific types of materialized views can be created as real-time materialized views. If you specify the `ENABLE ON QUERY COMPUTATION` clause for a materialized view that does not meet the requirements, an error will be returned. The requirements for real-time materialized views are the same as those for materialized views that support incremental refreshes. For more information, see the **Basic requirements for incremental refreshes** section in [Refresh a materialized view](400.refresh-materialized-views-of-mysql-mode.md).

  * Materialized views that use the `MIN` or `MAX` function cannot be created as real-time materialized views.
  * Aggregated materialized views with outer joins cannot be created as real-time materialized views.
  * Materialized views with set queries cannot be created as real-time materialized views.
  * Nested materialized views cannot be created as real-time materialized views.

* If the values of the system variables in the session that executes a query do not match the values of the session variables that are fixed in the materialized view, you must modify the system variables in the session to match the session variables fixed in the real-time materialized view. Otherwise, the real-time materialized view will be unavailable. In this case, query rewriting for the real-time materialized view will not take effect, or an error will be returned when you directly query the real-time materialized view.

**Here is an example:**

1. Create the `tbl2` table as the base table for the materialized view.

    ```sql
    CREATE TABLE tbl2(col1 INT, col2 INT, col3 INT);
    ```

2. Create a materialized view log on the `tbl2` table.

    ```sql
    CREATE MATERIALIZED VIEW LOG ON tbl2
        WITH PRIMARY KEY, ROWID, SEQUENCE (col1, col2, col3) INCLUDING NEW VALUES;
    ```

3. Create a real-time materialized view named `mv_tbl2` based on the `tbl2` table.

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl2
        ENABLE ON QUERY COMPUTATION
        AS SELECT col1, count(*) AS cnt
           FROM tbl2
           GROUP BY col1;
    ```

4. After you create the real-time materialized view, you can query the [DBA_MVIEWS](../../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/5000.o-dba_mviews-of-mysql-mode.md) view to check whether the materialized view is a real-time materialized view.

    ```sql
    SELECT MVIEW_NAME, ON_QUERY_COMPUTATION
    FROM oceanbase.DBA_MVIEWS
    WHERE MVIEW_NAME = 'mv_tbl2';
    ```

    The returned result is as follows:

    ```shell

    +------------+----------------------+
    | mv_tbl2    | Y                    |
    +------------+----------------------+
    1 row in set
    ```


### Create a materialized view that supports query rewrite

When you create a materialized view, specify the `ENABLE QUERY REWRITE` clause to enable query rewrite for the materialized view. For more information about query rewrite and rewrite control for materialized views, see [Query rewrite for materialized views](500.materialized-views-rewrite-of-mysql-mode.md).

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Specifying the <code>ENABLE QUERY REWRITE</code> clause for a materialized view does not guarantee that query rewrite will be performed for the materialized view. If the query rewrite conditions are not met, the query will not be rewritten, and no error will be returned. By default, the system variable <code>query_rewrite_enabled</code> is set to <code>false</code>, so materialized views specified with the <code>ENABLE QUERY REWRITE</code> clause will not be used for query rewrite by default.</p>
</main>

**Here is an example:**

1. Create a materialized view named `mv_spj_tbl1` based on the `tbl1` table and enable query rewrite for the materialized view.

    ```sql
    CREATE MATERIALIZED VIEW mv_spj_tbl1
        ENABLE QUERY REWRITE
        AS SELECT *
           FROM tbl1;
    ```

2. After the materialized view is created, you can query the [DBA_MVIEWS](../../../../700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/5000.o-dba_mviews-of-mysql-mode.md) view to check whether query rewrite is enabled for the materialized view.

    ```sql
    SELECT MVIEW_NAME, REWRITE_ENABLED
    FROM oceanbase.DBA_MVIEWS
    WHERE MVIEW_NAME = 'mv_spj_tbl1';
    ```

    The return result is as follows:

    ```shell
    +-------------+-----------------+
    | MVIEW_NAME  | REWRITE_ENABLED |
    +-------------+-----------------+
    | mv_spj_tbl1 | Y               |
    +-------------+-----------------+
    1 row in set
    ```

### Create a columnstore materialized view

OceanBase Database supports materialized views in rowstore, columnstore, and rowstore-columnstore redundant formats. You can specify the `mv_column_group_option` option to create a columnstore or rowstore-columnstore redundant materialized view. If a materialized view is created by joining multiple tables, creating a columnstore materialized view can improve the performance of some queries. You can specify the `WITH COLUMN GROUP(each column)` option to create a columnstore materialized view.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>If you do not specify the <code>mv_column_group_option</code> option, a rowstore materialized view will be created by default.</p>
</main>

**Here is an example:**

Create a columnstore materialized view named `mv_ec_tbl1` based on the `tbl1` table.

```sql
CREATE MATERIALIZED VIEW mv_ec_tbl1
    WITH COLUMN GROUP(each column)
    AS SELECT *
       FROM tbl1;
```

## Add a primary key when you create a materialized view

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If you specify a primary key for a materialized view, the maintenance or update of the materialized view will fail if the data does not meet the primary key constraints. </p>
</main>

**Here is an example:**

Create a materialized view named `mv_pk_tbl1` based on the `tbl1` table and specify a primary key for the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_pk_tbl1(v_id, v_name, PRIMARY KEY(v_id))
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

## Specify table options and partition options when you create a materialized view

When you create a materialized view, you can specify table options and partition options. You can set table options and design and configure partition options based on data characteristics and access patterns to improve query performance and management efficiency.

For more information about the parameters of table options and partition options, see [CREATE TABLE](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/2600.create-table-of-mysql-mode.md).

**Here is an example:**

Create a materialized view named `mv_pp_tbl1` based on the `tbl1` table. Set the parallelism of the materialized view to `5`. Hash partition the materialized view by the `col1` column and divide it into `8` partitions. Query the records in the `tbl1` table that meet the condition `col3 >= 20` as the base table and use the query result as the data of the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_pp_tbl1
    PARALLEL 5
    PARTITION BY HASH(col1) PARTITIONS 8
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

## Add an index to a materialized view

You cannot directly create an index in the statement for creating a materialized view. You can use the [CREATE INDEX](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/2200.create-index-of-mysql-mode.md) statement or the [ALTER TABLE](../../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1600.alter-table-of-mysql-mode.md) statement to create an index for a materialized view.

**Here is an example:**

* Create an index named `idx1_mv_tbl1` on the `col1` column of the materialized view `mv_tbl1`.

  ```sql
  CREATE INDEX idx1_mv_tbl1 ON mv_tbl1(col1);
  ```

* Create an index named `idx2_mv_tbl1` on the `col2` column of the materialized view `mv_tbl1`.

  ```sql
  ALTER TABLE mv_tbl1 ADD INDEX idx2_mv_tbl1(col2);
  ```

## Refresh a materialized view

OceanBase Database supports the following four refresh modes: full refresh, incremental refresh, hybrid refresh, and no refresh.

* Full refresh: The data of the materialized view is recalculated to ensure that it is consistent with the data of the source table.
* Incremental refresh: Only the data that corresponds to the changes in the source table is refreshed, without recalculation of the entire view.
* Hybrid refresh: The default refresh mode. An incremental refresh is first attempted. If it fails, a full refresh is executed.
* No refresh: The materialized view is refreshed only when it is created and cannot be refreshed again after creation.

For more information, see [Refresh a materialized view](400.refresh-materialized-views-of-mysql-mode.md).

### Create a materialized view with a complete refresh strategy

When creating a materialized view, use the `REFRESH COMPLETE` clause to set the refresh strategy to complete refresh.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If a materialized view is refreshed with a complete refresh, any dependent materialized views (nested materialized views) must also be refreshed with a complete refresh before an incremental refresh can be performed, otherwise an error will occur.</p>
</main>

**Here is an example:**

Create a materialized view named `mv_rc_tbl1` based on the `tbl1` table, set the refresh strategy to complete refresh (`REFRESH COMPLETE`), and specify that the data source for the materialized view consists of the `col1` and `col2` columns from the `tbl1` table where `col3` is greater than or equal to `20`.

```sql
CREATE MATERIALIZED VIEW mv_rc_tbl1
    REFRESH COMPLETE
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

#### Create a materialized view with a complete refresh strategy based on an external table

OceanBase Database supports creating a materialized view with a complete refresh strategy based on an external table.

For more information about external tables, see [About external tables](../../200.manage-tables-of-mysql-mode/1000.manage-external-tables-of-mysql-mode/100.about-external-tables-of-mysql-mode.md).

**Here is an example:**

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>The IP addresses in the example have been desensitized. When verifying, replace them with the actual IP addresses of your machine.</p>
</main>

The following example creates an external table based on an external file located on the local machine and in the MySQL mode of OceanBase Database. The steps are as follows:

1. Prepare the external file.

    Execute the following command to create a file named `ext_tbl1.csv` in the `/home/admin` directory on the machine where the OBServer node is located.

    ```shell
    [admin@xxx /home/admin]# vi ext_tbl1.csv
    ```

    The content of the file is as follows:

    ```shell
    1,'A1','2025-01-01'
    2,'A2','2025-02-01'
    3,'A3','2025-03-01'
    ```

2. Set the import file path.

    <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>For security reasons, when setting the system variable <code>secure_file_priv</code>, you can only modify the global variable by executing an SQL statement through a local Socket connection. For more information, see <a href="../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/12000.secure_file_priv-global.md">secure_file_priv</a>.</p>
    </main>

    1. Execute the following command to log in to the machine where the OBServer node is located.

        ```shell
        ssh admin@10.10.10.1
        ```

    2. Execute the following command to connect to the `mysql001` tenant using a local Unix Socket connection.

        ```shell
        obclient -S /home/admin/oceanbase/run/sql.sock -uroot@mysql001 -p******
        ```

    3. Execute the following SQL command to set the import path to `/home/admin`.

        ```sql
        SET GLOBAL secure_file_priv = "/home/admin";
        ```

3. Reconnect to the `mysql001` tenant.

    Here is an example:

    ```shell
    obclient -h10.10.10.1 -P2881 -uroot@mysql001 -p****** -A -Ddb_test
    ```

4. Create an external table named `ext_tbl1`.

    ```sql
    CREATE EXTERNAL TABLE ext_tbl1 ( 
        id INT, 
        name VARCHAR(50), 
        c_date    DATE
        )
        LOCATION = '/home/admin'
        FORMAT = (
          TYPE = 'CSV'
          FIELD_DELIMITER = ','
          FIELD_OPTIONALLY_ENCLOSED_BY ='\''
          )
        PATTERN = 'ext_tbl1.csv';
    ```

5. Create a materialized view named `mv_ext_tbl1` based on the external table `ext_tbl1` with a complete refresh strategy.

    ```sql
    CREATE MATERIALIZED VIEW mv_ext_tbl1
        REFRESH COMPLETE
        AS SELECT *
            FROM ext_tbl1;
    ```

6. View the data in the materialized view `mv_ext_tbl1`.

    ```sql
    SELECT * FROM mv_ext_tbl1;
    ```

    The returned result is as follows:

    ```shell
    +------+------+------------+
    | id   | name | c_date     |
    +------+------+------------+
    |    1 | A1   | 2025-01-01 |
    |    3 | A3   | 2025-03-01 |
    |    2 | A2   | 2025-02-01 |
    +------+------+------------+
    3 rows in set
    ```

### Create a materialized view with incremental refresh

When you create a materialized view, use the `REFRESH FAST` clause to set the refresh strategy to incremental refresh.

#### Considerations

* Currently, incremental refresh is supported for SQL statements that involve non-aggregated single-table queries, aggregated single-table queries, multi-table joins, multi-table joined aggregated queries, and `UNION ALL` queries. For SQL statements that do not fall into these five categories, incremental refresh is not supported. For more information about incremental refresh, see the **Incremental refresh** section in [Refresh a materialized view](400.refresh-materialized-views-of-mysql-mode.md).
* The `REFRESH FAST` method uses the records in the materialized view log to determine the content to be incrementally refreshed. Therefore, when you use incremental refresh to refresh a materialized view, you must create a materialized view log for the base table before you create the materialized view. For more information about how to create a materialized view log, see [Materialized view log](200.materialized-views-log-of-mysql-mode.md).

    <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>OceanBase Database supports automatic management of materialized view logs. If you enable automatic management of materialized view logs, you do not need to create a materialized view log for the base table before you create an incrementally refreshed materialized view. OceanBase Database automatically creates the corresponding materialized view log or updates the existing materialized view log table definition to include the columns required by the new materialized view. For more information, see <a href="250.automatic-management-materialized-views-log-of-mysql-mode.md">Automatic management of materialized view logs</a>.</p>
    </main>

* When you create a materialized view, you can add the `AS OF PROCTIME()` clause to the base table. If you use `AS OF PROCTIME()` outside the base table, an error is returned.

  * The `AS OF PROCTIME()` clause specifies to skip the refresh of the table during incremental refresh, thereby accelerating the incremental refresh of the materialized view. You do not need to create a materialized view log for the table specified by `AS OF PROCTIME()`. If you want to use an alias for the table, you must specify the alias after the `AS OF PROCTIME()` clause.
  * If you use a regular view declared as a dimension table (by using the <code>AS OF PROCTIME()</code> clause) as the base table of an incrementally refreshed materialized view, the following limitations apply:

    * All tables in the materialized view cannot be dimension tables, similar to the base table of the materialized view.

**Here is an example:**

1. Create a table named `tbl5` as the base table of the materialized view.

    ```sql
    CREATE TABLE tbl5 (col1 INT PRIMARY KEY, col2 INT, col3 INT);
    ```

2. Create a materialized view log for the `tbl5` table and specify the `SEQUENCE` option. This option indicates that the changes in the table are identified by sequence numbers. Specify the `col2` and `col3` columns to be recorded in the materialized view log.

    ```sql
    CREATE MATERIALIZED VIEW LOG ON tbl5
        WITH SEQUENCE (col2, col3) INCLUDING NEW VALUES;
    ```

3. Create a materialized view named `mv_tbl5` based on the `tbl5` table. Specify the incremental refresh strategy. In the query part, specify to group the records in the `tbl5` table by the `col2` column, and calculate the number of records in each group (`cnt`), the number of non-null records in the `col3` column (`cnt_col3`), and the sum of the `col3` column (`sum_col3`) as the result of the materialized view.

    ```sql
    CREATE MATERIALIZED VIEW mv_tbl5
        REFRESH FAST
        AS SELECT col2, COUNT(*) cnt, COUNT(col3) cnt_col3, SUM(col3) sum_col3 
           FROM tbl5 
           GROUP BY col2;
    ```

4. Create a materialized view named `mv2_tbl5_tbl1` based on the `tbl5` and `tbl1` tables. Specify the incremental refresh strategy. Join the `tbl5` and `tbl1` tables by the `col1` column. Use the `AS OF PROCTIME()` clause to specify to skip the refresh of the `tbl1` table during incremental refresh.

    ```sql
    CREATE MATERIALIZED VIEW mv2_tbl5_tbl1
        REFRESH FAST ON DEMAND
        AS SELECT 
            t5.col1 tbl5_c1,
            t1.col1 tbl1_c1,
            t5.col2 tbl5_c2,
            t1.col2 tbl1_c2
        FROM tbl5 t5
            INNER JOIN tbl1 AS OF PROCTIME() t1
            ON t5.col1 = t1.col1
        WHERE t5.col2 = 3;
    ```

5. Create an incrementally refreshed materialized view based on a regular view that is declared as a dimension table (by using the `AS OF PROCTIME()` clause).

   1. Create a view named `v1_tbl5` based on the `tbl5` table.

       ```shell
       obclient> CREATE VIEW v1_tbl5 AS SELECT * FROM tbl5;
       ```

   2. Create a materialized view named `mv3_tbl5_v_tbl5` based on the `tbl5` and `v1_tbl5` tables. Specify the incremental refresh strategy. Join the `tbl5` and `v1_tbl5` tables by the `col1` column. Use the `AS OF PROCTIME()` clause to specify the `v1_tbl5` view as a dimension table.

       ```shell
       obclient> CREATE MATERIALIZED VIEW mv3_tbl5_v_tbl5
           AS SELECT
               a.col1 a_c1,
               b.col1 b_c1
           FROM tbl5 a JOIN v1_tbl5 AS OF PROCTIME() b
           ON a.col1 = b.col1;
       ```

### Create a materialized view with hybrid refresh (default option)

When you create a materialized view, omit or specify the `REFRESH FORCE` clause to set the refresh strategy to hybrid refresh.

**Here is an example:**

Create a materialized view named `mv_rf_tbl1` based on the `tbl1` table. Specify the hybrid refresh strategy. Specify to select the `col1` and `col2` columns from the `tbl1` table where `col3` is greater than or equal to `20` as the data source of the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_rf_tbl1
    REFRESH FORCE
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

### Create a materialized view that is never refreshed

When you create a materialized view, use the `NEVER REFRESH` clause to specify that the materialized view is never refreshed. This means that the materialized view is only refreshed when it is created and cannot be refreshed again after it is created.

**Here is an example:**

Create a materialized view named `mv_nr_tbl1` based on the `tbl1` table. Specify the never-refresh strategy. Specify to select the `col1` and `col2` columns from the `tbl1` table where `col3` is greater than or equal to `20` as the data source of the materialized view.

```sql
CREATE MATERIALIZED VIEW mv_nr_tbl1
    NEVER REFRESH
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```

## Create a materialized view with an automatic refresh schedule

When you create a materialized view, you can specify the `START WITH datetime_expr` and `NEXT datetime_expr` clauses to create a background automatic refresh task for the materialized view.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If you use the <code>NEXT</code> clause, the time expression in the refresh schedule must be set to a future date and time. Otherwise, an error will occur.</p>
</main>

**Here is an example:**

Create a materialized view named `mv_rc_swn_tbl1` based on the `tbl1` table, specifying a full refresh strategy for the materialized view. Set the initial refresh time to the current date and schedule subsequent refreshes every `1` day.

```sql
CREATE MATERIALIZED VIEW mv_rc_swn_tbl1
    REFRESH COMPLETE
        START WITH sysdate() NEXT sysdate() + interval 1 day
    AS SELECT col1, col2
       FROM tbl1
       WHERE col3 >= 20;
```
