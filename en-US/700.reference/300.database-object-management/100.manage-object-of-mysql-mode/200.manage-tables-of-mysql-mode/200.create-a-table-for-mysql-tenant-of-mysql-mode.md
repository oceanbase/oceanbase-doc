## Create a replicated table

A replicated table is a special type of table in OceanBase Database. This table allows you to read the latest modifications on any "healthy" replica. For users who have low write requirements but high read latency and load balancing requirements, a replicated table is an excellent choice.

After you create a replicated table, a replica of this table is created on all OBServer nodes of the tenant. One of the replicas is selected as the leader to accept write requests, while the remaining replicas can only accept read requests.

All replicas need to report their status to the leader, mainly the replay progress, which indicates the data synchronization progress. Generally, the replay progress of a follower replica lags slightly behind that of the leader. As long as the lag does not exceed a certain threshold, the leader considers the replica to be "healthy" and can quickly replay the modifications on the leader. Once the leader considers a replica to be "healthy" for a certain period, it grants the follower a lease. In other words, the leader trusts the follower to remain "healthy" during this period and to provide strongly consistent read services. During this "trust" period, the leader confirms the replay progress of the follower before committing each replicated table transaction. After the follower replays the modifications of the transaction, the leader reports the transaction commit success to the user. At this point, the user can read the modifications of the committed transaction on the follower.

The feature of replicated tables has been available in OceanBase Database V3.x. For V4.x, due to significant changes in the architecture of OceanBase Database, the replicated tables in V4.x are designed to adapt to the new single-machine log stream architecture. They implement partition-based readable version verification and log stream-based lease granting mechanisms to ensure the correctness of strongly consistent reads.

Additionally, the replicated table feature in V4.x improves the ability to switch leaders without killing transactions. In V3.x, uncommitted replicated table transactions would fail when a leader switch was initiated by the user or the load balancer. In V4.x, these transactions can continue execution after the leader switch. Compared to V3.x, V4.x replicated tables also offer better write transaction performance and stronger disaster recovery capabilities, with less impact on read operations when a replica fails.

### Limitations of replicated tables

* Replicated tables:

  * Creation limitations: The sys tenant and meta tenant do not support creating replicated tables because they do not have broadcast log streams.
  * Write performance is affected by the number of nodes: Since replicated table writes need to be synchronized to all replicas, the more nodes there are, the greater the impact on write performance.
    * Workaround: Avoid having replicated table writes and reads in the same transaction. Pure writes or pure reads on replicated tables are fine.

  * Attribute conversion:

    * Replicated tables and table groups are mutually exclusive. Modifying the table group attribute of a replicated table will result in an error. Similarly, changing the attribute of a regular table to a replicated table will result in an error if the regular table belongs to a table group.
    * Converting a replicated table depends on load balancing and transfer, so ensure that the relevant configuration items are enabled.

  * Routing:

    * If a transaction contains writes to a replicated table, subsequent queries to the replicated table may be randomly routed to a follower. This can result in the replica being unreadable, as the observer will internally forward the request to the leader of the replicated table, affecting query performance.

      * In ODP V4.3.3, the routing strategy has been adjusted. If there are writes to a replicated table, subsequent queries will be routed to the leader of the replicated table.

    * Queries that join a replicated table with a regular table will be randomly routed based on the replicated table (for JOIN queries, ODP routes based on the first table). This may route to a non-leader node of the regular table, resulting in a remote plan.
    * When a regular table is converted to a replicated table, ODP cannot detect this change and cannot route queries to the replicated table to balance the load.

  * In a transaction, if a replicated table has been modified, subsequent queries will generate an execution plan that selects the local replica. However, due to the modification, an error indicating that the replica is unreadable will be reported. SQL retries will select the leader replica, and the plan cache will not hit, resulting in poor query performance.

      <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>In a transaction, if a replicated table is modified, OceanBase Database will always prioritize selecting the leader replica of the replicated table for queries, rather than directly selecting the local replica, to ensure query efficiency and avoid selecting the wrong replica.</p>
      </main>

* Broadcast log streams:

  * Each user tenant can have at most one broadcast log stream.
  * Attribute conversion between broadcast log streams and regular log streams is not supported.
  * Manual deletion of broadcast log streams is not supported. They are deleted along with the tenant.

When you create and use a columnstore table, if you import a large amount of data, you need to perform a **major compaction** to improve the read performance and perform **statistics collection** to adjust the execution strategy.

* **Major compaction**: After you import data in batches, we recommend that you perform a major compaction. After you import data, trigger a major compaction in the tenant to ensure that all data is compacted to the baseline layer. * **Statistics collection**: After you perform a major compaction, we recommend that you collect statistics. This is very important for the optimizer to generate effective query plans and execution strategies. Execute [GATHER_SCHEMA_STATS](../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/15900.dbms-stats-mysql/1800.gather-schema-stats-mysql.md) to collect statistics for all tables. Note that as the amount of data in a columnstore table increases, the major compaction may take longer.

### Specify the update model for a table

You can specify the update model for a table when you create it by adding the `MERGE_ENGINE` option to the `CREATE TABLE` statement. The SQL statement is as follows:

```sql
CREATE TABLE table_name column_definition
    MERGE_ENGINE = {delete_insert | partial_update}
    WITH COLUMN GROUP([all columns,] each column);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After you specify the <code>MERGE_ENGINE</code> option when you create a table, you cannot modify the configuration value of this option. </p>
</main>

The `MERGE_ENGINE` option specifies the update model for the table. Valid values are as follows:

* `partial_update`: This is the default value, indicating that the partial update model is used. Only the modified columns (delta) are recorded in each update. This model saves more storage space, but you need to merge multiple data versions to obtain the latest value during a query. This model is suitable for OLTP scenarios with frequent updates and low query requirements.
* `delete_insert`: This indicates that the full-column update model is used. Each update writes a complete row (delete the old row and insert the new row). This model prioritizes query performance. This model supports Skip Index for incremental data (Memtable/Delta SSTable). During a query, incremental data can be filtered and pushed down. If the filtering result does not involve updates to baseline data, baseline data and incremental data can be batch processed separately, reducing read amplification. This model is suitable for OLAP scenarios with a high proportion of incremental data, frequent complex queries, or batch processing and analysis.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The core difference between <code>delete_insert</code> and <code>partial_update</code> lies in the write granularity: the former writes all columns during each update, while the latter writes only the modified columns. Full-column writing enables <code>delete_insert</code> to support Skip Index for Delta SSTables, thereby achieving better filtering pushdown effects in analytical queries. </p>
</main>

If you do not specify the `MERGE_ENGINE` option, the value of this option is the same as the value of the [default_table_merge_engine](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md) parameter.

#### Scenarios

| Scenario | Recommended value | Description |
|------|----------|------|
| OLAP, analytical queries, and batch processing | `delete_insert` | When incremental data can be filtered, query performance is better. Note that incremental data occupies more storage space. |
| OLTP, frequent updates, and storage-sensitive scenarios | `partial_update` | Saves more storage space and is suitable for scenarios with frequent updates and low query requirements. |

For more information about other scenarios, see [Best practices](../../../../400.deploy/700.best-practices.md).

**Here are some examples:**

* Create a columnstore table `mer_tbl1` with the full-column update model (`delete_insert`).

    ```sql
    CREATE TABLE mer_tbl1 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert
        WITH COLUMN GROUP(each column);
    ```

* Create a rowstore/columnstore redundant table `mer_tbl2` with the full-column update model (`delete_insert`).

    ```sql
    CREATE TABLE mer_tbl2 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert
        WITH COLUMN GROUP(all columns, each column);
    ```

## Create a temporary table

A temporary table is a session-level special table used for temporarily storing intermediate data.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Temporary tables are supported starting from OceanBase Database V4.3.5 BP4. </p>
</main>

### Limitations

* Routing of temporary tables: Since temporary tables need to support load balancing like regular tables, by default, they cannot be bound to a specific server. Consider disabling load balancing if needed.
* In the serializable isolation level (Serializable), OceanBase Database does not support writing to temporary tables created within the same transaction.

* If a temporary table with the same name as a regular table exists in the current session, it is not recommended to use the database-level statistics collection feature in the current session, as the results may not meet expectations.

* Temporary tables are cleaned up through background logic, and their cleanup speed is limited to minimize impact on business operations. Therefore, in scenarios with a large number of temporary tables, it is recommended to manually delete them promptly.
* Temporary tables cannot be accessed via DBLink.
* When connecting to an OBServer through ODP, you need to manually adjust the [server_protocol](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575488), [client_session_id_version](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575403), and [proxy_id](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575542) parameters.

  Here are the steps:

  * Execute the following command to modify the communication protocol configuration of OBProxy.

    ```sql
    ALTER proxyconfig SET server_protocol = 'OceanBase 2.0';
    ```

  * Execute the following command to set the algorithm for generating the client session ID (Client Session ID) to version 2.

    ```sql
    ALTER proxyconfig SET client_session_id_version = 2;
    ```

  * Execute the following command to change the ODP ID to 1. Different ODPs should be assigned different numbers to ensure that the generated Client Session IDs do not conflict.

    ```sql
    ALTER proxyconfig SET proxy_id = 1;
    ```

### Example

Create a temporary table named `tbl1`:


<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Once the <code>MERGE_ENGINE</code> option is specified during table creation, its configuration value cannot be modified. </p>
</main>

The `MERGE_ENGINE` option is used to specify the update model of a table. The options are as follows:

* `partial_update`: specifies that the table uses a partial update model. In this model, only modified columns (deltas) are recorded in each update. This model consumes less storage space, but during queries, you need to merge the recorded data from multiple records to obtain the latest value. This model is recommended for OLTP scenarios that have frequent updates and low query requirements.
* `delete_insert`: specifies that the table uses a full-column update model. In this model, a complete row (delete the old row and insert the new row) is written in each update. The query performance is prioritized. This model supports Skip Index for incremental data (Memtable/Delta SSTable). During queries, filters can be pushed down on incremental data. If the filtering results do not involve updates to the baseline data, you can separately batch process baseline and incremental data to reduce read amplification. This model is recommended for OLAP scenarios that have high incremental data ratios and complex queries or batch processing analysis.
* `append_only`: specifies that the table can only be updated by the `INSERT` operation. All other DML and DDL operations that modify data in the table are disabled. The TTL feature can be used to clean up expired data. For more information about usage limitations, see [Usage limitations](#usage-limitations) of the update model.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>When you specify <code>delete_insert</code> or <code>partial_update</code>, the write granularity is the main difference between them. <code>delete_insert</code> writes the full row (delete the old row and insert the new row) in each update, while <code>partial_update</code> writes only the modified columns. Because <code>delete_insert</code> writes the full row, it can support Skip Index for Delta SSTables, which can enhance the filtering down effect during analytical queries. </p>
</main>

If the `MERGE_ENGINE` option is not specified, the value of the [default_table_merge_engine](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md) parameter is used.

### Scenarios

| Scenario | Recommended value | Description |
|------|----------|------|
| OLAP, analytical queries, batch processing | `delete_insert` | Filters on incremental data can be pushed down, which can enhance the query performance. However, more storage space is required for incremental data. |
| OLTP, frequent updates, storage-sensitive scenarios | `partial_update` | This model consumes less storage space. It is recommended for OLTP scenarios with frequent updates and low query requirements. |
| Use immutable data, efficient appending, and simplified queries | `append_only` | This model is recommended for high-throughput scenarios, such as log analysis and IoT data monitoring. The range query and aggregation computation efficiency are high.|

For more information about configurations, see [Best practices](../../../../400.deploy/700.best-practices.md).

### Usage limitations

If the table update model `MERGE_ENGINE` is specified as `append_only`, the following limitations exist:

* The following DML operations are disabled:

  * `UPDATE`
  * `DELETE`
  * `MERGE INTO`
  * `REPLACE`

* The `INSERT [IGNORE] xxx ON DUPLICATE KEY UPDATE` operation is not disabled. However, when actual data modifications are performed, the operation will return an error.

* The following DDL operations are disabled:

  * `TRUNCATE` tables and partitions.
  * Swap partitions.
  * Drop partitions.
  * Drop columns.
  * Reduce the value range of a column.
  * Perform dynamic partitioning.
  * Drop obsolete columns.
  * Add columns specified with `DEFAULT VALUE`.
  * Add auto-increment columns.

### Examples

* Create a table `mer_tbl1` with the full-column update model (`delete_insert`).

    ```shell
    obclient> CREATE TABLE mer_tbl1 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert;
    ```

* Create a columnstore table `mer_tbl2` with the full-column update model (`delete_insert`).

    ```shell
    obclient> CREATE TABLE mer_tbl2 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert
        WITH COLUMN GROUP(each column);
    ```

* Create a table with the `append_only` model and perform `INSERT`, `SELECT`, `UPDATE`, and `DELETE` operations.

  1. Create a table `mer_tbl3` with the `append_only` model.

      ```shell
      obclient> CREATE TABLE mer_tbl3 (col1 INT PRIMARY KEY, col2 VARCHAR(100))
          MERGE_ENGINE = append_only;
      ```

  2. Insert data into the `mer_tbl3` table.

      ```shell
      obclient> INSERT INTO mer_tbl3 VALUES(1, 'oceanbase');
      ```

  3. Query data from the `mer_tbl3` table.

      ```shell
      obclient> SELECT * FROM mer_tbl3;
      ```

      The returned result is as follows:

      ```shell
      +------+-----------+
      | col1 | col2      |
      +------+-----------+
      |    1 | oceanbase |
      +------+-----------+
      1 row in set
      ```

  4. Attempt to update data in the `mer_tbl3` table and verify whether an error is returned.

      ```shell
      obclient> UPDATE mer_tbl3 SET col2 = 'database' WHERE col1 = 1;
      ```

      The returned result is as follows:

      ```shell
      ERROR 1235 (0A000): update append_only table is not supported
      ```

  5. Attempt to delete data from the `mer_tbl3` table and verify whether an error is returned.

      ```shell
      obclient> DELETE FROM mer_tbl3 WHERE col1 = 1;
      ```

      The returned result is as follows:

      ```shell
      ERROR 1235 (0A000): delete from append_only table is not supported
      ```
