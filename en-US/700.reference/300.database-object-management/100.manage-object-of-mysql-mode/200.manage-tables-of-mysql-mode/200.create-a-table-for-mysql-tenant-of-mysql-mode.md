# Create a table

You can execute the `CREATE TABLE` statement to create a table.

This topic describes how to create a non-partitioned table. For information about how to create a partitioned table, see [Create a partitioned table](../300.manage-partitions-of-mysql-mode/200.create-a-partition-table-of-mysql-mode.md).

## Create a non-partitioned table

A non-partitioned table has only one partition.

The following is an example of creating a non-partitioned table:

```sql
obclient>CREATE TABLE table_name1(w_id int
, w_ytd decimal(12,2)
, w_tax decimal(4,4)
, w_name varchar(10)
, w_street_1 varchar(20)
, w_street_2 varchar(20)
, w_city varchar(20)
, w_state char(2)
, w_zip char(9)
, unique(w_name, w_city)
, primary key(w_id)
);

Query OK, 0 rows affected (0.09 sec)

obclient>CREATE TABLE table_name2 (c_w_id int NOT NULL
, c_d_id int NOT null
, c_id int NOT null
, c_discount decimal(4, 4)
, c_credit char(2)
, c_last varchar(16)
, c_first varchar(16)
, c_middle char(2)
, c_balance decimal(12, 2)
, c_ytd_payment decimal(12, 2)
, c_payment_cnt int
, c_credit_lim decimal(12, 2)
, c_street_1 varchar(20)
, c_street_2 varchar(20)
, c_city varchar(20)
, c_state char(2)
, c_zip char(9)
, c_phone char(16)
, c_since date
, c_delivery_cnt int
, c_data varchar(500)
, index icust(c_last, c_d_id, c_w_id, c_first, c_id)
, FOREIGN KEY (c_w_id) REFERENCES table_name1(w_id)
, primary key (c_w_id, c_d_id, c_id)
);

Query OK, 0 rows affected
```

In this example, two tables are created. Some constraints, such as primary keys and foreign keys, are defined on different columns. For more information about primary keys and foreign keys, see [Define column constraints](../200.manage-tables-of-mysql-mode/400.define-the-constraint-type-for-a-column-of-mysql-mode.md).

When you create columns in a table, select the correct data type for the columns. For more information about SQL data types, see [Data types](../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/100.data-type-overview-of-mysql-mode.md).

<main id="notice" type='explain'>
<h4>Note</h4>
<p>To ensure performance and facilitate maintenance, we recommend that you specify a primary key or a unique key when you create a table. If no existing columns can be used as the primary key, the system generates an auto-increment column as the hidden primary key after table creation. For more information about auto-increment columns, see <a href="300.define-an-auto-increment-column-of-mysql-mode.md">Define an auto-increment column</a>.</p>
</main>

## Create a replica table

A replica table is a special table in OceanBase Database. This table can read the latest data modifications from any "healthy" replica. For users who require less frequent writes but prioritize low read operation latency and better load balancing, a replica table is an excellent choice.

After a user creates a replica table, a replica of this table is created on every OBServer node in the tenant. One of these replicas is elected as the leader to accept write requests, while the others can only accept read requests.

All replicas must report their status to the leader, primarily focusing on their replay progress, which indicates the data synchronization progress. Generally, a follower's replay progress lags slightly behind that of the leader. As long as this lag remains within an acceptable threshold, the leader considers the replica "healthy" and capable of quickly replaying the leader's modifications. After a replica has been deemed "healthy" for a certain period, the leader grants it a lease. In simpler terms, the leader trusts the follower to remain "healthy" and provide strongly consistent read services for this period. During this "trust" period, before committing any transaction in a replica table, the leader verifies the replay progress of the follower. Once the follower has replayed the transaction's modifications, the leader notifies the user that the transaction has been successfully committed. At this point, the user can read the committed transaction's modifications from the follower.

The replica table feature was introduced in OceanBase Database V3.x. For V4.x, with a significant overhaul of the database's architecture, the replica table feature has been adapted to the new standalone log stream architecture. This includes the implementation of partition-based readable version verification and log stream-based lease granting mechanisms to ensure the correctness of strongly consistent reads.

Additionally, the V4.x version of the replica table feature enhances the ability to switch leaders without terminating ongoing transactions. When a user or the load balancer initiates a leader switch, uncommitted replica table transactions can continue execution after the switch, unlike in V3.x, where such transactions would fail. Compared with V3.x, the V4.x version of the replica table feature also offers better write transaction performance, stronger disaster recovery capabilities, and reduced impact on read operations in the event of a replica failure.

### Limitations on copy tables

* Limitations on copy tables:

  * Limitations on creating copy tables: You cannot create copy tables in the sys tenant or the meta tenant because broadcast logs are not enabled for these two tenants.
  * The write performance of copy tables is affected by the number of nodes. This is because all replicas of a copy table must be synchronized with the data written to the copy table. Therefore, the larger the number of nodes, the greater the impact on the write performance.
    * Workaround: Try to avoid performing read and write operations on a copy table in the same transaction. In other words, a copy table supports pure write or read operations.

  * Attribute conversion:

    * A copy table and a table group are mutually exclusive. If you try to modify the table group attribute of a copy table, an error is returned. If you want to convert a normal table to a copy table, the attribute modification command fails if the normal table belongs to a table group.
    * Load balancing and transfer must be enabled for a copy table to be converted.

  * Routing:

    * If a transaction contains write operations on a copy table, and you then query the copy table, the query may fail if the copy table is randomly routed to a follower. In this case, the observer node needs to forward the query request to the leader of the copy table, which degrades the query performance.

      * In ODP V4.3.3 and later, if a transaction contains write operations on a copy table, the query is routed to the leader of the copy table.

    * If you execute a `JOIN` query that joins a copy table and a normal table, the copy table is randomly routed, just like a normal table. In other words, ODP routes the `JOIN` query based on the first table. As a result, the query may be routed to a non-Leader node of the normal table, which leads to a remote plan.
    * Ordinary table attribute changes to a replicated table, ODP cannot perceive it, and cannot distribute pressure according to the routing of the replicated table.

  * If a copy table is modified in a transaction, the query operations performed after the modification are affected, as described below: When you query the copy table, the system generates an execution plan that selects a local replica of the copy table. However, because the copy table has been modified, the system reports an error indicating that the replica cannot be read. In this case, the SQL engine retries the query and selects the leader of the replica. However, because the execution plan is not cached in the plan cache, the query performance is poor.

      <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>In OceanBase Database V4.3.5 and later, if you modify a copy table in a transaction, the system always selects the leader of the copy table when you query the copy table, regardless of whether a local replica exists, to ensure query efficiency and avoid the selection of an incorrect replica.</p>
      </main>

* Limitations on broadcast log streams:

  * Each user tenant can have at most one broadcast log stream.
  * The conversion of attributes between a broadcast log stream and a normal log stream is not supported.
  * Broadcast log streams cannot be manually deleted and are automatically deleted when the corresponding tenant is deleted.

### Syntax for creating a duplicate table

The syntax for creating a duplicate table is the `CREATE TABLE` statement followed by the `DUPLICATE_SCOPE` option. Users can create duplicate tables, but the `sys` tenant cannot. The following statement shows how to create a duplicate table:

```sql
CREATE TABLE table_name column_definition DUPLICATE_SCOPE='none | cluster';
```

The `DUPLICATE_SCOPE` parameter specifies the attribute of the duplicate table. Valid values are:

* `none`: indicates a normal table.
* `cluster`: indicates a duplicate table. The leader needs to replicate transactions to all full-featured and read-only replicas of the current tenant.

If you do not specify `DUPLICATE_SCOPE` when you create a table, the default value is `none`.

```sql
CREATE TABLE dup_t1 (c1 int,c2 int) DUPLICATE_SCOPE= 'cluster';
```

When the first duplicate table of a tenant is created, the system automatically creates a special log stream named broadcast log stream. All newly created duplicate tables are created in this broadcast log stream. Compared with a normal log stream, a broadcast log stream has a replica automatically deployed on each OBServer node in the tenant. This ensures that, under ideal conditions, strong-consistency reads can be performed on the duplicate table in any OBServer node. You can query the broadcast log stream in which the duplicate table of the tenant is located by using the following SQL statement:

```sql
SELECT * FROM oceanbase.DBA_OB_LS WHERE flag LIKE "%DUPLICATE%";
```

Here is the sample result.

```shell
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+
| LS_ID | STATUS | PRIMARY_ZONE | UNIT_GROUP_ID | LS_GROUP_ID | CREATE_SCN          | DROP_SCN | SYNC_SCN            | READABLE_SCN        | FLAG      |
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+
|  1003 | NORMAL | z1;z2        |             0 |           0 | 1683267390195713284 |     NULL | 1683337744205408139 | 1683337744205408139 | DUPLICATE |
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+
1 rows in set
```

In this example, the log stream with `LS_ID` of `1003` is the broadcast log stream. All duplicate tables of the tenant are created in this log stream. For more information about broadcast log streams, see [Replica introduction](../../../../600.manage/300.replica-management/100.replica-introduction.md).

After a duplicate table is created, you can insert data into it and read data from it, just like a normal table. The difference is in how read requests are handled. If you connect to the database by using a proxy, the read request can be routed to any OBServer node for execution. If you connect to the database directly, the system executes the read request on a directly connected OBServer node if the local replica is readable. For more information about connection methods, see [Overview](../../../../300.develop/100.application-development-of-mysql-mode/100.connect-to-oceanbase-database-of-mysql-mode/100.connection-methods-overview-of-mysql-mode.md).

## Create a new table by copying data from an existing table

### Copy table data

You can execute the `CREATE TABLE AS SELECT` statement to copy the data but not the schema of a table. The constraint, index, default value, and partition of the table are lost during the copy.

A sample statement is as follows:

```sql
obclient>CREATE TABLE t1_copy AS SELECT * FROM t1;
Query OK, 3 rows affected
```

### Copy table schema

You can execute the `CREATE TABLE LIKE` statement to copy the schema but not the data of a table.

A sample statement is as follows:

```sql
obclient>CREATE TABLE t1_like like t1;
Query OK, 0 rows affected
```

## Create a rowstore table

OceanBase Database allows you to create rowstore tables and convert between rowstore and columnstore.

When [default_table_store_format=‘row’](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) (the default value), the created table is a rowstore table by default. When [default_table_store_format](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) is not `row`, you can specify the `WITH COLUMN GROUP(all columns)` option to create a rowstore table.

For information about how to convert between rowstore and columnstore, see [Modify a table](600.change-table-of-mysql-mode.md). For information about how to create a columnstore index, see [Create an index](../500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).

You can create a rowstore table by specifying `WITH COLUMN GROUP(all columns)`.

**Here is an example:**

```sql
CREATE TABLE tbl1_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(all columns);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>After you create a rowstore table by specifying the <code>WITH COLUMN GROUP(all columns)</code> option, the table remains in the row-based storage format even if you execute the <code>DROP COLUMN GROUP(all columns)</code> statement to drop this column group.</p>
</main>

## Create a columnstore table

OceanBase Database supports the creation of columnstore tables, conversion between rowstore and columnstore, and creation of columnstore indexes. When you create a table in OceanBase Database, the table is a rowstore table by default. You can use the `WITH COLUMN GROUP` option to explicitly specify to create a columnstore table or a redundant rowstore table.

For information about how to convert a rowstore table to a columnstore table, see [Modify a table](600.change-table-of-mysql-mode.md). For information about how to create a columnstore index, see [Create an index](../500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).

You can create a redundant rowstore-columnstore table by specifying `WITH COLUMN GROUP(all columns, each column)`.

**Here is an example:**

```sql
CREATE TABLE tbl1_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(all columns, each column);
```

You can create a columnstore table by specifying `WITH COLUMN GROUP(each column)`.

**Here is an example:**

```sql
CREATE TABLE tbl2_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(each column);
```

Take note of the following considerations if you have imported a large amount of data to a columnstore table:

* **Major compaction**: We recommend that you perform a major compaction after data is imported in batches. This helps improve read performance, because a major compaction organizes fragmented data and makes it more contiguous in physical storage, thus reducing disk I/O during reads. After a major compaction is triggered in the tenant, make sure that all data is compacted to the baseline layer. For more information, see [`MAJOR` and `MINOR`](../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1500.alter-system-freeze-of-mysql-mode.md).

* **Statistics collection**: We recommend that you collect statistics after a major compaction is performed. This is crucial for the optimizer to generate effective query plans and execution strategies. You can execute [GATHER_SCHEMA_STATS](../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/15900.dbms-stats-mysql/1800.gather-schema-stats-mysql.md) to collect statistics on all tables, or monitor the statistics collection progress by querying the [GV$OB_OPT_STAT_GATHER_MONITOR](../../../700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/6100.gv_ob_opt_stat_gather_monitor-of-mysql-mode.md) view.

Note that the major compaction speed may decrease as the data volume of the columnstore table increases.

## Create a heap-organized table

OceanBase Database supports the organization of index-organized tables and heap-organized tables.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Heap-organized tables are supported in OceanBase Database V4.3.5 and later, starting from V4.3.5 BP1. </p>
</main>

### Limitations

* For a heap-organized table with a unique key local index or a heap-organized table with a primary key, all partitioning key columns must be included in the primary key or unique key local index.
* OceanBase Database does not support the following DDL operations for heap-organized tables:

  * Operations on the primary key constraint
  * Modifying a column into the primary key
  * Changing the type or length of the primary key column from wide to narrow
  * Adding a primary key column
  * Modifying the primary key into an auto-increment column
  * Dropping the primary key column
  * Splitting partitions

### Syntax for specifying the table organization form

The syntax for specifying the table organization form when creating a table is to add the `ORGANIZATION` table option after the `CREATE TABLE` statement. The SQL statement is as follows:

```sql
CREATE TABLE table_name column_definition ORGANIZATION [=] {INDEX | HEAP};
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>In OceanBase Database V4.3.5, the <code>CREATE TABLE</code> statement supports the <code>ORGANIZATION</code> option in BP1 and later. </p>
</main>

The `ORGANIZATION` option specifies the storage order of data rows in the table. Valid values are as follows:

* `INDEX`: indicates that the table model is a clustered index table model, namely, an index-organized table.
* `HEAP`: indicates that the table model is a non-clustered index table model, namely, a heap-organized table.

If you do not specify the `ORGANIZATION` option, the default value of the [default_table_organization](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2150.default_table_organization.md) parameter is used.

**Here are some examples:**

* Specify the value of the `ORGANIZATION` option as `HEAP` when creating a table.

  ```sql
  CREATE TABLE ora_tbl1 (col1 INT, col2 INT) ORGANIZATION = HEAP;
  ```

* Create a table without specifying the `ORGANIZATION` option.

  Change the tenant-level parameter `default_table_organization` and then create a table. For more information about the `default_table_organization` parameter, see [default_table_organization](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2150.default_table_organization.md).

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>The current version parameter <code>default_table_organization</code> applies only to MySQL tenant users of OceanBase Database. It does not apply to the sys tenant or user tenants in Oracle mode. </p>
  </main>

  1. Set the value of the `default_table_organization` parameter to `HEAP`.

      ```sql
      ALTER SYSTEM SET default_table_organization = 'HEAP';
      ```

  2. Create a table named `ora_tbl2`.

      ```sql
      CREATE TABLE ora_tbl2(col1 INT, col2 INT);
      ```

  3. View the definition of the `ora_tbl2` table.

      ```sql
      SHOW CREATE TABLE ora_tbl2;
      ```

      The return result is as follows:

      ```shell
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      | Table    | Create Table                                                                                                                                                                                                                                                                                                                 |
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      | ora_tbl2 | CREATE TABLE `ora_tbl2` (
        `col1` int(11) DEFAULT NULL,
        `col2` int(11) DEFAULT NULL
      ) ORGANIZATION HEAP DEFAULT CHARSET = utf8mb4 ROW_FORMAT = DYNAMIC COMPRESSION = 'zstd_1.3.8' REPLICA_NUM = 1 BLOCK_SIZE = 16384 USE_BLOOM_FILTER = FALSE ENABLE_MACRO_BLOCK_BLOOM_FILTER = FALSE TABLET_SIZE = 134217728 PCTFREE = 0 |
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      1 row in set
      ```
