# Create a table

You can use the `CREATE TABLE` statement to create a table.

This topic describes how to create a non-partitioned table. For information about how to create and use a partitioned table, see [Create a partitioned table](../300.manage-partitions-of-mysql-mode/200.create-a-partition-table-of-mysql-mode.md).

## Create a non-partitioned table

Creating a non-partitioned table means creating a table with only one partition.

Here is an example of creating a non-partitioned table:

```sql
obclient>CREATE TABLE table_name1(w_id int
, w_ytd decimal(12,2)
, w_tax decimal(4,4)
, w_name varchar(10)
, w_street_1 varchar(20)
, w_street_2 varchar(20)
, w_city varchar(20)
, w_state char(2)
, w_zip char(9)
, unique(w_name, w_city)
, primary key(w_id)
);

Query OK, 0 rows affected (0.09 sec)

obclient>CREATE TABLE table_name2 (c_w_id int NOT NULL
, c_d_id int NOT null
, c_id int NOT null
, c_discount decimal(4, 4)
, c_credit char(2)
, c_last varchar(16)
, c_first varchar(16)
, c_middle char(2)
, c_balance decimal(12, 2)
, c_ytd_payment decimal(12, 2)
, c_payment_cnt int
, c_credit_lim decimal(12, 2)
, c_street_1 varchar(20)
, c_street_2 varchar(20)
, c_city varchar(20)
, c_state char(2)
, c_zip char(9)
, c_phone char(16)
, c_since date
, c_delivery_cnt int
, c_data varchar(500)
, index icust(c_last, c_d_id, c_w_id, c_first, c_id)
, FOREIGN KEY (c_w_id) REFERENCES table_name1(w_id)
, primary key (c_w_id, c_d_id, c_id)
);

Query OK, 0 rows affected
```

In this example, two tables are created, and some constraints are defined for the columns in the tables, including primary keys and foreign keys on different columns. For more information about primary keys and foreign keys, see [Define the constraint type for a column](../200.manage-tables-of-mysql-mode/400.define-the-constraint-type-for-a-column-of-mysql-mode.md).

When creating columns for a table, choose the correct data type. For more information about SQL data types, see [Data types](../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/100.data-type-overview-of-mysql-mode.md).

<main id="notice" type='explain'>
<h4>Note</h4>
<p>To ensure performance and facilitate later maintenance, we recommend that you design a primary key or unique key for a table. If no suitable column can be used as the primary key, you can omit the PRIMARY KEY clause when you create a table. After the table is created, the system automatically assigns an auto-increment column as the hidden primary key for the table. For more information about auto-increment columns, see <a href="300.define-an-auto-increment-column-of-mysql-mode.md">Define an auto-increment column</a>. </p>
</main>

## Create a replicated table

A replicated table is a special type of table in OceanBase Database. This table allows you to read the latest modifications to data on any "healthy" replica. For users who require low write frequency and high read performance with load balancing, a replicated table is an excellent choice.

When you create a replicated table, a replica of the table is created on every OBServer node in the tenant. One of these replicas is elected as the leader, which accepts write requests, while the remaining replicas only accept read requests.

All replicas need to report their status to the leader, primarily the replay progress, which indicates the data synchronization progress. Generally, the replay progress of followers lags slightly behind the leader. As long as the lag does not exceed a certain threshold, the leader considers the replica to be "healthy" and can quickly replay the modifications from the leader. Once the leader considers a replica "healthy" for a certain period, it grants the follower a lease. In other words, the leader trusts the follower to remain "healthy" and provide strongly consistent read services during this lease period. During this "trust" period, the leader will check the follower's replay progress before committing each transaction. After the follower replays the modifications of the transaction, the leader will inform the user that the transaction has been successfully committed. At this point, the user can read the modifications of the just-committed transaction on the follower.

The feature of replicated tables has been available in OceanBase Database V3.x. However, in V4.x, due to significant changes in the architecture of OceanBase Database, V4.x replicated tables have been adapted to the new single-machine log stream architecture. This adaptation includes the implementation of partition-based readable version number verification and log stream-based lease granting mechanisms to ensure the correctness of strongly consistent reads.

Additionally, V4.x has improved the ability to switch leaders without killing transactions. In V3.x, uncommitted replicated table transactions would fail when a leader switch was initiated by the user or load balancing. In V4.x, uncommitted replicated table transactions can continue to execute after the leader switch. Compared to V3.x, V4.x replicated tables also offer better write transaction performance and stronger disaster recovery capabilities, with less impact on read operations when a replica fails.

### Limitations of replicated tables

* Replicated tables:

  * Creation limitations: The sys and meta tenants do not support creating replicated tables because they do not have broadcast log streams.
  * Write performance is affected by the number of nodes: Since replicated table writes need to be synchronized to all replicas, the more nodes there are, the greater the impact on write performance.
    * Workaround: Avoid having both read and write operations on replicated tables within the same transaction. Pure write or pure read operations on replicated tables are acceptable.

  * Attribute conversion:

    * Replicated tables and table groups are mutually exclusive. Modifying the table group attribute of a replicated table will result in an error. When converting a regular table to a replicated table, if the regular table belongs to a table group, the attribute change command will also result in an error.
    * Converting a replicated table depends on load balancing and transfer, so ensure that the relevant configuration items are enabled.

  * Routing:

    * If a transaction involves a write operation on a replicated table, subsequent queries on the replicated table may be randomly routed to a follower. This can result in the replica being unreadable, as the observer will internally forward the request to the leader of the replicated table, which can impact query performance.

      * ODP V4.3.3 has adjusted the routing strategy. If there is a write operation on a replicated table, subsequent queries will be routed to the leader of the replicated table.

    * When querying a replicated table joined with a regular table, the query will be randomly routed based on the replicated table (for JOIN queries, ODP routes based on the first table). This may route to a non-leader node of the regular table, resulting in a remote plan.
    * When a regular table is converted to a replicated table, ODP cannot detect this change and cannot route queries to the replicated table to balance the load.

  * Within a transaction, if a replicated table has been modified, subsequent query operations will generate an execution plan that selects the local replica. However, due to the modification, an error indicating that the replica is unreadable will be returned. The SQL retry will select the leader replica, and the plan cache will not hit, leading to poor query performance.

      <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>Within a transaction, if a replicated table has been modified, OceanBase Database will always prioritize selecting the leader replica of the replicated table for queries, rather than directly selecting the local replica. This ensures improved query efficiency and avoids selecting the wrong replica.</p>
      </main>

* Broadcast log streams:

  * Each user tenant can have at most one broadcast log stream.
  * Attribute conversion between broadcast log streams and regular log streams is not supported.
  * Broadcast log streams cannot be manually deleted and will be deleted along with the tenant.

### Syntax for creating a replicated table

To create a replicated table, add the `DUPLICATE_SCOPE` option to the `CREATE TABLE` statement. Only user tenants can create replicated tables, and the `sys` tenant cannot create replicated tables. The SQL statement for creating a replicated table is as follows:

```sql
CREATE TABLE table_name column_definition DUPLICATE_SCOPE='none | cluster';
```

The `DUPLICATE_SCOPE` parameter specifies the attribute of the replicated table. Valid values are as follows:

* `none`: Indicates that the table is a regular table.
* `cluster`: Indicates that the table is a replicated table, and the leader needs to replicate transactions to all F and R replicas of the current tenant.

If you do not specify `DUPLICATE_SCOPE` when creating a table, the default value is `none`.

```sql
CREATE TABLE dup_t1 (c1 int,c2 int) DUPLICATE_SCOPE= 'cluster';
```

When the first replicated table is created in a tenant, the system will also create a special log stream called a broadcast log stream. Subsequent replicated tables will be created on this broadcast log stream. The difference between a broadcast log stream and a regular log stream is that a broadcast log stream automatically deploys a replica on every OBServer node within the tenant. This ensures that, under ideal conditions, a replicated table can provide strongly consistent reads on any OBServer node. You can use the following SQL statement to view the broadcast log stream where the replicated tables of a tenant are located:

```sql
SELECT * FROM oceanbase.DBA_OB_LS WHERE flag LIKE "%DUPLICATE%";
```

The query result is as follows.

```shell
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+-----------+
| LS_ID | STATUS | PRIMARY_ZONE | UNIT_GROUP_ID | LS_GROUP_ID | CREATE_SCN          | DROP_SCN | SYNC_SCN            | READABLE_SCN        | FLAG      | UNIT_LIST |
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+-----------+
|  1003 | NORMAL | z1;z2        |             0 |           0 | 1683267390195713284 |     NULL | 1683337744205408139 | 1683337744205408139 | DUPLICATE |           |
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+-----------+
1 rows in set
```

In the example, the log stream with `LS_ID` of `1003` is the broadcast log stream, and all replicated tables of the tenant are created on this log stream. For more information about broadcast log streams, see [Replica introduction](../../../../600.manage/300.replica-management/100.replica-introduction.md).

After a replicated table is created, you can perform insert and read/write operations on it, just like a regular table. However, for read requests, if you connect to the database using a proxy, the read request may be routed to any OBServer node for execution. If you connect to the database directly, the system will execute the read request on the directly connected OBServer node as long as the local replica is readable. For more information about database connection methods, see [Connection methods overview](../../../../300.develop/100.application-development-of-mysql-mode/100.connect-to-oceanbase-database-of-mysql-mode/100.connection-methods-overview-of-mysql-mode.md).

## Create a new table by copying data from an existing table

### Copy data from a table

You can use the `CREATE TABLE AS SELECT` statement to copy data from a table. However, the structure may not be exactly the same, and information such as constraints, indexes, default values, and partitions will be lost.

Example statement:

```sql
obclient>CREATE TABLE t1_copy AS SELECT * FROM t1;
Query OK, 3 rows affected
```

### Copy the structure of a table

You can use the `CREATE TABLE LIKE` statement to copy the structure of a table, but you cannot copy the data.

Example statement:

```sql
obclient>CREATE TABLE t1_like like t1;
Query OK, 0 rows affected
```

## Create a rowstore table

OceanBase Database allows you to create a rowstore table and convert a rowstore table to a columnstore table.

When the [default_table_store_format](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) parameter is set to `row` (the default value), a rowstore table is created by default. If the [default_table_store_format](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) parameter is set to a value other than `row`, you can specify the `WITH COLUMN GROUP(all columns)` option to create a rowstore table.

For more information about converting a rowstore table to a columnstore table, see [Change a table](600.change-table-of-mysql-mode.md). For more information about creating a columnstore index, see [Create an index](../500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).

You can specify the `WITH COLUMN GROUP(all columns)` option to create a rowstore table.

**Here is an example:**

```sql
CREATE TABLE tbl1_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(all columns);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>If you specify the <code>WITH COLUMN GROUP(all columns)</code> option to create a rowstore table, the table remains in rowstore format even if you later execute the <code>DROP COLUMN GROUP(all columns)</code> statement to drop the column group.</p>
</main>

## Create a columnstore table

OceanBase Database allows you to create a columnstore table, convert a rowstore table to a columnstore table, and create a columnstore index. By default, OceanBase Database creates a rowstore table when you create a table. You can specify the `WITH COLUMN GROUP` option to explicitly specify the storage format of the table as columnstore or rowstore with columnstore redundancy.

For more information about converting a rowstore table to a columnstore table, see [Change a table](600.change-table-of-mysql-mode.md). For more information about creating a columnstore index, see [Create an index](../500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).

You can specify the `WITH COLUMN GROUP(all columns, each column)` option to create a rowstore table with columnstore redundancy.

**Here is an example:**

```sql
CREATE TABLE tbl1_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(all columns, each column);
```

You can specify the `WITH COLUMN GROUP(each column)` option to create a columnstore table.

**Here is an example:**

```sql
CREATE TABLE tbl2_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(each column);
```

When you create and use a columnstore table, you need to perform a **major compaction** to improve the read performance and perform **statistics collection** to adjust the execution strategy if you have imported a large amount of data.

* **Major compaction**: After you batch import data, we recommend that you perform a major compaction. This helps improve the read performance because a major compaction organizes fragmented data into contiguous data in the physical storage, thereby reducing the disk I/O during read operations. After you import data, you can trigger a major compaction in the tenant to ensure that all data is compacted to the baseline layer. For more information, see [`MAJOR` and `MINOR`](../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1500.alter-system-freeze-of-mysql-mode.md).

* **Statistics collection**: After a major compaction is performed, we recommend that you collect statistics. This is important for the optimizer to generate effective query plans and execution strategies. You can execute the [GATHER_SCHEMA_STATS](../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/15900.dbms-stats-mysql/1800.gather-schema-stats-mysql.md) procedure to collect statistics for all tables. You can also query the [GV$OB_OPT_STAT_GATHER_MONITOR](../../../700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/6100.gv_ob_opt_stat_gather_monitor-of-mysql-mode.md) view to monitor the statistics collection progress.

Note that the speed of a major compaction may decrease as the amount of data in the columnstore table increases.

## Create a heap-organized table

OceanBase Database supports both index-organized tables and heap-organized tables.

### Limitations

* The primary key of a heap-organized table must contain all partitioning columns.
* The index name cannot be the same as the name of the first column of the primary key when you create an index on a heap-organized table.
* OceanBase Database does not support the following DDL operations on heap-organized tables:

  * Primary key constraint operations
  * Changing a column to a primary key
  * Changing the type or length of a primary key column from a larger to a smaller size
  * Adding a primary key column
  * Changing a primary key column to an auto-increment column
  * Dropping a primary key column
  * Splitting partitions

### Syntax to specify the table organization

To specify the table organization when you create a table, add the `ORGANIZATION` option to the `CREATE TABLE` statement. The SQL statement is as follows:

```sql
CREATE TABLE table_name column_definition ORGANIZATION [=] {INDEX | HEAP};
```

The `ORGANIZATION` option specifies the storage order of data rows in the table. Valid values are as follows:

* `INDEX`: specifies an index-organized table.
* `HEAP`: specifies a heap-organized table.

If you do not specify the `ORGANIZATION` option, the value of the [default_table_organization](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2150.default_table_organization.md) parameter is used.

**Here are some examples:**

* Specify the `ORGANIZATION` option as `HEAP` when you create a table.

  ```sql
  CREATE TABLE ora_tbl1 (col1 INT, col2 INT) ORGANIZATION = HEAP;
  ```

* Do not specify the `ORGANIZATION` option when you create a table.

  After you change the value of the tenant-level parameter `default_table_organization`, you can create a table. For more information about the `default_table_organization` parameter, see [default_table_organization](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2150.default_table_organization.md).

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>The <code>default_table_organization</code> parameter is supported only for user tenants in MySQL mode in OceanBase Database. It is not supported for the sys tenant and user tenants in Oracle mode. </p>
  </main>

  1. Set the value of the `default_table_organization` parameter to `HEAP`.

      ```sql
      ALTER SYSTEM SET default_table_organization = 'HEAP';
      ```

  2. Create a table named `ora_tbl2`.

      ```sql
      CREATE TABLE ora_tbl2(col1 INT, col2 INT);
      ```

  3. View the definition of the `ora_tbl2` table.

      ```sql
      SHOW CREATE TABLE ora_tbl2;
      ```

      The result set is as follows:

      ```shell
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      | Table    | Create Table                                                                                                                                                                                                                                                                                                                 |
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      | ora_tbl2 | CREATE TABLE `ora_tbl2` (
        `col1` int(11) DEFAULT NULL,
        `col2` int(11) DEFAULT NULL
      ) ORGANIZATION HEAP DEFAULT CHARSET = utf8mb4 ROW_FORMAT = DYNAMIC COMPRESSION = 'zstd_1.3.8' REPLICA_NUM = 1 BLOCK_SIZE = 16384 USE_BLOOM_FILTER = FALSE ENABLE_MACRO_BLOCK_BLOOM_FILTER = FALSE TABLET_SIZE = 134217728 PCTFREE = 0 |
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      1 row in set
      ```

## Create a temporary table

A temporary table is a session-level table used to temporarily store intermediate data.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Starting from OceanBase Database V4.3.5 BP4, you can create temporary tables. </p>
</main>

### Limitations

* Routing of temporary tables: Temporary tables need to support load balancing like regular tables. By default, temporary tables cannot be bound to a specific server. You can consider disabling load balancing.
* In the Serializable isolation level, OceanBase Database does not support writing to temporary tables created within the same transaction.

* If a temporary table with the same name as a regular table exists in the current session, it is not recommended to use the database-level statistics collection feature in this session, as the results may not meet expectations.

* Temporary tables are cleaned up by background logic. To avoid significant impact on business operations, the cleanup speed is limited. Therefore, it is recommended to manually delete temporary tables promptly in scenarios with heavy usage.
* Temporary tables cannot be accessed through DBLinks.
* When connecting to an OBServer through ODP, you need to manually adjust the [server_protocal](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575488), [client_session_id_version](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575403), and [proxy_id](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575542) parameters.

  Here are the steps:

  * Execute the following command to modify the communication protocol configuration of OBProxy.

    ```sql
    ALTER proxyconfig SET server_protocol = 'OceanBase 2.0';
    ```

  * Execute the following command to set the algorithm for generating the client session ID (Client Session ID) to version 2.

    ```sql
    ALTER proxyconfig SET client_session_id_version = 2;
    ```

  * Execute the following command to change the ODP ID to 1. Different ODPS should be set to different numbers to ensure that the generated Client Session IDs do not conflict.

    ```sql
    ALTER proxyconfig SET proxy_id = 1;
    ```

### Examples

Create a temporary table named `tbl1`:

```sql
CREATE TEMPORARY TABLE tbl1(col1 INT);
```

## Set table update mode

When creating a table, you can specify the table update model in the syntax by adding the table option `MERGE_ENGINE` after the `CREATE TABLE` statement. The SQL statement is as follows:

```sql
CREATE TABLE table_name column_definition
    MERGE_ENGINE = {delete_insert | partial_update | append_only};
```

<main id="notice" type='explain'>
  <h4>Description</h4>
  <p>Once <code>MERGE_ENGINE</code> is specified when creating a table, its configuration value cannot be modified.</p>
</main>

The `MERGE_ENGINE` parameter specifies the update model for the table, and its value can be set to:

* `partial_update`: This option is used in partial update mode. During an update, only the changed columns (delta) are recorded. This mode is more space-efficient but requires combining multiple datasets when querying to get the latest value. This option is suitable for OLTP scenarios with frequent updates and less querying needs.
* `delete_insert`: Indicates the full-column update mode. Each update writes complete rows (delete old row + insert new row). This mode supports Skip Index for incremental data (Memtable/Delta SSTable). During queries, incremental data can be filtered. If the filter does not involve updates to baseline data, the baseline data and incremental data can be batch-processed separately. This reduces read amplification and is suitable for OLAP scenarios with high incremental data ratios and the need for frequent complex queries or batch analysis.
* `append_only`: This update mode allows only `INSERT` operations and prohibits all DML and DDL operations that modify stored data. You can use the Compaction TTL feature for data cleanup in this mode. For more information on limitations, see [Limitations on update modes](#update-mode-limitations).

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The core difference between <code>delete_insert</code> and <code>partial_update</code> is the granularity of writes: <code>delete_insert</code> writes the entire column during each update, while <code>partial_update</code> only writes the modified columns. Full-column writes allow <code>delete_insert</code> to support Skip Indexes in Delta SSTables, which enhances the effectiveness of filter pushdown in analytical queries.</p>
</main>

The value of the `MERGE_ENGINE` option will be the same as the value of the system variable [default_table_merge_engine](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md) if you do not specify the `MERGE_ENGINE` option.

### Scenarios

| Scene | Recommended value | Description |
|------|----------|------|
| Online Analytical Processing, analytic queries, and batch processing | `delete_insert` | Query performance improves when incremental data can be filtered. Note that incremental data uses more storage space. |
| OLTP, high-frequency updates, storage-sensitive | `partial_update` | Saves more storage and is ideal for frequently updated data with less query demands. |
| Immutability, efficient appends, simplified queries | `append_only` | Suitable for high-throughput scenarios (e.g., logs, IoT data monitoring); efficient for range queries and aggregation calculations. |

For more information about configuration scenarios, see [Configure your database](../../../../400.deploy/700.best-practices.md).

### Limitations when updating models

If the value of the `MERGE_ENGINE` table option is `append_only`, then the following limitations apply:

* Prohibited DML syntax:

  * `UPDATE`
  * `DELETE`
  * `MERGE INTO`
  * `REPLACE`

* `INSERT [IGNORE] xxx ON DUPLICATE KEY UPDATE` is allowed, but an error will be generated when actual data modification occurs.

* Prohibit the following DDL:

  * `TRUNCATE` tables and partitions
  * Swap partitions
  * Drop partitions
  * Drop column
  * Reduce the column value range.
  * Dynamic partitioning
  * Drop obsolete columns
  * Add columns (specifying `DEFAULT VALUE` for the column)
  * Add an auto-incrementing column

### Example

* Create the `mer_tbl1` table and update the model to full column update ( `delete_insert` ).

    ```shell
    obclient> CREATE TABLE mer_tbl1 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert;
    ```

* Create a columnar table `mer_tbl2` and set the model to full column update (``delete_insert``).

    ```shell
    obclient> CREATE TABLE mer_tbl2 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert
        WITH COLUMN GROUP(each column);
    ```

* Create a table in `append_only` mode and perform `INSERT`, `SELECT`, `UPDATE`, and `DELETE` operations.

  1. Create a table named `mer_tbl3` and set its update model to `append_only`.

      ```shell
      obclient> CREATE TABLE mer_tbl3 (col1 INT PRIMARY KEY, col2 VARCHAR(100))
          MERGE_ENGINE = append_only;
      ```

  2. Insert data into table `mer_tbl3`.

      ```shell
      obclient> INSERT INTO mer_tbl3 VALUES(1, 'oceanbase');
      ```

  3. Query the `mer_tbl3` table.

      ```shell
      obclient> SELECT * FROM mer_tbl3;
      ```

      Response:

      ```shell
      +------+-----------+
      | col1 | col2      |
      +------+-----------+
      |    1 | oceanbase |
      +------+-----------+
      1 row in set
      ```

  4. Updating data in the `mer_tbl3` table returns an error.

      ```shell
      obclient> UPDATE mer_tbl3 SET col2 = 'database' WHERE col1 = 1;
      ```

      The result is as follows:

      ```shell
      ERROR 1235 (0A000): update append_only table is not supported
      ```

  5. An error occurs when you delete data from the `mer_tbl3` table.

      ```shell
      obclient> DELETE FROM mer_tbl3 WHERE col1 = 1;
      ```

      The query result is as follows:

      ```shell
      ERROR 1235 (0A000): delete from append_only table is not supported
      ```
