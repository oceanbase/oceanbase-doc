# Create a table

You can use the `CREATE TABLE` statement to create a table.

This topic describes how to create a non-partitioned table. For information about how to create and use a partitioned table, see [Create a partitioned table](../300.manage-partitions-of-mysql-mode/200.create-a-partition-table-of-mysql-mode.md).

## Create a non-partitioned table

Creating a non-partitioned table means creating a table with only one partition.

The following example shows how to create a non-partitioned table:

```sql
obclient>CREATE TABLE table_name1(w_id int
, w_ytd decimal(12,2)
, w_tax decimal(4,4)
, w_name varchar(10)
, w_street_1 varchar(20)
, w_street_2 varchar(20)
, w_city varchar(20)
, w_state char(2)
, w_zip char(9)
, unique(w_name, w_city)
, primary key(w_id)
);

Query OK, 0 rows affected (0.09 sec)

obclient>CREATE TABLE table_name2 (c_w_id int NOT NULL
, c_d_id int NOT null
, c_id int NOT null
, c_discount decimal(4, 4)
, c_credit char(2)
, c_last varchar(16)
, c_first varchar(16)
, c_middle char(2)
, c_balance decimal(12, 2)
, c_ytd_payment decimal(12, 2)
, c_payment_cnt int
, c_credit_lim decimal(12, 2)
, c_street_1 varchar(20)
, c_street_2 varchar(20)
, c_city varchar(20)
, c_state char(2)
, c_zip char(9)
, c_phone char(16)
, c_since date
, c_delivery_cnt int
, c_data varchar(500)
, index icust(c_last, c_d_id, c_w_id, c_first, c_id)
, FOREIGN KEY (c_w_id) REFERENCES table_name1(w_id)
, primary key (c_w_id, c_d_id, c_id)
);

Query OK, 0 rows affected
```

The example creates two tables and defines some constraints for the columns, including primary keys and foreign keys on different columns. For more information about primary keys and foreign keys, see [Define the constraint type for a column](../200.manage-tables-of-mysql-mode/400.define-the-constraint-type-for-a-column-of-mysql-mode.md).

When creating columns for a table, select the correct data type. For more information about SQL data types, see [Data types](../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/100.data-type-overview-of-mysql-mode.md).

<main id="notice" type='explain'>
<h4>Note</h4>
<p>To ensure performance and facilitate later maintenance, we recommend that you design a primary key or unique key for a table when you create it. If no suitable column can be used as a primary key, you can omit the PRIMARY KEY clause when you create a table. After the table is created, the system will automatically add a hidden primary key column with auto-increment values. For more information about auto-increment columns, see <a href="300.define-an-auto-increment-column-of-mysql-mode.md">Define an auto-increment column</a>. </p>
</main>

## Create a replicated table

A replicated table is a special type of table in OceanBase Database. This table can read the latest modifications to data on any "healthy" replica. For users who require low write frequency and high read latency and load balancing, a replicated table is a good choice.

After you create a replicated table, a replica of the table is created on each OBServer node in the tenant. One of the replicas is selected as the leader, which accepts write requests, while the other replicas only accept read requests.

All replicas need to report their status to the leader, mainly the replay progress, which indicates the data synchronization progress. Generally, the replay progress of a follower replica lags slightly behind that of the leader. As long as the lag does not exceed a threshold, the leader considers the replica to be "healthy" and can quickly replay the modifications on the leader. After the leader determines that a replica is "healthy" for a certain period, it grants the follower a lease. In other words, the leader trusts the follower to remain "healthy" and provide strongly consistent read services for the next period. During this "trust" period, the leader confirms the replay progress of the follower before committing each transaction on the replicated table. After the follower replays the modifications of the transaction, the leader reports to the user that the transaction is successfully committed. At this point, the user can read the modifications of the committed transaction on the follower.

The replicated table feature has been available in OceanBase Database V3.x. In OceanBase Database V4.x, the architecture has undergone significant changes. To adapt to the new single-node log stream architecture, V4.x introduces partition-based readable version number verification and log stream-based lease granting mechanisms to ensure the correctness of strongly consistent reads.

Additionally, V4.x enhances the ability to switch leaders without killing transactions. In V3.x, uncommitted transactions on a replicated table would fail when a leader switch was initiated by the user or load balancing. In V4.x, uncommitted transactions can continue to execute after a leader switch. Compared to V3.x, V4.x offers better write transaction performance and stronger disaster recovery capabilities. The impact of replica downtime on read operations is also reduced.

### Limitations of replicated tables

* Replicated tables:

  * Creation limitations: The sys and meta tenants do not support creating replicated tables because they do not have broadcast log streams.
  * Write performance is affected by the number of nodes: Since write operations on a replicated table need to be synchronized to all replicas, the more nodes there are, the greater the impact on write performance.
    * Workaround: Avoid combining read and write operations on a replicated table in the same transaction. Pure write or pure read operations on a replicated table are acceptable.

  * Attribute conversion:

    * Replicated tables and table groups are mutually exclusive. Modifying the table group attribute of a replicated table will result in an error. Similarly, converting a regular table to a replicated table will result in an error if the regular table belongs to a table group.
    * Converting a replicated table depends on load balancing and transfer. Ensure that the relevant configuration items are enabled.

  * Routing:

    * If a transaction involves a write operation on a replicated table, subsequent queries on the replicated table may be randomly routed to a follower. This can lead to issues with reading from the follower, as the observer may internally forward the request to the leader of the replicated table, affecting query performance.

      * In ODP V4.3.3, the routing strategy has been adjusted. If there is a write operation on a replicated table, subsequent queries will be routed to the leader of the replicated table.

    * Queries that join a replicated table with a regular table will be randomly routed based on the replicated table. For `JOIN` queries, ODP routes based on the first table. This may route to a non-leader node of the regular table, leading to a remote plan.
    * If the attribute of a regular table is changed to a replicated table, ODP cannot detect this change and cannot route based on the replicated table to distribute the load.

  * In a transaction, if a replicated table has been modified, subsequent query operations: When querying the replicated table, the generated execution plan will select the local replica. However, due to the modification, an error indicating that the replica is unreadable will be reported. The SQL retry will select the leader replica. In this case, the plan cache cannot be hit, leading to poor query performance.

      <main id="notice" type='explain'>
        <h4>Note</h4>
        <p>In a transaction, if a replicated table is modified, OceanBase Database always prioritizes selecting the leader replica of the replicated table for queries, rather than directly selecting the local replica, to ensure efficient query performance and avoid selecting the wrong replica.</p>
      </main>

* Broadcast log streams:

  * Each user tenant can have at most one broadcast log stream.
  * Attribute conversion between broadcast log streams and regular log streams is not supported.
  * Broadcast log streams cannot be manually deleted. They are deleted along with the tenant.

### Syntax for creating a replicated table

To create a replicated table, add the `DUPLICATE_SCOPE` option to the `CREATE TABLE` statement. Only user tenants can create replicated tables; the `sys` tenant cannot. The SQL statement for creating a replicated table is as follows:

```sql
CREATE TABLE table_name column_definition DUPLICATE_SCOPE='none | cluster';
```

The `DUPLICATE_SCOPE` parameter specifies the attribute of the replicated table. Valid values are as follows:

* `none`: The table is a regular table.
* `cluster`: The table is a replicated table. The leader needs to replicate transactions to all F and R replicas of the current tenant.

If you do not specify `DUPLICATE_SCOPE` when creating a table, the default value is `none`.

```sql
CREATE TABLE dup_t1 (c1 int,c2 int) DUPLICATE_SCOPE= 'cluster';
```

When the first replicated table is created in a tenant, the system automatically creates a special log stream called a broadcast log stream. Subsequent replicated tables are created on this broadcast log stream. The difference between a broadcast log stream and a regular log stream is that a broadcast log stream automatically deploys a replica on each OBServer node in the tenant. This ensures that, under ideal conditions, a replicated table can provide strongly consistent reads on any OBServer node. You can use the following SQL statement to view the broadcast log stream where the replicated tables of a tenant are located:

```sql
SELECT * FROM oceanbase.DBA_OB_LS WHERE flag LIKE "%DUPLICATE%";
```

The query result is as follows.

```shell
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+-----------+
| LS_ID | STATUS | PRIMARY_ZONE | UNIT_GROUP_ID | LS_GROUP_ID | CREATE_SCN          | DROP_SCN | SYNC_SCN            | READABLE_SCN        | FLAG      | UNIT_LIST |
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+-----------+
|  1003 | NORMAL | z1;z2        |             0 |           0 | 1683267390195713284 |     NULL | 1683337744205408139 | 1683337744205408139 | DUPLICATE |           |
+-------+--------+--------------+---------------+-------------+---------------------+----------+---------------------+---------------------+-----------+-----------+
1 rows in set
```

In the example, the log stream with `LS_ID` `1003` is the broadcast log stream. All replicated tables of the tenant are created on this log stream. For more information about broadcast log streams, see [Replicas](../../../../600.manage/300.replica-management/100.replica-introduction.md).

After a replicated table is created, you can perform insert and read/write operations on it, just like a regular table. The difference is that for read requests, if you connect to the database using a proxy, the read request may be routed to any OBServer node for execution. If you connect to the database directly, the system will execute the read request on the directly connected OBServer node as long as the local replica is readable. For more information about database connection methods, see [Overview of connection methods](../../../../300.develop/100.application-development-of-mysql-mode/100.connect-to-oceanbase-database-of-mysql-mode/100.connection-methods-overview-of-mysql-mode.md).

## Create a new table by replicating data from an existing table

### Replicate data from an existing table

You can use the `CREATE TABLE AS SELECT` statement to replicate data from an existing table. However, the structure will not be completely consistent, and information such as constraints, indexes, default values, and partitions will be lost.

Example statement:

```sql
obclient>CREATE TABLE t1_copy AS SELECT * FROM t1;
Query OK, 3 rows affected
```

### Replicate the structure of an existing table

You can use the `CREATE TABLE LIKE` statement to replicate the structure of an existing table. However, you cannot replicate the data.

Example statement:

```sql
obclient>CREATE TABLE t1_like like t1;
Query OK, 0 rows affected
```

## Create a rowstore table

OceanBase Database supports creating rowstore tables and converting rowstore tables to columnstore tables.

When the [default_table_store_format](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) parameter is set to `row` (the default value), the default table type is rowstore. If the [default_table_store_format](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2200.default_table_store_format.md) parameter is set to a value other than `row`, you can create a rowstore table by specifying the `WITH COLUMN GROUP(all columns)` option.

For more information about converting rowstore tables to columnstore tables, see [Change a table](600.change-table-of-mysql-mode.md). For more information about creating columnstore indexes, see [Create an index](../500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).

You can create a rowstore table by specifying the `WITH COLUMN GROUP(all columns)` option.

**Here is an example:**

```sql
CREATE TABLE tbl1_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(all columns);
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>If you specify the <code>WITH COLUMN GROUP(all columns)</code> option to create a rowstore table, the table remains in rowstore format even if you later execute the <code>DROP COLUMN GROUP(all columns)</code> statement to drop the column group. </p>
</main>

## Create a columnstore table

OceanBase Database supports creating columnstore tables, converting rowstore tables to columnstore tables, and creating columnstore indexes. By default, OceanBase Database creates rowstore tables. You can explicitly specify the `WITH COLUMN GROUP` option to create columnstore tables or rowstore-columnstore redundant tables.

For more information about converting rowstore tables to columnstore tables, see [Change a table](600.change-table-of-mysql-mode.md). For more information about creating columnstore indexes, see [Create an index](../500.manage-indexes-of-mysql-mode/200.create-an-index-of-mysql-mode.md).

You can create a rowstore-columnstore redundant table by specifying the `WITH COLUMN GROUP(all columns, each column)` option.

**Here is an example:**

```sql
CREATE TABLE tbl1_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(all columns, each column);
```

You can create a columnstore table by specifying the `WITH COLUMN GROUP(each column)` option.

**Here is an example:**

```sql
CREATE TABLE tbl2_cg (col1 INT PRIMARY KEY, col2 VARCHAR(50)) WITH COLUMN GROUP(each column);
```

When you create and use a columnstore table and import a large amount of data, you must perform a **major compaction** to improve the read performance and perform **statistics collection** to optimize the execution strategy.

* **Major compaction**: After you import data in batches, we recommend that you perform a major compaction. This helps improve the read performance because the major compaction organizes fragmented data into contiguous data in physical storage, thereby reducing the disk I/O during read operations. After you import data, you can trigger a major compaction in the tenant to ensure that all data is compacted to the baseline layer. For more information, see [`MAJOR and MINOR`](../../../500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/600.sql-statement-of-mysql-mode/1500.alter-system-freeze-of-mysql-mode.md).

* **Statistics collection**: After you perform a major compaction, we recommend that you collect statistics. This is important for the optimizer to generate effective query plans and execution strategies. You can execute the [GATHER_SCHEMA_STATS](../../../600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/15900.dbms-stats-mysql/1800.gather-schema-stats-mysql.md) procedure to collect statistics for all tables. You can also query the [GV$OB_OPT_STAT_GATHER_MONITOR](../../../700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/6100.gv_ob_opt_stat_gather_monitor-of-mysql-mode.md) view to monitor the statistics collection progress.

Note that as the data volume of a columnstore table increases, the major compaction speed may decrease.

## Create a heap-organized table

OceanBase Database supports two types of table organization: index-organized tables (IOTs) and heap-organized tables.

### Limitations

* The primary key of a heap-organized table must include all partitioning columns.
* The name of an index created on a heap-organized table must be different from the name of the primary key column.
* OceanBase Database does not support the following DDL operations on heap-organized tables:

  * Modifying the primary key constraint
  * Changing a column to a primary key
  * Changing the data type or length of a primary key column from a larger to a smaller size
  * Adding a primary key column
  * Changing a primary key column to an auto-increment column
  * Dropping a primary key column
  * Splitting partitions

### Syntax for specifying the table organization

To specify the table organization when creating a table, add the `ORGANIZATION` option to the `CREATE TABLE` statement. The SQL statement is as follows:

```sql
CREATE TABLE table_name column_definition ORGANIZATION [=] {INDEX | HEAP};
```

The `ORGANIZATION` parameter specifies the storage order of data rows in the table. Valid values are as follows:

* `INDEX`: specifies that the table is an index-organized table.
* `HEAP`: specifies that the table is a heap-organized table.

If you do not specify the `ORGANIZATION` option, its value is the same as the value of the [default_table_organization](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2150.default_table_organization.md) parameter.

**Here are some examples:**

* Specify the `ORGANIZATION` attribute as `HEAP` when creating a table.

  ```sql
  CREATE TABLE ora_tbl1 (col1 INT, col2 INT) ORGANIZATION = HEAP;
  ```

* Do not specify the `ORGANIZATION` option when creating a table.

  After you change the tenant-level parameter `default_table_organization`, you can create a table. For more information about the `default_table_organization` parameter, see [default_table_organization](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2150.default_table_organization.md).

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>In the current version, the <code>default_table_organization</code> parameter is only applicable to user tenants in MySQL mode of OceanBase Database. It is not supported for the sys tenant and user tenants in Oracle mode. </p>
  </main>

  1. Set the value of the `default_table_organization` parameter to `HEAP`.

      ```sql
      ALTER SYSTEM SET default_table_organization = 'HEAP';
      ```

  2. Create a table named `ora_tbl2`.

      ```sql
      CREATE TABLE ora_tbl2(col1 INT, col2 INT);
      ```

  3. View the definition of the `ora_tbl2` table.
  3. View the definition of the `ora_tbl2` table.

      ```sql
      SHOW CREATE TABLE ora_tbl2;
      ```

      The returned result is as follows:

      ```shell
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      | Table    | Create Table                                                                                                                                                                                                                                                                                                                 |
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      | ora_tbl2 | CREATE TABLE `ora_tbl2` (
        `col1` int(11) DEFAULT NULL,
        `col2` int(11) DEFAULT NULL
      ) ORGANIZATION HEAP DEFAULT CHARSET = utf8mb4 ROW_FORMAT = DYNAMIC COMPRESSION = 'zstd_1.3.8' REPLICA_NUM = 1 BLOCK_SIZE = 16384 USE_BLOOM_FILTER = FALSE ENABLE_MACRO_BLOCK_BLOOM_FILTER = FALSE TABLET_SIZE = 134217728 PCTFREE = 0 |
      +----------+------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
      1 row in set
      ```

### Specify a clustered column when creating a table

To specify a clustered column when creating a table, add the `CLUSTER BY` option to the `CREATE TABLE` statement. The SQL statement is as follows:

```sql
CREATE TABLE table_name (table_definition_list) CLUSTER BY (column_name_list);

column_name_list:
    column_name [, column_name ...]
```

**Parameters:**

`column_name`: the name of the clustered column used for sorting.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>In a MySQL tenant of OceanBase Database, if you do not explicitly specify the table organization (for example, <code>ORGANIZATION = HEAP</code>), but define the <code>CLUSTER BY</code> option, OceanBase Database will create a heap-organized table by default. </p>
</main>

**Here is an example:**

Create a table named `cb_tbl1` that is sorted by the `col2` and `col4` columns.

```shell
obclient> CREATE TABLE cb_tbl1 (
    col1 INT PRIMARY KEY,
    col2 INT,
    col3 DECIMAL(10, 2),
    col4 TIMESTAMP
    )
    CLUSTER BY (col2, col4);
```

## Create a temporary table

A temporary table is a session-level special table used for temporarily storing intermediate data.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Temporary tables are supported starting from OceanBase Database V4.3.5 BP4. </p>
</main>

### Limitations

* Routing of temporary tables: Since temporary tables need to support load balancing like regular tables, by default, they cannot be bound to a specific server. Consider disabling load balancing if needed.
* In the serializable isolation level (Serializable), OceanBase Database does not support writing to temporary tables created within the same transaction.

* If a temporary table with the same name as a regular table exists in the current session, it is not recommended to use the database-level statistics collection feature in the current session, as the results may not meet expectations.

* Temporary tables are cleaned up through background logic, and their cleanup speed is limited to minimize impact on business operations. Therefore, in scenarios with a large number of temporary tables, it is recommended to manually delete them promptly.
* Temporary tables cannot be accessed via DBLink.
* When connecting to an OBServer through ODP, you need to manually adjust the [server_protocol](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575488), [client_session_id_version](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575403), and [proxy_id](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000003575542) parameters.

  Here are the steps:

  * Execute the following command to modify the communication protocol configuration of OBProxy.

    ```sql
    ALTER proxyconfig SET server_protocol = 'OceanBase 2.0';
    ```

  * Execute the following command to set the algorithm for generating the client session ID (Client Session ID) to version 2.

    ```sql
    ALTER proxyconfig SET client_session_id_version = 2;
    ```

  * Execute the following command to change the ODP ID to 1. Different ODPs should be assigned different numbers to ensure that the generated Client Session IDs do not conflict.

    ```sql
    ALTER proxyconfig SET proxy_id = 1;
    ```

### Example

Create a temporary table named `tbl1`:

```sql
CREATE TEMPORARY TABLE tbl1(col1 INT);
```

## Specify the update model of a table

To specify the update model of a table when you create the table, you can add the `MERGE_ENGINE` option to the `CREATE TABLE` statement. The syntax of the SQL statement is as follows:

```sql
CREATE TABLE table_name column_definition
    MERGE_ENGINE = {delete_insert | partial_update | append_only};
```

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Once the <code>MERGE_ENGINE</code> option is specified during table creation, its configuration value cannot be modified. </p>
</main>

The `MERGE_ENGINE` option is used to specify the update model of a table. The options are as follows:

* `partial_update`: specifies that the table uses a partial update model. In this model, only modified columns (deltas) are recorded in each update. This model consumes less storage space, but during queries, you need to merge the recorded data from multiple records to obtain the latest value. This model is recommended for OLTP scenarios that have frequent updates and low query requirements.
* `delete_insert`: specifies that the table uses a full-column update model. In this model, a complete row (delete the old row and insert the new row) is written in each update. The query performance is prioritized. This model supports Skip Index for incremental data (Memtable/Delta SSTable). During queries, filters can be pushed down on incremental data. If the filtering results do not involve updates to the baseline data, you can separately batch process baseline and incremental data to reduce read amplification. This model is recommended for OLAP scenarios that have high incremental data ratios and complex queries or batch processing analysis.
* `append_only`: specifies that the table can only be updated by the `INSERT` operation. All other DML and DDL operations that modify data in the table are disabled. The TTL feature can be used to clean up expired data. For more information about usage limitations, see [Usage limitations](#usage-limitations) of the update model.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>When you specify <code>delete_insert</code> or <code>partial_update</code>, the write granularity is the main difference between them. <code>delete_insert</code> writes the full row (delete the old row and insert the new row) in each update, while <code>partial_update</code> writes only the modified columns. Because <code>delete_insert</code> writes the full row, it can support Skip Index for Delta SSTables, which can enhance the filtering down effect during analytical queries. </p>
</main>

If the `MERGE_ENGINE` option is not specified, the value of the [default_table_merge_engine](../../../800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2130.default_table_merge_engine.md) parameter is used.

### Scenarios

| Scenario | Recommended value | Description |
|------|----------|------|
| OLAP, analytical queries, batch processing | `delete_insert` | Filters on incremental data can be pushed down, which can enhance the query performance. However, more storage space is required for incremental data. |
| OLTP, frequent updates, storage-sensitive scenarios | `partial_update` | This model consumes less storage space. It is recommended for OLTP scenarios with frequent updates and low query requirements. |
| Use immutable data, efficient appending, and simplified queries | `append_only` | This model is recommended for high-throughput scenarios, such as log analysis and IoT data monitoring. The range query and aggregation computation efficiency are high.|

For more information about configurations, see [Best practices](../../../../400.deploy/700.best-practices.md).

### Usage limitations

If the table update model `MERGE_ENGINE` is specified as `append_only`, the following limitations exist:

* The following DML operations are disabled:

  * `UPDATE`
  * `DELETE`
  * `MERGE INTO`
  * `REPLACE`

* The `INSERT [IGNORE] xxx ON DUPLICATE KEY UPDATE` operation is not disabled. However, when actual data modifications are performed, the operation will return an error.

* The following DDL operations are disabled:

  * `TRUNCATE` tables and partitions.
  * Swap partitions.
  * Drop partitions.
  * Drop columns.
  * Reduce the value range of a column.
  * Perform dynamic partitioning.
  * Drop obsolete columns.
  * Add columns specified with `DEFAULT VALUE`.
  * Add auto-increment columns.

### Examples

* Create a table `mer_tbl1` with the full-column update model (`delete_insert`).

    ```shell
    obclient> CREATE TABLE mer_tbl1 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert;
    ```

* Create a columnstore table `mer_tbl2` with the full-column update model (`delete_insert`).

    ```shell
    obclient> CREATE TABLE mer_tbl2 (col1 INT, col2 INT)
        MERGE_ENGINE = delete_insert
        WITH COLUMN GROUP(each column);
    ```

* Create a table with the `append_only` model and perform `INSERT`, `SELECT`, `UPDATE`, and `DELETE` operations.

  1. Create a table `mer_tbl3` with the `append_only` model.

      ```shell
      obclient> CREATE TABLE mer_tbl3 (col1 INT PRIMARY KEY, col2 VARCHAR(100))
          MERGE_ENGINE = append_only;
      ```

  2. Insert data into the `mer_tbl3` table.

      ```shell
      obclient> INSERT INTO mer_tbl3 VALUES(1, 'oceanbase');
      ```

  3. Query data from the `mer_tbl3` table.

      ```shell
      obclient> SELECT * FROM mer_tbl3;
      ```

      The returned result is as follows:

      ```shell
      +------+-----------+
      | col1 | col2      |
      +------+-----------+
      |    1 | oceanbase |
      +------+-----------+
      1 row in set
      ```

  4. Attempt to update data in the `mer_tbl3` table and verify whether an error is returned.

      ```shell
      obclient> UPDATE mer_tbl3 SET col2 = 'database' WHERE col1 = 1;
      ```

      The returned result is as follows:

      ```shell
      ERROR 1235 (0A000): update append_only table is not supported
      ```

  5. Attempt to delete data from the `mer_tbl3` table and verify whether an error is returned.

      ```shell
      obclient> DELETE FROM mer_tbl3 WHERE col1 = 1;
      ```

      The returned result is as follows:

      ```shell
      ERROR 1235 (0A000): delete from append_only table is not supported
      ```
