# Create a DDL trigger

The Oracle-compatible mode of OceanBase Database supports system triggers. System triggers are classified into two categories based on the triggering event: database event triggers and DDL event triggers. Database event triggers are triggered by `LOGON` and `LOGOFF` events, while DDL event triggers are triggered by DDL statements. Starting from V4.4.2 BP4, OceanBase Database supports creating BEFORE DDL triggers.

DDL triggers are automatically executed before the execution of a DDL statement. They are commonly used to record DDL operation logs, audit DDL changes, and block non-compliant DDL operations by throwing exceptions.

## Scope of application

* Only user tenants in Oracle-compatible mode support DDL triggers. Creating system triggers that listen for the `SYS` schema is not allowed, meaning `ON SYS.SCHEMA` is not supported.
* Only the `BEFORE` trigger timing is supported. `AFTER DDL` triggers are not currently supported.
* Standby tenants in primary/standby databases do not trigger DDL triggers.
* DDL triggers are controlled by the overall system trigger switch, which is enabled by default.

## Syntax

```sql
CREATE [OR REPLACE] TRIGGER [schema.]trigger_name
  BEFORE ddl_event [OR ddl_event]...
  ON {[schema.]SCHEMA | DATABASE}
  [FOLLOWS [owner.]other_trigger]
  [ENABLE | DISABLE]
  [WHEN (condition)]
DECLARE
  ...
BEGIN
  ...
END;
/
```

The following operations do not trigger DDL triggers:

* OceanBase resource and tenant management statements, such as `RESOURCE POOL`, `RESOURCE UNIT`, `TENANT`, `STANDBY TENANT`, `TABLEGROUP`, etc.
* OceanBase or MySQL-compatible extension statements, such as `OPTIMIZE`, `SET GLOBAL`, `CREATE TABLE LIKE`, `LOCATION`, `CATALOG`, throttling rules, etc.
* Statements with different semantics in Oracle-compatible mode, such as `CREATE DATABASE`, `ALTER DATABASE`, `ALTER SYSTEM`, `ALTER SESSION`, etc.
* Internally derived actions of DDL, such as insertions and failure cleanup of CTAS, implicitly created or deleted indexes, container tables of materialized views, etc.
* Kernel internal actions, such as RootService internal SQL, subtasks and recovery of DDL tasks, RPC retransmission, log replay, standby database applications, etc.

## Limitations

When creating and using DDL triggers, note the following limitations:

* The matching rules for trigger scopes are as follows:

  * `ON SCHEMA` matches by the current user. That is, when the current user executes DDL, it triggers DDL triggers on the user's own schema; it does not match by the owner of the DDL target object.
  * `ON DATABASE` matches by the current tenant. Whenever any user within the current tenant executes DDL, it will be triggered.

* The execution order rules are as follows:

  * When the same DDL statement matches both schema-level and database-level triggers, the schema-level trigger is executed first, followed by the database-level trigger.
  * Within the same scope, you can use `FOLLOWS` to specify the execution order of triggers. If not specified, the execution order of multiple triggers is uncertain.
  * Specifying `FOLLOWS` across scopes is not supported. The referenced trigger must also be a DDL trigger, and their trigger event sets must have an intersection.

* Executing any DDL, DCL, or `ANALYZE` statements via SQL or PL's SPI interface is prohibited within the Trigger Body.

* Setting global variables and system variables is prohibited within the Trigger Body.

* A regular DDL trigger cannot execute `COMMIT` or `ROLLBACK`; otherwise, the `ORA-04092` error is returned. If a trigger is declared as an autonomous transaction using `PRAGMA AUTONOMOUS_TRANSACTION`, the commit in an autonomous transaction is independent of the batch transaction that triggered it.

* When the current trigger is the DDL target, it does not participate in its own triggering, for example, operations like `CREATE OR REPLACE TRIGGER` or `DROP TRIGGER`.

* DDL initiated internally by the kernel or on a standby tenant does not trigger triggers; when the same DDL is automatically retried, previously committed triggers are not re-executed.

### Transaction description

DDL triggers and subsequent DDL statements are not executed within the same transaction. The specific behavior is as follows:

1. All DDL triggers matched by a single DDL statement are executed sequentially within the same batch transaction. During execution, the session's automatic commit is temporarily disabled.
2. After all triggers are successfully executed, the batch transaction is committed once, and then the actual DDL statement is executed or a DDL request is sent to RootService.
3. If any trigger fails to execute, the entire batch transaction is rolled back, and the DDL is aborted without performing the actual DDL operation.
4. After the trigger batch transaction is committed, if the subsequent DDL execution fails, times out, or is canceled, the modifications already committed by the trigger will not be rolled back.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>Because triggers and DDL belong to two separate transactions, the logs recorded by the trigger or the data written by it still exist if the DDL fails. Business implementations must allow for this inconsistency. If you need to strictly ensure that trigger modifications succeed or fail together with the DDL, perform only validation or provide prompts within the trigger, and do not rely on the data written by the trigger to determine whether the DDL succeeded.</p>
</main>

## Privilege requirements

* To create a DDL trigger in your own schema, you must have the `CREATE TRIGGER` or `CREATE ANY TRIGGER` system privilege.
* To create a DDL trigger across schemas, or to listen for other users' schemas using `ON schema.SCHEMA`, you must have the `CREATE ANY TRIGGER` system privilege.
* To create a database-level DDL trigger (`ON DATABASE`), in addition to the above creation privileges, you must also have the `ADMINISTER DATABASE TRIGGER` system privilege.

## Example

Create a DDL log table to record DDL events.

```sql
CREATE TABLE ddl_log (
  event_name VARCHAR2(50),
  obj_type   VARCHAR2(50),
  obj_name   VARCHAR2(128),
  login_user VARCHAR2(128),
  ddl_time   DATE
);
```

Create a schema-level `BEFORE CREATE` trigger to record the object information of `CREATE` statements.

```sql
CREATE OR REPLACE TRIGGER trg_before_create
  BEFORE CREATE ON SCHEMA
BEGIN
  INSERT INTO ddl_log
    VALUES (ORA_SYSEVENT, ORA_DICT_OBJ_TYPE, ORA_DICT_OBJ_NAME, ORA_LOGIN_USER, SYSDATE);
END;
/
```

Execute a `CREATE TABLE` statement to verify that the trigger takes effect.

```sql
CREATE TABLE t_ddl_trigger_demo (id INT);
```

Query the log table to view the record for this `CREATE` event.

```sql
SELECT * FROM ddl_log;
```

Create a database-level `BEFORE DDL` trigger to record all DDL events within the current tenant. The user executing this example must have the `ADMINISTER DATABASE TRIGGER` system privilege in addition to basic creation privileges.

```sql
CREATE OR REPLACE TRIGGER trg_before_ddl
  BEFORE DDL ON DATABASE
BEGIN
  INSERT INTO ddl_log
    VALUES (ORA_SYSEVENT, ORA_DICT_OBJ_TYPE, ORA_DICT_OBJ_NAME, ORA_LOGIN_USER, SYSDATE);
END;
/
```

Create a `BEFORE DROP` trigger to block `DROP TABLE` operations by throwing an exception when a table is dropped.

```sql
CREATE OR REPLACE TRIGGER trg_before_drop
  BEFORE DROP ON SCHEMA
BEGIN
  IF ORA_DICT_OBJ_TYPE = 'TABLE' THEN
    RAISE_APPLICATION_ERROR(-20001, 'DROP TABLE is not allowed');
  END IF;
END;
/
```

After use, drop the triggers and tables created in the examples.

```sql
DROP TRIGGER trg_before_create;
```

```sql
DROP TRIGGER trg_before_ddl;
```

```sql
DROP TRIGGER trg_before_drop;
```

```sql
DROP TABLE t_ddl_trigger_demo;
```

```sql
DROP TABLE ddl_log;
```
