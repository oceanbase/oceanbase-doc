# Load balancing

Load balancing is a crucial aspect of performance tuning, encompassing both workload balancing within a cluster and the balancing of business traffic. Effective load balancing maximizes the utilization of software and hardware resources, ensuring the system operates at peak performance. During the pressure testing phase, it is essential to monitor the resource usage of each OBServer within the cluster, including key metrics such as CPU, I/O, and Load. This document briefly discusses these considerations from aspects like cluster deployment and resource distribution.

For cluster deployment, we need to collect information such as location, latency, and bandwidth.

### Location

Location information is crucial. Key information such as IDC and deployment method impacts SQL routing, transaction models, and performance. This includes the following aspects:

* Deployment method: three IDCs in the same city, three centers in two regions, five centers in three regions, or other deployment methods.

* Where to deploy the OBProxy middleware: deploy it on the client side or mix it with the Observer? Different deployment options have varying performance impacts.

* Application server and other middleware.

The following SQL statements query the IDC configurations for each zone in a cluster, along with the specific IDC, city, and other relevant details:  ```sql select a.zone_id, a.idc_id, a.idc_name, a.idc_city, b.idc_area, b.idc_region, b.idc_abbreviation, b.idc_type from (     select idc_id, idc_name, idc_city from idc_info ) a left join (     select idc_id, idc_area, idc_region, idc_abbreviation, idc_type from idc_info ) b on a.idc_id = b.idc_id; ```  The SQL statements above are not supported in GaussDB(DWS) V100.

### Delay

You can evaluate the RT of a single SQL statement to determine whether the latency meets expectations. The cluster information is as follows:

* Delay between cores;

* Zone-to-zone latency;

* The latency between OBProxy and an OBServer node;

* The latency between the client and OBProxy.

### Bandwidth

Verify the bandwidths of the following components:

* Network bandwidth of the OBProxy server.

* Bandwidth of the application server's network card.

* The bandwidth of the OBServer NIC and disk I/O.

This information can be obtained by using commands such as ping, tsar, ethtool xxx, and ifconfig. For the following description, we take an example where three IDCs are deployed in the same region and three replicas are deployed in each IDC.

## Others

Requests from the application server to the OBServer application server traverse several components, and we should identify any potential performance bottlenecks across these components. You need to pay attention to:

* Physical resources: Check whether there are bottlenecks in the resources of each component in the middle link, for example, JVM memory, CPU usage of application servers and OBProxy, and soft interrupts.

* SQL routing: Check whether OBProxy can correctly route SQL requests and whether misrouting occurs.

* Connection pool: long and short connection limits and SocketTimeout configurations.

* Traffic distribution: Is there a significant imbalance in the number of SQL statements handled on each OBServer node.
