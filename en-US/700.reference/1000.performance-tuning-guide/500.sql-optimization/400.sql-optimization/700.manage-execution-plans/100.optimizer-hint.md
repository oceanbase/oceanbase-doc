# Optimizer hint

The hint mechanism enables the optimizer to generate a specified execution plan.

Generally, the optimizer selects the best execution plan for user queries without hints. However, in some cases, the optimizer may fail to generate an optimal execution plan, and a hint can be used to specify the generation of a specific execution plan.

## Hint syntax

Hint is a special form of SQL comment. Specifically, a "+" is added after the left marker ("/*") of the comment. Since hints are comments, if the server cannot identify the hint in an SQL statement, the optimizer will ignore the hint and use the default plan generation logic. Additionally, hints only affect the logical structure of a generated plan, not the semantics of the SQL statement.

```sql
{ DELETE | INSERT | SELECT | UPDATE | REPLACE } /*+ [hint_text][,hint_text]... */
```

    <h4>Notice</h4>
    <p>When you use a MySQL C client to execute an SQL statement with a hint, you must use the <code>-c</code> option to log in. Otherwise, the MySQL client will remove the hint as a comment from your SQL statement, and the system cannot receive the hint.</p>
  </main>

## QB_NAME parameter

In a DML statement, every `query_block` has a `QB_NAME` (query block name), which can be specified by the user or automatically generated by the system. If you do not specify a `QB_NAME` with a hint, the system generates one for you in the order of `SEL$1`, `SEL$2`, `UPD$1`, and `DEL$1` from left to right (which is also the order parsed by the resolver).

You can use the `QB_NAME` parameter to uniquely identify each table or to specify the behavior of any query block. The `QB_NAME` in the `TBL_NAME` parameter is used to identify a table, and the first `QB_NAME` in a hint is used to identify the query block to which the hint applies.

The preceding SQL statement can also be written as follows:

```sql
SELECT /*+INDEX(t1 PRIMARY) INDEX(@SEL$2 t2@SEL$2 t2_c1)*/ * FROM t1 , (SELECT * FROM t2 WHERE c2 = 1 LIMIT 5) WHERE t1.c1 = 1;
```

or:

```sql
SELECT /*+INDEX(t1 PRIMARY)*/ * FROM t1 , (SELECT /*+INDEX(t2 t2_c1)*/ * FROM t2 WHERE c2 = 1 LIMIT 5) WHERE t1.c1 = 1;
```

or:

```sql
SELECT /*+INDEX(@SEL$1 t1 PRIMARY) INDEX(@SEL$2 t2 t2_c1)*/ * FROM t1 , (SELECT * FROM t2 WHERE c2 = 1 LIMIT 5) WHERE t1.c1 = 1;
```

## Hint application rules

The application rules for hints are as follows:

* If no query block is specified in a hint, the hint applies to the current query block.

  **Example 1: The hint cannot take effect because the `t2` table is in query block 2, and the hint cannot be rewritten to query block 1.**

  ```sql
  obclient> EXPLAIN SELECT /*+INDEX(t2 t2_c1)*/ *
          FROM t1 , (SELECT * FROM t2 WHERE c2 = 1 LIMIT 5)
          WHERE t1.c1 = 1;
  +-----------------------------------------------------------------------------------------------------------+
  | Query Plan                                                                                                |
  +-----------------------------------------------------------------------------------------------------------+
  | ======================================================================                                    |

  | |1 |├─TABLE RANGE SCAN         |t1(t1_c1)      |1       |7           |                                    |
  | |2 |└─MATERIAL                 |               |1       |3           |                                    |
  | |3 |  └─SUBPLAN SCAN           |ANONYMOUS_VIEW1|1       |3           |                                    |
  | |4 |    └─TABLE FULL SCAN      |t2             |1       |3           |                                    |

  | Outputs & filters:                                                                                        |
  | -------------------------------------                                                                     |
  ```

## Common hints and syntax

Unlike other databases, the optimizer of OceanBase Database is dynamically programmed. It has already considered all possible optimal execution plans. Therefore, hints are mainly used to specify the behavior of the optimizer and to execute SQL queries according to the specified hints.

### INDEX hint

The syntax of the `INDEX` hint is supported in both MySQL mode and Oracle mode.

* The syntax of the `INDEX` hint in Oracle mode is as follows:

```sql
SELECT/*+INDEX(table_name index_name) */ * FROM table_name;
```

* The syntax of the `INDEX` hint in MySQL mode is as follows:

```sql
table_name [[AS] alias] [index_hint_list]

index_hint_list:
index_hint [, index_hint] ...

index_hint:
USE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] ([index_list])
  | IGNORE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] (index_list)
  | FORCE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] (index_list)

index_list:
index_name [, index_name] ...
```

In the syntax of Oracle mode, you can specify only one `INDEX` for a table, whereas in the syntax of MySQL mode, you can specify multiple `INDEXES`. However, in OceanBase Database, if you specify multiple `INDEXES` in MySQL mode, the system will use the first `INDEX` to generate a `PATH`, regardless of whether the `INDEX` specified in the SQL statement has a `filter` clause that causes complete table scan and index access (namely, the current design of OceanBase Database assumes that the person who writes hints knows the database better than the program does). If the hint type is `IGNORE`, all specified `INDEXES` are ignored. The hint types `USE`, `FORCE`, and `Oracle` hints work in the same way. If the `INDEX` specified in the hint does not exist or is in the `invalid` state, the hint is ignored. If you ignore all `INDEXES`, including those on the primary table, the hint is ignored.

If an alias is assigned to a table name in an SQL statement in the form of `table_name [AS] alias`, you must use the table alias to make the `INDEX` hint take effect. Here is an example:

### FULL Hint

The syntax of the `FULL` hint is as follows:

```sql
/*+ FULL(table_name)*/
```

The `FULL` hint specifies to use a primary key scan for the specified table. It is equivalent to the `INDEX` hint `/*+ INDEX(table_name PRIMARY)*/`.

### ORDERED Hint

The syntax of the `ORDERED` hint is as follows:

```sql
 /*+ ORDERED */
```

If SQL rewriting occurs after this hint is specified, the database will join tables based on the order of `FROM_items` in the rewritten `stmt`, where `sub_query` is placed in the From Items in the position corresponding to the new table item.

### USE_MERGE hint

The syntax of the `USE_MERGE` hint is as follows:


It is unclear whether a merge join is commutative, namely, whether A merge join B is equivalent to B merge join A. ### USE_NL hint

The basic structure of a join hint is as follows:
`join_hint_name ( @ qb_name table_name_list)`
This hint specifies to generate a plan based on the hint semantics when the right table in the join matches table_name_list. Generally, you need to use the `LEADING` hint to specify the join order and make the tables in table_name_list the right tables. Otherwise, the hint will become invalid due to the change of the join order.

The table_name_list can be in any of the following forms:

* Single table: use_nl ( t1 ): Use Nested Loop Join when t1 is the right table.
* Multiple single tables: use_nl ( t1 t2 ... ): Use Nested Loop Join when t1 or t2 is the right table.
* Multiple tables: use_nl ( (t1 t2) ): Use Nested Loop Join when t1 join t2 is the right table, ignoring the join order and method of t1 and t2.
* Multiple groups of tables: use_nl ( t1 (t2 t3)  (t4 t5 t6) ... ): Use Nested Loop Join when t1 / t2 join t3 / t4 join t5 join t6 is the right table.

The `USE_NL` hint specifies to use the Nested Loop Join algorithm when joining tables. The syntax is as follows:

```sql
/*+ USE_NL(table_name_list) */
```

### PARALLEL hint

The `PARALLEL` hint specifies the degree of parallelism at the statement level. The syntax is as follows:

```sql
/*+ PARALLEL(n) */
```

In the syntax, `n` is an integer that specifies the degree of parallelism.

OceanBase Database also supports the `PARALLEL` hint at the table level. The syntax is as follows:

```sql
/*+ PARALLEL(table_name n) */
```

If both the global and table-level `PARALLEL` hints are specified, the table-level hint will be ignored. Here is an example:

### UNION_MERGE hint

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The <code>UNION_MERGE</code> hint is supported in OceanBase Database V4.3.5 and later. </p>
</main>

The <code>UNION_MERGE</code> hint specifies the execution plan to use index merge for a query. When the hint is provided, OceanBase Database will directly select the corresponding index merge plan.

The syntax is as follows:

```sql
/*+ UNION_MERGE(table_name index_name_list) */
```

The parameters are described as follows:

* `table_name`: the name of the table.
* `index_name_list`: the list of index names. The index names are separated by spaces.

**Here is an example:**

1. Create a table named `tbl1` that contains full-text indexes.

    ```sql
    CREATE TABLE tbl1 (
        col1 INT PRIMARY KEY,
        col2 INT,
        col3 VARCHAR(100),
        col4 VARCHAR(100),
        FULLTEXT INDEX ftidx3(col3),
        FULLTEXT INDEX ftidx4(col4)
    );
    ```

2. Use the `UNION_MERGE` hint to query the execution plan. Add the hint to the query statement to specify to use index merge for the full-text indexes `ftidx3` and `ftidx4` of the `tbl1` table.

    ```sql
    EXPLAIN SELECT /*+UNION_MERGE(tbl1 ftidx3 ftidx4)*/ * FROM tbl1
        WHERE col1 = 1 
        AND (MATCH(col3) AGAINST ("word1") OR MATCH(col4) AGAINST ("word1"));
    ```

    The return result is as follows:

    ```shell
    +----------------------------------------------------------------------------------------------------------------------------------------------------------------+
    | Query Plan                                                                                                                                                     |
    +----------------------------------------------------------------------------------------------------------------------------------------------------------------+

    | |ID|OPERATOR                    |NAME               |EST.ROWS|EST.TIME(us)|                                                                                    |

    | |0 |DISTRIBUTED INDEX MERGE SCAN|tbl1(ftidx3,ftidx4)|1       |45          |                                                                                    |

    |       = 1]), rowset=16                                                                                                                                         |
    ```
