# Optimizer Hint

The hint mechanism enables you to instruct the optimizer to generate a specific execution plan.

Typically, the optimizer selects the optimal execution plan for user queries without requiring explicit hints. However, in certain scenarios, the plan generated by the optimizer may not meet your requirements. In such cases, you can use hints to specify the desired execution plan.

## Syntax of hints

A hint is syntactically a special SQL comment, except that a "+" is added after the left marker ("/\*") in the comment. Since it is a comment, if the server cannot recognize a hint in an SQL statement, the optimizer will choose to ignore the user's hint and use the default plan generation logic to construct the logical structure. Furthermore, a hint only affects the logical structure of the plan generated by the optimizer, not the semantics of the SQL statement.

```sql
{ DELETE | INSERT | SELECT | UPDATE | REPLACE } /*+ [hint_text][,hint_text]... */
```

## QB_NAME parameter

In DML statements, each `query_block` has a `QB_NAME` (Query Block Name), which can be specified by the user or automatically generated by the system. If the user does not specify a `QB_NAME` using a hint, the system will generate it in the order of `SEL$1`, `SEL$2`, `UPD$1`, and `DEL$1` from left to right (which is also the parsing order of the resolver).

The `QB_NAME` can be used to precisely locate a table or to specify the behavior of any query block at a certain point. The `QB_NAME` in `TBL_NAME` is used to locate a table, and the first `QB_NAME` in a hint is used to specify which `query_block` the hint applies to.

## Rule for using hints

The general rules for using hints are as follows:

* A hint that does not specify a query block applies to the current query block.

  **Example 1: Since table `t2` is in query block 2 and cannot be promoted to query block 1 through rewriting, the hint does not take effect.**

## Common hints and syntax

Compared with the behavior of other databases, the optimizer in OceanBase Database is dynamic programming. It has considered all possible optimal paths. The main role of hints is to specify the behavior of the optimizer and execute SQL queries according to the hint.

### INDEX Hint

The syntax for the `INDEX` hint is supported in both MySQL-compatible mode and Oracle-compatible mode.

* The Oracle-compatible syntax for the `INDEX` hint is as follows:

```sql
SELECT/*+INDEX(table_name index_name) */ * FROM table_name;
```

* The MySQL-compatible syntax for the `INDEX` hint is as follows:

```sql
table_name [[AS] alias] [index_hint_list]

index_hint_list:
index_hint [, index_hint] ...

index_hint:
USE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] ([index_list])
  | IGNORE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] (index_list)
  | FORCE {INDEX|KEY}
  [FOR {JOIN|ORDER BY|GROUP BY}] (index_list)

index_list:
index_name [, index_name] ...
```

In the Oracle-compatible syntax, a table can specify only one `INDEX`, while in the MySQL-compatible syntax, multiple `INDEX`es can be specified. However, in OceanBase Database's MySQL-compatible mode, although specifying multiple `INDEX`es is supported, for the `USE` and `FORCE` methods, only the first `INDEX` is used to generate the `PATH`. This is because, according to the current design of OceanBase Database, the person who writes the hint understands better than the program which path is preferable. The `IGNORE` method ignores all specified `INDEX`es. The `USE`, `FORCE` methods, and the Oracle-compatible hint method are essentially the same. If the specified `INDEX` does not exist or is in an `invalid` state, the hint is invalid. For the `IGNORE` method, if all `INDEX`es, including those on the primary table, are ignored, the hint is invalid.

In an SQL statement, if a table name has an alias in the form `table_name [AS] alias`, the table alias must be written for the `INDEX` hint to take effect. Example:

### FULL Hint

The `FULL` hint is used to specify that a table should be scanned using the primary table scan method. The syntax is as follows:

```sql
/*+ FULL(table_name)*/
```

The `FULL` hint is used to select the primary table scan for a specified table, equivalent to the `INDEX` hint `/*+ INDEX(table_name PRIMARY)*/`.

### ORDERED Hint

The `ORDERED` hint can specify the join order based on the order of tables following `FROM`. The syntax is as follows:

```sql
 /*+ ORDERED */
```

If SQL rewriting occurs after this hint is specified, the join will be performed in the order of the From Items in the rewritten `stmt`, because during rewriting, the `sub_query` fills in new Table Items at the corresponding positions in the From Items.


### USE_MERGE Hint

`USE_MERGE` specifies to use the merge join algorithm when joining tables, with the specified table as the right table. The syntax is as follows:

```sql
 /*+ USE_MERGE(table_name_list) */
```

  <main id="notice" type='notice'>
    <h4>Note</h4>
    <p>In OceanBase Database, a merge join must have an equality condition in the <code>join-condition</code>. Therefore, for joining two tables without an equality condition, <code>use_merge</code> will be invalid.</p>
  </main>

There is currently no definitive conclusion on whether the merge join algorithm considers A Merge Join B equivalent to B Merge Join A. According to the cost model, the merge join algorithm distinguishes between the left and right tables when calculating costs, which also increases the flexibility of hints. Therefore, the current merge join distinction between left and right tables, that is, `use_merge`, only takes effect when a table serves as the right table.

### USE_NL Hint

The basic structure of a join-related hint is as follows:
`join_hint_name ( @ qb_name table_name_list)`
The basic semantics are that when the right table for the join matches table_name_list, the plan is generated according to the hint semantics. Generally, the `LEADING` hint is required to specify the join order, so that the tables in table_name_list are the right table; otherwise, the hint will become invalid as the join order changes.

table_name_list can be in the following forms:

* Single table use_nl ( t1 ): Uses nested loop join when t1 is the right table.
* Multiple single tables use_nl ( t1 t2 ... ): Uses nested loop join when t1 or t2, etc., is the right table.
* Multiple tables use_nl ( (t1 t2) ): Uses nested loop join when t1 join t2 is the right table, ignoring the join order and method of t1/t2.
* Multiple groups of tables use_nl ( t1 (t2 t3)  (t4 t5 t6) ... ): Uses nested loop join when t1 / t2 join t3 / t4 join t5 join t6, etc., are the right table.

`USE_NL` specifies a table as the right table, using the nested loop join algorithm during the join. The syntax is as follows:

```sql
/*+ USE_NL(table_name_list) */
```

### PARALLEL Hint

`PARALLEL` specifies the degree of parallelism at the statement level. The syntax is as follows:

```sql
/*+ PARALLEL(n) */
```

Here, `n` is an integer representing the degree of parallelism.

OceanBase Database also supports the `PARALLEL` hint at the table level. The syntax is as follows:

```sql
/*+ PARALLEL(table_name n) */
```

If both global and table-level parallelism are specified, the table-level parallelism hint will not take effect. Example:

```sql
obclient> CREATE TABLE tbl1 (col1 INT)  PARTITION BY HASH(col1) ;
```

### UNION_MERGE Hint

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p>The <code>UNION_MERGE</code> hint has been removed from OceanBase Database starting with version V4.4.1. Statements containing this hint are no longer supported.</p>
</main>

The `UNION_MERGE` hint specifies the execution method for index merge in a query plan. When a valid `UNION_MERGE` hint is provided, OceanBase Database directly selects the corresponding index merge plan.

The syntax is as follows:

```sql
/*+ UNION_MERGE(table_name index_name_list) */
```

Parameter description:

* `table_name`: The name of the table.
* `index_name_list`: A list of index names, separated by spaces.

**Example:**

1. Create a table `tbl1` with a full-text index.

    ```sql
    CREATE TABLE tbl1 (
        col1 INT PRIMARY KEY,
        col2 INT,
        col3 VARCHAR(100),
        col4 VARCHAR(100),
        FULLTEXT INDEX ftidx3(col3),
        FULLTEXT INDEX ftidx4(col4)
    );
    ```

2. Use the `UNION_MERGE` hint to view the execution plan. In the query, use the `UNION_MERGE` hint to specify table `tbl1` and indexes `ftidx3` and `ftidx4`.

    ```sql
    EXPLAIN SELECT /*+UNION_MERGE(tbl1 ftidx3 ftidx4)*/ * FROM tbl1
        WHERE col1 = 1
        AND (MATCH(col3) AGAINST ("word1") OR MATCH(col4) AGAINST ("word1"));
    ```

    The result description is as follows:

    * `DISTRIBUTED INDEX MERGE SCAN`: Indicates that index merge scanning is used in a distributed environment.
    * `is_index_back=true`: Indicates that a back-to-table operation is enabled.
    * `use_index_merge=true`: Indicates that index merge is enabled.
    * `filter_before_indexback[false,false]`: Indicates that the filter conditions were not applied before the back-to-table operation.

### PUSH_SUBQ Hint

The `PUSH_SUBQ` hint instructs the optimizer to execute subqueries that have not been rewritten as joins as early as possible. Typically, if not rewritten as joins, these subqueries would be evaluated after all table join calculations in the execution plan. If a subquery has a low computation cost and can filter out large amounts of data, executing it ahead of time may improve plan performance. Note that this hint becomes invalid if the subquery is rewritten as a join (`/+unnest/`). Applicable scenarios include:

* Subqueries have low execution overhead but can quickly filter out large amounts of data.
* You must use the results of subqueries as early as possible to narrow down the data range.

**The syntax is as follows:**

```sql
/*+ PUSH_SUBQ[(@qb_name)] */
```

Parameter description:

* `@qb_name`: Optional. Specifies an alias for the subquery (for more information, see **QB_NAME parameter** above). This helps the optimizer identify the object being hinted at. If omitted, the hint applies by default to the subquery where it is located.

**Example:**

Use the `PUSH_SUBQ` hint in a query to prompt the optimizer to execute the subquery early, thereby filtering data from the `tbl1` table in advance.

```sql
SELECT /*+ PUSH_SUBQ(@"SEL$2") */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```

### NO_PUSH_SUBQ Hint

The `NO PUSH_SUBQ` hint is the reverse operation of `PUSH_SUBQ`. It tells the optimizer to execute subqueries that have not been rewritten as joins last. This is useful when a subquery has a high cost or cannot significantly reduce the number of rows. Scenarios where this hint is applicable include:

* The subquery has a high execution cost, or its result has little impact on the data volume.
* You want to delay the execution of the subquery until other filtering conditions take effect, thereby reducing its input data volume.

**Syntax:**

```sql
/*+ NO_PUSH_SUBQ[(@qb_name)] */
```

Parameter description:

* `@qb_name`: Optional. Specifies an alias for the subquery.

**Example:**

Use the `NO PUSH_SUBQ` hint in a query to instruct the optimizer to defer the execution of the subquery until the end.

```sql
SELECT /*+ NO_PUSH_SUBQ */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```

### OPT_PARAM Hint

The `OPT_PARAM` hint is used to specify updates to some optimizer-related parameters/system variables at the query level.

**Syntax:**

```sql
/*+ OPT_PARAM(parameter_name [,] parameter_value) */
```

Parameter description:

* `parameter_name`: The name of the parameter or system variable.
* `parameter_value`: The value to be assigned to the variable.
The `OPT_PARAM` hint takes effect for the following parameters:
* `rowsets_enabled`: Enables/disables vectorization. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `rowsets_max_rows`: Sets the batch return row count `batch_size`. Data type: `INT`. Value range: `[0, 65535]`. Values cannot be enclosed in single quotes ('').
* `enable_newsort`: Allows/disables the newsort optimization in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `use_part_sort_mgb`: Allows/disables part sort merge group by in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `enable_in_range_optimization`: Allows/disables the in-range optimization in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `xsolapi_generate_with_clause`: Allows/disables CTE extraction rewriting in queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `preserve_order_for_pagination`: Adds `order by` to preserve order or prohibits adding `order by` for pagination queries. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `storage_card_estimation`: Whether to use storage layer row estimation. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `workarea_size_policy`: Sets the strategy for manually or automatically adjusting the SQL workarea size. Data type: `VARCHAR`. Valid values: `'MANUAL'` for manual adjustment and `'AUTO'` for automatic adjustment. Values must be enclosed in single quotes ('').
* `enable_rich_vector_format`: Enables/disables vectorization 2.0 (session-level parameter). Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes ('').
* `enable_skip_index`: Enables/disables skip index pruning in queries. Supported starting from V4.4.2 BP4. Data type: `VARCHAR`. Valid values: `'TRUE'` and `'FALSE'`. Values must be enclosed in single quotes (''). If not specified, it is enabled by default.
* `spill_compression_codec`: Specifies the compression algorithm for operators requiring temporary materialization. Data type: `VARCHAR`. Valid values: `NONE`, `LZ4`, `SNAPPY`, `ZLIB`, and `ZSTD`, representing different compression algorithms. Default is `NONE`, indicating no compression.
* `inlist_rewrite_threshold`: The threshold for the number of constants that can trigger rewriting from `INLIST` to a `VALUES` statement. Data type: `INT64`. Value range: `[1, 2147483647]`.
* `orc_filter_pushdown_level`: Indicates the pushdown level for statement-level ORC external table conditions. Valid values for `parameter_value` are as follows:

  * `0`: Disables pushdown of filter conditions.
  * `1`: Pushes down to the file level.
  * `2`: Pushes down to the stripe level.

  * `4`: Pushes down to the encoding level.

    ```sql

    WHERE c1 = 1;
    ```

  * Set the pushdown level for ORC conditions to the row index level.

    ```sql
    SELECT /*+opt_param('orc_filter_pushdown_level', '3') */ *
    FROM ext_orc_tbl
    WHERE c1 = 1;
    ```

  * Set the pushdown level for ORC conditions to the encoding level.

    ```sql
    SELECT /*+opt_param('orc_filter_pushdown_level', '4') */ * FROM ext_orc_tbl
    WHERE c1 = 1;
    ```

* Control the level to which Parquet external table conditions are pushed down at the statement level.

### INDEX_MERGE Hint

The `INDEX_MERGE` hint is used to control a specified table to use an index merge plan. If the specified index cannot generate an index merge plan, this hint is ignored. If no index is specified, it attempts to use an index merge plan whenever possible.

Using the `INDEX_MERGE` hint can generate an index merge plan when the value of the `_enable_index_merge` parameter is `False`.

**Syntax:**

```sql
/*+ INDEX_MERGE([@query_block_name] tbl_name [index_name [,index_name]...]) */
```

Parameter description:

* `@query_block_name`: Optional. Specifies the name of the query block affected by this hint. If omitted, it applies by default to the main query block of the current query.
* `tbl_name`: Specifies the table name.
* `index_name`: Optional. Specifies the index name. Multiple index names can be specified.

  * When the `index_name` parameter is not provided after the specified table, it controls the specified table to use an index merge plan.
  * When the `index_name` parameter is provided after the specified table, it controls the specified table to use the specified index to generate an index merge plan.

**Examples:**

* Specify an index name in the `INDEX_MERGE` hint.

    ```shell
    obclient> SELECT /*+ INDEX_MERGE(t1 idx_c2 idx_c3) */ * FROM t1
        WHERE c2 = 1
        AND c3 = 1
        AND c4 = 1;
    ```

* Do not specify an index name in the `INDEX_MERGE` hint.

    ```shell
    obclient> SELECT /*+ INDEX_MERGE(t1)*/ * FROM t1
        WHERE c2 = 1
        AND c3 = 1
        AND c4 = 1;
    ```

### NO_INDEX_MERGE Hint

The `NO_INDEX_MERGE` hint is used to control a specified table from generating an index merge plan using the specified index. If no index is specified, it prevents the table from generating an index merge plan.

When the `NO_INDEX_MERGE` hint conflicts with the `INDEX_MERGE` hint, both hints are ignored.

**Syntax:**

```sql
/*+ NO_INDEX_MERGE([@query_block_name] tbl_name [index_name [,index_name]...]) */
```

Parameter description:

* `@query_block_name`: Optional. Specifies the name of the query block for which this hint applies. If omitted, it applies by default to the main query block of the current query.
* `tbl_name`: Specifies the table name.
* `index_name`: Optional. Specifies the index name. Multiple index names can be specified.

  * When the `index_name` parameter is absent after the specified table, it means not to use the index merge plan.
  * When the `index_name` parameter is present after the specified table, it means not to use the specified index to generate the index merge plan.

**Example:**

```shell
obclient> SELECT /*+ NO_INDEX_MERGE(t1)*/ * FROM t1
    WHERE c2 = 1
    AND c3 = 1
    AND c4 = 1;
```
