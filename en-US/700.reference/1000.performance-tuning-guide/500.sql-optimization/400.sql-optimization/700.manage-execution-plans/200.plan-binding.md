# Plan binding

OceanBase Database uses the `CREATE OUTLINE` statement to bind an SQL statement to a specific execution plan, ensuring that the SQL always uses the specified plan in subsequent executions and avoiding performance fluctuations caused by improper optimizer choices. The `CREATE OUTLINE` statement supports the following plan binding modes:

* Exact binding: Binds an SQL statement to a specific execution plan on a one-to-one basis. This mode is suitable for single-database, single-table tuning scenarios.
* Template binding: Templates an outline using the `BINDING_RULE` clause, making it effective for multiple SQL statements that match the pattern (such as similar SQL statements in database or table sharding scenarios). This mode is suitable for database or table sharding, SaaS multi-tenancy, and other scenarios.

For existing services, if the plan selected by the optimizer is not optimal, you can perform plan binding online. This means you do not need to modify the SQL; instead, you use DDL operations to add a set of hints to the SQL. The optimizer then generates a better plan for the SQL based on these specified hints. This set of hints is called an outline.

## Outline view

The outline view is named `DBA_OB_OUTLINES`, and its columns are described in the following table.

| TENANT_ID | BIGINT(20) | NUMBER(38) | Tenant ID |
| DATABASE_ID | BIGINT(20) | NUMBER(38) | Database ID |
| OUTLINE_ID | BIGINT(20) | NUMBER(38) | Outline ID |
| DATABASE_NAME | VARCHAR2(128) | VARCHAR2(128) | Database Name |

## Precise binding

Precise binding is a native plan binding capability of OceanBase Database. It binds an SQL statement to a specific execution plan on a one-to-one basis using `SQL_TEXT` or `SQL_ID`. The behavior of an Outline row without `BINDING_RULE` is identical to previous versions.

### Create an Outline using SQL_TEXT

When you create an Outline using `SQL_TEXT`, a Key-Value pair is generated and stored in a Map. The Key is the parameterized text of the bound SQL, and the Value is the bound Hint. For specific parameterization principles, see [Quick parameterization](../../200.sql-execution-plan/200.fast-parameterization.md).

The syntax for creating an Outline using `SQL_TEXT` is as follows:

```sql
CREATE [OR REPLACE] OUTLINE <outline_name> ON <stmt> [ TO <target_stmt> ];
```

Explanation:

* Specifying `OR REPLACE` allows you to replace an existing execution plan.

* `stmt` is typically a DML statement with hints and original parameters.

* If `TO target_stmt` is not specified, it means that if the SQL passed to the database after parameterization matches the SQL in `stmt` without hints, this SQL will be bound to the execution plan generated by the hints in `stmt`.

  To ensure a fixed plan is executed for statements containing hints, you need `TO target_stmt` to specify the original SQL.

  Example:

  ```sql
  obclient> CREATE OUTLINE outline1 ON SELECT /*+NO_REWRITE*/ * FROM tbl1 WHERE col1 = 4
  AND col2 = 6 ORDER BY 2 TO SELECT  * FROM tbl1 WHERE col1 = 4 AND col2 = 6 ORDER BY 2;
  ```

  <main id="notice" type='notice'>
    <h4>Note</h4>
    <p>When using <code>target_stmt</code>, <code>stmt</code> and <code>target_stmt</code> must match exactly after removing hints.</p>
  </main>

In the following example, the optimizer chooses to perform a primary key scan. If the data volume increases, executing the index `idx_c2` would be a more optimized choice for this SQL. In this case, you can create an Outline to bind this SQL to the index plan and execute it.

```sql
obclient> CREATE TABLE t1 (c1 INT PRIMARY KEY, c2 INT, c3 INT, INDEX idx_c2(c2));
Query OK, 0 rows affected  

obclient> INSERT INTO t1 VALUES(1, 1, 1), (2, 2, 2), (3, 3, 3);
Query OK, 1 rows affected  

obclient> EXPLAIN SELECT * FROM t1 WHERE c2 = 1;

Query Plan:
===================================
|ID|OPERATOR  |NAME|EST. ROWS|COST|
-----------------------------------
|0 |TABLE SCAN|t1  |1        |37  |
===================================
Outputs & filters:
-------------------------------------
  0 - output([t1.c1], [t1.c2], [t1.c3]), filter([t1.c2 = 1]),
      access([t1.c2], [t1.c1], [t1.c3]), partitions(p0)
```

Create an Outline based on the following SQL statement:

```sql
obclient> CREATE OUTLINE otl_idx_c2
       ON SELECT/*+ INDEX(t1 idx_c2)*/ * FROM t1 WHERE c2 = 1;
Query OK, 0 rows affected
```

### Create an Outline using SQL_ID

The syntax for creating an Outline using `SQL_ID` is as follows:

```sql
obclient> CREATE OUTLINE outline_name ON sql_id USING HINT hint_text;
```

`SQL_ID` is the `SQL_ID` corresponding to the SQL statement to be bound. You can obtain it in the following ways:

* Query `V$OB_PLAN_CACHE_PLAN_STAT`.

* Query `GV$OB_SQL_AUDIT`.

* Generate an `SQL_ID` using MD5 for a parameterized original SQL statement. You can refer to the following script to generate the `SQL_ID` for the corresponding SQL.

  ```sql
  IMPORT hashlib
  sql_text='SELECT * FROM t1 WHERE c2 = ?'
  sql_id=hashlib.md5(sql_text.encode('utf-8')).hexdigest().upper()
  PRINT(sql_id)
  ```

Use the `SQL_ID` to bind an outline, as shown in the following example:

```sql
obclient> CREATE OUTLINE otl_idx_c2 ON 'ED570339F2C856BA96008A29EDF04C74'
USING HINT /*+ INDEX(t1 idx_c2)*/ ;
```

  <main id="notice" type='notice'>
    <h4>Notice</h4>
    <ul>
    <li>The hint format is <code>/*+ xxx */</code>. For detailed information about hints, see <a href="../700.manage-execution-plans/100.optimizer-hint.md">Optimizer Hint</a>.</li>
    <li>An outline created by using the <code>SQL_TEXT</code> method will overwrite an outline created by using the <code>SQL_ID</code> method. The <code>SQL_TEXT</code> method has a higher priority.</li>
    <li>If the SQL statement corresponding to <code>SQL_ID</code> already has hints, creating an outline with specified hints will overwrite all hints in the original statement.</li>
    </ul>
  </main>

## Template binding

Template binding is a new plan binding capability in OceanBase Database. It uses the `BINDING_RULE` clause to template an Outline, making it effective for multiple SQL statements that match the pattern. This is suitable for scenarios such as database and table sharding, or SaaS multi-tenancy, where data of the same model is distributed across multiple tables or databases.

### BINDING_RULE syntax

The syntax for creating a template Outline is as follows:

```sql
CREATE [OR REPLACE] OUTLINE outline_name ON stmt
    BINDING_RULE (binding_item);

binding_item:
    SCOPE = {DATABASE | TENANT}
    | MAP = {real_name TO 'pattern', ...}
```

The parameters are described as follows:

* `OR REPLACE`: Optional. When specified, existing execution plans will be replaced.
* `outline_name`: Specifies the name of the Outline to be created.
* `stmt`: Typically a DML statement with hints and original parameters.
* `BINDING_RULE (binding_item)`: Used to specify the scope of this Outline.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>For V4.4.2, the <code>BINDING_RULE</code> clause was introduced starting from V4.4.2 BP3.</p>
  </main>

  * `SCOPE = {DATABASE | TENANT}`:

    * `SCOPE = DATABASE`: The default value, meaning it only takes effect in the current database.
    * `SCOPE = TENANT`: Meaning it takes effect in all databases under the current tenant.

  * `MAP = {real_name TO 'pattern', ...}`: Specifies the wildcard rules for table names/database names. The left side is the actual table name or `db.table` format, and the right side is `pattern`. `pattern` can contain `${variable_name}` or `${variable_name:regex}`.

    <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p><ul>
      <li><code>${var}</code> or <code>${var:regex}</code>: Defines a variable named <code>var</code>, with an optional regular expression. If no regex is specified, it matches any non-empty string by default.</li>
      <li>When the left side of <code>MAP</code> is in the <code>db.table</code> format, the right-side <code>pattern</code> must be split into two groups of single quotes: <code>'db_pattern'.'table_pattern'</code>.</li>
      <li>In the same <code>BINDING_RULE</code>, variables must be defined before being referenced, and variables with the same name must have consistent values across all references.</li>
      </ul></p>
    </main>

### Four typical binding modes

| **Mode** | **SCOPE** | **MAP** | **Application scenarios** |
| ---------- | ----------- | --------- | -------------- |
| Exact binding | DATABASE (default) | empty | Single database and single table (original behavior) |
| Current Database Wildcard Sharded Table | DATABASE | Wildcard for Table Name Only | Within a single database`orders_001` … `orders_127`Partitioned tables |
| Cross-Database Exact Table Name | TENANT | empty | For tables with the same name across multiple databases, for example,`db_001.orders`、`db_002.orders` |
| Cross-database wildcard | TENANT | Including`db.table`wildcard | Compound wildcard for database name and table name |

### Cross-database binding for tables with the same name

In a database sharding architecture, there may be tables with the same name across multiple shards (for example, `db_001.orders` and `db_002.orders`). Using `SCOPE = TENANT` allows one Outline to cover all tables with the same name across all shards.

**Example:**

The `orders` table in all databases uses the `idx_status` index:

```shell
obclient> CREATE OUTLINE otl_orders
    ON SELECT /*+ index(orders, idx_status) */*
        FROM orders
        WHERE status = 'a'
    BINDING_RULE (SCOPE = TENANT);
```

* Example of a query hit in database `db_001`.

    ```shell
    obclient> USE db_001;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

* Example of a query hit in database `db_002`.

    ```shell
    obclient> USE db_002;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

* Example of a query hit in database `db_test`.

    ```shell
    obclient> USE db_test;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

### Wildcard for current database's sharded tables

In a sharded table architecture, a single database contains multiple sharded tables with a consistent naming pattern (for example, `orders_sh`, `orders_hz`, `orders_bj`). Using `MAP` with regular expression variables allows you to cover all sharded tables with a single outline.

**Example:**

The `orders_xx` series of sharded tables share the same outline:

```shell
obclient> CREATE OUTLINE otl_orders_tpl
    ON SELECT /*+ index(orders_sh, idx_status) */*
        FROM orders_sh
        WHERE status = 'a'
    BINDING_RULE (MAP = {orders_sh TO 'orders_${S:[a-z]+}'});
```

* Example of a query hit where `S=bj`.

    ```shell
    obclient> SELECT * FROM orders_bj WHERE status = 'pending';
    ```

* Example of a query hit where `S=hz`.

    ```shell
    obclient> SELECT * FROM orders_hz WHERE status = 'pending';
    ```

* Example of a non-hit query, as `001` does not match `[a-z]+`.

    ```shell
    obclient> SELECT * FROM orders_001 WHERE status = 'pending';
    ```

### Combined wildcard for database name and table name

In an architecture with combined database and table sharding (for example, `db_001.orders_sh`, `db_002.orders_bj`), you can use wildcards for both the database name and table name.

**Example:**

Effective only for databases in the `db_numeric` pattern + tables in the `orders_alpha` pattern:

```shell
obclient> CREATE OUTLINE otl_full
    ON SELECT *
        FROM db_001.orders_sh
        WHERE status = 'a'
    BINDING_RULE (
        SCOPE = TENANT,
        MAP = {db_001.orders_sh TO 'db_${D:[0-9]+}'.'orders_${S:[a-z]+}'}
        );
```

* Example of a hit query.

    ```shell
    obclient> SELECT *
        FROM db_002.orders_bj
        WHERE status = 'pending';
    ```

* Example of a miss query, where the database name does not match.

    ```shell
    obclient> SELECT *
        FROM test_db.orders_sh
        WHERE status = 'pending';
    ```

To cover all tables under a specific database, you can use the wildcard regular expression `${T:.*}`:

```shell
obclient> CREATE OUTLINE otl_db_all
    ON SELECT *
        FROM db_001.orders
        WHERE status = 'a'
    BINDING_RULE (
        SCOPE = TENANT,
        MAP = {db_001.orders TO 'db_${D:[0-9]+}'.'${T:.*}'}
        );
```

### Multi-table JOIN and variable consistency constraints

In multi-table `JOIN` scenarios, if all tables involved in the `JOIN` are sharded tables, you must ensure that the same variable has consistent values across all references to avoid incorrect table combination matching (for example, `orders_hz JOIN products_bj`).

Using the same variable name within the same `MAP` implements the consistency constraint.

**Example:**

The `S` in `orders_${S}` and `products_${S}` must be the same.

```shell
obclient> CREATE OUTLINE otl_join
    ON SELECT /*+ use_nl(orders_sh) */o.*, p.*
        FROM orders_sh o JOIN products_sh p
        ON o.id = p.order_id
    BINDING_RULE (
        MAP = {
            orders_sh TO 'orders_${S:[a-z]+}',
            products_sh TO 'products_${S}'
            }
        );
```

* Example of a hit query, where `S=hz`, `orders_hz JOIN products_hz`.

    ```shell
    obclient> SELECT o.*, p.*
        FROM orders_hz o JOIN products_hz p
        ON o.id = p.order_id;
    ```

* Example of a miss query, where `S=hz` for `orders` and `S=bj` for `products`. The variables are inconsistent, so the query automatically misses.

    ```shell
    obclient> SELECT o.*, p.*
        FROM orders_hz o JOIN products_bj p
        ON o.id = p.order_id;
    ```

## Scope and matching priority

### Scope

* `DATABASE` (default): The outline takes effect only in the current database. The database where the outline is created is the scope database.
* `TENANT`: The outline takes effect in all databases of the current tenant. You still need to execute `CREATE OUTLINE` in a certain database during creation, but the scope extends to the entire tenant.

### Matching priority

When the same SQL statement may match multiple outlines, OceanBase Database matches them in descending order of priority as follows:

1. Exact `signature` of the current database: exactly matches the parameterized text of the SQL statement.
2. `sql_id` of the current database: an outline created by `SQL_ID`.
3. `format outline`: an outline with `TO target_stmt`.
4. Current database template: a template outline with `SCOPE = DATABASE`.
5. Cross-database (tenant) template: a template outline with `SCOPE = TENANT`.

The current database template strictly takes precedence over the cross-database template, so ambiguity is avoided.

## Verify that an outline is created and takes effect

You must verify whether the created outline is successful and meets expectations. The verification methods for precise outlines and template outlines are slightly different.

### Verify a precise outline

To verify that a precise outline takes effect, perform the following three-step validation:

1. Confirm that the outline is successfully created.

   Check the `DBA_OB_OUTLINES` view to confirm whether the outline with the specified name has been successfully created.

   ```sql
   obclient> SELECT * FROM DBA_OB_OUTLINES WHERE OUTLINE_NAME = 'otl_idx_c2'\G

   *************************** 1. row ***************************
           tenant_id: 1001
         database_id: 1100611139404776
          outline_id: 1100611139404777
       database_name: test
        outline_name: otl_idx_c2
   visible_signature: SELECT * FROM t1 WHERE c2 = ?
            sql_text: SELECT/*+ index(t1 idx_c2)*/ * FROM t1 WHERE c2 = 1
      outline_target:
         outline_sql: SELECT /*+ BEGIN_OUTLINE_DATA INDEX(@"SEL$1" "test.t1"@"SEL$1" "idx_c2") END_OUTLINE_DATA*/*
   FROM t1 WHERE c2 = 1
   ```

2. Confirm that the new SQL generates a new execution plan using the bound outline.

   When executing a query with SQL bound to an outline, query the `outline_id` in the plan information corresponding to that SQL in the `GV$OB_PLAN_CACHE_PLAN_STAT` table. If the `outline_id` matches the `outline_id` found in `DBA_OB_OUTLINES`, it indicates the execution plan was generated according to the bound outline; otherwise, it was not.

   ```sql
   obclient> SELECT SQL_ID, PLAN_ID, STATEMENT, OUTLINE_ID, OUTLINE_DATA
         FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT
          WHERE STATEMENT LIKE '%SELECT * FROM t1 WHERE c2 =%'\G
   *************************** 1. row ***************************
         sql_id: ED570339F2C856BA96008A29EDF04C74
        plan_id: 17225
      statement: SELECT * FROM t1 WHERE c2 = ?
     outline_id: 1100611139404777
   outline_data: /*+ BEGIN_OUTLINE_DATA INDEX(@"SEL$1" "test.t1"@"SEL$1" "idx_c2") END_OUTLINE_DATA*/
   ```

3. Confirm that the generated execution plan meets expectations.

   After confirming the plan was generated by the bound outline, verify whether the generated plan meets expectations. You can query the `GV$OB_PLAN_CACHE_PLAN_EXPLAIN` table to check the shape of the cached execution plan in `plan_cache`. For specific viewing methods, refer to

   [Real-time execution plan display](../../200.sql-execution-plan/500.real-time-execution-plan-display.md).

   ```sql
   obclient> SELECT OPERATOR, NAME FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_EXPLAIN
         WHERE TENANT_ID = 1001 AND SVR_IP = '10.XXX.XXX.XXX'
          AND SVR_PORT = 30474 AND PLAN_ID = 17225;

   +--------------------+------------+
   | OPERATOR           | NAME       |
   +--------------------+------------+
   |  PHY_ROOT_TRANSMIT | NULL       |
   |   PHY_TABLE_SCAN   | t1(idx_c2) |
   +--------------------+------------+
   ```

### Verify a template outline

The verification method for a template outline is similar to that for a precise outline, but note the following points:

1. Confirm that the template outline is successfully created.

    Check the `pattern_rules` field in the `DBA_OB_OUTLINES` view to confirm whether it is a template outline. A non-empty `pattern_rules` field indicates it is a template outline. To view all template outlines:

    ```shell
    obclient> SELECT outline_name, visible_signature, pattern_rules
        FROM oceanbase.DBA_OB_OUTLINES
        WHERE pattern_rules IS NOT NULL
        AND pattern_rules != '';
    ```

2. Confirm whether the SQL hits the template outline.

    After a template outline is hit, the `outline_id` in `GV$OB_PLAN_CACHE_PLAN_STAT` will also be filled with the `ID` of the corresponding outline (`outline_id` greater than 0 indicates a hit). Query to check if it hit:

    ```shell
    obclient> SELECT outline_id, outline_data
        FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT
        WHERE query_sql LIKE '%your_marker%'
        LIMIT 1;
    ```

3. Multi-partition verification. For a template outline, it is recommended to use SQLs for different partitions to verify separately, ensuring all expected partitions correctly hit the template outline.

## Delete an outline

After deleting an outline, the corresponding SQL will no longer regenerate an execution plan based on the bound outline.

The syntax for dropping an outline is as follows:

```sql
DROP OUTLINE outline_name
    [BINDING_RULE (binding_item)];

binding_item:
    SCOPE = {DATABASE | TENANT}
```

The parameters are described as follows:

* `outline_name`: Specifies the name of the outline to be dropped.
* `BINDING_RULE (binding_item)`: Optional. Specifies the scope for dropping the outline.

  * `BINDING_RULE (SCOPE = DATABASE)`: The default value. Drops the outline at the current database level (equivalent to not specifying the `BINDING_RULE` parameter).
  * `BINDING_RULE (SCOPE = TENANT)`: Drops a cross-database (tenant-level) outline with the specified name.

  <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>For V4.4.2, the <code>BINDING_RULE</code> clause is introduced starting from V4.4.2 BP3.</p>
  </main>

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p><ul><li>To drop a precise outline (<code>SCOPE = DATABASE</code>), you must execute the statement in the corresponding database, or specify the database name in <code>outline_name</code>.</li><li>To drop a cross-database outline (<code>SCOPE = TENANT</code>), you can execute the statement in any database, but you must explicitly specify <code>BINDING_RULE(SCOPE = TENANT)</code>.</li></ul></p>
</main>

## Relationship between plan binding and execution plan caching

* After creating a precise outline using `SQL_TEXT`, the key used by SQL requests to find the outline when generating a new plan is the same as the key used by the plan cache, which is the parameterized text string of the SQL.
* Template outlines use a template signature for candidate filtering, then verify whether a match occurs through a regular expression pattern. The additional overhead during the template matching phase mainly comes from AST-level template signature generation and regular expression verification.
* When a precise outline is created or deleted, if the corresponding SQL receives a new request, it triggers the invalidation of the corresponding execution plan in the execution plan cache, updating it with the execution plan generated based on the bound outline.
* When a template outline is created or deleted, the plan caches for all SQL statements that match this template pattern become invalid.

* When an outline is created or deleted, if the corresponding SQL receives a new request, it triggers the invalidation of the corresponding execution plan in the execution plan cache, updating it with the execution plan generated based on the bound outline.

## Performance impact

| **Scenarios** | **Complexity** | **Note** |
| ---------- | ------------ | ---------- |
| No template outline found in the system. | O(1) | Via the `has_template_outline` short-circuit switch skips the template matching path, so tenants without a template outline incur no additional overhead. |
| Exact Outline Hit | O(1) | Reuses the original hash matching, so the performance of exact binding is not affected by the template binding feature. |
| Template outline matched | O(1) hash + n × O(T) pattern verification | `n`: the number of candidate templates with the same signature; `T`: the number of tables in the SQL statement. |
| Variable Consistency Verification | O(V) | `V`: the number of variables, typically ≤ 3. |

Regular expressions are limited in length (≤128 characters) and have a timeout mechanism to prevent pathological regular expressions from slowing down matching.

## Limitations and considerations

* When `MAP` contains `db.table` format, you must explicitly specify `SCOPE = TENANT`; otherwise, creation will fail.
* Within the same `BINDING_RULE`, each database name `pattern` and table name `pattern` can have at most one variable. Complex expressions should be split into multiple outlines.
* Variables must be defined before being referenced. A variable with the same name can only be defined once.
* The `db.*` syntax is not supported. Please use equivalent expressions such as `'db_${D:[0-9]+}'.'${T:.*}'`.
* Regular expressions use POSIX extended syntax and do not support complex features such as backreferences or zero-width assertions.
* Outlines with only `SCOPE = DATABASE` and no `MAP` behave exactly the same, equivalent to historical precise outlines.
* The `MAX_CONCURRENT` throttling type outlines currently do not support `BINDING_RULE`.
* Cross-tenant outline binding is not supported.
