# What's New

OceanBase Database V4.3.5 is the first LTS version for AP scenarios. Building on V4.3.4, the new version enhances product capabilities by introducing support for nested materialized views, improving full-text indexing and vector indexing features, and boosting data import and export capabilities through enabling direct load for specific partitions, allowing external tables to read files in the ORC format, and enabling the SELECT INTO OUTFILE statement to export data in the Parquet and ORC formats. Regarding optimizer capabilities, it evolves SPM based on baseline priority strategies, improves the optimizer's row estimation system, optimizes the inline cost verification of recursive common table expressions (CTEs), and enhances query range extraction capability.

In terms of compatibility, OceanBase Database enhances support for the XA transaction feature in MySQL tenants and refines the Latin1 character set in these tenants, and supports complex parameter types for remote procedure calls between Oracle tenants, facilitating smooth migration between Oracle and MySQL businesses, as well as between Oracle and PL/SQL applications.

In terms of performance optimization, V4.3.5 optimizes restore performance at the table level, import performance at the bypass level, DML performance, and DDL performance. The new version also introduces online conversion between row-based storage and columnar storage, support for quick intermediate column addition, and extended parallel DDL operations. To improve resource isolation, the update integrates statistics and clog log submission into resource isolation mechanisms and extends this isolation to the I/O layer. Additionally, the new version limits memory usage at the SQL statement level, optimizes memory usage in stored procedures, and reduces a tenant's memory resources consumption through a shared thread pool, enhancing stability in various scenarios. In terms of usability, it enhances diagnostic capabilities for ASH and WR, optimizes log stream replica parallel migration, and improves observability of the log synchronization link by adding monitoring views of log transmission links. These enhancements make OceanBase Database more user-friendly. The new version supports more ARRAY and XML expression scenarios and optimizes memory usage during the execution of JSON, XML, and GIS data types. It also enhances compatibility with OBKV and HBase and monitors the P95 and P99 metrics of OBKV.

This topic describes the key features and major performance improvements of OceanBase Database V4.3.5.

## Key features

* **Support for nested materialized views**

    In versions prior to V4.3.5, only materialized views could be built on regular user tables. In data warehouse scenarios, materialized views are used for data processing. To support lightweight real-time data warehouses, V4.3.5 allows you to create a nested materialized view based on an existing one. Nested materialized views support the same refresh methods as non-nested materialized views, including complete refreshes and incremental refreshes. Therefore, V4.3.5 supports Clogs for materialized views. The data freshness of a nested materialized view is related to that of its base tables. To ensure the freshness of data in upper-level materialized views, users must refresh the underlying materialized views first.

    For more information, see [Create a materialized view (MySQL mode)](700.reference/300.database-object-management/100.manage-object-of-mysql-mode/600.manage-views-of-mysql-mode/200.manage-materialized-views-of-mysql-mode/300.create-materialized-views-of-mysql-mode.md) or [Create a materialized view (Oracle mode)](700.reference/300.database-object-management/200.manage-object-of-oracle-mode/500.manage-views-of-oracle-mode/200.manage-materialized-views-of-oracle-mode/300.create-materialized-views-of-oracle-mode.md).

* **Support for specifying partitions to bypass import**

    V4.3.5 allows you to specify partitions in the `LOAD DATA` and `INSERT INTO SELECT` statements to perform direct load. However, you cannot specify partitions whose last-level partitioning type is hash or key.

    For more information, see [Full direct load](500.data-migration/1100.bypass-import/200.full-bypass-import.md) or [Incremental direct load](500.data-migration/1100.bypass-import/300.incremental-bypass-import.md).

* **Enhanced full-text index functionality**

    V4.3.5 continuously enhances the full-text index functionality, including:

    * Allowing you to create full-text indexes by using the `CREATE FULLTEXT INDEX` or `ALTER TABLE ADD FULLTEXT INDEX` statement.
    * Supporting cost-based full-text index plan selection. For an SQL query with multiple filters (including the `MATCH AGAINST` clause), a less costly index is selected for scan.
    * Supporting functional lookup:

      * Allowing multiple `MATCH AGAINST` clauses in a query statement.
      * Allowing other indexes to be used simultaneously with a full-text index.
      * Allowing the `MATCH AGAINST` clause to be used as a projection column without filter semantics.
      * Filtering results by using symbols like <= and < when filter semantics are applied to the `MATCH AGAINST` clause.
      * Linking multiple filters with AND or OR, where the filters have filter semantics or are the `MATCH AGAINST` clause.

    For more information, see [MATCH AGAINST](700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/400.functions-of-mysql-mode/1000.other-functions-of-mysql-mode/2250.match-against-of-mysql-mode.md).

* **Enhanced SELECT INTO OUTFILE functionality**

    V4.3.5 enhances the `SELECT INTO` export functionality, supporting the export of Parquet and ORC files by using `SELECT INTO`, specifying a compression algorithm when exporting CSV files by using `SELECT INTO`, and introducing new syntaxes for `SELECT INTO`.

    * Using the format syntax to set export options.
    * Specifying a compression algorithm when exporting CSV files.
    * Exporting Parquet files.
    * Exporting ORC files.

    For more information, see [Export data by using the OUTFILE statement](500.data-migration/1000.use-sql-statements-migrate-data/300.use-outfile-statements-to-migrate-data.md).

* **External tables**

    In V4.3.5, external tables can read ORC files.

    For more information, see [Create an external table (MySQL mode)](300.develop/100.application-development-of-mysql-mode/300.database-object-planning-of-mysql-mode/500.create-external-table-in-develop-of-mysql-mode.md) or [Create an external table (Oracle mode)](300.develop/200.application-development-of-oracle-mode/300.database-object-planning-of-oracle-mode/400.create-external-table-in-develop-of-oracle-mode.md).

* **Online quick add columns**

    For MySQL compatibility, V4.3.5 changes the DDL operation for intermediate column addition from offline DDL to online DDL, enhancing the performance of intermediate column addition. It supports both online `ADD COLUMN` and the combination of online `ADD COLUMN` and `MODIFY COLUMN`.

### Performance improvement

* **Asynchronous online DDL supported for row-to-column conversion**

    V4.3.0 introduced support for three storage formats: row-based, columnar, and hybrid row-column. Offline DDL is required for converting a rowstore table into a hybrid row-column table or a columnstore table, which may impact customers. To address this, V4.3.5 introduced asynchronous online DDL for converting rowstore tables into columnstore tables. Users can specify the `delayed` keyword when executing DDL statements to real-time modify the schema of tables without blocking data writes. Additionally, baseline data reorganization for columnar storage is performed asynchronously during baseline data merge. V4.3.5 now supports online DDL for converting rowstore tables into columnstore tables and hybrid row-column tables.

    For more information, see [Online DDL and Offline DDL operations](700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) and [Modify table settings](700.reference/300.database-object-management/100.manage-object-of-mysql-mode/200.manage-tables-of-mysql-mode/600.change-table-of-mysql-mode.md).

* **Vectorization enabled for direct load**

    Prior to V4.3.5, direct load implementation did not involve vectorization, and functions were processed row by row by write functions, resulting in high function call overheads. In addition, the process of writing SSTables was performed in the background without targeted optimization. V4.3.5 vectorizes the direct load path and optimizes columnar storage encoding, thereby improving the performance of direct load. Tests show that the direct load performance of columnstore tables without primary keys has been improved by about 2 times.

#### Reliability improvement

* **Backup supported for parameters and tenant resources**

    V4.3.5 introduces support for backing up cluster-level and tenant-level parameters. Cluster-level parameters can be backed up by specifying the path information in the `ALTER SYSTEM` statement. Tenant-level parameters are included in backup datasets and backed up together with data. When performing physical restore for a tenant, we recommend that you back up the resource configurations and replica distribution of the target tenant to the same specifications as the source tenant to ensure the success rate of physical restore and stability of subsequent business operations. V4.3.5 also allows you to back up the resource configurations of a tenant.

#### Security enhancement

* Full support for Rocky Linux 9.

### Usability improvement

* **Optimization of parallel migration of log stream replicas**

    Starting from V4.3.5, replicas of a log stream can be migrated in parallel to different zones. This can accelerate scaling operations, improve load balancing efficiency, and reduce the probability of replica rebuild in standby databases. However, the primary and standby tenants have different requirements for the parallel migration of log stream replicas: The primary tenant mainly uses this feature in PoC scenarios to accelerate scaling operations. In regular use, parallel migration may not be enabled because multiple replicas are migrated simultaneously, resulting in a large amount of data copied, which can affect the I/O performance of the primary replica. The standby database has a strong requirement for parallel migration. This feature can effectively reduce the probability of replica rebuild in the standby database. The tenant-level parameter `replica_parallel_migration_mode` controls the parallel migration of log stream replicas.

    For more information, see [replica_parallel_migration_mode](700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7330.replica_parallel_migration_mode.md).

#### OBKV/Multimodel

* **Json multi-valued indexes support complex DML statements**

    V4.3.5 enhances the support for complex DML statements by Json multi-valued indexes. Multi-valued predicates are supported in statements such as `UPDATE` and `DELETE`, and complex DML statements involving table access with multi-valued index lookup are supported.

* **Support for more ARRAY expressions**
    OceanBase Database supported the `ARRAY` data type in V4.3.3. To better support business applications involving the `ARRAY` type, V4.3.5 introduces support for more `ARRAY` expressions, catering to diverse business scenarios. The new version adds support for the expressions `array_append`, `array_distinct`, `arrayMap`, `array_remove`, `cardinality`, `element_at`, `array_contains_all`, `array_overlaps`, `array_to_string`, `array_to_string`, `array_agg`, `unnest`, and `rb_build`.

    For more information, see [Overview of array functions](700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/400.functions-of-mysql-mode/950.array-functions-of-mysql-mode/100.array-functions-overview-of-mysql-mode.md).

* **Enhanced vector index functionality**
    Besides enhancing the stability of existing vector index features, V4.3.5 increases the maximum vector dimension supported by vector indexes from 2,000 to 4,096 and introduces support for the cosine distance algorithm. Users can specify the cosine distance algorithm when creating or enabling vector indexes on tables, and use the `cosine_distance` expression as a filter condition in `SELECT` statements.

* **Compatibility enhancements for OBKV-HBase**

    OceanBase Database enhances compatibility with HBase 1.x/2.x in V4.3.5, including support for multiple namespaces, /ColumnRangeFilter/, /ColumnValueFilter/, /CheckAndMutateBuilder/, hybrid batch, and CheckAndMutateBuilder.

* **Histogram of OBKV response time**

    Building on the response time histogram feature introduced in V4.3.4, the new version adds OBKV-related statistics categories to the `[G]V$OB_QUERY_RESPONSE_TIME_HISTOGRAM` view. The categories are `TABLEAPI SELECT`, `TABLEAPI INSERT`, `TABLEAPI DELETE`, `TABLEAPI UPDATE`, `TABLEAPI REPLACE`, `TABLEAPI QUERY AND MUTATE`, `TABLEAPI OTHER`, `HBASE SCAN`, `HBASE PUT`, `HBASE DELETE`, `HBASE APPEND`, `HBASE INCREMENT`, `HBASE CHECK AND PUT`, `HBASE CHECK AND DELETE`, and `HBASE HYBRID BATCH`.
