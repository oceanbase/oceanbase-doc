# Non-optimal plan

The execution of an SQL statement goes through two phases: compilation and execution. In the compilation phase, the optimizer performs operations such as lexical analysis, syntax analysis, syntax optimization, and code generation to generate an execution plan. The plan is then submitted to the executor for execution, which returns the results. The process of parsing an SQL statement and generating an execution plan is called hard parsing. Hard parsing consumes resources and increases SQL latency. To avoid the overhead of hard parsing for each request, execution plans are cached in the plan cache. When the optimizer receives a subsequent SQL statement of the same type, it first checks the plan cache for a matching plan. If a matching plan is found in the cache, it is retrieved and submitted to the executor for execution, which returns the results. This process is called soft parsing. Therefore, whether an execution plan is cached in the plan cache and whether the plan is optimal are key factors in performance optimization.

![plan](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.1/manage/tuning-sql-new.png)

The optimizer may generate non-optimal execution plans due to various reasons, such as missing indexes, outdated statistics, and account privileges. Non-optimal execution plans lead to a high number of logical reads and large amounts of scanned data, which increases latency and reduces throughput.

You can determine whether a performance issue is an SQL issue and identify suspicious SQL statements by querying the `V$OB_SQL_AUDIT` view. You can then determine whether there is an issue with the execution plan by querying the relevant plan views. If the execution plan is suboptimal, you can bind it to a SQL statement by using the `CREATE OUTLINE` statement or recover from the suboptimal plan by scaling up or throttling back.
