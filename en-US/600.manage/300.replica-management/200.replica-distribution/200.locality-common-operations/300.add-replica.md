# Add a replica

This topic describes how to add a replica of a log stream in a tenant.

## Add replicas by modifying the locality

You can add replicas for a tenant by modifying the locality of the tenant in a cluster. For more information about how to modify the locality, see [Modify the locality](../200.locality-common-operations/200.modify-locality.md).

### Prerequisites

Before you add replicas, make sure that the tenant has a resource pool in the target zone. If not, you need to adjust the zone list of the existing resource pool or add a new resource pool for the tenant. If you add a new resource pool, the number of units in the new resource pool must be the same as that in the existing resource pool. For more information about how to modify the resource pool properties or create a resource pool, see [Modify the resource pool properties](../../../200.tenant-management/600.common-tenant-operations/900.modify-resource-pool-properties.md) or [Create a resource pool](../../../200.tenant-management/600.common-tenant-operations/200.manage-create-tenant.md).

You also need to check the resource allocation of nodes in the zone to be modified. If the nodes in the zone do not have enough resources to accommodate the required resource units, the locality modification will fail.

For information about the resource allocation of nodes in a zone, see [View tenant and resource information](../../../200.tenant-management/600.common-tenant-operations/400.view-tenant-information.md).

### Considerations

* The locality of a tenant cannot be empty.

* When the locality of a tenant changes, the replica distribution of all tables in the tenant will also change.

* If the previous round of locality modification for the tenant is not completed, the new round of modification cannot be executed.

* Only one action can be executed at a time when you modify the locality. For example, you cannot directly replace Zone3 with Zone4. Instead, you can first add Zone4 and then remove Zone3.

* Pay attention to the impact on the primary zone when you modify the locality. We recommend that you adjust the primary zone in advance.

  For example:

    1. If you need to reduce the number of replicas in Zone3, and Zone3 is the primary zone with the highest priority, the adjustment of the locality will affect the read and write services of the tenant.

    2. If the primary zone is set to RANDOM, the new zone4 will also provide read and write services.

### Procedure

Example: Modify the locality of the `mysql001` tenant from `FULL{1}@zone1, FULL{1}@zone2` to `FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3`, adding a replica in zone3.

<main id="notice" type='explain'>
<h4>Note</h4>
<p>This example only adds one zone. In practice, make sure that the number of added zones meets the majority principle. </p>
</main>

1. Log in to the sys tenant of the cluster as the root user.

   ```shell
   obclient -h172.30.xxx.xxx -P2883 -uroot@sys#obdemo -pxxxx -A
   ```

2. Enter the `oceanbase` database.

   ```shell
   obclient(root@sys)[(none)]> USE oceanbase;
   ```

3. Query the current locality of the `mysql001` tenant.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, PRIMARY_ZONE, LOCALITY FROM oceanbase.DBA_OB_TENANTS;
   ```

   The query result is as follows:

   ```shell
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE      | LOCALITY                                    |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   |         1 | sys         | SYS         | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1001 | META$1002   | META        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2                |
   |      1002 | mysql001    | USER        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2                |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   3 rows in set
   ```

   You can see that the `mysql001` tenant has one full-featured replica in zone1 and one full-featured replica in zone2.

4. Modify the locality of the `mysql001` tenant.

   ```shell
   obclient(root@sys)[oceanbase]> ALTER TENANT mysql001 locality="FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3";
   ```

5. Query the execution status of the locality modification task.

    ```shell
    obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_TENANT_JOBS WHERE JOB_TYPE = 'ALTER_TENANT_LOCALITY';
    ```

    The query result is as follows:

    ```shell
    +--------+-----------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+------------------------------------------------------------------------------+---------------------------------------------+----------------+-------------+
    | JOB_ID | JOB_TYPE              | JOB_STATUS | RESULT_CODE | PROGRESS | START_TIME                 | MODIFY_TIME                | TENANT_ID | SQL_TEXT                                                                     | EXTRA_INFO                                  | RS_SVR_IP      | RS_SVR_PORT |
    +--------+-----------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+------------------------------------------------------------------------------+---------------------------------------------+----------------+-------------+
    |      1 | ALTER_TENANT_LOCALITY | SUCCESS    |        NULL |        0 | 2023-01-05 19:38:38.416011 | 2023-01-05 19:38:38.416011 |      1002 | ALTER TENANT mysql001 locality='FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3' | FULL{1}@zone1, FULL{1}@zone2                | xx.xx.xx.237 |        2882 |
    +--------+-----------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+------------------------------------------------------------------------------+---------------------------------------------+----------------+-------------+
    1 row in set
    ```

    If the value of `JOB_STATUS` is `SUCCESS`, the locality modification task is executed successfully.

6. Query the updated locality of the `mysql001` tenant.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, PRIMARY_ZONE, LOCALITY FROM oceanbase.DBA_OB_TENANTS;
   ```

   The query result is as follows:

   ```shell
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE      | LOCALITY                                    |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   |         1 | sys         | SYS         | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1001 | META$1002   | META        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1002 | mysql001    | USER        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   3 rows in set
   ```

   By comparing the query results in step 3 and step 6, you can see that the locality of the `mysql001` tenant has changed from `FULL{1}@zone1, FULL{1}@zone2` to `FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3`. The `mysql001` tenant now has one full-featured replica in zone1, one full-featured replica in zone2, and one full-featured replica in zone3.

If the added zone participates in the leader election, you need to modify the primary zone. For more information, see [Adjust the primary zone](../../../200.tenant-management/600.common-tenant-operations/800.tenant-scale-in-and-out/400.adjust-primary-zone.md). If the added zone does not participate in the leader election, you do not need to modify the primary zone.

## Manually add a replica

When you modify the locality to add a replica, the system usually automatically adds the missing replicas. However, if the system does not work properly due to some exceptions, you can manually add the missing log stream replicas by using the `ALTER SYSTEM ADD REPLICA` command.

### Limitations

* Only the sys tenant can add replicas to the log streams of all tenants. User tenants can only add replicas to their own log streams.

* For the same log stream of a tenant, only one disaster recovery task (including adding, deleting, converting, and modifying replicas) can be executed at a time, except for replica migration tasks, which can be executed in parallel.

   The sys tenant can check the `CDB_OB_LS_REPLICA_TASKS` view to confirm if a disaster recovery task is running. User tenants can check the `DBA_OB_LS_REPLICA_TASKS` view for the same purpose.

### Prerequisites

* Before you execute the `ALTER SYSTEM ADD REPLICA` command, make sure that the current user has the `ALTER SYSTEM` privilege.

* Before you query a view, make sure that the current user has the `SELECT` privilege on the view.

  * `DBA_OB_TENANTS`

  * `DBA_OB_LS`/`CDB_OB_LS`

  * `GV$OB_UNITS`

  * `DBA_OB_LS_LOCATIONS`/`CDB_OB_LS_LOCATIONS`

* Before you execute the `ALTER SYSTEM ADD REPLICA` command, make sure that the target server has available resources (units) for the user and that the unit does not have a replica of the log stream.

### Procedure

Assume that you have a tenant named tenant1 with the Locality value `F@zone1,F@zone2,F@zone3`. The tenant has one F-type replica of log stream 1001 in each of zone1 and zone3, but no replica in zone2. Now, you need to manually add an F-type replica of log stream 1001 in zone2.

1. Log in to the cluster as the tenant.

    Here is an example:

    ```shell
    obclient -h172.30.xxx.xxx -P2883 -uroot@tenant1#obdemo -pxxxx -A
    ```

    For more information about how to connect to the database, see [Overview of database connection methods (MySQL mode)](../../../../300.develop/100.application-development-of-mysql-mode/100.connect-to-oceanbase-database-of-mysql-mode/100.connection-methods-overview-of-mysql-mode.md) and [Overview of database connection methods (Oracle mode)](../../../../300.develop/200.application-development-of-oracle-mode/100.connect-to-oceanbase-database-of-oracle-mode/100.connection-methods-overview-of-oracle-mode.md).

      ```shell
      obclient(root@sys)[oceanbase]> SELECT TENANT_NAME,TENANT_ID,LOCALITY FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME='tenant1';
      ```

    * User tenant

      :::tab
      tab MySQL mode

      Execute the following statement in MySQL mode:

      ```shell
       obclient(root@tenant1)[oceanbase]> SELECT TENANT_NAME,TENANT_ID,LOCALITY FROM oceanbase.DBA_OB_TENANTS;
      ```

      tab Oracle mode

      Execute the following statement in Oracle mode:

      ```shell
      obclient(SYS@tenant1)[SYS]> SELECT TENANT_NAME,TENANT_ID,LOCALITY FROM SYS.DBA_OB_TENANTS;
      ```

      :::

      Here is an example of the query result:

      ```shell
      +-------------+-----------+---------------------------------------------+
      | TENANT_NAME | TENANT_ID | LOCALITY                                    |
      +-------------+-----------+---------------------------------------------+
      ```

    * User tenant

      :::tab
      tab MySQL mode

      Execute the following statement in MySQL mode:

      ```shell
       obclient(root@tenant1)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_LS;
      ```

      tab Oracle mode

      Execute the following statement in Oracle mode:

      ```shell
      obclient(SYS@tenant1)[SYS]> SELECT * FROM SYS.DBA_OB_LS;
      ```

      :::

      ```shell
      +-------+--------+-------------------+---------------+-------------+---------------------+----------+---------------------+---------------------+------+----------------+
      | LS_ID | STATUS | PRIMARY_ZONE      | UNIT_GROUP_ID | LS_GROUP_ID | CREATE_SCN          | DROP_SCN | SYNC_SCN            | READABLE_SCN        | FLAG | UNIT_LIST      |
      ```


      tab Oracle mode

      Execute the following statement in Oracle mode:

      ```shell
      obclient(SYS@tenant1)[SYS]> SELECT SVR_IP, SVR_PORT, UNIT_ID, TENANT_ID, ZONE, ZONE_TYPE, STATUS FROM SYS.GV$OB_UNITS;
      ```

      :::

      Here is an example of the query result:

      ```shell
      +----------------+----------+---------+-----------+-------+-----------+--------+
      | SVR_IP         | SVR_PORT | UNIT_ID | TENANT_ID | ZONE  | ZONE_TYPE | STATUS |
      ```

      For more information about the fields in the `DBA_OB_LS_LOCATIONS` view, see [DBA_OB_LS_LOCATIONS](../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/4400.oceanbase-dba_ob_ls_locations-of-mysql-mode.md).

6. Execute the add-replica command.

   The SQL statement is as follows:

   ```sql
   ALTER SYSTEM ADD REPLICA LS [=] ls_id SERVER [=] 'svr_ip:svr_port' REPLICA_TYPE [=] 'replica_type' [DATA_SOURCE [=] 'data_source'] [PAXOS_REPLICA_NUM [=] paxos_replica_num] [TENANT [=] 'tenant_name'];
   ```

   The statement is used as follows:

   * `ls_id`: specifies the log stream ID of the replica to be added.

   * `svr_ip:svr_port`: specifies the IP address and port number of the target server for the replica to be added. Example: `172.xx.xxx.212:2882`.

   * `replica_type`: specifies the type of the replica to be added. The following replica types are supported:

     * Full-featured replica: specified by `FULL` or `F`.

     * Read-only replica: specified by `READONLY` or `R`.

     * Columnstore replica: specified by `COLUMNSTORE` or `C`.

   * `data_source`: specifies the data source address of the replica to be added. Example: `172.xx.xxx.192:2882`.

      If the specified data source is unavailable, an error is returned.

      If this parameter is not explicitly specified, the system automatically selects an available data source.

   * `paxos_replica_num`: specifies the number of quorum members for the log stream after modification, which is the number of full-featured (F) replicas in the tenant locality. A log stream can have at most 7 F replicas.

      When you specify this parameter, the following conditions must be met:

      1. After modification, `paxos_replica_num` must satisfy the majority requirement.

      2. The value of `paxos_replica_num` must be greater than or equal to the number of members in the `MEMBER_LIST` of the current leader replica.

      3. The absolute value of the change in `paxos_replica_num` must not exceed 1. For example, if the current `paxos_replica_num` is `2`, you can only change it to `3`.

      If any of the above conditions are not met, an error is returned. If this parameter is not explicitly specified, the system uses the default value of `paxos_replica_num`.

   * `tenant_name`: specifies the tenant to be operated on. The system tenant can specify other tenants, while a user tenant can only specify itself. If the tenant to be operated on is not explicitly specified, the default tenant is the current tenant. This statement does not support using `all`, `all_user`, or `all_meta` to specify all tenants, user tenants, or all Meta tenants.

   * This statement can only add one replica at a time. If you need to add multiple replicas, you must execute this statement multiple times.

   Here is an example:

   ```shell
   obclient> ALTER SYSTEM ADD REPLICA LS= 1001 SERVER='172.xx.xxx.212:2882' REPLICA_TYPE='F' DATA_SOURCE='172.xx.xxx.192:2882' PAXOS_REPLICA_NUM=3;
   ```

7. Query the log stream information again. You can see that an F replica has been added to the log stream.

    * System tenant

      ```shell
      obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_LS_LOCATIONS WHERE LS_ID=1001 AND TENANT_ID=1002;
      ```


      :::

      ```shell
      | CREATE_TIME                | MODIFY_TIME                | LS_ID | SVR_IP         | SVR_PORT | SQL_PORT | ZONE  | ROLE     | MEMBER_LIST                                                                                     | PAXOS_REPLICA_NUMBER | REPLICA_TYPE | LEARNER_LIST | REBUILD |
      +----------------------------+----------------------------+-------+----------------+----------+----------+-------+----------+-------------------------------------------------------------------------------------------------+----------------------+--------------+--------------+---------+
      | 2024-04-03 17:23:06.381521 | 2024-04-03 17:48:08.982791 |  1001 | 172.xx.xxx.192 |     2882 |     2881 | zone3 | FOLLOWER | NULL                                                                                            |                 NULL | FULL         |              | FALSE   |
      | 2024-04-03 17:48:05.812041 | 2024-04-03 17:48:09.985574 |  1001 | 172.xx.xxx.212 |     2882 |     2881 | zone2 | FOLLOWER | NULL                                                                                            |                 NULL | FULL         |              | FALSE   |
      | 2024-04-01 14:12:08.589084 | 2024-04-03 17:48:09.030020 |  1001 | 172.xx.xxx.226 |     2882 |     2881 | zone1 | LEADER   | 172.xx.xxx.192:2882:1712136186291857,172.xx.xxx.212:2882:1712137685774460,172.xx.xxx.226:2882:1 |                    3 | FULL         |              | FALSE   |
      ```
