# Data distribution

Data partitions are logical objects created based on the create table statement. They are used to divide and manage table data. Each tenant consists of multiple units. Log streams are distributed to these units based on certain rules, which determines the distribution of data partitions associated with the log streams across the units. This section explains the rules for the distribution of data and traffic.

OceanBase Database supports ordinary tables and partitioned tables. Partitioned tables can be further divided into subpartitioned tables and partitioned tables. A partitioned table consists of one or more partitions. An ordinary table is a special case of a partitioned table and consists of a single partition. OceanBase Database supports the following basic partitioning strategies: range partitioning, list partitioning, hash partitioning, and key partitioning.

## Unit Group

OceanBase Database V4.0 introduces restrictions on tenant management, requiring that all zones have the same number of units. The system numbers the units in each zone, and units with the same number (`UNIT_GROUP_ID`) across different zones form a unit group. Unit groups have the following characteristics:

* Each unit group is assigned a unique ID. This ID can be viewed in the `oceanbase.DBA_OB_UNITS` view of the sys tenant through the `UNIT_GROUP_ID` field.

* A single log stream belongs to only one unit group and is distributed across the units within that unit group. As a result, the same data partitions are distributed across all units in the unit group, based on the log stream, forming a consistent data set. This also requires that all zones have equivalent service capabilities.

* Starting from V4.0, OceanBase Database no longer supports configuring the number of units for a tenant on a per-zone basis; instead, adjustments must be made at the unit group level. For example, if you need to horizontally scale up the resources for a tenant, you must uniformly increase the number of units across all zones. Conversely, when scaling down, units must be removed by unit group. The unit group mechanism ensures consistent data distribution across different zones.

In the `sys` tenant, you can query all units and their corresponding unit groups using the `oceanbase.DBA_OB_UNITS` view. Example:

```shell
obclient> select UNIT_ID,TENANT_ID,UNIT_GROUP_ID,ZONE,SVR_IP,SVR_PORT from DBA_OB_UNITS where TENANT_ID = 1004;
+---------+-----------+---------------+--------------+-------------+----------+
| UNIT_ID | TENANT_ID | UNIT_GROUP_ID | ZONE         | SVR_IP      | SVR_PORT |
+---------+-----------+---------------+--------------+-------------+----------+
|    1004 |      1004 |          1003 | sa128_obv4_1 | xx.xx.xx.47 |     2882 |
|    1005 |      1004 |          1003 | sa128_obv4_2 | xx.xx.xx.81 |     2882 |
|    1006 |      1004 |          1003 | sa128_obv4_3 | xx.xx.xx.19 |     2882 |
+---------+-----------+---------------+--------------+-------------+----------+
3 rows in set
```

## Log stream group

The concept of log stream groups is introduced to accommodate the distribution of the primary zone across multiple zones. If the primary zone is a single zone, only a single log stream needs to be created within the unit group. If the primary zone spans multiple zones, multiple log streams need to be created within the unit group to scale the service capabilities horizontally. These log streams share the same distribution attributes and together form a log stream group. The number of log streams in a log stream group equals the number of zones in the primary zone.

Therefore, a log stream belongs to a single log stream group and cannot be changed; log stream groups correspond one-to-one with unit groups; all log streams in a log stream group are distributed across the corresponding unit group, with log stream leaders scattered across the primary zones.

The number of log streams in a log stream group dynamically changes based on the configuration of the tenant's primary zone, and its lifecycle is bound to that of the unit group.

In the `sys` tenant, you can view all log streams of the cluster and their corresponding log stream groups using the `oceanbase.CDB_OB_LS` view. Example:

```shell
obclient> select TENANT_ID,LS_ID,STATUS,PRIMARY_ZONE,UNIT_GROUP_ID,LS_GROUP_ID from oceanbase.CDB_OB_LS where TENANT_ID=1004;
+-----------+-------+--------+----------------------------------------+---------------+-------------+
| TENANT_ID | LS_ID | STATUS | PRIMARY_ZONE                           | UNIT_GROUP_ID | LS_GROUP_ID |
+-----------+-------+--------+----------------------------------------+---------------+-------------+
|      1004 |     1 | NORMAL | sa128_obv4_1;sa128_obv4_2,sa128_obv4_3 |             0 |           0 |
|      1004 |  1001 | NORMAL | sa128_obv4_1;sa128_obv4_2,sa128_obv4_3 |          1003 |        1001 |
+-----------+-------+--------+----------------------------------------+---------------+-------------+
2 rows in set
```

## Summary

To summarize, the following concepts introduced in this section are described:

* A unit is an abstraction of physical resources. Each unit occupies a certain amount of physical resources on a node, including CPU, memory, and storage space. Units are the basic units for resource scheduling. You can adjust the distribution of units on nodes in the same zone to achieve load balancing and disaster recovery between the nodes.

* Each tenant consists of several units. You can specify the number of units and the primary zone for a tenant to define a group of units that carry business traffic. You can conveniently scale the tenant capacity horizontally by placing each unit on a separate node.

* A log stream is a data frame that contains several data partitions and a sequence of redo logs. The Paxos protocol is used to synchronize logs between replicas to ensure data consistency between the replicas and thereby implement high availability of data. A log stream is also the commit unit of a transaction. If the modifications made by a transaction are completed within a single log stream, the transaction can be committed by using the one-phase atomic commit logic. If the modifications made by the transaction span multiple log streams, the transaction can be committed by using the two-phase atomic commit protocol of OceanBase Database. Log streams participate in distributed transactions. Each log stream has a location and a role. The location and role attributes are inherited by all data partitions in the log stream.

* The system assigns a number to each unit in every zone. Units with the same number form a unit group. A log stream is defined for each unit in the unit group. In other words, a unit group frames a group of log streams that are distributed only on the units in the unit group.

* The number of log stream groups in a zone is the same as the number of primary zones. In each log stream group, the number of log streams is the same as the number of zones in the primary zone list. Therefore, the list of zones in the primary zone can contain the leader of a log stream in the log stream group.

  For example, if a tenant is configured with `unit_num =2` and `primary_zone ='Z1,Z2,Z3'`, the tenant defines two unit groups, two log stream groups, and six log streams. The following figure shows an example.

OceanBase Database flexibly distributes data and traffic across multiple nodes at multiple levels. Units can be migrated between nodes in a zone for load balancing and disaster recovery.
