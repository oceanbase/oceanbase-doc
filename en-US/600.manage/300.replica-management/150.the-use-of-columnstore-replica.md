# Use columnstore replicas

To support the TP-enhanced mixed load (near real-time decision analysis) scenario, the OceanBase database provides support for columnar replicas (COLUMNSTORE, hereinafter referred to as C replicas). Users can deploy C replicas in an independent Zone. On the C replica, all user tables (including replicated tables, but excluding index tables, internal tables, and system tables) are stored in columnar format. OLAP workloads access the C replica through an independent proxy entry and execute decision analysis tasks in a weak read manner.

## Considerations

When using Copy C, the following items need to be noted:

* Starting from V4.3.5 BP1 version, it supports the deployment of multiple C replicas, and it is recommended to deploy up to 3 C replicas.

* Conversion between C副本 and F or R副本 is not supported.

* Since accessing Copy C requires the deployment of a standalone ODP, it is recommended to deploy only Copy C on the Zone where Copy C exists. Meanwhile, when deploying the ODP, its version must be ODP V4.3.2 or higher.

* Queries on the F/R replica are not allowed to be forwarded to the C replica. Conversely, user table queries on the C replica are not allowed to be forwarded to the F/R replica, otherwise, an error will be reported.

* The cluster with C replicas deployed will have an impact on the usage of resources such as CPU, memory, disk, and IO when performing DDL operations.

* The merging of C replicas is slower than that of F/R replicas. If the merging of C replicas is not completed, a new round of tenant-level merging cannot be initiated. Before manually triggering the merge, it is recommended to confirm whether all replicas in the previous round have completed merging by checking the [CDB_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/12000.o-cdb_ob_zone_major_compaction-of-sys-tenant.md) or [DBA_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13000.o-dba_ob_zone_major_compaction-of-mysql-mode.md) views.

  For more information about how to check the status of a major compaction, see [View the status of a major compaction](../../700.reference/200.system-management/500.manage-data-storage/200.merge-management/500.view-merge-process.md).

* Physical recovery does not support restoring C replicas. When specifying the Locality for a tenant, if C replicas are specified, the restore operation will fail.

* If the primary database does not have the C replica deployed, it is also not recommended to deploy the C replica on the secondary database.

## Deploy Replica C and Configure ODP

The following content mainly introduces how to deploy and configure ODP in the OceanBase cluster to access C replicas.

### Step 1: Deploy Replica C

To deploy C replicas in a cluster, you only need to specify the C replicas in the tenant's Locality. There are mainly the following two scenarios:

* Specify C replicas when creating tenants

* Increase C replicas by modifying the locality of tenants.

#### Specify C replicas when creating tenants

Assume that there is currently a deployed cluster, and the deployment mode of the cluster is 2F1A (two replicas + one arbitration service). The three Zones in the cluster are zone1, zone2, and zone3, with the arbitration service deployed on zone3. To create a tenant with C replicas on this cluster, follow these steps:

1. Find a server that can communicate with the cluster and deploy an ODP on the server.

   To avoid resource contention, it is recommended to deploy ODP on a dedicated server. When deploying ODP, the version must be ODP V4.3.2 or later. For more information about how to deploy an ODP, see [Deploy ODP](https://en.oceanbase.com/docs/common-odp-doc-en-10000000001735877).

2. Create a resource unit named `unit1`.

   ```shell
   obclient [oceanbase]> CREATE RESOURCE UNIT unit1, MAX_CPU=5, MIN_CPU=5, MEMORY_SIZE= '32G', MAX_IOPS=10000, MIN_IOPS=5000, LOG_DISK_SIZE=5301023539200;
   ```

3. Create a resource pool named `pool1` and specify `unit1` as the resource unit.

   ```shell
   obclient [oceanbase]> CREATE RESOURCE POOL pool1 UNIT='unit1', UNIT_NUM = 1, ZONE_LIST = ('zone1','zone2','zone3');
   ```

4. Create a tenant named `tenant_c` and specify the locality of the tenant as `F@zone1,F@zone2,C@zone3`.

   ```shell
   obclient [oceanbase]> CREATE TENANT tenant_c LOCALITY = 'F@zone1,F@zone2,C@zone3', primary_zone='zone1;zone2,zone3', RESOURCE_POOL_LIST=('pool1') SET ob_tcp_invited_nodes = '%';
   ```

   In this example, the created tenant is a MySQL-compatible tenant by default. If you want to create an Oracle-compatible tenant, you must explicitly set the `ob_compatibility_mode` system variable to `ob_compatibility_mode='oracle'`.

#### Add a columnstore replica by modifying the locality of a tenant

Assume there is a tenant named `tenant_c` in the current cluster, with a locality of `F@zone1,F@zone2,F@zone3`. The tenant's resource pool is `pool1`, and its `ZONE_LIST` is `'zone1','zone2','zone3'`. Now, to add a columnstore replica for the tenant, you can add `zone4` and then modify the tenant's locality to `F@zone1,F@zone2,F@zone3,C@zone4`. The steps are as follows:

1. Add a new zone named `zone4` to the cluster. For more information, see [Add a zone](../100.cluster-management/300.common-cluster-operations/800.add-a-zone.md).

2. Add a node to `zone4`. For more information, see [Add a node](../100.cluster-management/300.common-cluster-operations/400.add-a-node.md).

3. Find a server that can communicate with the cluster and deploy an ODP on the server.

   To avoid resource contention, it is recommended to deploy ODP on a dedicated server. When deploying ODP, the version must be ODP V4.3.2 or later. For more information about how to deploy an ODP, see [Deploy ODP](https://en.oceanbase.com/docs/common-odp-doc-en-10000000001735877).

4. Create a resource unit named `unit2`.

   ```shell
   obclient [oceanbase]> CREATE RESOURCE UNIT unit2, MAX_CPU=5, MIN_CPU=5, MEMORY_SIZE= '32G', MAX_IOPS=10000, MIN_IOPS=5000, LOG_DISK_SIZE=5301023539200;
   ```

5. Create a resource pool named `pool2` and specify `unit2` as the resource unit.

   ```shell
   obclient [oceanbase]> CREATE RESOURCE POOL pool2 UNIT = 'unit2', UNIT_NUM = 1, ZONE_LIST = ('zone4');
   ```

6. Add the `pool2` resource pool to the tenant.

   ```shell
   obclient [oceanbase]> ALTER TENANT tenant_c RESOURCE_POOL_LIST = ('pool1','pool2');
   ```

7. Modify the locality of the tenant to `F@zone1,F@zone2,F@zone3,C@zone4`.

   ```shell
   obclient [oceanbase]> ALTER TENANT tenant_c LOCALITY = 'F@zone1,F@zone2,F@zone3,C@zone4';
   ```

## Step 2: Configure routing policies and weak-consistency read requests

After the columnstore replica is deployed, you need to configure routing policies and weak-consistency read requests so that OLAP requests can be automatically converted into weak-consistency read requests and forwarded to the corresponding columnstore replica.

1. Log in to the ODP where the columnstore replica is located as the `root@proxysys` user.

   Here is an example of how to connect:

   ```shell
   [admin@obtest ~]$ obclient -uroot@proxysys -h10.10.10.1 -P2883 -p
   ```

2. Execute the following statements to configure routing policies and weak-consistency read requests.

   The following two parameter combinations are supported. You can choose either one for setup.

   * First combination

      * Configure SQL requests as read-only.

         ```shell
         obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
         ```

      * Configure SQL requests for weak-consistency reads.
   
         ```shell
         obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
         ```

      * Configure weak-read requests so that ODP routes all requests only to the zone where the columnstore replica resides and generates query plans for the columnstore replica.

         For example, assume that the zone where the columnstore replica resides is `zone4`.

         ```shell
         obclient> ALTER PROXYCONFIG SET proxy_primary_zone_name='zone4';
         ```

         ```shell
         obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
         ```

   * Second combination

      * Configure SQL requests as read-only.

         ```shell
         obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
         ```

      * Configure SQL requests for weak-consistency reads.
   
         ```shell
         obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
         ```

      * Configure weak-read requests so that all requests are routed only to the columnstore replica, and generate query plans for the columnstore replica.

         ```shell
         obclient> ALTER PROXYCONFIG SET route_target_replica_type = 'ColumnStore';
         ```

         ```shell
         obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
         ```

      * Configure weak-read requests to select only follower replicas. If no follower replicas are available, disconnect from the client.

         ```shell
         obclient> ALTER PROXYCONFIG SET proxy_route_policy='TARGET_REPLICA_TYPE_FOLLOWER_ONLY';
         ```

3. Execute the following statements to verify the configuration.

   ```shell
   obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_only';
   ```

   ```shell
   obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_consistency';
   ```

   ```shell
   obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_primary_zone_name';
   ```

   ```shell
   obclient> SHOW PROXYCONFIG ALL LIKE 'init_sql';
   ```

   ```shell
   obclient> SHOW PROXYCONFIG ALL LIKE 'route_target_replica_type';
   ```

   ```shell
   obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_route_policy';
   ```

After the configuration is successful, users can direct query requests to the columnstore replica through the independent ODP. By leveraging the batch processing advantages of the columnstore replica, queries can be accelerated without affecting the original OLTP workloads.

## Several scenarios where tables in a columnstore replica are stored using row-based storage

When a table is created in OceanBase Database, if it is created using row-based storage, the system creates a pure columnstore table in the columnstore replica; if it is created using columnar storage, the storage format in the columnstore replica is the same as that in the full-featured replica. Therefore, the columnstore replica is only responsible for converting user partitions of a rowstore table in the full-featured replica into columnar storage. This description applies only to the "final" storage format, which is columnar storage. In the columnstore replica, partitions are not necessarily stored using columnar storage at all times. In the following scenarios, partitions in the columnstore replica are stored using row-based storage. In these scenarios, the system automatically schedules a rowstore-to-columnar conversion task in the background and converts the latest baseline data into columnar storage.

| Scenario             | Description                                                          |
|-----------------|---------------------------------------------------------------|
| Add a replica             | For example, to modify the locality of a tablet from `F@z1, F@z2` to `F@z1, F@z2, C@z3`:<ul><li>When row-based baseline data is migrated from the source replica (F replica or R replica) to the target replica (C replica), the data is first copied to the C replica, and then an attempt is made to convert the data into columnar storage for the tablet. </li> <li>Since a rowstore-to-columnar conversion task is a special type of major compaction, if multiple attempts to convert the data fail (for example, the DAG Scheduler queue is full, there is significant I/O pressure, or there is insufficient disk space), the system provides weak-consistency read queries based on row-based storage. </li></ul>|
| Log stream rebuild                | When a log stream rebuild is triggered for the columnstore replica, the system pulls the corresponding baseline data from the source replica to the columnstore replica. If the baseline data is stored using row-based storage, the data remains in row-based storage until the background rowstore-to-columnar conversion task is completed and the data is converted into columnar storage. |
| Concurrency of add a replica and offline DDL  | If the columnstore replica is in the member list of a log stream and you perform offline DDL on the log stream, the system directly builds a columnar baseline on the columnstore replica. However, if an add-a-replica and offline DDL operation are performed concurrently, the columnstore replica cannot see the leader of the log stream on which the DDL task is being performed. In this case, the system builds a rowstore baseline on the columnstore replica and then converts the baseline into columnar storage after the background rowstore-to-columnar conversion task is completed. |
| Full direct load                   | At present, full direct load is supported only for rowstore tables. After a full direct load, a background rowstore-to-columnar conversion task is scheduled to convert the data into columnar storage. |
| Table-level restore                       | Since a columnstore table does not support table-level restore, a table-level restore in the columnstore replica is performed by first restoring the table to a rowstore format and then converting it into a columnar format after the background rowstore-to-columnar conversion task is completed. |

During a rowstore-to-columnar conversion, although the optimizer generates a columnar query plan, the actual execution still queries the rowstore baseline. You can query the [CDB_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/8120.o-cdb_ob_cs_replica_stats-of-sys-tenant.md) view (in a sys tenant) or the [DBA_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/8220.o-dba_ob_cs_replica_stats-of-mysql-mode.md) view (in a user tenant) for the available information about the columnstore replica and the progress of the rowstore-to-columnar conversion. After the conversion is complete, you can perform queries on the columnstore replica.

Here is an example that queries the row-based-to-columnar conversion progress of tablets in log streams across all tenants in a columnstore replica from a sys tenant:

```shell
obclient[oceanbase]> SELECT * FROM oceanbase.CDB_OB_CS_REPLICA_STATS;
```
