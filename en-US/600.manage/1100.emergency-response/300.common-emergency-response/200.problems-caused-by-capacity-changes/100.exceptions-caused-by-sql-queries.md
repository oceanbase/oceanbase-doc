# Exceptions caused by SQL queries

In practical production scenarios, apart from hardware and infrastructure failures, SQL query-related exceptions are among the most common causes of database service issues. This section focuses on analyzing and handling such exceptions in OceanBase Database.

## Scenario description

During normal database operation, you may encounter situations such as CPU usage spikes, high I/O, or memory surges caused by abnormal SQL execution. SQL exceptions can be categorized into the following types:

1. The business application has not released a new version, meaning no new SQL statements have been added. This scenario can be further divided into two cases:

   1. The external business traffic changes, leading to a sudden increase in SQL execution frequency or data volume.

   2. The original SQL execution plan is abnormal.

2. The business application has released a new version, introducing new SQL query logic that includes slow SQL statements.

## Business impact

SQL issues can lead to high CPU usage and memory exhaustion, causing business delays or even system crashes.

## Emergency handling process

The following sections describe how to quickly locate and handle each situation.

### The business has not released a new version, and no new SQL has been added.

Scenario 1: SQL execution count or data volume changes

In a normal database service scenario, due to marketing activities or increased user access, the execution count or data volume of a certain type of SQL in the database may increase. In this case, the preferred solution is to downgrade or throttle the business. If the business cannot directly throttle or downgrade, and if the instance's CPU/memory configuration can be increased, the preferred solution is to temporarily expand the database. For more information, see **Scale out or scale in** in the **Database Basic Management** section.

If there are no extra resources in the cluster, you can consider throttling specific SQL statements at the OceanBase Database kernel level. You can bind the SQL statement to an execution plan with the `hint max_concurrent` option to limit its concurrency and throttle the SQL statement. Here is an example:

```sql
CREATE OUTLINE outline_name ON sql_id USING HINT /*+max_concurrent(1)*/;
```

For more information about how to bind an outline, see **CREATE OUTLINE** in **SQL Reference (MySQL mode)** and **CREATE OUTLINE** in **SQL Reference (Oracle mode)**.

Scenario 2: The execution plan of the existing SQL statement is abnormal.

If the business has not released a new version, but the execution plan of the existing SQL statement in the database is abnormal, the following situations may occur:

1. The execution plan is incorrectly selected. In this case, you can clear the plan cache to force the SQL statement to re-parse and generate a correct execution plan.

   ```sql
   ALTER system flush plan cache [tenant_list] [global];
   ```

   <main id="notice" type='explain'>
    <h4>Note</h4>
    <ul>
    <li>tenant_list and global are optional parameters. If tenant_list is not specified, the execution plans of all tenants are cleared. Otherwise, only the execution plans of the specified tenant are cleared. If global is not specified, the execution plans of the local server are cleared. Otherwise, the execution plans of all servers where the tenant is located are cleared. By default, the minimum scope is cleared.</li>
    <li>tenant_list is specified as follows: tenant = 'tenant1, tenant2, tenant3....'</li>
    </ul>
   </main>

2. The wrong index is selected.

   After troubleshooting, it is found that the table has better indexes, but the execution plan does not use the correct index. If clearing the execution plan cache does not resolve the issue, you can bind the correct execution plan to the optimizer using an outline.

   Index binding is now supported in OCP for graphical operations. Please refer to the OCP user guide for the corresponding operations.

   For command-line execution of binding operations, here is an example: bind the SQL statement "SELECT * FROM t1 WHERE v1 = 3" to the primary key index.

   1. Log in to OceanBase Database as a business tenant (note that the -c parameter must be added to the mysql command).

   2. Create an outline.

      ```sql
      create outline bind_to_primary_key on SELECT/*+ index(t1 primary)*/ * FROM t1 WHERE v1 = 3;
      ```

   3. Verify that the outline is created successfully.

      ```sql
      SELECT * FROM oceanbase.gv$outline WHERE OUTLINE_NAME = 'bind_to_primary_key';
      ```

   4. Verify that the new SQL statement generates a new execution plan based on the bound outline.

      After executing the SQL statement with the bound outline, query the `gv$plan_cache_plan_stat` table to find the `outline_id` for the SQL statement. If the `outline_id` matches the `outline_id` found in the `gv$outline` table, it indicates that the execution plan was generated based on the bound outline.

      ```sql
      SELECT SQL_ID, PLAN_ID, STATEMENT, OUTLINE_ID, OUTLINE_DATA 
            FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT 
             WHERE STATEMENT LIKE '%SELECT * FROM t1 WHERE v1 = 3%';
      ```

   5. Verify that the generated execution plan meets the expected requirements.

      After confirming that the plan is generated based on the bound outline, verify whether the generated plan meets the expected requirements by querying the `gv$plan_cache_plan_stat` table to view the shape of the cached execution plan in the `plan_cache`.

      ```sql
      SELECT OPERATOR, NAME FROM oceanbase.V$OB_PLAN_CACHE_PLAN_STAT
            WHERE TENANT_ID = BusinessTenantID AND IP = 'xxx.xxx.xxx.xxx'
             AND PORT = xxxx AND PLAN_ID = The plan_id obtained in the previous step;
      ```

3. The index is missing.

   After troubleshooting, it is found that the table involved in the current SQL statement lacks the optimal index. Please create the corresponding index as needed.

   <main id="notice" type='notice'>
    <h4>Notice</h4>
    <ul>
    <li>
    <p>When creating an index, include as many of the queried columns as possible. The more columns included, the fewer rows need to be accessed from the table.</p>
    </li>
    <li>
    <p>For equality conditions, place them at the beginning of the composite index columns.</p>
    </li>
    <li>
    <p>Place the columns with large filtering and sorting data volumes at the beginning of the composite index columns.</p>
    </li>
    </ul>
   </main>

### Business releases a new version with new SQL logic

When a new version is released, new SQL statements are generated. In some cases, unreviewed slow SQL statements may consume excessive resources in the production environment, impacting core business operations. In such scenarios, it is necessary to identify and troubleshoot slow SQL statements in the database to address the issue and proceed with optimization.

1. Use OCP to locate slow SQL statements.

   You can view the top SQL statements with the highest execution time and frequency in the TOP SQL section of OCP, sorted from highest to lowest. For SQL statements that are incorrectly planned, you can bind them online. For SQL statements that require throttling, you need to confirm with the business development team to identify which SQL statements can be throttled.

2. Use the command line to locate slow SQL statements.

   1. Query the top SQL statements consuming the most CPU resources for a specific tenant.

      ```sql
      SELECT
       sql_id,
        avg(execute_time) avg_exec_time,
        count(*) cnt,
        avg(execute_time - TOTAL_WAIT_TIME_MICRO) cpu_time,
      RETRY_CNT,QUEUE_TIME,IS_HIT_PLAN
      FROM
       OCEANBASE.V$OB_SQL_AUDIT
      WHERE
        tenant_id = 1002 
      GROUP BY 
       1
      ORDER BY 
       (avg_exec_time * cnt) desc
      limit
       5;
      ```

   <main id="notice" type='explain'>
    <h4>Note</h4>
    <ul>
    <li>
    <p>If the value of EXECUTE_TIME is excessively large, it may indicate waiting events or an unusually high number of logical reads.</p>
    </li>
    <li>
    <p>The RETRY_CNT field indicates the number of retries. If this value is high, it may suggest lock conflicts or primary key switching issues.</p>
    </li>
    <li>
    <p>If QUEUE_TIME is excessively large, it indicates insufficient CPU resources.</p>
    </li>
    <li>
    <p>GET_PLAN_TIME represents the time taken to retrieve the execution plan. If this time is excessively long, it is typically accompanied by IS_HIT_PLAN＝0, indicating that the plan was not hit.</p>
    </li>
    </ul>
   </main>

   2. Other relevant queries.

      OceanBase Database provides two virtual tables, `V$OB_SQL_AUDIT` and `GV$OB_SQL_AUDIT`, which record the execution history of SQL statements over a certain period. The V$OB_SQL_AUDIT table stores the execution history of SQL statements on the local node, while the GV$OB_SQL_AUDIT table stores the execution history of SQL statements across the entire cluster. You can perform relevant queries based on your needs.

      1. Query the GV$OB_SQL_AUDIT table to find SQL statements executed by a specific tenant with an execution time greater than 1 second (1,000,000 microseconds).

         ```sql
         SELECT * FROM oceanbase.GV$OB_SQL_AUDIT WHERE tenant_id= <tenantid> AND elapsed_time> 1000000 limit 10;
         ```

      2. Query the histogram of SQL execution times in seconds.

         ```sql
         SELECT round(elapsed_time/1000000), count(*) FROM oceanbase.V$OB_SQL_AUDIT WHERE tenant_id = <tenant_id> GROUP BY  1;
         ```

3. Use OceanBase logs to locate slow SQL statements.

   In OceanBase Database, SQL statements with an execution time exceeding the trace_log_slow_query_watermark (a system parameter) will be logged as slow query messages in the observer log. The default value of this parameter is 100 ms. You can use the observer log to locate slow SQL statements. While this method is not as efficient or intuitive as the previous two methods, it can still be helpful in certain situations, such as when the cache in the sql_audit table has been evicted.

   The location of the slow SQL log is: `/home/admin/oceanbase/log`

   1. View all slow queries in the log.

      `fgrep '[slow query]' observer.log |sed -e 's/|/\n/g' | more`

   2. Query a specific slow query using the trace_id.

      `fgrep "<trace_id>" observer.log |sed -e 's/|/\n/g' | more`
