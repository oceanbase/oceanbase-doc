# SQL query-related exceptions

In practical production scenarios, excluding hardware and infrastructure failures, SQL query-related exceptions are likely the most common cause of database service anomalies. This section focuses on analyzing and handling SQL query-related exceptions in OceanBase Database.

## Scenario description

During normal database operation, it is common to encounter situations such as CPU usage spikes, high I/O, or memory surges caused by abnormal SQL execution. SQL exceptions can generally be categorized into the following scenarios:

1. No new version of the business application has been released, meaning no new SQL statements have been added. This scenario can be further divided into two subcategories:

   1. Changes in external business traffic result in a sudden increase in SQL execution frequency or a surge in data volume.

   2. The execution plans of existing SQL statements are abnormal.

2. A new version of the business application has been released, introducing new SQL query logic, which includes slow SQL statements.

## Business impact

SQL issues can easily lead to high CPU usage and memory exhaustion, resulting in business delays or even crashes.

## Emergency Handling Process

This section describes the quick location and handling methods for each situation.

### The business has not released a new version, and no new SQL statements have been added.

#### Scenario 1: SQL execution count or data volume changes

In a normal database service, due to marketing activities or increased user access, the execution count or data volume of existing SQL statements may increase. In such cases, the preferred solution is to downgrade or throttle the business. If the business cannot directly throttle or downgrade, consider temporarily expanding the tenant's CPU or memory resources. For more information about tenant scaling, see [Tenant scaling](../../../200.tenant-management/600.common-tenant-operations/800.tenant-scale-in-and-out/100.introduction-to-tenant-scale-in-and-out.md).

If the cluster does not have extra resources for expansion, consider throttling specific SQL statements at the OceanBase Database kernel level. You can bind an execution plan to an SQL statement and specify the `hint max_concurrent` parameter to limit the SQL statement's concurrency. Example:

```sql
CREATE OUTLINE outline_name ON sql_id USING HINT /*+max_concurrent(1)*/;
```

For more information about how to bind an outline, see [Plan binding](../../../../700.reference/1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/700.manage-execution-plans/200.plan-binding.md).

#### Scenario 2: Existing SQL execution plans are abnormal

If the business has not released a new version, but the execution plans of existing SQL statements in the database are abnormal, the following scenarios may occur:

1. The execution plan is selected incorrectly. In this case, you can clear the plan cache to force the SQL statement to re-parse and generate a correct plan.

   ```sql
   ALTER system flush plan cache [tenant_list] [global];
   ```

   <main id="notice" type='explain'>
    <h4>Note</h4>
    <ul>
    <li>tenant_list and global are optional parameters. If tenant_list is not specified, the execution plan cache of all tenants is cleared. Otherwise, only the execution plan cache of the specified tenant is cleared. If global is not specified, the execution plan cache of the local server is cleared. Otherwise, the execution plan cache of all servers where the tenant is located is cleared. By default, the minimum scope is cleared.</li>
    <li>tenant_list: tenant = 'tenant1, tenant2, tenant3....'</li>
    </ul>
   </main>

2. The wrong index is selected.

   After investigation, it is found that there is a better index in the table, but the execution plan does not use the correct index. If clearing the execution plan cache does not resolve the issue, you can bind an outline to specify the correct execution plan to the optimizer.

   Index binding is now supported in OCP through a graphical interface. Please refer to the OCP user guide for the corresponding operations.

   For command-line execution of binding operations, you can refer to the following example: bind the SQL statement `SELECT * FROM t1 WHERE v1 = 3` to use the primary key index.

   1. Log in to OceanBase as a business tenant (note that the -c parameter must be added to the mysql command).

   2. Create an outline.

      ```sql
      create outline bind_to_primary_key on SELECT/*+ index(t1 primary)*/ * FROM t1 WHERE v1 = 3;
      ```

   3. Verify that the outline is created successfully.

      ```sql
      SELECT * FROM oceanbase.gv$outline WHERE OUTLINE_NAME = 'bind_to_primary_key';
      ```

   4. Verify that the new SQL statement generates a new execution plan based on the bound outline.

      After executing the SQL statement with the bound outline, query the `gv$plan_cache_plan_stat` table for the `outline_id` of the SQL statement's plan. If the `outline_id` matches the one found in the `gv$outline` table, the execution plan was generated based on the bound outline; otherwise, it was not.

      ```sql
      SELECT SQL_ID, PLAN_ID, STATEMENT, OUTLINE_ID, OUTLINE_DATA
            FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT
             WHERE STATEMENT LIKE '%SELECT * FROM t1 WHERE v1 = 3%';
      ```

   5. Verify that the generated execution plan meets expectations.

      After confirming that the plan was generated based on the bound outline, verify that the plan meets expectations by querying the `gv$plan_cache_plan_stat` table for the shape of the cached execution plan in `plan_cache`.

      ```sql
      SELECT OPERATOR, NAME FROM oceanbase.V$OB_PLAN_CACHE_PLAN_STAT
            WHERE TENANT_ID = business tenant ID AND IP = 'xxx.xxx.xxx.xxx'
             AND PORT = xxxx AND PLAN_ID = the plan_id obtained in the previous step;
      ```

3. The optimal index is missing.

   After investigation, it is found that the optimal index is missing from the tables involved in the current SQL statement. Please create the corresponding index as needed.

   <main id="notice" type='notice'>
    <h4>Notice</h4>
    <ul>
    <li>
    <p>When creating an index, include as many of the queried columns as possible. The more columns included, the fewer rows will need to be retrieved from the table.</p>
    </li>
    <li>
    <p>Place equality conditions at the beginning of the composite index columns.</p>
    </li>
    <li>
    <p>Place columns with large amounts of filtering and sorting data at the beginning of the composite index columns.</p>
    </li>
    </ul>
   </main>

### A new version of the business is released, and new SQL logic is introduced

When a new version of the business is released, new SQL statements are generated. In some cases, unreviewed slow SQL statements may consume excessive resources in the production environment, impacting core business operations. In such scenarios, it is necessary to investigate the slow SQL statements in the database to identify the root cause and proceed with optimization.

1. Use OCP to locate the slow SQL statements.

   You can view the top SQL statements in the OCP Top SQL page based on their execution time and frequency over a specific period. These statements are sorted from highest to lowest. For SQL statements that are incorrectly planned, you can bind them directly online. For SQL statements that require throttling, you need to confirm with the business development team to identify the statements that can be throttled.

2. Use the command line to locate the slow SQL statements.

   1. Query the top SQL statements that consume the most CPU resources in a specific tenant.

      ```sql
      SELECT
       sql_id,
        avg(execute_time) avg_exec_time,
        count(*) cnt,
        avg(execute_time - TOTAL_WAIT_TIME_MICRO) cpu_time,
      RETRY_CNT,QUEUE_TIME,IS_HIT_PLAN
      FROM
       OCEANBASE.V$OB_SQL_AUDIT
      WHERE
        tenant_id = 1002
      GROUP BY
       1
      ORDER BY
       (avg_exec_time * cnt) desc
      limit
       5;
      ```

      <main id="notice" type='explain'>
      <h4>Note</h4>
      <ul>
      <li>
      <p>The EXECUTE_TIME value indicates the execution time of an SQL statement. If the value is excessively large, it may indicate that the statement is waiting for an event or has a high number of logical reads. </p>
      </li>
      <li>
      <p>The RETRY_CNT field indicates the number of retries. If the value is excessively large, it may indicate lock conflicts or leader switching. </p>
      </li>
      <li>
      <p>If the QUEUE_TIME value is excessively large, it indicates that the CPU resources are insufficient. </p>
      </li>
      <li>
      <p>The GET_PLAN_TIME field indicates the time taken to obtain the execution plan. If the value is excessively large, it is usually accompanied by IS_HIT_PLAN＝0, indicating that the plan was not hit. </p>
      </li>
      </ul>
      </main>

   2. Perform other relevant queries.

      OceanBase Database provides two virtual tables, `V$OB_SQL_AUDIT` and `GV$OB_SQL_AUDIT`, which record the execution history of SQL statements over a specific period. The `V$OB_SQL_AUDIT` table stores the execution history of SQL statements on the local node, while the `GV$OB_SQL_AUDIT` table stores the execution history of SQL statements across the entire cluster. You can perform relevant queries based on your needs.

      1. Query the `GV$OB_SQL_AUDIT` table to find SQL statements executed by a specific tenant with an execution time greater than 1 second (1,000,000 microseconds).

         ```sql
         SELECT * FROM oceanbase.GV$OB_SQL_AUDIT WHERE tenant_id= <tenantid> AND elapsed_time> 1000000 limit 10;
         ```

      2. Query the histogram of SQL execution time in seconds.

         ```sql
         SELECT round(elapsed_time/1000000), count(*) FROM oceanbase.V$OB_SQL_AUDIT WHERE tenant_id = <tenant_id> GROUP BY  1;
         ```

3. Use OceanBase Database logs to locate the slow SQL statements.

   In OceanBase Database, if the execution time of an SQL statement exceeds the trace_log_slow_query_watermark (a system parameter), a slow query message is printed in the observer log. The default value of this parameter is 100 ms. You can use the observer log to locate slow SQL statements. This method is not as efficient and intuitive as the previous two methods, but it can be helpful in some scenarios, such as when the cache in the sql_audit table has been evicted.

   The slow SQL log is stored in the `/home/admin/oceanbase/log` directory.

   1. View all slow queries in the log.

      `fgrep '[slow query]' observer.log |sed -e 's/|/\n/g' | more`

   2. Query a specific slow query based on its trace ID.

      `fgrep "<trace_id>" observer.log |sed -e 's/|/\n/g' | more`
