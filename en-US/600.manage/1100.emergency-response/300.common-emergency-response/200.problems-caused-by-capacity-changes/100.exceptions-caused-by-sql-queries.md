# SQL query exceptions

In production environments, besides hardware and infrastructure failures, SQL query exceptions are the most common cause of database service issues. This section focuses on analyzing and handling SQL query exceptions in OceanBase Database.

## Scenario description

During normal database operation, it is common to encounter situations such as CPU usage spikes, high I/O, or memory surges caused by abnormal SQL execution. SQL exceptions can generally be categorized into the following scenarios:

1. No new version of the business application has been released, meaning no new SQL statements have been added. This scenario can be further divided into two subcategories:

   1. A sudden increase in external business traffic leads to a surge in SQL execution frequency or data volume.

   2. The execution plan of the original SQL statements is abnormal.

2. A new version of the business application has been released, introducing new SQL query logic that includes slow SQL statements.

## Business impact

SQL issues can easily lead to high CPU usage and memory exhaustion, resulting in business delays or even system crashes.

## Emergency response process

The following sections describe how to quickly locate and handle each situation.

### The business has not released a new version and no new SQL statements have been added

Scenario 1: The execution count or data volume of SQL statements changes

If the execution count or data volume of a certain type of SQL statement in the database increases due to marketing activities or increased user access, and the execution plan is normal, the recommended solution is to downgrade or limit the traffic at the business level. If the business cannot directly limit the traffic or downgrade, you can increase the CPU or memory resources of the tenant. If the resources are available, you can temporarily expand the database. For more information about tenant expansion, see [Tenant scaling](../../../200.tenant-management/600.common-tenant-operations/800.tenant-scale-in-and-out/100.introduction-to-tenant-scale-in-and-out.md).

If the cluster does not have extra resources for expansion, you can limit the traffic of specified SQL statements at the OceanBase Database kernel level. You can bind an execution plan to an SQL statement and add the `hint max_concurrent` clause to limit the concurrency of the SQL statement. Example:

```sql
CREATE OUTLINE outline_name ON sql_id USING HINT /*+max_concurrent(1)*/;
```

For more information about how to bind an outline, see [Plan binding](../../../../700.reference/1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/700.manage-execution-plans/200.plan-binding.md).

Scenario 2: The execution plan of an existing SQL statement is abnormal

If the business has not released a new version, but the execution plan of an existing SQL statement in the database is abnormal, the following scenarios may occur:

1. The execution plan is incorrectly selected. In this case, you can clear the plan cache to force the SQL statement to perform hard parsing and generate a correct execution plan.

   ```sql
   ALTER system flush plan cache [tenant_list] [global];
   ```

   <main id="notice" type='explain'>
    <h4>Note</h4>
    <ul>
    <li>tenant_list and global are optional parameters. If tenant_list is not specified, the execution plan cache of all tenants is cleared. Otherwise, only the execution plan cache of the specified tenant is cleared. If global is not specified, the execution plan cache of the local server is cleared. Otherwise, the execution plan cache of all servers where the tenant is located is cleared. By default, the minimum scope is cleared.</li>
    <li>tenant_list is specified as follows: tenant = 'tenant1, tenant2, tenant3....'</li>
    </ul>
   </main>

2. The wrong index is selected.

   After troubleshooting, you find that the table contains a better index, but the execution plan does not use the correct index. If clearing the execution plan cache does not solve the problem, you can bind the correct execution plan to the SQL statement.

   Index binding is now supported in OCP with a graphical interface. Please refer to the OCP user guide for the corresponding operations.

   For command-line execution of binding operations, you can refer to the following example: bind the SQL statement `SELECT * FROM t1 WHERE v1 = 3` to the primary key index.

   1. Log in to OceanBase as a business tenant (note that you must add the -c parameter to the mysql command).

   2. Create an outline.

      ```sql
      create outline bind_to_primary_key on SELECT/*+ index(t1 primary)*/ * FROM t1 WHERE v1 = 3;
      ```

   3. Verify that the outline is created.

      ```sql
      SELECT * FROM oceanbase.gv$outline WHERE OUTLINE_NAME = 'bind_to_primary_key';
      ```

   4. Verify that the new SQL statement generates a new execution plan based on the bound outline.

      After executing the SQL statement with the bound outline, query the `gv$plan_cache_plan_stat` table to obtain the `outline_id` of the SQL statement. If the `outline_id` matches the `outline_id` obtained from the `gv$outline` table, the execution plan is generated based on the bound outline. Otherwise, it is not.

      ```sql
      SELECT SQL_ID, PLAN_ID, STATEMENT, OUTLINE_ID, OUTLINE_DATA 
            FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT 
             WHERE STATEMENT LIKE '%SELECT * FROM t1 WHERE v1 = 3%';
      ```

   5. Verify that the generated execution plan meets the expected requirements.

      After confirming that the execution plan is generated based on the bound outline, verify whether the generated plan meets the expected requirements. You can query the `gv$plan_cache_plan_stat` table to view the shape of the cached execution plan in the `plan_cache`.

      ```sql
      SELECT OPERATOR, NAME FROM oceanbase.V$OB_PLAN_CACHE_PLAN_STAT
            WHERE TENANT_ID = business_tenant_id AND IP = 'xxx.xxx.xxx.xxx'
             AND PORT = xxxx AND PLAN_ID = plan_id_obtained_in_previous_step;
      ```

3. The required index is missing.

   After troubleshooting, you find that the table involved in the current SQL statement lacks the optimal index. Please create the corresponding index as needed.

   <main id="notice" type='notice'>
    <h4>Notice</h4>
    <ul>
    <li>
    <p>When creating an index, include as many query columns as possible. This minimizes the number of rows that need to be accessed from the table.</p>
    </li>
    <li>
    <p>Place equality conditions at the beginning of the columns in a composite index.</p>
    </li>
    <li>
    <p>Place columns that filter and sort large amounts of data at the beginning of the columns in a composite index.</p>
    </li>
    </ul>
   </main>

### A new version of the business is released, and new SQL logic is introduced

When a new version of the business is released, new SQL statements are generated. In some cases, unreviewed slow SQL statements may consume excessive resources in the production environment, affecting core business operations. In such cases, it is necessary to identify slow SQL statements in the database to pinpoint the issue and proceed with subsequent optimization.

1. Use OCP to locate slow SQL statements.

   You can view the top SQL statements with the highest execution time and frequency in the TOP SQL page of OCP. These statements are sorted from highest to lowest. For SQL statements that are incorrectly planned, you can bind them online. For SQL statements that require throttling, you need to confirm with the business development team to identify which SQL statements can be throttled.

2. Use the command line to locate slow SQL statements.

   1. Query the top SQL statements that consume the most CPU resources in a specific tenant.

      ```sql
      SELECT
       sql_id,
        avg(execute_time) avg_exec_time,
        count(*) cnt,
        avg(execute_time - TOTAL_WAIT_TIME_MICRO) cpu_time,
      RETRY_CNT,QUEUE_TIME,IS_HIT_PLAN
      FROM
       OCEANBASE.V$OB_SQL_AUDIT
      WHERE
        tenant_id = 1002 
      GROUP BY 
       1
      ORDER BY 
       (avg_exec_time * cnt) desc
      limit
       5;
      ```

   <main id="notice" type='explain'>
    <h4>Note</h4>
    <ul>
    <li>
    <p>If the value of EXECUTE_TIME is excessively large, it may indicate waiting events or an unusually high number of logical reads.</p>
    </li>
    <li>
    <p>The RETRY_CNT field indicates the number of retries. If the number is very high, it may suggest lock conflicts or primary switchovers or similar events.</p>
    </li>
    <li>
    <p>If QUEUE_TIME is excessively large, it indicates insufficient CPU resources.</p>
    </li>
    <li>
    <p>GET_PLAN_TIME represents the time taken to obtain the execution plan. If this time is excessively long, it is usually accompanied by IS_HIT_PLAN＝0, indicating that the plan was not hit.</p>
    </li>
    </ul>
   </main>

   2. Perform other relevant queries.

      OceanBase Database provides two virtual tables, `V$OB_SQL_AUDIT` and `GV$OB_SQL_AUDIT`, which record the execution history of SQL statements over a certain period. The `V$OB_SQL_AUDIT` table stores the execution history of SQL statements on the local node, while the `GV$OB_SQL_AUDIT` table stores the execution history of SQL statements across the entire cluster. You can perform relevant queries based on your needs.

      1. Query the `GV$OB_SQL_AUDIT` table to find SQL statements executed by a specific tenant with an execution time greater than 1 second (1,000,000 microseconds).

         ```sql
         SELECT * FROM oceanbase.GV$OB_SQL_AUDIT WHERE tenant_id= <tenantid> AND elapsed_time> 1000000 limit 10;
         ```

      2. Query the histogram of SQL execution times in seconds.

         ```sql
         SELECT round(elapsed_time/1000000), count(*) FROM oceanbase.V$OB_SQL_AUDIT WHERE tenant_id = <tenant_id> GROUP BY  1;
         ```

3. Use OceanBase logs to locate slow SQL statements.

   In OceanBase Database, if the execution time of an SQL statement exceeds the trace_log_slow_query_watermark system parameter, a slow query message is printed in the observer log. The default value of this parameter is 100 ms. You can use the observer log to locate slow SQL statements. While this method is not as efficient and intuitive as the previous two methods, it can still be helpful in certain scenarios, such as when the cache in the sql_audit table has been evicted.

   The slow SQL log is recorded at the following location: `/home/admin/oceanbase/log`

   1. View all slow queries in the log.

      `fgrep '[slow query]' observer.log |sed -e 's/|/\n/g' | more`

   2. Query a specific slow query by trace_id.

      `fgrep "<trace_id>" observer.log |sed -e 's/|/\n/g' | more`
