# GTS standalone scenario

The global timestamp service (GTS) service of a tenant is carried by the tenant system log stream and provides global timestamps to all OBServer nodes under the tenant. Since its availability directly affects the availability of the entire tenant, when the number of nodes in the cluster is large and the QPS is high, it is necessary to isolate the GTS traffic from user traffic to prioritize the response time of GTS.

This topic describes how to expand the `UNIT_NUM` and enable GTS standalone mode to isolate GTS traffic from user traffic, thereby improving the stability of user business.

## Background information

The current version supports the GTS standalone feature, which is controlled by the tenant-level parameter [enable_gts_standalone](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2550.enable_gts_standalone.md). The default value is `False`. You can enable the GTS standalone feature as needed. After enabling it, the system automatically ensures that the system log stream where GTS resides is dedicated to a group of units.

## Scenario information

Assume that there is a tenant named `tenant1` with a locality of `F@zone1, F@zone2, A`, primary zones of `zone1` and `zone2`, and a `UNIT_NUM` of 2 in both `zone1` and `zone2`.

## Procedure

In this scenario, when the machine hosting the SYS log stream reaches its bottleneck, you can first expand the `UNIT_NUM` of all resource pools in the tenant from 2 to 3, then migrate and replicate the SYS log stream (log stream 1) to the newly added group of units after expansion, making log stream 1 dedicated to a group of units, and then enable GTS standalone mode.

The detailed steps are as follows:

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Disable automatic rebalancing for the tenant.

   Set the value of the tenant-level parameter [enable_rebalance](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2800.enable_rebalance.md) to `False` to prevent automatic rebalancing. The statement is as follows.

   ```shell
   obclient(root@sys)[(none)]> ALTER SYSTEM SET enable_rebalance = False TENANT = tenant1;
   ```

3. (Optional) Before expansion, if the number of nodes in a zone is insufficient, add one node to each of `zone1` and `zone2`.

   For more information about how to add a node, see [Add a node](../100.cluster-management/300.common-cluster-operations/400.add-a-node.md).

4. Adjust the `UNIT_NUM` of all resource pools in the tenant to 3.

   ```shell
   obclient(root@sys)[(none)]> ALTER RESOURCE TENANT tenant1 UNIT_NUM = 3;
   ```

   For more information about how to expand the tenant by adjusting the `UNIT_NUM`, see [Adjust the number of units to scale in or out a tenant](../200.tenant-management/600.common-tenant-operations/800.tenant-scale-in-and-out/300.adjust-unit-number.md).

5. Change the log stream.

   Modify the `UNIT_GROUP` (for homogeneous zones) or `UNIT_LIST` (for heterogeneous zones) of the SYS log stream (log stream 1) of the tenant `tenant1` to the newly added group of units after expansion, allowing log stream 1 to be dedicated to a group of units. The statement is as follows.

   :::tab
   tab Homogeneous zones

    ```shell
    obclient(root@sys)[(none)]> ALTER SYSTEM MODIFY LS 1 UNIT_GROUP unit_group_id TENANT = tenant1;
    ```

   In this statement, replace `unit_group_id` with the `UNIT_GROUP_ID` of the newly added group of units after expansion.

   tab Heterogeneous zones

   ```shell
   obclient(root@sys)[(none)]> ALTER SYSTEM MODIFY LS 1 UNIT_LIST (unit_id1,unit_id2) TENANT = tenant1;
   ```

   In this statement, replace `unit_id1` and `unit_id2` with the `UNIT_ID` of the newly added group of units after expansion.

   :::

   For more information about how to change the log stream, see [Change a log stream](../230.logstream-management/200.modify-a-logstream.md).

6. Enable the GTS standalone feature.

   Set the value of the tenant-level parameter [enable_gts_standalone](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2550.enable_gts_standalone.md) to `True`. The statement is as follows.

   ```shell
   obclient(root@sys)[(none)]> ALTER SYSTEM SET enable_gts_standalone = True TENANT = tenant1;
   ```

7. Re-enable automatic rebalancing for the tenant.

   Set the value of the tenant-level parameter [enable_rebalance](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2800.enable_rebalance.md) to `True`. The statement is as follows.

   ```shell
   obclient(root@sys)[(none)]> ALTER SYSTEM SET enable_rebalance = True TENANT = tenant1;
   ```

After expanding the `UNIT_NUM` and enabling GTS standalone mode in this scenario, the `UNIT_NUM` of the user log stream remains unchanged. Only the SYS log stream (log stream 1) is migrated and replicated, without log stream number balancing or transfer, ensuring the stability of user business.
