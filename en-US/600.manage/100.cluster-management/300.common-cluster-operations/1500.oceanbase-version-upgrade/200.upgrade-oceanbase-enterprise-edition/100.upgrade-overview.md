# Upgrade overview

OceanBase Database supports cluster upgrades using upgrade scripts. The upgrade process is transparent to applications, which do not need to perform any stop-write or stop-service operations on the server side. OceanBase Database upgrades zones in sequence. During the upgrade, partition leaders will actively switch between zones and redirect business traffic from the zone being upgraded to other zones.

This topic describes the limitations, considerations, and upgrade paths for upgrading OceanBase Database.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>OceanBase Database does not support upgrading from V4.2.x or earlier versions to V4.4.x. </p>
</main>

## Limitations

When you upgrade an OceanBase cluster, note the following limitations:

* DDL operations are disabled during the upgrade. They are enabled after the upgrade is completed.
* The `major freeze` operation is disabled during the upgrade. It is enabled after the upgrade is completed.
* Migration replication and load balancing are disabled during the upgrade.
* Physical backup and restore are disabled during the upgrade. This is because physical baseline backup (log archiving is not interrupted) and physical restore are not initiated during the upgrade.
* New tenants cannot be created during the upgrade.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If the OceanBase cluster is associated with an arbitration service, you must upgrade the arbitration service before you upgrade the OceanBase cluster. For more information about how to upgrade the arbitration service, see <a href="200.arbitration-services-version-upgrade.md">Upgrade the arbitration service</a>.<br>You can query the <a href="../../../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/15700.o-dba_ob_arbitration_service-of-sys-tenant.md">oceanbase.DBA_OB_ARBITRATION_SERVICE</a> view in the sys tenant to check whether the OceanBase cluster is associated with an arbitration service. </p>
</main>

## Considerations

When you upgrade an OceanBase cluster, note the following considerations:

* Log archiving is stopped when you upgrade an OceanBase cluster from V4.0 to V4.1.
* If the `ADD SERVER` or `DELETE SERVER` operation is required during the upgrade, contact OceanBase Technical Support.
* You cannot directly upgrade an OceanBase cluster from a transitional version. You must follow the upgrade sequence specified in the `oceanbase_upgrade_dep.yml` file.
* You must directly connect to the observer process of the Root Service to execute the upgrade script. You cannot use OceanBase Database Proxy (ODP) to connect to the Root Service.
* The following parameters may change during the upgrade. You must back up these parameters before the upgrade:

  * [server_permanent_offline_time](../../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/20300.server_permanent_offline_time.md)
  * [enable_rebalance](../../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2800.enable_rebalance.md)
  * [enable_rereplication](../../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/8000.enable_rereplication.md)

* Starting from OceanBase Database V4.3.0 Beta, the zlib_1.0 compression algorithm is no longer supported. During the upgrade, the following pre-checks are performed:

  * The `zlib` compression algorithm is no longer supported as the value of the `log_transport_compress_func` parameter. You must use another compression algorithm instead of the `zlib` compression algorithm.
  * If some tables use the `zlib` compression algorithm during the upgrade, you must replace the compression algorithm of these tables with another supported compression algorithm or disable compression during the upgrade.
  * The `zlib` compression algorithm is no longer supported as the value of the `tableapi_transport_compress_func` parameter. You must use another compression algorithm instead of the `zlib` compression algorithm.

* If you have used columnar tables in an ARM cluster or an x86 cluster that does not support the AVX2 (Advanced Vector Extensions 2) instruction set, you cannot upgrade the cluster from a V4.3 version (V4.3.0, V4.3.1, or V4.3.2) to V4.3.3 or later. This is to prevent data correctness risks after the upgrade.
* If you upgrade a V4.3 cluster to a V4.3.3 or later cluster, the standby tenant cannot parse the logs generated by the upgraded cluster. In this case, an error is returned when the standby tenant submits logs (the error is not persisted). For more information about how to restore data, see [Prepare for data restore](../../../../600.backup-and-recovery/600.restore-data/100.preparation-before-recovery.md).
* A tenant backed up in a V4.3.2 cluster cannot be restored in a V4.3.3 cluster.
* Data backed up in a V4.3.2 cluster cannot be upgraded to a V4.3.3 cluster.

## Upgrade considerations

### Non-shared storage mode

* You can smoothly upgrade an OceanBase cluster from V4.4.0/V4.4.0 BP1/V4.4.1 to V4.5.0.
* If you have not used vector indexes, you can upgrade an OceanBase cluster from V4.3.0/V4.3.1/V4.3.2/V4.3.3/V4.3.4/V4.3.5/V4.3.5 BP1/V4.3.5 BP2 to V4.5.0. However, this is only applicable to POC and test environments, and there is a certain risk of upgrade failure. If an upgrade failure occurs, the environment may need to be rebuilt.
* If you have used vector indexes, you must contact OceanBase Technical Support to evaluate whether you can upgrade an OceanBase cluster from V4.3.0/V4.3.1/V4.3.2/V4.3.3/V4.3.4/V4.3.5/V4.3.5 BP1/V4.3.5 BP2 to V4.5.0.
* You cannot upgrade an OceanBase cluster from a V4.2.x version or earlier to V4.5.0.

### Shared storage mode

* You can upgrade an OceanBase cluster from V4.4.0 BP1/V4.4.1/V4.4.1 hotfix1~3 to V4.5.0. If you upgrade a tenant with a single replica, the service is stopped.
* We recommend that you do not upgrade a cluster that uses V4.4.1 hotfix4 or V4.4.1 hotfix5 to V4.5.0.
* You cannot upgrade an OceanBase cluster from V4.3.5 BP2 or V4.4.0 to V4.5.0.
* Before you upgrade an OceanBase cluster from V4.4.0 BP1 to V4.5.0, you must upgrade the corresponding logservice cluster to V1.1.0.

**The meaning of the upgrade path diagram is described below:**

* For V4.2.x versions:

  * V4.0.0.0, V4.1.0.0, V4.1.0.2, and V4.2.0.0 can be upgraded to V4.2.1.11, and then to V4.2.5.7.
  * V4.2.2 to V4.2.4 can be directly upgraded to V4.2.5.7, or first upgraded to V4.2.5.0 to V4.2.5.6, and then to V4.2.5.7.
  * Barrier version: V4.2.1.11, V4.2.5.7.

* For V4.3.x versions:

  * Each V4.3.x version can be directly upgraded to V4.3.5.5.
  * V4.2.x and earlier versions cannot be upgraded to V4.3.x.

* For V4.4.x versions:

  * V4.4.0, V4.4.0.1, and V4.4.1 can be upgraded to V4.4.2.
  * V4.2.5 BP7 can be upgraded to V4.4.2.
