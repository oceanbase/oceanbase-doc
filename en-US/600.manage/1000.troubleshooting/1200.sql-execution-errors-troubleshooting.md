# Troubleshoot SQL execution errors

In database O&M, SQL execution errors are very common and can directly impact business. There are many reasons for SQL execution errors, such as failed database connection, insufficient user privileges, syntax errors, or data not meeting query conditions.

To help you quickly identify the root cause and efficiently resolve issues, the following sections summarize a clear and practical SQL error troubleshooting process. This process provides specific steps to increase problem-solving efficiency and minimize business impact, offering strong support for daily O&M work.

The SQL execution error troubleshooting process is shown in the following figure.

![SQL execution error troubleshooting process](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/V4xsql-execution-troubleshooting.png)

## Process

When an SQL execution error occurs, you can troubleshoot the issue based on the following process.

After an SQL execution error occurs, view the SQL error message. If the error message contains an error code, troubleshoot the issue based on the error code. If the error message does not contain an error code, determine the error type. The issue may be an application execution error or an SQL execution error:

1. If the issue is an application execution error, troubleshoot the application exception based on the error message. For more information, see [Application exceptions--error message does not contain OceanBase error code](1300.application-exception-without-ob-error-code.md) and [Application exceptions--error message contains OceanBase error code](1400.application-exception-with-ob-error-code.md).

2. If the issue is an SQL execution error, determine whether you can manually reproduce the error.

   1. If you cannot reproduce the error, search for information in the [Knowledge Base](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000324072) based on the SQL statement and troubleshoot the issue based on the information.
   2. If you can reproduce the error, reproduce the error scenario. Connect to the OceanBase cluster through port 2881 or 2883 based on the original scenario and execute the original SQL statement to reproduce the error scenario.

      After you reproduce the SQL error scenario, perform the following steps to collect information for troubleshooting.

      1. Execute the following statement to obtain `trace_id`.

         <main id="notice" type='notice'>
         <h4>Notice</h4>
         <p>You must execute the following statement immediately after the SQL error occurs; otherwise, the <code>trace_id</code> obtained by executing the following statement is not the one for the erroneous SQL statement. </p>
         </main>

         :::tab
         tab MySQL mode

         The following statement is executed to obtain `trace_id` in MySQL mode:

         ```shell
         obclient> SELECT last_trace_id();
         ```

         tab Oracle mode

         The following statement is executed to obtain `trace_id` in Oracle mode:

         ```shell
         obclient> SELECT last_trace_id() FROM DUAL;
         ```

         :::

      2. Obtain the host information based on the obtained `trace_id`.

         OceanBase clusters are generally deployed across multiple nodes. You can obtain the node where the SQL statement is actually executed based on the obtained `trace_id` and then filter logs based on the node.

         :::tab
         tab MySQL mode

         Execute the following statement in MySQL mode:

         ```shell
         obclient> SELECT * FROM oceanbase.GV$OB_SQL_AUDIT WHERE trace_id=last_trace_id;
         ```

         Replace `last_trace_id` with the obtained `trace_id`.

         tab Oracle mode

         Execute the following statement in Oracle mode:

         ```shell
         obclient> SELECT * FROM SYS.GV$OB_SQL_AUDIT WHERE trace_id=last_trace_id;
         ```

         Replace `last_trace_id` with the obtained `trace_id`.

         :::

         Based on the query result in the `GV$OB_SQL_AUDIT` view, the host corresponding to `svr_ip` is the one where the SQL statement is actually executed.

      3. Use the `ssh` command to log in to the host based on the obtained host information.

      4. Go to the log directory.

         For example, if the installation directory of OceanBase Database is `/home/admin/oceanbase`, the specific log path depends on your actual environment.

         ```shell
         cd /home/admin/oceanbase/log
         ```

      5. Execute the following command to filter out related information in the log.

         ```shell
         grep "${trace_id}" observer.log
         ```

         ```shell
         grep "${trace_id}" observer.log.xxx
         ```

         Replace `${trace_id}` with the obtained `trace_id`. Replace `observer.log.xxx` with a log file that contains timestamps. Replace `xxx` with the actual timestamp.

      6. Based on the information provided in the log, analyze the issue based on the error code or error message.

         For more information about logs and error codes, see [Overview of logs](../800.logging/100.logging-overview.md) and [Overview of error information](../../700.reference/900.error-code/600.error-code-of-mysql-mode/100.use-error-information-of-mysql-mode.md).

         If the information in the log is unclear, contact technical support for assistance.

## Case studies

The following case studies describe some typical scenarios where SQL execution errors occur.

:::tab
tab MySQL mode

* After the SQL error is reproduced, the error code is returned in the result.

  * When a `SELECT` statement contains many `OR` conditions, or many `AND`-connected `IN` conditions, or many `AND NOT` conditions, the database returns the error `-4013, No memory or reach tenant memory limit` when it executes the statement. For more information, see [Error -4013, Tenant memory full during SQL parsing](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000209941?back=kb).

* The error code is contained in the log.

  * When an `SQL` statement processes a `longtext` field, the error `ErrorCode=5098` is returned. For more information, see [SQL error: Varchar value is too long for the column](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000670003?back=kb).

  * When an `SQL` statement execution returns the error `error 4119 (RPC packet to send too long)`, and the `trace_id` is used to query `observer.log`, the information `obrpc packet payload execced its limit` is returned. For more information, see [Error -4119, RPC packet to send too long](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000210005?back=kb).

* Other error messages are contained in the log.

  * When the filter conditions of an SQL statement involve more than 64 fields, the error `-4002 Invalid argument` is returned. For more information, see [Error -4002 when filter conditions of an SQL statement involve more than 64 fields](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000450149?back=kb).

tab Oracle mode

* After the SQL error is reproduced, the error code is returned in the result.

  * A query statement contains columns `c1`, `c2`, and `c3`. Columns `c1` and `c2` hit indexes, and multiple `IN` expressions are on column `c1` or `c2`. `c1`, `c2`, and `c3` form a vector expression. When this statement is executed, it returns an `internal error` with the error code `ORA-00600`. For more information, see [SQL error 4016 with multiple IN expressions and vector expressions](https://www.oceanbase.com/knowledge-base/oceanbase-database-20000043623?back=kb).

* The error code is returned after the SQL statement is executed, and the error code is also contained in the log.

  * When an SQL statement is executed, it returns the error `Timeout` with the error code `ORA-00600`. For more information, see [SQL error timeout](https://www.oceanbase.com/knowledge-base/odc-1000000000262293?back=kb).

:::
