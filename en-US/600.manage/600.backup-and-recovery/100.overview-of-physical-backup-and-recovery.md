# Overview

Backup and restore is a core component of the high availability feature of OceanBase Database. It is mainly used to ensure data security, including preventing damage to the storage medium and user errors. If data is lost due to storage medium damage or user errors, you can restore the data.

## Overview

The backup and restore module of OceanBase Database provides backup, backup verification, restore, and cleanup features.

### Backup

OceanBase Database supports tenant-level physical backup. Physical backup consists of data backup and log archiving, which are two components. Here, the tenant refers to the user's User tenant. Physical backup is not supported for the `sys` tenant and Meta tenant.

Data backup refers to the feature of backing up data. This feature is divided into full backup and incremental backup:

* Full backup refers to the backup of all macroblocks.

* Incremental backup refers to the backup of macroblocks that have been added or modified since the last backup.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>Before performing a physical backup, you must enable the log archiving mode. </p>
</main>

The main data backed up by data backup includes the following:

* Tenant-related information, including tenant name, cluster name, time zone (timezone), replica distribution (locality), and tenant compatibility mode (MySQL or Oracle).

* All user table data

  <main id="notice" type='explain'>
  <h4>Note</h4>
  <p>Data backup backs up system variables and tenant configuration items, but does not back up cluster-level configuration items or private system table data. </p>
  </main>

Log archiving refers to the automatic archiving of log data. OBServer nodes periodically archive log data to the specified backup path. This process is fully automatic and does not require external triggers. After the log archiving service is enabled, the data dictionary is also archived.

### Backup verification

The backup verification feature of OceanBase Database is mainly used to solve the problems of the integrity and correctness of backup and archive data. Users can actively verify whether the backup set and archive logs are missing files, have physical data damage, or logical inconsistencies without performing actual restore operations.

Backup verification is divided into basic verification and physical verification based on the verification level. Specifically:

* Basic verification: only checks the completeness of the file list.

* Physical verification: checks the correctness and logical consistency of physical data.

Backup verification supports verification at different granularities, including verification of the entire backup and archive path, verification of specified backup sets or log archive pieces, and verification of specified paths across clusters.

### Restore

The overall architecture of physical restore is as follows:

1. Physical restore supports tenant-level restore and table-level restore.

   * Tenant-level restore: Tenant-level restore is the process of rebuilding a new tenant based on the backup data of an existing tenant. Tenant restore ensures global consistency across tables and partitions.

   * Table-level restore: Table-level restore is the process of restoring a user-specified table from backup data to an existing tenant. The existing tenant can be the same as the original tenant, a different tenant in the same cluster, or a tenant in a different cluster.

2. Tenant-level restore supports full restore and quick restore.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>Tenants restored by quick restore cannot be manually initiated for major compactions, cannot be backed up, and cannot be switched to or failover to the primary database. They can only exist as standby databases. </p>
   </main>

   * Full restore: Refers to restoring macroblock data and incremental logs. After all data is restored from the backup medium to the local environment, the restored tenant can provide services. The full restore process includes the Restore and Recover steps for tenant system tables and user tables. Restore refers to restoring the baseline data required for restore to the OBServer node of the target tenant. Recover refers to restoring the logs corresponding to the baseline to the corresponding OBServer node.

   * Quick restore: Refers to providing services to users without restoring macroblock data. This can reduce restore wait time and lower user costs.

3. Choose a restore point for your physical restore.

   * Full restore: No restore timestamp is specified.

   * Incomplete restore with specified SCN or timestamp: SCN is the precise version number in OceanBase Database. In Oracle mode, timestamps are precise to nanoseconds without any loss of precision. In MySQL mode, timestamps are precise to microseconds, with precision loss after microseconds.

For more information about the physical restore process, see [Restore process](../../700.reference/100.oceanbase-database-concepts/1000.high-data-reliability-and-availability/500.backup-and-recovery/400.recovery-architecture.md).

### Cleanup

OceanBase Database provides automatic and manual cleanup capabilities for backup data to allow users to handle backup data flexibly based on their business scenarios.

* Automatic cleanup: Based on the recovery window (recovery_window) mechanism. After users set the expiration time for backup data, the system periodically triggers cleanup tasks to remove expired backup sets and data archive pieces.

* Manual cleanup: Manual cleanup is divided into two types. The first type is manual cleanup of specified backup sets or log archive pieces. The second type is manual cleanup of all backup sets or data archive pieces in the entire path (data backup path or log archive path).

## Backup media requirements

OceanBase Database supports the following backup media: Alibaba Cloud OSS, NFS, Azure Blob, AWS S3, and object storage services that are compatible with the S3 protocol (such as Huawei OBS, Google GCS, and Tencent Cloud COS). Some of these backup media require meeting certain basic requirements before they can be used.

### SDK version requirements

In the current version, both the standalone node (SN) mode and the shared storage (SS) mode use obdal to access object storage. obdal is a unified framework for object storage based on OpenDAL. For more information about OpenDAL, see [OpenDAL](https://github.com/oceanbase/opendal).

In addition, the SDK version of the object storage service must be compatible with the version of the observer. The following table describes the compatible versions.

|                   | oss-c-sdk  | s3-cpp-sdk|
|-------------------|------------|-----------|
| 4.3.4 and later   | 3.11.2     | 1.11.156  |

## Directory structure

### Data backup directory

The data backup feature creates a directory at the backup destination and stores files of different types in the directory. The following table describes the directory structure.

```javascript
data_backup_dest
├── format.obbak                                            // The backup path's format information.
├── check_file
│   └── 1002_connect_file_20230111T193020.obbak             // The connectivity check file.
├── backup_sets                                             // The summary directory of data backup sets, which records all data backup sets.
│   ├── backup_set_1_full_end_success_20230111T193420.obbak // The end placeholder of a full backup.
│   ├── backup_set_1_full_start.obbak                       // The start placeholder of a full backup.
│   ├── backup_set_2_inc_start.obbak                        // The start placeholder of an incremental backup.
│   └── backup_set_2_inc_end_success_20230111T194420.obbak  // The end placeholder of an incremental backup.
└── backup_set_1_full                                        // The full backup set. Files ending with "full" indicate full backups, and files ending with "inc" indicate incremental backups.
    ├── file_list.0.obbak
    ├── backup_set_1_full_20230111T193330_20230111T193420.obbak // Placeholder for the start and end time of a full backup.
    ├── single_backup_set_info.obbak                        // The meta information of the current backup set.
    ├── tenant_backup_set_infos.obbak                       // The meta information of all full backups of the current tenant.
    ├── infos
    ├── logstream_1                                          // The data of log stream 1.
    └── logstream_1001                                       // The data of log stream 1001.
```

The data backup directory contains the following three types of data at the top level:

* `format.obbak`: The meta information of the backup path.

* `check_file`: The connectivity check file for the user data backup directory.

* `backup_sets`: The summary directory of data backup sets, which records all data backup sets.

* `backup_set_1_full`: This directory represents a data backup set. `backup_set_1` indicates that the `backup_set_id` of the backup set is `1`. If the directory name ends with `full`, the backup set is a full backup set. If it ends with `inc`, the backup set is an incremental backup set. Each data backup generates a corresponding backup set. After the data backup is completed, the backup set will no longer be modified.

  The following table describes the data in a data backup set.

  * `file_list.0.obbak`: The file records the files and directories in the current directory.

  * `backup_set_1_full_20230111T193330_20230111T193420.obbak`: This file records the ID, start time, and end time of the current backup set. This file is only for display.

  * `single_backup_set_info.obbak`: This file records the meta information of the current backup set, including the backup point and the dependent logs.

  * `tenant_backup_set_infos.obbak`: This file records the meta information of all backup sets of the current tenant.

  * `infos`: This directory records the meta information of the data backup set.

  * `logstream_1`: This directory records the data of log stream 1. Log stream 1 is the system log stream of the OceanBase Database tenant.

  * `logstream_1001`: This directory records the data of log stream 1001. Log streams with numbers greater than 1000 are user log streams of the OceanBase Database tenant.

### Cluster-level parameter backup directory

Every time a cluster-level parameter backup is initiated, the system generates a backup file in the specified directory. The following table describes the directory structure.

```javascript
cluster_parameters_backup_dest
├── cluster_parameter.20240710T103610.obbak # The information of non-default cluster-level parameters. The file name is in the format of `cluster_parameter.[timestamp]`.
└── cluster_parameter.20241018T140609.obbak
```

### Log archive directory

For backup media such as NFS, OSS, and Azure Blob, the log archive directory is created in the destination, and the types of files saved in each directory are as follows:

```javascript
log_archive_dest
    ├── check_file
    │   └── 1002_connect_file_20230111T193049.obbak // Connectivity check file
    ├── format.obbak                                // Metadata of the backup path
    ├── rounds                                      // Placeholder directory for Rounds
    │   └── round_d1002r1_start.obarc               // Placeholder for the start of a Round
    ├── pieces                                      // Placeholder directory for Pieces
    │   ├── piece_d1002r1p1_start_20230111T193049.obarc // Placeholder for the start of a Piece, named as piece_DESTID_ROUNDID_PIECEID_start_DATE
    │   └── piece_d1002r1p1_end_20230111T193249.obarc   // Placeholder for the end of a Piece, named as piece_DESTID_ROUNDID_PIECEID_end_DATE
    └── piece_d1002r1p1                             // Directory for a Piece, named as piece_DESTID_ROUNDID_PIECEID
        ├── file_list.0.obarc
        ├── piece_d1002r1p1_20230111T193049_20230111T193249.obarc // Records the continuous interval of the Piece
        ├── checkpoint
        ├── single_piece_info.obarc                 // Metadata of the Piece
        ├── tenant_archive_piece_infos.obarc        // Metadata of all frozen Pieces before the current Piece
        ├── file_info.obarc                         // List of all log stream files
        ├── logstream_1                             // Log stream 1
        └── logstream_1001                          // Log stream 1001
```

In the log archive directory above, the top-level directory contains the following three types of data:

* `format.obbak`: Records the metadata of the archive path, including information such as the tenant using the path.

* `check_file`: Used for connectivity check of the user log archive directory.

* `rounds`: A summary list of all Rounds in the log archive, recording the list of all Rounds.

* `pieces`: A summary list of all Pieces in the log archive, recording the list of all Pieces.

* `piece_d1002r1p1`: The directory for a Piece in the log archive, named as `piece_DESTID_ROUNDID_PIECEID`. Here, `DESTID` refers to the id corresponding to `log_archive_dest`; `ROUNDID` refers to the id of the log archive Round, which is a monotonically increasing integer; and `PIECEID` refers to the `piece_id` of the log archive Piece, which is also a monotonically increasing integer.

  In a log archive Piece directory, the following data is included:

  * `file_list.0.obarc`: This file records the files and directories contained in the current directory.

  * `piece_d1002r1p1_20230111T193049_20230111T193249.obarc`: This file shows the id, start, and end times of the current Piece and is only for informational purposes.

  * `checkpoint`: This directory records the archive point of the active Piece. The ObArchiveScheduler module regularly updates the archive point information in this directory.

  * `single_piece_info.obarc`: This file records the metadata of the current Piece.

  * `tenant_archive_piece_infos.obarc`: This file records the metadata of all frozen Pieces in the current tenant.

  * `file_info.obarc`: This file records the list of log stream files in the Piece.

  * `logstream_1`: This directory records the log files of log stream 1, which is the system log stream of the OceanBase Database tenant.

  * `logstream_1001`: This directory records the log files of log stream 1001, which is the user log stream of the OceanBase Database tenant.

## Differences between V3.x/V2.x features and V4.x features

### Log archiving

| Feature             | V3.x/V2.2x                                                     |  V4.x                                               |
|-------------------|---------------------------------------------------------------|-----------------------------------------------------|
| Archiving level     | Cluster level                                                  | Tenant level                                         |
| Archiving granularity | Partition level                                                | Log stream level                                      |
| Permissions         | You can only operate as the `sys` tenant. For example, you can set the archiving path, enable archiving, and check the archiving progress. | You can operate as the `sys` tenant or as an administrator of a user tenant. |
| Usage               | <ol><li>Use the <code>ALTER SYSTEM SET BACKUP_DEST</code> statement to set the cluster-level backup path.</li> <li>Use the <code>ALTER SYSTEM SET BACKUP_DEST_OPTION</code> statement to set the piece switching cycle. By default, the piece switching feature is disabled.</li></ol> | Use the <code>ALTER SYSTEM SET LOG_ARCHIVE_DEST</code> statement to set the tenant-level archiving path and the piece switching cycle. By default, the piece switching cycle is `1d` (1 day). The log archiving path and the data backup path can be independently configured. |
| Piece switching     | The piece switching feature is disabled by default. You can disable it. | The piece switching feature is enabled by default. |
| Method to set the archive lag target | Use the `ALTER SYSTEM SET LOG_ARCHIVE_CHECKPOINT_INTERVAL` statement. | Use the `ALTER SYSTEM SET ARCHIVE_LAG_TARGET` statement. |
| Result of executing the `ALTER SYSTEM ARCHIVELOG` statement in the `sys` tenant | Enables archiving for all tenants in the current cluster. After archiving is enabled, new tenants are automatically enabled for archiving. | Enables archiving for all tenants in the current cluster. After archiving is enabled, new tenants are not automatically enabled for archiving. |
| Log compression     | Use the `ALTER SYSTEM SET BACKUP_LOG_ARCHIVE_OPTION` statement. | Not supported. |
| Views               | The following three views are related to archiving: <ul><li>CDB_OB_BACKUP_ARCHIVELOG</li> <li>CDB_OB_BACKUP_ARCHIVELOG_SUMMARY</li> <li>CDB_OB_BACKUP_PIECE_FILES</li></ul> | The following eight views are related to archiving: <ul><li>CDB_OB_ARCHIVELOG</li> <li>DBA_OB_ARCHIVELOG</li> <li>CDB_OB_ARCHIVELOG_SUMMARY</li> <li>DBA_OB_ARCHIVELOG_SUMMARY <li>CDB_OB_ARCHIVE_DEST</li> <li>DBA_OB_ARCHIVE_DEST</li> <li>CDB_OB_ARCHIVELOG_PIECE_FILES</li> <li>DBA_OB_ARCHIVELOG_PIECE_FILES</li></ul> |
| Media requirements  | The media must be SSD.                                           | The media can be HDD or SSD.                           |
| Number of archive files | The number of files is proportional to the number of partitions. In a scenario with millions of partitions, a large number of small files are generated. | The number of files is small and not related to the number of partitions. No large number of small files is generated. |
| Standby archive      | Not supported.                                                  | Supported.                                            |

### Data backup

| Feature             | V3.x/V2.2x                                                       |  V4.x                                               |
|-------------------|------------------------------------------------------------------|------------------------------------------------------|
| Backup level           |  Cluster level                                                          | Tenant level                                              |
| Permissions               | You can perform backup operations only under the `sys` tenant, such as setting the backup path, initiating a backup, and viewing the backup progress.   | You can perform backup operations under the `sys` tenant or by using an admin user of a user tenant. |
| Backup path setting method  | You can set the cluster-level backup path by using the `ALTER SYSTEM SET BACKUP_DEST` statement.       |  You can set the tenant-level backup path by using the `ALTER SYSTEM SET DATA_BACKUP_DEST` statement. The data backup path and log archive path can be configured independently. |
| Specify a path for data backup  |  You can initiate data backup by executing the `ALTER SYSTEM BACKUP TENANT tenant_name_list TO backup_destination;` statement under the `sys` tenant. | Not supported                                   |
| BACKUP PLUS ARCHIVELOG feature | Not supported                                                  | Supported                                                  |
| Data space expansion           | Snapshots are retained during backup, which may cause storage space expansion.                       | Snapshots are not retained, so no storage space expansion occurs.                            |
| Backup from standby database           | Not supported                                                          | Supported                                                  |
| Views               | The following five views are related to backup: <ul><li>CDB_OB_BACKUP_JOB_DETAILS</li> <li>CDB_OB_BACKUP_SET_DETAILS</li> <li>CDB_OB_BACKUP_SET_EXPIRED</li> <li>CDB_OB_BACKUP_PROGRESS</li> <li>CDB_OB_BACKUP_SET_FILES</li></ul> | The following 10 views are related to backup: <ul><li>CDB_OB_BACKUP_JOBS</li> <li>DBA_OB_BACKUP_JOBS</li> <li>CDB_OB_BACKUP_JOB_HISTORY</li> <li>DBA_OB_BACKUP_JOB_HISTORY</li> <li>CDB_OB_BACKUP_TASKS</li> <li>DBA_OB_BACKUP_TASKS</li> <li>CDB_OB_BACKUP_TASK_HISTORY</li> <li>DBA_OB_BACKUP_TASK_HISTORY</li> <li>CDB_OB_BACKUP_SET_FILES</li> <li>DBA_OB_BACKUP_SET_FILES</li></ul>  |

### Physical restore

| Feature             | V3.x/V2.2x                                                       |  V4.x                                               |
|-------------------|------------------------------------------------------------------|-----------------------------------------------------|
| Data path           | You can specify the cluster-level backup path in the restore command.                                     | You need to specify both the data backup path and the log archive path.                |
| Restore concurrency setting     | Before initiating a restore command, you can set the restore concurrency by using the `ALTER SYSTEM SET RESTORE_CONCURRENCY` statement. | You can specify the `concurrecy` parameter in the restore command.                       |
| Key management       |<ol><li>Internal mode does not require key information. </li> <li>In KMS mode, if the original service is accessible, no key information is required. </li></ol> | <ol><li>You need to separately back up the primary key information. </li> <li>You need to specify the primary key address during restore. </li></ol> |
| Tenant role after restore | The primary tenant, which is the primary database.                                                   | The standby tenant, which is the standby database.                                       |
| Upgrade              | The tenant is automatically upgraded during restore.                                           | After restore, you need to manually upgrade the tenant.                             |
| Table-level restore          | Supported. You can restore a table only to a new tenant (a tenant created during restore). You cannot restore a table to an existing tenant.           | Supported starting from V4.2.1. You can restore a table only to an existing tenant. You cannot restore a table to a new tenant (a tenant created during restore).       |
| Fast restore          | Not supported                                                            | Supported starting from V4.3.3                                  |
| Use the `ADD RESTORE SOURCE` statement to restore | Supported                                            | Not supported                                               |
