# Schema recovery in table-level restore

After you perform a table-level restore, the restored schema information and its description are as follows:

| Schema  | Restorable? | Description                                                  |
|---------------|-----------|--------------------------------------------------------|
| Database      |    No      | When you perform a table-level restore, the corresponding database in the target tenant must exist. Otherwise, the restore will fail. For example, suppose the backed-up table belongs to a database named `INFO`. If you do not use the `REMAP TABLE` command (which allows you to rename the table to another database in the target tenant), the system will restore the table to the `INFO` database in the target tenant.      |
| Tablespace    |    No      | When you perform a table-level restore, the corresponding tablespace in the target tenant must exist. Otherwise, the restore will fail. For example, suppose the backed-up table belongs to a tablespace named `TS`. If you do not use the `REMAP TABLE` command (which allows you to rename the table to another tablespace in the target tenant), the system will restore the table to the `TS` tablespace in the target tenant.       |
| Tablegroup（Table group）  |     No      | When you perform a table-level restore, the corresponding table group in the target tenant must exist. Otherwise, the restore will fail. For example, suppose the backed-up table belongs to a table group named `TG`. If you do not use the `REMAP TABLE` command (which allows you to rename the table to another table group in the target tenant), the system will restore the table to the `TG` table group in the target tenant. |
| Table            |    Yes      | Only user tables can be restored. Columnstore and hybrid row-columnstore tables can be restored. System tables and temporary tables cannot be restored individually. |
| Partition          |    Yes      | N/A |
| Tablet        |    Yes      | N/A |
| Column            |    Yes      | N/A |
| Constraint          |    Yes      | The following constraints can be restored:<ul><li>`NOT NULL` constraint </li> <li>`UNIQUE KEY` constraint </li> <li>`PRIMARY KEY` constraint <main id="notice" type='notice'><h4>Notice</h4><p>In Oracle mode, if there are duplicate <code>PRIMARY KEY</code> constraint names, the entire table restore will fail. </p></main></li> <li>`CHECK` constraint</li></ul> <main id="notice" type='explain'><h4>Note</h4><p>If the constraint name is user-defined and already exists in the target tenant, it will not be restored. </p></main> |
| Foreign key          |    Yes      | During foreign key restoration, the system checks the integrity of the foreign key constraints. If a foreign key references a non-existent row, the foreign key restoration will fail. |
| View          |    No      | When you restore a table, the views associated with the table will not be restored. |
| Materialized view      |    No      | Materialized views associated with the table cannot be restored. |
| Materialized view log  |    No      | Materialized view logs associated with the table cannot be restored. |
| Local index      |    Yes      | N/A |
| Global index      |    Yes      | N/A |
| Full-text index      |    Yes      | N/A |
| JSON multi-value index |    Yes      | N/A |
| Vector index      |    Yes      | N/A |
| Spatial index      |    Yes      | When you perform a table-level restore, the coordinate system will not be restored. If the target tenant does not have a reference coordinate system, the spatial index will not be restored. If the target tenant has a coordinate system, the spatial index will be restored. |
| Auto-increment column        |    Yes      | N/A |
| Table without a primary key      |    Yes      | N/A |
| Statistics      |    Yes      | N/A |
| Trigger        |    Yes      | <ul><li> If the table is restored by its original name, the triggers associated with the table will be restored. Specifically:<ul><li> In Oracle mode, if the user who owns the trigger does not exist, the trigger restoration will fail. </li> <li> In MySQL mode, if the database that owns the trigger does not exist, the trigger restoration will fail. </li></ul></li> <li> If the table is renamed and restored by its new name, the triggers associated with the table will not be restored. </li></ul> |
| Function, stored procedure, and package |    No  | When you restore a table, the functions, stored procedures, and packages associated with the table will not be restored. |
| Synonym        |    No      | When you restore a table, the synonyms associated with the table will not be restored. |
| LOB          |    Yes      | N/A |
| Sequence     |    No      | When you restore a table, the sequences that the table depends on will not be restored. |
