# Perform table-level restore

This topic describes how to perform a table-level restore.

## Table-level restore

Table-level restore is a physical restore process that involves restoring data to an auxiliary tenant. This process can be performed in two ways: full restore and quick restore.

The [table-level restore process](../../../700.reference/100.oceanbase-database-concepts/1000.high-data-reliability-and-availability/500.backup-and-recovery/400.recovery-architecture.md) has three stages: physical restore of an auxiliary tenant, cross-tenant table import, and cleanup of the auxiliary tenant. In previous versions, the physical restore of an auxiliary tenant stage used the full restore method. This method requires all data from the source tenant to be restored to the auxiliary tenant from the backup media. This approach has two issues:

1. You must reserve sufficient CPU, memory, and disk resources on the cluster to support the temporary auxiliary tenant.
2. The process of restoring all data from the backup media to the auxiliary tenant consumes a significant amount of time and network bandwidth.

To address these issues, OceanBase Database now supports the quick restore method for restoring an auxiliary tenant. With this method, you only need to restore a read-only auxiliary tenant. User data within the tenant does not need to be restored from the backup media. Instead, during the cross-tenant table import stage, the backup macroblocks of the tables to be restored can be directly read from the backup media. This approach reduces the resource usage of the temporary auxiliary tenant during table-level restore and shortens the time required for the restore task.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>In the current version, the restore method used depends on the cluster deployment mode:
<ul><li>If the cluster is deployed in Shared-Nothing (SN) mode and the data version of the backup set used for restore is V4.3.5.0 or later, the system automatically uses the quick restore method to restore the auxiliary tenant during table-level restore. However, if the cluster is deployed in SN mode and the data version of the backup set used for restore is earlier than V4.3.5.0, the full restore method is still used to restore the auxiliary tenant.<p>You can check the data version of the backup set used for restore by querying the <code>TENANT_COMPATIBLE</code> column in the <code>CDB_OB_BACKUP_SET_FILES</code> view (sys tenant) or <code>DBA_OB_BACKUP_SET_FILES</code> view (user tenant).</p></li>
<li>If the cluster is deployed in Shared-Storage (SS) mode, the full restore method is still used to restore the auxiliary tenant during table-level restore.</li></ul>
</p>
</main>

After completing the table-level restore, you can query the `RESTORE_TYPE` column in the `CDB_OB_RESTORE_HISTORY` view of the `sys` tenant to confirm the restore method used for the auxiliary tenant.

## Limitations and considerations

* Only user tables can be restored. Temporary tables, views, materialized views, materialized view logs, and indexes cannot be restored individually.

* Tables with full-text indexes, JSON multi-value indexes, or vector indexes can be restored.

* Columnstore and hybrid row-columnstore tables can be restored.

* The compatibility of the source and target tenants must be consistent. For example, both tenants must be Oracle compatible or both must be MySQL compatible.

* The specified table name must match the actual table name stored in the system. For example, if a table named `test` is created in an Oracle mode tenant, but the actual stored table name is `TEST`, you must specify `TEST` when restoring the table. Otherwise, the system will report an error indicating that the table does not exist.

* Similar to tenant-level restore, table-level restore currently only supports restoring tables from a lower version backup set to the same or a higher version. Reverse restore between minor versions within the same version is not supported. For more information about the supported backup data versions for tenant-level restore, see [Preparations before restore](../600.restore-data/100.preparation-before-recovery.md).

* Table-level restore not only restores the table but also many associated pieces of information. However, some information is not restored. For details about the restorable information, see the **Schema information to be restored** section.

## Prerequisites

Since an auxiliary tenant is required during the table restore process, you need to create the necessary resource pools for the auxiliary tenant in the cluster where the target tenant is located before performing the table restore. For detailed operations on creating the required resource pools for the auxiliary tenant, see [Preparations before table-level restore](100.preparation-before-table-recovery.md).

## Procedure

1. Log in to the `sys` tenant of the cluster where the target tenant is located as the `root` user.

2. (Optional) If the backup data used for restoring the specified table is configured with encryption, configure the encryption information of the backup set.

You need to set the password for restoring the backup only when you set a password for data backup.

```sql
   SET DECRYPTION IDENTIFIED BY 'password';
   ```

In the preceding statement, replace `password` with the password added during backup. If the passwords for full backup and incremental backup are different, you need to specify multiple passwords, separated by commas (,). The password for full backup is specified in the preceding position, and the password for incremental backup is specified in the following position.

Here is an example when the passwords for full backup and incremental backup are the same:

```sql
   SET DECRYPTION IDENTIFIED BY '******';
   ```

Here is an example when the passwords for full backup and incremental backup are different:

```sql
   SET DECRYPTION IDENTIFIED BY '******','******';
   ```

3. (Optional) Set the parallelism for table-level restore.

* Single-table parallel restore

Before performing a table-level restore, you can set the concurrency by using the [recover_table_dop](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7325.recover_table_dop.md) parameter. After the concurrency is set, the system uses the parallelism in the following two stages:

* Main table data restore stage: The system splits each partition of the main table into multiple subtasks and executes the subtasks in parallel.
      * Index restore stage: The system rebuilds the indexes of the table based on the restored main table data by using parallel execution (Parallel Execution, PX).

Syntax:

```sql
      -- tenant_name specifies the target tenant.
      ALTER SYSTEM SET recover_table_dop=INT_VALUE tenant=tenant_name;
      ```

* Multi-table parallel restore (optional)

Before performing a multi-table table-level restore, you can set the concurrency by using the [recover_table_concurrency](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7320.recover_table_concurrency.md) parameter. After the concurrency is set, multiple tables can be restored in parallel, improving the restore performance.

Syntax:

```sql
      -- tenant_name specifies the target tenant.
      ALTER SYSTEM SET recover_table_concurrency=INT_VALUE tenant=tenant_name;
      ```

* Set the number of worker threads for main table data restore on each observer node of the tenant.

After you set the single-table parallelism `recover_table_dop` and multi-table parallelism `recover_table_concurrency`, you also need to set the number of worker threads for main table data restore on each observer node of the tenant by using the [ddl_thread_score](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/1850.ddl_thread_score.md) parameter. During the cross-tenant table import stage of table-level restore, the main table data restore depends on specific DAG threads on the target tenant.

Syntax:

```sql
      -- tenant_name specifies the target tenant.
      ALTER SYSTEM SET ddl_thread_score=INT_VALUE tenant=tenant_name;
      ```

<main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>
      <ul>
        <li><b>During the physical restore auxiliary tenant execution stage</b>, you can dynamically adjust the restore parallelism by modifying the <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3400.ha_high_thread_score.md">ha_high_thread_score</a> parameter. The adjustment takes effect immediately. The name of the auxiliary tenant can be obtained from the <a href="../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/10200.o-cdb_ob_recover_table_jobs-of-sys-tenant.md">CDB_OB_RECOVER_TABLE_JOBS</a> view. For more information, see <a href="../600.restore-data/200.initiate-the-tenant-restore.md">Physical Restore</a>.</li>
        <li><b>During the cross-tenant table import stage</b>, you can dynamically adjust the restore parallelism of multiple tables or single tables by modifying the <code>recover_table_concurrency</code> or <code>recover_table_dop</code> parameter of the target tenant. The adjustment takes effect immediately.</li>
      </ul>
      </p>
      </main>

4. Run the following command to restore the specified table.

The SQL statement is as follows:

```sql
   ALTER SYSTEM 
   RECOVER TABLE table_name_list 
   TO [TENANT [=]] dest_tenant_name 
   FROM uri 
   [UNTIL {TIME='timestamp'} | {SCN=scn} ]
   WITH 'restore_option' 
   [WITH KEY FROM 'backup_key_path' ENCRYPTED BY 'password']
   [REMAP TABLE remap_table_name_list] 
   [REMAP TABLEGROUP remap_tablegroup_list] 
   [REMAP TABLESPACE remap_tablespace_list]
   [DESCRIPTION [=] description];
   ```

The parameters are described as follows:

* `table_name_list`: the name of the table to be restored, in the `database_name.table_name1,database_name.table_name2,...` format. Separate multiple tables with commas (,).

When you specify `database_name` and `table_name`:

* `table_name` must be consistent with the actual table name stored in the system. For example, if you create a table named `test` in an Oracle mode tenant, the system actually stores the table as `TEST`. Therefore, you must specify the table name as `TEST` during restore. Otherwise, the system returns an error indicating that the table does not exist.

* If `database_name` or `table_name` contains special characters, enclose the `database_name` or `table_name` with special characters in backticks (``).

* If you want to restore all tables in a database, you can specify `database_name.*`.

* If you want to restore all user tables in the tenant, you can specify `*.*`.

* `dest_tenant_name`: the name of the tenant to which the table is to be restored. You can restore a table only to a user tenant, not to the `sys` tenant or Meta tenant.

* `uri`: the path for data backup and log archiving. The parameters are the same as those of the tenant-level physical restore command. If the data backup is initiated by using the PLUS ARCHIVELOG mode, specify only one path. Otherwise, specify at least two paths for data backup and log archiving, for example: `'file:///backup/archive, file:///backup/data'`.

* `{TIME='timestamp'} \| {SCN=scn}`: the restore endpoint, which specifies the point in time or SCN to which the data is to be restored. The endpoint must be included in the restored data. When you specify `TIME` or `SCN`, you must use `=` to connect the specified value. If you do not specify the `UNTIL` clause, the data is restored to the latest endpoint.

* `restore_option`: specifies the `pool_list`, `locality`, `primary_zone`, and `concurrency` parameters of the auxiliary tenant. The parameters are separated by `&`. We recommend that you specify the same values for `locality` and `primary_zone` as those for the source tenant.

The `concurrency` parameter specifies the number of CPU cores allocated to the auxiliary tenant. If you do not specify this parameter, the value of `MAX_CPU` is used. For example, in this topic, the value of `MAX_CPU` is 16.

For more information about the parameters, see [Table-level restore parameters](600.parameters-of-the-table-recovery.md).

* `WITH KEY FROM 'backup_key_path' ENCRYPTED BY 'password'`: specifies the key backup information of the encrypted tenant. This clause is required only when the source tenant is configured with transparent encryption.

* `backup_key_path`: the backup path of the key.

* `password`: the encryption password set during key backup.

For more information about key backup, see **Backup key** in [Preparations before data backup](../400.data-backup/100.preparation-before-data-backup.md).

* `remap_table_name_list`: specifies the new name of the restored table. You can rename only the table without changing the database to which the table belongs. You can also keep the table name unchanged and rename the database to which the table belongs. You can also rename the table and the database to which the table belongs. The source object and the renamed object are separated by a colon ( : ). The following are some examples:

* Rename the `student` table to `student2` without changing the database to which the table belongs: `REMAP TABLE school.student:student2`.

If the database to which the table belongs is not changed, the system will restore the table to the database with the same name in the target tenant. If the database with the same name does not exist in the target tenant, the table cannot be restored.

* Keep the `student` table name unchanged and rename the database to which the table belongs from `school` to `college`: `REMAP TABLE school.student:college.student`.
     * Rename the `student` table to `student2` and rename the database to which the table belongs from `school` to `college`: `REMAP TABLE school.student:college.student2`.
     * Restore all tables under the `school` database to the `college` database: <code>REMAP TABLE school.`*`:college.`*`</code>

<main id="notice" type='explain'>
     <h4>Note</h4>
     <p>If the <code>database_name</code> or <code>table_name</code> to be renamed contains special characters, the <code>database_name</code> or <code>table_name</code> containing special characters must be enclosed in backticks (``). </p>
     </main>

* `remap_tablegroup_list`: specifies the new name of the table group to which the table belongs. If the source table is bound to a table group, the system will restore the table to the table group with the same name in the target tenant. If the table group with the same name does not exist in the target tenant, the table cannot be restored. If the target tenant has other table groups, you can restore the table to other table groups by using this clause. The source object and the renamed object are separated by a colon ( : ).

For example, restore all tables in the source table group `tg1` to the target table group `newtg1`: `REMAP TABLEGROUP tg1:newtg1`.

* `remap_tablespace_list`: specifies the new name of the table space to which the table belongs. A table space is a logical unit in OceanBase Database, which is mainly used for data encryption. If the source table is bound to a table space, the system will restore the table to the table space with the same name in the target tenant. If the table space with the same name does not exist in the target tenant, the table cannot be restored. If the target tenant has other table spaces, you can restore the table to other table spaces by using this clause. The source object and the renamed object are separated by a colon ( : ).

For example, restore all tables in the source table space `ts1` to the target table space `newts1`: `REMAP TABLESPACE ts1:newts1`.

For more information about the table-level restore parameters, see [Table-level restore parameters](600.parameters-of-the-table-recovery.md).

Restore the `tbl1` and `tbl2` tables in the `infodb` database to the `infodb` database in the target tenant, rename the `tbl1` table to `newtbl`, and redirect the table group and table space of the `tbl1` table to `newtg1` and `newts1`, respectively. Example:

```sql
   ALTER SYSTEM 
   RECOVER TABLE infodb.tbl1,infodb.tbl2 
   TO TENANT oracle001 
   FROM 'file:///data/nfs/backup/data,file:///data/nfs/backup/archive' 
   UNTIL TIME='2023-09-30 00:00:00' 
   WITH 'pool_list=restore_pool'
   REMAP TABLE infodb.tbl1:newtbl 
   REMAP TABLEGROUP tg1:newtg1
   REMAP TABLESPACE ts1:newts1;
   ```

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><ul><li>If the table data is successfully restored, the table is considered to be successfully restored. Indexes, constraints, and other associated schemas may fail to be restored. </li><li>After a table-level restore is completed, we recommend that you restore the <code>ddl_thread_score</code>, <code>recover_table_concurrency</code>, and <code>recover_table_dop</code> parameters to their original values. Otherwise, the parallel parameters will be used for subsequent table-level restores. </li><li>The restoration of triggers associated with tables during a table-level restore will follow these rules: <ul><li>If the table name is not renamed in the table-level restore command (i.e., the table is restored with its original name), the triggers associated with the table will be restored. </li><li>If the table name is renamed in the table-level restore command (i.e., the table is restored with the new name), the triggers associated with the table will not be restored. </li></ul></li></ul></p>
  </main>

## What to do next

* After you initiate the table-level recovery, you can view the progress and results of the table-level recovery in the view. For more information, see [View the progress of table-level recovery](400.view-the-table-recovery-progress.md) and [View the results of table-level recovery](500.view-the-table-recovery-history.md).

* After the table-level recovery is completed, you also need to execute the following commands in the cluster where the auxiliary tenant is located to manually release the resource pool created for the auxiliary tenant.

    ```sql
    DROP RESOURCE POOL restore_pool;
    ```

    In this command, `restore_pool` indicates the name of the resource pool created for the auxiliary tenant during the preparation phase of the recovery.

    For more information about how to delete a resource pool, see [Delete a resource pool](../../200.tenant-management/600.common-tenant-operations/1500.resource-pool-management/600.delete-resource-pool.md).
