# Perform table-level restore

This topic describes how to perform a table-level restore.

## Table-level restore

In the physical restore auxiliary tenant phase of table-level restore, OceanBase Database supports full restore and quick restore.

[Table-level restore process](../../../700.reference/100.oceanbase-database-concepts/1000.high-data-reliability-and-availability/500.backup-and-recovery/400.recovery-architecture.md) consists of three phases: physical restore auxiliary tenant, cross-tenant table import, and cleanup auxiliary tenant. In earlier versions, the physical restore auxiliary tenant phase used full restore. This method requires restoring all data from the source tenant to the auxiliary tenant from the backup media. This method has the following two issues:

1. You must reserve sufficient CPU, memory, and disk resources in the cluster to support the temporary restore of the auxiliary tenant.
2. The process of restoring all data from the backup media to the auxiliary tenant consumes a large amount of time and network bandwidth.

To solve these issues, OceanBase Database supports the quick restore method for restoring the auxiliary tenant. When using the quick restore method, only a read-only auxiliary tenant is restored. User data in the tenant does not need to be restored from the backup media. Instead, during the cross-tenant table import phase, the backup macroblock data of the table to be restored is directly read from the backup media. This method reduces the resource usage for temporarily restoring the auxiliary tenant during table-level restore and shortens the recovery task time.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>The restore method varies depending on the cluster deployment mode:
<ul><li>If the cluster uses the Shared-Nothing (SN) mode, the system automatically uses the quick restore method to restore the auxiliary tenant during table-level restore. </li>
<li>If the cluster uses the Shared-Storage (SS) mode, the system still uses the full restore method to restore the auxiliary tenant during table-level restore. </li></ul>
</p>
</main>

## Limitations and considerations

* Only user tables can be restored. Temporary tables, views, materialized views, materialized view logs, and indexes cannot be restored separately.

* Vector indexes cannot be restored when tables are restored.

* Columnstore and hybrid row-column store tables can be restored.

* The source tenant and target tenant must be compatible. For example, both must be Oracle-compatible tenants or both must be MySQL-compatible tenants.

* The specified table name must be the same as the actual table name stored in the system. For example, if you create a table named `test` in an Oracle-compatible tenant, the actual table name stored in the system is `TEST`. Therefore, specify `TEST` when restoring the table. Otherwise, the system will report an error indicating that the table does not exist.

* Like tenant-level restore, table-level restore only supports restoring tables from backup data of a lower version to the same version or a later version. Reverse restore between minor versions within the same major version is not supported. For more information about the backup data versions supported by tenant-level restore, see [Preparations before restore](../600.restore-data/100.preparation-before-recovery.md).

* In addition to restoring the table, many related information will also be restored during table-level restore. However, some information will not be restored. For more information about the restorable information, see **Schema information to be restored** in this section.

## Prerequisites

Since the auxiliary tenant is used during the restore of the specified table, you must create a resource pool for the auxiliary tenant in the cluster where the target tenant is located before you perform table restore. For more information about how to create a resource pool for the auxiliary tenant, see [Preparations before table restore](100.preparation-before-table-recovery.md).

## Procedure

1. Log in to the `sys` tenant of the target tenant cluster as the `root` user.

2. (Optional) If the backup data used to restore the specified table is encrypted, you must configure the encryption information of the backup set.

   You need to set the restore password only when you added a password during data backup.

   ```sql
   SET DECRYPTION IDENTIFIED BY 'password';
   ```

   In this statement, `password` must be replaced with the password added during backup. If the passwords for full backup and incremental backup are different, you must enter multiple passwords, which are separated with commas (,). The full backup password is entered first, and the incremental backup password is entered later.

   If the passwords for full backup and incremental backup are the same, the statement is as follows:

   ```sql
   SET DECRYPTION IDENTIFIED BY '******';
   ```

   If the passwords for full backup and incremental backup are different, the statement is as follows:

   ```sql
   SET DECRYPTION IDENTIFIED BY '******','******';
   ```

3. (Optional) Set the table-level restore parallelism.

   * Single-table parallel restore

      Before you execute table-level restore, you can set the concurrency by using the [recover_table_dop](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7325.recover_table_dop.md) parameter. After you set the concurrency, the system uses the parallelism in the following two phases:

      * Primary table data restore phase: The system splits each partition of the primary table into multiple subtasks and restores the subtasks in parallel.
      * Index restore phase: The system rebuilds the table indexes by using the recovered primary table data and parallel execution (PX).

      The syntax is as follows:

      ```sql
      -- tenant_name is the name of the target tenant.
      ALTER SYSTEM SET recover_table_dop=INT_VALUE tenant=tenant_name;
      ```

   * Multi-table parallel restore (optional)

      Before you execute multi-table table-level restore, you can set the concurrency by using the [recover_table_concurrency](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7320.recover_table_concurrency.md) parameter. After you set the concurrency, multiple tables can restore data in parallel, improving the restore performance.

      The syntax is as follows:

      ```sql
      -- tenant_name is the name of the target tenant.
      ALTER SYSTEM SET recover_table_concurrency=INT_VALUE tenant=tenant_name;
      ```

   * Set the number of main table data restore worker threads on each observer node of a tenant

      After you set the single-table parallelism `recover_table_dop` and multi-table parallelism `recover_table_concurrency`, you also need to set the number of worker threads on each observer node of the tenant by using the [ddl_thread_score](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/1850.ddl_thread_score.md) parameter. The main table data restore phase of table-level restore across tenants depends on the specific DAG threads of the target tenant.

      The syntax is as follows:

      ```sql
      -- tenant_name is the name of the target tenant.
      ALTER SYSTEM SET ddl_thread_score=INT_VALUE tenant=tenant_name;
      ```

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>
      <ul>
        <li><b>During the physical restore auxiliary tenant execution phase</b>, you can dynamically adjust the restore parallelism by adjusting the <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3400.ha_high_thread_score.md">ha_high_thread_score</a> parameter. The adjustment takes effect immediately after it is made. You can view the name of the auxiliary tenant from the <a href="../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/10200.o-cdb_ob_recover_table_jobs-of-sys-tenant.md">CDB_OB_RECOVER_TABLE_JOBS</a> view. For more information, see <a href="../600.restore-data/200.initiate-the-tenant-restore.md">Physical restore</a>.</li>
        <li><b>During the cross-tenant table import phase</b>, you can dynamically adjust the multi-table or single-table restore parallelism by adjusting the <code>recover_table_concurrency</code> or <code>recover_table_dop</code> parameter of the target tenant. The adjustment takes effect immediately after it is made.</li>
      </ul>
      </p>
      </main>

4. Execute the following statement to restore the specified table.

   The SQL statement is as follows:

   ```sql
   ALTER SYSTEM 
   RECOVER TABLE table_name_list 
   TO [TENANT [=]] dest_tenant_name 
   FROM uri 
   [UNTIL {TIME='timestamp'} | {SCN=scn} ]
   WITH 'restore_option' 
   [WITH KEY FROM 'backup_key_path' ENCRYPTED BY 'password']
   [REMAP TABLE remap_table_name_list] 
   [REMAP TABLEGROUP remap_tablegroup_list] 
   [REMAP TABLESPACE remap_tablespace_list]
   [DESCRIPTION [=] description];
   ```

   The related parameters are described as follows:

   * `table_name_list`: the tables to be restored, in the `database_name.table_name1,database_name.table_name2,...` format. Multiple tables are separated with commas (,).

     When you specify `database_name` and `table_name`:

     * `table_name` must be the same as the name of the table stored in the system. For example, if you create a table named `test` in an Oracle tenant, the internal table name is `TEST`. Therefore, you must specify `TEST` when you restore the table. Otherwise, the system will return an error indicating that the table does not exist.

     * If `database_name` or `table_name` contains special characters, enclose the special characters in backticks (`` ` ``).

     * If you want to restore all tables in a database, you can use `database_name.*`.

     * If you want to restore all user tables in a tenant, you can use `*.*`.

   * `dest_tenant_name`: the name of the target tenant to which the table is to be restored. You can restore the table only to a user tenant, not to the `sys` tenant or Meta tenant.

   * `uri`: the path for data backup and log archiving. The parameters are the same as those in the tenant-level physical restore command. If the data backup is initiated by using the PLUS ARCHIVELOG mode, you only need to specify one path. Otherwise, you need to specify at least two paths for data backup and log archiving, for example: `'file:///backup/archive, file:///backup/data'`.

   * `{TIME='timestamp'} \| {SCN=scn}`: the restore point. The system restores the data to the specified point in time and includes the point in time. When you specify `TIME` or `SCN`, you must use `=` to connect the specified value. If you do not specify the `UNTIL` clause, the system restores the data to the latest point in time by default.

   * `restore_option`: the `pool_list`, `locality`, `primary_zone`, and `concurrency` parameters of the auxiliary tenant. The parameters are separated with `&`. We recommend that you keep the `locality` and `primary_zone` parameters consistent with those of the source tenant.

     If you do not specify the `concurrency` parameter, the value is equal to the MAX_CPU value allocated to the auxiliary tenant by default. For example, the system tenant allocated 16 MAX_CPU cores to the auxiliary tenant in this topic.

     For more information about the parameters, see [Table-level restore parameters](600.parameters-of-the-table-recovery.md).

   * `WITH KEY FROM 'backup_key_path' ENCRYPTED BY 'password'`: the key backup information of the encrypted tenant. You must specify the key backup information only when the source tenant is transparently encrypted.

     * `backup_key_path`: the path for key backup.

     * `password`: the encryption password set for the backup key.

     For more information about key backup, see **Backup keys** in [Preparations before backup](../400.data-backup/100.preparation-before-data-backup.md).

   * `remap_table_name_list`: the new name of the restored table. You can rename only the table name, leave the database to which the table belongs unchanged, or rename the table to another database. The source object and the renamed object are connected with a colon (:). The specific format is described as follows:

     * Rename the `student` table to `student2` without changing the database to which the table belongs: `REMAP TABLE school.student:student2`.

       If the database to which the table belongs is not changed, the system will restore the table to the database with the same name in the target tenant by default. If the database with the same name does not exist, the table restore will fail.

     * Do not change the table name, but rename the database to which the table belongs from `school` to `college`: `REMAP TABLE school.student:college.student`.
     * Rename the `student` table to `student2`, and rename the database to which the table belongs from `school` to `college`: `REMAP TABLE school.student:college.student2`.
     * Restore all tables in the `school` database to the `college` database: <code>REMAP TABLE school.`*`:college.`*`</code>

     <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>If the <code>database_name</code> or <code>table_name</code> to be renamed contains special characters, the special characters must be enclosed in backticks (`` ` ``). </p>
     </main>

   * `remap_tablegroup_list`: the name of the table group to which the table belongs. If the source table is bound to a table group, the system will restore the table to the table group with the same name in the target tenant by default. If the table group with the same name does not exist, the table restore will fail. If the target tenant has other table groups, you can use this statement to restore the table to other table groups. The source object and the renamed object are connected with a colon (:).

     For example, restore all tables in the source table group `tg1` to the table group `newtg1` in the target tenant: `REMAP TABLEGROUP tg1:newtg1`.

   * `remap_tablespace_list`: the name of the tablespace to which the table belongs. A tablespace is a logical unit in OceanBase Database. It is mainly used for data encryption. If the source table is bound to a tablespace, the system will restore the table to the tablespace with the same name in the target tenant by default. If the tablespace with the same name does not exist, the table restore will fail. If the target tenant has other tablespaces, you can use this statement to restore the table to other tablespaces. The source object and the renamed object are connected with a colon (:).

     For example, restore all tables in the source tablespace `ts1` to the tablespace `newts1` in the target tenant: `REMAP TABLESPACE ts1:newts1`.

   For more information about the parameters, see [Table-level restore parameters](600.parameters-of-the-table-recovery.md).

   Restore the `tbl1` and `tbl2` tables in the `infodb` database of the `infodb` database in the target tenant, rename the `tbl1` table to `newtbl`, and redirect the table group and tablespace to `newtg1` and `newts1`, respectively. The statement is as follows:

   ```sql
   ALTER SYSTEM 
   RECOVER TABLE infodb.tbl1,infodb.tbl2 
   TO TENANT oracle001 
   FROM 'file:///data/nfs/backup/data,file:///data/nfs/backup/archive' 
   UNTIL TIME='2023-09-30 00:00:00' 
   WITH 'pool_list=restore_pool'
   REMAP TABLE infodb.tbl1:newtbl 
   REMAP TABLEGROUP tg1:newtg1
   REMAP TABLESPACE ts1:newts1;
   ```

  <main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><ul><li>Table data is considered successfully restored if the table is restored, even if the index, constraint, or other associated schemas fail to be restored. </li><li>After table-level restore is completed, we recommend that you restore the <code>ddl_thread_score</code>, <code>recover_table_concurrency</code>, and <code>recover_table_dop</code> parameters. If you do not restore these parameters, subsequent table-level restores will be performed based on the specified parallelism parameters. </li><li>The restore of triggers associated with tables during table-level restore is performed in the following mode: <ul><li>If the restored table name is not renamed (REMAP TABLE mapping) in the table-level restore command, the table is restored based on the original table name, and the triggers associated with the table must be restored. </li><li>If the restored table name is renamed (REMAP TABLE mapping) in the table-level restore command, the table is restored based on the new table name, and the triggers associated with the table are not restored. </li></ul></li></ul></p>
  </main>

## Description of schema information that can be restored

After a table-level restore is performed, the following table describes the schema information that can be restored and its details.

| Schema information | Restorable | Description |
|---------------|-----------|--------------------------------------------------------|
| Database      |    No      | The database in the target tenant must exist when a table-level restore is performed. Otherwise, the restore will fail. For example, if the backup table belongs to the `INFO` database, the system will restore the table to the `INFO` database in the target tenant. You can use the `REMAP TABLE` statement to rename the table to another database in the target tenant. |
| Tablespace    |    No      | The tablespace in the target tenant must exist when a table-level restore is performed. Otherwise, the restore will fail. For example, if the backup table belongs to the `TS` tablespace, the system will restore the table to the `TS` tablespace in the target tenant. You can use the `REMAP TABLE` statement to rename the table to another tablespace in the target tenant. |
| Table group   |    No      | The table group in the target tenant must exist when a table-level restore is performed. Otherwise, the restore will fail. For example, if the backup table belongs to the `TG` table group, the system will restore the table to the `TG` table group in the target tenant. You can use the `REMAP TABLE` statement to rename the table to another table group in the target tenant. |
| Table         |    Yes     | Only user tables can be restored. System tables and temporary tables cannot be restored. |
| Partition     |    Yes     | N/A |
| Tablet        |    Yes     | N/A |
| Column        |    Yes     | N/A |
| Constraint    |    Yes     | The following constraints can be restored: <ul><li>`NOT NULL` constraints </li> <li>`UNIQUE KEY` constraints </li> <li>`PRIMARY KEY` constraints <main id="notice" type='notice'><h4>Notice</h4><p>If a <code>PRIMARY KEY</code> constraint name is duplicated, the restore will fail. </p></main></li> <li>`CHECK` constraints</li></ul> <main id="notice" type='explain'><h4>Note</h4><p>If a user-defined constraint already exists in the target tenant, it will not be restored. </p></main> |
| Foreign key   |    Yes     | During the restore of a foreign key, the system checks the integrity of the foreign key constraints. If a foreign key references a row that does not exist, the restore of the foreign key will fail. |
| View          |    No      | The views associated with the table will not be restored when the table is restored. |
| Local index   |    Yes     | N/A |
| Global index  |    Yes     | N/A |
| Auto-increment column |    Yes     | N/A |
| Table without a primary key |    Yes     | N/A |
| Statistics   |    Yes     | N/A |
| Trigger       |    Yes     | <ul><li> If the table is restored by using the original table name, the triggers associated with the table will be restored. Note that: <ul><li> In Oracle mode, if the user that owns the trigger does not exist, the restore of the trigger will fail. </li> <li> In MySQL mode, if the database that stores the trigger does not exist, the restore of the trigger will fail. </li></ul></li> <li> If the table is renamed and restored by using the new table name, the triggers associated with the table will not be restored. </li></ul> |
| Function, stored procedure, and package |    No     | The functions, stored procedures, and packages associated with the table will not be restored when the table is restored. |
| Synonym       |    No      | The synonyms associated with the table will not be restored when the table is restored. |
| Spatial index |    Yes     | The coordinate system will not be restored when a table-level restore is performed. If no reference coordinate system exists in the target tenant, the spatial index will not be restored. If a coordinate system exists in the target tenant, the spatial index will be restored. |
| LOB           |    Yes     | N/A |

## What to do next

* After initiating the restore for the specified table, you can view the progress and results of the table restore. For more information, see [View the progress of table-level restore](400.view-the-table-recovery-progress.md) and [View the results of table-level restore](500.view-the-table-recovery-history.md).

* After the restore for the specified table is complete, you also need to execute the following commands in the cluster where the auxiliary tenant is located to manually release the resource pool created for the auxiliary tenant.

    ```sql
    DROP RESOURCE POOL restore_pool;
    ```

    Here, `restore_pool` indicates the name of the resource pool created for the auxiliary tenant during the restore preparation.

    For more information about how to delete a resource pool, see [Delete a resource pool](../../200.tenant-management/600.common-tenant-operations/1500.resource-pool-management/600.delete-resource-pool.md).
