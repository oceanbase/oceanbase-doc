# Restore data by table

This topic describes how to restore data by table.

## Table-level restore

During the physical restore of an auxiliary tenant, you can either restore all data or only part of it. The former is called full restore, while the latter is known as quick restore.

The restore process involves three stages: restoring the auxiliary tenant, cross-tenant table migration, and auxiliary tenant cleanup. If full restore is used in the first stage, all data from the source tenant is restored to the auxiliary tenant from the backup media. This approach has the following drawbacks:

1. Sufficient CPU, memory, and disk resources must be reserved in the cluster to support the temporary auxiliary tenant during the restore process.
2. Restoring all data from the backup media to the auxiliary tenant consumes significant time and network bandwidth.

In contrast, quick restore creates only a read-only auxiliary tenant. User data does not need to be restored from the backup media. Instead, during the cross-tenant table migration stage, the backup macroblock data of the table to be restored is directly read from the backup media. This method reduces resource consumption for the temporary auxiliary tenant during table-level recovery and shortens the recovery task's duration.

The restore method used by OceanBase Database depends on the cluster's deployment mode:

* In shared-nothing mode, the system automatically uses the quick restore method to restore an auxiliary tenant during table-level restore.
* In shared mode, the system uses the full restore method to restore an auxiliary tenant during table-level restore.

<main id="notice" type='notice'>
  <h4>Note</h4>
  <p>The quick restore feature in shared-nothing mode is supported starting from V4.3.5 BP1.</p>
</main>

## Limitations

* Only user tables can be restored. Temporary tables, views, materialized views, materialized view logs, and indexes cannot be restored.

* Tables stored in columnar storage mode or hybrid row-column storage mode cannot be restored.

* The source and target tenants must be compatible. For example, both must be Oracle-compatible tenants or both must be MySQL-compatible tenants.

* The specified table name during restore must exactly match the actual table name stored in the system. For example, if you create a table named `test` in Oracle-compatible mode, the actual table name stored in the system is `TEST`. Therefore, you must specify the table name as `TEST` during restore. Otherwise, the system will return an error, indicating that the table does not exist.

* Similar to the backup data versions supported by tenant-level restore, table-level restore currently only supports restoring tables from lower-version backup data to the same or higher versions. Reverse restore between minor versions within the same major version is also not supported. For detailed information about the backup data versions supported by tenant-level restore, see [Preparations](../600.restore-data/100.preparation-before-recovery.md).

## Prerequisites

An auxiliary tenant is required for restoring a specified table. Therefore, before you restore a table, you must create a resource pool for the auxiliary tenant in the cluster where the target tenant resides. For more information, see [Preparations](100.preparation-before-table-recovery.md).

## Procedure

1. Log in to the `sys` tenant of the target cluster as the `root` user.

2. (Optional) If the backup data of the specified table is encrypted, configure the encryption information of the backup set.

   If a password is added when you back up data, you must configure a password for restoring the backup data.

   ```sql
   SET DECRYPTION IDENTIFIED BY 'password';
   ```

   In this example, you need to replace `password` with the password added when you back up data. If full backup and incremental backup use different passwords, you need to enter both passwords separated by a comma, with the password of full backup placed before that of incremental backup.

   Here is an example where full backup and incremental backup use the same password:

   ```sql
   SET DECRYPTION IDENTIFIED BY '******';
   ```

   Here is an example where full backup and incremental backup use different passwords:

   ```sql
   SET DECRYPTION IDENTIFIED BY '******','******';
   ```

3. (Optional) Set the table-level restore degree of parallelism.

   * Single-table restore

      Before you initiate a table-level restore, you can use the [recover_table_dop](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7325.recover_table_dop.md) parameter to specify the degree of parallelism. If you set this parameter, the system will restore data in the specified degree of parallelism across partitions of the primary table during the restore and the index creation phase. Specifically:

      * During the restore of the primary table data, the system will divide each partition of the primary table into multiple subtasks for parallel execution.
      * During the index creation phase, the system will use parallel execution (PX) based on the restored primary table data to rebuild the indexes of the table.

      The syntax is as follows:

      ```sql
      -- tenant_name  is the name of the target tenant.
      ALTER SYSTEM SET recover_table_dop=INT_VALUE tenant=tenant_name;
      ```

   * (Optional) Multi-table restore

      Before you initiate a multi-table restore, you can use the [recover_table_concurrency](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7320.recover_table_concurrency.md) parameter to specify the degree of parallelism. If you set this parameter, multiple tables can be restored in parallel to improve the restore performance.

      The syntax is as follows:

      ```sql
      -- tenant_name  is the name of the target tenant.
      ALTER SYSTEM SET recover_table_concurrency=INT_VALUE tenant=tenant_name;
      ```

   * Set the number of restore worker threads on each observer node for the primary table data.

      After you set the single-table degree of parallelism `recover_table_dop` and the multi-table degree of parallelism `recover_table_concurrency`, you also need to use the [ddl_thread_score](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/1850.ddl_thread_score.md) parameter to specify the number of restore worker threads on each observer node for the primary table data. Table-level restore involves cross-tenant data export. The restore of the primary table data depends on specific DAG threads in the target tenant.

      The syntax is as follows:

      ```sql
      -- tenant_name  is the name of the target tenant.
      ALTER SYSTEM SET ddl_thread_score=INT_VALUE tenant=tenant_name;
      ```

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>
      <ul>
        <li><b>Phase of physical restore in an auxiliary tenant</b>. You can dynamically adjust the restore parallelism by using the <a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3400.ha_high_thread_score.md">ha_high_thread_score</a> parameter. The adjustment takes effect immediately. The auxiliary tenant name can be obtained by querying the <a href="../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/10200.o-cdb_ob_recover_table_jobs-of-sys-tenant.md">CDB_OB_RECOVER_TABLE_JOBS</a> system view of the table-level restore task. For more information, see [Physical restore](../600.restore-data/200.initiate-the-tenant-restore.md). </li>
        <li><b>Phase of cross-tenant data export</b>. You can dynamically adjust the multi-table and single-table restore parallelism by using the <code>recover_table_concurrency</code> and <code>recover_table_dop</code> parameters, respectively. The adjustment takes effect immediately. </li>
      </ul>
      </p>
      </main>

4. Execute the following statement to restore the specified table.

   The SQL syntax is as follows:

   ```sql
   ALTER SYSTEM 
   RECOVER TABLE table_name_list 
   TO [TENANT [=]] dest_tenant_name 
   FROM uri 
   [UNTIL {TIME='timestamp'} | {SCN=scn} ]
   WITH 'restore_option' 
   [WITH KEY FROM 'backup_key_path' ENCRYPTED BY 'password']
   [REMAP TABLE remap_table_name_list] 
   [REMAP TABLEGROUP remap_tablegroup_list] 
   [REMAP TABLESPACE remap_tablespace_list]
   [DESCRIPTION [=] description];
   ```

   The parameters are described as follows:

   * `table_name_list`: the name of the table to restore, in the format of `database_name.table_name1,database_name.table_name2,...`. The table names are separated by commas (,).

     When you specify `database_name` and `table_name`:

     * You must specify `table_name` exactly the same as the table name stored in the system. For example, in Oracle-compatible mode, if you create a table named `test`, the system actually stores the table name as `TEST`. Therefore, when you restore the table, you must specify the table name as `TEST`. Otherwise, the system will return an error, indicating that the table does not exist.

     * If special characters are included in `database_name` or `table_name`, you need to enclose the special characters in backticks (`).

     * You can use the pattern `database_name.*` to specify all tables in a database.

     * You can use the pattern `*.*` to specify all user tables in a tenant.

   * `dest_tenant_name`: the name of the destination tenant to which the table is to be restored. You can restore a table only to a user tenant. The table cannot be restored to the `sys` tenant or the meta tenant.

   * `uri`: the path where the data backup is stored and the path where the log archive is stored. The parameters are the same as those in the tenant-level physical restore command. If the data backup is initiated by using the PLUS ARCHIVELOG method, you need to specify only one path. Otherwise, you need to specify at least two paths, namely, the data backup path and the log archive path, separated by commas (,). For example: `file:///backup/archive, file:///backup/data`.

   * `{TIME='timestamp'} \| {SCN=scn}`: the restore end point. The restore is performed to the specified point in time or SCN and includes the data and settings at the point in time or SCN. If you want to restore to a specific `TIME` or `SCN`, you must connect the specified value with an equal sign (=). If you do not specify the `UNTIL` clause, the restore is performed to the latest point in time or SCN.

   * `restore_option`: specifies the auxiliary tenant's `pool_list`, `locality`, `primary_zone`, and `concurrency`. The parameters are separated with `&`. When you specify `locality` and `primary_zone`, we recommend that you maintain the same configuration as the source tenant.

     If you do not specify the `concurrency` parameter, the default value, which is the number of CPU cores allocated to the auxiliary tenant, will be used. For example, in this topic, the system allocates 16 CPU cores to the auxiliary tenant.

     For more information about the parameters, see [Parameters for restoring a table](600.parameters-of-the-table-recovery.md).

   * `WITH KEY FROM 'backup_key_path' ENCRYPTED BY 'password'`: the encryption information of the destination tenant. You need to specify this parameter only when the source tenant is transparently encrypted.

     * `backup_key_path`: the backup path of the tenant key.

     * `password`: the encryption password added when you back up the tenant key.

     For more information about how to back up the tenant key, see **Back up the tenant key** in [Prepare before data backup](../400.data-backup/100.preparation-before-data-backup.md).

   * `remap_table_name_list`: the renamed table names. You can rename only the table name but keep the database name unchanged, or you can keep the table name unchanged but rename the database name, or you can rename both the table name and the database name. The source and destination table or database names are separated with a colon (:). Here are some examples:

     * Rename the table name from `student` to `student2` while keeping the database name unchanged: `REMAP TABLE school.student:student2`.

       If the database name remains unchanged, when you restore a table to a tenant, the system will restore the table to the database with the same name in the destination tenant by default. If there is no database with the same name, the table restoration will fail.

     * Keep the table name unchanged and rename the database name from `school` to `college`: `REMAP TABLE school.student:college.student`.
     * Rename the table name from `student` to `student2` and the database name from `school` to `college`: `REMAP TABLE school.student:college.student2`.
     * Restore all tables in the `school` database to the `college` tenant: <code>REMAP TABLE school.`*`:college.`*`</code>

     <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>If special characters are included in the <code>database_name</code> or <code>table_name</code> in the remapping information, you need to enclose the special characters in backticks (`). </p>
     </main>

   * `remap_tablegroup_list`: the renamed table groups. If the source table is bound to a table group, when you restore the table to a tenant, the system will restore the table to the table group with the same name in the destination tenant. If there is no table group with the same name, the table restoration will fail. If the destination tenant has other table groups, you can restore the table to another table group. The source and destination table group names are separated with a colon (:).

     For example, restore all tables in the `tg1` table group in the source tenant to the `newtg1` table group in the destination tenant: `REMAP TABLEGROUP tg1:newtg1`.

   * `remap_tablespace_list`: the renamed table spaces. Table spaces are logical units in OceanBase Database, where data is currently mainly encrypted. If the source table is bound to a table space, when you restore the table to a tenant, the system will restore the table to the table space with the same name in the destination tenant. If there is no table space with the same name, the table restoration will fail. If the destination tenant has other table spaces, you can restore the table to another table space. The source and destination table space names are separated with a colon (:).

     For example, restore all tables in the `ts1` table space in the source tenant to the `newts1` table space in the destination tenant: `REMAP TABLESPACE ts1:newts1`.

   For more information about the parameters, see [Parameters for restoring a table](600.parameters-of-the-table-recovery.md).

   Restore the tables `tbl1` and `tbl2` from the `infodb` database to the `infodb` database in the destination tenant, rename the restored table `tbl1` to `newtbl`, and redirect the table group and table space to which the table belongs. Here is an example:

   ```sql
   ALTER SYSTEM 
   RECOVER TABLE infodb.tbl1,infodb.tbl2 
   TO TENANT oracle001 
   FROM 'file:///data/nfs/backup/data,file:///data/nfs/backup/archive' 
   UNTIL TIME='2023-09-30 00:00:00' 
   WITH 'pool_list=restore_pool'
   REMAP TABLE infodb.tbl1:newtbl 
   REMAP TABLEGROUP tg1:newtg1
   REMAP TABLESPACE ts1:newts1;
   ```

  <main id="notice" type='notice'>
  <h4>Note</h4>
  <p><ul><li>Table data restore is successful immediately after the table is restored, regardless of whether the restoration of indexes, constraints, or other schema components succeeds or fails. </li><li>After the table-level restore is completed, we recommend that you reset the <code>ddl_thread_score</code>, <code>recover_table_concurrency</code>, and <code>recover_table_dop</code> parameters. If you do not restore these parameters, the subsequent table-level restores will be performed with the parameters that you set. </li><li>During table-level restore, the triggers associated with the tables are restored in the following order: <ul><li>If the restore command for tables does not include the REMAP TABLE clause (that is, the tables are restored with their original names), restore the triggers associated with the tables; </li><li>If the restore command for tables includes the REMAP TABLE clause (that is, the tables are restored with their new names), do not restore the triggers associated with the tables. </li></ul></li></ul></p>
  </main>

## What to do next

* After you initiate a restore for a specific table, you can query the view for the restore progress and result. For more information, see [View the restore progress by table](400.view-the-table-recovery-progress.md).

* After the restore for a specific table is completed, you must manually release the resource pool created for the auxiliary tenant in the cluster where the auxiliary tenant resides by running the following command.

    ```sql
    DROP RESOURCE POOL restore_pool;
    ```

    Here, `restore_pool` is the name of the resource pool created for the auxiliary tenant before the restore.

    For more information about how to delete a resource pool, see [Delete a resource pool](../../200.tenant-management/600.common-tenant-operations/1500.resource-pool-management/600.delete-resource-pool.md).
