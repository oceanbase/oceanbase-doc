# Automatically clean up expired backups

After a backup is successful, you can set a cleanup strategy for the tenant based on business needs. The tenant with a cleanup strategy will trigger an automatic cleanup every hour to promptly remove expired backups or archived data.

## Considerations

* Data cleanup for log archiving depends on data backup. Before cleaning up log archiving data, make sure that data backup files exist. If no data backup files exist, you cannot clean up log archiving data.

Automatic cleanup only supports cleaning up backup or archive data in the paths specified by `DATA_BACKUP_DEST` and `LOG_ARCHIVE_DEST`. It does not clean up data in backup or archive paths that are no longer in use. For scenarios where the backup destination or archive destination has been changed, data in the original backup or archive paths can only be manually cleaned up.

  For more information about how to manually clean up backup or archive data, see [Manually clean up specified backup or archive data](../100.manual-backup-cleanup/200.cleaning-up-specified-backup-data.md) and [Manually clear the backup destination or archive destination](../100.manual-backup-cleanup/300.clear-the-backup_dest_or_archivelog_dest.md).

* Automatic cleanup retains at least one valid backup data. If only one valid backup data exists, it will never be cleaned up.

* The automatic cleanup results vary depending on the backup media:

  * For scenarios where the backup media is NFS or an object storage service compatible with the S3 protocol (such as OBS or GCS), the system directly deletes backup files that meet the requirements.
  * For scenarios where the backup destination is S3/COS (accessed via the S3 protocol), the cleanup method of backup files depends on the values of the `delete_mode` parameter in `data_backup_dest` and `log_archive_dest`. For more information about the `delete_mode` parameter, see [SET LOG_ARCHIVE_DEST](../../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/3800.set-log-archive-dest.md) and [SET DATA_BACKUP_DEST](../../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/3500.set-data-backup-dest.md).

* In particular, for scenarios where the `enable_worm=true` parameter is configured in the path attributes, the system selects backup or archive data that meet the requirements based on the `RECOVERY_WINDOW` parameter during automatic cleanup. However, the success of the cleanup depends on the cleanup mode (`delete_mode` parameter) and the retention policy of the corresponding bucket.

  <main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>The <code>enable_worm=true</code> parameter applies to scenarios where the compliance retention policy (WORM) is enabled.</p>
  </main>

  For example, if a backup set is outside the `RECOVERY_WINDOW` but still within the WORM retention period, the following applies:

  * If the cleanup mode of the backup set is `delete`, the OceanBase Database will fail to clean up the backup set. You need to wait until the retention period of the object expires before the backup set can be cleaned up.

  * If the cleanup mode of the backup set is `tagging`, the OceanBase Database will tag the backup set. The object storage service will then delete the backup set at the end of its lifecycle, after the WORM retention period has expired.

## Set a cleanup policy for a user tenant

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Set a cleanup policy to enable automatic cleanup for the tenant.

   The syntax is as follows:

   ```sql
   ALTER SYSTEM ADD DELETE BACKUP POLICY [=] policy_name RECOVERY_WINDOW [=] recovery_window TENANT [=] tenant_name;
   ```

   Here:

   * `policy_name`: specifies the name of the cleanup policy. Valid values are as follows:

     * `default`: specifies that automatic cleanup applies only to backup and archive data in the paths specified by the `DATA_BACKUP_DEST` and `LOG_ARCHIVE_DEST` parameters of the tenant.
     * `log_only`: specifies that automatic cleanup applies only to archive data in the path specified by the `LOG_ARCHIVE_DEST` parameter of the tenant. This option is suitable for scenarios where data backup is not enabled and only log archiving is enabled. When the cleanup policy is set to `log_only`, the value of the `DATA_BACKUP_DEST` parameter of the tenant must be empty, indicating that data backup is not enabled. Conversely, if the cleanup policy is set to `log_only`, you cannot configure the backup destination by setting the `DATA_BACKUP_DEST` parameter.

   * The `recovery_window` parameter specifies the time window during which backup data can be recovered. For more information about this parameter, see [recovery_window parameter](../500.parameters-of-cleaning-up-backup.md).

   * The `TENANT` parameter specifies the tenant to which the cleanup policy applies. You must specify the name of a user tenant, and only one tenant name can be specified.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>Currently, only tenant-level cleanup policies are supported, and cluster-level cleanup policies are not supported. Each command can set only one cleanup policy for one tenant.</p>
   </main>

   Here are some examples:

   * Set a cleanup policy for the `mysql001` tenant.

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM ADD DELETE BACKUP POLICY 'default' RECOVERY_WINDOW '7d' TENANT mysql001;
     ```

   * Set a cleanup policy for the `oracle001` tenant.

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM ADD DELETE BACKUP POLICY 'log_only' RECOVERY_WINDOW '7d' TENANT oracle001;
     ```

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>Automatic cleanup tasks are triggered by the system every hour. Therefore, after setting a cleanup policy, you may need to wait for up to one hour before you can query the corresponding cleanup task.</p>
   </main>

3. View the set cleanup policy.

   After the cleanup policy is set, you can query the `oceanbase.CDB_OB_BACKUP_DELETE_POLICY` view to view the cleanup policies of all tenants.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID, POLICY_NAME, RECOVERY_WINDOW FROM oceanbase.CDB_OB_BACKUP_DELETE_POLICY;
   ```

   The query result is as follows:

   ```shell
   +-----------+-------------+-----------------+
   | TENANT_ID | POLICY_NAME | RECOVERY_WINDOW |
   +-----------+-------------+-----------------+
   |      1002 | default     | 7d              |
   |      1004 | log_only    | 7d              |
   +-----------+-------------+-----------------+
   2 rows in set
   ```

## Set the cleanup strategy for the current user tenant

1. Log in to the database as the tenant administrator of the user tenant.

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>The administrator user of a MySQL tenant is <code>root</code>, and that of an Oracle tenant is <code>SYS</code>. </p>
   </main>

2. Set the cleanup strategy to enable automatic cleanup for the tenant.

   The statement is as follows:

   ```sql
   ALTER SYSTEM ADD DELETE BACKUP POLICY [=] policy_name RECOVERY_WINDOW [=] recovery_window;
   ```

   The parameters are described as follows:

   * `policy_name`: specifies the name of the cleanup strategy. Valid values: `default` and `log_only`.

     * `default`: specifies that only backup and archive data in the paths specified by the `DATA_BACKUP_DEST` and `LOG_ARCHIVE_DEST` parameters are automatically cleaned up.
     * `log_only`: specifies that only log data in the archive path specified by the `LOG_ARCHIVE_DEST` parameter is automatically cleaned up. This option is applicable when only log archiving is enabled and no data backup is performed. If the cleanup strategy is set to `log_only`, the `DATA_BACKUP_DEST` parameter must be empty, indicating that data backup is not configured. Conversely, if the `DATA_BACKUP_DEST` parameter is set, the cleanup strategy cannot be set to `log_only`.

   * `recovery_window`: specifies the time window during which backup data can be restored. For more information about this parameter, see [recovery_window](../500.parameters-of-cleaning-up-backup.md).

   Here are some examples:

   :::tab
   tab MySQL mode

   In MySQL mode, set the cleanup strategy of the current tenant to `default` and set the backup restore time window to 7 days.

   ```shell
   obclient(root@mysql001)[(none)]> ALTER SYSTEM ADD DELETE BACKUP POLICY 'default' RECOVERY_WINDOW '7d';
   ```

   tab Oracle mode

   In Oracle mode, set the cleanup strategy of the current tenant to `log_only` and set the backup restore time window to 7 days.

   ```shell
   obclient(SYS@oracle001)[SYS] ALTER SYSTEM ADD DELETE BACKUP POLICY 'log_only' RECOVERY_WINDOW '7d';
   ```

   :::

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>The automatic cleanup task is triggered by the system every hour. Therefore, after you set the cleanup strategy, you may need to wait for a while (up to one hour) to query the corresponding cleanup task. </p>
   </main>

3. View the cleanup strategy.

   After the cleanup strategy is set, you can query the `oceanbase.DBA_OB_BACKUP_DELETE_POLICY` view in MySQL mode or the `sys.DBA_OB_BACKUP_DELETE_POLICY` view in Oracle mode to view the cleanup strategy of the current tenant.

   :::tab
   tab MySQL mode

   In MySQL mode, execute the following statement:

   ```shell
   obclient(root@mysql001)[oceanbase]> SELECT POLICY_NAME, RECOVERY_WINDOW FROM oceanbase.DBA_OB_BACKUP_DELETE_POLICY;
   ```

   The query result is as follows:

   ```shell
   +-------------+-----------------+
   | POLICY_NAME | RECOVERY_WINDOW |
   +-------------+-----------------+
   | default     | 7d              |
   +-------------+-----------------+
   1 row in set
   ```

   tab Oracle mode

   In Oracle mode, execute the following statement:

   ```shell
   obclient(SYS@oracle001)[SYS]> SELECT POLICY_NAME, RECOVERY_WINDOW FROM SYS.DBA_OB_BACKUP_DELETE_POLICY;
   ```

   The query result is as follows:

   ```shell
   +-------------+-----------------+
   | POLICY_NAME | RECOVERY_WINDOW |
   +-------------+-----------------+
   | log_only    | 7d              |
   +-------------+-----------------+
   1 row in set
   ```

   :::

## What to do next

* If you want to change the cleanup strategy, you must delete the existing strategy and then set a new one. For more information about how to delete a cleanup strategy, see [Delete a cleanup strategy](200.drop-the-cleanup-strategy.md).

* If you want to immediately perform a cleanup after setting the cleanup strategy, you can manually trigger an expired backup cleanup. For more information about how to manually trigger an expired backup cleanup, see [Manually trigger an expired backup cleanup](../100.manual-backup-cleanup/100.cleaning-up-expired-backup-data-manually.md).
