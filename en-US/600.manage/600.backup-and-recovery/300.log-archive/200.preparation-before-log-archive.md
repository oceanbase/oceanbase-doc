# Prepare for log archiving

This topic describes the preparations before you archive logs.

## Configure the log archive concurrency (optional)

Before you enable the archiving mode, you can configure the log archive concurrency to increase the log archiving speed of the tenant.

1. Log in to the database as the `sys` tenant user or the tenant administrator of the user tenant.

2. Execute a statement to set the `log_archive_concurrency` parameter.

   The tenant-level `log_archive_concurrency` parameter specifies the total number of worker threads for log archiving. This parameter takes effect immediately without the need to restart the OBServer node. The value range is [0, 100]. The default value is `0`, which indicates that OceanBase Database adapts the log archive concurrency. We recommend that you use the default value.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p>For small tenants (with less than or equal to 4 CPU cores), we recommend that you use the default value and do not modify the value of this parameter. </p>
   </main>

   The following examples show how to set the parameter:

   * Set the log archive concurrency for a user tenant as a tenant administrator of the `sys` tenant.

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10 TENANT = mysql_tenant;
     ```

   * Set the log archive concurrency for all user tenants as a `sys` tenant user.

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10 TENANT = all_user;
     ```

     or

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10 TENANT = all;
     ```

     <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>Starting from V4.2.1, OceanBase Database allows you to use <code>TENANT = all_user</code> and <code>TENANT = all</code> interchangeably to target all user tenants. We recommend that you use <code>TENANT = all_user</code> for now, as <code>TENANT = all</code> will be deprecated in the future. </p>

   * Set the log archive concurrency for the current tenant as a tenant administrator of the current tenant.

     ```sql
     ALTER SYSTEM SET log_archive_concurrency = 10;
     ```

   For more information about the `log_archive_concurrency` parameter, see [log_archive_concurrency](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/4300.log_archive_concurrency.md).

## Configure the archive destination

Before you start a log archiving task, you must execute the `ALTER SYSTEM` command to specify the `LOG_ARCHIVE_DEST` parameter. The system tenant does not contain user data and is a tenant used for cluster management. Backup and restore are not supported for the `sys` tenant. Therefore, you do not need to configure an archive destination for this tenant.

The operation of configuring an archive destination mainly involves setting the `LOCATION`, `BINDING`, and `PIECE_SWITCH_INTERVAL` parameters.

### Considerations

When you configure the destination for archiving, make sure that the archive path for each tenant is an independent empty directory, and that the archive paths for different tenants are not the same.

### Procedure

1. Log in to the database as the tenant administrator of the `sys` tenant or a user tenant.

   <main id="notice" type='explain'>
        <h4>Note</h4>
   <p>In MySQL mode, the administrator user is the <code>root</code> user, and in Oracle mode, the administrator user is the <code>SYS</code> user.</p>
   </main>

2. Configure the archive destination.

   * For the system tenant, configure the archive destination for the specified tenant.

     ```sql
     ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=archive_path [BINDING=archive_mode] [PIECE_SWITCH_INTERVAL=piece_switch_interval]' TENANT = tenant_name;
     ```

   * For a user tenant, configure the archive destination for the current tenant.

     ```sql
     ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=archive_path [BINDING=archive_mode] [PIECE_SWITCH_INTERVAL=piece_switch_interval]';
     ```

   <main id="notice" type='notice'>
   <h4>Note</h4>
   <p>For scenarios where OceanBase Database V4.0.x is upgraded to V4.1.0, the archive path must be changed after the upgrade. For scenarios where OceanBase Database V4.1.x is upgraded to V4.2.x, the archive path does not need to be changed after the upgrade. In addition, when OceanBase Database V4.1.x is upgraded to V4.2.x, log archiving can be performed during the upgrade.</p>
   </main>

   The following table describes the parameters.

   * `LOCATION` (required)

       The `LOCATION` parameter specifies the archive path. Currently, OceanBase Database supports the following archive media: NFS, Alibaba Cloud Object Storage Service (OSS), Amazon Simple Storage Service (S3), and object storage services that comply with the S3 protocol. For example, Huawei Object Storage Service (OBS), Google Cloud Storage (GCS), and Tencent Cloud Object Storage (COS). Some archive media may have certain requirements to meet. For more information about the requirements for each archive media, see the **Backup media requirements** section in [Overview of physical backup and restore](../100.overview-of-physical-backup-and-recovery.md).

      :::tab
      tab OSS

      When OSS is used as the archive media, in addition to specifying the archive path, `host`, `access_key`, and `access_id`, you can also configure the `delete_mode` parameter to specify the deletion mode for archive files. The `delete_mode` parameter supports the `delete` mode and the `tagging` mode. If you do not explicitly specify the `delete_mode` parameter, the `delete` mode is used by default.

      In addition, the `checksum_type` parameter can be used to specify a checksum algorithm to verify the integrity of archive files. The `checksum_type` parameter supports the values `md5` and `no_checksum`. If you do not explicitly specify the `checksum_type` parameter, the default value is `md5`.

      For more information about the `delete_mode` parameter and the `checksum_type` parameter, see [SET LOG_ARCHIVE_DEST](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/150.set-log-archive-dest.md).

      <main id="notice" type='notice'>
      <h4>Note</h4>
      <p>When an object storage service is used as the archive media, separate the parameters of the object storage service with the <code>&</code> character. Make sure that the values of the parameters contain only uppercase and lowercase letters, numbers, and the characters <code>/-_$+=</code>. If the values contain other characters, the settings may fail.</p>
      </main>

      Here are some examples:

      * Use OSS as the archive media. Specify the system tenant as the tenant `mysql_tenant`, configure the `delete_mode` parameter to `delete`, and specify the `checksum_type` parameter to `md5`.

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=oss://oceanbase-test-bucket/backup/archive?host=****.aliyun-inc.com&access_id=****&access_key=****&delete_mode=delete&checksum_type=md5' TENANT = mysql_tenant;
        ```

        If you do not want to verify the integrity of archive files, you can set the `checksum_type` parameter to `no_checksum`. Here is an example:

        ```shell
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=oss://oceanbase-test-bucket/backup/archive?host=****.aliyun-inc.com&access_id=****&access_key=****&delete_mode=delete&checksum_type=no_checksum' TENANT = mysql_tenant;
        ```

      * Use OSS as the archive media. Specify the user tenant as the current tenant, configure the `delete_mode` parameter to `delete`, and specify the `checksum_type` parameter to `md5`.

        ```shell
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=oss://oceanbase-test-bucket/backup/archive?host=****.aliyun-inc.com&access_id=****&access_key=****&delete_mode=delete&checksum_type=md5';
        ```

      In this example, `oss://` indicates that OSS is used as the archive media. The bucket name is `oceanbase-test-bucket`, and the path in the bucket is `/backup/archive`. The other parameters in the path are separated with `?`. The value of `host` specifies the host address of the bucket. The values of `access_id` and `access_key` specify the access key of `OSS`. The value of `delete_mode` is `delete`, and the checksum algorithm specified by the `checksum_type` parameter is MD5.

      After you set the `delete` mode or the `tagging` mode, for information about how to automatically clean up archived data, see [Automatically clean up backed-up data](../500.clear-backup-data/100.cleaning-up-backed-up-data-automatically.md).

      tab NFS

      <main id="notice" type='notice'>
      <h4>Note</h4>
      <p>Consider the following points when you use NFS as the archive media:</p>
      <ul>
      <li>The value of the <code>LOCATION</code> parameter cannot contain a question mark (?). </li>
      <li>The value of the <code>LOCATION</code> parameter must be an absolute path, and the OBServer node must have read and write permissions on the path specified by the <code>LOCATION</code> parameter. </li>
      <li>All OBServer nodes must mount the same NFS directory on the same server. To ensure normal archiving, use the parameters recommended in this topic to mount the NFS directory. For more information, see <a href="../200.deploy-nfs.md">Deploy an NFS client</a>. </li>
      </ul>
      </main>

      Here is an example of configuring NFS as the archive media for the specified tenant `mysql_tenant` in the system tenant:

      ```sql
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/nfs/backup/archive' TENANT = mysql_tenant;
      ```

      Here is an example of configuring NFS as the archive media for the current tenant in a user tenant:

      ```sql
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/nfs/backup/archive';
      ```

      In these examples, `file://` indicates that NFS is used as the archive media, and the archive path is `/data/nfs/backup/archive`.

      tab S3

      Like OSS, you can use the `delete_mode` parameter to specify the deletion mode for archive files when you use Amazon Simple Storage Service (S3) as the archive media. The `delete_mode` parameter is used in the same way as that for OSS. In addition, you can use the `checksum_type` parameter to specify a checksum algorithm to verify the integrity of archive files when you use S3 as the archive media. The `checksum_type` parameter supports the values `md5` and `crc32`. If you do not explicitly specify the `checksum_type` parameter, the default value is `md5`.

      For more information about the `delete_mode` parameter and the `checksum_type` parameter, see [SET LOG_ARCHIVE_DEST](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/150.set-log-archive-dest.md).

      <main id="notice" type='notice'>
      <h4>Note</h4>
      <p>When an object storage service is used as the archive media, separate the parameters of the object storage service with the <code>&</code> character. Make sure that the values of the parameters contain only uppercase and lowercase letters, numbers, and the characters <code>/-_$+=</code>. If the values contain other characters, the settings may fail.</p>
      </main>

      Here are some examples:

      * Use S3 as the archive media. Specify the system tenant as the tenant `mysql_tenant`, configure the `delete_mode` parameter to `delete`, and specify the `checksum_type` parameter to `crc32`.

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=******&s3_region=******&delete_mode=delete&checksum_type=crc32' TENANT = mysql_tenant;
        ```

      * Use S3 as the archive media. Specify the user tenant as the current tenant, configure the `delete_mode` parameter to `delete`, and specify the `checksum_type` parameter to `crc32`.

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=s3://oceanbase-test-bucket/backup/archive?host=s3.<region>.amazonaws.com&access_id=******&access_key=******&s3_region=******&delete_mode=delete&checksum_type=crc32';
        ```

      In these examples, `s3://` indicates that S3 is used as the archive media. The bucket name is `oceanbase-test-bucket`, and the path in the bucket is `/backup/archive`. The other parameters in the path are separated with `?`. The value of `host` specifies the domain name of the Amazon S3 service. The values of `access_id` and `access_key` specify the access key of S3. The value of `s3_region` is required when S3 is used as the archive media. It specifies the region where the S3 bucket is located. The value of `delete_mode` is `delete`, and the checksum algorithm specified by the `checksum_type` parameter is CRC32.

      tab Object storage services that comply with the S3 protocol

      Most object storage services comply with the S3 protocol. Therefore, object storage services that comply with the S3 protocol and meet the requirements of OceanBase Database can be used as the archive media for OceanBase Database. You can access these object storage services in the same way as you access S3. For example, Amazon Simple Storage Service (S3), Google Cloud Storage (GCS), and Tencent Cloud Object Storage (COS) are accessed through the S3 protocol.

      You can use the `checksum_type` parameter to specify a checksum algorithm to verify the integrity of archive files when you use object storage services that comply with the S3 protocol as the archive media. The `checksum_type` parameter supports only the value `md5`. If you do not explicitly specify the `checksum_type` parameter, the default value is `md5`. For more information about the `checksum_type` parameter, see [SET LOG_ARCHIVE_DEST](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/150.set-log-archive-dest.md).

If the values contain other characters, the settings may fail.</p>

   * Configure the `BINDING` attribute (optional)

        The `BINDING` attribute specifies the priority mode between archiving and business. The attribute supports the `Optional` and `Mandatory` modes. If you do not configure this attribute, the default mode is `Optional`.

        * The `Optional` mode indicates that business takes priority. In this mode, if the archiving speed of logs cannot keep up with the log generation speed, logs may be recycled before they are archived, causing a log stream interruption.

        * The `Mandatory` mode indicates that archiving takes priority. In this mode, if the archiving speed cannot keep up with the write speed of user data, users may not be able to write data.

        Here is an example of configuring the `BINDING` attribute when NFS is used as the archive media for the specified tenant `mysql_tenant` in the system tenant:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/nfs/backup/archive BINDING=Optional' TENANT = mysql_tenant;
        ```

        Here is an example of configuring the `BINDING` attribute when NFS is used as the archive media for the current tenant in a user tenant:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/nfs/backup/archive BINDING=Optional';
        ```

   * Configure the `PIECE_SWITCH_INTERVAL` attribute (optional)

        The `PIECE_SWITCH_INTERVAL` attribute specifies the interval for switching `piece`. The value range is `[1d, 7d]`. If you do not configure this attribute, the default value is `1d`.

        Here is an example of configuring the `PIECE_SWITCH_INTERVAL` attribute when NFS is used as the archive media for the specified tenant `mysql_tenant` in the system tenant:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/nfs/backup/archive BINDING=Optional PIECE_SWITCH_INTERVAL=1d' TENANT = mysql_tenant;
        ```

        Here is an example of configuring the `PIECE_SWITCH_INTERVAL` attribute when NFS is used as the archive media for the current tenant in a user tenant:

        ```sql
        obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/nfs/backup/archive BINDING=Optional PIECE_SWITCH_INTERVAL=1d';
        ```

3. After the configuration is completed, you can query the parameter settings in views.

   The `sys` tenant can query the parameter settings in the `CDB_OB_ARCHIVE_DEST` view, and a user tenant can query the parameter settings in the `DBA_OB_ARCHIVE_DEST` view. For more information about how to query the parameter settings, see [Query archiving parameters](../300.log-archive/800.view-parameters-of-log-archive.md).

### Considerations and descriptions after configuration

1. After the `LOG_ARCHIVE_DEST` parameter is successfully configured, the system creates a `format` file in the directory where the specified destination is located. The `format` file is used to verify the validity of the backup destination and ensure the integrity of data in the destination. Therefore, note the following points when you configure the destination for log archiving:

    * If the `format` file does not exist, the specified destination must be in an empty directory. Otherwise, the system returns error `-9080`, indicating that the file cannot be found.

    * If the `format` file already exists, its verification must pass before the configuration is successful. Otherwise, the system returns error `-9081`, indicating that the file does not match. The verification mainly checks whether the cluster, tenant, and backup destination type specified in the `format` file match those in the current operation.

    * If the `format` file does not exist or its verification fails during backup task execution, the task will fail.

2. After the destination for incremental backup is configured, the destination for subsequent incremental backup cannot be changed. For example, assume that the `BINDING` attribute of the NFS archive path `/data/nfs/backup/archive` is set to `Mandatory`, and the `PIECE_SWITCH_INTERVAL` attribute is set to `1d`. If you want to change the `PIECE_SWITCH_INTERVAL` attribute to `2d` while keeping the `BINDING` attribute as `Mandatory`, you still need to specify the value of the other attribute in the command. Otherwise, the attribute not specified will use the default value.

    You need to execute the following statements again for the modification.

    * Modify the settings of the system tenant for a specified tenant

      ```sql
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST = 'LOCATION=file:///data/nfs/backup/archive BINDING=Mandatory PIECE_SWITCH_INTERVAL=2d' TENANT = mysql_tenant;
      ```

    * Modify the settings of the current tenant for the current tenant

      ```sql
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST = 'LOCATION=file:///data/nfs/backup/archive BINDING=Mandatory PIECE_SWITCH_INTERVAL=2d';
      ```

3. After the archiving destination is set successfully, if the user changes the key information of the object storage due to security or other reasons, it is necessary to update the `access_id` and `access_key` information for the already set archiving path. For specific operations, refer to [Change the `access_id` and `access_key` Information for the Backup Path or Archiving Path](../450.change-sk-and-ak-for-the-backup-path-or-logarchive-path.md).

## (Optional) Configure archive lag

OceanBase Database uses the tenant-level parameter `archive_lag_target` to control the latency of log archiving for the tenant. This parameter supports units of ms, s, m, and h. The default value is 2m, which specifies the maximum interval between two consecutive archive I/O operations. This ensures that online logs can be archived in a timely manner, thereby reducing the risk of data loss.

OceanBase Database archives logs by log stream. If a log stream has logs written to it and the time since its last archive exceeds the value specified by the `archive_lag_target` parameter, the system will trigger an archive operation to archive all unarchived logs in this log stream.

For example, if the `archive_lag_target` parameter is set to `120s` (2 minutes), each log stream will attempt to trigger an archive operation every 2 minutes (unless other conditions are met, such as the archive buffer being full), ensuring that the time interval between two consecutive archive operations for this log stream is less than 2 minutes. Note that if the value of the `archive_lag_target` parameter is set to 0, real-time archiving is achieved.

For more information about the `archive_lag_target` parameter, see [archive_lag_target](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/200.archive_lag_target.md).

### Prerequisites

Make sure that the archive destination has been configured before you modify the value of the `archive_lag_target` parameter. If the archive destination is not configured, the system will return an error message indicating that the `log_archive_dest` parameter has not been set, and modifying the `archive_lag_target` parameter is not allowed.

### Considerations

* If the archive media is OSS, NFS, or COS, you can set the `archive_lag_target` parameter to any value within its valid range. If the archive media is an object storage service (OSS) compatible with the S3 protocol, the value of the `archive_lag_target` parameter must be greater than or equal to `60s`. If you set the parameter to a value less than `60s`, the system will return an error.

* We recommend that you set the `archive_lag_target` parameter to a reasonable value to prevent excessive I/O operations from affecting system performance, especially when object storage is used. A high value may fail to meet the timeliness requirements for data recovery. Therefore, you need to strike a balance between the RPO and the performance of the archive media based on your business needs.

### Procedure

1. Log in to the database as the tenant administrator of the `sys` tenant or a user tenant.

2. Depending on your needs, execute the appropriate statement to configure the archive lag.

   Here are the steps:

   * Configure the archive lag for a specified tenant as the `sys` tenant user

     ```shell
     obclient> ALTER SYSTEM SET archive_lag_target = '120s' TENANT = mysql_tenant;
     ```

     <main id="notice" type='notice'>
     <h4>Notice</h4>
     <p>When you configure the <code>archive_lag_target</code> parameter, you cannot use <code>TENANT = all_user</code> to specify all user tenants in the <code>sys</code> tenant. </p>

   * Configure the archive lag for the current tenant as a user tenant user

     ```shell
     obclient> ALTER SYSTEM SET archive_lag_target = '120s';
     ```
