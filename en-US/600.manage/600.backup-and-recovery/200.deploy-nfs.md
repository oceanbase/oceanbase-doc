# Deploy NFS

When you choose an backup media, we recommend that you use OSS as the destination. OSS is a stateless object storage service, which is more stable than NFS4, a stateful protocol.

If you want to use NFS as the destination, you can follow the steps in this section to deploy NFS. NFS is available in both software and hardware. However, software-based NFS is unstable and is prone to NFS Hang, which can cause backup tasks to be stuck or the machines mounting NFS to malfunction. Therefore, we recommend that you use dedicated NFS hardware.

## Considerations

* When you use an NFS environment, make sure that you mount the NFS share before you enable backup. If an issue occurs with NFS during backup, stop data backup and log archiving first, and then resolve the issue with NFS.

* OceanBase Database of the current version supports NFSv3 and later.

* We recommend that you use an NFS service running on SSD to avoid performance issues with NFS, which may lead to instability.

* When you use NFS as the backup medium, make sure that all OBServer nodes are mounted to the same NFS server. In addition, to ensure smooth backup, use the recommended parameters to mount NFS. For more information, see the **Deploy NFS Client** section in this topic.

* When you restart an OBServer node, make sure that the NFS client is started before the OBServer node.

* Before you start the OBServer node after you add a new server, make sure that the new server has successfully mounted NFS or can back up data to another medium.

## Deployment of the NFS software on the server

<main id="notice" type='notice'>
<h4>Note</h4>
<p>If you use an NFS hardware device, skip this section and proceed to deploy the NFS client. </p>
</main>

1. Log in to the NFS server.

2. Run the following command to install NFS using the YUM package manager.

   ```shell
   sudo yum install nfs-utils
   ```

3. Set up Exports.

   1. Choose an appropriate directory as the shared directory. When you choose a directory, consider the space and performance requirements of backup.

      For example, in this topic, the shared directory is `/data/nfs_server/`.

   2. Run the `sudo vim /etc/exports` command to open the configuration file and set the following parameters.

      ```shell
      /data/nfs_server/ xx.xx.xx.xx/16(rw,sync,all_squash)
      ```

      Here, `xx.xx.xx.xx` indicates the IP address range that is allowed to access the shared directory.

   3. Run the following command to grant permissions to the `nfsnobody` user to ensure that the `nfsnobody` user has the access privileges to the directory specified in the `exports` file.

      ```shell
      sudo chown nfsnobody:nfsnobody -R /data/nfs_server
      ```

4. Run the following command to restart NFS.

   ```shell
   sudo systemctl restart nfs-server
   ```

5. Set up the slot table.

   1. Run the `sudo vim /etc/sysctl.conf` command to open the `sysctl.conf` configuration file and add the following line to the file:

      ```xml
      sunrpc.tcp_max_slot_table_entries=128
      ```

   2. Run the following command to change the maximum number of concurrent NFS requests from the default 32 to 128.

      ```sql
      sudo sysctl -w sunrpc.tcp_max_slot_table_entries=128
      ```

      After the command executes successfully, you can run the `cat /proc/sys/sunrpc/tcp_max_slot_table_entries` command to check whether the setting takes effect. If the returned value is 128, the modification is successful.

   3. (Optional) Restart the server.

## Deploy an NFS client

When you deploy an NFS client, you must operate on all OBServer nodes.

The following example shows the procedure for deploying an NFS client on one OBServer node.

1. Log in to the OBServer node.

2. Run the following command to install NFS using the YUM package manager.

   ```shell
   sudo yum install nfs-utils
   ```

3. Set the slot table.

   1. Run the `sudo vim /etc/sysctl.conf` command to open the `sysctl.conf` configuration file and add the following line in the file:

      ```xml
      sunrpc.tcp_max_slot_table_entries=128
      ```

   2. Run the following command to change the maximum number of concurrent NFS requests to 128.

      ```sql
      sudo sysctl -w sunrpc.tcp_max_slot_table_entries=128
      ```

      After the command executes successfully, you can run the `cat /proc/sys/sunrpc/tcp_max_slot_table_entries` command to check whether the setting takes effect. If the returned value is 128, the modification is successful.

   3. (Optional) Restart the server.

4. Select an appropriate directory as the mount point and run the following command to mount NFS.

      :::tab
      tab NFS 3.x

      For example, in this topic, it is assumed that the NFS share is mounted to the `/data/nfs` directory. If no suitable directory exists, you can create one.

      ```shell
      sudo mount -tnfs -o rw,nfsvers=3,sync,lookupcache=positive,hard,nolock,timeo=600,wsize=1048576,rsize=1048576,namlen=255 10.10.10.1:/data/nfs_server /data/nfs
      ```

      tab NFS 4.x

      For example, in this topic, it is assumed that the NFS share is mounted to the `/data/nfs` directory. If no suitable directory exists, you can create one.

      ```shell
      sudo mount -tnfs -o rw,nfsvers=4.1,sync,lookupcache=positive,hard,timeo=600,wsize=1048576,rsize=1048576,namlen=255 10.10.10.1:/data/nfs_server /data/nfs
      ```

      :::

      In the command:

      * `nfsvers`: the NFS version.

      * `sync`: ensures that data is written synchronously to the server to ensure data consistency. If this parameter is not used, there may be data errors.

      * `lookupcache=positive`: specifies the way the operating system kernel manages the directory cache for a given mount point. Valid values are `all`, `none`, `pos`, and `positive`. The value `positive` is used to avoid mistakenly reporting the non-existence of directories or files when they are concurrently accessed, to ensure data consistency.

      * `hard`: the system will temporarily stall read/write requests from applications when NFS is unavailable to ensure data consistency. The `soft` option is not supported to avoid data errors.

      * `lock/nolock`: specifies whether to use the NLM protocol to lock files on the server. The default value is `lock`. The NFS 4.x protocol inherently supports file locking, but the NFS 3.x protocol does not. If the NFS 3.x protocol is used, we recommend that you add the `nolock` value during mounting to disable file locking.

      * `timeo`: the retry interval, in units of 0.1s. We recommend that you do not set this parameter to a large value. The recommended value is `600`.

      * `wsize`: the size of a write data block. We recommend that you set this parameter to `1048576`.

      * `rsize`: the size of a read data block. We recommend that you set this parameter to `1048576`.

      * `namlen`: We recommend that you set this parameter to `255`.

      * `10.10.10.1`: the IP address of the NFS server.

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <ul>
      <li>When you mount NFS 3/4, make sure that the parameters in the backup mounting environment include the recommended parameters in the example. </li>
      <li>In a Docker environment, mount NFS on the host machine and then map it to the Docker container. If you mount NFS directly in the Docker container, there may be a risk that the client gets stuck (hangs). </li>
      </ul>
      </main>

5. Run the following command to verify the performance of NFS after the mounting is completed.

   ```shell
   fio -filename=/data/nfs/fio_test -direct=1  -rw=randwrite -bs=2048K -size=100G  -runtime=300 -group_reporting -name=mytest  -ioengine=libaio -numjobs=1 -iodepth=64 -iodepth_batch=8 -iodepth_low=8 -iodepth_batch_complete=8
   ```

   For example, the execution result is as follows:

   ```shell
   Run status group 0 (all jobs):
   WRITE: io=322240MB, aggrb=1074.2MB/s, minb=1074.2MB/s, maxb=1074.2MB/s, mint=300006msec, maxt=300006msec
   ```
