# Configure resource isolation within a tenant

This topic describes how to configure resource isolation in MySQL mode.

## Configure resource isolation for resources such as CPU or IOPS

### Prerequisites

* Before you configure resource isolation, we recommend that you understand the basic concepts such as resource group, resource management plan, and resource management plan content. For more information about the basic concepts and applicable scenarios of resource isolation, see [Overview](../100.resource-isolation-overview.md).

* CPU resource isolation depends on cgroup. If you want to control CPU resource isolation, you must configure the cgroup directory and enable the cgroup feature before you configure resource isolation. For more information about how to configure the cgroup directory and enable the cgroup feature, see [Configure cgroup](../300.resource-isolation-of-mysql-mode/100.config-cgroups-of-enterprise-of-mysql.md).

  If you want to configure user-level resource isolation or function-level resource isolation and do not need to control CPU resource isolation (you only need to perform IOPS resource isolation), you do not need to configure cgroup. If you want to configure SQL-level resource isolation, you must configure cgroup regardless of whether you need to control CPU resource isolation.

* Before you perform IOPS resource isolation, you can perform disk performance calibration. For more information about how to perform disk performance calibration, see [Calibrate disk performance](../300.resource-isolation-of-mysql-mode/150.disk-performance-calibration-of-mysql-mode.md).

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>In the current version, IOPS resource isolation no longer strongly depends on disk performance calibration. </p>
   </main>

* Make sure that the users to be isolated are created. For more information about how to create a user, see [Create a user](../../../../500.security-and-permissions/300.access-control/200.user-and-permission/200.permission-of-mysql-mode/110.create-a-user-of-mysql-mode.md).

* If you want to configure SQL-level resource isolation, make sure that the databases, tables, and columns to be isolated are created.

### Background information

Resource isolation is divided into user-level, SQL-level, and function-level resource isolation. For more information about the three types of resource isolation, see [Overview](../100.resource-isolation-overview.md).

### Step 1 (Optional): Configure the MAX_IOPS and MIN_IOPS values of the tenant

<main id="notice" type='explain'>
<h4>Note</h4>
<p>If you have set <code>MAX_IOPS</code> and <code>MIN_IOPS</code> to the IOPS values corresponding to 16 KB reads when you created the tenant, or if you do not need to control IOPS resource isolation, skip this step. </p>
</main>

After you complete disk calibration, before you configure a resource management plan, make sure that the `MAX_IOPS` and `MIN_IOPS` values of the tenant are valid. In this context, valid values refer to the IOPS values corresponding to 16 KB reads, which are used as references for the tenant's IOPS configuration.

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Execute the following command to view the resource specifications of the tenant to be isolated.


   If the `MAX_IOPS` and `MIN_IOPS` values of the tenant are both the default values `INT64_MAX` (9223372036854775807), you need to plan the IOPS resources available to the tenant.

3. Execute the following command to confirm the OBServer nodes on which the tenant is deployed.

   ```sql
   obclient [oceanbase]> SELECT DISTINCT SVR_IP, SVR_PORT FROM oceanbase.CDB_OB_LS_LOCATIONS WHERE tenant_id = xxxx;
   ```

   The query result is as follows:

   ```shell
   +----------------+----------+
   | SVR_IP         | SVR_PORT |
   +----------------+----------+
   | xx.xxx.xxx.xx1 |    xxxx1 |

   | xx.xxx.xxx.xx1 |    xxxx3 |
   +----------------+----------+
   3 rows in set
   ```

4. Execute the following command to confirm the disk calibration value of the OBServer node where the tenant to be isolated is located. Use the disk calibration value corresponding to 16 KB reads as the upper limit for IOPS settings on this node.

   ```sql
   obclient [oceanbase]> SELECT * FROM oceanbase.GV$OB_IO_BENCHMARK WHERE MODE='READ' AND SIZE=16384;
   ```

   The query result is as follows:

   ```shell
   +----------------+----------+--------------+------+-------+-------+------+---------+
   | SVR_IP         | SVR_PORT | STORAGE_NAME | MODE | SIZE  | IOPS  | MBPS | LATENCY |
   +----------------+----------+--------------+------+-------+-------+------+---------+
   | xx.xxx.xxx.xx1 |    xxxx1 | DATA         | READ | 16384 | 48162 |  752 |     331 |
   | xx.xxx.xxx.xx1 |    xxxx2 | DATA         | READ | 16384 | 47485 |  741 |     336 |
   | xx.xxx.xxx.xx1 |    xxxx3 | DATA         | READ | 16384 | 48235 |  753 |     331 |
   +----------------+----------+--------------+------+-------+-------+------+---------+
   3 rows in set
   ```

   Based on the query result, use the disk calibration values of each node as the upper limit to plan the IOPS available to the tenant. Since multiple tenants may be deployed on the same OBServer node in the cluster, you can allocate the IOPS based on the actual business needs.

   For example, if two tenants are deployed on the same OBServer node in a cluster, and the disk IOPS baseline values corresponding to 16 KB reads on each OBServer node are the same (20,000 IOPS), and the expected loads of the two tenants are similar, you can divide the 20,000 IOPS equally between the two tenants (the actual IOPS allocation can be adjusted based on the business needs). In this case, you can set the `MAX_IOPS` and `MIN_IOPS` values of each tenant to 10,000. You can also set `MIN_IOPS` to a value less than `MAX_IOPS` based on the business needs.

5. Execute the following commands to modify the `MAX_IOPS` and `MIN_IOPS` values of the tenant.

   We recommend that you modify the `MIN_IOPS` value first, and then the `MAX_IOPS` value.

   ```sql
   ALTER RESOURCE UNIT unit_name MIN_IOPS = xxx;
   ```

   ```sql
   ALTER RESOURCE UNIT unit_name MAX_IOPS = xxx;
   ```

### Step 2: Configure a resource isolation plan

Assume that the `tp_user` and `ap_user` users already exist in the current tenant.

You can refer to the following steps to configure a resource isolation plan to ensure that the CPUs and IOPS resources of different users or background tasks are isolated.

1. Log in to the MySQL tenant in the cluster.

2. Use the `CREATE_CONSUMER_GROUP` procedure in the `DBMS_RESOURCE_MANAGER` package to create the resource group.

   The statement is as follows:

   ```sql
   CALL DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   CONSUMER_GROUP => 'group_name' ,
   COMMENT => 'coments'
   );
   ```

   The following table describes the related parameters:

   * `CONSUMER_GROUP` : specifies the name of the resource group.

   * `COMMENT`: The remark of the resource group.

   For example, create two resource groups named `interactive_group` and `batch_group`.

   ```shell
   obclient [test]> CALL DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   CONSUMER_GROUP => 'interactive_group' ,
   COMMENT => 'TP'
   );
   ```

   ```shell
   obclient [test]> CALL DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   CONSUMER_GROUP => 'batch_group' ,
   COMMENT => 'AP'
   );
   ```

   After a consumer group is created, you can query the `oceanbase.DBA_RSRC_CONSUMER_GROUPS` view to confirm the creation. For more information about the `oceanbase.DBA_RSRC_CONSUMER_GROUPS` view, see [oceanbase.DBA_RSRC_CONSUMER_GROUPS](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13800.o-dba_rsrc_group_mappings.md).

3. Call the `CREATE_PLAN` procedure in the `DBMS_RESOURCE_MANAGER` package to create the resource management plan.

   It's described as follows:

   ```sql
   CALL DBMS_RESOURCE_MANAGER.CREATE_PLAN(
   PLAN => 'plan_name',
   comment => 'coments');
   ```

   The parameters are described as follows:

   * `PLAN`: specifies the resource management plan name.

   * `COMMENT` : Enter comments for the resource management plan.

   For example, create a resource management plan named `daytime` and add comments.

   ```sql
   obclient [test]> CALL DBMS_RESOURCE_MANAGER.CREATE_PLAN(
   PLAN => 'daytime',
   comment => 'TPFirst');
   ```

   After the resource plan is created, you can query the `oceanbase.DBA_RSRC_PLANS` view to confirm the result. For more information about the `oceanbase.DBA_RSRC_PLANS` view, see [oceanbase.DBA_RSRC_PLANS](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/14000.o-dba_rsrc_plans-mysql.md).

4. Call the `CREATE_PLAN_DIRECTIVE` subprogram in the `DBMS_RESOURCE_MANAGER` system package to create the resource plan content. This is used to enable the resource plan and restrict the CPU and IOPS resources that a resource group can use.

   The statement is as follows:

   ```sql
   CALL DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE (
      PLAN => 'plan_name',
      GROUP_OR_SUBPLAN => 'group_name' ,
      COMMENT  => 'comments',
      MGMT_P1 => int_value,
      UTILIZATION_LIMIT => int_value,
      MIN_IOPS => int_value,
      MAX_IOPS => int_value,
      WEIGHT_IOPS => int_value,
      MAX_NET_BANDWIDTH => int_value,
      NET_BANDWIDTH_WEIGHT => int_value);
   ```

   The following table describes the related parameters:

   * `PLAN`: the name of the resource management plan.

   * `GROUP_OR_SUBPLAN` specifies the resource group.

   * `COMMENT` : A note describing the resource management plan, which is `NULL` by default.

   * `MGMT_P1`: specifies the percentage of CPU utilization at which the system is fully loaded. The default value is `100`.

   * `UTILIZATION_LIMIT` : The upper limit of the CPU resources used by the resource group. The default value is `100`, and the value ranges from 0 to 100, inclusive. `100` indicates that the maximum CPU resources of a tenant can be used. If you set the value to `70`, the maximum CPU resources that can be used by a tenant is 70%.

   * `MIN_IOPS` : The number of IOPS reserved in the resource group for IO contention. This value cannot exceed 100. The default value is `0`.

   * `MAX_IOPS` : Specifies the maximum I/O operations per second (IOPS) resources that can be used for a resource group. The sum can exceed 100. The default value is `100` .

   * `WEIGHT_IOPS` : the weight value for IOPS, which can exceed 100 in total and the default value is `0`.

   * `WEIGHT_IOPS`: A weight value for IOPS, which can be greater than 100 in total and defaults to `0`.

   * `MAX_NET_BANDWIDTH`: the maximum network bandwidth resources that can be used. This value can exceed 100 and defaults to `100`.

   * `NET_BANDWIDTH_WEIGHT`: the bandwidth weight value. The sum of all weights can be greater than 100, and the bandwidth will be proportionally divided. The default value is `0`.

   As follows:

   * Use `daytime` as the resource plan, bind `interactive_group` as the resource group, and specify that no more than 80% of the tenant's CPU resources are available. If I/O resources are competing, set the minimum available IOPS to 30% of the total IOPS, the maximum available IOPS to 90% of the total IOPS, the IOPS weight to 80, the maximum available bandwidth to 40% of the total bandwidth, and the bandwidth weight to 40.

      ```shell
      obclient [test]> CALL DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
      PLAN => 'daytime',
      GROUP_OR_SUBPLAN => 'interactive_group' ,
      COMMENT  => '',
      UTILIZATION_LIMIT =>80,
      MIN_IOPS => 30,
      MAX_IOPS => 90,
      WEIGHT_IOPS => 80,
      MAX_NET_BANDWIDTH => 40,
      NET_BANDWIDTH_WEIGHT => 40);
      ```

   * Specify `daytime` as the resource plan, bind the `batch_group` resource group, and set the upper limit of CPU resources available to the tenant to 40% of the total CPU resources. When I/O contention occurs, set the minimum available IOPS resources to 40%, the upper limit of IOPS resources available to 80%, IOPS resource weight to 70, the upper limit of available bandwidth resources to 30%, and bandwidth weight to 30.

      ```shell
      obclient [test]> CALL DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
      PLAN => 'daytime',
      GROUP_OR_SUBPLAN => 'batch_group' ,
      COMMENT  => '',
      UTILIZATION_LIMIT => 40,
      MIN_IOPS => 40,
      MAX_IOPS => 80,
      WEIGHT_IOPS => 70,
      MAX_NET_BANDWIDTH => 30,
      NET_BANDWIDTH_WEIGHT => 30);
      ```

   After the resource directive is created, you can query the `oceanbase.DBA_RSRC_PLAN_DIRECTIVES` view and `oceanbase.DBA_OB_RSRC_IO_DIRECTIVES` view to confirm the directive.

   For more information about the `oceanbase.DBA_RSRC_PLAN_DIRECTIVES` view, see [oceanbase.DBA_RSRC_PLAN_DIRECTIVES](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13900.o-dba_rsrc_plan_directives.md).

   For more information about the `oceanbase.DBA_OB_RSRC_IO_DIRECTIVES` view, see [oceanbase.DBA_OB_RSRC_IO_DIRECTIVES](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/11000.o-dba_ob_rsrc_io_directives.md).

5. Call the `SET_CONSUMER_GROUP_MAPPING` procedure in the `DBMS_RESOURCE_MANAGER` system package to create resource isolation match rules according to your actual usage scenarios.

   The statement is as follows:

   ```sql
   CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
      ATTRIBUTE => 'column | user | function', 
      VALUE => 'values',
      CONSUMER_GROUP => 'group_name');
   ```

   Here are the descriptions of the related parameters:

   * `ATTRIBUTE`: the attribute type, the attribute name is not case sensitive.

     * `column` represents resource isolation at the SQL level.

     * `user` specifies the resource isolation at the user level.

     * `function` indicates resource isolation at the Function level.

   * `VALUE` – Specify the value for the attribute.

     * If the attribute type is `column`, you need to specify the database name, table name, column name, constant value, and username.

       Where:

       * The database name and username are optional. The default database name is the current database name. If the username is not specified, the rule applies to all users, including those created in the current tenant.

       * The table name, column name, and constant value are mandatory and can only have one value each. When specifying the constant value, only numeric or string values are allowed.

       * The specified table, column, and user must exist.

     * If the attribute type is `user`, you just need to specify the username. Only one user can be specified.

     * If the attribute type is `function`, you need to specify the background tasks corresponding to the DAG thread: compaction_high, ha_high, compaction_mid, ha_mid, compaction_low, ha_low, ddl, ddl_high, clog_high, and opt_stats. You only need to specify one of these tasks. Only one task can be specified. For detailed information about these tasks, see [Overview](../100.resource-isolation-overview.md).

   * `CONSUMER_GROUP`: specifies the resource group that you want to bind. It indicates which resource group the statement will be bound to when the SQL statement matches the rules specified in `VALUE`. Only one resource group can be specified.

        If no resource group is specified, the system binds the statement to the built-in `OTHER_GROUPS` resource group. The resources for the built-in `OTHER_GROUPS` resource group are as follows:

        * MIN_IOPS = 100 - SUM(resources of other resource groups in the tenant)

        * MAX_IOPS = 100

        * WEIGHT_IOPS = 100

   Here are some examples:

   * Create an SQL-level resource isolation matching rule.

      * Specify that when a SQL statement executed by the `tp_user` user contains the `WHERE` clause `test.t.c3 = 3`, the statement is bound to the `batch_group` resource group and executes using the CPU and IOPS resources restricted by this resource group.

        <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>The SQL statement does not need to contain the <code>test.t.</code> prefix. As long as the <code>c3</code> column in the statement is resolved to <code>test.t.c3</code>, the statement will be bound to the resource group named <code>batch_group</code>. For example: <code>SELECT * FROM test.t WHERE c3 = 1;</code>. </p>
        </main>

        ```shell
        obclient [test]> CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'column',
        VALUE => 'test.t.c3=3 for tp_user',
        CONSUMER_GROUP => 'batch_group');
        ```

      * Specify that when a SQL statement executed by the `tp_user` user contains the `WHERE` clause `t.c3 = 5`, the statement is bound to the `interactive_group` resource group and executes using the CPU and IOPS resources restricted by this resource group.

        ```shell
        obclient [test]> CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'column',
        VALUE => 't.c3=5',
        CONSUMER_GROUP => 'interactive_group');
        ```

       In addition to calling the `SET_CONSUMER_GROUP_MAPPING` procedure to bind resource groups, OceanBase Database also supports binding resource groups using hints. Users can use hints to flexibly submit an SQL statement to a specified resource group. For example, if you want the SQL statement `SELECT * FROM T` to use resources restricted by the `batch_group` resource group, you can bind it to this resource group using hints, as shown below:

      ```shell
      obclient [test]> SELECT /*+resource_group('batch_group')*/ * FROM t;
      ```

      <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>After specifying the resource group using a hint, if the specified resource group does not exist, the default resource group <code>OTHER_GROUPS</code> is used. </p>
      </main>

   * Create a user-level resource isolation matching rule.

      * Specify that when the `tp_user` user executes an SQL statement, the statement is bound to the `interactive_group` resource group and executes using the CPU and IOPS resources restricted by this resource group.

        ```shell
        obclient [test]> CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'user',
        VALUE => 'tp_user',
        CONSUMER_GROUP => 'interactive_group');
        ```

      * Specify that when the `ap_user` user executes an SQL statement, the statement is bound to the `batch_group` resource group and executes using the CPU and IOPS resources restricted by this resource group.

        ```shell
        obclient [test]> CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'user',
        VALUE => 'ap_user',
        CONSUMER_GROUP => 'batch_group');
        ```

   * Create a function-level resource isolation matching rule.

      * Specify that when the `compaction_high` task is executed, the system binds the statement to the `interactive_group` resource group and executes using the CPU and IOPS resources restricted by this resource group.

        ```shell
        obclient [test]> CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'function',
        VALUE => 'compaction_high',
        CONSUMER_GROUP => 'interactive_group');
        ```

      * Specify that when the `ddl_high` task is executed, the system binds the statement to the `batch_group` resource group and executes using the CPU and IOPS resources restricted by this resource group.

        ```shell
        obclient [test]> CALL DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'function',
        VALUE => 'ddl_high',
        CONSUMER_GROUP => 'batch_group');
        ```

   After a rule is created, you can query the `oceanbase.DBA_RSRC_GROUP_MAPPINGS` view to confirm the result. For more information about the `oceanbase.DBA_RSRC_GROUP_MAPPINGS` view, see [oceanbase.DBA_RSRC_GROUP_MAPPINGS](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13800.o-dba_rsrc_group_mappings.md).

6. Enable an appropriate resource management plan for the resource group.

   Resource groups may be limited by different resources under different resource management plans. You must enable an appropriate resource management plan for the resource group.

   ```sql
   obclient [test]> SET GLOBAL resource_manager_plan = 'daytime';
   ```

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>If you do not need to limit resources, you can use the <code>SET GLOBAL resource_manager_plan = '';</code> statement to disable all resource plans. </p>
   </main>

### Considerations after configuration

* After adding resource isolation matching rules, if a user is deleted and then re-added, the resource isolation matching rules will still apply.

* Resource isolation matching rules take effect after they are added, but it may take up to 10 seconds for them to take effect, depending on the actual environment.

* SQL-level resource isolation has higher priority than user-level and function-level resource isolation.

* After adding resource isolation matching rules, they currently only take effect in statements such as `SELECT`, `INSERT`, `UPDATE`, and `DELETE`. They do not take effect in DDL or DCL statements, nor in PL. However, they can take effect in prepareStatement.

### Performance impact after configuration

* User-level and function-level resource isolation can determine which resource group to use before SQL parsing, so they have no impact on performance.

* The performance impact of SQL-level resource isolation mainly comes from retries. Unlike user-level and function-level resource isolation, which determine the resource group to use before SQL parsing, SQL-level resource isolation determines the resource group to use during SQL parsing or when a plan is cached. If the resource group determined during parsing or plan caching is different from the current one, the system will retry once to use the resource group specified by the matching rule to process the SQL.

  The performance impact of SQL-level resource isolation can be divided into the following three scenarios:

  1. If an SQL statement does not match any rule, it has almost no impact on performance.

  2. If an SQL statement matches a rule, and the rule specifies the `batch_group` resource group, the SQL will be executed using the `batch_group` resource. The next SQL statement will also be executed using the `batch_group` resource until it matches a rule that specifies a different resource group, at which point the system will retry. For a batch of continuously executed SQL statements all bound to the same resource group, this strategy ensures that only the first SQL statement in the batch requires a retry, while the subsequent SQL statements do not. This minimizes retries and has a minimal impact on performance.

  3. If each SQL statement is expected to use a different resource group than the previous one, each SQL statement will require a retry, resulting in a significant impact on performance.

## (Optional) Configure resource isolation for DDL worker threads

In the current version, DDL requests and DML requests compete for foreground worker threads. When a large number of DDL requests occur in a short period of time, it severely affects the normal requests of users. To minimize the impact on performance stability caused by thread resource contention, OceanBase Database has split the DDL worker thread resources from DML worker thread resources. You can choose to enable DDL worker thread resource isolation based on your business needs.

OceanBase Database uses the tenant-level hidden parameter `_enable_ddl_worker_isolation` to control whether to enable DDL worker thread resource isolation. The value and meaning of this parameter are as follows:

* `False`: DDL worker thread resource isolation is disabled. In this case, DDL requests and DML requests share worker threads and affect each other.

* `True`: DDL worker thread resource isolation is enabled. In this case, DDL requests use independent worker threads, and the number of DDL requests executed by a tenant at the same time is limited to avoid excessive impact on DML requests.

To enable DDL worker thread resource isolation, perform the following steps:

1. Log in to the MySQL tenant of the cluster as the `root` user.

   Here is an example of the connection command:

    ```shell
    obclient -h172.30.xxx.xxx -P2883 -uroot@mysqltenant#obdemo -pxxxx -A
    ```

2. View the value of the `_enable_ddl_worker_isolation` parameter.

   ```shell
   obclient [oceanbase]> SELECT * FROM oceanbase.GV$OB_PARAMETERS WHERE NAME LIKE '%_enable_ddl_worker_isolation%';
   ```

   Here is an example of the query result:

   ```shell
   +----------------+----------+-------+--------+-----------+------------------------------+-----------+-------+------------------------------------------+--------------+-------------------+---------------+-----------+
   | SVR_IP         | SVR_PORT | ZONE  | SCOPE  | TENANT_ID | NAME                         | DATA_TYPE | VALUE | INFO                                     | SECTION      | EDIT_LEVEL        | DEFAULT_VALUE | ISDEFAULT |
   +----------------+----------+-------+--------+-----------+------------------------------+-----------+-------+------------------------------------------+--------------+-------------------+---------------+-----------+
   | 172.xx.xxx.xxx |     2882 | zone1 | TENANT |      1002 | _enable_ddl_worker_isolation | NULL      | True  | a switch controling ddl thread isolation | ROOT_SERVICE | DYNAMIC_EFFECTIVE | False         | NO        |
   +----------------+----------+-------+--------+-----------+------------------------------+-----------+-------+------------------------------------------+--------------+-------------------+---------------+-----------+
   1 row in set
   ```

3. Modify the value of the `_enable_ddl_worker_isolation` parameter.

   ```shell
   obclient [oceanbase]> ALTER SYSTEM SET _enable_ddl_worker_isolation = True;
   ```
