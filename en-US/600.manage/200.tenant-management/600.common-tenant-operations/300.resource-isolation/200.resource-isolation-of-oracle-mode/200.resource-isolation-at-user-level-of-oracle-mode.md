# Configure resource isolation within a tenant

This topic describes how to configure resource isolation in Oracle mode.

## Prerequisites

* Before you configure resource isolation, we recommend that you understand the basic concepts, such as resource groups, resource management plans, and resource management plan contents. For more information, see [Overview of resource isolation](../100.resource-isolation-overview.md).

* CPU resource isolation depends on cgroups. If you want to control CPU resource isolation, you must configure the cgroup directory and enable the cgroup feature before you configure resource isolation. For more information, see [Configure cgroups](../200.resource-isolation-of-oracle-mode/100.config-cgroups-of-oracle-mode.md).

  When you configure user-level or function-level resource isolation, you do not need to configure cgroups if you only want to control IOPS resource isolation. When you configure SQL-level resource isolation, you must configure cgroups whether or not you want to control CPU resource isolation.

* Before you configure IOPS resource isolation, you can perform disk performance calibration. For more information, see [Calibrate disk performance](../200.resource-isolation-of-oracle-mode/150.disk-performance-calibration-of-oracle-mode.md).

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>In the current version, IOPS resource isolation no longer strongly depends on disk performance calibration. </p>
   </main>

* Make sure that you have created the users to be isolated. For more information, see [Create a user](../../../../500.security-and-permissions/300.access-control/200.user-and-permission/300.permission-of-oracle-mode/100.create-a-user-of-oracle-mode.md).

* If you want to configure SQL-level resource isolation, make sure that you have created the databases, tables, and columns to be isolated.

## Background information

Resource isolation is divided into user-level, SQL-level, and function-level resource isolation. For more information, see [Overview of resource isolation](../100.resource-isolation-overview.md).

## Step 1 (Optional): Configure the MAX_IOPS and MIN_IOPS values of a tenant to valid values

<main id="notice" type='explain'>
<h4>Note</h4>
<p>If you have set <code>MAX_IOPS</code> and <code>MIN_IOPS</code> to the IOPS values corresponding to 16 KB reads when you created the tenant, or you do not want to control IOPS resource isolation, you can skip this step. </p>
</main>

After you calibrate the disk, before you configure a resource management plan, make sure that the `MAX_IOPS` and `MIN_IOPS` values of the tenant are valid. In this context, valid values refer to the IOPS values corresponding to 16 KB reads as the reference values for tenant IOPS configuration.

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Execute the following command to view the resource specifications of the tenant to be isolated.

   ```sql
   obclient [oceanbase]> SELECT * FROM oceanbase.DBA_OB_UNIT_CONFIGS;
   ```

   The query result is as follows:

   ```shell
   +----------------+-----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+---------------------+---------------------+-------------+
   | UNIT_CONFIG_ID | NAME            | CREATE_TIME                | MODIFY_TIME                | MAX_CPU | MIN_CPU | MEMORY_SIZE | LOG_DISK_SIZE | MAX_IOPS            | MIN_IOPS            | IOPS_WEIGHT |
   +----------------+-----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+---------------------+---------------------+-------------+
   |              1 | sys_unit_config | 2023-12-19 13:55:04.463295 | 2023-12-19 13:56:08.969718 |       3 |       3 |  2147483648 |    3221225472 | 9223372036854775807 | 9223372036854775807 |           3 |
   |           1001 | small_unit      | 2023-12-19 13:56:09.851665 | 2023-12-19 13:56:09.851665 |       1 |       1 |  2147483648 |    6442450944 | 9223372036854775807 | 9223372036854775807 |           1 |
   |           1002 | medium_unit     | 2023-12-19 13:56:10.030914 | 2023-12-19 13:56:10.030914 |       8 |       4 |  8589934592 |   25769803776 | 9223372036854775807 | 9223372036854775807 |           4 |
   |           1003 | large_unit      | 2023-12-19 13:56:10.112115 | 2023-12-19 13:56:10.112115 |      16 |       8 | 21474836480 |   64424509440 | 9223372036854775807 | 9223372036854775807 |           8 |
   +----------------+-----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+---------------------+---------------------+-------------+
   4 rows in set
   ```

   If the `MAX_IOPS` and `MIN_IOPS` values of the tenant are both the default value `INT64_MAX` (9223372036854775807), you need to plan the IOPS resources available to the tenant.

3. Execute the following command to view the OBServer nodes on which the tenant is deployed.

   ```sql
   obclient [oceanbase]> SELECT DISTINCT SVR_IP, SVR_PORT FROM oceanbase.CDB_OB_LS_LOCATIONS WHERE tenant_id = xxxx;
   ```

   The query result is as follows:

   ```shell
   +----------------+----------+
   | SVR_IP         | SVR_PORT |
   +----------------+----------+
   | xx.xxx.xxx.xx1 |    xxxx1 |
   | xx.xxx.xxx.xx1 |    xxxx2 |
   | xx.xxx.xxx.xx1 |    xxxx3 |
   +----------------+----------+
   3 rows in set
   ```

4. Execute the following command to view the disk calibration values of the OBServer node where the tenant to be isolated is deployed. Use the disk calibration values corresponding to 16 KB reads as the upper limit of the IOPS settings of the node.

   ```sql
   obclient [oceanbase]> SELECT * FROM oceanbase.GV$OB_IO_BENCHMARK WHERE MODE='READ' AND SIZE=16384;
   ```

   The query result is as follows:

   ```shell
   +----------------+----------+--------------+------+-------+-------+------+---------+
   | SVR_IP         | SVR_PORT | STORAGE_NAME | MODE | SIZE  | IOPS  | MBPS | LATENCY |
   +----------------+----------+--------------+------+-------+-------+------+---------+
   | xx.xxx.xxx.xx1 |    xxxx1 | DATA         | READ | 16384 | 48162 |  752 |     331 |
   | xx.xxx.xxx.xx1 |    xxxx2 | DATA         | READ | 16384 | 47485 |  741 |     336 |
   | xx.xxx.xxx.xx1 |    xxxx3 | DATA         | READ | 16384 | 48235 |  753 |     331 |
   +----------------+----------+--------------+------+-------+-------+------+---------+
   3 rows in set
   ```

   Based on the query result, use the disk calibration values of each node as the upper limit to plan the IOPS available to the tenant. Since multiple tenants may be deployed on the same OBServer node in the cluster, you need to allocate the IOPS based on the actual business requirements.

   For example, assume that two tenants are deployed on the same OBServer node in a cluster. The disk IOPS baseline values corresponding to 16 KB reads of each OBServer node are the same, 20,000 IOPS. If the expected loads of the two tenants are similar, you can divide the 20,000 IOPS equally between the two tenants (the actual IOPS available to each tenant can be adjusted based on the business requirements). In this case, you can configure the `MAX_IOPS` and `MIN_IOPS` values of each tenant to 10,000. You can also set `MIN_IOPS` to a value less than `MAX_IOPS` based on the business requirements.

5. Execute the following commands to modify the `MAX_IOPS` and `MIN_IOPS` values of the tenant.

   We recommend that you modify the `MIN_IOPS` value first, and then the `MAX_IOPS` value.

   ```sql
   ALTER RESOURCE UNIT unit_name MIN_IOPS = xxx;
   ```

   ```sql
   ALTER RESOURCE UNIT unit_name MAX_IOPS = xxx;
   ```

## Step 2: Configure the resource isolation plan

Assume that the `tp_user` and `ap_user` users exist in the current tenant.

You can follow these steps to configure an instance isolation plan that enables different users or background tasks to use different CPU or IOPS resources.

1. Log in to the Oracle tenant in the cluster as the tenant administrator.

2. Call the `CREATE_CONSUMER_GROUP` procedure in the `DBMS_RESOURCE_MANAGER` system package to create two resource groups for resource isolation.

   The query statement is as follows:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   consumer_group => 'group_name' ,
   COMMENT => 'coments'
   );
   END; 
   ```

   The following table describes the related parameters:

   * `CONSUMER_GROUP` : Specifies the name of the resource group.

   * `COMMENT` : Enter a comment for the resource group.

   For example, you create two resource groups, named `big_group` and `small_group`.

   ```shell
   obclient [SYS]> delimiter //
   ```

   ```shell
   obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   consumer_group => 'big_group' ,
   COMMENT => 'TP'
   );
   END; //
   ```

   ```shell
   obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   consumer_group => 'small_group' ,
   COMMENT => 'AP'
   );
   END; //
   ```

   To confirm, you can query the `DBA_RSRC_CONSUMER_GROUPS` view. For more information about the `DBA_RSRC_CONSUMER_GROUPS` view, see [DBA_RSRC_CONSUMER_GROUPS](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18400.dba_rsrc_consumer_groups-of-oracle-mode.md).

3. Call the `CREATE_PLAN` subprogram in the `DBMS_RESOURCE_MANAGER` system package to create a resource management plan.

   The following statement is made:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN(
   PLAN => 'plan_name',
   COMMENT =>'coments'
   );
   END;
   ```

   The parameters are described as follows:

   * `PLAN`: The name of the resource management plan.

   * `COMMENT` : Enter remarks about the resource management plan.

   For example, create a resource management plan named `plan_a`.

   ```shell
   obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN(
   PLAN => 'plan_a');
   END; //
   ```

   Once created, you can query the `DBA_RSRC_PLANS` view to verify. For more information about the `DBA_RSRC_PLANS` view, see [DBA_RSRC_PLANS](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18700.dba_rsrc_plans-of-oracle-mode.md).

4. Call the `CREATE_PLAN_DIRECTIVE` subprogram in the `DBMS_RESOURCE_MANAGER` system package to create the resource management plan directive. This directive is used to limit the CPU and IOPS resources consumed by the resource group when the resource management plan is enabled.

   The statements are as follows:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
   PLAN => 'plan_name',
   GROUP_OR_SUBPLAN => 'group_name',
   COMMENT  => 'comments',
   MGMT_P1 => int_value,
   UTILIZATION_LIMIT => int_value,
   MIN_IOPS => int_value,
   MAX_IOPS => int_value,
   WEIGHT_IOPS => int_value,
   MAX_NET_BANDWIDTH => int_value,
   NET_BANDWIDTH_WEIGHT => int_value);
   END;
   ```

   The relevant parameters are described as follows:

   * `PLAN` : specifies the name of the associated resource management plan.

   * `GROUP_OR_SUBPLAN` : Specifies the resource group.

   * `COMMENT`: comments about the content of the resource management plan; default value is `NULL`.

   * `MGMT_P1` Specifies the relative maximum CPU utilization in percentage when the system is operating at full capacity. Default value is `100`.

   * `UTILIZATION_LIMIT` specifies the upper limit of the CPU resources used by the resource group. The default value of this parameter is `100`. The value of this parameter must be in the range (0, 100\]. If the value is `100`, the tenant can use all the CPU resources in the resource group. If the value is `40`, the tenant can use at most 40% of the CPU resources in the resource group.

   * `MIN_IOPS`: The IOPS resources reserved for the resource group when I/O contention occurs. The total does not exceed 100. The default value is `0`.

   * `MAX_IOPS`: specifies the maximum amount of IOPS resource that can be used by the resource group. The total of this parameter for all resource groups can exceed 100. The default value is `100`.

   * `WEIGHT_IOPS`: the weight value of IOPS, which can exceed 100 and defaults to `0`.

   * `MAX_NET_BANDWIDTH` specifies the maximum amount of bandwidth that can be used and is a percentage of the total bandwidth resource. By default, this value is `100`.

   * `NET_BANDWIDTH_WEIGHT`: The weight of the network bandwidth. The sum of weights can exceed 100. By default, the weight is `0`.

   Example:

   * Set resource plans to `plan_a`, bind the resource group `big_group`, and set the CPU usage limit for tenants to 60% of the total CPU resources. If an I/O contention occurs, set the minimum available IOPS to 20%, and specify an IOPS usage limit of 100% of the total IOPS resources. Additionally, set the IOPS resource weight to 20, the available network bandwidth to 50%, and the network bandwidth weight to 50%.

      ```shell
      obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
      PLAN => 'plan_a',
      GROUP_OR_SUBPLAN => 'big_group',
      COMMENT  => 'TP takes precedence',
      UTILIZATION_LIMIT =>60,
      MIN_IOPS => 20,
      MAX_IOPS => 100,
      WEIGHT_IOPS => 20,
      MAX_NET_BANDWIDTH => 50,
      NET_BANDWIDTH_WEIGHT =>50);
      END; //
      ```

   * Assign a resource plan named `plan_a` to the resource group `small_group`, and set the tenant's CPU resource upper limit to 40%. Also, configure the minimum available IOPS to 10%, the maximum IOPS resource usage to 90% of total IOPS, the IOPS resource weight to 30, the available network bandwidth to 60%, and the network bandwidth weight to 60.

      ```shell
      obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
      PLAN => 'plan_a',
      GROUP_OR_SUBPLAN => 'small_group' ,
      COMMENT  => 'AP first',
      UTILIZATION_LIMIT =>40,
      MIN_IOPS => 10,
      MAX_IOPS => 90,
      WEIGHT_IOPS => 30,
      MAX_NET_BANDWIDTH => 60,
      NET_BANDWIDTH_WEIGHT =>60);
      END; //
      ```

   The creation is successful. You can query the `DBA_RSRC_PLAN_DIRECTIVES` view and the `DBA_OB_RSRC_IO_DIRECTIVES` view to verify it.

   For more information about the `DBA_RSRC_PLAN_DIRECTIVES` view, see [DBA_RSRC_PLAN_DIRECTIVES](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18600.dba_rsrc_plan_directives-of-oracle-mode.md).

   For more information about the `DBA_OB_RSRC_IO_DIRECTIVES` view, see [DBA_OB_RSRC_IO_DIRECTIVES](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/15000.dba_ob_rsrc_io_directives-oracle.md).

5. Call the `SET_CONSUMER_GROUP_MAPPING` subprogram in the `DBMS_RESOURCE_MANAGER` package to create resource isolation matching rules based on the actual scenario.

   The statement is as follows:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
      ATTRIBUTE => 'column | user | function',
      VALUE => 'values',
      CONSUMER_GROUP => 'group_name');
      END;
   ```

   The parameters are described as follows:

   * `ATTRIBUTE`: specifies the attribute type. The attribute name is case-insensitive.

     * `column`: specifies SQL-level resource isolation.

     * `user`: specifies user-level resource isolation.

     * `function`: specifies function-level resource isolation.

   * `VALUE`: specifies the attribute value.

     * If the attribute type is `column`, you must specify the database name, table name, column name, constant value, and username.

       The following points apply:

       * The database name and username are optional. The default database name is the current database name, which is the same as the username. If no username is specified, the rule applies to all users, including those created in the current tenant.

       * The table name, column name, and constant value are required, and only one value can be specified for each. When specifying a constant value, only numerical or string values are supported.

       * When specifying the table name, column name, and username, the specified table, column, and user must exist.

       In Oracle mode of OceanBase Database, after the statement is executed, the database name, table name, column name, and username are automatically converted to uppercase. If you want to keep them in lowercase, you can enclose them in double quotation marks. Example:

       ```shell
       obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
       ATTRIBUTE        =>  'column',
       VALUE            => '"test"."t1"."c3" = 3 for "user_big"',
       CONSUMER_GROUP   => 'big_group');
       END; //
       ```

     * If the attribute type is `user`, you must specify the username. Only one user can be specified.

     * If the attribute type is `function`, you must specify one of the following background tasks corresponding to the DAG thread: compaction_high, ha_high, compaction_mid, ha_mid, compaction_low, ha_low, ddl, ddl_high, clog_high, and opt_stats. Only one task can be specified. For more information about these tasks, see [Overview](../100.resource-isolation-overview.md).

   * `CONSUMER_GROUP`: specifies the resource group to which the SQL statement is bound. When the SQL statement matches the rule specified by `VALUE`, it is bound to the specified resource group. Only one resource group can be specified.

        If no resource group is specified, the system binds the statement to the built-in `OTHER_GROUPS` resource group. The resources of the built-in `OTHER_GROUPS` resource group are as follows:

        * MIN_IOPS = 100 - SUM of the total resources of other resource groups in the tenant

        * MAX_IOPS = 100

        * WEIGHT_IOPS = 100

   Examples:

   * Create a SQL-level resource isolation matching rule.

      * Specify that when a SQL statement executed by the `tp_user` user contains the `sys.t.c3 = 3` condition in the `WHERE` clause, the statement is bound to the `big_group` resource group and uses the CPU and IOPS resources limited by this resource group.

        <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>When executing a SQL statement, it is not necessary for the statement to contain <code>sys.t.</code>. As long as <code>c3</code> is resolved to <code>sys.t.c3</code>, the statement is bound to the <code>big_group</code> resource group. Example: <code>SELECT * FROM sys.t WHERE c3 = 1;</code>. </p>
        </main>

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'column',
        VALUE => 'sys.t.c3=3 for tp_user',
        CONSUMER_GROUP => 'big_group');
        END; //
        ```

      * Specify that when a SQL statement executed by the `tp_user` user contains the `t.c3=5` condition in the `WHERE` clause, the statement is bound to the `small_group` resource group and uses the CPU and IOPS resources limited by this resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'column',
        VALUE => 't.c3=5',
        CONSUMER_GROUP => 'small_group');
        END; //
        ```

      In addition to binding a resource group by calling the `SET_CONSUMER_GROUP_MAPPING` subprogram, OceanBase Database also supports binding a resource group by using a hint. You can use a hint to flexibly submit the SQL statement to be executed to a specified resource group. For example, if the SQL statement to be executed is `SELECT * FROM T` and you want the statement to use the resources limited by the `big_group` resource group, you can use a hint to bind the statement to the `big_group` resource group as follows:

      ```shell
      obclient [SYS]> SELECT /*+resource_group('big_group')*/ * FROM T;
      ```

      <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>After you specify a resource group by using a hint, if the resource group does not exist, the statement is executed in the default resource group <code>OTHER_GROUPS</code>. </p>
      </main>

   * Create a user-level resource isolation matching rule.

      * Specify that SQL statements executed by the `tp_user` user are bound to the `big_group` resource group and use the CPU and IOPS resources limited by this resource group.

        ```sql
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'user',
        VALUE => 'tp_user',
        CONSUMER_GROUP => 'big_group');
        END; //
        ```

      * Specify that SQL statements executed by the `ap_user` user are bound to the `small_group` resource group and use the CPU and IOPS resources limited by this resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'user',
        VALUE => 'ap_user',
        CONSUMER_GROUP => 'small_group');
        END; //
        ```

   * Create a function-level resource isolation matching rule.

      * Specify that when the `ha_high` task is executed, the system binds the task to the `big_group` resource group and uses the CPU and IOPS resources limited by this resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'function',
        VALUE => 'ha_high',
        CONSUMER_GROUP => 'big_group');
        END; //
        ```

      * Specify that when the `ddl_high` task is executed, the system binds the task to the `small_group` resource group and uses the CPU and IOPS resources limited by this resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'function',
        VALUE => 'ddl_high',
        CONSUMER_GROUP => 'small_group');
        END; //
        ```

   After the resource group is created, you can query the `DBA_RSRC_GROUP_MAPPINGS` view to confirm the creation. For more information about the `DBA_RSRC_GROUP_MAPPINGS` view, see [DBA_RSRC_GROUP_MAPPINGS](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18500.dba_rsrc_group_mappings-of-oracle-mode.md).

6. Enable an appropriate resource management plan for the resource group.

   The resources limited for the same resource group may vary across different resource management plans. You need to enable an appropriate resource management plan for the resource group.

   ```shell
   obclient [SYS]>delimiter ;
   ```

   ```shell
   obclient [SYS]> ALTER SYSTEM SET resource_manager_plan = 'plan_a';
   ```

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>If you do not want to limit resources, you can use the <code>ALTER SYSTEM SET resource_manager_plan = '';</code> statement to disable all resource plans. </p>
   </main>

## Considerations after configuration

* After adding resource isolation matching rules, if you delete a user and then recreate it, the resource isolation matching rules still apply.

* After adding resource isolation matching rules, they may take effect within 10 seconds. The actual time may vary depending on the environment.

* SQL-level resource isolation has higher priority than user-level and function-level resource isolation.

* After adding resource isolation matching rules, they are currently effective only in statements such as `SELECT`, `INSERT`, `UPDATE`, and `DELETE`. They are not effective in DDL and DCL statements or in PL. However, they can be effective in prepareStatement.

## Performance impact after configuration

* User-level and function-level resource isolation can determine which resource group to use before parsing an SQL statement, so they do not affect performance.

* The performance impact of SQL-level resource isolation mainly comes from retries. Unlike user-level and function-level resource isolation, which can determine the resource group to use before parsing an SQL statement, SQL-level resource isolation can only determine the resource group to use after parsing the SQL statement or when it hits the plan cache. If the resource group determined at this point is different from the current one, the system will retry to use the resource group specified by the matching rule to process the SQL statement.

  The performance impact of SQL-level resource isolation can be categorized into the following three scenarios:

  1. If an SQL statement does not match any rule, it has almost no impact on performance.

  2. If an SQL statement matches a rule, and the rule specifies the `big_group` resource group, the SQL statement will be executed using the `big_group` resource group. The next SQL statement will also be executed using the `big_group` resource group until a rule is matched that indicates a switch to another resource group. At this point, the system will retry to use the resource group specified by the matching rule to process the SQL statement. In scenarios where a batch of SQL statements is executed continuously and all are bound to the same resource group, using this strategy ensures that only the first SQL statement in the batch requires a retry, while subsequent SQL statements do not. This minimizes retries and has a minimal impact on performance.

  3. If each SQL statement is expected to use a different resource group from the previous one, each statement will require a retry, which can significantly impact performance.
