# Configure resource isolation within a tenant

This topic describes how to configure resource isolation in Oracle mode.

## Configure resource isolation for resources such as CPU and IOPS

### Prerequisites

* Before you configure resource isolation, we recommend that you understand the basic concepts, such as resource group, resource management plan, and resource management plan content. For more information about the basic concepts and applicable scenarios of resource isolation, see [Overview of resource isolation](../100.resource-isolation-overview.md).

* CPU resource isolation relies on cgroup. If you want to control CPU resource isolation, you must configure the cgroup directory and enable the cgroup feature before you configure resource isolation. For more information, see [Configure cgroup](../200.resource-isolation-of-oracle-mode/100.config-cgroups-of-oracle-mode.md).

  When you configure user-level or function-level resource isolation, you do not need to configure cgroup if you do not want to control CPU resource isolation (you only want to isolate IOPS resources). However, you must configure cgroup when you configure SQL-level resource isolation, regardless of whether you want to control CPU resource isolation.

* Before you configure IOPS resource isolation, you can perform disk performance calibration. For more information, see [Calibrate disk performance](../200.resource-isolation-of-oracle-mode/150.disk-performance-calibration-of-oracle-mode.md).

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>In the current version, IOPS resource isolation no longer strongly depends on disk performance calibration. </p>
   </main>

* Make sure that the user to be isolated has been created. For more information, see [Create a user](../../../../500.security-and-permissions/300.access-control/200.user-and-permission/300.permission-of-oracle-mode/100.create-a-user-of-oracle-mode.md).

* If you want to configure SQL-level resource isolation, make sure that the database, table, and column to be isolated have been created.

### Background information

Resource isolation is divided into user-level, SQL-level, and function-level resource isolation. For more information, see [Overview of resource isolation](../100.resource-isolation-overview.md).

### Step 1 (Optional): Configure the MAX_IOPS and MIN_IOPS parameters of a tenant to valid values

<main id="notice" type='explain'>
<h4>Note</h4>
<p>If you have set the <code>MAX_IOPS</code> and <code>MIN_IOPS</code> parameters to the IOPS values corresponding to 16 KB reads when you created the tenant, or if you do not want to control IOPS resource isolation, skip this step. </p>
</main>

After you calibrate the disk performance, before you configure the resource isolation plan, make sure that the `MAX_IOPS` and `MIN_IOPS` parameters of the tenant are set to valid values. In this context, valid values refer to the IOPS values corresponding to 16 KB reads, which serve as the reference values for the tenant's IOPS configuration.

3. Execute the following command to view the OBServer nodes on which the tenant is deployed.

   obclient [oceanbase]> SELECT DISTINCT SVR_IP, SVR_PORT FROM oceanbase.CDB_OB_LS_LOCATIONS WHERE tenant_id = xxxx;

   ```sql
   obclient [oceanbase]> SELECT * FROM oceanbase.GV$OB_IO_BENCHMARK WHERE MODE='READ' AND SIZE=16384;
   ```

   The query result is as follows:

   Based on the query result, use the disk calibration values of each node as the upper limit to plan the IOPS available to the tenant. If multiple tenants are deployed on the same OBServer node in the cluster, you can allocate the IOPS based on the actual business needs.

   For example, if two tenants are deployed on the same OBServer node in a cluster, and the disk IOPS values corresponding to 16 KB reads are the same (20,000 IOPS) for both nodes, and the expected workloads of the two tenants are similar, you can divide the 20,000 IOPS evenly between the two tenants (the actual IOPS allocation can be adjusted based on the business needs). In this case, you can set the `MAX_IOPS` and `MIN_IOPS` parameters of each tenant to 10,000. Alternatively, you can set `MIN_IOPS` to a value less than `MAX_IOPS` based on your business requirements.

5. Execute the following commands to modify the `MAX_IOPS` and `MIN_IOPS` parameters of the tenant.

   We recommend that you modify the `MIN_IOPS` parameter first, and then the `MAX_IOPS` parameter.

   ```sql
   ALTER RESOURCE UNIT unit_name MIN_IOPS = xxx;
   ```

   ```sql
   ALTER RESOURCE UNIT unit_name MAX_IOPS = xxx;
   ```

### Step 2: Configure a resource isolation plan

Assume that two users, `tp_user` and `ap_user`, exist in the current tenant.

You can follow the following steps to configure a resource isolation plan so that resources, such as CPU and IOPS, are used differently by different users and background tasks.

1. Log in to the Oracle tenant of the cluster as the tenant administrator.

2. Call the `CREATE_CONSUMER_GROUP` procedure of the `DBMS_RESOURCE_MANAGER` package to create two resource groups required for resource isolation.

   The statement is as follows:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   consumer_group => 'group_name' ,
   COMMENT => 'coments'
   );
   END; 
   ```

   The parameters are described as follows:

   * `CONSUMER_GROUP`: specifies the name of the resource group.

   * `COMMENT`: specifies the remarks of the resource group.

   For example, create two resource groups named `big_group` and `small_group`.

   ```shell
   obclient [SYS]> delimiter //
   ```

   ```shell
   obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   consumer_group => 'big_group' ,
   COMMENT => 'TP'
   );
   END; //
   ```

   ```shell
   obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_CONSUMER_GROUP(
   consumer_group => 'small_group' ,
   COMMENT => 'AP'
   );
   END; //
   ```

   After you create the resource groups, you can query the `DBA_RSRC_CONSUMER_GROUPS` view to confirm the creation. For more information about the `DBA_RSRC_CONSUMER_GROUPS` view, see [DBA_RSRC_CONSUMER_GROUPS](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18400.dba_rsrc_consumer_groups-of-oracle-mode.md).

3. Call the `CREATE_PLAN` procedure of the `DBMS_RESOURCE_MANAGER` package to create a resource management plan.

   The statement is as follows:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN(
   PLAN => 'plan_name',
   COMMENT =>'coments'
   );
   END;
   ```

   The parameters are described as follows:

   * `PLAN`: specifies the name of the resource management plan.

   * `COMMENT`: specifies the remarks of the resource management plan.

   For example, create a resource management plan named `plan_a`.

   ```shell
   obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN(
   PLAN => 'plan_a');
   END; //
   ```

   After you create the resource management plan, you can query the `DBA_RSRC_PLANS` view to confirm the creation. For more information about the `DBA_RSRC_PLANS` view, see [DBA_RSRC_PLANS](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18700.dba_rsrc_plans-of-oracle-mode.md).

4. Call the `CREATE_PLAN_DIRECTIVE` procedure of the `DBMS_RESOURCE_MANAGER` package to create the content of the resource management plan, so that CPU resources and IOPS resources of the resource groups are limited when the resource management plan is enabled.

   The statement is as follows:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
   PLAN => 'plan_name',
   GROUP_OR_SUBPLAN => 'group_name',
   COMMENT  => 'comments',
   MGMT_P1 => int_value,
   UTILIZATION_LIMIT => int_value,
   MIN_IOPS => int_value,
   MAX_IOPS => int_value,
   WEIGHT_IOPS => int_value,
   MAX_NET_BANDWIDTH => int_value,
   NET_BANDWIDTH_WEIGHT => int_value);
   END;
   ```

   The parameters are described as follows:

   * `PLAN`: specifies the name of the resource management plan to which the content belongs.

   * `GROUP_OR_SUBPLAN`: specifies the resource group.

   * `COMMENT`: specifies the remarks of the resource management plan content. The default value is `NULL`.

   * `MGMT_P1`: specifies the relative available maximum CPU percentage when the system is under full load. The default value is `100`.

   * `UTILIZATION_LIMIT`: specifies the CPU resource usage upper limit of the resource group. The default value is `100`. The value is in the range of (0, 100\]. `100` indicates that the resource group can use up to 100% of the CPU resources of the tenant. If the value is `40`, the resource group can use up to 40% of the CPU resources of the tenant.

   * `MIN_IOPS`: specifies the reserved IOPS resources of the resource group when there is an I/O contention, and the total reserved IOPS resources cannot exceed 100. The default value is `0`.

   * `MAX_IOPS`: specifies the maximum IOPS resources of the resource group. The total IOPS resources can exceed 100. The default value is `100`.

   * `WEIGHT_IOPS`: specifies the IOPS weight of the resource group. The total IOPS weights can exceed 100. The default value is `0`.

   * `WEIGHT_IOPS`: specifies the IOPS weight of the resource group. The total IOPS weights can exceed 100. The default value is `0`.

   * `MAX_NET_BANDWIDTH`: specifies the maximum network bandwidth resources that can be used. The total network bandwidth resources can exceed 100. The default value is `100`.

   * `NET_BANDWIDTH_WEIGHT`: specifies the network bandwidth weight. The total network bandwidth weights can exceed 100. The weights are proportionally split. The default value is `0`.

   Here are some examples:

   * Create a resource plan named `plan_a` and bind the `big_group` resource group to it. The utilization limit of CPU resources is 60% of the total CPU resources of the tenant. If an I/O contention occurs, the minimum reserved IOPS resources is 20% of the total IOPS resources. The maximum IOPS resource is 100% of the total IOPS resources. The IOPS weight is 20. The maximum network bandwidth resources is 50% of the total network bandwidth resources. The network bandwidth weight is 50.

      ```shell
      obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
      PLAN => 'plan_a',
      GROUP_OR_SUBPLAN => 'big_group',
      COMMENT  => 'TP  priority',
      UTILIZATION_LIMIT =>60,
      MIN_IOPS => 20,
      MAX_IOPS => 100,
      WEIGHT_IOPS => 20,
      MAX_NET_BANDWIDTH => 50,
      NET_BANDWIDTH_WEIGHT =>50);
      END; //
      ```

   * Create a resource plan named `plan_a` and bind the `small_group` resource group to it. The utilization limit of CPU resources is 40% of the total CPU resources of the tenant. If an I/O contention occurs, the minimum reserved IOPS resources is 10% of the total IOPS resources. The maximum IOPS resource is 90% of the total IOPS resources. The IOPS weight is 30. The maximum network bandwidth resources is 60% of the total network bandwidth resources. The network bandwidth weight is 60.

      ```shell
      obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.CREATE_PLAN_DIRECTIVE(
      PLAN => 'plan_a',
      GROUP_OR_SUBPLAN => 'small_group' ,
      COMMENT  => 'AP  priority',
      UTILIZATION_LIMIT =>40,
      MIN_IOPS => 10,
      MAX_IOPS => 90,
      WEIGHT_IOPS => 30,
      MAX_NET_BANDWIDTH => 60,
      NET_BANDWIDTH_WEIGHT =>60);
      END; //
      ```

   After the resource management plan is created, you can query the `DBA_RSRC_PLAN_DIRECTIVES` view and the `DBA_OB_RSRC_IO_DIRECTIVES` view to confirm the creation.

   For more information about the `DBA_RSRC_PLAN_DIRECTIVES` view, see [DBA_RSRC_PLAN_DIRECTIVES](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18600.dba_rsrc_plan_directives-of-oracle-mode.md).

   For more information about the `DBA_OB_RSRC_IO_DIRECTIVES` view, see [DBA_OB_RSRC_IO_DIRECTIVES](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/15000.dba_ob_rsrc_io_directives-oracle.md).

5. Call the `SET_CONSUMER_GROUP_MAPPING` subprogram in the `DBMS_RESOURCE_MANAGER` package to create resource isolation matching rules based on your actual use case.

   The statement is as follows:

   ```sql
   BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
      ATTRIBUTE => 'column | user | function',
      VALUE => 'values',
      CONSUMER_GROUP => 'group_name');
      END;
   ```

   The parameters are described as follows:

   * `ATTRIBUTE`: specifies the attribute type. The attribute name is not case-sensitive.

     * `column`: specifies SQL-level resource isolation.

     * `user`: specifies user-level resource isolation.

     * `function`: specifies function-level resource isolation.

   * `VALUE`: specifies the attribute value.

     * If the attribute type is `column`, you must specify the database name, table name, column name, constant value, and username.

       The following points apply:

       * The database name and username are optional. The default database name is the current database name, which is the same as the username. If you do not specify the username, the rule applies to all users, including those created in the current tenant.

       * The table name, column name, and constant value are required. You can specify only one value for each. When you specify a constant value, you can specify only a number or a string.

       * When you specify the table name, column name, or username, the specified table, column, and user must exist.

       In Oracle mode of OceanBase Database, after the statement is executed, the database name, table name, column name, and username are automatically converted to uppercase. If you want to keep them in lowercase, you can enclose them in double quotation marks. Example:

       ```shell
       obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
       ATTRIBUTE        =>  'column',
       VALUE            => '"test"."t1"."c3" = 3 for "user_big"',
       CONSUMER_GROUP   => 'big_group');
       END; //
       ```

     * If the attribute type is `user`, you must specify the username. You can specify only one user.

     * If the attribute type is `function`, you must specify one of the following background tasks corresponding to the DAG thread: compaction_high, ha_high, compaction_mid, ha_mid, compaction_low, ha_low, ddl, ddl_high, clog_high, and opt_stats. You can specify only one task. For more information about these tasks, see [Overview](../100.resource-isolation-overview.md).

   * `CONSUMER_GROUP`: specifies the resource group to which the statement is bound. This parameter indicates the resource group to which the statement is bound when the SQL statement matches the rule specified by `VALUE`. You can specify only one resource group.

        If you do not specify the resource group to which the statement is bound, the system automatically binds the statement to the built-in `OTHER_GROUPS` resource group. The resources of the built-in `OTHER_GROUPS` resource group are as follows:

        * MIN_IOPS = 100 - SUM of the total IOPS of other resource groups in the tenant

        * MAX_IOPS = 100

        * WEIGHT_IOPS = 100

   Example:

   * Create a SQL-level resource isolation matching rule.

      * Specify that when a SQL statement with the `WHERE` clause containing `sys.t.c3 = 3` is executed by the `tp_user` user, the statement is bound to the `big_group` resource group and uses the CPU and IOPS resources limited by the resource group.

        <main id="notice" type='notice'>
        <h4>Notice</h4>
        <p>When you execute a SQL statement, you do not need to specify <code>sys.t.</code> in the statement. You only need to ensure that <code>c3</code> is resolved to <code>sys.t.c3</code>. In this case, the statement is bound to the <code>big_group</code> resource group. Example: <code>SELECT * FROM sys.t WHERE c3 = 1;</code>. </p>
        </main>

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'column',
        VALUE => 'sys.t.c3=3 for tp_user',
        CONSUMER_GROUP => 'big_group');
        END; //
        ```

      * Specify that when a SQL statement with the `WHERE` clause containing `t.c3=5` is executed, the statement is bound to the `small_group` resource group and uses the CPU and IOPS resources limited by the resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'column',
        VALUE => 't.c3=5',
        CONSUMER_GROUP => 'small_group');
        END; //
        ```

      In addition to calling the `SET_CONSUMER_GROUP_MAPPING` subprogram to bind a resource group, OceanBase Database also supports binding a resource group by using a hint. You can use a hint to flexibly submit an SQL statement to a specified resource group. For example, the SQL statement to be submitted is `SELECT * FROM T`. If you want the statement to use the resources limited by the `big_group` resource group, you can use a hint to bind the statement to the `big_group` resource group. Example:

      ```shell
      obclient [SYS]> SELECT /*+resource_group('big_group')*/ * FROM T;
      ```

      <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>If you specify a resource group by using a hint, the statement is executed in the default resource group <code>OTHER_GROUPS</code> if the specified resource group does not exist. </p>
      </main>

   * Create a user-level resource isolation matching rule.

      * Specify that SQL statements executed by the `tp_user` user are bound to the `big_group` resource group and use the CPU and IOPS resources limited by the resource group.

        ```sql
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'user',
        VALUE => 'tp_user',
        CONSUMER_GROUP => 'big_group');
        END; //
        ```

      * Specify that SQL statements executed by the `ap_user` user are bound to the `small_group` resource group and use the CPU and IOPS resources limited by the resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'user',
        VALUE => 'ap_user',
        CONSUMER_GROUP => 'small_group');
        END; //
        ```

   * Create a function-level resource isolation matching rule.

      * Specify that when the `ha_high` task is executed, the system binds the task to the `big_group` resource group and uses the CPU and IOPS resources limited by the resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'function',
        VALUE => 'ha_high',
        CONSUMER_GROUP => 'big_group');
        END; //
        ```

      * Specify that when the `ddl_high` task is executed, the system binds the task to the `small_group` resource group and uses the CPU and IOPS resources limited by the resource group.

        ```shell
        obclient [SYS]> BEGIN DBMS_RESOURCE_MANAGER.SET_CONSUMER_GROUP_MAPPING(
        ATTRIBUTE => 'function',
        VALUE => 'ddl_high',
        CONSUMER_GROUP => 'small_group');
        END; //
        ```

   After the resource group is created, you can query the `DBA_RSRC_GROUP_MAPPINGS` view to confirm the creation. For more information about the `DBA_RSRC_GROUP_MAPPINGS` view, see [DBA_RSRC_GROUP_MAPPINGS](../../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/18500.dba_rsrc_group_mappings-of-oracle-mode.md).

6. Enable an appropriate resource management plan for the resource group.

   The resources limited to the same resource group may vary in different resource management plans. You need to enable an appropriate resource management plan for the resource group.

   ```shell
   obclient [SYS]>delimiter ;
   ```

   ```shell
   obclient [SYS]> ALTER SYSTEM SET resource_manager_plan = 'plan_a';
   ```

   <main id="notice" type='explain'>
   <h4>Note</h4>
   <p>If no resources need to be limited, you can disable all resource plans by executing the <code>ALTER SYSTEM SET resource_manager_plan = '';</code> statement. </p>
   </main>

### Considerations after configuration

* After adding resource isolation matching rules, if a user is deleted and then recreated, the resource isolation matching rules still apply.

* Resource isolation matching rules do not take effect immediately after they are added. It is estimated that they may take effect within 10 seconds, depending on the actual environment.

* SQL-level resource isolation has a higher priority than user-level and function-level resource isolation.

* After adding resource isolation matching rules, they currently only take effect in statements such as `SELECT`, `INSERT`, `UPDATE`, and `DELETE`. They do not take effect in DDL or DCL statements, nor in PL. However, they can take effect in prepareStatement.

### Performance impact after configuration

* User-level and function-level resource isolation can determine which resource group to use before the SQL is parsed, so they do not affect performance.

* The performance impact of SQL-level resource isolation mainly comes from retries. Unlike user-level and function-level resource isolation, which determine the resource group to use before the SQL is parsed, SQL-level resource isolation can only determine the resource group to use during SQL parsing or when a plan cache hit occurs. If the resource group determined at this point is different from the one currently being used, the system will retry once to use the resource group specified by the matching rule to process the SQL.

  The performance impact of SQL-level resource isolation can be divided into the following three scenarios:

  1. If an SQL statement does not match any rule, it has almost no impact on performance.

  2. If an SQL statement matches a rule, assuming the resource group specified by the rule is `big_group`, not only will this SQL statement be executed using the resources of `big_group`, but the next SQL statement will also be executed using the resources of `big_group` until it matches a rule that specifies a different resource group, at which point the system will retry. In scenarios where a batch of SQL statements is executed consecutively and all are bound to the same resource group, using this strategy ensures that only the first SQL statement in the batch requires a retry, while subsequent SQL statements do not. This minimizes retries and has a minimal impact on performance.

  3. If each SQL statement is expected to use a different resource group from the previous one, each SQL statement will require a retry, which has a significant impact on performance.

## (Optional) Configure resource isolation for DDL worker threads

In the current version, DDL requests and DML requests compete for foreground worker threads. If a large number of DDL requests occur within a short period, it will severely impact normal user requests. To minimize performance stability issues caused by thread resource contention, OceanBase Database has separated DDL worker thread resources from DML worker thread resources. You can choose to enable DDL worker thread resource isolation based on your business needs.

OceanBase Database uses the tenant-level hidden parameter `_enable_ddl_worker_isolation` to control DDL thread resource isolation. The value and meaning of this parameter are as follows:

* `False`: DDL worker thread resource isolation is disabled. In this scenario, DDL requests and DML requests share worker threads, which may affect each other.

* `True`: DDL worker thread resource isolation is enabled. In this scenario, DDL requests use dedicated worker threads, and the number of DDL requests executed by the tenant at the same time is limited to minimize impact on DML requests.

To enable DDL worker thread resource isolation, follow these steps:

1. Log in to the Oracle tenant of the cluster as the `SYS` user.

   Here is an example of the connection command:

    ```shell
    obclient -h172.30.xxx.xxx -P2883 -usys@oracletenant#obdemo -pxxxx -A
    ```

2. Query the current value of the parameter `_enable_ddl_worker_isolation`.

   ```shell
   obclient(SYS@oracle001)[SYS]> SELECT * FROM SYS.GV$OB_PARAMETERS WHERE NAME LIKE '%_enable_ddl_worker_isolation%';
   ```

   Here is an example of the query result:

   ```shell
   +----------------+----------+-------+--------+-----------+------------------------------+-----------+-------+------------------------------------------+--------------+-------------------+---------------+-----------+
   | SVR_IP         | SVR_PORT | ZONE  | SCOPE  | TENANT_ID | NAME                         | DATA_TYPE | VALUE | INFO                                     | SECTION      | EDIT_LEVEL        | DEFAULT_VALUE | ISDEFAULT |
   +----------------+----------+-------+--------+-----------+------------------------------+-----------+-------+------------------------------------------+--------------+-------------------+---------------+-----------+
   | 172.xx.xxx.xxx |     2882 | zone1 | TENANT |      1004 | _enable_ddl_worker_isolation | NULL      | False | a switch controling ddl thread isolation | ROOT_SERVICE | DYNAMIC_EFFECTIVE | False         | YES       |
   +----------------+----------+-------+--------+-----------+------------------------------+-----------+-------+------------------------------------------+--------------+-------------------+---------------+-----------+
   1 row in set
   ```

3. Modify the value of the parameter `_enable_ddl_worker_isolation`.

   ```shell
   obclient(SYS@oracle001)[SYS]> ALTER SYSTEM SET "_enable_ddl_worker_isolation" = True;
   ```
