# Smooth scaling in and out with heterogeneous zones

For businesses highly sensitive to latency, when scaling in or out, it's crucial to limit load balancing operations on nodes hosting log stream leaders. These operations include transfer tasks, log stream replica migration, and leader switching. By using heterogeneous zones, you can avoid leader switching and replica migration during peak hours, ensuring a smoother scaling process.

## Considerations

In general, only the zones where the `UNIT_NUM` changes will have replication migration during scaling or rollback operations. Other zones will not have log stream migration, only local transfer. However, if the tenant is not in a balanced state before scaling operations, such as during partition balancing or if a new scaling task is initiated before the previous one is completed, the system cannot guarantee that other zones will not have log stream migration.

## Scenario 1: Expand or shrink the cluster by adding or removing zones

If the `PRIMARY_ZONE` of a tenant is spread across multiple zones and cannot be concentrated in a single zone, you need to use the locality change method to expand or shrink the cluster. This involves first adding or removing zones and then using the locality change method to add replicas to the new zones. This process ensures a balanced distribution of replicas.

Let's take an expansion as an example.

### Scenario

Assume that the current tenant is tenant1, with a locality of `F@zone1, F@zone2, A`, and the `PRIMARY_ZONE` is `zone1, zone2`. The tenant has a resource pool named `pool` that is distributed across `zone1` and `zone2`, with a `UNIT_NUM` of 2 (configured as 2:2). The distribution of user log streams is shown in the following figure:

![Before Expansion](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-1-1-new.png)

Now, the `UNIT_NUM` of the tenant's resource pool needs to be expanded to 4:4.

### Procedure

1. Log in to the `sys` tenant of the cluster as the `root` user.

2. Disable the `enable_ls_leader_balance` parameter.

   The tenant-level parameter [enable_ls_leader_balance](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2760.enable_ls_leader_balance.md) is the switch for log stream leader balancing. When the global load balancing switch enable_rebalance is enabled, this parameter can independently control the automatic balancing of log stream leaders. The default value is `True`, which means that automatic balancing of log stream leaders is enabled by default.

   ```shell
   obclient(root@sys)[(none)]> ALTER SYSTEM SET enable_ls_leader_balance = False TENANT = 'tenant1';
   ```

3. Add two zones with four nodes each and add resources to the tenant in the new zones.

   1. Add zones zone3 and zone4 to the cluster. For more information, see [Add a zone](../../../100.cluster-management/300.common-cluster-operations/800.add-a-zone.md).

   2. Add four nodes to each of the newly added zones zone3 and zone4. For more information, see [Add a node](../../../100.cluster-management/300.common-cluster-operations/400.add-a-node.md).

   3. Create a resource pool named `pool2` with the same unit specification as the original one and a `UNIT_NUM` of 4 in the newly added zones zone3 and zone4.

      ```shell
      obclient(root@sys)[(none)]> CREATE RESOURCE POOL pool2 UNIT='unit_name', UNIT_NUM = 4, ZONE_LIST=('zone3','zone4');
      ```

      Replace `unit_name` with the actual unit name.

   4. Modify the tenant's resource pool to include the newly added resource pool `pool2`.

      ```shell
      obclient(root@sys)[(none)]> ALTER TENANT tenant1 RESOURCE_POOL_LIST =('pool','pool2');
      ```

      After the operation is successful, the tenant will have 2 units in `zone1`, 2 units in `zone2`, 4 units in `zone3`, and 4 units in `zone4`.

4. Modify the tenant's locality to include the newly added zones `zone3` and `zone4`.

   Change the locality from `F@zone1, F@zone2, A` to `F@zone1, F@zone2, F@zone3, F@zone4, A`. The statement is as follows:

   ```shell
   obclient(root@sys)[(none)]> ALTER TENANT tenant1 LOCALITY="F@zone1，F@zone2，F@zone3，F@zone4，A";
   ```

   After the statement is executed successfully, the system will automatically complete the log stream replicas on the new units and evenly distribute them across each unit. Since only Follower replicas are added, there will be no leader switching.

   At this point, the distribution of user log streams is as shown in the following figure.

   ![Distribution after adding zones](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-1-2-new.png)

5. Set the `PRIMARY_ZONE` of the tenant to the newly added zones `zone3` and `zone4`, and enable the `enable_ls_leader_balance` parameter.

   Change the `PRIMARY_ZONE` from `zone1,zone2` to `zone3,zone4`. The statement is as follows:

1. Set the primary zone of the tenant to `zone3` and `zone4`.

   ```shell
   obclient(root@sys)[(none)]> ALTER TENANT tenant1 PRIMARY_ZONE='zone3,zone4';
   ```

   Enable the `enable_ls_leader_balance` parameter.

   ```shell
   obclient> ALTER SYSTEM SET enable_ls_leader_balance = True TENANT = 'tenant1';
   ```

   After the preceding statements are executed, the leader replicas of the log streams are automatically switched to `zone3` and `zone4`. The process is fast and the impact is controllable when only the `PRIMARY_ZONE` of the log streams is changed.

2. Modify the locality of the tenant again and remove `zone1` and `zone2` from the locality.

   Change the locality from `F@zone1, F@zone2, F@zone3, F@zone4, A` to `F@zone3, F@zone4, A`. The statement is as follows:

   ```shell
   obclient(root@sys)[(none)]> ALTER TENANT tenant1 locality="F@zone3，F@zone4，A";
   ```

   After the preceding statement is executed, the replicas of the log streams in `zone1` and `zone2` are deleted, and the replicas in `zone3` and `zone4` are not affected.

3. Modify the resource pool of the tenant and remove the original resource pool `pool`, retaining only the newly added resource pool `pool2`.

   ```shell
   obclient(root@sys)[(none)]> ALTER TENANT tenant1 RESOURCE_POOL_LIST =('pool2');
   ```

   After the original resource pool `pool` is removed from the tenant, the original two-node `zone1` and `zone2` can also be deleted.

   After the operation is completed, only `zone3` and `zone4` with 4 nodes (`UNIT_NUM` is 4) remain under the current tenant, and the expansion is complete.

### Scenario 2: In-place scaling

For tenants with a high concentration of `PRIMARY_ZONE`, in-place scaling can be performed. This ensures that only the Follower replicas are moved to the new zone.

Let's take scaling out as an example.

### Scenario Information

Assume that there is a tenant named `tenant1` with a Locality of `F@zone1, F@zone2, A`, and the `PRIMARY_ZONE` is `zone1`. The tenant has a resource pool named `pool` distributed across `zone1` and `zone2`, with a `UNIT_NUM` of 2 (i.e., `UNIT_NUM` is configured as 2:2). The distribution of user log streams is shown in the following figure.

![Before in-place scaling](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-image2-1-new.png)

Now, the `UNIT_NUM` of the tenant's resource pool needs to be scaled out to 4:4.

### Procedure

1. Log in to the cluster as the `root` user in the `sys` tenant.

2. Split the tenant's resource pool into `pool1` in `zone1` and `pool2` in `zone2`.

   ```shell
   obclient(root@sys)[(none)]> ALTER RESOURCE POOL pool SPLIT INTO ('pool1','pool2') ON ('zone1','zone2');
   ```

   For more information about splitting resource pools, see [Merge and split resource pools](../1500.resource-pool-management/500.merge-and-splitting-resource-pools.md).

3. Change the `UNIT_NUM` of the split resource pool `pool2` to 4.

   ```shell
   obclient(root@sys)[(none)]> ALTER RESOURCE POOL pool2 UNIT_NUM = 4;
   ```

   After the statement is executed successfully, the log streams will automatically split and be distributed across 4 units in `zone1`. At this point, the distribution of user log streams is as follows.

   ![After scaling out the UNIT_NUM in zone2](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-image2-2-new.png)

4. Change the `PRIMARY_ZONE` of the tenant to `zone2`.

   ```shell
   obclient(root@sys)[(none)]> ALTER TENANT tenant1 PRIMARY_ZONE='zone2';
   ```

5. Change the `UNIT_NUM` of the split resource pool `pool1` to 4.

   ```shell
   obclient(root@sys)[(none)]> ALTER RESOURCE POOL pool1 UNIT_NUM = 4;
   ```

   After the statement is executed successfully, the system will start balancing. Once the balancing is complete, the scaling out is done. The final distribution of user log streams is as follows.

   ![After scaling out the UNIT_NUM in zone1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-image2-3-new.png)

6. (Optional) If you want the Leader replicas to remain concentrated in `zone1`, you can change the `PRIMARY_ZONE` of the tenant back to `zone1`.

   ```shell
   obclient(root@sys)[(none)]> ALTER TENANT tenant1 PRIMARY_ZONE='zone1';
   ```
