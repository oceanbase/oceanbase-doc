# Tenant pre-expansion

OceanBase Database implements the pre-expansion feature to achieve smooth scaling of tenants. This feature is achieved by configuring the expansion factor (`ls_scale_out_factor`) for the tenant, which determines the number of log streams to be created before the tenant is scaled out. By generating a sufficient number of log streams in advance, the log stream status and location can be matched with the post-expansion state. This allows for a smooth scaling operation.

## Introduction to scale-out factor

In earlier versions, a tenant could have only one log stream on each node. If a node had many log streams, it could directly trigger log stream position redistribution during scaling out without needing to use Transfer to split log streams.

To define that a tenant had enough log streams before scaling out, OceanBase Database introduced the concept of scale-out factor (`ls_scale_out_factor`). The scale-out factor indicates how many log streams one log stream needs to be split into to meet future scaling-out requirements.

### Formula for calculating the scale-out factor

In OceanBase Database, the number of normal log streams for a tenant (excluding system and broadcast log streams) is calculated as: `number of tenant UNIT_NUMs (U) × number of tenant PRIAMRY_ZONEs with the highest priority (P)`.

Assume that before scaling out, the number of tenant UNIT_NUMs is U1, and the number of tenant PRIAMRY_ZONEs with the highest priority is P1. After scaling out, the number of tenant UNIT_NUMs is U2, and the number of tenant PRIAMRY_ZONEs with the highest priority is P2. The formula for calculating the scale-out factor (`ls_scale_out_factor`) is as follows:

`ls_scale_out_factor = LCM(U1 × P1, U2 × P2) / (U1 × P1)`

In other words, the least common multiple (LCM) of `(U1 × P1)` and `(U2 × P2)` divided by `(U1 × P1)` gives the scale-out factor for the tenant.

## Pre-expansion

Assume that the current tenant is `mq_t1`, with Locality set to `F@zone1, F@zone2, F@zone3`. Each zone has one unit, and the `PRIMARY_ZONE` is distributed across `zone1` and `zone2`. The goal is to increase the tenant's `UNIT_NUM` to 2 while keeping the number of `PRIMARY_ZONE` priorities unchanged. The steps for pre-expansion are as follows:

1. Log in to the sys tenant of the cluster as the `root` user.

   A sample connection is as follows:

   ```shell
   obclient -h172.30.xxx.xxx -P2883 -uroot@sys#obdemo -pxxxx -A
   ```

2. View the `TENANT_ID`, `UNIT_NUM`, and `PRIAMRY_ZONE` information for the tenant `mq_t1`.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, PRIMARY_ZONE, LOCALITY, UNIT_NUM FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME = 'mq_t1';
   ```

   The query result is as follows:

   ```shell
   +-----------+-------------+-------------+-------------------+---------------------------------------------+----------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE      | LOCALITY                                    | UNIT_NUM |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+----------+
   |      1002 | mq_t1       | USER        | zone1,zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |        1 |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+----------+
   1 row in set
   ```

3. Calculate the value of ls_scale_out_factor and configure the tenant's scaling factor.

   In this example, the `UNIT_NUM` value before expansion is 1, and the number of priorities for `PRIAMRY_ZONE` is 2. After expansion, the `UNIT_NUM` value is 2, and the number of priorities for `PRIMARY_ZONE` remains 2. Using the scaling factor formula, the scaling factor is calculated as `LCM(2 * 1, 2 * 2)/(2 * 1) = 2`.

   Set the value of [ls_scale_out_factor](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/5160.ls_scale_out_factor.md) based on the calculated scaling factor.

   ```shell
   obclient(root@sys)[oceanbase]> ALTER SYSTEM SET ls_scale_out_factor = 2 TENANT = mq_t1;
   ```

4. Set the values of both [enable_rebalance](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2800.enable_rebalance.md) and [enable_transfer](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3000.enable_transfer.md) to `True` to allow the tenant to generate a sufficient number of log streams.

   ```shell
   obclient(root@sys)[oceanbase]> ALTER SYSTEM SET enable_rebalance = True TENANT = mq_t1;
   ```

   ```shell
   obclient(root@sys)[oceanbase]> ALTER SYSTEM SET enable_transfer = True TENANT = mq_t1;
   ```

5. After the tenant generates a sufficient number of log streams, check if the number of `NORMAL` status log streams meets the expectation.

   According to the scaling factor formula, the number of `NORMAL` status log streams (excluding system and broadcast log streams) after expansion should be: `UNIT_NUM` value before expansion (U1) × number of priorities for `PRIAMRY_ZONE` before expansion (P1) × scaling factor (ls_scale_out_factor). In this case, it should be `1 × 2 × 2 = 4`.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID, STATUS, COUNT(*) FROM oceanbase.CDB_OB_LS WHERE TENANT_ID = 1002 AND FLAG = '' AND LS_ID != 1 GROUP BY STATUS;
   ```

   A sample query result is as follows:

   ```shell
   +-----------+--------+----------+
   | TENANT_ID | STATUS | COUNT(*) |
   +-----------+--------+----------+
   |      1002 | NORMAL |        4 |
   +-----------+--------+----------+
   1 row in set
   ```

6. Confirm that there are no load balancing tasks for the tenant to be expanded.

   ```shell
   obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.CDB_OB_BALANCE_JOBS WHERE TENANT_ID = 1002;
   ```

   If the query result is empty, the pre-expansion operation is complete.
