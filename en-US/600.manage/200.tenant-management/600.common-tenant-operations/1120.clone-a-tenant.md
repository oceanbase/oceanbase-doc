# Clone a tenant

You can clone a new tenant based on a specified source tenant. The number of units and the distribution of units across OBServer nodes in the cloned tenant are the same as those in the source tenant.

## Limitations

* You cannot clone a tenant during a switchover.

  For more information about switchover, see [Switchover](../../400.high-availability/300.physical-standby-database-disaster-recovery/600.role-switch/200.perform-switchover.md).

* You cannot clone a tenant during the addition, deletion, or attribute change of a leader server.

  You can run the `SELECT * FROM oceanbase.CDB_OB_BALANCE_JOBS WHERE tenant_id = XXX;` statement in the system tenant (`sys` tenant) to confirm this.

* You cannot clone a tenant during a transfer.

  You can run the `SELECT * FROM oceanbase.CDB_OB_BALANCE_JOBS WHERE tenant_id = XXX;` statement in the system tenant (`sys` tenant) to confirm whether a transfer task is in progress.

* You cannot clone a tenant during a unit migration.

  You can run the `SELECT * FROM oceanbase.DBA_OB_UNITS WHERE MIGRATE_FROM_SVR_PORT IS NOT NULL;` statement in the system tenant (`sys` tenant) to confirm whether a unit migration task is in progress.

* You cannot clone a tenant when you reduce the `UNIT_NUM` value in the resource pool to scale down the tenant.

* You cannot clone a tenant when an OBServer node hosting a unit in the source tenant is unavailable.

* You cannot clone a tenant when a disaster recovery task is in progress for the log stream replica of the source tenant.

  To confirm whether a disaster recovery task is in progress for the log stream replica of the source tenant, perform the following operations:

  * In the system tenant, query the `CDB_OB_LS_REPLICA_TASKS` view by specifying the `tenant_id` of the current tenant. If the query result is not empty, a disaster recovery task is in progress for the log stream replica of the source tenant.

  * In a user tenant, query the `DBA_OB_LS_REPLICA_TASKS` view. If the query result is not empty, a disaster recovery task is in progress for the log stream replica of the source tenant.

* You cannot clone a tenant during an upgrade.

* You cannot clone a tenant of OceanBase Database of a version earlier than V4.3.0.

## Considerations

* The new tenant cloned from the source tenant is strictly isolated from the source tenant in terms of data and resources. Any data modification in the new tenant does not affect the source tenant, and vice versa. The new tenant does not compete with the source tenant for resources such as CPU and memory.

* In the initial state, the source tenant and the new tenant share physical macroblocks. As the source tenant and the new tenant write data separately, the shared macroblocks gradually decrease and the exclusive macroblocks gradually increase. The storage space occupied by the two tenants increases accordingly. You must pay attention to the storage space occupied by the OBServer nodes.

* During the execution of a tenant clone task, you cannot perform the following operations:

  * Perform a switchover on the source tenant.

  * Scale in or out the source tenant by modifying the `UNIT_NUM` value or the primary zone priority.

  * Add or remove replicas for the source tenant, or adjust the replica distribution.

  * Manually perform a transfer on the source tenant.

  * Manually migrate units of the source tenant.

  * Upgrade the source tenant.

  If you must perform the above operations, you can cancel the tenant clone task and then perform the operations. For more information about how to cancel a tenant clone task, see [Cancel a tenant clone task](1130.cancel-the-tenant-clone-task.md).

## Prerequisites

The tenant clone feature depends on the log archiving feature of the tenant. Before you execute a tenant clone operation, make sure that log archiving is enabled for the source tenant, and log archiving cannot be disabled during the tenant clone operation. For more information about how to configure the archive destination for the source tenant and enable log archiving, see [Prepare for log archiving](../../600.backup-and-recovery/300.log-archive/200.preparation-before-log-archive.md) and [Enable log archiving](../../600.backup-and-recovery/300.log-archive/300.open-the-log-archive-mode.md).

## Background information

The tenant clone feature applies to various scenarios. Some scenarios are as follows:

* When you want to test a new version of an application, you can quickly clone an online tenant to create a test tenant and use the test tenant to test the new application version.

* When you want to perform high-risk operations such as DDL operations on the database, you can:

  * Quickly clone an online tenant to create a test tenant, run the DDL statement on the test tenant, and verify the execution result.

  * Clone an online tenant to create a small-scale tenant at the current time point before you execute the DDL statement. If the DDL statement fails, you can quickly roll back the data.

## Procedure

1. Log in to the `sys` tenant of the cluster as the `root` user.

    ```shell
    obclient -h172.30.xx.xx -P2883 -uroot@sys#cluster -p**** -A
    ```

2. Execute the following statement to clone a tenant.

    ```sql
    CREATE TENANT new_tenant_name FROM source_tenant_name
       WITH
       RESOURCE_POOL [=] resource_pool_name,
       UNIT [=] unit_config;
    ```

    The parameters are described as follows:

    * `new_tenant_name`: the name of the new tenant to be cloned. You can clone only one tenant at a time. If you want to clone multiple tenants, you must wait for the current cloning task to complete before you can start cloning another tenant.

    * `source_tenant_name`: the name of the source tenant.

    * `resource_pool_name`: the name of the resource pool for the new tenant. When you clone a tenant, the system automatically creates a resource pool for the new tenant based on the resource distribution of the source tenant.

    * `unit_config`: the unit specification for the new tenant. You can specify an existing unit specification in the system or create a new one. For more information about how to query existing unit specifications, see [View resource specifications](1600.resource-specification-management/100.view-resource-unit-configuration.md).

    Here is an example of cloning a new tenant named `clone_tnt` from the `mysql` tenant:

    ```sql
    obclient [oceanbase]> CREATE TENANT clone_tnt FROM mysql
	 WITH
       RESOURCE_POOL = clone_tnt_pool,
	 UNIT= S1_unit_config;
    ```

    In this example, the new tenant is assigned to the `clone_tnt_pool` resource pool with the `S1_unit_config` unit specification. The number of units and their distribution across OBServer nodes are the same as those of the source tenant.

3. During the cloning task, you can view the status of the task by querying the views.

## What to do next

* After the tenant cloning task is completed, the new tenant is a standby tenant. You can continue to use this new tenant as a standby tenant or switch it to a primary tenant. For more information about how to switch a standby tenant to a primary tenant, see [Switch a standby tenant to a primary tenant](../../600.backup-and-recovery/600.restore-data/600.active-standby-tenant.md).

* In scenarios where the arbitration service is deployed, the arbitration service is not enabled by default for the new tenant. If you want to enable the arbitration service, you can enable it for the new tenant after the cloning task is completed. For more information, see [Enable the arbitration service for a tenant](../../400.high-availability/400.arbitration-high-availability/200.enable-the-arbitration-service.md).
