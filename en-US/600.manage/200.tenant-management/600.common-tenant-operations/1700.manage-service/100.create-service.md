# Create a service

You can use the OCP console or the CLI to create a service in a user tenant. This topic explains how to create a service using the CLI. We recommend that you use the OCP console to create and manage services. For more information, see [Overview](https://www.oceanbase.com/docs/common-ocp-1000000001126930) and [Manage service names](https://www.oceanbase.com/docs/common-ocp-1000000001740041).

## Background information

In OceanBase Database V2.x or V3.x, the Physical Standby Database feature is provided in the form of primary/standby clusters. The name of each cluster is the same as that of its primary cluster, and different primary/standby clusters have different names. Therefore, the cluster name can uniquely identify a primary/standby cluster. When you use ODP to connect to a database, you can specify the cluster name to route the connection to the primary cluster automatically.

In V4.1.0 and later, the Physical Standby Database feature is provided in the form of primary/standby tenants. The primary and standby tenants can be in different clusters, and are unaware of each other. To enable automatic routing to the primary tenant, OceanBase Database introduces the service concept. Multiple tenants, either in the same cluster or different clusters, can be grouped into a service. When you use ODP to connect to a database, you can specify the service name to route the connection to the primary tenant automatically.

## Limitations

* You cannot create a service for the `sys` tenant or the meta tenant.

* A user tenant can create at most one service.

* You cannot execute the `CREATE SERVICE` statement in a session where the service name is used as the username.

* The OCP and ODP products are required. The following version requirements apply:

   * ODP: V4.3.1 and later

   * OCP: V4.3.1 and later

## Considerations

When you create a service for a tenant, make sure that the service contains at most one primary tenant. We recommend that you use OCP to manage primary/standby tenants and services. For more information, see [OCP documentation](https://www.oceanbase.com/docs/common-ocp-1000000001126929).

## Prerequisites

* The user has the `ALTER SYSTEM` privilege, which is required to execute the `CREATE SERVICE` command.

* When creating a service for a tenant, make sure that there are no offline units in the tenant. If there are offline units, after the `CREATE SERVICE` command is executed, the service cannot be used on some units for a while. We recommend that you wait for the offline units to recover or become permanently offline before you create a service. Alternatively, you can create a service and then start it after the offline units recover or become permanently offline.

  To check whether there are offline units in the tenant, perform the following steps:

  1. Log in to the `sys` tenant of the cluster where the target tenant resides as the `root` user.

  2. Query whether there are offline units in the tenant and obtain the `LAST_OFFLINE_TIME` of the offline units.

     ```shell
     obclient [oceanbase]> SELECT SVR_IP, SVR_PORT, LAST_OFFLINE_TIME, NOW() FROM oceanbase.DBA_OB_SERVERS WHERE LAST_OFFLINE_TIME IS NOT NULL AND (SVR_IP, SVR_PORT) IN (SELECT DISTINCT SVR_IP, SVR_PORT FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = user_tenant_id);
     ```

     Here, the `user_tenant_id` parameter needs to be replaced with the `TENANT_ID` of the target tenant.

     If the query result set is empty, there are no offline units. If the query result set is not empty, proceed to the next step to determine whether the units are temporarily or permanently offline.

  3. If there are offline units in the tenant, query the value of the `server_permanent_offline_time` parameter. Then, based on the `LAST_OFFLINE_TIME` obtained in the previous step and the value of the parameter, determine the permanent offline time of the units.
    The cluster-level parameter `server_permanent_offline_time` specifies the time threshold for considering a node offline, namely, the time after which a node is considered offline if its heartbeats are interrupted. After a node is considered offline, its data replicas need to be automatically supplemented. For more information about this parameter, see [server_permanent_offline_time](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/300.cluster-level-configuration-items/20300.server_permanent_offline_time.md).

    ```shell
    obclient [oceanbase]> SHOW PARAMETERS LIKE 'server_permanent_offline_time';
    ```

    Based on the query result, if `LAST_OFFLINE_TIME + server_permanent_offline_time` is less than or equal to `NOW()`, the unit is considered permanently offline. Otherwise, the unit is temporarily offline.

* The `SWITCHOVER_STATUS` of the tenant is `NORMAL` when you create a service for the tenant. In other words, the tenant is not in the switchover process.

   To check the `TENANT_ROLE` and `SWITCHOVER_STATUS` of a tenant, perform the following steps:

  * Query the `TENANT_ROLE` and `SWITCHOVER_STATUS` of a specified tenant from the sys tenant.

    ```shell
    obclient [oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_ROLE, SWITCHOVER_STATUS FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME = mysql_tenant;
    ```

  * Query the `TENANT_ROLE` and `SWITCHOVER_STATUS` of the current tenant from the current tenant.

    ```shell
    obclient [oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_ROLE, SWITCHOVER_STATUS FROM oceanbase.DBA_OB_TENANTS;
    ```

    ```shell
    obclient [SYS]> SELECT TENANT_ID, TENANT_NAME, TENANT_ROLE, SWITCHOVER_STATUS FROM SYS.DBA_OB_TENANTS;
    ```

## Procedure

When you create a service for a tenant, if the tenant has a primary/standby relationship with another tenant, you must create services with the same name for the primary and standby tenants, respectively.

1. Log in to the cluster as the tenant administrator of a user tenant or the sys tenant.

2. Query the `TENANT_ROLE` of the specified tenant.

   Since a service can have at most one primary tenant, you must query the role of the tenant before you create a service.

   Here is a sample statement:

   ```shell
   obclient [oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_ROLE FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME = mysql_tenant;
   ```

3. Query the tenants in the service you want to create.

   <main id="notice" type='notice'>
   <h4>Notice</h4>
   <p> The following statement can query the name and tenant ID of all primary and standby tenants in the current cluster only. In a cross-cluster standby scenario, you must also query the corresponding cluster. </p>
   </main>

   Here is a sample statement:

   ```shell
   obclient [oceanbase]> SELECT t.tenant_id, t.tenant_name, t.tenant_role
   FROM oceanbase.CDB_OB_SERVICES AS s JOIN oceanbase.DBA_OB_TENANTS AS t
   ON s.tenant_id = t.tenant_id 
   WHERE s.service_name = 's_hz';
   ```

   Based on the query result and the tenant roles, make sure that the service you want to create has at most one primary tenant.

4. Create a service for the tenant.

   The sample statement is as follows:

   ```sql
   ALTER SYSTEM CREATE SERVICE service_name [TENANT [=] tenant_name];
   ```

   In the statement above:

   * `service_name`: the name of the service to be created.
   * `TENANT [=] tenant_name`: the name of the tenant for the service. Only the sys tenant can specify a tenant. A user tenant cannot specify a tenant.

   Here are some examples:

   * Create a service named `s_hz` in the system tenant for the `mysql_tenant` tenant.

      ```shell
      obclient [oceanbase]> ALTER SYSTEM CREATE SERVICE s_hz TENANT = mysql_tenant;
      ```

   * Create a service named `s_hz` in the user tenant for the current tenant.

      ```shell
      obclient > ALTER SYSTEM CREATE SERVICE s_hz;
      ```

   After the command is executed, if the response is `Query OK`, you can connect to all machines except those that are permanently offline in the tenant through the specified service name; if the response is `OB_SERVICE_NOT_FULLY_STARTED`, you can connect to some but not all of the machines except those that are permanently offline in the tenant through the specified service name. To verify which machines support connection through the service name, you can query the [CDB_OB_TENANT_EVENT_HISTORY](../../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/11400.o-cdb_ob_tenant_event_history-of-sys-tenant.md) view in the system tenant or the [DBA_OB_TENANT_EVENT_HISTORY (MySQL mode)](../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12200.o-dba_ob_tenant_event_history-of-mysql-mode.md) or [DBA_OB_TENANT_EVENT_HISTORY (Oracle mode)](../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/16100.dba_ob_tenant_event_history-of-oracle-mode.md) view in the user tenant.

## Next steps

After the primary and standby tenants have the same-named services and the clusters to which the primary and standby tenants belong are both under the OCP and associated with the same OBProxy cluster, you can connect to the database by using the service name, to implement automatic routing to the primary and standby tenants. A sample connection string is as follows:

```shell
obclient -hip -Pport -uuser_name@SERVICE:service_name
```

where:

* `ip`: the IP address of the OBProxy cluster.
* `port`: the port number of the OBProxy cluster.
* `user_name`: the username of the tenant to log in.
* `service_name`: the service name of the tenant to log in.

A sample connection string is as follows:

```shell
obclient -h10.xx.xx.xx -P2883 -uuser1@SERVICE:s_hz
```

For more information about connection strings, see [Overview (MySQL mode)](../../../../300.develop/100.application-development-of-mysql-mode/100.connect-to-oceanbase-database-of-mysql-mode/100.connection-methods-overview-of-mysql-mode.md) and [Overview (Oracle mode)](../../../../300.develop/200.application-development-of-oracle-mode/100.connect-to-oceanbase-database-of-oracle-mode/100.connection-methods-overview-of-oracle-mode.md).
