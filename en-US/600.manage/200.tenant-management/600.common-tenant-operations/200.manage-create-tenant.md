# Create a tenant

OceanBase Database is a native distributed database. You can run multiple database instances in the same database. The first step is to create a tenant (database instance) and use the database instance as you would a traditional standalone database. This topic describes how to create a tenant.

## Procedure for creating a user tenant

OceanBase Database only supports the creation of user tenants. The system tenant is automatically created when the cluster is created. Creating a user tenant involves a series of operations: first, define a resource specification; then, based on that specification, create a resource pool; and finally, create the tenant and assign it to the resource pool. Therefore, the order for creating a tenant is: resource specification -> resource pool -> tenant.

1. [Create a resource specification](#step-1-create-a-resource-specification): Creating a resource specification involves defining the specifications without allocating actual resources. You can view all resource specifications through the `DBA_OB_UNIT_CONFIGS` view. Resource specifications can be reused. It is recommended to abstract different specifications based on business scenarios, such as small, medium, and large specifications, to reduce operational complexity. However, when multiple tenants share the same resource specification and one tenant requires emergency expansion due to insufficient resources, you cannot directly adjust the original specification. Instead, you need to create a new independent resource specification and switch to it, or directly replace it with a larger resource specification.

2. [Create a resource pool](#step-2-create-a-resource-pool): When creating a resource pool, actual Units are created, and resources are allocated based on the specifications. If the reserved resources on the corresponding nodes are insufficient, the creation will fail. You can view the resource allocation information of all nodes through the `GV$OB_SERVERS` view. If the creation is successful, you can view the resource pool and its corresponding Units through the `DBA_OB_RESOURCE_POOLS` view and `DBA_OB_UNITS` view. Resource pools cannot be reused. After a tenant is successfully created, the specified resource pool will be allocated to it.

3. [Create a tenant](#step-3-create-a-tenant): When creating a tenant, you can specify the `RESOURCE_POOL_LIST` to assign the resource pool to the tenant. You can view all tenants through the `DBA_OB_TENANTS` view. You can use a separate resource pool for each zone with an independent resource specification. Alternatively, you can use the same resource pool for all zones, which means all zones will use the same resource specification. In addition to the resource pool list, other important attributes and system variables include compatibility mode, primary zone, locality, and connection allowlist. The resource pool list is a required field when creating a tenant. The root user password for a new tenant is empty. Please set the password before using it.

## Resource planning

Before creating a tenant, it is essential to plan the resources. Adjusting resources after tenant creation can be very complicated. The foundation of effective resource planning is a deep understanding of the business scenarios, allowing for more active participation in the design of the business database architecture.

Consider the following when planning resources:

* Reserve a certain amount of resources on each node for emergency expansion when a tenant's capacity is insufficient.

* For businesses with a large amount of write operations, set a larger memory and log disk specification. For businesses that heavily consume CPU resources, distribute them across different nodes to avoid load imbalance and hotspots that could impact business performance.

* The cluster configuration item `resource_hard_limit` defines the percentage of CPU resource over-subscription, also known as the "over-subscription configuration item." OceanBase Database only supports CPU over-subscription and does not support over-subscription for other resources. CPU over-subscription is suitable for scenarios where different tenants in the same cluster have peak loads at different times, thereby improving overall resource utilization. If multiple tenants have peak loads simultaneously, enabling CPU over-subscription may lead to CPU resource contention and mutual impact between tenants.

* The resource specification of a Unit cannot exceed the total allocatable resources of a single node. For a single Unit tenant (where the `UNIT_NUM` of the resource pool is 1), if the capacity reaches its limit, you can either replace it with a server of a larger specification or horizontally scale it to multiple Units to utilize resources from multiple nodes. When designing a multi-Unit tenant, carefully plan the distribution of business data across Units to avoid performance degradation caused by distributed transactions. If the business volume is expected to exceed the single-node capacity limit, design data sharding in advance. Data sharding should aim to minimize the use of distributed transactions.

  For businesses migrating from traditional databases to OceanBase Database, a peer architecture is often adopted for smooth migration. This involves using a single Unit tenant design to ensure that business access to the database still only requires accessing a single node. As the business volume increases and reaches the single-node capacity limit, it can be expanded to a multi-Unit tenant. Business data can be divided into multiple groups based on the business scenarios. Each group of business data is placed in one Unit, ensuring that each business's database access does not cross nodes. This achieves horizontal scaling without performance loss. This is one of the architectural advantages of OceanBase Database over traditional databases, namely, easy horizontal scalability that allows for effortless capacity expansion beyond the single-node limit.

## Considerations

OceanBase Database supports two types of tenants: MySQL-compatible and Oracle-compatible. When creating a tenant, you need to specify the type. Once a tenant is created, its type cannot be modified. Therefore, plan the tenant type before creating it.

## Step 1: Create a resource specification

A resource specification defines resources such as CPU, memory, disk space, and IOPS.

<main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Based on extensive experience with OceanBase Database V3.x, OceanBase Database V4.0 has significantly improved its resource management features:</p>
    <ul>
        <li>Supports unit-level management of resources such as CPU, memory, log disk space, and IOPS, but does not support unit-level management of data disk space and session count. For compatibility with V3.x maintenance tools and test cases, the <code>CREATE RESOURCE UNIT</code> statement still allows specifying <code>MAX_DISK_SIZE</code> and <code>MAX_SESSION_NUM</code>, but these parameters will not take effect and will not generate errors.</li>
        <li>Supports CPU over-provisioning, controlled by the configuration item <code>resource_hard_limit</code>. In the <code>GV$OB_SERVERS</code> view, the <code>CPU_CAPACITY</code> and <code>CPU_CAPACITY_MAX</code> fields represent the total CPU capacity and over-provisioned CPU capacity of a node, respectively, with <code>CPU_CAPACITY_MAX = CPU_CAPACITY * resource_hard_limit</code>.</li>
        <li>Does not support memory over-provisioning, as it may lead to unstable tenant operations.</li>
        <li>Supports log disk space isolation between tenants. The system reserves log disk space for each tenant to prevent one tenant's heavy writes in V3.x from exhausting the log disk and affecting other tenants.</li>
        <li>Supports IOPS isolation between tenants. Three IOPS specification parameters are introduced: <code>MIN_IOPS</code>, <code>MAX_IOPS</code>, and <code>IOPS_WEIGHT</code>. By default, these parameters do not need to be specified, and the system calculates them based on CPU specifications. If the sum of all Units' <code>MIN_IOPS</code> on a node exceeds the disk IOPS limit, IOPS resources will be allocated based on the <code>IOPS_WEIGHT</code> weights.</li>
        <li>The Meta tenant does not have an independent Unit. When creating a tenant, the system reserves resources for the Meta tenant by default, deducting them from user tenant resources. The Meta tenant's resources are configured with default settings and cannot be specified by users.</li>
        <li>When creating a resource specification, CPU specifications and memory specifications are mandatory. Other parameters can be automatically calculated, with log disk space calculated based on memory specifications and IOPS specifications based on CPU specifications.</li>
    </ul>
</main>

**Procedure**

1. Log in to the `sys` tenant of the cluster as the `root` user.

    ```shell
    obclient -h172.30.xx.xx -P2883 -uroot@sys#cluster -p**** -A
    ```

2. Switch to the `oceanbase` database.

    ```shell
    obclient(root@sys)[(none)]> USE oceanbase;
    ```

3. Use the `DBA_OB_UNIT_CONFIGS` view to obtain existing resource specification information.

    ```shell
    obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_UNIT_CONFIGS;
    ```

    The returned result is as follows:

    ```shell
    +----------------+-----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+----------------+---------------------+---------------------+-------------+---------------------+----------------------+

    +----------------+-----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+----------------+---------------------+---------------------+-------------+---------------------+----------------------+

    |           1001 | unit001         | 2025-05-16 11:31:08.531754 | 2025-05-16 11:31:08.531754 |       2 |       2 |  6442450944 |   19327352832 |           NULL | 9223372036854775807 | 9223372036854775807 |           2 | 9223372036854775807 |                    2 |
    +----------------+-----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+----------------+---------------------+---------------------+-------------+---------------------+----------------------+
    2 rows in set
    ```

   For more information about the `DBA_OB_UNIT_CONFIGS` view, see [DBA_OB_UNIT_CONFIGS](../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/23700.o-dba_ob_unit_configs-of-sys-tenant.md).

4. Use the `CREATE RESOURCE UNIT` statement to create a resource specification.

    The syntax is as follows:

    ```sql
    CREATE RESOURCE UNIT unit_name 
        MEMORY_SIZE [=] 'size_value',
        MAX_CPU [=] cpu_num,  
        [MAX_IOPS [=] iops_num,]
        [MIN_CPU [=] cpu_num,]
        [MIN_IOPS [=] iops_num,]
        [IOPS_WEIGHT [=]iopsweight,]
        [MAX_NET_BANDWIDTH [=] bandwidth_num,] 
        [NET_BANDWIDTH_WEIGHT [=] bandwidth_weight_num,]
        [LOG_DISK_SIZE [=] 'size_value'];
    ```

    Parameters:

    When creating a resource specification, MAX_CPU and MEMORY_SIZE are required.

    * `unit_name`: the name of the resource specification.
    * `MEMORY_SIZE`: the memory specification, with a minimum value controlled by the hidden configuration item `__min_full_resource_pool_memory`, defaulting to 5 GB and adjustable to a minimum of 4 GB. OceanBase Database V4.0 does not support memory over-provisioning.
    * `MAX_CPU`: the maximum CPU specification, with `MIN_CPU` as the minimum CPU specification, measured in cores. If `MIN_CPU` is not specified, it defaults to the value of `MAX_CPU`.
    * `MIN_CPU`: the minimum CPU specification, with the sum of all tenants' `MIN_CPU` values not exceeding the node's total CPU capacity `CPU_CAPACITY`.
    * `MAX_IOPS` and `MIN_IOPS`: specify the upper and lower limits of IOPS resources available for the current Unit, with a minimum value of 1024 and requiring `MAX_IOPS >= MIN_IOPS`.

       After setting `MAX_IOPS` and `MIN_IOPS`, OceanBase Database internally processes these values as the IOPS for 16 KB reads. It is recommended to set `MAX_IOPS` and `MIN_IOPS` to the IOPS values corresponding to 16 KB reads calculated for the disk to facilitate resource isolation within tenants. For more information about IOPS benchmark calculation, see [Disk performance calibration](300.resource-isolation/300.resource-isolation-of-mysql-mode/150.disk-performance-calibration-of-mysql-mode.md). For detailed information about resource isolation within tenants, see [Resource isolation overview](300.resource-isolation/100.resource-isolation-overview.md).

      If IOPS-related parameters are not specified, their internal default values are as follows:

      * If both `MIN_IOPS` and `MAX_IOPS` are not specified, the system automatically allocates IOPS resources based on `IOPS_WEIGHT`, with:

        * `MIN_IOPS` and `MAX_IOPS` both set to `INT64_MAX`.

        * If `IOPS_WEIGHT` is not specified, it defaults to `MIN_CPU`.

        * If `IOPS_WEIGHT` is specified, the specified value is used.

      * If only `MAX_IOPS` is specified, `MIN_IOPS` takes the value of `MAX_IOPS`. Similarly, if only `MIN_IOPS` is specified, `MAX_IOPS` takes the value of `MIN_IOPS`. In this case:

        * If `IOPS_WEIGHT` is not specified, it defaults to `0`.

    * `MAX_NET_BANDWIDTH`: specifies the maximum network bandwidth available for each Unit of a tenant, with a minimum value of 1 MB. If not specified, the default value is `INT64_MAX`.

    * `NET_BANDWIDTH_WEIGHT`: specifies the network bandwidth weight of a tenant's Unit, used to calculate the bandwidth allocated to each tenant by each OBServer. The minimum value is 0. If not specified, the system automatically calculates `NET_BANDWIDTH_WEIGHT` as follows:

       * If `MAX_NET_BANDWIDTH` is specified, `NET_BANDWIDTH_WEIGHT` is set to 0.

       * If `MAX_NET_BANDWIDTH` is not specified, `NET_BANDWIDTH_WEIGHT = MIN_CPU`.

    * `LOG_DISK_SIZE`: the size of the log disk. OceanBase Database V4.0 manages the log disk space per tenant. The system reserves log disk space for each tenant to achieve tenant isolation. If you do not specify this parameter, the default value is three times the memory size, with a minimum of 2 GB.
    * OceanBase Database V4.0 supports IOPS isolation between tenants. The `MAX_IOPS`, `MIN_IOPS`, and `IOPS_WEIGHT` parameters determine the IOPS specifications. By default, you do not need to specify these IOPS specification parameters. The system automatically calculates them based on the CPU specifications.

    * When specifying a value for a parameter, you can use a pure number without quotes, or you can use a number with a unit and quotes (for example, `'1T'`, `'1G'`, `'1M'`, and `'1K'`).

      The following table describes the parameters:

      * For the integer parameters `MAX_CPU`, `MIN_CPU`, `MAX_IOPS`, `MIN_IOPS`, `IOPS_WEIGHT`, and `NET_BANDWIDTH_WEIGHT`, if you specify a value with a unit and quotes, the unit represents the number of units. For example, '1K' = 1000 and '1M' = 1000000. For example, `MAX_IOPS='2K'` is equivalent to `MAX_IOPS=2000`.

        If you specify a value without a unit and quotes, the value is treated as a pure number. For example, '100' = 100 and '1000' = 1000.

      * For the capacity parameters `MEMORY_SIZE`, `MAX_NET_BANDWIDTH`, and `LOG_DISK_SIZE`, if you specify a value with a unit and quotes, the unit represents bytes. For example, '1K' = 1024 and '1M' = 1024 * 1024.

        If you specify a value without a unit and quotes, the default unit is MB. For example, '100' = '100M' = 100 * 1024 * 1024.

    For more information about the `CREATE RESOURCE UNIT` statement, see [CREATE RESOURCE UNIT](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/700.create-resource-unit.md).

    Here is an example:

    Create a resource specification named `S1_unit_config` with 1 CPU core, 5 GB of memory, and 6 GB of log disk space.

    ```shell
    obclient(root@sys)[oceanbase]> CREATE RESOURCE UNIT S1_unit_config
                    MEMORY_SIZE = '5G',
                    MAX_CPU = 1, MIN_CPU = 1,
                    LOG_DISK_SIZE = '6G',
                    MAX_IOPS = 10000, MIN_IOPS = 10000, IOPS_WEIGHT=1;
    ```

5. Query the `DBA_OB_UNIT_CONFIGS` view to confirm that the resource specification was created successfully.

    ```shell
    obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_UNIT_CONFIGS WHERE NAME = 'S1_unit_config';
    ```

    The result set is as follows:

    ```shell
    +----------------+----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+----------------+----------+----------+-------------+---------------------+----------------------+
    | UNIT_CONFIG_ID | NAME           | CREATE_TIME                | MODIFY_TIME                | MAX_CPU | MIN_CPU | MEMORY_SIZE | LOG_DISK_SIZE | DATA_DISK_SIZE | MAX_IOPS | MIN_IOPS | IOPS_WEIGHT | MAX_NET_BANDWIDTH   | NET_BANDWIDTH_WEIGHT |
    +----------------+----------------+----------------------------+----------------------------+---------+---------+-------------+---------------+----------------+----------+----------+-------------+---------------------+----------------------+
    |           1002 | S1_unit_config | 2025-05-28 10:20:38.299456 | 2025-05-28 10:20:38.299456 |       1 |       1 |  5368709120 |    6442450944 |           NULL |    10000 |    10000 |           1 | 9223372036854775807 |                    1 |

    1 row in set
    ```

## Step 2: Create a resource pool

After you create a resource specification, you can specify the resource specification when you create a resource pool. This way, you can use the corresponding number of resource units and allocate them to the corresponding tenant.

**Prerequisites**

* Make sure that the cluster has enough available resources to create a resource pool. For more information, see [View tenant and resource information](../600.common-tenant-operations/400.view-tenant-information.md).
* When you create a resource pool, you must specify its resource specification. Before you execute the create resource pool operation, make sure that a resource specification is available. For more information about how to create a resource specification, see [Step 1: Create a resource specification](#step-1-create-a-resource-specification).

**Procedure**

1. Log in to the sys tenant of the cluster as the root user.

    ```shell
    obclient -h172.30.xx.xx -P2883 -uroot@sys#cluster -p**** -A
    ```

2. Enter the `oceanbase` database.

    ```shell

    ```

   For more information about the `DBA_OB_RESOURCE_POOLS` view, see [DBA_OB_RESOURCE_POOLS](../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/21000.o-dba_ob_resource_pools-of-sys-tenant.md).

4. Execute the `CREATE RESOURCE POOL` statement to create a resource pool.

    The syntax is as follows:

    ```sql
    CREATE RESOURCE POOL poolname 
        UNIT [=] unitname, 
        UNIT_NUM [=] unitnum, 
        ZONE_LIST [=] ('zone' [, 'zone' ...]);
    ```

    Parameter description:

    * `UNIT`: the resource specification of the resource pool.
    * `UNIT_NUM`: the number of resource units in the resource pool in the specified zone. The value of this parameter must be less than the number of nodes in the specified zone. Each node can have at most one resource unit of the same tenant.
    * `ZONE_LIST`: the zones in which the resource pool is distributed. OceanBase Database creates `UNIT_NUM` resource units in each zone specified in `ZONE_LIST`. Each resource unit has the resource specification specified by the `UNIT` parameter.

    For more information about the `CREATE RESOURCE POOL` statement, see [CREATE RESOURCE POOL](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/600.create-resource-pool.md).

    Example:

    * Create a resource pool named `mq_pool_01` and create one resource unit in zone1 and one resource unit in zone2. The resource specification of each resource unit is `S1_unit_config`.

      ```shell
      obclient(root@sys)[oceanbase]> CREATE RESOURCE POOL mq_pool_01 
                        UNIT='S1_unit_config', 
                        UNIT_NUM=1, 
                        ZONE_LIST=('zone1','zone2'); 
      ```

    * Create a resource pool named `mq_pool_02` and create two resource units in zone3. The resource specification of each resource unit is `S1_unit_config`.

      ```shell
      obclient [oceanbase]> CREATE RESOURCE POOL mq_pool_02 
                        UNIT='S1_unit_config', 
                        UNIT_NUM=2, 
                        ZONE_LIST=('zone3'); 
      ```

## Step 3: Create a tenant

After you create a resource pool, you can assign the resource pool to a tenant according to business requirements.

**Prerequisites**

Make sure that an available resource pool is available. For more information about how to create a resource pool and resource units, see [Create a resource pool](#step-2-create-a-resource-pool).

**Considerations**

OceanBase Database supports two types of tenants: MySQL-compatible tenants and Oracle-compatible tenants. When you create a tenant, you need to specify the type of the tenant. Once a tenant is created, its type cannot be changed. Therefore, before you create a tenant, you need to plan the type of the tenant.

**Procedure**

1. Log in to the sys tenant of the cluster as the root user.

    ```shell
    obclient -h172.30.xx.xx -P2883 -uroot@sys#cluster -p**** -A
    ```

2. Log in to the `oceanbase` database.

    ```sql
    obclient(root@sys)[(none)]> USE oceanbase;
    ```

3. You can query the `DBA_OB_TENANTS` view to view the information about all tenants.

    ```shell
    obclient(root@sys)[oceanbase]> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, CREATE_TIME, MODIFY_TIME, PRIMARY_ZONE, LOCALITY, COMPATIBILITY_MODE, STATUS, TENANT_ROLE FROM oceanbase.DBA_OB_TENANTS;
    ```

4. (Optional) If you want to create a tenant of the heterogeneous zone deployment (heterogeneous zone mode), modify the configuration template in which you specify the `zone_deploy_mode` parameter as `hetero`. Do not modify the value of the `zone_deploy_mode` parameter in the `CREATE TENANT` statement.

    ```shell
    obclient(root@sys)[oceanbase]> ALTER SYSTEM SET zone_deploy_mode = 'hetero' tenant = 'seed';
    ```

    <main id="notice" type='explain'>
    <h4>Note</h4>
    <p>Other than editing the template, you can create a tenant that is deployed in a homogeneous zone and modify the <code>zone_deploy_mode</code> parameter of the tenant to <code>hetero</code>. </p>
    </main>

    After the command is executed successfully, all tenants created subsequently are allowed to be heterogeneously deployed.

5. Execute the `CREATE TENANT` statement to create a tenant.

    The syntax is as follows:

    ```sql
    CREATE TENANT [IF NOT EXISTS] tenant_name  
        PRIMARY_ZONE [=] zone,
        RESOURCE_POOL_LIST [=](poolname [, poolname...])
        [ENABLE_ARBITRATION_SERVICE = {true | false}]
        {SET | SET VARIABLES | VARIABLES} system_var_name = expr [,system_var_name = expr] ...
    ```

    Parameters:

    * `IF NOT EXISTS`: Optional. If a tenant with the specified name already exists and `IF NOT EXISTS` is not specified, an error occurs.
    * `tenant_name`：specifies the tenant name. The tenant name must not be a reserved word of OceanBase Database.
    * `PRIMARY_ZONE`：Specifies the primary zone of the tenant.

      `PRIMARY_ZONE` specifies the preferred zones that the tenant uses for read and write services. In reality, it is a list of multiple zones. When a list contains multiple zones, the zones separated by a semicolon (;) are ranked in order from highest to lowest priority, and the zones separated by a comma (,) have the same priority, meaning that the traffic is distributed among multiple zones, and these zones simultaneously provide services.

      For example, if the configuration is `primary_zone = 'zone1;zone2,zone3'`, the system first uses zone1 for reads and writes. If zone1 is unavailable, the system uses zone2 and zone3 simultaneously.

      <main id="notice" type='notice'>
       <h4>Note</h4>
       <p>When specifying the <code>PRIMARY_ZONE</code>, you can set the value to RANDOM, which must be in uppercase. In this case, all zones of the specified tenant are the primary zones with the highest priority.</p>
      </main>

    * `RESOURCE_POOL_LIST`: the list of resource pools to allocate to the tenant. Required. If multiple resource pools are specified:

      * In the homogeneous Zone mode, the number of `UNIT_NUM` resources across resource pools must be consistent.
      * In a hybrid zone deployment, a tenant can have multiple resource pools with varying `UNIT_NUM` values. However, the same `UNIT_NUM` values can be specified in the tenant’s resource pools. Each tenant can have a maximum of two types of `UNIT_NUM` values. For example, a tenant has three resource pools named <code>pool1</code>, <code>pool2</code>, and <code>pool3</code>. The `unit_num` values of the three resource pools are 2, 4, and 4 respectively. If you change the `unit_num` value of <code>pool3</code> to 1, the system will return an error message <code>More than two distinct unit_num in a single tenant not allowed</code>.

      The zone list for tenant replica distribution inherits from the `ZONE_LIST` attribute of `RESOURCE_POOL_LIST`, the number of tenant replicas inherits from the number of entries in the `ZONE_LIST` attribute of `RESOURCE_POOL_LIST`, and the number of units in each zone for the tenant inherits from the `UNIT_NUM` value in `RESOURCE_POOL_LIST`.
      Properties, units' resource specifications, and units' resource specifications of tenant are inherited from the properties in the `RESOURCE_POOL_LIST` statement.

      <main id="notice" type='notice'>
       <h4>Note</h4>
       <p>Multiple resource pools that belong to the same tenant must have disjoint <code>ZONE_LIST</code> lists. </p>
      </main>

    * `ENABLE_ARBITRATION_SERVICE`: specifies whether to enable arbitration service for the tenant. If not specified, the arbitration service of the default tenant is disabled. If the arbitration service is disabled when a tenant is created, you can enable it after the tenant is created. For more information, see [Enable the arbitration service for a tenant](../../400.high-availability/400.arbitration-high-availability/200.enable-the-arbitration-service.md).

      <main id="notice" >
      <h4>Applicability</h4>
      <p>Only available in OceanBase Database Enterprise Edition. OceanBase Database Community Edition does not support arbitration services.</p>
      </main>

    * `system_var_name`: the name of the system variable or configuration parameter.

      * `ob_tcp_invited_nodes`: specifies the list of client IPs that are allowed to connect to the tenant. In the example, `%` indicates that all clients are allowed to connect to the tenant. If the value of `ob_tcp_invited_nodes` is not explicitly specified, only the local IP address can connect to the tenant. For more information about the settings of the allowlist, see [View and set the allowlist](../600.common-tenant-operations/500.view-and-set-whitelist.md).
      * `ob_compatibility_mode`: Specifies the compatibility mode for a tenant, which can be either MySQL mode or Oracle mode. This parameter can only be specified when creating a tenant. If you do not explicitly specify `ob_compatibility_mode`, the default value is MySQL mode.

      * `ob_compatibility_control`: specifies whether to keep the behavior of MySQL 5.7 or MySQL 8.0 for features with conflicting behaviors. When you create a MySQL-compatible tenant, you must specify this variable. You can specify this variable only when you create a tenant. After a tenant is created, you cannot modify this variable. If you do not explicitly specify `ob_compatibility_control`, the system keeps the behavior of MySQL 5.7 by default.

    For more information about the `CREATE TENANT` statement, see [CREATE TENANT](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/800.create-tenant.md).

    Here are some examples:

    * Create a tenant named `mq_t1` (MySQL-compatible by default) with the resource pool `mq_pool_01`, the primary zone `zone1`, and all IP addresses allowed to connect to the database.

        The zone list for replica distribution of the tenant is inherited from the `zone_list` attribute of the `resource_pool_list` parameter. The number of replicas of the tenant is inherited from the number of zones in the `zone_list` attribute of the `resource_pool_list` parameter. The number of units in each zone of the tenant is inherited from the `unit_num` attribute of the `resource_pool_list` parameter. The resource specifications of the tenant's units are inherited from the `unit` attribute of the `resource_pool_list` parameter.

        ```shell
        obclient(root@sys)[oceanbase]> CREATE TENANT IF NOT EXISTS mq_t1 
                        PRIMARY_ZONE='zone1', 
                        RESOURCE_POOL_LIST=('mq_pool_01')
                        set OB_TCP_INVITED_NODES='%';
        ```

    * Create an Oracle-compatible tenant named `oracle_tenant1`. You must explicitly specify `ob_compatibility_mode='oracle'`.

        ```shell
        obclient(root@sys)[oceanbase]> CREATE TENANT IF NOT EXISTS oracle_tenant1 
                        PRIMARY_ZONE='zone1', 
                        RESOURCE_POOL_LIST=('mq_pool_01')
                        SET OB_TCP_INVITED_NODES='%',
                        ob_compatibility_mode='oracle';
        ```

    * Create a tenant named `mq_t2` (MySQL-compatible by default) with the resource pools `mq_pool_01` and `mq_pool_02`, the primary zones `zone1` and `zone2`, and all IP addresses allowed to connect to the database.

        ```shell
        obclient(root@sys)[oceanbase]> CREATE TENANT IF NOT EXISTS mq_t2 
                        PRIMARY_ZONE='zone1,zone2', 
                        RESOURCE_POOL_LIST=('mq_pool_01','mq_pool_02')
                        set OB_TCP_INVITED_NODES='%';
        ```

7. After the tenant is created, you can log in to the tenant.

   The default administrator user is `root` in MySQL-compatible mode and `sys` in Oracle-compatible mode. The password of the administrator user is empty. You must change the password of the administrator user. Here is an example.

    * MySQL-compatible mode

      1. Log in to the `mq_t1` tenant as the `root` user.

          ```shell
          obclient -h172.30.xx.xx -P2883 -uroot@mq_t1#cluster  -A
          ```

      2. Execute the following statement to change the password of the `root` user.

          ```shell
          obclient(root@mq_t1)[(none)]> ALTER USER root IDENTIFIED BY '****';
          Query OK, 0 rows affected
          ```

    * Oracle-compatible mode

      1. Log in to the `oracle_tenant1` tenant as the `SYS` user.

          ```shell
          obclient -h172.30.xx.xx -P2883 -usys@oracle_tenant1#cluster  -A
          ```

      2. Execute the following statement to change the password of the `SYS` user.

          ```shell
          obclient(syst@oracle_tenant1)[SYS]> ALTER USER sys IDENTIFIED BY ****;
          Query OK, 0 rows affected
          ```

8. After you change the password of the administrator user, log in to the tenant again.

    * MySQL-compatible mode

        ```shell
        obclient -h172.30.xx.xx -P2883 -uroot@mq_t1#cluster -p**** -A
        ```

    * Oracle-compatible mode

        ```shell
        obclient -h172.30.xx.xx -P2883 -usys@oracle_tenant1#cluster -p**** -A
        ```
