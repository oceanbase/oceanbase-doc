# Set log restore source

You must set a log restore source for both physical standby tenants based on log archiving and those based on network connection. In both deployment scenarios, the log restore source can be changed at any time based on your business requirements, and you can also switch between the two types of log restore sources. This topic describes how to set a log restore source for a physical standby tenant based on log archiving, and how to set a log restore source for a physical standby tenant based on network connection.

## Considerations

When you switch the log restore source from one type to another type, make sure that the log restore source before and after the switch is consistent with the source tenant specified when the standby tenant was created. In other words, either the log archives of the source tenant or the source tenant itself can be used. If the log restore sources before and after the switch are inconsistent, the data of the standby tenant cannot be restored and you will have to create a new standby tenant.

## Physical standby tenant based on log archive

For a standby tenant created by using physical backup and restore (with logs), the default restore source for the standby tenant is set to the log archive destination of the primary tenant or the standby tenant. Therefore, you usually do not need to set the restore source. If you want to change the log restore source to the primary tenant, follow the procedure described in the **Physical standby tenant based on network connection** section of this topic.

For a standby tenant created by using other methods (such as creating an empty standby tenant or using the `BACKUP DATABASE PLUS ARCHIVELOG` feature), if you want to set the log restore source to the log archive of the primary tenant, perform the following operations.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>If the backup media of the primary tenant or the standby tenant changes the key information of the backup media during the operation of the physical standby tenant, perform the following operations to reconfigure the log restore source. </p>
</main>

1. Log in to the `sys` tenant of the standby tenant or the cluster to which the standby tenant belongs as the administrator.

2. Configure the restore source of the standby tenant to point to the archive destination of the primary tenant.

   * Configure the restore source of the standby tenant for the `sys` tenant of the standby tenant.

     ```sql
     ALTER SYSTEM SET LOG_RESTORE_SOURCE ='LOCATION=archive_path' TENANT = tenant_name;
     ```

   * Configure the restore source of the standby tenant for the standby tenant.

     ```sql
     ALTER SYSTEM SET LOG_RESTORE_SOURCE ='LOCATION=archive_path';
     ```

   In the commands, the `LOCATION` parameter specifies the archive destination of the primary tenant.

   The following example shows how to configure the restore source when the archive media is Object Storage Service (OSS) or Network File System (NFS).

   :::tab
   tab Alibaba Cloud OSS

   If the archive media of the primary tenant is OSS, use the following example to configure the restore source for the standby tenant in the `sys` tenant of the standby tenant or the standby tenant:

   ```shell
   obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE ='location=oss://oceanbase-test-bucket/backup/archive?host=****.aliyun-inc.com&access_id=****&access_key=****' TENANT = standby_tenant;
   ```

   ```shell
   obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE ='location=oss://oceanbase-test-bucket/backup/archive?host=****.aliyun-inc.com&access_id=****&access_key=****';
   ```

   tab NFS

   If the archive media of the primary tenant is NFS, use the following example to configure the restore source for the standby tenant in the `sys` tenant of the standby tenant or the standby tenant:

   ```shell
   obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE ='location=file:///data/1/sh_archive' TENANT = standby_tenant;
   ```

   ```shell
   obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE ='location=file:///data/1/sh_archive';
   ```

   :::

## Physical standby tenant created based on a network connection

The standby tenant created by using the empty tenant method has a default log restore source that is specified by the `LOG_RESTORE_SOURCE` parameter in the `CREATE STANDBY TENANT` statement. The default log restore source directly points to the primary tenant. Therefore, it is usually not necessary to configure the log restore source. If you want to change the log restore source to use the log archives of the primary tenant, you must perform the operations described in the **Physical standby tenant created based on log archives** section of this topic.

For a standby tenant created by using a method other than the empty tenant method (such as the backup and restore (with logs) feature and the `BACKUP DATABASE PLUS ARCHIVELOG` feature), if you want to set the log restore source to point to the primary tenant or the source standby tenant, you must run the `ALTER SYSTEM SET LOG_RESTORE_SOURCE` command to manually specify the log restore source.

### Step 1: Create a user for accessing views

The standby tenant needs to access some system views of the primary tenant or the source tenant to connect to the primary system views of the primary tenant or the source tenant. Therefore, a user dedicated for accessing views must be granted the query permissions on these system views. You can either provide a user that already has the required permissions on the primary tenant or source tenant, or create a new user with the required permissions on the primary tenant or source tenant for the current standby tenant.

The system views that the standby tenant needs to access are as follows:

* `GV$OB_LOG_STAT`: This view is used to obtain the server list of the primary tenant, the log stream LSN range of the replica service, and the role (whether it is a leader).

  For more information about the `GV$OB_LOG_STAT` view, see [GV$OB_LOG_STAT](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/1300.gv-ob_log_stat-of-mysql-mode.md).

* `GV$OB_UNITS`: This view is used to query all unit information of the primary tenant, such as the replica status, zone, and region, which is used for filtering, obtaining, and maintaining tenant machine connections.

  For more information about the `GV$OB_UNITS` view, see [GV$OB_UNITS](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/4600.gv-ob_units-of-mysql-mode.md).

* `GV$OB_PARAMETERS`: This view is used to query essential metadata of the primary tenant, such as `cluster_id` and `tenant_id`.

  For more information about the `GV$OB_PARAMETERS` view, see [GV$OB_PARAMETERS](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/2100.gv-ob_parameters-of-mysql-mode.md).

* `DBA_OB_ACCESS_POINT`: This view is used to obtain access point information. If the access point changes in scenarios such as tenant migration and disaster recovery, the standby tenant can automatically detect the change without manual modification by the user.

  For more information about the `DBA_OB_ACCESS_POINT` view, see [DBA_OB_ACCESS_POINT](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/5700.o-dba_ob_access_point-of-mysql-mode.md).

* `DBA_OB_TENANTS`: This view is used to obtain the compatible mode of the primary tenant.

  For more information about the `DBA_OB_TENANTS` view, see [DBA_OB_TENANTS](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12300.o-dba_ob_tenants-of-mysql-mode.md).

* `DBA_OB_LS`: This view is used to obtain the log stream list and status of the primary tenant.

  For more information about the `DBA_OB_LS` view, see [DBA_OB_LS](../../../../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/9600.o-dba_ob_ls-of-mysql-mode.md).

Create a user dedicated for accessing views and grant required privileges to this user.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>In OceanBase Database, the username and privilege information of a user are synchronized between the primary and standby tenants, and users cannot be created or privileges granted on a standby tenant. Therefore, if the source of the current standby tenant is another standby tenant, you need to create a user dedicated for accessing views and grant required privileges on the primary tenant corresponding to the current standby tenant.</p>
</main>

#### MySQL mode

1. Log in to the primary tenant as the administrator.

2. Execute the following command to create a new user.

   ```shell
   obclient [oceanbase]> CREATE USER rep_user IDENTIFIED BY '******';
   ```

3. Grant privileges to the user.

   For example, grant the `SELECT` privilege on all tables in the `oceanbase` database to the user. You can also grant the `SELECT` privilege on views such as `GV$OB_LOG_STAT`, `GV$OB_UNITS`, `GV$OB_PARAMETERS`, `DBA_OB_ACCESS_POINT`, `DBA_OB_TENANTS`, and `DBA_OB_LS` in the `oceanbase` database.

   ```shell
   obclient [oceanbase]> GRANT SELECT ON oceanbase.* TO rep_user;
   ```

#### Oracle mode

1. Log in to the primary tenant as the administrator.

2. Create a new user.

   ```shell
   obclient [SYS]> CREATE USER rep_user IDENTIFIED BY '******';
   ```

3. Grant the `STANDBY_REPLICATION` role to the new user `rep_user`.

   The `STANDBY_REPLICATION` role is a system-defined role that contains the `CREATE SESSION` system privilege and query privileges on the following views by default:

   * GV$OB_LOG_STAT
   * GV$OB_UNITS
   * GV$OB_PARAMETERS
   * DBA_OB_ACCESS_POINT
   * DBA_OB_TENANTS
   * DBA_OB_LS
   * DBA_OB_LS_HISTORY

   Use the following statement to grant the role:

   ```shell
   obclient [SYS]> GRANT STANDBY_REPLICATION TO rep_user;
   ```

### Step 2: Obtain the access endpoint information of the primary tenant or source standby tenant

For a network-based physical standby database, you also need to obtain the access endpoint information of the primary tenant or source standby tenant when setting the log restore source. The endpoint information includes the IP address and port number of the OBServer node where the tenant replica resides.

1. Log in to the primary tenant or source standby tenant as the administrator.

2. Execute the following command to obtain the access endpoint information.

   * MySQL mode

     ```shell
     obclient [oceanbase]> SELECT * FROM oceanbase.DBA_OB_ACCESS_POINT;
     ```

     <main id="notice" type='explain'>
     <h4>Note</h4>
     <p>If you are logged in to the <code>sys</code> tenant, you need to query the <code>CDB_OB_ACCESS_POINT</code> view for the access endpoint information.</p>
     </main>

   * Oracle mode

     ```shell
     obclient [SYS]> SELECT * FROM SYS.DBA_OB_ACCESS_POINT;
     ```

   The query result is as follows:

   ```shell
   +-----------+-------------+-------------+----------+
   | TENANT_ID | TENANT_NAME | SVR_IP      | SQL_PORT |
   +-----------+-------------+-------------+----------+
   |      1004 | mysql       | xx.xx.xx.22 |    17855 |
   |      1004 | mysql       | xx.xx.xx.23 |    17857 |
   |      1004 | mysql       | xx.xx.xx.24 |    17859 |
   +-----------+-------------+-------------+----------+
   3 rows in set
   ```

   In this example, the queried tenant has three replicas. If the primary tenant or source standby tenant is a single-replica tenant, only one row is returned.

### Step 3: Check the settings of the primary tenant

In the current primary-standby architecture, if the primary tenant performs operations such as scaling down or log transfer, the log streams of the primary tenant may be deleted and the logs may be recycled, which can cause log synchronization to be stuck in the standby tenant. To avoid this issue, you must enable the archiving mode on the primary tenant or set the tenant-level parameter [ls_gc_delay_time](../../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/5100.ls_gc_delay_time.md).

To check whether the archiving mode is enabled on the primary tenant or whether the parameter `ls_gc_delay_time` is set:

* Check whether the archiving mode is enabled on the primary tenant

  1. Log in to the `sys` tenant of the primary tenant or the cluster where the primary tenant resides as the administrator.

  2. Check whether the archiving mode is enabled.

     * In the `sys` tenant of the cluster where the primary tenant resides

       ```shell
       obclient> SELECT LOG_MODE FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME='mysql';
       ```

     * In the user tenant

       :::tab
       tab MySQL mode

       Query whether the archiving mode is enabled in MySQL mode:

       ```shell
       obclient> SELECT LOG_MODE FROM oceanbase.DBA_OB_TENANTS;
       ```

       tab Oracle mode

       Query whether the archiving mode is enabled in Oracle mode:

       ```shell
       obclient> SELECT LOG_MODE FROM SYS.DBA_OB_TENANTS;
       ```

       :::

     The following example shows the query result:

     ```shell
     +--------------+
     | LOG_MODE     |
     +--------------+
     | NOARCHIVELOG |
     +--------------+
     1 row in set
     ```

     If the value of the column is `ARCHIVELOG`, the archiving mode is enabled for the primary tenant. If the value is `NOARCHIVELOG`, the archiving mode is disabled. If it is disabled, follow the steps in [Enable the log archive mode](../../../../600.backup-and-recovery/300.log-archive/300.open-the-log-archive-mode.md) to enable it.

* Check whether the value of the `ls_gc_delay_time` parameter is greater than `0s`

  The tenant-level parameter `ls_gc_delay_time` specifies the delayed deletion time of log streams. The default value is `0s`, which indicates that the log stream delayed deletion feature is disabled. If this parameter is set and the archiving mode is disabled, a log stream that meets the deletion conditions will be retained for a certain period before it is recycled.

  1. Log in to the primary tenant as the administrator.

  2. Query the value of the `ls_gc_delay_time` parameter in the primary tenant.

     ```shell
     obclient> SHOW PARAMETERS LIKE '%ls_gc_delay_time%';
     ```

     If the value of the parameter is `0s`, the parameter is not set. You can set it as needed. For more information about how to set the `ls_gc_delay_time` parameter, see [ls_gc_delay_time](../../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/5100.ls_gc_delay_time.md).

### Step 4: Set the log restore source

1. Log in to the `sys` tenant of the standby tenant or the cluster where the standby tenant is located as the administrator.

2. Execute the following statement to set the log restore source.

   * Set the log restore source of the standby tenant in the `sys` tenant of the cluster where the standby tenant is located.

     ```sql
     ALTER SYSTEM SET LOG_RESTORE_SOURCE ='SERVICE=$ip_list USER=$user_name@$tenant_name PASSWORD=$password' TENANT = standby_tenant_name;
     ```

   * Set the log restore source of the current tenant in the standby tenant.

     ```sql
     ALTER SYSTEM SET LOG_RESTORE_SOURCE ='SERVICE=$ip_list USER=$user_name@$tenant_name PASSWORD=$password';
     ```

   The following table describes some parameters.

   * `$ip_list`: the IP address and SQL port number of the OBServer node in the primary tenant or the standby tenant of the source. The information about the OBServer node is obtained in Step 2. You can omit the information about some OBServer nodes. 
   * `$user_name`: the username of the dedicated user created in Step 1 for accessing the view.
   * `$tenant_name`: the name of the primary tenant or the standby tenant of the source to which you want to connect.
   * `$password`: the password of the dedicated user.

   Here are some examples:

   ```shell
   obclient > ALTER SYSTEM SET LOG_RESTORE_SOURCE = 'SERVICE=11.xx.xx.22:17855;11.xx.xx.23:17857;11.xx.xx.24:17859 USER=rep_user@mysql PASSWORD=******' TENANT = standby_tenant;
   ```

   ```shell
   obclient > ALTER SYSTEM SET LOG_RESTORE_SOURCE = 'SERVICE=11.xx.xx.22:17855;11.xx.xx.23:17857;11.xx.xx.24:17859 USER=rep_user@mysql PASSWORD=******';
   ```

   After you set the log restore source, you can query the `CDB_OB_LOG_RESTORE_SOURCE` view in the system tenant (`sys` tenant) or the `DBA_OB_LOG_RESTORE_SOURCE` view in the user tenant to check whether the setting is successful. For more information, see [View log restore source information](../300.view-log-restore-source.md).
