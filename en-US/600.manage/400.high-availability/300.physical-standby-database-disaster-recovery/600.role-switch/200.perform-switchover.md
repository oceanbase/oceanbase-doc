# Switchover

When the primary tenant is available, you can switch the primary tenant with one of the standby tenants to ensure data consistency.

The following sections provide instructions for switchover based on the two deployment modes of the physical standby database.

## Limitations

* You cannot change the tenant role of the system tenant (`sys`) to `STANDBY`. The role of the system tenant is always `PRIMARY`.

* Before you switch a standby tenant to the primary tenant, all replicas of all log streams of the standby tenant must be online. Otherwise, you must wait for the corresponding replicas to go offline permanently. You can query the `DBA_OB_LS` view of the standby tenant or the `CDB_OB_LS` view of the `sys` tenant in the standby tenant or the cluster where the standby tenant is located to check whether all replicas of all log streams are online. For more information about log stream replicas, see [Replica introduction](../../../300.replica-management/100.replica-introduction.md).

* You cannot execute the Switchover command in a session established by using a service name. For more information about services, see [Create a service](../../../200.tenant-management/600.common-tenant-operations/1700.manage-service/100.create-service.md).

## Overview

This topic describes how to perform a switchover between two tenants in a physical standby tenant setup with a network connection. Switchover involves three main steps: verifying and initiating a switchover, performing a switchover, and configuring log restore settings. Before you start, make sure the system meets the prerequisites.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>During a switchover, you must first verify the switchover, and then initiate the switchover. </p>
</main>

1. Verify the switchover.

   1. Log in to the `sys` tenant of the primary tenant or the primary tenant cluster as the administrator.

   2. Execute the `SWITCHOVER TO STANDBY VERIFY` command to verify whether the `SWITCHOVER` command can be executed successfully.

      * Execute the `SWITCHOVER TO STANDBY VERIFY` command in the `sys` tenant of the primary tenant cluster.

        ```sql
        ALTER SYSTEM SWITCHOVER TO STANDBY TENANT [=] tenant_name VERIFY;
        ```

        Example:

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY TENANT = mysql VERIFY;
        ```

      * Execute the `SWITCHOVER TO STANDBY VERIFY` command in the primary tenant.

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY VERIFY;
        ```

        If the command returns `OK`, it means the verification is successful, and you can proceed to the next step.

        If an error occurs, see [Switchover or failover errors](../../../1000.troubleshooting/800.physical-standby-database/200.switchover-failed.md) for handling methods, and then retry.

   3. Execute the primary-to-standby switchover command.

      * Execute the `SWITCHOVER TO STANDBY` command in the `sys` tenant of the primary tenant cluster.

        ```sql
        ALTER SYSTEM SWITCHOVER TO STANDBY TENANT = tenant_name;
        ```

        Example:

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY TENANT = mysql;
        ```

      * Execute the `SWITCHOVER TO STANDBY` command in the primary tenant.

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY;
        ```

   4. Query the `DBA_OB_TENANTS` view to check whether the primary tenant has been switched to a standby tenant.

      * Query the `DBA_OB_TENANTS` view in the `sys` tenant of the primary tenant cluster.

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS FROM oceanbase.DBA_OB_TENANTS;
        ```

      * Query the `DBA_OB_TENANTS` view in the primary tenant.

        In MySQL mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS FROM oceanbase.DBA_OB_TENANTS;
        ```

        In Oracle mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS FROM SYS.DBA_OB_TENANTS;
        ```

      An example of the query result:

      ```shell
      +-------------+-------------+-------------+-------------------+
      | TENANT_NAME | TENANT_TYPE | TENANT_ROLE | SWITCHOVER_STATUS |
      +-------------+-------------+-------------+-------------------+
      | mysql       | USER        | STANDBY     | NORMAL            |
      +-------------+-------------+-------------+-------------------+
      1 row in set
      ```

      The switchover is successful if `TENANT_ROLE` is `STANDBY` and `SWITCHOVER_STATUS` is `NORMAL`.

2. Execute the standby-to-primary switchover command.

   1. Log in to the `sys` tenant of the standby tenant or the standby tenant cluster as the administrator.

   2. Execute the standby-to-primary switchover command.

      * Execute the `SWITCHOVER TO PRIMARY` command in the `sys` tenant of the standby tenant cluster.

        ```sql
        ALTER SYSTEM SWITCHOVER TO PRIMARY TENANT = tenant_name;
        ```

        Example:

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO PRIMARY TENANT = standby1;
        ```

      * Execute the `SWITCHOVER TO PRIMARY` command in the standby tenant.

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO PRIMARY;
        ```

   3. Query the `DBA_OB_TENANTS` view to check whether the standby tenant has been switched to the primary tenant.

      * Query the `DBA_OB_TENANTS` view in the `sys` tenant of the standby tenant cluster.

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS FROM oceanbase.DBA_OB_TENANTS;
        ```

      * Query the `DBA_OB_TENANTS` view in the standby tenant.

        In MySQL mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS FROM oceanbase.DBA_OB_TENANTS;
        ```

        In Oracle mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS FROM SYS.DBA_OB_TENANTS;
        ```

      An example of the query result:

      ```shell
      +-----------------+-------------+-------------+-------------------+
      | TENANT_NAME     | TENANT_TYPE | TENANT_ROLE | SWITCHOVER_STATUS |
      +-----------------+-------------+-------------+-------------------+
      | standby1        | USER        | PRIMARY     | NORMAL            |
      +-----------------+-------------+-------------+-------------------+
      1 row in set
      ```

      The standby-to-primary switchover is successful if the `TENANT_ROLE` of the original standby tenant has changed to `PRIMARY` and `SWITCHOVER_STATUS` has changed to `NORMAL`.

3. Configure a log restore source for the original primary tenant.

   You can configure a log restore source before or after the switchover.

   1. Log in to the `sys` tenant of the original primary tenant or the original primary tenant cluster as the administrator.

   2. Execute the following command to configure a log restore source.

      * Configure a log restore source in the `sys` tenant of the original primary tenant cluster.

        ```sql
        ALTER SYSTEM SET LOG_RESTORE_SOURCE ='SERVICE=$ip_list USER=$user_name@$tenant_name PASSWORD=$password' TENANT = tenant_name;
        ```

      * Configure a log restore source in the original primary tenant.

        ```sql
        ALTER SYSTEM SET LOG_RESTORE_SOURCE ='SERVICE=$ip_list USER=$user_name@$tenant_name PASSWORD=$password';
        ```

      The following parameters are described in this section:

      * `$ip_list`: the IP address and SQL port number of the OBServer node of the new primary tenant. You do not need to specify all OBServer nodes.
      * `$user_name`: the user created in the new primary tenant for accessing system views.
      * `$tenant_name`: the tenant name of the new primary tenant.
      * `$password`: the password of the user for accessing system views.

      Example:

      ```shell
      obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE = 'SERVICE=11.xx.xx.22:17855;11.xx.xx.23:17857;11.xx.xx.24:17859 USER=rep_user2@standby_tenant PASSWORD=******' TENANT = mysql;
      ```

      ```shell
      obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE = 'SERVICE=11.xx.xx.22:17855;11.xx.xx.23:17857;11.xx.xx.24:17859 USER=rep_user2@standby_tenant PASSWORD=******';
      ```

      For more information about how to configure a log restore source, see [Set a log restore source](../300.log-transport-service/200.configure-the-log-transport-service/100.set-log-restore-source.md).

   3. Query the `DBA_OB_TENANTS` view to check whether log synchronization is in progress.

      After you configure a log restore source, log synchronization will automatically start because the original primary tenant has been switched to a standby tenant. You can query the `DBA_OB_TENANTS` view to check whether log synchronization is in progress.

      * Query the `DBA_OB_TENANTS` view in the `sys` tenant of the original primary tenant cluster.

        ```shell
        # Query the tenant ID. A tenant ID that is even indicates a user tenant.
        obclient> SELECT TENANT_ID, SYNC_SCN FROM oceanbase.DBA_OB_TENANTS;
        # Query information based on the user tenant ID.
        obclient> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS, SCN_TO_TIMESTAMP(SYNC_SCN), RECOVERY_UNTIL_SCN FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_ID = $user_tenant_id;
        ```

      * Query the `DBA_OB_TENANTS` view in the original primary tenant.

        In MySQL mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS, SCN_TO_TIMESTAMP(SYNC_SCN), RECOVERY_UNTIL_SCN FROM oceanbase.DBA_OB_TENANTS;
        ```

        In Oracle mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS, SCN_TO_TIMESTAMP(SYNC_SCN), RECOVERY_UNTIL_SCN FROM SYS.DBA_OB_TENANTS;
        ```

      In MySQL mode, the query result is as follows:

      ```shell
      +-------------+-------------+-------------+-------------------+----------------------------+---------------------+
      | TENANT_NAME | TENANT_TYPE | TENANT_ROLE | SWITCHOVER_STATUS | SCN_TO_TIMESTAMP(SYNC_SCN) | RECOVERY_UNTIL_SCN  |
      +-------------+-------------+-------------+-------------------+----------------------------+---------------------+
      | mysql       | USER        | STANDBY     | NORMAL            | 2023-04-18 13:46:20.887793 | 4611686018427387903 |
      +-------------+-------------+-------------+-------------------+----------------------------+---------------------+
      1 row in set
      ```

      Based on the query result, if the value of the `RECOVERY_UNTIL_SCN` column is equal to the maximum SCN (4611686018427387903), it indicates that the original primary tenant is continuously synchronizing logs. Otherwise, the original primary tenant is not continuously synchronizing logs.

## A physical standby database with log archiving

In this scenario, a switchover involves the following three phases: activate log archiving mode for the standby tenant --> switch the primary tenant to a standby tenant --> switch the standby tenant to a primary tenant.

<main id="notice" type='notice'>
<h4>Notice</h4>
<p>Before performing a switchover, you must first switch the primary tenant to a standby tenant. Otherwise, a problem may occur. For example, two primary tenants may exist at the same time or the standby tenant cannot synchronize logs. In this scenario, the standby tenant does not perceive the status of the original primary tenant. If you switch the standby tenant to a primary tenant in advance, the <code>ALTER SYSTEM SWITCHOVER TO PRIMARY</code> statement may still be executed without errors. </p>
</main>

1. Activate log archiving mode for the standby tenant.

   In a physical standby database with log archiving, the original primary tenant needs to synchronize all modifications from the new primary tenant (the original standby tenant) by continuously reading the standby tenant's archived logs. Therefore, the new primary tenant (the original standby tenant) must be in log archiving mode. Additionally, to ensure log continuity, the new primary tenant (the original standby tenant) must enable log archiving before the switchover.

   1. Log in to the `sys` tenant of the standby tenant or the cluster in which the standby tenant is located.

   2. Configure the destination of the standby tenant's log archiving.

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>For different tenants, use different archive paths. </p>
       </main>

      The main parameters to configure are `LOCATION`, `PIECE_SWITCH_INTERVAL`, and `BINDING`.

      * Configure the destination of log archiving for the standby tenant in the `sys` tenant of the cluster in which the standby tenant is located.

        ```sql
        ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=archive_path [PIECE_SWITCH_INTERVAL=piece_switch_interval] [BINDING=archive_mode]' TENANT = tenant_name;
        ```

      * Configure the destination of log archiving for the standby tenant.

        ```sql
        ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=archive_path [PIECE_SWITCH_INTERVAL=piece_switch_interval] [BINDING=archive_mode]';
        ```

      The descriptions of the relevant parameters are as follows:

      * `LOCATION`: specifies the destination of the log archiving. Currently, OceanBase Database supports the NFS and Alibaba Cloud OSS media for log archiving.

      * `BINDING`: specifies the priority of the log archiving to the business. Currently, it supports the `Optional` and `Mandatory` modes. If not configured, the default is the `Optional` mode.

        * The `Optional` mode gives priority to the business. In this mode, when the log archiving speed cannot keep up with the speed at which logs are generated, some logs may be archived and then recycled, which can cause a break in the data stream.

        * The `Mandatory` mode gives priority to the log archiving. If log archiving cannot keep up with the business data writing, users may fail to write data.

      * `PIECE_SWITCH_INTERVAL`: specifies the cycle at which a piece is switched. The value ranges from [1d, 7d]. If not specified, the default value is 1d.

      Assume that the archive media is NFS. An example of configuring the archive path as `file:///data/1/standby2_archive2/` and the archive mode as `Optional` is as follows:

      ```shell
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/1/standby2_archive2/ BINDING=optional' TENANT = standby2;
      ```

      ```shell
      obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST='LOCATION=file:///data/1/standby2_archive2/ BINDING=optional';
      ```

   3. Enable log archiving for the standby tenant.

      * Enable log archiving for the standby tenant in the `sys` tenant of the cluster in which the standby tenant is located.

        Example:

        ```shell
        obclient> ALTER SYSTEM ARCHIVELOG TENANT = standby2;
        ```

        In this example, `standby2` is the name of the standby tenant. You must replace it with the actual tenant name in the environment.

      * Enable log archiving for the standby tenant.

        ```shell
        obclient> ALTER SYSTEM ARCHIVELOG;
        ```

   4. Check whether the archiving state is `DOING`.

      * Query the view in the `sys` tenant of the cluster in which the standby tenant is located.

        ```shell
        obclient> SELECT DEST_ID, ROUND_ID, DEST_NO, STATUS, CHECKPOINT_SCN, CHECKPOINT_SCN_DISPLAY, PATH FROM oceanbase.CDB_OB_ARCHIVELOG;
        ```

      * Query the view in the standby tenant.

        MySQL mode:

        ```shell
        obclient> SELECT DEST_ID, ROUND_ID, DEST_NO, STATUS, CHECKPOINT_SCN, CHECKPOINT_SCN_DISPLAY, PATH FROM oceanbase.DBA_OB_ARCHIVELOG;
        ```

        Oracle mode:

        ```shell
        obclient> SELECT DEST_ID, ROUND_ID, DEST_NO, STATUS, CHECKPOINT_SCN, CHECKPOINT_SCN_DISPLAY, PATH FROM SYS.DBA_OB_ARCHIVELOG;
        ```

        An example of the MySQL mode query result is as follows:

        ```shell
        +---------+----------+---------+--------+---------------------+----------------------------+---------------------------------------+
        | DEST_ID | ROUND_ID | DEST_NO | STATUS | CHECKPOINT_SCN      | CHECKPOINT_SCN_DISPLAY     | PATH                                 -|
        +---------+----------+---------+--------+---------------------+----------------------------+---------------------------------------+
        |    1001 |        1 |       0 | DOING  | 1680265982125159110 | 2023-03-31 20:33:02.125159 | file:///data/1/standby2_archive2      -|
        +---------+----------+---------+--------+---------------------+----------------------------+---------------------------------------+
        1 row in set
        ```

      The query result shows that the `STATUS` value is `DOING`, indicating that archiving is working properly. The `CHECKPOINT_SCN` and `CHECKPOINT_SCN_DISPLAY` parameters indicate the current archiving progress.

      For more information about how to view the archiving state, see [View the archiving progress](../../../600.backup-and-recovery/300.log-archive/600.view-log-archive-progress.md).

2. Switch the primary tenant to a standby tenant.

   1. Log in to the database as a tenant administrator of the primary tenant or the `sys` tenant of the cluster in which the primary tenant is located.

   2. Execute the `SWITCHOVER TO STANDBY VERIFY` statement to check whether the `SWITCHOVER` statement can be executed successfully.

      * In the `sys` tenant of the cluster in which the primary tenant is located, execute the `SWITCHOVER TO STANDBY VERIFY` statement.

        ```sql
        ALTER SYSTEM SWITCHOVER TO STANDBY TENANT [=] tenant_name VERIFY;
        ```

        Example:

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY TENANT = mysql2 VERIFY;
        ```

      * In the primary tenant, execute the `SWITCHOVER TO STANDBY VERIFY` statement.

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY VERIFY;
        ```

        If the statement returns `OK`, the verification passes. You can then proceed to the next step.

        If an error occurs, follow the instructions in the error message to handle the error. For more information, see [Switchover or failover failed](../../../1000.troubleshooting/800.physical-standby-database/200.switchover-failed.md).

   3. After the verification passes, execute the primary-to-standby switchover statement to switch the primary tenant to a standby tenant.

      * In the `sys` tenant of the cluster in which the primary tenant is located, switch the primary tenant to a standby tenant.

        ```sql
        ALTER SYSTEM SWITCHOVER TO STANDBY TENANT = tenant_name;
        ```

        Example:

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY TENANT = mysql2;
        ```

      * In the primary tenant, switch the tenant to a standby tenant.

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO STANDBY;
        ```

   4. Query the `DBA_OB_TENANTS` view to confirm whether the primary tenant has been switched to a standby tenant.

      * In the `sys` tenant of the cluster in which the primary tenant is located, query the view.

        ```shell
        obclient> SELECT TENANT_ID, TENANT_NAME,TENANT_TYPE,TENANT_ROLE,SWITCHOVER_STATUS 
        FROM oceanbase.DBA_OB_TENANTS 
        WHERE TENANT_NAME='mysql2';
        ```

      * In the primary tenant, query the view.

        MySQL mode:

        ```shell
        obclient> SELECT TENANT_ID, TENANT_NAME,TENANT_TYPE,TENANT_ROLE,SWITCHOVER_STATUS 
        FROM oceanbase.DBA_OB_TENANTS 
        WHERE TENANT_NAME='mysql2';
        ```

        Oracle mode:

        ```shell
        obclient> SELECT TENANT_ID, TENANT_NAME,TENANT_TYPE,TENANT_ROLE,SWITCHOVER_STATUS 
        FROM SYS.DBA_OB_TENANTS 
        WHERE TENANT_NAME='mysql2';
        ```

       An example of the query result is as follows:

       ```shell
       +-----------+-------------+-------------+-------------+-------------------+
       | TENANT_ID | TENANT_NAME | TENANT_TYPE | TENANT_ROLE | SWITCHOVER_STATUS |
       +-----------+-------------+-------------+-------------+-------------------+
       |      1004 | mysql2      | USER        | STANDBY     | NORMAL            |
       +-----------+-------------+-------------+-------------+-------------------+
       1 row in set
       ```

      As shown in the query result, the `TENANT_ROLE` of the primary tenant has changed to `STANDBY`, and the `SWITCHOVER_STATUS` has changed to `NORMAL`, indicating that the primary-to-standby switchover was successful.

   5. Query the `SYNCHRONIZED` field in the `V$OB_ARCHIVE_DEST_STATUS` view and wait for the primary tenant to complete archiving.

      In a physical standby tenant scenario based on log archiving, the standby tenant must read all logs from the original primary tenant's log archive before it can be switched to the primary tenant. Since log archiving is in asynchronous mode, after the original primary tenant is switched to a standby tenant, you need to check whether the log archive on the original primary tenant is complete.

      * MySQL mode

        ```shell
        obclient> SELECT * FROM oceanbase.V$OB_ARCHIVE_DEST_STATUS WHERE TENANT_ID = 1004;
        ```

      * Oracle mode

        ```shell
        obclient> SELECT * FROM SYS.V$OB_ARCHIVE_DEST_STATUS WHERE TENANT_ID = 1004;
        ```

      The query result in MySQL mode is as follows:

      ```shell
      +-----------+---------+--------------------------------+--------+---------------------+--------------+---------+
      | TENANT_ID | DEST_ID | PATH                           | STATUS | CHECKPOINT_SCN      | SYNCHRONIZED | COMMENT |
      +-----------+---------+--------------------------------+--------+---------------------+--------------+---------+
      |      1004 |    1001 | file:///data/1/sh_archive      | DOING  | 1684638569520797277 | YES          |         |
      +-----------+---------+--------------------------------+--------+---------------------+--------------+---------+
      1 row in set
      ```

      If the `SYNCHRONIZED` field shows `YES`, it indicates that the primary tenant has completed archiving.

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>Before you execute the standby-to-primary switchover, make sure that the <code>SYNCHRONIZED</code> field shows <code>YES</code>. Otherwise, the data of the new primary tenant after the switchover may be incomplete. </p>
      </main>

3. Switch the standby tenant to the primary tenant.

   1. Log in to the database as the tenant administrator of the `sys` tenant in the standby tenant or the standby tenant's cluster.

   2. Execute the standby-to-primary switchover command to switch the standby tenant to the primary tenant.

      <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>Before the standby-to-primary switchover command is executed, the system checks whether the standby tenant has synchronized all logs to the restore source. Therefore, the execution time of the standby-to-primary switchover command depends on the synchronization progress between the standby tenant and the primary tenant. </p>
      </main>

      * The `sys` tenant in the standby tenant's cluster switches the standby tenant to the primary tenant.

        ```sql
        ALTER SYSTEM SWITCHOVER TO PRIMARY TENANT = tenant_name;
        ```

        Example:

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO PRIMARY TENANT = standby2;
        ```

      * The standby tenant switches itself to the primary tenant.

        ```shell
        obclient> ALTER SYSTEM SWITCHOVER TO PRIMARY;
        ```

   3. Query the `DBA_OB_TENANTS` view to confirm whether the standby tenant has been switched to the primary tenant.

      * The `sys` tenant in the standby tenant's cluster queries the view.

        ```shell
        obclient> SELECT TENANT_ID, TENANT_NAME,TENANT_TYPE,TENANT_ROLE,SWITCHOVER_STATUS 
        FROM oceanbase.DBA_OB_TENANTS 
        WHERE TENANT_NAME='standby2';
        ```

      * The primary tenant queries the view.

        MySQL mode:

        ```shell
        obclient> SELECT TENANT_ID, TENANT_NAME,TENANT_TYPE,TENANT_ROLE,SWITCHOVER_STATUS 
        FROM oceanbase.DBA_OB_TENANTS 
        WHERE TENANT_NAME='standby2'';
        ```

        Oracle mode:

        ```shell
        obclient> SELECT TENANT_ID, TENANT_NAME,TENANT_TYPE,TENANT_ROLE,SWITCHOVER_STATUS 
        FROM SYS.DBA_OB_TENANTS 
        WHERE TENANT_NAME='standby2'';
        ```

      The query result is as follows:

      ```shell
      +-----------+----------------------------+-------------+-------------+-------------------+
      | TENANT_ID | TENANT_NAME                | TENANT_TYPE | TENANT_ROLE | SWITCHOVER_STATUS |
      +-----------+----------------------------+-------------+-------------+-------------------+
      |      1006 | standby2                   | USER        | PRIMARY     | NORMAL            |
      +-----------+----------------------------+-------------+-------------+-------------------+
      1 row in set
      ```

      If the `TENANT_ROLE` of the standby tenant has changed to `PRIMARY`, and the `SWITCHOVER_STATUS` is `NORMAL`, the standby-to-primary switchover is successful.

4. Set the restore source for the new standby tenant (original primary tenant) to receive the archive logs from the new primary tenant.

   If the original primary tenant did not set a log restore source before the switchover, the log synchronization point will remain at the time of the switchover. Therefore, you need to set a log restore source for the original primary tenant, pointing to the new primary tenant.

   You can set the log restore source before or after the primary-to-standby switchover.

   1. Log in to the database as the tenant administrator of the `sys` tenant in the new standby tenant or the new standby tenant's cluster.

   2. Execute the following command to configure the restore source for the new standby tenant (original primary tenant).

      * The `sys` tenant in the new standby tenant's cluster sets the restore source for the new standby tenant.

        ```sql
        ALTER SYSTEM SET LOG_RESTORE_SOURCE ='LOCATION=archive_path' TENANT = tenant_name;
        ```

      * The new standby tenant sets its own restore source.

        ```sql
        ALTER SYSTEM SET LOG_RESTORE_SOURCE ='LOCATION=archive_path';
        ```

      The `LOCATION` attribute specifies the archive destination of the new primary tenant.

      Example:

      ```shell
      obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE ='LOCATION=file:///data/1/standby2/archive2' TENANT = mysql2;

      obclient> ALTER SYSTEM SET LOG_RESTORE_SOURCE ='LOCATION=file:///data/1/standby2/archive2';
      ```

   3. After the restore source is set, query the `DBA_OB_TENANTS` view to confirm whether the original primary tenant is in continuous log synchronization mode.

      After the primary tenant is switched to a standby tenant, continuous log synchronization is automatically enabled. Therefore, no special processing is required. You can query the `DBA_OB_TENANTS` view to confirm.

      * The `sys` tenant in the original primary tenant's cluster queries the view.

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS, SCN_TO_TIMESTAMP(SYNC_SCN), RECOVERY_UNTIL_SCN FROM oceanbase.DBA_OB_TENANTS;
        ```

      * The original primary tenant queries the view.

        MySQL mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS, SCN_TO_TIMESTAMP(SYNC_SCN), RECOVERY_UNTIL_SCN FROM oceanbase.DBA_OB_TENANTS;
        ```

        Oracle mode:

        ```shell
        obclient> SELECT TENANT_NAME, TENANT_TYPE, TENANT_ROLE, SWITCHOVER_STATUS, SCN_TO_TIMESTAMP(SYNC_SCN), RECOVERY_UNTIL_SCN FROM SYS.DBA_OB_TENANTS;
        ```
