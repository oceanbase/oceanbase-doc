# Enable security audit

This topic describes how to enable the audit feature and set the storage location for audit records.

In OceanBase Database, audit-related operations are generally performed by the built-in `ORAAUDITOR` user. The password and privileges of this user are specified by the `SYS` user.

## Procedure

1. Log in to the Oracle-compatible tenant as the `SYS` user and unlock the `ORAAUDITOR` user.

   ```shell
   obclient> ALTER USER ORAAUDITOR ACCOUNT UNLOCK;
   ```

   <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>The <code>ORAAUDITOR</code> user is created by default in OceanBase Database. This user is locked by default and must be enabled before you can use audit.</p>
   </main>

2. Change the login password of the `ORAAUDITOR` user.

   For security reasons, the login password of the `ORAAUDITOR` user must be specified by the `SYS` user. If you need to change this password later, you can specify a new one.

   ```shell
   obclient> ALTER USER ORAAUDITOR IDENTIFIED BY ******;
   ```

3. Grant privileges to the `ORAAUDITOR` user.

   The `ORAAUDITOR` user has no privileges by default. To perform security audit-related operations, you must grant the `CREATE SESSION` privilege to the `ORAAUDITOR` user using the `GRANT` statement. If you want to allow the `ORAAUDITOR` user to view audit records, you need to grant the `SELECT ANY DICTIONARY` privilege.

   ```shell
   obclient> GRANT CREATE SESSION, SELECT ANY DICTIONARY TO ORAAUDITOR;
   ```

4. Enable the audit feature and set the storage location for audit records.

   You can enable the audit feature by configuring the `audit_trail` parameter. The change takes effect immediately after the successful execution. The valid values of this parameter are as follows:

   * `NONE`: Disable audit. This is the default value.

   * `OS`: Write audit records to local disk files.

   * `DB`: Write audit records to internal tables.

   * `DB,EXTENDED / DB_EXTENDED`: Write audit records to internal tables and include the executed SQL statements in the records.

   Example:

   ```shell
   obclient> ALTER SYSTEM SET audit_trail = 'DB,EXTENDED';
   ```

   For more information about the `audit_trail` parameter, see [audit_trail](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/400.audit_trail.md).

   <main id="notice" type='explain'>
      <h4>Note</h4>
      <p>Audit records can be written to either internal tables or local disk files:</p>
      <ul>
      <li>Write to disk files: Records are written asynchronously to the <code><installation_directory>/audit/</code> directory, with the default file being <code>/home/admin/oceanbase/audit/observer_xx_xxxxxx.aud</code>.</li>
      <li>Write to internal tables: Audit information is directly written to system tables. The internal table <code>__all_tenant_security_audit_record</code> stores audit records; the internal tables <code>__all_virtual_audit_operation</code> or <code>__all_virtual_audit_action</code> store the mapping between audit-related <code>ID</code> and <code>Name</code>.</li>
      </ul>
   </main>

## Audit log encryption

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>The audit log encryption feature in Oracle-compatible mode is supported starting from V4.6.1.</p>
</main>

When an Oracle-compatible tenant writes audit records to disk files (`audit_trail` set to `LOG`), it supports storing archived logs in plaintext or encrypted format. Encryption is implemented using the `audit_log_encryption` parameter and the audit functions `AUDIT_LOG_ENCRYPTION_PASSWORD_SET()` and `AUDIT_LOG_ENCRYPTION_PASSWORD_GET()`. For specific steps, see the configuration documentation at the end of this topic.
