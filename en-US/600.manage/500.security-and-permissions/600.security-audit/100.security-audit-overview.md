# Security audit overview

Data encryption and access control can significantly reduce security risks. However, it is still necessary to record the actions of users with privileges to prevent login information leaks or the abuse of access permissions. The audit feature strengthens an enterprise’s ability to meet data security and compliance requirements, and is the primary tool for tracking user activities.

<main id="notice" >
  <h4>Applicability</h4>
  <p>This content applies only to OceanBase Database Enterprise Edition. The audit feature is not supported in OceanBase Database Community Edition </p>
</main>

## Audit in MySQL-compatible mode

You can specify the types of requests to be audited by using filters, such as login/logout requests, DML statements, and CMD statements. The requests are recorded in audit files on the local disk or in Alibaba Cloud OSS, and the records are rotated, cleaned, and compressed according to specified policies.

### Overview

In MySQL-compatible mode of OceanBase Database, the database audit feature audits specific events by using a series of filters. Filters can screen events based on dimensions such as account, event type, and event attributes, and determine whether to audit the filtered events. After configuring filters, you must apply them to users for the filters to take effect. The relationship between filters and users is one-to-many: one filter can be applied to multiple users, but each user can have only one filter. You can also set a default filter, which applies to all users who do not have a filter specified.

### Procedure

The audit procedure in MySQL-compatible mode consists of the following steps: enabling security audit, setting and viewing audit rules, viewing audit records, and disabling security audit. When enabling security audit, you need to specify the audit scope and note any usage restrictions, then create and configure filters for data filtering. Setting and viewing audit rules involves specifying log policies, formats, data masking, output paths, archiving, cleaning, and compression. Audit records can be viewed through logs. When disabling security audit, you must clear filter configurations and delete filters.

## Audit in Oracle-compatible mode

Auditing is performed on a tenant basis by an auditor with the `ORAAUDITOR` role. It records SQL statements that conform to Oracle standards and data object operations, saving the audit results to disk files or database tables. Unified auditing and deletion of audit data are not supported.

### Overview

* Auditing is conducted on a tenant basis. An audit initiated by Tenant A applies only to operations performed by users within Tenant A and does not affect users in other tenants.

* Only the `ORAAUDITOR` role can perform audit operations, which meets the requirements for separation of duties.

* The audit content and syntax are consistent with standard Oracle auditing, except that unified auditing is not supported.

* Audit results can be saved to disk files or database tables.

* Both SQL statements and data object operations are supported for auditing.

* Deletion of audit data is not supported.

### Procedure

Audit checks are performed after a user SQL statement has finished executing and before the response packet is prepared. The audit check procedure is as follows:

1. Determine whether auditing applies to the current user based on tenant, username, and configuration settings.

2. Parse the SQL statement to identify all auditable operations. A single SQL statement may contain multiple different operations. For example, in the statement `insert into t1 select * from t2, t3`, the operations are `(insert, t1)`, `(select, t2)`, and `(select, t3)`.

3. For each operation, check whether it matches any audit rule.

4. Each operation that matches an audit rule generates a separate audit record. Depending on configuration settings, audit records can be stored in internal tables or files.
