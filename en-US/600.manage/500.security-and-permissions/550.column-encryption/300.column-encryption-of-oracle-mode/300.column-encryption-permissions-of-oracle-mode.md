# Column encryption privilege management

After you configure column encryption rules, proper privilege management is crucial for data security. This topic provides a detailed overview of the privilege system and management syntax for column encryption in OceanBase Database, helping you establish a robust privilege control mechanism to ensure that sensitive data is only accessible to authorized users.

## Prerequisites

Before you use the sensitive rule, you must enable TDE encryption and create a master key:

```sql
-- Set the TDE method to internal or obcloud.
ALTER SYSTEM SET tde_method = '<encryption_method>';
ALTER INSTANCE ROTATE INNODB MASTER KEY;	-- The first execution of this statement takes about 20 seconds for the key to take effect.
```

For more information about the `tde_method` parameter, see [tde_method](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7800.tde_method.md).

## Privilege types

The column encryption feature uses a rule-based privilege model to control user access to sensitive columns through data protection rules. OceanBase Database adds dedicated privilege types in the Oracle authorization model to support column encryption, including system privileges and sensitive rule-level privileges.
    
### System privileges

| Privilege name | Description | Default owner | Upgrade processing | Privilege limitations | Scope | Inclusion relationship |
|---------|------|-----------|----------|----------|----------|----------|
| CREATE SENSITIVE RULE | Allows users to create and drop sensitive rules. | SYS user. | Automatically granted when the database is upgraded. | This privilege cannot be revoked from the `SYS` user. | You can use the `CREATE SENSITIVE RULE` and `DROP SENSITIVE RULE` statements. | Included in `ALL PRIVILEGES`. |
| PLAINACCESS | Grants access to all plain text data, not subject to data protection rules. | SYS user. | Automatically granted during system upgrades. | The `PLAINACCESS` privilege cannot be revoked from the SYS user. | Access to all plain text data not subject to any data protection rules. | **Not included** in `ALL PRIVILEGES`. |

### Rule-level privileges

| Privilege name | Description | Scope | Granted automatically |
|---------|------|----------|----------|
| PLAINACCESS | Allows a user to access plain-text data of the columns associated with the specified rule. | A user that has the `PLAINACCESS` privilege for the rule can access the plain-text data of the columns associated with the rule. | The user who creates the rule will **not** automatically have the `PLAINACCESS` privilege for the rule. |

## Privilege management

### Granting privileges

:::tab

tab Grant system privileges

The syntax is as follows:

```sql
-- Grants the CREATE SENSITIVE RULE privilege to a user or role. This privilege is only at the system level.
GRANT CREATE SENSITIVE RULE TO <user_or_role_list>;

-- Grants the PLAINACCESS privilege at the system level to a user or role.
GRANT PLAINACCESS ANY SENSITIVE RULE TO  <user_or_role_list>;
```

The parameters are described as follows:

| Parameter | Description | Example |
|------|------|------|
| `user_or_role_list` | A list of users or roles, separated by commas. | `u1, u2, r1` |

Here are some examples:

```sql
-- Grants the CREATE SENSITIVE RULE privilege at the system level to user u1.
GRANT CREATE SENSITIVE RULE TO u1;

-- You can grant privileges to multiple users or roles at a time.
-- Grants the CREATE SENSITIVE RULE privilege at the system level to user u2 and role r1.
GRANT CREATE SENSITIVE RULE TO u2, r1;
```

tab Grant rule-level privileges

The syntax is as follows:

```sql
-- Grants rule-level privileges. Note that you must use the SENSITIVE RULE keyword.
GRANT PLAINACCESS ON SENSITIVE RULE <rule_name> TO <user_or_role_list>;
```

The parameters are described as follows:

| Parameter | Description | Example |
|------|------|------|
| `rule_name` | The name of the sensitive rule. | `'salary_encryption'`, `'credit_card_rule'`
| `user_or_role_list` | A list of users or roles, separated by commas. | `u1, u2, r1` |

Here are some examples:

```sql
-- Grants the PLAINACCESS privilege at the system level to user u1. You can also grant the privilege to multiple users or roles at a time.
GRANT PLAINACCESS ANY SENSITIVE RULE TO u1;

-- Grants the PLAINACCESS privilege to user u1 for rule r1.
-- You can also grant the privilege to multiple users or roles at a time. However, you can only grant the privilege for one rule at a time.
GRANT PLAINACCESS ON SENSITIVE RULE r1 TO u1;
```

:::

Note that you cannot grant the `PLAINACCESS` privilege at the table or column level. Using the following syntax will result in an error:

```sql
-- Incorrect example
GRANT PLAINACCESS ON <database>.<table> (<col_list>) TO <user_or_role_list>;
```

### Revoking privileges

:::tab

tab Revoke system privileges

The syntax is as follows:

```sql
-- Revokes the CREATE SENSITIVE RULE privilege from a user or role. This privilege is only at the system level.
REVOKE CREATE SENSITIVE RULE FROM <user_or_role_list>;

-- Revokes the PLAINACCESS privilege at the system level from a user or role.
REVOKE PLAINACCESS ANY SENSITIVE RULE FROM <user_or_role_list>;
```

The parameters are described as follows:

| Parameter | Description | Example |
|------|------|------|
| `user_or_role_list` | A list of users or roles, separated by commas. | `u1, u2, r1` |

Here are some examples:

```sql
-- Revokes the CREATE SENSITIVE RULE privilege from user u1.
REVOKE CREATE SENSITIVE RULE FROM u1;

-- You can revoke privileges from multiple users or roles at a time.
-- Revokes the CREATE SENSITIVE RULE privilege from user u2 and role r1.
REVOKE CREATE SENSITIVE RULE FROM u2, r1;
```

tab Revoke rule-level privileges

The syntax is as follows:

```sql
-- Revokes rule-level privileges. Note that you must use the SENSITIVE RULE keyword.
REVOKE PLAINACCESS ON SENSITIVE RULE <rule_name> FROM <user_or_role_list>;
```

The parameters are described as follows:

| Parameter | Description | Example |
|------|------|------|
| `rule_name` | The name of the sensitive rule. | `'salary_encryption'`, `'credit_card_rule'` |
| `user_or_role_list` | A list of users or roles, separated by commas. | `u1, u2, r1` |

Here are some examples:

```sql
-- Revokes the PLAINACCESS privilege at the system level from user u1. You can also revoke the privilege from multiple users or roles at a time.
REVOKE PLAINACCESS ANY SENSITIVE RULE FROM u1;

-- Revokes the PLAINACCESS privilege from user u1 for rule r1.
-- You can also revoke the privilege from multiple users or roles at a time. However, you can only revoke the privilege for one rule at a time.
REVOKE PLAINACCESS ON SENSITIVE RULE r1 FROM u1;
```

:::

Note that you cannot revoke the `PLAINACCESS` privilege at the table or column level. Using the following syntax will result in an error:

```sql
-- Incorrect example
REVOKE PLAINACCESS ON <database>.<table> (<col_list>) FROM <user_or_role_list>;
```

### View privileges

:::tab

tab View sensitive rules

You can view all sensitive data protection rules in the current tenant or all sensitive rules associated with a specified table or user. You can use the `LIKE` clause to filter the rule names.

Syntax:

```sql
SHOW SENSITIVE RULES opt_show_condition
| SHOW SENSITIVE RULES from_or_in relation_factor from_or_in USER user_factor opt_show_condition
| SHOW SENSITIVE RULES from_or_in USER user_factor opt_show_condition;
```

Parameters:

| Parameter | Description | Example |
|------|------|------|
| `opt_show_condition` | Optional display condition, such as the `LIKE` clause. | `LIKE '%rule1%'` |
| `from_or_in` | Optional FROM clause. | `FROM` or `IN` |
| `relation_factor` | Table name. | `tb1`, `employees` |
| `user_factor` | Username. | `u1`, `u2` |

Examples:

```sql
-- View all sensitive rules in the current tenant.
SHOW SENSITIVE RULES;

-- View all data protection rules associated with tb1.
SHOW SENSITIVE RULES FROM tb1;

-- View all data protection rules associated with u1.tb1.
SHOW SENSITIVE RULES FROM tb1 FROM u1;

-- View all data protection rules associated with u1.
SHOW SENSITIVE RULES FROM USER u1;

-- Filter rule names using the LIKE clause.
SHOW SENSITIVE RULES LIKE '%rule1%';
SHOW SENSITIVE RULES FROM tb1 LIKE '%rule1%';
SHOW SENSITIVE RULES FROM tb1 FROM u1 LIKE '%rule1%';
SHOW SENSITIVE RULES FROM USER u1 LIKE '%rule1%';
```

The returned result is as follows:

| Column | rule_id | rule_name | POLICY | METHOD | ENABLED | PROTECT_COLS |
| --- | --- | --- | --- | --- | --- | --- |
| Example | 1 | 'ENCRYPT_COL' | 'ENCRYPTION' | 'AES-256-ECB' | 'YES' | 'user1.tbl1(col_1, col_2), user2.tbl2(col_3), user3.tbl4(col_4, col_5)' |

Field description:

| Field | Description | Example value |
|--------|------|--------|
| `rule_id` | The rule ID, which is automatically generated by the system. | `1`, `2` |
| `rule_name` | The rule name. | `'ENCRYPT_COL'` |
| `POLICY` | The policy type. | `'ENCRYPTION'` |
| `METHOD` | The encryption method. | `'AES-256-ECB'` |
| `ENABLED` | Indicates whether the rule is enabled. | `'YES'`, `'NO'` |
| `PROTECT_COLS` | The protected columns, in the `user.table(columns)` format. | `'user1.tbl1(col_1, col_2)'`. Columns of different tables are separated with commas. |

tab View privilege information

In Oracle-compatible mode, you cannot use the `SHOW GRANTS` statement to view related privilege information. Instead, you can view the following views:

| View | Description |
|--------|------|
| [DBA_OB_SENSITIVE_RULE_PLAINACCESS_USERS](../../../../700.reference/700.system-views/500.system-view-of-oracle-mode/200.dictionary-view-of-oracle-mode/14131.dba_ob_sensitive_rule_plainaccess_users-of-oracle-mode.md) | Views all users with plain access privileges. |
| `ALL_OBJECTS`, `DBA_OBJECTS`, and `USER_OBJECTS` | Views the protected objects of sensitive rules. |
| `DBA_TAB_PRIVS`, `DBA_SYS_PRIVS`, `ALL_TAB_PRIVS`, `USER_TAB_PRIVS`, and `ROLE_TAB_PRIVS` | Views the granted rule-level plain access (PLAINACCESS) privileges. |
| `USER_SYS_PRIVS` and `ROLE_SYS_PRIVS` | Views the granted system-level create sensitive rule (CREATE SENSITIVE RULE) privileges and plain access (PLAINACCESS) privileges. |

:::
