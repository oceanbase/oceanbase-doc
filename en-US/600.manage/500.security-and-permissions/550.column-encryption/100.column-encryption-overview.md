# Overview of column encryption

This topic describes the column encryption feature provided by OceanBase Database and provides an example. This feature can be used to protect sensitive data stored in a database by returning encrypted data based on encryption rules when query results are returned. This feature is supported by MySQL and Oracle tenants.

<main id="notice" type='notice'>
  <h4>Applicability</h4>
  <p>OceanBase Database Community Edition does not support column encryption. </p>
</main>

## How it works

You can create column-level sensitive data rules for an existing table as a database administrator, or you must be granted the `CREATE SENSITIVE RULE` privilege at the user level. Assume that a column named A is specified as a protected column by a rule named R. If a user queries column A and does not have the privilege to access the plaintext data in column A on rule R, the database denies the user's query request.

* User has plaintext access to `R`: The projection expression containing the A column will correctly return plaintext results.

* A projection expression containing Column A returns the value of Column A encrypted in accordance with the described method.

## Data Protection Policies

You can create a sensitive rule by using the `CREATE SENSIVE RULE` syntax. Syntax is as follows:

```sql
CREATE SENSITIVE RULE <rule_name> 
ON <sensitive_field_list>
USING ENCRYPTION [ = <encryption_method>];
```

Here are some details:

* Data protection rules: Currently, only the `ENCRYPTION` type is supported for data protection rules. You can specify the encryption algorithm when you create a rule.
* Scope of the rule: Each rule can specify the protection of one or more columns across different databases and tables. A column can be protected by at most one data protection rule.
* Privileges required: The user who creates a rule must have both the `CREATE SENSITIVE RULE` privilege at the user level and the full access privilege on the specified columns (including the `SELECT`, `INSERT`, `UPDATE`, and `REFERENCE` privileges). **The user who creates the rule does not automatically inherit the plaintext access privilege for the rule; it must be separately authorized.**

## Access control mechanism

* User-level plaintext access: A user with user-level plaintext access can access plaintext data and will not be affected by data protection rules.
* Explicit access on a rule level: If a user has explicit access to a rule, this rule does not affect this user. The user can explicitly access data protected by this rule.
* Users without privileges: If a user doesn't have row-level privileges for a column or a rule, they can't access the encrypted data under the column protected by the rule.

## Differences with Function Encryption

The [ENHANCED_AES_ENCRYPT](../../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/400.functions-of-mysql-mode/500.encryption-and-compression-functions-of-mysql-mode/820.enhanced-aes-encrypt-of-mysql-mode.md) function is an AES encryption function in OceanBase Database.

| Feature | Column encryption | `ENHANCED_AES_ENCRYPT` function |
|------|------------|---------------------------|
| Usage | Configure rules through DDL | Manually invoke in SQL statements |
| Access control | Fine-grained rule-based access | Requires ENCRYPT privileges |
| Query experience | Automatically returns plain or encrypted text based on permissions | Always returns encrypted text, requires manual decryption |
| Index support | Encrypted column indexes | Supported but require special handling |
| Application compatibility | Fully compatible with existing applications | Requires modification of application code |
