# Create an index

This topic describes how to create an index by using SQL statements. It also provides the prerequisites, index overview, limitations, and recommendations for creating an index, and provides some examples.

For information about other methods of creating an index, see <a href="../../../700.reference/500.sql-reference/100.sql-syntax/300.common-tenant-of-oracle-mode/900.sql-statement-of-oracle-mode/100.ddl-of-oracle-mode/2400.create-table-of-oracle-mode.md">CREATE TABLE</a> or <a href="../../../700.reference/500.sql-reference/100.sql-syntax/300.common-tenant-of-oracle-mode/900.sql-statement-of-oracle-mode/100.ddl-of-oracle-mode/1000.alter-table-of-oracle-mode.md">ALTER TABLE</a> statement.</p>

## Overview

An index is also called a secondary index. It is an optional table structure. OceanBase Database uses a clustered index table model. For the primary key specified by users, the system automatically generates a primary key index. For other indexes created by users, they are secondary indexes. You can decide based on your business needs which fields to create indexes on to accelerate queries on those fields.

For more information about indexes in OceanBase Database, see [Overview](../../../700.reference/100.oceanbase-database-concepts/400.database-objects/100.database-objects-of-oracle-mode/300.index-of-oracle-mode/100.the-index-overview-of-oracle-mode.md).

## Prerequisites

Before you create an index, make sure that the following conditions are met:

* You have deployed an OceanBase cluster and created an Oracle tenant. For more information about how to deploy an OceanBase cluster, see [Overview](../../../400.deploy/100.deploy-overview.md).

* You have connected to an Oracle tenant of OceanBase Database. For more information about how to connect to OceanBase Database, see [Overview](../100.connect-to-oceanbase-database-of-oracle-mode/100.connection-methods-overview-of-oracle-mode.md).

* You have created a table. For more information about how to create a table, see [Create a table](../300.database-object-planning-of-oracle-mode/200.create-table-of-oracle-mode-in-develop.md).

* You have the `INDEX` privilege and the `ALTER` privilege on the table to which you want to add an index. For more information about how to query the privileges of the current user, see [Query the privileges of the current user](../../../600.manage/500.security-and-permissions/300.access-control/200.user-and-permission/300.permission-of-oracle-mode/600.view-user-permissions-of-oracle-mode.md). If you do not have the required privileges, contact the administrator to grant you the privileges. For more information about how to grant privileges to a user, see [Grant privileges to a user directly](../../../600.manage/500.security-and-permissions/300.access-control/200.user-and-permission/300.permission-of-oracle-mode/200.authority-of-oracle-mode.md).

## Limitations on creating indexes

* In OceanBase Database, the name of an index must be unique within the schema.

* The length of the name of an index cannot exceed 128 bytes.

* An index can have multiple unique indexes, but the values of the columns must be unique.

* If you want to use a local unique index to constrain data uniqueness, the local unique index must contain the table partitioning key.

* Limitations on function indexes

    In Oracle mode of OceanBase Database, the expressions of some system functions are not supported as function indexes. For more information, see [System functions supported as function indexes](../../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/400.manage-indexes-of-oracle-mode/500.function-index-list-of-supported-functions-of-oracle-mode.md) and [System functions not supported as function indexes](../../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/400.manage-indexes-of-oracle-mode/600.function-index-list-of-not-supported-functions-of-oracle-mode.md).

## Index creation recommendations

* We recommend that you use an index name that can succinctly describe the columns and purpose of the index. For example, `idx_customer_name`. For more information about naming, see [Object naming conventions](../../../700.reference/400.database-design-specifications-and-practices/100.object-naming-conventions/100.overview-of-object-naming-conventions.md).

* If the partitioning rules and the number of partitions of a global index are the same as those of the primary table, we recommend that you create a local index.

* We recommend that you issue an SQL statement for index creation in parallel, and the number of concurrent SQL statements should not exceed the number of CPU cores specified in the tenant specification. For example, if the tenant specification specifies 4 CPU cores (4C), we recommend that you create no more than 4 indexes in parallel.

* Avoid creating too many indexes on tables that are frequently updated. Create indexes on fields that are frequently used for queries.

* We recommend that you do not create indexes on tables that contain a small amount of data. This is because the time required to query all data may be shorter than the time required to traverse the index, and the index may not improve performance.

* We recommend that you do not create indexes when the modification performance is much higher than the retrieval performance.

* To create an efficient index:

  * The index should contain all the columns required for queries. The more columns the index contains, the fewer rows need to be returned.

  * Always place the equality condition at the beginning.

  * Place the conditions that filter and sort large amounts of data at the beginning.

## Example

### Example 1: Create a unique index

If you want to ensure that the indexed column has no duplicate values, you can create a unique (`UNIQUE`) index.

Use the following SQL statement to create a table named `TEST_TBL1` and create a unique index based on the `col2` column for the table `TEST_TBL1`.

1. Create the `TEST_TBL1` table.

    ```sql
    CREATE TABLE TEST_TBL1(col1 NUMBER, col2 NUMBER, col3 VARCHAR2(50), PRIMARY KEY(col1));
    ```

2. Create a unique index named `IDX_TEST_TBL1_COL2` based on the `col2` column for the table `TEST_TBL1`.

    ```sql
    CREATE UNIQUE INDEX IDX_TEST_TBL1_COL2 ON TEST_TBL1(col2);
    ```

3. View the index information of the `TEST_TBL1` table.

    ```sql
    SELECT INDEX_NAME,INDEX_TYPE,TABLE_OWNER,TABLE_NAME,UNIQUENESS FROM user_indexes WHERE table_name='TEST_TBL1';
    ```

    The returned result is as follows:

    ```shell
    +---------------------------------+------------+-------------+------------+------------+
    | INDEX_NAME                      | INDEX_TYPE | TABLE_OWNER | TABLE_NAME | UNIQUENESS |
    +---------------------------------+------------+-------------+------------+------------+
    | TEST_TBL1_OBPK_1703316804944854 | NORMAL     | SYS         | TEST_TBL1  | UNIQUE     |
    | IDX_TEST_TBL1_COL2              | NORMAL     | SYS         | TEST_TBL1  | UNIQUE     |
    +---------------------------------+------------+-------------+------------+------------+
    2 rows in set
    ```

### Example 3: Create a local index

A local index is created on data of a single partition. Therefore, the index key values of a local index are in one-to-one correspondence with the data in the table. That is, a partition of a local index corresponds to a partition of the table, and they have the same partitioning rules. Therefore, for a local unique index, it can only ensure the uniqueness within a partition but not the global uniqueness of the table data. The keyword used to create a local index is `LOCAL`.

If you want to use a local unique index to enforce data uniqueness, the local unique index must include the table partitioning key.

Use the following SQL statement to create a partitioned table named `TBL3_F_RL` and create a local unique index based on the `col1` and `col2` columns for the table `TBL3_F_RL`.

1. Create a non-templated Range + List partitioned table named `TBL3_F_RL`.

    ```sql
    CREATE TABLE TBL3_F_RL(col1 NUMBER,col2 NUMBER)
      PARTITION BY RANGE(col1)
        SUBPARTITION BY LIST(col2)
      (PARTITION p0 VALUES LESS THAN(100)
        (SUBPARTITION sp0 VALUES(1,3),
         SUBPARTITION sp1 VALUES(4,6),
         SUBPARTITION sp2 VALUES(7,9)),
       PARTITION p1 VALUES LESS THAN(200)
        (SUBPARTITION sp3 VALUES(1,3),
         SUBPARTITION sp4 VALUES(4,6),
         SUBPARTITION sp5 VALUES(7,9))
       );
    ```

2. Create an index named `IDX_TBL3_F_RL_COL1_COL2` based on the `col1` and `col2` columns for the table `TBL3_F_RL`.

    ```sql
    CREATE UNIQUE INDEX IDX_TBL3_F_RL_COL1_COL2 ON TBL3_F_RL(col1,col2) LOCAL;
    ```

3. View the index information of the `TBL3_F_RL` table.

    ```sql
    SELECT INDEX_NAME,INDEX_TYPE,TABLE_OWNER,TABLE_NAME,UNIQUENESS FROM user_indexes WHERE table_name='TBL3_F_RL';
    ```

    The returned result is as follows:

    ```shell
    +-------------------------+------------+-------------+------------+------------+
    | INDEX_NAME              | INDEX_TYPE | TABLE_OWNER | TABLE_NAME | UNIQUENESS |
    +-------------------------+------------+-------------+------------+------------+
    | IDX_TBL3_F_RL_COL1_COL2 | NORMAL     | SYS         | TBL3_F_RL  | UNIQUE     |
    +-------------------------+------------+-------------+------------+------------+
    1 row in set
    ```

### Example 4: Create a global index

The keyword used to create a global index is `GLOBAL`. Compared with a local index, a global index has the following characteristics: the partitioning rules of a global index are independent of those of the table, and you can specify the partitioning rules and the number of partitions of a global index, which do not need to be consistent with those of the table.

* In Oracle mode of OceanBase Database, if you do not specify the index attribute keyword, the default index attribute is `GLOBAL`, which means that the created index is a global index and the index table has only one partition.

* The partitioning rules of a global index do not need to be consistent with those of the table.

* If the partitioning rules and the number of partitions of a global index are the same as those of the primary table, we recommend that you create a local index. This is because maintaining a global index is more expensive than maintaining a local index. In addition, a global index cannot ensure that the physical location of its partitions is the same as that of the primary table partitions, unless you specify that the global index and the primary table are in the same table group.

Use the following SQL statement to create a partitioned table named `TBL4_H` and create a global index based on the `col2` column for the table `TBL4_H`.

1. Create a hash-partitioned table named `TBL4_H`.

    ```sql
    CREATE TABLE TBL4_H(col1 NUMBER PRIMARY KEY,col2 NUMBER)
      PARTITION BY HASH(col1) PARTITIONS 5;
    ```

2. Create a global index named `IDX_TBL4_H_COL2` based on the `col2` column for the table `TBL4_H`. The index is a range-partitioned index.

    ```sql
    CREATE INDEX IDX_TBL4_H_COL2 ON TBL4_H(col2) GLOBAL
      PARTITION BY RANGE(col2)
       (PARTITION p0 VALUES LESS THAN(100),
        PARTITION p1 VALUES LESS THAN(200),
        PARTITION p2 VALUES LESS THAN(300)
       );
    ```

3. View the index information of the `TBL4_H` table.

    ```sql
    SELECT INDEX_NAME,INDEX_TYPE,TABLE_OWNER,TABLE_NAME,UNIQUENESS FROM user_indexes WHERE table_name='TBL4_H';
    ```

    The returned result is as follows:

    ```shell
    +------------------------------+------------+-------------+------------+------------+
    | INDEX_NAME                   | INDEX_TYPE | TABLE_OWNER | TABLE_NAME | UNIQUENESS |
    +------------------------------+------------+-------------+------------+------------+
    | TBL4_H_OBPK_1703321659273683 | NORMAL     | SYS         | TBL4_H     | UNIQUE     |
    | IDX_TBL4_H_COL2              | NORMAL     | SYS         | TBL4_H     | NONUNIQUE  |
    +------------------------------+------------+-------------+------------+------------+
    2 rows in set
    ```

### Example 5: Create a function index

An index built based on the values of one or more columns in a table is called a function index. A function index is an optimization technique. By using a function index, you can quickly locate the matching function value during a query, thus avoiding repeated calculations and improving query efficiency.

In OceanBase Database in Oracle mode, some system functions are not supported for use in function indexes. For more information, see [System functions supported for use in function indexes](../../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/400.manage-indexes-of-oracle-mode/500.function-index-list-of-supported-functions-of-oracle-mode.md) and [System functions not supported for use in function indexes](../../../700.reference/300.database-object-management/200.manage-object-of-oracle-mode/400.manage-indexes-of-oracle-mode/600.function-index-list-of-not-supported-functions-of-oracle-mode.md).

#### Session variable fixation mechanism

The session variable fixation mechanism in a function index ensures that the calculation semantics of the index are consistent when the index is created and used. This prevents incorrect results due to changes in the session environment, such as "index hit but incorrect result".

**Working principle**

When you create a function index, the system automatically analyzes the index expression to identify which session variables (such as `time_zone`, `nls_date_format`, and `nls_timestamp_format`) the expression depends on. It then saves the current values of these variables to the index metadata.

When a query hits the function index:

1. The system retrieves the session variable snapshot saved when the index was created based on the `local_session_var_id` in the index expression.
2. During expression type inference and calculation, the saved variable values are used instead of the current session variable values.
3. The calculation results are ensured to be consistent with those when the index was created.

**Supported session variables**

The following session variables can be fixed in a function index:

| Variable | Description | Mode |
|--------|------|----------|
| `time_zone` | The time zone setting, which affects the results of time-related functions (such as SYSDATE and CURRENT_TIMESTAMP). | MySQL/Oracle |
| `sql_mode` | The SQL mode, which affects SQL syntax parsing and execution behavior. | MySQL |
| `nls_date_format` | The date format in Oracle mode. | Oracle |
| `nls_timestamp_format` | The timestamp format in Oracle mode. | Oracle |
| `nls_timestamp_tz_format` | The timestamp with time zone format in Oracle mode. | Oracle |
| `collation_connection` | The character set collation for the connection, which affects string comparisons and function results. | MySQL |
| `max_allowed_packet` | The maximum allowed data packet size. | MySQL |
| `ob_compatibility_version` | The OceanBase compatibility version. | MySQL/Oracle |

The system dynamically infers the variables that need to be fixed based on the index expression. For example, if the index expression contains time-related functions such as `SYSDATE` or `CURRENT_TIMESTAMP`, the `time_zone` variable is fixed. If the expression contains date formatting functions, the corresponding NLS format variables are fixed. If the expression contains string functions, the `collation_connection` variable may be fixed.

**Considerations**

**Avoid using volatile expressions**

Although the system automatically fixes session variables, it is recommended to minimize the use of functions affected by the session in the index. Instead, use deterministic columns:

```sql
-- ❌ Not recommended (depends on time_zone)
CREATE INDEX idx_sysdate ON logs ((TRUNC(SYSDATE)));

-- ✅ Recommended (uses a deterministic column)
CREATE INDEX idx_log_date ON logs ((TRUNC(log_time)));
```

**No need to manually manage session variables**

The system automatically handles session variable consistency. You do not need to worry about changes in the current session variables affecting the correctness of existing function indexes. During queries, the system automatically uses the variable snapshots saved when the indexes were created.

Use the following SQL statements to create a table named `TEST_TBL5` and create a function index on the `id` column of the `TEST_TBL5` table.

1. Create the `TEST_TBL5` table.

    ```sql
    CREATE TABLE TEST_TBL5(id NUMBER, name VARCHAR2(18));
    ```

2. Create a function index named `IDX_TEST_TBL5_ID` on the `id` column of the `TEST_TBL5` table.

    ```sql
    CREATE INDEX IDX_TEST_TBL5_ID ON TEST_TBL5 ((id+1));
    ```

3. Use the following SQL statement to view the created function index.

    ```sql
    SELECT INDEX_NAME,INDEX_TYPE,TABLE_OWNER,TABLE_NAME,UNIQUENESS FROM user_indexes WHERE table_name='TEST_TBL5';
    ```

    The return result is as follows:

    ```shell
    +-----------------+-----------------------+-------------+------------+------------+
    | INDEX_NAME      | INDEX_TYPE            | TABLE_OWNER | TABLE_NAME | UNIQUENESS |
    +-----------------+-----------------------+-------------+------------+------------+
    | IDX_TEST_TBL5_ID | FUNCTION-BASED NORMAL | SYS         | TEST_TBL5  | NONUNIQUE  |
    +-----------------+-----------------------+-------------+------------+------------+
    1 row in set
    ```

### Example 6: Create a spatial index

A spatial index is a database index used for processing and optimizing spatial data. It is widely used in geographic information systems (GIS) and for storing and querying location data. The syntax for creating a spatial index in OceanBase Database is different from that in Oracle. The SRID of a spatial index column is specified when the table is created.

Consider the following notes when you create a spatial index:

* Before you use GIS features, you must configure GIS meta data for the business tenant. For more information, see [Preparations](../../../700.reference/500.sql-reference/100.sql-syntax/300.common-tenant-of-oracle-mode/300.basic-elements-of-oracle-mode/100.built-in-data-types-of-oracle-mode/1200.spatial-data-type-of-oracle-mode/400.create-spatial-indexes-of-oracle-mode.md).
* For information about how to create a spatial index constraint on a partitioned table, see [Constraints](../../../700.reference/500.sql-reference/100.sql-syntax/300.common-tenant-of-oracle-mode/300.basic-elements-of-oracle-mode/100.built-in-data-types-of-oracle-mode/1200.spatial-data-type-of-oracle-mode/400.create-spatial-indexes-of-oracle-mode.md).

1. Create a table named `TEST_TBL6`.

    ```shell
    obclient [test]> CREATE TABLE TEST_TBL6(id NUMBER PRIMARY KEY, name VARCHAR2(32), shape SDO_GEOMETRY SRID 4326);
    ```

2. Create a spatial index named `IDX_TBL6_G` on the `shape` column of the `TEST_TBL6` table.

    ```shell
    obclient [test]> CREATE INDEX IDX_TBL6_G ON TEST_TBL6(shape) INDEXTYPE IS MDSYS.SPATIAL_INDEX;
    ```

3. View the index information of the `TEST_TBL6` table.

    ```shell
    obclient [test]> SELECT INDEX_NAME,INDEX_TYPE,TABLE_OWNER,TABLE_NAME,UNIQUENESS FROM user_indexes WHERE table_name='TEST_TBL6';
    ```

    The return result is as follows:

    ```shell
    +---------------------------------+------------+-------------+------------+------------+
    | INDEX_NAME                      | INDEX_TYPE | TABLE_OWNER | TABLE_NAME | UNIQUENESS |
    +---------------------------------+------------+-------------+------------+------------+
    | TEST_TBL6_OBPK_1718852454772761 | NORMAL     | SYS         | TEST_TBL6  | UNIQUE     |
    | IDX_TBL6_G                      | DOMAIN     | SYS         | TEST_TBL6  | NONUNIQUE  |
    +---------------------------------+------------+-------------+------------+------------+
    2 rows in set
    ```

### Example 7: Create a columnstore index

After you create a table named `TEST_TBL7`, create a columnstore index named `IDX1_TBL7_CG`.

1. Create a table named `TEST_TBL7`.

   ```sql
   CREATE TABLE TEST_TBL7(id NUMBER, name VARCHAR2(20), age NUMBER);
   ```

2. Create a columnstore index named `IDX1_TBL7_CG` on the `TEST_TBL7` table and store redundant data of the `age` column in the index table.

   ```sql
   CREATE INDEX IDX1_TBL7_CG ON TEST_TBL7(name) STORING(age) WITH COLUMN GROUP(each column);
   ```

3. View the index information of the `TEST_TBL7` table.

    ```shell
    obclient [test]> SELECT INDEX_NAME,INDEX_TYPE,TABLE_OWNER,TABLE_NAME,UNIQUENESS FROM user_indexes WHERE table_name='TEST_TBL7';
    ```

    The return result is as follows:

    ```shell
    +--------------+------------+-------------+------------+------------+
    | INDEX_NAME   | INDEX_TYPE | TABLE_OWNER | TABLE_NAME | UNIQUENESS |
    +--------------+------------+-------------+------------+------------+
    | IDX1_TBL7_CG | NORMAL     | SYS         | TEST_TBL7  | NONUNIQUE  |
    +--------------+------------+-------------+------------+------------+
    1 row in set (0.026 sec)
    ```
