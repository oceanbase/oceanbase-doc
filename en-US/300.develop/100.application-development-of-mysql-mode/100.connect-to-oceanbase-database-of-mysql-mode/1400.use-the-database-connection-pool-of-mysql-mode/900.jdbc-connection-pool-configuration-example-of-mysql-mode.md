# JDBC configuration examples

This topic describes how to configure JDBC. JDBC is an API for Java database connections. OceanBase Database provides a JDBC driver that allows Java applications to connect to OceanBase Database. For more information about how to download the JDBC driver, see [OceanBase JDBC driver](https://en.oceanbase.com/softwarecenter-enterprise).

To achieve the best performance when you use JDBC to connect to a database, you need to configure some parameters. This topic describes some recommended configurations.

The following example shows how to connect to a database by using JDBC:

```java
conn=jdbc:oceanbase://xxx.xxx.xxx.xxx:2881/test?rewriteBatchedStatements=TRUE&allowMultiQueries=TRUE&useLocalSessionState=TRUE&useUnicode=TRUE&characterEncoding=utf-8&socketTimeout=10000&connectTimeout=30000
```

In this example, the following parameters are configured:

* `rewriteBatchedStatements`: Set this parameter to `TRUE`.

  * By default, the JDBC driver of OceanBase Database ignores the executeBatch() method and executes a group of SQL statements one by one. In this case, batch insertions are actually single insertions, which results in low performance. To execute batch insertions, set this parameter to `TRUE`. In this case, the driver executes SQL statements in batches. For example, you can use the addBatch() method to combine multiple insert statements on the same table into one insert statement with multiple values.

  * You must use the prepareStatement() method to prepare each insert statement, and then call the addBatch() method. Otherwise, the statements cannot be executed in batches.

* `allowMultiQueries`: Set this parameter to `TRUE`.

  The JDBC driver allows you to concatenate multiple SQL statements with semicolons (;) into one SQL statement and send it to the server.

* `useLocalSessionState`: Set this parameter to `TRUE` to avoid frequent queries of session variables in OceanBase Database.

  The session variables include autocommit, read_only, and transaction isolation.

* `socketTimeout`: The time that a socket waits for an SQL statement to return a result.

* `connectTimeout`: The time that a connection waits for a connection to be established.

* `useCursorFetch`: Set this parameter to `TRUE`.

  For a query statement that involves a large amount of data, the database server creates a cursor and distributes data to the client in batches based on the value of the fetchSize parameter. If you set this parameter to `TRUE`, the useServerPrepStmts parameter is automatically set to `TRUE`.

* `useServerPrepStmts`: Specifies whether to use the prepared statement protocol to send SQL statements to the database server.

  If you set this parameter to `TRUE`, the SQL statements are executed in two steps:

  * The SQL statements containing `?` are sent to the database server for preparation (`SQL_audit: request_type=5`).

  * The actual values are used to execute the SQL statements in the database (`SQL_audit: request_type=6`).

* `cachePrepStmts`: Specifies whether to enable the prepared statement cache in the JDBC driver to cache prepared statements and avoid repeated preparations on the client and server sides. If you set `cachePrepStmts=TRUE`, the driver avoids repeated preparations when you execute batch operations by using `useServerPrepStmts=TRUE` and the same SQL statement.

* `prepStmtCacheSQLLimit`: The maximum length of an SQL statement that can be cached in the prepared statement cache. If the length of an SQL statement exceeds this value, the statement cannot be cached. prepStmtCacheSize: The maximum number of SQL statements that can be cached in the prepared statement cache.

* `maxBatchTotalParamsNum`: The maximum number of parameters that can be supported by an SQL statement in a batch operation (that is, the maximum number of `?` symbols in the SQL statement). If the number of parameters exceeds this value, the batch SQL statement is split.
