# Vector indexes

This topic describes how OceanBase Database creates, queries, maintains, and drops vector indexes.

A vector index in OceanBase Database can be an HNSW index, an HNSW_SQ index, or an IVF index.

* HNSW index: An HNSW index supports dimensions up to 4,096. It is a memory-based index that must be fully loaded into memory. It supports DML operations and real-time queries.

* HNSW_SQ index: An HNSW_SQ index offers query performance, recall, and build speed similar to those of an HNSW index, but uses half to one-third of the memory. It is suitable for scenarios that require high performance and recall.

* (Experimental feature) IVF index: An IVF index is a database table-based index that does not occupy resident memory. It is suitable for scenarios with large data volumes, where performance is not a concern and costs need to be controlled.

* L2, inner product (IP), and cosine distance can be used as the distance metric for a vector index.

* Vector queries can be performed with filters. The filters can be scalar-type conditions or spatial conditions, such as ST_Intersects. Multi-valued indexes, full-text indexes, and global indexes cannot be used as prefetcher.

* You can create vector indexes and full-text indexes on the same table.

## Prerequisites

Before you use an HNSW or HNSW_SQ index, you must enable it by setting [ob_vector_memory_limit_percentage](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md). IVF, IVF_SQ, and IVF PQ indexes do not need to reside in memory, so you do not need to manually set this parameter to enable the vector feature.

```sql
ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
```

## Overview

A vector index query is an approximate nearest neighbor query and does not guarantee 100% accuracy. The recall rate measures the accuracy of vector query, which is the ratio of the number of correct results to the total number of results. For example, if an approximate nearest neighbor query can consistently return 9 correct results among 10, the recall rate is 90%. The recall rate is affected by the construction parameters and query parameters.

## Query parameters

Index query parameters are specified when the index is created and cannot be modified. However, session variables can be used to set the parameters for HNSW/HNSW_SQ indexes (`ob_hnsw_ef_search`) and IVF/IVF_SQ/IVF_PQ indexes (`ob_ivf_nprobes`). If a session variable is set, its value takes precedence. For more information, see [ob_hnsw_ef_search](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

The syntax is as follows:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num);
```

The notes are as follows:

* The query syntax has the following requirements:
  * The `APPROXIMATE`/`APPROX` keyword must be specified to select the vector index path.
  * The `ORDER BY` and `LIMIT` clauses must be included.
  * The `ORDER BY` clause supports only one vector condition.
  * The value range of `LIMIT + OFFSET` is `(0, 16384]`.

* The distance function selection rules are as follows:
  * If `APPROXIMATE`/`APPROX` is not specified, the query plan will not choose the vector index path, but an error is not returned when the `inner_product`, `negative_inner_product`, or `L2` distance function is called.
  * If `APPROXIMATE`/`APPROX` is specified, the distance function does not match that supported by the vector index algorithm. In this case, the query plan will not choose the vector index path, but an error is not returned.
  * If `APPROXIMATE`/`APPROX` is specified, the expression is `inner_product`. In this case, the query plan will not choose the vector index path.
  * If `APPROXIMATE`/`APPROX` is specified, the expression is `negative_inner_product` or `L2`, and it matches that supported by the vector index algorithm, the query plan will choose the vector index path.

* Other notes:
  * The `WHERE` condition is used as a filter condition after the vector index query.
  * The `LIMIT` clause is not specified, an error is returned.

## Index creation, query, and deletion examples

### Considerations

You can create a vector index when you create a table or create a table without an index and add the index later. Consider the following points when you create an index:

* Once a vector index is created, you cannot modify any parameters of the index.

* You must use the `VECTOR` keyword when you create a vector index.

* The parameters and description for creating an index are the same whether you create the index when you create a table or later.

* If a large amount of data is to be imported, we recommend that you import the data and then create an index to ensure the query performance.

* We recommend that you create an HNSW_SQ index, IVF index, IVF_SQ index, or IVF_PQ index after you write the data and rebuild the index after you write a substantial amount of incremental data. For more information, see the Examples section below.

#### HNSW_SQ index example

```sql
CREATE TABLE hgraph_vecindex_suite_table_test (c1 INT AUTO_INCREMENT, c2 VECTOR(3), PRIMARY KEY(c1), VECTOR INDEX idx1(c2) WITH (distance=l2, type=hnsw_sq, lib=vsag));
```

The parameters of an HNSW or HNSW_SQ index are described as follows:

| Parameter | Default value | Value range | Required | Description | Remarks |
|------|--------|----------|----------|------|------|
| distance |  | l2/inner_product/cosine | Yes | The type of the vector distance function. | l2 indicates the Euclidean distance, inner_product indicates the inner product distance, and cosine indicates the cosine distance. |
| type |  | hnsw | Yes | The type of the index. | Currently, only `hnsw` and `hnsw_sq8` are supported. |
| lib | vsag | vsag | No | The type of the vector index library. | Currently, only the VSAG vector library is supported. |
| m | 16 | [5,64] | No | The maximum number of neighbors for an HNSW index node. | The value indicates the trade-off between index construction speed and query performance. |
| ef_construction | 200 | [5,1000] | No | The size of the candidate set during index construction. It is an HNSW index parameter. | The value indicates the trade-off between index construction speed and index quality. `ef_construction` must be greater than `m`. |
| ef_search | 64 | [1,1000] | No | The size of the candidate set during query. It is an HNSW index parameter. | The value indicates the trade-off between query speed and recall rate. |

```sql

```

## Index maintenance

When a large amount of incremental data is generated, query performance will decrease. To reduce the volume of incremental data tables, OceanBase Database introduced the `DBMS_VECTOR` package for maintaining vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF_SQ/IVF_PQ indexes do not support incremental refreshes. </p>
</main>

If a large amount of data is written after the index is created, we recommend that you use an incremental refresh.

The syntax is as follows:

```shell
  PROCEDURE refresh_index(
    IN     idx_name               VARCHAR(65535),                 ---- Index name
    IN     table_name             VARCHAR(65535),                 ---- Table name
    IN     idx_vector_col         VARCHAR(65535) DEFAULT NULL,    ---- Vector column name
    IN     refresh_threshold      INT DEFAULT 10000,              ---- Number of incremental data records
    IN     refresh_type           VARCHAR(65535) DEFAULT NULL);   ---- FAST
```

An incremental refresh is initiated every 15 minutes. If more than 10,000 incremental data records are generated, an incremental refresh is automatically initiated.

### Complete refresh

If a large amount of data is updated or deleted after the index is created, we recommend that you use a complete refresh.

The syntax is as follows:

```shell
  PROCEDURE rebuild_index(
    IN     idx_name                VARCHAR(65535),                    ---- Index name
    IN     table_name              VARCHAR(65535),                    ---- Table name
    IN     idx_vector_col          VARCHAR(65535) DEFAULT NULL,       ---- Vector column name
    IN     delta_rate_threshold    FLOAT DEFAULT 0.2,                 ---- Proportion of incremental data
    IN     idx_organization        VARCHAR(65535) DEFAULT NULL,       ---- Index type
    IN     idx_distance_metrics    VARCHAR(65535) DEFAULT 'EUCLIDEAN',---- Distance type
    IN     idx_parameters          LONGTEXT DEFAULT NULL,             ---- Index parameters
    IN     idx_parallel_creation   INT DEFAULT 1);                    ---- Degree of parallelism for creating the index, reserved, only supported in the syntax
```

A complete refresh is initiated every 24 hours. If more than 20% of the original data is added, a complete refresh is automatically initiated. A complete refresh will clear the original index and rebuild a new index in the background. It is a time-consuming process.

Create a test table.

```sql

```

INSERT INTO vector_index_test VALUES(4, '[0.148869,0.878546,0.028024]');
INSERT INTO vector_index_test VALUES(5, '[0.334970,0.857377,0.886132]');
INSERT INTO vector_index_test VALUES(6, '[0.117582,0.302352,0.471198]');

```sql

call dbms_vector.rebuild_index('idx1','t1','c2');
```
