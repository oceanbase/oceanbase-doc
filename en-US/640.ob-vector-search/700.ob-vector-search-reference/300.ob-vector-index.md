# Vector indexes

This topic describes how OceanBase Database creates, queries, maintains, and drops vector indexes.

The features of OceanBase Database vector indexes are as follows:

* Support for HNSW indexes: The maximum dimension for index columns is 4096. HNSW is an in-memory index that must be fully loaded into memory. It supports DML operations and real-time queries.

* Support for HNSW SQ index: The HNSW SQ index offers similar build speed, query performance, and recall rate as the HNSW index but reduces total memory usage to 50–33% of the original. This makes it ideal for scenarios requiring high performance and recall rates.

* (Experimental feature) Support for IVF/IVF SQ/IVF PQ indexes: IVF indexes are implemented based on database tables and do not require memory residency, making them suitable for scenarios with large data volumes, lower performance requirements, and cost sensitivity. IVF SQ and IVF PQ indexes further reduce storage costs.

* Support for L2, Inner Product (IP), and Cosine Distance as distance algorithms for indexing.

* Support for vector queries with filtering conditions: Filtering conditions can include scalar-type conditions or spatial relationships, such as ST_Intersects. However, multi-value indexes, full-text indexes, and global indexes are not yet supported as pre-filters.

* Support for creating both vector indexes and full-text indexes on the same table.

## Prerequisites

Before using HNSW or HNSW SQ vector indexes, you need to enable the vector feature by configuring the parameter [ob_vector_memory_limit_percentage](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md). IVF, IVF SQ, and IVF PQ indexes do not need to be loaded into memory, so you do not need to manually set this parameter to enable the vector feature.

```sql
ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
```

## Overview of index queries

Vector index queries are a type of approximate nearest neighbor (ANN) query and do not guarantee 100% accuracy in the results. The accuracy of vector queries is measured by the recall rate. For example, when searching for the 10 nearest neighbors, if 9 correct results are consistently returned, the recall rate is 90%. The recall rate can be explained as follows:

* The recall rate is influenced by both build parameters and query parameters.

* Index query parameters are specified during index creation and cannot be modified afterward. However, they can be adjusted through session variables: for HNSW/HNSW SQ indexes, use `ob_hnsw_ef_search`; for IVF/IVF SQ/IVF PQ indexes, use `ob_ivf_nprobes`. If a session variable is set, its value takes precedence. For more information about how to configure these parameters, see [ob_hnsw_ef_search](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

The query syntax is as follows:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num);
```

How to use this statement:

* Query syntax requirements:
  * The `APPROXIMATE`/`APPROX` keyword must be specified to use the vector index path.
  * The query must include both the `ORDER BY` and `LIMIT` clauses.
  * The `ORDER BY` clause supports only a single vector condition.
  * The valid range for `LIMIT + OFFSET` is `(0, 16384]`.

* Rules for distance functions:
  * If `APPROXIMATE`/`APPROX` is not specified, calling `inner_product`, `negative_inner_product`, or `L2` will not use the vector index path in the query plan, but no error will be raised.
  * If `APPROXIMATE`/`APPROX` is specified but the distance function does not match the vector index algorithm, the query plan will not use the vector index path, but no error will be raised.
  * If `APPROXIMATE`/`APPROX` is specified and the expression is `inner_product`, the query plan will not use the vector index path.
  * If `APPROXIMATE`/`APPROX` is specified and the expression is `negative_inner_product` or `L2`, and these match the vector index algorithm, the query plan will use the vector index path.

* Additional notes:
  * The `WHERE` condition will act as a filtering condition after the vector index query is executed.
  * If the `LIMIT` clause is not specified, an error will be raised.

## Examples of creating, querying, and dropping indexes

* The distance function selection rules are as follows:
  * If `APPROXIMATE`/`APPROX` is not specified, the query plan will not choose the vector index path, but an error is not returned when the `inner_product`, `negative_inner_product`, or `L2` distance function is called.
  * If `APPROXIMATE`/`APPROX` is specified, the distance function does not match that supported by the vector index algorithm. In this case, the query plan will not choose the vector index path, but an error is not returned.
  * If `APPROXIMATE`/`APPROX` is specified, the expression is `inner_product`. In this case, the query plan will not choose the vector index path.
  * If `APPROXIMATE`/`APPROX` is specified, the expression is `negative_inner_product` or `L2`, and it matches that supported by the vector index algorithm, the query plan will choose the vector index path.

* Other notes:
  * The `WHERE` condition is used as a filter condition after the vector index query.
  * The `LIMIT` clause is not specified, an error is returned.

## Index creation, query, and deletion examples

### Considerations

OceanBase Database allows you to create vector indexes either during table creation or after the table has been created. When creating a vector index, keep the following points in mind:

* Once a vector index is created, its parameters cannot be modified.

* The `VECTOR` keyword must be included when creating a vector index.

* The parameters and descriptions for creating an index after table creation are the same as those for creating it during table creation.

* If the dataset is large, we recommend that you complete data insertion before creating the index to achieve optimal query performance.

* For HNSW SQ, IVF, IVF SQ, and IVF PQ indexes, we recommend that you create the index after data insertion and rebuild the index after inserting a significant amount of additional data. Specific instructions for creating each type of index are provided in the examples below.

#### HNSW SQ index example


The parameters of an HNSW/HNSW SQ index are described as follows:

| Parameter | Default value | Value range | Required? | Description | Remarks |
|------|--------|----------|----------|------|------|
| distance |  | l2/inner_product/cosine | Yes | The type of vector distance function. | l2 indicates the Euclidean distance, inner_product indicates the inner product distance, and cosine indicates the cosine distance. |
| type |  | hnsw | Yes | The type of index. | Currently, `hnsw` and `hnsw_sq8` are supported. |
| lib | vsag | vsag | No | The type of vector index library. | Currently, only the VSAG vector library is supported. |
| m | 16 | [5,64] | No | The maximum number of neighbors for an HNSW index node. This parameter is used during index construction. | Larger values result in slower index construction but better query performance. |
| ef_construction | 200 | [5,1000] | No | The size of the candidate set during HNSW index construction. This parameter is used during index construction. | Larger values result in slower index construction but higher index quality. `ef_construction` must be greater than `m`. |
| ef_search | 64 | [1,1000] | No | The size of the candidate set during HNSW index query. This parameter is used during query. | Larger values result in slower queries but higher recall rates. |

## Index maintenance

When there is a large amount of incremental data, query performance may decline. To reduce the data volume in the incremental data table, OceanBase Database introduces `DBMS_VECTOR` for vector index maintenance.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF SQ/IVF PQ indexes do not support incremental refreshes. </p>
</main>

If a large amount of data is written after the index is created, we recommend that you use an incremental refresh.

The syntax is as follows:

```shell
  PROCEDURE refresh_index(
    IN     idx_name               VARCHAR(65535),                 ---- Index name
    IN     table_name             VARCHAR(65535),                 ---- Table name
    IN     idx_vector_col         VARCHAR(65535) DEFAULT NULL,    ---- Vector column name
    IN     refresh_threshold      INT DEFAULT 10000,              ---- Number of incremental data records
    IN     refresh_type           VARCHAR(65535) DEFAULT NULL);   ---- FAST
```

An incremental refresh is initiated every 15 minutes. If more than 10,000 incremental data records are generated, an incremental refresh is automatically initiated.

### Complete refresh

If a large amount of data is updated or deleted after the index is created, we recommend that you use a complete refresh.

The syntax is as follows:

```shell
  PROCEDURE rebuild_index(
    IN     idx_name                VARCHAR(65535),                    ---- Index name
    IN     table_name              VARCHAR(65535),                    ---- Table name
    IN     idx_vector_col          VARCHAR(65535) DEFAULT NULL,       ---- Vector column name
    IN     delta_rate_threshold    FLOAT DEFAULT 0.2,                 ---- Proportion of incremental data
    IN     idx_organization        VARCHAR(65535) DEFAULT NULL,       ---- Index type
    IN     idx_distance_metrics    VARCHAR(65535) DEFAULT 'EUCLIDEAN',---- Distance type
    IN     idx_parameters          LONGTEXT DEFAULT NULL,             ---- Index parameters
    IN     idx_parallel_creation   INT DEFAULT 1);                    ---- Degree of parallelism for creating an index, reserved, only supported in the syntax
```

A complete refresh is initiated every 24 hours. If more than 20% of the original data is added, a complete refresh is automatically initiated. A complete refresh will clear the original index and rebuild a new index in the background. Therefore, it is a time-consuming process.
