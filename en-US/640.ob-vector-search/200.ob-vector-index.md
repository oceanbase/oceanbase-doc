# Create a vector index

This topic describes how to create, query, maintain, and drop vector indexes in OceanBase Database.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Sparse vector indexes and HNSW_BQ indexes are supported starting from V4.3.5 BP2.</p>
</main>

## Description and limitations

OceanBase vector indexes are described as follows:

| Index type | Description | Scenarios |
|-----------|------|----------|
| HNSW      | The maximum dimension of indexed columns is 4096. The HNSW index is a memory-based index that must be fully loaded into memory. It supports DML and real-time queries. |  |
| HNSW_SQ   | The HNSW_SQ index offers similar construction speed, query performance, and recall rate as the HNSW index, but reduces overall memory usage to 1/2 to 1/3 of the original. | Scenarios with high performance and recall rate requirements. |
| HNSW_BQ   | The HNSW_BQ index has a slightly lower recall rate compared to the HNSW index, but significantly reduces memory usage. The BQ quantization compression algorithm (Rabitq) can compress vectors to 1/32 of their original size. The memory optimization effect of the HNSW_BQ index becomes more pronounced as the vector dimension increases. |  |
| IVF| An IVF index implemented based on database tables, which does not require resident memory. | Scenarios with lower performance requirements but large data volumes and cost sensitivity. |
| IVF_PQ| An IVF_PQ index implemented based on database tables, which does not require resident memory. On top of IVF, PQ quantization technology is applied. The recall rate of the index is slightly lower than that of the IVF index, but the performance is higher. The PQ quantization compression algorithm can generally compress vectors to 1/16 to 1/32 of their original size. | Scenarios with lower performance requirements but large data volumes and cost sensitivity. |
| IVF_SQ (Experimental feature)| An IVF_SQ index implemented based on database tables, which does not require resident memory. On top of IVF, SQ quantization technology is applied. The recall rate of the index is slightly lower than that of the IVF index, but the performance is higher. The SQ quantization compression algorithm can generally compress vectors to 1/3 to 1/4 of their original size. | Scenarios with lower performance requirements but large data volumes and cost sensitivity. |

Some other notes:

* OceanBase Database supports the L2, inner product, and cosine distance as the index distance algorithm for dense vector indexes, and the inner product as the index distance algorithm for sparse vector indexes.
* OceanBase Database supports vector queries with filter conditions. The filter conditions can be scalar conditions or spatial relationships, such as ST_Intersects. Multi-value indexes, full-text indexes, and global indexes cannot be used as pre-filterers.
* OceanBase Database allows you to create vector and full-text indexes on the same table. Vector indexes include dense and sparse indexes.
* For more information about how vector indexes support offline DDL operations, see [Offline DDL operations](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md).

The limitations are described as follows:

* For OceanBase Database V4.3.5 BP3, creating columnstore vector indexes is currently not supported.

## Preparations

Before you use the HNSW, HNSW_SQ, or HNSW_BQ vector index, you must enable the vector feature by setting [ob_vector_memory_limit_percentage](../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md). The IVF index does not require memory residency, so you do not need to set this parameter to enable the vector feature.

```sql
ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
```

## Overview of index queries

Vector index queries are approximate nearest neighbor queries and do not guarantee 100% accuracy. The accuracy of vector queries is measured by recall. For example, if a query for the 10 nearest neighbors can stably return 9 correct results, the recall is 90%. The recall is affected by the following factors:

* The build parameters and query parameters.
* The index query parameters are specified when the index is created and cannot be modified. However, you can set session variables to specify the parameters. The `ob_hnsw_ef_search` variable specifies the parameters for the HNSW/HNSW_SQ/HNSW_BQ index, and the `ob_ivf_nprobes` variable specifies the parameters for the IVF index. If you set a session variable, its value is prioritized. For more information, see [ob_hnsw_ef_search](../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

The syntax for dense vector index queries and sparse vector index queries is the same, as shown in the following example:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num);
```

The syntax is subject to the following constraints:

* Syntax requirements:
  * The `APPROXIMATE`/`APPROX` keyword must be specified for the vector index path to be selected.
  * The `ORDER BY` and `LIMIT` clauses must be specified.
  * The `ORDER BY` clause supports only a single vector condition.
  * The value of `LIMIT + OFFSET` must be in the range of (0, 16384].

* Rules for distance functions:
  * If the `APPROXIMATE`/`APPROX` keyword is not specified, the `inner_product`, `negative_inner_product`, or `L2` function is called. The query plan does not select the vector index path, but no error is reported.
  * If the `APPROXIMATE`/`APPROX` keyword is specified, but the distance function does not match the vector index algorithm, the query plan does not select the vector index path, but no error is reported.
  * If the `APPROXIMATE`/`APPROX` keyword is specified, and the expression is `inner_product`, the query plan does not select the vector index path.
  * If the `APPROXIMATE`/`APPROX` keyword is specified, and the expression is `negative_inner_product` or `L2`, and the distance function matches the vector index algorithm, the query plan selects the vector index path.

* Other notes:
  * The `WHERE` condition is used as a filter after the vector index query.
  * If the `LIMIT` clause is not specified, an error is reported.

## Create, query, and drop indexes

### Considerations

OceanBase Vector indexes can be created either during table creation or after the table is created. When creating a vector index, note the following:

* After a vector index is created, no parameters can be modified.
* The `VECTOR` keyword is required when creating a vector index.
* The parameters and descriptions for an index created after the table is created are the same as those for an index created during table creation.
* If a large amount of data is involved, we recommend that you write the data first and then create the index to achieve the optimal query performance.

* We recommend that you create the HNSW_SQ, IVF, IVF_SQ, or IVF_PQ index after you write data and then rebuild the index after you write a large amount of incremental data. For more information about how to create each index, see the specific examples below.

* Sparse vector indexes can be created only during table creation and cannot be created after the table is created.

* [Character types](../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/200.table-of-mysql-mode/200.data-type-of-mysql-mode/400.string-data-type-of-mysql-mode.md): The VARCHAR type.

The size of the primary key information is calculated as follows:

```sql
SET @table_name = 'test'; -- Replace this with the name of the table to be queried.

SELECT
    CASE
        WHEN COUNT(*) <> COUNT(result_value) THEN 'not support'
        ELSE COALESCE(SUM(result_value), 'not support')
    END AS extra_info_size
FROM (
    SELECT
        CASE
            WHEN vdt.data_type_class IN (1, 2, 3, 4, 6, 8, 9, 14, 27, 28) THEN 8 -- For numeric types, add 8 to extra_info_size.
            WHEN oc.data_type = 22 THEN oc.data_length -- For the VARCHAR type, add data_length to extra_info_size.
            ELSE NULL -- Other types are not supported.
        END AS result_value
    FROM
        oceanbase.__all_column oc
    JOIN
        oceanbase.__all_virtual_data_type vdt
    ON
        oc.data_type = vdt.data_type
    WHERE
        oc.rowkey_position != 0
        AND oc.table_id = (SELECT table_id FROM oceanbase.__all_table WHERE table_name = @table_name)
) AS result_table;

-- The calculated result is 8 bytes.
```

## Index maintenance

When there is an excessive amount of incremental data, the query performance decreases. To reduce the amount of data in incremental data tables, OceanBase Database introduces the `DBMS_VECTOR` package for maintaining vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF_SQ/IVF_PQ indexes do not support incremental refreshes. </p>
</main>

If a large amount of data is written after an index is created, we recommend that you use incremental refreshes.

The syntax is as follows:

```shell
  PROCEDURE refresh_index(
    IN     idx_name               VARCHAR(65535),                 ---- Index name.
    IN     table_name             VARCHAR(65535),                 ---- Table name.
    IN     idx_vector_col         VARCHAR(65535) DEFAULT NULL,    ---- Name of the vector column.
    IN     refresh_threshold      INT DEFAULT 10000,              ---- Number of incremental data records.
    IN     refresh_type           VARCHAR(65535) DEFAULT NULL);   ---- FAST
```

Incremental refreshes check every 15 minutes. If the number of incremental data records exceeds 10,000, incremental refreshes are automatically executed.

### Full refresh

If a large amount of data is updated or deleted after an index is created, we recommend that you use full refreshes.

The syntax is as follows:

```shell
  PROCEDURE rebuild_index(
    IN     idx_name                VARCHAR(65535),                    ---- Index name.
    IN     table_name              VARCHAR(65535),                    ---- Table name.
    IN     idx_vector_col          VARCHAR(65535) DEFAULT NULL,       ---- Name of the vector column.
    IN     delta_rate_threshold    FLOAT DEFAULT 0.2,                 ---- Ratio of incremental data.
    IN     idx_organization        VARCHAR(65535) DEFAULT NULL,       ---- Index type.
    IN     idx_distance_metrics    VARCHAR(65535) DEFAULT 'EUCLIDEAN',---- Distance type.
    IN     idx_parameters          LONGTEXT DEFAULT NULL,             ---- Index parameters.
    IN     idx_parallel_creation   INT DEFAULT 1);                    ---- Degree of parallelism for parallel index creation. This parameter is reserved and supported only for syntax purposes.
```

Full refreshes check every 24 hours. If the amount of new data exceeds 20% of the original data, full refreshes are automatically executed. Full refreshes are executed asynchronously in the background. First, a new index is created, and then the old index is replaced. During the rebuild, the old index remains available, but the overall process is relatively slow.

## Performance optimization

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Currently, only IVF indexes are supported. </p>
</main>

OceanBase Database provides an automatic performance optimization mechanism for IVF indexes. This mechanism improves query performance by implementing cache management and regular maintenance.

### Optimization mechanism

The performance optimization mechanism for IVF indexes consists of two automatic tasks:

1. Cache preheating task: This task periodically checks all IVF indexes. If an index is found to have no corresponding cache, it automatically triggers cache preheating to load index data into the memory. Additionally, cache preheating is automatically triggered when an IVF index is created.
2. Cache cleanup task: This task periodically checks all IVF caches. If an IVF cache is found to have an index that has been deleted, it automatically clears the invalid cache to release memory resources. Additionally, cache cleanup is automatically triggered when an IVF index is deleted.

### Configure the optimization cycle

The system allows you to customize the time window for performance optimization tasks to avoid executing them during peak hours, which could affect performance.

In the `oceanbase` database, you can set the execution cycle by configuring the `vector_index_optimize_duty_time` parameter:

```sql
ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
```

The configuration is described as follows:

* The time format is `[start time, end time]`.
* The preceding configuration indicates that optimization tasks are executed only from 23:00:00 to 24:00:00.
* Optimization tasks are not initiated in other periods to avoid affecting normal business operations.

### Monitor optimization tasks

1. View the current task status

    You can view the status of running or pending optimization tasks by querying the `DBA_OB_VECTOR_INDEX_TASKS` view:

    ```sql
    -- You must query the view in a MySQL tenant.
    SELECT * FROM oceanbase.DBA_OB_VECTOR_INDEX_TASKS;
    ```

    A sample return result is as follows:

    ```shell
    +----------+---------------------+---------+----------------------------+----------------------------+--------------+----------+-----------+------------------+----------+------------------------------------+
    | TABLE_ID | TABLET_ID           | TASK_ID | START_TIME                 | MODIFY_TIME                | TRIGGER_TYPE | STATUS   | TASK_TYPE | TASK_SCN         | RET_CODE | TRACE_ID                           |
    +----------+---------------------+---------+----------------------------+----------------------------+--------------+----------+-----------+------------------+----------+------------------------------------+
    |   500020 | 1152921504606846990 | 2002281 | 1970-08-23 17:10:23.174127 | 1970-08-23 17:10:23.174137 | USER         | FINISHED |         2 | 1750671687770026 |        0 | YAFF00B9E4D97-00063839E6BD9BBC-0-1 |
    +----------+---------------------+---------+----------------------------+----------------------------+--------------+----------+-----------+------------------+----------+------------------------------------+
    1 row in set
    ```

    The task status is described as follows:

    * `STATUS = 0`: PREPARE. The task is waiting to be executed.
    * `STATUS = 1`: RUNNING. The task is being executed.
    * `STATUS = 3`: FINISHED. The task has been completed.

    The task type is described as follows:

    * `TASK_TYPE = 2`: IVF cache preheating task.
    * `TASK_TYPE = 3`: IVF cache cleanup task.

2. View the history task records

    Completed tasks (`STATUS = 3`) are automatically archived to the history table every 10 seconds, regardless of whether they were successful. You can view the history records by querying the `DBA_OB_VECTOR_INDEX_TASKS_HISTORY` view:

    ```sql
    -- Query the history records of a specified task.
    SELECT * FROM oceanbase.DBA_OB_VECTOR_INDEX_TASKS_HISTORY WHERE TASK_ID=2002281;
    ```

    A sample return result is as follows:


### Cancel an optimization task

You can cancel a specified task by using the following command:

```sql
-- Obtain the trace_id from the DBA_OB_VECTOR_INDEX_TASK_HISTORY view.
ALTER SYSTEM CANCEL TASK <trace_id>;
```

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>You can cancel a task only if it is in the failed retry stage, and the <code>ALTER SYSTEM CANCEL TASK</code> command is executed. If the backend task is stuck in a specific execution stage, it cannot be canceled by using this command. </p>
</main>

Here is an example:

```sql
-- Log in to the SYS tenant and obtain the trace_id of the specified task.
SELECT * FROM oceanbase.DBA_OB_VECTOR_INDEX_TASK_HISTORY WHERE TASK_ID=2037736;

+----------+---------------------+---------+----------------------------+----------------------------+--------------+----------+-----------+------------------+----------+------------------------------------+
|   500041 | 1152921504606847008 | 2037736 | 1970-08-23 17:10:23.203821 | 1970-08-23 17:10:23.203821 | USER         | PREPARED |         2 | 1750682301145225 |       -1 | YAFF00B9E4D97-00063839E6BDDEE0-0-1 |
```
