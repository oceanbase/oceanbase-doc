# Create a vector index

This topic describes how to create, query, maintain, and delete a vector index in OceanBase Database.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Sparse vector indexes and HNSW_BQ indexes are supported starting from V4.3.5 BP2.</p>
</main>

Here are the specific details about vector indexes in OceanBase Database:

* HNSW indexes are supported: The maximum dimension of index columns is 4,096. HNSW indexes are memory-based indexes that need to be fully loaded into memory. They support DML operations and real-time queries.

* HNSW_SQ indexes are supported: HNSW_SQ indexes offer similar construction speed, query performance, and recall rate as HNSW indexes, but they reduce memory usage to 1/2 to 1/3 of the original. They are suitable for scenarios with high performance and recall rate requirements.

* HNSW_BQ indexes are supported: Compared with HNSW indexes, HNSW_BQ indexes have a slightly lower recall rate but significantly reduce memory usage. Using the BQ quantization compression algorithm (Rabitq), vectors can be compressed to 1/32 of their original size. As the vector dimensions increase, the memory optimization effect of HNSW_BQ indexes becomes more pronounced.

* (Experimental feature) IVF indexes are supported: Unlike HNSW and HNSW_SQ indexes, IVF indexes are implemented based on database tables and do not occupy resident memory. They are suitable for scenarios with large data volumes, where performance is not a major concern, and costs need to be controlled.

* Distance algorithms: Dense vector indexes support L2, inner product (IP), and cosine distance as index distance algorithms, while sparse vector indexes support inner product as the index distance algorithm.

* Vector queries with filters are supported: The filter can be a scalar condition or a spatial relationship, such as `ST_Intersects`. Multi-valued indexes, full-text indexes, and global indexes are not supported as pre-filters.

* Indexes on the same table: Vector indexes and full-text indexes, including dense and sparse types, can be created on the same table.

* DDL operations: For more information about DDL operations on vector indexes, see [Offline DDL](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md).

## Preparations

Before using HNSW, HNSW_SQ, or HNSW_BQ vector indexes, you need to enable the vector functionality by configuring the parameter [ob_vector_memory_limit_percentage](../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md). IVF indexes do not require resident memory, so this parameter does not need to be manually configured to enable the vector functionality.

```sql
ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
```

## Overview of index queries

Vector index queries are a type of approximate nearest neighbor (ANN) query, which does not guarantee 100% accuracy of the results. The accuracy of vector queries is measured by the recall rate. For example, when searching for the 10 nearest neighbors, if 9 correct results are consistently returned, the recall rate is 90%. The recall rate is explained as follows:

* The recall rate is influenced by both index construction parameters and query parameters.

* Index query parameters are specified during index creation and cannot be modified afterward. However, they can be adjusted using session variables: for HNSW, HNSW_SQ, and HNSW_BQ indexes, use `ob_hnsw_ef_search`; for IVF indexes, use `ob_ivf_nprobes`. If session variables are set, their values will take precedence. For more information about how to configure these settings, see [ob_hnsw_ef_search](../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

Dense vector index queries and sparse vector index queries use the same syntax, as shown below:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num);
```

Details are as follows:

* Query syntax requirements:
  * The `APPROXIMATE`/`APPROX` keyword must be specified to select the vector index query path.
  * The query must include both `ORDER BY` and `LIMIT` clauses.
  * The `ORDER BY` clause supports only a single vector condition.
  * The value range for `LIMIT + OFFSET` is `(0, 16384]`.

* Rules for using distance functions:
  * If `APPROXIMATE`/`APPROX` is not specified, calling `inner_product`, `negative_inner_product`, or `L2` will not select the vector index query path, but no error will be raised.
  * If `APPROXIMATE`/`APPROX` is specified but the distance function does not match the vector index algorithm, the query plan will not select the vector index query path, but no error will be raised.
  * If `APPROXIMATE`/`APPROX` is specified and the expression is `inner_product`, the query plan will not select the vector index query path.
  * If `APPROXIMATE`/`APPROX` is specified and the expression is either `negative_inner_product` or `L2`, and it matches the vector index algorithm, the query plan will select the vector index query path.

* Additional notes:
  * `WHERE` conditions will be applied as post-filtering conditions after the vector index query.
  * If the `LIMIT` clause is not specified, an error will be raised.

## Examples of index creation, query, and deletion

### Considerations

OceanBase vector indexes can be created in two ways: during table creation or after the table has been created. Please note the following when working with vector indexes:

* Once a vector index is created, no parameters can be modified.

* The `VECTOR` keyword must be included when creating a vector index.

* The parameters and descriptions for post-creation indexes are the same as those for indexes created during table creation.

* If the dataset is large, it is recommended to finish writing all data first and then create the index to achieve optimal query performance.

* It is recommended to create HNSW_SQ indexes, IVF indexes, IVF_SQ indexes, and IVF_PQ indexes after inserting data. If a significant amount of incremental data is added later, rebuilding the index is advised. Detailed instructions for creating each type of index are provided in the examples below.

* Sparse vector indexes can only be created at the time of table creation and do not support creation afterward.

#### HNSW_SQ index example

```sql
CREATE TABLE hgraph_vecindex_suite_table_test (c1 INT AUTO_INCREMENT, c2 VECTOR(3), PRIMARY KEY(c1), VECTOR INDEX idx1(c2) WITH (distance=l2, type=hnsw_sq, lib=vsag));
```

The following table describes the parameters of the HNSW and HNSW_SQ indexes.

| Parameter | Default value | Value range | Required？ | Description | Remarks |
|------|--------|----------|----------|------|------|
| distance |  | l2/inner_product/cosine | Yes  | Specifies the vector distance function type.  | `l2` represents Euclidean distance, `inner_product` represents inner product distance, and `cosine` represents cosine distance. |
| type | hnsw | Yes | Specifies the index type. | Currently supports `hnsw`, `hnsw_sq8`, and `hnsw_bq`. |
| lib  | vsag | vsag  | No  | Specifies the vector index library type.  | Currently, only the VSAG vector library is supported. |
| m  | 16   | [5, 64] | No  | A parameter for building HNSW/HNSW_SQ/HNSW_BQ indexes, indicating the maximum number of neighbors per node. | Larger values slow down index construction but improve query performance.  |
| ef_construction      | 200           | [5, 1000]         | No       | A parameter for building HNSW/HNSW_SQ/HNSW_BQ indexes, specifying the size of the candidate set during index construction. | Larger values slow down index construction but improve index quality. `ef_construction` must be greater than `m`. |
| ef_search            | 64            | [1, 1000]         | No       | A parameter for querying HNSW/HNSW_SQ/HNSW_BQ indexes, specifying the size of the candidate set during queries. | Larger values slow down queries but increase recall rate.                                         |
| extra_info_max_size  | 0             | [0, 16384]        | No       | A parameter for building HNSW/HNSW_SQ/HNSW_BQ indexes, setting the maximum size (in bytes) of each primary key's information. The primary key of the table is stored in the index to accelerate queries. | <code>0</code>: Do not store primary key information.<br/><code>1</code>: Force storing primary key information, ignoring size limits. In this case, the table's primary key type (see details below) must be a supported type.<br/><code>Greater than 1</code>: Set the maximum size (in bytes) of primary key information. In this case, the following conditions must be met:<ul><li>The size of the primary key information (calculation method explained below) must be smaller than the set size limit.</li><li>The table's primary key type must be a supported type.</li></ul> |

The primary key types supported by `extra_info_max_size` include:

* [Numeric types](../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/200.table-of-mysql-mode/200.data-type-of-mysql-mode/200.numeric-data-type-of-mysql-mode.md): Supports integer types, floating-point types, and Bit_value types.
* [Date and time types](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/100.data-type-of-mysql-mode/300.date-and-time-types-of-mysql-mode/100.date-and-time-types-of-mysql-mode.md)
* [Character types](../700.reference/100.oceanbase-database-concepts/400.database-objects/200.database-objects-of-mysql-mode/200.table-of-mysql-mode/200.data-type-of-mysql-mode/400.character-data-type-of-mysql-mode.md): Supports the VARCHAR type.

Method for calculating the size of primary key information:

```sql
SET @table_name = 'test'; -- Replace with the table_name you want to query

SELECT 
    CASE 
        WHEN COUNT(*) <> COUNT(result_value) THEN 'not support' 
        ELSE COALESCE(SUM(result_value), 'not support') 
    END AS extra_info_size
FROM (
    SELECT
        CASE 
            WHEN vdt.data_type_class IN (1, 2, 3, 4, 6, 8, 9, 14, 27, 28) THEN 8 -- For numeric types, extra_info_size += 8
            WHEN oc.data_type = 22 THEN oc.data_length -- For VARCHAR types, extra_info_size += data_length
            ELSE NULL -- Other types are not supported
        END AS result_value
    FROM 
        oceanbase.__all_column oc
    JOIN 
        oceanbase.__all_virtual_data_type vdt 
    ON 
        oc.data_type = vdt.data_type
    WHERE 
        oc.rowkey_position != 0 
        AND oc.table_id = (SELECT table_id FROM oceanbase.__all_table WHERE table_name = @table_name)
) AS result_table;

-- The calculated result is 8 bytes
```

## Index maintenance

When there is too much incremental data, query performance may degrade. To reduce the amount of data in the incremental data table, OceanBase introduces `DBMS_VECTOR` for maintaining vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Incremental refresh is not supported for IVF, IVF_SQ, and IVF_PQ indexes.</p>
</main>

If a large amount of data is written after the index is created, we recommend that you use incremental refresh.

The syntax is as follows:

```shell
  PROCEDURE refresh_index(
    IN     idx_name               VARCHAR(65535),                 ---- The name of the index.
    IN     table_name             VARCHAR(65535),                 ---- The name of the table.
    IN     idx_vector_col         VARCHAR(65535) DEFAULT NULL,    ---- The name of the vector column.
    IN     refresh_threshold      INT DEFAULT 10000,              ---- The threshold of incremental data.
    IN     refresh_type           VARCHAR(65535) DEFAULT NULL);   ---- The refresh type. Value: FAST.
```

Incremental refresh is checked every 15 minutes. If more than 10,000 pieces of incremental data are generated, incremental refresh is automatically triggered.

### Full refresh

If a large amount of data is updated or deleted after the index is created, we recommend that you use full refresh.

The syntax is as follows:

```shell
  PROCEDURE rebuild_index(
    IN     idx_name                VARCHAR(65535),                    ---- The name of the index.
    IN     table_name              VARCHAR(65535),                    ---- The name of the table.
    IN     idx_vector_col          VARCHAR(65535) DEFAULT NULL,       ---- The name of the vector column.
    IN     delta_rate_threshold    FLOAT DEFAULT 0.2,                 ---- The threshold of incremental data.
    IN     idx_organization        VARCHAR(65535) DEFAULT NULL,       ---- The index type.
    IN     idx_distance_metrics    VARCHAR(65535) DEFAULT 'EUCLIDEAN',---- The distance type.
    IN     idx_parameters          LONGTEXT DEFAULT NULL,             ---- The index parameters.
    IN     idx_parallel_creation   INT DEFAULT 1);                    ---- The parallelism of index creation. Reserved. Supported only in syntax.
```

Full refresh is checked every 24 hours. If the amount of new data exceeds 20% of the original data, full refresh is automatically triggered. Full refresh clears the original index and rebuilds a new index in the background, which is time-consuming.
