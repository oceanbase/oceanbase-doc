# Create a vector index

This topic describes how to create, search, maintain, and drop vector indexes in OceanBase Database.

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Sparse vector indexes and HNSW_BQ indexes are supported starting from V4.3.5 BP2.</p>
</main>

## Index types

OceanBase Database supports the following vector index types:

| Index type | Description | Applicable Scenarios |
|------------|-------------|---------------------|
| HNSW       | The maximum dimension of the indexed column is 4096. HNSW is a memory-based index that requires full loading into memory. It supports DML operations and real-time retrieval. |  |
| HNSW_SQ    | HNSW_SQ provides similar construction speed, retrieval performance, and recall rate as HNSW, but reduces overall memory usage to 1/2 to 1/3 of that of HNSW. | Scenarios where high performance and recall are required. |
| HNSW_BQ    | HNSW_BQ has a slightly lower recall rate compared to HNSW, but significantly reduces memory usage. The BQ quantization algorithm (Rabitq) compresses vectors to 1/32 of their original size. As the vector dimension increases, the memory optimization effect of HNSW_BQ becomes more pronounced. |  |
| IVF        | The IVF index is implemented based on database tables and does not occupy resident memory. | Scenarios where performance is not a priority, but large data volume and cost sensitivity are factors. |
| IVF_PQ     | The IVF_PQ index is implemented based on database tables and does not occupy resident memory. It applies the PQ quantization technique on top of IVF. The recall rate of IVF_PQ is slightly lower than that of IVF, but its performance is higher. The PQ quantization algorithm can compress vectors to 1/16 to 1/32 of their original size in most scenarios. | Scenarios where performance is not a priority, but large data volume and cost sensitivity are factors. |
| IVF_SQ (Experimental feature) | The IVF_SQ index is implemented based on database tables and does not occupy resident memory. It applies the SQ quantization technique on top of IVF. The recall rate of IVF_SQ is slightly lower than that of IVF, but its performance is higher. The SQ quantization algorithm can compress vectors to 1/3 to 1/4 of their original size in most scenarios. | Scenarios where performance is not a priority, but large data volume and cost sensitivity are factors. |

Other notes:

* Dense vector indexes support L2, inner product, and cosine distance as index distance algorithms. Sparse vector indexes support only inner product.
* Vector index retrieval supports the use of some distance functions. For more information, see [Use SQL functions](250.ob-vector-function.md).
* Vector retrieval with filter conditions is supported. The filter conditions can be scalar conditions or spatial relationships, such as ST_Intersects. Multi-valued indexes, full-text indexes, or global indexes cannot be used as pre-filters.
* Vector indexes and full-text indexes can be created on the same table. Vector indexes include both dense and sparse types.
* For information about the support of vector indexes for offline DDL operations, see [Offline DDL](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md).

The following limitations apply:

* In OceanBase Database V4.3.5 BP3, columnstore vector indexes cannot be created.

## Configure vector index memory

OceanBase Database vector search allows you to set [ob_vector_memory_limit_percentage](../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md) to configure the memory for vector indexes:

* **Before you use HNSW, HNSW_SQ, or HNSW_BQ indexes in OceanBase Database of a version earlier than V4.3.5 BP3**, you must manually set `ob_vector_memory_limit_percentage` to `30` to obtain the best search performance. If you do not set this parameter, no memory is allocated for the vector index, and an error is returned when you create the index. IVF, IVF_SQ, and IVF_PQ indexes do not require constant memory allocation, so you can ignore this parameter. A sample configuration is as follows:
    ```sql
    ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
    ```

* **Starting with OceanBase Database V4.3.5 BP3**, vector search is enabled by default. The default value of `0` indicates the adaptive mode, where the system automatically adjusts the memory usage ratio for vector index data in the tenant without manual adjustment:
  * If the actual memory of the tenant is 8 GB or less, the value is automatically set to `40`.
  * If the actual memory of the tenant is more than 8 GB, the value is automatically set to `50`.

## Index memory estimation and actual usage query

You can use the `DBMS_VECTOR` system package to estimate and query index memory usage:

* Use the [INDEX_VECTOR_MEMORY_ADVISOR](../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/500.index-vector-memory-advisor-mysql.md) procedure to estimate index memory usage before the table is created.
* Use the [INDEX_VECTOR_MEMORY_ESTIMATE](../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/400.index-vector-memory-estimate-mysql.md) procedure to analyze index memory usage after the table is created and data has been inserted.

The vector index memory estimation returns two pieces of information: the minimum memory configuration required to create the vector index, and the actual memory usage after HNSW_SQ and IVF indexes are created.

## Index creation syntax and notes

OceanBase Database allows you to create vector indexes in two ways: **during table creation** and **after table creation**. Take note of the following points when creating a vector index:

* After a vector index is created, its parameters cannot be modified.
* The `VECTOR` keyword must be specified when creating a vector index.
* The parameters and descriptions for vector indexes created after table creation are the same as those for indexes created at table creation.
* If a large amount of data is stored in a table, it is recommended to complete data writing before creating a vector index to obtain optimal search performance.
* For HNSW_SQ, IVF, IVF_SQ, and IVF_PQ indexes, it is recommended to create the index after writing data, and to rebuild the index after writing a large amount of incremental data. For more information about creating these indexes, see the specific examples below.
* Sparse vector indexes can only be created at table creation and do not support creation after table creation.

:::tab
tab HNSW/HNSW_SQ/HNSW_BQ

Syntax for creating a vector index during table creation:

```sql
CREATE TABLE table_name (
    column_name1 data_type1,
    column_name2 data_type2,
    ...,
    VECTOR INDEX index_name (column_name) WITH (param1=value1, param2=value2, ...)
);
```

Syntax for creating a vector index after table creation:

```sql
-- You can set the parallelism to improve index construction performance. The maximum value is the number of CPU cores × 2.
CREATE [/*+ parallel $value*/] VECTOR INDEX index_name ON table_name(column_name) WITH (param1=value1, param2=value2, ...);
```

Calculation method for the size of primary key information:

```sql
SET @table_name = 'test'; -- Replace the value with the name of the table to be queried.

SELECT
    CASE
        WHEN COUNT(*) <> COUNT(result_value) THEN 'not support'
        ELSE COALESCE(SUM(result_value), 'not support')
    END AS extra_info_size
FROM (
    SELECT
        CASE
            WHEN vdt.data_type_class IN (1, 2, 3, 4, 6, 8, 9, 14, 27, 28) THEN 8 -- For a numeric type, add 8 to extra_info_size.
            WHEN oc.data_type = 22 THEN oc.data_length -- For a VARCHAR type, add data_length to extra_info_size.
            ELSE NULL -- Other types are not supported.
        END AS result_value
    FROM
        oceanbase.__all_column oc
    JOIN
        oceanbase.__all_virtual_data_type vdt
    ON
        oc.data_type = vdt.data_type
    WHERE
        oc.rowkey_position != 0
        AND oc.table_id = (SELECT table_id FROM oceanbase.__all_table WHERE table_name = @table_name)
) AS result_table;

-- The result is 8 bytes.
```

## Index search syntax and notes

Vector index search is an approximate nearest neighbor search and does not guarantee 100% accuracy. The accuracy metric for vector index search is recall rate. For example, if you search for the 10 nearest neighbors and 9 correct results are returned, the recall rate is 90%. Recall rate is described as follows:

* Recall rate is affected by both index construction parameters and search parameters.
* Index search parameters are specified when you build the index and cannot be modified afterward. However, you can set them through session variables: `ob_hnsw_ef_search` for HNSW/HNSW_SQ/HNSW_BQ indexes, and `ob_ivf_nprobes` for IVF indexes. If session variables are set, their values take precedence. For more information, see [ob_hnsw_ef_search](../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

The syntax for both dense and sparse vector index searches is the same, as shown below:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num);
```

Some notes about vector index search:

* Syntax requirements:
  * The `APPROXIMATE` or `APPROX` keyword must be specified; otherwise, the system performs a full-table scan instead of using vector indexes.
  * Both `ORDER BY` and `LIMIT` clauses are required.
  * Only one vector condition is supported in the `ORDER BY` clause.
  * The combined value of `LIMIT` and `OFFSET` must be in the range `(0, 16384]`.

* Rules for distance functions:
  * If you specify `APPROXIMATE`/`APPROX` and the distance function is supported by the current version and matches the vector index algorithm, the system uses vector indexes for the search.
  * If you specify `APPROXIMATE`/`APPROX`, but the distance function does not match the vector index algorithm, the system does not use vector indexes for the search, but no error is returned.
  * If you specify `APPROXIMATE`/`APPROX`, but the distance function is not supported in the current version, the system does not use vector indexes for the search and returns an error.
  * If you do not specify `APPROXIMATE`/`APPROX`, even if the distance function is supported in the current version, the system does not use vector indexes for the search, but no error is returned.

* Other notes:
  * The `WHERE` clause is applied as a filter after vector index search.
  * Omitting the `LIMIT` clause will result in an error.

## Maintenance

When there is a large amount of incremental data, the search performance will decrease. To reduce the amount of data in the incremental data table, OceanBase introduces `DBMS_VECTOR` to maintain vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF_SQ/IVF_PQ indexes do not support incremental refresh. </p>
</main>

If a large amount of data is written after an index is created, we recommend that you perform an incremental refresh by using the `REFRESH_INDEX` procedure. For more information, see [REFRESH_INDEX](../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/200.refresh-index-mysql.md).

Incremental refreshes are performed every 15 minutes. If the incremental data exceeds 10,000 records, an incremental refresh is automatically performed.

### Full refresh (rebuild)

If a large amount of data is updated or deleted after an index is created, we recommend performing a full refresh using the `REBUILD_INDEX` procedure. For more information, see [REBUILD_INDEX](../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

The system checks every 24 hours, and if the amount of new data exceeds 20% of the original data, a full refresh is automatically triggered. The full refresh runs asynchronously in the background: a new index is created first, and then the old index is replaced. During the rebuilding process, the old index remains available, but the process is relatively slow.

Considerations:

* When performing [offline DDL](../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) operations (such as `ALTER TABLE` to modify the table schema or primary key), the index table will be rebuilt. Since parallelism cannot be specified for index rebuilding, the system defaults to single-threaded execution. For large data volumes, this can result in a slow rebuild process and affect the overall efficiency of the offline DDL operation.
* If you need to modify index parameters during rebuilding, you must specify both `type` and `distance` in the parameter list, and their values must match the original index type. For example, if the original index type is `hnsw` and the distance algorithm is `l2`, you must specify `type=hnsw` and `distance=l2` during rebuilding.
* Index rebuilding supports:
    * Modifying the values of `m`, `ef_search`, and `ef_construction`
    * Online rebuilding of the `ef_search` parameter
    * Rebuilding between `hnsw` and `hnsw_sq` index types
    * Rebuilding between `ivf_flat` and `ivf_flat`, `ivf_sq8` and `ivf_sq8`, `ivf_pq` and `ivf_pq` index types
    * Specifying the degree of parallelism during rebuilding. For examples, see [REBUILD_INDEX](../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).
* Index rebuilding does not support:
    * Modifying the `type` or `distance` values
    * Rebuilding between `hnsw` and `ivf` index types
    * Rebuilding between `hnsw` and `hnsw_bq` index types
    * Cross-rebuilding among `ivf_flat`, `ivf_pq`, and `ivf_sq8` index types

## Performance optimization

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Only the IVF index is supported. </p>
</main>

OceanBase Database provides an automatic performance optimization mechanism for the IVF index to improve search performance through cache management and regular maintenance.

### Optimization mechanism

The performance optimization mechanism for IVF indexes involves two automatic tasks:

1. Cache warm-up task: Regularly checks all IVF indexes. If an index does not have a corresponding cache, the system automatically triggers cache warm-up to load the index data into memory. Additionally, when an IVF index is created, the cache is automatically warmed up.
2. Cache cleanup task: Regularly checks all IVF caches. If a cache corresponds to an index that has been deleted, the system automatically cleans up the invalid cache to release memory resources. Additionally, when an IVF index is deleted, the cache is automatically cleared.

### Configure the optimization execution window

The system supports customizing the execution window for performance optimization tasks to avoid impacting performance during peak business hours.

In the `oceanbase` database, you can set the execution window using the `vector_index_optimize_duty_time` parameter:

```sql
ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
```

Configuration notes:

* The time format is `[start time, end time]`.
* The above configuration specifies that optimization tasks will only run from 23:00:00 to 24:00:00.
* Optimization tasks will not be initiated during other periods, helping to avoid impact on normal business operations.

### Cancel an optimization task

You can cancel a specified task by using the following command:

```sql
-- trace_id is obtained from the DBA_OB_VECTOR_INDEX_TASKS_HISTORY view.
ALTER SYSTEM CANCEL TASK <trace_id>;
```

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>You can cancel a task only in the retry phase of the task failure by executing the <code>ALTER SYSTEM CANCEL TASK</code> command. If a background task is stuck in a specific execution phase, it cannot be canceled by using this command. </p>
</main>
