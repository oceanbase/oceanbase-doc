# Monitor and maintain the vector index

This topic describes how to monitor and maintain the vector index of OceanBase Database.

## Monitor

You can view the basic information and real-time status of vector indexes in the system view.

* You can query the [[G]V$OB_HNSW_INDEX_INFO](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/950.gv-ob_hnsw_index_info-of-mysql-mode.md) view to obtain the basic information and real-time status of HNSW indexes.
* You can query the [[G]V$OB_IVF_INDEX_INFO](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/960.gv-ob_ivf_index_info-of-mysql-mode.md) view to obtain the basic information and real-time status of IVF indexes.
* You can query the [[G]V$OB_SINDI_INDEX_INFO](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/3450.gv-ob_sindi_index_info-of-mysql-mode.md) view to obtain the basic information and real-time status of in-memory sparse indexes.

## Maintenance

If the amount of incremental data is too large, the search performance will be affected. To reduce the amount of data in the incremental data table, OceanBase Database introduces the `DBMS_VECTOR` package to maintain vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This feature is supported for HNSW, semantic, and in-memory sparse indexes, but not for IVF indexes. </p>
</main>

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If the semantic index is in asynchronous embedding mode, incremental refresh will trigger additional embedding of data to ensure that incremental data is correctly converted into vectors and added to the index. </p>
</main>

If a large amount of data is written after the index is created, we recommend that you use the `REFRESH_INDEX` procedure for incremental refresh. For more information, see [REFRESH_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/200.refresh-index-mysql.md).

Incremental refresh is checked every 15 minutes. If the number of incremental data exceeds 10,000, incremental refresh is automatically executed.

### Full refresh (rebuild)

#### Manual full table rebuild

If a large amount of data is updated or deleted after the index is created, we recommend that you use the `REBUILD_INDEX` procedure to perform a full refresh. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

A full refresh is performed every 24 hours. If the amount of new data exceeds 20% of the original data, a full refresh is automatically performed. A full refresh is performed in the background and asynchronously. First, a new index is created, and then the old index is replaced. During the rebuild process, the old index remains available, but the overall process is relatively slow.

We also provide the `vector_index_memory_saving_mode` parameter to control the memory usage during index rebuild. Enabling this mode can reduce the memory consumption during the rebuild process of partitioned table vector indexes. Typically, vector index rebuild requires twice the memory of the index. When this mode is enabled, the system temporarily deletes the memory index of a partition after the index is built for that partition, thereby effectively reducing the total memory required for the rebuild. For more information, see [vector_index_memory_saving_mode](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md).

Consider the following notes:

* When you perform an [offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) operation (such as `ALTER TABLE` to modify the table structure or primary key), the index table is rebuilt. Since parallelism cannot be specified for index rebuild, the system uses a single thread by default. Therefore, when the amount of data is large, the rebuild process is slow, which affects the overall efficiency of the offline DDL operation.
* If you need to modify the index parameters during index rebuild, you must specify both `type` and `distance` in the parameter list, and they must be consistent with the original index type. For example, if the original index type is `hnsw` and the distance algorithm is `l2`, you must specify `type=hnsw` and `distance=l2` during the rebuild.
* During index rebuild, the following operations are supported:
    * Modifying the `m`, `ef_search`, and `ef_construction` values.
    * Online rebuild of the `ef_search` parameter.
    * Rebuilding the index type between `hnsw` and `hnsw_sq`.
    * Rebuilding the index type between `ivf_flat` and `ivf_flat`, and between `ivf_pq` and `ivf_pq`.
    * Specifying the parallelism during the rebuild. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

* During index rebuild, the following operations are not supported:
    * Modifying the `type` and `distance` types.
    * Rebuilding the index type between `hnsw` and `ivf`.
    * Rebuilding the index type between `hnsw` and `hnsw_bq`.
    * Cross-rebuilding the index types between `ivf_flat` and `ivf_pq`.

#### Automatic partition rebuild (recommended)

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><li>If you upgrade your vector database from a version earlier than V4.5.0 to V4.5.0, you must manually rebuild all vector indexes before you can perform automatic partition rebuilds after the upgrade. </li><li>This feature is supported for HNSW, semantic, and memory sparse indexes, but not for IVF indexes. </li></p>
</main>

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>During automatic partition rebuilds, the system processes incremental data and snapshot tasks simultaneously to ensure the consistency and integrity of the index data. </p>
</main>

The current version triggers automatic partition rebuild tasks in the following two scenarios:

* When you execute vector index search statements.
* When a scheduled check is performed. You can manually configure the execution cycle.

1. Configure the execution cycle

    In the `oceanbase` database, set the [vector_index_optimize_duty_time](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8250.vector_index_optimize_duty_time.md) parameter to configure the execution cycle. Here is an example:

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    After you configure the parameter as shown in the preceding example, the partition rebuild task is executed only between 23:00:00 and 24:00:00. For more information about the parameter, see the corresponding parameter documentation.

2. View the task progress and history

    You can query the [CDB/DBA_OB_VECTOR_INDEX_TASKS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12950.o-dba_ob_vector_index_tasks-of-mysql-mode.md) or [CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12960.o-dba_ob_vector_index_task_history-of-mysql-mode.md) view to view the task progress and history.

    You can use the `status` field to determine the current status of the task:

    * 0 (PREPARE): The task is waiting to be executed.
    * 1 (RUNNING): The task is being executed.
    * 2 (PENDING): The task is paused.
    * 3 (FINISHED): The task has been completed.

    The tasks that have been completed, that is, the tasks with the `status=FINISHED` value, are stored in the history table regardless of whether they are successful. For more information, see the corresponding view documentation.

3. Cancel a task

    To cancel a task, you can obtain the trace_id from the `DBA_OB_VECTOR_INDEX_TASKS` or `CDB_OB_VECTOR_INDEX_TASKS` view and execute the following command:

    ```sql
    ALTER SYSTEM CANCEL TASK <trace_id>;
    ```
    Here is an example:
    ```sql
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```
