# Monitor and maintain indexes

This topic describes how to monitor and maintain vector indexes in OceanBase Database.

## Monitoring

You can view the basic information and real-time status of vector indexes in the system view.

* You can query the [[G]V$OB_HNSW_INDEX_INFO](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/950.gv-ob_hnsw_index_info-of-mysql-mode.md) view to obtain the basic information and real-time status of HNSW vector indexes.
* You can query the [[G]V$OB_IVF_INDEX_INFO](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/960.gv-ob_ivf_index_info-of-mysql-mode.md) view to obtain the basic information and real-time status of IVF vector indexes.

## Maintenance

When the amount of incremental data is large, the search performance will decrease. To reduce the amount of data in the incremental data table, OceanBase Database introduces the `DBMS_VECTOR` package for maintaining vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF_PQ indexes do not support incremental refresh. </p>
</main>

If you write a large amount of data after creating an index, we recommend that you use the `REFRESH_INDEX` procedure to perform an incremental refresh. For more information, see [REFRESH_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/200.refresh-index-mysql.md).

An incremental refresh is performed every 15 minutes. If the number of incremental data entries exceeds 10,000, an incremental refresh is automatically performed.

### Full refresh (rebuild)

#### Manually Rebuild the Index

If a large amount of data is updated or deleted after the index is created, we recommend that you use the `REBUILD_INDEX` procedure to perform a full refresh. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

A full refresh is performed every 24 hours. If the amount of new data exceeds 20% of the original data, a full refresh is automatically performed. The full refresh is performed in the background and asynchronously. First, a new index is created, and then the old index is replaced. During the rebuild, the old index remains available, but the overall process is relatively slow.

We also provide the `vector_index_memory_saving_mode` parameter to control the memory usage during index rebuilds. Enabling this mode can reduce the memory consumption during the rebuild of vector indexes in partitioned tables. Typically, vector index rebuilds consume twice the memory of the index. When this mode is enabled, the system temporarily deletes the memory index of a partition after it is built to release memory, effectively reducing the total memory required for the rebuild. For more information, see [vector_index_memory_saving_mode](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md).

Consider the following notes:

* When you perform an [offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) operation (such as `ALTER TABLE` to modify the table structure or primary key), the index table will be rebuilt. Since parallelism cannot be specified during index rebuilds, the system defaults to using a single thread. Therefore, when the amount of data is large, the rebuild process can be slow, which affects the overall efficiency of the offline DDL operation.
* If you need to modify the index parameters during the rebuild, you must specify both `type` and `distance` in the parameter list, and they must match the original index type. For example, if the original index type is `hnsw` and the distance algorithm is `l2`, you must specify both `type=hnsw` and `distance=l2` during the rebuild.
* During the rebuild, you can:
    * Modify the values of `m`, `ef_search`, and `ef_construction`.
    * Online rebuild the `ef_search` parameter.
    * Rebuild the index type between `hnsw` and `hnsw_sq`.
    * Rebuild the index type between `ivf_flat` and `ivf_flat`, or between `ivf_pq` and `ivf_pq`.
    * Set the parallelism during the rebuild. For an example, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

* During the rebuild, you cannot:
    * Modify the `type` and `distance` parameters.
    * Rebuild the index type between `hnsw` and `ivf`.
    * Rebuild the index type between `hnsw` and `hnsw_bq`.
    * Rebuild the index type between `ivf_flat` and `ivf_pq`.

#### Automatic partition rebuild (Recommended)

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><li>This feature is supported starting from V4.4.1. If your vector database is upgraded from an earlier version to V4.4.1, you need to manually rebuild all vector indexes after the upgrade. Otherwise, automatic partition rebuild tasks may not execute as expected. </li><li>This feature is only supported for HNSW, HNSW_SQ, and HNSW_BQ indexes. </li></p>
</main>

Automatic partition rebuild tasks are triggered in the following two scenarios:

* When a vector index search statement is executed.
* During scheduled checks, which can be manually configured to run at specified intervals.

1. Configure the execution interval

    In the `oceanbase` database, set the [vector_index_optimize_duty_time](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8250.vector_index_optimize_duty_time.md) parameter to define the execution interval. Here is an example:

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    After this configuration, partition rebuild tasks will only run between 23:00:00 and 24:00:00. For more details, refer to the parameter description in the corresponding documentation.

2. View task progress and history

    You can check the progress and history of tasks by querying the [CDB/DBA_OB_VECTOR_INDEX_TASKS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12950.o-dba_ob_vector_index_tasks-of-mysql-mode.md) or [CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12960.o-dba_ob_vector_index_task_history-of-mysql-mode.md) views.

    Use the `status` field to determine the current status of a task:

    * 0 (PREPARE): The task is waiting to be executed.
    * 1 (RUNNING): The task is being executed.
    * 2 (PENDING): The task has been paused.
    * 3 (FINISHED): The task has completed.

    Tasks that have completed execution (status `FINISHED`) are stored in the history table, regardless of whether they were successful. For more details, refer to the corresponding view documentation.

3. Cancel a task

    To cancel a task, first obtain the trace_id from the `DBA_OB_VECTOR_INDEX_TASKS` or `CDB_OB_VECTOR_INDEX_TASKS` view, and then execute the following command:

    ```sql
    ALTER SYSTEM CANCEL TASK <trace_id>;
    ```
    Here is an example:
    ```sql
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```
