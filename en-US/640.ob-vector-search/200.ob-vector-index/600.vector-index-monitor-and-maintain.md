# Monitor and maintain vector indexes

This topic describes how to monitor and maintain vector indexes in OceanBase Database.

## Maintenance

If there is a large amount of incremental data, the search performance will be affected. To reduce the amount of data in the incremental data table, OceanBase Database introduces the `DBMS_VECTOR` package for vector index maintenance.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This feature supports HNSW series indexes, semantic indexes, and in-memory sparse indexes, but not IVF series indexes. </p>
</main>

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>If the semantic index is in asynchronous embedding mode, incremental refresh will trigger additional data embedding to ensure that the incremental data is correctly converted into vectors and added to the index. </p>
</main>

If a large amount of data is written after the index is created, we recommend that you use the `REFRESH_INDEX` procedure to perform incremental refresh. For more information, see [REFRESH_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/200.refresh-index-mysql.md).

Incremental refresh checks every 15 minutes. If the number of incremental data entries exceeds 10,000, an incremental refresh is automatically performed.

### Full refresh (rebuild)

#### Manual full table rebuild

If a large amount of data is updated or deleted after an index is created, we recommend that you use the `REBUILD_INDEX` procedure to perform a full refresh. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

A full refresh is performed every 24 hours. If the amount of new data exceeds 20% of the original data, a full refresh is automatically performed. The full refresh is performed in the background and asynchronously. First, a new index is created, and then the old index is replaced. During the rebuild process, the old index remains available, but the overall process is relatively slow.

We also provide the `vector_index_memory_saving_mode` configuration item to control the memory usage during index rebuilds. Enabling this mode can reduce the memory consumption during the rebuild of vector indexes in partitioned tables. Typically, vector index rebuilds require twice the memory of the index. When this mode is enabled, the system releases memory by temporarily deleting the memory index of a partition after the index for that partition is built. This effectively reduces the total memory required for the rebuild. For more information, see [vector_index_memory_saving_mode](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md).

Consider the following notes:

* When you perform [offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) operations (such as `ALTER TABLE` to modify the table structure or primary key), the index table is rebuilt. Since parallelism cannot be specified during index rebuilds, the system uses a single thread by default. Therefore, when the amount of data is large, the rebuild process is relatively slow, which affects the overall efficiency of the offline DDL operation.
* If you need to modify index parameters during index rebuilds, you must specify both `type` and `distance` in the parameter list. Additionally, the values of `type` and `distance` must be consistent with those of the original index. For example, if the original index type is `hnsw` and the distance algorithm is `l2`, you must specify `type=hnsw` and `distance=l2` during the rebuild.
* During index rebuilds, the following operations are supported:
    * Modifying the values of `m`, `ef_search`, and `ef_construction`.
    * Online rebuild of the `ef_search` parameter.
    * Rebuilding the index type between `hnsw` and `hnsw_sq`.
    * Rebuilding the index type between `ivf_flat` and `ivf_flat`, or between `ivf_pq` and `ivf_pq`.
    * Specifying parallelism during the rebuild. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

* During index rebuilds, the following operations are not supported:
    * Modifying the `type` and `distance` parameters.
    * Rebuilding the index type between `hnsw` and `ivf`.
    * Rebuilding the index type between `hnsw` and `hnsw_bq`.
    * Rebuilding the index type between `ivf_flat` and `ivf_pq`.

#### Automatic partition rebuild (recommended)

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><li>After you upgrade your vector database from an earlier version to V4.5.0, you must manually perform a full table rebuild for all vector indexes after the upgrade. Otherwise, the system cannot automatically perform partition rebuilds. </li><li>This feature supports HNSW, semantic, and memory sparse indexes, but not IVF indexes. </li></p>
</main>

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>During automatic partition rebuilds, the system processes incremental data and snapshot tasks to ensure the consistency and integrity of the index data. </p>
</main>

The current version triggers automatic partition rebuild tasks in the following two scenarios:

* When you execute vector index search statements.
* During scheduled checks, which you can manually configure.

1. Configure the execution cycle

    In the `oceanbase` database, you can configure the execution cycle by using the [vector_index_optimize_duty_time](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8250.vector_index_optimize_duty_time.md) configuration item. Here is an example:

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    After the preceding configuration is completed, the partition rebuild task is executed only between 23:00:00 and 24:00:00. The task is not initiated during other periods. For more information about the parameters, see the corresponding configuration item documentation.

2. View the task progress and history

    You can query the [CDB/DBA_OB_VECTOR_INDEX_TASKS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12950.o-dba_ob_vector_index_tasks-of-mysql-mode.md) or [CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12960.o-dba_ob_vector_index_task_history-of-mysql-mode.md) view to view the task progress and history.

    <main id="notice" type='notice'>
      <h4>Notice</h4>
      <p>The preceding views cover partition rebuild tasks, segment merge tasks, and segment merge dump tasks. You can distinguish the task types by using the <code>TASK_TYPE</code> field in the views. </p>
    </main>

    You can view the current status of a task by using the `status` field:

    * 0 (PREPARE): The task is waiting to be executed.
    * 1 (RUNNING): The task is being executed.
    * 2 (PENDING): The task is paused.
    * 3 (FINISHED): The task is completed.

    After a task is completed, it is stored in the history table regardless of whether it was successful. For more information, see the corresponding view documentation.

3. Cancel a task

    To cancel a task, you can obtain the trace_id from the `DBA_OB_VECTOR_INDEX_TASKS` or `CDB_OB_VECTOR_INDEX_TASKS` view and execute the following command:

    ```sql
    ALTER SYSTEM CANCEL TASK <trace_id>;
    ```
    Here is an example:
    ```sql
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```

### Manually trigger a flush or compact (Alternative)

The flush and compact processes of incremental segments are usually triggered automatically by the background modules of the database system when specific conditions are met. OceanBase Database also allows you to manually trigger a flush or compact by using the `FLUSH_INDEX` and `COMPACT_INDEX` procedures in the `DBMS_VECTOR` package. This way, you can perform maintenance based on your actual needs.

For more information about the syntax and examples, see [FLUSH_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/600.flush-index-mysql.md) and [COMPACT_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/700.compact-index-mysql.md).

After the flush or compact is triggered, you can query the `DBA_OB_VECTOR_INDEX_TASKS` view. A task with `task_type=5` indicates a flush task, and a task with `task_type=6` indicates a compact task. These tasks are usually executed quickly. If no records are found in the `DBA_OB_VECTOR_INDEX_TASKS` view, you can query the `DBA_OB_VECTOR_INDEX_TASK_HISTORY` view for historical tasks.
