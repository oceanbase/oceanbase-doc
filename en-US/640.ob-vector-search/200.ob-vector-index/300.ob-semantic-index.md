# Semantic index

This topic describes how to use semantic indexes in OceanBase Database.

<main id="notice" type='explain'>
  <h4>Note</h4>
  <p>This feature is available only in OceanBase Database Enterprise Edition. </p>
</main>

## Overview

The semantic index leverages the built-in embedding capability of OceanBase Database to greatly simplify the process of using vector indexes. It makes the concept of vectors transparent to users: you can directly write the original data (such as text) that you want to store, and OceanBase Database will automatically convert it into vectors and build the index internally. During searches, you only need to provide the original search content, and OceanBase Database will automatically perform the embedding and search the vector index, significantly improving the ease of use.

Considering the performance overhead of embedding models, the semantic index provides both synchronous and asynchronous embedding options for users to choose from:
* Synchronous mode: Embedding and indexing occur immediately after data is written, ensuring real-time visibility of the data.
* Asynchronous mode: Data embedding and indexing are performed in batches by background tasks, significantly improving write performance. However, data visibility will have some delay. You can flexibly set the trigger cycle of the background tasks based on your requirements for data visibility.

Additionally, tables with semantic indexes can also perform brute-force searches. Brute-force search refers to searching by scanning the entire table to obtain the exact results of the top n closest rows.

## Supported features

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This feature is currently only supported for HNSW, HNSW_BQ, and HNSW_SQ indexes. </p>
</main>

The syntax for updating, deleting, and searching in the semantic index in the current version is the same as that for HNSW series indexes. The memory management method is also the same. The semantic index supports monitoring and maintenance processes. In asynchronous mode, incremental refreshes will also trigger data embedding.

The supported features are as follows:

| Module | Feature | Description |
|------|--------|------|
| DDL | Create a semantic index when creating a table | You can create a semantic index on a `VARCHAR` column when creating a table. |
| DDL | Create a semantic index after table creation | You can create a semantic index on a `VARCHAR` column in an existing table. |
| DDL | Multiple indexes on a single column | You can create multiple semantic indexes on the same column, which can be used with different models, distance algorithms, or index parameters. |
| Search | `semantic_distance` function | You can use this function to perform vector search by passing in the original data. |
| Search | `semantic_vector_distance` function | You can use this function to perform vector search by passing in the vector. The function has two usage scenarios:<ul><li>If the SQL statement contains the `APPROXIMATE` or `APPROX` clause, vector index search will be performed. </li><li>If the SQL statement does not contain the `APPROXIMATE` or `APPROX` clause, brute-force search will be performed by scanning the entire table. </li></ul> |
| DBMS_VECTOR | `REFRESH_INDEX` | You can use this function to perform index incremental refreshes and asynchronous embedding, just like with regular vector indexes. |
| DBMS_VECTOR | `REBUILD_INDEX` | You can use this function to perform index full rebuilds, just like with regular vector indexes. |

Some usage considerations are as follows:

* In synchronous mode, write performance may be affected by embedding performance. In asynchronous mode, data visibility will have some delay.
* For scenarios involving repeated searches, it is recommended to use the AI Function Service to pre-obtain the query vector to avoid embedding during each search.

## Prerequisites

### Register an embedding model and endpoint

Before using the semantic index, you must register an embedding model and endpoint. Here is an example:

```sql
CALL DBMS_AI_SERVICE.DROP_AI_MODEL ('ob_embed');
CALL DBMS_AI_SERVICE.DROP_AI_MODEL_ENDPOINT ('ob_embed_endpoint');

CALL DBMS_AI_SERVICE.CREATE_AI_MODEL(
'ob_embed', '{
    "type": "dense_embedding",
    "model_name": "BAAI/bge-m3"
}');

CALL DBMS_AI_SERVICE.CREATE_AI_MODEL_ENDPOINT (
'ob_embed_endpoint', '{
    "ai_model_name": "ob_embed",
    "url": "https://api.siliconflow.cn/v1/embeddings",
    "access_key": "sk-xxxxxxxxxxxxxxxxxxxxxxxxxxx",
    "provider": "siliconflow"
}');
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p>Please replace <code>access_key</code> with your actual API Key. The vector dimension of the BAAI/bge-m3 model is 1024. Therefore, you must use <code>dim=1024</code> when creating a semantic index. </p>
</main>

### Manually enable the semantic index

You can enable the semantic index feature by setting the tenant-level parameter `_enable_semantic_index` to ON. By default, this parameter is OFF:

```sql
ALTER SYSTEM SET _enable_semantic_index = true;
```

## Syntax and description

### Create

Semantic indexes support **creation during table creation** and **post-creation**. When creating an index, note the following:

* You must specify a `VARCHAR` column for the index.
* You can create multiple semantic indexes on the same column.
* The `model` and `sync_mode` parameters are not supported for regular vector indexes.
* The parameters and descriptions for post-creation are the same as those for creation during table creation.

:::tab
tab Create during table creation

You can create a semantic index by using the `CREATE TABLE` statement. You can specify the `sync_mode` or `async` parameter to initiate a background task for synchronization or asynchronous indexing. In synchronous mode, the system automatically converts `VARCHAR` data to vector data during data insertion. In asynchronous mode, the system periodically or manually completes the data conversion.

Syntax:

```sql
CREATE TABLE table_name (
    column_name1 data_type1,
    column_name2 VARCHAR, -- Text column
    ...,
    VECTOR INDEX index_name (column_name2) WITH (param1=value1, param2=value2, ...)
);
```

tab Post-creation

You can create a semantic index on an existing `VARCHAR` column of a table. When creating an index, you can specify the `sync_mode` or `async` parameter to initiate a background task for synchronization or asynchronous indexing. In synchronous mode, all existing `VARCHAR` data is embedded into vectors. In asynchronous mode, the system periodically or manually completes the embedding.

Syntax:

```sql
CREATE VECTOR INDEX index_name 
ON table_name(varchar_column_name) 
WITH (param1=value1, param2=value2, ...);
```

:::

The `param` parameters are described as follows:

| Parameter | Default Value | Value Range | Required | Description | Notes |
|------|--------|----------|----------|------|------|
| `distance` |  | `l2`/`inner_product`/`cosine` | Yes | Specifies the vector distance algorithm type. | `l2` indicates Euclidean distance, `inner_product` indicates inner product distance, and `cosine` indicates cosine distance. |
| `type` |  | `hnsw` / `hnsw_bq` / `hnsw_sq` | Yes | Specifies the index algorithm type. |  |
| `lib` | `vsag` | `vsag` | No | Specifies the vector index library type. | Only the VSAG vector library is supported. |
| `model` |  | Name of a registered model | Yes | Specifies the name of the large language model used for embedding. | You must register the model with the AI function service before creating an index.<main id="notice" type='notice'><h4>Note</h4><p>This parameter is not supported for regular vector indexes.</p></main> |
| `dim` |  | Positive integer, up to 4096 | Yes | Specifies the vector dimension after embedding. | The value must match the dimension provided by the model. |
| `sync_mode` | `async` | `immediate`/`manual`/`async` | No | Specifies the synchronization mode between data and the index. | `immediate` indicates synchronous mode, `manual` indicates manual mode, and `async` indicates asynchronous mode.<main id="notice"><h4>Note</h4><p>This parameter is not supported for regular vector indexes.</p></main> |
| `sync_interval` | `10s` | Time interval, such as `10s`, `1h`, or `1d` | No | Specifies the trigger cycle of the background task in asynchronous mode. | The numeric part must be a positive number, and the unit can be seconds (s), hours (h), or days (d). |

Other vector index parameters (such as `m`, `ef_construction`, and `ef_search`) are used in the same way as in regular HNSW/HNSW_BQ indexes. For more information, see the HNSW series index documentation in the related topics at the end of this document.

### Search

Semantic indexes support two search methods:

* Text-based search
* Vector search
    * You can specify the `APPROXIMATE`/`APPROX` clause to perform nearest-neighbor search using the vector index.
    * You can also omit the `APPROXIMATE`/`APPROX` clause to perform brute-force search using full-table scanning.

The following are the usage notes and considerations for using hints:

* When multiple semantic indexes exist on the same column, you must use the `VECTOR_INDEX` hint to explicitly specify the vector index to be used. Otherwise, an error will be returned. With the `VECTOR_INDEX` hint, you can not only select a specific vector index in the query statement but also flexibly configure pre-filtering or post-filtering conditions to improve the accuracy and flexibility of the search.
* The `VECTOR_INDEX` hint can be used with the `INDEX` hint.
* For more information about the usage of the above two hints, see [VECTOR_INDEX Hint](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/100.basic-elements-of-mysql-mode/600.annotation-of-mysql-mode/400.hint-of-mysql-mode/200.hint-list-of-mysql-mode/200.optimizer-hint-of-mysql-mode/900.hints-related-to-vector-index-hint-of-mysql-mode.md).

:::tab
tab Text-based search

You can use the `semantic_distance` expression to perform vector search by passing in the original text.

Syntax:

```sql
SELECT ... FROM table_name 
ORDER BY semantic_distance(column_name, 'query_text') [APPROXIMATE|APPROX] 
LIMIT n;
```

where:
* `column_name`: the text column specified when the semantic index was created.
* `query_text`: the original text to be searched.
* `n`: the number of rows to return.

tab Vector search

1. With the `APPROXIMATE` clause: You can use the `semantic_vector_distance` expression to perform vector search by passing in the vector. When the search statement contains the `APPROXIMATE`/`APPROX` clause, the vector index is used for search. Syntax:

    ```sql
    SELECT ... FROM table_name 
    ORDER BY semantic_vector_distance(column_name, 'query_vector') [APPROXIMATE|APPROX] 
    LIMIT n;
    ```

    where:
    * `column_name`: the text column specified when the semantic index was created.
    * `query_vector`: the query vector.
    * `n`: the number of rows to return.

2. Without the `APPROXIMATE` clause: You can use the `semantic_vector_distance` expression to perform vector search by passing in the vector. When the search statement does not contain the `APPROXIMATE`/`APPROX` clause, the system performs brute-force search by scanning the entire table to obtain the exact results of the nearest n rows. During the search, the system retrieves the type of `distance` from the table schema and performs a full-table scan. The vector distance is calculated for each row to ensure the accuracy of the results. Syntax:

    ```sql
    SELECT ... FROM table_name 
    ORDER BY semantic_vector_distance(column_name, 'query_vector') 
    LIMIT n;
    ```
    The parameters are the same as those in the case with the `APPROXIMATE` clause.

:::

For more information about the syntax of the `APPROXIMATE`/`APPROX` clause, see the HNSW series index documentation in the related topics at the end of this document.

## Create, update, search, and delete examples

DML operations (`INSERT`, `UPDATE`, `DELETE`) for semantic indexes are the same as for regular vector indexes. When inserting or updating `VARCHAR` data, the system synchronizes or asynchronously embeds vectors based on the `sync_mode` parameter.

### Create during table creation

Create the `vector_idx` index when you create the `items` table:

```sql
-- Assume that the ob_embed model has been created (see "Prerequisites" for registration details)
CREATE TABLE items (
    id BIGINT PRIMARY KEY,
    doc VARCHAR(100),
    VECTOR INDEX vector_idx(doc)
    WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=async, sync_interval=10s)
);
```

Insert data into the `items` table. The system automatically embeds the vector:

```sql
INSERT INTO items(id, doc) VALUES(1, 'Rose');
```

### Create after table creation

Create the `items` table first, then use the `CREATE VECTOR INDEX` statement to create the `vector_idx` index:

```sql
CREATE TABLE items (
    id BIGINT PRIMARY KEY,
    doc VARCHAR(100)
);

-- Assume that the ob_embed model has been created (see "Prerequisites" for registration details)
CREATE VECTOR INDEX vector_idx
ON items (doc)
WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=async, sync_interval=10s);
```

Insert data into the `items` table. The system automatically embeds the vector:

```sql
INSERT INTO items(id, doc) VALUES(1, 'Rose');
```

### Update

When updating `VARCHAR` data, the system re-embeds the vector:

* In synchronous mode: The vector is re-embedded immediately after the update.
* In asynchronous mode: The vector is re-embedded by a background task during the next trigger cycle.

Example:

```sql
UPDATE items SET doc = 'Lily' WHERE id = 1;
```

### Delete

Deletion operations are the same as for regular vector indexes. Simply delete the data.

Example:

```sql
DELETE FROM items WHERE id = 1;
```

### Search

:::tab
tab Search using raw text

```sql
-- Assume that the ob_emb model has been created
CREATE TABLE items (
    id INT PRIMARY KEY,
    doc varchar(100),
    VECTOR INDEX vector_idx(doc)
    WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=immediate)
);

INSERT INTO items(id, doc) VALUES(1, 'Rose');
INSERT INTO items(id, doc) VALUES(2, 'Sunflower');
INSERT INTO items(id, doc) VALUES(3, 'Rose');
INSERT INTO items(id, doc) VALUES(4, 'Sunflower');
INSERT INTO items(id, doc) VALUES(5, 'Rose');

-- Search using raw text
SELECT id, doc FROM items
ORDER BY semantic_distance(doc, 'Sunflower')
APPROXIMATE LIMIT 3;
```

The result set is as follows:

```sql
+----+-----------+
| id | doc       |
+----+-----------+
|  2 | Sunflower |
|  4 | Sunflower |
|  5 | Rose      |
+----+-----------+
3 rows in set
```

tab Search using a vector (with APPROXIMATE clause)

Use the `semantic_vector_distance` expression to search by vector. If the `APPROXIMATE` or `APPROX` clause is present in the search statement, the vector index is used for the search.

```sql
-- Assume that the ob_emb model has been created (see "Prerequisites" for registration details)
CREATE TABLE items (
    id INT PRIMARY KEY,
    doc varchar(100),
    VECTOR INDEX vector_idx(doc)
    WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=immediate)
);

INSERT INTO items(id, doc) VALUES(1, 'Rose');
INSERT INTO items(id, doc) VALUES(2, 'Lily');
INSERT INTO items(id, doc) VALUES(3, 'Sunflower');
INSERT INTO items(id, doc) VALUES(4, 'Rose');

-- Obtain the query vector
SET @query_vector = AI_EMBED('ob_embed', 'Sunflower');

-- Search using the vector
SELECT id, doc FROM items
ORDER BY semantic_vector_distance(doc, @query_vector)
APPROXIMATE LIMIT 3;
```

The result set is as follows:

```shell
+----+-----------+
| id | doc       |
+----+-----------+
|  3 | Sunflower |
|  1 | Rose      |
|  4 | Rose      |
+----+-----------+
3 rows in set
```

tab Search using a vector (without APPROXIMATE clause)

```sql
-- Perform a brute-force search using the vector (exact results)
SELECT id, doc FROM items
ORDER BY semantic_vector_distance(doc, @query_vector)
LIMIT 3;
```

The result set is as follows:

```shell
+----+-----------+
| id | doc       |
+----+-----------+
|  3 | Sunflower |
|  4 | Rose      |
|  1 | Rose      |
+----+-----------+
3 rows in set
```

:::
