# Create a semantic index

This topic describes how to create a semantic index in OceanBase Database.

## Overview

The semantic index leverages the built-in embedding capabilities of OceanBase Database to greatly simplify the process of using vector indexes. It makes the concept of vectors transparent to users: you can directly write the original data (such as text) that you want to store, and OceanBase Database will automatically convert it into vectors and build an index internally. During retrieval, you only need to provide the original query content, and OceanBase Database will automatically embed it and retrieve the vector index, significantly enhancing the ease of use.

Considering the performance overhead of embedding models, the semantic index provides both synchronous and asynchronous embedding options for users to choose from:
* Synchronous mode: Embedding and indexing are performed immediately after data is written, ensuring real-time data visibility.
* Asynchronous mode: Data embedding and indexing are batch processed by background tasks, which significantly improves write performance, but with delayed data visibility. You can flexibly set the trigger cycle of background tasks based on your requirements for data visibility.

Additionally, tables with semantic indexes can also perform brute-force searches. Brute-force search refers to a full-table scan to retrieve the exact results of the nearest n rows.

## Supported features

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>This feature is only supported for the HNSW and HNSW_BQ indexes in the current version. </p>
</main>

This feature supports the full lifecycle of semantic index creation, update, deletion, and retrieval, and is compatible with the `REFRESH_INDEX` and `REBUILD_INDEX` procedures in the `DBMS_VECTOR` system package. The syntax for updates, deletions, and retrievals is identical to that of regular vector indexes. In asynchronous mode, `REFRESH_INDEX` will additionally trigger data embedding. For details on creation and retrieval, see the following sections.

The supported features are as follows:

| Module | Feature | Description |
|------|--------|------|
| DDL | Create a semantic index when creating a table | You can create a semantic index on a `VARCHAR` column when creating a table. |
| DDL | Create a semantic index after table creation | You can create a semantic index on a `VARCHAR` column of an existing table. |
| Retrieval | `semantic_distance` function | This function allows you to perform vector retrieval by passing in the original data. |
| Retrieval | `semantic_vector_distance` function | This function allows you to perform vector retrieval by passing in a vector. It has two usage scenarios:<ul><li>When the SQL statement contains the `APPROXIMATE` or `APPROX` clause, it will use the vector index for retrieval.</li><li>When the SQL statement does not contain the `APPROXIMATE` or `APPROX` clause, it will perform a brute-force search by scanning the entire table.</li></ul> |
| DBMS_VECTOR | `REFRESH_INDEX` | The usage is the same as for regular vector indexes. It is used to perform incremental index refreshes and triggers embedding in asynchronous mode. |
| DBMS_VECTOR | `REBUILD_INDEX` | The usage is the same as for regular vector indexes. It is used to perform full index rebuilds. |

Some usage considerations are as follows:

* In synchronous mode, write performance may be affected by the embedding performance. In asynchronous mode, data visibility will be delayed.
* For scenarios involving repeated retrievals, it is recommended to use the AI Function Service to pre-obtain the query vector, avoiding embedding during each retrieval.

## Prerequisites

### Register an embedding model and endpoint

Before using a semantic index, you must register an embedding model and endpoint. Here is an example:

```sql
CALL DBMS_AI_SERVICE.DROP_AI_MODEL ('ob_embed');
CALL DBMS_AI_SERVICE.DROP_AI_MODEL_ENDPOINT ('ob_embed_endpoint');

CALL DBMS_AI_SERVICE.CREATE_AI_MODEL(
'ob_embed', '{
    "type": "dense_embedding",
    "model_name": "BAAI/bge-m3"
}');

CALL DBMS_AI_SERVICE.CREATE_AI_MODEL_ENDPOINT (
'ob_embed_endpoint', '{
    "ai_model_name": "ob_embed",
    "url": "https://api.siliconflow.cn/v1/embeddings",
    "access_key": "sk-xxxxxxxxxxxxxxxxxxxxxxxxxxx",
    "provider": "siliconflow"
}');
```

<main id="notice" type='explain'>
<h4>Note</h4>
<p>Replace <code>access_key</code> with your actual API Key. The vector dimension of the BAAI/bge-m3 model is 1024. Therefore, you must specify <code>dim=1024</code> when creating a semantic index. </p>
</main>

### Enable the semantic index feature

You can enable the semantic index feature by setting the tenant-level parameter `_enable_semantic_index` to `ON`. By default, this parameter is `OFF`:

```sql
ALTER SYSTEM SET _enable_semantic_index = true;
```

## Syntax and description

The semantic index supports two creation methods: **creating it when creating a table** and **creating it after table creation**. When creating an index, note the following:

* You must specify a `VARCHAR` column for the index.
* The `model` and `sync_mode` parameters cannot be configured for regular vector indexes.
* The parameters and descriptions for creating an index after table creation are the same as those for creating it when creating a table.

### Create an index when creating a table

You can use the `CREATE TABLE` statement to create a semantic index. You can specify the index parameters to initiate a background task in synchronous or asynchronous mode. In synchronous mode, the `VARCHAR` data is automatically converted into vector data during insertion. In asynchronous mode, the data conversion is completed periodically or manually.

#### Syntax

```sql
CREATE TABLE table_name (
    column_name1 data_type1,
    column_name2 VARCHAR, -- Text column
    ...,
    VECTOR INDEX index_name (column_name2) WITH (param1=value1, param2=value2, ...)
);
```

#### Parameter description

| Parameter | Default value | Value range | Required | Description | Remarks |
|------|--------|----------|----------|------|------|
| `distance` |  | `l2`/`inner_product`/`cosine` | Yes | Specifies the vector distance algorithm. | `l2` specifies the Euclidean distance, `inner_product` specifies the inner product distance, and `cosine` specifies the cosine distance. |
| `type` |  | `hnsw` / `hnsw_bq` | Yes | Specifies the index algorithm. |  |
| `lib` | `vsag` | `vsag` | No | Specifies the vector index library type. | Only the VSAG vector library is supported. |
| `model` |  | Name of a registered model | Yes | Specifies the name of the large language model used for embedding. | You must register this model with the AI Function Service before creating an index. <main id="notice" type='notice'><h4>Note</h4><p>Regular vector indexes do not support this parameter. </p></main> |
| `dim` |  | A positive integer, up to 4096 | Yes | Specifies the vector dimension after embedding. | It must match the dimension provided by the model. |
| `sync_mode` | `async` | `immediate`/`manual`/`async` | No | Specifies the synchronization mode for data and index. | `immediate` specifies synchronous mode, `manual` specifies manual mode, and `async` specifies asynchronous mode. <main id="notice"><h4>Note</h4><p>Regular vector indexes do not support this parameter. </p></main> |
| `sync_interval` | `10s` | Time interval, such as `10s`, `1h`, or `1d` | No | Specifies the trigger cycle of background tasks in asynchronous mode. | The numeric part must be a positive number, and the unit can be seconds (s), hours (h), or days (d). |

Other vector index parameters (such as `m`, `ef_construction`, and `ef_search`) are used in the same way as in regular vector indexes. For more information, see the relevant documentation at the end of this topic.

### Create an index after table creation

You can create a semantic index on a `VARCHAR` column of an existing table. When creating an index after table creation, you can specify the index parameters to initiate a background task in synchronous or asynchronous mode. In synchronous mode, all existing `VARCHAR` data will be embedded into vectors. In asynchronous mode, the embedding will be completed periodically or manually.

#### Syntax

```sql
CREATE VECTOR INDEX index_name 
ON table_name(varchar_column_name) 
WITH (param1=value1, param2=value2, ...);
```

#### Parameter description

The parameter description is the same as when creating an index when creating a table. For more information, see the preceding section.

## Create, update, and delete examples

The DML operations (`INSERT`, `UPDATE`, and `DELETE`) for semantic indexes are the same as those for regular vector indexes. When you insert or update data of the `VARCHAR` type, the system synchronously or asynchronously embeds the data based on the value of the `sync_mode` parameter.

### Create during table creation

Create the `vector_idx` index when you create the `items` table:

```sql
-- Assume that the ob_embed model has been created (please refer to the "Prerequisites" section for registration)
CREATE TABLE items (
    id BIGINT PRIMARY KEY,
    doc VARCHAR(100),
    VECTOR INDEX vector_idx(doc)
    WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=async, sync_interval=10s)
);
```

Insert data into the `items` table. The system automatically embeds the data:

```sql
INSERT INTO items(id, doc) VALUES(1, 'Rose');
```

### Create after table creation

Create the `items` table first, and then create the `vector_idx` index by using the `CREATE VECTOR INDEX` statement:

```sql
CREATE TABLE items (
    id BIGINT PRIMARY KEY,
    doc VARCHAR(100)
);

-- Assume that the ob_embed model has been created (please refer to the "Prerequisites" section for registration)
CREATE VECTOR INDEX vector_idx
ON items (doc)
WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=async, sync_interval=10s);
```

Insert data into the `items` table. The system automatically embeds the data:

```sql
INSERT INTO items(id, doc) VALUES(1, 'Rose');
```

### Update

When you update data of the `VARCHAR` type, the system re-embeds the data.

* In synchronous mode: The system re-embeds the data immediately after the update.
* In asynchronous mode: The system re-embeds the data in the background when the next trigger cycle is reached.

Example:

```sql
UPDATE items SET doc = 'Lily' WHERE id = 1;
```

### Delete

The delete operation is the same as that for regular vector indexes. You can directly delete data.

Example:

```sql
DELETE FROM items WHERE id = 1;
```

## Search

A semantic index supports the following search methods:

* Text-based search
* Vector-based search

For more information about the `APPROXIMATE`/`APPROX` clause, see the relevant section in the "Create a vector index" topic.

### Text-based search

You can use the `semantic_distance` expression to perform a vector-based search by passing in the original text.

#### Syntax

```sql
SELECT ... FROM table_name 
ORDER BY semantic_distance(column_name, 'query_text') [APPROXIMATE|APPROX] 
LIMIT n;
```

where:
* `column_name` specifies the text column specified when the semantic index is created.
* `query_text` specifies the original text to be searched.
* `n` specifies the number of rows to be returned.

#### Example

```sql
-- Assume that the ob_emb model has been created.
CREATE TABLE items (
    id INT PRIMARY KEY,
    doc varchar(100),
    VECTOR INDEX vector_idx(doc)
    WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=immediate)
);

INSERT INTO items(id, doc) VALUES(1, 'Rose');
INSERT INTO items(id, doc) VALUES(2, 'Sunflower');
INSERT INTO items(id, doc) VALUES(3, 'Rose');
INSERT INTO items(id, doc) VALUES(4, 'Sunflower');
INSERT INTO items(id, doc) VALUES(5, 'Rose');

-- Perform a text-based search.
SELECT id, doc FROM items
ORDER BY semantic_distance(doc, 'Sunflower')
APPROXIMATE LIMIT 3;
```

The return result is as follows:

```sql
+----+-----------+
| id | doc       |
+----+-----------+
|  2 | Sunflower |
|  4 | Sunflower |
|  5 | Rose      |
+----+-----------+
3 rows in set
```

### Vector-based search (with APPROXIMATE clause)

You can use the `semantic_vector_distance` expression to perform a vector-based search by passing in the vector. If the `APPROXIMATE`/`APPROX` clause is specified in the search statement, the vector index is used for the search.

#### Syntax

```sql
SELECT ... FROM table_name 
ORDER BY semantic_vector_distance(column_name, 'query_vector') [APPROXIMATE|APPROX] 
LIMIT n;
```

where:
* `column_name` specifies the text column specified when the semantic index is created.
* `query_vector` specifies the query vector.
* `n` specifies the number of rows to be returned.

#### Example

```sql
-- Assume that the ob_emb model has been created. For more information, see the "Prerequisites" section.
CREATE TABLE items (
    id INT PRIMARY KEY,
    doc varchar(100),
    VECTOR INDEX vector_idx(doc)
    WITH (distance=l2, lib=vsag, type=hnsw, model=ob_embed, dim=1024, sync_mode=immediate)
);

INSERT INTO items(id, doc) VALUES(1, 'Rose');
INSERT INTO items(id, doc) VALUES(2, 'Lily');
INSERT INTO items(id, doc) VALUES(3, 'Sunflower');
INSERT INTO items(id, doc) VALUES(4, 'Rose');

-- Obtain the query vector.
SET @query_vector = AI_EMBED('ob_embed', 'Sunflower');

-- Perform a vector-based search.
SELECT id, doc FROM items
ORDER BY semantic_vector_distance(doc, @query_vector)
APPROXIMATE LIMIT 3;
```

The return result is as follows:

```shell
+----+-----------+
| id | doc       |
+----+-----------+
|  3 | Sunflower |
|  1 | Rose      |
|  4 | Rose      |
+----+-----------+
3 rows in set
```

### Vector-based search (without APPROXIMATE clause)

You can use the `semantic_vector_distance` expression to perform a vector-based search by passing in the vector. If the `APPROXIMATE`/`APPROX` clause is not specified in the search statement, a brute-force search is performed by scanning the entire table. The search returns the exact results of the first n rows with the smallest distances. During the search, the `distance` type is obtained from the table schema, and the entire table is scanned. The vector distance is calculated for each row to ensure the exact results.

#### Syntax

```sql
SELECT ... FROM table_name 
ORDER BY semantic_vector_distance(column_name, 'query_vector') 
LIMIT n;
```

where:
* `column_name` specifies the text column specified when the semantic index is created.
* `query_vector` specifies the query vector.
* `n` specifies the number of rows to be returned.

#### Example

```sql
-- Perform a brute-force search (exact results).
SELECT id, doc FROM items
ORDER BY semantic_vector_distance(doc, @query_vector)
LIMIT 3;
```

The return result is as follows:

```shell
+----+-----------+
| id | doc       |
+----+-----------+
|  3 | Sunflower |
|  4 | Rose      |
|  1 | Rose      |
+----+-----------+
3 rows in set
```

## Index maintenance

You can use the `DBMS_VECTOR` system package to maintain a semantic index, including incremental refresh and full rebuild.

### Incremental refresh

If a large amount of data is written after the index is created, we recommend that you perform an incremental refresh by using the `REFRESH_INDEX` procedure. For more information, see the relevant topic.

The following points apply to semantic indexes:
* The usage is the same as that of a regular vector index. For more information, see the relevant topic.
* In asynchronous mode, `REFRESH_INDEX` will trigger additional embedding of data to ensure that incremental data is correctly converted into vectors and added to the index.

### Full refresh (rebuild)

If a large amount of data is updated or deleted after the index is created, we recommend that you perform a full refresh by using the `REBUILD_INDEX` procedure. For more information, see the relevant topic.

The following points apply to semantic indexes:
* The usage is the same as that of a regular vector index. For more information, see the relevant topic.
* The task merges incremental data and snapshots.
