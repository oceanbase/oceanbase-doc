# Vector index

This topic describes how to create, search, maintain, and drop vector indexes in OceanBase Database.

## Index types

OceanBase Database supports the following vector index types:

| Index type | Description | Applicable scenarios |
|-----------|------|----------|
| HNSW      | The maximum dimension of the indexed column is 4096. The HNSW index is an in-memory index that must be fully loaded into memory. |  |
| HNSW_SQ   | The HNSW_SQ index provides similar construction speed, search performance, and recall rate to the HNSW index, but the total memory usage is reduced to 1/2 to 1/3 of the original. | Scenarios with high requirements for performance and recall rate. |
| HNSW_BQ   | The HNSW_BQ index has a slightly lower recall rate than the HNSW index but significantly reduces memory usage. The RabbitQ quantization compression algorithm can compress vectors to 1/32 of their original size. As the vector dimension increases, the memory optimization effect of the HNSW_BQ index becomes more pronounced. |  |
| IVF| The IVF index is implemented based on a database table and does not occupy resident memory. | Scenarios with low performance requirements, large data volumes, and cost sensitivity. |
| IVF_PQ| The IVF_PQ index is implemented based on a database table and does not occupy resident memory. It applies the PQ quantization technique to the IVF index. The recall rate of the IVF_PQ index is slightly lower than that of the IVF index, but its performance is higher. The PQ quantization compression algorithm can generally compress vectors to 1/16 to 1/32 of their original size. | Scenarios with low performance requirements, large data volumes, and cost sensitivity. |
| IVF_SQ (Experimental feature)| The IVF_SQ index is implemented based on a database table and does not occupy resident memory. It applies the SQ quantization technique to the IVF index. The recall rate of the IVF_SQ index is slightly lower than that of the IVF index, but its performance is higher. The SQ quantization compression algorithm can generally compress vectors to 1/3 to 1/4 of their original size. | Scenarios with low performance requirements, large data volumes, and cost sensitivity. |

Other notes:

* The dense index supports L2, inner product (IP), and cosine distance as index distance algorithms.
* Vector index search supports the use of partial distance functions. For more information, see [Use SQL functions](../250.ob-vector-function.md).
* Vector search with filter conditions is supported. Filter conditions can be scalar conditions or spatial relationships such as ST_Intersects. Multi-value indexes, full-text indexes, and global indexes cannot be used as pre-filterers.
* You can create vector indexes and full-text indexes in the same table. Vector indexes include dense and in-memory sparse indexes.
* For information about the support of vector indexes for offline DDL operations, see [Offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md).
* Vector index search supports the use of partial distance functions. For more information, see [Use SQL functions](../250.ob-vector-function.md).

Limitations:

* In V4.4.1, you cannot create a columnstore vector index.

## Configure the memory for vector indexes

OceanBase Database allows you to configure the memory for vector indexes by setting the [ob_vector_memory_limit_percentage](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md) parameter:

* **Before you use the HNSW/HNSW_SQ/HNSW_BQ vector index in versions earlier than V4.4.1**, you must manually set the `ob_vector_memory_limit_percentage` parameter to enable vector search. We recommend that you set the parameter to `30` for optimal search performance. If you do not set the parameter, the system does not allocate memory to the vector index, and an error is returned when you create the index. Here is an example of how to configure the parameter:
    ```sql
    ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
    ```

* **Starting from V4.4.1**, vector search is enabled by default. The default value of `0` indicates adaptive mode, where the system automatically adjusts the memory usage ratio for vector indexes in the tenant without manual intervention:
  * If the actual memory of the tenant is 8 GB or less, the value is automatically adjusted to `40`.
  * If the actual memory of the tenant is more than 8 GB, the value is automatically adjusted to `50`.

## Query index memory estimation and actual usage

You can use the `DBMS_VECTOR` system package to estimate index memory:

* Before you create a table, you can call the [INDEX_VECTOR_MEMORY_ADVISOR](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/500.index-vector-memory-advisor-mysql.md) procedure to estimate the index memory.
* After you create a table and insert data into it, you can call the [INDEX_VECTOR_MEMORY_ESTIMATE](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/400.index-vector-memory-estimate-mysql.md) procedure to analyze the index memory.

The vector index memory estimation returns two pieces of information: the minimum memory configuration required to create a vector index, and the actual memory usage after the HNSW_SQ and IVF indexes are created.

We also provide the `load_vector_index_on_follower` parameter to control whether the `follower` role automatically loads the memory vector index. For more information, see [load_vector_index_on_follower](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/4235.load_vector_index_on_follower.md). If weak reads are not required, you can disable this parameter to reduce the memory occupied by the vector index.

## Syntax and description

OceanBase Database supports creating vector indexes in two ways: **creating vector indexes when creating tables** and **creating vector indexes after table creation**. When creating vector indexes, note the following:

* The `VECTOR` keyword is required.
* The parameters and descriptions for creating vector indexes after table creation are the same as those for creating vector indexes when creating tables.
* If the data volume is large, we recommend that you write the data first and then create the index to achieve the best search performance.
* We recommend that you create the HNSW_SQ, IVF, IVF_SQ, or IVF_PQ index after writing data and rebuild the index after writing a large amount of incremental data. For more information about how to create each index, see the specific examples in the following sections.

```sql
        ELSE COALESCE(SUM(result_value), 'not support')

        CASE
            WHEN vdt.data_type_class IN (1, 2, 3, 4, 6, 8, 9, 14, 27, 28) THEN 8 -- numeric data types, extra_info_size += 8

        oceanbase.__all_column oc
    JOIN
        oceanbase.__all_virtual_data_type vdt
    ON
        oc.data_type = vdt.data_type
    WHERE
        oc.rowkey_position != 0
        AND oc.table_id = (SELECT table_id FROM oceanbase.__all_table WHERE table_name = @table_name)
) AS result_table;

-- The result is 8 bytes.
```

## Search syntax and description

Vector index search is an approximate nearest neighbor search and does not guarantee 100% accuracy in the results. The accuracy of vector search is measured by the recall rate. For example, if the search returns 9 correct results out of 10 nearest neighbors, the recall rate is 90%. The recall rate is described as follows:

* The recall rate is affected by the construction parameters and search parameters.
* Index search parameters are specified when creating an index and cannot be modified afterward. However, you can set these parameters through session variables. For HNSW/HNSW_SQ/HNSW_BQ indexes, use the `ob_hnsw_ef_search` parameter. For IVF indexes, use the `ob_ivf_nprobes` parameter. If a session variable is set, its value is prioritized. For more information, see [ob_hnsw_ef_search](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

The syntax for searching a dense index is as follows:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num);
```

The search usage is described as follows:

* Search requirements:
  * The `APPROXIMATE`/`APPROX` keyword must be specified for the search to use the vector index instead of a full table scan.
  * The `ORDER BY` and `LIMIT` clauses must be included.
  * The `ORDER BY` clause only supports a single vector condition.
  * The value of `LIMIT + OFFSET` must be in the range `(0, 16384]`.

* Distance function usage rules:
  * If the `APPROXIMATE`/`APPROX` keyword is specified, the search will use the vector index if the distance function is supported in the current version and matches the vector index algorithm.
  * If the `APPROXIMATE`/`APPROX` keyword is specified, the search will not use the vector index if the distance function does not match the vector index algorithm, but it will not return an error.
  * If the `APPROXIMATE`/`APPROX` keyword is specified, the search will not use the vector index and will return an error if the distance function is not supported in the current version.
  * If the `APPROXIMATE`/`APPROX` keyword is not specified, the search will not use the vector index if the distance function is supported in the current version, but it will not return an error.

* Other considerations:
  * The `WHERE` condition will be used as a filter after vector index search.
  * If the `LIMIT` clause is not specified, an error will be returned.

## Maintenance

When the amount of incremental data is large, the search performance will be affected. To reduce the amount of incremental data in the data table, OceanBase Database provides the `DBMS_VECTOR` package to maintain vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF_SQ/IVF_PQ indexes do not support incremental refresh. </p>
</main>

If you write a large amount of data after you create an index, we recommend that you use the `REFRESH_INDEX` procedure to perform an incremental refresh. For more information, see [REFRESH_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/200.refresh-index-mysql.md).

The system checks for incremental data every 15 minutes. If the number of incremental data entries exceeds 10,000, the system automatically performs an incremental refresh.

### Full refresh (rebuild)

#### Manual full table rebuild

If a large amount of data is updated or deleted after an index is created, we recommend that you use the `REBUILD_INDEX` procedure to perform a full refresh. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

The system checks for a full refresh every 24 hours. If the new data exceeds 20% of the original data, a full refresh is automatically performed. The full refresh is performed in the background and asynchronously. First, a new index is created, and then the old index is replaced. During the rebuild, the old index remains available, but the overall process is relatively slow.

We also provide the `vector_index_memory_saving_mode` parameter to control the memory usage during index rebuild. Enabling this mode can reduce the memory consumption during the rebuild of vector indexes in partitioned tables. Typically, vector index rebuild requires twice the memory of the index. When this mode is enabled, the system temporarily deletes the memory index of a partition after the index is built for that partition, thereby effectively reducing the total memory required for the rebuild. For more information, see [vector_index_memory_saving_mode](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md).

Consider the following notes:

* When you perform [offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) operations (such as `ALTER TABLE` to modify the table structure or primary key), the index table is rebuilt. Since parallelism cannot be specified during index rebuild, the system uses a single thread by default. Therefore, when the amount of data is large, the rebuild process is relatively slow, which affects the overall efficiency of the offline DDL operation.
* If you need to modify the index parameters during index rebuild, you must specify both `type` and `distance` in the parameter list, and they must be consistent with the original index type. For example, if the original index type is `hnsw` and the distance algorithm is `l2`, you must specify `type=hnsw` and `distance=l2` during the rebuild.
* During index rebuild, the following operations are supported:
    * Modify the values of `m`, `ef_search`, and `ef_construction`.
    * Online rebuild the `ef_search` parameter.
    * Rebuild the index type between `hnsw` and `hnsw_sq`.
    * Rebuild the index type between `ivf_flat` and `ivf_flat`, `ivf_sq8` and `ivf_sq8`, and `ivf_pq` and `ivf_pq`.
    * Set the parallelism during rebuild. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).
* During index rebuild, the following operations are not supported:
    * Modify the `type` and `distance` types.
    * Rebuild the index type between `hnsw` and `ivf`.
    * Rebuild the index type between `hnsw` and `hnsw_bq`.
    * Cross-rebuild the index types between `ivf_flat`, `ivf_pq`, and `ivf_sq8`.

#### Automatic partition rebuild (recommended)

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><li>This feature is available starting from OceanBase Database V4.4.1. If you upgrade your vector cluster from a previous version to V4.4.1, you need to manually perform a full table rebuild for all vector indexes after the upgrade. Otherwise, the automatic partition rebuild task may not execute after the upgrade. </li><li>This feature is supported only for HNSW, HNSW_SQ, and HNSW_BQ indexes. </li></p>
</main>

The current version triggers automatic partition rebuild tasks in the following two scenarios:

* When you execute vector index search statements.
* During scheduled checks, which you can manually configure to execute at specific intervals.

1. Configure the execution interval

    In the `oceanbase` database, configure the execution interval using the [vector_index_optimize_duty_time](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8250.vector_index_optimize_duty_time.md) parameter. Here is an example:

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    After the above configuration, the partition rebuild task will only execute between 23:00:00 and 24:00:00. It will not execute during other time periods. For more information about the parameters, see the corresponding configuration item documentation.

2. View task progress and history

    You can query the [CDB/DBA_OB_VECTOR_INDEX_TASKS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12950.o-dba_ob_vector_index_tasks-of-mysql-mode.md) or [CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12960.o-dba_ob_vector_index_task_history-of-mysql-mode.md) view to view the task progress and history.

    You can determine the current status of the task based on the `status` field:

    * 0 (PREPARE): The task is waiting to be executed.
    * 1 (RUNNING): The task is being executed.
    * 2 (PENDING): The task is paused.
    * 3 (FINISHED): The task has been completed.

    The tasks with the `status=FINISHED` are stored in the history table regardless of whether they were successful. For more information, see the corresponding view documentation.

3. Cancel a task

    To cancel a task, you can obtain the trace_id from the `DBA_OB_VECTOR_INDEX_TASKS` or `CDB_OB_VECTOR_INDEX_TASKS` view and execute the following command:

    ```sql
    ALTER SYSTEM CANCEL TASK <trace_id>;
    ```
    Here is an example:
    ```sql
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```

## Performance optimization

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Only IVF indexes are supported. </p>
</main>

OceanBase Database provides an automatic performance optimization mechanism for IVF indexes. This mechanism improves search performance by managing cache and performing regular maintenance.

### Optimization mechanism

The performance optimization of IVF indexes includes two automatic tasks:

1. Cache warming task: The system periodically checks all IVF indexes. If an index's corresponding cache does not exist, it automatically triggers cache warming to load the index data into memory. Additionally, when an IVF index is created, the cache is automatically warmed.
2. Cache cleanup task: The system periodically checks all IVF caches. If a cache's corresponding index has been deleted, it automatically cleans up the invalid cache to release memory resources. Additionally, when an IVF index is deleted, the cache is automatically cleaned up.

### Configure the execution cycle of optimization

The system allows you to customize the execution window for performance optimization tasks to avoid impacting performance during peak business hours.

In the `oceanbase` database, you can set the execution cycle using the `vector_index_optimize_duty_time` parameter:

```sql
ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
```

The configuration details are as follows:

* The time format is `[start time, end time]`.
* The above configuration indicates that the optimization task is executed only between 23:00:00 and 24:00:00.
* Optimization tasks are not initiated during other periods to avoid affecting normal business operations.

### Monitor optimization tasks

OceanBase Database provides the capability to monitor optimization tasks for vector indexes:

* You can view the status of running or pending tasks using the [DBA_OB_VECTOR_INDEX_TASKS](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/24150.o-dba_ob_vector_index_tasks-of-sys-tenant.md) view.
* You can view the history of completed tasks using the [DBA_OB_VECTOR_INDEX_TASK_HISTORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12960.o-dba_ob_vector_index_task_history-of-mysql-mode.md) view.

Here are some examples of how to use these features:

1. View the current task status

    You can use the `DBA_OB_VECTOR_INDEX_TASKS` view to check the status of running or pending tasks:

    ```sql
    -- Query in a MySQL tenant
    SELECT * FROM oceanbase.DBA_OB_VECTOR_INDEX_TASKS;
    ```

    Example output:


    * `TASK_TYPE = 2`: IVF cache warming task.

### Cancel an optimization task

You can run the following command to cancel a specified task.

```sql
-- trace_id is obtained from the DBA_OB_VECTOR_INDEX_TASKS_HISTORY view.
ALTER SYSTEM CANCEL TASK <trace_id>;
```

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>You can cancel a task only during the retry phase of the task execution. If the task is stuck in a certain phase, you cannot cancel it by running the <code>ALTER SYSTEM CANCEL TASK</code> command. </p>
</main>
