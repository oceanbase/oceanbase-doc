# Dense vector index

This topic describes how to create, search, maintain, and drop a vector index in OceanBase Database.

## Index types

The following table describes the vector index types supported by OceanBase Database.

| Index type | Description | Applicable scenarios |
|-----------|------|----------|
| HNSW      | The maximum dimension of the indexed column is 4096. HNSW is an in-memory index. You must load the entire index into memory. |  |
| HNSW_SQ   | HNSW_SQ provides a similar index construction speed, search performance, and recall rate as HNSW, but reduces the total memory usage to 1/2 to 1/3 of that of HNSW. | Scenarios with high requirements on performance and recall rate. |
| HNSW_BQ   | HNSW_BQ provides a slightly lower recall rate than HNSW but significantly reduces memory usage. The RabbitQ algorithm can compress vectors to 1/32 of their original size. As the dimension of the vectors increases, the memory optimization effect of HNSW_BQ becomes more significant. |  |
| IVF| The IVF index is implemented based on database tables and does not occupy resident memory. | Scenarios with low performance requirements, large data volumes, and cost sensitivity. |
| IVF_PQ| The IVF_PQ index is implemented based on database tables and does not occupy resident memory. It applies the PQ quantization algorithm to the IVF index. The recall rate of IVF_PQ is slightly lower than that of IVF, but its performance is higher. The PQ quantization algorithm can compress vectors to 1/16 to 1/32 of their original size in most scenarios. | Scenarios with low performance requirements, large data volumes, and cost sensitivity. |
| IVF_SQ (Experimental feature) | The IVF_SQ index is implemented based on database tables and does not occupy resident memory. It applies the SQ quantization algorithm to the IVF index. The recall rate of IVF_SQ is slightly lower than that of IVF, but its performance is higher. The SQ quantization algorithm can compress vectors to 1/3 to 1/4 of their original size in most scenarios. | Scenarios with low performance requirements, large data volumes, and cost sensitivity. |

Some other notes:

* The dense index supports L2, inner product (IP), and cosine distance as the index distance algorithms.
* You can call some distance functions during vector index search. For more information, see [Use SQL functions](../250.ob-vector-function.md).
* You can specify a filter condition for vector search. The filter condition can be a scalar condition or a spatial relationship, such as ST_Intersects. Multi-value indexes, full-text indexes, and global indexes cannot be used as pre-filtering indexes.
* You can create a vector index and a full-text index in the same table. The vector index can be a dense index or an in-memory sparse index.
* For information about whether a vector index supports offline DDL operations, see [Offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md).
* You can call some distance functions during vector index search. For more information, see [Use SQL functions](../250.ob-vector-function.md).

Limitations:

* In V4.4.1, you cannot create a columnstore vector index.

## Configure vector index memory

OceanBase Database allows you to configure vector index memory by setting the [ob_vector_memory_limit_percentage](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md) parameter:

* **Before you use HNSW, HNSW_SQ, or HNSW_BQ vector indexes in versions earlier than V4.4.1**, you must manually set the `ob_vector_memory_limit_percentage` parameter to enable the vector search feature. We recommend that you set the value to `30` for optimal search performance. If you do not set the parameter, the system will not allocate memory for the vector index, and an error will be returned when you create an index. Here is an example of how to configure this parameter:
    ```sql
    ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
    ```

* **Starting from V4.4.1**, the vector search feature is enabled by default. The default value of `0` indicates the adaptive mode, where the system automatically adjusts the memory usage ratio for vector index data in the tenant without manual intervention:
  * If the actual memory of the tenant is 8 GB or less, the value is automatically adjusted to `40`.
  * If the actual memory of the tenant exceeds 8 GB, the value is automatically adjusted to `50`.

## Query index memory estimation and actual usage

You can use the `DBMS_VECTOR` package to estimate index memory:

* Before you create a table, you can call the [INDEX_VECTOR_MEMORY_ADVISOR](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/500.index-vector-memory-advisor-mysql.md) procedure to estimate index memory.
* After you create a table and insert data, you can call the [INDEX_VECTOR_MEMORY_ESTIMATE](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/400.index-vector-memory-estimate-mysql.md) procedure to analyze index memory.

The vector index memory estimation returns two pieces of information: the minimum memory configuration required to create a vector index and the actual memory usage after the HNSW_SQ and IVF indexes are created.

We also provide the `load_vector_index_on_follower` parameter to control whether the `follower` role automatically loads the memory vector index. For more information, see [load_vector_index_on_follower](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/4235.load_vector_index_on_follower.md). If weak reads are not required, you can disable this parameter to reduce the memory usage of the vector index.

* The `VECTOR` keyword is required.
* The parameters and descriptions for creating an index after you create a table are the same as those for creating an index when you create a table.
* If the data volume is large, we recommend that you write the data and then create the index to achieve the best search performance.
* We recommend that you create the HNSW_SQ, IVF, IVF_SQ, or IVF_PQ index after you write data and rebuild the index after you write a large amount of incremental data. For more information about how to create each index, see the specific examples in the following sections.

```sql
        oc.rowkey_position != 0
```

## Search syntax and description

Vector index search is approximate nearest neighbor search and does not guarantee 100% accurate results. The accuracy of vector search is measured by recall. For example, if 10 nearest neighbors are queried and 9 correct results are returned, the recall is 90%. The following describes recall:

* Recall is affected by the build parameters and search parameters.
* Index search parameters are specified when you build an index and cannot be modified afterward. However, you can set session variables to override the default values. For HNSW, HNSW_SQ, and HNSW_BQ indexes, set the `ob_hnsw_ef_search` session variable. For IVF indexes, set the `ob_ivf_nprobes` session variable. If you set a session variable, its value is used. For more information, see [ob_hnsw_ef_search](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

The syntax for searching a dense index is as follows:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num) [PARAMETERS ($param1=$value1, ...)];
```

The following describes how to use the search feature:

* Search requirements:
  * You must specify the `APPROXIMATE` or `APPROX` keyword. Otherwise, the search will not use the vector index and will instead perform a full table scan.
  * You must include the `ORDER BY` and `LIMIT` clauses.
  * The `ORDER BY` clause can only contain a single vector condition.
  * The value of `LIMIT + OFFSET` must be in the range `(0, 16384]`.

* Rules for using distance functions:
  * If you specify the `APPROXIMATE` or `APPROX` keyword, the search will use the vector index if the distance function is supported by the current version and matches the vector index algorithm.
  * If you specify the `APPROXIMATE` or `APPROX` keyword, the search will not use the vector index if the distance function does not match the vector index algorithm, but it will not return an error.
  * If you specify the `APPROXIMATE` or `APPROX` keyword, the search will not use the vector index and will return an error if the distance function is not supported by the current version.
  * If you do not specify the `APPROXIMATE` or `APPROX` keyword, the search will not use the vector index, but it will not return an error.

* Similarity threshold parameter (`similarity`):
  * Syntax: Add `PARAMETERS (similarity=$value)` after the `LIMIT` clause, where `$value` is the similarity threshold (range: `[0, 1]`). Generally, a higher similarity value indicates a closer match and a smaller distance. This is an exception for the `inner_product` distance function, where a larger distance indicates a closer match.
  * Function: After specifying the similarity threshold, only results with a similarity value greater than or equal to the threshold are returned.
  * Supported index types: HNSW, HNSW_SQ, HNSW_BQ, IVF, and IVF_PQ.
  * Supported distance types:
    * During queries, you can specify the similarity for `cosine_distance` and `l2_distance` indexes. For `l2_distance`, it is recommended to normalize the vectors, which can improve the accuracy of similarity search. For more information about vector normalization, see [Use SQL functions - Vector normalization](../250.ob-vector-function.md).
    * You cannot specify the similarity for `inner_product` indexes during queries. This will return an error `not support`.
  * Correspondence between similarity and distance:
    * `cosine_distance`=`2 - 2 * similarity`
    * `l2_distance`=`sqrt(1 / similarity -1)`

* Other considerations:
  * The `WHERE` clause serves as a filter after vector index search.
  * If you do not specify the `LIMIT` clause, an error will be returned.

## Maintenance

When the amount of incremental data is large, the search performance decreases. To reduce the amount of data in the incremental data table, OceanBase Database introduces the `DBMS_VECTOR` package to maintain vector indexes.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF_SQ/IVF_PQ indexes do not support incremental refresh. </p>
</main>

If you write a large amount of data after you create an index, we recommend that you use the `REFRESH_INDEX` procedure to perform an incremental refresh. For more information, see [REFRESH_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/200.refresh-index-mysql.md).

An incremental refresh is performed every 15 minutes. If the number of incremental data rows exceeds 10,000, an incremental refresh is automatically performed.

### Full refresh (rebuild)

#### Manual full table rebuild

If a large amount of data is updated or deleted after an index is created, we recommend that you use the `REBUILD_INDEX` procedure to perform a full refresh. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

A full refresh is automatically triggered every 24 hours if the new data exceeds 20% of the original data. The full refresh is performed in the background asynchronously. First, a new index is created, and then the old index is replaced. During the rebuild process, the old index remains available, but the overall process is relatively slow.

We also provide the `vector_index_memory_saving_mode` parameter to control the memory usage during index rebuild. Enabling this mode reduces the memory consumption during the rebuild of vector indexes in partitioned tables. Typically, vector index rebuild requires twice the memory of the index. When this mode is enabled, the system temporarily deletes the memory index of a partition after the index is built for that partition, thereby effectively reducing the total memory required for the rebuild. For more information, see [vector_index_memory_saving_mode](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md).

Consider the following notes:

* When you perform an [offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) operation (such as `ALTER TABLE` to modify the table structure or primary key), the index table will be rebuilt. Since parallelism cannot be specified during index rebuild, the system uses a single thread by default. Therefore, when the data volume is large, the rebuild process will be relatively slow, thereby affecting the overall efficiency of the offline DDL operation.
* If you need to modify the index parameters during index rebuild, you must specify both `type` and `distance` in the parameter list, and they must be consistent with the original index type. For example, if the original index type is `hnsw` and the distance algorithm is `l2`, you must specify both `type=hnsw` and `distance=l2` during the rebuild.
* During index rebuild, the following operations are supported:
    * Modifying the values of `m`, `ef_search`, and `ef_construction`.
    * Online rebuild of the `ef_search` parameter.
    * Rebuilding the index type between `hnsw` and `hnsw_sq`.
    * Rebuilding the index type between `ivf_flat` and `ivf_flat`, `ivf_sq8` and `ivf_sq8`, and `ivf_pq` and `ivf_pq`.
    * Specifying parallelism during the rebuild. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).
* During index rebuild, the following operations are not supported:
    * Modifying the `type` and `distance` types.
    * Rebuilding the index type between `hnsw` and `ivf`.
    * Rebuilding the index type between `hnsw` and `hnsw_bq`.
    * Cross-rebuilding between `ivf_flat`, `ivf_pq`, and `ivf_sq8`.

#### Automatic partition rebuild (Recommended)

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><li>This feature is available starting from OceanBase Database V4.4.1. If your vector cluster is upgraded from a previous version to V4.4.1, you need to manually perform a full table rebuild for all vector indexes after the upgrade. Otherwise, automatic partition rebuild tasks may not be executed after the upgrade. </li><li>This feature is only supported for HNSW, HNSW_SQ, and HNSW_BQ indexes. </li></p>
</main>

The current version triggers automatic partition rebuild tasks in the following two scenarios:

* When a vector index search statement is executed.
* During scheduled checks, which can be manually configured to execute at specific intervals.

1. Configure the execution interval

    In the `oceanbase` database, configure the execution interval using the [vector_index_optimize_duty_time](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8250.vector_index_optimize_duty_time.md) parameter. Example:

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    After the above configuration, the partition rebuild task will only be executed between 23:00:00 and 24:00:00, and will not be initiated during other time periods. For more information, see the parameter description in the corresponding parameter documentation.

2. View task progress and history

    You can query the [CDB/DBA_OB_VECTOR_INDEX_TASKS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12950.o-dba_ob_vector_index_tasks-of-mysql-mode.md) or [CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12960.o-dba_ob_vector_index_task_history-of-mysql-mode.md) view to view the task progress and history.

    You can determine the current status of the task based on the `status` field:

    * 0 (PREPARE): The task is waiting to be executed.
    * 1 (RUNNING): The task is being executed.
    * 2 (PENDING): The task is paused.
    * 3 (FINISHED): The task has been completed.

    Tasks that have completed execution, regardless of success or failure, are archived to the history table. For more information, see the corresponding view documentation.

3. Cancel a task

    To cancel a task, obtain the trace_id from the `DBA_OB_VECTOR_INDEX_TASKS` or `CDB_OB_VECTOR_INDEX_TASKS` view and execute the following command:

    ```sql
    ALTER SYSTEM CANCEL TASK <trace_id>;
    ```
    Example:
    ```sql
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```

## Performance optimization

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>At present, only IVF indexes are supported. </p>
</main>

OceanBase Database provides an automatic performance optimization mechanism for IVF indexes. It improves search performance by managing cache and performing regular maintenance.

### Optimization mechanisms

The performance optimization of IVF indexes includes two automatic tasks:

1. Cache preheating task: This task periodically checks all IVF indexes. If the cache corresponding to an index does not exist, the cache is automatically preheated to load the index data into memory. Additionally, when an IVF index is created, the cache is automatically preheated.
2. Cache cleanup task: This task periodically checks all IVF caches. If the cache corresponds to an index that has been deleted, the cache is automatically cleaned up to release memory resources. Additionally, when an IVF index is deleted, the cache is automatically cleaned up.

### Configure the execution cycle of optimization tasks

The system allows you to customize the execution window for performance optimization tasks to avoid running them during peak business hours, which can impact performance.

In the `oceanbase` database, you can configure the execution cycle using the `vector_index_optimize_duty_time` parameter:

```sql
ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
```

The configuration details are as follows:

* The time format is `[start time, end time]`.
* The above configuration specifies that optimization tasks are executed only between 23:00:00 and 24:00:00.
* Optimization tasks are not initiated during other time periods to avoid affecting normal business operations.

### Monitor optimization tasks

OceanBase Database provides the capability to monitor optimization tasks:

* You can view the status of running or pending tasks in the [DBA_OB_VECTOR_INDEX_TASKS](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/24150.o-dba_ob_vector_index_tasks-of-sys-tenant.md) view.
* You can view the history of completed tasks in the [DBA_OB_VECTOR_INDEX_TASK_HISTORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/12960.o-dba_ob_vector_index_task_history-of-mysql-mode.md) view.

Here are some examples of how to use these features:

1. View the current task status

    You can view the status of running or pending tasks in the `DBA_OB_VECTOR_INDEX_TASKS` view:

    ```sql
    -- Query in a MySQL tenant
    SELECT * FROM oceanbase.DBA_OB_VECTOR_INDEX_TASKS;
    ```

### Cancel an optimization task

You can run the following command to cancel a specified task.

```sql
-- trace_id is obtained from the DBA_OB_VECTOR_INDEX_TASKS_HISTORY view.
ALTER SYSTEM CANCEL TASK <trace_id>;
```

<main id="notice" type='notice'>
  <h4>Notice</h4>
