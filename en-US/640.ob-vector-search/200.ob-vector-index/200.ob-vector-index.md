# Dense vector index

This topic describes how to create, search, maintain, and drop vector indexes in OceanBase Database.

## Index types

The following table describes the vector index types supported by OceanBase Database.

| Index type | Description | Applicable scenarios |
|-----------|------|----------|
| HNSW      | The maximum dimension of an HNSW index column is 4096. An HNSW index is an memory-based index that needs to be fully loaded into memory. It supports DML operations and real-time search. |  |
| HNSW_SQ   | An HNSW_SQ index provides nearly the same construction speed, search performance, and recall rate as an HNSW index, but uses only 1/2 to 1/3 of the memory of an HNSW index. | Scenarios with high requirements for performance and recall rate. |
| HNSW_BQ   | An HNSW_BQ index has a slightly lower recall rate than an HNSW index but significantly reduces memory usage. The Rabitq algorithm can compress vectors to 1/32 of their original size. As the dimension of the vectors increases, the memory optimization effect of an HNSW_BQ index becomes more pronounced. |  |
| IVF| An IVF index implemented based on a database table does not occupy resident memory. | Scenarios with high data volume and cost sensitivity, but low performance requirements. |
| IVF_PQ| An IVF_PQ index implemented based on a database table does not occupy resident memory. It applies the PQ quantization algorithm to an IVF index. The recall rate of an IVF_PQ index is slightly lower than that of an IVF index, but its performance is higher. The PQ quantization algorithm can compress vectors to 1/16 to 1/32 of their original size in most scenarios. | Scenarios with high data volume and cost sensitivity, but low performance requirements. |
| IVF_SQ (Experimental feature) | An IVF_SQ index implemented based on a database table does not occupy resident memory. It applies the SQ quantization algorithm to an IVF index. The recall rate of an IVF_SQ index is slightly lower than that of an IVF index, but its performance is higher. The SQ quantization algorithm can compress vectors to 1/3 to 1/4 of their original size in most scenarios. | Scenarios with high data volume and cost sensitivity, but low performance requirements. |

Some other notes:

* Dense indexes support L2, inner product (IP), and cosine distance as index distance algorithms.
* Vector index search supports calling partial distance functions. For more information, see [Use SQL functions](../250.ob-vector-function.md).
* Vector search supports filtering. The filter conditions can be scalar-type conditions or spatial relationships, such as ST_Intersects. Multi-value indexes, full-text indexes, and global indexes cannot be used as pre-filterers.
* You can create a vector index and a full-text index in the same table. The vector index includes both dense and memory-based sparse types.
* For information about how to use an offline DDL operation on a vector index, see [Offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md).
* Vector index search supports calling partial distance functions. For more information, see [Use SQL functions](../250.ob-vector-function.md).

Limitations:

* For V4.4.1, you cannot create a columnstore vector index.

## Configure vector index memory

OceanBase Database allows you to configure vector index memory by setting the [ob_vector_memory_limit_percentage](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md) parameter:

* **Before you create a vector index of the HNSW/HNSW_SQ/HNSW_BQ type in versions earlier than V4.4.1**, you must manually set the `ob_vector_memory_limit_percentage` parameter to enable vector search. We recommend that you set the parameter to `30` for optimal search performance. If you do not set the parameter, the system does not allocate memory for vector indexes, and an error is returned when you create an index. Example:
    ```sql
    ALTER SYSTEM SET ob_vector_memory_limit_percentage = 30;
    ```

* **Starting from V4.4.1**, vector search is enabled by default. The default value of `0` indicates the adaptive mode, in which the system automatically adjusts the memory usage ratio of vector index data in a tenant without manual intervention:
  * If the actual memory of a tenant is 8 GB or less, the value is automatically adjusted to `40`.
  * If the actual memory of a tenant is more than 8 GB, the value is automatically adjusted to `50`.

## Query the estimated and actual memory usage of an index

You can use the `DBMS_VECTOR` package to estimate the memory usage of an index.

* Before a table is created, you can call the [INDEX_VECTOR_MEMORY_ADVISOR](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/500.index-vector-memory-advisor-mysql.md) procedure to estimate the memory usage of an index.
* After a table is created and data is inserted into the table, you can call the [INDEX_VECTOR_MEMORY_ESTIMATE](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/400.index-vector-memory-estimate-mysql.md) procedure to analyze the memory usage of an index.

The memory usage of a vector index is estimated to return the minimum memory configuration required to create the vector index and the actual memory usage after the HNSW_SQ and IVF indexes are created.

We also provide the `load_vector_index_on_follower` parameter to control whether the `follower` role automatically loads the memory vector index. For more information about the syntax and examples, see [load_vector_index_on_follower](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/4235.load_vector_index_on_follower.md). If weak reads are not required, you can disable this parameter to reduce the memory usage of the vector index.

## Syntax and description

OceanBase Database supports creating a vector index in two ways: **creating a vector index when you create a table** and **creating a vector index after the table is created**. When you create a vector index, note the following:

* You must specify the `VECTOR` keyword.
* The parameters and their descriptions for creating a vector index after the table is created are the same as those for creating a vector index when you create a table.
* If the data volume is large, we recommend that you write all data to the table and then create the vector index to achieve the best search performance.
* We recommend that you create the HNSW_SQ, IVF, IVF_SQ, or IVF_PQ index after you write data to the table and rebuild the index after you write a large amount of incremental data. For more information about how to create each index, see the specific examples in the following sections.

```sql
        ELSE COALESCE(SUM(result_value), 'not support')

FROM (
    SELECT
        CASE
            WHEN vdt.data_type_class IN (1, 2, 3, 4, 6, 8, 9, 14, 27, 28) THEN 8 -- extra_info_size += 8 for numeric types

        oceanbase.__all_column oc
    JOIN
        oceanbase.__all_virtual_data_type vdt
    ON
        oc.data_type = vdt.data_type
    WHERE
        oc.rowkey_position != 0
        AND oc.table_id = (SELECT table_id FROM oceanbase.__all_table WHERE table_name = @table_name)
) AS result_table;

-- The calculation result is 8 bytes.
```

## Search syntax and description

Vector index search is an approximate nearest neighbor search and does not guarantee 100% accuracy in the results. The accuracy of vector search is measured by recall. For example, if you can stably return 9 correct results when you search for the 10 nearest neighbors, the recall is 90%. The following table describes the recall:

* The recall is affected by the construction parameters and search parameters.
* Index search parameters are specified when you build an index and cannot be modified afterward. However, you can set session variables to modify them. For an HNSW/HNSW_SQ/HNSW_BQ index, you can set the `ob_hnsw_ef_search` parameter. For an IVF index, you can set the `ob_ivf_nprobes` parameter. If you set a session variable, its value takes precedence. For more information, see [ob_hnsw_ef_search](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/550.ob_hnsw_ef_search.md) and [ob_ivf_nprobes](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/400.session-system-variable/560.ob_ivf_nprobes.md).

The search syntax for dense indexes is as follows:

```sql
SELECT ... FROM $table_name ORDER BY $distance_function($column_name, $vector_expr) [APPROXIMATE|APPROX] LIMIT $num (OFFSET $num);
```

The following table describes how to use search.

* Syntax requirements:
  * You must specify the `APPROXIMATE` or `APPROX` keyword. Otherwise, the search will not use the vector index but will perform a full table scan.
  * The `ORDER BY` and `LIMIT` clauses are required.
  * The `ORDER BY` clause supports only a single vector condition.
  * The value of `LIMIT + OFFSET` must be in the range (0, 16384].

* Rules for using distance functions:
  * If you specify the `APPROXIMATE` or `APPROX` keyword, call a distance function supported by the current version, and the distance function is compatible with the vector index algorithm, the search will use the vector index.
  * If you specify the `APPROXIMATE` or `APPROX` keyword, call a distance function supported by the current version, and the distance function is incompatible with the vector index algorithm, the search will not use the vector index, but no error will be returned.
  * If you specify the `APPROXIMATE` or `APPROX` keyword, call a distance function not supported by the current version, the search will not use the vector index, and an error will be returned.
  * If you do not specify the `APPROXIMATE` or `APPROX` keyword, call a distance function supported by the current version, the search will not use the vector index, but no error will be returned.

* Similarity threshold parameter (`similarity`):
  * Syntax: Add `PARAMETERS (similarity=$value)` after the `LIMIT` clause, where `$value` is the similarity threshold (value range: `[0, 1]`). Generally, the higher the similarity value, the more similar the results and the smaller the distance. The exception is `inner_product`, where a larger distance indicates greater similarity.
  * Function: When a similarity threshold is specified, only results with similarity greater than or equal to the threshold will be returned.
  * Supported index types: HNSW, HNSW_SQ, HNSW_BQ, IVF, IVF_PQ.
  * Supported distance types:
    * When querying, similarity can be specified for indexes with `cosine_distance` and `l2_distance` distance types. For `l2_distance`, it is recommended to perform L2 normalization on vectors, which helps improve the accuracy of similarity search. For details and examples on vector normalization, see [Using SQL Functions - Vector Normalization](../250.ob-vector-function.md).
    * Similarity cannot be specified for indexes with the `inner_product` distance type during querying (an error `not support` will be reported).
  * Correspondence between similarity and distance:
    * `cosine_distance` = `2 - 2 * similarity`
    * `l2_distance` = `sqrt(1 / similarity - 1)`

* Other considerations:
  * The `WHERE` clause specifies the filtering conditions after the vector index search.
  * If you do not specify the `LIMIT` clause, an error will be returned.

## Maintenance

If the amount of incremental data is excessive, search performance will decrease. To reduce the amount of incremental data in the data table, OceanBase Database introduces the `DBMS_VECTOR` package for vector index maintenance.

### Incremental refresh

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>IVF/IVF_SQ/IVF_PQ indexes do not support incremental refresh. </p>
</main>

If a large amount of data is written after the index is built, we recommend that you use the `REFRESH_INDEX` procedure to perform an incremental refresh. For more information, see [REFRESH_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/200.refresh-index-mysql.md).

The system checks for incremental data every 15 minutes. If the number of incremental data entries exceeds 10,000, an incremental refresh is automatically performed.

### Full refresh (rebuild)

#### Manual full table rebuild

If a large amount of data is updated or deleted after an index is created, we recommend that you use the `REBUILD_INDEX` procedure to perform a full refresh. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).

A full refresh is automatically performed every 24 hours if the amount of new data exceeds 20% of the original data. The full refresh is performed in the background and asynchronously. First, a new index is created, and then the old index is replaced. During the rebuild, the old index remains available, but the overall process is relatively slow.

We also provide the `vector_index_memory_saving_mode` parameter to control the memory usage during index rebuild. Enabling this mode reduces the memory consumption during the rebuild of vector indexes in partitioned tables. Typically, vector index rebuild consumes twice the memory of the index. With the memory-saving mode enabled, the system temporarily deletes the memory index of a partition after the index is built in that partition, thereby effectively reducing the total memory required for the rebuild. For more information, see [vector_index_memory_saving_mode](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md).

Consider the following notes:

* When you perform an [offline DDL](../../700.reference/500.sql-reference/100.sql-syntax/200.common-tenant-of-mysql-mode/700.ddl-function-of-mysql-mode/150.online-and-offline-ddl-list-of-mysql-mode.md) operation (such as `ALTER TABLE` to modify the table structure or primary key), the index table is rebuilt. Since parallelism cannot be specified during index rebuild, the system uses a single thread by default. Therefore, the rebuild process may be slow when the data volume is large, which affects the overall efficiency of the offline DDL operation.
* If you need to modify the index parameters during index rebuild, you must specify both `type` and `distance` in the parameter list. Additionally, the `type` and `distance` values must be consistent with the original index type. For example, if the original index type is `hnsw` and the distance algorithm is `l2`, you must specify both `type=hnsw` and `distance=l2` during the rebuild.
* During index rebuild, the following operations are supported:
    * Modifying the values of `m`, `ef_search`, and `ef_construction`.
    * Online rebuild of the `ef_search` parameter.
    * Rebuilding the index type between `hnsw` and `hnsw_sq`.
    * Rebuilding the index type between `ivf_flat` and `ivf_flat`, `ivf_sq8` and `ivf_sq8`, and `ivf_pq` and `ivf_pq`.
    * Specifying the parallelism during rebuild. For more information, see [REBUILD_INDEX](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/300.rebuild-index-mysql.md).
* During index rebuild, the following operations are not supported:
    * Modifying the `type` and `distance` values.
    * Rebuilding the index type between `hnsw` and `ivf`.
    * Rebuilding the index type between `hnsw` and `hnsw_bq`.
    * Rebuilding the index type between `ivf_flat`, `ivf_pq`, and `ivf_sq8`.

#### Automatic partition rebuild (recommended)

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p><li>This feature is available starting from OceanBase Database V4.4.1. If you upgrade a vector cluster from a version earlier than V4.4.1 to V4.4.1, you must manually perform a full table rebuild of all vector indexes after the upgrade. Otherwise, automatic partition rebuild tasks may not execute as expected. </li><li>This feature is only supported for HNSW, HNSW_SQ, and HNSW_BQ indexes. </li></p>
</main>

The current version triggers automatic partition rebuild tasks in the following two scenarios:

* When vector index search statements are executed.
* During scheduled checks, which can be manually configured to run at specific intervals.

1. Configure the execution interval

    In the `oceanbase` database, configure the execution interval using the [vector_index_optimize_duty_time](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8250.vector_index_optimize_duty_time.md) parameter. Example:

    ```sql
    ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
    ```
    After the above configuration, the partition rebuild task will only execute between 23:00:00 and 24:00:00. For more information, see the parameter description in the corresponding configuration item documentation.

2. View task progress and history

    You can view task progress and history by querying the `CDB/DBA_OB_VECTOR_INDEX_TASKS` or `CDB/DBA_OB_VECTOR_INDEX_TASK_HISTORY` view.

    The `status` field indicates the current status of the task:

    * 0 (PREPARE): The task is waiting to be executed.
    * 1 (RUNNING): The task is being executed.
    * 2 (PENDING): The task is paused.
    * 3 (FINISHED): The task has completed.

    Tasks with a status of `FINISHED` are stored in the history table, regardless of whether they were successful. For more information, see the view documentation.

3. Cancel a task

    To cancel a task, you can obtain the trace_id from the `DBA_OB_VECTOR_INDEX_TASKS` or `CDB_OB_VECTOR_INDEX_TASKS` view and execute the following command:

    ```sql
    ALTER SYSTEM CANCEL TASK <trace_id>;
    ```
    Example:
    ```sql
    ALTER SYSTEM CANCEL TASK "Y61480BA2D976-00063084E80435E2-0-1";
    ```

## Performance optimization

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>Only IVF indexes are supported. </p>
</main>

OceanBase Database provides an automatic performance optimization mechanism for IVF indexes. This mechanism improves search performance through cache management and regular maintenance.

### Optimization mechanisms

The performance optimization of IVF indexes includes two automatic tasks:

1. Cache warming task: Periodically checks all IVF indexes. If the cache corresponding to an index does not exist, it automatically triggers cache warming to load the index data into memory. Additionally, when creating an IVF index, the cache is automatically warmed.
2. Cache cleanup task: Periodically checks all IVF caches. If the cache corresponds to an index that has been deleted, it automatically cleans up the invalid cache to release memory resources. Additionally, when deleting an IVF index, the cache is automatically cleaned up.

### Configure the execution cycle of optimization tasks

The system allows you to customize the execution window for performance optimization tasks to avoid performance impact during peak business hours.

In the `oceanbase` database, you can configure the execution cycle using the `vector_index_optimize_duty_time` parameter:

```sql
ALTER SYSTEM SET vector_index_optimize_duty_time='[23:00:00, 24:00:00]';
```

The configuration details are as follows:

* The time format is `[start time, end time]`.
* The above configuration indicates that optimization tasks are executed only from 23:00:00 to 24:00:00.
* Optimization tasks are not initiated during other periods to avoid affecting normal business operations.

### Monitor optimization tasks

OceanBase Database provides the capability to monitor optimization tasks for vector indexes:

* You can view running or pending tasks using the `DBA_OB_VECTOR_INDEX_TASKS` view.
* You can view historical task records using the `DBA_OB_VECTOR_INDEX_TASK_HISTORY` view.

Here are some examples of how to use these features:

1. View the current task status

    Use the `DBA_OB_VECTOR_INDEX_TASKS` view to check for running or pending tasks:

    ```sql
    -- Query in a MySQL tenant
    SELECT * FROM oceanbase.DBA_OB_VECTOR_INDEX_TASKS;
    ```

    Example return result:

    ```shell
    +----------+---------------------+---------+----------------------------+----------------------------+--------------+----------+-----------+------------------+----------+------------------------------------+

    +----------+---------------------+---------+----------------------------+----------------------------+--------------+----------+-----------+------------------+----------+------------------------------------+
    |   500020 | 1152921504606846990 | 2002281 | 1970-08-23 17:10:23.174127 | 1970-08-23 17:10:23.174137 | USER         | FINISHED |         2 | 1750671687770026 |        0 | YAFF00B9E4D97-00063839E6BD9BBC-0-1 |
    +----------+---------------------+---------+----------------------------+----------------------------+--------------+----------+-----------+------------------+----------+------------------------------------+
    1 row in set
    ```

    Task status description:

    * `STATUS = 0`: PREPARE, the task is waiting to be executed.
    * `STATUS = 1`: RUNNING, the task is being executed.

    Task type description:

    * `TASK_TYPE = 2`: IVF cache warming task.
    * `TASK_TYPE = 3`: IVF cache cleanup task.


### Cancel an optimization task

You can run the following command to cancel a specified task.

```sql
-- trace_id is obtained from the DBA_OB_VECTOR_INDEX_TASKS_HISTORY view.
ALTER SYSTEM CANCEL TASK <trace_id>;
```

<main id="notice" type='notice'>
  <h4>Notice</h4>
  <p>You can cancel a task only during the task retry phase after the task fails. If a background task is stuck in a certain execution phase, you cannot cancel the background task by running this statement. </p>
</main>
