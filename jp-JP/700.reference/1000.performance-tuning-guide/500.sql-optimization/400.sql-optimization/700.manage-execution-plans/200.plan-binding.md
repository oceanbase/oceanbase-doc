# プランのバインド

OceanBaseデータベースは `CREATE OUTLINE` ステートメントを使用してSQLステートメントと特定の実行計画をバインドし、そのSQLが以降の実行時に常に指定された実行計画を使用するよう保証します。これにより、オプティマイザーの選択が不適切であることによるパフォーマンスの変動を回避できます。OceanBaseデータベースの `CREATE OUTLINE` は、以下のプランバインドモードをサポートしています：

* 厳密バインド：特定のSQLステートメントと特定の実行計画を一対一でバインドします。単一データベース・単一テーブルのチューニングシナリオに適しています。
* テンプレートバインド：`BINDING_RULE` 句を使用してアウトラインをテンプレート化し、パターンに合致する複数のSQL（例えば、データベースやテーブルのシャーディングシナリオでの類似した複数のSQL）に同時に適用します。データベースやテーブルのシャーディング、SaaSマルチテナントなどのシナリオに適しています。

既に稼働中の業務において、オプティマイザーが選択した計画が十分に最適化されていない場合、オンラインでプランのバインドを行うことができます。つまり、業務側でSQLを変更する必要はなく、DDL操作を通じて一連のHintをSQLに追加することで、オプティマイザーが指定されたHintのセットに基づいて、そのSQLに対してより優れた計画を生成するようにします。このHintのセットをアウトラインと呼びます。

## 厳密バインディング

厳密バインディングは、OceanBaseの既存の計画バインディング機能であり、`SQL_TEXT`または`SQL_ID`を使用して特定のSQLと特定の実行計画を一対一でバインドします。`BINDING_RULE`を指定しないOutlineの動作は、過去のバージョンと完全に一致します。

### SQL_TEXTを使用したOutlineの作成

`SQL_TEXT`を使用してOutlineを作成すると、Key-Valueペアが生成され、Mapに格納されます。ここで、KeyはバインドされたSQLのパラメータ化後のテキスト、ValueはバインドされたHintです。具体的なパラメータ化の原則については、[クイックパラメータ化](../../200.sql-execution-plan/400.fast-parameterization.md)を参照してください。

`SQL_TEXT`を使用してOutlineを作成する構文は以下のとおりです：

```sql
CREATE [OR REPLACE] OUTLINE <outline_name> ON <stmt> [ TO <target_stmt> ];
```

説明は以下のとおりです：

* `OR REPLACE`を指定すると、既存の実行計画を置き換えることができます。

* ここで、`stmt`は通常、Hintと元のパラメータを含むDMLステートメントです。

* `TO target_stmt`を指定しない場合、データベースが受け付けたSQLをパラメータ化したテキストと、`stmt`からHintを除去してパラメータ化したテキストが一致すれば、そのSQLに`stmt`内のHintをバインドして実行計画を生成します。

  Hintを含むステートメントに対して固定の計画を実行したい場合は、元のSQLを指定するために`TO target_stmt`が必要です。

  例：

  ```sql
  obclient> CREATE OUTLINE outline1 ON SELECT /*+NO_REWRITE*/ * FROM tbl1 WHERE col1 = 4
  AND col2 = 6 ORDER BY 2 TO SELECT  * FROM tbl1 WHERE col1 = 4 AND col2 = 6 ORDER BY 2;
  ```

  <main id="notice" type='notice'>
    <h4>注意</h4>
    <p><code>target_stmt</code>を使用する場合、<code>stmt</code>と<code>target_stmt</code>がHintを除去した後、完全に一致することが厳密に要求されます。</p>
  </main>

以下の例では、オプティマイザーは主キースキャンを選択しました。データ量が増加した場合、インデックス `idx_c2` を使用すると、このSQLはより最適化されます。この時、アウトラインを作成してこのSQLにインデックス計画をバインドし、実行できます。

```sql
obclient> CREATE TABLE t1 (c1 INT PRIMARY KEY, c2 INT, c3 INT, INDEX idx_c2(c2));
Query OK, 0 rows affected

obclient> INSERT INTO t1 VALUES(1, 1, 1), (2, 2, 2), (3, 3, 3);
Query OK, 1 rows affected

obclient> EXPLAIN SELECT * FROM t1 WHERE c2 = 1;

Query Plan:
===================================
|ID|OPERATOR  |NAME|EST. ROWS|COST|
-----------------------------------
|0 |TABLE SCAN|t1  |1        |37  |
===================================
Outputs & filters:
-------------------------------------
  0 - output([t1.c1], [t1.c2], [t1.c3]), filter([t1.c2 = 1]),
      access([t1.c2], [t1.c1], [t1.c3]), partitions(p0)
```

以下のSQL文に基づいてアウトラインを作成します：

```sql
obclient> CREATE OUTLINE otl_idx_c2
       ON SELECT/*+ INDEX(t1 idx_c2)*/ * FROM t1 WHERE c2 = 1;
Query OK, 0 rows affected
```

### SQL_IDを使用してアウトラインを作成する

`SQL_ID` を使用してアウトラインを作成する構文は以下のとおりです：

```sql
obclient> CREATE OUTLINE outline_name ON sql_id USING HINT hint_text;
```

`SQL_ID` はバインドするSQLに対応する `SQL_ID` であり、以下の方法で取得できます：

* `V$OB_PLAN_CACHE_PLAN_STAT` をクエリすることで取得します。

* `GV$OB_SQL_AUDIT` をクエリすることで取得します。

* パラメータ化された元のSQLを使用して、MD5で `SQL_ID` を生成します。以下のスクリプトを参照して、対応するSQLの `SQL_ID` を生成できます。

  ```sql
  IMPORT hashlib
  sql_text='SELECT * FROM t1 WHERE c2 = ?'
  sql_id=hashlib.md5(sql_text.encode('utf-8')).hexdigest().upper()
  PRINT(sql_id)
  ```

`SQL_ID` を使用してアウトラインをバインドします。以下の例を参照してください：

```sql
obclient> CREATE OUTLINE otl_idx_c2 ON 'ED570339F2C856BA96008A29EDF04C74'
USING HINT /*+ INDEX(t1 idx_c2)*/ ;
```

  <main id="notice" type='notice'>
    <h4>注意</h4>
    <ul>
    <li>Hintの形式は <code>/*+ xxx */</code> です。Hintの説明に関する詳細は、<a href="../700.manage-execution-plans/100.optimizer-hint.md">Optimizer Hint</a> を参照してください。</li>
    <li><code>SQL_TEXT</code> 方式で作成されたアウトラインは、<code>SQL_ID</code> 方式で作成されたアウトラインを上書きします。<code>SQL_TEXT</code> 方式の優先順位が高いです。</li>
    <li><code>SQL_ID</code> に対応するSQL文にすでにHintがある場合、アウトラインの作成時に指定したHintが、元のSQL文のすべてのHintを上書きします。</li>
    </ul>
  </main>

## テンプレートバインディング

テンプレートバインディングは、OceanBaseが新たに追加した実行計画のバインディング機能です。`BINDING_RULE` 句を使用してアウトラインをテンプレート化し、パターンに一致する複数のSQLに対して同時に適用できます。データベースやテーブルのシャーディング、SaaS型マルチテナントなど、同一モデルのデータが複数のテーブルやデータベースに分散しているシナリオに適しています。

### BINDING_RULE構文

テンプレートアウトラインを作成する構文は以下のとおりです：

```sql
CREATE [OR REPLACE] OUTLINE outline_name ON stmt
    BINDING_RULE (binding_item);

binding_item:
    SCOPE = {DATABASE | TENANT}
    | MAP = {real_name TO 'pattern', ...}
```

パラメータの説明は以下のとおりです：

* `OR REPLACE`：オプションです。`OR REPLACE` を指定すると、既存の実行計画を置き換えることができます。
* `outline_name`：作成するアウトライン名を指定します。
* `stmt`：一般的には、ヒントと元のパラメータを持つDMLステートメントです。
* `BINDING_RULE (binding_item)`：このアウトラインの適用レベルを指定するために使用されます。

  <main id="notice" type='explain'>
    <h4>説明</h4>
    <p>V4.4.2バージョンでは、V4.4.2 BP3バージョンから <code>BINDING_RULE</code> 句が導入されました。</p>
  </main>

  * `SCOPE = {DATABASE | TENANT}`：

    * `SCOPE = DATABASE`：デフォルト値で、現在のデータベースでのみ有効であることを意味します。
    * `SCOPE = TENANT`：現在のテナント内のすべてのデータベースで有効であることを意味します。

  * `MAP = {real_name TO 'pattern', ...}`：テーブル名/データベース名のワイルドカードルールを指定します。左側は実際のテーブル名または `db.table` の形式で、右側は `pattern` です。`pattern` には `${変数名}` または `${変数名:正規表現}` を記述できます。

    <main id="notice" type='notice'>
      <h4>注意</h4>
      <p><ul>
      <li><code>${var}</code> または <code>${var:regex}</code>：<code>var</code> という名前の変数を定義し、正規表現パターンを指定することができます。正規表現が指定されていない場合、デフォルトで任意の非空文字列に一致します。</li>
      <li><code>MAP</code> の左側が <code>db.table</code> の形式の場合、右側の <code>pattern</code> ではデータベース名とテーブル名のパターンをそれぞれ単一引用符で囲み、ドットで区切る必要があります：<code>'db_pattern'.'table_pattern'</code>。</li>
      <li>同一の <code>BINDING_RULE</code> 内では、変数は定義後に参照する必要があります。同名の変数は、すべての参照箇所で値が一致している必要があります。</li>
      </ul></p>
    </main>

### 四種類の典型的なバインディングモード

| **モード** | **SCOPE** | **MAP** | **適用シナリオ** |
|----------|-----------|---------|--------------|
| 厳密バインディング | DATABASE（デフォルト）| 空 | 単一データベース・単一テーブル（既存の動作）|
| 現在のデータベース内のシャードテーブルのワイルドカード指定 | DATABASE | テーブル名のみをワイルドカードで指定 | 単一データベース内の `orders_001` … `orders_127` などのシャードテーブル |
| データベースをまたいだ厳密なテーブル名 | TENANT | 空 | データベースをまたいだ同名テーブル、例えば `db_001.orders`、`db_002.orders` |
| データベースをまたいだワイルドカード | TENANT | `db.table` を含むワイルドカード | データベース名 + テーブル名の組み合わせによるワイルドカード |

### データベースをまたいだ同名テーブルのバインディング

データベースシャーディングアーキテクチャでは、複数のデータベースに同名のテーブル（例えば `db_001.orders`、`db_002.orders`）が存在することがあります。`SCOPE = TENANT` を使用すると、一つのアウトラインですべてのデータベースの同名テーブルをカバーできます。

**例：**

すべてのデータベースの `orders` テーブルは `idx_status` インデックスを使用します：

```shell
obclient> CREATE OUTLINE otl_orders
    ON SELECT /*+ index(orders, idx_status) */*
        FROM orders
        WHERE status = 'a'
    BINDING_RULE (SCOPE = TENANT);
```

* データベース `db_001` でのクエリヒット例。

    ```shell
    obclient> USE db_001;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

* データベース `db_002` でのクエリヒット例。

    ```shell
    obclient> USE db_002;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

* データベース `db_test` でのクエリヒット例。

    ```shell
    obclient> USE db_test;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

### 現在のデータベース内のシャードテーブルのワイルドカード指定

シャーディングアーキテクチャでは、単一のデータベース内に一定の命名規則に従う複数のシャードテーブル（例：`orders_sh`、`orders_hz`、`orders_bj`）が存在します。`MAP` を正規表現変数と組み合わせることで、1つのアウトラインですべてのシャードテーブルをカバーできます。

**例：**

`orders_xx` シリーズのシャードテーブルは同じアウトラインを共有します：

```shell
obclient> CREATE OUTLINE otl_orders_tpl
    ON SELECT /*+ index(orders_sh, idx_status) */*
        FROM orders_sh
        WHERE status = 'a'
    BINDING_RULE (MAP = {orders_sh TO 'orders_${S:[a-z]+}'});
```

* クエリヒット例 `S=bj`。

    ```shell
    obclient> SELECT * FROM orders_bj WHERE status = 'pending';
    ```

* クエリヒット例 `S=hz`。

    ```shell
    obclient> SELECT * FROM orders_hz WHERE status = 'pending';
    ```

* クエリミス例。`001` は `[a-z]+` に一致しません。

    ```shell
    obclient> SELECT * FROM orders_001 WHERE status = 'pending';
    ```

### データベース名 + テーブル名の組み合わせによるワイルドカード

データベースとテーブルを組み合わせて分割したアーキテクチャ（例：`db_001.orders_sh`、`db_002.orders_bj`）では、データベース名とテーブル名の両方に対してワイルドカードを使用できます。

**例：**

`db_数字` パターンのデータベースと `orders_英字` パターンのテーブルにのみ有効です：

```shell
obclient> CREATE OUTLINE otl_full
    ON SELECT *
        FROM db_001.orders_sh
        WHERE status = 'a'
    BINDING_RULE (
        SCOPE = TENANT,
        MAP = {db_001.orders_sh TO 'db_${D:[0-9]+}'.'orders_${S:[a-z]+}'}
        );
```

* クエリヒットの例。

    ```shell
    obclient> SELECT *
        FROM db_002.orders_bj
        WHERE status = 'pending';
    ```

* クエリミスの例、データベース名が一致しません。

    ```shell
    obclient> SELECT *
        FROM test_db.orders_sh
        WHERE status = 'pending';
    ```

特定のデータベース内のすべてのテーブルをカバーする場合は、汎用正規表現 `${T:.*}` を使用できます：

```shell
obclient> CREATE OUTLINE otl_db_all
    ON SELECT *
        FROM db_001.orders
        WHERE status = 'a'
    BINDING_RULE (
        SCOPE = TENANT,
        MAP = {db_001.orders TO 'db_${D:[0-9]+}'.'${T:.*}'}
        );
```

### 複数テーブルJOINと変数一貫性制約

複数テーブルの `JOIN` シナリオでは、`JOIN` の対象となる複数のテーブルがすべてシャーディングされている場合、同じ変数が参照されるすべての箇所で一貫した値を持つことを保証する必要があります。これにより、誤ったテーブルの組み合わせマッチング（例：`orders_hz JOIN products_bj`）を防ぎます。

同一の `MAP` 内で同じ変数名を使用することで、一貫性制約を実現できます。

**例：**

`orders_${S}` と `products_${S}` の `S` は同じでなければなりません。

```shell
obclient> CREATE OUTLINE otl_join
    ON SELECT /*+ use_nl(orders_sh) */o.*, p.*
        FROM orders_sh o JOIN products_sh p
        ON o.id = p.order_id
    BINDING_RULE (
        MAP = {
            orders_sh TO 'orders_${S:[a-z]+}',
            products_sh TO 'products_${S}'
            }
        );
```

* クエリヒットの例、`S=hz、orders_hz JOIN products_hz`。

    ```shell
    obclient> SELECT o.*, p.*
        FROM orders_hz o JOIN products_hz p
        ON o.id = p.order_id;
    ```

* クエリミスの例、`orders` の `S=hz`、`products` の `S=bj`、変数が一致しないため、自動的にミスとなります。

    ```shell
    obclient> SELECT o.*, p.*
        FROM orders_hz o JOIN products_bj p
        ON o.id = p.order_id;
    ```

## スコープとマッチング優先順位

### スコープ

* `DATABASE`（デフォルト）：アウトラインは現在のデータベース内でのみ有効です。アウトラインを作成したデータベースがスコープデータベースとなります。
* `TENANT`：アウトラインは現在のテナント内のすべてのデータベースで有効です。作成時は引き続き特定のデータベースで `CREATE OUTLINE` を実行する必要がありますが、スコープはテナント全体に拡張されます。

### マッチング優先順位

同一のSQLが複数のアウトラインにマッチする可能性がある場合、OceanBaseデータベースは以下の優先順位で高いものから低いものへとマッチングを試みます：

1.  現在のデータベースの厳密な `signature`：厳密に一致するSQLパラメータ化テキスト。
2.  現在のデータベースの `sql_id`：`SQL_ID` で作成されたアウトライン。
3.  `format outline`：`TO target_stmt` を含むアウトライン。
4.  現在のデータベーステンプレート：`SCOPE = DATABASE` のテンプレートアウトライン。
5.  データベース間（テナント内）テンプレート：`SCOPE = TENANT` のテンプレートアウトライン。

現在のデータベーステンプレートはデータベース間テンプレートよりも優先順位が高く、曖昧さは生じません。

## 作成したOutlineが有効かどうかを確認する

Outlineが正常に作成され、期待どおりに機能するかを検証する必要があります。厳密OutlineとテンプレートOutlineの検証方法は若干異なります。

### 厳密Outlineの検証

厳密Outlineが有効になっているかを確認するには、以下の3つのステップで検証します：

1. Outlineが正常に作成されたことを確認します。

   `DBA_OB_OUTLINES`ビューを確認し、対応する名前のOutlineが正常に作成されたかどうかを確認します。

   ```sql
   obclient> SELECT * FROM DBA_OB_OUTLINES WHERE OUTLINE_NAME = 'otl_idx_c2'\G

   *************************** 1. row ***************************
           tenant_id: 1001
         database_id: 1100611139404776
          outline_id: 1100611139404777
       database_name: test
        outline_name: otl_idx_c2
   visible_signature: SELECT * FROM t1 WHERE c2 = ?
            sql_text: SELECT/*+ index(t1 idx_c2)*/ * FROM t1 WHERE c2 = 1
      outline_target:
         outline_sql: SELECT /*+ BEGIN_OUTLINE_DATA INDEX(@"SEL$1" "test.t1"@"SEL$1" "idx_c2") END_OUTLINE_DATA*/*
   FROM t1 WHERE c2 = 1
   ```

2. 新しいSQLの実行時に、バインドされたOutlineに基づいて新しい実行計画が生成されたかどうかを確認します。

   OutlineにバインドされたSQLで新しいクエリを実行した後、`GV$OB_PLAN_CACHE_PLAN_STAT` テーブルのそのSQLに対応する計画情報の `outline_id` を確認します。`outline_id` が `DBA_OB_OUTLINES` で確認した `outline_id` と同じ場合、バインドされたOutlineに従って生成された実行計画であることを意味し、そうでない場合はそうではありません。

   ```sql
   obclient> SELECT SQL_ID, PLAN_ID, STATEMENT, OUTLINE_ID, OUTLINE_DATA
         FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT
          WHERE STATEMENT LIKE '%SELECT * FROM t1 WHERE c2 =%'\G
   *************************** 1. row ***************************
         sql_id: ED570339F2C856BA96008A29EDF04C74
        plan_id: 17225
      statement: SELECT * FROM t1 WHERE c2 = ?
     outline_id: 1100611139404777
   outline_data: /*+ BEGIN_OUTLINE_DATA INDEX(@"SEL$1" "test.t1"@"SEL$1" "idx_c2") END_OUTLINE_DATA*/
   ```

3. 生成された実行計画が期待通りであるかどうかを確認します。

   バインドされたOutlineによって生成された計画であることを確認した後、生成された計画が期待通りであるかどうかを確認する必要があります。`GV$OB_PLAN_CACHE_PLAN_EXPLAIN` テーブルをクエリして、`plan_cache` にキャッシュされた実行計画の形を確認することができます。具体的な確認方法については、以下を参照してください。

   [リアルタイム実行計画の表示](../../200.sql-execution-plan/500.real-time-execution-plan-display.md)

   ```sql
   obclient> SELECT OPERATOR, NAME FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_EXPLAIN
         WHERE TENANT_ID = 1001 AND SVR_IP = '10.XXX.XXX.XXX'
          AND SVR_PORT = 30474 AND PLAN_ID = 17225;

   +--------------------+------------+
   | OPERATOR           | NAME       |
   +--------------------+------------+
   |  PHY_ROOT_TRANSMIT | NULL       |
   |   PHY_TABLE_SCAN   | t1(idx_c2) |
   +--------------------+------------+
   ```

### テンプレートOutlineの検証

テンプレートOutlineの検証方法は厳密Outlineと類似していますが、以下の点に注意する必要があります：

1. テンプレートOutlineが正常に作成されたことを確認します。

    `DBA_OB_OUTLINES` ビューの `pattern_rules` フィールドを確認し、テンプレートOutlineであるかどうかを確認します。`pattern_rules` が空でない場合、テンプレートOutlineです。すべてのテンプレートOutlineを確認するには：

    ```shell
    obclient> SELECT outline_name, visible_signature, pattern_rules
        FROM oceanbase.DBA_OB_OUTLINES
        WHERE pattern_rules IS NOT NULL
        AND pattern_rules != '';
    ```

2. SQLがテンプレートOutlineにヒットしたかどうかを確認します。

    テンプレートOutlineにヒットすると、`GV$OB_PLAN_CACHE_PLAN_STAT` の `outline_id` にも対応するOutlineの `ID` が設定されます (`outline_id` が0より大きい場合はヒットを意味します)。ヒットしたかどうかを確認するには：

    ```shell
    obclient> SELECT outline_id, outline_data
        FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT
        WHERE query_sql LIKE '%your_marker%'
        LIMIT 1;
    ```

3. 複数テーブルの検証。テンプレートOutlineについては、異なるシャーディングテーブルのSQLを使用して個別に検証し、すべての期待されるシャーディングテーブルが正しくテンプレートOutlineにヒットすることを確認することをお勧めします。

## Outlineの削除

Outlineを削除すると、対応するSQLはバインドされたOutlineに基づいて実行計画を再生成しなくなります。

アウトラインを削除する構文は以下のとおりです：

```sql
DROP OUTLINE outline_name
    [BINDING_RULE (binding_item)];

binding_item:
    SCOPE = {DATABASE | TENANT}
```

パラメータの説明は以下のとおりです：

* `outline_name`：削除するアウトライン名を指定します。
* `BINDING_RULE (binding_item)`：オプションです。アウトラインの削除レベルを指定するために使用します。

  * `BINDING_RULE (SCOPE = DATABASE)`：デフォルト値です。現在のデータベースレベルのアウトラインを削除することを指定します（`BINDING_RULE` パラメータを指定しない場合と同等です）。
  * `BINDING_RULE (SCOPE = TENANT)`：指定された名前のデータベース間（テナントレベル）アウトラインを削除します。

  <main id="notice" type='explain'>
    <h4>説明</h4>
    <p>V4.4.2バージョンでは、V4.4.2 BP3バージョンから <code>BINDING_RULE</code> 句が導入されました。</p>
  </main>

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p><ul><li>厳密アウトライン（<code>SCOPE = DATABASE</code>）を削除する場合、対応するデータベースで実行するか、<code>outline_name</code> にデータベース名を指定する必要があります。</li><li>データベース間アウトライン（<code>SCOPE = TENANT</code>）を削除する場合、任意のデータベースで実行できますが、<code>BINDING_RULE(SCOPE = TENANT)</code> を明示的に指定する必要があります。</li></ul></p>
</main>

## プランバインディングと実行計画キャッシュの関係

* `SQL_TEXT` を使用して厳密アウトラインを作成すると、SQLリクエストが新しい計画を生成してアウトラインを検索する際に使用するキーと、計画キャッシュが使用するキーは同じになります。つまり、どちらもSQLパラメータ化後のテキスト列です。
* テンプレートアウトラインは、Template Signatureを使用して候補をフィルタリングし、正規表現Patternの検証を通過した場合にヒットと判断します。テンプレートマッチング段階の追加オーバーヘッドは、主にASTレベルでのTemplate Signatureの生成と正規表現の検証によるものです。
* 厳密アウトラインの作成または削除時に、対応するSQLに新しいリクエストがあると、実行計画キャッシュ内の対応する実行計画が無効になり、バインドされたアウトラインに基づいて生成された実行計画に更新されます。
* テンプレートアウトラインの作成または削除時には、そのテンプレートパターンに一致するすべてのSQLの計画キャッシュが無効になります。

* アウトラインの作成または削除後、対応するSQLに新しいリクエストがあると、実行計画キャッシュ内の対応する実行計画が無効になり、バインドされたアウトラインに基づいて生成された実行計画に更新されます。

## パフォーマンスへの影響

| **シナリオ** | **複雑さ** | **説明** |
|----------|------------|----------|
| システム内にテンプレートアウトラインがない場合 | O(1) | `has_template_outline` ショートサーキットスイッチによりテンプレートマッチングパスがスキップされるため、テンプレートアウトラインのないテナントでは追加のオーバーヘッドが発生しません。|
| 厳密アウトラインヒット | O(1) | 既存のハッシュマッチングを再利用するため、厳密バインドのパフォーマンスはテンプレートバインド機能の影響を受けません。|
| テンプレートアウトラインマッチング | O(1) ハッシュ + n × O(T) Pattern検証 | `n` は同じシグネチャを持つ候補テンプレートの数、`T` はSQL内のテーブル数です。|
| 変数一貫性検証 | O(V) | `V` は変数数で、通常は ≤ 3 です。|

正規表現の長さは制限されており（≤128文字）、タイムアウトメカニズムも備えているため、病的な正規表現によるマッチングの遅延を防ぎます。

## 制限と注意事項

* `MAP` に `db.table` 形式が含まれる場合、`SCOPE = TENANT` を明示的に指定する必要があります。そうでない場合、作成時にエラーが発生します。
* 同一の `BINDING_RULE` 内で、各データベース名 `pattern` とテーブル名 `pattern` には最大1つの変数しか使用できません。複雑な式は複数のアウトラインに分割してください。
* 変数は定義後に参照する必要があります。同名の変数定義は1回だけ可能です。
* `db.*` 構文はサポートされていません。`'db_${D:[0-9]+}'.'${T:.*}'` などの等価表現を使用してください。
* 正規表現は `POSIX` 拡張構文を採用しており、逆参照やゼロ幅アサーションなどの複雑な機能はサポートされていません。
* `SCOPE = DATABASE` のみで `MAP` がない場合、アウトラインの動作は完全に変わらず、従来の厳密アウトラインと同等です。
* `MAX_CONCURRENT` スロットリング系アウトラインは、現在 `BINDING_RULE` をサポートしていません。
* テナント間のアウトラインバインディングはサポートされていません。
