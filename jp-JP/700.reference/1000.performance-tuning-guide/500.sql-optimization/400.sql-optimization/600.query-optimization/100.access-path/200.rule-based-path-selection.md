# ルールに基づくパス選択

本記事では、OceanBaseデータベースのパス選択ルール体系について説明します。

現在、OceanBaseデータベースのパス選択ルール体系は、プレフィックスルール（順方向ルール）とSkyline剪枝ルール（逆方向ルール）に分かれています。プレフィックスルールは、クエリがどのインデックスを使用するかを直接決定し、強いマッチングを持つルール体系です。

Skyline剪枝ルールは、2つのインデックスを比較し、ある定義された次元で一方のインデックスがもう一方のインデックスより優れている（Dominate）場合、劣るインデックスは除外されます。最後に除外されなかったインデックスに対してコスト比較を行い、最適な実行計画を選択します。

現在、OceanBaseデータベースのオプティマイザーは、まずプレフィックスルールを優先してインデックスを選択します。一致するインデックスがない場合、Skyline剪枝ルールが一部の劣るインデックスを除外し、最後にコストモデルが除外されなかったインデックスの中からコストが最も低いパスを選択します。

## 前提条件

現在のOceanBaseデータベースにおけるプリフィルタールールは、単純な単一テーブルスキャンにのみ使用されます。プリフィルタールールは強力なマッチングルールであり、一度ヒットすると、そのルールで指定されたインデックスが直接選択されるため、誤った実行計画が選ばれるのを防ぐために、その適用シナリオは制限されています。

現在のOceanBaseデータベースでは、「クエリ条件がすべてのインデックスキーをカバーできるかどうか」と「そのインデックスを使用する際に再テーブルアクセスが必要かどうか」という2つの情報に基づき、プリフィルタールールを優先順位に応じて以下の3種類のマッチングタイプに分類しています：

* 「一意インデックスが完全一致 + 再テーブルアクセス不要（主キーは一意インデックスとして処理される）」の場合、そのインデックスを選択します。複数のこのようなインデックスが存在する場合、インデックス列数が最も少ないものを選択します。

* 「通常インデックスが完全一致 + 再テーブルアクセス不要」の場合、そのインデックスを選択します。複数のこのようなインデックスが存在する場合、インデックス列数が最も少ないものを選択します。

* 「一意インデックスが完全一致 + 再テーブルアクセスあり + 再テーブルアクセス数が一定のしきい値未満」の場合、そのインデックスを選択します。複数のこのマッチングタイプのインデックスが存在する場合、再テーブルアクセス数が最も少ないものを選択します。

ここで注意が必要なのは、インデックスの完全一致とは、インデックスキーすべてに等しい条件（`get`または`multi-get`に対応）が存在することを指します。

以下の例では、クエリQ1はインデックス`uk1`にヒットします（一意インデックスが完全一致 + 再テーブルアクセス不要）；クエリQ2はインデックス`uk2`にヒットします（一意インデックスが完全一致 + 再テーブルアクセスあり + 再テーブルアクセス行数が最大4行）。

1. テーブル`test`を作成します。

    ```shell
    obclient> CREATE TABLE test(a INT PRIMARY KEY,
        b INT,
        c INT,
        d INT,
        e INT,
        UNIQUE KEY UK1(b,c),
        UNIQUE KEY UK2(c,d)
        );
    ```

2. クエリ例です。

    Q1：

    ```shell
    obclient> SELECT b,c FROM test WHERE (b = 1 OR b = 2) AND (c = 1 OR c =2);
    ```

    Q2：

    ```shell
    obclient> SELECT * FROM test WHERE (c = 1 OR c =2) AND (d = 1 OR d = 2);
    ```

## Skyline剪枝規則

Skyline演算子は、2001年に学術界によって提案された新しいデータベース演算子です（標準SQL演算子ではありません）。それ以来、学術界ではSkyline演算子に関する多くの研究（構文、意味論、実行などを含む）が行われています。

Skylineという言葉は文字通り、空の中のいくつかの境界点を指し、これらの点が探索空間における最適解の集合を形成します。例えば、価格が最も安く、距離が最も短いホテルを探す場合、これを二次元空間に例えることができます。横軸が価格、縦軸が距離を表し、二次元空間上の各点が一つのホテルを表します。下図のように、最適解は必ずこの空の境界線上にあります。点AがSkyline上にない場合、両方の次元で点Aよりも優れた点BをSkyline上で必ず見つけることができます。このシナリオでは、それは距離が近く、価格が安いホテルであり、点Bが点Aを支配すると言います。したがって、ユーザーが複数の次元の重みを測定できない場合、または複数の次元を総合的に定量化できない場合（総合的に定量化できる場合は、「SQL関数+ `ORDER BY`」を使用すれば解決できます）、Skylineアルゴリズムを使用できます。

<!-- ![skyline-pruning-rules.png](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.1/700.reference/1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/600.query-optimization/100.access-path/skyline-pruning-rules.png) -->

Skylineの原理は、与えられたオブジェクト集合Oから、他のオブジェクトに支配されていないオブジェクトの集合を見つけることです。あるオブジェクトAがすべての次元で別のオブジェクトBに支配されておらず、かつAが少なくとも一つの次元でBを支配する場合、AはBを支配すると言います。したがって、Skylineでは次元の選択と、各次元における支配関係の定義が重要です。N個のインデックスからなるパス`<idx_1，idx_2，idx_3...idx_n>`がオプティマイザーによって選択可能であり、クエリQに対してインデックス`idx_x`が定義された次元でインデックス`idx_y`を支配する場合、インデックス`idx_y`を事前に除外し、最終的なコスト計算に含めないことができます。

## 次元の定義

Skyline剪枝規則では、各インデックス（主キーも一種のインデックスです）に対して、以下の3つの次元が定義されています：

* 再テーブルアクセスの有無

* Interesting Orderの有無

* インデックスのプレフィックスがQuery Rangeを抽出できるかどうか

以下の例を用いて説明します：

```shell
obclient> CREATE TABLE skyline(pk INT PRIMARY KEY,
    a INT,
    b INT,
    c INT,
    KEY idx_a_b(a, b),
    KEY idx_b_c(b, c),
    KEY idx_c_a(c, a)
    );
```

* テーブルへの再アクセス：このクエリでメインテーブルに再アクセスが必要かどうかを示します。

  ```shell
  /* インデックス idx_a_b を使用する場合、メインテーブルに再アクセスが必要です。インデックス idx_a_b には列 c が含まれていないため*/
  obclient>SELECT /*+INDEX(skyline idx_a_b)*/ * FROM skyline;
  ```

* Interesting Order：利用可能な適切な順序があるかどうかを考慮します。

  ```shell
  /* インデックス idx_b_c はORDER BYステートメントを省略できます*/
  obclient>SELECT pk, b FROM skyline ORDER BY b;
  ```

* インデックスのプレフィックスがクエリ範囲を抽出できるかどうか。

  ```shell
  /* インデックス idx_c_a を使用すると、必要な行の範囲を迅速に特定でき、テーブル全体をスキャンする必要がありません*/
  obclient>SELECT pk, b FROM skyline WHERE c > 100 AND c < 2000;
  ```

これら3つの次元に基づき、Skylineはインデックス間のDominate関係を定義しています。インデックスAが3つの次元すべてでインデックスBより劣っておらず、少なくとも1つの次元でBより優れている場合、インデックスBに基づいて最終的に生成される実行計画はインデックスAより優れている可能性がないため、インデックスBを直接削除できます。判断基準は以下の通りです：

* インデックス `idx_A` でテーブルへの再アクセスが不要であり、インデックス `idx_B` でテーブルへの再アクセスが必要な場合、この次元ではインデックス `idx_A` が `idx_B` をDominatesします。

* インデックス `idx_A` から抽出されたInteresting Orderがベクトル `Va<a1, a2, a3 ...an>` で、インデックス `idx_B` から抽出されたInteresting Orderがベクトル `Vb<b1, b2, b3...bm>` であり、かつ `n > m` で、`ai = bi (i=1..m)` の場合、この次元ではインデックス `idx_A` が `idx_B` をDominatesします。

* インデックス idx_A でQuery Rangeを抽出できる列の集合が `Sa<a1, a2, a3 ...an>` で、インデックス `idx_B` でQuery Rangeを抽出できる列の集合が `Sb <b1, b2, b3...bm>` であり、`Sa` が `Sb` のSuper Setの場合、この次元ではインデックス `idx_A` が `idx_B` をDominatesします。

### テーブルへの再アクセス

テーブルへの再アクセスとは、クエリで必要な列がインデックスに含まれているかどうかを確認することです。主テーブルとインデックステーブルの両方にInteresting Orderがなく、Query Rangeを抽出できない場合など、特定のシナリオでは特別な検討が必要です。そのような場合、直接メインテーブルを参照することが必ずしも最適解とは限りません。

```shell
obclient> CREATE TABLE t1(pk INT PRIMARY KEY,
    a INT,
    b INT,
    c INT,
    v1 VARCHAR(1000),
    v2 VARCHAR(1000),
    v3 VARCHAR(1000),
    v4 VARCHAR(1000),
    INDEX idx_a_b(a, b)
    );
```

```shell
obclient>SELECT a, b,c FROM t1 WHERE b = 100;
```

| **インデックス**  | **Index Back** | **Interesting Order** | **Query Range** |
|---------|----------------|-----------------------|-----------------|
| primary | no             | no                    | no              |
| idx_a_b | yes            | no                    | no              |

メインテーブルは非常に広く、インデックステーブルは非常に狭いため、次元分析によればメインテーブルはインデックス `idx_a_b` をDominatesします。しかし、インデックススキャンに加えてテーブルへの再アクセスが必要な場合、それがメインテーブルの全表スキャンよりもコストが高いとは限りません。簡単に言えば、インデックステーブルは1つのマクロブロックしか読み取らなくて済む可能性がありますが、メインテーブルは10個のマクロブロックを必要とする可能性があります。このような場合、ルールを緩和し、具体的なフィルタ条件を総合的に考慮する必要があります。

### Interesting Order

オプティマイザーは、Interesting Orderを利用して基盤となる順序を活用することで、基盤レベルでスキャンされた行のソートが不要になります。また、`ORDER BY` を排除し、`MERGE GROUP BY` を実行したり、パイプラインを向上させたり（マテリアライズが不要な場合）することも可能です。

```shell
obclient> CREATE TABLE skyline(pk INT PRIMARY KEY,
    v1 INT,
    v2 INT,
    v3 INT,
    v4 INT,
    v5 INT,
    KEY idx_v1_v3_v5(v1, v3, v5),
    KEY idx_v3_v4(v3, v4)
    );
```

```shell
obclient> CREATE TABLE tmp (c1 INT PRIMARY KEY, c2 INT, c3 INT);
```

```shell
obclient> (SELECT DISTINCT v1, v3 FROM skyline JOIN tmp
    WHERE skyline.v1 = tmp.c1
    ORDER BY v1, v3)
    UNION (SELECT c1, c2 FROM tmp);
```

<!-- ![image](https://help-static-aliyun-doc.aliyuncs.com/assets/img/zh-CN/1248744061/p167292.png "image") -->

実行計画からわかるように、`ORDER BY` が排除され、`MERGE DISTINCT` が使用されており、`UNION` も `SORT` を行っていません。基盤レベルの `TABLE SCAN` で得られた順序が、上位の演算子で利用できることがわかります。言い換えれば、`idx_v1_v3_v5` が出力する行の順序を保持することで、後続の演算子が順序を保ちながらより最適な操作を実行できます。オプティマイザーは、これらの順序を認識した場合にのみ、より最適な実行計画を生成できます。

そのため、Skyline剪枝における Interesting Orderの判断では、各インデックスが最大限に活用できる順序を十分に考慮する必要があります。例えば、前述の例では最大の順序は実際には `(v1, v3)` であり、単に `v1` だけではありません。`MERGE JOIN` で得られた順序 `(v1, v3)` は、`MERGE DISTINCT` 演算子を経て、最終的に `UNION DISTINCT` 演算子に至ります。

### Query Range

Query Rangeの抽出により、基盤レベルが抽出されたRangeに基づいて特定のマクロブロックを直接特定しやすくなり、ストレージ層のI/Oが削減されます。

例えば、`SELECT * FROM t1 WHERE pk < 100 AND pk > 0` は、一次インデックスの情報に基づいて特定のマクロブロックを直接特定でき、クエリを高速化します。Query Rangeが正確であればあるほど、データベースがスキャンする行数を減らすことができます。

```shell
obclient> CREATE TABLE t1 (pk INT PRIMARY KEY,
    a INT,
    b INT,
    c INT,
    KEY idx_b_c(b, c),
    KEY idx_a_b(a, b)
    );
```

```shell
obclient> SELECT b FROM t1 WHERE a = 100 AND b > 2000;
```

インデックス `idx_b_c` が抽出できるQuery Rangeのインデックスプレフィックスは (b) であり、インデックス `idx_a_b` が抽出できるQuery Rangeのインデックスプレフィックスは (a, b) です。したがって、この観点から見ると、インデックス `idx_a_b` は `idx_b_c` をDominatesします。
