# SQLチューニングの概要

SQLチューニングとは、SQLの実行計画、実行モニタリング情報、システム構成、システム負荷など、さまざまな要素を総合的に分析し、SQLの実行戦略を調整することで、リソース利用率を最大限に引き出すことを指します。

SQLチューニングの方法は、一般的に単一SQLのチューニングとシステム全体のSQLチューニングに分けられます。

## 単一SQLのチューニング

単一SQLのチューニングでは、チューニング対象はそのSQLの実行そのものであり、主なチューニング目標には、そのSQLの実行時間や実行時のリソース消費量などが含まれます。一般的なチューニング手法としては、アクセスパスの調整、実行順序の変更、論理的な書き換えなどが挙げられます。

単一SQLの実行計画に関するパフォーマンスチューニングは、単一テーブルへのアクセスと複数テーブルへのアクセスという2つのシナリオに分類されます。

| **シナリオ** |        **SQLチューニングのポイント**     |
|--------|----------------------------|
| 単一テーブルアクセス   | <ul><li> アクセスパスでインデックススキャンが有効になっているかどうか。インデックススキャンを使用すると、データへのアクセス量を削減できます。</li>   <li>適切なインデックスが作成されているかどうか。インデックスソートを使用して、ソートや集計などの時間のかかる操作を削減します。</li>   <li> パーティションカットが正しく行われているかどうか。適切なパーティション条件は、不要なパーティションアクセスを削減できます。</li>   <li> クエリの並列度を向上させているかどうか。パーティション数が多い場合、並列度を高めることで、より多くのリソースを犠牲にして単一のSQLクエリの性能を向上させます。</li></ul>    |
| 複数テーブルアクセス   | 単一テーブルのSQLチューニングに加えて、以下の複数テーブル間の結合にも注意が必要です： <ul><li> 結合順序</li>   <li> 結合アルゴリズム</li>   <li> スタンドアロンまたは並列結合のデータ再分散方式   <li> クエリの書き換え </li> </ul>                                                                                                                                     |

## システム全体のSQLチューニング

システム全体のSQLチューニングの目的は、システム全体のスループットや利用率を向上させることです。このプロセスでは、通常複数のSQLの実行計画を組み合わせて現在のシステム負荷特性を総合的に分析し、ホットスポット行の競合やBuffer Cacheのヒット率など、グローバルな観点からのチューニングポイントに重点を置きます。

スループットに関するパフォーマンスチューニングでは、一定のリソース（CPU、I/O、ネットワークなど）の条件下で、データベースシステムが処理できるリクエスト量を最大化することを主な考慮事項とします。主に以下の点に注目します：

|     **主な方法**      |      **説明**       |
|-------------------|-----------------------------|
| スローSQLの最適化           | 具体的なスローSQLを特定した後、個々のSQLに対してパフォーマンスチューニングを行います。詳細については、例[特定の期間内に実行時間が上位N位のリクエストを照会する](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/1000.query-the-top-n-requests-with-the-most-execution-time.md)を参照してください。  |
| SQLリクエストトラフィックリソースの均衡    | 例[クラスタのSQLリクエストトラフィックが均衡しているかどうかを確認する](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/600.check-whether-the-sql-request-traffic-is-balanced.md)を参照してください。 均衡に影響を与える主な要因は以下のとおりです： <ul><li> `ob_read_consistency`の設定</li>   <li> Primary Zoneの設定</li>   <li> ProxyまたはJavaクライアントルーティングポリシー関連の設定</li>   <li> ビジネス上のホットクエリパーティションが均衡しているかどうか </li>   |
| サブプランのRPCリクエストトラフィックリソースの均衡 | 例[分散サブプランのRPC実行数が均衡しているかどうかを確認する](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/1200.check-whether-the-number-of-distributed-rpc-executions-is-balanced.md)を参照してください。 サブプランのリクエストが均等になるかどうかに影響を与える主な要因は以下のとおりです： <ul><li> OBServerノード内部のルーティングポリシー関連の設定</li>   <li> ビジネス上のホットクエリのパーティションが均衡しているかどうか  </li> |
