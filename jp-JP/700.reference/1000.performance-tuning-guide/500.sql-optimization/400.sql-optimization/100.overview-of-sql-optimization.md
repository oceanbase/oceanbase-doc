# SQLチューニングの概要

SQLチューニングとは、SQLの実行計画、実行監視情報、システム構成、システム負荷など、多角的な要素を総合的に分析し、SQLの実行戦略を調整することで、リソース利用を最大化することです。

SQLチューニングの手法は、一般的に単一SQLチューニングとシステムSQLチューニングに分けられます。

## 単一SQLチューニング

単一SQLチューニングでは、最適化の対象はチューニング対象のSQL実行そのものです。一般的なチューニングの目標には、そのSQLの実行時間やランタイムのリソース消費などが含まれます。一般的なチューニング手法には、アクセスパスの調整、実行順序の変更、論理的な書き換えなどがあります。

単一SQLの実行計画に対するパフォーマンスチューニングは、単一テーブルアクセスと複数テーブルアクセスの2つのシナリオに分けられます。

| **シナリオ** |        **SQLチューニングの注目ポイント**     |
|--------|----------------------------|
| 単一テーブルアクセス   | <ul><li> アクセスパスがインデックススキャンを有効にしているかどうか。インデックススキャンを使用すると、データへのアクセス量を削減できます。</li>   <li>適切なインデックスが作成されているかどうか。インデックスソートを使用して、ソートや集計など時間のかかる操作を削減します。</li>   <li> パーティションプルーニングが正しく行われているかどうか。適切なパーティション条件により、不必要なパーティションアクセスを削減できます。</li>   <li> クエリの並列度が向上しているかどうか。パーティション数が多い場合、並列度を向上させることで、より多くのリソースを犠牲にして単一SQLクエリのパフォーマンス向上を図ります。</li></ul>    |
| 複数テーブルアクセス   | 単一テーブルのSQLチューニングに加え、以下のような複数テーブル間の結合問題にも注意する必要があります： <ul><li> 結合の順序</li>   <li> 結合アルゴリズム</li>   <li> 跨マシンまたは並列結合のデータ再配分方法   <li> クエリの書き換え </li> </ul>                                                                                                                                     |

## システムSQLチューニング

システムSQLチューニングの目的は、システム全体のスループットやシステム利用率などを向上させることです。システムSQLチューニングのプロセスでは、通常、複数のSQLの実行計画を組み合わせ、現在のシステム負荷特性を総合的に分析する必要があります。主にホットスポット行の競合やBuffer Cacheのヒット率など、グローバルなチューニングポイントに注目します。

スループットに対するパフォーマンスチューニングでは、一定のリソース(CPU、I/O、ネットワークなど)の条件下で、データベースシステムのリクエスト処理量を最大化することを主な考慮事項とします。主に以下の点に注目します：

|     **主要な方法**      |      **説明**       |
|-------------------|-----------------------------|
| 遅延延SQLの最適化           | 具体的な遅延延SQLを特定した後、単一SQLに対してパフォーマンスチューニングを行います。例：[特定期間内に実行時間が上位N位のリクエストを照会する](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/1000.query-the-top-n-requests-with-the-most-execution-time.md)。  |
| SQLリクエストトラフィックリソースの均等化    | 例：[クラスタのSQLリクエストトラフィックが均等かどうかを確認する](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/600.check-whether-the-sql-request-traffic-is-balanced.md)を参照してください。 均等化に影響を与える主な要因は以下の通りです： <ul><li> `ob_read_consistency` の設定方法</li>   <li> Primary Zoneの設定方法</li>   <li> ProxyまたはJavaクライアントのルーティングポリシー関連設定</li>   <li> 業務上のホットクエリパーティションが均等かどうか </li>   |
| サブプランのRPCリクエストトラフィックリソースの均等化 | 例：[分散サブプランのRPC実行数が均等かどうかを確認する](300.monitor-sql-execution-performance/400.sql-performance-analysis-example/1200.check-whether-the-number-of-distributed-rpc-executions-is-balanced.md)を参照してください。 サブプランのリクエストが均等であるかどうかに影響を与える主な要因は以下の通りです： <ul><li> OBServerノード内部のルーティングポリシー関連設定</li>   <li> 業務上のホットクエリのパーティションが均等かどうか  </li> |
