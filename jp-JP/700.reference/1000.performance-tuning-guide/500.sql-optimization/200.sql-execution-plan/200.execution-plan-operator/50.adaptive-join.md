# Adaptive Join

通常、結合操作を含むクエリを実行する際、オプティマイザーは計画生成段階で統計情報に基づいて最適な結合方法を選択します。しかし、これらの統計情報が不正確または古くなっている場合があり、オプティマイザーが選択した結合戦略が最適でない可能性があります。例えば、オプティマイザーが統計情報に基づいてテーブルの行数を少ないと推定した場合、NLJ（Nested-Loop Join）を使用することを選択するかもしれませんが、実際の行数が予想よりもはるかに多い場合、HJ（Hash Join）の方がパフォーマンスが良い選択肢となる可能性があります。
この問題を解決するために、適応型結合（Adaptive Join、AJ）機能が導入されました。この機能により、データベースは実行時に動的に最も適切な結合方法を選択できるようになり、事前の統計情報に完全に依存する必要がなくなりました。

例：

このSQLが生成するadaptive join計画は以下のとおりであり、クエリ対象の地域が大きい場合でも小さい場合でも、パフォーマンスの良い結合アルゴリズムを選択できるようになります。

```sql
obclient> CREATE TABLE users(id int, region int, name varchar(100));
Query OK, 0 rows affected (0.088 sec)

obclient> CREATE TABLE orders(id int, user_id int);
Query OK, 0 rows affected (0.080 sec)

obclient> CREATE INDEX idx_userid ON orders(user_id);
Query OK, 0 rows affected (0.486 sec)

obclient> EXPLAIN SELECT COUNT(1) FROM orders o, users u WHERE u.region = "?" AND u.id = o.user_id;
+-----------------------------------------------------------------------------------------------+
| Query Plan                                                                                     |
+-----------------------------------------------------------------------------------------------+
| ======================================================================================         |
| |ID|OPERATOR                          |NAME                    |EST.ROWS|EST.TIME(us)|         |
| --------------------------------------------------------------------------------------         |
| |0 |SCALAR GROUP BY                   |                        |1       |9833        |         |
| |1 |└─HASH JOIN                       |                        |4952    |9743        |         |
| |2 |  ├─NESTED-LOOP JOIN              |                        |512     |9743        |         |
| |3 |  │ ├─STATISTICS COLLECTOR        |                        |512     |176         |         |
| |4 |  │ │ └─TABLE FULL SCAN           |U                       |512     |96          |         |
| |5 |  │ └─DISTRIBUTED TABLE RANGE SCAN|ORDERS_alias(IDX_USERID)|10      |18          |         |
| |6 |  └─TABLE FULL SCAN               |O(IDX_USERID)           |9999    |273         |         |
| ======================================================================================         |
```

オプティマイザーはこの計画を生成する際に、行数のしきい値を計算します。左テーブルの行数がこのしきい値を下回る場合、`nested loop join` の方がパフォーマンスが良く、そうでない場合は `hash join` の方がパフォーマンスが良いです。

実行段階では、計画内の3番目の `statistics collector` 演算子が左テーブルのデータを収集し、行数がしきい値を超えているかどうかを判断します。しきい値を超えていない場合、1番目の `hash join` 演算子を `bypass` に設定し、そうでない場合は2番目の `nested loop join` 演算子を `bypass` に設定します。`bypass` に設定された演算子は、下層の演算子のデータをそのまま上層に吐き出し、実際の処理は行いません。

場合によっては、左テーブルの行数が大幅に変化し、オプティマイザーが `adaptive join` を生成していない可能性があります。その場合は、ヒントを追加して手動で `adaptive join` の使用を指定することができます。関連するヒントは `use_adaptive` です。
上記の例にヒントを追加したSQLは以下のとおりです：

```sql
obclient> EXPLAIN SELECT /*+ leading(u o) use_adaptive(o) */ count(1) FROM orders o, users u WHERE u.region = 1 AND u.id = o.user_id;
```

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p><code>use_adaptive</code> で指定するのは結合の右テーブルでなければなりません。</p>
</main>
