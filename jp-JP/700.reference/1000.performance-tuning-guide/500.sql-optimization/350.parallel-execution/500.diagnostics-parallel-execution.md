# パラレル実行の問題診断

パラレル実行の問題を診断するには、大きく2つの側面からアプローチできます。まず、システム全体として、ネットワーク、ディスクI/O、CPUがフルに使われていないかどうかを確認します。次に、具体的なSQL文に焦点を当て、問題のあるSQL文がどこにあり、その内部状態はどうなっているかを特定します。

## システム診断

業務が比較的忙しいシステムでパフォーマンスの問題が発生した場合、まずはシステムレベルで初期診断を行う必要があります。一般的には以下の2つの方法があります：

* OCP（OceanBase Cloud Platform）：システム性能の可視化観測をサポートします。
* tsarなどのコマンドラインシステムツール：ネットワーク、ディスク、CPUなどの履歴モニタリングデータの照会をサポートします。

tsarはシステム監視およびパフォーマンス分析ツールであり、CPU、ディスク、ネットワークなどの詳細情報を提供できます。以下はtsarコマンドのいくつかの一般的な使用法です：

CPU使用率を確認する：

```sql
tsar --cpu
```

ディスクI/O使用状況を確認する：

```sql
tsar --io
```

ネットワーク転送速度を確認する：

```sql
tsar --traffic
```

上記の例に加えて、tsarは他のオプションやパラメータもサポートしています。例えば、パラメータ-d 2を使用すると2日前から現在までのデータを確認でき、-i 1は1分ごとに1回の収集表示を意味します。

過去2日間のCPU使用状況を確認する：

```sql
tsar -n 2 -i 1 --cpu
```

ディスクまたはネットワークがパンクした場合は、まずハードウェア容量が不足しているか、同時実行の負荷が高すぎるという観点から問題を解決します。

## SQL診断

パラレル実行に関する問題が発生した場合、SQL層面、パラレル実行スレッド層面、演算子層面から順次確認することができます。

### SQLがまだ実行中であることを確認する

SQLが正常に実行されているかどうかを確認します。TIMEフィールドに注目し、`GV$OB_PROCESSLIST`ビューのTIMEフィールドが毎回増加しており、かつSTATEがACTIVEであれば、Queryはまだ実行中であることを示します。

SQLが繰り返し再試行されていないかどうかを確認します。SQLが繰り返し再試行により結果を返していない場合、RETRY_CNT、RETRY_INFOフィールドに関連情報が記録されます。そのうちRETRY_CNTは再試行回数を表し、RETRY_INFOは最後の再試行の原因を表します。
再試行が発生していない場合、RETRY_CNTは0です。TOTAL_TIMEフィールドは、各再試行を含む累計実行時間を表します。

SQLが繰り返し再試行されていることが判明した場合、RETRY_INFOに記載されているエラーコードに基づいて、介入が必要かどうかを判断します。V4.1以前では、最も一般的なエラーは-4138（OB_SNAPSHOT_DISCARDED）でした。このような状況に遭遇した場合は、[パラレル実行の分類](150.classification-of-parallel-execution.md)を参照して、undo_retention値を大きくすることで解決できます。

```sql
-- MySQLモード
SELECT
  TENANT,INFO,TRACE_ID,STATE,TIME,TOTAL_TIME,RETRY_CNT,RETRY_INFO
FROM
  oceanbase.GV$OB_PROCESSLIST;

-- Oracleモード
SELECT
  TENANT,INFO,TRACE_ID,STATE,TIME,TOTAL_TIME,RETRY_CNT,RETRY_INFO
FROM
  sys.GV$OB_PROCESSLIST;
```

### SQLがまだ実行中のパラレルクエリであることを確認する

OBServerクラスタ内で、すべてのアクティブなパラレル実行スレッドは`GV$OB_PX_WORKER_STAT`ビューで確認できます。

```sql
-- MySQLモード
obclient> SELECT * FROM oceanbase.GV$OB_PX_WORKER_STAT;
SESSION_ID: 3221520411
 TENANT_ID: 1002
    SVR_IP: 192.xx.xx.xx
  SVR_PORT: 19510
  TRACE_ID: Y4C360B9E1F4D-0005F9A76E9E66B2-0-0
     QC_ID: 1
    SQC_ID: 0
 WORKER_ID: 0
    DFO_ID: 0
START_TIME: 2023-04-23 17:29:17.372461

-- Oracleモード
obclient> SELECT * FROM SYS.GV$OB_PX_WORKER_STAT;
SESSION_ID: 3221520410
 TENANT_ID: 1004
    SVR_IP: 192.xx.xx.xx
  SVR_PORT: 19510
  TRACE_ID: Y4C360B9E1F4D-0005F9A76E9E66B1-0-0
     QC_ID: 1
    SQC_ID: 0
 WORKER_ID: 0
    DFO_ID: 0
START_TIME: 2023-04-23 17:29:15.372461
```

`GV$OB_PROCESSLIST`から取得したTRACE_IDを組み合わせることで、このビューを通じて、SQLが現在どのDFOを実行しているか、また実行時間などの情報を確認できます。

このビューで何も見つからない場合でも、`GV$OB_PROCESSLIST`には依然として対応するSQLが表示されている可能性があります。その理由としては以下のものが考えられます：

* すべてのDFOが完了し、結果セットが大きいため、現在クライアントへのデータ出力段階にある。
* 最上位のDFO以外のすべてのDFOが完了している。

### 各演算子の実行状況の確認

oceanbase.GV$SQL_PLAN_MONITOR(MySQL)またはSYS.GV$SQL_PLAN_MONITOR(Oracle)を使用して、各パラレルワーカースレッド内の各演算子の実行状態を確認できます。V4.1以降では、`GV$SQL_PLAN_MONITOR`には2つの部分のデータが含まれます：

* 実行完了した演算子。実行完了とは、この演算子がcloseインターフェースを呼び出し、現在のスレッドでデータを処理しなくなったことを指します。
* 実行中の演算子。実行中とは、この演算子がまだcloseインターフェースを呼び出しておらず、データ処理中であることを指します。この部分の演算子のデータを読み取るには、クエリ`GV$SQL_PLAN_MONITOR`ビューのwhere条件でrequest_id < 0を指定する必要があります。request_id < 0条件でこのビューをクエリする場合、これを「リアルタイムSQL PLAN MONITOR」へのアクセスとも呼びます。このアクセスインターフェースは今後変更される可能性があります。

V4.1以前では、実行完了した演算子の状態のみを確認できました。

`GV$SQL_PLAN_MONITOR`にはいくつか重要なフィールドがあります：

* TRACE_ID：1つのSQLを一意に識別します。
* PLAN_LINE_ID：実行計画内の演算子の番号で、explainステートメントで確認できる番号に対応します。
* PLAN_OPERATION：演算子名。例えば、TABLE SCAN、HASH JOINなどです。
* OUTPUT_ROWS：現在の演算子が出力した行数。
* FIRST_CHANGE_TIME：演算子が最初の行データを吐き出した時間。
* LAST_CHANGE_TIME：演算子が最後の行データを吐き出した時間。
* FIRST_REFRESH_TIME：演算子の監視開始時間。
* LAST_REFRESH_TIME：演算子の監視終了時間。

上記のいくつかのフィールドに基づいて、演算子がデータを処理する主要な動作を基本的に描き出すことができます。以下にいくつかのシナリオを例示します：

* 実行完了したSQLを確認し、各演算子が実行にいくつのスレッドを使用しているかを確認します：

```sql
SELECT PLAN_LINE_ID, PLAN_OPERATION, COUNT(*) THREADS
FROM GV$SQL_PLAN_MONITOR
WHERE TRACE_ID = 'YA1E824573385-00053C8A6AB28111-0-0'
GROUP BY PLAN_LINE_ID, PLAN_OPERATION
ORDER BY PLAN_LINE_ID;

+--------------+------------------------+---------+
| PLAN_LINE_ID | PLAN_OPERATION         | THREADS |
+--------------+------------------------+---------+
|            0 | PHY_PX_FIFO_COORD      |       1 |
|            1 | PHY_PX_REDUCE_TRANSMIT |       2 |

|            3 | PHY_TABLE_SCAN         |       2 |

```

* 実行中のSQLを確認し、現在実行中の演算子と使用しているスレッド数、吐き出された行数を確認します：

```sql
SELECT PLAN_LINE_ID, CONCAT(LPAD('', PLAN_DEPTH, ' '), PLAN_OPERATION) OPERATOR, COUNT(*) THREADS, SUM(OUTPUT_ROWS) ROWS
FROM GV$SQL_PLAN_MONITOR
WHERE TRACE_ID = 'YA1E824573385-00053C8A6AB28111-0-0' AND REQUEST_ID < 0
GROUP BY PLAN_LINE_ID, PLAN_OPERATION, PLAN_DEPTH
ORDER BY PLAN_LINE_ID;
```

* 実行完了したSQLを確認し、各演算子が処理した行数と吐き出した行数を確認します：

```sql
SELECT PLAN_LINE_ID, CONCAT(LPAD('', PLAN_DEPTH, ' '), PLAN_OPERATION) OPERATOR, SUM(OUTPUT_ROWS) ROWS
FROM GV$SQL_PLAN_MONITOR
WHERE TRACE_ID = 'Y4C360B9E1F4D-0005F9A76E9E6193-0-0'
```

### スローPDMLの診断

V3.x系では、PDMLには一定の特殊性があり、長時間実行されるPDMLステートメントは`undo_retention`変数の制限を受けます。実行時間が`undo_retention`を超えると、SQLレベルで自動リトライが発生する可能性があり、ユーザー側から見るとこのPDMLステートメントが終了しないように見えます。

以下のいくつかのビューからPDMLの問題を診断できます：

1. PDMLが実行中であることを確認します。

   ```sql
   obclient> SELECT * FROM .all_virtual_px_worker.stat;
   ```

2. PDMLの合計実行回数(threadsフィールド)を確認します。これが並列度よりも大幅に大きい場合、リトライが発生していることを意味します。

   ```sql
   obclient> select op_id,op,rows,rescan, threads, (close_time - open_time) open_dt, (last_row_eof_time-first_row_time) row_dt, open_time, close_time, first_row_time, last_row_eof_time FROM
   -> (
   -> select plan_line_id op_id, concat(lpad('', plan_depth, ''), plan operation) op, sum(output_rows) rows, sum(STARTS) rescan,min(first_refresh_time) open_time, max(last_refresh_time) close_time,min(first_change_time) first_row_time, max(last_change_time) last_row_eof_time,count(1) threads from oceanbase.gv$sql_plan_monitor where trace_id = 'YB42C0A8051D-000600EFF65FBCFB-0-0' group by plan_line_id, plan_operation order by plan_line_id
   -> )a;
   ```

3. processlist仮想テーブルからさらにリトライが発生していることを確認できます。retry_cntフィールドが0より大きい場合です。

   ```sql
   -- time: 今回のリトライが実行されている時間
   -- total_time: ユーザーがSQLを開始してから現在までの経過時間
   -- retry_cnt: 既にリトライが何回行われたか。リトライが発生していない場合、retry_cnt = 0
   -- retry_info: 最後のリトライがどのエラーコードによってトリガーされたか
   select time, total_time, trace_id, retry_cnt, retry_info
   from __all_virtual_processlist;
   ```

4. undo_retentionを変更し、その値を単一PDML実行の最大時間よりも大きくします。単位は「秒」です。

   ```sql
   obclient> SHOW VARIABLES LIKE "%undo%"
   +---------------+-------+
   | Variable_name | Value |
   +---------------+-------+
   | undo_retention| 1800  |
   +---------------+-------+
   1 row in set
   ```
