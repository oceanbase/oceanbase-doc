# ブラックリストメカニズム

ODPはブラックリストメカニズムを使用して、OBServerノードのピークシフトコンパクション、アップグレード、リーダー切り替え、ダウン、起動および停止などのプロセスにおけるOBServerノードへのアクセス制御を適応的に処理します。

## 背景情報

ODPには、ダウン状態のブラックリストとアクティブながら利用不可能なブラックリストの2種類があり、パラメータ設定によってこれらのブラックリストを管理できます。

ブラックリストを使用することで、主に以下のシナリオでのアクセス制御を実現できます：

* オフピーク時のコンパクション時に、コンパクション中のゾーンにトラフィックがない場合。

* クラスタのアップグレード時に、アップグレード中のOBServerノードまたはゾーンへのアクセスを許可しない場合。

* OBServerノードがダウンした後、そのOBServerノードへのアクセスを許可しない場合。

* パーティション移行後、移行前のOBServerノードへのアクセスを許可しない場合。

* アクセス対象のOBServerノードにテナントリソースが存在しない場合、リトライを行う場合。

* OBServerノードがアクティブながら利用不可能（メモリ上限超過、タイムアウト、OBServerノードの初期化および終了）の場合、リトライを行う場合。

## ダウン状態のブラックリスト

特定のOBServerノードがダウンした、または手動で`stop server`コマンドを実行してそのOBServerノードが外部へのサービス提供を一時停止した場合、そのOBServerノードをダウン状態のブラックリストに追加します。これにより、アプリケーションはそのノードにアクセスせず、再度ノードの状態が正常であることが検出されるまで、ブラックリストから除外されません。

OBServerノードの状態が以下のいずれかの場合、そのサーバーはダウン状態のブラックリストに追加されます：

* 所属するOBServerノードの`start_service_time`項目の値が0です。

* 所属するOBServerノードの`status`項目の値が`inactive`です。

## アクティブながら利用不可能なブラックリスト

アクティブながら利用不可能なブラックリストとダウン状態のブラックリストの違いは、OBServerノードの状態が一時的または不確定であるため、一定時間ごとにリトライが行われ、リトライでそのOBServerノードが正常に戻ったことが確認された場合、そのOBServerノードをブラックリストから除外します。

OBServerノードの状態が以下のいずれかの場合、そのOBServerノードはアクティブながら利用不可能なブラックリストに追加されます：

* 所属するゾーンがコンパクション/アップグレード中の場合。

* 所属するサーバーがコンパクション/アップグレード中の場合。

* OBServerノードがアクティブな状態で発生したエラーはすべてエラーパケットとして返されます。OBServerノードがシステムエラーを返した場合、例えば、リソース制限、接続数制限、システムメモリ上限超過、データパケット検証エラー、初期化中、終了中、OBServerノードのレスポンスタイムアウト、クライアント接続タイムアウト、またはODP待機タイムアウトなど、そのOBServerノードのアクティブながら利用不可能なカウントが1増加します。もしOBServerノードがN秒以内にM回のアクティブながら利用不可能な失敗カウントがある場合、そのOBServerノードをアクティブながら利用不可能なブラックリストに追加します。

* オフピーク時のコンパクション開始時、Root Serviceはまず内部テーブルの設定を更新してゾーンのコンパクション状態を更新し、次にコンパクションが必要なゾーン上のプライマリを他のゾーンに切り替えます。ODPは定期的にゾーン状態テーブルを更新してゾーンの状態を取得し、ゾーンの状態が更新されると、そのゾーン内のOBServerノードはすべてアクティブながら利用不可能に設定されます。オフピーク時のコンパクション処理中、コンパクション中のゾーンのOBServerノードはすべてアクティブながら利用不可能なブラックリストに含まれます。

## ブラックリストの優先順位

ダウン状態のブラックリスト \> アクティブながら利用不可能なブラックリスト（ゾーンのコンパクション/アップグレード \> OBServerノードのコンパクション/アップグレード）。

## ブラックリスト内のOBServerへの強制アクセス

選択可能なすべてのOBServerノードがブラックリストに含まれている場合、ブラックリスト内のOBServerノードに対して強制的にリトライが行われます。

## ブラックリストの構成パラメータ

1. クライアント上でrootユーザーとしてクラスタの`sys`テナントにログインします。

2. 以下のコマンドを実行してODPの構成パラメータを確認します。

   ```sql
   obclient> SHOW PROXYCONFIG;
   ```

3. `ALTER proxyconfig SET key=value` コマンドを実行してODPの指定された構成パラメータを更新します。構成パラメータの更新は即時に反映されます。

   ブラックリストに関連する構成パラメータの説明は、次の表のとおりです。

   |            **構成パラメータ**            |           **説明**           |
   |-------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|
   | enable_congestion             | ブロックリストメカニズムを有効にするかどうかを指定します。デフォルトは有効です。ブロックリストメカニズムの実行に問題が発生した場合、このオプションを一時的に無効にしてODPが正常に動作できるようにすることができます。      |
   | congestion_failure_threshold  | OBServerノードがN秒以内に何回エラーを起こすと、そのサーバーをブロックリストに追加するかを設定します。このパラメータ値が0未満の場合、ブロックリストに含まれるすべてのサーバーがブロックリストから解除されます。 |
   | congestion_fail_window        | エラー統計周期の時間（秒）を設定します。デフォルト値は120秒です。このエラー統計周期内にエラー回数が`congestion_failure_threshold`の値を超えた場合、そのサーバーをブロックリストに追加します。このパラメータ値は動的に調整することもできます。このパラメータを変更すると、現在のエラー統計カウントがリセットされ、新しいfail windowに従ってエラー回数の統計が最初から再開されます。 |
   | congestion_retry_interval     | ブロックリストまたはアベイラブルブロックリストに追加されたサーバーのリトライ周期を設定します。デフォルト値は20秒です。       |
   | min_keep_congestion_interval  | ブロックリストに追加されたサーバーが、いつブロックリストから解除されることを許可するかを設定します。            |
   | min_congested_connect_timeout | クライアント接続タイムアウト値を設定します。接続タイムアウトが発生した場合、サーバーをアベイラブルブロックリストに追加します。デフォルト値は100msです。           |

## ブラックリストの確認

1. クライアントから `root` ユーザーでクラスタの `sys` テナントにログインします。

2. 以下のコマンドを実行して、ブラックリスト情報を確認します。

   ステートメントは次のとおりです：

   ```sql
   SHOW PROXYCONGESTION [all] [clustername];
   ```

   関連パラメータの説明は以下のとおりです：

     * オプションを指定しない場合、すべてのクラスタのブラックリスト情報を照会できます。

     * `all` のみを指定した場合、すべてのクラスタのOBServerノード情報（ブラックリスト内および外のOBServerノード情報を含む）が表示されます。

     * `clustername` のみを指定した場合、指定されたクラスタのブラックリスト情報が表示されます。

     * `all` と `clustername` を同時に指定した場合、指定されたクラスタのOBServerノード情報が表示されます。
