# SQL実行計画

実行計画（Execution Plan）とは、データベースにおけるSQLクエリ文の実行プロセスを記述したものです。

ユーザーは `EXPLAIN` コマンドを使用して、オプティマイザーが指定されたSQLに対して生成した論理実行計画を確認できます。あるSQLのパフォーマンス問題を分析する場合、通常はまずそのSQLの実行計画を確認し、各実行ステップに問題がないか調査する必要があります。したがって、実行計画を理解することはSQL最適化の前提条件であり、実行計画を構成する演算子を把握することが `EXPLAIN` コマンドを理解する鍵となります。

## EXPLAINコマンドの形式

OceanBaseデータベースの実行計画コマンドには3つのモードがあります：`EXPLAIN BASIC`、`EXPLAIN`、および `EXPLAIN EXTENDED`。これら3つのモードは、実行計画に表示される詳細の粒度が異なります。

* `EXPLAIN BASIC` コマンドは、最も基本的な計画の表示に使用されます。

* `EXPLAIN EXTENDED` コマンドは、最も詳細な計画の表示に使用されます（通常、問題のトラブルシューティング時にこの表示モードを使用します）。

* `EXPLAIN` コマンドで表示される情報は、一般ユーザーが計画全体の実行方法を理解するのに役立ちます。

`EXPLAIN` コマンドの形式は以下のとおりです：​​

```sql
EXPLAIN [BASIC | EXTENDED | PARTITIONS | FORMAT = format_name] [PRETTY | PRETTY_COLOR] explainable_stmt
format_name:
  { TRADITIONAL | JSON }
explainable_stmt:
  { SELECT statement
 | DELETE statement
 | INSERT statement
 | REPLACE statement
 | UPDATE statement }
```
`EXPLAIN` コマンドは `SELECT`、`DELETE`、`INSERT`、`REPLACE`、および `UPDATE` ステートメントに適用され、オプティマイザーが提供するステートメントの実行計画に関する情報を表示します。これには、ステートメントの処理方法、テーブルの結合方法、結合の順序などの情報が含まれます。

一般的に、`EXPLAIN EXTENDED` コマンドを使用して、テーブルスキャンの範囲セグメントを表示できます。`EXPLAIN OUTLINE` コマンドを使用すると、アウトライン情報を表示できます。

`FORMAT` オプションを使用して出力形式を選択できます。`TRADITIONAL` はテーブル形式で出力を表示することを意味し、これがデフォルト設定です。`JSON` は `JSON` 形式で情報を表示することを意味します。

`EXPLAIN PARTITIONS` を使用して、パーティションテーブルに関わるクエリをチェックすることもできます。非パーティションテーブルのクエリをチェックする場合はエラーは発生しませんが、`PARTITIONS` 列の値は常に `NULL` になります。

複雑な実行計画については、`PRETTY` または `PRETTY_COLOR` オプションを使用して、計画ツリー内の親ノードと子ノードを線や色付きの線で結び、実行計画をより読みやすく表示できます。例：
```sql
obclient> CREATE TABLE p1table(c1 INT ,c2 INT) PARTITION BY HASH(c1) PARTITIONS 2;
Query OK, 0 rows affected

obclient> CREATE TABLE p2table(c1 INT ,c2 INT) PARTITION BY HASH(c1) PARTITIONS 4;
Query OK, 0 rows affected

obclient> EXPLAIN EXTENDED PRETTY_COLOR SELECT  * FROM p1table p1 JOIN p2table p2 ON p1.c1=p2.c2\G
```

## 実行計画の構造と演算子情報

OceanBaseデータベースの実行計画は以下のように表示されます：

```sql
|ID|OPERATOR              |NAME       |EST. ROWS|COST |
-------------------------------------------------------
|0 |LIMIT                 |           |100      |81141|
|1 | TOP-N SORT           |           |100      |81127|
|2 |  HASH GROUP BY       |           |2924     |68551|
|3 |   HASH JOIN          |           |2924     |65004|
|4 |    SUBPLAN SCAN      |VIEW1      |2953     |19070|
|5 |     HASH GROUP BY    |           |2953     |18662|
|6 |      NESTED-LOOP JOIN|           |2953     |15080|
|7 |       TABLE SCAN     |ITEM       |19       |11841|
|8 |       TABLE SCAN     |STORE_SALES|161      |73   |
|9 |    TABLE SCAN        |DT         |6088     |29401|
=======================================================
```

この例から、OceanBaseデータベースの計画表示はOracleデータベースと類似していることがわかります。OceanBaseデータベースの実行計画における各列の意味は以下の表のとおりです。

|  **列名**   |           **意味**           |
|-----------|----------------------------|
| ID        | 実行木を先祖順に走査して得られた番号（0から始まる）。 |
| OPERATOR  | 操作演算子の名前。                   |
| NAME      | 対応するテーブル操作のテーブル名（インデックス名）。             |
| EST. ROWS | この操作演算子の出力行数の推定値。              |
| COST      | この操作演算子の実行コスト（マイクロ秒）。            |

  <main id="notice" type='explain'>
    <h4>説明</h4>
    <p>テーブル操作において、<code>NAME</code> フィールドには、その操作で扱われるテーブルの名前（エイリアス）が表示されます。インデックスを使用してアクセスする場合は、名前の後の括弧内にそのインデックスの名前が表示されます。例えば、<code>t1(t1_c2)</code> はインデックス <code>t1_c2</code> を使用していることを示します。スキャンの順序が降順の場合は、後ろに <code>RESERVE</code> キーワードが追加されます。例：<code>t1(t1_c2,RESERVE)</code>。</p>
  </main>

OceanBaseデータベースの `EXPLAIN` コマンドの出力の最初の部分は、実行計画のツリー構造の表示です。ツリー内での各操作の階層は、演算子内でのインデントによって示されます。ツリーの階層関係はインデントで表現され、階層が深いものが優先的に実行されます。階層が同じ演算子は、指定された演算子の実行順序に従って実行されます。

OceanBaseデータベースの `EXPLAIN` コマンドの出力の2番目の部分は、各操作演算子の詳細情報です。これには出力式、フィルター条件、パーティション情報、および各演算子固有の情報（ソートキー、結合キー、プッシュダウン条件など）が含まれます。例：

```sql
Outputs & filters:
-------------------------------------
  0 - output([t1.c1], [t1.c2], [t2.c1], [t2.c2]), filter(nil), sort_keys([t1.c1, ASC], [t1.c2, ASC]), prefix_pos(1)
  1 - output([t1.c1], [t1.c2], [t2.c1], [t2.c2]), filter(nil),
      equal_conds([t1.c1 = t2.c2]), other_conds(nil)
  2 - output([t2.c1], [t2.c2]), filter(nil), sort_keys([t2.c2, ASC])
  3 - output([t2.c2], [t2.c1]), filter(nil),
      access([t2.c2], [t2.c1]), partitions(p0)
  4 - output([t1.c1], [t1.c2]), filter(nil),
      access([t1.c1], [t1.c2]), partitions(p0)
```
