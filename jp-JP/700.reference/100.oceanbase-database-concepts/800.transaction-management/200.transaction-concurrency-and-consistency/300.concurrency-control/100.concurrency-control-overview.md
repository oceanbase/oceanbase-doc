# 並行制御の概要

## 並行制御モデル

各トランザクションは複数の読み書き操作を含み、操作対象はデータベース内部の異なるデータです。最も単純な並行制御としては、直列（serial）実行があります。これは、あるプロセスが別のプロセスが一つの操作を完了し（トリガー操作への応答を受信するまで）、次の操作を開始しないことを指します。しかし、これは明らかに高い同時実行性のニーズには適合しません。そのため、研究者たちは直列化可能（serializable）という概念を提案しました。これは、トランザクション内の複数の操作を並列（非直列）に実行することで、直列実行と同じ結果を得ることができるというものです。

トランザクション内の読み書き操作を利用して、トランザクション間の依存関係を構築することができます（依存関係とは、トランザクションを直列実行順に直列化した場合のトランザクションの順序付けを示します。トランザクションBがトランザクションAに依存する場合、トランザクションAはトランザクションBより前に配置されるべきです）：

* 書き込み依存（Write Dependency）：トランザクションAがデータXを変更した後、トランザクションBが同一データXを再変更する場合、トランザクションBはトランザクションAに依存します。

* 書き込み読み取り依存（Read Dependency）：トランザクションAがデータXを読み取った後、そのデータXがトランザクションBによって変更されたものである場合、トランザクションAはトランザクションBに依存します。

* 読み取り依存（Anti Dependency）：トランザクションAがデータXを読み取った後、トランザクションBが同一データXを再変更する場合、トランザクションBはトランザクションAに依存します。

このように依存関係によって定義される直列化可能性は、一般的に競合直列化可能（conflict serializable）と呼ばれ、上記の競合メカニズムを通じて容易に分析できます。トランザクション間の競合関係が環状にならない限り、競合直列化可能性が保証されます。一般的な実装メカニズムとしては、2段階ロックと楽観的ロックの2種類があります。前者は排他的にロックを追加することで他のトランザクションの競合変更を制限し、デッドロック検出メカニズムによって環状になるトランザクションをロールバックすることで環状を防ぎます。後者はコミット時の検出段階で、環状になる可能性のあるすべてのトランザクションをロールバックすることで環状を防ぎます。

しかし実際には、直列化可能な分離レベルを実装している商用データベースは非常に少なく、上記の2つの実装メカニズムはいずれも大きなパフォーマンスコストを伴います。そのため、一般的には許容可能な環状条件を許可することで一部の例外を露呈させ、トランザクションのパフォーマンスと拡張性を向上させます。その中でも、スナップショット読み取りと既コミット読み取りは、比較的一般的な例外を許容する並行制御です。スナップショット読み取り分離レベルは、複数バージョンのデータの維持に依存し、読み取り時に固定された読み取りバージョン番号を使用して対応するバージョンのデータを読み取ります。そのため、同一トランザクション内の異なるデータ間で、読み書き競合によって環状が発生することがあります。例えば、トランザクションAがデータバージョン1のXを読み取り、変更してデータバージョン2のYを生成した後、トランザクションBがデータバージョン1のYを取得し、変更してデータバージョン2のXを生成する場合、トランザクションAとトランザクションBの間に環状が発生していることが明確にわかります。このような例外は、私たちがよく言う「書き込みスキュー（Write Skew）」です。これはスナップショット読み取りがユーザーに露呈する例外です。一方、既コミット読み取り分離レベルでは、非再現読み取りなどの例外が露呈し、これはトランザクション内部での2回の読み取り結果が異なることを意味します。分離レベルの抽象化をどのように定義するかが、ユーザーにパフォーマンスと意味的使いやすさのバランスを提供することが、トランザクション分離レベル（Isolation）設計の鍵の一つです。

## OceanBaseデータベースの並行制御モデル

OceanBaseデータベースは現在、スナップショット読み取りとコミット済み読み取りの2種類の分離レベルをサポートしており、分散セマンティクスにおいて分離レベルが外部整合性を保証します。

### 複数バージョンデータ＆トランザクションテーブル

読み書きの排他性をサポートするために、OceanBaseデータベースは設計段階から複数バージョンをストレージとして採用し、トランザクションがグローバルに対して2つのバージョン番号、すなわち読み取りバージョン番号とコミットバージョン番号を維持するようにしました。これらは図に示されている `ローカル最大読み取りタイムスタンプ` と `最大コミットタイムスタンプ` です。次に、メモリ内では各更新ごとに新しいバージョンが記録されます（これにより読み書きの排他性が実現されます）。

図に示されているように、メモリ内にはデータA、B、Cの3行があります。各バージョンは（ts）、値（val）、トランザクションID（txn）を通じて更新が維持され、複数の更新が同時に維持されることで複数バージョンが保たれます。また、メモリ内にはトランザクションテーブルが存在し、このテーブルには各トランザクションのID、状態、およびバージョンが記録されています。トランザクションの開始およびコミット時には、グローバルタイムスタンプキャッシュサービス（Global Timestamp Cache）からタイムスタンプを取得し、読み取りタイムスタンプおよびコミットタイムスタンプの参照部分として使用します。

![並行制御1](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.1/EN_US/700.reference/100.oceanbase-database-concepts/Concurrency-control-1.png)

図からわかるように、グローバルタイムスタンプ取得サービスは、最大で遭遇したトランザクションの読み取りタイムスタンプと、既にコミットされたトランザクションのコミットタイムスタンプをそれぞれ130と100として維持しています（後ほどこれら2つのタイムスタンプの役割について説明します）。メモリ内では、データAにはバージョン100でコミットされたデータaが含まれています。対応するトランザクションはトランザクション10です。同様に、データBには未決定バージョンのデータjと対応するトランザクション12が含まれ、データCには未決定バージョンのデータxと対応するトランザクション15が含まれています。トランザクションテーブルには対応するトランザクションとその状態が含まれており、例えばトランザクション15は現在バージョン130で2フェーズコミット状態に入っています。

### コミットリクエスト処理

OceanBaseデータベースの分散トランザクションは、簡単に言えばRUNNING、PREPARE、COMMITの3つの状態があります。トランザクションの状態は分散環境下では原子的に確認できないため、PREPAREは2フェーズコミットに追加された段階です。そのため、トランザクション内で `ローカルコミットバージョン番号`（local commit version、すなわちprepare version）を維持し、トランザクションの `グローバルコミットバージョン番号`（global commit version、すなわちcommit version）は、すべてのパーティションのローカルコミットバージョン番号の最大値によって決定されます。各パーティションに対する保証として、最終的なトランザクションの `グローバルコミットバージョン番号` は必ずローカルパーティションの `ローカルコミットバージョン番号` 以上であることが求められます。この保証は、後に読み書きリクエストの並行制御を実装する際の鍵となります。

トランザクションがコミットされると、対応する2フェーズコミットが実行され、参加者の各パーティションからローカルの `最大読み取りタイムスタンプ` をローカルコミットタイムスタンプとして取得します。この保証は、単一値の読み書き競合（anti dependency）を防ぐためのものであり、この保証に基づくと、コミットタイムスタンプは以前のすべての読み取りよりも大きいことが保証されます。そのため、直列実行においては、これら以前の読み取りの後に配置することができます。図に示されているように、トランザクション12はコミット段階に入り、状態をPREPAREに設定し、ローカルトランザクションバージョン番号をローカルの `最大読み取りタイムスタンプ` 120と、GTSが150の最大値である150を `ローカルトランザクションバージョン番号` として設定します。

![並行制御2](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.1/EN_US/700.reference/100.oceanbase-database-concepts/Concurrency-control-2.png)

2フェーズが終了する前に、私たちの保証は `グローバルコミットタイムスタンプ` が `ローカルコミットタイムスタンプ` 以上であることだけです。2フェーズコミットのコミットメッセージを受信すると、グローバルのコミットタイムスタンプがわかります。図に示されているように、状態をコミットに補完し、タイムスタンプを160に設定し、非同期で更新データに反映させます。これにより、その後はトランザクションテーブルを照会する必要がなくなります。次に、 `最大コミットトランザクションタイムスタンプ` を更新して、その後の読み取りリクエストの最適化を提供し、ロックキュー内で対応するトランザクションをアライズします。

![並行制御3](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.1/EN_US/700.reference/100.oceanbase-database-concepts/Concurrency-control-3.png)

### 書き込みリクエスト処理

データを書き込む際、書き込み競合（write dependency）を保証するために、変更には2段階ロックプロトコルが使用されます。書き込みリクエストがトリガーされた場合、その行のマルチバージョンで実行中のトランザクションがあることが検出されると、このリクエストはロックマネージャーに入れられて待機します。OceanBaseデータベースでは、ロックマネージャー内に待機キューが実装されており、ロックまたはタイムアウトによってこの書き込みリクエストが再開されます。図に示すように、データBを更新しようとしたとき、アクティブなトランザクション12がデータBを変更しているため、この書き込みリクエストはロックキューに入れられ、トランザクション12の再開を待機します。

![並行制御4](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.1/EN_US/700.reference/100.oceanbase-database-concepts/Concurrency-control-4.png)

スナップショット読み取り分離レベルは、読み書き競合（anti dependency）と書き込み読み取りリクエスト（read dependency）のループ、つまり更新損失（lost update）を防ぐために設計されています。書き込みまたは再開後にロックが正常に取得された場合でも、読み取りタイムスタンプをその行に維持されている`最大コミットトランザクションタイムスタンプ`と比較します。読み取りタイムスタンプが行上の最大コミットトランザクションタイムより小さい場合、そのトランザクションはロールバックされます。例えば、上記の図で書き込み操作の読み取りタイムスタンプが100であり、トランザクション12がタイムスタンプ160でコミットされた場合、書き込み操作に対応するトランザクションのロールバックがトリガーされ、対応するエラー（`TRANSACTION_SET_VIOLATION`）が発生します。

### 読み取りリクエスト処理

読み取り時には、読み取りバージョン番号を使用して対応するデータを読み取ります。実際の読み取り時には、読み取りバージョン番号を使用してローカルの`最大読み取りタイムスタンプ`を更新します。以前に与えられた保証により、分散環境下での読み取りリクエストを非常にスマートに処理できます。

次に、それぞれのケースを詳しく分析します。コミットまたはロールバックされたトランザクションを読み取る場合、`グローバルコミットタイムスタンプ`と状態を比較することで、対応するデータを読み取る必要があるかどうかを簡単に推測できます。以下の図に示すように、読み取りリクエストr1は読み取りバージョン番号として90を使用して読み取りを行い、スナップショット読み取りのポリシーに基づいて、バージョン番号80、データbのデータを読み取ります。

`RUNNING`状態のトランザクションを読み取る場合、`ローカル最大読み取りタイムスタンプ`が引き上げられるため、その後の`RUNNING`状態のトランザクションは必ずより大きな`ローカルタイムスタンプ`で2段階コミットに進みます。保証とスナップショット読み取りの概念に基づき、このデータを安全にスキップできます。以下の図に示すように、読み取りリクエストr2は読み取りバージョン番号として130を使用して読み取りを行い、まず`最大読み取りトランザクションタイムスタンプ`を引き上げて、その後のトランザクションが130より大きい`ローカルコミットバージョン/グローバルコミットバージョン`でコミットされるようにします。その後、2段階コミットに進んでいないトランザクション12をスキップして、バージョン番号100、データbのデータを読み取ります。

PREPARE状態のトランザクションを読み取る場合、与えられた保証により、`ローカルタイムスタンプ`が読み取りタイムスタンプより大きいトランザクションについては、前述の分析と同様に、読み取る必要がないことを保証できます。しかし、`ローカルタイムスタンプ`が読み取りタイムスタンプより小さい場合、このタイムスタンプの最終的な`グローバルコミットタイムスタンプ`と読み取りタイムスタンプとの関係を確認できないため、解決策として、その行のトランザクションをスマートに待機します（内部では`lock for read`と呼ばれます）。2段階コミットはOceanBaseデータベースの仮定では非常に迅速に完了するプロセスであるはずです。以下の図に示すように、読み取りリクエストr3は読み取りバージョン番号として140を使用して読み取りを行い、まず`最大読み取りトランザクションタイムスタンプ`を引き上げて、その後のトランザクションが140より大きい`ローカルコミットバージョン/グローバルコミットバージョン`でコミットされるようにします。その後、2段階コミット状態で`ローカルコミットタイムスタンプ`が130のトランザクションが最終的に`グローバルコミットタイムスタンプ`と読み取りタイムスタンプ140との関係を決定するのを待ちます。
