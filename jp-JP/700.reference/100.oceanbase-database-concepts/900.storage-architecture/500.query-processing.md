# クエリ処理

OceanBaseデータベースは現在、プル型のtable_scanイテレーションプロセスを使用しています。各行をSQL層にイテレーションして出力する際には、以下のいくつかの段階を経ています：

1. 各SSTableはquery rangeに基づいてスキャン対象となるマクロブロックと対応するマイクロブロックを特定し、各マイクロブロックに対してスキャンを開き、必要な行全体を出力します。

2. MemTable/Minor SSTable/Major SSTableの複数のイテレータは、それぞれの行をイテレーションします。

3. ベスト・オブ・ザ・ワールド木を使用して、複数のイテレータの現在のrowkeyが同一かどうかに基づいて、fuseに参加する必要がある行数を決定します。

4. fuse後の最終的な結果行は、必要に応じて投影され、最終的な結果行が取得されます。

5. 最終的な結果行を用いて、SQLのfilterコールバック関数を呼び出して検査を行い、条件を満たす場合は上位に返します。

## クエリの下押し

LSM-Treeアーキテクチャのストレージエンジンでは、一般的に以下の問題に直面します：

* 過度かつ頻繁なイテレーションと主キー比較。特にOLAP業務において、多くのシナリオでテーブルはほとんど更新されず、データはほぼすべてのベースラインMajor SSTableに格納されています。MemTableとMinor SSTableには、増分または更新データがわずかしか存在しません。理想的な状況では、ほとんどのパスが迅速に直接Major SSTableからスキャンできるべきであり、主キーが交差する可能性がある場合のみ、Major SSTable、MemTable、Minor SSTableのいずれかをfuse対象とします。しかし、現実的な実装では、各行ごとにストレージ内のイテレータと比較し、主キーが一致するかどうかを判断する必要があります。これは、効率が著しく低下する一方で、今後ベクトル化拡張の可能性もほぼ失われることになります。

* フィルタ演算子の計算時間が遅すぎる。上記の点から、最終的な結果の正確性を保証するため、すべての行がfuseされた後にのみデータが最新の状態であることが保証されるため、現在のフィルタ演算子のチェックは、各行のイテレーションの最後に行われています。

* 不要な投影が多い。マイクロブロックからスキャンして上位に持ち上げられた行は、最終的にユーザーが必要とするすべての列がすでに投影されていることを保証する必要があります。複数のイテレーションとfuseを経て、filter計算で条件を満たした場合、直接返すことができます。しかし、条件を満たさない場合、filterに必要な列以外の他の投影列は無駄になります。

以上より、OceanBaseデータベースは、フィルタ演算子をストレージ層に下押しすることで、上記の問題を解決しています。以下に図を示します：

![query-downward-pressure.png](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.1/700.reference/100.oceanbase-database-concepts/900.storage-architecture/query-downward-pressure.png)

1. 演算子の下押し：OceanBaseデータベースは、データ間で交差がない状態を迅速に区別できるようになります。つまり、major SSTableと増分データの間に交差がないデータ範囲を認識できるため、この範囲のデータはmajor SSTableのみをアクセスすれば最新の最終状態を取得できます。そのため、このデータに対してフィルタ演算子を直接下押しすることができます。

2. 演算子によるフィルタリング：各下押しされたfilter式は、ストレージ層が理解できる形式に解析・分割され、対応する列情報およびそのフィルタ条件式が含まれます。また、フィルタ条件の複雑さに基づいて、ブラックボックスとホワイトボックスの2種類のモードにさらに細分化できます。

   1. SQL層に基づくフィルタリング（ブラックボックス）：例えば、a * 2 > 3 のような式計算型のフィルタ条件は、ストレージ層では処理できません。依然として、SQL層の関数にコールバックして処理する必要があります。この場合、演算子をマイクロブロックデコーダー層に下押しした後は、さらに下押しすることはできず、filterノードの情報に基づいて対応する列を投影し、その後SQL層のコールバック関数を呼び出して結果を計算する必要があります。

   2. ストレージに基づくフィルタリング（ホワイトボックス）：例えば、a > 1 または b = 'abc' のような単純で一般的なフィルタ条件は、ストレージ層が意味を理解し、処理可能なfilterノードです。SQL層は、対応する演算子およびその定数式をさらに解析し、ストレージ層はこのfilterノードを各列に対応するデコードルールにさらに下押しすることができます。これにより、投影のオーバーヘッドをさらに削減し、同時にencoding情報を活用して高速化が可能になります。
