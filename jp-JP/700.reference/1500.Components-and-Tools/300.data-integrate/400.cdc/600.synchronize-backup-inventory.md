# obcdcはスタンバイデータベースの同期をサポートしています

## 背景

obcdcが外部にサービスを提供して以来、同期対象は主データベースのみであり、お客様環境ではobcdcがスタンバイデータベースのデータを消費するニーズが存在します。具体的には以下の通りです：

* ローカルデータベースのデータを消費するニーズがあります：obcdcのデータを消費するアプリケーションとデータベースの主データベースが異なる場合、業務上はローカルのスタンバイデータベースから増分トランザクションデータを消費することを優先します。

* プライマリ/スタンバイ切り替え後のデータ消費能力：obcdcは主データベースのみを同期でき、1つのobcdcは1つのクラスタのデータしか同期できません。もし主データベースとスタンバイデータベースが同一クラスタ内にない場合、またはプライマリ/スタンバイ切り替えが発生した場合、データリンクが途絶えてしまいます。

* obcdcの実行は主データベースへの影響が小さいものの、一部のお客様は依然としてobcdcを使用してスタンバイデータベースを同期し、主データベースへの影響を軽減したいと考えています。

上記の問題を解決するため、obcdcはスタンバイデータベースのデータを直接消費する機能を提供します。

## 機能の概要

オンラインモードでは、同期対象のテナントの現在のテナント名を同期アローリストに追加するために、`tb_white_list` を設定する必要があります。オフラインモード（`refresh_mode=data_dict` および archive_dest などのアーカイブメタ情報が設定されている場合）では、この制限はありません。

起動ポイントの制限：

* 起動時、obcdcソーステナントの状態は `NORMAL` である必要があります。

* 起動ポイントに対応する時刻において、obcdcソーステナントの状態は `NORMAL` である必要があります。

* テナントの `RESTORE_SCN`（ユーザー指定の復旧ポイント。システムテナントから [CDB_OB_RESTORE_HISTORY](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/10100.o-cdb_ob_restore_history-of-sys-tenant.md)ビューで照会可能）以下の起動ポイントはサポートされていません。

* `RECOVERY_UNTIL_SCN`（現在のテナントの最大復旧ポイント。 [DBA_OB_TENANTS](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/22200.o-dba_ob_tenants-of-sys-tenant.md)ビューで照会可能）より大きい起動ポイントはサポートされていません。

* 起動ポイントがテナントの `REPLAYABLE_SCN`（現在のテナントで再現可能なスナップショットバージョン。 [DBA_OB_TENANTS](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/22200.o-dba_ob_tenants-of-sys-tenant.md)ビューで照会可能）より大きい場合、テナントの `REPLAYABLE_SCN` が起動ポイントを上回るまで再試行し、その後に起動に成功します。再試行タイムアウト時にはプロセスが終了します。

* 起動ポイントが `READABLE_SCN`（現在のテナントで読み取り可能なスナップショットバージョン。 [DBA_OB_TENANTS](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/22200.o-dba_ob_tenants-of-sys-tenant.md)ビューで照会可能）より大きい場合、テナントの `READABLE_SCN` が起動ポイントを上回るまで再試行し、その後に起動に成功します。再試行タイムアウト時にはプロセスが終了します。

* ディクショナリモードでは、最新のベースラインの生成時間（`SNAPSHOT_SCN`。システムテナントから [CDB_OB_DATA_DICTIONARY_IN_LOG](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/7800.o-cdb_ob_data_dictionary_in_log-of-sys-tenant.md)ビュー、または通常のテナントから [DBA_OB_DATA_DICTIONARY_IN_LOG](../../../700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/17400.o-dba_ob_data_dictionary_in_log-of-sys-tenant.md)ビューで照会可能）を取得します。取得した `SNAPSHOT_SCN` も上記のすべての起動ポイントの制約を満たしていなければならず、そうでない場合もプロセスは終了します。

* 起動ポイントがトランザクションの途中に位置する場合、obcdcは起動ポイント以前のそのトランザクションのすべてのclogログをリプルする必要があり、そのトランザクションの最も古いclogログも上記のすべての制約を満たしている必要があります。

## よくある質問

ここでは、obcdc同期スタンバイデータベース機能に関連するよくある質問を挙げます。obcdcの汎用的な問題については、ここでは説明しません。

### obcdc起動失敗、プロセスが終了

**主要な現象**：

* obcdcプロセスが終了し、obcdcログが回収されていない場合、obcdc起動成功の重要なログ`init obcdc succ`が見つかりません。

* 以下のいずれかの重要なログが存在します：

  * 起動時点でclogログ時点がサービスされていない重要なログ`[ADD_TENANT][FAIL][clog_NOT_SERVE]`を確認します。

  * 起動時点が読み取り不可能な重要なログ`[ADD_TENANT][FAIL][NOT_READABLE]`を確認します。

  * データディクショナリの`SNAPSHOT_SCN`がサービス範囲外である重要なログ`[ADD_TENANT][DATA_DICT][REFRESH_BASELINE][FAIL][clog_NOT_SERVE][LOG_AT Dict_SNAPSHOT]`。

**問題の原因**：obcdcの起動時点が上記[機能の概要](#機能の概要)の制約を満たしていません。

**解決策**：起動時点を調整して制約に適合させるか、またはプライマリデータベースからのデータ同期に切り替えます。

### obcdc起動成功、しかし運用開始後しばらくでプロセスが終了

**主要な現象**：

* obcdcの初期化に成功し、具体的には：obcdcログが回収されていない場合、起動成功の重要なログ`init obcdc succ`が表示されるか、定期的に`TLOG.COMMITTER`モジュールの`HEARTBEAT`キーワードログが更新されているのが確認できます。

* `[MISS_LOG][HANDLE_DONE]`ログが存在し、その後に続く`ret`が`OB_SUCCESS`ではありません。

**問題の原因**：起動時点が長時間トランザクションの途中であり、obcdcはそのトランザクションを完全にフェッチする必要があります。このトランザクションの前方のログ時点が`RESTORE_SCN`より小さい場合、obcdcはそのログを取得できず、一定時間再試行した後にプロセスが終了します。

**解決策**：起動時点をリセット（後退）するか、またはプライマリデータベースからのデータ同期に切り替えます。
