# クエリ戦略に関連するヒント

クエリ戦略に関連するヒントには、USE_HASH_AGGREGATIONヒント、NO_USE_HASH_AGGREGATIONヒント、USE_LATE_MATERIALIZATIONヒント、NO_USE_LATE_MATERIALIZATIONヒント、USE_NL_MATERIALIZATIONヒント、NO_USE_NL_MATERIALIZATIONヒント、PUSH_SUBQ、NO PUSH_SUBQが含まれます。

## USE_HASH_AGGREGATION ヒント

`USE_HASH_AGGREGATION` ヒントは、オプティマイザーに対し、計画を生成する際にHASH集約アルゴリズムを強制的に使用してSQLステートメントを実行するよう指示します。

`USE_HASH_AGGREGATION` ヒントの構文は次のとおりです：

```sql
/*+ USE_HASH_AGGREGATION*/
```

`USE_HASH_AGGREGATION` ヒントの例は次のとおりです：

```sql
SELECT /*+ USE_HASH_AGGREGATION */ e.department_id, sum(e.salary)
FROM employees e
WHERE e.department_id = 1001;
GROUP BY e.department_id;
```

## NO_USE_HASH_AGGREGATION ヒント

`NO_USE_HASH_AGGREGATION` ヒントは、オプティマイザーに対し、SQLステートメントを実行する際にHASH集約アルゴリズムを使用しないよう指示します。

`NO_USE_HASH_AGGREGATION` ヒントの構文は次のとおりです：

```sql
/*+ NO_USE_HASH_AGGREGATION*/
```

`NO_USE_HASH_AGGREGATION` ヒントの例は次のとおりです：

```sql
SELECT /*+ NO_USE_HASH_AGGREGATION */ e.department_id, sum(e.salary)
FROM employees e
WHERE e.department_id = 1001;
GROUP BY e.department_id;
```

## USE_LATE_MATERIALIZATION ヒント

`USE_LATE_MATERIALIZATION` ヒントは、オプティマイザーに対し、遅延マテリアライゼーションビューを有効にするよう指示します。

`USE_LATE_MATERIALIZATION` ヒントの構文は次のとおりです：

```sql
/*+ USE_LATE_MATERIALIZATION*/
```

`USE_LATE_MATERIALIZATION` ヒントの例は次のとおりです：

```sql
SELECT /*+ USE_LATE_MATERIALIZATION*/ e.department_id, sum(e.salary)
FROM employees e
WHERE e.department_id = 1001;
GROUP BY e.department_id;
```

## NO_USE_LATE_MATERIALIZATION ヒント

`NO_USE_LATE_MATERIALIZATION` ヒントは、オプティマイザーに対し、遅延マテリアライゼーションビューを無効にするよう指示します。

`NO_USE_LATE_MATERIALIZATION` ヒントの構文は次のとおりです：

```sql
/*+ NO_USE_LATE_MATERIALIZATION*/
```

`NO_USE_LATE_MATERIALIZATION` ヒントの例は次のとおりです：

```sql
SELECT /*+ NO_USE_LATE_MATERIALIZATION*/ e.department_id, sum(e.salary)
FROM employees e
WHERE e.department_id = 1001;
GROUP BY e.department_id;
```

## USE_NL_MATERIALIZATION ヒント

`USE_NL_MATERIALIZATION` ヒントは、オプティマイザーに対し、テーブルを内部テーブル（サブツリー）として指定した場合に、データをキャッシュするためのマテリアライゼーション演算子を生成するよう強制的に指示します。

`USE_NL_MATERIALIZATION` ヒントの構文は次のとおりです：

```sql
/*+ USE_NL_MATERIALIZATION ( [ @queryblock ] tablespec [ tablespec ]... ) */
```

`USE_NL_MATERIALIZATION` ヒントの例は次のとおりです：

```sql
SELECT /*+ USE_NL_MATERIALIZATION(departments) */ *
FROM employees, departments
WHERE employees.department_id = departments.department_id;
```

## NO_USE_NL_MATERIALIZATION ヒント

`NO_USE_NL_MATERIALIZATION` ヒントは、指定されたテーブルを内部テーブル（サブツリー）として指定した場合、オプティマイザーにデータをキャッシュするためのマテリアライズド演算子を生成しないよう強制的に指示します。

`NO_USE_NL_MATERIALIZATION` ヒントの構文は次のとおりです：

```sql
/*+ NO_USE_NL_MATERIALIZATION ( [ @queryblock ] tablespec [ tablespec ]... ) */
```

`NO_USE_NL_MATERIALIZATION` ヒントの例は次のとおりです：

```sql
SELECT /*+ NO_USE_NL_MATERIALIZATION(departments) */ *
FROM employees, departments
WHERE employees.department_id = departments.department_id;
```

## PUSH_SUBQ ヒント

<main id="notice" type='explain'>
  <h4>説明</h4>
  <p><ul><li>OceanBaseデータベースV4.3.5では、V4.3.5 BP2バージョンから <code>PUSH_SUBQ</code> ヒントがサポートされています。</li><li>OceanBaseデータベースV4.2.5では、V4.2.5 BP4バージョンから <code>PUSH_SUBQ</code> ヒントがサポートされています。</li></ul></p>
</main>

`PUSH_SUBQ` ヒントは、オプティマイザーに対し、結合に書き換えられないサブクエリを早期に実行するよう指示します。通常、これらのサブクエリは結合に書き換えられない場合、実行計画のすべてのテーブル結合計算の後に配置されます。サブクエリの計算コストが低く、大量のデータをフィルタリングできる場合、早期実行により計画のパフォーマンスが向上する可能性があります。ただし、サブクエリが結合（`/+unnest/`）に書き換えられた場合、このヒントは無効になります。適用シナリオは以下のとおりです：

* サブクエリの実行コストは小さいものの、大量のデータを迅速にフィルタリングできます。
* サブクエリの結果を早期に利用して、データ範囲を絞り込む必要があります。

**構文は次のとおりです：**

```sql
/*+ PUSH_SUBQ[(@qb_name)] */
```

パラメータの説明：

* `@qb_name`：オプションのパラメータで、サブクエリのエイリアスを指定します（詳細については、上記の**QB_NAMEパラメータ**を参照）。ヒントの対象を明確に示すために使用されます。省略した場合、デフォルトでヒントが含まれるサブクエリに対して有効になります。

**例：**

クエリ内で `PUSH_SUBQ` ヒントを使用して、オプティマイザーにサブクエリを早期に実行し、`tbl1` テーブルのデータを事前にフィルタリングするよう指示します。

```sql
SELECT /*+ PUSH_SUBQ(@"SEL$2") */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```

## NO PUSH SUBQ ヒント

<main id="notice" type='explain'>
  <h4>説明</h4>
  <p><ul><li>OceanBaseデータベースV4.3.5では、V4.3.5 BP2バージョンから <code>NO_push_SUBQ</code> ヒントがサポートされています。</li><li>OceanBaseデータベースV4.2.5では、V4.2.5 BP4バージョンから <code>NOPushSubQ</code> ヒントがサポートされています。</li></ul></p>
</main>

`NO PUSH SUBQ` ヒントは `PUSH_SUBQ` の逆の操作であり、オプティマイザーが結合に書き換えられなかったサブクエリを最後に実行するようにします。サブクエリのコストが高い場合や、行数を大幅に削減できない場合に適しています。適用シナリオは以下のとおりです：

* サブクエリの実行オーバーヘッドが大きい、またはその結果がデータ量に与える影響が小さい場合。
* サブクエリの実行を他のフィルタリング条件が有効になってから遅延させ、入力データ量を削減する必要がある場合。

**構文は以下のとおりです：**

```sql
/*+ NO_PUSH_SUBQ[(@qb_name)] */
```

パラメータの説明：

* `@qb_name`：オプションのパラメータで、サブクエリのエイリアスを指定します。

**例：**

クエリ内で `NO PUSH SUBQ` ヒントを使用して、オプティマイザーにサブクエリの実行を最後まで遅延させるよう指示します。

```sql
SELECT /*+ NO_PUSH_SUBQ */ *
FROM tbl1, tbl2
WHERE tbl1.col1 = (SELECT MAX(tbl3.col1)
                   FROM tbl3
                   WHERE tbl3.col2 = tbl2.col2);
```
