# その他のHint

OceanBaseデータベースは、CURSOR_SHARING_EXACT Hint、MONITOR Hint、PX_JOIN_FILTER Hint、NO_PX_JOIN_FILTER Hint、QB_NAME Hint、READ_CONSISTENCY Hint、QUERY_TIMEOUT Hint、LOG_LEVEL Hint、USE_PLAN_CACHE Hint、TRANS_PARAM Hint、TRACING Hint、STAT Hint、TOPK Hint、およびTRACE_LOG Hintもサポートしています。

## CURSOR_SHARING_EXACT ヒント

OceanBaseデータベースは、SQLステートメント内のリテラルをバインド変数に置き換える機能をサポートしており、この機能は`CURSOR_SHARING`変数によって制御されます。つまり、`cursor_sharing='exact'`の場合、パラメータ化は不要です。詳細については、[cursor_sharing](../../../../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/2000.cursor_sharing-global.md)を参照してください。

ユーザーは`CURSOR_SHARING_EXACT`ヒントを指定して、オプティマイザーにこの動作を無効にするよう指示できます。このヒントを指定すると、OceanBaseデータベースはSQLステートメントを実行する際にリテラルをバインド変数に置き換えることなく、パラメータ書き換えを実現します。

`CURSOR_SHARING_EXACT`ヒントの構文は次のとおりです：

```sql
/*+ CURSOR_SHARING_EXACT */
```

`CURSOR_SHARING_EXACT`ヒントの例は次のとおりです：

```sql
obclient> CREATE TABLE t(c1 INT PRIMARY KEY,c2 VARCHAR(20));
Query OK, 0 rows affected

obclient> INSERT INTO t VALUES(5,'oceanbase');
Query OK, 1 row affected

obclient> SELECT /*+ CURSOR_SHARING_EXACT*/ * FROM t WHERE c1=5 AND c2 ='oceanbase';
+----------+----------+
|    C1    |   C2     |
+----------+----------+
|    5     | oceanbase|
+---------------------+
1 row in set

obclient> SELECT query_sql, statement FROM gv$ob_plan_cache_plan_stat; GV$OB_PLAN_CACHE_PLAN_STAT
+---------------------------------------------------------------------------+---------------------------------------------------------------+
|  query_sql                                                                |   statement                                                   |
+---------------------------------------------------------------------------+---------------------------------------------------------------+
| SELECT /*+ CURSOR_SHARING_EXACT*/ * FROM t WHERE c1=5 AND c2 ='oceanbase' |  SELECT /*+ CURSOR_SHARING_EXACT*/ * FROM t WHERE c1=5 AND c2 ='oceanbase' |
+-------------------------------------------------------------------------------------------------------------------------------------------+
1 row in set
```

## MAX_CONCURRENT ヒント

`MAX_CONCURRENT` ヒントは、SQLステートメントの最大同時実行スレッド数を指定するために使用されます。例えば、`MAX_CONCURRENT(1)` に設定することで、SQLステートメントが単一スレッドモードで実行されるように指定できます。これは、いかなる時点でも、タスクを処理しているのは1つのスレッドだけであることを意味します。

`MAX_CONCURRENT` ヒントの構文は次のとおりです：

```sql
/*+ MAX_CONCURRENT() */
```

注意：`MAX_CONCURRENT()` の値は負の数に設定できますが、SQLステートメントの並列制御には影響しません。`MAX_CONCURRENT()` の値は、0より大きい正の整数に設定することを推奨します。

## QB_NAME ヒント

`QB_NAME` ヒントを使用してクエリブロックの名前を定義します。この名前は外部クエリのヒントで使用することも、インラインビューのヒントで使用することもでき、その結果、命名されたクエリブロック内でのテーブルへのクエリに影響を与えます。

`QB_NAME` ヒントの構文は次のとおりです：

```sql
/*+ QB_NAME ( queryblock ) */
```

2つ以上のクエリブロックが同じ名前を持つ場合、または同一のクエリブロックが2回ヒントで異なる名前を指定された場合、オプティマイザーはそのクエリブロックを参照するすべての名前とヒントを無視します。`QB_NAME` ヒントで名前付けされていないクエリブロックには、システムが生成した一意の名前が付けられます。これらの名前は計画表に表示されることもありますし、クエリブロック内の他のヒントで使用されることもあります。

`QB_NAME` ヒントの例は次のとおりです：

```sql
SELECT /*+ QB_NAME(qb) FULL(@qb e) */ employee_id, last_name
FROM employees e
WHERE last_name = 'Smith';
```

## READ_CONSISTENCY ヒント

`READ_CONSISTENCY` ヒントは、サーバーに対し、特定のSQL文が読み取るテーブルモードを弱い整合性（パラメータ `WEAK` を指定）

または強い整合性（パラメータ `STRONG` を指定）として指定するよう指示します。

`READ_CONSISTENCY` ヒントの構文は次のとおりです：

```sql
/*+ READ_CONSISTENCY(WEAK[STRONG]) */
```

`READ_CONSISTENCY` ヒントの例は次のとおりです：

```sql
SELECT /*+ READ_CONSISTENCY(WEAK) */ *
FROM employees
WHERE employees.department_id = 1001;
```

リピータブルリード（Repeatable Read）およびシリアライズ可能（Serializable）の分離レベルでは、弱い整合性の読み取りリクエストの実行がサポートされています。例は以下のとおりです。

  ```sql
  obclient> SET transaction read only;
  Query OK, 0 rows affected (0.001 sec)
  obclient> SELECT /*+ read_consistency(weak)*/ * FROM t WHERE a=2;
  +------+------+
  | ID   | A    |
  +------+------+
  | NULL |    2 |
  +------+------+
  1 row in set (0.001 sec)
  ```

## QUERY_TIMEOUT ヒント

`QUERY_TIMEOUT` ヒントは、サーバーに特定のSQL文の実行時のタイムアウト時間をマイクロ秒単位で指定します。

`QUERY_TIMEOUT` ヒントの構文は次のとおりです：

```sql
/*+ QUERY_TIMEOUT (intnum) */
```

例えば、このクエリが1秒以内にステートメントを実行しない場合、タイムアウトエラーが返されます。

```sql
SELECT /*+ QUERY_TIMEOUT(1000000) */ *
FROM employees e
WHERE e.department_id = 1001;
```

/*+ LOG_LEVEL ([']log_level[']) */

## USE_PLAN_CACHE ヒント

`USE_PLAN_CACHE` ヒントは、サーバーが特定のSQL文を実行する際に計画キャッシュメカニズムで実行するかどうかを指示します。パラメータ `NONE` は計画キャッシュメカニズムを実行しないことを意味し、パラメータ `DEFAULT` はサーバー自身の設定に従って計画キャッシュメカニズムを実行するかどうかを決定することを意味します。

`USE_PLAN_CACHE` ヒントの構文は次のとおりです：

```sql
/*+ USE_PLAN_CACHE (NONE[DEFAULT]) */
```

例えば、以下のステートメントでは計画キャッシュメカニズムが実行されません：

```sql
SELECT /*+ USE_PLAN_CACHE(NONE) */ *
FROM employees e
WHERE e.department_id = 1001;
```

## TRANS_PARAM ヒント

`TRANS_PARAM` ヒントは、サーバーがトランザクションを実行する際にパラメータ `param` で指定されたパラメータに従って実行するかどうかを指示します。現在サポートされているパラメータは、トランザクションレベルの早期ロック解放 `FORCE_EARLY_LOCK_FREE` のみです。`FORCE_EARLY_LOCK_FREE` の値が **TRUE** の場合はサポートされていることを示し、**FALSE** の場合はサポートされていないことを示します。ここでのパラメータ名とパラメータ値は、シングルクォート（' '）で囲む必要があります。ただし、パラメータ値が数値型の場合は、クォートを省略できます。

`TRANS_PARAM` ヒントの構文は次のとおりです：

```sql
/*+ TRANS_PARAM ['param' , 'param_value'] */
```

`TRANS_PARAM` ヒントの例は次のとおりです：

```sql
SELECT /*+ TRANS_PARAM('FORCE_EARLY_LOCK_FREE' 'TRUE') */ *
FROM employees e
WHERE e.department_id = 1001;
```

## TOPK ヒント

`TOPK` ヒントは、サーバーに曖昧クエリの精度と最小行数を設定するよう指示します。パラメータ `PRECSION` の値は整数で、範囲は \[0,100\] です。これは曖昧クエリ実行時の行数の割合を表します。パラメータ `MINIMUM_ROWS` は、返す最小行数を指定するために使用されます。

`TOPK` ヒントの構文は次のとおりです：

/*+ TOPK(PRECISION MINIMUM_ROWS) */

`TOPK` ヒントの例は次のとおりです：

```sql
SELECT /*+ TOPK(1,10) */ *
FROM employees e
WHERE e.department_id = 1001;
```
