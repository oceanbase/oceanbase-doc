# パラレルインポートとデータ圧縮の体験

本記事では、パラレルインポートとデータ圧縮に関する使用方法と説明を紹介します。

## パラレルインポート

Operational OLAPにおいて、分析クエリに加えて非常に重要な要素があります。それは大量データのパラレルインポート、すなわちデータのバッチ処理能力です。OceanBaseデータベースのパラレル実行フレームワークは、DMLステートメントもパラレル処理（Parallel DML）で実行可能であり、マルチノード構成のデータベースでは複数マシンによる同時書き込みを実現し、大規模トランザクションの一貫性を保証します。さらに非同期ダンプメカニズムと組み合わせることで、メモリ不足時におけるLSM-Treeストレージエンジンによる大規模トランザクションへの対応を大幅に最適化することができます。

この例を通してPDMLを体験してみましょう。引き続きTPC-Hの`lineitem`テーブルを基に、同じテーブル構造を持つ空のテーブル`lineitem2`を作成します。次に`INSERT INTO ...SELECT`方式を用いて、1つのSQL文で`lineitem`の全600万行のデータを新しいテーブル`lineitem2`に挿入します。以下では、PDMLを無効にした場合と有効にした場合でそれぞれ実行し、その効果と違いを観察します。

まず、`lineitem`のテーブル構造をコピーして`lineitem2`を作成します。注意点として、OceanBaseデータベースではパーティションテーブルを使用してデータ拡張を行います。この例では16個のパーティションを使用しているため、対応する`lineitem2`も完全に同一である必要があります：

### デフォルトモードで実行、PDMLを有効にしない

`lineitem2` を作成した後、まずデフォルト設定でパラレル処理を有効にせずに挿入します。これは600万行の大規模トランザクションであるため、OceanBaseデータベースのデフォルトのトランザクションタイムアウト値をより大きな値（単位：μs）に調整する必要があります。

```shell
# SET ob_query_timeout = 1000000000;
# SET ob_trx_timeout = 1000000000;
```

データを挿入し、実行結果は以下のとおりです：

```shell
obclient [test]> INSERT INTO lineitem2 SELECT * FROM lineitem;
Query OK, 6001215 rows affected (1 min 47.312 sec)
Records: 6001215  Duplicates: 0  Warnings: 0
```

パラレル処理を有効にしない場合、単一トランザクションで600万行のデータを挿入するのに、OceanBaseでは107秒かかりました。

### PDML実行を有効にする

次に、Hintを追加してPDMLの実行オプションを有効にします。再度挿入する前に、前回挿入したデータをクリアすることに注意してください。

```shell
obclient [test]> TRUNCATE TABLE lineitem2;
obclient [test]> INSERT /*+ parallel(16) enable_parallel_dml */ INTO lineitem2 SELECT * FROM lineitem;
```

今回の実行時間を見てみましょう：

```shell
obclient> TRUNCATE TABLE lineitem2;
Query OK, 0 rows affected (0.108 sec)

obclient> INSERT /*+ parallel(16) enable_parallel_dml */ INTO lineitem2 SELECT * FROM lineitem;
Query OK, 6001215 rows affected (22.117 sec)
Records: 6001215  Duplicates: 0  Warnings: 0
```

PDMLを有効にすると、同じテーブルに600万行のデータを挿入するのに、OceanBaseデータベースでの所要時間は約22秒に短縮されました。PDML機能によるパフォーマンス向上は約5倍です。この機能は、ユーザーが一括データ処理を必要とするシナリオで役立ちます。

## データ圧縮

OceanBaseデータベースは、LSM-Tree構造に基づいて独自のストレージエンジンを開発しています。データは大まかにベースラインデータ（SSTable）と増分データ（MemTable）の2つに分類され、ベースラインデータはディスクに保存され、増分変更はメモリ内で行われます。これにより、一方ではデータがディスク上でよりコンパクトな形式で格納できるようになります。さらに、ディスク上のベースラインデータは頻繁に更新されないため、OceanBaseデータベースは汎用的な圧縮アルゴリズムを用いてベースラインデータを再度圧縮し、OceanBaseデータベースにおけるデータストレージでは非常に高い圧縮率を得ることができます。同時に、このデータ圧縮によってクエリや書き込み性能の低下は生じません。以下では、OceanBaseデータベースに大量の外部データをインポートし、データ圧縮率を観察する方法について説明します。

### データの準備

まず、データ準備ツール[CreateData.jar](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.3.0/200.quickstart/CreateData.jar)を使用して、5000万行のシミュレーションデータを`/home/soft`ディレクトリに生成します。データ生成には約10～20分かかります。他のツールを使用してテストデータを生成することもできます。


### データのインポート

OceanBaseデータベースに組み込まれているLoad Dataコマンドを使用してデータをインポートできます。Load Dataは並列インポートもサポートしています。インポート開始前に以下の設定を行います。Load Dataコマンドは、データファイルがOBServerノードのローカルに存在する場合にのみサポートされます。リモートからデータをインポートしたい場合は、OceanBaseデータベースのobloaderツールを参照してください。

```shell
obclient [test]> SET GLOBAL secure_file_priv = "/";
obclient [test]> GRANT FILE ON *.* to username;
```

    <p>セキュリティ上の理由により、<code>secure_file_priv</code> を変更するSQLステートメントは、ローカル接続のクライアントからのみ実行できます。詳細については、<a href="../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/11500.secure_file_priv-global.md">secure_file_priv</a>を参照してください。</p>

設定完了後、セッションを再接続することで設定が有効になります。次に、セッションのトランザクションタイムアウト時間を再設定し、実行中にタイムアウトで終了しないようにします。

```shell
obclient [test]> SET ob_query_timeout=1000000000;
obclient [test]> SET ob_trx_timeout=1000000000;
```

その後、インポートステートメントを実行します：

```shell
obclient [test]> LOAD DATA /*+ parallel(16) */ INFILE '/home/soft/t_f1.csv' INTO table t_f1 fields TERMINATED BY '\|' LINES TERMINATED BY '\n';
```

並列インポートを有効にすると、10GBのデータの処理に約4分かかります。本記事では、テナントのCPU並列度を16に設定していますが、ご自身の環境に応じて適切な並列度を設定できます。並列度が高いほど、インポート速度は速くなります。
