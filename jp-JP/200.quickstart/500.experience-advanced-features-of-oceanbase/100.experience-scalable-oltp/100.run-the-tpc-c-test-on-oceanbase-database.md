# OceanBase データベースにおける TPC-C テストの実行

TPC-C は、TPC の管理組織 (Transaction Processing Performance Council) が発表した一連のパフォーマンステスト基準の 1 つであり、発表以来、データベース業界のパフォーマンステストにおいて重要なベンチマークとなっています。世界中の主要データベースベンダーは、TPC 評議会にテスト結果を提出しており、TPC-C テストのランキングで上位を目指すことを目指しています。OceanBase データベースは、2019 年と 2020 年の 2 回、TPC-C の世界記録を更新し、分散型リレーショナルデータベースとして初めて、ランキングに掲載されました。

本記事では、OceanBase データベース上で TPC-C テストを実行することにより、OceanBase データベースの OLTP 性能を検証します。

## TPC-C について

### データベースモデル

TPC-C ベンチマークはデータベースの初期状態を規定しており、ITEM テーブルには 10 万種類の商品が固定で含まれ、倉庫の数はテスト規模に応じて調整可能です。`WAREHOUSE` テーブルに `W` 件のレコードがあると仮定すると、以下のようになります：

- `STOCK` テーブルには、W×10 万件のレコードが必要です (各倉庫はそれぞれ 10 万種類の商品在庫データに対応)。
-`DISTRICT` テーブルには、W×10 件のレコードが必要です (各倉庫はそれぞれ 10 の地域にサービスを提供)。
- `CUSTOMER` テーブルには、W×10×3000 件のレコードが必要です (各地域に 3000 人の顧客)。
- `HISTORY` テーブルには、W×10×3000 件のレコードが必要です (顧客ごとに 1 件の取引履歴)。
- `ORDER` テーブルには、W×10×3000 件のレコード (地域ごとに 3000 件の注文) が存在し、最後に生成された 900 件の注文は `NEW-ORDER` テーブルに追加され、各注文には 5 ～ 15 件の `ORDER-LINE` レコードがランダムに生成されます。

テストプロセスにおいて、各地域 (`DISTRICT`) には対応する端末 (`Terminal`) が 1 つずつあり、ユーザーへのサービス提供をシミュレートします。各端末のライフサイクルにおいて、様々なトランザクションが繰り返し実行されます。1 つのトランザクションサイクルが完了すると、次のトランザクションサイクルに移行します。

顧客が注文すると、複数の注文明細 (`ORDER-LINE`) を含む注文 (`ORDER`) が生成され、新規注文 (`NEW-ORDER`) リストに追加されます。

顧客が注文に対する支払いを行うと、取引履歴 (`HISTORY`) が生成されます。1 つの注文 (`ORDER`) には平均 10 件の注文明細 (`ORDER-LINE`) が含まれており、そのうち 1% はリモート倉庫から取得する必要があります。これらが TPC-C モデルにおける 9 つのデータテーブルです。

### トランザクションのタイプ

このベンチマークには 5 種類のトランザクションが含まれています。

- NewOrder：新規注文リクエストでは、倉庫から 5 ～ 15 個のアイテムがランダムに選択され、新しい注文が作成されます。そのうち 1% のトランザクションで、ロールバック (つまり `err`) が必要になります。一般的には、新規注文リクエストが、全トランザクションリクエストの 45% を超えることはありません。
- Payment：注文の支払いが完了すると、顧客アカウントの残高が更新され、支払い状況が反映されます。これは全トランザクションリクエストの 43% を占めています。
- OrderStatus：直近注文クエリでは、いずれかのユーザーがランダムに選択され、そのユーザーの最新注文を照会した上で、注文内の各商品のステータスが表示されます。これは全トランザクションリクエストの 4% を占めています。
- Delivery：配送シミュレーションのバッチ処理トランザクションにより、注文ユーザーの残高を更新し、NewOrder から出荷伝票を削除します。これは全トランザクションリクエストの 4% を占めています。
- StockLevel：在庫切れ状態の分析は、全トランザクションリクエストの 4% を占めています。

## 環境の準備

### OceanBase クラスター

デプロイされた OceanBase クラスターのタイプによって、OceanBase データベースのパフォーマンスの評価方法は異なります。クイックスタートセクションで作成した単一ノードの OceanBase クラスターを例にすると、本記事では OceanBase データベースのスタンドアロンモードにおける動作状況を確認できます。OceanBase データベースの分散アーキテクチャにおけるスケーラブルな OLTP 性能を検証したい場合は、最低 3 ノードの OceanBase クラスターでテストすることを推奨します。

この例で使用されているテナントモードは MySQL モードで、テナント名は `test` です。独自のテナントを作成することができますが、詳細な手順については、[マルチテナント機能を試す](../400.experience-multi-tenant-features.md) を参照してください。

### BenchmarkSQL のインストール

TPC の管理組織は、TPC-C について厳格かつ詳細なテスト基準を定義しています。通常、開発者が TPC-C のシナリオをシミュレートしてテストを行う場合、一般的に使用されているオープンソースのテストツールを利用できます。本記事で使用している BenchmarkSQL は、[BenchmarkSQL の公式サイト](https://sourceforge.net/projects/benchmarksql/) からダウンロードしてください。

  <h4>説明</h4>
  <p><ul><li><code>db</code>：データベースのタイプを指定します。ここは、テンプレートとの一貫性を保つようにしてください。</li><li><code>driver</code>：ドライバーファイルとして、MySQL の JDBC ドライバーを使用することを推奨します：<code>mysql-connector-java-5.1.47</code>、<a href="https://downloads.mysql.com/archives/c-j/">ドライバーダウンロードページ</a>。</li><li><code>conn</code>：ここでは、IP アドレスには OceanBase Server の IP を入力し、ポートには OceanBase Server のデプロイメントポートを指定することを推奨します。その他の部分はテンプレートと同じ設定のままにしてください。</li><li><code>user</code> & <code>password</code>：環境で使用されているユーザー名、テナント名、パスワードに基づいて設定できます。環境に複数の OceanBase クラスターが存在する場合、<code>user</code> の形式は <code>{user_name}@{tenant_name}#{cluster_name}</code> を推奨します。</li><li><code>warehouses</code>：ウェアハウスの数を指定します。ウェアハウスの数によってパフォーマンステストの結果が決まります。複数ノードの OceanBase クラスターをテストする場合は、1000 以上のウェアハウスを選択することを推奨します。マシンのリソース設定が限られている場合、100 個のウェアハウスを選択してテストを実行できます。</li><li><code>loadWorkers</code>：ウェアハウスデータの読み込み時の同時実行数を指定します。マシンのスペックが高い場合、この値は 100 など、大きめに設定できます。マシンのスペックが限られている場合、この値は同時実行数 10 など、小さめに設定する必要があります。過度の同時実行はメモリ消費の急増を招き、エラーによりデータの読み込みをやり直す必要が出てくる可能性があります。</li><li><code>terminals</code>：パフォーマンステスト時の同時実行数を指定します。提案の同時実行数は倉庫数の 10 倍を超えないようにしてください。これを超えると、不要なロック待ちが発生します。本番環境では、このパラメーターを最大 1000 に設定することを推奨します。テスト環境では、100 から開始することを推奨します。</li><li><code>runMins</code>：パフォーマンステストの継続時間を指定します。時間が経つにつれて、データベースのパフォーマンスと安定性がより試されることになります。10 分未満は推奨しません。本番環境では、1 時間以上にすることを推奨します。</li></p>
</main>

### テーブルの作成

テーブル作成スクリプトは通常、benchmarkSQL の `run/sql.common` ディレクトリまたはその他の指定ディレクトリに配置されます。テーブル作成スクリプトは、パーティションテーブル方式で作成し、ほとんどのテーブルはウェアハウス ID に基づいて HASH パーティション化されます。パーティション数は、テスト対象のデータ規模とマシン数によって決まります。
クラスターにマシンが 1 台または 3 台しかない場合、パーティション数は 9 に設定します。もし倉庫数が 5000 以上、またはクラスター内のノード数が多い場合、パーティション数を 99 に調整することができます。


### データの読み込み

データのロードはデータの初期化を意味します。データの読み込み速度はマシンの構成によって異なり、マシンの性能が高いほど読み込み速度が速くなります。

```shell
./runLoader.sh props.ob
```

データの読み込みに使用する `INSERT` SQL は、`props.ob` 内の JDBC URL で指定された Batch Insert 機能を利用しています。この機能を有効にすると、書き込みパフォーマンスが大幅に向上します。

## テスト開始

パフォーマンステストを開始する前に、該当テナントにログインしてクラスターマージ (メジャーフリーズ) を実行し、より良いテスト結果を得ることを推奨します。以下の方法で手動でマージをトリガーできますが、このプロセスは必須ではありません。



TPC-C は、tpmC 値 (1 分あたりのトランザクション数) を使用して、システムの最大有効スループットを測定します。ここで、Transactions は NewOrder Transactions を基準としており、最終的な測定単位は 1 分間に処理される注文数になります。

## OceanBase データベース Scalable OLTP の検証

上記のテストでは、単一ノードクラスターの場合でも、複数ノードクラスターの場合でも、トランザクション処理に参加するのはデフォルトで 1 つのレプリカ Zone、およびテナント Leader が存在するレプリカのみです。これは、デフォルト設定では、テナントの Leader が Zone の次元に沿って、特定の優先順位で分散されているためです。

OceanBase は分散データベースとして、ユーザーは 1 つのテナントのすべてのデータパーティションで複数の Leader を複数のレプリカに Shuffle して分散させることができ、コンピューティング処理能力を複数のマシンで線形に拡張することができます。

3 ノード以上のクラスター設定の場合、管理者権限で以下のコマンドを実行し、テストを再実行することで、分散クラスターのスケールアウトモードにおける処理能力を体感できます。

```shell
obclient> ALTER TENANT test SET PRIMARY_ZONE='zone1';
```
