# OceanBaseデータベースにおけるTPC-Cテスト

TPC-Cは、TPC（Transaction Processing Performance Council）が策定した一連の性能テスト基準の一つであり、その登場以来、データベース業界における性能評価の重要な指標となっています。世界中の主要なデータベースベンダーは、TPC-Cテストのランキングでより良い成績を収めることを目指して、TPC委員会にテスト結果を提出しています。OceanBaseデータベースは2019年と2020年の2度にわたり、TPC-Cの世界記録を更新し、ランキング表上で初めての分散リレーショナルデータベースとなりました。

本記事では、OceanBaseデータベース上でTPC-Cテストを実行することで、OceanBaseデータベースのOLTP能力を体験します。

## TPC-Cについて

### データベースモデル

TPC-Cベンチマークでは、データベースの初期状態が規定されています。その中で、ITEMテーブルには固定された10万種類の商品が含まれ、倉庫の数はテスト規模に応じて調整可能です。`WAREHOUSE`テーブルに`W`件のレコードがあると仮定すると、以下のようになります：

- `STOCK`テーブルにはW×10万件のレコードが存在します（各倉庫に対応する10万種類の商品の在庫データ）。
- `DISTRICT`テーブルにはW×10件のレコードが存在します（各倉庫が10の地区にサービスを提供）。
- `CUSTOMER`テーブルにはW×10×3000件のレコードが存在します（各地区に3000人の顧客がいる）。
- `HISTORY`テーブルにはW×10×3000件のレコードが存在します（各顧客に1件の取引履歴）。
- `ORDER`テーブルにはW×10×3000件のレコードが存在します（各地区に3000件の注文があり）、最後に生成された900件の注文は`NEW-ORDER`テーブルに追加され、各注文にはランダムに5〜15件の`ORDER-LINE`レコードが生成されます。

テストプロセスにおいて、各地域（`DISTRICT`）にはそれぞれ対応する端末（`Terminal`）があり、ユーザーへのサービス提供をシミュレートします。各端末のライフサイクル内で、さまざまなトランザクションを繰り返し実行し、端末が1つのトランザクションのサイクルを終えると、次のトランザクションのサイクルに入ります。

顧客が注文すると、複数の注文明細（`ORDER-LINE`）を含む注文（`ORDER`）が生成され、新規注文（`NEW-ORDER`）リストに追加されます。

顧客が注文を支払うと、取引履歴（`HISTORY`）が生成されます。各注文（`ORDER`）には平均して10件の注文項目（`ORDER-LINE`）が含まれ、そのうち1%はリモート倉庫から取得する必要があります。これらがTPC-Cモデルにおける9つのデータテーブルです。

### トランザクションタイプ

このベンチマークには5種類のトランザクションが含まれます：

- NewOrder：新規注文リクエストは、特定の倉庫からランダムに5〜15点の商品を選択し、新規注文を作成します。そのうち1%のトランザクションはロールバック（すなわち`err`）が必要です。一般的に、新規注文リクエストは全トランザクションリクエストの45%を超えることはありません。
- Payment：注文の支払いは顧客アカウント残高を更新し、支払い状況を反映します。全トランザクションリクエストの43%を占めます。
- OrderStatus：最近の注文クエリはランダムに1人のユーザーを選択し、そのユーザーの最新の注文を照会し、その注文内の各商品の状態を表示します。全トランザクションリクエストの4%を占めます。
- Delivery：配送はバッチ処理トランザクションをシミュレートし、その注文ユーザーの残高を更新し、出荷伝票をNewOrderから削除します。全トランザクションリクエストの4%を占めます。
- StockLevel：在庫不足状態の分析は、全トランザクションリクエストの4%を占めます。

## 環境準備

### OceanBaseクラスタ

デプロイされたOceanBaseクラスタの種類によって、OceanBaseデータベースのパフォーマンスを評価する方法は異なります。クイックスタートガイドに従って単一ノードのOceanBaseクラスタを構築した場合、本記事ではそのマシン上でのOceanBaseデータベースの動作状況を確認できます。一方、OceanBaseデータベースの分散アーキテクチャにおけるスケーラブルなOLTP性能を検証したい場合は、少なくとも3つ以上のノードで構成されるOceanBaseクラスタでのテストを推奨します。

この例で使用されているテナントモードはMySQLモードで、テナント名は`test`です。独自のテナントを作成することも可能です。詳細な手順については、[マルチテナント機能の体験](../400.experience-multi-tenant-features.md)を参照してください。

### BenchmarkSQLのインストール

TPCは、TPC-Cに対して厳密かつ詳細なテスト基準を定義しています。一般的に、開発者がTPC-Cのシナリオを模倣してテストを行う場合、現在よく使われているオープンソースのテストツールを利用できます。例えば、本記事で使用しているBenchmarkSQLは、[BenchmarkSQL公式ダウンロードURL](https://sourceforge.net/projects/benchmarksql/)からダウンロードできます。

TPC-Cは、tpmC値（Transactions per Minute）を使用してシステムの最大有効スループットを測定します。ここで、TransactionsはNewOrder Transactionを基準とし、最終的な測定単位は1分間に処理される注文数となります。

## OceanBaseデータベースのスケーラブルなOLTPを体験する

上記のテストでは、単一ノードクラスタのテストであっても、複数ノードクラスタのテストであっても、デフォルトではトランザクション処理に参加するのは1つのレプリカゾーン、すなわちテナントリーダーが存在するレプリカのみです。これは、デフォルト設定では、テナントのリーダーがゾーン単位で一定の優先順位に基づいて分散されているためです。

OceanBaseは分散型データベースとして、ユーザーはテナントの全データパーティションの複数のリーダーを複数のレプリカにShuffle分散させることで、計算処理能力のマルチマシンによる線形スケールアップを実現できます。

クラスタ環境が3ノード以上の構成である場合、管理者権限で以下のコマンドを実行し、再度テストを開始するだけで、スケールアウトモードにおける分散型クラスタの処理能力を体験できます。

```sql
alter tenant test set primary_zone='zone1';
```
