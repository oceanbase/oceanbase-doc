# OceanBase データベースのホットスポット行更新機能の検証

オンライン取引や e コマース業界の発展に伴い、ビジネスシステムのホットスポットにおける同時実行の負荷が、徐々に大きな課題となっています。ホットスポットのアカウントにおける残高が短時間に大量に更新されたり、人気商品がマーケティングキャンペーンで時間限定で販売されたりする状況は、まさにこのシナリオを如実に示しています。ホットスポット更新とは、短時間内にデータベース内で同一行データの特定のフィールド値 (残高、在庫など) を大量に同時更新することです。このボトルネックは主に、リレーショナルデータベースがトランザクションの一貫性を維持するために、データ行の更新がすべて「ロック -> 更新 -> ログ書き込みとコミット -> ロック解除」というプロセスを経る必要があること、またこのプロセスが逐次的であることによります。それで、ホットスポット行の更新パフォーマンス向上のための鍵は、ロック保持時間をできる限り短縮することにあります。

学術的には早くから「早期ロック解放 (Early Lock Release)」(ELR) 方式が提案されてきましたが、ELR の例外処理シナリオが非常に複雑なこともあり、業界では成熟した本番実装例がほとんどありません。OceanBase データベースは、この問題に対して継続的な探求を通じて、分散アーキテクチャに基づく実装方法を提案し、類似のビジネスシナリオで単一行を同時更新する能力を向上させました。これは OceanBase データベースの「スケーラブルな OLTP」の主要な機能の 1 つとなっています。

本記事では、複数の単一行を同時実行で更新するシナリオを構築することで、OceanBase データベースの ELR 機能の使用方法と効果を比較して説明します。複数の同時実行による負荷が発生するシナリオでの検証のため、この例と同等かこれを上回るノード仕様での実証および検証がより効果的であり、推奨されます。OceanBase データベースの ELR の設計と実装原理は複雑なため、本記事では詳細な説明については省略いたします。

この例では、16 コア、128 GB 構成のノードを使用し、OceanBase データベースの ELR 機能を段階的に検証していきます。

## 手順 1：テストテーブルを作成し、テストデータを挿入します

まず、テストデータベースにテーブルを作成し、テストデータを挿入します。

```sql
CREATE TABLE `sbtest1` (
   `id` int(11) NOT NULL AUTO_INCREMENT,
   `k` int(11) NOT NULL DEFAULT '0',
   `c` char(120) NOT NULL DEFAULT '',
   `pad` char(60) NOT NULL DEFAULT '',
   PRIMARY KEY (`id`)
);

INSERT INTO sbtest1 VALUES(1,0,'aa','aa');
```

この例では、`UPDATE sbtest1  SET k=k+1 WHERE id=1` のようなステートメントを用いて、プライマリキーによるクエリ方式で `k` 列に対する同時更新を行います。より多くのデータを挿入してテストすることもできますが、単一行に対する同時実行の負荷テストであるため、全体的な結果には基本的に影響しません。

## 手順 2：並行更新シナリオの構築

この例では、Python のマルチスレッドを用いて同時更新をシミュレートします。50 個の Thread を同時に起動し、各 Thread で id=1 の行データの k フィールドの値を 1 ずつ増加させます。ご自身で構築した環境でも、以下のスクリプト `ob_elr.py` を直接使用してテストできます。スクリプト内のデータベース接続情報を変更するだけで利用可能です。

```python
#!/usr/bin/env python3

from concurrent.futures import ThreadPoolExecutor
import pymysql
import time
import threading

# database connection info
config = {
    'user': 'root@test',
    'password': '****',
    'host': 'xxx.xxx.xxx.xxx',
    'port': 2881,
    'database': 'test'
}

# parallel thread and updates in each thread
parallel = 50
batch_num = 2000

# update query
def update_elr():
    update_hot_row = ("update sbtest1 set k=k+1 where id=1")
    cnx = pymysql.connect(**config)
    cursor = cnx.cursor()

    for i in range(0,batch_num):
        cursor.execute(update_hot_row)
    cursor.close()
    cnx.close()

start=time.time()

with ThreadPoolExecutor(max_workers=parallel) as pool:
    for i in range(parallel):
        pool.submit(update_elr)

end = time.time()
elapse_time = round((end-start),2)

print('Parallel Degree:',parallel)
print('Total Updates:',parallel*batch_num)
print('Elapse Time:',elapse_time,'s')
print('TPS on Hot Row:' ,round(parallel*batch_num/elapse_time,2),'/s')
```

## 手順 3：デフォルト設定でテストを実行する

比較対象として、まず ELR をデフォルトで有効にせずにテストを行い、テストマシン上で `ob_elr.py` スクリプトを直接実行します。

この例では、50 の同時実行数で、合計 100000 回の更新を行います。

```shell
./ob_elr.py
```

実行完了後、テストスクリプトは実行時間と TPS を出力します。

```shell
[root@obce00 ~]# ./ob_elr.py
Parallel Degree: 50
Total Updates: 100000
Elapse Time: 54.5 s
TPS on Hot Row: 1834.86 /s
```

テスト結果は次のとおりです：

ELR を有効にしないデフォルト設定で、この例のテスト環境では、単一行の並行更新の TPS は 1834.86/s です。

## 手順 4：OceanBase データベースの ELR 設定を開く

次に、OceanBase データベースのホットスポット行機能を有効化します。まず、`root` ユーザーでクラスターの `sys` テナントにログインする必要があります。

```shell
[root@obce00 ~]# obclient -h127.0.0.1 -P2881 -uroot@sys  -Doceanbase -A -p -c
```

次に以下の 2 つのパラメーターを設定します。`enable_early_lock_release` パラメーターは、特定のテナントまたは全テナント (つまり `tenant=all`) に適用できます。

``` sql
ALTER SYSTEM SET _max_elr_dependent_trx_count = 1000;
ALTER SYSTEM SET enable_early_lock_release=true tenant= test;
```

## 手順 5：OceanBase データベースの ELR を有効化してテストする

ホットスポット行機能を有効にした後、再度テストを実行しました。実行前に、テーブル `sbtest` の `id=1` のレコードを確認します。`k` フィールドの値は 100000 ですが、これはデフォルト設定で 100000 回の更新が実行されたためです。

```shell
SELECT * FROM sbtest1 WHERE id=1;
+----+--------+----+-----+
| id | k      | c  | pad |
+----+--------+----+-----+
|  1 | 100000 | aa | aa  |
+----+--------+----+-----+
1 row in set
```

次に、テストマシンで `ob_elr.py` を再度実行します。同時実行数は 50 のまま、合計 100000 回更新します。

```shell
./ob_elr.py
```

実行完了後、テストスクリプトは実行時間と TPS を出力します：

```shell
[root@obce00 ~]# ./ob_elr.py
Parallel Degree: 50
Total Updates: 100000
Elapse Time: 12.16 s
TPS on Hot Row: 8223.68 /s
```

テスト結果は次のとおりです：

OceanBase データベースで ELR による早期行ロック解除機能を有効化すると、単一行更新の TPS は 8223.68/s に達し、デフォルト設定と比較して約 4.5 倍向上します。

同時に、テーブル `sbtest1` の `k` 値が 200000 であることが確認できます。つまり、今回の処理で 100000 回更新されました。

```sql
SELECT * FROM sbtest1 WHERE id=1;
+----+--------+----+-----+
| id | k      | c  | pad |
+----+--------+----+-----+
|  1 | 200000 | aa | aa  |
+----+--------+----+-----+
1 row in set
```

この例では単一行の同時更新のシナリオのみを説明しましたが、OceanBase データベースの ELR 機能は複数ステートメントトランザクションの同時更新もサポートしており、ステートメント数とシナリオの違いによって、同様に顕著なパフォーマンス向上を実現できます。

また、OceanBase データベースの ELR は、複数地域にデプロイされた高ネットワーク遅延のシナリオにも適用できます。例えば、単一トランザクションがデフォルトのシナリオで 30 ms の場合、並行処理で ELR を有効にすると、TPS スループットが約 100 倍向上します。

OceanBase データベースのログプロトコルは Multi-Paxos に基づいて構築されており、2PC コミットプロセスが最適化されているため、ELR を有効にした場合、ノードのクラッシュや再起動、リーダーの切り替えが発生しても、OceanBase データベースはトランザクションの一貫性を保証できます。これらの実験を自分で実施して検証できます。
