# システムアーキテクチャ

OceanBaseデータベースは、シェアードナッシング（Shared-Nothing）型の分散クラスタアーキテクチャを採用しており、各ノード間は完全に対等です。各ノードには独自のSQLエンジン、ストレージエンジン、トランザクションエンジンが備わっており、一般的なPCサーバーで構成されるクラスタ上で動作します。これにより、高い拡張性、高可用性、高性能、低コスト、そして主要なデータベースとの高い互換性という核心的な特徴を備えています。

![OceanBaseクラスタアーキテクチャ図](https://obportal.s3.ap-southeast-1.amazonaws.com/doc/img/OceanBase-Database-EN/ob-cluster-arch.png)

OceanBaseデータベースのクラスタは複数のノードで構成されます。これらのノードはいくつかのアベイラビリティゾーン（Zone）に属し、各ノードは一つのアベイラビリティゾーンに属します。アベイラビリティゾーンは論理的概念であり、クラスタ内で類似したハードウェア可用性を持つノード群を示します。その意味合いは、異なるデプロイモードによって変わります。例えば、クラスタ全体が同一のデータセンター（IDC）内に配置されている場合、一つのアベイラビリティゾーンのノードは同一のラックやスイッチに属することがあります。一方、クラスタが複数のデータセンター（IDC）にまたがっている場合、各アベイラビリティゾーンはそれぞれ一つのデータセンター（IDC）に対応します。各アベイラビリティゾーンには、IDCとリージョン（Region）という二つの属性があり、そのアベイラビリティゾーンが属するIDCおよびIDCが属するリージョンを表します。一般的に、リージョンとはIDCが所在する都市を指します。アベイラビリティゾーンのIDCとリージョン属性は、デプロイ時の実際の状況を反映させる必要があり、これによりクラスタ内の自動ディザスタリカバリ処理や最適化戦略がより効果的に機能します。業務によるデータベースシステムへの高可用性要件の違いに応じて、OceanBaseクラスタは複数のデプロイモードを提供しています。デプロイモードの詳細については、[OceanBaseクラスタの高可用性デプロイソリューションの概要](../400.deploy/200.introduction-to-oceanbase-cluster-high-availability-deployment-scheme.md)を参照してください。

OceanBaseデータベースでは、あるテーブルのデータを特定の分割ルールに基づいて水平方向に複数のシャードに分割することができ、各シャードをテーブルパーティションと呼び、略してパーティション（Partition）とも呼びます。ある行のデータは一つのパーティションにのみ属します。パーティションのルールは、ユーザーがテーブル作成時に指定します。これにはHash、Range、Listなどのタイプのパーティションが含まれ、さらにサブパーティションもサポートされています。例えば、取引データベースの注文テーブルでは、まずユーザーIDに基づいて複数のパーティションに分割し、次に各パーティションを月ごとに複数のサブパーティションに分割することができます。サブパーティションテーブルにおいて、サブパーティションの各パーティションは物理パーティションであり、パーティションは単なる論理的概念です。一つのテーブルの複数のパーティションは、一つのアベイラビリティゾーン内の複数のノードに分散配置することができます。各物理パーティションには、データを格納するためのストレージ層オブジェクトがあり、これをTabletと呼び、順序付けられたデータレコードを格納するために使用されます。

ユーザーがTablet内のレコードを変更する際、データの永続性を保証するために、RedoログをTabletに対応するログストリーム（Log Stream、LS）に記録する必要があります。各ログストリームは、そのノード上の複数のTabletをサポートします。データを保護し、ノード障害発生時にもサービスを中断しないようにするため、各ログストリームとそれに属するTabletには複数のレプリカがあります。一般的に、複数のレプリカは複数の異なるアベイラビリティゾーンに分散配置されます。複数のレプリカのうち、変更操作を受け入れるのは一つだけであり、これをリーダーレプリカ（Leader）と呼び、他のレプリカをフォロワーレプリカ（Follower）と呼びます。リーダーとフォロワーのレプリカ間では、Multi-Paxosに基づく分散コンセンサスプロトコルによってレプリカ間のデータの一貫性が実現されます。リーダーレプリカが属するノードに障害が発生した場合、一つのフォロワーレプリカが新しいリーダーレプリカとして選出され、サービスを継続します。

クラスタの各ノード上では、observerと呼ばれるサービスプロセスが実行され、その内部には複数のOSスレッドが含まれます。ノードの機能はすべて対等です。各サービスは、自身が属するノード上のパーティションデータのアクセスを担当し、またそのノードにルーティングされるSQL文の解析と実行も担当します。これらのサービスプロセス間はTCP/IPプロトコルを介して通信します。同時に、各サービスは外部アプリケーションからの接続リクエストを監視し、接続とデータベースセッションを確立し、データベースサービスを提供します。observerサービスプロセスの詳細については、[スレッドの概要](../700.reference/100.oceanbase-database-concepts/1200.observer-node-architecture/300.observer-thread-model/100.thread-introduction.md)を参照してください。

大規模な複数の業務データベースのデプロイ管理を簡素化し、リソースコストを削減するために、OceanBaseデータベースは独自のマルチテナント機能を提供しています。一つのOceanBaseクラスタ内では、相互に隔離された複数のデータベース「インスタンス」を作成でき、これをテナントと呼びます。アプリケーションの観点から見ると、各テナントは独立したデータベースインスタンスと同等です。さらに、各テナントはMySQLまたはOracle互換モードを選択できます。アプリケーションがMySQLテナントに接続すると、そのテナント内でユーザーやデータベースを作成でき、独立したMySQLデータベースと同様の使用体験が得られます。同様に、アプリケーションがOracleテナントに接続すると、そのテナント内でスキーマやロールを作成・管理でき、独立したOracleデータベースと同様の使用体験が得られます。新しいクラスタが初期化されると、sysという特殊な名前のテナントが自動的に作成され、これをシステムテナントと呼びます。システムテナントにはクラスタのメタデータが保存されており、MySQL互換モードのテナントです。

<h4>適用対象</h4>
<p>OceanBaseデータベースCommunity Editionは、MySQLモードのみを提供します。</p>

テナントのリソースを隔離するため、各observerプロセス内には、異なるテナントに属する複数の仮想コンテナがあり、これをリソースユニット（Unit）と呼びます。リソースユニットにはCPUとメモリリソースが含まれます。各テナントの複数ノード上のリソースユニットは、一つのリソースプールを形成します。

OceanBaseデータベースがアプリケーションから内部のパーティションやレプリカの配置などの詳細を隠蔽し、アプリケーションが分散データベースにアクセスすることを、単一のデータベースにアクセスするのと同じくらい簡単にするために、OceanBaseデータベースプロキシODP（OceanBase Database Proxy、OBProxyとも呼ばれる）サービスを提供しています。アプリケーションは直接OceanBaseデータベースノードと接続するのではなく、まずODPに接続し、ODPがSQLリクエストを適切なOceanBaseデータベースノードに転送します。ODPはステートレスのサービスであり、複数のODPノードがネットワークロードバランシング（例えば、SLB）を通じてアプリケーションに統一されたネットワークアドレスを提供します。
