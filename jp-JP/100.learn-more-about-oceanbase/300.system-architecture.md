# システムアーキテクチャ

OceanBase データベースは、シェアードナッシング (Shared-Nothing、SN) モードと共有ストレージ (Shared-Storage、SS) モードの 2 種類のデプロイモードをサポートしています。

## SN モード

SN モードの分散クラスターアーキテクチャは、OceanBase データベースで一般的に使用されるデプロイ方法です。SN モードでは、各ノードは完全に対等であり、各ノードは独自の SQL エンジン、ストレージエンジン、トランザクションエンジンを備え、一般的な PC サーバーで構成されたクラスター上で動作し、高い拡張性、高可用性、高性能、低コスト、主要データベースとの高い互換性などの主要な特性を備えています。

![OceanBase クラスターアーキテクチャ図](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.3.1/oceanbase-cluster-system-architecture.png)

OceanBase データベースのクラスターは、複数のノードで構成されています。これらのノードは複数のゾーン (Zone) に属し、各ノードは 1 つのゾーンに属します。ゾーンは論理的な概念であり、クラスター内で類似のハードウェア可用性を持つノードのグループを表し、異なるデプロイモードでは異なる意味を持ちます。例えば、クラスター全体が同じデータセンター (IDC) 内にデプロイされている場合、1 つのゾーンのノードは、同じラック、同じ vSwitch などに属することが可能です。クラスターが複数のデータセンターに分散されている場合、各ゾーンは 1 つのデータセンターに対応できます。各ゾーンは、IDC とリージョン (Region) の 2 つの属性を持ち、そのゾーンが属する IDC と、その IDC の属するリージョンを示します。通常、リージョンは IDC の所在都市を指します。ゾーンの IDC と Region 属性は、デプロイ時の実際の状況を反映する必要があります。これにより、クラスター内の自動ディザスタリカバリ処理と最適化戦略がより効果的に機能します。ビジネスにおけるデータベースシステムの高可用性ニーズの違いに応じて、OceanBase クラスターは複数のデプロイモードを提供しています。デプロイモードの詳細については、[OceanBase クラスター高可用性デプロイプランの概要](../400.deploy/200.introduction-to-oceanbase-cluster-high-availability-deployment-scheme.md) を参照してください。

OceanBase データベースでは、1 つのテーブルのデータは、特定の分割ルールに従って水平に複数のシャードに分割できます。各シャードはテーブルパーティション、または単にパーティション (Partition) と呼ばれます。1 行のデータは、1 つのパーティションのみに属します。パーティションのルールは、ユーザーがテーブル作成時に指定します。Hash、Range、List などのパーティションタイプが含まれ、二次パーティションもサポートしています。例えば、取引データベースの注文テーブルは、まずユーザー ID ごとに複数の一次パーティションに分割し、次に月ごとに各一次パーティションを複数の二次パーティションに分割できます。二次パーティションテーブルでは、二次パーティションの各パーティションは物理的なパーティションであり、一次パーティションは論理的な概念に過ぎません。1 つのテーブルの複数のパーティションは、1 つのゾーン内の複数のノードに分散できます。各物理的なパーティションには、データを格納するためのオブジェクトストレージがあります。これを Tablet と呼び、順序付けられたデータレコードを格納します。

ユーザーが Tablet 内のレコードを修正すると、データの永続性を確保するために、Redo ログを Tablet に対応するログストリーム (Log Stream、LS) に書き込む必要があります。各ログストリームは、それが属するノード上の複数の Tablet にサービスを提供します。データ保護とノード障害時のサービス継続性を確保するため、各ログストリームとそれに属する Tablet は複数レプリカを保有します。一般的に、複数のレプリカは複数の異なるゾーンに分散されています。複数のレプリカのうち、変更操作を受け付けるのはただ 1 つのレプリカのみであり、これをプライマリレプリカ (Leader) と呼び、他のレプリカはセカンダリレプリカ (Follower) と呼びます。プライマリレプリカとセカンダリレプリカ間は、Multi-Paxos に基づく分散型コンセンサスプロトコルによってデータの一貫性が確保されます。プライマリレプリカが属するノードに障害が発生した場合、セカンダリレプリカの 1 つが新しいプライマリレプリカとして選出され、サービスを提供し続けます。

クラスターの各ノードでは、複数の OS スレッドが含まれている observer と呼ばれるサービスプロセスが実行されます。ノードの機能はすべて対等です。各サービスは、自身が属するノード上のパーティションデータのアクセスを担当するとともに、マシンにルーティングされた SQL 文の解析と実行も担当します。各ノード上の observer サービスプロセス間は、TCP/IP プロトコルで通信を行います。同時に、各サービスは外部アプリケーションからの接続要求を監視し、接続とデータベースセッションを確立し、データベースサービスを提供します。observer サービスプロセスの詳細については、[スレッドの概要](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001973718) を参照してください。

大規模な複数の業務データベースをデプロイする管理を簡素化し、リソースコストを削減するため、OceanBase データベースは独自のマルチテナント機能を提供します。OceanBase クラスター内には、互いに隔離された複数のデータベース「インスタンス」を作成できます。これをテナントと呼びます。アプリケーションの観点から見ると、各テナントは独立したデータベースインスタンスに相当します。それだけでなく、各テナントは MySQL または Oracle 互換モードを選択できます。アプリケーションが MySQL テナントに接続すると、テナント内でユーザーおよび Database を作成できます。これにより、独立した MySQL データベースを使用するのと同じような体験が得られます。同様に、アプリケーションが Oracle テナントに接続すると、テナント内で schema を作成したり、ロールを管理したりできます。これにより、独立した Oracle データベースを使用するのと同じような体験が得られます。新しいクラスターを初期化すると、sys という名前の特別なテナントが作成され、システムテナントと呼ばれます。システムテナントにはクラスターのメタデータが保存されており、これは、MySQL 互換モードのテナントです。

テナントのリソースを隔離するために、各 observer プロセス内には、異なるテナントに属する複数のリソースユニット (Unit) と呼ばれる仮想コンテナを持つことができます。リソースユニットには、CPU とメモリのリソースが含まれます。各テナントは、複数のノード上のリソースユニットによりリソースプールを構成します。

OceanBase データベースがアプリケーションを内部パーティションやレプリカの分散などの詳細から保護し、アプリケーションが分散型データベースへのアクセスをスタンドアロンデータベースへのアクセスと同じくらい容易にするために、OceanBase データベースプロキシ ODP (OceanBase Database Proxy、OBProxy とも呼ばれる) サービスを提供しています。アプリケーションは OceanBase データベースノードに直接接続するのではなく、まず ODP に接続し、その後 ODP によって SQL リクエストが適切な OceanBase データベースノードに転送されます。ODP はステートレスなサービスであり、複数の ODP ノードはネットワーク負荷分散 (例：SLB) によってアプリケーションに統一されたネットワークアドレスを提供します。

## SS モード

マルチクラウド環境において、よりコストパフォーマンスの高いデータベースサービスをユーザーに提供するため、OceanBase データベースは汎用オブジェクトストレージを基盤に共有ストレージ (SS) モードを実現しました。これによりクラウド上でクラウドネイティブデータベースサービスを提供し、データベースの使用コストを削減しつつ、パフォーマンスとユーザビリティを向上させています。

![OceanBase クラスターアーキテクチャ図 (SS モード)](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.3.4/system-architecture%28ss-mode%29.png)

SS モードは、ストレージとコンピューティングを分離したアーキテクチャを採用しています。各テナントは共有オブジェクトストレージにデータとログを保存し、各テナントはノードのローカルストレージにホットデータとログをキャッシュします。

テナントのログストリームレプリカ間は Paxos によってログのコピーが行われます。各レプリカのログはまずノードのローカルストレージに書き込まれ、各プライマリレプリカはフルログをオブジェクトストレージにアップロードします。各セカンダリレプリカはログのホットスポットを自動的に識別し、ローカルに少量のホットスポットログのみをキャッシュします。

各プライマリレプリカは、フルベースラインデータ 1 つをオブジェクトストレージにアップロードする役割を担い、レプリカ間でオブジェクトストレージ上のベースラインデータを共有し、全レプリカがデータのホットスポットを自動的に検出し、ローカルにのみホットスポットデータをキャッシュします。テナントの各レプリカは個別にダンプされ、ダンプデータはレプリカ間で共有されません。
