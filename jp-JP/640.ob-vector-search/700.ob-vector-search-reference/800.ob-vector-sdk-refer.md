# 互換性に関する説明

このドキュメントでは、OceanBaseのベクトル検索機能とMilvusのデータモデルマッピング関係、SDKインターフェースの互換性、および関連する概念の対照説明について説明します。

## Milvusとの概念マッピング

Milvusに精通しているユーザーがOceanBaseのベクトルストレージ機能を容易に利用できるようにするため、両者の違いと共通点を分析し、関連する概念間のマッピングを提供します。

### データモデル

| **データモデルの階層** | **Milvus** | **OceanBase** | **説明** |
|------------|---------|-----------|-----------|
| 第一層 | Shards | Partition | Milvusは、スキーマ定義時に特定の列を`partition_key`として設定することでパーティションルールを定めます。<br>OceanBaseはrange/range columns、list/list columns、hash、key、およびサブパーティション戦略をサポートしています |
| 第二層 | Partitions | ≈Tablet | Milvusは、同一Shard内（Shardsは通常主キーでパーティション化される）で他の列に基づいてブロックを分割し、読み取り性能を向上させることをサポートしています。<br>OceanBaseは、パーティション内で主キーに従ってソートすることで実現します |
| 第三層 | Segments | MemTable+SSTable | 両者ともダンプ動作を有します |

### SDK

このセクションでは、OceanBaseのベクトルストレージSDKであるpyobvectorとMilvusのSDKであるpymilvusの概念的な違いについて説明します。

pyobvectorには2つの使用モードがあります：

1. pymilvus MilvusClient軽量互換モード：このモードはMilvusクライアントで一般的に使用されるインターフェースに互換性があり、Milvusに精通しているユーザーにとって非常に使いやすく、概念マッピングは不要です。

2. SQLAlchemy拡張モード：このモードはPython SQLAlchemyのベクトル機能拡張として機能し、リレーショナルデータベースの操作モードを保持しています。説明には概念マッピングが必要です。

pyobvectorの具体的なインターフェース使用ドキュメントについては、[pyobvector Python SDKインターフェース説明](../700.ob-vector-search-reference/900.ob-vector-search-supported-clients-and-languages/200.ob-vector-pyobvector.md)を参照してください。

## Milvusとの互換性

### Milvus SDK

`load_collection()`/`release_collection()`/`close()`などSQLAlchemyのサポートが必要なものを除き、以下の表に記載されているインターフェースはすべて互換性があります。

**Collection操作**

| **インターフェース** | **説明** |
|---|---|
| create_collection() | 指定されたSchemaに基づいてベクトルテーブルを作成します。 |
| get_collection_stats() | データテーブルの統計情報（レコード数など）を確認します。 |
| describe_collection() | ベクトルテーブルの詳細なメタ情報を提供します。 |
| has_collection() | テーブルが存在するかどうかを判断します。 |
| list_collections() | 存在するテーブルを一覧表示します。 |
| drop_collection() | テーブルを削除します。 |

**FieldとSchemaの定義**

| **インターフェース** | **説明** |
|---|---|
| create_schema() | Schemaのメモリ構造を作成し、列定義を追加します。 |
| add_field() | 使用時には、create_schema->add_field->...->add_field のシーケンスを呼び出します。</br>または、FieldSchemaのリストを手動で構築し、CollectionSchemaのコンストラクタを使用してSchemaを作成することもできます。 |

**ベクトルインデックス**

| **インターフェース** | **説明** |
|---|---|
| list_indexes() | すべてのインデックスを一覧表示します。 |
| create_index() | 1回の呼び出しで複数のベクトルインデックスを作成できます。まず、prepare_index_paramsを使用してインデックスパラメータリストオブジェクトを初期化し、add_indexを複数回呼び出して複数のインデックスパラメータを設定し、最後にcreate_indexを呼び出してインデックスを作成します。 |
| drop_index() | ベクトルインデックスを削除します。 |
| describe_index() | インデックスのメタデータ（Schema）を取得します。 |

**ベクトルインデックス**

| **インターフェース** | **説明** |
|---|---|
| search() | ANNクエリインターフェース：<ul><li>collection_name：テーブル名</li><li>data：検索対象のベクトル</li><li>filter：フィルタリング操作。`WHERE`と同等です</li><li>limit：上位K件</li><li>output_fields：投影列。`SELECT`と同等です</li><li>partition_names：パーティション名（Milvus Liteはサポートしていません）</li><li>anns_field：インデックス列名</li><li>search_params：ベクトル距離関数名、インデックスアルゴリズム関連パラメータ</li></ul> |
| query() | filter点を含むクエリ、つまり`SELECT ... WHERE ids IN (..., ...) AND <filters>`です。 |
| get() | filter点を含まないクエリ、つまり`SELECT ... WHERE ids IN (..., ...)`です。 |
| delete() | ベクトルの集合を削除します。`DELETE FROM ... WHERE ids IN (..., ...)`。 |
| insert() | ベクトルの集合を挿入します。 |
| upsert() | 主キー競合による更新を伴う挿入。 |

**collectionメタデータの同期**

| **インターフェース** | **説明** |
|---|---|
| load_collection() | データベース内のテーブル構造(Schema)をPythonアプリケーションのメモリにロードし、アプリケーションがオブジェクト指向でデータベーステーブルを操作できるようにします。これはオブジェクト関係マッピング(ORM)フレームワークの標準機能です。 |
| release_collection() | Pythonアプリケーションのメモリからロードされたテーブル構造(Schema)を解放し、関連リソースを解放します。これはORMフレームワークの標準機能であり、メモリ管理に使用されます。 |
| close() | データベース接続を閉じ、関連リソースを解放します。これはORMフレームワークの標準機能です。 |

### pymilvus

#### データモデル

MilvusのデータモデルはShards->Partitions->Segmentsの3つのレベルに分かれており、OceanBaseとの互換性比較は以下の通りです：

* ShardsはOceanBaseのPartitionの概念に対応します。

* Partitionsには現在OceanBaseに対応する概念がありません。

* Milvusは同一Shard内（Shardsは通常主キーでパーティション化されます）で他の列に基づいてブロックを分割し、読み取り性能を向上させることをサポートしています。OceanBaseでは、パーティション内で主キーに従ってソートすることで実現します。

* Segmentsは[MemTable](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/200.MEMTable.md) + [SSTable](../../700.reference/100.oceanbase-database-concepts/900.storage-architecture/200.data-storage/300.SSTable.md)に類似しています。

#### Milvus Lite APIの互換性

##### collection操作

1. Milvus create_collection()：

    ```python
    create_collection(
        collection_name: str,
        dimension: int,
        primary_field_name: str = "id",
        id_type: str = DataType,
        vector_field_name: str = "vector",
        metric_type: str = "COSINE",
        auto_id: bool = False,
        timeout: Optional[float] = None,
        schema: Optional[CollectionSchema] = None, # Used for custom setup

    OceanBaseとの互換性説明は以下の通りです：

    * collection_name：互換性あり、実際にはtable_nameとなります。

    * dimension：互換性あり、vector(dim)となります。

    * primary_field_name：互換性あり、主キー列名となります。

    * id_type：互換性あり、主キー列の列型となります。

    * vector_field_name：互換性あり、ベクトル列名となります。

    * auto_id：互換性あり、auto incrementとなります。

    * timeout：互換性あり、OceanBaseはhintによってサポートします。

    * schema：互換性あり。

    * index_params：互換性あり。

    ```

    OceanBaseとの互換性説明は以下の通りです：

    * APIの互換性。

    * 戻り値の互換性：`{ 'row_count': ... }`。

## MySQLプロトコルとの互換性

* リクエストの送信方法：すべてのAPIは通常のクエリSQLを通じて実装されており、互換性の問題はありません。

* レスポンス結果セットの処理：新規に追加されたベクトルデータ要素の処理を考慮する必要があります。現在、stringとbytesの2種類の要素の解析をサポートしています。今後ベクトルデータ要素の伝送方式が変更された場合でも、SDKを更新することで互換性を維持できます。
