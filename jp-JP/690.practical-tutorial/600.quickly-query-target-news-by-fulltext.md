# 全文インデックスを使用した膨大なニュースデータの効率的な検索の実現

## 背景情報

OceanBase の全文インデックス機能は、実際の運用で発生するさばざまな問題を効果的に解決することができます。特にシステムログ分析、ユーザー行動分析とペルソナ分析などのシナリオで力を発揮します。この機能は、データに対し高速かつ効率的にフィルタリングと選別を行うことができます。また、質の高い関連性評価も行うことができます。さらに、疎ベクトル (Sparse Vector) と密ベクトル (Dence Vector) を組み合わせたマルチウェイリコールアーキテクチャを採用することで、OceanBase は特定の知識領域の RAG システムで、より効率的なリコール効果を実現することができます。

本チュートリアルでは、ニュース情報のビジネスシナリオを例に説明します。このシナリオでは、検索システムに高い要求を突きつける 3 つの主要な課題が存在します：

- **リアルタイム性に関する要件**：TB レベルのデータからターゲットの情報を迅速に特定します。
- **セマンティックの複雑さ**：単語分割、類義語の処理など、自然言語処理における課題を解決します。
- **混合クエリに関する需要**：テキスト検索と構造化クエリを統合し、機能の最適化を向上させます。

本チュートリアルでは、全文インデックス機能を使用して、膨大な情報の中からターゲットニュースをすばやく検索する方法を紹介します。クエリのキーワードから、さらに改善された OceanBase の全文インデックスの機能、パフォーマンス、およびユーザビリティについて紹介します。

## 原理の概要

OceanBase ストレージエンジンでは、ユーザーのドキュメント (doc) とクエリ (query) は、トークナイザーで複数のキーワード (word / token) に分割されます。これらのキーワードとドキュメントの統計情報の特徴は、内部の補助テーブル (tablet) に格納され、情報検索段階での関連性評価 (ranking) に使用されます。OceanBase は、高度な BM25 アルゴリズムを採用しています。このアルゴリズムは、ユーザーのクエリステートメント中のキーワードと保存されているドキュメントの関連性スコアを高精度に算出し、最終的に条件を満たすドキュメントとそのスコアを出力します。

全文インデックスのクエリ処理では、OceanBase の高性能クエリエンジンと組み合わせることで、OceanBase データベースは TAAT / DAAT クエリ処理用に最適化され、複数のインデックス間の union merge をサポートしています。このような改善により、全文インデックスはより複雑なクエリ機能の処理が可能になり、ユーザーのデータ検索に関する需要を満たすことができます。

## 前提条件

OceanBase の全文インデックス機能のスムーズな操作を体験していただくため、次の前提条件が満たされていることをご確認ください：

1. **環境要件**：OceanBase V4.3.5 BP1 以降のバージョンのクラスターをデプロイし、MySQL モードのテナントを作成していること。OceanBase クラスターのデプロイ方法については、[デプロイの概要](../400.deploy/100.deploy-overview.md) を参照してください。デプロイ完了後、以下の SQL を使用してクラスターとテナント情報を検証してください：

   ```sql
   -- クラスター情報の検証
   SELECT * FROM GV$OB_SERVERS;

   -- テナント情報の検証
   SELECT * FROM oceanbase.DBA_OB_TENANTS;
   ```

2. **権限設定**：作成した MySQL モードのテナントに挿入とクエリを実行する権限が付与されていること。権限設定の詳細については、[直接権限の付与](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001974757) を参照してください。

3. **データベースの作成**：データベースが作成されていることを確認してください。詳細な手順については、[データベースの作成](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001971662) を参照してください。

## 操作手順

以下の操作手順に従って、OceanBase の全文インデックス、一般的なビュー、およびクエリテクニックを体験してください。

### 手順 1：データセットをインポートする

OceanBase には言語に対応した IK トークナイザ―と、従来の自然言語処理と比べてより効率的なブールモードが内蔵されています。ここでは [中国語版サッカースポーツニュースデータセット](https://github.com/ej0cl6/SportsSum) を使用して OceanBase にデータをインポートし、`sport_data_whole` という名前のプライマリキーなしパーティションテーブルを作成します。このテーブルには、3 つの可変長文字列 (`event`、`date`、`news`) が含まれます。また、IK トークナイザ―を使用して、`news` フィールドに全文インデックスを作成し、モードを `max_word` に指定します。


<main id="notice" type='explain'>
<h4>説明</h4>
<p>IK トークナイザ―の <code>smart</code> モードと <code>max_word</code> モードの違いは、smart モードでは最も長い単語にマッチングした後、それより短い単語へのマッチングが続行されないことです。<br>OceanBase に内蔵されているトークナイザ―には、英語に適した space と beng、および文字長で分割された n-gram も含まれています。</p>
</main>

```sql
-- テーブルを作成し、IK トークナイザ―を使用して全文インデックスを実行する
CREATE TABLE sport_data_whole (
    event VARCHAR(64),
    date VARCHAR(16),
    news VARCHAR(65535),
    FULLTEXT INDEX (news) WITH PARSER ik PARSER_PROPERTIES=(ik_mode="max_word")
);
```

クライアントのローカルファイル経由で、ニュースデータセットをテーブルにインポートします。所要時間は約 30 秒程度です。

```sql
-- データのインポート
LOAD DATA /*+ PARALLEL(8) */ LOCAL INFILE '/home/sports_data_whole.csv' INTO TABLE sport_data_whole
FIELDS TERMINATED BY ',' LINES TERMINATED BY '\n';
```

データのインポートした後、テーブル上にニュース件数は合計 5268 件、平均ニュース長は約 2700 字、元のデータサイズは約 57 MB と表示されます。高効率な圧縮処理が実行されると、実際のストレージ容量の合計は 30 MB 未満になり、その大部分は全文インデックスの逆引き副テーブルと正引きの副テーブルで占められます。これらのテーブルには、大量の単語分割レコードが格納されています。

```sql
-- インポートされた行数の検証
SELECT AVG(LENGTH(news)), COUNT(*) FROM sport_data_whole;
```

結果は次のとおりです：

```sql

|         2781.6900 |     5268 |
+-------------------+----------+
1 row in set
```


### 手順 2：全文インデックスを利用してクエリする

格納されているニュースデータセットとインデックスを使用することで、複数の条件を組み合わせた検索や高度なフィルタリングによる検索を実行することができます。例えば、サッカーファンが、"バイエルン" と "オウンゴール" を含むニュースを検索する場合、ブールモードを使用できます。

インデックスのない文字列 `LIKE` マッチと比べ、ブールモードの構文はシンプルで、クエリ速度も高速です。

```sql
-- ブールモードでクエリを実行し、"オウンゴール" と "バイエルン" の両方が含まれるニュースを検索する
SELECT COUNT(*) FROM sport_data_whole
WHERE MATCH (news) AGAINST ('+オウンゴール +バイエルン' IN BOOLEAN MODE);
```

結果は次のとおりです：

```sql
+----------+
| count(*) |
+----------+
|        2 |
+----------+
1 row in set (0.03 sec)
```

対照的に、`LIKE` クエリを使用する場合は以下のようになります：

```sql
-- LIKE 構文を使用してクエリを実行する
SELECT COUNT(*) FROM sport_data_whole
WHERE news LIKE '%オウンゴール%' AND news LIKE '%バイエルン%';
```

結果は次のとおりです：

```sql
+----------+
| count(*) |
+----------+
|        2 |
+----------+
1 row in set (0.08 sec)
```

返ってきた 2 件のニュースについて、さらにランキング (ranking) を実行することができます。出力結果のスコアから、クエリとの関連性がより高いニュースはどちらであるかを判断します。

```sql
-- ニュースのイベント、日付、スコアを返し、関連性を判断する
SELECT event, date, MATCH (news) AGAINST ('オウンゴール バイエルン') AS score
FROM sport_data_whole
WHERE MATCH (news) AGAINST ('+オウンゴール +バイエルン' IN BOOLEAN MODE);
```

結果は次のとおりです：

```sql
+-------+------+---------------------+
| event | date | score               |
+-------+------+---------------------+
| ucl   | 0278 |  0.4657063867776557 |
| ucl   | 0201 | 0.41760566608994765 |
+-------+------+---------------------+
2 rows in set
```

また、ブールモードでは、逆向きに特定のキーワードを除外することも可能です。例えば、ほとんどのサッカーの試合ではファウル行為がみられます。もし、激しい試合でも、レッドカードやイエローカード、またファウルすらなかった試合を知りたい場合は、ブールモードの `-` 演算子を使用できます。

```sql
-- イエローカード、レッドカード、ファウルがなかった激しい試合のクエリを実行する
SELECT COUNT(*) FROM sport_data_whole
WHERE MATCH (news) AGAINST ('+激しい -イエローカード -レッドカード -ファウル' IN BOOLEAN MODE);
```

結果は次のとおりです：

```sql
+----------+
| count(*) |
+----------+
|       31 |
+----------+
1 row in set
```

### 手順 3：チューニングする

#### `TOKENIZE` 関数を使用してチューニングを実行する

全文インデックスのクエリ結果が期待どおりではない場合、通常は単語分割の結果が最適でないことが原因です。OceanBase は、単語分割効果のテストをサポートする高速な `TOKENIZE` 関数を提供しています。この関数は、すべてのトークナイザ―と対応する属性をサポートしており、`TOKENIZE` 関数を使用して、単語分割のトークナイザーの処理結果を検証することができます。

例えば、次の例では、手動の単語分割の結果をみると、辞書の海外スポーツ選手の名前に関するサポートが十分でないことが分かります (例：ボアテング、ゲッツェ)。これは、人名で検索する時に、検索結果の精度に影響を与える可能性があります。

#### union merge を使用してチューニングを実行する

本章の最後では、混合クエリにおける全文インデックスと通常のインデックスを比較し、union merge の使用によるパフォーマンス向上について説明します。デモンストレーションの効果を高めるため、`sport_data_whole` テーブルの `date` 列に通常のローカルインデックスを作成します。`SHOW INDEX` コマンドを使用することで、インデックスが有効になっているかどうかを確認できます。

```sql
-- date 列に通常のインデックスを追加します
ALTER TABLE sport_data_whole ADD INDEX (date);

-- インデックスの状況を確認します
SHOW INDEX FROM sport_data_whole;
```

結果は次のとおりです：

```sql
+------------------+------------+----------+--------------+-------------+-----------+-------------+----------+--------+------+------------+-----------+---------------+---------+------------+
| Table            | Non_unique | Key_name | Seq_in_index | Column_name | Collation | Cardinality | Sub_part | Packed | Null | Index_type | Comment   | Index_comment | Visible | Expression |

| sport_data_whole |          1 | news     |            1 | news        | A         |        NULL | NULL     | NULL   | YES  | FULLTEXT   | available |               | YES     | NULL       |
```

2 つのインデックス条件が `OR` で結合されている場合、フィルタリング性能の良い条件下では、union merge は、通常のインデックスでフィルタリングしてから結果を返すモード (プランに `has_functional_lookup=true` がある) よりも高速です。次に、2 つの異なるプランでの推定時間を比較します。

```sql
-- UNION_MERGE を使用したクエリを比較します

FROM sport_data_whole
WHERE date = '0322' OR (MATCH (news) AGAINST ('+オウンゴール' IN BOOLEAN MODE));
```

## MySQL パフォーマンスの比較

OceanBase と MySQL の全文インデックスのパフォーマンスの違いを比較するため、MySQL の全文インデックスの機能を参考にしています。MySQL は中国語の単語分割機能が弱いため、英語データセット `wikir1k` (369,721 行を含みます。1 行あたり平均 100 語) を選択し、パフォーマンスを比較します。

以下は、さまざまなシナリオで自然言語モードとブールモードを比較した結果です。このように、大量の単語分割や結果を返すことが必要なシナリオでは、OceanBase のパフォーマンスは MySQL を大幅に上回ります。小さな結果セットの場合、計算量はさほど多くないため、クエリエンジンの優位性は目立ちません。2 つのエンジンのパフォーマンスはほぼ同等ということができます。

**テスト環境**：OceanBase テナントの仕様は 8c 16g、MySQL バージョンは 8.0.36 for Linux on x86_64 (MySQL Community Server - GPL) を使用します。

### パフォーマンスの比較のまとめ

上記のデータの比較から、OceanBase で複雑な全文インデックスを実行する場合、自然言語モードとブールモードのいずれも、MySQL よりもはるかに優れたパフォーマンスを示していることがわかります。特に、大量の単語分割を必要とするクエリや、結果の規模が大きいクエリを処理する場合、OceanBase の優位性はより明らかです。これは、開発者やデータアナリストがデータベースを選択する際の強力な参考資料となります。特に、膨大なデータを効率的に検索する必要があるアプリケーションシナリオで、OceanBase は強力なパフォーマンスとフレキシブルなクエリ機能の力をはっきりと証明しています。

OceanBase の全文インデックス機能は、複雑なクエリ処理を実行する際、常に高速な応答時間を提供し、高並列処理と高性能な検索を必要とする実際のアプリケーションシナリオに適しています。
