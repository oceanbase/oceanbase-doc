# ストレージ構造とクエリパフォーマンスを最適化するためのベストプラクティス

データベースシステムの設計と最適化において、データテーブルの設計は非常に重要な作業です。適切な設計は、データの完全性と整合性を確保するだけでなく、クエリのパフォーマンス、ストレージ効率、システムの拡張性を大幅に向上させることができます。データ量の増加とクエリパターンの複雑化に伴い、データテーブルを科学的に設計し、適切なストレージ構造とインデックス戦略を選択することが、データベースを最適化する上で重要な課題となっています。

本記事では、選択テーブルのストレージ形式、単一テーブルのプライマリキーなし列ストアテーブル、パーティション設計、プライマリキー設計、HTAP シナリオでのインデックスの使用などについて、データテーブル設計のベストプラクティスを紹介します。

## テーブルのストレージ形式の選択

OceanBase は、テーブルデータ列ストレージおよび行列両方の冗長ストレージをサポートしており、ビジネスシナリオに応じて適切なデータストレージ形式を選択できます。

+ **列ストアの適用シナリオ**：ビジネスが純粋な OLAP 分析系の場合は、列指向ストレージを選択できます。
+ **行列混合ストレージの使用シナリオ**：ビジネスが HTAP 型のシナリオで、OLAP 分析系のビジネスと OLTP トランザクション型のビジネスの両方を含む場合、分析クエリのパフォーマンスを維持しつつ、ポイントクエリのパフォーマンスも保証したいのであれば、行列両方の冗長ストレージを設定することができます。

テナントレベルの設定項目 [default_table_store_format](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001972072) を使用して、テーブルのデフォルトストレージ形式を設定します。

```sql
-- テナント内テーブルのデフォルトストレージ形式を列ストアに設定
ALTER SYSTEM SET default_table_store_format = 'column';

-- テナント内テーブルのデフォルトストレージ形式を行列両方の冗長ストレージに設定
ALTER SYSTEM SET default_table_store_format = "compound";
```

## 単一テーブルのプライマリキーなし列ストアテーブルの選択

データウェアハウスやオンライン分析処理 (OLAP) のシナリオでは、ビジネスデータテーブルのデータ量は非常に膨大であり、ほとんどのクエリは特定の列のみを対象とします。ビジネスに特別な要件がない場合、例えばデータの一意性の保証、データの重複書き込みの回避、またはトランザクション更新や挿入操作を行う必要がある場合などは、プライマリキーなし列ストアテーブルを作成する方が効率的です：

+ データインポート：データはプライマリキーでソートする必要がないため、大規模データのインポートパフォーマンスはプライマリキーテーブルよりも高速です。
+ プライマリキーの管理コストを削減します。

```sql
show parameters like "%store_format%";

  CREATE TABLE customer (
  user_id bigint NOT NULL,
  login_time timestamp NOT NULL,
  customer_name varchar(100) NOT NULL,    -- 顧客名は最大 100 文字と仮定する
  phone_num bigint NOT NULL,               -- 電話番号は bigint 型で保存する
  city_name varchar(50) NOT NULL,          -- 都市名は最大 50 文字と仮定する
  sex int NOT NULL,                        -- 性別は int 型で保存する (例：0 は女性、1 は男性)
  id_number varchar(18) NOT NULL,          -- 身分証番号は最大 18 文字と仮定する
  home_address varchar(255) NOT NULL,      -- 自宅住所は最大 255 文字と仮定する
  office_address varchar(255) NOT NULL,    -- 会社住所は最大 255 文字と仮定する
  age int NOT NULL                         -- 年齢は int 型で保存する
);
```

## データテーブルのパーティション選択

パーティション技術により、大きなテーブルをより小さく、管理しやすい複数のサブテーブルに分割することで、クエリとデータ管理の両面で大きなメリットをもたらします。パーティションは通常、時間やリージョンなど、データの特定のフィールドに基づいて行われます。

### パーティションシナリオ

+ **データ量が非常に多い**：データテーブルのレコード数が億単位、あるいはそれ以上に達すると、単一テーブル操作はクエリのパフォーマンス低下を引き起こし、データベースのリソースボトルネックに繋がる可能性があります。
+ **クエリが特定のフィールドに依存する頻度が高い**：例えば、時間フィールドはよく使われるクエリ条件の 1 つであり、時間によるパーティション化によって、時間関連のクエリの効率を向上させることができます。

### パーティション戦略選択

+ **Range パーティション**：時間範囲でパーティション化するのが適しており、特にデータが時間順に生成され、通常時間でフィルタリングされる場合に適しています。
+ **Hash パーティション**：ハッシュアルゴリズムを用いてデータを複数のパーティションに均等に分散させる方法で、明確なクエリパターンが存在しないシナリオに適しています。
+ **List パーティション**：離散的なデータに適しており、例えば地域ごとにパーティションを分ける場合に用いられます。

AP シナリオでは、通常、複数のディメンションの分析クエリが関係します。もし、どのディメンションでもデータをパーティション化できず、かつ各クエリに適用できない場合は、パーティション化によってデータを複数のマシンに分散し、分散ノードの計算能力を活用する必要があります。そのような場合は、以下のようにパーティションキーを選択して Hash パーティション化を行い、ユーザーデータをできるだけ均等に分散させることができます：

+ NDV はパーティション数よりもはるかに大きいです。
+ この列のデータに偏りはない、もしくはごくわずかな偏りがあるのみです。例：取引 ID、ユーザー ID、または自動インクリメントなど。
+ 整数列と日時列を優先的に選択し、その後 varchar/char を検討します。
+ 高頻度で出現するクエリ条件のフィールドを優先的に選択することで、パーティションプルーニングを容易にします。

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL
)
PARTITION BY HASH(user_id) PARTITIONS 128;
```

分散型データベースでは、複数のテーブルがパーティション分割されているため、データが異なるマシンに分散される可能性があります。そのため、Join クエリなどの複雑な操作を実行する場合、マシン間の通信が必要になります。テーブルグループ機能を利用することで、マシン間アクセスによるクエリのパフォーマンス低下を回避できます。

sharding プロパティが ADAPTIVE のテーブルグループ tg1 と、パーティションテーブル customer と sales を 2 つ作成します。2 つのパーティションテーブルを結合する際に、結合条件にパーティションキーを含む結合条件が含まれる場合、Partition Wise Join を使用してパフォーマンスを向上させることができます。

```sql
CREATE TABLEGROUP tg1 SHARDING = 'ADAPTIVE';

-- 顧客情報テーブル
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL)
  TABLEGROUP = tg1
  PARTITION BY HASH(user_id) PARTITIONS 128;
-- 取引テーブル
CREATE TABLE sales (
  order_id INT,
  user_id INT primary key,
  item_id INT,
  item_count INT)
  TABLEGROUP = tg1
  PARTITION BY HASH(user_id) PARTITIONS 128;


SELECT * FROM customer, sales where customer.user_id = sales.user_id;
```

ビジネスデータの量が非常に多く、かつクエリの特性が明確である場合は、サブパーティションを作成することで、パーティションプルーニング機能をさらに活用し、クエリの高速化を図ることができます。AP クエリの特性として、通常は直近の 1 日分または 1 か月分のデータを対象にした時間プロパティを持つクエリが多いため、サブパーティションキーには、時間タイプのフィールドまたは時間関数を選択することを推奨します。また、範囲クエリを容易にするために、range パーティションを選択します。

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    -- プライマリキーはすべてのパーティションキー (user_id と age) を含みます
    PRIMARY KEY (user_id, age, login_time)
)
-- プライマリパーティション：user_id に基づいてハッシュ分散する
PARTITION BY HASH(user_id)
PARTITIONS 128
SUBPARTITION BY RANGE(age)
SUBPARTITION TEMPLATE (
    -- パーティションの例：年齢層別に分類する
    SUBPARTITION p_youth VALUES LESS THAN (25),      -- 年齢 < 25
    SUBPARTITION p_adult VALUES LESS THAN (40),      -- 25 ≤ age <40
    SUBPARTITION p_middle_aged VALUES LESS THAN (60),-- 40 ≤ age <60
    SUBPARTITION p_senior VALUES LESS THAN (MAXVALUE) -- 60 歳以上
);
```

## プライマリキー設計

プライマリキー設計は、リレーショナルデータベースのテーブル設計におけるコア部分であり、OceanBase では、プライマリキーがデータの一意性を保証するだけでなく、データがプライマリキー順にソートされるため、範囲指定のクエリにおいてもプライマリキーを活用することで、パフォーマンスを最適化することができます。異なるプライマリキー設計プランは、さまざまなビジネスのシナリオに適しています。

### プライマリキーを追加するシナリオ

+ **データの一意性を保証する**：テーブル内のデータにおいて、各レコードの一意性を保証する必要がある場合、プライマリキーを設計する必要があります。
+ **クエリ効率の向上**：プライマリキーは、オプティマイザーがより効率的なクエリプランを生成するのに役立ちます。特に、データクエリがプライマリキーに依存する場合、クエリで必ず指定されるフィールドをプライマリキーフィールドとして設定することを推奨します。これにより、プライマリキーを利用してクエリのパフォーマンスを向上させることができます。

```sql
CREATE TABLE customer (
    user_id BIGINT NOT NULL,
    login_time TIMESTAMP NOT NULL,
    customer_name VARCHAR(100) NOT NULL,
    phone_num BIGINT NOT NULL,
    city_name VARCHAR(50) NOT NULL,
    sex INT NOT NULL,
    id_number VARCHAR(18) NOT NULL,
    home_address VARCHAR(255) NOT NULL,
    office_address VARCHAR(255) NOT NULL,
    age INT NOT NULL,
    -- プライマリキーはすべてのパーティションキー (user_id と age) を含みます
    PRIMARY KEY (user_id, age, login_time)
)
-- プライマリパーティション：user_id に基づいてハッシュ分散する
PARTITION BY HASH(user_id)
PARTITIONS 128
SUBPARTITION BY RANGE(age)
SUBPARTITION TEMPLATE (
    -- パーティションの例：年齢層別に分類する
    SUBPARTITION p_youth VALUES LESS THAN (25),      -- 年齢 < 25
    SUBPARTITION p_adult VALUES LESS THAN (40),      -- 25 ≤ age <40
    SUBPARTITION p_middle_aged VALUES LESS THAN (60),-- 40 ≤ age <60
    SUBPARTITION p_senior VALUES LESS THAN (MAXVALUE) -- 60 歳以上
);
```

説明：

1. プライマリキーを持つテーブルのデータインポートは、プライマリキーなしテーブルよりもパフォーマンスが劣ります。これは、テーブルデータがプライマリキーに基づいてソートされるためです。
2. プライマリキーを持つパーティションテーブルのプライマリキーには、すべてのパーティションキーを含める必要があります。

## HTAP シナリオにおけるクエリ最適化

OceanBaseは、HTAP (混合トランザクションと分析処理) シナリオをサポートするためのさまざまな手段を提供し、トランザクション型 (TP) と分析型 (AP) の両方のビジネスのニーズを同時に満たすことができます。OceanBase は、データテーブルが行ストア、列ストア、および行列両方の冗長ストレージ形式をサポートするだけでなく、インデックステーブルもストレージ形式を指定できます。行ストアと列ストアの利点を組み合わせることで、それぞれのシナリオに対応できます。

列ストアインデックスの作成方法については、[MySQL モードでの列ストアインデックスの作成](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001973654) および [Oracle モードでの列ストアインデックスの作成](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001973637) を参照してください。

### 行ストアのベーステーブル + 列ストアのインデックス

適用シナリオ：トランザクション型のビジネスが主体であり、同時に一定の分析型クエリのニーズも存在するワイドテーブルに対して使用されます。  
最適化戦略：分析系クエリのパフォーマンスを向上させるために、列ストアインデックスを作成します。

+ メリット：一部の列に対してのみ冗長ストレージを行い、列ストア形式を採用しています。
+ デメリット：クエリステートメントに応じて適切なフィールドを特定し、列ストアインデックスを作成する必要があり、データ書き込み時にはインデックステーブルデータのメンテナンスも行うため、書き込みパフォーマンスは若干劣ります。

### 列ストアベースライン + 行ストアインデックス

適用シナリオ：分析型ビジネスを主体としつつ、効率的な単純クエリ (例えばポイントクエリ) への対応も必要とします。  
最適化戦略：インデックスを作成する際、テーブルへのアクセスを回避するために、カバリングインデックスを作成できます。

+ メリット：現在、一部の列データを冗長ストレージするのみで、列ストアテーブルを行ストアテーブルまたは行列両方の冗長テーブルにオンラインで変換することはサポートされていません。行ストアインデックスを追加することで、クエリのパフォーマンスを向上させることができます。
+ デメリット：クエリステートメントに応じて適切なフィールドを特定し、行ストアインデックスを作成する必要があり、データ書き込み時にはインデックステーブルデータのメンテナンスも行うため、書き込みパフォーマンスは若干劣ります。

### 行列両方冗長性ストレージ：行ストアベースライン + 列ストアベースライン

適用シナリオ：トランザクション型と分析型の両方のクエリを同時に扱う必要があり、さらにクエリのパターンも多様です。  
最適化戦略：ベースラインデータを 2 つ冗長ストレージし、システムはクエリの特性に基づいて適切な実行計画を生成できます。クエリのロジックではデフォルトで範囲スキャンを行い、列ストアモードで実行されます。ポイントクエリは行ストアモードにフォールバックします。

+ メリット：ビジネスのクエリ特性を分析する必要はなく、分析系クエリの結果は強整合性を持っています。
+ デメリット：より多くのディスク容量を消費し、実行計画が不正確になる可能性があります。

### 列ストアレプリカ：2F1A1C

適用シナリオ：典型的な HTAP ビジネスでは、分析型クエリがトランザクション型ビジネスに影響を与えることを避けつつ、分析クエリの結果は弱整合性の読み取りでも許容されます。  
最適化戦略：列ストアレプリカの分離特性を利用することで、AP/TP ビジネスが互いに影響することなく、ビジネスのクエリを実行できます。

+ メリット：
    1. マルチレプリカによる冗長なデータを保存しないことで、ディスク容量の使用量を削減できます。
    2. AP/TP ビジネスは相互に隔離されています。
    3. データ書き込みのパフォーマンスへの影響はありません。
+ デメリット：
    1. 列ストアレプリカは弱整合性の読み取りを行います。
    2. 独立したアクセスエントリーが必要です。
