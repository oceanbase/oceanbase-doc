# スムーズなスケーリングの適用例

RTに高度に依存する一部の業務では、テナントのスケーリングを実行する際に、ログストリームのリーダーが存在するノードで実行されるロードバランシング操作を厳しく制限する必要があります。これらのロードバランシング操作には、Transferタスク、ログストリームレプリカの移行複製、リーダーのフェイルオーバーなどが含まれます。このような場合、異種ゾーンを利用することで、ビジネスのピーク時にリーダーのフェイルオーバーやリーダーレプリカの移行が発生するのを回避し、スケーリングプロセス全体をよりスムーズにすることができます。

## 制限事項

OceanBaseデータベースV4.2.5では、テナントの異種ゾーンモードがV4.2.5 BP5バージョンからサポートされています。

## 注意事項

原則として、スケーリングやロールバック操作を実行する際には、`UNIT_NUM` の数が変更されるゾーンのみで移行コピーが発生し、他のゾーンではログストリームの移行コピーは行われず、ローカル転送のみが行われます。ただし、スケーリング操作を実行する前にテナントが不均衡な状態にある場合、例えばシステムがパーティションの均衡化を行っている場合や、前のスケーリングタスクが完了する前に新たなスケーリングタスクが開始された場合、システムは他のゾーンへのログストリームの移行を保証できません。

## シナリオ1：新しいゾーンを追加してスケーリングを行う

テナントの `PRIMARY_ZONE` が分散されており、単一のゾーンに集中できない場合、スムーズなスケーリングを実現するためには、ローカリティ変更という方法を用いる必要があります。具体的には、まずスケールアップまたはスケールダウン後の新しいゾーンを追加し、その後ローカリティ変更によって新しいゾーン上にレプリカを追加します。この補完プロセスにより、均等なバランスで完了させることが可能です。

以下では、スケールアップを例に説明します。

### シナリオ情報

現在、テナントtenant1があり、そのローカリティは`F@zone1、F@zone2、A`で、`PRIMARY_ZONE`は`zone1,zone2`です。テナントにはリソースプール`pool`があり、`zone1`と`zone2`に分散しており、`UNIT_NUM`は2です（つまり`UNIT_NUM`の設定は2:2です）。

<!-- ![拡張前](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-1-1-new.png) -->

現在、テナントのリソースプールの`UNIT_NUM`を4:4に拡張する必要があります。

### 手順

1. `root`ユーザーでクラスタの`sys`テナントにログインします。

2. パラメータ`enable_ls_leader_balance`を無効にします。

   テナントレベルのパラメータ[enable_ls_leader_balance](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2760.enable_ls_leader_balance.md)は、ログストリームリーダーのバランシングを有効にするスイッチです。自動ロードバランシングの総合スイッチであるenable_rebalanceが有効な場合、このパラメータでログストリームリーダーの自動バランシングを個別に制御できます。デフォルト値は`True`であり、ログストリームリーダーの自動バランシングがデフォルトで有効であることを示しています。

   ```shell
   obclient> ALTER SYSTEM SET enable_ls_leader_balance = False TENANT = 'tenant1';
   ```

3. 4ノードのゾーンを2つ追加し、新しいゾーンにテナント用のリソースを追加します。

   1. [ゾーンの追加](../../../100.cluster-management/300.common-cluster-operations/800.add-a-zone.md)を参照して、クラスタにそれぞれzone3、zone4を追加します。

   2. [ノードの追加](../../../100.cluster-management/300.common-cluster-operations/400.add-a-node.md)を参照して、新しく追加したzone3、zone4にそれぞれ4つのノードを追加します。

   3. 新しく追加したZone3、Zone4に、元のUnit仕様と同じで`UNIT_NUM`が4のリソースプール`pool2`を作成します。

      ```shell
      obclient [oceanbase]> CREATE RESOURCE POOL pool2 UNIT='unit_name', UNIT_NUM = 4, ZONE_LIST=('zone3','zone4');
      ```

      ここで、`unit_name`は実際のUnit名に置き換える必要があります。

   4. テナントのリソースプールを変更し、新しく追加したリソースプール`pool2`をテナントに割り当てます。

      ```shell
      obclient> ALTER TENANT tenant1 RESOURCE_POOL_LIST =('pool','pool2');
      ```

      実行が成功すると、テナントの`zone1`、`zone2`、`zone3`、`zone4`上の`UNIT_NUM`はそれぞれ2:2:4:4となります。

4. テナントのローカリティを変更し、新しく追加した`zone3`、`zone4`をローカリティに追加します。

   ローカリティを`F@zone1，F@zone2，A`から`F@zone1，F@zone2，F@zone3，F@zone4，A`に変更します。ステートメントは以下のとおりです。

   ```shell
   obclient> ALTER TENANT tenant1 LOCALITY="F@zone1，F@zone2，F@zone3，F@zone4，A";
   ```

   ステートメントの実行が成功すると、システムは新しく追加されたUnit上にログストリームレプリカを自動的に補完し、各Unit上に均等に分散します。このプロセスでは新しく追加されるのはすべてフォロワーレプリカであるため、リーダー切り替えは発生しません。

   <!-- この時点で、ユーザーのログストリームの分布状況は以下の図のとおりです。 -->

   <!-- ![新規ゾーン追加後の拡張](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-1-2-new.png) -->

5. テナントの`PRIMARY_ZONE`を新しく追加した`zone3`、`zone4`に変更し、パラメータ`enable_ls_leader_balance`を有効にします。

   `PRIMARY_ZONE`を`zone1,zone2`から`zone3,zone4`に変更します。ステートメントは以下のとおりです。

   ```shell
   obclient> ALTER TENANT tenant1 PRIMARY_ZONE='zone3,zone4';
   ```

   パラメータ`enable_ls_leader_balance`を有効にします。ステートメントは以下のとおりです：

   ```shell
   obclient> ALTER SYSTEM SET enable_ls_leader_balance = True TENANT = 'tenant1';
   ```

   上記のステートメントがすべて実行されると、各ログストリームは自動的にリーダーレプリカを`zone3`、`zone4`に切り替えます。ログストリームの`PRIMARY_ZONE`のみを変更する場合、プロセスは迅速で、影響範囲もコントロール可能です。

6. 再びテナントのローカリティを変更し、ローカリティから`zone1`、`zone2`を削除します。

   ローカリティを`F@zone1，F@zone2，F@zone3，F@zone4，A`から`F@zone3，F@zone4，A`に変更します。ステートメントは以下のとおりです。

   ```shell
   obclient> ALTER TENANT tenant1 locality="F@zone3，F@zone4，A";
   ```

   ステートメントの実行が成功すると、`zone1`、`zone2`のログストリームレプリカは削除され、`zone3`、`zone4`には影響しません。

7. テナントのリソースプールを変更し、元のリソースプール`pool`を削除し、新しく追加したリソースプール`pool2`のみを保持します。

   ```shell
   obclient> ALTER TENANT tenant1 RESOURCE_POOL_LIST =('pool2');
   ```

   元のリソースプール`pool`がテナントから削除されると、元の2ノードの`zone1`、`zone2`も削除できます。

   操作完了後、現在のテナントには4ノード(`UNIT_NUM`が4)の`zone3`、`zone4`のみが残り、拡張が完了します。

## シナリオ2：ローカルでのスケーリング

`PRIMARY_ZONE`に集中している一部のテナントでは、ローカルでのスケーリングを行うことができます。ローカルでのスケーリングは、フォロワー・レプリカが存在するゾーンのみを操作することを保証します。

以下は拡張を例として説明します。

### シナリオ情報

現在、テナントtenant1があり、そのローカリティは`F@zone1、F@zone2、A`で、`PRIMARY_ZONE`は`zone1`です。テナントにはリソースプール`pool`があり、`zone1`と`zone2`に分散しており、`UNIT_NUM`は2です（つまり`UNIT_NUM`の設定は2:2です）。

<!-- ![ローカル拡張前](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-image2-1-new.png) -->

現在、テナントのリソースプールの`UNIT_NUM`を4:4に拡張する必要があります。

### 手順

1. `root`ユーザーでクラスタの`sys`テナントにログインします。

2. テナントのリソースプールを`zone1`の`pool1`と`zone2`の`pool2`に分割します。

   ```shell
   obclient> ALTER RESOURCE POOL pool SPLIT INTO ('pool1','pool2') ON ('zone1','zone2');
   ```

   リソースプールの分割の詳細な操作と説明については、[リソースプールのコンパクションと分割](../1500.resource-pool-management/500.merge-and-splitting-resource-pools.md)を参照してください。

3. 分割されたリソースプール`pool2`の`UNIT_NUM`を4に変更します。

   ```shell
   obclient> ALTER RESOURCE POOL pool2 UNIT_NUM = 4;
   ```

   ステートメントの実行が成功すると、ログストリームは自動的に分割され、`zone1`上の4つのUnitに分散されます。

   <!-- ![zone2のUNIT_NUM拡張](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-image2-2-new.png) -->

4. テナントの`PRIMARY_ZONE`を`zone2`に変更します。

   ```shell
   obclient> ALTER TENANT tenant1 PRIMARY_ZONE='zone2';
   ```

5. 分割されたリソースプール`pool1`の`UNIT_NUM`を4に変更します。

   ```shell
   obclient> ALTER RESOURCE POOL pool1 UNIT_NUM = 4;
   ```

   ステートメントの実行が成功すると、システム内部での均衡が開始され、均衡が完了すると拡張が完了します。

   <!-- ![zone1のUNIT_NUM拡張](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/management/smooth-scaling-out-image2-3-new.png) -->

6. （オプション）リーダー・レプリカを引き続き`zone1`に集中させたい場合は、テナントの`PRIMARY_ZONE`を再び`zone1`に変更できます。

   ```shell
   obclient> ALTER TENANT tenant1 PRIMARY_ZONE='zone1';
   ```
