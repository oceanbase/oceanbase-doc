# Unit Numberの調整によるテナントのスケーリング

テナントのスケーリングとは、本質的にはテナントのサービス能力、すなわち計算能力やストレージ容量を向上または低下させることです。これは、単一ノードのサービス能力を向上させることで達成することも、サービスノードを追加することで達成することも可能です。本記事では、Unit Numberを変更することでサービスノードを増減し、テナント全体のサービス能力を向上または低下させ、テナントのスケールアップまたはスケールダウンを実現する方法について説明します。

Unit Numberの変更には、Unit Numberを大きくする場合と小さくする場合が含まれます。

## 背景情報

V4.x以前のバージョンでは、OceanBaseデータベースはテナントの同構成ゾーンモードのみをサポートしており、テナント内の各ゾーンにおけるユニット数が一定であることが求められました。また、各ゾーンのユニットを一元管理するため、システムではユニットグループという仕組みが導入されました。これにより、異なるゾーン間でも同一の番号(`UNIT_GROUP_ID`)を持つユニットは同一のユニットグループに属することになります。同構成ゾーンモードのテナントにおいて、ユニット数を増減させる場合、実質的にはユニットグループ単位でユニットの作成・削除が行われることになります。

V4.2.5バージョンから、OceanBaseデータベースはV4.2.5 BP5以降のバージョンで、テナントの異構成ゾーンモードをサポートするようになりました。異構成ゾーンモードでは、テナント内の各ゾーンの`UNIT_NUM`は同一でも異なっても構いませんが、同一テナント内のすべてのゾーンで使用可能な`UNIT_NUM`は最大でも2種類までです。ログストリームの分散はもはやユニットグループに結びつけられなくなり、各ゾーンのレプリカは対称的なユニットに限定される必要もなくなりました。異構成ゾーンモードのテナントにおいては、テナント全体のユニット数を一括で増減させるほか、複数のリソースプールが存在する場合には、特定のリソースプールのユニット数を個別に増減させることで、リソースプール単位でのスケーリングが可能になりました。

<main id="notice" type='notice'>
<h4>注意</h4>
<p>通常、既存のテナントやアップグレードされたテナントは、デフォルトで同構成ゾーンモードに設定されています。異構成ゾーンモードを有効にするには、テナントレベルの構成パラメータ<code>zone_deploy_mode</code>の値を<code>hetero</code>(異構成ゾーンモード)に変更する必要があります。一度変更すると、<code>homo</code>(同構成ゾーンモード)に戻すことはできません。</p>
</main>

## 前提条件

テナントのスケーリングアップおよびスケーリングダウン操作を実行する前に、以下の操作が必要です：

* テナント内のロードバランシングポリシーを設定する

  テナント内のロードバランシングポリシーは、テナントレベルの構成パラメータ `enable_rebalance` と `enable_transfer` によって共同で制御されます。

  パラメータ `enable_rebalance` は、システムテナントではテナント間のロードバランシングを行うかどうかを制御し、ユーザーテナントではテナント内のロードバランシングを行うかどうかを制御します。デフォルト値は `true` であり、設定後はOBServerノードの再起動なしで即時に反映されます。

  パラメータ `enable_transfer` は、テナント内のTransfer機能を有効にするかどうかを制御します。デフォルト値は `true` であり、設定後はOBServerノードの再起動なしで即時に反映されます。その中で：

  * パラメータ `enable_rebalance` の値が `false` の場合、パラメータ `enable_transfer` の値が `true` であっても `false` であっても、システムは自動ロードバランシングを行いません。

  * パラメータ `enable_rebalance` の値が `true` かつ `enable_transfer` の値も `true` の場合、テナントのスケーリングアップまたはスケーリングダウン操作時に、システムが自動的にパーティションの分布を調整し、ロードバランシングを実現します。

  * パラメータ `enable_rebalance` の値が `true` かつ `enable_transfer` の値が `false` の場合、テナントのスケーリングアップまたはスケーリングダウン操作時に、システムはTransfer操作を開始できず、ログストリーム移行による限られた均衡しか実現できません。

   詳細な設定方法は以下の通りです：

  * システムテナントで指定テナントのロードバランシングポリシーを設定する

    * システムテナントで指定テナントのテナント内ロードバランシングとテナント内Transfer機能を有効にする

       ```sql
       ALTER SYSTEM SET enable_rebalance = true TENANT = 'tenant_name';
       ```

       ```sql
       ALTER SYSTEM SET enable_transfer = true TENANT = 'tenant_name';
       ```

       上記のステートメントは、指定テナントのパラメータ `enable_rebalance` と `enable_transfer` の値を `true` に設定することを示します。

    * システムテナントで、`sys` テナントおよびMetaテナントを除くすべてのユーザーテナントのテナント内ロードバランシングとテナント内Transfer機能を有効にする

       ```sql
       ALTER SYSTEM SET enable_rebalance = true TENANT = all_user;
       ```

       ```sql
       ALTER SYSTEM SET enable_transfer = true TENANT = all_user;
       ```

       または

       ```sql
       ALTER SYSTEM SET enable_rebalance = true TENANT = all;
       ```

       ```sql
       ALTER SYSTEM SET enable_transfer = true TENANT = all;
       ```

       上記のステートメントは、すべてのユーザーテナントのパラメータ `enable_rebalance` と `enable_transfer` の値を `true` に設定することを示します。

       <main id="notice" type='explain'>
       <h4>説明</h4>
       <p>OceanBaseデータベースはV4.2.1バージョンから、<code>TENANT = all_user</code> と <code>TENANT = all</code> は同じ意味を持ちます。有効範囲がすべてのユーザーテナントの場合、<code>TENANT = all_user</code> を使用することを推奨します。<code>TENANT = all</code> は今後廃止され、使用されなくなります。</p>
       </main>

  * ユーザーテナントで自身のテナントのロードバランシングポリシーを設定する

    :::tab
    タブ MySQLモード

    MySQLテナントで、このテナントのテナント内ロードバランシングとテナント下のTransfer機能を有効にするステートメントは以下のとおりです：

    ```sql
    ALTER SYSTEM SET enable_rebalance = true;
    ```

    ```sql
    ALTER SYSTEM SET enable_transfer = true;
    ```

    tab Oracleモード

    Oracleテナントで、そのテナント内のロードバランシングおよびテナント内のTransfer機能を有効にするステートメントは以下のとおりです：

    ```sql
    ALTER SYSTEM SET enable_rebalance = 'true';
    ```

    ```sql
    ALTER SYSTEM SET enable_transfer = 'true';
    ```

    :::

  パラメータ `enable_rebalance` および `enable_transfer` の詳細については、[enable_rebalance](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2900.enable_rebalance.md) および [enable_transfer](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3100.enable_transfer.md) を参照してください。

* アイドル状態のリソースプールは占有されているリソースとしてカウントされるため、スケーリングアップ前に、テナントが削除された場合は、対応するリソースプールも一緒に削除してリソースを解放することを推奨します。

  リソースプールの削除に関する操作については、[リソースプールの削除](../1500.resource-pool-management/600.delete-resource-pool.md) を参照してください。

* テナントのスケーリングダウンを行う前に、テナントが使用中のメモリを解放するために、一度デフラストレーションを行うことを推奨します。

  デフラストレーションを手動でトリガーする操作については、[デフラストレーションの手動トリガー](../../../../700.reference/200.system-management/500.manage-data-storage/100.dump-management/300.trigger-dump-manually.md) を参照してください。

## 注意事項

ユニット数を調整してテナントのスケーリングを行う際には、以下の点に注意する必要があります。

* スケーリング中は、テナントのローカリティを変更することを禁止します。
* スケーリング中は、テナントのリソースプールの`ZONE_LIST`範囲を拡大することを禁止します。
* スケーリング中は、テナントに新しいリソースプールを追加することを禁止します。
* スケーリング中は、リソースプールのメジャーコンパクションを実行することを禁止します。
* スケーリング中は、`DELETING`状態のユニットに対して移行操作を実行することを禁止します。

## ユニット番号の増加

### テナントのすべてのリソースプールのユニット数を増やす

同一構成ゾーンモードのテナントまたは異構成ゾーンモードのテナントは、`ALTER RESOURCE TENANT` ステートメントを使用して、テナントのすべてのリソースプールのユニット数を一括で増やすことができます。以下では、テナント `mysql001` のすべてのリソースプールのユニット数を増やす例を挙げて操作方法を説明します。

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

   ```shell
   obclient -h172.30.xxx.xxx -P2883 -uroot@sys#obdemo -pxxxx -A
   ```

2. `oceanbase` データベースに移動します。

   ```shell
   obclient> use oceanbase;
   ```

3. テナント `mysql001` の情報を確認し、その `TENANT_ID` を取得します。

   ```shell
   obclient> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, PRIMARY_ZONE, LOCALITY, TENANT_ROLE, UNIT_NUM, ZONE_UNIT_NUM_LIST FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME = 'mysql001';
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE       | LOCALITY                                    | TENANT_ROLE | UNIT_NUM | ZONE_UNIT_NUM_LIST      |
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   |      1006 | mysql001    | USER        | zone1;zone2;zone3  | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 | PRIMARY     |        1 | zone1:1,zone2:1,zone3:1 |
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   1 row in set
   ```

   クエリ結果によると、テナントの `TENANT_ID` は1006であり、このテナントの各ゾーン上のユニット数は1:1:1です。

4. テナント `mysql001` が保有するユニットを確認します。

   ```shell
   obclient> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   | UNIT_ID | TENANT_ID | STATUS | RESOURCE_POOL_ID | UNIT_GROUP_ID | ZONE  | UNIT_CONFIG_ID |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   |    1013 |      1006 | ACTIVE |             1002 |          1023 | zone2 |           1001 |
   |    1014 |      1006 | ACTIVE |             1001 |          1023 | zone1 |           1001 |
   |    1015 |      1006 | ACTIVE |             1003 |          1023 | zone3 |           1001 |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   3 rows in set
   ```

   クエリ結果から、テナント `mysql001` は各ゾーンに1つずつユニットを持ち、これら3つのユニットに対応する `UNIT_GROUP_ID` が同じであることがわかります。

5. テナント `mysql001` の `UNIT_NUM` を2に変更します。

   ```shell
   obclient> ALTER RESOURCE TENANT mysql001 UNIT_NUM = 2;
   ```

6. コマンドの実行が成功した後、現在のユニットの状態を確認します。

   ```shell
   obclient> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   | UNIT_ID | TENANT_ID | STATUS | RESOURCE_POOL_ID | UNIT_GROUP_ID | ZONE  | UNIT_CONFIG_ID |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   |    1013 |      1006 | ACTIVE |             1002 |          1024 | zone2 |           1001 |
   |    1014 |      1006 | ACTIVE |             1001 |          1024 | zone1 |           1001 |
   |    1015 |      1006 | ACTIVE |             1003 |          1024 | zone3 |           1001 |
   |    1025 |      1006 | ADDING |             1001 |          1025 | zone1 |           1001 |
   |    1026 |      1006 | ADDING |             1002 |          1025 | zone2 |           1001 |
   |    1027 |      1006 | ADDING |             1003 |          1025 | zone3 |           1001 |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   6 rows in set
   ```

   新規追加されるユニットはすべて `ADDING` 状態であり、内部の均衡処理が完了すると、ユニットの状態は `ADDING` 状態から `ACTIVE` 状態に変わります。

   <main id="notice" type='notice'>
   <h4>注意</h4>
   <ul><li>OceanBaseデータベースの以前のバージョンでは、<code>UNIT_NUM</code> の拡張は同期プロセスでしたが、V4.2.5 BP5バージョン以降では、<code>UNIT_NUM</code> の拡張は非同期プロセスに変更され、新規追加されるユニットは <code>ADDING</code> 状態になります。</li>
   <li>拡張プロセス中（新規追加されるユニットがまだ <code>ADDING</code> 状態の場合）、ロールバック操作がサポートされます。<p>例えば、この例では、<code>ALTER RESOURCE TENANT mysql001 UNIT_NUM = 1;</code> ステートメントを実行して <code>UNIT_NUM</code> を元の値に戻すことができます。ロールバック時、元の <code>ADDING</code> 状態のユニットは直接 <code>DELETING</code> 状態に変わります。ただし、ロールバック操作を実行する際、指定された UNIT_GROUP を削除する方法でロールバックすることはサポートされておらず、システムは自動的に <code>ADDING</code> 状態のユニットを選択して削除します。</p></li>
   <li>拡張プロセス終了前は、ロールバック操作のみが許可され、<code>UNIT_NUM</code> を他の値に変更することは禁止されています。</li></ul>
   </main>

7. ユニット数を増やすタスクの実行状態を確認します。

   ```shell
   obclient> SELECT * FROM oceanbase.DBA_OB_TENANT_JOBS WHERE JOB_TYPE='ALTER_RESOURCE_TENANT_UNIT_NUM' AND TENANT_ID=1006;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +--------+--------------------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+-----------------------------------------------------------+-------------------+--------------+-------------+
   | JOB_ID | JOB_TYPE                       | JOB_STATUS | RESULT_CODE | PROGRESS | START_TIME                 | MODIFY_TIME                | TENANT_ID | SQL_TEXT                                                  | EXTRA_INFO        | RS_SVR_IP    | RS_SVR_PORT |
   +--------+--------------------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+-----------------------------------------------------------+-------------------+--------------+-------------+
   |     26 | ALTER_RESOURCE_TENANT_UNIT_NUM | SUCCESS    |           0 |      100 | 2025-06-18 10:10:19.430962 | 2025-06-18 10:10:54.229794 |      1006 | ALTER RESOURCE TENANT mysql001 UNIT_NUM = 2               | new unit num: '2' | 6.xx.xxx.xxx |       29700 |
   +--------+--------------------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+-----------------------------------------------------------+-------------------+--------------+-------------+
   1 row in set
   ```

   クエリ結果において、以下のフィールドに基づいて対応するタスクレコードを見つけます：

   * `START_TIME`：タスクの開始時間。
   * `SQL_TEXT`：タスクに対応するSQLステートメント。
   * `EXTRA_INFO`：変更前後のユニット数。

   対応する変更レコードにおいて、`JOB_STATUS` の値が `SUCCESS` の場合、ユニット数を増やすタスクの実行が成功したことを示します。

   ビュー `DBA_OB_TENANT_JOBS` の詳細なフィールドの説明については、[DBA_OB_TENANT_JOBS](../../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/22200.o-dba_ob_tenants-of-sys-tenant.md)を参照してください。

8. テナント `mysql001` の変更後のユニットを確認します。

   ```shell
   obclient> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   | UNIT_ID | TENANT_ID | STATUS | RESOURCE_POOL_ID | UNIT_GROUP_ID | ZONE  | UNIT_CONFIG_ID |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   |    1013 |      1006 | ACTIVE |             1002 |          1024 | zone2 |           1001 |
   |    1014 |      1006 | ACTIVE |             1001 |          1024 | zone1 |           1001 |
   |    1015 |      1006 | ACTIVE |             1003 |          1024 | zone3 |           1001 |
   |    1025 |      1006 | ACTIVE |             1001 |          1025 | zone1 |           1001 |
   |    1026 |      1006 | ACTIVE |             1002 |          1025 | zone2 |           1001 |
   |    1027 |      1006 | ACTIVE |             1003 |          1025 | zone3 |           1001 |
   +---------+-----------+--------+------------------+---------------+-------+----------------+
   6 rows in set
   ```

上記の例により、テナント `mysql001` のすべてのリソースプールのユニット数を1から2に変更します。変更前はテナントが各ゾーンに1つのユニットを持ち、変更後はテナントが各ゾーンに2つのユニットを持つことで、テナントの拡張が実現されました。

### テナントの単一リソースプールのユニット数を増やす

異種ゾーンモードのテナントに複数のリソースプールがある場合、`ALTER RESOURCE POOL` ステートメントを使用して、特定のリソースプールのユニット数を個別に増やすことができます。同種ゾーンモードのテナントではこの方法はサポートされていません。

以下は、テナント `mysql001` のリソースプール `pool2` のユニット数を増やす例です。

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

   ```shell
   obclient -h172.30.xxx.xxx -P2883 -uroot@sys#obdemo -pxxxx -A
   ```

2. `oceanbase` データベースに移動します。

   ```shell
   obclient> use oceanbase;
   ```

3. テナント `mysql001` の情報を確認し、その `TENANT_ID` を取得します。

   ```shell
   obclient> SELECT TENANT_ID, TENANT_NAME, TENANT_TYPE, PRIMARY_ZONE, LOCALITY, TENANT_ROLE, UNIT_NUM, ZONE_UNIT_NUM_LIST FROM oceanbase.DBA_OB_TENANTS WHERE TENANT_NAME = 'mysql001';
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE       | LOCALITY                                    | TENANT_ROLE | UNIT_NUM | ZONE_UNIT_NUM_LIST      |
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   |      1006 | mysql001    | USER        | zone1;zone2;zone3  | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 | PRIMARY     |        2 | zone1:2,zone2:2,zone3:2 |
   +-----------+-------------+-------------+--------------------+---------------------------------------------+-------------+----------+-------------------------+
   1 row in set
   ```

   クエリ結果によると、テナントの `TENANT_ID` は1006であり、各ゾーン上のユニット数は2:2:2です。

4. 現在のテナントのリソース構成情報を確認します。

   ```shell
   obclient> SELECT c.TENANT_ID, e.TENANT_NAME, concat(c.NAME, ': ', d.NAME) `pool:conf`,c.ZONE_LIST, concat(c.UNIT_COUNT, ' unit: ', d.min_cpu, 'C/', ROUND(d.MEMORY_SIZE/1024/1024/1024,0), "G") unit_info
                FROM oceanbase.DBA_OB_RESOURCE_POOLS c, oceanbase.DBA_OB_UNIT_CONFIGS d, oceanbase.DBA_OB_TENANTS e
                WHERE c.UNIT_CONFIG_ID=d.UNIT_CONFIG_ID AND c.TENANT_ID=e.TENANT_ID AND c.TENANT_ID=1006;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+------------------+-----------+---------------+
   | TENANT_ID | TENANT_NAME | pool:conf        | ZONE_LIST | unit_info     |
   +-----------+-------------+------------------+-----------+---------------+
   |      1006 | mysql001    | pool3: test_unit |   zone3   | 2 unit: 1C/8G |
   |      1006 | mysql001    | pool2: test_unit |   zone2   | 2 unit: 1C/8G |
   |      1006 | mysql001    | pool1: test_unit |   zone1   | 2 unit: 1C/8G |
   +-----------+-------------+------------------+-----------+---------------+
   3 rows in set
   ```

   クエリ結果によると、テナント `mysql001` には `pool1`、`pool2`、`pool3` の合計3つのリソースプールがあり、それぞれ `zone1`、`zone2`、`zone3` に配置されています。

5. 実際のニーズに応じて、テナント `mysql001` のリソースプール `pool2` の `UNIT_NUM` を3に変更します。

   ```shell
   obclient> ALTER RESOURCE POOL pool2 UNIT_NUM = 3;
   ```

6. コマンド実行が成功した後、現在のユニットの状態を確認します。

   ```shell
   obclient> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

## ユニット数を小さくする

### 注意事項

テナントのUnit Numberを小さくする前に、GTS専用が有効になっているかどうか確認する必要があります。GTS専用機能は、テナントレベルの構成パラメータ[enable_gts_standalone](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2550.enable_gts_standalone.md)で制御され、デフォルト値は`False`であり、無効な状態です。

GTS専用が有効になっている場合、以下の点に注意する必要があります：

* GTS専用が有効になると、テナント内の各ゾーンの`UNIT_NUM`が2以上であることが求められます。テナントのいずれかのゾーンを`UNIT_NUM`が2未満にスケールダウンすると、システムエラーが発生します。

* 指定されたUNIT_LISTまたはUnit Groupを削除してUnit Numberを小さくする際、GTS専用のUnitまたはUnit Groupを削除するUnitを指定することはできません。そうしないと、システムエラーが発生します。

### テナントのすべてのリソースプールのUnit Numberを小さくする

      ```shell
      obclient> ALTER RESOURCE POOL pool2 UNIT_NUM = 1 DELETE UNIT=(1011);
      ```

7. コマンド実行が成功した後、現在のUnitの状態を確認します。

   ```shell
   obclient> SELECT UNIT_ID, TENANT_ID, STATUS, RESOURCE_POOL_ID, UNIT_GROUP_ID, ZONE, UNIT_CONFIG_ID FROM oceanbase.DBA_OB_UNITS WHERE TENANT_ID = 1006;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +---------+-----------+----------+------------------+---------------+-------+----------------+
   | UNIT_ID | TENANT_ID | STATUS   | RESOURCE_POOL_ID | UNIT_GROUP_ID | ZONE  | UNIT_CONFIG_ID |
   +---------+-----------+----------+------------------+---------------+-------+----------------+
   |    1006 |      1006 | ACTIVE   |             1003 |          1019 | zone3 |           1001 |
   |    1011 |      1006 | DELETING |             1002 |          1019 | zone2 |           1001 |
   |    1012 |      1006 | ACTIVE   |             1001 |          1019 | zone1 |           1001 |
   |    1013 |      1006 | ACTIVE   |             1002 |          1020 | zone2 |           1001 |
   |    1014 |      1006 | ACTIVE   |             1001 |          1020 | zone1 |           1001 |
   |    1015 |      1006 | ACTIVE   |             1003 |          1020 | zone3 |           1001 |
   +---------+-----------+----------+------------------+---------------+------+-----------------+
   6 rows in set
   ```

   削除待ちのユニットは `DELETING` 状態であることがわかります。

   <main id="notice" type='notice'>
   <h4>注意</h4>
   <ul><li>OceanBaseデータベースでは、<code>UNIT_NUM</code> の縮小は非同期プロセスです。縮小プロセス中（削除待ちのユニットが依然として <code>DELETING</code> 状態の場合）、ロールバック操作がサポートされます。<p>例えば、この例では <code>ALTER RESOURCE POOL pool2 UNIT_NUM = 2;</code> ステートメントを実行して <code>UNIT_NUM</code> を元の値に戻すことができます。ロールバック時、元の <code>DELETING</code> 状態のユニットは直接 <code>ADDING</code> 状態に変更されます。</p></li>
   <li>縮小プロセス中は、ロールバック操作のみがサポートされており、<code>UNIT_NUM</code> を他の値に変更することは禁止されています。</li></ul>
   </main>

8. Unit数を減らすタスクの実行状態を確認します。
