# テーブル単位のリカバリの実行

この記事では、主にテーブル単位のリカバリの方法について説明します。

## 制限

* ユーザーテーブルのみの復元がサポートされており、一時テーブル、ビュー、インデックスなどの個別復元はサポートされていません。

* テーブル復元のソーステナントとターゲットテナントの互換性は一致している必要があります。例えば、どちらもOracle互換テナント、またはどちらもMySQL互換テナントである必要があります。

* テーブルを復元する際には、指定したテーブル名がシステムに実際に保存されているテーブル名と一致している必要があります。例えば、Oracleモードのテナントでテーブル`test`を作成した場合、システム内部に実際に保存されているテーブル名は`TEST`です。そのため、テーブルを復元する際にはテーブル名として`TEST`を指定する必要があります。そうしない場合、システムはエラーを報告し、テーブルが存在しないことを示します。

* テナントレベルの復元でサポートされるバックアップデータのバージョンと同様に、テーブルレベルの復元でも現在は低バージョンのバックアップデータから同一バージョンまたはそれ以上のバージョンへのテーブル復元のみがサポートされており、同一バージョン内の小さなバージョン間での逆復元はサポートされていません。テナントレベルの復元でサポートされるバックアップデータのバージョンの詳細については、[復元前の準備](../600.restore-data/100.preparation-before-recovery.md)を参照してください。

* テーブルレベルの復元では、テーブルの復元に加えて、そのテーブルに関連付けられた多くの情報も復元されますが、一部の情報は復元されません。具体的に復元可能な情報については、このセクションの**復元されるスキーマ情報の説明**を参照してください。

## 前提条件

指定されたテーブルの復元プロセスでは補助テナントを使用するため、テーブル復元を行う前に、ターゲットテナントが属するクラスタ内で補助テナント用の必要なリソースプールを作成する必要があります。補助テナント用の必要なリソースプールを作成する詳細な操作については、[テーブルレベル復元前の準備](100.preparation-before-table-recovery.md)を参照してください。

## 手順

1. `root`ユーザーで、ターゲットテナントが存在するクラスタの`sys`テナントにログインします。

2. (オプション)指定されたテーブルを復元する際に使用されるバックアップデータに暗号化機能が設定されている場合は、バックアップセットの暗号化情報を設定する必要があります。

   バックアップの復元パスワードは、データバックアップ時にパスワードが追加された場合にのみ設定する必要があります。

   ```sql
   SET DECRYPTION IDENTIFIED BY 'password';
   ```

   ここで、`password`はバックアップ時に追加したパスワードに置き換える必要があります。フルバックアップと増分バックアップで設定されたパスワードが異なる場合は、複数のパスワードを入力し、パスワード間は英字のカンマで区切ります(フルバックアップのパスワードを先に、増分バックアップのパスワードを後に配置します)。

   フルバックアップと増分バックアップで設定されたパスワードが同じ場合の例：

   ```sql
   SET DECRYPTION IDENTIFIED BY '******';
   ```

   フルバックアップと増分バックアップで設定されたパスワードが異なる場合の例：

   ```sql
   SET DECRYPTION IDENTIFIED BY '******','******';
   ```

3. (オプション)テーブルレベルの復元並列度を設定します。

   * 単一テーブルの並列復元

      テーブルレベルの復元を実行する前に、構成パラメータ[recover_table_dop](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7815.recover_table_dop.md)を使用して並列度を設定できます。設定後、システムは以下の2つの段階でこの並列度を使用します：

      * メインテーブルデータ復元段階：システムはメインテーブルの各パーティションを複数のサブタスクに分割してパラレル実行します。
      * インデックス復元段階：システムは復元されたメインテーブルデータに基づいて、パラレル実行(Parallel Execution, PX)を利用してテーブルのインデックスを再構築します。

      構文は次のとおりです：

      ```sql
      -- tenant_name はターゲットテナントです
      ALTER SYSTEM SET recover_table_dop=INT_VALUE tenant=tenant_name;
      ```

   * 複数テーブルの並列復元 (オプション)

      複数テーブルのテーブルレベルの復元を実行する前に、構成パラメータ[recover_table_concurrency](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7810.recover_table_concurrency.md)を使用して並列度を設定できます。設定後、複数のテーブルが並列して復元タスクを実行でき、復元性能が向上します。

      構文は次のとおりです：

      ```sql
      -- tenant_name はターゲットテナントです
      ALTER SYSTEM SET recover_table_concurrency=INT_VALUE tenant=tenant_name;
      ```

   * テナント内の各observerノード上のメインテーブルデータ復元ワーカースレッド数の設定

      単一テーブルの並列度`recover_table_dop`と複数テーブルの並列度`recover_table_concurrency`を設定した後、テナント内の各observerノードの補完データワーカースレッド数も[ddl_thread_score](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/1950.ddl_thread_score.md)構成パラメータを使用して設定する必要があります。テーブルレベルの復元のテナント間テーブルエクスポート段階では、メインテーブルデータの復元はターゲットテナント上の特定のDAGスレッドに依存します。

      構文は次のとおりです：

      ```sql
      -- tenant_name はターゲットテナントです
      ALTER SYSTEM SET ddl_thread_score=INT_VALUE tenant=tenant_name;
      ```

      <main id="notice" type='notice'>
      <h4>注意</h4>
      <p>
      <ul>
        <li><b>物理復元補助テナント実行段階</b>では、<a href="../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/3500.ha_high_thread_score.md">ha_high_thread_score</a>構成パラメータを調整することで、復元の並列度を動的に調整できます。調整は即時に反映されます。補助テナント名は、テーブルレベルの復元のタスク進捗表<a href="../../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/10000.o-cdb_ob_recover_table_jobs-of-sys-tenant.md">CDB_OB_RECOVER_TABLE_JOBS</a>から確認できます。具体的な調整方法については、<a href="../600.restore-data/200.initiate-the-tenant-restore.md">物理復元</a>を参照してください。</li>
        <li><b>テナント間テーブルエクスポート段階</b>では、ターゲットテナントの<code>recover_table_concurrency</code>または<code>recover_table_dop</code>構成パラメータを調整することで、複数テーブル/単一テーブルの復元の並列度を動的に調整できます。調整は即時に反映されます。</li>
      </ul>
      </p>
      </main>

4. 以下のコマンドを実行して、指定されたテーブルを復元します。

   構文は次のとおりです：

   ```sql
   ALTER SYSTEM
   RECOVER TABLE table_name_list
   TO [TENANT [=]] dest_tenant_name
   FROM uri
   [UNTIL {TIME='timestamp'} | {SCN=scn} ]
   WITH 'restore_option'
   [WITH KEY FROM 'backup_key_path' ENCRYPTED BY 'password']
   [REMAP TABLE remap_table_name_list]
   [REMAP TABLEGROUP remap_tablegroup_list]
   [REMAP TABLESPACE remap_tablespace_list]
   [DESCRIPTION [=] description];
   ```

   パラメータの詳細については、[テーブルレベルの復元関連パラメータの紹介](600.parameters-of-the-table-recovery.md)を参照してください。

   `infodb`データベース内のテーブル`tbl1`と`tbl2`をターゲットテナントの`infodb`データベースに復元し、テーブル`tbl1`の名前を`newtbl`に変更し、テーブルが属するテーブルグループを`newtg1`にリダイレクトし、テーブルが属するテーブルスペースを`newts1`にリダイレクトする場合を想定します。例：

   ```sql
   ALTER SYSTEM
   RECOVER TABLE infodb.tbl1,infodb.tbl2
   TO TENANT oracle001
   FROM 'file:///data/nfs/backup/data,file:///data/nfs/backup/archive'
   UNTIL TIME='2023-09-30 00:00:00'
   WITH 'pool_list=restore_pool'
   REMAP TABLE infodb.tbl1:newtbl
   REMAP TABLEGROUP tg1:newtg1
   REMAP TABLESPACE ts1:newts1;
   ```

  <main id="notice" type='notice'>
  <h4>注意</h4>
  <p><ul><li>テーブルデータの復元が成功した場合、テーブルの復元は成功したことを意味します。インデックス、制約、またはその他の関連するスキーマの復元が失敗しても構いません。</li><li>テーブルレベルの復元が終了した後、<code>ddl_thread_score</code>、<code>recover_table_concurrency</code>、および<code>recover_table_dop</code>構成パラメータの設定を元に戻すことを推奨します。復元しない場合、今後のテーブルレベルの復元は設定された並列パラメータに従って実行されます。</li></ul></p>
  </main>

## 復元されるスキーマ情報の説明

テーブル単位での復元を実行した後、復元されるスキーマ情報とその詳細は以下の通りです。

| スキーマ情報 | 復元可能か | 説明                                                  |
|---------------|-----------|--------------------------------------------------------|
| データベース      |    不可      | テーブル単位の復元を実行する際、ターゲットテナント内に対応するデータベースが存在していなければ、復元は失敗します。例えば、仮想デバイスでバックアップされたテーブルが元々`INFO`という名前のデータベースに属していた場合、`REMAP TABLE`コマンドを使用しない限り（`REMAP TABLE`コマンドはテーブルをターゲットテナント内の別のデータベースにリネームできます）、システムは復元時にテーブルをターゲットテナント内の`INFO`という名前のデータベースに配置します。      |
| テーブルスペース    |    不可      | テーブル単位の復元を実行する際、ターゲットテナント内に対応するテーブルスペースが存在していなければ、復元は失敗します。例えば、仮想デバイスでバックアップされたテーブルが元々`TS`という名前のテーブルスペースに属していた場合、`REMAP TABLE`コマンドを使用しない限り（`REMAP TABLE`コマンドはテーブルをターゲットテナント内の別のテーブルスペースにリネームできます）、システムは復元時にテーブルをターゲットテナント内の`TS`という名前のテーブルスペースに配置します。       |
| テーブルグループ          |     不可      | テーブル単位の復元を実行する際、ターゲットテナント内に対応するテーブルグループが存在していなければ、復元は失敗します。例えば、仮想デバイスでバックアップされたテーブルが元々`TG`という名前のテーブルグループに属していた場合、`REMAP TABLE`コマンドを使用しない限り（`REMAP TABLE`コマンドはテーブルをターゲットテナント内の別のテーブルグループにリネームできます）、システムは復元時にテーブルをターゲットテナント内の`TG`という名前のテーブルグループに配置します。 |
| テーブル            |    はい      | ユーザーテーブルのみの復元をサポートし、システムテーブルや一時テーブルの復元はサポートしていません。 |
| パーティション          |    はい      | N/A |
| タブレット        |    はい      | N/A |
| 列            |    はい      | N/A |
| 约束          |    はい      | 復元可能な約束は以下の通りです：<ul><li>`NOT NULL` 约束 </li> <li>`UNIQUE KEY` 约束 </li> <li>`PRIMARY KEY` 约束 <main id="notice" type='notice'><h4>注意</h4><p>Oracleモードでは、重複する<code>PRIMARY KEY</code>約束名が存在すると、テーブル全体の復元が失敗します。</p></main></li> <li>`CHECK` 约束</li></ul> <main id="notice" type='explain'><h4>説明</h4><p>約束名がユーザー定義であり、かつターゲットテナント内に既に存在する場合は、復元しません。</p></main> |
| 外部キー          |    はい      | 外部キーを復元する過程で、システムは外部キー約束の整合性をチェックします。外部キー参照が存在しない行が検出された場合、その外部キーの復元は失敗します。 |
| ビュー          |    不可      | テーブルを復元する際、そのテーブルに関連付けられたビューは復元されません。 |
| ローカルインデックス      |    はい      | N/A |
| グローバルインデックス      |    はい      | N/A |
| 自動インクリメント列        |    はい      | N/A |
| 主キーのないテーブル      |    はい      | N/A |
| 統計情報      |    はい      | N/A |
| トリガー        |    はい      | <ul><li> テーブルを元のテーブル名で復元する場合、そのテーブルに関連付けられたトリガーも復元されます。その中で：<ul><li>Oracleモードでは、トリガーが存在するユーザーが存在しない場合、そのトリガーの復元は失敗します。</li> <li>MySQLモードでは、トリガーが存在するデータベースが存在しない場合、そのトリガーの復元は失敗します。</li></ul></li> <li>テーブルがリネームされている場合、すなわち新しいテーブル名で復元する場合、そのテーブルに関連付けられたトリガーは復元されません。</li></ul> |
| 関数、ストアドプロシージャ、パッケージ |    不可  | テーブルを復元する際、そのテーブルに関連付けられた関数、ストアドプロシージャ、パッケージは復元されません。 |
| シノニム        |    不可      | テーブルを復元する際、そのテーブルに関連付けられたシノニムは復元されません。 |
| 空間インデックス      |    はい      | テーブル単位の復元を実行する際、座標系は復元されません。ターゲットテナントに参照座標系が存在しない場合、空間インデックスは復元されません。ターゲットテナントに座標系が存在する場合、空間インデックスは復元されます。 |
| LOB          |    はい      | N/A |

## 次のステップ

* 指定したテーブルの復旧を開始した後、ビューを使用してテーブル復旧の進捗状況と結果を確認できます。具体的な操作については、[テーブルレベルの復旧の進捗状況を確認する](400.view-the-table-recovery-progress.md)および[テーブルレベルの復旧結果を確認する](500.view-the-table-recovery-history.md)を参照してください。

* 指定したテーブルの復旧が終了した後、スタンバイテナントが存在するクラスタで以下のコマンドを実行し、スタンバイテナント用に作成されたリソースプールを手動で解放する必要があります。

    ```sql
    DROP RESOURCE POOL restore_pool;
    ```

    ここで、`restore_pool` は復旧前の準備時にスタンバイテナント用に作成されたリソースプールの名前を表します。

    リソースプールの削除に関する詳細な操作と説明については、[リソースプールの削除](../../200.tenant-management/600.common-tenant-operations/1500.resource-pool-management/600.delete-resource-pool.md)を参照してください。
