# バックアップパスとアーカイブパスのソース側設定例

データセンター間またはリージョン間でのデプロイメントアーキテクチャでは、ネットワーク帯域幅リソースが一般的により逼迫しているため、バックアップパスとアーカイブパスを設定する際には、パスがアクセス可能なゾーン、IDC、またはリージョンを考慮し、既存のネットワークリソースを最大限に活用し、データセンター間またはリージョン間のトラフィック発生を回避し、データ転送効率を向上させる必要があります。

このセクションでは、2リージョン3データセンターのデプロイメントアーキテクチャを例に、ユーザーにバックアップパスとアーカイブパスのソース側設定のガイドを提供します。

## シナリオ情報

以下の図は、2リージョン3データセンター構成のデプロイアーキテクチャを示しており、バックアップに関わるデータフローが示されています。OceanBaseデータベースの5つのレプリカは、3つのデータセンター（IDC）と2つの都市に分散して配置されています。具体的には、2（深セン南山区）+2（深セン宝安区）+1（杭州市）です。通常の状況では、リーダーレプリカは主に深セン南山区の2つのゾーンに集中しており、`PRIMARY_ZONE`の設定は`z1,z2`となっています。ルートサービス（RS）のリーダーはZ2のobs4上に配置されています。

仮に、バックアップメディアであるNFSが深セン南山区のデータセンター（IDC1）にデプロイされており、ユーザーが同一都市内のデータセンター間でのNFSへのアクセスを許可する一方で、都市間でのアクセスは許可しないように設定した場合を想定します。この設定に基づき、深セン南山区のデータセンター（IDC1）および深セン宝安区のデータセンター（IDC2）の両方のOBServerノードはNFSにアクセス可能です。ただし、深セン南山区のデータセンター（IDC1）のOBServerノードからのNFSへのアクセスは同一データセンター内でのアクセスとなり、一方で深セン宝安区のデータセンター（IDC2）のOBServerノードからのNFSへのアクセスはデータセンター間のネットワークトラフィックを発生させます。また、杭州市のデータセンターのOBServerノードはNFSがマウントされていないため、NFSにアクセスできません。

### バックアップパスのソース情報の設定

データバックアップのレプリカはデフォルトで利用可能なすべてのFレプリカから選択され、通常はフォロワーレプリカが優先的に選ばれるため、上図から分かるように、Root Service（RS）はバックアップタスクをobs10（杭州データセンターのOBServerノード）にスケジュールする可能性があります。しかし、obs10はNFSにアクセスできないため、バックアップタスクの実行に失敗します。そのため、バックアップパスのソース側を設定し、バックアップタスクを実行できるノードの範囲を制限する必要があります。

このシナリオでは、バックアップが都市間でNFSにアクセスすることを許可しないというルールに基づき、バックアップパスのソース情報を`region=Region1`、`idc=IDC1,IDC2`、または`zone=Z1,Z2,Z3,Z4`に設定できます。設定時には、データバックアップのメタ情報ファイルはRSノードによって操作されるため、RSノードがソース側の設定範囲外にある場合にバックアップパスへのアクセス権を失い、バックアップタスクの実行に失敗することを避けるため、テナントの`PRIMARY_ZONE`を`ALTER TENANT tenant_name PRIMARY_ZONE='z1,z2'`に設定することを推奨します。

仮想バックアップパスが`file:///data/nfs/backup/data`の場合、ユーザーテナント内でバックアップパスのソース情報を`region=Region1`に設定するステートメントは次のとおりです：

```shell
obclient> ALTER SYSTEM SET DATA_BACKUP_DEST = 'file:///data/nfs/backup/data?region=Region1';
```

設定が成功すると、RSはもはやバックアップタスクを`Region2`のノードに転送せず、`Region1`内でバックアップサービスを提供できるノードにのみ転送します。また、RSはフォロワーレプリカを優先してバックアップタスクを実行し、バックアップタスクによるリーダーレプリカの負荷増加が他の業務に影響を与えることを防ぎます。

同時に、上述の説明から分かるように、ソース側が`region=Region1`、`idc=IDC1,IDC2`、または`zone=Z1,Z2,Z3,Z4`に設定された後、優先順位がないため、多くのバックアップタスクが`IDC2`内のフォロワーレプリカに転送される可能性があります（下図参照）。この場合、バックアップデータによって生成されるトラフィックはデータセンター間のトラフィックとなります。ユーザーのデータセンター間ネットワーク帯域幅リソースが逼迫している場合は、ソース側の設定を`idc=IDC1;IDC2`または`zone=Z1,Z2;Z3,Z4`に変更できます。

<!-- ![バックアップタスクがIDC2に転送される](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/600.backup-and-recovery/after_config_fixed.png) -->

例えば、以下のステートメントを使用してソース側の設定を`idc=IDC1;IDC2`に変更できます。

```shell
obclient> ALTER SYSTEM CHANGE EXTERNAL_STORAGE_DEST PATH='file:///data/nfs/backup/data' SET ATTRIBUTE='idc=IDC1;IDC2';
```

変更後、RSがバックアップタスクを実行するノードを選択する際、IDC1内のノードは高い優先順位を持ち、`IDC2`内のノードは優先順位が低くなります。これにより、バックアップはできるだけ同一データセンター内のネットワークリソースを使用できます。`IDC2`を代替バックアップパスとして設定することで、異常時（例：`IDC1`内のノードがダウンした場合）に対するバックアップタスクの耐性を向上させると同時に、RSが`IDC2`に切り替わった後にRSがバックアップメディアへのアクセス権を失い、バックアップに失敗することを防ぐことができます。

<!-- ![バックアップパスのソース設定の変更](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/600.backup-and-recovery/modify_the_configuration.png) -->

### ログアーカイブパスのソース情報の設定

同様に、ログアーカイブについても、このシナリオでは、都市間でのNFSへのアクセスが許可されないというルールに基づき、アーカイブパスのソース情報を `region=Region1`、`idc=IDC1;IDC2`、または `zone=Z1,Z2;Z3,Z4` として設定することができます。ログアーカイブのすべてのトラフィックはリーダー複製によって書き込まれるため、ログアーカイブパスに関しては、アクセス権限のみが存在し、アクセス優先順位の違いはありません。したがって、設定時には、`zone=Z1,Z2;Z3,Z4` は `zone=Z1,Z2,Z3,Z4` と同等であり、`idc=IDC1;IDC2` は `idc=IDC1,IDC2` と同等です。

例えば、ユーザーテナントの `PRIMARY_ZONE` が `PRIMARY_ZONE='Z1,Z2,Z3,Z4'` で、アーカイブパスが `file:///data/nfs/backup/archive` の場合、以下の2つのシナリオが考えられます：

#### シナリオ1：初期シナリオで、ネットワーク帯域幅リソースが十分な場合

初期シナリオでは、ログアーカイブのネットワークトラフィックが少ないため、ユーザーテナントはアーカイブパスのソース情報を `region=Region1` と設定することで、Region1内のノードのみがアーカイブパスにアクセスできるように制限できます：

```shell
obclient> ALTER SYSTEM SET LOG_ARCHIVE_DEST = 'LOCATION=file:///data/nfs/backup/archive?region=Region1';
```

設定が成功すると、運用保守やその他の理由によりリーダー複製が `Region2` に切り替わった場合でも、予期しないアクセスリクエスト（つまり、`Region2` 内のOBServerノードからアーカイブパスへのアクセスリクエスト）を防ぐことができます。システムがリーダー複製が `Region2` 上でアーカイブパスにアクセスしていることを検出すると、エラーログ（エラーコード `-9063`）を送信し、運用保守担当者に対して、以下の点を確認するよう警告します：(1) Locality名の変更によりノードがアクセス権限を失っていないか、(2) リーダー複製の位置がアクセス権限を持たないノードに切り替わっていないか、およびソース設定を適時更新するか、手動でリーダー複製をアクセス権限を持つOBServerノードに切り替える必要があるかを確認します。

#### シナリオ2：ネットワーク帯域幅リソースが逼迫している場合

データの継続的な書き込みに伴い、ログアーカイブのネットワークトラフィックが増加した場合、アーカイブパスのソース設定を `idc=IDC1` に変更し、同時にテナントの `PRIMARY_ZONE` を `PRIMARY_ZONE='Z1,Z2'` に変更できます。

<main id="notice" type='explain'>
<h4>説明</h4>
<p>テナントの <code>PRIMARY_ZONE</code> はソース設定と一致させる必要があります。これは、リーダー複製がソース設定の範囲外にあるためにアーカイブパスへのアクセス権限を失い、最終的にアーカイブの進捗が妨げられることを防ぐためです。</p>
</main>

```shell
obclient> ALTER SYSTEM CHANGE EXTERNAL_STORAGE_DEST PATH='file:///data/nfs/backup/archive' SET ATTRIBUTE='idc=IDC1';
```
