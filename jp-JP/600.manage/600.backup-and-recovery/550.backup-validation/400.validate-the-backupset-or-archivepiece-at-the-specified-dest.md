# 指定パスのバックアップセットまたはログアーカイブピースの検証

OceanBaseデータベースは、指定されたパス下のバックアップセットまたはログアーカイブピースの検証をサポートしています。この方法は、クラスタ間でのバックアップデータやコールドスタンバイデータの検証に適しています。

## 制限事項と注意点

* チェックタスクは、バックアップメディアに頻繁にアクセスしてデータを読み取るため、バックアップタスクのネットワークリソースを占有します。そのため、ユーザーテナントがバックアップタスクを実行しておらず、負荷が低い時にチェックタスクを実行することを推奨します。

* バックアップチェックの検証レベルを指定する場合：

  * V4.4.2バージョンでは、V4.4.2 BP2バージョン（V4.4.2 BP2バージョンを除く）以前のバックアップセットおよびログアーカイブピースについては、Basic検証、すなわちファイルの整合性検証はサポートされていません。

  * V4.3.4バージョン（V4.3.4バージョンを除く）以前のバックアップセットについては、Physical検証、すなわち物理データの正確性および論理的一貫性検証はサポートされていません。

* チェック対象のバックアップセットに増分バックアップセットが含まれている場合、Physical検証レベルでは、指定したパスにその増分バックアップセットが依存するフルバックアップセットが含まれている必要があります。そうでない場合、チェックは失敗します。

## 指定パス下のバックアップセットのチェック

### システムテナントがユーザーテナントの指定パス下のバックアップセットに対してバックアップチェックを開始する場合

1. `root`ユーザーでクラスタの`sys`テナントにログインします。

   接続例は以下のとおりです。データベースへの接続時は、実際の環境に準じてください。

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. 以下のコマンドを実行し、ユーザーテナントの指定パス下のバックアップセットに対するチェックを開始します。

   ステートメントは以下のとおりです：

   ```sql
   ALTER SYSTEM VALIDATE BACKUPSET [= 'backup_set_id[,backup_set_id,...]'] DATA_BACKUP_DEST = 'data_backup_path' [LEVEL = { 'basic' | 'physical' }] TENANT = tenant_name;
   ```

   ステートメント内の関連パラメータの説明は以下のとおりです：

   * `BACKUPSET`：チェック対象のバックアップセットを指定します。テナントが指定したバックアップパス下のすべてのバックアップセット、または指定したバックアップセットのリストをチェックすることができます。バックアップセットのリストを指定する場合、複数のバックアップセットの`backup_set_id`は半角カンマで区切ります。バックアップセットの`backup_set_id`が指定されていない場合、デフォルトでテナントが指定したバックアップパス下のすべてのバックアップセットがチェックされます。

     クラスタ間やコールドスタンバイデータのシナリオでは、バックアップセットの`backup_set_id`はバックアップディレクトリ内のファイル名から取得できます。バックアップディレクトリ構造の詳細については、[物理バックアップとリストアの概要](../100.overview-of-physical-backup-and-recovery.md)の**データバックアップディレクトリ**を参照してください。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p><code>backup_set_id</code>を指定しない場合、システムは現在設定されているバックアップパス下のすべてのバックアップセットを取得してチェックするため、多数のチェックタスクが生成され、時間がかかります。すべてのバックアップセットをチェックする必要がない場合は、チェックコマンドで<code>backup_set_id</code>を指定することを推奨します。</p>
     </main>

   * `DATA_BACKUP_DEST`：バックアップセットの保存パスを指定します。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p>OceanBaseデータベースは現在、単一のコマンドで複数のパスを指定することをサポートしていません。そのため、パスを指定した後に<code>backup_set_id</code>を指定して増分バックアップセットをチェックすると、その増分バックアップセットが依存する他のバックアップセット情報を読み取れないため、エラーが発生する可能性があります。エラーコードは9159です。</p>
     </main>

   * `LEVEL`：オプションパラメータで、チェックレベルを表します。指定しない場合、デフォルト値は`physical`です。詳細は以下のとおりです：

     * `basic`検証：ファイルリストの整合性のみをチェックします。

     * `physical`検証：物理データの正確性と論理的一致性をチェックします。

   * `TENANT`：検証タスクを実行するユーザーテナントを指定します。

   例：

   * システムテナントは、指定されたユーザーテナント`mysqltenant`の指定されたバックアップパス下のすべてのバックアップセットに対してBasic検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE BACKUPSET DATA_BACKUP_DEST = 'file:///data/nfs/backup/data' LEVEL = 'basic' TENANT = mysqltenant;
     ```

   * システムテナントは、指定されたユーザーテナント`mysqltenant`の指定されたバックアップパス下で`backup_set_id`が1および2のバックアップセットに対してPhysical検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE BACKUPSET = '1,2' DATA_BACKUP_DEST = 'file:///data/nfs/backup/data' LEVEL = 'physical' TENANT = mysqltenant;
     ```

3. ステートメントの実行が成功した後、`CDB_OB_BACKUP_VALIDATE_JOBS`、`CDB_OB_BACKUP_VALIDATE_TASKS`、`CDB_OB_BACKUP_VALIDATE_JOB_HISTORY`、および`CDB_OB_BACKUP_VALIDATE_TASK_HISTORY`ビューを使用して、検証タスクの状態、進捗状況、および実行結果を確認できます。

   バックアップ検証の進捗状況を確認する詳細な操作と説明については、[バックアップ検証の進捗状況を確認する](600.view-the-backup-validation-process.md)を参照してください。

   バックアップ検証結果を確認する詳細な操作と説明については、[バックアップ検証結果を確認する](700.view-the-backup-validation-history.md)を参照してください。

### ユーザーテナントが自身のテナント内の指定パス下のバックアップセットに対してバックアップ検証を開始する

1. ユーザーテナントのテナント管理者がデータベースにログインします。

   <main id="notice" type='explain'>
   <h4>説明</h4>
   <p>MySQLテナントの管理者ユーザーは<code>root</code>ユーザー、Oracleテナントの管理者ユーザーは<code>SYS</code>ユーザーです。</p>
   </main>

   接続例は以下のとおりです。データベースへの接続時は、実際の環境に準じてください。

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@mysql001#obdemo -p***** -A
   ```

2. 以下のコマンドを実行し、指定パス下のバックアップセットの検証を開始します。

   ステートメントは以下のとおりです：

     </main>

   * `DATA_BACKUP_DEST`：バックアップセットの保存パスを指定します。

     </main>

   * `LEVEL`：オプションパラメータで、検証レベルを示します。指定しない場合、デフォルト値は`physical`です。詳細は以下の通りです：

     * `basic` 検証：ファイルリストの整合性のみをチェックします。

     * `physical` 検証：物理データの正確性および論理的一貫性をチェックします。

## 指定パスのログアーカイブピースの検証

### システムテナントがユーザーテナントの指定パスのログアーカイブピースに対してバックアップ検証を開始する

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

   接続例は以下のとおりです。データベースへの接続時は、実際の環境に準じてください。

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. 以下のコマンドを実行し、ユーザーテナントの指定パス下のログアーカイブピースに対する検証を開始します。

   ステートメントは以下のとおりです：

   ```sql
   ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE [= 'piece_id[,piece_id,...]'] LOG_ARCHIVE_DEST = 'log_archive_path' [LEVEL = { 'basic' | 'physical' }] TENANT = tenant_name;
   ```

   ステートメント内の関連パラメータの説明は以下のとおりです：

   * `ARCHIVELOG_PIECE`：検証対象のログアーカイブピースを指定します。テナントが指定したアーカイブパス下のすべてのアーカイブピース、または指定されたアーカイブピースリストを検証できます。アーカイブピースリストを指定する場合、複数の `piece_id` を半角カンマで区切ります。`piece_id` が指定されていない場合、デフォルトでテナントが指定したアーカイブパス下のすべてのログアーカイブピースを検証します。

     クラスタ間やコールドスタンバイデータのシナリオでは、ログアーカイブピースの `piece_id` はアーカイブディレクトリ内のファイル名から取得できます。アーカイブディレクトリ構造の詳細については、[物理バックアップとリストアの概要](../100.overview-of-physical-backup-and-recovery.md) の **ログアーカイブディレクトリ** を参照してください。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p><code>piece_id</code> を指定しない場合、システムは指定されたアーカイブパス下のすべてのアーカイブピースを取得して検証するため、多数の検証タスクが生成され、時間がかかります。すべてのアーカイブピースを検証する必要がない場合は、検証コマンドで <code>piece_id</code> を指定することを推奨します。</p>
     </main>

   * `LOG_ARCHIVE_DEST`：ログアーカイブピースの保存先パスを指定します。

   * `LEVEL`：オプションパラメータで、検証レベルを表します。指定しない場合、デフォルト値は `physical` です。詳細は以下のとおりです：

     * `basic` 検証：ファイルリストの整合性のみをチェックします。

     * `physical` 検証：物理データの正確性と論理的一致性をチェックします。

   * `TENANT`：検証タスクを実行するユーザーテナントを指定するために使用します。

   例：

   * システムテナントが指定アーカイブパス下のすべてのアーカイブピースに対してBasic検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE LOG_ARCHIVE_DEST = 'file:///data/nfs/backup/archive' LEVEL = 'basic' TENANT = tenant1;
     ```

   * システムテナントが指定アーカイブパス下の `piece_id` が1、2のログアーカイブピースに対してPhysical検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE = '1,2' LOG_ARCHIVE_DEST = 'file:///data/nfs/backup/archive' LEVEL = 'physical' TENANT = tenant1;
     ```

3. ステートメントの実行が成功すると、`CDB_OB_BACKUP_VALIDATE_JOBS`、`CDB_OB_BACKUP_VALIDATE_TASKS`、`CDB_OB_BACKUP_VALIDATE_JOB_HISTORY`、および `CDB_OB_BACKUP_VALIDATE_TASK_HISTORY` ビューを使用して、検証タスクの状態、進捗状況、および実行結果をそれぞれ確認できます。

   バックアップ検証の進捗状況を確認する詳細な操作と説明については、[バックアップ検証の進捗状況を確認する](600.view-the-backup-validation-process.md) を参照してください。

   バックアップ検証結果の詳細な操作と紹介については、[バックアップ検証結果の確認](700.view-the-backup-validation-history.md)を参照してください。
