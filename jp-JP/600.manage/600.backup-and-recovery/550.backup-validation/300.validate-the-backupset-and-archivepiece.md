# 指定されたバックアップセットまたはログアーカイブピースの検証

OceanBaseデータベースでは、指定されたバックアップセットまたはログアーカイブピースの検証をサポートしています。ユーザーは業務ニーズに応じて、現在のバックアップパス配下の指定されたバックアップセットのみを検証するか、現在のアーカイブパス配下のログアーカイブピースのみを検証するかを選択できます。

## 使用上の制限と注意事項

* このドキュメントは、クラスタ内のテナントにおける `DATA_BACKUP_DEST` および `LOG_ARCHIVE_DEST` で現在指定されているパス配下のバックアップセットまたはログアーカイブピースを検証する場合にのみ適用されます。現在のバックアップおよびアーカイブパス配下のすべてのバックアップセットとアーカイブピースを検証する必要がある場合は、[バックアップパスとアーカイブパス全体の検証](200.validate-the-data-backup-dest-and-log-archive-dest.md) を参照してください。

  また、バックアップ宛先またはアーカイブ宛先を変更したシナリオにおいて、元のバックアップパスまたはアーカイブパス配下のデータを検証する必要がある場合は、[指定パス配下のバックアップセットまたはログアーカイブピースの検証](400.validate-the-backupset-or-archivepiece-at-the-specified-dest.md) を参照してください。

* 検証タスクは、バックアップメディアに頻繁にアクセスしてデータを読み取るため、バックアップタスクのネットワークリソースを占有します。そのため、ユーザーテナントがバックアップタスクを実行しておらず、負荷が低い時に検証タスクを実行することを推奨します。

* バックアップ検証の検証レベルを指定する際：

  * V4.4.2バージョンでは、V4.4.2 BP2バージョン（V4.4.2 BP2バージョンを除く）以前のバックアップセットおよびログアーカイブピースについては、Basic検証、すなわちファイルの整合性検証はサポートされていません。

  * V4.3.4バージョン（V4.3.4バージョンを除く）以前のバックアップセットについては、Physical検証、すなわち物理データの正確性および論理的一貫性検証はサポートされていません。

* 検証対象のバックアップセットに増分バックアップセットが含まれている場合、Physical検証レベルでは、現在のパス配下にその増分バックアップセットが依存するフルバックアップセットが含まれている必要があります。そうでない場合、検証は失敗します。

## 指定バックアップセットの検証

### システムテナントからユーザーテナントの指定バックアップセットへのバックアップ検証の開始

1. `root`ユーザーでクラスタの`sys`テナントにログインします。

   接続例は以下のとおりです。データベースへの接続時は、実際の環境に準じてください。

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. （オプション）検証対象のユーザーテナントのバックアップセットの `backup_set_id` を取得します。

   ```shell
   obclient(root@sys)[(none)]> SELECT a.TENANT_ID, b.TENANT_NAME, a.BACKUP_SET_ID, a.BACKUP_TYPE, a.STATUS, a.FILE_STATUS, a.PATH
   FROM oceanbase.CDB_OB_BACKUP_SET_FILES a, oceanbase.DBA_OB_TENANTS b
   WHERE a.TENANT_ID = b.TENANT_ID
   AND b.TENANT_NAME = 'mysqltenant';
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+---------------+-------------+---------+-------------+------------------------------------------+
   | TENANT_ID | TENANT_NAME | BACKUP_SET_ID | BACKUP_TYPE | STATUS  | FILE_STATUS | PATH                                     |
   +-----------+-------------+---------------+-------------+---------+-------------+------------------------------------------+
   |      1002 | mysqltenant |             1 | FULL        | SUCCESS | AVAILABLE   | file:///data/nfs/backup/data             |
   |      1002 | mysqltenant |             2 | FULL        | SUCCESS | AVAILABLE   | file:///data/nfs/backup/data             |
   +-----------+-------------+---------------+-------------+---------+-------------+------------------------------------------+
   2 rows in set
   ```

3. 以下のコマンドを実行し、ユーザーテナントの指定バックアップセットに対する検証を開始します。

   ステートメントは次のとおりです：

   ```sql
   ALTER SYSTEM VALIDATE BACKUPSET [= 'backup_set_id[,backup_set_id,...]'] [LEVEL = { 'basic' | 'physical' }] [TENANT = tenant_name];
   ```

   ステートメント内の関連パラメータの説明は以下のとおりです：

   * `BACKUPSET`：検証対象のバックアップセットを指定します。テナントの現在のバックアップパス配下のすべてのバックアップセット、または指定されたバックアップセットのリストを検証することをサポートします。バックアップセットのリストを指定する場合、複数のバックアップセットの `backup_set_id` は半角カンマで区切ります。バックアップセットの `backup_set_id` を指定しない場合、デフォルトでテナントの現在のバックアップパス配下のすべてのバックアップセットが検証されます。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p><code>backup_set_id</code> を指定しない場合、システムは現在設定されているバックアップパス配下のすべてのバックアップセットを取得して検証するため、多数の検証タスクが生成され、時間がかかります。すべてのバックアップセットを検証する必要がない場合は、検証コマンドで <code>backup_set_id</code> を指定することを推奨します。</p>
     </main>

   * `LEVEL`：オプションパラメータで、検証レベルを表します。指定しない場合、デフォルト値は `physical` です。詳細は以下のとおりです：

     * `basic`検証：ファイルリストの整合性のみをチェックします。

     * `physical`検証：物理データの正確性と論理的一致性をチェックします。

   * `TENANT`：検証タスクを実行するユーザーテナントを指定します。指定しない場合、クラスタ内のすべてのユーザーテナントの指定されたバックアップセットを検証します。

   例：

   * システムテナントは、すべてのユーザーテナントの現在のバックアップパスにあるすべてのバックアップセットに対してBasic検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE BACKUPSET LEVEL = 'basic';
     ```

   * システムテナントは、ユーザーテナント`mysqltenant`の現在のバックアップパスにあるすべてのバックアップセットに対してBasic検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE BACKUPSET LEVEL = 'basic' TENANT = mysqltenant;
     ```

   * システムテナントは、ユーザーテナント`mysqltenant`の現在のバックアップパスにある`backup_set_id`が1および2のバックアップセットに対してPhysical検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE BACKUPSET = '1,2' LEVEL = 'physical' TENANT = mysqltenant;
     ```

   * システムテナントは、すべてのユーザーテナントの現在のバックアップパスにある`backup_set_id`が1および2のバックアップセットに対してPhysical検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE BACKUPSET = '1,2' LEVEL = 'physical';
     ```

4. ステートメントの実行が成功した後、`CDB_OB_BACKUP_VALIDATE_JOBS`、`CDB_OB_BACKUP_VALIDATE_TASKS`、`CDB_OB_BACKUP_VALIDATE_JOB_HISTORY`、および `CDB_OB_BACKUP_VALIDATE_TASK_HISTORY` ビューを使用して、検証タスクの状態、進捗状況、および実行結果を確認できます。

   バックアップ検証の進捗状況を確認する詳細な操作と説明については、[バックアップ検証の進捗状況を確認する](600.view-the-backup-validation-process.md)を参照してください。

   バックアップ検証結果を確認する詳細な操作と説明については、[バックアップ検証結果を確認する](700.view-the-backup-validation-history.md)を参照してください。

### ユーザーテナントが自身の指定バックアップセットに対してバックアップ検証を開始する

1. ユーザーテナントのテナント管理者がデータベースにログインします。

   <main id="notice" type='explain'>
   <h4>説明</h4>
   <p>MySQLテナントの管理者ユーザーは<code>root</code>ユーザー、Oracleテナントの管理者ユーザーは<code>SYS</code>ユーザーです。</p>
   </main>

   接続例は以下のとおりです。データベースへの接続時は、実際の環境に準じてください。

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@mysql001#obdemo -p***** -A
   ```

2. （オプション）検証対象のバックアップセットの`backup_set_id`を取得します。

   :::tab
   tab MySQLモード

   MySQLモードでのクエリステートメントは以下のとおりです：

   ```shell
   obclient(root@mysqltenant)[(none)]> SELECT BACKUP_SET_ID, BACKUP_TYPE, STATUS, FILE_STATUS, PATH FROM oceanbase.DBA_OB_BACKUP_SET_FILES;
   ```

   tab Oracleモード

   Oracleモードでのクエリステートメントは以下のとおりです：

   ```shell
   obclient(SYS@oracletenant)[SYS]> SELECT BACKUP_SET_ID, BACKUP_TYPE, STATUS, FILE_STATUS, PATH FROM SYS.DBA_OB_BACKUP_SET_FILES;
   ```

   :::

3.  以下のコマンドを実行して、指定したバックアップセットの検証を開始します。

   ステートメントは以下のとおりです：

   ```sql
   ALTER SYSTEM VALIDATE BACKUPSET [= 'backup_set_id[,backup_set_id,...]'] [LEVEL = { 'basic' | 'physical' }];
   ```

   * `BACKUPSET`：検証するバックアップセットを指定します。テナントの現在のバックアップパス配下のすべてのバックアップセット、または指定されたバックアップセットのリストを検証できます。バックアップセットのリストを指定する場合、複数のバックアップセット `backup_set_id` の間は半角カンマで区切ります。バックアップセットの `backup_set_id` を指定しない場合、デフォルトでテナントの現在のバックアップパス配下のすべてのバックアップセットが検証されます。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p><code>backup_set_id</code> を指定しない場合、システムは現在設定されているバックアップパス配下のすべてのバックアップセットを取得して検証するため、多数の検証タスクが生成され、時間がかかります。すべてのバックアップセットを検証する必要がない場合は、検証コマンドで <code>backup_set_id</code> を指定することを推奨します。</p>
     </main>

   * `LEVEL`：オプションパラメータで、検証レベルを表します。指定しない場合、デフォルト値は `physical` です。詳細は以下のとおりです：

     * `basic` 検証：ファイルリストの整合性のみをチェックします。

     * `physical` 検証：物理データの正確性と論理的一致性をチェックします。

   例：

   * ユーザーテナントが自身の現在のバックアップパス配下のすべてのバックアップセットに対してBasic検証を開始します。

     ```shell
     obclient> ALTER SYSTEM VALIDATE BACKUPSET LEVEL = 'basic';
     ```

   * ユーザーテナントが自身の現在のバックアップパス配下で `backup_set_id` が1および2のバックアップセットに対してPhysical検証を開始します。

     ```shell
     obclient> ALTER SYSTEM VALIDATE BACKUPSET = '1,2' LEVEL = 'physical';
     ```

   バックアップ検証の進捗状況を確認する詳細な操作と紹介については、[バックアップ検証の進捗状況を確認する](600.view-the-backup-validation-process.md)を参照してください。

## 指定されたログアーカイブピースの検証

### システムテナントがユーザーテナントの指定ログアーカイブピースに対してバックアップ検証を開始する

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

   接続例は以下のとおりです。データベースへの接続時は、実際の環境に準じてください。

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

2. （オプション）検証対象のユーザーテナントのログアーカイブピースの `piece_id` を取得します。

   ```shell
   obclient(root@sys)[(none)]> SELECT a.TENANT_ID, b.TENANT_NAME, a.ROUND_ID, a.PIECE_ID, a.STATUS, a.FILE_STATUS, a.PATH
   FROM oceanbase.CDB_OB_ARCHIVELOG_PIECE_FILES a, oceanbase.DBA_OB_TENANTS b
   WHERE a.TENANT_ID = b.TENANT_ID
   AND b.TENANT_NAME = 'mysqltenant';
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+----------+----------+--------+-------------+---------------------------------------------+
   | TENANT_ID | TENANT_NAME | ROUND_ID | PIECE_ID | STATUS | FILE_STATUS | PATH                                        |
   +-----------+-------------+----------+----------+--------+-------------+---------------------------------------------+
   |      1002 | mysqltenant |        1 |        1 | ACTIVE | AVAILABLE   | file:///data/nfs/backup/archive             |
   |      1002 | mysqltenant |        1 |        2 | ACTIVE | AVAILABLE   | file:///data/nfs/backup/archive             |
   +-----------+-------------+----------+----------+--------+-------------+---------------------------------------------+
   2 row in set
   ```

3. 以下のコマンドを実行し、ユーザーテナントに対して指定ログアーカイブピースの検証を開始します。

   ステートメントは以下のとおりです：

   ```sql
   ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE [= 'piece_id[,piece_id,...]'] [LEVEL = { 'basic' | 'physical' }] [TENANT = tenant_name];
   ```

   ステートメント内の関連パラメータの説明は以下のとおりです：

   * `ARCHIVELOG_PIECE`：検証対象のログアーカイブピースを指定します。テナントの現在のアーカイブパス下のすべてのアーカイブピース、または指定されたアーカイブピースリストを検証できます。アーカイブピースリストを指定する場合、複数の `piece_id` は半角カンマで区切ります。`piece_id` を指定しない場合、デフォルトでテナントの現在のアーカイブパス下のすべてのログアーカイブピースが検証されます。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p><code>piece_id</code> を指定しない場合、システムは現在設定されているアーカイブパス下のすべてのアーカイブピースを取得して検証するため、多数の検証タスクが生成され、時間がかかります。すべてのアーカイブピースを検証する必要がない場合は、検証コマンドで <code>piece_id</code> を指定することを推奨します。</p>
     </main>

   * `LEVEL`：オプションパラメータで、検証レベルを示します。指定しない場合、デフォルト値は `physical` です。詳細は以下のとおりです：

     * `basic` 検証：ファイルリストの整合性のみをチェックします。

     * `physical` 検証：物理データの正確性と論理的一致性をチェックします。

   * `TENANT`：オプションパラメータで、検証タスクを実行するユーザーテナントを指定するために使用します。指定しない場合、クラスタ内のすべてのユーザーテナントの指定アーカイブピースが検証されます。

   例：

   * システムテナントが、すべてのユーザーテナントの現在のアーカイブパス下のすべてのアーカイブピースに対して Basic 検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE LEVEL = 'basic';
     ```

   * システムテナントが、ユーザーテナント `mysqltenant` の現在のアーカイブパス下のすべてのアーカイブピースに対して Basic 検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE LEVEL = 'basic' TENANT = mysqltenant;
     ```

   * システムテナントは、ユーザーテナント `mysqltenant` の現在のアーカイブパスにある `piece_id` が1および2のログアーカイブピースに対して物理検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE = '1,2' LEVEL = 'physical' TENANT = mysqltenant;
     ```

   * システムテナントは、すべてのユーザーテナントの現在のアーカイブパスにある `piece_id` が1および2のログアーカイブピースに対して物理検証を開始します。

     ```shell
     obclient(root@sys)[(none)]> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE = '1,2' LEVEL = 'physical';
     ```

4. ステートメントの実行が成功した後、`CDB_OB_BACKUP_VALIDATE_JOBS`、`CDB_OB_BACKUP_VALIDATE_TASKS`、`CDB_OB_BACKUP_VALIDATE_JOB_HISTORY`、および `CDB_OB_BACKUP_VALIDATE_TASK_HISTORY` ビューを使用して、検証タスクの状態、進捗状況、および実行結果を確認できます。

   バックアップ検証の進捗状況を確認する詳細な操作と説明については、[バックアップ検証の進捗状況を確認する](600.view-the-backup-validation-process.md)を参照してください。

   バックアップ検証結果を確認する詳細な操作と説明については、[バックアップ検証結果を確認する](700.view-the-backup-validation-history.md)を参照してください。

     <main id="notice" type='notice'>
     <h4>注意</h4>
     <p><code>piece_id</code> を指定しない場合、システムは現在設定されているアーカイブパス配下のすべてのアーカイブピースを取得して検証するため、多数の検証タスクが生成され、時間がかかります。すべてのアーカイブピースを検証する必要がない場合は、検証コマンドに <code>piece_id</code> を指定することを推奨します。</p>
     </main>

   * `LEVEL`：オプションのパラメータで、検証レベルを示します。指定しない場合、デフォルト値は `physical` です。詳細は以下のとおりです：

     * `basic` 検証：ファイルリストの整合性のみをチェックします。

     * `physical` 検証：物理データの正確性と論理的一致性をチェックします。

   例：

   * ユーザーテナントは、現在のアーカイブパス配下にある自身のテナントのすべてのアーカイブピースに対して Basic 検証を開始します。

     ```shell
     obclient> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE LEVEL = 'basic';
     ```

   * ユーザーテナントは、現在のアーカイブパス配下で `piece_id` が1および2のログアーカイブピースに対して Physical 検証を開始します。

     ```shell
     obclient> ALTER SYSTEM VALIDATE ARCHIVELOG_PIECE = '1,2' LEVEL = 'physical';
     ```

4. ステートメントの実行が成功した後、`DBA_OB_BACKUP_VALIDATE_JOBS`、`DBA_OB_BACKUP_VALIDATE_TASKS`、`DBA_OB_BACKUP_VALIDATE_JOB_HISTORY`、および `DBA_OB_BACKUP_VALIDATE_TASK_HISTORY` ビューを使用して、検証タスクの状態、進捗状況、および実行結果をそれぞれ確認できます。

   バックアップ検証の進捗状況を確認する詳細な操作と紹介については、[バックアップ検証の進捗状況を確認する](600.view-the-backup-validation-process.md)を参照してください。

   バックアップ検証結果を確認する詳細な操作と紹介については、[バックアップ検証結果を確認する](700.view-the-backup-validation-history.md)を参照してください。
