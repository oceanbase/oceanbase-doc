# 指定されたパスでのリカバリの実行

データバックアップセット(backup_set)とログアーカイブ(archivelog_piece)が業務上の理由により他のパスに手動で移動した場合、対応するbackup_setとarchivelog_pieceをロードしてからリカバリコマンドを発行することでテナントを復旧できます。

## 前提条件

* 復元対象のbackup_setとarchivelog_pieceの保存パスが取得済みであることを確認してください。

* 復元対象のbackup_setとarchivelog_pieceが同一テナントに属していることを確認してください。現在、同一テナント内のbackup_setおよびarchivelog_pieceからのみ新しいテナントへの復元が許可されています。

* 復元前の準備が完了していることを確認してください。具体的な操作については、[復元前の準備](../600.restore-data/100.preparation-before-recovery.md)を参照してください。

## 手順

1. `root`ユーザーで、復元対象のテナントが存在するクラスタの`sys`テナントにログインします。

2. （オプション）`ALTER SYSTEM RESTORE...PREVIEW`コマンドを実行し、元のデータバックアップパスとログアーカイブパス、および希望する復元時刻を指定します。

   ステートメントは次のとおりです：

   ```sql
   ALTER SYSTEM RESTORE FROM 'uri' UNTIL { TIME='timestamp' | SCN=scn } PREVIEW;
   ```

   関連パラメータの説明は以下のとおりです：

   * `uri`：元のデータバックアップパスとログアーカイブパスを指定します。英語のカンマで区切ります。

   * `TIME='timestamp' | SCN=scn`：希望する復元のタイムスタンプまたはSCNを指定します。このステートメントを実行する際には、時間を明示的に指定する必要があります。

   例：

   * 元のデータバックアップパスとログアーカイブパスを指定し、指定されたSCN `1712650554000909004`に復元することを希望します。

      ```shell
      obclient [oceanbase]> ALTER SYSTEM RESTORE FROM 'file:///ob_backup/data, file:///ob_backup/archive' UNTIL SCN = 1712650554000909004 PREVIEW;
      ```

   * 元のデータバックアップパスとログアーカイブパスを指定し、指定されたタイムスタンプ `2024-04-09 16:15:54`に復元することを希望します。

      ```shell
      obclient [oceanbase]> ALTER SYSTEM RESTORE FROM 'file:///ob_backup/data, file:///ob_backup/archive' UNTIL TIME = '2024-04-09 16:15:54' PREVIEW;
      ```

3. （オプション）`SHOW RESTORE PREVIEW`コマンドを実行して、指定された時間に復元するために必要なbackup_setとarchivelog_pieceを表示します。

   <main id="notice" type='notice'>
   <h4>注意</h4>
   <p><code>ALTER SYSTEM RESTORE...PREVIEW</code>コマンドの実行が成功した後にのみ、<code>SHOW RESTORE PREVIEW</code>コマンドを実行する必要があります。そうしないと、必要な結果を取得できません。</p>
   </main>

   ```shell
   obclient [oceanbase]> SHOW RESTORE PREVIEW;
   ```

   例えば、結果は次のとおりです：

   ```shell
   +--------------+-----------+--------------------------------------------------------------------------------+------------------------------------------------------------------------------+
   | backup_type  | backup_id | backup_dest                                                                    | description                                                                  |

   | BACKUP_PIECE |         2 | file:///ob_backup/archive/piece_d1002r1p2                                      | start_scn_display: 20240409T160154, checkpoint_scn_display: 20240409T160353. |
   | BACKUP_PIECE |         3 | file:///ob_backup/archive/piece_d1002r1p3                                      | start_scn_display: 20240409T160354, checkpoint_scn_display: 20240409T160553. |
   | BACKUP_PIECE |         4 | file:///ob_backup/archive/piece_d1002r1p4                                      | start_scn_display: 20240409T160554, checkpoint_scn_display: 20240409T160754. |
   | BACKUP_PIECE |         5 | file:///ob_backup/archive/piece_d1002r1p5                                      | start_scn_display: 20240409T160754, checkpoint_scn_display: 20240409T160953. |
   | BACKUP_PIECE |         6 | file:///ob_backup/archive/piece_d1002r1p6                                      | start_scn_display: 20240409T160954, checkpoint_scn_display: 20240409T161154. |

   9 rows in set
   ```

   クエリ結果には、指定された時間に復元するために必要なすべてのbackup_setとarchivelog_piece、およびこれらのファイルの元のデータバックアップとログアーカイブの宛先パスが表示されます。業務上の必要により、一部またはすべてのファイルを手動で他のパスまたはストレージメディアに移動した場合は、実際の状況に応じて、各backup_setとarchivelog_pieceの元のパスから現在のパスへのマッピング関係を自分で維持する必要があります。

   例えば、上記のクエリ結果では、`BACKUP_PIECE`が`1`のarchivelog_pieceを使用して復元する必要がありますが、そのファイルはすでに手動で`oss://test_bucket/archive/piece_1`に移動されています。そのため、`ADD RESTORE SOURCE`コマンドを使用してバックアップパスを読み込む際には、新しい保存パス`oss://test_bucket/archive/piece_1`を選択する必要があります。

4. `ADD RESTORE SOURCE`コマンドを実行して、復元に必要なbackup_setとarchivelog_pieceをそれぞれ読み込みます。

   ロードパスのステートメントは次のとおりです：

   ```sql
   ALTER SYSTEM ADD RESTORE SOURCE 'restore_path';
   ```

   ステートメントの使用方法：

   * `restore_path`：読み込むbackup_setまたはarchivelog_pieceのパスを入力します。1つのパスでも複数のパスでも構いません。

      <main id="notice" type='notice'>
      <h4>注意</h4>
      <p>読み込むbackup_setまたはarchivelog_pieceがオブジェクトストレージに保存されている場合、各backup_setまたはarchivelog_pieceのパスに含まれる<code>host</code>、<code>access_id</code>、および<code>access_key</code>などのパラメータ情報がすべて同一であることが求められます。</p>
      </main>

   * このステートメントは、同一セッション内で連続して複数回実行できます。同一セッション内で複数回実行する場合、システムは復元ソースリストに増分で追加します。

   例：

   1. 復元対象のbackup_setを読み込みます。

      ```shell
      obclient [oceanbase]> ALTER SYSTEM ADD RESTORE SOURCE 'file:///ob_backup/data/backup_set_1_full';
      ```

   2. 復元対象のarchivelog_pieceを読み込みます。

      ```shell
      obclient [oceanbase]> ALTER SYSTEM ADD RESTORE SOURCE 'file:///ob_backup/archive/piece_d1002r1p1,file:///ob_backup/archive/piece_d1002r1p2';
      ```

      ```shell
      obclient [oceanbase]> ALTER SYSTEM ADD RESTORE SOURCE 'oss://test_bucket/archive/piece_1?host=***&access_id=x****&access_key=****';
      ```

5. （オプション）backup_setまたはarchivelog_pieceの読み込み中に、誤ったパスが入力されたことが判明した場合、以下のステートメントを実行して以前の入力を取り消し、正しい復元パスを再度読み込むことができます。

    ```shell
    obclient [oceanbase]> ALTER SYSTEM CLEAR RESTORE SOURCE;
    ```

6. すべてのパスの読み込みが成功した後、復元コマンドを呼び出します。

   <main id="notice" type='notice'>
   <h4>注意</h4>
   <ul>
   <li>復元コマンドを実行する際には、<code>ADD RESTORE SOURCE</code>コマンドを実行したセッションと同一のセッションである必要があります。異なるセッション（元のセッションが中断されたか、新しいセッションが使用された場合）であると、以前に読み込んだ復元ソースリストがクリアされます。</li>
   <li><code>ADD RESTORE SOURCE</code>コマンドを実行した後、同一セッション内でバックアップ宛先を指定する復元コマンドを使用してテナントを復元することは許可されません。</li>
   <li>復元コマンドを実行した後、復元に成功したかどうかにかかわらず、以前に読み込んだ復元ソースリストはクリアされます。復元コマンドを再度呼び出す必要がある場合は、復元に必要なbackup_setとarchivelog_pieceを再度読み込む必要があります。</li>
   </ul>
   </main>

   以下のステートメントを実行します：

   ```sql
   ALTER SYSTEM RESTORE restore_tenant_name [UNTIL {TIME='timestamp' | SCN=scn} ] WITH 'restore_option';
   ```

   パラメータの一部の説明は以下のとおりです：

   * `restore_tenant_name`：復元対象の新しいテナントの名前。

   * `UNTIL {TIME='timestamp' | SCN=scn}`：復元する時間を指定します。

      * `timestamp`：復元するタイムスタンプを指定します。

      * `scn`：復元するSCNを指定します。

      * `UNTIL TIME='timestamp'`または`UNTIL SCN=scn`を指定しない場合、デフォルトでは復元可能な最新のポイントに復元されます。

   * `restore_option`：`pool_list`、`locality`、`primary_zone`、`concurrency`を指定できます。異なるパラメータ間は`&`で区切ります。`locality`と`primary_zone`を指定する際は、ソーステナントと同構成に保つことを推奨します。異構成の場合、復元後に新しいテナントがプライマリテナントとしてアクティブ化されると、ロードバランシング操作が発生し、パフォーマンスに影響を与える可能性があります。

      * `pool_list`：必須項目。復元対象の新しいテナントが作成されたリソースプールを入力します。複数のリソースプールは、英語のカンマ（,）で区切ります。

      * `Locality`：新しいテナントのレプリカ配置のローカリティ情報を指定します。新しいテナントが存在するクラスタの`pool_list`のゾーン情報と一致させる必要があります。ソーステナントと同構成の場合、新しいテナントのFレプリカ数がソーステナントと同じであることを推奨します。

      * `primary_zone`：新しいテナントのリーダーレプリカの優先位置を指定します。`pool_list`および`locality`と一致させる必要があります。ソーステナントと同構成の場合、新しいテナントの第一優先順位のPrimary Zone数がソーステナントと同じであることを推奨します。

      * `concurrency`：データ復元の並列度を指定します。指定しない場合、デフォルトでそのテナントに割り当てられたMAX_CPU数に等しくなります。例えば、本記事では、システムテナントが復元対象のテナントに割り当てたMAX_CPUは16です。

      各パラメータの詳細については、[物理復元関連パラメータの紹介](800.parameters-of-the-restore.md)を参照してください。

   復元コマンドを呼び出す例は次のとおりです：

   * 指定されたパスからテナント`mysql`を指定されたSCN`1658285759724047000`に復元し、リソースプールを`restore_pool`と指定します。

      ```shell
      obclient [oceanbase]> ALTER SYSTEM RESTORE mysql UNTIL SCN = 1712650554000909004 WITH 'pool_list=restore_pool';
      ```

   * 指定されたパスからテナント`mysql`を指定されたタイムスタンプ`2024-04-09 16:15:54`に復元し、リソースプールを`restore_pool`と指定します。

      ```shell
      obclient [oceanbase]> ALTER SYSTEM RESTORE mysql UNTIL TIME = '2024-04-09 16:15:54' WITH 'pool_list=restore_pool';
      ```

## 次のステップ

* リカバリタスクを開始した後、ビューを使用してリカバリの進捗状況と結果を確認できます。具体的な操作については、[リカバリの進捗状況を確認する](../600.restore-data/400.view-the-restore-progress.md)を参照してください。

* リカバリタスクが完了した場合、低バージョンのバックアップデータから高バージョンのクラスタに復元するシナリオでは、復元されたテナントをアップグレードする必要があります。具体的な操作については、[リカバリ完了後のテナントのアップグレード](610.update-the-tenant-after-the-restore.md)を参照してください。

* 物理リカバリのプロセスは物理スタンバイデータベースと統一されており、物理リカバリ後のテナントはスタンバイテナントとなります。その後、このテナントはスタンバイテナントとして関連サービスを提供することも、プライマリテナントとしてサービスを提供することもできます。スタンバイテナントとして引き続きログアーカイブを行い、ソーステナントからログを再生する詳細な操作については、[スタンバイテナントによるセグメントログ再生](510.recover-the-standby-tenant.md)を参照してください。スタンバイテナントをプライマリテナントに変更する詳細な操作については、[スタンバイテナントをプライマリテナントに変更する](600.active-standby-tenant.md)を参照してください。
