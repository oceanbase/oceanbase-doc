# アーカイブログバックアップの開始

<main id="notice" type='explain'>
<h4>説明</h4>
<p>V4.4.2バージョンでは、V4.4.2 BP3バージョンからアーカイブログのバックアップがサポートされています。</p>
</main>

ログをアーカイブした後、アーカイブ済みのログデータをバックアップし、ログアーカイブの出力先 `LOG_ARCHIVE_DEST` にあるフリーズ(FROZEN)状態のアーカイブピースを独立したバックアップ出力先 `BACKUP_ARCHIVE_DEST` にバックアップできます。バックアップ完了後、元のアーカイブメディア上のログデータは安全に回収でき、アーカイブ容量が解放されるため、アーカイブメディアの容量上限に達してアーカイブが途絶えることを防ぐことができます。

アーカイブログバックアップの典型的なユースケースは以下のとおりです：

* アーカイブ容量の回収：古いアーカイブピースを定期的にバックアップし、`DELETE INPUT`オプションを使用して、ソース側にあるバックアップ済みのアーカイブログファイルを自動的にクリーンアップします。
* 階層型ストレージ：ログアーカイブの出力先に最新のログを保存し、バックアップの出力先により古いフリーズログを保存します。

## 前提条件

アーカイブログバックアップを開始する前に、以下の条件を満たしていることを確認する必要があります：

* アーカイブモードが有効になっていること。テナントの `LOG_MODE` が `ARCHIVELOG` の場合にのみ、アーカイブログバックアップを開始できます。アーカイブモードを有効にする操作については、[アーカイブモードの有効化](300.open-the-log-archive-mode.md)を参照してください。

## アーカイブログのバックアップ宛先の設定

アーカイブログバックアップを開始する前に、アーカイブログのバックアップ宛先を設定する必要があります。これは、アーカイブログバックアップファイルの保存パスを指定するために使用されます。システムテナントのみが `TENANT = <tenant_name>` 句を使用して操作対象のテナントを指定する必要があります。ユーザーテナントは自身のテナントに対してのみこの操作を実行できるため、この句を指定する必要はありません。

### システムテナントによるアーカイブログのバックアップ宛先の設定

`sys` テナントは、クラスタ内の指定したユーザーテナントのアーカイブログのバックアップ宛先を設定できます。

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

2. 以下のステートメントを実行し、指定したユーザーテナントのアーカイブログのバックアップ宛先を設定します。

   ```sql
   ALTER SYSTEM SET BACKUP_ARCHIVE_DEST = 'location=<backup_archive_path>' TENANT = <tenant_name>;
   ```

   ここで、`<backup_archive_path>` はバックアップ宛先の保存パスであり、NFS、Alibaba Cloud OSS、Azure Blob、AWS S3、およびS3プロトコル互換のオブジェクトストレージなどのストレージメディアをサポートしています。`<backup_archive_path>` の詳細な形式については、[SET BACKUP_ARCHIVE_DEST](../../../700.reference/500.sql-reference/100.sql-syntax/100.system-tenants/200.alter-system/3850.set-backup-archive-dest.md)を参照してください。

   <main id="notice" type='explain'>
   <h4>説明</h4>
   <p>アーカイブログのバックアップ宛先は、ログアーカイブの宛先と同じにすることはできません。つまり、BACKUP_ARCHIVE_DEST と LOG_ARCHIVE_DEST の保存パス情報は異なっている必要があります。</p>
   </main>

   例：

   * バックアップ宛先のストレージメディアがNFSの場合。

      ```sql
      obclient [(none)]> ALTER SYSTEM SET BACKUP_ARCHIVE_DEST = 'location=file:///data/nfs/backup/backup_archive' TENANT = mysql_tenant;
      ```

   * バックアップ宛先のストレージメディアがOSSの場合。

      ```sql
      obclient [(none)]> ALTER SYSTEM SET BACKUP_ARCHIVE_DEST = 'location=oss://oceanbase-test-bucket/backup/backup_archive?host=****.aliyun-inc.com&access_id=****&access_key=****' TENANT = mysql_tenant;
      ```

### ユーザーテナントによるアーカイブログのバックアップ宛先の設定

ユーザーテナントは自身のテナントに対してアーカイブログのバックアップ宛先を設定でき、他のテナントには影響しません。

1. テナント管理者がデータベースにログインします。

    この例では、`root` ユーザーで `mysql_tenant` テナントにログインするか、`SYS` ユーザーで `oracle_tenant` テナントにログインすることができます。

2. 以下のステートメントを実行し、自身のテナントのアーカイブログバックアップ宛先を設定します。

   ```sql
   ALTER SYSTEM SET BACKUP_ARCHIVE_DEST = 'location=<backup_archive_path>';
   ```

   <main id="notice" type='explain'>
   <h4>説明</h4>
   <p>アーカイブログのバックアップ宛先は、ログアーカイブの宛先と同じにすることはできません。つまり、BACKUP_ARCHIVE_DESTとLOG_ARCHIVE_DESTのストレージパス情報は異なっている必要があります。</p>
   </main>

   例：

   * バックアップ宛先のストレージメディアはNFSです。

      ```sql
      obclient [(none)]> ALTER SYSTEM SET BACKUP_ARCHIVE_DEST = 'location=file:///data/nfs/backup/backup_archive';
      ```

   * バックアップ宛先のストレージメディアはOSSです。

      ```sql
      obclient [(none)]> ALTER SYSTEM SET BACKUP_ARCHIVE_DEST = 'location=oss://oceanbase-test-bucket/backup/backup_archive?host=****.aliyun-inc.com&access_id=****&access_key=****';
      ```

## アーカイブログバックアップの開始

バックアップ宛先の設定が完了したら、`ALTER SYSTEM BACKUP ARCHIVELOG` ステートメントを使用してアーカイブログバックアップを開始できます。ステートメントは以下のとおりです：

```sql
ALTER SYSTEM BACKUP ARCHIVELOG ALL [DELETE INPUT] [TENANT = <tenant_name>];
```

`DELETE INPUT` オプションを指定するかどうかによって、アーカイブログバックアップの動作は異なります：

* `DELETE INPUT` を指定しない場合、アーカイブ済みのログデータのみを `BACKUP_ARCHIVE_DEST` にバックアップし、ソース側のアーカイブログファイルは削除しません。
* `DELETE INPUT` を指定した場合、現在のタスクでFROZEN状態のすべてのPieceが正常にバックアップされた後にのみ、システムはクリーンアップタスクを生成し、ソース側にあるバックアップ済みのアーカイブログファイルを自動的に削除してストレージ容量を解放します。アーカイブログバックアップタスクが失敗した場合は、ソース側のコピーはクリーンアップされません。

アーカイブログバックアップのタスク説明は以下のとおりです：

* アーカイブログバックアップは非同期タスクであり、ステートメントの実行が成功したことは、タスクが作成・送信されたことを意味するだけです。タスクはバックグラウンドで実行され、バックアップタスク関連のビューでタスクの進捗状況と結果を確認できます。
* アーカイブログバックアップはPiece単位で処理され、コピー後も元のディレクトリ構造とファイル形式を完全に保持し、アーカイブログに一切の変更を加えません。
* アーカイブログバックアップはFROZEN状態のPieceのみを処理し、Pieceのフリーズを自動的にトリガーしたり、書き込み中のACTIVE Pieceをバックアップしたりすることはありません。また、ログアーカイブがソース側のACTIVE Pieceへの書き込みを継続することにも影響しません。FROZEN状態のPieceが存在しない場合、タスクは正常に完了しますが、データはコピーされません。
* タスク開始時に、今回バックアップ対象となるPieceが特定されます。既にバックアップ済みのPieceは再度バックアップされません。タスク実行中に新たにフリーズしたPieceは、次回のアーカイブログバックアップタスクで処理されます。
* Pieceのバックアップが成功すると、そのPieceのバックアップ宛先上のコピーファイルの状態は`AVAILABLE`に更新されます。

<main id="notice" type='explain'>
<h4>説明</h4>
<p>アーカイブログバックアップはPieceごとに並列スケジューリングされ、ファイルレベルでログアーカイブ宛先からバックアップ宛先へデータをコピーします。単一Pieceのコピーは、ログストリームディレクトリに従って分割・並列実行されます。コピー速度はPieceのデータサイズ、および両宛先のストレージの読み書きスループットとリクエスト遅延に依存し、このプロセスではOBServerノード上で追加のI/Oオーバーヘッドは発生しません。</p>
</main>

### システムテナントによるアーカイブログバックアップの開始

`sys` テナントは、クラスタ内の指定されたテナントに対してアーカイブログバックアップを開始できます。このコマンドを実行する際、システムテナントのみが `TENANT = <tenant_name>` 句を使用して操作対象のテナントを指定する必要があります。

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

2. 以下のステートメントを実行して、アーカイブログバックアップを開始します。

   * `mysql_tenant` テナントに対してアーカイブログバックアップを開始する例：

      ```sql
      obclient [(none)]> ALTER SYSTEM BACKUP ARCHIVELOG ALL TENANT = mysql_tenant;
      ```

   * `mysql_tenant` テナントに対してアーカイブログバックアップを開始し、バックアップ完了後にソース側のアーカイブログファイルを自動的に削除する例：

      ```sql
      obclient [(none)]> ALTER SYSTEM BACKUP ARCHIVELOG ALL DELETE INPUT TENANT = mysql_tenant;
      ```

   コマンドが正常に実行されると、システムは指定されたテナントに対してアーカイブログバックアップを開始します。

### ユーザーテナントによるアーカイブログバックアップの開始

ユーザーテナントは自身のテナントに対してアーカイブログバックアップを開始でき、他のテナントには影響しません。ユーザーテナントは自身のテナントでのみこのコマンドを実行できるため、`TENANT` 句を指定する必要はありません。

1. テナント管理者がデータベースにログインします。

    この例では、`root`ユーザーで`mysql_tenant`テナントにログインするか、`SYS`ユーザーで`oracle_tenant`テナントにログインすることができます。

2. 以下のステートメントを実行して、アーカイブログバックアップを開始します。

   * 自身のテナントに対してアーカイブログバックアップを開始する例：

      ```sql
      obclient [(none)]> ALTER SYSTEM BACKUP ARCHIVELOG ALL;
      ```

   * 自身のテナントに対してアーカイブログバックアップを開始し、バックアップ完了後にソース側のアーカイブログファイルを自動的に削除する例：

      ```sql
      obclient [(none)]> ALTER SYSTEM BACKUP ARCHIVELOG ALL DELETE INPUT;
      ```

   コマンドが正常に実行されると、システムは該当テナントに対してアーカイブログバックアップを開始します。

## 注意事項

* `DELETE INPUT` はソース側の物理レプリカを削除します。使用する前に、バックアップ先のストレージの信頼性とアクセス可能性を確認し、リストアプロセスも検証してください。

* CDCを使用してアーカイブデータを直接消費する必要がある場合は、`DELETE INPUT`オプションの使用は推奨されません。ソース側のFROZEN状態のPieceがクリーンアップされると、CDCがデータディクショナリを読み取れなくなる可能性があります。

* バックアップ先にはFROZEN状態のPieceのみが保存されます。より新しいポイントへのリストア時には、通常、新しいPieceとACTIVE状態の末尾部分を含むログアーカイブ先を提供する必要があります。リストア時には、データバックアップパス、ログアーカイブパス、アーカイブログバックアップパスを同時に指定できます。システムは必要に応じて対応するPieceを読み取ります。関連する操作については、[リストアの開始](../600.restore-data/200.initiate-the-tenant-restore.md)を参照してください。

* 現在のバックアップクリーンアップポリシーはアーカイブログバックアップに対応しています。バックアップクリーンアップ設定の `RECOVERY_WINDOW` はバックアップ先のレプリカにも適用されます。つまり、ログアーカイブ先とバックアップ先は `default` または `log_only` クリーンアップポリシーのクリーンアップ境界を共有し、それぞれの出力先に独立した `RECOVERY_WINDOW` を設定することはサポートされていません。自動的に期限切れバックアップをクリーンアップする操作の詳細については、[自動的に期限切れバックアップをクリーンアップする](../500.clear-backup-data/50.automatic-backup-cleanup/100.cleaning-up-backed-up-data-automatically.md)を参照してください。

* アーカイブログバックアップと期限切れバックアップのクリーンアップタスクは同一テナント上で同時実行できません。システムはどちらか一方のタスクを拒否または遅延させます。

* アーカイブログバックアップは他のタスクと以下の排他関係にあります：

  * `BACKUP_ARCHIVE_DEST` の変更とアーカイブログバックアップの開始は排他的です：`BACKUP_ARCHIVE_DEST` を変更している間にアーカイブログバックアップを開始すると失敗します。アーカイブログバックアップタスクが終了していない間は `BACKUP_ARCHIVE_DEST` の変更を許可せず、システムは `OPT_NOT_ALLOW` エラーを返します。

  * `BACKUP_ARCHIVE_DEST` の変更と `PLUS ARCHIVELOG` パラメータを持つデータバックアップタスクは排他的です：`PLUS ARCHIVELOG` パラメータを持つデータバックアップタスクの実行中には、`BACKUP_ARCHIVE_DEST` からPieceファイルをコピーする可能性があるため、Pieceがコピーされながら削除される状況を避けるために、`BACKUP_ARCHIVE_DEST` を変更している間に `PLUS ARCHIVELOG` パラメータを持つデータバックアップタスクを開始すると失敗します。`PLUS ARCHIVELOG` パラメータを持つデータバックアップタスクの実行中に `BACKUP_ARCHIVE_DEST` を変更すると、変更操作が失敗し、システムは `OPT_NOT_ALLOW` エラーを返します。

  * `DELETE INPUT` を伴うアーカイブログバックアップによって開始されるソース側レプリカのクリーンアップタスクと、`PLUS ARCHIVELOG` パラメータを持つデータバックアップタスクは排他的です：クリーンアップタスクを開始する前に、システムは同一テナント内で実行中の `PLUS ARCHIVELOG` パラメータを持つデータバックアップタスクがないかチェックします。もしある場合、アーカイブログバックアップは正常に実行されますが、対応するクリーンアップタスクは失敗します。`PLUS ARCHIVELOG` パラメータを持つデータバックアップタスクを開始する前に、システムは実行中のソース側レプリカのクリーンアップタスクがないかチェックします。もしある場合、そのデータバックアップタスクは失敗し、クリーンアップタスクが終了するのを待ってから再度開始する必要があります。
