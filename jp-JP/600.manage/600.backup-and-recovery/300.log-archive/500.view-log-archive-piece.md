# Piece情報の確認

ログアーカイブを有効にすると、ビューを通じてPiece情報を確認できます。

## 背景

このセクションでは、ログアーカイブにおけるPieceの表示方法についてのみ説明します。Pieceの詳細については、[ログアーカイブの概要](../300.log-archive/100.overview-of-log-archive.md)を参照してください。

## システムテナントによるすべてのテナントのすべてのPiece情報の確認

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

   上記の例では、テナントIDが `1002` のテナントには4つのPiece情報があり、テナントIDが `1004` のテナントには2つのPiece情報があります。

   `1002` テナントの4つのPieceについて：

   * `piece_id` がそれぞれ `1` から `3` の3つのPieceの `round_id` はすべて `1` であり、これら3つのPieceはすべて第1ラウンドのアーカイブで生成されたことを示しています。`piece 4` は第2ラウンドのアーカイブで生成されました。`piece 1` のログの連続範囲は `'2022-06-01 06:00:00.000000'` から `'2022-06-02 05:59:00.000000'` で、元のログデータ量は `25GB`、アーカイブ後の実際のデータ量も `25GB`、データ圧縮率は `1.00` です。また、`piece 1` の `FILE_STATUS` フィールドの値は `DELETED` であり、このPieceのデータは期限切れによりクリーンアップされたことを示しています。`STATUS` フィールドの値は `FROZEN` であり、このPieceのデータは完全であり、今後ログがアーカイブされることはないことを示しています。

   * `piece id` が `2` から `4` の3つのPieceの `FILE_STATUS` フィールドの値は `AVAILABLE` であり、これら3つのPieceのデータはまだアクセス可能であること、つまり削除されていないことを示しています。`piece 3` の `CHECKPOINT_SCN` が `'2022-06-04 06:00:00.000000'` に達する前に `FROZEN` に変わった原因は、ユーザーがアーカイブを停止したため、`piece 3` にデータをアーカイブしなくなったことです。現在、`1002` テナントは第2ラウンドのアーカイブを進行中であり、`piece 4` はそのラウンドで生成された最初のPieceで、`STATUS` は `ACTIVE` であり、アーカイブ中のPieceであることを示しています。
   `1004` テナントもアーカイブを進行中であり、これは同テナントにとっての第1ラウンドのアーカイブです。既に2つのPieceが生成されており、`piece id` はそれぞれ `1` と `2` です。`piece 1` は完了しており、状態は `FROZEN` です。`piece 2` は現在アーカイブ中で、状態は `ACTIVE` です。

## ユーザーテナントが自身のテナント内のすべてのPiece情報を確認する

ユーザーテナントは、`oceanbase.DBA_OB_ARCHIVELOG_PIECE_FILES` ビュー（MySQLモード）および `sys.DBA_OB_ARCHIVELOG_PIECE_FILES` ビュー（Oracleモード）を使用して、自身のテナント内のすべてのPiece情報を確認できます。

1. ユーザーテナントのテナント管理者がデータベースにログインします。

   <main id="notice" type='explain'>
   <h4>説明</h4>
   <p>MySQLテナントの管理者ユーザーは <code>root</code> ユーザー、Oracleテナントの管理者ユーザーは <code>SYS</code> ユーザーです。</p>
   </main>

2. 以下のステートメントを実行して、現在のテナントのすべてのPieceを確認します。

   MySQLテナントで自身のテナント内のすべてのPieceを確認する例：
