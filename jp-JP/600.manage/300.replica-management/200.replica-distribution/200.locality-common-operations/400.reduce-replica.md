# レプリカの削減

本記事では、テナント内のログストリームのレプリカ数を削減する方法について説明します。

## Localityを変更してレプリカを削減する

クラスタ内の特定のテナントのLocalityを変更することで、そのテナント配下のログストリームのレプリカ数を削減できます。Localityの変更手順および注意事項の詳細については、[Localityの変更](../200.locality-common-operations/200.modify-locality.md)を参照してください。

### 前提条件

Localityを変更する前に、変更対象Zone上の各ノードのリソース割り当て状況を確認する必要があります。Zone上のノードのリソースが不足し、テナントが必要とするリソースユニットを格納できない場合は、Localityの変更を実行できません。

Zone上の各ノードのリソース割り当て状況については、[テナントとリソース情報の確認](../../../200.tenant-management/600.common-tenant-operations/400.view-tenant-information.md)を参照してください。

### 注意事項

* テナントのLocalityは空にすることはできません。

* テナントのLocalityが変更されると、そのテナント配下のすべてのテーブルのレプリカ配置も変更されます。

* 前回のテナントLocalityの変更が完了する前に、新たなテナントLocalityの変更を実行することはできません。

* レプリカを削減した後、リソースを解放する場合は、対象テナントのリソースプールを縮小する必要があります。

   `z1,z2,z3` を例にすると、`z3` を削除する場合、以下の2つのシナリオがあります：

   1. テナントが `z3` 上に独立したリソースプールを持っている場合。例えば、テナントが `resource_pool1` と `resource_pool2` の2つのリソースプールを持ち、そのうち `resource_pool2` が `z3` に配置されている場合、レプリカを削減した後は、`resource_pool2` をテナントのリソースプールリストから削除し、その後リソースプールを削除してリソースを実際に解放することができます。リソースプールの削除手順の詳細については、[リソースプールの削除](../../../200.tenant-management/600.common-tenant-operations/1500.resource-pool-management/600.delete-resource-pool.md)を参照してください。

   2. `z3` 上に独立したリソースプールがない場合。例えば、テナントのリソースプール `resource_pool1` が `z2` と `z3` に配置されている場合、レプリカを削減した後は、`resource_pool1` の `zone` リストから `z3` を削除する必要があります。これにより、リソースが実際に解放されます。リソースプールの `zone` リストの調整手順の詳細については、[リソースプール属性の変更](../../../200.tenant-management/600.common-tenant-operations/900.modify-resource-pool-properties.md)を参照してください。

### 手順

例：テナント `mysql001` のLocalityを `FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3` から `FULL{1}@zone1, FULL{1}@zone2` に変更し、テナントのレプリカ数を削減します。

<main id="notice" type='explain'>
<h4>説明</h4>
<p>ここでは、1つのZoneを削減する例を挙げています。実際の操作では、削減後のZoneの数が多数派の原則を満たす必要がある点に注意してください。</p>
</main>

1. `root` ユーザーでクラスタのsysテナントにログインします。

   ```shell
   obclient -h172.30.xxx.xxx -P2883 -uroot@sys#obdemo -pxxxx -A
   ```

2. `oceanbase` データベースに入ります。

   ```shell
   obclient(root@sys)[(none)]> use oceanbase;
   ```

3. テナント `mysql001` のLocalityを変更する前の状態を確認します。

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID,TENANT_NAME,TENANT_TYPE,PRIMARY_ZONE,LOCALITY FROM oceanbase.DBA_OB_TENANTS;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE      | LOCALITY                                    |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   |         1 | sys         | SYS         | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1001 | META$1002   | META        | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1002 | mysql001    | USER        | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   3 rows in set
   ```

   テナント `mysql001` がゾーン1、ゾーン2、ゾーン3にそれぞれフル機能レプリカを1つずつ持っていることが確認できます。

4. テナント `mysql001` のローカリティを変更します。

   ```shell
   obclient(root@sys)[oceanbase]> ALTER TENANT mysql001 locality="FULL{1}@zone1, FULL{1}@zone2";
   ```

5. ローカリティ変更タスクの実行状態を確認します。

   ```shell
   obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_TENANT_JOBS WHERE JOB_TYPE = 'ALTER_TENANT_LOCALITY';
   ```

   クエリ結果は次のとおりです：

   ```shell
   +--------+-----------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+------------------------------------------------------------------------------+---------------------------------------------+----------------+-------------+
   | JOB_ID | JOB_TYPE              | JOB_STATUS | RESULT_CODE | PROGRESS | START_TIME                 | MODIFY_TIME                | TENANT_ID | SQL_TEXT                                                                     | EXTRA_INFO                                  | RS_SVR_IP      | RS_SVR_PORT |

   +--------+-----------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+------------------------------------------------------------------------------+---------------------------------------------+----------------+-------------+
   1 row in set
   ```

   `JOB_STATUS` が `SUCCESS` の場合、ローカリティ変更タスクは正常に実行されたことを示します。

6. テナント `mysql001` の変更後のローカリティを確認します。

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID,TENANT_NAME,TENANT_TYPE,PRIMARY_ZONE,LOCALITY FROM oceanbase.DBA_OB_TENANTS;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE      | LOCALITY                                    |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   |         1 | sys         | SYS         | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1001 | META$1002   | META        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2                |
   |      1002 | mysql001    | USER        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2                |
   ```

   ステップ3とステップ6のクエリ結果を比較すると、テナント `mysql001` のローカリティは元の `FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3` から `FULL{1}@zone1, FULL{1}@zone2` に変更され、テナント `mysql001` のレプリカ数が減少しています。

## レプリカの手動削除

Localityを変更してレプリカ数を削減する場合、通常はシステムが自動的に余分なレプリカを削除します。しかし、一部の異常な理由によりシステムが正常に動作しない場合は、`ALTER SYSTEM REMOVE REPLICA`コマンドを使用して余分なログストリームのレプリカを手動で削除できます。

### 使用上の制限

* システムテナント(sysテナント)はすべてのテナントのログストリームを管理できますが、ユーザーテナントは自身のテナントのログストリームのみを管理できます。

* テナント内の同一ログストリームについて、レプリカ移行タスクは複数並列実行可能ですが、その他のディザスタリカバリタスク(レプリカの追加、削除、レプリカタイプの変更、ログストリームの法定メンバー数の変更など)は、1回につき1つのみ実行できます。

   sysテナントはビュー`CDB_OB_LS_REPLICA_TASKS`を参照して実行中のディザスタリカバリタスクを確認できます。ユーザーテナントはビュー`DBA_OB_LS_REPLICA_TASKS`を参照して実行中のディザスタリカバリタスクを確認できます。

### 前提条件

* レプリカ削除操作を実行する前に、現在のユーザーが`ALTER SYSTEM`権限を持っていることを確認してください。持っていない場合は`ALTER SYSTEM REMOVE REPLICA`コマンドを実行できません。

* ビューをクエリする前に、現在のユーザーが以下のビューに対する`SELECT`権限を持っていることを確認してください。持っていない場合は関連情報をクエリできません。

  * `DBA_OB_TENANTS`

  * `DBA_OB_LS`/`CDB_OB_LS`

  * `DBA_OB_LS_LOCATIONS`/`CDB_OB_LS_LOCATIONS`

### 手順

現在、tenant1テナントがあり、そのLocalityが`F@zone1,F@zone3`であると仮定します。同時に、tenant1テナントのログストリーム1001は`zone1`、`zone2`、`zone3`にそれぞれFタイプのレプリカを1つずつ持っています。今回は`zone2`上のレプリカを手動で削除する必要があります。

5. レプリカ削除コマンドを実行します。

   ステートメントは以下のとおりです：

   ```sql
   ALTER SYSTEM REMOVE REPLICA LS [=] ls_id SERVER [=] 'svr_ip:svr_port' [PAXOS_REPLICA_NUM [=] paxos_replica_num] [TENANT [=] 'tenant_name'];
   ```

   ステートメントの使い方：

   * `ls_id`：削除対象のレプリカのログストリームIDを指定します。

   * `svr_ip:svr_port`：削除対象のレプリカが存在するサーバーのIPアドレスとポート番号を指定します。例：`172.xx.xxx.212:2882`。

   * `paxos_replica_num`：変更後のログストリームの過半数メンバー数、すなわちテナントのローカリティにおけるフル機能型（F）レプリカの数を指定します。また、同一ログストリームのFレプリカ数は最大7個です。

      このパラメータの値を指定する場合、以下の条件を満たす必要があります：

      1. 変更後の `paxos_replica_num` は過半数を満たす必要があります。

      2. `paxos_replica_num` の値は、現在のリーダーレプリカの `MEMBER_LIST` に含まれるメンバー数以上である必要があります。

      3. `paxos_replica_num` の値の変化幅は1を超えてはなりません。例えば、この例では現在の `paxos_replica_num` は `3` なので、`paxos_replica_num` を `2` に変更することしかできません。

      指定した値が上記のいずれかの条件を満たさない場合、システムはエラーを返します。この値を明示的に指定しない場合、システムは現在のデフォルトの `paxos_replica_num` を使用します。

   * `tenant_name`：操作対象のテナントを指定します。システムテナントは他のテナントを指定できますが、ユーザーテナントは自身のテナントのみを指定できます。操作対象のテナントを明示的に指定しない場合、デフォルトのテナント名は現在のテナントになります。このステートメントでは、`all`、`all_user`、`all_meta` などを使用してすべてのテナント、ユーザーテナント、およびすべてのMetaテナントを指定することはできません。

   * このステートメントでは、一度に1つのレプリカしか削除できません。

   ログストリーム1001の `172.xx.xxx.212:2882` 上のレプリカを削除し、削除後の `PAXOS_REPLICA_NUM` を2に設定する例を以下に示します：

   ```shell
   obclient> ALTER SYSTEM REMOVE REPLICA LS = 1001 SERVER = '172.xx.xxx.212:2882' PAXOS_REPLICA_NUM = 2;
   ```
