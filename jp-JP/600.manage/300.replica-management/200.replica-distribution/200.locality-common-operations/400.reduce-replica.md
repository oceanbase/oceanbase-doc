# レプリカの削減

本記事では、テナント内のログストリームのレプリカ数を削減する方法について説明します。

## Localityの変更によるレプリカの削減

クラスタ内の特定のテナントのLocalityを変更することで、そのテナント配下のログストリームのレプリカ数を削減できます。Localityの変更手順および注意点の詳細については、[Localityの変更](../200.locality-common-operations/200.modify-locality.md)を参照してください。

### 前提条件

Localityを変更する前に、変更対象のZone上の各ノードのリソース割り当て状況を確認する必要があります。Zone上のノードのリソースが不足しており、テナントが必要とするリソースユニットを格納できない場合は、Localityの変更できません。

Zone上の各ノードのリソース割り当て状況については、[テナントとリソース情報の確認](../../../200.tenant-management/600.common-tenant-operations/400.view-tenant-information.md)を参照してください。

### 注意事項

* テナントのLocalityは空欄不可です。

* テナントのLocalityが変更されると、そのテナント配下のすべてのテーブルのレプリカ配置も変更されます。

* 前回のテナントLocalityの変更が完了する前に、新たなテナントLocalityは変更できません。

* レプリカを削減した後、リソースを解放する場合は、対象テナントのリソースプールを縮小する必要があります。

   `z1,z2,z3` を例にすると、`z3` を削除する場合、以下の2つのシナリオがあります：

   1. テナントが `z3` 上に独立したリソースプールを持っている場合。例えば、テナントが `resource_pool1` と `resource_pool2` の2つのリソースプールを持ち、そのうち `resource_pool2` が `z3` に配置されている場合、レプリカを削減した後は、`resource_pool2` をテナントのリソースプールリストから削除し、必要に応じてリソースプールを削除してリソースを実際に解放する必要があります。リソースプールの削除手順の詳細については、[リソースプールの削除](../../../200.tenant-management/600.common-tenant-operations/1500.resource-pool-management/600.delete-resource-pool.md)を参照してください。

   2. `z3` 上に独立したリソースプールがない場合。例えば、テナントのリソースプール `resource_pool1` が `z2` と `z3` に配置されている場合、レプリカを削減した後は、`resource_pool1` の `zone` リストから `z3` を削除し、リソースを実際に解放する必要があります。リソースプールの `zone` リストを調整する手順の詳細については、[リソースプールのプロパティの変更](../../../200.tenant-management/600.common-tenant-operations/900.modify-resource-pool-properties.md)を参照してください。

### 操作手順

例：テナント `mysql001` のLocalityを変更し、`FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3` から `FULL{1}@zone1, FULL{1}@zone2` に変更して、テナントのレプリカ数を削減します。

<main id="notice" type='explain'>
<h4>説明</h4>
<p>ここではゾーンを1つ削減する例を示していますが、実際の操作では、削減後のゾーン数が過半数の原則を満たすように注意してください。</p>
</main>

1. `root` ユーザーでクラスタのsysテナントにログインします。

   ```shell
   obclient -h172.30.xxx.xxx -P2883 -uroot@sys#obdemo -pxxxx -A
   ```

2. `oceanbase` データベースに入ります。

   ```shell
   obclient(root@sys)[(none)]> use oceanbase;
   ```

3. テナント `mysql001` のLocalityを変更する前の状態を確認します。

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID,TENANT_NAME,TENANT_TYPE,PRIMARY_ZONE,LOCALITY FROM oceanbase.DBA_OB_TENANTS;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE      | LOCALITY                                    |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   |         1 | sys         | SYS         | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1001 | META$1002   | META        | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1002 | mysql001    | USER        | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   3 rows in set
   ```

   テナント `mysql001` はzone1、zone2、zone3にそれぞれフル機能レプリカを1つずつ持っていることが確認できます。

4. テナント `mysql001` のLocalityを変更します。

   ```shell
   obclient(root@sys)[oceanbase]> ALTER TENANT mysql001 locality="FULL{1}@zone1, FULL{1}@zone2";
   ```

5. Locality変更タスクの実行状態を確認します。

   ```shell
   obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.DBA_OB_TENANT_JOBS WHERE JOB_TYPE = 'ALTER_TENANT_LOCALITY';
   ```

   クエリ結果は次のとおりです：

   ```shell
   +--------+-----------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+------------------------------------------------------------------------------+---------------------------------------------+----------------+-------------+
   | JOB_ID | JOB_TYPE              | JOB_STATUS | RESULT_CODE | PROGRESS | START_TIME                 | MODIFY_TIME                | TENANT_ID | SQL_TEXT                                                                     | EXTRA_INFO                                  | RS_SVR_IP      | RS_SVR_PORT |

   +--------+-----------------------+------------+-------------+----------+----------------------------+----------------------------+-----------+------------------------------------------------------------------------------+---------------------------------------------+----------------+-------------+
   1 row in set
   ```

   `JOB_STATUS` が `SUCCESS` の場合、Locality変更タスクは正常に実行されたことを意味します。

6. テナント `mysql001` のLocalityを変更した後の状態を確認します。

   ```shell
   obclient(root@sys)[oceanbase]> SELECT TENANT_ID,TENANT_NAME,TENANT_TYPE,PRIMARY_ZONE,LOCALITY FROM oceanbase.DBA_OB_TENANTS;
   ```

   クエリ結果は次のとおりです：

   ```shell
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   | TENANT_ID | TENANT_NAME | TENANT_TYPE | PRIMARY_ZONE      | LOCALITY                                    |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   |         1 | sys         | SYS         | zone1;zone2;zone3 | FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3 |
   |      1001 | META$1002   | META        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2                |
   |      1002 | mysql001    | USER        | zone1;zone2       | FULL{1}@zone1, FULL{1}@zone2                |
   +-----------+-------------+-------------+-------------------+---------------------------------------------+
   3 rows in set
   ```

   ステップ3とステップ6のクエリ結果を比較すると、テナント `mysql001` のLocalityは元の `FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3` から `FULL{1}@zone1, FULL{1}@zone2` に変更され、テナント `mysql001` のレプリカ数が削減されました。

## レプリカの手動削除

Localityを変更してレプリカ数を減らす場合、通常はシステムが余分なレプリカを自動的に削除します。ただし、何らかのエラーでシステムが正常に動作しない場合は、`ALTER SYSTEM REMOVE REPLICA` コマンドを使用して余分なログストリームレプリカを手動で削除できます。

### 使用上の制限

* システムテナント(sysテナント)はすべてのテナントのログストリームを管理できますが、ユーザーテナントは自身のテナントのログストリームのみを管理できます。

* テナント内の同一ログストリームについて、レプリカ移行タスクは複数をパラレル実行可能ですが、その他のディザスタリカバリタスク(レプリカの追加、削除、レプリカタイプの変更、ログストリームの規定メンバー数の変更など)は、1回につき1つのみ実行できます。

   sysテナントはビュー`CDB_OB_LS_REPLICA_TASKS`を参照することで、実行中のディザスタリカバリタスクがあるかどうかを確認できます。ユーザーテナントはビュー`DBA_OB_LS_REPLICA_TASKS`を参照することで、実行中のディザスタリカバリタスクがあるかどうかを確認できます。

### 前提条件

* レプリカ削除操作を実行する前に、現在のユーザーが`ALTER SYSTEM`権限を持っていることを確認してください。持っていない場合は`ALTER SYSTEM REMOVE REPLICA`コマンドを実行できません。

* ビューをクエリする前に、現在のユーザーが以下のビューに対する`SELECT`権限を持っていることを確認してください。持っていない場合は関連情報をクエリできません。

  * `DBA_OB_TENANTS`

  * `DBA_OB_LS`/`CDB_OB_LS`

  * `DBA_OB_LS_LOCATIONS`/`CDB_OB_LS_LOCATIONS`

### 操作手順

現在、tenant1 テナントが存在し、そのLocalityは `F@zone1,F@zone3` です。また、tenant1 テナントのログストリーム1001は、`zone1`、`zone2`、`zone3` にそれぞれFタイプのレプリカを1つずつ持っています。今回は、手動で `zone2` 上のレプリカを削除する必要があります。

5. レプリカ削除コマンドを実行します。

   ステートメントは以下のとおりです：

   ```sql
   ALTER SYSTEM REMOVE REPLICA LS [=] ls_id SERVER [=] 'svr_ip:svr_port' [PAXOS_REPLICA_NUM [=] paxos_replica_num] [TENANT [=] 'tenant_name'];
   ```

   ステートメントの使用方法：

   * `ls_id`：削除対象のレプリカを持つログストリームIDを指定します。

   * `svr_ip:svr_port`：削除対象のレプリカが存在するサーバーのIPアドレスとポート番号を指定します。例：`172.xx.xxx.212:2882`。

   * `paxos_replica_num`：変更後のログストリームの規定メンバー数、つまりテナントのLocalityに含まれるフル機能型（F）レプリカの数を指定します。また、同一ログストリームのFレプリカ数は最大7個です。

      このパラメータの値を指定する場合、以下の条件を満たす必要があります：

      1. 変更後の `paxos_replica_num` は過半数を維持する必要があります。

      2. `paxos_replica_num` の値は、現在のリーダーレプリカの `MEMBER_LIST` に含まれるメンバー数以上である必要があります。

      3. `paxos_replica_num` の値の変化幅は1を超えてはなりません。例えば、この例では現在の `paxos_replica_num` が `3` なので、`paxos_replica_num` を `2` に変更できます。

      指定した値が上記のいずれかの条件を満たさない場合、システムはエラーを返します。この値を明示的に指定しない場合、システムは現在のデフォルトの `paxos_replica_num` を使用します。

   * `tenant_name`：操作対象のテナントを指定します。システムテナントは他のテナントを指定できますが、ユーザーテナントは自身のテナントしか指定できません。操作対象のテナントを明示的に指定しない場合、デフォルトのテナント名は現在のテナントになります。このステートメントでは、`all`、`all_user`、`all_meta` などを使用してすべてのテナント、ユーザーテナント、およびすべてのMetaテナントを指定することはできません。

   * このステートメントでは、1回につき1つのレプリカしか削除できません。

   ログストリーム1001の `172.xx.xxx.212:2882` 上のレプリカを削除し、削除後の `PAXOS_REPLICA_NUM` を2に指定する例は以下のとおりです：

   ```shell
   obclient> ALTER SYSTEM REMOVE REPLICA LS = 1001 SERVER = '172.xx.xxx.212:2882' PAXOS_REPLICA_NUM = 2;
   ```
