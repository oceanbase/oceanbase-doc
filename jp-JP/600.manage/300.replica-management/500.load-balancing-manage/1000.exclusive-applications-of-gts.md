# GTS専用アプリケーションのケーススタディ

テナントのGTS（global timestamp service）サービスは、テナントシステムログストリームによって提供され、テナント内のすべてのOBServerノードにグローバルタイムスタンプを供給します。その可用性はテナント全体の可用性に直接影響するため、クラスタ内のノード数が多く、QPSが非常に高い場合には、GTSトラフィックとユーザートラフィックを分離し、GTSの応答時間を優先的に保証する必要があります。

このセクションでは、`UNIT_NUM` を使用してスケールアップし、GTS専用モードを有効にすることで、GTSトラフィックとユーザートラフィックを分離し、ユーザー業務の安定性を向上させる方法について説明します。

## 背景情報

V4.2.5バージョンでは、OceanBaseデータベースはV4.2.5 BP5バージョンからGTS専有機能をサポートしています。GTS専有機能はテナントレベルの構成パラメータ[enable_gts_standalone](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2550.enable_gts_standalone.md)で制御され、デフォルトは無効です。ユーザーは必要に応じてGTS専有機能を有効にすることができます。有効にすると、システムは自動的にGTSが存在するシステムログストリームが専用のUnitグループを確保します。

## シナリオ情報

現在、テナント`tenant1`があり、そのローカリティは`F@zone1、F@zone2、A`、プライマリゾーンは`zone1,zone2`であるとします。テナントの`zone1`および`zone2`の`UNIT_NUM`はどちらも2です。

## 手順

このシナリオでは、SYSログストリームが配置されているマシンがボトルネックに達した場合、業務の安定性を確保するために、まずテナント内のすべてのリソースプールの `UNIT_NUM` を2から3に拡張し、次にSYSログストリーム（1番目のログストリーム）を拡張後に追加されたユニットグループに移行コピーして、1番目のログストリームがユニットグループを専有するようにします。その後、GTS専用モードを有効にします。

詳細な手順は以下のとおりです。

1. `root` ユーザーでクラスタの `sys` テナントにログインします。

2. テナント内の自動バランシング機能を無効にします。

   テナントレベルの構成パラメータ [enable_rebalance](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2900.enable_rebalance.md) の値を `False` に設定して、自動バランシングを回避します。ステートメントは以下のとおりです。

   ```shell
   obclient> ALTER SYSTEM SET enable_rebalance = False TENANT = tenant1;
   ```

3. （オプション）拡張前に、ゾーン内のノード数が不足している場合は、ゾーン1とゾーン2にそれぞれ1つのノードを追加する必要があります。

   ノードの追加の詳細な操作と説明については、[ノードの追加](../../100.cluster-management/300.common-cluster-operations/400.add-a-node.md)を参照してください。

4. テナント内のすべてのリソースプールの `UNIT_NUM` を3に調整します。

   ```shell
   obclient> ALTER RESOURCE TENANT tenant1 UNIT_NUM = 3;
   ```

   `UNIT_NUM` を使用した拡張の詳細な操作と説明については、[Unit Numberの調整によるテナントのスケーリング](../../200.tenant-management/600.common-tenant-operations/800.tenant-scale-in-and-out/300.adjust-unit-number.md)を参照してください。

5. ログストリームを変更します。

   テナント `tenant1` のSYSログストリーム（1番目のログストリーム）の `UNIT_GROUP`（同構成ゾーンモード）/`UNIT_LIST`（異構成ゾーンモード）を拡張後に追加されたユニットグループに変更して、1番目のログストリームがユニットグループを専有できるようにします。ステートメントは以下のとおりです。

   :::tab
   tab 同構成ゾーンモード

    ```shell
    obclient> ALTER SYSTEM MODIFY LS 1 UNIT_GROUP unit_group_id TENANT = tenant1;
    ```

   ここで、`unit_group_id` は実際の環境に応じて、スケールアップ後に追加されたユニットに対応する `UNIT_GROUP_ID` に置き換える必要があります。

   tab 異種ゾーンモード

   ```shell
   obclient> ALTER SYSTEM MODIFY LS 1 UNIT_LIST (unit_id1,unit_id2) TENANT = tenant1;
   ```

   ここで、`unit_id1`、`unit_id2` は実際の環境に応じて、スケールアップ後に追加されたユニットの `UNIT_ID` に置き換える必要があります。

   :::

   ログストリームの変更の詳細な操作と説明については、[ログストリームの変更](../../230.logstream-management/200.modify-a-logstream.md)を参照してください。

6. GTS専用モードを有効にします。

   テナントレベルの構成パラメータ [enable_gts_standalone](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2550.enable_gts_standalone.md) の値を `True` に設定します。ステートメントは以下のとおりです。

   ```shell
   obclient> ALTER SYSTEM SET enable_rebalance = True TENANT = tenant1;
   ```

7. テナント内の自動バランシング機能を再び有効にします。

   テナントレベルの構成パラメータ [enable_rebalance](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/2900.enable_rebalance.md) の値を `True` に設定して、自動バランシングを回避します。ステートメントは以下のとおりです。

   ```shell
   obclient> ALTER SYSTEM SET enable_rebalance = True TENANT = tenant1;
   ```

このシナリオでは、テナントの `UNIT_NUM` を拡張してGTS専用モードを有効にした後、ユーザーログストリームの `UNIT_NUM` は変更されず、SYSログストリーム（1番目のログストリーム）のみが移行コピーされました。ログストリームの数のバランシングやTransferは行われなかったため、ユーザー業務の安定性が確保されました。
