# ODP パフォーマンス分析

## 基礎理論

### パフォーマンスチューニング

パフォーマンスチューニングは、ソフトウェアとハードウェアの能力を最大限に引き出し、実環境でシステムの最適なパフォーマンスを実現することで、ソフトウェアとハードウェアのコストパフォーマンスを向上させ、顧客のコストを削減することを目的としています。以下のように、`perf stat` コマンドを使用して一定期間のハードウェア性能指標データを収集できます。

```bash

   182250.331423      task-clock (msec)         #   18.221 CPUs utilized
      3,259,379      context-switches          #    0.018 M/sec
      1,628,966      cpu-migrations            #    0.009 M/sec
               51      page-faults               #    0.000 K/sec
442,995,845,816      cycles                    #    2.431 GHz

   45,556,284,037      branches                  #  249.965 M/sec
      662,510,643      branch-misses             #    1.45% of all branches

```

### パフォーマンスチューニングの手順

パフォーマンスチューニングの主な手順は以下のとおりです：

1. 最適化目標の特定。

   1. スループット：スループットは主にCPU情報とコンポーネントのボトルネックに注目します。現在、ODPとOceanBaseデータベースはどちらもCPUをフル稼働させることができます。

   2. レイテンシ：アクセスパス上のコンポーネント数と各区間の所要時間に注目する必要があります。ネットワークレイテンシも重要な要素です。

   3. エクスペリエンス：全体を考慮すると、ビジネス側に近いほど最適化効果が顕著になる可能性があります。

2. ストレステストと情報収集：対象データを収集するだけでなく、各コンポーネントのCPU消費量、ネットワークレイテンシなどのデータも収集する必要があります。

3. ストレス分析によるパフォーマンスボトルネックの特定：上記で収集したデータから、まずボトルネックを引き起こすコンポーネントを特定し、その後詳細な分析を進めます。

4. 最適化の実施：現在の最適化は主にパラメータ調整やデプロイメントの調整ですが、特殊な場合はコードを修正してバージョンアップを行う必要があります。

5. 最適化効果の確認：主にレイテンシとスループットが顧客要件またはテスト結果を満たしているかどうかを確認します。

## ODP パフォーマンス

### 関連データの概要

パフォーマンス関連データの概要は以下のとおりです：

* qps = 同時実行数 * (1000ms / rt)。

* rt = 1000ms / (qps / 同時実行数)。

* 同一データセンター内のネットワークレイテンシは、基本的に100μs以内です。

* OceanBaseデータベースの転送効率は、ODPの50%に満たない。

ODPの性能データの概要：

* システム全体の専有性能は2万～3.5万の間であり、CPU型番などの影響を受ける。負荷が小さくHTを経由しない場合、性能はさらに高くなる。

* OceanBaseデータベースと混合デプロイする場合、競合が発生するため、ODPに対してロードバランシングを行う方が性能が良い。

* 他のデプロイ方法と比較して、クライアント側にデプロイする方法が最も性能が優れている。

* ARMプラットフォームをサポートしているが、ARMプラットフォームの性能はx86システムほど良くない。

### 問題の解決

ODPの主な問題はQPSとRTである：

* QPS：一般的にはスケールアウトで解決できる。スケールアウトが不可能な場合は、単一マシンの性能向上を検討する。CPUが十分でもQPSが上がらない場合は、具体的な問題に基づいて分析する必要がある。

* RT：Slow Queryログを確認することでODPの処理時間を確認できる。ODP自体の処理時間はμ秒レベルだが、全体のアーキテクチャの方がRTに与える影響が大きい。

問題を解決する際には、実現したい目標を明確に区別する必要がある。例えば、ODPがボトルネックとなり（CPUが満杯の状態）、OMSのデータ移行が遅くなった場合、ODPインスタンスの数を増やすことで問題をより迅速に解決できる。

### スレッドモデル

topコマンドの`-H`パラメータでスレッド状況を確認できる。ODPのワーカースレッドはobproxyおよびスレッド名がET NETで始まるスレッドである。ODPはスレッド間の共有を基本的に排除しているため、各スレッドは独立して動作し、各リクエストは均等に各ワーカースレッドに分散される。

### パラメータ調整

性能チューニングに関わる主なパラメータは以下の通りである：

```sql
alter proxyconfig set enable_compression_protocol=false; --圧縮を無効にしてCPU使用率を下げる
alter proxyconfig set proxy_mem_limited='16G'; --OOMを防ぐため、実環境に応じて動的に調整可能
alter proxyconfig set enable_prometheus=false;
alter proxyconfig set enable_metadb_used=false;
alter proxyconfig set enable_standby=false;
alter proxyconfig set enable_strict_stat_time=false;
alter proxyconfig set use_local_dbconfig=true; --3.x系でのみ利用可能
alter proxyconfig set work_thread_num= xxx; --xxxは実際のコア数以下に設定する
```

### ルーティングの正確性

OceanBaseデータベースの転送効率はODPほど高くないため、コアシナリオにおいてODPのルーティング正確性は非常に重要であり、可能な限りすべてlocal計画にすることが望ましい。非コアシナリオでは、このような厳密な要件を課す必要はない。現在、ODPは通常のテーブル、パーティションテーブル、LDC、プライマリゾーンなどのルーティングをサポートしている。詳細については、[データルーティング](https://en.oceanbase.com/docs/enterprise-odp-enterprise-en-10000000000864182)の章を参照してください。

#### ツールによる確認

ツールによる確認の主な方法は以下のとおりです：

1. topコマンド

   1. topコマンドを使用してODPのCPU使用率をリアルタイムで確認します。CPU使用率がOceanBaseデータベースを超えた場合、パフォーマンスが異常である可能性があり、さらなる分析が必要です。

   2. top -Hを使用してスレッドのCPU消費を確認します。ODPのスレッド消費は非常に均等です。

2. perfコマンド

   1. perf topを使用してホットスポット関数を確認します。現在、ODPではどの関数も5%を超える割合で使用されていません。

   2. perf statを使用してハードウェア指標を確認します。異なるCPUを分析する際に役立ちます。

3. ログ出力

   ログはパフォーマンスに大きな影響を与えます。ODPのログ生成速度を確認します。もし1〜2秒ごとに1つのログが生成されている場合、パフォーマンスへの損害は大きいです。
