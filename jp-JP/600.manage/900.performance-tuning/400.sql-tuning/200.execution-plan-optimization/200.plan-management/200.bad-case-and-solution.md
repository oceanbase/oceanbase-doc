# プランキャッシュの欠点とソリューション

## プランキャッシュの欠点

前のセクションで説明したように、パラメータ化されたSQLに対して実行計画が生成されると、その計画はプランキャッシュに保存され、以降のSQL実行ではこの実行計画が再利用されます。このような計画の再利用は計画生成時間を節約できますが、データに偏りがある場合には問題が生じることがあります。以下に例を示します。

テーブル`t1`の定義は以下のとおりです。`c1`列には2つの値しかなく、値`0`が全データの1%、値`1`が全データの99%を占めていると仮定します。`c2`列には1から10までの10個の値があり、それぞれ10%ずつを占めています。すると、`SELECT * FROM t1 WHERE c1 = ? AND c2 = ?`というSQLに対して、計画生成時にオプティマイザーが見た条件が`c1 = 0 and c2 = 1`だった場合、オプティマイザーはインデックス`idx1`を使用することを選択します。まずインデックスから`c1 = 0`を満たす1%のデータを取得し、その後インデックスを使ってテーブルに戻り、`C2 = 1`で条件を満たさないデータをフィルタリングして返します。この場合、1%のデータをスキャンし、インデックスを使ってテーブルに戻る1%のデータをスキャンするだけでクエリが完了します。しかし、もしその後 server が別のSQLを受信し、ユーザーが指定した条件が`c1 = 1 and c2 = 1`に変わった場合、以前に生成された計画を再利用すると、まずインデックス`idx1`から`C1 = 1`を満たす99%のデータを取得し、その後インデックスを使ってテーブルに戻り、`C2 = 1`で条件を満たさないデータをフィルタリングして返すことになります。この場合、99%のデータをスキャンし、インデックスを使ってテーブルに戻る99%のデータをスキャンする必要があります。明らかに、このSQLに対してはインデックス`idx2`を使用する方が良い選択です。なぜなら、どのような値を取る場合でも、`idx2`を使用する場合は常に10%のデータをスキャンし、テーブルに戻る10%のデータをスキャンするだけで済むため、SQLの実行時間がより安定するからです。

```sql
create table t1 (
  c1 int,
  c2 int,
  c3 int,
  key idx1 (c1),
  key idx2 (c2)
);
```

このような場合、ユーザーはoutlineを使用してSQLに実行計画をバインドし、このクエリで`idx2`インデックスを使用するよう強制できます（データベースやテーブルをシャーディングする場合は、1つのテンプレートOutlineですべてのシャードテーブルをカバーでき、テーブルごとに作成する必要はありません）。もちろん、このSQLに対しては実際にはもっと良い最適化方法がありますが、これは本記事の要旨とは異なるため、詳細には触れません。

## プランバインディング

プランバインディングは、OceanBaseデータベースが提供するメカニズムであり、SQLを変更することなく、データベース内にoutlineを作成することで実行計画を制御できるようにします。OceanBaseデータベースは、2つの方法でOutlineを作成できます。1つは`SQL_TEXT`（ユーザーが実行するパラメータ付きの元のステートメント）を使用する方法で、もう1つは`SQL_ID`を使用する方法です。

V4.4.2 BP3より前のバージョンでは、Outlineを作成するには、対応するデータベースで実行する必要がありました。OceanBaseデータベースV4.4.2では、V4.4.2 BP3バージョンから`BINDING_RULE`句が導入され、Outlineの適用範囲を設定するために使用されます。この機能には以下の特徴があります：

* データベース間バインディング：1つのOutlineは、テナント内のすべての同名テーブルに適用されます。
* テンプレートバインディング：`${var:regex}`を使用してテーブル名やデータベース名をワイルドカードで表現することで、1つのOutlineで任意の命名規則を持つデータベースやテーブルのシャーディングをカバーできます。
* 複数テーブル変数制約：`JOIN`で複数のシャードテーブルを結合する場合、同一の変数は常に同じ値を取る必要があります。これにより、誤ったマッチングを防ぐことができます。
* 完全な後方互換性：`BINDING_RULE`を明示的に記述しない場合、その動作は過去のバージョン（V4.4.2 BP3より前）と一致します。

### SQL_TEXTを使用してOutlineを作成する

`SQL_TEXT`を使用してOutlineを作成すると、Key-Valueペアが生成され、Mapに格納されます。ここで、KeyはバインドされたSQLのパラメータ化後のテキスト、ValueはバインドされたHintです。具体的なパラメータ化の原則については、[クイックパラメータ化](../../../../../700.reference/1000.performance-tuning-guide/500.sql-optimization/200.sql-execution-plan/400.fast-parameterization.md)を参照してください。

`SQL_TEXT`を使用してOutlineを作成する構文は以下のとおりです：

```sql
CREATE [OR REPLACE] OUTLINE outline_name ON stmt
    [TO target_stmt
    | BINDING_RULE (binding_item)];

binding_item:
    SCOPE = {DATABASE | TENANT}
    | MAP = {real_name TO 'pattern', ...}
```

パラメータの説明は以下のとおりです：

* `OR REPLACE`：オプションです。`OR REPLACE`を指定すると、既存の実行計画を置き換えることができます。
* `outline_name`：作成するOutlineの名前を指定します。
* `stmt`：通常はHintと元のパラメータを持つDMLステートメントです。
* `TO target_stmt`：`TO target_stmt`を指定しない場合、データベースが受け付けたSQLをパラメータ化したテキストと、`stmt`からHintを除去してパラメータ化したテキストが一致すれば、そのSQLに`stmt`内のHintをバインドして実行計画を生成します。Hintを含むステートメントに対して固定の計画を実行したい場合は、元のSQLを指定するために`TO target_stmt`が必要です。例：

    ```shell
    obclient> CREATE OUTLINE outline1
        ON SELECT /*+NO_REWRITE*/ * FROM tbl1
          WHERE col1 = 4
          AND col2 = 6
          ORDER BY 2
        TO SELECT * FROM tbl1
          WHERE col1 = 4
          AND col2 = 6
          ORDER BY 2;
    ```

    <main id="notice" type='notice'>
      <h4>注意</h4>
      <p><code>target_stmt</code>を使用する場合、<code>stmt</code>と<code>target_stmt</code>がHintを除去した後完全に一致することが厳密に要求されます。</p>
    </main>

* `BINDING_RULE (binding_item)`：オプションです。このOutlineの適用範囲を指定するために使用されます。

  <main id="notice" type='explain'>
    <h4>説明</h4>
    <p>V4.4.2バージョンでは、V4.4.2 BP3バージョンから <code>BINDING_RULE</code> 句が導入されました。</p>
  </main>

  * `SCOPE = {DATABASE | TENANT}`：

    * `SCOPE = DATABASE`：デフォルト値で、現在のデータベース内でのみ有効です。
    * `SCOPE = TENANT`：現在のテナント内のすべてのデータベースで有効です。

  * `MAP = {real_name TO 'pattern', ...}`：左側の実際のテーブル名/`db.table` に右側の `pattern` を適用します。`pattern` には `${変数名}` または `${変数名:正規表現}` を記述できます。例については、以下の **現在のデータベース内のシャードテーブルのワイルドカード指定** の内容を参照してください。

    <main id="notice" type='notice'>
      <h4>注意</h4>
      <p><ul>
        <li><code>MAP</code> の左側が <code>db.table</code> 形式の場合、右側の <code>pattern</code> ではデータベース名とテーブル名のパターンをそれぞれ単一引用符で囲み、ドットで区切る必要があります：<code>'db_pattern'.'table_pattern'</code>。</li>
        <li>同一の <code>BINDING_RULE</code> 内では、変数は定義後に参照する必要があります。同名の変数は、すべての参照箇所で一貫した値を取る必要があります。</li>
      </ul></p>
    </main>

### SQL_IDを使用してアウトラインを作成する

`SQL_ID` を使用してアウトラインを作成する構文は以下のとおりです：

```shell
obclient> CREATE OUTLINE outline_name ON sql_id USING HINT hint_text;
```

`SQL_ID` は、バインド対象のSQLに対応する `SQL_ID` であり、以下の方法で取得できます：

* `V$OB_PLAN_CACHE_PLAN_STAT` をクエリすることで取得します。
* `GV$OB_SQL_AUDIT` をクエリすることで取得します。
* パラメータ化された元のSQLを使用し、MD5で `SQL_ID` を生成します。以下のスクリプトを参考に、対応するSQLの `SQL_ID` を生成できます。

    ```sql
    IMPORT hashlib
    sql_text='SELECT * FROM t1 WHERE c2 = ?'
    sql_id=hashlib.md5(sql_text.encode('utf-8')).hexdigest().upper()
    PRINT(sql_id)
    ```

`SQL_ID` を使用してアウトラインをバインドする例は以下のとおりです：

```shell
obclient> CREATE OUTLINE otl_idx_c2
    ON 'ED570339F2C856BA96008A29EDF04C74'
    USING HINT /*+ INDEX(t1 idx_c2)*/ ;
```

### シャーディングシナリオにおけるテンプレートバインド

#### クロスデータベースの同名テーブルバインド

シャーディングアーキテクチャでは、複数のデータベースに同名のテーブル（例：`db_001.orders`、`db_002.orders`）が存在することがあります。`SCOPE = TENANT` を使用することで、1つのアウトラインですべてのデータベースの同名テーブルをカバーできます。

**例：**

すべてのデータベースの `orders` テーブルは `idx_status` インデックスを使用します：

```shell
obclient> CREATE OUTLINE otl_orders
    ON SELECT /*+ index(orders, idx_status) */*
        FROM orders
        WHERE status = 'a'
    BINDING_RULE (SCOPE = TENANT);
```

* データベース `db_001` 内のクエリヒット例。

    ```shell
    obclient> USE db_001;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

* データベース `db_002` 内のクエリヒット例。

    ```shell
    obclient> USE db_002;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

* データベース `db_test` 内のクエリヒット例。

    ```shell
    obclient> USE db_test;
    ```

    ```shell
    obclient> SELECT * FROM orders WHERE status = 'pending';
    ```

#### 現在のデータベース内のシャードテーブルのワイルドカード指定

シャーディングアーキテクチャでは、単一のデータベース内に名前パターンが一致する複数のシャードテーブル（例：`orders_sh`、`orders_hz`、`orders_bj`）が存在します。`MAP` と正規表現変数を組み合わせることで、1つのアウトラインですべてのシャードテーブルをカバーできます。

**例：**

`orders_xx` シリーズのシャードテーブルは、同じアウトラインを共有します：

```shell
obclient> CREATE OUTLINE otl_orders_tpl
    ON SELECT /*+ index(orders_sh, idx_status) */*
        FROM orders_sh
        WHERE status = 'a'
    BINDING_RULE (MAP = {orders_sh TO 'orders_${S:[a-z]+}'});
```

* クエリヒット例 `S=bj`。

    ```shell
    obclient> SELECT * FROM orders_bj WHERE status = 'pending';
    ```

* クエリヒット例 `S=hz`。

    ```shell
    obclient> SELECT * FROM orders_hz WHERE status = 'pending';
    ```

* クエリミス例。`001` は `[a-z]+` にマッチしません。

    ```shell
    obclient> SELECT * FROM orders_001 WHERE status = 'pending';
    ```
