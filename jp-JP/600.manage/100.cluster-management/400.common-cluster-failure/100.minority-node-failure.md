# 少数派ノード障害

このセクションでは、少数派ノード障害の処理フローについて説明します。

## 背景

OceanBaseデータベースは分散型データベースであり、典型的なデプロイメントパターンはマルチレプリカアーキテクチャです。この章では、いずれのログストリームにも影響を与えない多数派レプリカを持つノードの障害についてのみ説明します。例えば、3レプリカデプロイメントアーキテクチャでは、任意の1つのノードが障害を起こしても多数派には影響しません。5レプリカデプロイメントアーキテクチャでは、任意の2つのノードが障害を起こしても多数派には影響しません。一部のログストリームでレプリカが欠けている場合、予想される許容度より少ないノード障害が多数派に影響を与える可能性があります。このようなシナリオについては、[多数派ノード障害](../400.common-cluster-failure/200.majority-node-failure.md)を参照してください。

一般的なノード障害には、主に以下のものがあります：

* ノードのハードウェア異常によりダウンすること。

* ノードのハードウェア異常によりダウンしていないが、そのノード上のobserverプロセスが異常終了すること。例えば、ホストメモリの障害によりobserverプロセスがクラッシュする場合。

* ノードのハードウェア異常によりダウンしていないが、そのノード上のobserverプロセスの状態が異常になること。例えば、I/O異常によりobserverプロセスの読み書きリクエストがタイムアウトする場合。

* ノードのハードウェア異常によりダウンしていないが、そのノード上のobserverプロセスがSSTableまたはRedoLogに誤ったデータを書き込み、その後のChecksum検証でそれが検出されること。

* OceanBaseデータベースのBugによりobserverプロセスが異常を起こすこと。例えば、スレッドが停止したり、メモリが上限に達したり、プロセスがクラッシュしたりする異常。

## 手順

OceanBaseデータベースのBugによりobserverプロセスが異常を起こした場合、まずはノードを速やかに隔離する必要があります。ノードの隔離に関する操作については、[ノードの隔離](../300.common-cluster-operations/600.isolation-a-node.md)を参照してください。サービスに影響がない場合は、現場を保持し、OceanBaseテクニカルサポートに連絡して対応を依頼することができます。サービスに影響がある場合は、速やかにプロセスを再起動または起動し、その後OceanBaseテクニカルサポートに連絡して対応を依頼する必要があります。

ハードウェア異常によりノードが異常を起こした場合、またはハードウェア異常が疑われる場合は、その異常なノードを隔離して交換する必要があります。具体的な操作手順は以下のとおりです：

1. `root`ユーザーでクラスタの`sys`テナントにログインします。

   接続例は以下のとおりです。データベースへの接続時は、実際の環境に準じてください。

   ```shell
   obclient -h10.xx.xx.xx -P2883 -uroot@sys#obdemo -p***** -A
   ```

   より詳細なデータベース接続操作の手順については、[データベース接続の概要（MySQLモード）](../../../300.develop/100.application-development-of-mysql-mode/100.connect-to-oceanbase-database-of-mysql-mode/100.connection-methods-overview-of-mysql-mode.md)および[データベース接続の概要（Oracleモード）](../../../300.develop/200.application-development-of-oracle-mode/100.connect-to-oceanbase-database-of-oracle-mode/100.connection-methods-overview-of-oracle-mode.md)を参照してください。

2. 異常なノードに対して、できるだけ早く`Stop Server`または`Force Stop Server`操作を実行し、業務トラフィックに影響を与えないように実行が成功することを確認します。

   `Stop Server`のステートメントは以下のとおりです：

   ```shell
   obclient [(none)]> ALTER SYSTEM STOP SERVER 'svr_ip:svr_port';
   ```

   例：

   ```shell
   obclient [(none)]> ALTER SYSTEM STOP SERVER '172.xx.xx.xx:2882';
   ```

   `Force Stop Server` のステートメントは以下のとおりです：

   ```shell
   obclient [(none)]> ALTER SYSTEM FORCE STOP SERVER 'svr_ip:svr_port';
   ```

   例：

   ```shell
   obclient [(none)]> ALTER SYSTEM FORCE STOP SERVER 172.xx.xx.xx:2882';
   ```

   `Stop Server` および `Force Stop Server` 操作の内部実行プロセスに関する詳細は、[分離ノード](../300.common-cluster-operations/600.isolation-a-node.md)を参照してください。

3. 異常ノードが存在するゾーンにノードを追加します。

    ノードの追加手順の詳細については、[ノードの追加](../300.common-cluster-operations/400.add-a-node.md)を参照してください。

4. 新規ノード上で異常ノード上のレプリカを補完します。

   以下の3つのシナリオがあります：

   * observerプロセスが既に終了している場合。

      主動的にUnit移行を開始することも、Root Serviceが自動的にUnit移行を開始するのを待つこともできます。observerプロセスが終了してから永続的オフライン時間を超えると、Root Serviceは自動的にUnit移行を開始します。永続的オフライン時間はシステム構成パラメータ`server_permanent_offline_time`で制御され、システム構成パラメータ`enable_rereplication`が有効である必要があります。

      手動でUnit移行を開始する操作の詳細については、[Unit移行](../../300.replica-management/200.replica-distribution/200.locality-common-operations/700.unit-migration.md)を参照してください。

   * 異常ノード上のデータエラー、またはプロセス状態の異常により移行Unit操作が停止した場合、またはプロセス状態の異常によりグローバル状態が異常になった場合（例：マージが停止した場合）。

      observerプロセスを手動でkillし、その後、最初のシナリオ（observerプロセスが既に終了している場合）の処理を参照して対処できます。

   * ハードウェアの潜在的な問題があり、クラスタのグローバル状態が異常にならない場合。

      このシナリオではobserverプロセスをKillする必要はありません（observerをKillした後にクラスタのリスクエクスポージャーが大きくなるのを避けるため）。主動的にUnit移行を開始し、異常ノード上のUnitをすべて新規ノードに移行できます。

      手動でUnit移行を開始する操作の詳細については、[Unit移行](../../300.replica-management/200.replica-distribution/200.locality-common-operations/700.unit-migration.md)を参照してください。

   <main id="notice" type='explain'>
      <h4>説明</h4>
      <p> 常に主動的にUnit移行を開始することを推奨します：</p>
      <ul>
      <li>主動的な移行により、異常ノード上のすべてのUnitを新ノードに移行することができ、Root Serviceが自動的に開始するのを防ぎ、元のUnitトポロジー構造を維持し、ノード間のバランスを崩すのを回避できます。</li>
      <li>Root Serviceが自動的にUnit移行を開始する場合、プロセスが終了してから永続的オフライン時間を超えるのを待つ必要があり、ノード異常のリスクエクスポージャーが高まります。</li>
      <li>主動的にUnit移行を開始することで、移行トラフィックがクラスタリソースに占める割合をリアルタイムで監視し、アプリケーショントラフィックへの影響を避けることができます。
      <p>ノード異常を発見した際、ノードの終了から永続的オフライン時間を超えており、かつRoot Serviceが既にUnit移行を自動的に開始している場合は、移行後のトポロジー構造を観察し、移行トラフィックがクラスタリソースに占める割合を確認し、業務担当者への連絡を適切に行う必要があります。</p>
      </li></ul>
   </main>

5. 操作終了後、`oceanbase.DBA_OB_UNIT_JOBS`ビューでデータ補完の進捗状況を確認できます。

   ```shell
   obclient [(none)]> SELECT * FROM oceanbase.DBA_OB_UNIT_JOBS WHERE JOB_TYPE = 'MIGRATE_UNIT';
   +--------+--------------+------------+-------------+----------+----------------------------+----------------------------+-----------+---------+----------+------------+------------+-------------+
   | JOB_ID | JOB_TYPE     | JOB_STATUS | RESULT_CODE | PROGRESS | START_TIME                 | MODIFY_TIME                | TENANT_ID | UNIT_ID | SQL_TEXT | EXTRA_INFO | RS_SVR_IP  | RS_SVR_PORT |
   +--------+--------------+------------+-------------+----------+----------------------------+----------------------------+-----------+---------+----------+------------+------------+-------------+
   |      4 | MIGRATE_UNIT | INPROGRESS |        NULL |        0 | 2023-01-04 17:22:02.208219 | 2023-01-04 17:22:02.208219 |      1004 |    1006 | NULL     | NULL       |xx.xx.xx.238|        2882 |
   +--------+--------------+------------+-------------+----------+----------------------------+----------------------------+-----------+---------+----------+------------+------------+-------------+
   ```

   クエリ結果が空の場合、Unitの移行が完了し、データの補完に成功したことを意味します。

6. 異常ノード上のUnitが新規ノード上で補完された後、異常ノードを削除します。

   ノードの削除手順の詳細については、[ノードの削除](../300.common-cluster-operations/500.delete-a-node.md)を参照してください。
