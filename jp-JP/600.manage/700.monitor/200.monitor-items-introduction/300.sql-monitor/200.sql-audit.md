# SQL Audit

`GV$OB_SQL_AUDIT`は最も一般的に使用されるSQL監視ビューであり、各SQLリクエストのソース、実行状態、リソース消費量、待機イベントを記録します。さらに、SQLテキストや実行計画などの重要な情報も記録しています。このビューはSQL問題の診断に役立つ強力なツールです。

このビューには多数のフィールドがあるため、段階的に紹介します。主なフィールドの説明は以下の通りです：

* `TENANT_ID`：リクエストのテナントID。
* `SVR_IP`：リクエストを受信したサーバーノードのIPアドレス。
* `CLIENT_IP`：リクエストを送信したクライアントのIPアドレス。
* `REQUEST_TIME`：リクエスト到着時間。
* `REQUEST_ID`：リクエストのID。リクエストの1回の実行を識別し、時間とともに増加します。外部監視システムはこのフィールドをカーソルとして使用し、監査情報を取得できます。
* `IS_INNER_SQL`：内部SQLリクエストかどうか。
* `IS_EXECUTOR_RPC`：現在のリクエストがRPCリクエストかどうか。
* `SQL_ID`：特定のSQLを識別するためのIDです。同一のSQLが複数回実行された場合、`SQL_ID`は同じですが、`REQUEST_ID`は異なります。
* `QUERY_SQL`：SQLステートメントの完全なテキスト。OceanBaseデータベースでは、`SQL_ID`と`SQL_TEXT`を使用して実行計画をバインドできます。
* `SID`：セッションを識別するためのIDです。この接続上のすべてのSQLおよび待機イベントに関連付けることができます。`GV$OB_PROCESSLIST`ビューの`ID`フィールドに対応します。
* `TX_ID`：トランザクションを識別するためのIDです。そのトランザクションのすべてのSQLに関連付けることができます。トランザクション内で連続して実行される2つのSQLの開始時刻と終了時刻に大きな差がある場合、そのパイプライン上での所要時間が長いことを示しています。
* `TRACE_ID`：このSQLリクエストのtrace IDです。他の監視メトリクスやログのクエリに関連付けることができます。
* `IS_HIT_PLAN`：Plan Cache内のPlanにヒットしたかどうか。SQLの最適化は時間がかかるため、繰り返し実行を避けるために、生成された計画をPlan Cacheに格納し、次回実行時には直接Plan CacheからPlanを取得します。Plan Cacheにヒットしない場合をハードパースと呼び、Plan Cacheにヒットした場合をソフトパースと呼びます。ハードパースはSQLのパフォーマンスに影響を与え、処理時間を増加させます。テナントのPlan Cacheヒット率が低すぎる場合、Plan Cacheの空き容量が小さすぎてPlanが頻繁にエージェントされていないか確認する必要があります。
* `PLAN_ID`：実行計画のIDです。この計画の詳細情報や統計情報をクエリするために使用できます。
* `PLAN_HASH`：実行計画のHash値です。
* `PLAN_TYPE`：実行計画のタイプです。値は`0`、`1`、`2`、`3`であり、`1`、`2`、`3`はそれぞれローカル計画、リモート計画、分散計画に対応します。`0`は実行計画なしを示し、例えばcommitステートメントなどが該当します。
* `AFFECTED_ROWS`：影響を受けた行数。
* `RETURN_ROWS`：戻された行数。
* `RET_CODE`：実行結果の戻りコード。
* `EVENT`：最長待機イベント名。
* `P1TEXT ~ P3TEXT`：待機イベントのパラメータ1〜3。
* `P1 ~ P3`：待機イベントのパラメータ値1〜3。
* `LEVEL`：待機イベントのレベル。
* `WAIT_CLASS_ID`：待機イベントが属するカテゴリID。
* `WAIT_CLASS`：待機イベントが属するカテゴリ名。
* `STATE`：待機イベントの状態。
* `WAIT_TIME_MICRO`：この待機イベントで待機した時間（マイクロ秒）。
* `TOTAL_WAIT_TIME_MICRO`：実行プロセス全体で待機した総時間（マイクロ秒）。
* `TOTAL_WAITS`：実行プロセスでの総待機回数。
* `ELAPSED_TIME`：今回の実行にかかった総時間（リクエストから実行終了まで）。複数のサブフェーズで構成されています：
    * `NET_TIME`：RPCの送信からリクエストの受信までの時間。
    * `NET_WAIT_TIME`：リクエスト受信からキューへの入列までの時間。
    * `QUEUE_TIME`：キュー時間。現在のテナントのリクエストの積み上がり状況を反映します。
    * `DECODE_TIME`：キューから出た後のDecode時間。
    * `GET_PLAN_TIME`：実行計画の生成時間。現在のテナントのPlan Cacheの健全性を反映します。
    * `EXECUTE_TIME`：計画の実行時間。
* `EXECUTE_TIME`：今回の実際の実行時間。CPU時間と`TOTAL_WAIT_TIME_MICRO`で構成されています。`TOTAL_WAIT_TIME_MICRO`は`APPLICATION_WAIT_TIME`、`CONCURRENCY_WAIT_TIME`、`USER_IO_WAIT_TIME`、`SCHEDULE_TIME`などの部分で構成されています。`EXECUTE_TIME`は実際にかかった実行の総時間であり、CPU計算に必要な時間(`CPU_TIME`)と各種待機時間(`TOTAL_WAIT_TIME_MICRO`)を含みます。
    * `APPLICATION_WAIT_TIME`：すべてのapplicationクラスイベントの合計時間。
    * `CONCURRENCY_WAIT_TIME`：すべてのconcurrencyクラスイベントの合計時間。
    * `USER_IO_WAIT_TIME`：すべての`user_io`クラスイベントの合計時間。
    * `SCHEDULE_TIME`：すべての`schedule`クラスイベントの時間。
* 論理読み取り：リクエストの実行中にデータを読み取る際、まず各レベルのキャッシュ（`ROW_CACHE_HIT`、`BLOOM_FILTER_CACHE_HIT`、`BLOCK_CACHE_HIT`などのフィールドに対応）を読み取ります。すべてヒットしない場合、実際のディスク読み取りが1回発生します（`DISK_READS`フィールドに対応）。キャッシュ読み取り回数とディスク読み取り回数を統計することで、そのリクエストの実行プロセスでスキャンされた行数を算出できます（スキャン行数は実際の物理読み取りとは等しくなく、まず各レベルのキャッシュがスキャンされます）。これにより、そのSQLが最適化が必要かどうかを判断できます。
    * `ROW_CACHE_HIT`：行キャッシュヒット回数。
    * `BLOOM_FILTER_CACHE_HIT`：bloom filterキャッシュヒット回数。
    * `BLOCK_CACHE_HIT`：ブロックキャッシュヒット回数。
    * `DISK_READS`：物理読み取り回数。
* `RETRY_CNT`：再試行回数。
* `TABLE_SCAN`：そのリクエストにフルテーブルスキャンが含まれているかどうかを判断します。
* `CONSISTENCY_LEVEL`：一貫性レベル。
* `MEMSTORE_READ_ROW_COUNT`：MemStoreで読み取った行数。
* `SSSTORE_READ_ROW_COUNT`：SSStoreで読み取った行数。
* `REQUEST_MEMORY_USED`：そのリクエストで消費されたメモリ。
* `INSERT_DUPLICATE_ROW_COUNT`: `insertup`または`replace into`時の重複行数を記録します。

`GV$OB_SQL_AUDIT`ビューのデータは設定可能なメモリ領域に格納され、各テナントは各ノード上に独立したキャッシュを持ちます。メモリ使用量またはレコード数がエージェントの上限に達すると自動エージェントがトリガーされ、最も古いデータが優先的に削除されます。経験豊富なDBAがSQL問題を調査する際、しばしば最初に行うことはSQL Audit機能を無効にして現場を保存し、ジッターが発生した監視データがエージェントされるのを防ぐことです。

以下のパラメータを使用してSQL Audit機能の動作を制御できます：

* `enable_sql_audit`：クラスタ構成パラメータで、すべてのテナントのSQL Audit機能を有効にするかどうかを制御します。動的に反映されます。
* `ob_enable_sql_audit`：テナントレベルのシステム変数で、現在のテナントでSQL Audit機能を有効にするかどうかを制御します。動的に反映されます。
* `ob_sql_audit_percentage`：テナントレベルのシステム変数で、現在のテナントのSQL Audit機能がテナントメモリの何割を占有するかを制御します。動的に反映されます。SQL Auditがメモリを過度に占有するのを防ぐため、システムはメモリの上限を1GBに設定しています。

    <main id="notice" type='explain'>
      <h4>説明</h4>
      <ul><li>テナントにジッターが発生した場合、一般的な症状は「テナントCPUがフル稼働」および「すべてのSQL RTが急上昇」です。この場合、まずSQL RTの急上昇が第一の原因かどうかを判断する必要があります（SQL自体の問題がRTの急上昇を引き起こしたのか、それとも他の問題がSQL RTの急上昇を引き起こしたのか）。</li>
      <li>上記で紹介したこのSQLは非常に有効なツールです。<code>SQL_ID</code>に基づいて集計し、リソース消費量で降順に並べ替えます（リソース消費量は<code>avg_exec_time * cnt</code>と見なすことができます）。上位のSQLに明らかな異常がないか観察することで、第一の原因であるかどうかを判断できます。</li></ul>
