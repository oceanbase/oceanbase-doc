# SQLクエリによる異常

本番運用において、ハードウェアやインフラの障害を除けば、データベースサービスの異常を引き起こす多くの要因の中で、SQLクエリによる異常は最も一般的なケースです（おそらく最も一般的なケースです）。ユーザーが特に注目する問題として、このセクションでは、OceanBaseにおいてSQLクエリによる異常をどのように分析・処理するかについて重点的に説明します。

## シナリオの概要

データベースが正常に稼働している過程で、異常なSQL実行によりCPU使用率が急上昇したり、I/O負荷が高くなったり、メモリ使用量が急増したりすることがよくあります。SQL異常は通常、以下のような状況に分類されます：

1. 業務アプリケーションに新しいバージョンがリリースされておらず、新しいSQLが追加されていない場合。この場合はさらに以下の2つに分類されます：

   1. 外部業務トラフィックの変化により、SQL実行回数が急増したり、データ量が急増したりする場合。

   2. 元のSQL実行計画が異常な場合。

2. 業務アプリケーションに新しいバージョンがリリースされ、新しいSQLクエリロジックが追加された場合。その中にはスローSQLが含まれている場合があります。

## 業務への影響

SQLの問題は、CPU使用率の急上昇やメモリ枯渇などを容易に引き起こし、業務の遅延やクラッシュなどの影響を及ぼす可能性があります。

## 緊急対応の手順

以下では、各状況における迅速な特定と対処方法について説明します。

### 業務に新しいバージョンがリリースされておらず、新しいSQLが追加されていない場合

ケース1：SQL実行回数またはデータ量の変化

データベースが正常にサービスを提供している状態で、業務のマーケティングキャンペーンやユーザーアクセスの増加などの理由により、データベース内の既存の特定のSQLの実行回数のみが増加したり、データ量が増加したりする場合、実行計画が正常であれば、通常は業務レベルでの降格または制限を優先的に選択します。業務が直接制限または降格できない場合、その時点でテナントのCPU/メモリ構成を増やせる場合は、データベースの一時的な拡張を優先的に実行します。テナントの拡張に関する詳細は、[テナントの拡張と縮小](../../../200.tenant-management/600.common-tenant-operations/800.tenant-scale-in-and-out/100.introduction-to-tenant-scale-in-and-out.md)を参照してください。

その時点でクラスタ内に拡張用の余剰リソースがない場合。この場合、OBカーネルレベルで指定SQLの制限を実行することを検討できます。SQLの実行計画に`hint max_concurrent`を追加してバインドすることで、SQLの並列実行を制限し、SQLの制限を実現できます。例：

```sql
CREATE OUTLINE outline_name ON sql_id USING HINT /*+max_concurrent(1)*/;
```

outlineのバインディング操作の詳細については、[計画のバインディング](../../../../700.reference/1000.performance-tuning-guide/500.sql-optimization/400.sql-optimization/700.manage-execution-plans/200.plan-binding.md)を参照してください。

ケース2：既存のSQL実行計画が異常な場合

業務に新しいバージョンがリリースされていないにもかかわらず、データベース内の既存のSQL実行計画が異常な場合、一般的に以下のような状況に分類されます：

1. 実行計画の選択が誤っている場合、この場合はまずplan cacheをクリアすることで、SQLを再びハードパースに強制的に送り、正しい計画を生成することができます。

   ```sql
   ALTER system flush plan cache [tenant_list] [global];
   ```

   <main id="notice" type='explain'>
    <h4>説明</h4>
    <ul>
    <li>tenant_listとglobalはオプションフィールドです。tenant_listが指定されていない場合、すべてのテナントの実行計画キャッシュをクリアします。指定されている場合は、指定されたテナントのみをクリアします。globalが指定されていない場合、ローカルの実行計画キャッシュをクリアします。指定されている場合は、そのテナントが存在するすべてのサーバー上の計画キャッシュをクリアします。デフォルトでは最小範囲です。</li>
    <li>tenant_listの例：tenant = 'tenant1, tenant2, tenant3....'</li>
    </ul>
   </main>

2. インデックスの選択が誤っています。

   調査の結果、テーブルにはより適したインデックスが存在し、実行計画が正しいインデックスにアクセスしていないことが判明しました。実行計画キャッシュをクリアしても問題が解決しない場合は、outlineをバインドすることで、オプティマイザーに正しい実行計画を指示できます。

   インデックスのバインドは、現在OCPでグラフィカル操作としてサポートされています。OCPユーザーガイドを参照して対応する操作を実行してください。

   コマンドラインでバインド操作を実行する場合は、以下の例を参考にしてください：SELECT \* FROM t1 WHERE v1 = 3 このSQLを主キーインデックスにバインドします。

   1. 業務テナントとしてOceanBaseにログインします（mysqlコマンドでは -c パラメータを追加する必要があります）。

   2. outlineを作成します。

      ```sql
      create outline bind_to_primary_key on SELECT/*+ index(t1 primary)*/ * FROM t1 WHERE v1 = 3;
      ```

   3. Outlineが正常に作成されたことを確認します。

      ```sql
      SELECT * FROM oceanbase.gv$outline WHERE OUTLINE_NAME = 'bind_to_primary_key';
      ```

   4. 新しいSQLがバインドされたOutlineによって新しい実行計画が生成されたことを確認します。

      OutlineにバインドされたSQLで新しいクエリを実行した後、`GV$OB_PLAN_CACHE_PLAN_STAT` テーブルの該当SQLの計画情報における `outline_id` を確認します。`outline_id` が `gv$outline` で検索した `outline_id` と一致すれば、バインドされたOutlineに従って生成された実行計画であることを意味します。一致しない場合はそうではありません。

      ```sql
      SELECT SQL_ID, PLAN_ID, STATEMENT, OUTLINE_ID, OUTLINE_DATA
            FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT
             WHERE STATEMENT LIKE '%SELECT * FROM t1 WHERE v1 = 3%';
      ```

   5. 生成された実行計画が期待通りであることを確認します。

      Outlineによって生成された計画であることを確認した後、生成された計画が期待通りかどうかを確認する必要があります。`GV$OB_PLAN_CACHE_PLAN_STAT` テーブルをクエリして、`plan_cache` にキャッシュされた実行計画の形状を確認することができます。

      ```sql
      SELECT OPERATOR, NAME FROM oceanbase.GV$OB_PLAN_CACHE_PLAN_STAT
            WHERE TENANT_ID = 業務テナントID AND IP = 'xxx.xxx.xxx.xxx'
             AND PORT = xxxx AND PLAN_ID = 前のステップで検索した plan_id;
      ```

3. インデックスが欠落しています。

   調査の結果、現在のSQLが関与するテーブルに最適なインデックスが欠けていることが判明しました。必要に応じて対応するインデックスを作成してください。

   <main id="notice" type='notice'>
    <h4>注意</h4>
    <ul>
    <li>
    <p>インデックス作成時には、可能な限りすべてのクエリ対象列を含めること。含まれる列が多いほど、テーブルへの再アクセス回数を最小限に抑えられる。</p>
    </li>
    <li>
    <p>等価条件は常に複合インデックスの先頭列に配置する。</p>
    </li>
    <li>
    <p>データ量の多いフィールドのフィルタリングやソート処理は、複合インデックスの先頭列の後に配置する。</p>
    </li>
    </ul>
   </main>

### ビジネスの新バージョンリリースに伴い、新たなSQLロジックが発生した場合

ビジネスの新バージョンがリリースされる際には、新しいSQLが生成される。場合によっては、レビューされていないスローSQLが本番環境で過剰なリソースを消費し、コアビジネスに影響を与える可能性がある。このような場合、データベース内のスローSQLを調査して問題の原因を特定し、その後の最適化処理を行う必要がある。

1. OCPを使用してスローSQLを検索する。

   OCPのTOP SQLページで、直近の期間において実行時間が長く、実行回数が最も多いクエリを確認し、高い順に並べ替えることができる。実行計画が誤っているSQLについては、その場でオンラインでバインドする。トラフィック制限が必要なSQLについては、ビジネス開発部門の確認情報と照合し、制限可能なSQLを特定する。

2. コマンドラインでスローSQLを検索する。

   1. 特定のテナントでCPU消費量が最も多い上位SQLを照会する。

      ```sql
      SELECT
       sql_id,
        avg(execute_time) avg_exec_time,
        count(*) cnt,
        avg(execute_time - TOTAL_WAIT_TIME_MICRO) cpu_time,
      RETRY_CNT,QUEUE_TIME,IS_HIT_PLAN
      FROM
       oceanbase.V$OB_SQL_AUDIT
      WHERE
        tenant_id = 1002
      GROUP BY
       1
      ORDER BY
       (avg_exec_time * cnt) desc
      limit
       5;
      ```

   <main id="notice" type='explain'>
    <h4>説明</h4>
    <ul>
    <li>
    <p>その中でEXECUTE_TIMEの値が大きすぎる場合、待機イベントの存在や論理読み取り回数が異常に多いことが考えられる。</p>
    </li>
    <li>
    <p>RETRY_CNTフィールドはリトライ回数を示しており、回数が多い場合、ロック競合やプライマリ切り替えなどが発生している可能性がある。</p>
    </li>
    <li>
    <p>QUEUE_TIMEが大きすぎる場合、CPUリソースが不足していることを示している。</p>
    </li>
    <li>
    <p>GET_PLAN_TIMEは実行計画の取得にかかった時間であり、時間が長い場合、通常はIS_HIT_PLAN＝0を伴い、これは計画にヒットしなかったことを意味する。</p>
    </li>
    </ul>
   </main>

   2. その他の関連クエリ。

      OceanBaseは、最近のSQL実行履歴を記録するために、仮想テーブル`V$OB_SQL_AUDIT`と`GV$OB_SQL_AUDIT`を提供している。V$OB_SQL_AUDITはローカルのSQL実行履歴を格納し、GV$OB_SQL_AUDITはクラスタ全体のSQL実行履歴を格納する。必要に応じて関連するクエリを実行できる。

      1. GV$OB_SQL_AUDITテーブルを照会する。例えば、特定のテナントで実行時間が1秒（1000000マイクロ秒）を超えるSQLを照会する。

         ```sql
         SELECT * FROM oceanbase.GV$OB_SQL_AUDIT WHERE tenant_id= <tenantid> AND elapsed_time> 1000000 limit 10;
         ```

      2. SQL実行時間の分布ヒストグラムを秒単位で表示します。

         ```sql
         SELECT round(elapsed_time/1000000), count(*) FROM oceanbase.V$OB_SQL_AUDIT WHERE tenant_id = <tenant_id> GROUP BY  1;
         ```

3. OceanBaseのログからスローSQLを検索する。

   OceanBaseにおいて、SQLの実行時間がtrace_log_slow_query_watermark（システムパラメータ）を超える場合、observerログにはスロークエリメッセージが出力されます。このパラメータのデフォルト値は100msです。observerログを通じてスローSQLを検索できます。この方法は前述の2つの方法ほど効率的で直感的ではありませんが、sql_auditのキャッシュが既に削除されている場合など、特定の問題のトラブルシューティングに役立つ場合もあります。

   スローSQLログの保存場所：`/home/admin/oceanbase/log`

   1. ログ内のすべてのスロークエリを確認します。

      `fgrep '[slow query]' observer.log |sed -e 's/|/\n/g' | more`

   2. trace_idに基づいて特定のスロークエリを検索します。

      `fgrep "<trace_id>" observer.log |sed -e 's/|/\n/g' | more`
