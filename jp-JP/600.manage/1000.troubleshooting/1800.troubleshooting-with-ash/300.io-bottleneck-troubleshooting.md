# I/Oボトルネック問題のトラブルシューティング

データベースの運用において、I/O問題はよく見られる問題の一つです。主に以下の2つのシナリオに分類されます：

* 一つ目は、特定のSQLの実行過程で主なコストがディスク読み取りにかかっており、どのデータベースオブジェクトやSQL演算子と関連付けられているかを調査したい場合です。

* 二つ目は、OCP監視でデータベースのディスク読み書き負荷が非常に高いことが確認され、その負荷の発生源を知りたい場合です。

皆様が迅速に問題の根本原因を特定し、効率的に解決できるよう支援するため、ここでは明確で実用的なI/O問題のトラブルシューティングプロセスをまとめました。このプロセスは、明確な操作手順を提供し、問題処理の効率を向上させ、業務への影響を可能な限り低減することを目的としており、日常の運用保守作業を強力にサポートします。

I/O問題は主に以下の2つのシナリオに分類されます：

* **SQLレベルの問題**：特定のSQLの実行過程でディスク読み取りのコストが高く、データベースオブジェクトや演算子と関連付けて分析する必要があります。

* **クラスタレベルの問題**：OCP監視でディスクの読み書き負荷が高いことが表示され、負荷の発生源を特定する必要があります。

## プロセスの紹介

1. I/O関連の問題があるかどうかを確認します。

   以下の方法で確認できます：

   * OCPにログインし、**Physical IOPS** と **Physical IOTPS** のパフォーマンス監視から、ノードレベル（OBServer次元）とテナントレベル（テナント次元）のI/O帯域幅を確認します。特定のノードまたはテナントのI/O帯域幅が高い場合、I/O関連の問題が存在する可能性があります。

   * ASHレポートの **Top Foreground DB Time** と **Top Background DB Time** を確認し、`db file data read`、`db file compact read`、`db file compact write`、`row store disk write` など、File/Disk、Read/Writeに関連するI/O関連の待機イベント（対応する `Wait Class` の値が `USER_IO` および `SYSTEM_IO`）の割合が高い場合、I/O関連の問題が存在する可能性があります。

2. クラスタレベルの問題をトラブルシューティングします。

   1. 問題が発生した時間帯のノードおよびテナントに対応するASHレポートを取得します。

   2. **Top Foreground DB Time** および **Top Background DB Time** の内容を確認し、I/Oの発生源を調べます。

      フォアグラウンドのI/O関連待機イベントの割合が高い場合、現在のI/O負荷が主にフォアグラウンドセッションに集中していることを意味します。この場合は、手順3に進み、SQLレベルの問題をトラブルシューティングします。

      そうでない場合、I/Oの発生源をさらに調査します。

   3. I/Oの発生源をさらに調査します。

      1. **Top IO Bandwidth** の内容を確認します。`IO Size(MB)`の数値が大きいほど、問題発生時に対応するモジュールから送信されたIOの総サイズが大きいことを示しています。

      2. `IO Size(MB)`が大きい`Program Module Action/SQL ID`フィールドを選択し、対応する情報を取得します。PX/DASの実行関連情報であれば、次のSQLレベルの問題調査に進みます。それ以外の場合は、関連ドキュメントを参照して処理するか、テクニカルサポートに連絡して分析および対処を依頼します。

3. SQLレベルの問題を調査します。

   これまでに取得した問題発生時のノード、テナントに対応するASHレポートに基づき、フロントエンドのIO関連待機イベントの割合が高い場合、さらに調査を進めることができます：

   1. **Top SQL with Top Event** および **Top SQL with Top Opreator** の内容を確認します。

      * **Top SQL with Top Event**：取得したASHレポートで実行コストが最も高いSQLを表示し、`Top Event`列には該当SQLで最も割合の高い待機イベントを表示します。

      * **Top SQL with Top Opreator**：取得したASHレポートで実行コストが最も高いSQLを表示し、`Top Operator`および`Top Event`列にはそのSQLに対応するコストが最も高い演算子IDとevent_idを表示します。

        この2つのテーブルを確認することで、IO関連待機イベントに対応するSQLおよび対応する演算子IDを取得できます。

   2. IOがどのデータベースのテーブルパーティションへのアクセスによるものかをさらに知りたい場合は、**Top DB Object** セクションを確認してください。ここでは、ユーザーのSQLが最も頻繁にアクセスするtablet_idがリストアップされています。

   3. 取得した情報に基づき、関連ドキュメントを参照して処理するか、テクニカルサポートに連絡して分析および対処を依頼します。
