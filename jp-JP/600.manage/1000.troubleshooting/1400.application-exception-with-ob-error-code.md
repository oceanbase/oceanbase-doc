# アプリケーション例外 -- エラーメッセージにOceanBaseエラーコードが含まれる場合

データベースの運用中には、アプリケーションエラー、データベース接続エラー、データベース権限問題、データベースリソース問題、ネットワーク問題など、さまざまな異常状況が頻繁に発生します。これらすべてのケースの中で、アプリケーション例外というものがありますが、そのエラーメッセージにはOceanBaseエラーコードが含まれています。

このようなシナリオにおける問題の根本原因を迅速に特定し、効率的に解決するために、ここではアプリケーション例外でありながらエラーメッセージにOceanBaseエラーコードが含まれる場合の明確かつ実用的なトラブルシューティングプロセスをまとめました。このプロセスは、明確な操作手順を提供し、問題処理の効率を向上させ、業務への影響を最小限に抑えることを目的としており、日常的な運用保守作業を強力に支援します。

## プロセスの紹介

アプリケーションの実行に異常が発生し、エラーメッセージにOceanBaseのエラーコードが含まれている場合は、このプロセスに従って問題のトラブルシューティングを行うことができます。

まず、OBClientを使用してデータベースに接続した後、手動で問題を再現できるかどうかを判断します。

* はいの場合、問題を再現した上でさらに調査を進めることができます。

* いいえの場合、プログラム設定のデータソース情報を確認する必要があります。

### 問題の再現による問題の特定

1. OBClientを使用して、2881（SQLポート番号、デフォルトは2881ですが、カスタマイズされている場合は実際のポート番号に置き換えてください）でOceanBaseクラスタに接続します。

2. エラーが報告されたSQL文を手動で実行し、問題シナリオを再現します。

3. 以下のステートメントを実行して、trace_idを取得します。

    <main id="notice" type='notice'>
    <h4>注意</h4>
    <p>エラーが報告されたSQL文を実行した後、直ちに以下のステートメントを実行する必要があります。そうしないと、エラーが報告されたSQL文の <code>trace_id</code> が照会されません。</p>
    </main>

    :::tab
    タブ MySQLモード

    MySQLモードで`trace_id`を取得するステートメントは次のとおりです：

    ```shell
    obclient> SELECT last_trace_id();
    ```

    tab Oracleモード

    Oracleモードで`trace_id`を取得するステートメントは次のとおりです：

    ```shell
    obclient> SELECT last_trace_id() FROM DUAL;
    ```

    :::

4. 実際にSQL文を実行したホスト情報を取得します。

    OceanBaseクラスタは通常複数のノードで構成されており、以下のSQL文を使用して実際にSQL文を実行したノードを取得し、その後ログフィルタリングを行うことができます。

    :::tab
    タブ MySQLモード

    MySQLモードでは、次のステートメントを実行します。

    ```shell
    obclient> SELECT * FROM oceanbase.GV$OB_SQL_AUDIT WHERE trace_id=last_trace_id;
    ```

    ここで、`last_trace_id` は前のステップで取得した `trace_id` に置き換える必要があります。

    tab Oracleモード

    Oracleモードで以下のステートメントを実行します：

    ```shell
    obclient> SELECT * FROM SYS.GV$OB_SQL_AUDIT WHERE trace_id=last_trace_id;
    ```

    ここで、`last_trace_id` は前のステップで取得した `trace_id` に置き換える必要があります。

    :::

    `GV$OB_SQL_AUDIT` ビューのクエリ結果によると、`svr_ip` に対応するホストが実際にそのSQL文を実行したホストです。

5. 取得したホスト情報に基づいて、`ssh` コマンドを使用して対応するホストにログインします。

6. ログが保存されているディレクトリに移動します。

    以下は、OceanBaseデータベースのインストールディレクトリが `/home/admin/oceanbase` である場合の例です。ログの具体的な保存パスは、実際の環境に基づいてください。

    ```shell
    cd /home/admin/oceanbase/log
    ```

7. 以下のコマンドを実行して、ログ内の関連情報をフィルタリングします。

    ```shell
    grep "${trace_id}" observer.log
    ```

    ```shell
    grep "${trace_id}" observer.log.xxx
    ```

    ここで、 `${trace_id}` は前のステップで取得した `trace_id` に置き換える必要があります。`observer.log.xxx` はタイムスタンプ付きのログファイルであり、`xxx` はSQLエラーが発生した時間に基づいて実際のタイムスタンプに置き換える必要があります。

8. ログから提供される情報と、関連するエラーメッセージなどを組み合わせて、問題を分析します。

    ログに関する詳細は、[ログの概要](../800.logging/100.logging-overview.md)を参照してください。ログ内の情報が不明確な場合は、技術サポート担当者に連絡して、問題の特定を支援してもらってください。

### プログラム設定のデータソース情報

1. データソースに基づいてアクセスリンクを明確にします。

2. アクセスリンクには、以下の情報が含まれるアドレスの数を明確にします。

    * OBProxyの数とアドレス情報

    * OBServerホストの数とアドレス情報

3. OBProxyを経由するかどうかを判断します。

    * はい、OBProxyを経由する場合は、以下の手順でさらに調査を進めます：

      1. `ssh` コマンドを使用して、対応するOBProxyノードにログインします。

      2. `cd` コマンドを使用して、OBProxyのログディレクトリに移動します。OBProxyのログは、そのインストールディレクトリの `/log` ディレクトリに保存されています。

      3. 以下のコマンドを実行して、エラーログをフィルタリングします。

         ```shell
         grep "エラーテキスト" obproxy_error.log obproxy_error.log.xxx | grep "エラー発生時点"
         ```

      4. フィルタリングされたログエントリに基づいて、エラーが発生したSQLがルーティングされたOBServerノードを特定します。

      5. 再び `ssh` コマンドを使用して、対応するOBServerノードにログインし、調査を続けます。

    * いいえ、OBProxyを経由しない場合は、以下の手順でさらに調査を進めます：

      1. `ssh` コマンドを使用して、対応するOBServerノードにログインします。

      2. ログが保存されているディレクトリに移動します。

         以下は、OceanBaseデータベースのインストールディレクトリが `/home/admin/oceanbase` である場合の例です。ログの具体的な保存パスは、実際の環境に基づいてください。

         ```shell
         cd /home/admin/oceanbase/log
         ```

      3. 以下のコマンドを実行して、エラーログをフィルタリングします。

         ```shell
         grep "sending error" observer.log observer.log.xxx | grep "エラーコード'
         ```

      4. フィルタリングされたログに基づいて、trace_idを取得し、trace_idを使用してログをさらにフィルタリングします。

         ```shell
         grep "trace id" observer.log observer.log.xxx
         ```

      5. ログが提供する情報と関連するエラーメッセージなどを組み合わせて、問題を分析します。

         ログに関する詳細は、[ログの概要](../800.logging/100.logging-overview.md)を参照してください。ログ内の情報が不明確な場合は、テクニカルサポート担当者に連絡して調査を支援してください。

## タイプケース

:::tab
タブ 一般（モードを問わない）

* 普通の業務テナントの一般ユーザーがOceanBaseデータベースのポート2881に直接接続しようとすると、エラー`ERROR 1040 (08004): Too many connections`が発生します。具体的なトラブルシューティング手順については、[一般ユーザー接続時にエラーERROR 1040 (08004): Too many connectionsが発生した場合](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000002356015)を参照してください。

* ビジネスで頻繁に接続と切断が行われるシナリオでは、接続数が一定量に達すると、接続エラー4016が発生します。具体的なトラブルシューティング手順については、[OceanBaseデータベースV4.xバージョンで接続エラー4016が発生した場合](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000780934)を参照してください。

タブ MySQLモード

* アプリケーションがINSERTステートメントを実行したところ、エラー00918が発生しました。具体的なトラブルシューティング手順については、[アプリケーションのINSERT実行時にエラー00918が発生した場合](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000002393334?back=kb)を参照してください。

tab Oracleモード

* OceanBaseデータベースのDBLinkを使用して大規模なLOBデータにアクセスしようとすると、次のエラーが発生します：`ORA-00600: internal error code, arguments: -4007, Not supported feature or function`。具体的なトラブルシューティング手順については、[DBLinkを使用してLOBタイプにアクセスする際にエラー：-4007、Not supported feature or functionが発生した場合の原因と解決方法](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000001260056)を参照してください。

:::
