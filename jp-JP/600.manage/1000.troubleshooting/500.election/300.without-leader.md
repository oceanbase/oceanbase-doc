# リーダーなし

リーダーなしのエラーは -4038 です。4038 エラーが発生した場合、次の 2 つの可能性があります：

* 現在のリーダーは存在しますが、そのリーダーが現在のノードではない可能性があります。これは、リーダー切り替え後に Location Cache が更新されていないためです。
* 現在のリーダーが存在しません。ログストリームのネットワーク接続性を調査する必要があります。

## 現在のリーダーが存在する場合

リーダー切り替え後（異常なリーダー切り替えおよび優雅なリーダー切り替えを含む）に Location Cache が更新されていないため、リモート実行時に宛先ノードがもはやリーダーではなくなり、4038 エラーコードが返され、ステートメントレベルで再試行される可能性があります。以下の方法で確認できます：

* `DBA_OB_SERVER_EVENT_HISTORY` ビューを使用して、実際にリーダー切り替えが発生したかどうかを確認します。
* システムログを確認して、宛先側から実際に 4038 エラーコードが返されたかどうかを確認します。

## 現在のリーダーが存在しない場合

ログストリームにリーダーが存在するかどうかは、下から上へと選挙モジュール、CLOG モジュール、RoleChangeService モジュールの 3 つのモジュールに依存します。したがって、ログストリームにリーダーが存在しない場合、下から上への方法で調査することができます：

1. Election Leader が存在するかどうかを確認します。
2. CLOG Leader が存在するかどうかを確認します。
3. RoleChangeService モジュールが正常に動作しているかどうかを確認します。

### Election Leader の有無を確認する

ログストリームが存在する任意のノードで、システムログを確認して現在の Election Leader を照会できます。例えば、以下のコマンドは、1 テナント 1 ログストリームの Election Leader を照会します。他のログストリームを照会する場合は、T1 と id:1 を他のテナントとログストリームの ID に置き換えるだけです。

```shell
grep 'T1_.*{id:1}' ./election.log | grep 'dump acceptor info'
```

ここで、`lease:{owner:"xx.xx.xx.xx:xxxxx"` はそのログストリームの Election Leader を表し、`xx.xx.xx.xx` は IP アドレスを表し、`xxxxx` はポート番号を表します。

現在の Election Leader が存在しない場合、ログストリームのネットワーク接続状態に問題がある可能性が非常に高いです。例えば：

* テナントがメモリ不足でメッセージを受信できないが、送信は可能なため、一方向のネットワーク接続が発生している。
* ワークキューの積み上がりによりメッセージを受信できない。
* ノードが Stop 状態にあるためメッセージを受信できない。
* その他の理由によるネットワーク接続性の問題。

さらに、ネットワークインタラクション統計情報に基づいてログストリームレベルのネットワーク接続性を分析する必要があります。以下のコマンドで照会できます。

```shell
grep 'T1_.*{id:1}' ./election.log | grep 'dump message count'
```

このログは、ローカルレプリカと他のレプリカ間のメッセージ送受信履歴を集計し、IPアドレスとメッセージタイプで分類して、最後のやり取りのタイムスタンプを記録します。

ネットワーク接続統計データに基づき、どのノードに異常があるか、問題が送信側にあるのか受信側にあるのかを初期判断し、該当するノードでさらに調査を進めることができます。

システムログに加えて、内部ビューのイベント検索と分析も可能です。システムテナントの`DBA_OB_SERVER_EVENT_HISTORY`ビューから検索できます。

```shell
obclient >
SELECT VALUE4,svr_ip,svr_port,event,name3,value3
FROM DBA_OB_SERVER_EVENT_HISTORY
WHERE module="ELECTION" AND value1=$tenant_id AND value2=$ls_id
ORDER BY VALUE4 limit 10;
```

Election Leaderが存在する場合、次にCLOG Leaderが存在するか確認します。

### CLOG Leaderの有無の確認

Election Leaderの存在が確認された場合、次にCLOG Leaderが存在するか調査を進めます。

クラスタが利用可能な場合（SQLクライアントが接続可能な場合）、システムテナントの`GV$OB_LOG_STAT`ビューから検索できます。

```shell
obclient >
select * from GV$OB_LOG_STAT
where tenant_id=$tenant_id and ls_id=$ls_id and role="LEADER";
```

    <h4>注意</h4>
    <p>検索結果のノード数がmemberlist内のレプリカ数より少ない場合、一部のログストリームレプリカの状態に異常が発生している可能性があり、さらに調査が必要です。</p>
</main>

クラスタが利用不可な場合（SQLクライアントが接続できない場合）、システムログを調査します。前の手順で取得したElection Leaderノードで、以下のコマンドを実行します。

```shell
grep 'Txxx_.*PALF_DUMP.*palf_id=xxxx,' observer.log.* | less
# ここで、Txxxはtenant_idです。例えば、T1001は1001テナントのログを検索します。
# palf_idはログストリームidです。例えば、palf_id=1001は1001ログストリームのログを検索します。
```

ログ内のroleがFollowerの場合、CLOG Leaderは存在しないことを意味し、CLOG Leaderが存在しない原因をさらに調査する必要があります。

CLOG Leaderが存在する場合、RoleChangeServiceが正常に動作しているか確認します。

### RoleChangeServiceの動作状況の確認

CLOGでロール切り替えが発生すると、RoleChangeServiceのタスクキューに非同期タスクが投入されます。RoleChangeServiceのバックグラウンドスレッドがプライマリ/スタンバイ切り替え作業を実行します。システムログを調査することで、RoleChangeServiceの動作状況を確認できます。コマンドは以下のとおりです。

```shell
grep 'Txxx_RCS' observer.log rootservice.log.xxxx -h | sort | less
```

* 最後のログが`end handle_role_change_event_`ではない場合、プライマリ切り替え動作で停止したことを意味します。問題を確認するため、最後のログのスタックを詳しく調べることができます。

* 最後のログが`end handle_role_change_event_`であり、かつCLOGにプライマリが存在する場合、RoleChangeServiceモジュールに異常があることを意味し、さらに調査が必要です。

## テナントがプライマリを持たない一般的な原因

### クロック偏差

現在のElectionモジュールは、任意の2つのOBServer間の時刻偏差が2秒を超えないことを前提としています。これを超えるとリーダー不在の状態になる可能性があります。以下のコマンドでOBServer間の時刻が同期されているか確認できます。

```shell
sudo clockdiff $IP
```

結果で偏差値が2秒を超えている場合は、時刻サービスが正常に動作しているかさらに確認する必要があります。一般的な時刻サービスにはNTPやChronyが含まれます。

### テナント/テーブル/パーティションの削除

特定のテナントが削除されたり、テーブルやパーティションが削除されたりした場合、複数のレプリカの削除タイミングが一致しない可能性があります。もしリーダーが最後に削除された場合、投票を受け取れず再選に失敗し、リース期限切れ時にリーダー不在の状態が発生する可能性があります。

### 多数派レプリカのダウン

レプリカがダウンした場合、正常なレプリカでは多数派を維持できず、リーダー不在の状態が発生します。

### ネットワーク問題

多数派レプリカのプロセスがすべて存在し、ダウンも発生していないにもかかわらず、リーダーレプリカのシステムログに `leader lease is expired` エラーが表示された場合、リーダーレプリカの再選（自身のリース延長）に失敗したことを意味します。ネットワーク障害（単方向/双方向のネットワーク分離、RPCリクエストのバックログ、RPC遅延）が発生している可能性があるため、さらに調査する必要があります。

エラーの例は以下のとおりです。

### システム負荷が高い

システムのload値が非常に高い場合、リーダー不在の状態を引き起こす可能性があります。システムコマンドを使用して、対応する時間点のload値が正常かどうか確認できます。

### clogディスクが満杯

clogディスクの使用量がしきい値（テナント構成パラメータ `log_disk_utilization_limit_threshold` で制御、デフォルト値は95%）を超えると、書き込みが強制的に停止されます。この時点でそのノード上のレプリカはリーダーに選出されることができません。多数派レプリカが存在するノードでこのような状況が発生した場合、クラスタはリーダー不在となります。

### テナントメモリが満杯

テナントのMemTableメモリが満杯になると、ログの再生を続けることができず、それによってログの回収（回収は再生やダンプに依存しています）ができなくなります。したがって、CLOGディスクが満杯になるのを防ぐため、テナントメモリが満杯になった場合、レプリカはリーダーからのログ受信を続けることが許可されません。多数派のフォロワーでテナントメモリが満杯になると、リーダーのログ同期が停止し、多数派を維持できずにクラスタがリーダー不在となります。

### CLOG reconfirm失敗

Electionモジュールが正常に動作し、リーダーが選出されたにもかかわらず、CLOGモジュールでreconfirmを実行する際に失敗した場合、リーダーは自発的に辞任します。reconfirm失敗の原因をさらに調査する必要があります。

### Takeover失敗

CLOG reconfirmが成功すると、takeover状態に入り、RoleChangeServiceモジュールが具体的な就任ロジックを実行します。RoleChangeServiceモジュールに異常が発生した場合、クラスタはリーダー不在となります。Takeover失敗の原因をさらに調査する必要があります。

### トランザクションコールバックの実行異常

リーダーレプリカのトランザクションスライディングウィンドウの左端のCLOGログが一定のしきい値（10秒）を超えて多数派に達せずに滑り出た場合、リーダーが異常に辞任し、クラスタがリーダー不在となります。

エラーの例は以下のとおりです。


さらに調査できる事項：

* ローカルのCLOGディスクへの書き込みが遅い場合は、CLOGディスクの負荷や待機時間などの指標を調査します。
* フォロワーレプリカのディスクへの書き込みが遅い場合は、上記と同じ方法で調査します。
* リーダーとフォロワー間のネットワークが遅い場合。例えば、`packet fly cost too much time` が表示され、ネットワークパケットの転送に時間がかかりすぎる場合です。
