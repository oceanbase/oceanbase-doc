# SQL実行エラーのトラブルシューティング

データベースの運用保守において、SQL実行エラーは非常に一般的であり、業務に直接影響を与える可能性があります。SQL実行エラーの原因は多岐にわたります。例えば、データベースへの接続が正しくできない、データベースユーザー権限が不足している、構文エラー、またはデータがクエリ条件を満たしていないなどが挙げられます。

皆様が迅速に問題の根本原因を特定し、効率的に解決できるよう支援するため、以下に明確で実用的なSQLエラーのトラブルシューティングプロセスをまとめました。このプロセスは、明確な操作手順を提供し、問題処理の効率を向上させ、業務への影響を最小限に抑えることを目的としています。これにより、日常的な運用保守作業を強力にサポートします。

## プロセスの紹介

SQL実行時にエラーが発生した場合、以下のプロセスに従って問題のトラブルシューティングを行うことができます。

SQL実行時にエラーが発生した後、まずはSQLエラーメッセージを確認する必要があります。エラーメッセージに明確なエラーコードが含まれている場合は、そのエラーコードをもとに問題のトラブルシューティングを行います。明確なエラーコードが欠けている場合は、その問題のエラータイプを判断し、アプリケーション実行エラーか手動SQL実行エラーかを特定します。

1. アプリケーション実行エラーの場合、具体的なトラブルシューティング方法については、[アプリケーション例外 -- エラーメッセージにOceanBaseエラーコードが含まれない場合](1300.application-exception-without-ob-error-code.md)および[アプリケーション例外 -- エラーメッセージにOceanBaseエラーコードが含まれる場合](1400.application-exception-with-ob-error-code.md)を参照してください。

2. 手動SQL実行エラーの場合、手動で再現可能かどうかを判断します。

   1. 再現できない場合は、SQL文を元に[ナレッジベースドキュメント](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000324072)で関連内容を検索し、参考にしながらトラブルシューティングを行います。
   2. 再現可能な場合は、まず問題シナリオを再現します。元のシナリオに基づき、2881または2883ポートを使用してOceanBaseクラスタに接続し、元のSQL文を実行して問題シナリオを再現します。

      SQLエラーシナリオを再現した後、以下の手順に従って関連情報を収集し、問題のトラブルシューティングを行います。

      1. 以下のステートメントを実行して、`trace_id`を取得します。

         <main id="notice" type='notice'>
         <h4>注意</h4>
         <p>エラーが発生したSQLを実行した直後に、次のステートメントを実行する必要があります。そうしないと、照会されるのはエラーが発生したSQLの<code>trace_id</code>ではありません。</p>
         </main>

         :::tab
         tab MySQLモード

         MySQLモードで`trace_id`を取得するステートメントは次のとおりです：

         ```shell
         obclient> SELECT last_trace_id();
         ```

         tab Oracleモード

         Oracleモードで`trace_id`を取得するステートメントは次のとおりです：

         ```shell
         obclient> SELECT last_trace_id() FROM DUAL;
         ```

         :::

      2. 取得した`trace_id`に基づいて、実際にそのSQLを実行したホスト情報を取得します。

         OceanBaseクラスタは一般的にマルチノードでデプロイされており、以下のSQLを使用してSQLが実際に実行されたノードを取得し、その後ログフィルタリングを行うことができます。

         :::tab
         タブ MySQLモード

         MySQLモードでは、次のステートメントを実行します。

         ```shell
         obclient> SELECT * FROM oceanbase.GV$OB_SQL_AUDIT WHERE trace_id=last_trace_id;
         ```

         ここで、`last_trace_id` は前のステップで取得した `trace_id` に置き換える必要があります。

         tab Oracleモード

         Oracleモードで以下のステートメントを実行します：

         ```shell
         obclient> SELECT * FROM SYS.GV$OB_SQL_AUDIT WHERE trace_id=last_trace_id;
         ```

         ここで、`last_trace_id` は前のステップで取得した `trace_id` に置き換える必要があります。

         :::

         `GV$OB_SQL_AUDIT`ビューのクエリ結果に基づくと、`svr_ip`に対応するホストが実際にそのSQLを実行したホストです。

      3. 取得したホスト情報に基づいて、`ssh`コマンドを使用して対応するホストにログインします。

      4. ログが保存されているディレクトリに移動します。

         以下は、OceanBaseデータベースのインストールディレクトリを`/home/admin/oceanbase`とした例です。ログの具体的な保存パスは、実際の環境に基づいてください。

         ```shell
         cd /home/admin/oceanbase/log
         ```

      5. 以下のコマンドを実行して、ログ内の関連情報をフィルタリングします。

         ```shell
         grep "${trace_id}" observer.log
         ```

         ```shell
         grep "${trace_id}" observer.log.xxx
         ```

         ここで、 `${trace_id}`は前のステップで取得した`trace_id`に置き換える必要があります。`observer.log.xxx`はタイムスタンプ付きのログファイルであり、`xxx`はSQLエラーが再現された時間に基づいて実際のタイムスタンプに置き換える必要があります。

      6. ログが提供する情報に基づいて、エラーコードや関連するエラーメッセージなどを組み合わせて問題を分析します。

         ログおよびエラーコードに関する詳細については、[ログの概要](../800.logging/100.logging-overview.md)および[エラーメッセージの概要](../../700.reference/900.error-code/600.error-code-of-mysql-mode/100.use-error-information-of-mysql-mode.md)を参照してください。

         ログ内の情報が不明確な場合は、技術サポート担当者に連絡し、トラブルシューティングの支援を依頼してください。

## タイプケース

以下は、一部の典型的なSQL実行エラーのトラブルシューティング事例です。

:::tab
tab MySQLモード

* SQLエラーが再現された後、データベースの実行結果にエラーコード情報が含まれます。

  * `SELECT` ステートメントに多数の `OR` 条件、または大量の `AND` で結合された `IN` 条件、あるいは多数の `AND NOT` 条件が含まれている場合、`SELECT` ステートメントの実行時にエラー `-4013, No memory or reach tenant memory limit` が発生します。具体的なトラブルシューティング手順については、[SQL解析段階でエラー-4013、テナントメモリ満杯](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000209941?back=kb)を参照してください。

* ログにエラーコード情報が含まれます。

  * SQLステートメントを実行して `longtext` 型のフィールドを処理する際、エラー `ErrorCode=5098` が発生します。具体的なトラブルシューティング手順については、[SQLエラー：Varchar value is too long for the column](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000670003?back=kb)を参照してください。

  * SQL実行エラー `error 4119 (RPC packet to send too long)` が発生し、同時に `trace_id` を使用して `observer.log` を照会すると、情報 `obrpc packet payload execced its limit` が表示されます。具体的なトラブルシューティング手順については、[SQL実行エラー -4119、RPC packet to send too long](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000210005?back=kb)を参照してください。

* ログにその他のエラー情報が含まれます。

  * SQLステートメントのフィルタ条件において、同一ではないフィールドの判断条件が64個を超えると、エラー `-4002 Invalid argument` が発生します。具体的なトラブルシューティング手順については、[SQLステートメントのフィルタ条件に同一ではないフィールドの判断条件が64個を超えるとエラー-4002が発生する](https://www.oceanbase.com/knowledge-base/oceanbase-database-1000000000450149?back=kb)を参照してください。

tab Oracleモード

* SQLエラーが再現された後、データベースの実行結果にエラーコード情報が含まれます。

  * `c1,c2,c3` 列を含むクエリステートメントでは、列 `c1,c2` がインデックスヒットし、かつ `c1` または `c2` 列に複数の `in` 式が存在する場合、`c1/c2/c3` のいずれかがベクトル式を形成します。このステートメントを実行する際に `internal error` が発生し、エラーコードは `ORA-00600` となります。具体的なトラブルシューティング手順については、[複数のinおよびベクトル式を含むSQL実行エラー4016](https://www.oceanbase.com/knowledge-base/oceanbase-database-20000043623?back=kb)を参照してください。

* SQL実行後にエラーコードがあり、ログのエラーコード情報と組み合わせて使用します。

  * SQLステートメントの実行時に `Timeout` エラーが発生し、エラーコードは `ORA-00600` です。具体的なトラブルシューティング手順については、[SQL実行エラーtimeout](https://www.oceanbase.com/knowledge-base/odc-1000000000262293?back=kb)を参照してください。

:::
