# ラテラル派生テーブル

本記事では、ラテラル派生テーブル(Lateral Derived Table)の基本的な概念、構文、および関連する例を紹介します。

## ラテラル派生テーブルの概要

派生テーブル(Derived Table)とは、`FROM` 句内で使用されるサブクエリであり、このサブクエリが生成する結果セットは一時的に外側のクエリでテーブルとして使用されます。派生テーブルは通常、データをグループ化および集計する場合、または特定の条件を満たすデータセットを作成して主クエリでさらに使用するために用いられます。

一方、ラテラル派生テーブル(Lateral Derived Table)とは、特別なタイプの派生テーブルであり、`LATERAL` キーワードを使用して、派生テーブルを指定し、同じ `FROM` 句内で以前に定義された他のテーブルや派生テーブルのフィールドを参照できるようにします。これにより、派生テーブル内のサブクエリは同一の `FROM` 句内で定義されたテーブルに依存でき、これらのテーブルの列値にアクセスできます。

ラテラル派生テーブルの主な特徴は、それらが `FROM` 句内で先に定義されたテーブルの列を参照できることです。これは一般的な派生テーブルにはない機能です。

## LATERALキーワードの使用方法

```sql
SELECT select_list
FROM table_name1,
LATERAL (SELECT select_list
         FROM table_name2
         WHERE table_name2.col_name = table_name1.col_name) AS lateral_derived_table_name;
[...]
```

**パラメータの説明：**

| **パラメータ** | **説明** |
|----------|----------|
| select_list | 検索する列のリストで、列名、式、集約関数などを指定できます。複数の列をカンマで区切って指定できます。|
| table_name1 | クエリ対象となるメインテーブルです。|
| LATERAL | 横方向に結合されたサブクエリ（横方向に派生したテーブル）を指定するために使用されます。|
| table_name2 | フェッチ元のテーブルで、`LATERAL` サブクエリ内で参照され、`table_name1` の各行データに関連する追加情報を提供します。|
| lateral_derived_table_name | フェッチ元のテーブルの別名で、後続のクエリで参照するために使用されます。|
| [...] | `WHERE` 句などのオプションのクエリ句です。|

## 例

### テストテーブルを作成し、テストデータを追加する

1. テーブル `students` を作成します。

    ```sql
    CREATE TABLE students (
      id NUMBER PRIMARY KEY,
      name VARCHAR2(50) NOT NULL,
      age NUMBER
    );
    ```

2. テーブル `students` に3件のデータを挿入します。

    ```sql
    INSERT INTO students
      VALUES (1, 'name1', 20),
      (2, 'name2', 22),
      (3, 'name3', 21);
    ```

3. テーブル `scores` を作成します。

    ```sql
    CREATE TABLE scores (
      id NUMBER PRIMARY KEY,
      student_id NUMBER,
      subject VARCHAR2(50) NOT NULL,
      score DECIMAL(5, 2),
      FOREIGN KEY (student_id) REFERENCES students(id)
    );
    ```

4. テーブル `scores` に9件のデータを挿入します。

    ```sql
    INSERT INTO scores
      VALUES (1, 1, 'A', 86.5),
      (2, 1, 'B', 90.0),
      (3, 1, 'C', 91.5),
      (4, 2, 'A', 86.0),
      (5, 2, 'B', 92.0),
      (6, 2, 'C', 89.5),
      (7, 3, 'A', 93.0),
      (8, 3, 'B', 92.5),
      (9, 3, 'C', 85.0);
    ```

### テストデータの照会

`students` と `scores` の2つのテーブルから、各生徒の氏名、平均点、および最高点を取得します。

Q1：複数のサブクエリを使用して要件データを取得します。`scores` テーブルに対して2回独立したグループ化集計操作を行い、それぞれで平均点と最高点を計算するために `scores` テーブルを2回スキャンします。その後、`WHERE` 句を使用して結果を `students` テーブルと結合します。

```sql
SELECT st.name, sc.avg_score, scs.max_score
FROM students st,
  (SELECT student_id, AVG(score) avg_score
   FROM scores
   GROUP BY student_id) sc,
   (SELECT student_id, MAX(score) max_score
   FROM scores
   GROUP BY student_id) scs
WHERE sc.student_id = st.id
AND scs.student_id = st.id;
```

実行結果は次のとおりです：

```shell
+-------+-------------------------------------------+-----------+
| NAME  | AVG_SCORE                                 | MAX_SCORE |
+-------+-------------------------------------------+-----------+
| name1 | 89.33333333333333333333333333333333333333 |      91.5 |
| name2 | 89.16666666666666666666666666666666666667 |        92 |
| name3 | 90.16666666666666666666666666666666666667 |        93 |
+-------+-------------------------------------------+-----------+
3 rows in set
```

Q2：`LATERAL` キーワードを使用して要件データを取得します。`LATERAL` キーワード（横方向の派生テーブル）を使用し、1行のSQLステートメント内で各生徒の平均点と最高点を同時に計算します。また、各生徒 `ID` に対してのみ `scores` テーブルを1回スキャンします。

```sql
SELECT st.name, ld_tbl.avg_score, ld_tbl.max_score
FROM students st,
  LATERAL (SELECT AVG(score) avg_score, MAX(score) max_score
           FROM scores sc
           WHERE sc.student_id = st.id) ld_tbl;
```

実行結果は次のとおりです：

```shell
+-------+-------------------------------------------+-----------+
| NAME  | AVG_SCORE                                 | MAX_SCORE |
+-------+-------------------------------------------+-----------+
| name1 | 89.33333333333333333333333333333333333333 |      91.5 |
| name2 | 89.16666666666666666666666666666666666667 |        92 |
| name3 | 90.16666666666666666666666666666666666667 |        93 |
+-------+-------------------------------------------+-----------+
3 rows in set
```

Q2は、`scores` テーブルに対する重複スキャンを回避しているため、大規模なデータセットを処理する場合にQ1よりも高いパフォーマンスを発揮する可能性があります。また、Q2の書き方はより明確でコンパクトであり、理解や保守が容易です。
