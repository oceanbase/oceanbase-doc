# データベース接続プールの設定

データベース接続プールの設定は、システムとデータベース間の効率的で安定した接続を確保するための重要な手順です。適切な接続プール設定は、データベース接続数を効果的に管理し、高並列による接続枯渇問題を回避するだけでなく、適切なタイムアウト設定により、無効な接続をタイムリーにクリーンアップし、システムのパフォーマンスを確保することもできます。

本記事では、接続プールの基本概念、異なる接続プールの比較、選択ガイド、接続プールパラメーターの推奨設定、およびJDBC設定の重要なパラメーターについて紹介し、開発者がデータベースアクセスを最適化するのを支援します。

## 接続プールの基本概念

データベース接続プールは、データベース接続を管理するための技術であり、アプリケーションとデータベースの間に接続プールを構築し、あらかじめ一定数のデータベース接続を作成し、これらの接続をメモリに保存します。アプリケーションがデータベースにアクセスする必要があるとき、毎回新しい接続を作成するのではなく、接続プールから直接接続を取得し、使用後に接続を接続プールに返却することができます。

接続プールの主な利点には、次のものが含まれます：

* **パフォーマンスの向上**：接続の頻繁な作成と破棄によるオーバーヘッドを避けます。
* **リソース管理**：データベース接続の数を制御し、接続枯渇を防ぎます。
* **接続の再利用**：接続の利用率を向上させ、リソースの無駄を削減します。
* **接続モニタリング**：接続状態のモニタリングと統計情報を提供します。

## 接続プールパラメーター

### 接続プール設定の推奨

* 管理コンソールの日常運用においては、最低2つの接続を維持されることが推奨されます。具体的な接続数は、ビジネスの同時実行数とトランザクションの所要時間に応じて調整します。

* 接続のアイドルタイムアウト時間を設定します。30分を推奨しています。

  MySQLでは、デフォルトで8時間後に接続を切断しますが、クライアントはそれを認識できず、結果としてダーティ接続になります。接続プールは、ハートビートやtestOnBorrowなどのメカニズムを使用して、接続が有効かどうかを確認できます。この時間内に接続が使用されなかった場合、接続は直接切断されます。

## JDBC設定パラメーター

JDBCにおけるいくつかの重要なパラメーターは、必ず設定する必要があります。いずれも接続プールのConnectionPropertiesまたはJdbcUrlに設定することができます。具体的なパラメーターとその説明は以下の表のとおりです。

| パラメーター           | 説明                                                |
|----------------|-----------------------------------------------------|
| socketTimeout  | ネットワークSocketのタイムアウトをミリ秒単位で定義しています。値が0の場合、タイムアウト制限がないことを意味します。システム変数 `max_statement_time` を設定することで、クエリの実行時間を制限することもできます。デフォルト値：0（標準設定）。|
| connectTimeout | 接続タイムアウト値（ミリ秒単位）。値が0の場合、タイムアウト制限がないことを意味します。デフォルト値：30000。 |

### JDBC設定例

本記事では、JDBC設定例を紹介します。

JDBCを使用してデータベースに接続する際は、データベース使用のパフォーマンスを最大限にするために、関連するパラメーターを設定する必要があります。ここでは、いくつか関連するパラメーターの設定をご紹介します。

JDBC接続の例は以下のとおりです：

```java
conn=jdbc:oceanbase://xxx.xxx.xxx.xxx:3306/test?rewriteBatchedStatements=TRUE&allowMultiQueries=TRUE&useLocalSessionState=TRUE&useUnicode=TRUE&characterEncoding=utf-8&socketTimeout=10000&connectTimeout=30000
```

この接続では、関係する設定パラメーターは以下のとおりです：

* `rewriteBatchedStatements`：TRUEに設定することが推奨されます。

  * OceanBaseのJDBCドライバーは、デフォルトではexecuteBatch()ステートメントを無視し、一括で実行される一連のSQLステートメントを分割して、1つずつデータベースに送信します。この場合、一括挿入は実際には単一挿入となり、直接的にパフォーマンスの低下につながります。一括挿入を実際に実行するには、このパラメーターをTRUEに設定する必要があります。これにより、ドライバーはSQLを一括処理で実行します。つまり、addBatchメソッドを使用して、同一テーブル上の複数のinsertステートメントを結合し、1つのinsertステートメント内の複数のvalues値の形式にすることで、batch insertのパフォーマンスを向上させます。

  * 必ずprepareStatementメソッドを使用して、各insertをprepareしてから、addBatchを実行する必要があります。そうしないと、統合実行がされません。

* `allowMultiQueries`：TRUEに設定することが推奨されます。

  JDBCドライバーは、アプリケーションコードが複数のSQLをセミコロン（;）で連結して、1つのSQLステートメントとしてserverに送信することを許可しています。

* `useLocalSessionState`：トランザクションが頻繁的にOBデータベースにsession変数クエリSQLを送信するのを回避するには、TRUEに設定することが推奨されます。

  session変数は主に：autocommit、read_only、およびtransaction isolation。

* `socketTimeout`：SQL実行時に、socketがSQLの応答を待機する時間。

* `connectTimeout`：接続確立時に、接続を待機する時間。

* `useCursorFetch`：`TRUE` に設定することが推奨されます。

  大規模なデータ量のクエリステートメントに対して、データベースServerはCursorを作成し、FetchSizeのサイズに応じてデータをClientに配布します。このプロパティを `TRUE` に設定すると、自動的に `useServerPrepStms=TRUE` も設定されます。

* `useServerPrepStms`：SQLをデータベースserverに送信するためにPSプロトコルを使用するかどうかを制御します。

  `TRUE` に設定されている場合、SQLはデータベース内で2つのステップで実行されます。

  * `？` を含むSQLステートメントをデータベースServerに送信してPrepareします（`SQL_audit: request_type=5`）。

  * データベース内で実際のValueを使用してExecute（`SQL_audit: request_type=6`）。

* `cachePrepStmts`：JDBC driverがPreparedStatmentをキャッシュするためにPS cacheを有効にするかどうかを制御し、prepareの重複実行（client側とserver側）を回避します。`cachePrepStmts=TRUE` は、`useServerPrepStms=TRUE` を使用して同一のSQLにbatch executeを繰り返すシナリオに有効です。各batch excecuteには、prepareと `executecachePrepStmts=TRUE` が含まれ、重複するprepare操作を回避できます。

* `prepStmtCacheSQLLimit`：PS cacheに格納可能なSQLの長さには制限があり、長すぎるSQLはキャッシュに格納できません。prepStmtCacheSize：PS cacheに保存できるSQLの数。

* `maxBatchTotalParamsNum`：batch操作において、1つのSQLが最大、サポートできるパラメーターの数（つまり、batch内の `?` の数）。パラメーター数が制限を超えた場合、batch SQLは分割されます。
