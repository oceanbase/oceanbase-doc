# 列存副本的使用与自动路由

为满足 TP 与 AP 混合负载等场景，OceanBase 数据库提供**列存副本**（COLUMNSTORE，简称 **C 副本**）。C 副本可部署在独立 Zone 上；用户表在该副本中以列存格式存储，有利于降低大范围扫描代价、提升分析型查询效率。

本文说明 C 副本的基本概念与限制、在租户中的部署步骤，以及 **方式一（经独立 ODP）** 与 **方式二（直连 OBServer + 自动路由）** 的选型与操作要点。从 **OceanBase V4.6.0** 起，方式二依赖 **`ap_query_*` 系统变量** 等实现列存副本自动路由；读一致性相关说明见下文第三章。

关于「哪些语句会尝试列存路径」等判定细则，参见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

## 快速决策：方式一还是方式二

| 若您的情况是…… | 建议 |
| -------------- | ---- |
| OceanBase **低于 V4.6.0** | 必须使用 **方式一**（独立 ODP + ODP 侧路由与弱读配置）。 |
| **V4.6.0 及以上**，希望减少专用列存 ODP 的运维 | 优先 **方式二**（直连或经普通 ODP 到 OBServer，用 `ap_query_route_policy` 等控制）。 |
| **V4.6.0 及以上**，但仍要求 **AP 与 TP 入口完全隔离**、分析流量固定走专用代理 | 可继续采用 **方式一**。 |

选定后，请到 **「一、认识列存副本」** 对照注意项，再到 **「二、使用列存副本」** 完成部署与访问配置。

## 一、认识列存副本

### C 副本是什么

**列存副本（C 副本）** 是 OceanBase 的一种只读副本类型，主要用于承载 **分析型（AP）只读查询**。数据在 C 副本上以 **列存** 组织，与全能副本（F）、只读副本（R）等配合使用：TP 写入与常规强读仍主要落在 F/R；AP 扫描可在 C 副本上获得更合适的存储形态。

本文以下所说的 **「列存副本」** 与 **「C 副本」** 同义；**OBServer** 指数据库进程所在节点；**ODP** 指 OceanBase 数据库代理。 **独立 ODP** 指专用于将 AP 弱读定向到 C 副本的一套 ODP 部署及配置；**普通 ODP** 指未按方式一做列存专线配置的代理，仅转发到 OBServer。

### 两种访问形态

按 **OceanBase 版本** 与 **是否需要专用 AP 入口**，常见两种形态如下。

| 形态 | 适用版本 | 典型场景 | 是否推荐 / 是否必须 |
| ---- | -------- | -------- | -------------------- |
| **方式一：经独立 ODP 访问 C 副本** | **V4.6.0 之前** | 必须将 AP 经专用代理打到 C 副本 | **旧版本必选** |
| **方式一** | **V4.6.0 及以上** | TP 与 AP **物理隔离**，分析连接独立 ODP | 按架构需要选用 |
| **方式二：直连 OBServer + 自动路由** | **V4.6.0 及以上** | 不单独维护列存专用 ODP，由系统自动尝试列存计划 | **多数场景推荐** |

**方式一要点：** 在 ODP（`proxysys`）上配置 **弱读**，并把弱读请求 **限定到 C 副本所在 Zone 或 ColumnStore 副本类型**，常配合会话初始化中的 **`ob_route_policy = COLUMN_STORE_ONLY`**，以便生成列存侧执行计划。具体命令见 **「二、使用列存副本」** 中方式一小节。

**方式二要点：** 业务使用常规连接串连接 **OBServer**，或经 **普通 ODP** 转发（只要 SQL 到达 OBServer）。是否在 C 副本上规划只读部分，由 OBServer 上 **`ap_query_*`** 及 [路由判定规则](300.ap-query-column-replica-routing-rules.md) 决定，**无需**再配置方式一中的 ODP 路由项。

### 使用限制

以下条目为 **硬性限制**，规划前请确认：

* C 副本与 **F** 或 **R** 副本 **不支持** 互相转换。
* **物理恢复** 不支持恢复 C 副本；租户的 Locality 若包含 C 副本，恢复将失败。
* **V4.6.0 之前**：R 副本上的查询 **不允许** 转发到 C 副本；C 副本上的用户表查询 **不允许** 转发到 F/R 副本，否则报错。**V4.6.0 起** 支持从 **F 副本** 将查询转发到 C 副本（以当前版本说明为准）。

### 部署建议

* 从 V4.3.5 BP1 起支持多个 C 副本，建议最多 **3** 个。
* 采用 **方式一** 时，建议 C 副本所在 Zone **尽量只部署 C 副本**；独立 ODP 版本需 **ODP V4.3.2 及以上**。
* 主库未部署 C 副本时，**备库不建议** 部署 C 副本。

### 运维注意事项

* 集群存在 C 副本时，**DDL** 会额外占用 CPU、内存、磁盘与 IO。
* C 副本 **合并** 通常慢于 F/R；**上一轮合并未完成时，无法发起新一轮租户级合并**。手动合并前建议查看 [CDB_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/12000.o-cdb_ob_zone_major_compaction-of-sys-tenant.md)、[DBA_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13000.o-dba_ob_zone_major_compaction-of-mysql-mode.md)，详见 [查看合并信息](../../700.reference/200.system-management/500.manage-data-storage/200.merge-management/500.view-merge-process.md)。

### C 副本上暂为行存的几种场景

**结论（可先记住）：** 在补副本、日志流 Rebuild、部分 DDL 与导入等过程中，C 副本上部分数据可能 **暂时仍以行存基线** 存在，后台 **行转列** 完成后才变为列存。此期间 **查询仍可执行**；若优化器已生成列存计划，实际仍可能读行存基线，属预期现象。

**背景（简要）：** 行存表在 C 副本上的 **目标形态** 为列存；列存表在 C 副本侧可与 F 副本对齐。C 副本承担将 F 副本侧行存用户数据 **转换为列存** 的职责；**「列存」指稳定后的存储形态**，并非每个时刻、每个分区都已转换完毕。

| 场景 | 说明 |
| ---- | ---- |
| **补副本（增加副本）** | 例如 Locality 由 `F@z1, F@z2` 变为 `F@z1, F@z2, C@z3`：基线从 F/R 迁到 C 时可能先为行存并发起行转列；若行转列多次失败（如 DAG 队列满、I/O 或磁盘压力），可能先提供基于行存的弱读。 |
| **日志流 Rebuild** | C 副本日志流 Rebuild 时从源端拉取的基线若为行存，则暂时为行存，再行转列。 |
| **补副本与 Offline DDL 并发** | 并发下 C 副本可能对 DDL 所在日志流 Leader 不可见，会先构建行存基线，再行转列。 |
| **全量旁路导入** | 当前可先向 C 副本导入行存，再由后台行转列。 |
| **表级恢复** | 列存表表级恢复能力受限时，C 副本上可能先恢复为行存，再行转列。 |

可通过 [CDB_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/8120.o-cdb_ob_cs_replica_stats-of-sys-tenant.md)（系统租户）、[DBA_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/8220.o-dba_ob_cs_replica_stats-of-mysql-mode.md)（用户租户）查看行转列进度；待任务完成后再依赖 C 副本纯列存读性能更稳妥。

sys 租户查询示例：

```sql
SELECT * FROM oceanbase.CDB_OB_CS_REPLICA_STATS;
```

示例输出（字段含义以实际版本为准）：

```text
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
| TENANT_ID | SVR_IP         | SVR_PORT | LS_ID | TOTAL_TABLET_CNT | AVAILABLE_TABLET_CNT | TOTAL_MACRO_BLOCK_CNT | AVAILABLE_MACRO_BLOCK_CNT | AVAILABLE |
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
|      1004 | xx.xxx.xxx.212 |    63000 |  1001 |             1019 |                 1019 |                 10706 |                     10706 | TRUE      |
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
```

可用 `AVAILABLE_TABLET_CNT / TOTAL_TABLET_CNT` 或 `AVAILABLE_MACRO_BLOCK_CNT / TOTAL_MACRO_BLOCK_CNT` 粗估进度。仅当该日志流上 Tablet 均可用时，日志流才视为完全可用。

## 二、使用列存副本

**部署 C 副本**（本节「步骤一」）与 **是否部署独立 ODP** 无必然关系：完成 Locality 中的 C 副本后，**仅当采用方式一** 时，才需要继续部署并配置 **独立 ODP**。**方式二** 无需为列存单独新增 ODP 步骤。

### 步骤一：在租户中部署 C 副本

在租户 **Locality** 中指定 C 副本即可，常见两类操作：

* **场景 A**：新建租户时即包含 C 副本。
* **场景 B**：为已有租户增加 C 副本（新 Zone + 调整 Locality）。

以下 SQL 中的 **CPU、内存、磁盘等数值仅为示例**，请按实际负载与资源规划调整。

#### 场景 A：新建包含 C 副本的租户

以下以 **2F1A**（两副本 + 1 仲裁）及 zone1、zone2、zone3 为例说明 **创建租户与 C 副本** 的流程，**并非**要求集群必须是该拓扑；请以实际集群与资源规划为准。

1. 创建资源单元 `unit1`。

    ```sql
    CREATE RESOURCE UNIT unit1,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

2. 创建资源池 `pool1`。

    ```sql
    CREATE RESOURCE POOL pool1
        UNIT='unit1',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone1','zone2','zone3');
    ```

3. 创建租户 `tenant_c`，Locality 为 `F@zone1,F@zone2,C@zone3`。

    ```sql
    CREATE TENANT tenant_c
        LOCALITY = 'F@zone1,F@zone2,C@zone3',
        PRIMARY_ZONE='zone1;zone2,zone3',
        RESOURCE_POOL_LIST=('pool1') SET ob_tcp_invited_nodes = '%';
    ```

    默认一般为 MySQL 模式；Oracle 模式需通过 [ob_compatibility_mode](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/6100.ob_compatibility_mode-global.md) 指定 `ob_compatibility_mode='oracle'`。

#### 场景 B：为已有租户增加 C 副本

假设租户 `tenant_c` 当前 Locality 为 `F@zone1,F@zone2,F@zone3`，资源池 `pool1` 的 `ZONE_LIST` 为 `'zone1','zone2','zone3'`。拟新增 **zone4** 上的 C 副本，目标 Locality 为 `F@zone1,F@zone2,F@zone3,C@zone4`：

1. 添加 Zone **zone4**，参见 [添加 Zone](../../600.manage/100.cluster-management/300.common-cluster-operations/800.add-a-zone.md)。
2. 向 **zone4** 添加节点，参见 [添加节点](../../600.manage/100.cluster-management/300.common-cluster-operations/400.add-a-node.md)。
3. 创建资源单元 `unit2`。

    ```sql
    CREATE RESOURCE UNIT unit2,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

4. 创建资源池 `pool2`，`ZONE_LIST = ('zone4')`。

    ```sql
    CREATE RESOURCE POOL pool2
        UNIT = 'unit2',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone4');
    ```

5. 为租户增加资源池 `pool2`。

    ```sql
    ALTER TENANT tenant_c RESOURCE_POOL_LIST = ('pool1','pool2');
    ```

6. 修改 Locality。

    ```sql
    ALTER TENANT tenant_c LOCALITY = 'F@zone1,F@zone2,F@zone3,C@zone4';
    ```

### 方式一：经独立 ODP 访问 C 副本

适用于 **V4.6.0 之前**，或 **V4.6.0+** 仍需 **专用独立 ODP** 将 AP 弱读固定路由到 C 副本、与 TP 链路隔离的场景。

#### 部署 ODP

在可与集群互通的机器上部署 **专用于访问 C 副本** 的 ODP（建议单机部署），版本 **不低于 ODP V4.3.2**。步骤见 [部署 ODP](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000001600960)。

#### 配置路由转发策略及弱读

使用 `root@proxysys` 登录该 ODP，例如：

```shell
obclient -uroot@proxysys -h10.10.10.1 -P2883 -p
```

下列 **组合一** 与 **组合二** 任选其一。**选择建议：**

* 已明确 **C 副本所在 Zone**，且希望弱读流量按 Zone 收敛时，优先 **组合一**（`proxy_primary_zone_name`）。
* 更希望按 **副本类型（ColumnStore）** 路由、而不绑定固定 Zone 名时，使用 **组合二**（`route_target_replica_type`）。

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>ODP 配置项含义可能与字面不完全一致。示例中 <code>obproxy_read_consistency = 1</code> 表示弱一致性读。<code>obproxy_read_only</code> 等参数请以当前使用的 ODP 版本文档为准。</p>
</main>

* **组合一**

  * 只读与弱读相关项：

      ```shell
      obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
      obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
      ```

  * 弱读时仅路由到 C 副本所在 Zone（示例为 `zone4`），并生成列存侧计划：

      ```shell
      obclient> ALTER PROXYCONFIG SET proxy_primary_zone_name='zone4';
      obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
      ```

* **组合二**

  * 只读与弱读相关项：

      ```shell
      obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
      obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
      ```

  * 弱读时按 ColumnStore 副本路由并生成列存计划：

      ```shell
      obclient> ALTER PROXYCONFIG SET route_target_replica_type = 'ColumnStore';
      obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
      ```

  * 弱读仅选从副本，从副本均不可用时断开连接：

      ```shell
      obclient> ALTER PROXYCONFIG SET proxy_route_policy='TARGET_REPLICA_TYPE_FOLLOWER_ONLY';
      ```

修改后建议执行：

```shell
obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_only';
obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_consistency';
obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_primary_zone_name';
obclient> SHOW PROXYCONFIG ALL LIKE 'init_sql';
obclient> SHOW PROXYCONFIG ALL LIKE 'route_target_replica_type';
obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_route_policy';
```

配置成功后，OLAP 业务通过该 **独立 ODP** 接入，将查询定向到 C 副本。

### 方式二：直连 OBServer 并使用自动路由（V4.6.0 及以上）

适用于已完成 **C 副本部署**、且不采用方式一中 **独立 ODP 专线配置** 的场景。请使用常规方式连接 **OBServer**，或经 **普通 ODP** 将请求转发至 OBServer。

**最小验证示例**（表名、条件请按环境替换）：

```sql
-- 1. 确认自动路由相关变量存在及默认值
SHOW VARIABLES LIKE 'ap_query%';

-- 2. 本会话保持默认 AUTO 或显式指定（可选）
SET SESSION ap_query_route_policy = 'AUTO';

-- 3. 查看是否出现列存侧相关计划（以实际算子为准）
EXPLAIN SELECT COUNT(*) FROM your_table;
```

是否在 C 副本上规划只读部分，由 **`ap_query_route_policy`、`ap_query_cost_threshold`、`ap_query_replica_fallback`** 与 [路由判定规则](300.ap-query-column-replica-routing-rules.md)、读一致性等共同决定。完整变量说明见 **「三、列存副本自动路由」**。

## 三、列存副本自动路由

<a id="cs-auto-routing"></a>

从 **OceanBase V4.6.0** 起，可通过系统变量与 Hint 控制只读查询是否在 **C 副本** 上规划与执行（**列存副本自动选择 / 自动路由**）。**`ap_query_route_policy`** 为主开关：在只读路径规划阶段，控制是否尝试识别分析型查询并生成列存侧计划。

**何时尝试列存路径**、与 AP 查询的关系、常见否例等，见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

<main id="notice" type='notice'>
  <h4>说明</h4>
  <p>从 V4.6.0 起，<strong>不强制</strong>为使用 C 副本而单独部署 ODP 并配置「二、方式一」中的 ODP 项；直连 OBServer 或经普通 ODP 时，可在本节通过会话/全局变量控制列存选择。</p>
</main>

### 适用版本与前提

* **版本**：OceanBase **V4.6.0 及以上**。
* **租户**：目标租户已在 Locality 中配置 **C 副本**，且副本可提供读服务。
* **变量**：执行 `SHOW VARIABLES LIKE 'ap_query%';`，确认 `ap_query_route_policy`、`ap_query_cost_threshold`、`ap_query_replica_fallback` 等是否存在。

### 快速上手

1. 确认已完成 **「二、使用列存副本」** 中的 C 副本部署，且副本可用。
2. 执行 `SHOW VARIABLES LIKE 'ap_query%';`。默认多为 **`ap_query_route_policy = AUTO`**，满足 [路由判定规则](300.ap-query-column-replica-routing-rules.md) 时会尝试列存计划；若无需改动策略，**不必**额外 `SET`。
3. 需要本会话强制或关闭自动选列存时，再设置 `ap_query_route_policy` 等（见下文章节）。
4. 对目标 SQL 执行 `EXPLAIN`，结合 `DBA_OB_CS_REPLICA_STATS` / `CDB_OB_CS_REPLICA_STATS` 与 **「一、暂为行存」** 所述进度，确认 C 副本与行转列状态。

**最短验证路径**可对照 **「二、方式二」** 中的三行 SQL 示例。

### 系统变量说明

下列变量用于列存副本自动选择；含义以集群 `SHOW VARIABLES` 及当前版本文档为准。

**`ap_query_route_policy` 取值（全文统一表述）：**

| 取值 | 含义 |
| ---- | ---- |
| **OFF** | 关闭列存副本自动选择逻辑；相关查询按行存等默认路径规划（与 V4.6.0 前习惯接近）。 |
| **AUTO** | 由优化器按规则与代价 **自动判断是否尝试** 列存侧计划（默认）。 |
| **FORCE** | 在满足前提条件时，**优先尝试** 在 C 副本上执行只读查询。 |

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_route_policy';
obclient> SET ap_query_route_policy = 'AUTO';
obclient> SET ap_query_route_policy = 'FORCE';
```

**`ap_query_cost_threshold`**：在 **AUTO** 下，**单并行度** 计划代价超过该阈值时，参与是否尝试列存侧计划的判断。默认值请以 `SHOW VARIABLES` 为准（常见默认 `200000`）。

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_cost_threshold';
obclient> SET SESSION ap_query_cost_threshold = 300000;
```

**`ap_query_replica_fallback`**：目标为 C 副本但副本不可用或无法完成规划时，是否允许回退行存。

| 取值 | 含义 |
| ---- | ---- |
| ON | 允许回退，查询尽量成功。 |
| OFF | 不因该原因回退，可能报错。 |

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_replica_fallback';
obclient> SET SESSION ap_query_replica_fallback = OFF;
```

#### 与 ob_route_policy 的关系

* **`ap_query_route_policy`**：作用于 **优化器是否尝试生成列存侧计划**（自动选择 / 强制 / 关闭）。
* **`ob_route_policy`**：作用于 **OBServer 内部读路径可选的副本类型**（如 `COLUMN_STORE_ONLY` 等）。

二者 **层次不同**，不是简单替代关系。**方式一** 中常在 `init_sql` 里设置 **`ob_route_policy = COLUMN_STORE_ONLY`**，与 ODP 路由项共同把流量导向列存；**方式二** 以 **`ap_query_*`** 为主。若同时设置，**语义与优先级以当前 OceanBase 版本说明为准**。详见 [ob_route_policy](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8900.ob_route_policy-global.md)。

### 按场景选择策略

在已理解上一节变量含义的前提下，可按下表选型。

| 场景诉求 | 策略建议 | 说明 |
| -------- | -------- | ---- |
| 多数场景：先试行存，满足 AP 特征再试 C 副本 | `ap_query_route_policy = AUTO`（默认） | 结合代价、并行等判断；可用 `ap_query_cost_threshold` 调节敏感度。 |
| 本会话分析读尽量稳定走 C 副本 | `ap_query_route_policy = FORCE` | 写入仍走主副本。 |
| 关闭自动选列存 | `ap_query_route_policy = OFF` | 同 **OFF** 统一表述。 |
| C 副本故障时可接受回落行存 | `ap_query_replica_fallback = ON`（默认） | |
| 必须只走列存，失败则报错 | `ap_query_replica_fallback = OFF` | |
| AUTO 下更多查询尝试列存 | **降低** `ap_query_cost_threshold` | 如 `100000`。 |
| AUTO 下仅很重查询才尝试列存 | **提高** `ap_query_cost_threshold` | 如 `300000`。 |
| 单条 SQL 与会话默认不同 | Hint，见下一节 | |

### 查询级别控制

适用于 **临时验证**、**单条 SQL 调优** 或 **不改会话全局默认** 时，在语句上使用 Hint：

* 该语句尽量按列存侧策略规划（在策略与副本允许的前提下）：

    ```shell
    obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'FORCE')*/ *
       FROM t1, t2
       WHERE t1.c1 = t2.c1;
    ```

* 该语句关闭自动选列存：

    ```shell
    obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'OFF')*/ *
        FROM t1, t2
        WHERE t1.c1 = t2.c1;
    ```

<a id="cs-read-consistency"></a>

### 列存副本上的读一致性

**V4.6.0 之前**，访问 C 副本时通常仅支持弱读（`ob_read_consistency = 'weak'`）。**V4.6.0 起**支持在 C 副本上 **强一致性读**。变量全局说明见 [ob_read_consistency](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8700.ob_read_consistency-global.md)。

#### 列存副本强读（简化理解）

强读场景下，事务层会基于 **全局一致性快照** 检查 C 副本（Follower）**日志回放是否已追到可读点**；必要时 **等待回放**，再执行查询。以下为 **便于理解的简化步骤**，非实现细节承诺：

1. 获取全局一致性快照版本（如经 GTS）。
2. 判断 C 副本是否已回放到该版本。
3. 未就绪则等待；就绪后执行读。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>强读可能因等待回放而增加延迟；极短的点查通常不适合在 C 副本上强读。</p>
</main>

#### 强读与弱读对比

| 特性 | 强读 | 弱读 |
| ---- | ---- | ---- |
| 一致性 | 与主副本一致 | 最终一致，可能略旧 |
| 延迟 | 可能需等待回放 | 通常更低 |
| 典型场景 | 高一致性 AP 读 | 可容忍短暂延迟的 AP 读 |
| 设置 | `ob_read_consistency = 'strong'`（默认） | `ob_read_consistency = 'weak'` |

**建议：** 一致性要求高时使用强读（默认）；可容忍延迟时，弱读往往性能更好。

在 **`ap_query_route_policy = AUTO`** 时，系统会综合 **弱读、并行度、代价阈值** 等条件判断是否尝试列存侧计划；**弱读是可能触发尝试的条件之一**，并非唯一条件。完整条件表见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

### 验证与排错建议

建议按顺序排查：

1. **C 副本**：租户 Locality 是否包含 C；副本是否可用；行转列是否完成（见 **「一、暂为行存」** 与 `CDB_OB_CS_REPLICA_STATS` / `DBA_OB_CS_REPLICA_STATS`）。
2. **变量**：`SHOW VARIABLES LIKE 'ap_query%';`，确认 `ap_query_route_policy` 等是否符合预期。
3. **执行计划**：对目标 SQL 执行 `EXPLAIN`（或查看实际执行计划），是否出现列存侧相关算子。
4. **仍未走列存**：对照 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md) 中的基本条件与 AUTO 触发项。

无 C 副本的租户：开启上述变量通常不会改变无列存时的基本规划行为。
