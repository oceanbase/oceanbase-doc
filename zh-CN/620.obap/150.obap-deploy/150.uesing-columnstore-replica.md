# 列存副本的使用与自动路由

为满足 TP 与 AP 混合负载（准实时决策分析）等场景，OceanBase 数据库提供**列存副本**（COLUMNSTORE，简称 **C 副本**）。用户可将 C 副本部署在独立 Zone 上；在 C 副本上，用户表（含复制表，不含索引表、内部表、系统表）以列存格式存储，便于分析型扫描。

本文主要介绍 **C 副本的概念、约束、暂为行存**、**如何使用 C 副本**（两种架构形态下的部署与访问步骤）、**列存副本自动路由**（V4.6.0 起 `ap_query_*` 等与读一致性说明）。路由判定细则见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

## 什么是列存副本

### 两种典型架构形态

按 **OceanBase 版本与访问路径**，使用 C 副本常见有两种形态，请先对照业务版本与是否需要专用 AP 入口选型，再进入**列存副本使用**中的对应小节。

| 形态 | 适用版本与典型场景 | 访问路径概要 |
| ---- | ------------------ | ------------ |
| **形态一：经独立 ODP 访问 C 副本** | **V4.6.0 之前**必须使用本形态；若 **V4.6.0 及之后**仍需将 AP 与 TP **流量物理隔离**、统一走**专用代理**访问 C 副本，也可继续采用 | **部署 C 副本 → 部署专用于 C 副本访问的 ODP（建议 V4.3.2+）→ 在 ODP 上配置弱读与仅指向 C 副本的路由项（见下文形态一）→ 业务连接该 ODP** |
| **形态二：直连（或常规连接）+ 自动路由** | **OceanBase V4.6.0 及以上**，且无需单独再为 C 副本搭一套「列存专用 ODP」时 **推荐** | **部署 C 副本 → 使用标准方式连接 OBServer 或现有通用 ODP → 通过会话/全局变量 `ap_query_route_policy` 等由优化器自动尝试列存计划（见本文「三、列存副本自动路由」）** |

形态一下列配置的作用是：**把 OLAP 只读请求配成弱读**，并让 ODP **只把这类请求路由到 C 副本所在 Zone 或 ColumnStore 副本类型**，同时在连接上注入 `ob_route_policy = COLUMN_STORE_ONLY` 等，从而生成列存侧执行计划。若您采用 **形态二**，则**不需要**再为「上列存」单独做这一套 ODP 侧配置；是否走列存由 **OBServer 侧** `ap_query_*` 与判定规则决定（经普通 ODP 时，只要转发到 OBServer，同样由这些变量生效）。

### 注意事项

使用 C 副本时，请注意：

* 从 V4.3.5 BP1 起支持多个 C 副本，建议最多 **3** 个 C 副本。
* C 副本与 **F** 或 **R** 副本 **不支持** 互相转换。
* **形态一** 下建议 C 副本所在 Zone **尽量只部署 C 副本**；独立 ODP 版本需 **ODP V4.3.2 及以上**。**形态二** 不强制单独部署 ODP，但若仍使用 ODP，请关注 ODP 与 OBServer 版本配套说明。
* **V4.6.0 之前**：R 副本上的查询 **不允许** 转发到 C 副本；C 副本上用户表查询 **不允许** 转发到 F/R 副本，否则报错。**V4.6.0 起**：支持 **F 副本** 上的查询转发到 C 副本（具体行为以版本说明为准）。
* 集群存在 C 副本时，**DDL** 会额外占用 CPU、内存、磁盘与 IO。
* C 副本 **合并** 通常比 F/R 慢；C 副本未完成合并时，**无法** 发起新一轮租户级合并。手动合并前建议查看 [CDB_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/12000.o-cdb_ob_zone_major_compaction-of-sys-tenant.md) 或 [DBA_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13000.o-dba_ob_zone_major_compaction-of-mysql-mode.md)，详见 [查看合并信息](../../700.reference/200.system-management/500.manage-data-storage/200.merge-management/500.view-merge-process.md)。
* **物理恢复** 不支持恢复 C 副本；Locality 中含 C 时恢复会失败。
* 主库未部署 C 副本时，**备库也不建议** 部署 C 副本。

### C 副本上暂为行存的几种场景

在 OceanBase 中，若表创建时为**行存表**，系统会在 C 副本上形成对应的**纯列存**终态；若表创建时为**列存表**，C 副本侧存储方式与 F 副本对齐。C 副本负责把 F 副本上行存用户分区**转换为列存**；在转换完成前，部分场景下分区会**暂时以行存**存在，需由后台**行转列**任务再变为列存。

| 场景 | 描述 |
| ---- | ---- |
| **补副本（增加副本）** | 例如 Locality 由 `F@z1, F@z2` 变为 `F@z1, F@z2, C@z3`：行存基线从源端迁到 C 副本时先为行存并尝试行转列；若行转列多次失败（如 DAG 队列满、I/O 或磁盘压力等），系统可能先提供**基于行存的弱读**。 |
| **日志流 Rebuild** | C 副本日志流 Rebuild 时从源端拉取的基线若为行存，则暂时为行存，待行转列后变为列存。 |
| **补副本与 Offline DDL 并发** | 并发下 C 副本可能对执行 DDL 的日志流 Leader 不可见，会先构建**行存基线**，再行转列。 |
| **全量旁路导入** | 当前可先向 C 副本导入行存，再由后台行转列。 |
| **表级恢复** | 列存表表级恢复能力受限时，C 副本上可能先恢复为行存，再行转列。 |

上述过程中，优化器可能已生成列存计划，但实际仍可能读行存基线。可通过 [CDB_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/8120.o-cdb_ob_cs_replica_stats-of-sys-tenant.md)（系统租户）、[DBA_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/8220.o-dba_ob_cs_replica_stats-of-mysql-mode.md)（用户租户）查看行转列进度；待任务完成后再依赖 C 副本上的纯列存读性能更稳妥。

sys 租户下查询示例：

```shell
obclient[oceanbase]> SELECT * FROM oceanbase.CDB_OB_CS_REPLICA_STATS;
```

查询结果如下：

```shell

| TENANT_ID | SVR_IP         | SVR_PORT | LS_ID | TOTAL_TABLET_CNT | AVAILABLE_TABLET_CNT | TOTAL_MACRO_BLOCK_CNT | AVAILABLE_MACRO_BLOCK_CNT | AVAILABLE |
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
|      1004 | xx.xxx.xxx.212 |    63000 |  1001 |             1019 |                 1019 |                 10706 |                     10706 | TRUE      |
|      1006 | xx.xxx.xxx.212 |    63000 |  1001 |              133 |                  133 |                   875 |                       875 | TRUE      |
```

可用 `AVAILABLE_TABLET_CNT / TOTAL_TABLET_CNT` 或 `AVAILABLE_MACRO_BLOCK_CNT / TOTAL_MACRO_BLOCK_CNT` 粗估进度；仅当日志流上 Tablet 均可用时，该日志流才视为完全可用。

## 使用列存副本

以下先说明如何在租户 **Locality** 中部署 C 副本（两种场景 **形态一 / 形态二 共用**），再分别给出 **形态一**（独立 ODP + ODP 配置）与 **形态二**（直连 + 后续章节中的自动路由）的后续步骤。

### 步骤一：部署 C 副本

在租户 Locality 中指定 C 副本即可，常见两类操作：

* **场景 A**：新建租户时即包含 C 副本。
* **场景 B**：为已有租户增加 C 副本（新 Zone + 改 Locality）。

#### 场景 A：新建包含 C 副本的租户

假设集群为 2F1A（两副本+ 1 个仲裁服务），Zone 为 zone1、zone2、zone3，仲裁服务部署在 zone3。需要在该集群上创建一个含有 C 副本的租户，步骤如下：

1. 创建资源单元 `unit1`。

    ```shell
    obclient> CREATE RESOURCE UNIT unit1,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

2. 创建资源池 `pool1`。

    ```shell
    obclient> CREATE RESOURCE POOL pool1
        UNIT='unit1',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone1','zone2','zone3');
    ```

3. 创建租户 `tenant_c`，Locality 为 `F@zone1,F@zone2,C@zone3`。

    ```shell
    obclient> CREATE TENANT tenant_c
        LOCALITY = 'F@zone1,F@zone2,C@zone3',
        PRIMARY_ZONE='zone1;zone2,zone3',
        RESOURCE_POOL_LIST=('pool1') SET ob_tcp_invited_nodes = '%';
    ```

    默认一般为 MySQL 模式；Oracle 模式需通过 [ob_compatibility_mode](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/6100.ob_compatibility_mode-global.md) 指定 `ob_compatibility_mode='oracle'`。

#### 场景 B：为已有租户增加 C 副本

假设租户 `tenant_c` 当前为 `F@zone1,F@zone2,F@zone3`，资源池 `pool1` 的 `ZONE_LIST` 为 zone1–zone3。拟增加 zone4 上的 C 副本，Locality 目标为 `F@zone1,F@zone2,F@zone3,C@zone4`：

1. 添加 Zone `zone4`，参见 [添加 Zone](../../600.manage/100.cluster-management/300.common-cluster-operations/800.add-a-zone.md)。
2. 向 zone4 **添加节点**，参见 [添加节点](../../600.manage/100.cluster-management/300.common-cluster-operations/400.add-a-node.md)。
3. 创建资源单元 `unit2`。

    ```shell
    obclient> CREATE RESOURCE UNIT unit2,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

4. 创建资源池 `pool2`，`ZONE_LIST = ('zone4')`。

    ```shell
    obclient> CREATE RESOURCE POOL pool2
        UNIT = 'unit2',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone4');
    ```

5. 为租户挂载 `pool2`。

   ```shell
   obclient> ALTER TENANT tenant_c RESOURCE_POOL_LIST = ('pool1','pool2');
   ```

6. 修改 Locality。

   ```shell
   obclient> ALTER TENANT tenant_c LOCALITY = 'F@zone1,F@zone2,F@zone3,C@zone4';
   ```

### 形态一：经独立 ODP 访问 C 副本

适用于 **V4.6.0 之前**，或 **V4.6.0+** 仍需 **专用 ODP** 将 AP 弱读 **固定** 打到 C 副本、与 TP 入口分离的场景。

#### 部署 ODP

在可与集群互通的机器上部署 **专用于访问 C 副本** 的 ODP（建议单机部署以免资源争抢），版本 **不低于 ODP V4.3.2**。部署步骤见 [部署 ODP](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000001600960)。

#### 配置路由转发策略及弱读

下列配置在 **ODP（proxysys）** 上执行，用于：将 SQL 配为**只读 + 弱读**，并把弱读请求**限定到 C 副本所在 Zone 或 ColumnStore 副本**，同时在会话初始化 SQL 中设置 **`ob_route_policy = COLUMN_STORE_ONLY`**，以便生成列存侧计划。请按实际 Zone、副本类型选择下列 **两种组合之一**。

1. 使用 `root@proxysys` 登录该 ODP，例如：

    ```shell
    [admin@obtest ~]$ obclient -uroot@proxysys -h10.10.10.1 -P2883 -p
    ```

2. 执行配置（任选一种组合）。

    * **组合一**

      * 只读、弱读：

          ```shell
          obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
          obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
          ```

      * 弱读时请求仅路由到 C 副本所在 Zone（示例为 `zone4`），并生成 C 副本计划：

          ```shell
          obclient> ALTER PROXYCONFIG SET proxy_primary_zone_name='zone4';
          obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
          ```

    * **组合二**

      * 只读、弱读：

          ```shell
          obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
          obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
          ```

      * 弱读时路由到 ColumnStore 副本并生成列存计划：

          ```shell
          obclient> ALTER PROXYCONFIG SET route_target_replica_type = 'ColumnStore';
          obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
          ```

      * 弱读仅选从副本，从副本均不可用时断开客户端：

          ```shell
          obclient> ALTER PROXYCONFIG SET proxy_route_policy='TARGET_REPLICA_TYPE_FOLLOWER_ONLY';
          ```

3. 校验示例：

    ```shell
    obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_only';
    obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_consistency';
    obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_primary_zone_name';
    obclient> SHOW PROXYCONFIG ALL LIKE 'init_sql';
    obclient> SHOW PROXYCONFIG ALL LIKE 'route_target_replica_type';
    obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_route_policy';
    ```

#### 使用方式

OLAP 业务通过上述 **独立 ODP** 接入，将查询定向到 C 副本，利用列存批量扫描，并与原有 OLTP 入口隔离。

### 形态二：直连或通过常规连接使用 C 副本（V4.6.0 及以上）

适用于已在租户中完成 **C 副本部署**、且希望 不再依赖列存专用 ODP + 上述 ODP 路由项 的场景。

使用 **标准连接串** 连接 **OBServer**，或经 **未按形态一配置列存专线的** 普通 ODP 访问（请求最终到达 OBServer 即可）。是否在列存副本上规划/执行只读部分，由 **列存副本自动路由**章节 中的 `ap_query_route_policy`、`ap_query_cost_threshold`、`ap_query_replica_fallback` 等与优化器、读一致性变量共同决定；细则见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

## 列存副本自动路由

从 **OceanBase 数据库 V4.6.0** 起，支持通过系统变量与 Hint 控制只读查询在 C 副本上的规划与执行（**列存副本自动选择 / 自动路由**）。会话级（可配合全局）变量 **`ap_query_route_policy`** 为主开关：在只读路径规划阶段，开启或关闭「识别分析型查询并尝试 C 副本」的逻辑，或强制 / 关闭列存侧规划。

**何时尝试列存路径、与 AP 查询的关系、常见不走列存的情况** 等，见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

### 适用版本与前提

* **版本**：OceanBase **V4.6.0 及以上**。
* **租户**：目标租户已在 Locality 中配置 **C 副本**，且副本可读。
* **变量**：用 `SHOW VARIABLES LIKE 'ap_query%';` 确认 `ap_query_route_policy`、`ap_query_cost_threshold`、`ap_query_replica_fallback` 等是否存在及默认值。

### 功能概述

V4.6.0 起提供列存副本自动选择能力，主要优势：

1. **零配置倾向**：默认 `AUTO` 下由系统识别 AP 特征并尝试 C 副本（仍可通过变量与 Hint 调节）。
2. **资源利用**：TP / AP 分流，充分利用 C 副本计算资源。
3. **支持强读**：C 副本上可强一致性读（见下文「列存副本上的读一致性」）。
4. **灵活控制**：`OFF`、`AUTO`、`FORCE` 满足不同场景。

`AUTO` 下优化器如何先试行存再重试列存，见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md) 中的「AUTO 模式的工作流程」。

### 快速上手

* 在已存在 **可用 C 副本** 的前提下，一般 **`ap_query_route_policy` 默认为 `AUTO`**，满足判定规则时会尝试列存计划；无需为「开启能力」额外执行 `SET`，除非要改为 `FORCE` / `OFF` 或调阈值。
* 用 `ap_query_cost_threshold` 调节 **AUTO** 下对「重查询」的敏感度；用 `ap_query_replica_fallback` 控制 C 副本不可用或规划失败时是否**回落行存**。

操作顺序建议：

1. 确认已完成本文 **列存副本使用** 中的 C 副本部署。
2. 核对变量：`SHOW VARIABLES LIKE 'ap_query%';`
3. 按需本会话调整，例如：`SET SESSION ap_query_route_policy = 'FORCE';` 或调整 `ap_query_cost_threshold`、`ap_query_replica_fallback`。
4. 对目标 SQL 做 `EXPLAIN`，查看是否出现列存相关算子；并结合 `DBA_OB_CS_REPLICA_STATS` / `CDB_OB_CS_REPLICA_STATS` 排查 C 副本状态。

### 按场景选择策略

| 场景诉求 | 策略建议 | 说明 |
| -------- | -------- | ---- |
| 智能选择：先试行存，满足 AP 特征再试 C 副本（多数场景） | `ap_query_route_policy = AUTO`（默认） | 结合代价、并行等判断；可用 `ap_query_cost_threshold` 调节。 |
| 会话内分析读尽量稳定走 C 副本 | `ap_query_route_policy = FORCE` | 写入仍走主副本。 |
| 与升级前列存行为对齐、关闭自动选列存 | `ap_query_route_policy = OFF` | 按行存等默认路径规划。 |
| C 副本故障时可接受回落行存 | `ap_query_replica_fallback = ON`（默认） | 降低查询失败率。 |
| 必须只走列存，失败则报错 | `ap_query_replica_fallback = OFF` | |
| AUTO 下更多查询尝试列存 | **降低** `ap_query_cost_threshold` | 如 `100000`。 |
| AUTO 下仅很重查询才尝试列存 | **提高** `ap_query_cost_threshold` | 如 `300000`。 |
| 单条 SQL 与会话默认不同 | Hint `/*+opt_param('ap_query_route_policy', '...')*/` | 见下文「查询级别控制」。 |

### 列存副本上的读一致性

**V4.6.0 之前**，路由到 C 副本时通常仅弱读（`ob_read_consistency = 'weak'`）。**V4.6.0 起**支持在 C 副本上 **强一致性读**，便于在列存上满足更高一致性需求。全局变量说明见 [ob_read_consistency](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8700.ob_read_consistency-global.md)。

#### 列存副本强读工作原理

查询识别为 AP 且路由到 C 副本、并使用强读（默认）时，事务层大致步骤：

1. 通过 **GTS** 获取全局一致性快照版本。
2. 检查 C 副本（Follower）是否已回放到该版本。
3. 若未就绪则 **等待回放**。
4. 就绪后执行强读。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>强读可能因等待 Follower 回放而增加延迟，极短查询通常不适合在 C 副本上强读。</p>
</main>

#### 强读与弱读对比

| **特性** | **强读** | **弱读** |
|----------|----------|----------|
| 一致性 | 与主副本一致 | 最终一致，可能略旧 |
| 延迟 | 可能需等待回放 | 通常更低 |
| 典型场景 | 高一致性 AP 读 | 可容忍短暂延迟的 AP 读 |
| 设置 | `ob_read_consistency = 'strong'`（默认） | `ob_read_consistency = 'weak'` |

**建议**：一致性要求高用强读（默认）；可容忍延迟时弱读往往性能更好。仅当 `ap_query_route_policy = AUTO` 时，弱读还会作为尝试列存计划的触发条件之一，见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

### 系统变量说明

下列变量在多数 V4.6.0+ 版本中共通；以集群 `SHOW VARIABLES` 为准。

#### ap_query_route_policy

| 取值 | 含义概要 |
|------|----------|
| OFF | 关闭自动选择，按行存等路径规划，接近 V4.6.0 前习惯。 |
| AUTO | 默认：优化器判断是否采用 C 副本侧计划。 |
| FORCE | 前提满足时尽量在 C 副本执行只读。 |

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_route_policy';
obclient> SET ap_query_route_policy = 'AUTO';
obclient> SET ap_query_route_policy = 'FORCE';
```

#### ap_query_cost_threshold

`AUTO` 下与代价相关：**单并行度** 计划代价超过该阈值时参与是否尝试 C 副本的判断（默认常见为 `200000`，以实际为准）。

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_cost_threshold';
obclient> SET SESSION ap_query_cost_threshold = 300000;
```

#### ap_query_replica_fallback

目标为 C 副本但不可用或无法完成规划时，是否允许回退行存。

| 取值 | 含义概要 |
| ---- | -------- |
| ON | 允许回退，尽量完成查询。 |
| OFF | 不因该原因回退，可能报错。 |

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_replica_fallback';
obclient> SET SESSION ap_query_replica_fallback = OFF;
```

#### 与 ob_route_policy 的关系

[ob_route_policy](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8900.ob_route_policy-global.md) 用于 OBServer 内部副本路由（如 `COLUMN_STORE_ONLY`）。与 `ap_query_*` 同时设置时的语义与优先级以当前版本说明为准。

### 查询级别控制

单条语句使用 Hint，避免改会话全局配置：

```shell
obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'FORCE')*/ *
   FROM t1, t2
   WHERE t1.c1 = t2.c1;
```

```shell
obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'OFF')*/ *
    FROM t1, t2
    WHERE t1.c1 = t2.c1;
```

### 验证与排错建议

* 用 `EXPLAIN`（或执行后计划视图）查看列存侧算子。
* 用 `DBA_OB_CS_REPLICA_STATS` / `CDB_OB_CS_REPLICA_STATS` 看 C 副本就绪与行转列进度（见本文第一章）。
* 无 C 副本的租户：上述变量通常不会改变无列存时的规划结果。
