# 列存副本的使用与自动路由

为满足 TP 与 AP 混合负载（准实时决策分析）等场景，OceanBase 数据库提供**列存副本**（COLUMNSTORE，简称 **C 副本**）。用户可将 C 副本部署在独立 Zone 上；在 C 副本上，用户表（含复制表，不含索引表、内部表、系统表）以列存格式存储，便于分析型扫描。

本文主要介绍 **C 副本的概念、约束、暂为行存**、**如何使用 C 副本**（两种架构形态下的部署与访问步骤）、**列存副本自动路由**（V4.6.0 起 `ap_query_*` 等与读一致性说明）。路由判定细则见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

## 什么是列存副本

### 两种典型架构形态

按 **OceanBase 版本与访问路径**，使用 C 副本常见有两种形态，请先对照业务版本与是否需要专用 AP 入口选型，再进入**列存副本使用**中的对应小节。

| 形态 | 适用版本与典型场景 | 访问路径概要 |
| ---- | ------------------ | ------------ |
| **方式一：经独立 ODP 访问 C 副本** | **OceanBase V4.6.0 之前**必须使用方式一 | 部署 C 副本 → 部署专用于 C 副本访问的 ODP（建议 V4.3.2+）→ 在 ODP 上配置弱读与仅指向 C 副本的路由项（见下文方式一）→ 业务连接该 ODP |
| **方式二：直连+ 自动路由** | **OceanBase V4.6.0 及以上**，且无需单独再为 C 副本部署 ODP | 部署 C 副本 → 使用标准方式连接 OBServer → 通过会话/全局变量 `ap_query_route_policy` 等由优化器自动尝试列存计划（参见本文**列存副本自动路由**） |

方式一下列配置的作用是：**把 OLAP 只读请求配成弱读**，并让 ODP **只把这类请求路由到 C 副本所在 Zone 或 ColumnStore 副本类型**，同时在连接上注入 `ob_route_policy = COLUMN_STORE_ONLY` 等，从而生成列存侧执行计划。若您采用 **方式二**，则**不需要**部署 ODP；是否走列存由 **OBServer 侧** `ap_query_*` 与判定规则决定（若经普通 ODP 路由，只要转发到 OBServer，同样由这些变量生效）。

### 注意事项

使用 C 副本时，请注意：

* 从 V4.3.5 BP1 起支持多个 C 副本，建议最多 **3** 个 C 副本。
* C 副本与 **F** 或 **R** 副本 **不支持** 互相转换。
* **方式一** 下建议 C 副本所在 Zone **尽量只部署 C 副本**；独立 ODP 版本需 **ODP V4.3.2 及以上**。**方式二**（即 OceanBase V4.6.0 及以上）不强制单独部署 ODP。
* R 副本上的查询不允许转发到 C 副本；F 副本上的查询可以转发到 C 副本。C 副本上的用户表查询不允许转发到 F/R 副本，否则会报错。
* C 副本 **合并** 通常比 F/R 慢；C 副本未完成合并时，**无法** 发起新一轮租户级合并。手动合并前建议查看 [CDB_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/12000.o-cdb_ob_zone_major_compaction-of-sys-tenant.md) 或 [DBA_OB_ZONE_MAJOR_COMPACTION](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/13000.o-dba_ob_zone_major_compaction-of-mysql-mode.md)，详见 [查看合并信息](../../700.reference/200.system-management/500.manage-data-storage/200.merge-management/500.view-merge-process.md)。
* **物理恢复** 不支持恢复 C 副本；Locality 中含 C 时恢复会失败。
* 主库未部署 C 副本时，**备库也不建议** 部署 C 副本。

### C 副本上暂为行存的几种场景

在 OceanBase 数据库中，如果一张表在被创建时为行存表，则系统会在 C 副本上创建对应的纯列存表；如果一张表在被创建时为列存表，则在 C 副本上的存储方式将与 F 副本保持一致。故，对于 C 副本而言，仅负责将 F 副本上行存的用户表的用户分区转换为列存存储，且该描述仅表示 “最终” 状态为列存。在 C 副本上，并非任意时刻分区均表现为列存形式，在以下场景中， C 副本上的用户表分区会暂时为行存，需要系统自发调度行转列任务，将最新的基线数据转换为列存。

| 场景             | 描述                                                          |
|-----------------|---------------------------------------------------------------|
| 补副本（增加副本）             | 以修改 Locality 使得 `F@z1, F@z2` 变更为 `F@z1, F@z2, C@z3` 为例：<ul><li>行存基线从源端（F 副本或者 R 副本）迁移到目的端（C 副本）时，会先拷贝行存到 C 副本上，并尝试为该 Tablet 发起行转列。</li> <li>由于行转列也是一类特殊的合并，如果多次尝试行转列失败（例如 DAG Scheduler 队列满或 I/O 压力大或磁盘空间不足等），系统就会提供基于行存的弱读查询。</li></ul>|
| 日志流 Rebuild                | 当触发 C 副本上日志流的 Rebuid 时，系统将会从源端拉取相应的基线到 C 副本。若基线数据为行存，则暂时为行存，待后台调度行转列任务后再转为列存。|
| 补副本与 Offline DDL 并发场景  | 当 C 副本在日志流成员列表中时，若执行 Offline DDL，系统将会直接在 C 副本上构建列存基线。然而，当补副本与 Offline DDL 并发时，C 副本对执行 DDL 任务的日志流 Leader 不可见，此时系统在 C 副本上将会先构建出行存的基线，待后台调度行转列任务后再转为列存。|
| 全量旁路导入                   | 全量旁路导入当前仅支持先向 C 副本上导入行存，待后台调度行转列任务后转为列存。|
| 表级恢复                       | 由于当前列存表暂不支持表级恢复，因此 C 副本上的表级恢复仅支持先恢复为行存，待后台调度行转列任务后再转为列存。|

上述场景下，在进行行存转列存的过程中，尽管当前优化器生成的是列存查询计划，但实际执行的仍然是对行存基线的查询。用户可以通过视图 [CDB_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/300.system-view-of-sys-tenant/200.dictionary-view-of-sys-tenant/8120.o-cdb_ob_cs_replica_stats-of-sys-tenant.md)（系统租户）和 [DBA_OB_CS_REPLICA_STATS](../../700.reference/700.system-views/400.system-view-of-mysql-mode/200.dictionary-view-of-mysql-mode/8220.o-dba_ob_cs_replica_stats-of-mysql-mode.md)（用户租户）来查询 C 副本的可用信息及行转列的进度，待行转列任务完全结束后，再进行 C 副本上的查询。

sys 租户下，查询所有租户 C 副本日志流中 Tablet 行转列进度的示例如下：

```shell
obclient[oceanbase]> SELECT * FROM oceanbase.CDB_OB_CS_REPLICA_STATS;
```
查询结果如下：
```shell
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
| TENANT_ID | SVR_IP         | SVR_PORT | LS_ID | TOTAL_TABLET_CNT | AVAILABLE_TABLET_CNT | TOTAL_MACRO_BLOCK_CNT | AVAILABLE_MACRO_BLOCK_CNT | AVAILABLE |
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+
|      1004 | xx.xxx.xxx.212 |    63000 |  1001 |             1019 |                 1019 |                 10706 |                     10706 | TRUE      |
|      1006 | xx.xxx.xxx.212 |    63000 |  1001 |              133 |                  133 |                   875 |                       875 | TRUE      |
+-----------+----------------+----------+-------+------------------+----------------------+-----------------------+---------------------------+-----------+

```

从第一行查询结果可知，租户 ID 为 1004 的租户，其 C 副本所在的服务器为 `xx.xxx.xxx.212`，端口号为 `63000`； C 副本日志流的 ID 为 `1001`；当前需要转换为列存的分区总数为 `1019`，可用的分区总数为 `1019`；当前总的基线宏块数为 `10706`，可用的基线宏块数为 `10706`。用户可以通过 `AVAILABLE_TABLET_CNT / TOTAL_TABLET_CNT` 或者 `AVAILABLE_MACRO_BLOCK_CNT /TOTAL_MACRO_BLOCK_CNT` 来大致估算行转列的进度。仅当日志流上的所有 Tablet 均可用时，该日志流才完全可用。

## 使用列存副本

以下先说明如何在租户 **Locality** 中部署 C 副本（两种场景 **方式一 / 方式二 共用**），再分别给出 **方式一**（独立 ODP + ODP 配置）与 **方式二**（直连 + 后续章节中的自动路由）的后续步骤。

### 步骤一：部署 C 副本

在租户 Locality 中指定 C 副本即可，常见两类操作：

* **场景 A**：新建租户时即包含 C 副本。
* **场景 B**：为已有租户增加 C 副本（新 Zone + 改 Locality）。

#### 场景 A：新建包含 C 副本的租户

假设当前有一个已部署好的集群，且集群的部署模式为 2F1A（两副本+ 1 个仲裁服务）。集群中的 3 个 Zone 分别为 zone1、zone2、zone3，仲裁服务部署在 zone3 上。需要在该集群上创建一个含有 C 副本的租户，步骤如下：

1. 找到一台能够与当前集群网络互通的机器，并在该机器上部署 ODP。

   为防止资源争抢，建议 ODP 单独部署在一台机器上。部署 ODP 时，要求其版本必须为 ODP V4.3.2 及以上版本。有关部署 ODP 的详细操作，参见 [部署 ODP](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000001600960)。

2. 创建资源单元 `unit1`。

    ```shell
    obclient> CREATE RESOURCE UNIT unit1,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

3. 创建资源池 `pool1`，指定资源单元为 `unit1`。

    ```shell
    obclient> CREATE RESOURCE POOL pool1
        UNIT='unit1',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone1','zone2','zone3');
    ```

4. 创建租户 `tenant_c`，Locality 为 `F@zone1,F@zone2,C@zone3`。

    ```shell
    obclient> CREATE TENANT tenant_c
        LOCALITY = 'F@zone1,F@zone2,C@zone3',
        PRIMARY_ZONE='zone1;zone2,zone3',
        RESOURCE_POOL_LIST=('pool1') SET ob_tcp_invited_nodes = '%';
    ```

    本示例中，创建的租户默认为 MySQL 兼容模式租户，如果需要创建 Oracle 兼容模式租户，需要通过系统变量 [ob_compatibility_mode](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/6100.ob_compatibility_mode-global.md) 指定 `ob_compatibility_mode='oracle'`。

#### 场景 B：为已有租户增加 C 副本

假设当前集群中有一个名为 `tenant_c` 的租户，其 Locality 为 `F@zone1,F@zone2,F@zone3`，租户的资源池为 `pool1`，其 `ZONE_LIST` 范围为 `'zone1','zone2','zone3'`。现在需要为租户增加 C 副本，可以增加一个 `Zone4`，然后修改租户的 Locality 为 `F@zone1,F@zone2,F@zone3,C@zone4`，步骤如下：
1. 在集群中添加新的 Zone `zone4`。添加 Zone 的详细操作，参见 [添加 Zone](../100.cluster-management/300.common-cluster-operations/800.add-a-zone.md)。
2. 向 `zone4` 内增加节点。添加节点的详细操作，参见 [添加节点](../100.cluster-management/300.common-cluster-operations/400.add-a-node.md)。

3. 找到一台能够与当前集群网络互通的机器，并在该机器上部署 ODP。

   为防止资源争抢，建议 ODP 单独部署在一台机器上。部署 ODP 时，要求其版本必须为 ODP V4.3.2 及以上版本。有关部署 ODP 的详细操作，参见 [部署 ODP](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000001600960)。

4. 创建资源单元 `unit2`。

    ```shell
    obclient> CREATE RESOURCE UNIT unit2,
        MAX_CPU=5,
        MIN_CPU=5,
        MEMORY_SIZE= '32G',
        MAX_IOPS=10000,
        MIN_IOPS=5000,
        LOG_DISK_SIZE=5301023539200;
    ```

5. 创建资源池 `pool2`，指定资源单元为 `unit2`。

    ```shell
    obclient> CREATE RESOURCE POOL pool2
        UNIT = 'unit2',
        UNIT_NUM = 1,
        ZONE_LIST = ('zone4');
    ```

6. 为租户增加资源池 `pool2`。

   ```shell
   obclient> ALTER TENANT tenant_c RESOURCE_POOL_LIST = ('pool1','pool2');
   ```

7. 修改租户的 Locality 为 `F@zone1,F@zone2,F@zone3,C@zone4`。

   ```shell
  obclient [oceanbase]> ALTER TENANT tenant_c LOCALITY = 'F@zone1,F@zone2,F@zone3,C@zone4';
   ```

### 方式一：经独立 ODP 访问 C 副本

适用于 **V4.6.0 之前**，或 **V4.6.0+** 仍需 **专用 ODP** 将 AP 弱读 **固定** 打到 C 副本、与 TP 入口分离的场景。

#### 部署 ODP

在可与集群互通的机器上部署 **专用于访问 C 副本** 的 ODP（建议单机部署以免资源争抢），版本 **不低于 ODP V4.3.2**。部署步骤见 [部署 ODP](https://www.oceanbase.com/docs/common-odp-doc-cn-1000000001600960)。

#### 配置路由转发策略及弱读

下列配置在 **ODP（proxysys）** 上执行，用于：将 SQL 配为**只读 + 弱读**，并把弱读请求**限定到 C 副本所在 Zone 或 ColumnStore 副本**，同时在会话初始化 SQL 中设置 **`ob_route_policy = COLUMN_STORE_ONLY`**，以便生成列存侧计划。请按实际 Zone、副本类型选择下列 **两种组合之一**。

1. 使用 `root@proxysys` 登录该 ODP，例如：

    ```shell
    [admin@obtest ~]$ obclient -uroot@proxysys -h10.10.10.1 -P2883 -p
    ```

2. 执行配置（任选一种组合）。

    * **组合一**

      * 只读、弱读：

          ```shell
          obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
          obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
          ```

      * 弱读时请求仅路由到 C 副本所在 Zone（示例为 `zone4`），并生成 C 副本计划：

          ```shell
          obclient> ALTER PROXYCONFIG SET proxy_primary_zone_name='zone4';
          obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
          ```

    * **组合二**

      * 只读、弱读：

          ```shell
          obclient> ALTER PROXYCONFIG SET obproxy_read_only = 0;
          obclient> ALTER PROXYCONFIG SET obproxy_read_consistency = 1;
          ```

      * 弱读时路由到 ColumnStore 副本并生成列存计划：

          ```shell
          obclient> ALTER PROXYCONFIG SET route_target_replica_type = 'ColumnStore';
          obclient> ALTER PROXYCONFIG SET init_sql='set @@ob_route_policy = COLUMN_STORE_ONLY';
          ```

      * 弱读仅选从副本，从副本均不可用时断开客户端：

          ```shell
          obclient> ALTER PROXYCONFIG SET proxy_route_policy='TARGET_REPLICA_TYPE_FOLLOWER_ONLY';
          ```

3. 修改成功后，通过以下语句，确认修改结果。

    ```shell
    obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_only';
    obclient> SHOW PROXYCONFIG ALL LIKE 'obproxy_read_consistency';
    obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_primary_zone_name';
    obclient> SHOW PROXYCONFIG ALL LIKE 'init_sql';
    obclient> SHOW PROXYCONFIG ALL LIKE 'route_target_replica_type';
    obclient> SHOW PROXYCONFIG ALL LIKE 'proxy_route_policy';
    ```
配置成功后，对于 OLAP 业务，用户可以通过该独立的 ODP 将查询请求定向到 C 副本，利用列存批量处理的优势加速查询，且不影响原有的 OLTP 业务。

### 方式二：直连使用 C 副本（V4.6.0 及以上）

适用于已在租户中完成 **C 副本部署**、且希望 不再依赖列存专用 ODP + 上述 ODP 路由项 的场景。

使用 **标准连接串** 连接 **OBServer**，或经 **未按方式一配置列存专线的** 普通 ODP 访问（请求最终到达 OBServer 即可）。是否在列存副本上规划/执行只读部分，由 **列存副本自动路由**章节 中的 `ap_query_route_policy`、`ap_query_cost_threshold`、`ap_query_replica_fallback` 等与优化器、读一致性变量共同决定；细则见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

## 列存副本自动路由

从 **OceanBase 数据库 V4.6.0** 起，支持通过系统变量与 Hint 控制只读查询在 C 副本上的规划与执行（**列存副本自动选择 / 自动路由**）。会话级（可配合全局）变量 **`ap_query_route_policy`** 为主开关：在只读路径规划阶段，开启或关闭「识别分析型查询并尝试 C 副本」的逻辑，或强制 / 关闭列存侧规划。

**何时尝试列存路径、与 AP 查询的关系、常见不走列存的情况** 等，见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

### 适用版本与前提

* **租户**：目标租户已在 Locality 中配置 **C 副本**，且副本可读。
* **变量**：用 `SHOW VARIABLES LIKE 'ap_query%';` 确认 `ap_query_route_policy`、`ap_query_cost_threshold`、`ap_query_replica_fallback` 等是否存在及默认值。

### 快速上手

* 在已存在 **可用 C 副本** 的前提下，一般 **`ap_query_route_policy` 默认为 `AUTO`**，满足判定规则时会尝试列存计划；无需为「开启能力」额外执行 `SET`，除非要改为 `FORCE` / `OFF` 或调阈值。
* 用 `ap_query_cost_threshold` 调节 **AUTO** 下对「重查询」的敏感度；用 `ap_query_replica_fallback` 控制 C 副本不可用或规划失败时是否**回落行存**。

操作顺序建议：

1. 确认已完成本文 **列存副本使用** 中的 C 副本部署。
2. 核对变量：`SHOW VARIABLES LIKE 'ap_query%';`
3. 按需本会话调整，例如：`SET SESSION ap_query_route_policy = 'FORCE';` 或调整 `ap_query_cost_threshold`、`ap_query_replica_fallback`。
4. 对目标 SQL 做 `EXPLAIN`，查看是否出现列存相关算子；并结合 `DBA_OB_CS_REPLICA_STATS` / `CDB_OB_CS_REPLICA_STATS` 排查 C 副本状态。

### 按场景选择策略

下表用于快速选型；具体语义与边界以当前版本文档及 `SHOW VARIABLES` 为准。
| 场景诉求 | 策略建议 | 说明 |
| -------- | -------- | ---- |
| 智能选择：先尝试行存副本，如果查询满足 AP 特征则重试使用列存副本，推荐大多数场景使用 | `ap_query_route_policy = AUTO`（默认） | 由优化器结合代价、并行等因素判断是否生成列存副本侧计划；可用 `ap_query_cost_threshold` 调节敏感度。 |
| 会话内分析查询强制使用列存副本（在副本可用前提下） | `ap_query_route_policy = FORCE` | 适合明确隔离到 C 副本的只读分析链路；写入仍走主副本。 |
| 完全不要自动选列存，行为对齐升级前习惯 | `ap_query_route_policy = OFF` | 不启用列存副本自动选择逻辑。 |
| 列存副本故障时可接受回落到行存执行 | `ap_query_replica_fallback = ON`（默认） | 降低因 C 副本不可用导致的查询失败。 |
| 必须只在列存上执行，不可用则失败 | `ap_query_replica_fallback = OFF` | 便于严格区分链路，但副本异常时查询可能报错。 |
| 在 AUTO 下希望更多查询尝试列存 | 适当 **降低** `ap_query_cost_threshold` | 阈值越小，越容易触发列存侧计划重试（如设置阈值为 100000）。 |
| 在 AUTO 下仅希望很重查询才尝试列存 | 适当 **提高** `ap_query_cost_threshold` | 减少小查询走列存的概率（如设置阈值为 300000）。 |
| 单条 SQL 与全局会话策略不同 | 使用 Hint `/*+opt_param('ap_query_route_policy', '...')*/` | 见下文「查询级别控制」。 |

### 列存副本上的读一致性

**V4.6.0 之前**，路由到 C 副本时通常仅弱读（`ob_read_consistency = 'weak'`）。**V4.6.0 起**支持在 C 副本上 **强一致性读**，便于在列存上满足更高一致性需求。全局变量说明见 [ob_read_consistency](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8700.ob_read_consistency-global.md)。

#### 列存副本强读工作原理

查询识别为 AP 且路由到 C 副本、并使用强读（默认）时，事务层大致步骤：

1. 通过 **GTS** 获取全局一致性快照版本。
2. 检查 C 副本（Follower）是否已回放到该版本。
3. 若未就绪则 **等待回放**。
4. 就绪后执行强读。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>强读可能因等待 Follower 回放而增加延迟，极短查询通常不适合在 C 副本上强读。</p>
</main>

#### 强读与弱读对比

| **特性** | **强读** | **弱读** |
|----------|----------|----------|
| 一致性 | 与主副本一致 | 最终一致，可能略旧 |
| 延迟 | 可能需等待回放 | 通常更低 |
| 典型场景 | 高一致性 AP 读 | 可容忍短暂延迟的 AP 读 |
| 设置 | `ob_read_consistency = 'strong'`（默认） | `ob_read_consistency = 'weak'` |

**建议**：一致性要求高用强读（默认）；可容忍延迟时弱读往往性能更好。仅当 `ap_query_route_policy = AUTO` 时，弱读还会作为尝试列存计划的触发条件之一，见 [AP 查询与列存副本路由判定规则](300.ap-query-column-replica-routing-rules.md)。

### 系统变量说明

下列变量用于列存副本自动选择。

#### ap_query_route_policy

控制是否以及如何自动选择列存副本执行查询，常见取值包括：

| 取值 | 含义概要 |
|------|----------|
| OFF | 关闭自动选择，按行存等路径规划，查询行为与 V4.6.0 之前版本一致。 |
| AUTO | 默认策略：由优化器判断是否采用列存副本侧计划。 |
| FORCE | 在满足前提条件时，尽量在列存副本上执行只读查询。 |

示例：

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_route_policy';
obclient> SET ap_query_route_policy = 'AUTO';
obclient> SET ap_query_route_policy = 'FORCE';
```

#### ap_query_cost_threshold


在 `AUTO` 策略下，与优化器代价相关的阈值；**单并行度** 计划代价超过该阈值时，会参与是否尝试列存副本侧计划的判断。默认值请以 `SHOW VARIABLES` 为准（默认值为 `200000`）。

示例：

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_cost_threshold';
obclient> SET SESSION ap_query_cost_threshold = 300000;
```

#### ap_query_replica_fallback

当目标为 C 副本但副本不可用或无法完成规划时，是否允许回退到行存副本执行。

| 取值 | 含义概要 |
| ---- | -------- |
| ON | 允许回退，查询尽量成功完成。 |
| OFF | 不允许因该原因回退，可能直接报错。 |

```shell
obclient> SHOW VARIABLES LIKE 'ap_query_replica_fallback';
obclient> SET SESSION ap_query_replica_fallback = OFF;
```

#### 与 ob_route_policy 的关系

[ob_route_policy](../../700.reference/800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/8900.ob_route_policy-global.md) 用于设置 OBServer 内部选择数据副本的路由策略；取值为 `COLUMN_STORE_ONLY` 等时，读路径会限定到对应副本类型。

### 查询级别控制

在单条语句上使用 Hint，避免改会话全局配置：

* 强制该语句按列存副本侧策略规划（在策略与副本允许的前提下）：


    ```shell
    obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'FORCE')*/ *
       FROM t1, t2
       WHERE t1.c1 = t2.c1;
    ```

* 该语句关闭自动选择列存，选择主副本执行：

    ```shell
    obclient> EXPLAIN SELECT /*+opt_param('ap_query_route_policy', 'OFF')*/ *
        FROM t1, t2
        WHERE t1.c1 = t2.c1;
    ```

### 验证与排错建议

* 使用 `EXPLAIN`（或实际执行后的计划视图）查看是否出现列存侧算子。
* 结合 `DBA_OB_CS_REPLICA_STATS` / `CDB_OB_CS_REPLICA_STATS` 等视图确认 C 副本数据就绪与延迟情况，参见 [使用列存副本](../../600.manage/300.replica-management/150.the-use-of-columnstore-replica.md)。
* 未部署 C 副本的租户：开启上述变量通常不会改变无列存时的基本规划行为；仍以实际版本为准。
