# 查询加速概述

## 什么是查询加速

在分析处理（AP）场景中，单次查询往往需要扫描海量数据、执行复杂聚合与连接，查询响应时间（RT）和资源利用率直接决定分析效率与业务体验。**查询加速** 指通过优化器、并行执行与针对性配置，让分析型 SQL 跑得更快、更稳、更省资源，在不大幅改写业务 SQL 的前提下，获得更短的响应时间与更可预期的资源占用。

## 如何查询加速

OceanBase 在 AP 场景下的查询加速主要从两条路径入手：

- **优化器侧**：让优化器基于准确、及时的统计信息生成更优执行计划（含行存/列存路径选择、分布式计划、SkipIndex 利用等），避免大表全扫、错误连接顺序等高代价计划。
- **执行侧**：通过并行查询（多线程/多机协同）充分利用 CPU 与 IO，缩短单查询 RT；配合合理的并行度（手动 DOP 或 Auto DOP），在加速查询的同时控制资源争用。

## 何时进行查询加速

在以下情况中，建议主动进行查询加速相关的配置与调优：

- **大表或分区表分析**：表/分区数据量很大，全表或大范围扫描耗时长，需要依赖准确统计信息选择列存/行存路径与扫描范围，并借助并行度提升吞吐、缩短 RT。
- **批量导入或大批量更新后**：数据变化大，默认统计信息可能尚未更新或不够准确，易导致执行计划不优；可配合在线统计信息收集、维护窗口或手动收集，并在需要时开启或调整并行度。
- **分析查询 RT 不满足需求**：已确认瓶颈在计划或并行资源时，可优先检查统计信息是否及时、准确，再评估是否开启 Auto DOP 或调大手动 DOP 及相关参数。
- **多查询并发导致资源争用**：开启并行后系统负载过高，需通过 `parallel_degree_limit`、`parallel_min_scan_time_threshold` 等参数限制并行门槛与上限，或结合资源组/租户隔离做整体管控。

针对上述场景，可以按**先表结构、再统计信息与并行度**的顺序逐步配置与调优，即可在 AP 场景下获得更优的执行计划、更短的响应时间与更可控的资源占用。
