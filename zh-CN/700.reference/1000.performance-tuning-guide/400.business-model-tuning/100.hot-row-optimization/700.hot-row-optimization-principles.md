# 热点行性能优化原理说明

<main id="notice" >
    <h4>功能适用性</h4>
    <p>该功能仅适用于 OceanBase 数据库企业版。</p>
</main>

热点行指短时间内被大量并发请求反复更新的同一行或少量几行。典型现象是：应用侧并发已经很高，但数据库侧吞吐无法继续线性提升，锁等待主要集中在同一行的更新链路上。

应用侧通常会观察到以下表现：

* 并发继续升高，但 TPS 增长放缓甚至不再增长。

* 平均响应时间和 P99 延迟上升。

* SQL 本身很简单，但大量请求都在更新同一行或少量几行。

OceanBase 针对热点行更新提供两类优化：

* ELR（Early Lock Release，提前解行锁）：缩短单个事务持有行锁的时间。

* Group Commit（热点行组提交）：将同一热点行上的多次并发 `UPDATE` 聚合执行，减少重复执行和重复提交的固定开销。

两者解决的问题不同，可以叠加使用。

## 热点行更新为什么慢

普通 `UPDATE` 对一行数据的修改是 Read-Modify-Write 的过程：当最终结果写入 MemTable 时加上行锁，直到事务提交完成才释放锁。事务提交流程可拆为三步：

1. 将事务的 commit log 写入日志系统缓存。

2. 系统将日志刷盘，同时同步到 Follower。

3. 多数派写入成功后，修改事务状态为已提交并释放行锁。

即：

```text
等待行锁 → 执行 UPDATE → commit log 写缓存 → 日志刷盘+同步 → 提交完成 → 释放行锁
```

当大量请求更新同一行时，瓶颈主要来自以下两个方面：

* **一是行锁串行。**

  同一时刻，同一行只能被一个事务更新。一个事务持有行锁期间（从加锁到释放的全过程），其他事务只能排队等待。并发越高，排队越长。

* **二是固定开销重复。**

  每个事务都要独立执行一次 SQL、生成一次事务日志、完成一次提交。即使所有事务更新的都是同一行，这些固定动作仍会按事务数重复发生。

因此，热点行优化需要同时降低两类开销：

* 缩短每个事务占用行锁的时间。

* 减少大量相似更新重复执行、重复提交的次数。

ELR 解决第一类开销，Group Commit 解决第二类开销。

## ELR：缩短行锁持有时间

在常规提交流程中，事务通常要等提交日志完成多数派同步后，才释放行锁。对于热点行来说，后续事务一直等在这把行锁后面，提交等待时间会直接放大为行锁等待时间。

ELR 的核心思想是：在事务已完成本地日志写入、具备继续推进提交的条件后，提前释放行锁，让后续事务可以更早开始执行。

![传统提交流程与 ELR 提交流程对比](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/700.reference/diagram_1.jpg)

这样做的收益很直接：行锁不再覆盖完整的提交等待过程，后续更新可以更早拿到锁。在热点行场景下，哪怕单个事务只缩短了一小段持锁时间，叠加到大量排队请求上，也会显著提升整体吞吐。

ELR 不改变事务最终提交或回滚的正确性。后续事务即使更早拿到行锁，也仍然受事务依赖关系约束；前序事务最终提交或回滚后，后续事务再按一致性规则继续完成。

ELR 的收益显著：提前释放行锁带来的单行更新吞吐能力有数倍提升。在更高规格的硬件和跨地域部署场景下，ELR 将网络时间和磁盘 I/O 时间移出行锁覆盖范围，对多机房网络延迟较高的部署形态尤其有效。

因此，ELR 的特点是：

* 收益主要体现在热点行更新的锁等待降低。

* ELR 不会减少 SQL 执行次数，也不会减少事务提交次数。

* 应用请求仍按原有事务语义执行，优化过程对应用透明。

## Group Commit：减少重复执行和重复提交

ELR 缩短了持锁时间，但每个事务仍然各自执行一次 `UPDATE`、各自提交一次。并发继续升高时，这些重复固定开销仍然会成为瓶颈。

Group Commit 的核心思想是：对于同一条 SQL 模板、同一热点行上的多个并发 `UPDATE`，由数据库将它们聚合为一批进行处理。

![Group Commit 聚合执行前后对比](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/700.reference/diagram_2.jpg)

聚合只发生在执行和提交阶段，每个请求仍然是独立的数据库请求，各自持有独立的客户端连接。批量执行完成后，数据库将各自的执行结果（成功、失败或影响 0 行）分别返回给对应的客户端，各请求之间互不干扰。

聚合后，收益主要来自三个方面。

* **执行通路合并。** 多个请求不再各自执行一遍 SQL 计划，而是共享一次批量执行通路。

* **提交开销合并。** 多个请求不再各自完成一次独立提交，而是由聚合后的提交路径统一完成。

* **热点行争用收敛。** 同一热点行上的并发更新被收敛到批量处理过程中，减少多个事务在同一行上反复争抢的开销。

Group Commit 改变的是“执行和提交的组织方式”，每个请求仍按事务语义返回成功、失败或影响 0 行等结果。

聚合键由数据库自动解析主键列或唯一索引列得到，无需显式指定。批量执行时，对同一行的中间结果记录在行缓存中，后续更新从缓存读取前序结果继续计算，一批执行结束后将最终结果写入存储层。

热点行 Group Commit 除了带来主要性能提升的**聚合**执行语义外，还存在**自动提交**这一层事务语义。在事务提交层面，聚合后的整批请求在执行结束后进行统一提交，若聚合语句之后事务内还存在其他语句，这些语句执行时将脱离原有事务上下文，导致事务语义被割裂，甚至引发脏读等一致性问题。因此，为保证事务语义完整，携带 `GROUP_COMMIT` Hint 的 `UPDATE` 语句**必须**作为事务内的**最后一条** DML 执行。

## ELR 与 Group Commit 如何协同

ELR 与 Group Commit 针对的问题和作用位置不同：

| 优化 | 解决的问题 | 作用位置 |
|------|------------|----------|
| ELR | 行锁持有时间长 | 提前释放行锁 |
| Group Commit | 相似更新重复执行、重复提交 | 批量执行和提交 |

二者组合使用时，收益按以下顺序叠加：

1. ELR 让行锁更快释放，排队请求更快进入可执行状态。

2. 同一热点行上的并发请求更容易在短时间内聚集起来。

3. Group Commit 将这些请求批量执行和提交，进一步摊薄固定开销。

可以理解为：ELR 让请求更快流动起来，Group Commit 让流动起来的请求成批处理。

![ELR 与 Group Commit 协同工作机制](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/700.reference/diagra_3.jpg)

两者的使用方式也有所不同：

| 对比项 | ELR | Group Commit |
|--------|-----|--------------|
| 是否需要改 SQL | 通常不需要 | 需要添加 `GROUP_COMMIT(TRUE\|FALSE)` Hint |
| 主要收益 | 降低行锁等待 | 降低重复执行和提交开销 |
| 适合形态 | 高并发热点更新 | 同一热点行上的高并发参数化 `UPDATE` |

## UPDATE 位置对持锁时间的影响

![UPDATE 位置对持锁时间的影响](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer-enterprise/V4.2.5/700.reference/diagram_4.jpg)

上述优化作用于 `UPDATE` 执行及事务提交阶段。但在此之前，`UPDATE` 在事务中的位置本身已经决定了基本的持锁时长。

单语句事务中，`UPDATE` 从读取数据时开始加锁，直到事务提交完成后才释放。多语句事务中，如果 `UPDATE` 语句放在事务开头，后续 SQL 的执行耗时都算在其持锁时间内；当 `UPDATE` 语句放在事务最后一条执行时，其持锁时间与单语句事务中的持锁时间基本相同。

ELR 和 Group Commit 都可以缩短提交阶段的耗时，但无法缩短被前置 SQL 拉长的持锁时间。因此，将热点 `UPDATE` 放在事务最后一条执行，是优化性能的关键。

## 使用边界

热点行优化适合高并发、短事务、集中更新同一行或少量几行的场景。

以下情况中，优化收益可能不明显：

* 并发不高，短时间内难以形成有效聚合。

* 更新分散在大量不同的行上，不是热点行更新。

* SQL 模板不固定，或不同请求无法被识别为同一类更新。

* 事务较长，前置写入较多，导致热点 `UPDATE` 不能稳定进入聚合路径。

* 事务包含跨日志流写入或并行 DML，Group Commit 无法聚合。

* 携带 `GROUP_COMMIT` Hint 的 `UPDATE` 语句无法放在事务最后一条执行。
