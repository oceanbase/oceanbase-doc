# 热点行组提交使用方式及最佳实践

<main id="notice" >
    <h4>功能适用性</h4>
    <p>该功能仅适用于 OceanBase 数据库企业版。</p>
</main>

在秒杀抢购、热点账户扣款、库存扣减、高并发计数器等业务中，大量并发请求会在极短时间内更新同一行数据。关系型数据库为保证事务一致性，对同一行的更新需经过“加锁 → 执行 → 写日志提交 → 放锁”的过程，这个过程在行级是串行的：一个事务持锁期间，其余事务只能排队，且每个事务都需独立承担一遍 SQL 执行与事务提交的固定开销。并发越高，行锁排队与重复开销越成为吞吐瓶颈。

热点行组提交（Group Commit）针对这一瓶颈：通过一个 SQL Hint，由数据库内核把同一热点行上的多个并发 `UPDATE` 自动聚合为**一次执行、一次提交**，从而提升热点行的写入吞吐。聚合过程由内核自动完成，对应用透明，应用只需声明 Hint 并满足下述使用规则即可。

## 前提条件

### 打开租户开关

热点行组提交由租户级配置 `_enable_hotspot_group_commit` 控制，默认关闭，将其设置为 `true` 即可开启：

```sql
ALTER SYSTEM SET _enable_hotspot_group_commit = true tenant = xxx;
```

`tenant` 可指定具体租户，也可指定 `all` 对全部租户生效。

### 客户端启用 PS 协议

热点行组提交只在服务端预编译（Prepared Statement，PS）协议下生效。在 JDBC 连接串上开启 `useServerPrepStmts`，使连接使用服务端 PS（Prepare/Execute）协议：

```text
jdbc:oceanbase://host:2881/test?useServerPrepStmts=true
```

应用侧使用 `PreparedStatement` 执行携带 Hint 的语句，参数以占位符 `?` 绑定：

```java
PreparedStatement ps = conn.prepareStatement(
    "UPDATE /*+ GROUP_COMMIT(TRUE) */ account SET balance = balance - ? WHERE id = ?");
ps.setLong(1, 100);
ps.setLong(2, 1);
ps.executeUpdate();
```

### 关闭自由路由

热点行组提交语句所在的事务需关闭[自由路由（Free Route）](../../../1200.database-proxy/700.route-management/400.odp-routing-policy/400.transaction-routing.md)。未关闭时携带 Hint 的语句执行失败，错误码为 `-4007`，报错信息 `txn free route is enabled, need to disable it by hint or configuration`。可通过两种方式进行关闭：

* 租户级配置（自由路由功能在多数场景下能带来明显的性能提升，如非必要，建议采用第二种方式）：

  ```sql
  ALTER SYSTEM SET _enable_transaction_internal_routing = false tenant = xxx;
  ```

* Hint：在热点 `UPDATE` 的前一条 DML 上添加 `TRANS_PARAM('DISABLE_TX_FREE_ROUTE' 'true')`，自下一条语句起生效，本事务内自由路由功能将不再开启：

  ```sql
  INSERT /*+ TRANS_PARAM('DISABLE_TX_FREE_ROUTE' 'true') */ INTO trade_log VALUES (?, ?, ?);
  ```

### Plan Cache

Plan Cache 须保持开启。热点行组提交的聚合键信息在 SQL 预编译时写入 PS Cache，若 Plan Cache 关闭，每次执行均无法获取聚合键信息，但不报错，会静默退化为逐条执行的普通 `UPDATE`。Plan Cache 由租户级系统变量 [ob_enable_plan_cache](../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/7200.ob_enable_plan_cache-global.md) 控制，默认开启，如需手动开启，可执行以下语句：

```sql
SET GLOBAL ob_enable_plan_cache = ON;
```

### UPDATE 必须作为事务内最后一条 DML 执行

该约束是聚合请求执行时事务语义正确的前置条件，详细信息请参见[热点行性能优化原理说明](700.hot-row-optimization-principles.md)。

## Hint 配置方式

热点行组提交通过 SQL Hint 启用，其语法为 `/*+ GROUP_COMMIT(bool rollback_on_no_affect_row) */`，该 Hint 需紧跟在 `UPDATE` 关键字之后。

从语义上看，该 Hint 包含三个层次的含义：

* **GROUP —— 聚合执行**

  声明本条 `UPDATE` 参与热点行聚合。数据库内核将同一 SQL 模板、作用于同一热点行上的多个并发 `UPDATE` 归并为一个批次，共享一次批量执行通路。聚合键由数据库自动从 `WHERE` 子句中推导（主键或唯一键），无需显式指定。

* **COMMIT —— 统一提交**

  聚合批次内的全部请求在执行结束后会统一提交，为保证事务语义正确，带有该 Hint 的 `UPDATE` **必须**作为事务内的**最后一条** DML 执行。

* **rollback_on_no_affect_row —— 请求级影响行数检查**

  该参数作用于聚合批次中的**每一个子请求**，而非整批请求，即对每个子请求执行结果的 `affected_rows`（执行影响行数）做额外判断：

  * `TRUE`：数据库在执行每个子请求后检查其 `affected_rows`。若某个子请求的 `affected_rows = 0`，则**仅回滚该子请求**，并向该请求返回错误码 `-6290`；同一批次内的其他子请求不受影响，照常提交。

  * `FALSE`：不对聚合批次内各个请求执行结果的 `affected_rows` 做额外检查，子请求执行完成即视为成功提交（`commit_on_success`），`affected_rows = 0` 时返回 `0`，正常提交。

  因此，`TRUE` 在默认的“执行成功即提交”逻辑之上增加了一层子请求级的影响行数校验，而 `FALSE` 保持默认行为不变。

  该部分示例基于以下表结构：

  ```sql
  CREATE TABLE account (
      id           BIGINT       NOT NULL,
      user_id      BIGINT       NOT NULL,
      biz_id       BIGINT       NOT NULL,
      balance      BIGINT       NOT NULL,
      gmt_modified TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
      PRIMARY KEY (id),
      UNIQUE KEY uk_user_biz (user_id, biz_id)
  );
  ```

  `TRUE` 与 `FALSE` 的选择取决于 `UPDATE` 语句是否包含可能使 `affected_rows = 0` 的 `WHERE` 条件，以及出现该情形时是否需要向客户端明确报错。

  * `WHERE` 中包含条件表达式（如 `balance >= ?`），条件不满足导致 `affected_rows = 0` 时，需回滚并报错。

    ```sql
    UPDATE /*+ GROUP_COMMIT(TRUE) */ account
        SET balance = balance - ?
        WHERE id = ? AND balance >= ?;
    ```

  * `WHERE` 中仅包含等值定位条件，`affected_rows = 0` 属于可接受的执行结果，正常提交。

    ```sql
    UPDATE /*+ GROUP_COMMIT(FALSE) */ account
        SET balance = balance + ?
        WHERE id = ?;
    ```

## 规则与约束

在已开启热点行组提交且通过 PS 协议携带 Hint 执行时，语句需满足下述规则，违反时语句会执行失败或功能不生效：执行失败时错误码为 `-4007`（`OB_NOT_SUPPORTED`），功能不生效时按普通 `UPDATE` 执行，具体行为以各规则中的说明为准；未走 PS 协议或未开启功能时，Hint 不生效，同样按普通 `UPDATE` 执行，不报错。

### 协议与语句

* 仅支持标准两阶段 PS 协议，文本协议、二合一 PS 协议均不支持，具体行为见下方说明。

* 仅支持 `UPDATE` 语句；`INSERT`、`DELETE`、`SELECT` 携带 `GROUP_COMMIT` Hint 时不生效，Hint 会被忽略。

* 不支持在 PL（存储过程）中使用，执行失败，错误码为 `-4007`。

* 文本协议执行带 Hint 的 `UPDATE`：不生效，按普通 `UPDATE` 执行。

* 二合一 PS 协议执行带 Hint 的 `UPDATE`：执行失败，错误码为 `-4007`。

### WHERE 与聚合键

热点行组提交通过识别 `WHERE` 子句中的主键或唯一键，对并发更新同一行的请求进行分组聚合。语句需同时满足以下全部规则，否则执行失败并返回错误码 `-4007`。

* **支持的语句类型**

  * 键值必须用 `?` 占位，不能使用字面值常量，否则会执行失败，返回错误码 `-4007`，提示 `key matched in where condition but with value`。

    ```sql
    UPDATE /*+ GROUP_COMMIT(TRUE) */ account SET balance = balance - ? WHERE id = ?;
    ```

  * 仅识别 `=` 和 `<=>`。`>`、`<`、`>=`、`<=`、`!=`、`BETWEEN` 不参与键推导。在键已被完整覆盖的前提下，附加非等值条件不影响聚合。

    ```sql
    UPDATE /*+ GROUP_COMMIT(TRUE) */ account SET balance = balance - ? WHERE id = ? AND gmt_modified > ?;
    ```

  * 支持单元素 `IN (?)`。优化器会将其改写为 `= ?`，热点行组提交正常识别。该改写依赖 `_inlist_rewrite_threshold`（默认 1000），仅当其被设为 1 时不改写，热点行组提交对其不生效。

    ```sql
    UPDATE /*+ GROUP_COMMIT(TRUE) */ account SET balance = balance - ? WHERE id IN (?);
    ```

  * 主键优先于唯一键。WHERE 同时覆盖主键和唯一键时，按主键聚合。

    ```sql
    -- id（主键）与 uk_user_biz（唯一键）都被覆盖，按主键 id 聚合
    UPDATE /*+ GROUP_COMMIT(TRUE) */ account SET balance = balance - ? WHERE id = ? AND user_id = ? AND biz_id = ?;
    ```

  * 不能同时完整命中多个唯一键。若无主键命中且完整覆盖了两个及以上唯一键，执行失败，返回错误码 `-4007`，提示 `multiple unique key matched in where condition`。

  * 分区表可以使用全局唯一索引作为聚合键，使用时仍需完整覆盖唯一键列并以 `?` 绑定。

    ```sql
    CREATE TABLE t_part (
        id   BIGINT NOT NULL,
        g_id BIGINT NOT NULL,
        val  BIGINT NOT NULL,
        PRIMARY KEY (id),
        UNIQUE KEY uk_g_id (g_id) GLOBAL
    ) PARTITION BY HASH(id) PARTITIONS 16;

    UPDATE /*+ GROUP_COMMIT(TRUE) */ t_part SET val = val - ? WHERE g_id = ?;
    ```

* **SET 子句约束**

  * 命中的键列不能出现在 SET 子句中，执行失败，返回错误码 `-4007`，提示 `updating key columns in group commit`。只更新非键列：

    ```sql
    UPDATE /*+ GROUP_COMMIT(TRUE) */ account SET balance = balance - ? WHERE id = ?;
    ```

  * SET 子句中不能嵌套子查询，例如 `SET val = (SELECT ...)`。

* **适用范围**

  * 仅支持单表 `UPDATE`，多表更新（JOIN UPDATE）执行失败，返回错误码 `-4007`，提示 `multiple table update or join update`。

* **Oracle 模式限制**

  * `WHERE rowid = ?` 不能用作聚合键。`rowid` 是 Oracle 模式下表中每行数据的物理地址伪列，因其并非表上定义的主键或唯一键，无法参与聚合键推导。

* **不支持的写法**

  * 无法定位到聚合键：`WHERE` 未完整覆盖主键或唯一键的全部列。执行失败，返回 `-4007`。

    ```sql
    -- 表: t(id INT PRIMARY KEY, val INT)
    UPDATE /*+ GROUP_COMMIT(TRUE) */ t SET val = val - ? WHERE val > ?;
    ```

  * 无法定位到聚合键：键列使用字面值常量。执行失败，返回 `-4007`。

    ```sql
    -- 表: t(id INT PRIMARY KEY, val INT)
    UPDATE /*+ GROUP_COMMIT(TRUE) */ t SET val = val - ? WHERE id = 1;
    ```

  * 无法定位到聚合键：键列使用非等值操作符。执行失败，返回 `-4007`。

    ```sql
    -- 表: t(id INT PRIMARY KEY, val INT)
    UPDATE /*+ GROUP_COMMIT(TRUE) */ t SET val = val - ? WHERE id > ?;
    ```

  * 无法定位到聚合键：同时命中多个唯一键，且未命中主键。执行失败，返回 `-4007`。

    ```sql
    -- 表: t(id INT, uk1 INT, uk2 INT, val INT, UNIQUE KEY(uk1), UNIQUE KEY(uk2))
    UPDATE /*+ GROUP_COMMIT(TRUE) */ t SET val = val - ? WHERE uk1 = ? AND uk2 = ?;
    ```

  * 无法定位到聚合键：SET 中修改命中的键列。执行失败，返回 `-4007`。

    ```sql
    -- 表: t(id INT PRIMARY KEY, val INT)
    UPDATE /*+ GROUP_COMMIT(TRUE) */ t SET id = ? WHERE id = ?;
    ```

  * SET 中包含子查询。执行失败，返回 `-4007`。

    ```sql
    -- 表: t(id INT PRIMARY KEY, val INT)
    UPDATE /*+ GROUP_COMMIT(TRUE) */ t SET val = (SELECT MAX(val) FROM t2) WHERE id = ?;
    ```

  * 涉及多表。执行失败，返回 `-4007`。

    ```sql
    UPDATE /*+ GROUP_COMMIT(TRUE) */ t1
    JOIN t2 ON t1.id = t2.t1_id
    SET t1.val = t1.val - ?
    WHERE t1.id = ?;
    ```

### 表限制

存在以下情况时，热点行组提交不生效，语句按普通 `UPDATE` 执行：

* 表上定义了 UDF、Trigger 或外键。

* 语句更新全局索引列。

* 表既无主键也无唯一键（无可用聚合键）。

分区表可以使用热点行组提交，但需注意：

* 可以基于主键、唯一键或全局唯一索引定位单行。

* 不支持更新分区键列、主键列、唯一键列或全局索引列。更新分区键列执行失败，返回 `-4007`。

### 事务要求

热点行组提交可以用于单语句事务，也可以用于已经包含前置 DML 的显式事务。事务需满足以下要求：

* **事务已关闭自由路由。** 可通过租户级配置关闭自由路由。若按事务关闭，需在热点 `UPDATE` 之前的 DML 上添加 `TRANS_PARAM('DISABLE_TX_FREE_ROUTE' 'true')` Hint，该 Hint 从下一条语句开始生效，且本事务内关闭后不可再开启。

* **若存在前置 DML，前置 DML 只涉及一个日志流。** 如果前置 DML 涉及多张表，需保证这些写入落在同一[日志流（Log Stream）](../../../100.oceanbase-database-concepts/500.distributed-database-objects/300.data-partitions-and-replicas/200.logstream.md)内；可通过将相关表放入同一个 [表组（Table Group）](../../../300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md) 实现。

* **若存在前置 DML，前置 DML 未使用[并行 DML（PDML）](../../500.sql-optimization/300.distributed-execution-plan/1000.parallel-dml.md)。** 如果事务内更早执行的 DML 已经使用了 PDML，本次优化不生效。

## 最佳实践

推荐按事务形态组织热点行组提交：优先使用单语句事务；需要前置 DML 时，再使用多语句事务。完整的端到端体验请参见[《体验 OceanBase 数据库热点行更新能力》](200.experience-the-hot-row-update-capability-of-oceanbase-database.md)。

### 单语句事务

在 autocommit 模式下，通过 `PreparedStatement` 执行一条固定的参数化 `UPDATE`。JDBC 连接串开启 `useServerPrepStmts=true`，并复用预编译句柄。

该部分示例基于以下表结构：

```sql
CREATE TABLE t_hot (
    id  BIGINT PRIMARY KEY,
    val BIGINT NOT NULL
);
```

`TRUE`/`FALSE` 根据影响 0 行时的处理方式选择：

* 需要在影响 0 行时回滚并返回错误，使用 `GROUP_COMMIT(TRUE)`。

* 需要在影响 0 行时正常提交并返回 `affected_rows = 0`，使用 `GROUP_COMMIT(FALSE)`。

```sql
UPDATE /*+ GROUP_COMMIT(TRUE) */ t_hot
    SET val = val - ?
    WHERE id = ? AND val >= ?;
```

```sql
UPDATE /*+ GROUP_COMMIT(FALSE) */ t_hot
    SET val = val + ?
    WHERE id = ?;
```

### 多语句事务

热点 `UPDATE` 前已有其他 DML 时，将关闭自由路由的 Hint 固定放在前置 DML 上，然后执行带 `GROUP_COMMIT` Hint 的 `UPDATE`。

同时，在携带 `GROUP_COMMIT` Hint 的 `UPDATE` 语句执行后，应正常显式调用 COMMIT/ROLLBACK 语句：一方面，尽管 Group Commit 自带事务自动提交语义，再次执行 COMMIT 的开销很低；另一方面，一旦租户级配置关闭了 Group Commit 功能，事务将缺少正常的提交和回滚操作，影响业务逻辑执行的完整性。

`t_hot` 表沿用单语句事务一节中的定义，并新增 `t_log` 表：

```sql
CREATE TABLE t_log (
    id     BIGINT PRIMARY KEY,
    ref_id BIGINT NOT NULL,
    amount BIGINT NOT NULL
);
```

```sql
BEGIN;
INSERT /*+ TRANS_PARAM('DISABLE_TX_FREE_ROUTE' 'true') */
    INTO t_log(id, ref_id, amount)
    VALUES (?, ?, ?);
UPDATE /*+ GROUP_COMMIT(TRUE) */ t_hot
    SET val = val - ?
    WHERE id = ? AND val >= ?;
COMMIT;
```

前置 DML 保持固定、少量；涉及多张表时，将相关表放入同一个 [表组（Table Group）](../../../300.database-object-management/100.manage-object-of-mysql-mode/400.manage-table-groups-of-mysql-mode/100.about-table-groups-of-mysql-mode.md)。

```sql
CREATE TABLE t_log (
    id     BIGINT PRIMARY KEY,
    ref_id BIGINT NOT NULL,
    amount BIGINT NOT NULL
) TABLEGROUP = tg_hot;

CREATE TABLE t_hot (
    id  BIGINT PRIMARY KEY,
    val BIGINT NOT NULL
) TABLEGROUP = tg_hot;
```

### 不适合使用热点行组提交的场景

* **低并发场景。** 并发请求数不足以及时填满聚合批次，延迟增加且吞吐收益有限，此时单独使用 [ELR](700.hot-row-optimization-principles.md) 即可满足需求。

* **非热点行场景。** 更新分散在多行上，每行各自形成排队队列，单个队列内的请求数不足以触发有效聚合。

* **事务内包含大量前置写入。** 前置 DML 过多容易在执行热点 `UPDATE` 前触发事务日志写出（受租户级配置项 `_private_buffer_size` 控制，前置 DML 累积的日志量超过该阈值即落盘），导致聚合失效。若业务必须大量前置写入，可适当调大 `_private_buffer_size`，确保前置 DML 累积的日志在热点 `UPDATE` 执行前不落盘，或将热点 `UPDATE` 拆为独立事务。

* **热点行更新的 `UPDATE` 语句无法置于事务内语句的最后。** 该约束用于保证聚合请求执行时的事务语义正确，详细信息请参见[热点行性能优化原理说明](700.hot-row-optimization-principles.md)。

## 错误码

| 错误码 | 名称 | 触发场景 |
|--------|------|---------|
| `-6290` | `OB_ROLLBACK_ON_NO_AFFECTED_ROWS` | `GROUP_COMMIT(TRUE)` 且子请求影响 0 行，回滚该子请求并返回错误 |
| `-4007` | `OB_NOT_SUPPORTED` | 语句不满足热点行组提交使用规则 |
