# 向量索引

本文介绍 HNSW 系列索引和 IVF 系列索引的原理。

## HNSW 系列索引

OceanBase 数据库的 HNSW 向量索引，分为静态基线索引和动态增量索引两部分：静态基线索引只读，一旦生成不再修改；动态增量索引支持读写。DML（插入、更新、删除）先写入动态增量索引；当增量达到一定规模时转储到磁盘。查询时分别查询静态基线索引和动态增量索引，将结果归并后返回给 SQL 层。
当增量部分达到一定规模时，会触发增量与基线的合并，以控制 Segment 数量、保证查询性能。

### 索引存储

#### 数据组织

向量索引的数据组织引入了段（Segment）概念，分区内按段组织数据。引入持久化增量后，存在四类段：

![](https://obbusiness-private.oss-cn-shanghai.aliyuncs.com/doc/img/observer/V4.6.0/HNSW%E7%B4%A2%E5%BC%95segment%EF%BC%88%E6%A8%AA%EF%BC%89.png)

| 段 | 说明 | 存储位置 | 读写 |
|---------|------|----------|------|
| 基线索引 | 全量重建产生的只读索引 | 5号表（BLOB） | 只读 |
| 活跃增量 | 内存中可写的增量索引 | 内存 | 读写 |
| 冻结增量 | 活跃增量满后冻结 | 内存 | 只读 |
| 已持久化增量 | 冻结后落盘的增量 | 5号表（BLOB） | 只读 |
 
其他说明：

* 基线只有一个段，增量可有多个段。
* 增量段可能含未提交/回滚数据，需配合可见性位图过滤。

#### 内部辅助表

向量索引依赖几张内部辅助表来管理工作，为避免外部用户理解困难，这里给出通俗说明：

| 通俗名称 | 内部代号 | 用途 |
|---------|------|----------|
| 主键映射表 | rowkey_vid | 记录主表 rowkey 与向量 ID 的对应关系 |
| ID回表表 | vid_rowkey | 向量查询后，通过 ID 找到主表 rowkey 用于回表 |
| 增量操作日志 | delta_buffer（3号表） | 实时记录 DML 操作的向量 ID（插入/删除） |
| 可见性快照表 | index_id_table（4号表） | 记录哪些向量是可见的、哪些已删除 |
| 索引数据表 | index_snapshot_data_table（5号表） | 持久化存储向量索引数据（序列化的 HNSW 图） |

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>为什么需要这么多表？</p>
  <p>向量索引和普通索引不同：向量索引库（如 VSAG）不支持实时删除，需要通过额外的表来跟踪哪些向量是"有效的"，查询时传入这些信息来过滤掉已删除的数据。这些内部表由系统维护，用户无需直接操作。</p>
</main>

:::tab
tab 增量操作日志（delta_buffer）

这是一个类似日志的表，记录所有新增和删除的向量 ID：

| 列 | 说明 |
|---------|------|
| vid | 向量 ID |
| Type | 操作类型：'I'=插入, 'D'=删除 |
| vector | 向量数据 |
| ora_rowscn | 版本号，用于判断可见性 |

插入 → 写一行 Type='I'
删除 → 写一行 Type='D'

tab 可见性快照表（index_id_table）

增量操作日志会不断增长，查询时实时扫描全表太慢。可见性快照表定期将增量日志中的变更"凝固"下来，形成稳定的快照，减少查询时的扫描量。

tab 索引数据表（index_snapshot_data_table）

向量索引（HNSW 图结构）以 BLOB 二进制 形式存储在这张表中，不是一个个独立文件。

:::

### DML 操作

本节介绍向量索引的 DML 操作，包括插入、删除和更新。

#### 核心概念

* vid：向量 ID，每个向量唯一的标识，由系统自增生成
* rowkey：主表的行主键
* bitmap：位图，记录哪些 vid 是有效的、哪些已删除

#### 操作流程

1. 插入
    * 生成新的 vid
    * 写入 主键映射表（rowkey → vid）和 ID回表表（vid → rowkey）
    * 写入 增量操作日志，标记 Type='I'
    * 内存活跃增量索引添加新向量

2. 更新（索引列）
    * 根据 rowkey 查到旧的 vid
    * 生成新的 vid
    * 更新映射表
    * 增量操作日志写入两条记录：(old_vid,'D') + (new_vid,'I')
    * 新的 vid 和向量写入活跃增量索引

3. 删除
    * 根据 rowkey 查到 vid
    * 删除映射表中的记录
    * 增量操作日志写入 (vid,'D')
    * 图索引不实时删节点，而是查询时通过 bitmap 过滤

### 转储与合并

#### 转储

将内存中的增量数据持久化到磁盘，并收缩日志表：

1. 冻结：当活跃增量达到阈值（如内存/行数），将其冻结（不再写入） → 产生冻结增量
2. 持久化：将冻结增量序列化，写入 5 号表存储
3. 更新元数据：更新索引的元数据（版本号、段列表）

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>向量索引的"转储"与 memtable 转储不同——增量转储后仍可能保留在内存供查询，直至合并或淘汰。</p>
</main>

#### 合并

| 类型 | 触发条件 | 作用 |
|---------|------|----------|
| 增量合并 | 已持久化增量 ≥ 2 个 | 合并多个增量，减少查询时的归并开销 |
| 基线重建 | 增量向量数超过基线 | 全量重建，生成新的只读基线索引 |

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>合并可同时做量化压缩（如 FP32 → SQ/BQ），节省存储空间。</p>
</main>

### 索引查询

这里介绍流程和过滤器的实现原理。

#### 查询流程

索引查询流程包含以下步骤：

1. 构造有效向量集合（valid_bitmap）
    * 合并可见性快照 + 增量操作日志
    * 过滤掉未提交、已回滚、已删除的向量

2. 选择要查询的段
    * 基线索引 + 所有增量段

3. 多路检索与归并
    * 对每个段调用 KNN 搜索
    * 传入 valid_bitmap 过滤无效向量
    * 归并结果，Top-N 排序

4. 回表
    * 用 vid 在 ID回表表 查到 rowkey
    * 用 rowkey 回主表取完整行数据

#### 过滤器

查询时支持两种过滤器：

| 场景 | 说明 |
|---------|------|
| Pre_filter | 先过滤主表数据，再查向量索引（适合过滤条件筛选性强的场景） |
| Post_filter | 查询向量索引后，在候选结果上过滤（适合大多数向量结果都有效的情况） |

### 常见问题

Q: 为什么删除操作不实时删节点？
A: HNSW 是图结构，删除节点会影响图的连通性，可能导致"孤岛"影响召回率。因此采用"软删除"——通过 bitmap 标记已删除，查询时过滤。

Q: 为什么要分基线和增量两部分？
A: 向量索引库（HNSW）构建索引代价高，不适合频繁更新。改为：
* 基线：只读，定期全量重建，适合查询
* 增量：内存可写，支持实时 DML，定期合并到基线

Q: vid 和 rowkey 是什么关系？
A: 
* rowkey：主表的行主键，是用户在 SQL 中使用的
* vid：向量索引内部使用的 ID，随每次插入/更新自动生成
* 两者通过映射表关联，查询时需要"回表"转换
