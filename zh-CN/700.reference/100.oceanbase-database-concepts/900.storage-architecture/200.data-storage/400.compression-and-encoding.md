# 压缩与编码

本文介绍 OceanBase 数据库中压缩与编码的方法和特性。

## 压缩技术概述

数据库系统中普遍都会对数据进行不同程度的压缩来减小存储成本，一些面向 AP 的列存数据库的按列编码压缩还能够提高某些查询的性能。但对于大部分压缩算法，越高的压缩率也就意味着更复杂的计算和更慢的压缩/解压速度。在传统的 B 树存储结构下的数据库中，数据压缩可能会给数据写入带来 CPU 的计算压力，影响写入性能。但 OceanBase 数据库的 LSM-Tree 架构使数据的压缩只发生在 Compaction 阶段，不会影响数据的写入，同时也使能够使用压缩率更高的压缩方法，在一些客户的应用场景中也证明了 OceanBase 数据库在压缩能力上的优势。

## 数据压缩方式

在 OceanBase 数据库中，当 MemTable 占用内存空间大小达到一定阈值或每日合并时会触发转储/合并，MemTable 中的数据落盘并合并成静态的 SSTable 数据。相对于 MemTable，SSTable 中的数据量会更大，冷数据也相对更多。在合并不断产生新的 SSTable的过程中 OceanBase 数据库会对 SSTable 中的数据进行压缩和编码，来节省数据在硬盘上的存储空间，同时减小对 SSTable 进行查询时产生的 IO。在 SSTable 中，数据是以块为单位来组织的，2Mb 定长的宏块方便对存储空间进行管理，宏块内部变长的微块则方便我们对数据进行压缩。微块有两种存储格式，flat 微块（未编码）和 encoding 微块（编码），OceanBase 数据库的数据压缩与编码都是在微块的粒度上进行的。对于一个 encoding 格式的微块，需要经历 **填充行 -> 编码 -> 通用压缩（可选）-> 加密（可选）** 的流程后完成构建，成为最后落盘的数据块，并写入到定长的宏块中。这个流程中的**编码和通用压缩就是 OceanBase 数据库对数据进行压缩的两种方式**。

## 通用压缩

通用压缩指的是压缩算法对数据内部的结构没有了解的情况下，直接对数据块进行压缩。

这种压缩往往是根据二进制数据的特征进行编码来减少存储数据的冗余，并且压缩后的数据不能随机访问，压缩和解压都要以整个数据块为单位进行。

### 支持算法

OceanBase 数据库支持四种压缩算法：`snappy`、`lz4`、 `zstd`、`zlib_lite_1.0`。

其中 `zlib_lite_1.0` 算法是 OceanBase 数据库新引入的一种数据压缩算法，旨在提升数据库压缩和解压缩的性能，可以用在表的数据压缩解压缩中。该算法基于 Deflate 算法，并且基于 Intel 的 In-Memory Analytics Accelerator (Intel® IAA) 加速器，以充分利用硬件功能，并确保跨多个平台的兼容性，包括 x86 和 ARM 架构。`zlib_lite_1.0` 在提高数据处理效率的同时，确保了对传统 zlib 库的兼容性，为用户提供了一个高性能且灵活的压缩解决方案。

* **zlib_lite_1.0 算法特性**

  * **跨平台兼容性**：`zlib_lite_1.0` 支持 x86 和 ARM 两大流行硬件平台，保证了在不同的系统架构上均能稳定运行。
  * **硬件加速支持**：在具备 Intel IAA 硬件加速条件的机器上，`zlib_lite_1.0` 能够利用硬件资源实现数据压缩和解压缩的加速，从而显著提升性能。
  * **软件加速备选**：在不支持硬件加速的 x86 机器上，算法可自动回退到软件加速方式，确保不会因硬件限制而影响压缩效率。
  * **zlib 库兼容**：`zlib_lite_1.0` 设计时考虑了与传统 zlib 库的兼容性，使得现有依赖 zlib 库的应用无需修改即可利用新算法的性能优势。
  * **性能调优设计**：`zlib_lite_1.0` 经过定制优化，相比传统 `zlib` 算法，在保持相同压缩率的前提下提供了更快的压缩和解压缩速度。

OceanBase 数据库的 `zlib_lite_1.0` 压缩算法是一种高效、兼容且灵活的数据压缩解决方案，它利用先进的硬件加速技术和软件优化来提供卓越的性能。无论是在存储成本控制、数据传输效率提升还是实时数据处理方面，`zlib_lite_1.0` 都展现出其显著的优势，特别适用于现代多平台、性能敏感的数据库应用场景。

### 压缩性能

  在 OceanBase 数据库内部对默认 16kb 大小的微块进行压缩的测试中：

  | 压缩算法 | 压缩速度| 压缩率 |
  | --------| -------| ------ |
  | snappy         | 快 | 低 |
  | lz4            | 快 | 低 |
  | zlib_lite_1.0  | 慢 | 高 |
  | zstd           | 慢 | 高 |

  `lz4` 压缩率与 `snappy` 相似但压缩解压速度更快；`zstd` 压缩率与 `zlib_lite_1.0` 相似但压缩解压速度也更快。

### 模式支持

* 在 MySQL 模式下，用户可指定单独选择压缩算法。
* 在 Oracle 模式下，仅支持用户选择 `lz4` 或 `zstd` 压缩算法。

## 数据编码（Encoding）

在通用压缩的基础上，OceanBase 数据库自研了一套对数据库进行行列混存编码的压缩方法（encoding）。和通用压缩不同，encoding 的基础建立在压缩算法感知数据块内部数据的格式和语义的基础上。

OceanBase 数据库是一个关系型数据库，数据是以表的形式来组织的，表中的每一列都有固定的类型，这就保证了同一列数据在逻辑上存在着一定的相似性；而且在一些场景下，业务的表中相邻的行之间数据也可能会更相似，所以如果将数据按列进行压缩并存储在一起就可以带来更好的压缩效果。

因此，OceanBase 数据库引入了一种 encoding 格式的微块，与所有数据逐行序列化到块中的 flat 格式的微块不同，encoding 格式的微块是行列混存的，逻辑上仍然是一组行的数据存在微块里，但微块会按列对数据进行编码，编码后的定长数据存储在微块内部的列存区，部分变长数据还是按行存储在变长区。而且在 encoding 微块中，数据是可以随机访问的，当需要读微块中的一行数据时，可以只对这一行数据进行解码，避免了部分解压算法读一部分数据要解压整个数据块的计算放大；在向量化执行的过程中也可以对指定的列进行解码，降低了投影的开销。

### 数据编码格式

OceanBase 数据库支持多种的编码格式，包括列编码、字符串编码、列间编码以及复合编码的方式对数据进行压缩存储。

* **列编码格式**

  OceanBase 数据库提供了多种按列进行压缩的编码格式，包括列存数据库中常见的字典编码（Dictionary Encoding）、游程编码（Run-Length Encoding）、整形差值编码（Delta Encoding）、常量编码（Constant Encoding）等。

  * **字典编码**：通过在微块内部构建字典，存储每行的引用来进行数据压缩。尤其适用于微块内的数据基数较小时的场景，能够有效减少实际存储的数据量。

  * **游程编码**：通过在微块内部构建字典，存储每行的引用来实现数据压缩。在字典编码的基础上，对连续的相同数据采用游程编码，进一步提高压缩率。

  * **整形差值编码**：适用于存储的列是一个定长的数值，如 `timestamp`、`bigint` 等，且微块中的数据分布在一个值域内的场景。通过只存储每一行的值与微块中最小值的差值，然后做 bit-packing，能够带来较好的压缩效果。

  * **常量编码**：当一个微块内的一列数据基本都是相同的数据时，可以通过常量编码只存储常量和微块内不等于常量的值，以进一步提高数据的压缩率。

  这些按列进行压缩的编码格式适用于不同的数据特征和场景，能够提高数据的压缩效率，并优化存储空间的利用。

* **字符串编码格式**

  针对字符串类型数据，OceanBase 数据库设计了前缀编码（prefix encoding）、定长字符串差值编码（string diff encoding）、十六进制编码（Hex encoding）等多种编码格式，以实现对较长的业务 ID 和带格式的字符串数据的高效压缩。

  * **前缀编码**：当一列数据中有相似的前缀时，采用前缀编码。前缀编码存储前缀和每行数据的尾缀，以实现对相似前缀的数据进行压缩。

  * **定长字符串差值编码**：在数据列中包含定长的字符串，并且其中几个字节相同时，采用定长字符串差值编码。该编码存储模式串和每行的差值数据，以实现对定长字符串中相似部分的数据进行压缩。

  * **十六进制编码**：当微块中一列字符串数据的字符基数小于 16 时，采用十六进制编码。该编码方式使用一个十六进制数来表示字符，以实现对字符基数较小的字符串数据进行压缩。

* **列间编码格式**

  在业务存储的表中，除了同一列数据之间存在相似性，不同列的数据之间也可能有一定的关系。因此 OceanBase 数据库引入了列间编码（span-column Encoding），包括列间等值编码（Column equal encoding）和列间子串编码(Column prefix encoding)，以实现不同列数据之间的关联压缩，提高宏块的压缩率。

  * **列间等值编码**：当两列数据大部分相同时，使用列间等值编码。该编码形式使一整列数据都成为另外一列的引用，以实现数据的压缩存储，降低数据的冗余性。
  * **列间子串编码**：当一列数据是另外一列数据的前缀时，可以使用列间子串编码。仅存储完整的一列和一列的后缀，以实现对数据的压缩并降低冗余性。

  这种列间编码能够有效降低数据冗余，提高压缩率，尤其对于重复的时间戳和复合列等具有较好的压缩效果。然而，在编码和解码时会更加复杂，需要对不同列数据是否符合编码规则进行探测，并在解码时需要根据引用访问被引用的列的数据，进行处理后解码出数据。相对于其他的编码，这种方式对 CPU 不太友好，而且在有些情况下可能出现不同列之间可以级联引用的情况，需要进行特殊处理。因此，在列间编码的使用过程中需要权衡这种复杂性带来的额外开销和压缩效果带来的性能优势。

* **复合编码格式**

  在每列自己编码的基础上，OceanBase 数据库支持一列数据采用多种编码方式进行压缩，但复合编码方式会导致编解码的复杂性增加。

  * **复合编码**：支持在每列自己编码的基础上对一列数据采用多种编码方式进行压缩。例如，`hex` 编码可以与其他字符串编码叠加，从而提供了更大的灵活性。然而，这种方式也会导致编码解码变得更为复杂。

  * **自适应编码**：OceanBase 数据库所支持的编码格式不仅与表的schema相关，同时也与微块内的值域等数据本身的特征相关。因此，在设计表数据模型时要指定列编码来实现最佳的压缩效果并非易事。OceanBase 数据库支持在合并过程中自适应地探测更合适的编码方式来对数据进行编码以达到更高的压缩率。

在 V3.2.x 版本后，encoding 又支持了向量化执行和 filter 下压，能够在编码后的数据上根据编码的特征进行过滤，降低了一些 overhead，对于一些编码也能够提高过滤效率，对部分列存的定长数据，也支持使用 AVX2 指令集进行 SIMD 的加速过滤。同时对于一些微块内部按列存存储的数据，向量化执行中直接按列来进行解码对 cache 和分支预测也都更加友好。

当然，除了这些优势外，encoding 也会带来一些问题，其中最直接的是编码解码带来的额外开销，包括合并过程中带来的 CPU 计算压力，查询逐行迭代时复杂的解码带来的 CPU 开销和解码器本身的开销等。OceanBase 数据库在这些问题上进行了一些优化，包括将解码器和对应的数据一起 Cache 在内存中等。但是对于一些复杂的编码格式，解码本身带来的额外性能开销也是无法避免的。OceanBase 数据库也会一直尝试在查询性能，内存占用，存储成本上进行更多的权衡。

## 配置压缩选项

### 相关配置项

OceanBase 数据库支持通过 DDL 来对表级别的压缩/编码方式来进行配置。但对已经生成了 SSTable 的表进行压缩选项的变更时，为了避免给一次合并带来太大的 IO 写入压力，需要通过渐进合并的方式逐渐重写全部的微块数据，来完成压缩选项的变更。渐进合并的轮次可以通过表级配置项 [default_progressive_merge_num](../../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/1400.default_progressive_merge_num.md) 来设置。

### 配置示例

* 建表时指定压缩选项

  :::tab
  tab MySQL 模式

  ```sql
  obclient> create table xxx row_format = $value compression = $value;
  ```

  tab Oracle 模式

  ```sql
  obclient> create table xxx $value;
  ```

  :::

* 修改一个表的压缩选项

  :::tab
  tab MySQL 模式

  ```sql
  obclient> alter table xxx [set] row_format = $value compression = $value;
  ```

  tab Oracle 模式

  ```sql
  obclient> alter table xxx [move] $value;
  ```

  :::

* **compression 字段**

  MySQL 模式中 `compression` 的选项取值如下：
