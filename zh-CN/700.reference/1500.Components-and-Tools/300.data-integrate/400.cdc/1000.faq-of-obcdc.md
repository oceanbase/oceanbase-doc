# obcdc 常见问题

本文介绍 obcdc 的常见的问题和注意事项。

## 如何判断启动时间戳是否过小

obcdc 支持配置日志回拉时间点，obcdc 会拉取提交时间大于该时间点的日志，这个时间点，称之为“启动时间戳”。

### 注意事项

1. obcdc 支持集群级（多租户）同步，同步整个集群时，需要尽量保证所有机器的时钟同步。否则有可能导致各租户的 GTS 时间相差大，进一步导致 obcdc 因安全位点回退，退出进程。
obcdc 4.x 当前版本推荐一个 obcdc 仅同步一个租户。
2. obcdc 目前不支持同步有备租户的集群。
3. 只有 `fetching_log_mode=direct` 且 `meta_data_refresh_mode=data_dict` 时才能完全离线地消费日志，其他模式组合均需要向 OBServer 节点发送请求，即需要配置 OBServer 节点的入口，包括 `cluster_url` 或 `rootserver_list`。

### 启动时间戳限制

obcdc 在回拉单租户数据时，回拉位点过小时，obcdc 可能无法启动，具体限制参考如下说明：

1. 同步单租户

   1. 当 `fetching_log_mode=integrated` 时

       1. 未开启归档

          用户指定的 obcdc 的启动时间戳至少需要大于租户的所有日志流最大的 `BEGIN_SCN`，该位点可通过在该租户下执行如下 SQL 查询得到。

           ```shell
           SELECT CEIL(MAX(BEGIN_SCN)/1000) AS START_TS_US FROM oceanbase.GV$OB_LOG_STAT;
           ```

       2. 开启归档

          用户指定的 obcdc 的回拉位点至少需要大于下面两者的最小值。

          1. 租户的所有日志流最大的 `BEGIN_SCN`。
          2. 租户归档开启的时间，即 `START_SCN`，租户归档开启的时间可以通过在该租户下执行如下SQL查询得到。

             ```shell
             SELECT CEIL(MAX(START_SCN)/1000) as START_TS_US  FROM oceanbase.DBA_OB_ARCHIVELOG;
             ```

   2. 当 `fetching_log_mode=direct` 时，只支持同步单租户，需要保证 obcdc 的启动时间戳大于归档日志的开启时间点。

      若使用数据字典模式，需要保证启动时间大于租户数据字典中最小的 `snapshot_scn`，租户数据字典中最小的 `snapshot_scn` 可以通过在该租户下执行如下 SQL 查询得到。

       ```shell
       SELECT CEIL(MIN(snapshot_scn)/1000) FROM oceanbase.DBA_OB_DATA_DICTIONARY_IN_LOG;
       ```

       <main id="notice" type='explain'>
         <h4>说明</h4>
         <p>您也可在系统租户下指定 <code>tenant_id</code> 查询 oceanbase.CDB_OB_DATA_DICTIONARY_IN_LOG 视图。</p>
       </main>

2. 同步多租户

    回拉集群（多个租户）数据时，用户指定的 obcdc 启动时间戳需要保证在该时间戳上每个租户都需要满足上述单租户的条件。

## 虚拟生成列功能使用限制

自 OceanBase 数据库 V4.x 开始，对于未在列上明确标记为 `STORED` 的生成列，将按照虚拟生成列处理，值不再记录到 clog 中。

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>obcdc 在 V4.2.5.0 之前不支持输出虚拟生成列。</p>
</main>

当 OceanBase 数据库版本处于 [4.2.5.0, 4.3.0.0) U [4.3.4.0, +∞) 范围内时，使用版本位于[4.2.5.0, 4.3.0) U [4.3.5.5, 4.4.0) U [4.4.2.0, +∞) 范围的 obcdc 且配置了 `enable_output_virtual_generated_column=1` 时，可以同步部分场景写入的虚拟生成列。但是不保证对各类生成列表达式都支持。

当用户需要使用该功能时，需要提前对用到的虚拟生成列进行测试验证，如遇到需要同步但不支持的虚拟生成列，可以将该列设置为 STORED 生成列。目前存在如下情况时，确认无法支持：
  
* 生成列规则涉及时区。

* 生成列规则涉及系统函数，比如 `FROM_TZ`、`NULLIF`。
  
* 生成列使用 JSON 函数，且使用了 `JSON PATIAL UPDATE` 功能时。

## 表级恢复功能使用限制

* OceanBase 数据库自 V4.2.1 起提供了表级恢复功能，因底层也借助了旁路导入的实现，因此不支持数据同步。

* 当 OceanBase 数据库和 obcdc 版本都处在 [4.2.5, 4.3.0) U [4.4.2, 4.5.0) U [4.6.0, +∞) 范围内时，obcdc 可以输出表级恢复执行完成后的表的增量数据变更，但不会输出创建表的 DDL。

## 旁路导入使用限制

* 全量旁路导入：导入数据未走事务路径时，obcdc 不支持。
* 增量旁路导入：obcdc 自 V4.2.5.0 版本支持。
* 增量基线导入：obcdc 不支持输出。

## 可信列标记逻辑说明

在 OceanBase 数据库 V4.x 版本中，clog 中不一定会记录 DML 操作的行的所有列信息，但 obcdc 会输出 DML 操作的行的所有列。对于 OceanBase 集群 clog 中记录的列值，obcdc 会标记该列为可信列（列值来源为 Redo 日志），对于 OceanBase 集群 clog 中没有记录的列，obcdc 将会标记为不可信列（列值来源为 obcdc 自行生成，通常为 `NULL`）。

对 obcdc 的下游消费者，需要根据列值是否可信，调整自己的消费逻辑，防止将不可信列的数据传输给下游而带来数据正确性的问题。

消息库中 `ValueOrigin.h` 中的 enum 类型 `VALUE_ORIGIN` 代表了列值来源，`VALUE_ORIGIN::REDO` 代表列值来源于 Redo 日志，说明该列为可信的。`VALUE_ORIGIN::PADDING` 说明列值为 obcdc 自己生成，不代表真实列值；obcdc 下游消费者可以通过解析出的每列的 `binlogbuf` 中的 `m_origin` 字段获取该列的可信标记。

## obcdc 自什么版本支持 MOW 表

对 OceanBase 数据库 V4.3.5 BP5 之前版本写入的 MOW 表数据，使用 V4.3.5 BP5 及之前版本的 obcdc 可能遇到非预期异常，使用 V4.3.5 BP6 及之后版本的 obcdc 则不会输出涉及的 OUTROW LOB 数据（标记为不可信列）。

OceanBase 数据库 V4.3.5 BP5 及之后版本写入的 MOW 表数据，obcdc 可以正常处理。

## obcdc 自什么版本支持 MINIMAL MODE

obcdc 可以同步 OceanBase 数据库 V4.3.x 及之后版本写入的 minimal 模式数据，对于其中不涉及变更的列，obcdc 会将该列值输出为 `NULL`，并标记为不可信列。
