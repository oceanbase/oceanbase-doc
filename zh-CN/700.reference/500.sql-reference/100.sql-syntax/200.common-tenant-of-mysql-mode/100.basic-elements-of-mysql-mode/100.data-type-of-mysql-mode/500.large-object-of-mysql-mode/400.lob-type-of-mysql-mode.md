# LOB 类型

`LOB` 类型是用于存储 TEXT、BLOB、JSON、Geometry 等数据类型。
`LOB` 的存储的方式分为内联存储（INROW）和外联存储（OUTROW）两种。

## 内联存储

内联存储是将 LOB 数据与主表行存储在一起，在读取 LOB 数据时只需要进行一次存储访问操作。

## 外联存储

外联存储是将 LOB 数据存储在 LOB 辅助表中，在读取 LOB 数据时需要读取主表行，获取外联 LOB 的定位符（locator），之后根据定位符信息去 LOB 辅助表中读取实际的 LOB 数据，在这个过程中需要进行两次存储访问操作。

## LOB 存储转换

LOB 数据的存储是内联存储还是外联存储，取决于 LOB 列的数据量。假如设定一个阈值为 8192 字节，如果超过 8192 字节 则为外联存储，否则为内联存储。

```shell
obclient> CREATE TABLE t(pk int, data text) LOB_INROW_THRESHOLD = 8192;
```

上述 DDL 指定了表中 LOB 列的 INROW 转 OUTROW 阈值为 8192 字节，其中 `LOB_INROW_THRESHOLD` 表示 LOB 列的阈值。

* 当 LOB 列的数据小于等于 8192 字节时，LOB 数据和主表行存储在一起。
* 当 LOB 列的数据大于 8192 字节时，会将所有数据存储到 LOB 辅助表中。

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p><code>lob_inrow_threshold</code>的值从大改小需要触发 Offline DDL。</p>
</main>

内联存储相对于外联存储具有更好的性能表现，它能够减少存储访问次数，提高读取 LOB 数据的效率。特别是在需要频繁访问 LOB 数据的场景下，选择内联存储能够加快查询速度并降低系统开销。

## LOB 类型

在 MySQL 模式下，常见的 LOB 类型按字母顺序排列如下：

- **ARRAY**：用于存储数组数据类型，允许存储多个值的集合。
- **Roaringbitmap**：用于存储位图数据，主要用于图像处理和表示。
- **BLOB**（Binary Large Object）：用于存储二进制数据，如图像或文件，最大长度为 65,535 字节。
- **GEOMETRY**：用于存储地理空间数据，支持空间分析和操作。
- **JSON**：用于存储 JSON 格式的数据，便于处理结构化数据。
- **LONGTEXT**：用于存储大量的文本数据，最大长度为 536,870,910 字节。
- **LONGBLOB**：用于存储大量的二进制数据，最大长度为 536,870,910 字节。
- **MEDIUMBLOB**：用于存储中等量的二进制数据，最大长度为 16,777,215 字节。
- **MEDIUMTEXT**：用于存储中等量的文本数据，最大长度为 16,777,215 字节。
- **TEXT**：用于存储较少量的文本数据，最大长度为 65,535 字节。

## LOB meta 表可观测性

外联（OUTROW）存储场景下，LOB 实际数据存放在 **LOB 辅助表（LOB meta 表）** 中；主表 LOB 列中保存磁盘定位符（disk LOB locator），其中带有 **LOB ID**，LOB meta 表以 LOB ID 为主键关联多行元数据。问题定位时，经常需要确认 LOB meta 表上是否存在数据、是否存在指定 LOB ID 等，因此需要提供受控的只读观测能力。

LOB meta 表属于内部实现对象，默认与索引表类似，**不开放**通过表名直接 `SELECT` 访问。在补齐「表名到内部表 ID」等元数据映射后，可通过 **租户级配置项**（行为类似 [ob_enable_index_direct_select](../../../../../../800.configuration-items-and-system-variables/200.system-variable/300.global-system-variable/6900.ob_enable_index_direct_select-global.md)）显式开启；开启后，方允许对 LOB meta 表发起只读查询，便于排查是否存在指定 LOB ID、行数是否与预期一致等。

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>具体配置项名称、取值及与版本的对应关系，以当前版本的配置项 / 系统变量文档为准。</p>
</main>

## LOB 一致性校验

外联存储时，主表与 LOB meta 表通过 **LOB ID** 关联：主表定位符中的 LOB ID 集合，应与 LOB meta 表中出现的 LOB ID 集合一致。若出现「主表有而 meta 无」「meta 有而主表无」等不一致，可能导致读取异常或空间无法回收等问题。

本能力在实现上包含 **一致性校验** 与内部维护等子能力。**面向使用与运维文档的说明以一致性校验为主**：通过 **LOB 校验任务（Lob Task）** 扫描主表收集 LOB ID 集合，并与 LOB meta 表扫描得到的 LOB ID 集合做对比，输出是否一致及差异信息，便于在低峰期巡检或在故障排查时确认数据关系是否正常。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>校验会扫描主表与 LOB meta 相关数据，对 I/O 与 CPU 有一定开销，请在业务低峰期执行，并结合下文为任务配置合适的资源组。</p>
</main>

### 触发方式

* **定时触发**：可按运维策略配置周期性校验（具体调度方式与参数以产品版本说明为准）。
* **主动触发**：支持由管理员发起的一次性校验任务，语义上类似通过 `ALTER SYSTEM` 等系统命令主动触发合并（Major Freeze）的方式；**具体语句名称、参数及权限要求请参考对应版本的 SQL 参考或运维手册。**

任务提交后，可通过产品提供的 **任务 / 视图**（若版本已开放）查询进度与结果摘要。

### 与资源组配合使用

为避免校验任务与在线业务争抢 CPU、IOPS，建议在租户内为执行校验的会话或用户配置 **资源隔离**：

1. 了解资源组、资源管理计划等概念，参见 [资源隔离概述](../../../../../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/100.resource-isolation-overview.md)。
2. 在 MySQL 租户内创建专用资源组，并在资源管理计划中为其分配 **CPU_WEIGHT / MAX_CPU**、**MIN_IOPS / MAX_IOPS** 等限额，使校验任务占用可控的份额；操作步骤参见 [配置租户内资源隔离](../../../../../../../600.manage/200.tenant-management/600.common-tenant-operations/300.resource-isolation/300.resource-isolation-of-mysql-mode/200.resource-isolation-at-user-level-of-mysql-mode.md)。
3. 将用于发起 LOB 一致性校验的数据库用户映射到上述资源组（例如通过 `DBMS_RESOURCE_MANAGER` 的会话/用户级映射能力，具体以当前版本支持的映射方式为准），再在该用户会话中提交校验任务。
