# 索引类型选择

OceanBase 数据库提供了多种向量索引算法，用户可以依据使用场景的不同选择合适的索引。

## HNSW 还是 IVF？

OceanBase 的向量索引分为两大类：

* 基于图的 HNSW 系列索引：HNSW、HNSW_SQ、HNSW_BQ。
* 基于磁盘的 IVF 系列索引：IVF、IVF_PQ、IVF_SQ（实验特性）。

这两种索引类型各有侧重。HNSW 系列索引通常提供更高的查询性能，但需要占用更多常驻内存；而 IVF 系列索引在缓存充足时性能表现良好，且能够不依赖常驻内存运行。关于内存用量的估算方法，您可以参考[向量索引内存管理](../200.ob-vector-index-memory-management.md)。然而，选择 HNSW 还是 IVF 并非仅基于内存考量，业务场景、数据规模、性能指标以及资源约束等多个维度都需综合评估，下文将详细对比其核心差异并提供选择建议。

### 核心差异对比

| 对比维度 | HNSW 系列 | IVF 系列 |
|---------|-----------|----------|
| 存储方式 | 基于内存的图结构索引 | 基于磁盘的索引 |
| 内存占用 | 需要完整载入内存，内存占用高 | 可不占用常驻内存，内存占用低 |
| 查询性能（QPS） | 极高，毫秒级响应 | 较高，在缓存充足时接近 HNSW |
| 召回率 | 高，可达 99% | 较高，略低于 HNSW，可通过参数调优 |
| 构建速度 | 较慢，需要构建图结构 | 较快，基于聚类算法 |
| 适用数据量 | 百万级到亿级 | 千万级到百亿级 | // TODO：微信文章里没有区分开，都是百万-》亿级
| 成本 | 内存成本高 | 存储成本低，适合大规模数据 |
| 实时性 | 支持实时 DML 操作 | 支持实时 DML 操作 |

### 选择建议

#### 选择 HNSW 系列的场景

* **高性能要求**：需要毫秒级响应，QPS 要求高（如实时推荐、在线搜索）。
* **数据量适中**：百万级到千万级数据，内存资源充足。
* **高召回率要求**：对搜索准确性要求极高，需要 99% 以上的召回率。
* **实时更新频繁**：需要频繁进行 DML 操作，要求实时生效。
* **内存资源充足**：有足够的内存预算，可以接受较高的内存成本。

#### 选择 IVF 系列的场景

* **大规模数据**：数据量达到千万级甚至百亿级，内存无法容纳全部索引。
* **成本敏感**：需要控制内存成本，优先考虑存储成本。
* **数据增长快**：数据量持续快速增长，需要可扩展的解决方案。
* **查询频率适中**：QPS 要求不是特别高，可以接受略慢的响应时间。
* **只增不删场景**：数据主要是追加写入，较少删除和更新。

### 性能与资源权衡

#### 内存资源考虑

* **HNSW 系列**：
  * 内存占用 = 向量数据大小 × 索引开销系数（通常 1.5-3 倍）
  * 例如：100 万条 768 维向量（约 2.3 GB），HNSW 索引约需 4-7 GB 内存
  * HNSW_SQ 可降低到 1.5-2.5 GB，HNSW_BQ 可降低到 0.1-0.2 GB

* **IVF 系列**：
  * 内存占用 = 缓存大小（可配置，通常为索引大小的 10-30%）
  * 极端情况下可以不占用常驻内存，完全基于磁盘查询
  * 例如：1 亿条 768 维向量（约 230 GB），IVF 索引可仅占用 20-70 GB 内存（缓存模式）

#### 查询性能对比

* **HNSW 系列**：
  * QPS：通常可达数千到数万 QPS（取决于数据量和参数配置）
  * 延迟：1-10 毫秒（p99）
  * 召回率：99%+（通过调整 `ef_search` 参数）

* **IVF 系列**：
  * QPS：数百到数千 QPS（取决于缓存命中率和参数配置）
  * 延迟：5-50 毫秒（p99，缓存命中时接近 HNSW）
  * 召回率：95-99%（通过调整 `nprobes` 参数）

### 决策流程图

```
开始选择索引
    │
    ├─ 数据量 < 1000 万 且 内存充足？
    │   ├─ 是 → 选择 HNSW 系列
    │   │       ├─ 追求最高召回率 → HNSW
    │   │       ├─ 追求最高性能 → HNSW_SQ
    │   │       └─ 追求最佳性价比 → HNSW_BQ
    │   │
    │   └─ 否 → 继续判断
    │
    ├─ 数据量 > 1000 万 或 内存受限？
    │   ├─ 是 → 选择 IVF 系列
    │   │       ├─ 追求更高召回率 → IVF
    │   │       └─ 追求更高性能 → IVF_PQ
    │   │
    │   └─ 否 → 根据 QPS 和成本选择
    │
    └─ QPS 要求 > 5000？
        ├─ 是 → 优先考虑 HNSW 系列
        └─ 否 → 可考虑 IVF 系列（成本更低）
```

### 混合使用策略

在实际生产环境中，可以考虑混合使用策略：

* **热数据 + 冷数据**：对热点数据使用 HNSW 索引保证高性能，对冷数据使用 IVF 索引降低成本。
* **分区表策略**：使用分区表，不同分区根据数据特征选择不同的索引类型。
* **渐进式迁移**：初期使用 HNSW 保证性能，随着数据量增长逐步迁移到 IVF。

### 总结

* **优先选择 HNSW**：如果数据量在千万级以内，内存充足，且对性能要求高。
* **优先选择 IVF**：如果数据量超过千万级，内存受限，或成本敏感。
* **具体选择**：根据实际的数据规模、性能要求、成本预算和业务场景进行权衡。

## HNSW 系列用于高性能场景

内存图索引的性能会明显高于磁盘索引，但由于需要常驻内存，因此内存成本高，且需要数据总量动态平衡，如果数据明显增多则需要扩容：

* 百万级数据量：通常要求最高召回率和高性能，使用 HNSW 索引。
* 百万～千万数据量：通常要求高召回和高性能，使用 HNSW_SQ 索引，占用内存约为 HNSW 索引的 1/4 ～ 1/3。
* 千万～亿数据量：通常要求高召回和较高性能，使用 HNSW_BQ 索引，占用内存约为 HNSW 索引的 1/30。

这几种索引中 HNSW_SQ 的性能最高，HNSW 的召回率最高，但在标准数据集下都可以通过调节参数获得 99% 的召回率。召回率是稠密索引进行最近邻搜索的准确率，例如在查询 10 个最近邻时，若能稳定返回 9 个正确结果，则召回率为 90%。

<main id="notice" type='notice'>
    <h4>注意</h4>
    <p>HNSW_BQ 是高压缩率的量化算法，在低维向量下的召回率上限可能较低。为避免性能损失，建议 HNSW_BQ 使用在 512 维及以上的向量上。</p>
</main>

### 参数建议

同系列的索引在不同的数据量下，推荐的索引构建和查询参数是不相同的。本节给出百万和千万数据量下，768 维度向量，HNSW/HNSW_SQ/HNSW_BQ 索引的建议配置供参考。对于亿级别的向量数据，请参考本文后续章节选用 IVF_PQ 索引，或分区表下的 HNSW_BQ 索引。

<main id="notice" type='notice'>
    <h4>注意</h4>
    <p>对于数据量预计会增长的场景，建议根据最终数据量进行参数设置。</p>
</main>

| 场景 | 索引类型 | 参数建议 |
|---|---|---|
| 最高召回<br>（内存占用最多） | HNSW | 百万数据量：m = 16，ef_construction = 200，ef_search = 100，其他参数默认 |
| 最高性能<br>（内存占用较少） | HNSW_SQ | 百万数据量：m = 16，ef_construction = 200，ef_search = 100，其他参数默认<br>千万数据量：m = 32，ef_construction = 400，ef_search = 350，其他参数默认 |
| 最佳性价比<br>（内存占用少，性能好） | HNSW_BQ | 百万数据量：m = 16，ef_construction = 200，ef_search = 100，其他参数默认<br>千万数据量：m = 32，ef_construction = 400，ef_search = 1000，refine_k = 10，其他参数默认<br>亿级数据量：使用分区表，m = 32，ef_construction = 400，ef_search = 1000，refine_k = 10，其他参数默认 |

### 百万级数据量详细说明

以 100 万条 768 维向量数据为例（使用上表中的构建参数），补充说明内存占用和召回率调优：

内存占用：

| 索引类型 | 建议租户内存 | 说明 |
|---------|------------|------|
| HNSW | 15 GB | 向量索引内存大小建议值为 7.3 GB。从 V4.3.5 BP3 版本开始，租户内存大于 8 GB 时，向量索引默认最多使用租户内存的 50%；租户内存小于等于 8 GB 时，向量索引默认最多使用租户内存的 40%。因此大约需要 15 GB 的租户内存。 |
| HNSW_SQ | 6 GB | 向量索引内存大小建议值为 2.1 GB。 |
| HNSW_BQ | 6 GB | HNSW_BQ 索引在构建过程中需要使用高精度的向量。从 V.4.1 版本开始，HNSW_BQ 默认使用 HNSW_SQ 作为索引构建中的缓存，因此对于非分区表，HNSW_BQ 所需要的内存和 HNSW_SQ 相同。构建完成后，HNSW_BQ 索引只占用约 405 MB 的内存。<br/>在分区表场景下，OceanBase 会依据租户内存大小控制并发构建的分区数，因此对于 HNSW_BQ 索引，可以配置租户内存为 HNSW_BQ 索引查询时占用量 + 单分区 SQ 索引占用量。 |

召回率调优：

通过调整 `ef_search` 和 `refine_k`（仅 HNSW_BQ）参数，可以通过更多的向量计算来提高召回率，但相应的会降低查询性能。在不同 TopN 下可将参数设置为下表中的建议值，如果需要进一步提升召回率，则可将参数值设置得更大一些。

<main id="notice" type='notice'>
    <h4>注意</h4>
    <p>召回率和数据特征有直接关系，下表给出的是 768 维标准数据集下，召回率达到 0.95 左右的建议值。</p>
</main>

| TopN | ef_search | refine_k（仅 HNSW_BQ） |
|------|-----------|----------------------|
| Top10 | 64 | 4 |
| Top100 | 240 | 4 |
| Top1000 | 1500 | 4 |

极限召回率说明：

几种索引算法的极限召回率不同。在本节设置建议的构建参数下，将 `ef_search` 设置为 1000 时，QPS 会降低到 0.95 召回率下的 1/3，但只有 HNSW 能达到 0.99 以上的召回率。HNSW_BQ 索引可以通过进一步增加 `refine_k` 来提高召回率，但性能也会进一步下降。

极限召回率参考值（ef_search = 1000）：
* HNSW 索引：召回率 0.991
* HNSW_SQ 索引：召回率 0.9786
* HNSW_BQ 索引：召回率 0.9897（ef_search = 1000，refine_k = 10）

## IVF 系列用于高容量场景

磁盘索引用于高容量场景，可以做到完全不依赖常驻内存，对**数据量非常大**或者**只增不删**的场景，建议使用磁盘索引：

* IVF 索引：构建会相对更快，但构建过程中的内存占用也相对更高，相比 IVF_PQ 索引查询会慢一些，召回会更高。
* IVF_PQ 索引：构建会慢一些，构建过程中的内存占用也相对低，但比 IVF 的查询性能更高，召回率略低。

<main id="notice" type='notice'>
    <h4>注意</h4>
    <p>IVF_PQ 是高压缩率的量化算法，在低维向量下的召回率上限可能较低。为避免性能损失，建议 IVF_PQ 使用在 128 维及以上的向量上。</p>
</main>

### 参数建议

| 场景 | 索引类型 | 参数建议 |
|---|---|---|
| 低成本<br>（内存占用极少） | IVF_PQ | 百万数据量：nlist=1000, m=向量维度/2，nprobes = 20<br>千万数据量：nlist=3000, m=向量维度 / 2，nprobes = 20<br>亿级数据量：使用分区表，nlist=3000, m=向量维度 / 2，nprobes = 20 |
