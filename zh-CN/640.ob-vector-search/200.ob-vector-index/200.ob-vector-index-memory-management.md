# 向量索引内存管理

本文档介绍如何估算和管理 OceanBase 数据库中**所有类型向量索引**的内存占用。

## 配置向量索引内存

OceanBase 向量搜索通过设置 [ob_vector_memory_limit_percentage](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6150.ob_vector_memory_limit_percentage.md) 配置向量索引内存：

该参数默认值为 `0` ，表示自适应模式，即系统自动调整租户中的向量索引数据的内存占用比例，无需手动调整：
  * 租户实际内存为 8GB 及以下时，该值自适应为 `40`。
  * 租户实际内存为 8GB 以上时，该值自适应为 `50`。

## 索引内存估算与实际占用查询

支持通过 `DBMS_VECTOR` 系统包进行索引内存估算：

* 未建表时，通过 [INDEX_VECTOR_MEMORY_ADVISOR](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/500.index-vector-memory-advisor-mysql.md) 过程估算索引内存。
* 已建表且插入数据时，通过 [INDEX_VECTOR_MEMORY_ESTIMATE](../../700.reference/600.pl-reference/200.pl-mysql/1000.pl-system-package-mysql/17850.dbms-vector-mysql/400.index-vector-memory-estimate-mysql.md) 过程分析索引内存。

向量索引内存估算会返回两项信息：创建向量索引所需的最少内存配置，以及 HNSW_SQ 和 IVF 索引创建完成后的实际内存占用情况。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>对于内存稀疏索引，<code>IDX_TYPE</code> 参数必须指定为 <code>SINDI</code>（不区分大小写），否则内存估算将无法进行。</p>
</main>

实际占用内存的详细信息可以通过视图 [GV$OB_VECTOR_MEMORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/4650.gv-ob_vector_memory-of-mysql-mode.md) 或 [V$OB_VECTOR_MEMORY](../../700.reference/700.system-views/400.system-view-of-mysql-mode/300.performance-view-of-mysql-mode/35350.v-ob_vector_memory-of-mysql-mode.md) 获取。

## 索引重建内存优化

对于分区表的向量索引重建操作，我们还提供了 `vector_index_memory_saving_mode` 配置项来控制索引重建的内存占用。开启此模式可以降低分区表向量索引重建（rebuild）过程中的内存消耗。通常，向量索引重建需要消耗相当于索引两倍的内存。开启省内存模式后，系统会在分区表单个分区构建完成后，通过暂时删除该分区的内存索引来释放内存，从而有效降低重建操作所需的总内存。语法和示例请参见[vector_index_memory_saving_mode](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/8240.vector_index_memory_saving_mode.md)。

## HNSW 系列索引增量段（Incremental Segment）数据持久化与合并控制

向量索引在分区内以 **段（Segment）**（为分区中一部分向量构建的内存向量索引）为单位组织。其中，**Active Segment** 为 DML 写入的向量构建的内存索引段（不做量化）；冻结后变为 **Frozen Segment**，不再写入新向量；落盘后成为 **Persistence Incremental Segment**（持久化后仍占内存，需等后台合并量化后才会释放）。Active Segment、Frozen Segment 和 Persistence Incremental Segment 均需携带 **Valid Bitmap** 用于过滤未提交或已删除的向量，统称为 **Incremental Segment（增量段）**。与之相对，**Baseline Segment（基线段）** 不需携带 Valid Bitmap，当前每个分区仅有一个。

针对单个分区，可通过以下配置项控制 **Active Segment** 的冻结落盘时机，以及 **Incremental Segment** 与 **Baseline Segment** 的 **Segment Merge（段合并）** 时机：

### ob_vector_index_active_segment_max_size

`ob_vector_index_active_segment_max_size` 用于控制 HNSW 系列索引单分区内 **Active Segment** 的最大内存占用量。当 Active Segment 内存超过该阈值时，系统会强制触发**冻结**：该段变为 Frozen Segment 并持久化落盘，落盘后对应数据成为 Persistence Incremental Segment。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>Frozen Segment 落盘为 Persistence Incremental Segment 后并不会立即释放内存，需等后台合并任务对其量化并合并进 Baseline Segment 后，内存才会降低。</p>
</main>

语法和示例请参见 [ob_vector_index_active_segment_max_size](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6145.ob_vector_index_active_segment_max_size.md)。

### ob_vector_index_merge_trigger_percentage

`ob_vector_index_merge_trigger_percentage` 用于控制增量段（Incremental Segment）的向量内存占整个分区向量索引内存的最大比例。当增量段占比超过该值时，系统将自动触发段合并（Segment Merge）操作，将 Incremental Segment 与 Baseline Segment 合并。

两个配置项的区别：

| 配置项 | 控制对象 | 触发操作 |
|--------|----------|----------|
| ob_vector_index_active_segment_max_size | Active Segment 内存（绝对值） | 冻结并落盘，变为 Frozen Segment / Persistence Incremental Segment |
| ob_vector_index_merge_trigger_percentage | Incremental Segment 占分区索引的比例 | Segment Merge，与 Baseline Segment 合并 |

<main id="notice" type='explain'>
  <h4>说明</h4>
  <p>上述配置分别作用于<b>单段写入与落盘</b>与<b>增量段与基线的合并</b>两条链路，二者配合可平衡写入性能、查询性能与内存占用。如需深入理解可参考原理文档。</p>
</main>

语法与示例请参见 [ob_vector_index_merge_trigger_percentage](../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/6147.ob_vector_index_merge_trigger_percentage.md)。
