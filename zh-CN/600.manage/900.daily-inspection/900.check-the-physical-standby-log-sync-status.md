# 检查主备租户的日志同步与回放状态

本文主要介绍在日常维护中如何对主备租户的日志同步与回放状态进行检查。

## 步骤一：检查保护模式和租户级位点（SCN）

在 OceanBase 数据库 V4.4.2 版本中，从 V4.4.2 BP1 版本开始支持最大保护和最大可用模式。对于主备租户来说，每个租户的保护模式和保护级别均保持独立，只有强同步的备租户，其保护模式和保护级别与主租户一致，其它异步同步的备租户的保护模式和保护级别一直维持在 `MAXIMUM PERFORMANCE`。

可以通过 `DBA_OB_TENANTS` 视图来查询租户的保护模式。此外，`DBA_OB_TENANTS` 视图中的租户级 SCN（`SYNC_SCN`、`REPLAYABLE_SCN`、`READABLE_SCN` 等字段）提供了租户数据同步和可用性状态的关键指标，是运维人员监控主备同步进度、诊断同步问题的重要依据。

可以在主租户上检查保护模式和租户级位点（SCN）。

* 主租户所在集群的 `sys` 租户下，执行以下语句。

  ```shell
  obclient(root@sys)[(none)]> SELECT tenant_id, tenant_name, tenant_role, protection_mode, protection_level,
        sync_scn, replayable_scn, readable_scn
        FROM oceanbase.DBA_OB_TENANTS
        WHERE tenant_type = 'USER';
  ```

* 主租户下，执行以下语句。

  MySQL 模式：

  ```shell
  obclient(root@mysql001)[(none)]> SELECT tenant_role, protection_mode, protection_level,
        sync_scn, replayable_scn, readable_scn
        FROM oceanbase.DBA_OB_TENANTS;
  ```

  Oracle 模式：

  ```shell
  obclient(sys@oracle001)[SYS]> SELECT tenant_role, protection_mode, protection_level,
        sync_scn, replayable_scn, readable_scn
        FROM SYS.DBA_OB_TENANTS;
  ```

其中：

* `protection_mode`：当前租户的保护模式。取值包括 `MAXIMUM PERFORMANCE`（最大性能）、`MAXIMUM PROTECTION`（最大保护）、`MAXIMUM AVAILABILITY`（最大可用）等。

* `protection_level`：当前租户的保护级别。取值包括 `MAXIMUM PERFORMANCE`（最大性能）、`MAXIMUM PROTECTION`（最大保护）、`MAXIMUM AVAILABILITY`（最大可用）、`RESYNCHRONIZATION`（追赶日志状态）等。

* `sync_scn`：全局同步位点。租户下所有日志流中最小的 `sync_scn`，即所有 Leader 副本的 `end_scn`（日志流达成多数派的最后一条日志的时间戳）中的最小值。表示该位点之前的所有日志均已同步到了备租户。

* `replayable_scn`：全局可回放位点。物理备库场景下，表示该位点之前的所有日志在备租户上均可回放。

* `readable_scn`：全局可读位点。租户下所有日志流中最小的 `readable_scn`，即所有日志流多数派已回放位点中的最小值。表示该位点之前的所有数据在备租户上均可读取。

## 步骤二：检查各日志流的同步模式

日志流的同步模式决定了主备租户之间日志的同步方式。强同步模式下，由主租户向备租户推送日志；异步同步模式下，由备租户向主租户拉取日志。

在主租户上通过 `GV$OB_LOG_STAT` 视图检查各日志流的同步模式。

* 主租户所在集群的 `sys` 租户下，执行以下语句：

  ```shell
  obclient(root@sys)[(none)]> SELECT tenant_id, ls_id, role, sync_mode
         FROM oceanbase.GV$OB_LOG_STAT
         WHERE tenant_id = xxx AND role = 'LEADER';
  ```

* 主租户下，执行以下语句。

  MySQL 模式：

  ```shell
  obclient(root@mysql001)[(none)]> SELECT ls_id, role, sync_mode
         FROM oceanbase.GV$OB_LOG_STAT
         WHERE role = 'LEADER';
  ```

  Oracle 模式：

  ```shell
  obclient(sys@oracle001)[SYS]> SELECT ls_id, role, sync_mode
         FROM SYS.GV$OB_LOG_STAT
         WHERE role = 'LEADER';
  ```

其中，`sync_mode` 的取值如下：

* `SYNC`：表示强同步模式
* `ASYNC`：表示异步同步模式
* `PRE_ASYNC`：表示正在从强同步模式切换为异步同步模式

## 步骤三：检查日志流的传输状态（仅适用于强同步模式下）

当主租户处于强同步模式下时（即 `GV$OB_LOG_STAT` 视图中 `sync_mode = SYNC`），在主租户上通过 `GV$OB_LS_LOG_TRANSPORT_STAT` 视图检查主租户的每个日志流向备租户推送日志的传输状态。

<main id="notice" type='notice'>
<h4>注意</h4>
<p>对于 V4.4.2 版本，从 V4.4.2 BP2 版本开始支持 <code>GV$OB_LS_LOG_TRANSPORT_STAT</code> 视图。</p>
</main>

* 主租户所在集群的 `sys` 租户下，执行以下语句。

  ```shell
  obclient(root@sys)[(none)]> SELECT tenant_id, ls_id,
       end_scn, last_sent_scn, standby_end_scn,
       standby_addr
  FROM oceanbase.GV$OB_LS_LOG_TRANSPORT_STAT
  WHERE tenant_id = xxx AND role = 'LEADER' AND enabled = 1;
  ```

* 主租户下，执行以下语句。

  MySQL 模式：

  ```shell
  obclient(root@mysql001)[(none)]> SELECT ls_id,
       end_scn, last_sent_scn, standby_end_scn,
       standby_addr
  FROM oceanbase.GV$OB_LS_LOG_TRANSPORT_STAT
  WHERE role = 'LEADER' AND enabled = 1;
  ```

  Oracle 模式：

  ```shell
  obclient(sys@oracle001)[SYS]> SELECT ls_id,
       end_scn, last_sent_scn, standby_end_scn,
       standby_addr
  FROM SYS.GV$OB_LS_LOG_TRANSPORT_STAT
  WHERE role = 'LEADER' AND enabled = 1;
  ```

其中：

* `end_scn`：表示主租户日志流当前的最大 SCN。

* `last_sent_scn`：表示主租户最近一次发送给备租户的日志的 SCN。

* `standby_end_scn`：表示备租户当前已接收并确认的日志的最大 SCN。

* `standby_addr`：表示备租户上该日志流 Leader 的地址信息。

## 步骤四：检查日志的接收状态

主备同步过程中，在备租户上通过查询 `GV$OB_LS_LOG_RESTORE_STATUS` 视图检查备租户的日志接收是否正常。

* 备租户所在集群的 `sys` 租户下，执行以下语句。

  ```shell
  obclient(root@sys)[(none)]> SELECT tenant_id, ls_id, sync_lsn, sync_scn, sync_status, err_code
  FROM oceanbase.V$OB_LS_LOG_RESTORE_STATUS WHERE tenant_id = xxx;
  ```

* 备租户下，执行以下语句。

  MySQL 模式：

  ```shell
  obclient(root@mysql001)[(none)]> SELECT ls_id, sync_lsn, sync_scn, sync_status, err_code
  FROM oceanbase.V$OB_LS_LOG_RESTORE_STATUS;
  ```

  Oracle 模式：

  ```shell
  obclient(sys@oracle001)[SYS]> SELECT ls_id, sync_lsn, sync_scn, sync_status, err_code
  FROM SYS.V$OB_LS_LOG_RESTORE_STATUS;
  ```

其中：

* `sync_lsn`：备库最大连续多数派的位点/最大可消费位点（LSN）。表示备租户上该日志流已经连续接收并确认的日志的物理位置。

* `sync_scn`：备库最大连续多数派的位点/最大可消费位点（SCN）。与 `sync_lsn` 对应，表示备租户上该日志流已经连续接收并确认的日志的逻辑时间点。

* `sync_status`：日志流的恢复状态。

* `err_code`：错误码信息。

## 步骤五：检查日志的回放状态

主备同步过程中，在备租户上通过查询 `GV$OB_LS_LOG_REPLAY_STAT` 视图检查备租户的日志回放是否正常。

<main id="notice" type='notice'>
<h4>注意</h4>
<p>对于 V4.4.2 版本，从 V4.4.2 BP2 版本开始支持 <code>GV$OB_LS_LOG_REPLAY_STAT</code> 视图。</p>
</main>

* 备租户所在集群的 `sys` 租户下，执行以下语句。

  ```shell
  obclient(root@sys)[(none)]> SELECT tenant_id, ls_id,
       end_lsn - unsubmitted_lsn AS submit_lag,
       pending_cnt
  FROM oceanbase.GV$OB_LS_LOG_REPLAY_STAT
  WHERE tenant_id = xxx AND role = 'FOLLOWER';
  ```

* 备租户下，执行以下语句。

  MySQL 模式：

  ```shell
  obclient(root@mysql001)[(none)]> SELECT ls_id,
       end_lsn - unsubmitted_lsn AS submit_lag,
       pending_cnt
  FROM oceanbase.GV$OB_LS_LOG_REPLAY_STAT
  WHERE role = 'FOLLOWER';
  ```

  Oracle 模式：

  ```shell
  obclient(sys@oracle001)[SYS]> SELECT ls_id,
       end_lsn - unsubmitted_lsn AS submit_lag,
       pending_cnt
  FROM SYS.GV$OB_LS_LOG_REPLAY_STAT
  WHERE role = 'FOLLOWER';
  ```

其中：

* `end_lsn`：Palf 已持久化的位点，表示该位点之前的所有日志都已经完成回放处理。

* `unsubmitted_lsn`：表示下一条待提交到回放队列的日志的 LSN，是日志回放待处理列队的起始位置。

* `submit_lag`：`end_lsn - unsubmitted_lsn` 的值，表示待提交至回放队列的日志段长度。如果差值长时间无变化，则可能表示回放卡住。

* `pending_cnt`：等待回放的任务数量，反映了回放处理的积压情况。
