## 物理备库日志同步与回放异常诊断

物理备库场景下，受网络、资源、系统负载、环境等多方面因素的影响，主备租户（主备库）的日志同步或回放可能会出现异常。

本文档提供了诊断流程和关键系统视图，帮忙快速定位和解决异常。

## 诊断链路

在 OceanBase 数据库中，主备租户之间的日志流转主要分为三个阶段：日志传输 -> 日志接收 -> 日志回放。系统提供了以下视图来监控各个阶段主备租户的同步状态。

| 视图名                                                        |   描述                                  |
|--------------------------------------------------------------|-----------------------------------------|
| `GV$OB_LS_LOG_TRANSPORT_STAT` \/ `V$OB_LS_LOG_TRANSPORT_STAT`| 展示强同步模式下主租户的每个日志流向备租户推送日志的传输状态。 |
| `V$OB_LS_LOG_RESTORE_STATUS`                                 | 展示租户每个日志流的日志恢复状态。 |
| `GV$OB_LS_LOG_REPLAY_STAT` \/ `V$OB_LS_LOG_REPLAY_STAT`      | 展示租户上每个日志流的日志回放进度。 |

当主备租户之间的日志同步出现异常时，可以按照以下链路进行诊断：

1. 强同步模式下，在主租户上，查询视图 `GV$OB_LS_LOG_TRANSPORT_STAT` / `V$OB_LS_LOG_TRANSPORT_STAT`，检查日志是否正常发送，以及备租户是否确认。

   <main id="notice" type='notice'>
   <h4>注意</h4>
   <p>由于日志传输服务仅在强同步模式下工作，仅当主租户为强同步模式时，才可以通过该方式查看主租户日志的传输状态。异步同步模式下，由备租户向主租户拉取日志。</p>
   </main>

2. 在备租户上，查询视图 `V$OB_LS_LOG_RESTORE_STATUS`，检查日志的拉取或接收是否正常。

3. 在备租户上，查询视图 `GV$OB_LS_LOG_REPLAY_STAT` / `V$OB_LS_LOG_REPLAY_STAT`，检查日志回放是否正常，有无卡住、回放慢的情况。

## 诊断流程

### 日志传输阶段

<main id="notice" type='notice'>
<h4>注意</h4>
<p>由于日志传输服务仅在强同步模式下工作，仅当主租户为强同步模式时，才可以通过以下方式查看主租户日志的传输状态。异步同步模式下，由备租户向主租户拉取日志。</p>
</main>

强同步模式下，在日志传输阶段，主要通过视图 `GV$OB_LS_LOG_TRANSPORT_STAT` / `V$OB_LS_LOG_TRANSPORT_STAT` 中的以下字段来确认日志的传输状态：

* `end_lsn`：表示 Palf 上实际的位点。主库会从 Palf 上读取日志，然后发送给备库。

* `last_sent_lsn`：表示主库上一次读取的最大位点。

* `standby_end_lsn`：表示备库持久化的位点。备库在接收到主库发送的日志之后，会向备库的 Palf 持久化日志。

方法如下：

1. 查看主租户所有节点的日志流传输状态。

   * 主租户所在集群的 `sys` 租户下，执行以下语句。

     ```shell
     obclient(root@sys)[(none)]> SELECT tenant_id, svr_ip, svr_port, ls_id, role, enabled,
                   end_lsn, last_sent_lsn, standby_end_lsn,
                   standby_addr
               FROM oceanbase.GV$OB_LS_LOG_TRANSPORT_STAT
               WHERE tenant_id= xxx AND role = 'LEADER';
     ```

   * 主租户下，执行以下语句。

     :::tab
     tab  MySQL 模式

     语句如下：

     ```shell
     obclient(root@mysql001)[(none)]> SELECT svr_ip, svr_port, ls_id, role, enabled,
                   end_lsn, last_sent_lsn, standby_end_lsn,
                   standby_addr
               FROM oceanbase.GV$OB_LS_LOG_TRANSPORT_STAT
               WHERE role = 'LEADER';
     ```

     tab Oracle 模式

     语句如下：

     ```shell
     obclient(sys@oracle001)[(none)]> SELECT svr_ip, svr_port, ls_id, role, enabled,
                   end_lsn, last_sent_lsn, standby_end_lsn,
                   standby_addr
               FROM SYS.GV$OB_LS_LOG_TRANSPORT_STAT
               WHERE role = 'LEADER';
     ```

     :::

2. 查看传输延迟情况。

   * 主租户所在集群的 `sys` 租户下，执行以下语句。

     ```shell
     obclient(root@sys)[(none)]> SELECT tenant_id, ls_id,
                end_lsn - last_sent_lsn AS read_lag,
                last_sent_lsn - standby_end_lsn AS network_lag
            FROM oceanbase.GV$OB_LS_LOG_TRANSPORT_STAT
            WHERE tenant_id = xxx AND role = 'LEADER' AND enabled = 1;
     ```

   * 主租户下，执行以下语句。

     :::tab
     tab  MySQL 模式

     语句如下：

     ```shell
     obclient(root@mysql001)[(none)]> SELECT ls_id,
                end_lsn - last_sent_lsn AS read_lag,
                last_sent_lsn - standby_end_lsn AS network_lag
            FROM oceanbase.GV$OB_LS_LOG_TRANSPORT_STAT
            WHERE role = 'LEADER' AND enabled = 1;
     ```

     tab Oracle 模式

     语句如下：

     ```shell
     obclient(sys@oracle001)[SYS]> SELECT ls_id,
                end_lsn - last_sent_lsn AS read_lag,
                last_sent_lsn - standby_end_lsn AS network_lag
            FROM SYS.GV$OB_LS_LOG_TRANSPORT_STAT
            WHERE role = 'LEADER' AND enabled = 1;
     ```

     :::

     其中：

     * `read_lag`：`end_lsn - last_sent_lsn` 的值，表示主租户向备租户发送日志的延迟量。

     * `network_lag`：`last_sent_lsn - standby_end_lsn` 的值，表示备租户接收日志的延迟量。

根据两次查询结果，参考下表进行问题诊断：

| 问题现象                       |  判断方法                                           | 可能原因                                |
|-------------------------------|----------------------------------------------------|-----------------------------------------|
| 事务提交延迟高                 | `STANDBY_END_LSN` 远小于 `END_LSN`                  | 强同步等待备库确认 |
| 读取延迟大                     | `END_LSN - LAST_SENT_LSN` 的值持续增大               | 主库 I/O 瓶颈或读取慢 |
| 网络或备库写入延迟大            | `LAST_SENT_LSN - STANDBY_END_LSN` 的值持续增大       | 网络拥塞或备库写盘慢 |
| 备库不可达                     |  `STANDBY_ADDR = '0.0.0.0:0' `                      |   备库无主或网络问题导致无法查询备库的日志流 Leader |

### 日志接收阶段

在日志接收阶段，无论租户是否处于强同步模式，均可以通过视图 `V$OB_LS_LOG_RESTORE_STATUS` 来确认日志流的日志接收情况。

方法如下：

* 备租户所在集群的 `sys` 租户下，执行以下语句。

  ```shell
  obclient(root@sys)[(none)]> SELECT tenant_id, ls_id, sync_lsn, sync_scn, sync_status, err_code
                 FROM oceanbase.V$OB_LS_LOG_RESTORE_STATUS WHERE tenant_id = xxx;
  ```

* 备租户下，执行以下语句。

  :::tab
  tab  MySQL 模式

  语句如下：

  ```shell
  obclient(root@mysql001)[(none)]> SELECT ls_id, sync_lsn, sync_scn, sync_status, err_code
                 FROM oceanbase.V$OB_LS_LOG_RESTORE_STATUS;
  ```

  tab Oracle 模式

  语句如下：

  ```shell
  obclient(sys@oracle001)[SYS]> SELECT ls_id, sync_lsn, sync_scn, sync_status, err_code
                 FROM SYS.V$OB_LS_LOG_RESTORE_STATUS;
  ```

  :::

其中：

* `sync_scn`：表示该日志流的同步位点。

* `sync_status`：表示该日志流同步状态，其中，`NORMAL` 表示该日志流的日志同步状态正常，如果为其他状态则表示异常。日志同步状态及其含义如下表所示。

  | 日志同步状态            | 诊断结果                                                                              |
  |------------------------|--------------------------------------------------------------------------------------|
  | NORMAL                 | 正常同步中                                                                            |
  | SOURCE HAS A GAP       | 备租户与源端日志有 gap，主租户的日志未同步到备租户就已回收。需要重建备租户才能恢复。          |
  | STANDBY LOG NOT MATCH  | 恢复日志与备租户冲突，可能是出现双 PRIMARY 或者日志恢复源设置错误。需要为备租户重新设置日志恢复源。     |
  | CHECK USER OR PASSWORD | 复制账户用户名或密码不对，无法访问原主租户。需要为备租户重新设置日志恢复源。                            |
  | CHECK NETWORK          | 主租户不可达，需要检查网络是否异常                                                           |
  | RESTORE SUSPEND        | 备租户已经恢复到指定位点                                                                |
  | STANDBY NEED UPGRADE   | 备租户的 Binary 版本落后，需要升级                                                        |
  | PRIMARY TENANT DROPPED | 主租户已经被删除                                                                       |
  | FETCH LOG TIMEOUT      | 同步日志超时，需要排查网络健康状况或者调大备租户日志同步超时的租户级配置项 `standby_db_fetch_log_rpc_timeout`，有关 `standby_db_fetch_log_rpc_timeout` 的详细说明请参见 [standby_db_fetch_log_rpc_timeout](../../../700.reference/800.configuration-items-and-system-variables/100.system-configuration-items/400.tenant-level-configuration-items/7600.standby_db_fetch_log_rpc_timeout.md)  |
  | STANDBY IN THROTTLING  | 备租户写入限速中                                                                       |
  | STANDBY LOG DISK IS FULL | 备租户磁盘空间不足                                                                   |
  | WAIT LOG STREAM CREATED  | 等待备租户创建日志流完成                                                              |
  | NOT AVAILABLE          | 其他异常导致的日志同步不可用                                                            |

### 日志回放阶段

在日志回放阶段，主要通过视图 `GV$OB_LS_LOG_REPLAY_STAT` / `V$OB_LS_LOG_REPLAY_STAT` 中的以下字段来确认日志回放进度及回放延迟情况：

* `end_lsn`：表示 Palf 已持久化的位点。

* `unsubmitted_lsn`：表示下一条待提交到回放队列的日志的位点。

* `min_unreplayed_lsn`：表示回放队列中最小未回放的日志的位点。

* `pending_cnt`：等待回放的任务数量。

方法如下：

1. 查看租户所有节点的回放进度。

   * 备租户所在集群的 `sys` 租户下，执行以下语句。

     ```shell
     obclient(root@sys)[(none)]> SELECT tenant_id, svr_ip, svr_port, ls_id, role, enabled,
       end_lsn, unsubmitted_lsn, min_unreplayed_lsn,
       pending_cnt
     FROM oceanbase.GV$OB_LS_LOG_REPLAY_STAT WHERE tenant_id = xxx;
     ```

   * 备租户下，执行以下语句。

     :::tab
     tab  MySQL 模式

     语句如下：

     ```shell
     obclient(root@mysql001)[(none)]> SELECT svr_ip, svr_port, ls_id, role, enabled,
       end_lsn, unsubmitted_lsn, min_unreplayed_lsn,
       pending_cnt
     FROM oceanbase.GV$OB_LS_LOG_REPLAY_STAT;
     ```

     tab Oracle 模式

     语句如下：

     ```shell
     obclient(sys@oracle001)[SYS]> SELECT svr_ip, svr_port, ls_id, role, enabled,
       end_lsn, unsubmitted_lsn, min_unreplayed_lsn,
       pending_cnt
     FROM SYS.GV$OB_LS_LOG_REPLAY_STAT;
     ```

     :::

2. 查看回放延迟。

   * 备租户所在集群的 `sys` 租户下，执行以下语句。

     ```shell
     obclient(root@sys)[(none)]> SELECT tenant_id, ls_id,
       end_lsn - unsubmitted_lsn AS submit_lag,
       unsubmitted_lsn - min_unreplayed_lsn AS replay_lag,
       pending_cnt
      FROM oceanbase.GV$OB_LS_LOG_REPLAY_STAT
      WHERE tenant_id = xxx AND role = 'FOLLOWER';
     ```

   * 备租户下，执行以下语句。

     :::tab
     tab  MySQL 模式

     语句如下：

     ```shell
     obclient(root@mysql001)[(none)]> SELECT ls_id,
       end_lsn - unsubmitted_lsn AS submit_lag,
       unsubmitted_lsn - min_unreplayed_lsn AS replay_lag,
       pending_cnt
      FROM oceanbase.GV$OB_LS_LOG_REPLAY_STAT
      WHERE role = 'FOLLOWER';
     ```

     tab Oracle 模式

     语句如下：

     ```shell
     obclient(sys@oracle001)[SYS]> SELECT ls_id,
       end_lsn - unsubmitted_lsn AS submit_lag,
       unsubmitted_lsn - min_unreplayed_lsn AS replay_lag,
       pending_cnt
      FROM SYS.GV$OB_LS_LOG_REPLAY_STAT
      WHERE role = 'FOLLOWER';
     ```

     :::

根据两次查询结果，参考下表进行诊断：

| 问题现象                       |  判断方法                                           | 可能原因                                |
|-------------------------------|----------------------------------------------------|-----------------------------------------|
| 日志分发慢                     | `END_LSN - UNSUBMITTED_LSN` 持续增大                | submit 线程瓶颈或提交阶段阻塞            |
| 日志回放速度跟不上              |  `PENDING_CNT` 高，位点之间差值大                    | 回放线程不够，存在大事务或热点分区         |
