# CPU 占用不均问题排查

在数据库运维场景中，CPU 使用过高或使用不均是非常常见的。该场景产生的原因有以下两个大方向：

* 一是集群环境异常导致的 CPU 异常，例如网卡中断、磁盘故障、驱动故障、第三方服务（如安全服务）导致 OBServer 所在节点的部分 CPU 资源被其他进程抢占，导致监控上看到节点 CPU 异常。

* 二是 observer 进程自身占用了过多的 CPU 资源。例如 SQL 执行、远程执行、后台线程或 RPC 执行等。

当识别到 CPU 异常的场景，首先需要使用 Linux 系统监控，例如 tsar 等手段排除第一类问题。本文主要聚焦于对第二类问题的定位，即排查 observer 进程为什么占用了较多的 CPU 资源。

在进行 CPU 使用过高或使用不均问题排查前，先整体介绍下通用的排查思路以及常见的原因。

* 通过查看 ASH Report 的前后台负载，定位如下场景的根因：

  * 租户的 Leader 节点接收了更多的内部 RPC/inner SQL 请求，形成 CPU 热点。

    排查思路：查看 ASH Report 的后台负载，定位内部 RPC/inner SQL 是如何产生的，关联 SQL 维度进行分析。

  * PX 并行执行并发度设置不合适导致 CPU 爆。

    排查思路：在 ASH Report 中会看到大部分的数据库任务是 PX 并行执行相关，关联 SQL 维度进行分析，调整并行度。

  * 以转储合并为代表的一系列后台任务消耗了过多的 CPU 资源。

    排查思路：查看 ASH Report 的后台负载，定位内部 RPC/inner SQL 是如何产生的，关联 SQL 维度进行分析。

  * OceanBase 数据库内部的重试事件消耗了过多的 CPU 资源。

    排查思路：查看 ASH Report 中 retry 类的等待事件，关联 SQL 维度进行分析。

* 通过 ASH Report 下钻分析定位如下场景的根因：

  * ODP 路由出错，导致 SQL 流量集中在一个节点上。

    排查思路：查看 ASH Report 的前后台负载，发现前台负载集中在一个节点上或者后台负载有很多 `Action` 为 `OB_REMOTE_SYNC_EXECUTE `的事件开销。再根据 `GV$OB_SQL_AUDIT` 中的 `partition_hit` 相关列，查看 ODP 路由是否命中。

  * 表结构分布不均导致 SQL 压力不均。

    排查思路：查看前后台负载后定位热点节点、租户等思路，再查看 ASH Report 数据中的 tablet_id 访问情况，找出访问次数最高的 tablet_id 进行均衡。

  * 使用频繁账号导致用户 SQL 在某些分区比较热。

    排查思路：分析使用频繁账号对应的分区数据，合理规划数据分布。

## 流程介绍

### 步骤一：确认节点上 CPU 使用率高的进程为 observer 进程

在进行问题排查前，先确认指定节点上 CPU 使用率高的进程是否为 observer 进程，语句如下。

```shell
ps -eo pid,user,%cpu,cmd --sort=-%cpu
```

示例输出如下：

```shell
PID      USER     %CPU    CMD
124648   user_a   99.9    other_process
1332     user_b   50.5    observer
```

根据返回结果：

* 如果 CPU 占用高的进程是 observer，则需要再进一步排查 OceanBase 内部线程。

* 如果是其他进程（如 other_process），需联系相关用户进行调整。

### 步骤二：排查 OceanBase 内部线程

1. 排查 OBServer 中的可疑线程。

   如果 observer 进程占用 CPU 高，可通过以下命令查看其线程情况：

   ```shell
   top -p `pidof observer` -H
   ```

   该命令可显示 observer 进程中各线程的 CPU 使用情况，帮助用户判断是否是租户工作线程占用过高。

2. 根据 ASH Report，查看整体负载，定位热点租户。

   查看 ASH Report 中的 **Top Active Tenants** 部分，根据相应信息定位热点租户。

   判断同一个租户的平均活跃会话（`Average Active Sessions`）是否高于该租户的 `CPU 核数 * 4`（以 `租户分配的 CPU 核数 * 4` 进行预估）：

   1. 若 `Average Active Sessions` 较高，则说明当前系统负载处于高水位，当前租户为热点租户。

   2. 再判断当前租户的负载集中在前台还是后台。

      1. 若前台会话的 `Avg Active Sessions` 比较高，则说明当前租户的负载集中在前台会话。

      2. 若后台会话的 `Avg Active Sessions` 比较高，则说明当前租户的负载集中在后台会话。

3. 定位热点节点。

   查看 ASH Report 中的 **Top Node Load** 部分，通过判断同一个 IP 下，前后台会话对应的平均活跃会话数（Avg Active Sessions）的差值是否大于 20% 来判断当前节点是否为热点节点。

   * 如果是，则说明系统中存在节点级负载不均衡。

   * 如果不是，则不需要特别关注某一个节点的执行信息。

4. 分析数据库耗时。

   定位到热点租户或热点节点后，可以分析当前数据库耗时。

   * 若负载集中在前台会话，则需要进一步分析 **Top Foreground DB Time** 部分的内容。

     对于前台会话，有三类事件会消耗 CPU 资源，`Event Name` 值为 `ON CPU` 的事件以及少部分有 CPU 开销的等待事件。其中：

     * `ON CPU`：数据库认为当前会话正在消耗 CPU 资源处理任务。

     * 等待事件：

       * 以 `retry` 开头的等待事件：表示 OceanBase 数据库内部正在进行某种类型的重试，OceanBase 数据库内部的重试机制会消耗部分 CPU 资源。

       * `exec inner sql wait`：表示执行过程中发出的访问内部表的 SQL 结果返回，例如获取用户表位置、Schema 信息等，该过程也会消耗部分 CPU 资源。

   * 若负载集中在后台会话，则需要进一步分析 **Top Background DB Time** 部分的内容。

     对于后台会话，除了关注前台会话部分提到的三种事件外，还需关注后台任务的属性。`Program`、`Module`、`Action` 三个字段标注了后台任务的属性：

     * 若 `Action` 字段对应的值为 `OB_DAS_ASYNC_ACCESS`，说明后台任务为 SQL 远程 DAS 执行。

     * 若 `Program` 字段对应的值有类似 `xxx_PxPool`，说明后台任务为 PX 并行执行。

     * 若 `Program` 字段对应的值有类似 `xxx_DAG`，说明后台任务为转储合并任务。

     * 若 `Program` 字段对应的值有类似 `xxx_RPC_REQUEST`，说明后台任务为 OBServer 节点内部发送的 RPC 任务。

     <main id="notice" type='explain'>
     <h4>说明</h4>
     <p>以上是常见的后台任务类型，除此之外还有上百种其他的后台任务类型。</p>
     </main>

5. 经过上面的分析，已经可以明确 CPU 开销主要集中的节点、租户、以及具体的任务类型，基本确认了数据库系统的主要 CPU 开销在哪里。一般情况下，以上的排查步骤已经可以帮助我们定位问题的大方向以及可能出现的瓶颈点。但一些场景下，我们仍希望继续下钻分析获取更多信息。

   根据前面的分析，若后台任务开销主要在 PX 或 DAS 执行，则需要知道执行对应的 sql_id 是什么，可以构造如下 SQL 进行查询。

   <main id="notice" type='explain'>
   <h4>说明</h4>
   <p>请根据实际环境，修改查询中的时间范围（<code>sample_time</code>）、节点的 IP 地址（<code>svr_ip</code>）、租户 ID（<code>tenant_id</code>）等过滤条件。</p>
   </main>

   ```shell
   obclient(root@sys)[oceanbase]> SELECT ash.tenant_id as tenant_id,
        svr_ip, svr_port, sql_id,
        sql_plan_line_id, -- 算子ID
        program, module, action, time_model,
        name.name as event,
        count(*) as cnt,
        max(sample_time),
        min(sample_time)
        FROM oceanbase.CDB_WR_ACTIVE_SESSION_HISTORY ash
        LEFT JOIN oceanbase.V$EVENT_NAME name on ash.event_no = name.`event#`
        WHERE
        sample_time BETWEEN '2025-09-09 20:00:00' AND '2025-09-09 20:10:00'--对应时间段
        AND svr_ip = '192.168.1.1' --热点节点
        AND tenant_id = 1002 -- 热点租户
        AND program LIKE '%xxxx%' -- 匹配 Event Name 值为 ON CPU 的 Program
        GROUP BY tenant_id, svr_ip, svr_port, sql_id, sql_plan_line_id, program, module, action, time_model, event
        ORDER BY cnt desc
        LIMIT 200;
   ```

   下面列举几个示例进行说明。

   * 示例 1：`*_SQL_CMD`，表示当前数据库的用户 SQL 请求消耗了过多 CPU 资源，根因可能是数据分布不均衡、ODP 路由错误等。

     可以根据如下 SQL 来定位高消耗的 SQL。

     ```shell
     obclient(root@sys)[oceanbase]> SELECT ash.tenant_id as tenant_id,
        svr_ip, svr_port, sql_id,
        sql_plan_line_id, -- 算子ID
        program, module, action, time_model,
        name.name as event,
        count(*) as cnt,
        max(sample_time),
        min(sample_time)
        FROM oceanbase.CDB_WR_ACTIVE_SESSION_HISTORY ash
        LEFT JOIN oceanbase.V$EVENT_NAME name on ash.event_no = name.`event#`
        WHERE
        sample_time BETWEEN '2025-09-09 20:00:00' AND '2025-09-09 20:10:00'
        AND svr_ip = '192.168.1.1'
        AND tenant_id = 1002
        AND program LIKE '%_SQL_CMD%' -- 筛选用户 SQL 请求
        GROUP BY tenant_id, svr_ip, svr_port, sql_id, sql_plan_line_id, program, module, action, time_model, event
        ORDER BY cnt desc
        LIMIT 200;
     ```

   * 示例 2：`*_RPC_PROCESS*`，表示处理 RPC 请求消耗了过多的 CPU 资源，根因可能是以转储合并为代表的一系列后台任务消耗了过多的 CPU 资源；租户的 Leader 节点会接受更多的内部 rpc/inner sql 请求。

     可以根据如下 SQL 来定位高消耗的 SQL。

     ```shell
     obclient(root@sys)[oceanbase]> SELECT ash.tenant_id as tenant_id,
        svr_ip, svr_port, sql_id, program, module, action, time_model,
        name.name as event,
        count(*) as cnt,
        max(sample_time),
        min(sample_time)
        FROM oceanbase.CDB_WR_ACTIVE_SESSION_HISTORY ash
        LEFT JOIN oceanbase.V$EVENT_NAME name on ash.event_no = name.`event#`
        WHERE
        sample_time BETWEEN '2025-09-09 20:00:00' AND '2025-09-09 20:10:00'
        AND svr_ip = '192.168.1.100'
        AND tenant_id = 1
        AND (program LIKE '%_RPC_PROCESS%')
        GROUP BY tenant_id, svr_ip, svr_port, sql_id, program, module, action, time_model, event
        ORDER BY cnt desc
        LIMIT 200;
     ```

   * 示例 3：`*PX*` 或 `*_DAS_*`，表示远程执行消耗了过多的 CPU 资源，根因可能是 PX 并行执行并发度设置不合适。

     可以根据如下 SQL 来定位高消耗的 SQL。

     ```shell
     obclient(root@sys)[oceanbase]> SELECT ash.tenant_id as tenant_id,
        svr_ip, svr_port, sql_id, program, module, action, time_model,
        name.name as event,
        count(*) as cnt,
        max(sample_time),
        min(sample_time)
        FROM
        oceanbase.CDB_WR_ACTIVE_SESSION_HISTORY ash
        LEFT JOIN oceanbase.V$EVENT_NAME name on ash.event_no = name.`event#`
        WHERE
        sample_time BETWEEN '2025-09-09 20:00:00' AND '2025-09-09 20:10:00'
        AND svr_ip = '192.168.1.1'
        AND tenant_id = 1002
        AND (IN_PX_EXECUTION = 'Y' or IN_REMOTE_DAS_EXECUTION = 'Y')
        GROUP BY tenant_id, svr_ip, svr_port, sql_id, program, module, action, time_model, event
        ORDER BY cnt desc
        LIMIT 200;
     ```

6. 根据获取的信息，参考相关文档处理或联系技术支持协助处理。
