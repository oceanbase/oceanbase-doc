# 使用 ASH 排查问题的通用思路

ASH（Active Session History）是 OceanBase 数据库中用于记录活动会话历史信息的核心诊断工具，能够帮助 DBA 快速定位性能瓶颈和故障根因。

根据排查复杂度，ASH 可解决的问题分为以下两类：

* **第一类问题**：通过 ASH 中的特定指标信号即可明确排查方向。例如：CPU 资源异常占用、IO 资源异常占用、特定等待事件瓶颈、会话级资源消耗等。

* **第二类问题**：需要联合 ASH 多个维度信息，采用发散性方法论进行重构整合，该类问题对 ASH 使用者的要求较高。

基于上述问题分类，ASH 在以下场景中相比传统监控具有显著优势：

1. **实时动态问题诊断**：当 SQL 响应时间突然飙升或系统资源遇到瓶颈时，传统监控无法观察数据库的所有活跃会话，而 ASH 可以实时捕获细粒度信息。

2. **分布式系统跨节点问题**：OceanBase 数据库的 SQL 执行链路通常涉及多个 OBServer 节点，ASH 可通过 `trace_id`/`sql_id` 等信息关联多节点执行信息，实现全链路追踪。

3. **SQL 执行阶段级诊断**：ASH 能够观察 SQL 算子级执行情况，结合等待事件、执行阶段等信息，提供 plan_monitor 等手段无法提供的信息。

4. **资源争用与竞争分析**：当多个会话争夺同一资源（如锁、缓存）或某个会话占用过多 CPU 时，ASH 可通过实时活跃会话追踪和等待事件关联进行精准排查。

5. **会话级问题排查**：针对单一会话长时间异常、阻塞或长事务等场景，可直接筛选 session_id 分析其历史行为，比 processlist 提供更全面的诊断信息。

6. **后台任务开销分析**：在 ASH 模型中，后台任务被视为后台 Session，通过 `Program`、`Module`、`Action` 字段标记属性，并通过等待事件等维度细粒度分析后台任务执行开销。

7. **冷启动与初始化问题**：Session 频繁建立连接后又断开连接、SQL 解析和计划生成慢等场景，这些通常是传统监控的盲区。

## 通用排查思路

### 步骤一：确认性能问题的表现形式

可以通过以下方式进行确认：

* 观察系统 QPS 下降、RT 升高、CPU 负载异常或 IO 等待激增等现象。

* 通过 OCP 监控、Linux 系统工具（tsar/iostat）等外部手段交叉验证。

### 步骤二：获取 ASH 报告

可以根据对当前场景的初步分析获取对应的 ASH 报告。

首次获取 ASH 报告时，建议不限制任何参数，仅输入时间范围，生成全集群报告以便了解整体状况。再根据初步分析结果，针对特定租户、节点、SQL_ID 等生成更细化的报告。HTML 报告提供了更强的可读性和交互能力，建议优先使用。

* 生成基础报告（全集群）。

  至少需要输入报告开始时间和报告结束时间等两个参数。

  例如，`sys` 租户下，执行以下命令获取整个集群的 ASH 报告。

  ```shell
  obclient(root@sys)[oceanbase]> CALL DBMS_WORKLOAD_REPOSITORY.ASH_REPORT('2025-09-23 17:14:00', '2025-09-30 18:14:00',report_type=>'html') \G
  ```

* 仅获取特定 SQL_ID 相关执行记录的 ASH 报告。

  假设特定 SQL_ID 为 `1CA21C86CCF10D8635BF62C17BEA7128`，在 `sys` 租户下，执行以下命令，获取 ASH 报告。

  ```shell
  obclient(root@sys)[oceanbase]> CALL DBMS_WORKLOAD_REPOSITORY.ASH_REPORT('2025-09-23 17:14:00', '2025-09-30 18:14:00',
                                          sql_id=>'1CA21C86CCF10D8635BF62C17BEA7128',report_type=>'html') \G
  ```

* 获取某特定 OBServer 节点的 ASH 报告。

  假设某个 OBServer 节点的 IP 为 `192.168.0.1`，在 `sys` 租户下，执行以下命令，获取 ASH 报告。

  ```shell
  obclient(root@sys)[oceanbase]> CALL DBMS_WORKLOAD_REPOSITORY.ASH_REPORT('2025-09-23 17:14:00', '2025-09-30 18:14:00',
                                          svr_ip=>'192.168.0.1', svr_port=>'2828',report_type=>'html') \G
  ```

### 步骤三：解读报告，问题定位

1. 初步定位。

   所有资源消耗（CPU、IO、锁等）最终都会体现为等待事件，ASH 通过采样机制记录这些事件。重点关注以下报告模块：

   * **Top Foreground DB Time**：定位前台会话的主要耗时事件。

   * **Top Blocking Sessions**：快速识别阻塞源。

   * **Top IO Events**：区分 IO 来源（日志写入、用户 SQL、后台任务）。

   典型场景识别：

   * 行锁阻塞：`row lock wait` 事件占比突出。

   * CPU 瓶颈：需结合后台任务、并行执行、重试事件等综合判断。

   * IO 瓶颈：出现 `palf write`、DAG 相关等待事件或 SQL 关联的磁盘读。

2. 根据初步定位场景，进行详细定位。

   * **阻塞源定位**。适用于锁等待场景。

     当前 ASH 中等待事件 `row lock wait` 占比突出时，按照如下方式进行进一步问题定位。

     1. 获取 Top 阻塞会话。

        示例如下：

        ```shell
        obclient(root@sys)[oceanbase]> SELECT blocking_session_id, count(1) AS cnt FROM oceanbase.GV$OB_ACTIVE_SESSION_HISTORY
            WHERE sample_time BETWEEN '2025-09-23 17:14:00' AND '2025-09-30 18:14:00'
            AND event = 'row lock wait'
            GROUP BY blocking_session_id
            ORDER BY cnt desc;
        ```

        根据查询结果：

        * 若某个 `blocking_session_id` 占比绝对多数，说明存在长事务或慢查询持有锁未释放。

        * 若多个 `blocking_session_id` 占比相近，表明存在并发热点，可能是单行记录高频更新、热点分区集中访问或大小账号数据分布不均等问题。

     2. 获取持有锁的事务 ID。

        根据上一步中获取的阻塞会话 ID（`blocking_session_id`），进一步获取持有锁的事务 ID，示例如下：

        ```shell
        obclient(root@sys)[oceanbase]> SELECT tx_id, count(1) as cnt FROM oceanbase.GV$OB_ACTIVE_SESSION_HISTORY
            WHERE sample_time BETWEEN '2025-09-23 17:14:00' AND '2025-09-30 18:14:00'
            AND blocking_session_id = xxxx
            GROUP BY tx_id
            ORDER BY cnt desc;
        ```

     3. 获取持有锁的 SQL_ID。

        根据上一步中获取的事务 ID（`tx_id`），进一步获取持有锁的 SQL_ID，示例如下：

        ```shell
        obclient(root@sys)[oceanbase]> SELECT * FROM oceanbase.GV$OB_SQL_AUDIT
            WHERE tx_id = xxx
            ORDER BY request_time desc\G
        ```

        通过上述递进式查询，可精确到具体的阻塞会话、事务和 SQL 语句。

   * **资源热点定位**。适用于 CPU/IO 不均场景。

     当数据库 CPU 问题和 IO 问题比较明显时，可以按照下列思路进行排查。

      * 路由正确性：检查视图 `GV$OB_SQL_AUDIT` 中的 `partition_hit` 列，确认 ODP 路由是否均衡。

      * 数据分布：分析 ASH 中的 `tablet_id` 访问频次，识别热点分区。

      * Leader 分布：租户的 Leader 节点会承担更多内部 RPC/Inner SQL，需查看 ASH 后台负载。

      * 并行执行：ASH 报告中出现大量 PX 任务时，需关联 SQL 维度调整并行度。

      * 后台任务：`Program` 为 DAG 相关的等待事件通常代表转储合并带来的 IO 或 CPU 消耗。

      详细排查操作，参见 [CPU 使用不均问题排查](200.cpu-usage-imbalance-troubleshooting.md) 和 [IO 瓶颈问题排查](300.io-bottleneck-troubleshooting.md)。

## 解决方案

* 针对行锁阻塞，可以尝试采用如下方法处理：

  * 优化持有锁的业务逻辑，缩短事务持续时间。

  * 热点行拆分或应用层限流。

  * 通过 ASH Report 的 **Top Blocking Sessions** 持续监控等。

* 针对 CPU 使用不均，可以尝试采用如下方法处理：

  * 修正 ODP 路由规则，确保流量均衡。

  * 调整分区策略，打散热点 Tablet。

  * 优化 PX 并行度参数。

  * 将重试事件高的 SQL 进行业务改造等。

* 针对 IO 瓶颈，可以尝试采用如下方法处理：

  * 优化高磁盘读的 SQL 执行计划。

  * 调整转储合并触发时机。

  * 扩容 IO 资源或采用更高性能的存储介质。
