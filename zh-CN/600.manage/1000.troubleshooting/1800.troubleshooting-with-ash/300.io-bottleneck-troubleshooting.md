# IO 瓶颈问题排查

在数据库运行过程中，IO 问题是较常见的一种问题，它主要分为以下两种场景：

* 一是某类 SQL 在执行过程中主要开销都在读磁盘，希望排查读取的磁盘和什么数据库对象、或 SQL 算子相关联。

* 二是从 OCP 监控中看到数据库读写磁盘压力很大，希望知道磁盘压力的来源。

为了帮助大家快速定位问题根源并高效解决，这里总结了一套清晰、实用的 IO 问题排查流程。这套流程提供了明确的操作步骤，旨在提升问题处理效率，尽可能降低对业务的影响，为日常运维工作提供有力的支持。

IO 问题主要分为两类场景：

* **SQL 级别问题**：某些 SQL 执行过程中磁盘读取开销较大，需关联数据库对象或算子分析。

* **集群级别问题**：OCP 监控中显示磁盘读写压力大，需定位压力来源。

IO 瓶颈问题排查流程如下。

## 流程介绍

1. 确认是否有 IO 相关问题。

   可以通过以下方法进行确认：

   * 登录 OCP，从 **物理 IO 次数** 和 **物理 IO 吞吐量** 性能监控中，查看节点级（OBServer 维度）和租户级（租户维度）的 IO 带宽，当某节点或某租户的 IO 带宽较大，说明可能有 IO 相关的问题。

   * 查看 ASH Report 中的 **Top Foreground DB Time** 和 **Top Background DB Time**，若发现有 IO 相关的等待事件，例如 `db file data read`、`db file compact read`、`db file compact write`、`row store disk write` 等与 File/Disk、Read/Write 相关的等待事件（对应 `Wait Class` 的值为 `USER_IO` 和 `SYSTEM_IO`）占比比较高，则说明可能有 IO 相关问题。

2. 进行集群级别问题排查。

   1. 获取问题时段对应节点对应租户的 ASH Report。

   2. 观察 **Top Foreground DB Time** 和 **Top Background DB Time** 部分内容，查看 IO 来源。

      若前台 IO 相关等待事件占比较高，说明当前 IO 负载主要集中在前台会话，需要跳转到步骤 3，进行 SQL 级别问题排查。

      否则，继续进一步排查 IO 的来源。

   3. 进一步排查 IO 的来源。

      1. 观察 **Top IO Bandwidth** 部分的内容，`IO Size(MB)` 数值越大，说明在问题时段里，对应的模块下发 IO 的总大小越大。

      2. 选择 `IO Size(MB)` 较大的 `Program Module Action/SQL ID` 字段，获取对应的信息。如果是 PX/DAS 执行相关信息，则执行下一步，进行 SQL 级别问题排查。否则，参考相关文档处理或联系技术支持协助分析处理。

3. 进行 SQL 级别问题排查。

   根据前面获取的问题时段对应节点对应租户的 ASH Report，前台 IO 相关等待事件占比较高时，可以进一步进行排查：

   1. 观察 **Top SQL with Top Event** 和 **Top SQL with Top Opreator** 部分内容。

      * **Top SQL with Top Event**：展示获取的 ASH Report 中执行开销最大的 SQL，并且在 `Top Event` 列展示对应 SQL 占比最高的等待事件。

      * **Top SQL with Top Opreator**：展示获取的 ASH Report 中执行开销最大的 SQL，并且在 `Top Operator` 和 `Top Event` 列展示该 SQL 对应的开销最大的算子 ID 和 event_id。

        通过观察这两个表格，可以获取 IO 相关等待事件对应的 SQL，以及对应的算子 ID。

   2. 如果还希望知道 IO 是由于访问哪个数据库的表分区导致的，可以继续观察 **Top DB Object** 部分，它列举了用户 SQL 访问最频繁的 tablet_id。

   3. 根据获取的信息，参考相关文档处理或联系技术支持协助分析处理。
