# 创建宏块级冷热策略

本文将向您介绍如何使用 SQL 语句在不是分区表的情况下，手动指定一段时间内数据为热点数据，即创建宏块级冷热策略。

## 使用方法

创建宏块级冷热策略需要在 `STORAGE_CACHE_POLICY` 语法中指定 `GRANULARITY = "block"`。详细语法信息，参见 [创建表级热点缓存策略](200.create-table-level-storage-cache-policy-of-mysql-mode.md)。

当前创建宏块级冷热策略可以使用 **内部 trans_version 方案** 和 **自定义时间列方案**。

### 内部 trans_version 方案

* 功能点：

  使用系统内部时间列判断热点有效期，根据数据真正写入时间做判断。用户无需感知内部实现。

* 使用建议：

  适合无法提供业务时间列、或需要 “开箱即用” 的场景。

* 注意事项：

  在进行大规模结构性变更后（如 DDL/旁路导入/建索引等场景），可能出现短期内热点判定过多导致真正的热点被挤占情况。

**示例如下：**

创建表 `tbl1`，使用内部 `trans_version` 创建宏块级冷热策略，即 `STORAGE_CACHE_POLICY` 中无需指定 `BOUNDARY_COLUMN`。

```shell
obclient> CREATE TABLE tbl1 (
    col1 INT,
    col2 DATE NOT NULL,
    col3 VARCHAR(100))
    STORAGE_CACHE_POLICY (
        HOT_RETENTION = 6 DAY,
        GRANULARITY = 'block');
```

### 自定义时间列方案

* 功能点：

  使用用户指定的业务时间列判断热点有效期。

* 使用建议：

  适合对热点范围控制更精细、且业务时间列稳定可靠的场景。

* 注意事项：

  若自定义时间列无法用于有效过滤，系统会无法进行预热，热点判定精度下降。

**示例如下：**

创建表 `tbl2`，使用自定义时间列 `col2` 创建宏块级冷热策略。

```shell
obclient> CREATE TABLE tbl2 (
    col1 INT,
    col2 DATE NOT NULL,
    col3 VARCHAR(100))
    STORAGE_CACHE_POLICY (
        BOUNDARY_COLUMN = 'col2',
        HOT_RETENTION = 6 DAY,
        GRANULARITY = 'block');
```

## 其它正交场景注意事项

### DDL/旁路导入/建索引

* 使用系统内部时间列时（`rans_version` 过滤）：DDL 会重新生成数据，执行后可能导致短期内预热更多宏块。
* 使用自定义时间列时：若 DDL 影响到时间列的过滤能力，需确保策略仍可正常生效，否则不做预热。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>DDL 操作时，主表上索引的内部时间列会一起改变。</p>
</main>

### 备份恢复

热点缓存数据不包含在备份/恢复流程中，恢复后热点会按当前策略重新建立。

如不希望恢复期间受到策略影响，可通过租户配置项 `enable_manual_storage_cache_policy` 关闭人工策略。

### 辅助索引

* 使用系统内部时间列时：辅助索引表均可按内部时间列进行过滤。
* 使用自定义时间列时：若辅助索引表不包含自定义列，将不进行预热。
* `LOCAL INDEX`/`UNIQUE KEY`：默认按 `hot` 预热。
* `GLOBAL INDEX`：可单独设置策略。
* `LOB` 列：默认为 `auto`（避免挤占过多本地空间）。

<main id="notice" type='notice'>
  <h4>注意</h4>
  <p>更新主表数据时，索引的内部时间列不会同步变化；如需精确控制索引冷热，建议手动为索引单独设置策略。</p>
</main>
